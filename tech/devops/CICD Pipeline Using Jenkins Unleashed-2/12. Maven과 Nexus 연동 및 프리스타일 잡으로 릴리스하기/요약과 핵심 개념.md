# 요약과 핵심 개념

이 장은 Git으로 소스를 관리하고, Nexus에 아티팩트를 올리고, 젠킨스 프리스타일 잡이 둘을 이어 주는 흐름을 한 번에 다뤘다. 이 문서는 장 끝의 Summary를 바탕으로 핵심 개념과 명령, 다음 장 안내를 정리한다.

---

## 1. 장 요약

원서의 Summary가 짚은 내용은 다음과 같다.

- 분산 버전 관리 시스템인 Git을 설명했다. `git init`, `git add`, `git commit`, `git push` 같은 명령을 살폈다.
- GitLab에 중앙 저장소를 만들고 Java API 소스 코드를 푸시했다.
- 브랜치 개념을 익히고, 기능 개발과 단위 테스트가 끝난 뒤 두 브랜치를 병합하는 방법을 봤다.
- 널리 쓰는 아티팩트 저장소인 Nexus를 알아봤다.
- 장 끝에서 Maven과 Nexus를 연동하고, 젠킨스 잡을 실행해 Calculator API의 새 버전을 Nexus에 릴리스했다.
- 다음 장은 자동으로 트리거되는 젠킨스 잡 만들기를 다룬다.

---

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
| --- | --- |
| 분산 버전 관리 | 로컬 저장소와 중앙 저장소를 함께 쓰는 방식. 네트워크 없이도 이력 관리가 된다 |
| Git / GitLab | Git은 버전 관리 도구, GitLab은 웹의 중앙 저장소 서비스 |
| 브랜치 | 원본에 영향을 주지 않고 작업하는 코드 갈래 |
| .gitignore | 추적하지 않을 파일과 디렉터리 목록 |
| 아티팩트 | 빌드가 만든 결과물(JAR, WAR 등) |
| Nexus | 조직 내부용 아티팩트 저장소 |
| 호스티드 저장소 | Nexus가 직접 아티팩트를 보관하는 저장소. 이 장은 Maven2 (hosted)를 썼다 |
| distributionManagement | pom.xml에서 배포할 저장소를 적는 태그 |
| settings.xml | Nexus 로그인 정보를 두는 파일. `<id>`가 pom.xml과 같아야 한다 |
| Merge Request | 브랜치를 Master에 합쳐 달라는 GitLab의 요청 |

---

## 3. 명령어 한눈에 보기

| 명령 | 역할 |
| --- | --- |
| `git init` | 빈 로컬 저장소 생성 |
| `git checkout -b <브랜치>` | 새 브랜치를 만들고 이동 |
| `git add` | 변경을 스테이징 영역에 추가 |
| `git commit -m "<메시지>"` | 스테이징한 변경을 브랜치에 커밋 |
| `git push -u <URL> <브랜치>` | 브랜치를 중앙 저장소로 푸시 |
| `Nexus.exe /run` | Nexus 서버 실행 |
| `Nexus.exe /install <이름>` | Nexus를 Windows 서비스로 설치 |
| `mvn deploy` | 빌드 전 단계를 거쳐 아티팩트를 저장소에 배포 |

---

## 4. 이 장의 흐름 다시 보기

1. 코드를 로컬 저장소에서 브랜치로 커밋한다.
2. GitLab 중앙 저장소로 푸시하고 Merge Request로 Master에 병합한다.
3. 젠킨스 잡이 Master 브랜치를 가져온다.
4. 잡이 Maven `deploy` 목표를 실행해 컴파일, 테스트, 패키징을 거친다.
5. 완성된 JAR가 Nexus의 호스티드 저장소에 올라간다.

잡이 아직은 사람이 직접 실행 버튼을 눌러야 시작된다. 다음 장에서 이 부분을 자동으로 바꾼다.
