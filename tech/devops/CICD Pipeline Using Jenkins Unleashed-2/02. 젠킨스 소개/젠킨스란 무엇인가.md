# 젠킨스란 무엇인가

이 문서는 Jenkins가 어떤 도구이고 왜 CI/CD에 필요한지, 그리고 어떤 사연으로 태어났는지를 정리한다. 먼저 수작업으로 CI/CD를 돌릴 때 생기는 문제를 보고, 그다음 Jenkins의 정의와 역사를 차례로 살핀다.

Jenkins를 한 줄로 말하면 "소프트웨어를 만드는 반복 작업을 대신 돌려 주는 자동화 서버"다. 식당 주방의 자동 조리 라인을 떠올리면 쉽다. 재료 손질, 굽기, 담기를 사람이 매번 순서대로 하면 실수가 나지만, 라인을 한 번 짜 두면 주문이 들어올 때마다 같은 순서로 같은 맛이 나온다.

---

## 1. 왜 자동화 서버가 필요한가

CI/CD(지속적 통합과 지속적 배포)는 작은 변경을 자주 합치고, 그때마다 테스트하고, 결과를 바로 피드백으로 받는 습관이다. 변경이 작으면 문제가 생겨도 원인을 찾기 쉽다. 하지만 이 과정을 사람이 손으로 하면 품이 많이 들고, 지루하고, 번거롭고, 실수하기 쉽다.

애자일(Agile) 개발 방식도 같은 방향을 본다. 애자일은 변경을 조금씩 쌓아 가며 매번 동작하는 제품을 내놓는 방식이다. 팀은 새 기능이 동작하는 모습만이 아니라, 그 기능 덕에 소프트웨어에 가치가 얼마나 더해졌는지도 볼 수 있어야 한다. 작게 자주 낸다는 철학이 CI/CD와 닮았기 때문에 둘은 잘 어울린다.

### 한 번의 흐름에 걸리는 도구들

애플리케이션 하나를 처리하는 작업 흐름(워크플로)은 대개 이렇게 흘러간다.

1. Git이나 SVN 같은 소스 코드 관리 시스템에서 최신 코드를 받아 온다.
2. 컴파일러를 실행해 코드를 컴파일한다.
3. 단위 테스트를 실행한다. 이때는 또 다른 도구와 맞물려 돌아간다.

여러 도구와 기술에 걸친 이 흐름을 하루에 몇 번씩 사람이 직접 돌리면 개발자, QA, 지원 엔지니어 모두 부담을 느낀다. Jenkins는 이 부담을 덜어 준다.

### Jenkins가 해 주는 일

| 할 수 있는 일 | 설명 |
| --- | --- |
| 여러 플랫폼에서 빌드 | 애플리케이션을 서로 다른 플랫폼에서 빌드할 수 있다 |
| 풀 리퀘스트 통합 자동화 | 풀 리퀘스트(변경을 합쳐 달라는 요청)를 받아 합치는 과정을 자동으로 처리한다 |
| 아티팩트 게시 | 아티팩트(빌드 결과물)를 Nexus 같은 아티팩트 저장소에 올린다 |
| 도구 조율 | 서로 다른 테스트 프레임워크와 테스트 컨테이너를 순서에 맞게 엮는다 |

표를 읽는 법은 간단하다. 단위 테스트 도구나 통합 테스트 도구는 각자 잘하는 일이 있지만, 그것만으로는 품질 좋은 빌드가 나오지 않는다. 이 도구들을 하나의 흐름으로 묶어 지휘하는 역할이 Jenkins의 몫이라는 것이 저자의 설명이다.

Jenkins는 정해 둔 주기에 따라 여러 도구와 맞물려 처음부터 끝까지 이어지는 작업 흐름을 실행한다. 이 일을 팀원에게 불필요한 압박을 주지 않으면서 해낸다는 점이 핵심이다.

## 2. Jenkins의 정의

Jenkins는 소프트웨어 개발 과정의 여러 단계를 자동화한다. 구체적으로는 다음 일을 맡는다.

- 중앙 소스 코드 저장소(리포지터리)에서 최신 코드를 가져온다.
- 소스 코드를 컴파일한다.
- 단위 테스트를 실행한다.
- 구현 결과를 여러 종류의 아티팩트로 패키징한다.
- 이 아티팩트를 여러 환경에 배포한다.

Jenkins는 무료이며 오픈 소스인 서버다. Java로 만들었고, 개발에 참여하는 다양한 도구 계열을 지원한다. 실행 방식은 Apache Tomcat 같은 서블릿 컨테이너(Java 웹 애플리케이션을 올려 돌리는 실행 환경) 안에서 도는 서버 시스템이다.

| 항목 | 내용 |
| --- | --- |
| 성격 | 자동화 서버 |
| 비용·라이선스 | 무료, 오픈 소스 |
| 구현 언어 | Java |
| 실행 환경 | Apache Tomcat 같은 서블릿 컨테이너 안에서 동작 |
| 지원 범위 | 소프트웨어 개발에 쓰이는 여러 계열의 도구 |

이 표에서 눈여겨볼 점은 Jenkins 자체가 Java 웹 애플리케이션이라는 것이다. 그래서 뒤 장에서 설치할 때 Java 버전이 중요해진다.

## 3. Jenkins의 역사

Jenkins의 이야기는 2004년에 시작한다. 개발자 Kohsuke Kawaguchi는 당시 Sun Microsystems에서 Java 개발자로 일하며 여러 프로젝트에 참여하고 있었다. 그는 자기 코드 때문에 빌드가 깨지는 상황을 싫어했다. 그래서 코드를 저장소에 커밋(올리기)하기 전에, 그 코드가 제대로 동작할지 미리 알 방법을 찾게 됐다.

이 호기심이 Hudson이라는 자동화 서버로 이어졌다. 이후 흐름은 아래와 같다.

| 시기 | 사건 |
| --- | --- |
| 2004년 | Kawaguchi가 Sun Microsystems에서 빌드 실패를 미리 막을 방법을 찾기 시작함 |
| 그 결과 | 자동화 서버 Hudson이 만들어짐 |
| 2011년 | 독립적인 Hudson 오픈 소스 커뮤니티와 Oracle(이때는 Sun Microsystems를 품고 있었다) 사이에 분쟁이 벌어짐 |
| 분쟁 이후 | 프로젝트가 갈라져 나와(포크, fork) Jenkins라는 이름이 붙음 |
| 이후 한동안 | Jenkins와 Hudson이 함께 존재했으나 사람들은 Jenkins를 더 선호함 |
| 2020년 1월 | Hudson 프로젝트가 종료됨. Jenkins는 지금도 활발함 |

포크는 한 프로젝트의 소스를 복사해 별도 프로젝트로 독립시키는 일이다. 갈림길에서 개발자 커뮤니티가 선택한 쪽이 Jenkins였고, 그 결과 Hudson은 문을 닫았다.
