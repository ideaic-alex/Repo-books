# CI-CD 이해하기

이 장은 Jenkins를 배우기 전에 CI/CD(지속적 통합과 지속적 배포)가 무엇이고 왜 필요한지를 다진다. 애자일 개발에서 코드 변경이 잦아지면 어떤 문제가 생기는지, 지속적 통합(CI)이 그것을 어떻게 줄이는지, 변경이 로컬 개발에서 배포까지 어떤 순서로 흐르는지를 차례로 정리한다. 마지막에는 계산기 웹 애플리케이션 사례로 흐름을 따라간다.

이 장은 특정 언어나 도구를 가정하지 않는다. Jenkins 자체는 다음 장에서 소개하므로, 여기서는 개념과 작업 흐름을 이해하는 데 집중한다.

---

## 1. 핵심 요점

- 애자일은 요구사항을 묶음으로 나눠 1~3주짜리 스프린트마다 구현하므로 코드 변경이 자주 생긴다.
- 변경을 한꺼번에 합치면 회귀 결함, 통합 결함, 병합 충돌이 생기고 해결에 몇 시간이 걸린다.
- CI는 개발자의 작업을 메인 브랜치에 자주 합쳐서 충돌과 결함을 일찍, 빠르게 해결하는 방식이다.
- 개발 흐름은 로컬 단위 테스트, 푸시와 병합, 컴파일, 테스트, 아티팩트 배포 순서로 이어진다.
- TDD는 테스트를 먼저 쓰고 실패를 확인한 뒤 코드를 만들어 통과시키는 방법이다.
- 개발 환경에서 되던 것이 운영 환경에서 안 될 수 있으므로 CD로 자주 배포해 문제를 일찍 드러낸다.
- 계산기 사례는 덧셈 기능 추가부터 Selenium 같은 도구의 E2E 테스트까지를 한 번에 보여 준다.
- 이 과정을 손으로 반복하면 힘들기 때문에 다음 장에서 자동화 서버 Jenkins를 소개한다.
