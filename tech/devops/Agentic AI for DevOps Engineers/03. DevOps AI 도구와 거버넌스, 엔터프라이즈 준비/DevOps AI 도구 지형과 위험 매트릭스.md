# DevOps AI 도구 지형과 위험 매트릭스

앞 장에서는 Azure OpenAI를 GitHub Actions에 붙여 인프라의 일부처럼 다뤘다. 그러나 DevOps에서 AI는 한 곳에만 있지 않다. IDE, 개발자 PC, GitHub 풀 리퀘스트(PR), 파이프라인, 채팅 도구, 보안 플랫폼, 클라우드 포털 어디에나 나타날 수 있다.

설계 없이 도구부터 고르면 그림자 AI(shadow AI, 조직이 모르는 사이 퍼진 비공식 AI 사용), 비용 난립, 정책 공백, 보안 위험이 생긴다. AI가 한번 들어오면 일을 만들고, 검토하고, 자동화하고, 배포하는 방식 자체의 일부가 되기 때문이다. 그래서 먼저 생태계를 다섯 계층으로 나누어 계층마다 목적과 위험 수준을 따져 본다.

---

## 1. 다섯 계층으로 보는 도구 지형

### 1-1. IDE 기반 AI

대부분의 조직이 가장 먼저 시작하는 계층이다. 예로 GitHub Copilot, Claude Code, JetBrains AI Assistant가 있다. 코드 생성, 리팩터링, 테스트 생성, 문서화를 돕는 것이 목적이다. 원서는 위험 수준을 중간으로 본다. 코드 품질이 떨어지거나, 지식재산이 새거나, 팀 전체의 프롬프트(AI에게 주는 지시문) 작성 규율이 약해질 수 있기 때문이다.

### 1-2. 풀 리퀘스트 AI

협업 계층에서 동작한다. 예로 GitHub Copilot의 PR 요약, AI 코드 리뷰 도구, 링크 제안 봇이 있다. 요약, 코드 품질 강조, 위험 표시가 목적이며 팀 협업을 보강하는 자리다. 원서는 2장에서 이 계층을 꽤 길게 구현했다고 상기시킨다. AI 응답이 사람이 만든 검토 흐름 안으로 들어올 때 가드레일(AI가 범위를 벗어나지 못하게 하는 안전장치)이 왜 필요한지도 봤다. 결정적 출력, 즉 자동화가 받아들이기 전에 AI 응답이 예측 가능한 구조를 지키게 하면 팀이 더 많은 통제권을 갖는다.

### 1-3. 파이프라인 수준 AI

더 강력하지만 잘못 구현하면 더 위험하다. 예로 GitHub Actions 안의 Azure OpenAI, 직접 만든 AI 검증 단계, AI가 만든 아티팩트(산출물), 테스트 생성이 있다. 목적은 자동 분석, 구조화된 출력, 릴리스 커뮤니케이션이다. 이 계층은 릴리스 산출물, 공지, 의사결정 지원에 영향을 줄 수 있어서 AI를 넣기에 가장 민감한 곳 가운데 하나다.

### 1-4. 클라우드 네이티브 AI

엔터프라이즈 정렬이 이뤄지는 계층이다. 예로 Azure OpenAI와 Azure AI Studio, AWS Bedrock, Google Vertex AI가 있다. 목적은 기업용 LLM 호스팅, 모델 거버넌스(조직 차원의 통제 체계), 데이터 거주지(data residency, 데이터가 놓이는 지역) 통제다. 앞선 실습에서 공개 OpenAI API 대신 Azure OpenAI를 쓴 이유가 이것이다. Azure 안에서는 조직 수준의 통제가 훨씬 많고, AWS 중심 조직이라면 Bedrock이 비슷한 통제를 줄 수 있다. 이런 요소는 거버넌스 관점에서 반드시 따져야 한다.

### 1-5. 보안과 컴플라이언스 속 AI

보안과 규정 준수 영역에서도 AI 사용이 늘고 있다. 예로 AI 보안 스캔 도구, 코드 취약점 설명, 컴플라이언스 요약이 있다. 취약점을 설명하고, 경보를 분류하고, 위험 검토를 돕는 것이 목적이다. 모범 사례를 아는 사람도 안전하지 않은 코드를 한 조각쯤 쓰게 마련인데, AI가 그 코드의 잠재적 영향을 풀어 주면 도움이 된다. 다만 AI는 보안 통제를 대신하지 않고 돕기만 한다.

## 2. 위험 매트릭스

원서의 표 3.1을 옮긴 것이다. 위험 평가는 저자 본인의 분석이며 업계에서도 대체로 공감될 것이라고 밝힌다.

| 계층 | 예시 | 위험 수준 | 엔터프라이즈 적합 |
|---|---|---|---|
| IDE AI | Copilot | 중간 | 정책에 따라 다름 |
| PR AI | 내장 요약 | 중간 | 예 |
| 파이프라인 AI | Azure OpenAI | 높음 | 예 |
| 클라우드 AI | Azure OpenAI | 매우 높음 | 예 |
| 외부 LLM API | 공개 OpenAI | 변동 | 더 위험 |

AI를 쓰기 시작하면 오류 가능성이 생기므로 최소 중간 위험으로 본다는 것이 저자의 전제다. AI가 워크플로에 들어온 순간 진짜로 낮은 위험은 없다. 얼마나 깊이 통합되고 무엇에 영향을 주도록 허락되느냐에 따라 높음, 매우 높음, 변동이 된다.

참고(노트 작성자): 표의 값은 원문 그대로 옮겼다. 추출본에서 'Depends on thepolicy'처럼 띄어쓰기가 깨진 곳은 '정책에 따라 다름'으로 복원했다.

이 매트릭스는 조직 어디에서 AI 통합이 위험해질 수 있는지 찾는 길잡이다. 그래도 AI는 도구일 뿐이다. 도구를 쓰는 사람이 올바르게 쓰도록 교육받아야 한다.

## 3. 핵심 정리

- 도구 지형은 IDE, PR, 파이프라인, 클라우드, 보안과 컴플라이언스의 다섯 계층이다.
- 계층마다 목적과 위험이 다르며, 파이프라인과 클라우드 계층이 가장 민감하다.
- 설계 없이 도구를 고르면 그림자 AI, 비용 난립, 정책 공백, 보안 위험이 생긴다.
- 위험은 쓰기 시작한 순간 최소 중간이며, 통합 깊이와 영향 범위에 따라 올라간다.
