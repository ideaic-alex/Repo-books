# 머리말과 이 책에 대하여

이 문서는 Trevoir Williams가 쓴 'Agentic AI for DevOps Engineers: Building autonomous CI/CD, infrastructure, and operations workflows'(Packt)의 머리말(Preface)과 책 소개를 정리한 것이다. 책이 누구를 위해 쓰였는지, 8개 장이 어떤 순서로 이어지는지, 따라 하려면 무엇을 준비해야 하는지를 먼저 훑어 둔다. 본격적인 내용으로 들어가기 전에 전체 지도를 손에 쥐는 용도다.

이 책은 생성형 AI(문장이나 코드를 새로 만들어 내는 AI)를 DevOps 업무에 넣는 방법을 다룬다. 처음에는 AI를 보조 도구로 쓰다가, 점차 범위를 좁힌 에이전트(스스로 판단하고 도구를 호출해 일을 처리하는 AI 프로그램)를 파이프라인에 넣고, 마지막에는 여러 에이전트와 관측성까지 이어 가는 구성이다. 이 노트는 장별로 같은 형식으로 정리하며, 이 문서는 그 첫머리에 해당한다.

---

## 1. 책의 목적과 대상 독자

머리말은 문제의식에서 출발한다. 생성형 AI는 개발자가 실험 삼아 쓰는 단계를 넘어, 소프트웨어를 계획하고 만들고 테스트하고 배포하고 운영하고 감시하는 시스템 안으로 들어오고 있다. 반복 작업을 줄이고, 복잡한 데이터를 이해하도록 돕고, 전문 지식에 접근할 문을 넓혀 준다는 장점이 있다. 반면 새로운 운영 위험도 생긴다. 채팅창에서 나온 그럴듯하지만 틀린 제안은 불편한 정도로 끝나지만, 같은 제안이 CI/CD(코드 변경을 자동으로 빌드·테스트·배포하는 흐름) 워크플로 안에 들어가면 인프라, 보안, 실제 운영 환경에 영향을 줄 수 있다.

저자는 필요한 것이 과장된 선전이나 따로 노는 시연이 아니라 실험에서 통제된 구현으로 가는 현실적인 길이라고 본다. 이 책은 그 길을 제시하고, 생성형 AI 기능을 운영 시스템을 믿을 만하게 만드는 엔지니어링 규율과 연결하려고 쓰였다. 책 전체를 관통하는 운영 원칙은 한 문장이다. AI는 돕거나 제안하고, 결정론적 자동화(같은 입력에 항상 같은 결과를 내는 검증과 실행)가 검증하고 실행하며, 책임질 엔지니어가 중대한 결정을 쥔다. 엔지니어의 판단을 자동화로 없애는 것이 아니라 반복 노동을 줄이고 가시성을 높여 더 자신 있게 소프트웨어를 내놓게 하는 것이 목표다.

머리말이 밝힌 대상 독자와 전제는 다음과 같다.

| 구분 | 내용 |
|---|---|
| 주 독자 | 전달과 운영 과정에 생성형 AI를 넣되 신뢰성과 통제를 유지하려는 DevOps 엔지니어 |
| 함께 도움이 되는 독자 | CI/CD를 다루는 개발자, 플랫폼·클라우드 엔지니어, SRE(사이트 신뢰성 엔지니어), 인시던트(서비스 장애나 사고) 대응자, 보안 엔지니어, 솔루션·클라우드 아키텍트, 기술 리드와 엔지니어링 관리자 |
| 전제 지식 | 소스 관리, 풀 리퀘스트(PR), CI/CD, 클라우드 인프라, 자동화된 전달의 목적을 이해하고 있음. 브랜치, 커밋, 개발과 운영 환경의 차이, 신원과 비밀 값 관리도 알고 있어야 함 |
| 필요 없는 것 | 대규모 언어 모델(LLM) 애플리케이션이나 AI 에이전트 제작 경험 |
| 이 책이 아닌 것 | 프로그래밍, Git, DevOps 기초 입문서가 아니라 실무자 대상 책 |

머리말이 정리한 오래 가는 관심사는 일곱 가지다. 통제된 컨텍스트, 최소 권한 접근, 구조화된 출력, 결정론적 검증, 안전한 도구 사용, 추적 가능성, 책임 있는 사람의 의사결정이다. 저자는 예제가 특정 제품 묶음을 쓰지만 이 일곱 가지 교훈은 다른 환경으로 옮길 수 있다고 말한다.

참고(노트 작성자): 머리말 본문에는 저자 소개 문단이 따로 없고, 저자 이름은 이 노트의 작업 지시에서 받았다. 머리말에서 저자는 스스로를 .NET, Microsoft Azure, 클라우드 아키텍처, DevOps, AI 지원 개발을 다루는 소프트웨어·시스템 엔지니어, 저술가, 기술 교육자라고 소개한다.

## 2. 기준 구현의 기술 스택

머리말은 기준 구현(reference implementation)이 사용하는 제품을 밝힌다. GitHub, GitHub Actions(GitHub의 워크플로 자동화 기능), GitHub Copilot(코드 작성을 돕는 AI), Azure OpenAI, .NET 10, C#, Microsoft Agent Framework, OpenTelemetry, Aspire Dashboard다. 한 회사 계열로 묶여 실용적이고 일관된 조합이라는 것이 저자의 설명이다. 예제는 YAML, JSON, Markdown 프롬프트 파일, 셸 명령, Bicep(Azure 인프라를 코드로 선언하는 언어), C#을 쓴다. 에이전트 구현의 주 언어는 C#이며, 다른 객체지향 언어에 익숙하면 구조를 따라가 다른 플랫폼에 옮길 수 있다고 한다.

## 3. 책의 구성

책은 8개 장(그 뒤에 혜택 안내 장이 붙는다)으로 이루어진다. 아래 한 줄 요약은 PDF 목차와 'What this book covers'에서 확인한 내용만 옮긴 것이다. 개별 장의 상세 내용은 각 장 폴더에서 다룬다.

| 장 | 한국어 제목 | 한 줄 요약 |
|---|---|---|
| 1 | DevOps를 위한 생성형 AI 개념 | 생성형 AI와 LLM을 소개하고, AI를 DevOps 수명주기에 대응시키며, AI 지원과 AI 자율을 구분하고, 환각(hallucination)·드리프트·월권을 살핀다 |
| 2 | DevOps에서 생성형 AI의 실무 활용 | 생성, 검증, 모니터링의 수명주기로 Bicep IaC, CI 파이프라인 작성, PR 검증, 릴리스 노트, 인시던트 분류에 AI를 적용하되 검토와 승인은 사람이 쥔다 |
| 3 | DevOps AI 도구와 거버넌스, 엔터프라이즈 준비 | 개별 워크플로에서 한 걸음 물러나 기업의 AI 도구 지형을 본다. 위험 기반 도구 선택, 가드레일, 감사와 책임, 조직 도입, 투자수익(ROI) 측정을 다룬다 |
| 4 | 생성형 AI를 DevOps 파이프라인에 통합하기 | Azure OpenAI를 GitHub Actions에 통합한다. 모델 접근 준비, 비밀 값 관리, 재사용 액션, 구조화·검증된 출력, 컨텍스트 엔지니어링, 비용·성능 통제, 텔레메트리, 안전한 통합 패턴, AI 보강 ChatOps를 다룬다 |
| 5 | CI/CD 실패 분류와 PR 품질 평가를 위한 에이전틱 AI | DevOps 에이전트의 구조를 정의하고, CI 실패 분류와 PR 품질 평가를 맡는 범위 좁은 .NET 10 에이전트를 만든다. 안전/위험한 CI/CD 작업, 스키마 검증, 실패 양상, 점진적 자율성을 살핀다 |
| 6 | 고급 시나리오: 메모리와 MCP | 에이전트가 무엇을 기억해야 하는지 설명하고, GitHub 이슈를 검증되는 메모리 장부로 구현한다. MCP(Model Context Protocol)를 소개하고 C# MCP 서버를 만들어 테스트한 뒤 기존 PR 에이전트와 워크플로를 표준화된 도구에 연결한다 |
| 7 | 멀티 에이전트 인시던트 대응과 에이전트 관측성 | 여러 에이전트로 나누는 것이 정당한 경우와 오케스트레이션 패턴을 비교하고, 멀티 에이전트 인시던트 대응 워크플로를 만든다. 평가와 OpenTelemetry 계측을 더해 독립 실행 Aspire Dashboard에서 확인한다 |
| 8 | 맺음말과 다음 단계 | 책의 운영 원칙을 운영 준비 점검표, 점진적 자율성 모델, 측정 가능한 도입 기준, 책임 있는 구현을 위한 실용적 다음 단계로 모은다 |

PDF 목차의 장 아래 절 제목으로 보면 장마다 성격이 다르다. 2장과 4장, 5장, 6장, 7장은 단계(Step)로 쪼갠 실습(Demo)이 중심이다. 3장은 도구 지형, 가드레일, 감사와 책임, 도입 플레이북, ROI 측정 같은 거버넌스(조직의 규칙과 책임 체계) 이야기다. 8장은 점검표와 다음 학습 안내로 마무리한다. 목차에는 9장 'Unlock Your Exclusive Benefits'도 있으나 책 본문이 아니라 혜택 활성화 안내다.

## 4. 읽는 순서 안내

머리말은 실습이 누적식이라고 못 박는다. 따라서 처음 읽는 사람은 1장부터 순서대로 읽는 편이 안전하다. 저장소를 소스 관리 아래 두고, 제공된 시작 상태에서 출발해, AI가 만든 제안을 모두 검토한 뒤 받아들이고, 문서화된 검증 단계를 실행하고, 직접 구현해 본 다음에야 완성 기준본과 비교하라는 것이 머리말의 권고다.

| 독자 상황 | 권장 읽기 범위 | 이유 |
|---|---|---|
| 생성형 AI를 DevOps에 처음 적용한다 | 1장부터 순서대로 | 개념, 실무 활용, 거버넌스, 통합, 에이전트로 점진적으로 쌓인다 |
| 개념은 알고 당장 AI 보조 작업이 궁금하다 | 2장 | IaC, 파이프라인 작성, PR 검증, 릴리스 노트, 인시던트 분류의 실습이 있다 |
| 도입 정책과 통제가 관심사다 | 3장 | 도구 지형, 가드레일, 감사, 도입 플레이북, ROI를 다룬다 |
| 파이프라인에 모델 호출을 넣으려 한다 | 4장 | Azure OpenAI 통합, 재사용 액션, 비용·보안 패턴이 있다 |
| 에이전트를 만들고 싶다 | 5~7장 | 에이전트, 메모리와 MCP, 멀티 에이전트와 관측성을 차례로 다룬다 |
| 정리와 점검표가 필요하다 | 8장 | 운영 준비 점검표와 다음 단계가 있다 |

5장 이후의 실습은 앞 장에서 만든 저장소와 워크플로를 이어받는다(예: 6장은 기존 PR 에이전트와 워크플로를 MCP 도구에 연결한다). 건너뛰려면 먼저 앞 장의 결과물이 있는지 확인한다.

## 5. 실습에 필요한 준비물

머리말의 Technical requirements는 호스팅된 모델 API를 쓰므로 로컬 GPU가 필요 없고, 인터넷이 되는 최신 Windows, macOS, Linux 개발 장비면 충분하다고 한다. 기준 환경은 다음과 같다.

| 준비물 | 쓰이는 곳 |
|---|---|
| .NET 10 SDK | 에이전트 장에서 .NET 10의 파일 기반 C# 앱을 `dotnet run --file` 명령으로 실행 |
| Git과 GitHub 계정 | GitHub Actions, Issues, PR이 켜진 저장소. 브랜치, 워크플로 파일, 환경, 저장소 변수, 비밀 값을 만들 권한이 필요 |
| Visual Studio Code와 C# Dev Kit 확장 | C# 실습(Visual Studio나 JetBrains Rider도 가능) |
| GitHub Copilot과 Copilot Chat | 2장의 AI 지원 코딩과 인프라 시연 |
| Azure 구독 | Microsoft Foundry와 Azure OpenAI 접근, 배포된 채팅 모델, 그 엔드포인트·키·배포 이름을 가져올 권한 |
| Azure CLI와 Bicep CLI | 인프라 코드 실습 |
| jq | JSON 검증용 명령줄 도구. GitHub 호스팅 Ubuntu 러너에는 있지만 로컬이나 자체 호스팅 환경은 설치가 필요할 수 있다 |
| Postman(MCP 요청 지원) | 로컬 stdio MCP 서버 테스트 |
| Docker Desktop 등 OCI 호환 컨테이너 런타임 | 독립 실행 Aspire Dashboard 실습. 로컬 포트 18888, 4317, 4318이 비어 있어야 한다 |

주의할 점이 몇 가지 있다. 예제는 Azure OpenAI를 기준 모델 제공자로 쓰지만 워크플로 패턴은 다른 관리형이나 자체 호스팅 모델 서비스에 맞게 바꿀 수 있다. 일부 Azure SDK와 Microsoft Agent Framework 패키지는 시연을 준비할 때 사전 출시(prerelease) 버전이었으므로, 재현하려면 책 저장소에 고정된 버전을 쓰거나 최신 공식 릴리스 노트를 보고 전체를 다시 테스트해야 한다. 로그, 인시던트, PR, 관측성 실습에는 합성 또는 정제된 데이터를 쓰라고 권한다. 예제 코드는 책의 GitHub 저장소(Packt의 Agentic-AI-for-DevOps-Engineers)에 있고, 시작(start)과 완성(finish) 내용이 나뉘어 있어 실습은 start에서 시작하고 finish로 비교·검증한다.

## 6. 이 노트의 읽는 법

이 노트는 원서를 장별 폴더로 나누어 한국어로 새로 풀어 쓴 학습 노트다. 번역서가 아니라 설명 노트이므로 원문 문장을 그대로 옮기지 않고, 개념과 실습 절차, 설정 값, 주의점을 같은 정보량으로 다시 구성한다.

- 각 장 폴더에는 Readme.md가 있고, 그 안에 핵심 요점과 문서 목록이 있다. 장에 들어가면 Readme.md를 먼저 읽고 필요한 문서로 이동한다.
- 문서는 주제별로 나뉘며 각각 독립해서 읽을 수 있게 썼다.
- 영어 용어는 처음 나올 때 한국어 풀이를 붙인다. 에이전트, 파이프라인, 워크플로, 가드레일(안전 울타리 역할의 제한 장치), 인시던트, 풀 리퀘스트(PR), 거버넌스, 컴포지트 액션(여러 단계를 하나로 묶은 재사용 액션), 프롬프트(모델에 주는 지시문) 같은 용어는 노트 전체에서 같은 말로 통일한다.
- GitHub, Azure, Bicep 같은 제품 이름과 메뉴 이름, 코드, 명령어, 경로는 영어 그대로 둔다.
- 원서의 스크린샷은 싣지 않고 글과 표로 풀어 설명한다.
- 코드는 핵심 줄만 짧게 옮긴다. PDF에서 글자가 깨진 부분은 문맥으로 복원하고, 불확실하면 그렇게 밝힌다.
- 원문에 없는 보충은 '참고(노트 작성자):'로 따로 표시한다.
- 책의 화면과 패키지 버전은 시간이 지나면 달라진다. 실제 화면이나 버전이 다르면 최신 공식 문서를 함께 확인한다.
