# 운영 준비 체크리스트와 점진적 자율성 도입

이 문서는 AI 보조 워크플로나 에이전틱 워크플로를 실험 단계에서 운영 단계로 올리기 전에 던져야 할 열 가지 질문과, 권한을 단계적으로 늘리는 네 단계의 도입 경로를 다룬다. 앞 문서의 원칙이 "무엇을 믿을 것인가"라면, 이 문서는 "언제 믿고 얼마나 맡길 것인가"에 대한 실무 점검표다.

원서의 말대로, 운영으로 승격하기 전에는 주변의 엔지니어링 시스템이 아래 질문 각각에 답할 수 있는지 확인해야 한다. 답할 수 없는 질문이 있다면 그 항목이 아직 승격 준비가 안 된 부분이다. 자동차 출고 전 점검표와 같다. 엔진이 돌아간다는 것만으로는 출고할 수 없고, 브레이크, 에어백, 연료, 서비스 이력까지 확인해야 한다.

---

## 1. 운영 준비 체크리스트 열 가지

| 항목 | 확인할 질문 |
|---|---|
| 과업 적합성 | 이 과업이 정말 언어 이해, 종합, 확률적 추론의 이점을 받는가? 일반적인 결정론적 자동화가 더 안전하고 단순하지 않은가 |
| 신뢰할 수 있는 컨텍스트 | 입력이 관련 있고, 최신이며, 권한이 확인되고, 범위가 제한되고, 신뢰 수준에 따라 분류되어 있는가? 신뢰할 수 없는 이슈 텍스트, 로그, PR 내용이 지시를 조작할 수 있는가 |
| 출력 계약 | 기대하는 결과가 스키마, 제약된 형식, 산출물 유형, 명시적 합격 기준으로 정의되어 있는가 |
| 결정론적 검증 | 생성된 출력이 사용되기 전에 구문과 스키마 검사, 도메인 규칙, 테스트, 보안 스캔, 정책 평가, 환경별 검증을 통과하는가 |
| 권한 경계 | 모델이나 에이전트가 이 과업에 필요한 ID, 도구, 저장소, 환경, 작업만 가지고 있는가 |
| 사람 승인 | 어떤 행동에 검토가 필요하고, 승인 책임자는 누구이며, 실행 전에 승인이 있었음을 시스템이 증명할 수 있는가 |
| 관측성 | 운영자가 민감 데이터를 노출하지 않고 모델 요청, 컨텍스트 소스, 도구 호출, 검증 결과, 재시도, 지연, 오류, 최종 행동을 추적할 수 있는가 |
| 비용과 성능 통제 | 모델 선택, 토큰 사용량, 실행 빈도, 타임아웃, 재시도, 동시성, 도구 호출이 제한되고 모니터링되는가 |
| 실패 처리 | 모델이 시간 초과되거나, 형식이 잘못된 출력을 내거나, 과업을 거부하거나, 없는 도구를 부르거나, 워크플로 일부만 마쳤을 때 어떻게 되는가? 재시도는 제한되고, 반복 행동은 멱등이며, 롤백이나 수동 복구가 가능한가 |
| 변경 관리 | 프롬프트, 스키마, 모델 구성, 도구, 정책, 평가, 의존성이 다른 운영 코드와 같은 규율 있는 과정으로 버전 관리, 검토, 시험, 릴리스되는가 |

용어를 두 가지 풀어 둔다. 멱등(idempotent)은 같은 행동을 여러 번 반복해도 결과가 한 번 한 것과 같다는 뜻이다. 재시도가 중복 배포나 중복 티켓을 만들지 않으려면 필요한 성질이다. 출력 계약은 7장 실습에서 JSON 필드 목록과 타입 결과 클래스로 구현했고, 결정론적 검증은 필수 필드 검사와 80점 평가 함수가 그 예다. 관측성과 변경 관리는 7장의 트레이스, 프롬프트 버전 관리와 곧바로 이어진다. 나머지 항목도 이 책이 앞 장들에서 다룬 통제에 대응한다.

참고(노트 작성자): 위 표의 "확인할 질문"은 원서의 질문을 이해해 다시 풀어 쓴 것이다. 용어 풀이와 7장과의 대응은 원서에 없는 노트 작성자의 보충이다.

## 2. 점진적 자율성: 네 단계

원서는 처음부터 완전 자율 워크플로로 시작하지 말고, 단계적으로 권한을 늘리는 도입 경로를 권한다.

| 단계 | 허용하는 것 | 시스템이 하지 않는 것 |
|---|---|---|
| 1. 보조(Assist) | 설명, 요약, 릴리스 노트 초안, 테스트 제안, 인프라 검토에 AI를 쓴다 | 운영 리소스를 수정하지 않는다. 정보만 낸다 |
| 2. 제안(Propose) | 브랜치, PR, 이슈, 구성 초안, 복구 계획을 만들게 한다 | 모든 변경이 눈에 보이고 일반 CI 검증과 검토를 통과해야 한다 |
| 3. 승인 후 실행(Act with approval) | 정책 검사와 명시적 승인 이후에만 제한된 행동을 허용한다. 예: 실패한 워크플로 재실행, 인시던트 열기, 사전 정의된 복구 적용 | 승인 없이는 실행하지 않는다 |
| 4. 제한된 자율성(Bounded autonomy) | 팀이 충분한 근거를 쌓은 반복적이고 위험이 낮은 행동만 자동화한다 | 엄격한 한도, 감사 기록, 중단 조건, 롤백, 에스컬레이션 경로를 유지한다 |

이 경로를 이 노트에서는 점진적 자율성이라고 부른다. 단계를 오르는 기준은 시간이 지났다는 사실이 아니라 근거다. 워크플로는 평가, 운영 이력, 인시던트 검토가 기존 통제가 효과적임을 확인할 때만 다음 단계로 올라간다. 자율성은 근거에 기반해 부여해야 한다는 것이 원서의 말이다.

### 2-1. 이 책의 앞 장들과 연결해서 보기

- 7장의 인시던트 워크플로는 읽기 전용 분석과 사람 승인 관문을 둔 설계이므로 보조에서 제안 사이에 놓인다. 운영 변경 조치는 승인 관문 뒤에 남겨 둔다.
- 7장의 "자율성을 주기 전에 텔레메트리를 요구한다"는 운영 모델은 3단계 이상으로 올리기 위한 선결 조건이다.
- 4단계에서도 한도, 감사 기록, 중단 조건, 롤백, 에스컬레이션이 사라지지 않는다. 자동화한다는 것은 감독을 없앤다는 뜻이 아니다.

참고(노트 작성자): 2-1절의 연결 해석은 노트 작성자의 보충이다. 원서는 어느 장의 어떤 워크플로가 몇 단계에 속하는지 명시하지 않는다.

## 3. 이 절의 요점

체크리스트는 한 번 통과하면 끝나는 문서가 아니다. 모델, 프롬프트, 도구, 정책이 바뀔 때마다 다시 확인하는 점검표다. 그리고 점진적 자율성은 점검표의 답이 쌓은 근거를 바탕으로 한 계단씩 올라가는 길이다. 다음 문서에서는 그 근거를 어떻게 측정하는지, 그리고 책을 덮은 뒤 무엇을 할지 다룬다.
