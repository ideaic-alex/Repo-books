# 성과 측정, 다음 단계, 학습 이어가기와 최종 요점

이 문서는 8장의 뒷부분이다. AI를 도입한 뒤 성과를 어떻게 재는지, 책을 덮은 뒤 실천할 일곱 가지 다음 단계, 특정 업체에 묶이지 않으면서 학습을 이어 갈 영역, 그리고 새 AI 워크플로를 승인하기 전에 던질 다섯 가지 질문과 책의 마무리 메시지를 정리한다.

한 줄로 요약하면, 사용량이 아니라 결과를 재고, 작게 시작해 근거를 쌓고, 책임질 사람을 정해 둔다는 것이다.

---

## 1. 성과 측정과 지속적 개선

AI를 도입하기 전에 기준선(baseline)을 정한다. 그래야 워크플로가 모델 사용량만 늘린 것이 아니라 실제 엔지니어링 결과를 개선했는지 알 수 있다. 원서가 제시한 측정 영역은 여섯 가지다.

| 영역 | 측정할 내용 |
|---|---|
| 효율 | 절약한 엔지니어링 시간, 사이클 타임, 리드 타임, 생성 출력을 검토하고 고치는 데 쓴 시간 |
| 수용과 수정 | 제안이 그대로 수용된 비율, 수정 후 수용된 비율, 거부된 비율, 사람 전문가에게 올라간 비율 |
| 품질과 안전 | 검증 실패, 테스트 실패, 보안 발견 사항, 오탐, 미탐, 정책 위반, 빠져나간 결함 |
| 신뢰성과 성능 | 지연, 타임아웃 비율, 재시도 비율, 형식이 잘못된 응답, 사용 불가 도구, 성공적 완료율 |
| 비용 | 요청당 비용이 아니라, 성공적이고 수용된 결과당 모델, 컴퓨팅, 저장, 운영 비용 |
| 운영 영향 | 인시던트 감지 시간, 평균 해결 시간(MTTR), 배포 실패율, 롤백 빈도, 릴리스 신뢰도의 변화 |

비용 항목의 관점이 특히 중요하다. 요청 한 건이 싸더라도 대부분 거부되어 다시 해야 한다면 수용된 결과당 비용은 높다. 반대로 요청당 비용이 조금 높아도 대부분 그대로 수용된다면 훨씬 효율적일 수 있다.

이 측정치를 정기적으로 검토하고, 실패 사례와 사람이 한 수정 사례를 평가 케이스로 보관한다. 사용량만으로는 성공을 정의할 수 없다. 워크플로가 허용 가능한 위험, 비용, 운영 한도를 넘지 않으면서 전달을 개선할 때만 진짜 가치가 있다는 것이 원서의 말이다.

## 2. 다음 단계: 점진적이고 안전하게 AI 도입하기

책을 바탕으로 한 실천 경로는 일곱 가지다.

1. 데모를 스스로 다시 만든다. 완성된 소스에 바로 의존하지 말고 직접 구현한 뒤 참조 구현과 비교해 차이를 설명해 본다.
2. 샘플 프로젝트를 확장한다. AI 보조 DevOps 시나리오 하나를 추가하고, 입력과 출력을 정하고, 결과를 쓰기 전에 통과해야 할 결정론적 검사를 명시한다.
3. 재사용 가능한 엔지니어링 자산을 만든다. 일회성 대화에 의존하지 말고 버전 관리되는 프롬프트, 스키마, 워크플로 템플릿, 위협 모델, 평가 케이스, 검증 체크리스트를 유지한다.
4. 위험이 낮은 시범 운영 하나로 시작한다. 범위가 정해진 워크플로를 골라 측정 가능한 성공과 실패 기준을 정하고, 비운영 환경에서 돌리며, 수동 대체 수단을 남긴다.
5. 도구를 추가하기 전에 권한과 실패 양상을 검토한다. 각 도구가 무엇을 읽거나 바꿀 수 있는지, 인자를 어떻게 검증하는지, 도구를 쓸 수 없거나 모호한 데이터를 돌려줄 때 워크플로가 어떻게 행동하는지 문서화한다.
6. 잘된 것과 수정이 필요했던 것을 기록한다. 그 사례로 프롬프트, 정책, 평가, 엔지니어와 검토자 교육을 개선한다.

## 3. 학습 이어가기

좋아하는 도구와 방식이 있는 것은 자연스럽지만, 벤더 종속(vendor lock-in)은 피해야 한다. 효과적인 학습은 AI 기반 DevOps 시스템을 믿을 수 있게 만드는 핵심 역량을 강화하는 것이다. 원서가 꼽은 여섯 영역은 다음과 같다.

| 영역 | 구체적으로 다룰 것 |
|---|---|
| 프롬프트, 컨텍스트, 구조화 출력 | 스키마로 제약한 응답, 컨텍스트 선택, 출처 관리(provenance), 신뢰할 수 없는 지시에 대한 방어 |
| 평가와 회귀 테스트 | 대표 데이터셋, 적대적 사례, 합격 기준, 모델이나 프롬프트 변경 간 비교 |
| AI 보안과 거버넌스 | 프롬프트 주입, 과도한 권한(excessive agency), 비밀 값 노출, 의존성 위험, ID, 권한 부여, 감사 가능성 |
| 관측성과 운영 경제 | 분산 트레이싱, 도구 호출 텔레메트리, 품질 신호, 지연, 토큰 소비, 비용 귀속 |
| 에이전트 메모리, MCP, 안전한 도구 계약 | 모든 상태 소스와 행동 인터페이스의 명확한 소유권, 보존, 격리, 버전 관리, 권한 부여 |
| 사람 개입, 멀티 에이전트, 이벤트 기반 설계 | 장시간 워크플로를 위한 명시적 조율, 에스컬레이션, 보상(compensation), 멱등성, 복구 |

원서는 도입하는 플랫폼, 모델, SDK, 보안 제공자의 최신 공식 문서를 쓰고, 그 제품이 변하면 아키텍처 결정도 다시 살펴보라고 권한다. 구현 세부가 변해도 이 장의 원칙은 지키라는 것이다.

## 4. 최종 요점: 다섯 가지 질문

새 AI 기반 DevOps 워크플로를 승인하기 전에 다섯 가지 질문을 가져가라고 원서는 말한다.

1. AI가 왜 올바른 수단인가? 과업이 언어 이해나 확률적 추론의 이점을 받는지, 결정론적 자동화가 더 명확하고 안전한 곳에 AI를 쓰는 것은 아닌지 확인한다.
2. 워크플로가 무엇에 접근하고 무엇을 바꿀 수 있는가? 권한을 주기 전에 모든 컨텍스트 소스, ID, 권한, 도구, 환경, 부작용을 파악한다.
3. 어떤 근거가 결과를 받아들일 만하게 만드는가? 출력이나 행동을 신뢰하기 전에 통과해야 할 스키마, 테스트, 정책, 평가, 승인을 정의한다.
4. 워크플로는 어떻게 멈추고 복구하는가? 운영 사용 전에 타임아웃, 한도, 안전한 실패 동작, 롤백, 에스컬레이션, 수동 대체 수단을 설계한다.
5. 누가 책임지는가? 워크플로, 승인, 인시던트, 운영에 도달하는 것의 결과에 책임질 소유자를 지정한다.

### 책의 마지막 메시지

생성형 AI는 DevOps 팀이 쓰고, 요약하고, 분석하고, 우선순위를 정하고, 작업을 자동화하도록 돕는다. 그러나 장기적인 유용성은 잘 짜인 엔지니어링 시스템에 달려 있다. 판단과 언어 이해가 중요한 곳에 AI를 쓰고, 해법이 분명한 곳에는 결정론적 코드를 쓰며, 근거가 뒷받침할 때만 자율성을 높인다. 모든 워크플로를 시험 가능하고, 관측 가능하고, 안전하고, 되돌릴 수 있고, 책임 소재가 분명하게 유지한다. 목표는 엔지니어를 DevOps에서 밀어내는 것이 아니라, 더 나은 도구를 쥐여 주되 운영에 나가는 것에 대한 책임은 엔지니어가 계속 지게 하는 것이다.
