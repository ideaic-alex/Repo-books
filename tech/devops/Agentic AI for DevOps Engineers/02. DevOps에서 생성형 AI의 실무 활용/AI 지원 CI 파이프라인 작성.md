# AI 지원 CI 파이프라인 작성

YAML 기반 파이프라인 설정은 유연하지만 엄격하다. 들여쓰기가 한 칸 틀리거나, 중첩이 잘못되거나, 키가 빠지거나, 트리거를 잘못 이해하면 간단한 CI 워크플로도 멈춘다. DevOps 엔지니어는 파이프라인이 무엇을 해야 하는지 알아야 할 뿐 아니라 GitHub Actions나 Azure Pipelines가 요구하는 정확한 문법으로 그 의도를 표현해야 한다.

이 문서는 AI를 초안과 최적화의 파트너로 써서 .NET 애플리케이션의 CI 파이프라인을 만드는 실습을 다룬다. 핵심은 최소 워크플로로 시작해 검증하고, 조금씩 개선하며, 권한을 좁게 유지한다는 것이다.

---

## 1. 왜 AI가 CI 작성에 도움이 되는가

CI 파이프라인은 저장소가 달라도 비슷한 패턴을 따른다. 대부분의 팀이 의존성 복원, 애플리케이션 컴파일, 자동 테스트 실행, 테스트 결과 게시, PR 검증, 의존성 캐시, 보안 취약점 스캔, 배포용 산출물 준비를 반복해서 필요로 한다. 이런 패턴을 매번 처음부터 손으로 쓰면 정작 중요한 엔지니어링 결정에서 주의가 흩어진다. 중요한 결정이란 무엇이 파이프라인을 트리거하는지, 어떤 품질 게이트를 둘지, 무엇이 빌드를 실패시키는지, 워크플로가 팀의 전달 과정을 어떻게 가장 잘 돕는지다.

AI는 DevOps 전문성의 대체재가 아니라 초안과 최적화 파트너로 본다. 명확한 프롬프트로 애플리케이션 스택, 저장소 구조, 브랜치 전략, 빌드 요구, 테스트 명령, 러너(실행 환경), 품질 검사를 설명하면 AI가 초기 YAML 워크플로를 만든다. 다만 그 결과는 저장소 구조, 보안 모델, 명명 규칙, 권한, 비밀 값, 빌드 요구에 맞춰 검토하고 테스트하고 손봐야 한다. 낮은 가치의 문법 작업을 줄이고 초안을 빠르게 만들어, 신뢰성과 유지보수성과 릴리스 확신에 집중하게 하는 것이 목적이다. 파이프라인은 단지 맞아 보이는 것을 넘어 복원, 빌드, 테스트, 검증을 전문적인 DevOps 기준에 맞게 해야 한다.

---

## 2. 실습의 목표

main 브랜치로의 푸시와 PR에서 트리거되어 의존성을 복원하고, 솔루션을 빌드하고, 테스트를 실행하고, 패키지를 캐시하고, 최소 권한을 적용하는 CI 워크플로를 만든다. 그리고 실제 CI 실행으로 결과를 검증한다.

## 3. 단계별 진행

### 3-1. 1단계: 첫 CI 워크플로 만들기

`.github/workflows/ci.yaml` 파일을 만든다(폴더가 없으면 함께 만들어진다). 파일을 연 채로 Copilot Chat에 첫 버전을 요청한다. 프롬프트에 담긴 맥락과 요구는 다음과 같다.

- 대상은 .NET 10 저장소, 솔루션 경로 `src/GenAIDevOps.sln`, 테스트는 `src/OrderService.Tests` 아래의 xUnit 프로젝트
- 트리거는 PR과 main 푸시, 러너는 ubuntu-latest
- 단계는 체크아웃, .NET 10 설정, 복원, Release 빌드
- NuGet 캐시 추가, 최소 권한(가능한 곳은 읽기 전용), 단순하고 안정적으로(아직 매트릭스 없음)
- 배포 단계는 추가하지 말 것

생성된 뒤 에디터 경고를 처리하기 전에 구조를 먼저 검토한다. main 푸시와 PR 트리거, permissions 블록, ubuntu-latest에서 도는 잡, 그리고 체크아웃, .NET 설정, 복원, 빌드, 테스트 단계가 있어야 한다.

참고(노트 작성자): 원문의 프롬프트는 파일명을 ci.yml이라 쓰고 파일은 ci.yaml로 만들게 되어 있어 표기가 어긋난다. 원문 그대로의 불일치이며, 이 노트에서는 본문 지시를 따라 ci.yaml로 적었다.

### 3-2. 2단계: 생성된 YAML 검증하기

기본 체크리스트로 점검한다.

| 점검 항목 | 확인 내용 |
|---|---|
| 트리거 | 의도한 이벤트에서 시작하는가 |
| 권한 | 워크플로에 필요한 만큼으로 제한되었는가 |
| SDK 버전 | 올바른 .NET SDK 버전을 쓰는가 |
| 단계 순서 | 복원, 빌드, 테스트 순서가 맞는가 |
| 액션 버전 | GitHub Actions와 액션 버전이 최신인가 |
| 배포 단계 | 추가되지 않았는가 |

에디터에 YAML 빨간 줄이 보이면 탭이 원인인지 확인한다. YAML은 탭이 아니라 공백을 쓰므로 들여쓰기 오류가 흔하다. Copilot에게 규칙(YAML은 공백을 쓴다)과 추정 원인(탭), 요청(필요한 최소 수정)을 명시한 구체적인 프롬프트로 고치게 한다.

워크플로를 커밋하고 GitHub에 푸시한 뒤 Actions 탭에서 첫 CI 실행을 본다. 빌드는 참조 누락 같은 프로젝트 수준 문제로 여전히 실패할 수 있고, 이 단계에서는 괜찮다. 당장의 목표는 CI 워크플로가 돌고 실패가 예상한 복원, 빌드, 테스트 단계에서 일어나는지 확인하는 것이다. CI는 개발 과정을 믿는 대신 변경을 검증해 코드베이스를 지킨다.

### 3-3. 3단계: 워크플로 개선과 디버깅

다음은 속도와 신뢰성 개선이다. 프롬프트의 제약은 이렇다.

- 당분간 단일 잡 유지
- 동시성(concurrency) 제어를 추가해 같은 브랜치나 PR에서 진행 중인 실행을 취소
- NuGet 캐시의 정확성을 높여 오래된 캐시를 방지
- 명시적 설정으로 결정론적 빌드 보장
- 최소 권한 유지, 개선 사항을 주석으로 간단히 설명, 배포 단계 금지

Copilot은 새 커밋이 푸시되면 같은 브랜치의 이전 실행을 취소하는 동시성 제어를 제안했다. 시간을 아끼고 대기열 경합을 줄인다. 또 명시적인 결정론적 빌드 설정과 의존성 캐시 변경도 제안했는데, 워크플로를 더 반복 가능하게 하고 실행 간 불필요한 작업을 줄인다.

이어서 테스트 결과 업로드를 추가한다. .NET 테스트 TRX 출력용 경로를 쓰고, 성공이든 실패든 항상(always) 업로드하도록 한 단계를 요청한다. 테스트 단계는 TRX를 쓰도록 바뀌고, 결과를 산출물(artifact)로 올리는 단계가 추가된다. 그러면 성공과 실패 모두의 테스트 출력을 워크플로 산출물에서 살펴보기 쉽다.

커밋하고 푸시한 뒤, 동시성이 동작하는지 보려면 이전 실행이 아직 진행 중일 때 작은 변경을 한 번 더 푸시한다. 오래된 실행이 취소되고 새 실행이 시작되어야 한다. 이 실습에서는 다시 돌린 뒤 복원 잡이 MSBUILD의 알 수 없는 스위치 오류(MSB1001)로 실패했다.

### 3-4. 4단계: 실패 진단하고 고치기

오류 메시지를 Copilot Chat에 붙여 넣고, 가장 작고 안전한 수정, 실패 이유, 재발 방지 방법을 요청한다. 진단은 이랬다. `dotnet build`와 `dotnet test`는 configuration 플래그를 쓰지만 `dotnet restore`는 쓰지 않는다. 앞서 생성된 변경 하나가 복원 단계에 release 구성을 넣어 실패했다. 가장 작은 수정은 `dotnet restore`에서 그 인자를 빼고 빌드와 테스트 단계에는 그대로 두는 것이다.

커밋하고 푸시한다. 저장소에 프로젝트 오류가 있으면 이후 빌드에서 여전히 실패할 수 있지만, 여기서는 CI 워크플로 단계 자체가 유효한지가 목표다. 복원이 고쳐졌다면 남은 실패는 파이프라인 문법이나 명령 사용이 아니라 프로젝트 빌드나 테스트에서 비롯된 것이다.

---

## 4. 실습의 교훈

이 실습은 AI가 파이프라인 YAML을 만들고 개선하는 데 도움이 되지만, 틀린 명령 인자나 플랫폼 특유의 실수를 끌어들일 수도 있음을 보여 준다. 같은 AI 보조가 실패 진단도 도울 수 있지만, 엔지니어가 권고를 검토하고 올바른 수정을 적용할 만큼 워크플로를 이해해야 한다. 요약하면 최소 워크플로로 시작해 검증하고, 조금씩 개선하며, 권한을 좁게 유지한다. AI는 엔지니어가 무엇을 물어야 하고 무엇을 확인해야 하는지 알 때 가장 쓸모 있다. 그렇지 않으면 그럴듯하지만 워크플로를 엉뚱한 방향으로 이끄는 변경을 제안할 수 있다.

참고(노트 작성자): 원문에는 이 실습의 YAML 전체가 실려 있지 않고 프롬프트와 Copilot의 제안 설명 위주다(YAML은 스크린샷으로 제시된 것으로 보인다). 그래서 이 문서에도 YAML 코드는 싣지 않았다.
