# AI 지원 릴리스 노트 생성

릴리스 소통도 AI 지원이 쓸모 있는 영역이다. 릴리스 문서는 독자에 따라 필요한 수준이 달라서 너무 기술적이거나 너무 모호해지기 쉽다. 팀이 커밋 로그를 그대로 복사해 붙이기도 하지만, 커밋 로그는 릴리스되는 내용을 잘 대표하지 못할 때가 많고 영향, 위험, 깨지는 변경에 대한 중요한 맥락이 빠질 수 있다.

AI는 빌드 메타데이터와 PR 맥락에서 구조화된 릴리스 보고서를 만들 수 있다. 릴리스를 요약하는 수작업을 줄이고, 팀 사이에서 릴리스 문서를 표준화하며, 사람의 실수와 문서 누락을 막는다. 이 문서의 실습은 사실을 바꾸지 않으면서 PR 메타데이터만으로 릴리스 노트를 만들고, 결과를 초안 릴리스로 올려 사람이 검토하게 하는 워크플로다.

---

## 1. 실습의 목표와 핵심 제약

결정론적이고 메타데이터 기반인 릴리스 노트를 만드는 GitHub Actions 워크플로를 만든다. 핵심 제약은 병합된 풀 리퀘스트(PR)에서 얻을 수 있는 메타데이터만 쓴다는 것이다. PR의 제목, 레이블, 작성자, 본문에 없는 변경을 추론해서는 안 된다.

## 2. 단계별 진행

### 2-1. 1단계: 릴리스 노트 워크플로 만들기

`.github/workflows/release-notes.yml`을 만들고 Copilot에게 요청한다. 요구는 main 푸시에서 실행, 병합된 PR 메타데이터 수집, PR 제목과 레이블과 작성자와 본문 추출, 구조화된 JSON 파일 `release-report.json` 출력, 최소 권한이다. 아직 릴리스 노트는 만들지 말라고 명시한다.

결과는 GitHub Script로 관련 메타데이터를 읽어 `release-report.json`을 만들고 산출물로 올리는 워크플로다. 이후 단계에서 재사용할 구조화된 원본 파일이 릴리스 과정에 생기는 셈이다.

### 2-2. 2단계: 메타데이터로 마크다운 릴리스 노트 만들기

JSON 보고서는 자동화에는 유용하지만 릴리스 소통에는 사람이 읽을 형식도 필요하다. Copilot에게 `release-report.json`으로 `release-notes.md`를 만들게 하되 레이블로 변경을 묶는다.

| 묶음 | 기준 레이블 |
|---|---|
| Features | release:minor |
| Fixes | release:patch |
| Breaking changes | release:major |
| Infrastructure | area:infra |

조건은 제공된 메타데이터만 쓰고 메타데이터를 넘어 추론하지 말라는 것이다. Copilot은 JSON 보고서를 읽어 `release-notes.md`를 만드는 섹션을 추가하고, JSON과 Markdown 파일을 모두 내려받게 업로드 단계도 갱신한다. 이 단계가 중요한 이유는 릴리스 노트를 결정론적으로 유지하기 때문이다. 불완전한 맥락에서 AI 비서가 요약을 지어내게 두지 않고 레이블과 메타데이터로 정보를 묶는다.

### 2-3. 3단계: 검증하고 초안 릴리스 만들기

생성된 릴리스 노트가 비어 있지 않은지 확인하는 검증 단계를 추가한다. AI가 만든 출력을 재사용하기 전에 검증하는 것이다. 이어서 GitHub 릴리스를 초안(draft)으로 만드는 단계를 추가한다. 초안 릴리스의 본문은 생성된 릴리스 노트를 쓰므로, 사람이 게시 전에 검토할 수 있다.

원문은 이 초안 릴리스가 워크플로의 거버넌스 통제라고 말한다. AI는 릴리스 문서 생성을 돕지만 릴리스를 자동으로 게시하지 않으며, 사람 리뷰어가 게시 전에 생성된 내용을 여전히 확인한다.

### 2-4. 4단계: 워크플로 권한 디버깅

릴리스 생성은 처음에 403 오류로 실패한다. 워크플로가 새 릴리스 태그를 만들려 하는데 워크플로 권한이 `contents: read`로 지정되어 토큰이 읽기 권한뿐이기 때문이다. 관련 오류 로그를 Copilot 채팅에 붙여 넣어 진단시키면 워크플로가 contents에 대한 쓰기 권한을 필요로 한다고 짚는다. 권한을 필요한 곳에 한해 읽기 전용에서 쓰기로 바꾼다.

권한 수정을 main에 직접 커밋하고 푸시하면 워크플로가 성공한다. 이번 실행에서는 의미 있는 기능, 수정, 깨지는 변경이 없었지만 생성된 초안 릴리스 노트는 구조화된 출력을 보여 준다. 워크플로 생성은 AI가 돕지만 결과를 검증하고, 실패를 해석하고, 올바른 수정을 적용하는 것은 여전히 엔지니어다.

### 2-5. 5단계: 기능 릴리스로 테스트

더 의미 있는 릴리스를 시험하려면 기능 브랜치(예: `git checkout -b feature/add-version-endpoint`)를 만든다. 주문 서비스에 버전 엔드포인트를 추가한다. 데모에서는 버전 값을 하드코딩하거나 최종 구현에 따라 프로젝트 파일에서 읽어도 된다. Copilot으로 커밋 메시지를 만들면 저장소의 실제 변경에 근거하므로 수작업 자리표시 메시지보다 깔끔해져 릴리스 문서의 질이 오를 수 있다.

명확한 제목(예: Add version endpoint to expose build metadata)으로 PR을 만들고 `release:minor`, `area:API` 같은 레이블을 단다. PR을 병합하면 릴리스 노트 워크플로가 새 초안 릴리스를 만든다. 생성된 노트에는 PR 번호, 제목, 작성자, 레이블, 본문 메타데이터에 근거한 기능 항목이 들어 있다.

---

## 3. 실습의 교훈

이 워크플로는 자동화되고 구조화된 릴리스 노트 절차를 제공한다. PR 메타데이터를 수집해 JSON 보고서를 만들고, Markdown 릴리스 노트를 만들며, 출력을 검증하고, 초안 릴리스를 준비한다. 중요한 점은 릴리스가 초안으로 남는다는 것이다. AI는 문서 생산을 돕고 사람이 검토해 게시한다. 이렇게 하면 릴리스 권한을 AI 비서에게 넘기지 않으면서 릴리스 소통에 유용한 워크플로가 된다.

참고(노트 작성자): 원문은 이 실습의 어느 단계에서도 모델을 호출하지 않는다. 노트가 만들어지는 방식은 레이블 기반 그룹핑 같은 템플릿 규칙이고, AI(Copilot)는 워크플로 코드를 쓰는 데 쓰였다. 모델 호출을 파이프라인에 넣는 것은 4장의 주제로 보인다.
