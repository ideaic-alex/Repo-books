# 요약과 핵심 개념

이 장은 다섯 가지 실습으로 이뤄진다. AI로 Bicep IaC를 쓰고, GitHub Actions CI 파이프라인을 쓰고, PR 검증 워크플로를 만들고, 릴리스 노트를 만들고, 인시던트를 분류한다. 모든 실습이 생성, 검증, 모니터링의 같은 패턴을 반복한다. 이 문서는 다섯 실습을 한 번에 되짚고 핵심 용어를 정리한다.

원서의 요약은 이렇게 이어진다. IaC에서는 AI가 Azure Bicep 템플릿의 뼈대를 만들고 다듬었으며 엔지니어가 구조, 검증, 배포 결정을 쥐었다. CI 작성에서는 GitHub Actions YAML 생성, 캐시와 동시성 개선, 워크플로 실패 진단을 도왔고, 파이프라인 개발은 빨라지지만 검증 과정이 올바름을 결정해야 한다. PR 검증에서는 품질 게이트를 강제하고 커버리지를 수집하며 메타데이터 기반의 결정론적 PR 요약 댓글을 만들었고 AI는 자문 역할이었다. 릴리스 노트에서는 초안 릴리스로 일관성을 높이면서 사람의 거버넌스를 지켰다. 인시던트 분류에서는 실패를 요약하고 구조화된 노트를 만들어 평균 이해 시간을 줄였다. 다음 장은 기업 차원의 질문(어떤 AI 도구를 둘지, 가드레일을 어떻게 세울지, 감사와 ROI)으로 넘어간다.

## 1. 장 전체 흐름

| 실습 | 만든 것 | 검증 수단과 결과 |
|---|---|---|
| AI 지원 IaC | main.bicep(Log Analytics, Container Apps 환경, 컨테이너 앱), dev.bicepparam | what-if 반복, 경고와 오류를 AI와 수작업으로 수정, ACR 이름 고유화와 잘못된 섹션 제거 후 배포 성공 |
| CI 파이프라인 | ci.yaml(복원, 빌드, 테스트, NuGet 캐시, 동시성, TRX 업로드) | Actions 탭 실행 확인, 동시성 취소 확인, MSB1001 오류를 restore에서 구성 인자 제거로 해결 |
| PR 검증 | pr-validation.yml(빌드 테스트, 포맷 검사, 의존성 검토, 커버리지 70%) | 의존성 검토는 Advanced Security가 없어 비활성화, 요약 댓글 생성 확인 |
| 릴리스 노트 | release-notes.yml, release-report.json, release-notes.md | 비어 있지 않은지 검증, 403 오류를 contents 쓰기 권한으로 해결, 기능 PR 병합으로 초안 확인 |
| 인시던트 분류 | 의도적 실패 PR, 구조화된 인시던트 노트 | Explain error로 요약, 노트를 검증한 뒤 지식 베이스 후보로 사용 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 생성, 검증, 모니터링 | 이 장의 수명주기. AI가 초안을 만들고 사람과 결정론적 도구가 검증한다 |
| Bicep | Azure 리소스를 코드로 선언하는 IaC 언어 |
| what-if 배포 | 리소스를 만들기 전에 배포를 시뮬레이션해 무엇이 바뀔지 보여 주는 명령. 잡음이 있을 수 있다 |
| 관리 ID, AcrPull | 비밀번호 없이 ACR에서 이미지를 가져오게 하는 방식과 그에 필요한 최소 역할 |
| 파라미터 파일(.bicepparam) | 환경별(dev, test, prod) 값을 담는 파일. 비밀 값은 넣지 않는다 |
| 최소 권한(permissions) | 워크플로 토큰에 필요한 권한만 주는 설정. 필요할 때만 쓰기를 연다 |
| 동시성(concurrency) | 같은 브랜치나 PR에서 진행 중인 이전 실행을 취소해 중복 실행을 막는 기능 |
| 품질 게이트 | 포맷 검사, 의존성 검토, 커버리지 기준처럼 병합 전에 통과해야 하는 검사 |
| 결정론적 PR 요약 | 메타데이터와 템플릿 규칙으로만 만드는 요약. 환각을 줄인다 |
| 초안(draft) 릴리스 | AI가 만든 릴리스 노트를 사람이 검토한 뒤 게시하게 하는 거버넌스 통제 |
| 평균 이해 시간 | 인시던트에서 무슨 일이 일어났는지 이해하기까지 걸리는 시간. AI가 줄이려는 지표 |
| Explain error | GitHub Actions에서 실패한 워크플로 로그를 Copilot이 설명해 주는 옵션 |

## 3. 자주 놓치는 점

- 폴더와 파일 구조는 AI에게 맡기지 말고 엔지니어가 먼저 만든다.
- 한 번에 큰 프롬프트를 쓰지 말고 작은 프롬프트로 키운다. 하지 말아야 할 것도 프롬프트에 적는다.
- AI가 만든 ACR 이름은 전역 고유성 때문에 충돌할 수 있다. 생성된 이름을 그대로 쓰지 않는다.
- `dotnet restore`에는 configuration 플래그를 붙이지 않는다. 빌드와 테스트에만 쓴다.
- YAML 오류의 흔한 원인은 탭이다. 공백으로 바꾼다.
- 의존성 검토 액션은 GitHub Advanced Security가 꺼진 저장소에서 실패할 수 있다.
- 워크플로가 릴리스 태그를 만들려면 contents 쓰기 권한이 필요하다. 읽기 전용이면 403이 난다.
- what-if 출력의 잡음이나 거짓 양성을 알고 읽는다.
- 외부 AI 도구에 질문할 때는 워크플로 이름, 실패 단계, 오류 발췌, 최근 변경 요약을 직접 줘야 한다. 출력의 질은 맥락의 질에 달려 있다.
- 어느 실습이든 AI 출력은 검증 전까지 제안일 뿐이고, 승인과 게시는 사람이 한다.
