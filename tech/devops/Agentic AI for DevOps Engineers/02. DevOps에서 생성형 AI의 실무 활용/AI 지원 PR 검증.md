# AI 지원 PR 검증

테스트가 통과했다고 해서 릴리스가 맞다는 보장은 없다. 테스트가 통과해도 위험은 빠져 있을 수 있다. 테스트 커버리지가 곧 정확성도 아니다. 테스트가 핵심이 아닌 기능에 치우쳐 있거나, 핵심 기능을 겨냥하더라도 잘못 쓰였을 수 있기 때문이다.

AI는 테스트 아이디어 초안, 테스트 실패 설명, 빠진 커버리지 식별, 테스트 입력 요약, 위험한 변경 부각으로 릴리스 확신을 높이는 데 도움이 된다. 위험이 더 일찍 눈에 보이고 실패가 더 이해하기 쉬워진다. 반면 AI가 릴리스를 승인하거나, 실패한 테스트를 무시하거나, 검토 없이 테스트를 생성하거나, 스스로 행동해서는 안 된다. 가장 안전한 패턴은 AI를 자문 역할에 두는 것이다. 릴리스 확신은 자동 승인이 아니라 더 많은 정보를 가진 사람의 결정에서 나온다.

---

## 1. 실습의 목표

앞의 빌드용 CI 파이프라인에서 한 걸음 나아가 더 엄격한 풀 리퀘스트(PR) 검증 워크플로를 만든다. 이 워크플로는 PR에서만 돌고, AI를 권위가 아니라 리뷰어를 돕는 지원으로 취급한다.

## 2. 단계별 진행

### 2-1. 1단계: 워크플로 만들기

`.github/workflows/pr-validation.yml`을 만들고 Copilot Chat에 첫 초안을 요청한다. 프롬프트의 핵심 요구는 다음과 같다.

- .NET 10 솔루션(`src/GenAIDevOps.sln`), 워크플로는 PR에서만 실행, main을 대상으로 한 pull_request에 트리거
- 권한은 contents: read, pull-requests: write
- 잡 세 개: build-test(복원, Release 빌드, Release 테스트), formatting-check(`dotnet format --verify-no-changes`), dependency-review(GitHub 공식 dependency-review-action)
- 포맷이나 테스트가 실패하면 워크플로 실패, YAML은 읽기 쉽고 운영 수준으로, 배포 단계는 넣지 않음

CI 때와 마찬가지로 수락 전에 YAML을 검토한다. 탭이 쓰였으면 공백으로 고치게 한다. 결과에는 main 대상 PR 트리거, 명확한 권한, 복원, 빌드, 테스트 잡이 있어야 하며, 코드가 `.editorconfig` 같은 프로젝트 표준에 맞는지 비교하는 포맷 검사도 있어야 한다.

참고(노트 작성자): 원문 프롬프트의 `dotnet format –verify-no-changes`는 하이픈이 긴 줄표로 깨져 있다. 실제 옵션은 `--verify-no-changes`로 복원해 적었다. 원문의 `pr-validation.yml`과 그림 캡션의 `pr-validation.yaml` 표기도 섞여 있다.

### 2-2. 2단계: 더 엄격한 품질 게이트 추가

PR 검증에는 의존성 검토(dependency review)도 넣을 수 있다. 의존성의 취약점과 라이선스 문제를 확인하는 단계로, 변경이 병합되기 전 PR 과정에 품질 게이트 하나를 더 얹는다.

다음으로 테스트 커버리지를 수집하고 최소 기준을 강제하게 한다. 프롬프트는 Coverlet을 쓴 .NET 테스트로 커버리지를 수집하고, 70% 아래로 떨어지면 실패시키며, 커버리지 보고서를 산출물로 올리게 한다. Copilot은 테스트 잡을 수정해 커버리지를 모으고 보고서를 올린다. CI 때와 같은 방식으로 동시성 제어도 넣어, 같은 PR 브랜치에 커밋이 여러 번 푸시될 때 중복 검증이 쌓이지 않게 한다.

### 2-3. 3단계: 결정론적 PR 요약 추가

이제 AI가 거드는 부분이다. 목표는 기존 PR 메타데이터를 바탕으로 결정론적인 PR 요약 댓글을 만드는 것이다. 워크플로는 파일 변경을 지어내거나 PR에 있는 정보 이상을 추론해서는 안 된다. 프롬프트는 PR 제목과 커밋 메시지를 써서 다음 항목이 담긴 댓글을 게시하도록 한다.

| 댓글 항목 | 내용 |
|---|---|
| 변경 요약 | PR 변경 사항 요약 |
| 위험 평가 | 낮음, 중간, 높음 |
| 테스트 고려 사항 | 테스트 시 유의점 |
| 인프라 영향 | 예 또는 아니오 |

조건은 결정론적이고 템플릿 기반으로, 파일 변경을 환각하지 말라는 것이다. Copilot이 위험 평가를 어떻게 정할지, 인프라 영향을 어떻게 식별할지, 테스트 고려 사항 줄에 무엇을 쓸지 되묻는 질문을 할 수 있다. 이때 보조가 말하지 않은 세부를 추론하게 두지 말고 메타데이터에 근거한 결정론적 규칙을 준다. 생성된 잡은 PR 번호, 제목, 커밋 등 GitHub 컨텍스트 값과 PR 메타데이터를 써서 템플릿 기반 댓글 본문을 만든다. 그래서 요약이 결정론적으로 유지되고 환각 출력 위험이 줄어든다.

### 2-4. 4단계: PR에서 워크플로 테스트

새 브랜치를 만들어(예: `git checkout -b ci/pr-validation-demo`) 워크플로 변경을 푸시하고 GitHub에서 PR을 만든다. 이 실습에서는 의존성 검토 잡이 실패했다. 저장소에 필요한 GitHub Advanced Security 기능이 꺼져 있기 때문이다. 이 환경에서는 의존성 검토 단계를 주석 처리하고 필수 needs 목록에서도 뺐다. 푸시하자 워크플로가 성공했고, 생성된 PR 요약 댓글이 PR에 나타났다. 댓글에는 변경 요약, 커밋 메시지, 위험 평가, 검사 상태 같은 구조화된 정보가 담겼다.

GitHub Copilot이 PR 화면에서 별도의 AI 리뷰를 하고 개선을 제안할 수도 있다. 유용하지만 사람의 검토는 여전히 필요하다. IDE의 Copilot과 GitHub의 Copilot이 서로 다른 관점을 보여 줄 수 있고 최종 결정은 사람 리뷰어에게 있다.

---

## 3. 실습의 교훈

이 실습은 PR 검증에서 AI의 가장 안전한 역할을 보여 준다. AI는 요약하고, 설명하고, 위험을 부각할 수 있지만 자문에 머물러야 한다. 워크플로는 리뷰어의 가시성을 높이고, 릴리스 결정은 계속 사람의 책임이다.
