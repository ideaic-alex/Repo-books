# AI 지원 IaC 실습

2장은 생성(generate), 검증(validate), 모니터링(monitor)이라는 단순한 수명주기를 따른다. AI가 인프라 템플릿, CI 워크플로, PR 요약, 릴리스 문서, 인시던트 노트의 초안을 만들 수 있지만, 모든 출력은 검토하고 테스트하고 필요하면 고쳐서 기존 엔지니어링 절차에 통합해야 한다. 목표는 통제권을 AI 비서에게 넘기는 것이 아니라 초안 작성, 설명, 문제 해결, 문서화를 빠르게 하면서 검증, 승인, 최종 결정은 사람이 쥐는 것이다.

이 문서는 첫 주제인 코드형 인프라(IaC, Infrastructure as Code)를 다룬다. Azure 인프라를 Bicep으로 쓰면서 GitHub Copilot의 도움을 받는 실습이다. 핵심은 작은 프롬프트로 조금씩 키우고, 매번 what-if로 검증하며, AI가 낸 틀린 부분은 엔지니어가 고친다는 흐름이다.

---

## 1. 실습 준비물과 저장소 구조

실습에는 다음이 필요하다. VS Code(다른 IDE도 가능), GitHub Copilot과 Copilot Chat(다른 AI 보조로도 같은 흐름을 따를 수 있고, 무료 등급이면 충분하다), Azure CLI(설치 후 `az login`으로 인증), Bicep CLI(대개 Azure CLI에 포함되어 따로 설치하지 않아도 된다), 그리고 Copilot 사용을 위한 GitHub 계정이다. 책의 코드는 저장소의 start 폴더(실습 시작 기준선)와 finish 폴더(완성본, 비교와 검증용)로 나뉘어 있다.

## 2. IaC가 AI의 자연스러운 첫 진입점인 이유

IaC는 텍스트 기반이고 패턴이 많아서 DevOps에서 AI를 처음 쓰기에 자연스러운 곳이다. AI는 인프라 정의의 초안을 쓰고 설명할 때 효과적이다. 한편 DevOps는 결정론적 배포를 요구하며 IaC가 그 반복 가능성을 보장해 준다. AI가 도울 수 있는 일은 다음과 같다.

- 템플릿 뼈대 만들기
- 리소스 간 관계 제안
- 파라미터 파일 생성
- 기존 템플릿 설명
- 조심해서 쓰면 흔한 IaC 안티패턴 피하기

그러나 AI가 만든 인프라가 자동으로 맞는 것은 아니다. 리소스, 권한, 설정이 조직 정책과 보안 기대에 맞는지 엔지니어가 반드시 확인해야 한다.

## 3. 실습의 목표

컨테이너화된 워크로드를 위한 동작하는 Bicep 배포를 만든다. 기대 결과는 세 가지다. 프로젝트 안의 깔끔한 폴더 구조, Azure CLI로 하는 반복 가능한 배포 흐름, 그리고 Copilot 출력에 환각이나 잘못된 설정이 없는지 확인하는 검증 체크리스트다. Azure와 Bicep을 쓰지만 기본 원리는 다른 클라우드와 DevOps 환경에도 같이 적용된다.

---

## 4. 단계별 진행

### 4-1. 1단계: 첫 Bicep 템플릿 만들기

`infra` 폴더와 그 안의 `bicep` 폴더는 처음엔 비어 있다. 여기서 원문이 강조하는 원칙이 있다. 파일과 폴더 구조는 AI에게 맡기지 않는다. 엔지니어가 `infra/bicep/main.bicep`을 직접 만들고, 그다음에 AI에게 내용을 채우게 한다. 그래야 프로젝트 구성을 엔지니어가 쥐고, 비서가 맥락 없이 구조를 결정하는 일이 없다.

main.bicep을 연 채로 Copilot Chat에 첫 프롬프트를 준다. 요구는 최소한으로 한다.

- 단일 파일(main.bicep)
- 파라미터 둘: location(기본값은 resourceGroup().location), environmentName(dev/test/prod)
- 배포 대상은 Log Analytics Workspace 하나뿐
- 최신 안정 API 버전 사용, 기본 태그 추가, 의도적으로 최소화하고 읽기 쉽게
- 금지 항목으로 Container Apps, ACR, 비밀 값, 역할 할당을 명시

이 프롬프트의 목적은 배포하고 검토할 수 있는 가장 작은 의미 있는 출발점이지 완전한 운영용 환경이 아니다. 제안은 수락 전에 최소 체크리스트로 검토한다.

| 점검 항목 | 의미 |
|---|---|
| 파라미터가 명시적인가 | 값이 템플릿 안에 숨어 있지 않다 |
| 이름이 하드코딩되지 않았는가 | 환경별로 바꿀 수 있다 |
| 미리 보기(preview) API를 쓰지 않았는가 | 의도적으로 필요한 경우만 허용 |
| SKU 선택이 합리적인가 | 과한 사양이 없다 |
| 리소스 관계가 이해되는가 | 연결 구조를 읽을 수 있다 |
| 권한과 ID가 보안 기대와 맞는가 | 과한 권한이 없다 |

AI가 만든 코드는 반드시 운영 가능하다고 볼 수 없다. 쓰기 전에 걸러야 한다.

### 4-2. 2단계: 첫 배포 검증하기

Azure 구독과 인증된 Azure CLI 세션이 필요하다. 먼저 리소스 그룹을 만든다(책의 예는 이름이 rg-genai-devops-dev, 지역은 eastus).

```
az group create -n rg-genai-devops-dev --location eastus
az deployment group what-if --resource-group rg-genai-devops-dev --template-file infra/bicep/main.bicep --parameters environmentName=dev
```

what-if는 리소스를 실제로 만들기 전에 배포를 시뮬레이션하는 명령이다. 출력에 거짓 양성이나 잡음이 있을 수 있지만, 배포 실행 전에 Azure가 무엇이 생성되거나 바뀔 것으로 예상하는지 보여 주는 중요한 검증 단계다. 결과가 받아들일 만하면 같은 인자로 `az deployment group create`를 실행해 실제 배포하고, 성공적인 프로비저닝 출력을 확인한다.

### 4-3. 3단계: 작은 단위로 템플릿 확장하기

첫 배포가 성공하면 확장한다. 두 번째 프롬프트는 기존 리소스를 재사용하면서 Azure Container Apps 환경(Environment)을 Log Analytics Workspace에 연결해 추가하게 한다. 제약은 기존 파라미터 재사용, 아직 Container App은 추가하지 말 것, 이름은 결정론적으로, 새 리소스를 설명하라는 것이다. 원문은 작은 프롬프트를 쓰면 환경을 점진적으로 쌓을 수 있어 한 번에 전부 만들게 하는 것보다 각 변경을 검토하고 검증하고 고치기 쉽다고 한다.

제안을 검토하면 컨테이너 앱 환경 이름 같은 항목과 어떤 리소스가 추가되었는지 설명을 볼 수 있다. 수락한 뒤 what-if를 다시 돌린다. 템플릿이 바뀌었으므로 새 리소스를 안전하게 추가할 수 있는지 확인하는 단계다.

이번 실행에서 Bicep이 경고를 낸다. listKeys를 호출하는 대신 리소스 심볼 참조를 쓰라는 내용이다. 경고가 가리키는 줄을 찾아 Copilot에게 이 코드를 평가하고 경고를 처리하라고 요청하면 Bicep 도구와 개발 환경의 맥락 정보를 써서 수정안을 낸다. 원서 그림 설명에 따르면 이때 Copilot은 Azure Bicep MCP 도구를 참고해 고친다. 수정을 수락한 뒤 what-if를 다시 돌려 경고가 사라졌고 새로 깨진 것이 없음을 확인한다.

### 4-4. 4단계: 컨테이너 앱 추가와 이미지 접근 보안

이제 Azure Container App 하나를 또 한정된 프롬프트로 추가한다. 요구는 다음과 같다.

- 포트 8080의 외부 HTTP ingress
- 이미지 이름과 태그는 파라미터
- 시스템 할당 관리 ID(managed identity) 사용
- ACR 관리자 자격 증명은 사용하지 않음
- 이미지는 이미 있다고 가정
- 역할 할당은 아직 추가하지 말 것

이미지를 파라미터로 요구해 컨테이너 이미지를 바꿀 수 있게 하고, 보안상 중요한 ACR 관리자 자격 증명을 피한다. 다음 보안 중심 프롬프트는 컨테이너 앱이 관리 ID로 ACR에서 이미지를 가져오도록 템플릿을 고친다. 제약은 AcrPull 역할만 사용, 역할 할당 범위는 ACR로 한정, ACR 관리자 사용자 비활성 유지, 변경 최소화다.

이 시점에 오류가 여러 개 나타날 수 있다. 문법 오류도 있고 빠진 파라미터 때문인 것도 있다. Copilot에게 `containerAppName`, `acrName`, `imageName`, `imageTag` 파라미터를 추가하게 하면 대부분 사라진다. 문법 오류가 남으면 해당 코드를 선택해 평가하고 고치라고 요청한다. 이 실습에서 남은 문제는 Container Apps 정의의 CPU 값이었다. JSON 형식으로 맞춰야 했고, 고친 뒤 what-if를 다시 돌리면서 필요한 파라미터 값을 제공한다.

### 4-5. 5단계: 파라미터 파일 만들기

템플릿이 여러 파라미터를 요구하므로 `infra/bicep/parameters/dev.bicepparam` 파일을 만든다. Copilot에게 main.bicep의 파라미터를 바탕으로 안전하고 일반적인 값을 채우되 비밀 값은 넣지 말라고 요청한다. 이 파일은 main.bicep을 참조하고 개발 환경에 필요한 값을 정의한다. dev, test, prod가 각각 자기 파라미터 파일을 가질 수 있다. 마지막으로 `--parameters infra/bicep/parameters/dev.bicepparam`으로 배포를 다시 실행한다.

## 5. AI가 만든 문제를 검토하기

실습 중 수동으로 고쳐야 했던 문제는 두 가지다.

| 문제 | 원인과 조치 |
|---|---|
| ACR 이름 중복 | AI가 만든 ACR 이름이 이미 사용 중이었다. ACR 이름은 공개적으로 접근되고 DNS에 등록되므로 전역에서 유일해야 하며, 이름을 고유하게 바꿨다 |
| 구조적 오류 | main.bicep에 생성된 일부 섹션이 틀려 제거해야 했다. 레지스트리 섹션이 ID 설정을 잘못 처리했고, ACR pull 역할 할당 섹션도 배포가 성공하기 전에 제거했다 |

수정 후 배포가 성공했다. 원문은 이것이 AI 지원 인프라 작성의 가치와 한계를 보여 주는 사례라고 평한다. Copilot은 문법 대부분을 뼈대로 만들어 템플릿을 빠르게 진전시키지만 틀린 결정도 내린다. 출력을 디버깅하고, 플랫폼 요구를 이해하고, 최종 구현을 선택하는 책임은 엔지니어에게 남는다.

참고(노트 작성자): 원문에서 4단계의 두 번째 역할 할당 프롬프트와 5단계 결과 사이에, 결국 역할 할당 섹션을 제거해 배포했다는 대목이 나온다. 이 경우 AcrPull 권한 부여가 템플릿에 남지 않았을 가능성이 있다. 원문은 이후 이미지 가져오기 권한을 어떻게 처리했는지 다루지 않는다.
