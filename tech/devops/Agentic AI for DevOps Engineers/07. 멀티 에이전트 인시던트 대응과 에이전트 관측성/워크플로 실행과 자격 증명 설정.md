# 워크플로 실행과 자격 증명 설정

이번 실습은 앞에서 만든 워크플로를 실제로 돌린다. 세 전문가를 동시에 실행하고, 응답을 모은 뒤, 모인 증거를 인시던트 지휘관에게 넘겨 타입이 정해진 종합 결과를 얻는다. 시작 전에 프롬프트 파일과 인시던트 파일이 모두 존재하는지 확인해야 한다. 모델 호출이 시작된 뒤에 파일이 없다는 사실을 아는 것은 시간과 비용 낭비이기 때문이다.

이 문서는 짧은 편이다. 원서의 이 부분은 환경 변수 설정, 명령 한 줄, 출력 읽는 법으로 이뤄져 있다. 그래서 필요한 사전 조건과 설정 값, 출력에서 확인할 항목을 빠짐없이 정리하는 데 집중한다.

---

## 1. 사전 조건

7장 도입부의 기술 요구사항에서 실습 전체에 필요한 것을 정리하면 다음과 같다.

| 항목 | 내용 |
|---|---|
| 런타임 | .NET 10 SDK, C#을 지원하는 편집기나 IDE. 예제는 `dotnet run --file`로 실행하는 파일 기반 앱 |
| 참조 구현 | 저장소 `trevoirwilliams/genai-devops-teaching-guide`의 커밋 `05c9cf0266de60bc8f3dee8c16af62812c94c0ed`에 고정 |
| 실행 위치 | finish 디렉터리. 상대 경로 `ai/prompts`, `ai/samples`가 맞게 풀리기 때문 |
| Azure OpenAI | 채팅 모델이 배포된 리소스와 그 배포를 호출할 권한 |
| 환경 변수 | AZURE_OPENAI_ENDPOINT, AZURE_OPENAI_API_KEY, AZURE_OPENAI_DEPLOYMENT |
| 컨테이너 런타임 | Docker Desktop 또는 OCI 호환 런타임(Aspire Dashboard 실습용) |
| 로컬 포트 | 18888, 4317, 4318을 비워 둘 것(대시보드 화면과 OTLP 수신기용) |
| 데이터 | 합성 또는 정제된 인시던트 데이터 |

마지막 항목에는 경고가 붙어 있다. 참조 관측성 데모는 교육 목적으로 민감한 메시지 텔레메트리를 켜 두므로, 이 설정을 운영 로그, 비밀 값, 개인정보, 기타 기밀 데이터에 쓰면 안 된다. 이 이야기는 6번째 문서에서 다시 나온다.

## 2. 자격 증명을 설정하고 실행하기

### 2-1. 저장소 준비

저장소 루트에서 고정된 참조 커밋을 체크아웃하고 finish 디렉터리로 이동한다.

```
git checkout 05c9cf0266de60bc8f3dee8c16af62812c94c0ed
cd finish
```

### 2-2. 환경 변수 설정

엔드포인트, API 키, 배포 이름 세 가지를 환경 변수로 넣는다. 셸마다 문법이 다르다. PowerShell은 `$env:이름 = "값"`, 명령 프롬프트는 `set 이름=값`, macOS나 Linux의 Bash는 `export 이름="값"` 형태다. 이 노트에서는 값을 아래 자리표시자로만 쓴다.

```powershell
$env:AZURE_OPENAI_ENDPOINT = "<your-endpoint>"
$env:AZURE_OPENAI_API_KEY = "<your-key>"
$env:AZURE_OPENAI_DEPLOYMENT = "<your-deployment>"
```

API 키 같은 비밀 값은 코드나 저장소에 쓰지 않고 환경 변수로 넣는 것이 원칙이다. 코드가 키를 읽는 위치도 환경 변수 한 곳뿐이다.

### 2-3. 앱 실행

.NET 10 파일 기반 앱을 실행한다. 중간의 `--` 구분자는 뒤따르는 인시던트 디렉터리를 dotnet 옵션이 아니라 앱 인자로 넘기라는 뜻이다.

```
dotnet run --file ai/agents/MultiAgentIncidentResponseWorkflow.cs -- ai/samples/incidents/orderservice-sev2
```

## 3. 출력 읽는 법

실행 후 확인할 것을 순서대로 적는다.

1. 콘솔 출력을 본다. 세 전문가가 동시에 실행되므로 스트리밍 업데이트가 뒤섞여 나올 수 있고, 실행마다 순서가 달라질 수 있다. 그 뒤 워크플로가 완성된 전문가 결과를 서로 구분된 취합 구획으로 출력한다. 원서 그림 7.2가 이 장면, 즉 뒤섞인 스트리밍 다음에 취합 출력이 나오는 터미널 화면을 보여 준다.
2. 취합된 전문가 출력을 검토한다. 각 에이전트 출력에 무엇이 담겨야 하는지는 다음과 같다.
   - 배포 파이프라인 에이전트: 의심되는 문제, 수집한 증거, 높은 신뢰도 평가, 권고 조치.
   - 런북 준수 에이전트: 승인된 즉시 조치, 롤백 조언, 검증 단계.
   - OrderService 상태 확인 에이전트: 지연 증가, 500 오류의 증거, 높은 오류율. 샘플 데이터와 일치한다.
3. 지휘관의 최종 출력을 본다. 인시던트 ID, 경영진 요약, 유력 원인, 즉시 조치, 롤백 권고, 검증 계획, 이해관계자 메시지가 나온다(원서 그림 7.3).

## 4. 이 실습이 보여 주는 것

이 실행은 전문가 에이전트들로의 팬아웃과 조율 에이전트로의 팬인을 실제로 보여 준다. 운영 환경이라면 같은 읽기 전용 분석을 호스팅 서비스 안에서 돌려, 검증을 통과한 인시던트 꾸러미를 인시던트 관리 API, 대시보드, 협업 채널에 게시할 수 있다. 어떤 운영 변경 조치든 명시적인 승인 관문 뒤에 남겨야 한다는 점은 여전하다. 이렇게 여러 전문 에이전트를 조율해 인시던트 대응이나 분류를 도울 수 있다는 것이 원서의 결론이다.

## 5. 실행이 안 될 때 확인할 곳

참고(노트 작성자): 아래는 원서의 코드 동작에서 유추한 점검 목록이며 원서가 직접 나열한 것은 아니다.

- 환경 변수 이름이 틀리거나 비어 있으면 코드가 "AZURE_OPENAI_ENDPOINT를 설정하라" 같은 예외를 던진다.
- finish 디렉터리가 아닌 곳에서 실행하면 프롬프트 폴더 경로가 맞지 않을 수 있다. 프롬프트는 현재 디렉터리 기준으로 읽기 때문이다.
- 인시던트 폴더에 다섯 파일 중 하나라도 빠지면 `ReadRequiredFileAsync`가 예외를 던진다.
- 2분 안에 끝나지 않으면 취소 토큰이 작업을 중단한다.

다음 문서에서는 이 워크플로를 운영하려면 무엇을 관측하고 평가해야 하는지 이론을 살펴본다.
