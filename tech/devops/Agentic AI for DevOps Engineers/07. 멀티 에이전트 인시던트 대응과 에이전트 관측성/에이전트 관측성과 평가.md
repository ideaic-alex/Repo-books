# 에이전트 관측성과 평가

여러 에이전트가 인시던트를 분석하는 워크플로를 만들었다면, 다음 질문은 "이것이 제대로 일하고 있는지 어떻게 아는가"다. 이 절은 에이전트를 운영할 때 필요한 관측성(observability, 시스템 내부 상태를 로그, 트레이스, 지표로 들여다볼 수 있는 정도)과 평가(evaluation)의 개념을 다룬다. 코드는 나오지 않고 이론과 운영 모델이 중심이다. 다음 문서의 실습이 이 이론을 구현한다.

일반 애플리케이션 모니터링은 "서비스가 건강한가"를 묻는다. 에이전트는 여기에 더해 네 가지를 물어야 한다. 에이전트가 어떤 판단 경로를 거쳤는가, 어떤 도구를 호출했는가, 어떤 컨텍스트를 썼는가, 출력이 정확하고 안전하고 쓸모 있었는가. 에이전트의 실패는 인프라 실패이기보다 논리 실패인 경우가 많고, DevOps에서 보이지 않는 에이전트는 그 자체로 운영 위험이라고 원서는 말한다.

---

## 1. 에이전트 관측성의 세 축

| 축 | 무엇을 보는가 |
|---|---|
| 트레이싱(Tracing) | 단계와 도구 호출에 걸친 실행 흐름 |
| 모니터링(Monitoring) | 지연, 실패, 토큰 사용량, 처리량, 비용 |
| 평가(Evaluation) | 출력 품질, 안전성, 과업 완수, 정확성 |

DevOps 팀에게 이 세 축은 디버깅, 거버넌스(통제와 책임 체계), 성능 튜닝, 안전한 롤아웃 결정을 뒷받침한다.

## 2. 트레이스, 로그, 지표

세 가지 텔레메트리(원격 계측 데이터) 신호는 담는 내용이 다르다.

- 트레이스: 에이전트 실행, 모델 호출, 도구 호출, 재시도, 대체 경로(fallback), 실패 경로를 포함한다.
- 로그: 상관 ID가 붙은 구조화된 이벤트, 도구의 입력과 출력, 정책 결정, 가드레일 결과를 담는다.
- 지표(metrics): 분당 요청 수, 토큰 수, 지연 백분위수, 도구 오류율, 과업 성공률, 평가 통과율을 다룬다.

### 에이전트 트레이스가 담아야 할 항목

필수로 권장되는 것은 상관 ID 또는 트레이스 ID, 에이전트 이름과 버전, 사용자 또는 트리거한 워크플로의 ID, 사용한 모델, 프롬프트 또는 프롬프트 참조, 수행한 도구 호출, 재시도 횟수, 각 단계에 걸린 시간이다. 선택 항목으로는 토큰 사용량, 비용 추정, 안전 플래그, 평가 점수와의 연결이 있다.

이 목록에서 "에이전트 이름과 버전", "프롬프트 참조"가 들어 있다는 점이 중요하다. 나중에 프롬프트를 고쳤을 때 어느 버전의 프롬프트가 그 결과를 냈는지 거꾸로 추적할 수 있어야 하기 때문이다.

## 3. 모니터링과 평가는 다르다

평가는 모니터링과 같지 않다. 모니터링은 무언가가 빠른지, 실패하는지, 비싼지를 답한다. 평가는 그것이 정확한지, 근거에 기반했는지, 지시를 따랐는지, 도구를 적절히 썼는지, 안전했는지를 답한다. 원서의 표현으로, 빠른 에이전트도 틀릴 수 있고 안정적인 에이전트도 안전하지 않을 수 있다. 응답 시간이 짧고 오류가 0이어도 엉뚱한 롤백을 권하고 있을 수 있다는 뜻이다.

### DevOps 에이전트에게 중요한 평가 항목

| 항목 | 질문 |
|---|---|
| 과업 준수 | 에이전트가 운영 지시를 제대로 따랐는가 |
| 도구 정확성 | 올바른 도구를 올바른 인자로 썼는가 |
| 출력 품질 | 쓸모 있고 실행 가능한가 |
| 안전성 | 안전하지 않거나 정책을 어기는 출력을 피했는가 |
| 운영 효율 | 시간이 얼마나 걸렸고 토큰을 얼마나 썼는가 |
| 사람에게 유용한가 | 엔지니어인 우리가 이 출력을 믿을 수 있는가 |

## 4. 평가는 생애주기 전반에서 한다

- 배포 전: 골든 데이터셋(정답이 정해진 대표 사례 모음), 벤치마크 실행, 임계값 점검을 쓴다.
- 지속적 통합(CI): 스모크 평가(핵심만 빠르게 보는 평가), 회귀 감지, 신뢰도 점수가 떨어지면 빌드 실패 처리를 한다.
- 운영 중: 표본 추출 기반의 지속 평가, 드리프트(시간이 지나며 성능이나 입력 특성이 달라지는 현상)나 품질 저하 시 경보, 점수나 트레이스를 인시던트와 연결한다.

## 5. 한 번 구현하고 환경마다 백엔드를 고른다

원서의 예시는 이렇다. 로컬 개발에서는 독립 실행형 Aspire Dashboard로 OpenTelemetry 신호를 살펴보고, 운영 환경에서는 같은 계측을 Azure Monitor/Application Insights나 Grafana 같은 내구성 있는 백엔드로 내보낸다. 모델과 에이전트 평가를 더하는 플랫폼 계층은 선택 사항이다. 근본 원리는 계측을 한 번 구현하고 환경마다 맞는 백엔드를 고르는 것이다. 원서 그림 7.4는 계측된 .NET 에이전트에서 OpenTelemetry를 거쳐 로컬과 운영 관측성 백엔드로 이어지는 텔레메트리 흐름을 그린 것이며, 이 노트에서는 글로 설명했다.

## 6. 권장 운영 모델

원서가 권하는 관측성 운영 모델을 여섯 가지로 정리한다.

1. 사람이 루프 안에 있는 상태(human in the loop)로 시작한다.
2. 자율성을 주기 전에 텔레메트리를 요구한다.
3. 사용 사례마다 합격 기준(임계값)을 정한다.
4. 프롬프트 변경을 코드 변경처럼 다룬다. 프롬프트, 도구, 평가 데이터셋에 버전을 붙인다.
5. 실패한 트레이스를 정해진 주기로 검토한다.
6. 모델, 프롬프트, 도구가 바뀐 뒤에는 항상 평가를 다시 돌린다.

2번이 이 책 전체를 관통하는 점진적 자율성(자율 권한을 단계적으로 늘리는 도입 방식)의 핵심 조건이다. 관측되지 않는 에이전트에게는 더 큰 권한을 주지 않는다. 8장의 체크리스트에서 이 원칙이 다시 정리된다.

| 이론 요소 | 다음 문서의 대응 |
|---|---|
| 트레이스(실행 흐름) | 루트 활동과 입력 로딩, 전문가 실행 활동, 모델 클라이언트 활동이 폭포 모양으로 나열됨 |
| 로그(구조화 이벤트) | 워크플로 시작, 전문가 업데이트, 완료 로그가 Structured logs에 쌓임 |
| 지표 | 실행, 실패, 응답 카운터와 점수, 소요 시간 히스토그램 |
| 평가 | 여덟 개 검사와 80점 기준의 결정론적 구조 점검 |
| 환경별 백엔드 | 로컬은 Aspire Dashboard, 운영은 Azure Monitor나 Grafana |

참고(노트 작성자): 원서 6번 항목의 문장에는 "human in the loop" 앞뒤로 색인 표시 조각이 섞여 추출되어 있었다. 문맥상 "사람이 개입하는 상태로 시작한다"는 뜻으로 복원했다. 또 위 표의 질문 열은 원서 평가 항목의 설명을 우리말로 다시 풀어 쓴 것이다.
