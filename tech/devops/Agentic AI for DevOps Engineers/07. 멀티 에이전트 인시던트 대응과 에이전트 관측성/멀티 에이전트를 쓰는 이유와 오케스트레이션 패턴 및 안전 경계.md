# 멀티 에이전트를 쓰는 이유와 오케스트레이션 패턴 및 안전 경계

이 절은 에이전트 하나로 충분한데도 굳이 여러 에이전트를 나누어 쓰는 이유가 무엇인지, 여러 에이전트를 어떤 순서와 모양으로 엮는지(오케스트레이션, 여러 에이전트의 실행 순서와 결과 취합을 조율하는 일), 그리고 그 과정에서 지켜야 할 안전 경계를 다룬다. 7장의 실습은 모두 이 설계 원칙 위에 서 있으므로 코드를 보기 전에 먼저 이해해 두는 것이 좋다.

원서의 핵심 태도는 한 문장이다. 멀티 에이전트는 "있어 보여서" 쓰는 것이 아니라, 역할을 나누었을 때 실제로 이득이 있을 때만 쓴다. 병원 응급실에 비유하면, 환자 한 명을 의사 한 명이 전부 보는 것보다 접수, 검사, 진단, 처치 담당이 나뉘어 있을 때 빠르고 실수가 적은 것과 같다. 다만 담당이 지나치게 많아지면 서로 떠넘기다 오히려 혼란이 생긴다.

---

## 1. 왜 에이전트를 여러 개로 나누는가

보통은 도구를 가진 에이전트 하나가 기본 선택이다. 그러나 인시던트(서비스 장애나 이상 징후 사건) 분류와 관리 같은 업무는 에이전트 하나가 감당하기에는 컨텍스트(모델이 한 번에 볼 수 있는 입력 범위)가 너무 커질 수 있다. 또 도구와 데이터 소스가 너무 많아지면 서로 엉키는 조율 위험도 커진다. 그래서 인시던트 대응처럼 책임이 자연스럽게 갈라지는 업무에서는 역할별로 지시문을 좁히고, 컨텍스트 창을 작게 하고, 출력을 명확히 하는 편이 낫다.

원서가 예로 든 인시던트 대응의 에이전트 역할은 다섯 가지다.

| 역할 | 하는 일 |
|---|---|
| 인시던트 접수 에이전트 | 경보나 티켓 정보를 정리해 구조화된 인시던트 컨텍스트로 만든다 |
| 증거 에이전트 | 로그, 지표, 트레이스, 배포 이력, 런북(운영 절차서)을 모은다 |
| RCA(근본 원인 분석) 에이전트 | 유력한 결함 영역과 이를 뒷받침하는 증거를 찾는다 |
| 복구 에이전트 | 안전한 다음 조치와 롤백 선택지의 초안을 쓴다 |
| 커뮤니케이션 에이전트 | 상황실이나 이해관계자용 상황 공지를 쓴다 |

이 역할들은 책임이 서로 크게 겹치면 안 된다. 하나를 여럿으로 쪼개는 목적이 전문화이므로, 겹치면 쪼갠 의미가 사라진다.

### 멀티 에이전트가 값어치를 하는 경우

- 인시던트가 서로 다른 전문 영역을 요구할 때다. 예를 들어 분류, 런북 조회, 수정 계획, 위험 검토는 각각 전문가가 있으면 좋다.
- 병렬 처리와 독립적인 교차 점검이 중요할 때다. 에이전트들이 꼭 차례로 돌 필요는 없고, 각자 맡은 일을 동시에 펼친 뒤 하나의 결론으로 모을 수 있다.

이때 결과물은 한 에이전트의 의견이 아니라 구조화된 합의, 즉 각 에이전트의 결과를 묶은 하나의 꾸러미여야 한다.

## 2. 오케스트레이션 패턴 세 가지

| 패턴 | 동작 방식 | 적합한 경우 |
|---|---|---|
| 순차(Sequential) | 에이전트 A가 끝나면 B에게, 다시 C에게 넘기는 통제된 인수인계 | 앞 단계 결과가 뒤 단계의 입력일 때 |
| 병렬(Concurrent) | 여러 에이전트가 동시에 증거를 수집한다 | 서로 독립적인 증거 수집 |
| 하이브리드 팬아웃/팬인 | 독립 전문가들이 동시에 돈 뒤(팬아웃), 결과를 모아(팬인) 조율 에이전트나 결정론적 함수에 넘겨 통제된 종합을 한다 | 전문가 의견을 모아 최종 판단을 만들 때 |

원서가 명시적으로 피하라고 한 것이 있다. 자유 형식의 그룹 채팅(에이전트끼리 정해진 규칙 없이 대화하는 방식)은 긴급한 운영 경로에 쓰지 말라는 것이다. 대신 명시적인 계약(입출력 약속), 구조화된 출력, 그리고 운영 환경을 바꾸거나 영향이 큰 조치 전에 반드시 거치는 사람의 승인 관문을 쓴다.

### 이벤트 트리거와 이벤트 라우터

멀티 에이전트 시스템은 대개 이벤트로 시작한다. 경보나 실패가 트리거(시작 신호)가 된다. 이벤트 라우터는 구독과 필터, 전달과 재시도, 그리고 전달에 실패한 메시지를 따로 보관하는 데드레터링(dead-lettering)을 맡는다. 전달에 실패한 정보가 그냥 사라지지 않고 제대로 처리되도록 하는 장치다.

## 3. 안전 경계와 가드레일

멀티 에이전트도 이 책 전체에서 단일 에이전트에 적용해 온 안전 원칙을 그대로 따른다.

1. 에이전트는 기본적으로 읽기 전용이며, 운영 환경을 스스로 바꿀 자율권이 없다.
2. 운영 변경이나 영향이 큰 조치는 사람이 승인한다. 읽기 전용 증거 수집은 정해진 범위 안에서 자동으로 두어도 된다.
3. 도구 접근과 자격 증명은 역할별로 제한한다.
4. 프롬프트(에이전트에게 주는 지시문), 도구 호출, 출력, 승인, 상관 식별자(correlation identifier, 한 사건에 얽힌 기록을 묶는 ID)를 적절한 보존 기간, 접근 통제, 무결성 보호와 함께 기록해 감사할 수 있게 한다.
5. 각 에이전트에 제한된 타임아웃과 재시도를 두고, 오케스트레이터가 부분 결과, 전달 실패, 사람 운영자에게 올리는 에스컬레이션을 어떻게 처리할지 정의한다.

## 4. 참조 아키텍처

원서 그림 7.1은 이벤트 트리거, 이벤트 라우터, 오케스트레이션 서비스, 전문 에이전트들, 사람 승인 관문으로 구성된 구조를 보여 준다. 글로 풀면 이렇다. 문제가 감지되면 인시던트 워크플로(여러 단계를 정해진 순서로 실행하는 작업 흐름)가 시작된다. 중앙의 오케스트레이션 서비스가 멀티 에이전트 과정을 띄우고, 에이전트들은 모델 추론에 운영 컨텍스트를 결합해 일한다. 결과는 운영 채널로 보내지되, 사람이 승인 관문으로 통제권을 쥔다.

이 그림은 .NET 10, Microsoft Azure, Microsoft Agent Framework를 참조 구현으로 썼지만 구조 자체는 특정 업체에 매이지 않는다. 이벤트 소스, 오케스트레이션 런타임, 모델 제공자, 컨텍스트 저장소, 관측성 백엔드, 운영 채널을 다른 것으로 바꿔도 같은 책임과 안전 경계를 유지하면 된다.

## 5. 이 절의 결론

멀티 에이전트 인시던트 대응은 새로움이 아니라 전문화가 목적이다. 이 시나리오에는 하이브리드 팬아웃/팬인이 어울린다. 전문가들이 증거를 동시에 모아 분석하고, 지휘관(commander) 에이전트가 그 결과를 종합한다. 구조화된 출력, 결정론적 검증, 적절한 사람 승인, 관측성, 감사 가능성은 나중에 덧붙일 것이 아니라 처음부터 설계에 들어가야 할 요구사항이다.
