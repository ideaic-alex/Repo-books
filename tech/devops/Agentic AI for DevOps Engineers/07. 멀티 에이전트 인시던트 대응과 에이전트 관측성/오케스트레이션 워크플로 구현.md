# 오케스트레이션 워크플로 구현

앞에서 만든 샘플 데이터와 프롬프트를 읽어 세 전문가를 동시에 돌리고, 결과를 모아 지휘관 에이전트에게 넘기는 C# 프로그램을 만든다. 파일은 `ai/agents/MultiAgentIncidentResponseWorkflow.cs`이고, 별도의 프로젝트 파일 없이 `dotnet run --file`로 실행하는 .NET 10 파일 기반 앱이다. 완성된 검증본은 원서가 안내하는 Packt 저장소의 `finish/ai/agents/MultiAgentIncidentResponseWorkflow.cs`에 고정되어 있다.

이 코드를 읽는 요령은 흐름을 먼저 잡는 것이다. 설정 읽기, 입력 파일 읽기와 길이 제한, 공유 인시던트 꾸러미 만들기, 프롬프트 불러오기, 전문가 에이전트 생성, 병렬 워크플로 실행, 결과 취합, 지휘관 호출, 결과 검증과 출력이라는 21단계가 위에서 아래로 이어진다. 원서는 이를 번호 붙은 단계로 안내한다. 아래도 같은 순서로 풀어 쓴다.

---

## 1. 준비 단계 (단계 1~4)

1. 파일 맨 위에 패키지 지시문을 넣는다. 대상 프레임워크는 net10.0, Nullable과 ImplicitUsings는 켜고, 경고를 오류로 취급하며, PublishAot는 끈다. 쓰는 패키지는 Azure.AI.OpenAI 2.8.0-beta.1, Azure.Identity 1.13.2, Microsoft.Agents.AI.OpenAI와 Microsoft.Agents.AI.Workflows 1.0.0-rc3, Microsoft.Extensions.AI 10.3.0이다. 일부 패키지는 책을 쓸 당시 프리뷰 버전이었으므로, 업그레이드하고 전체를 다시 시험하기 전에는 참조 코드의 버전을 그대로 유지하라고 원서가 당부한다.
2. 네임스페이스와 Azure OpenAI 설정을 넣는다. 엔드포인트는 `AZURE_OPENAI_ENDPOINT`, 키는 `AZURE_OPENAI_API_KEY` 환경 변수에서 읽고, 없으면 예외를 던진다. 배포 이름은 `AZURE_OPENAI_DEPLOYMENT`가 우선이고 `AZURE_OPENAI_DEPLOYMENT_NAME`도 받으며, 둘 다 없으면 이 비관측 버전에서는 `gpt-4o-mini`가 기본값이다. 취소 토큰은 2분 제한을 둔다.
3. Azure OpenAI 클라이언트를 만들어 `IChatClient`(모델 호출을 추상화한 인터페이스)로 바꾼다. 원서는 현재 Agent Framework 문서가 워크플로에 이 방식을 보여 준다고 설명한다.
4. 인시던트 폴더 위치를 정한다. 첫 번째 실행 인자가 있으면 그 경로를 쓰고, 없으면 finish 디렉터리 기준 `ai/samples/incidents/orderservice-sev2`다.

```csharp
var chatClient = new AzureOpenAIClient(new Uri(endpoint),
    new System.ClientModel.ApiKeyCredential(apiKey))
    .GetChatClient(deploymentName).AsIChatClient();
```

## 2. 입력 읽기와 길이 제한 (단계 5~7)

5. 인시던트 JSON, 파이프라인 로그, 애플리케이션 오류, 서비스 상태, 런북을 비동기로 읽는다. 도우미 `ReadRequiredFileAsync`는 파일이 없으면 모델을 부르기 전에 예외를 던져 워크플로 시작 자체를 막는다. 필요한 입력이 빠진 채로 모델이 추측하게 두지 않으려는 설계다.
6. 모델에 보낼 신뢰할 수 없는 운영 텍스트의 양을 제한한다. 로그와 런북은 20,000자, 상태 JSON은 10,000자까지다.
7. 자르기 도우미 `Truncate`는 한도를 넘으면 앞부분만 남기고 끝에 "데모 안전을 위해 잘림" 표시를 붙인다.

여기서 길이 제한은 비용과 컨텍스트 범위를 통제하는 가드레일(안전 장치)이다. 로그가 수 MB여도 모델에 모두 보내지 않는다.

## 3. 공유 꾸러미와 에이전트 만들기 (단계 8~11)

8. 공유 인시던트 꾸러미를 만든다. 수집한 텍스트를 INCIDENT, PIPELINE LOG, APPLICATION ERRORS, SERVICE HEALTH, RUNBOOK이라는 이름표로 구획을 나눠 하나의 문자열로 이어 붙인다. 세 전문가가 모두 같은 증거를 본다.
9. 프롬프트 폴더(현재 디렉터리 기준 `ai/prompts`)에서 네 개의 프롬프트 파일을 읽어 각각 지시문 변수에 담는다.
10. 전문가 `ChatClientAgent` 세 개를 만든다. 각각 공유 채팅 클라이언트, 자기 프롬프트, 고유한 이름을 받는다. 이름은 PipelineAnalystAgent, AppHealthAgent, RunbookAgent다.
11. `AgentWorkflowBuilder.BuildConcurrent`에 세 에이전트 배열을 넘겨 병렬 워크플로를 만든다.

```csharp
var workflow = AgentWorkflowBuilder.BuildConcurrent(
    [pipelineAgent, appHealthAgent, runbookAgent]);
```

## 4. 실행과 결과 취합 (단계 12~15)

12. 입력 메시지를 만든다. 역할은 user, 내용은 공유 인시던트 꾸러미 한 개다.
13. `InProcessExecution.RunStreamingAsync`로 병렬 워크플로를 같은 프로세스 안에서 실행하고, 스트리밍 이벤트를 켜는 `TurnToken(emitEvents: true)`를 보낸다.
14. 이벤트 스트림을 지켜본다. `AgentResponseUpdateEvent`는 전문가가 쓰는 중간 출력을 콘솔에 찍고, `WorkflowOutputEvent`는 취합된 메시지 목록을 준다. 취합 결과가 비어 있으면 예외로 거부한다.
15. 취합 메시지에서 assistant 역할의 메시지만 뽑아 `GetMessageText`로 글자를 정리하고(빈 것은 제외) 각 전문가의 완성된 결과를 출력한다. `GetMessageText`는 메시지 텍스트를 문자열로 바꿔 앞뒤 공백을 제거하는 작은 도우미다.

세 전문가가 동시에 돌기 때문에 스트리밍 출력이 뒤섞여 보일 수 있고, 실행마다 순서가 다를 수 있다. 이 점은 다음 문서의 실행 결과에서 다시 확인한다.

## 5. 지휘관 호출과 검증 (단계 16~21)

16. 지휘관을 별도의 `ChatClientAgent`로 만든다(이름은 IncidentCommanderAgent). 지휘관이 받는 것은 인시던트 메타데이터와 취합된 전문가 출력뿐이다. 원본 로그를 다시 주지 않으므로 컨텍스트가 작다.
17. 지휘관 프롬프트를 만든다. "인시던트 꾸러미", "전문가 출력들", "최종 구조화 인시던트 대응을 만들라"는 세 덩어리로 구성한다.
18. `RunAsync<IncidentCommanderResult>`로 타입이 정해진 구조화 출력을 요청하고 결과 객체를 꺼낸다.
19. 출력 전에 모든 필수 필드를 검증한다. 이 결정론적 계층이 있어서, 불완전한 지휘관 응답이 성공한 인시던트 꾸러미로 취급되는 일이 막힌다.
20. 검증 도우미 `ValidateCommanderResult`는 내부 함수 `Require`로 일곱 개 필드(IncidentId, ExecutiveSummary, LikelyCause, ImmediateAction, RollbackRecommendation, ValidationPlan, StakeholderMessage)가 비어 있지 않은지 확인하고, 비면 예외를 던진다.
21. 지휘관 결과 타입 `IncidentCommanderResult`를 정의한다. 일곱 개의 문자열 속성을 가진 sealed 클래스이며, 구조화 생성과 결정론적 검증이 같은 타입을 공유한다.

```csharp
ValidateCommanderResult(finalResult);
Console.WriteLine(JsonSerializer.Serialize(finalResult,
    new JsonSerializerOptions { WriteIndented = true }));
```

## 6. 설계에서 챙길 점

| 설계 요소 | 이유 |
|---|---|
| 필수 파일 없으면 즉시 실패 | 입력이 빠진 채 모델이 추측하는 상황 방지 |
| 입력 길이 제한 | 비용, 컨텍스트, 신뢰할 수 없는 텍스트의 양 통제 |
| 병렬 전문가 + 지휘관 | 팬아웃/팬인, 각자 작은 컨텍스트 |
| 타입 결과 + 필수 필드 검증 | 모델 출력을 신뢰하기 전 결정론적 관문 통과 |
| 2분 취소 토큰 | 모델 호출이 멈춰도 워크플로가 무한정 대기하지 않음 |

참고(노트 작성자): 위 표의 "이유" 열은 원서 문장을 그대로 옮긴 것이 아니라, 원서의 코드 주석과 설명에서 읽히는 의도를 노트 작성자가 정리한 것이다. 코드의 일부 줄은 PDF 추출 과정에서 줄 바꿈 위치가 어긋나 있었으나(예: 파일 이름 문자열이 중간에 끊김) 의미는 문맥으로 복원했다.

에이전트 코드가 끝났으므로 다음 문서에서 자격 증명을 설정하고 워크플로를 실행해 본다.
