# 도구와 MCP

메모리가 에이전트에 연속성을 준다면, 도구는 에이전트가 바깥 시스템과 상호작용할 수 있게 하는 능력이다. 언어를 만들어 내는 것만으로는 실제 시스템을 살펴보거나 바꿀 수 없다. 이 문서는 도구가 무엇이고, MCP(Model Context Protocol)가 그 사이에서 무엇을 표준화하며, 무엇은 표준화하지 않는지를 정리한다.

여기서 가장 중요한 구분은 모델이 필요하다고 판단하는 일과 도구가 실행되는 일이 다른 곳에서 일어난다는 점이다. 이 구분이 뒤의 MCP 서버 구축 실습의 설계 이유가 된다.

---

## 1. 도구와 MCP의 정의

도구는 AI 에이전트가 외부 시스템과 상호작용하게 하는 능력이다. MCP는 호환되는 호스트가 MCP 서버가 노출한 도구를 발견하고, 인자를 넣고, 결과를 받는 방식을 표준화한다. 모델이 도구가 필요하다고 판단할 수는 있지만, 도구는 모델 바깥의 애플리케이션 코드에서 실행된다.

비유하면 MCP는 가전제품의 표준 콘센트 규격과 같다. 제품마다 다른 플러그를 만들지 않고 규격을 맞추면, 어떤 제품이든 같은 방식으로 꽂을 수 있다. 하지만 규격이 있다고 해서 전기 안전장치(차단기)까지 규격이 대신해 주는 것은 아니다. 뒤에서 말하듯 인가와 감사는 MCP가 하지 않는다.

## 2. MCP의 가치

MCP는 AI 애플리케이션을 도구와 데이터 소스에 연결하는 일관된 계약을 정의한다. 에이전트마다 별도의 연동 경로를 내장하는 대신, 팀은 승인된 기능을 MCP 서버로 노출하고 호환되는 클라이언트에서 재사용할 수 있다.

DevOps에서 도구가 필요한 예는 PR 파일 조회, 배포 상태 읽기, 텔레메트리 점검, 통제된 워크플로 댓글 게시 등이다. 에이전트가 무엇을 할 수 있는지는 도구의 권한과 구현 경계가 정한다.

## 3. 도구가 늘어나면 생기는 운영 문제

원서가 드는 네 가지 주의점은 다음과 같다.

| 주의점 | 내용 |
|---|---|
| 안정된 계약 | 도구의 입출력 계약이 함부로 바뀌면 안 된다 |
| 정확한 설명 | 도구 설명이 정밀해야 모델이 올바른 도구를 고른다 |
| 최소 권한 | 권한은 "least privilege" 원칙을 따라야 한다 |
| 결과 검증 | 결정론적 워크플로에 영향을 주기 전에 결과를 검증해야 한다 |

또한 서로 겹치는 도구를 너무 많이 노출하면 도구 선택의 신뢰도가 떨어질 수 있다. 앞 장 PR 에이전트가 도구를 세 개만 노출한 이유와 통한다.

## 4. MCP가 표준화하는 것과 하지 않는 것

MCP가 표준화하는 것은 MCP 클라이언트와 서버 사이의 발견과 호출이다. 반대로 MCP는 인가(authorization), 감사(auditing), 검증, 에이전트 간 조율 프로토콜을 대신하지 않는다. 이런 통제는 둘러싼 애플리케이션과 워크플로의 책임으로 남는다.

| MCP가 하는 것 | MCP가 하지 않는 것(애플리케이션의 책임) |
|---|---|
| 도구 발견 | 인가 |
| 인자 전달과 호출 | 감사 |
| 결과 수신 | 입출력 검증 |
| | 에이전트 간 조율 |

이 원칙은 다음 실습에서 적용된다. 일부러 아주 작게 고른 GitHub 작업 몇 개를 로컬 .NET 10 MCP 서버로 노출하는 것이다.

참고(노트 작성자): 5장 요약은 6장이 메모리, MCP, 멀티 에이전트 워크플로, 관측 가능성을 다룬다고 예고하지만, 실제 6장 본문에는 메모리와 MCP만 있다. 멀티 에이전트와 관측 가능성은 7장 도입부(Multi-Agent Incident Response and Agent Observability)에 나온다. 원서 안의 이 불일치는 노트에서 바로잡지 않고 그대로 밝혀 둔다.

## 5. 핵심 정리

- 도구는 에이전트가 외부 시스템과 상호작용하는 능력이고, 모델은 필요 여부만 판단하며 실행은 모델 밖의 코드가 한다.
- MCP는 도구 발견, 인자 전달, 결과 수신의 방식을 표준화해 승인된 기능을 서버로 노출하고 재사용하게 한다.
- 도구가 늘면 계약 안정, 정확한 설명, 최소 권한, 결과 검증이 필요하고, 겹치는 도구가 많으면 선택이 불안해진다.
- MCP는 인가, 감사, 검증, 에이전트 간 조율을 대신하지 않는다. 그것은 애플리케이션과 워크플로의 책임이다.
