# DevOps 에이전트의 메모리

6장은 DevOps 에이전트가 반복되는 워크플로에서 더 쓸모 있어지게 하는 두 가지 능력을 다룬다. 하나는 오래 남는 메모리이고, 다른 하나는 표준화된 도구 접근이다. 이 문서는 첫 번째, 즉 에이전트가 무엇을 기억해야 하고 무엇을 기억하면 안 되는지를 다룬다. 장의 흐름은 메모리 이론, GitHub 이슈를 장부로 쓰는 메모리 실습, MCP(Model Context Protocol, 에이전트가 도구를 찾고 호출하는 표준 규약) 소개, C# MCP 서버 구축, Postman 시험, 기존 PR 품질 에이전트를 MCP에 연결하고 워크플로를 갱신하는 순서다.

실습에 들어가기 전에 로컬 개발 환경, 저장소 설정, 자격 증명, 보조 도구가 갖춰져 있는지 확인해야 한다. 아래에 준비물을 먼저 적는다.

---

## 1. 실습 준비물

이 장의 실습은 원서 저장소(PacktPublishing/Agentic-AI-for-DevOps-Engineers)의 완성 구현을 쓴다. 원서는 강의 가이드 안의 특정 커밋을 가리킨다고 적었으나 커밋 값은 본문에 없다. finish 아래 파일은 참조 구현이며, 워크플로 실습을 따라 할 때는 finish 디렉터리를 작업 샘플 루트로 쓰거나 해당 파일을 작업 저장소 루트로 복사한다.

| 준비물 | 설명 |
|---|---|
| .NET 10 SDK와 C# 편집기 | Visual Studio, C# Dev Kit이 있는 VS Code, JetBrains Rider 중 하나 |
| Git, GitHub 계정, 저장소 | Issues, 풀 리퀘스트(PR), GitHub Actions가 켜져 있어야 함 |
| 앞 장에서 만든 것 | ChatOps 워크플로와 PR 품질 에이전트 |
| Azure OpenAI 리소스와 배포 | AZURE_OPENAI_ENDPOINT, AZURE_OPENAI_API_KEY, AZURE_OPENAI_DEPLOYMENT로 설정 |
| GH_CHATOPS_TOKEN 시크릿 | 메모리를 쓰는 ChatOps 워크플로가 PR을 읽고 이슈 댓글을 쓰는 권한 |
| PR_ANALYSIS_TOKEN 시크릿 | MCP 조회용 PR 읽기 권한. 통제된 댓글 도구를 시험할 때만 이슈 쓰기 권한을 추가 |
| 저장소 변수 | CHATOPS_MEMORY_ISSUE_NUMBER, CHATOPS_MEMORY_MAX_CHARS, CHATOPS_MEMORY_MAX_ITEMS |
| Postman | 로컬 stdio 서버를 시험하려면 MCP 요청을 지원하는 버전 |
| jq | GitHub 호스티드 Ubuntu 러너에는 포함. 로컬 실행은 따로 설치 |

참고(노트 작성자): 시크릿과 토큰의 값은 이 노트에 적지 않는다. 이름만 쓴다.

## 2. 왜 메모리가 필요한가

메모리가 없으면 DevOps 에이전트는 이전 실패를 추적하지 못하고, 반복되는 패턴을 알아채지 못하며, 이슈를 지능적으로 상향(escalation)하지 못한다. 메모리가 있으면 맥락 유지, 추세 분석, 더 나은 상향 결정이 가능하다. 앞 문서에서 본 에이전트 구성 요소 중 메모리 부품을 이 장에서 구체화하는 셈이다.

## 3. DevOps에 쓰이는 메모리의 종류

에이전트 시스템에는 여러 종류의 메모리가 있지만 DevOps 작업은 그중 일부를 쓴다.

| 종류 | 담는 것 |
|---|---|
| 단기 메모리 | 대화 맥락, 현재 작업 세부 정보, 임시 추론 상태 |
| 장기 메모리 | 과거 상호작용, 사실, 시스템 지식, 조직 정책 |
| 이벤트 기반 메모리 | 시스템의 이벤트, 관측 신호, 시스템의 동작과 결과 |

세 번째 이벤트 기반 메모리는 시스템 안에서 무슨 일이 있었는지의 믿을 만한 기록이 되기 때문에 특히 중요하다고 원서는 강조한다. 원서의 그림 6.1은 네 가지 범주를 나란히 비교한다. 여기서 네 번째는 앞의 세 종류에 더해 워크플로 진행 상태(이미 수행한 조사 단계)까지 포함한 것으로 읽힌다. 이 구분은 원서 본문의 서술과 그림 설명을 합쳐 복원한 것이다. 그림이 말하는 요점은 오래 남는 메모리는 에이전트 맥락의 한 측면일 뿐이고, 짧게 사는 작업 상태, 과거 지식, 시스템 이벤트, 워크플로 진행이 각각 다른 기능을 하므로 달리 관리해야 한다는 것이다. 어느 맥락이든 오래 남게 되면 출처(provenance), 검증, 보존 기간, 삭제 문제를 저장 방식이 함께 고려해야 한다.

## 4. 무엇을 저장하고 무엇을 피하나

메모리 종류를 아는 것은 첫 단계일 뿐이다. 더 중요한 운영상 결정은 어떤 정보가 오래 남길 만큼 믿을 만하고, 어떤 정보가 보안, 개인정보, 신뢰성 위험을 부를지 가려내는 일이다.

### 4-1. 저장할 만한 것

- 운영 지식: 배포 절차나 인프라 구성 같은 것.
- 시스템 이벤트: 빌드 실패, 배포 결과, 인시던트 알림. 자동화와 문제 해결에 쓸 과거 맥락이 된다.
- 관측 데이터의 검증된 요약, 또는 원본 로그, 지표, 트레이스에 대한 참조. 제한 없는 원본 텔레메트리를 오래 남는 메모리에 복사하면 안 된다.
- 워크플로 맥락: 조사에서 이미 수행한 단계. 같은 동작의 반복을 피하고 해결로 더 효율적으로 나아가게 돕는다.

### 4-2. 저장하면 안 되는 것

- 민감한 데이터, 자격 증명, 비밀 값, 개인 식별 정보(PII).
- 임시 추론 과정: 즉석의 사고 연쇄(chain of thought)나 비공개 프롬프트 맥락.
- 검증되지 않은 모델 출력. AI 응답에는 환각이 들어 있을 수 있고, 검증 없이 보관하면 메모리 저장소가 오염된다.

## 5. 운영용 메모리의 안전장치

다음 실습의 GitHub 이슈 장부는 일부러 가볍게 만든 것이라 개념 시연에는 적합하지만, 운영용 메모리 저장소에는 더 많은 통제가 필요하다. 원서가 꼽는 통제는 출처, 검증, 범위, 보존, 삭제, 중복 제거, 동시 쓰기다. 보관하는 각 항목은 어디서 왔는지, 언제 저장됐는지, 검증됐는지를 밝혀야 한다. 오래 남는 메모리에는 로그나 모델 응답의 무제한 복사본이 아니라 간결하고 재사용할 수 있는 사실이나 관례를 담는다.

비유하면 팀 위키에 올릴 글과 같다. 회의 중 오간 잡담이나 확인되지 않은 추측이 아니라, 출처가 있고 검토된 규칙만 올려야 나중에 위키를 믿을 수 있다.

## 6. 안전장치에서 실습으로

위 안전장치는 무엇이 오래 남는 메모리에 들어갈 수 있는지를 정한다. 다음 문서의 실습은 이 원칙을 워크플로로 바꾼다. 응답하기 전에 승인된 항목을 읽고, 쓰기 전에 제안된 항목을 검증한다.

## 7. 핵심 정리

- 메모리가 없으면 반복 패턴 감지와 지능적 상향이 안 된다.
- DevOps가 쓰는 메모리는 단기, 장기, 이벤트 기반이며, 워크플로 진행 상태도 따로 관리할 대상이다.
- 저장할 것은 운영 지식, 시스템 이벤트, 검증된 요약이나 참조, 워크플로 맥락이다.
- 비밀과 PII, 임시 추론, 검증되지 않은 모델 출력은 저장하지 않는다.
- 운영용에는 출처, 검증, 범위, 보존, 삭제, 중복 제거, 동시 쓰기 통제가 필요하고, 각 항목에 출처와 저장 시각과 검증 여부를 남긴다.
- 원서에서 그림은 싣지 않았다. 그림 6.1의 내용은 본문 설명으로 대신했다.
