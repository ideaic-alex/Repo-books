# Postman으로 MCP 서버 시험

서버를 에이전트에 연결하기 전에, Postman이 MCP 도구를 발견하고, 인자를 넘기고, 로컬 stdio 전송으로 GitHub API 응답을 받을 수 있는지 따로 확인한다. 빌드 성공은 서버가 컴파일된다는 뜻일 뿐이고, 클라이언트가 서버를 실행하고 도구를 찾아 인자를 묶고 응답을 받는 것까지는 보장하지 않는다. 이 시험은 그 프로토콜 동작을 에이전트와 분리해 확인하는 단계다.

Postman은 로컬 서버 프로세스를 직접 시작하고, MCP 세션을 협상하고, 발견된 도구를 나열하고, 형식이 있는 인자로 각 도구를 부를 수 있는 입력 양식을 제공한다.

---

## 1. Postman에 stdio MCP 서버 연결하기

단계는 원서 번호를 따랐다.

1. postman.com에서 Postman을 내려받고 계정을 만든다.
2. 새 워크스페이스를 만든다. 예를 들어 이름은 MCP testing이다. MCP 테스트 자산을 관련 없는 API 컬렉션과 분리하려는 전용 워크스페이스다.
3. 새 MCP 요청을 만든다. 요청 유형 아이콘이 기본적으로 HTTP라면 눌러서 MCP로 바꾼다. 이 전환이 Postman이 일반 HTTP 요청을 보내는 대신 MCP를 협상하게 만든다.
4. 전송 방식으로 표준 입력/출력(stdio)을 고르고 stdio 명령을 설정한다.
   - Windows에서는 생성된 앱 호스트 mcp/DevOps.McpServer/bin/Debug/net10.0/DevOps.McpServer.exe를 쓴다.
   - macOS나 Linux에서는 .exe 접미사 없는 같은 이름의 DevOps.McpServer 앱 호스트를 쓴다.
   - 클라이언트가 명령과 인자 칸을 따로 지원하면, 명령은 dotnet, 인자는 DevOps.McpServer.dll의 절대 경로로 넣어도 유효하다.
5. 환경 변수 PR_ANALYSIS_TOKEN을 추가하고 PR 읽기 권한이 있는 GitHub 토큰을 넣는다(`<GitHub 토큰>`). 이름이 GITHUB_로 시작하지 않는 이유는, GITHUB_ 접두어가 GitHub Actions의 기본 제공 변수 이름에 예약되어 있어서 사용자 정의 MCP 서버 토큰은 일관되게 PR_ANALYSIS_TOKEN으로 부르기 때문이다.
6. Connect를 누르고 요청이 나오면 접근을 허용한다. 이것은 로컬 프로세스에 대한 명시적 신뢰 결정이다. stdio 접근을 허락하면 Postman이 서버를 실행할 수 있게 되므로, 승인하기 전에 명령 경로와 환경 변수를 검토해야 한다. 터미널 창이 뜰 수 있고, 서버가 제공하는 도구들이 화면에 나타나야 한다.
7. github_get_pull_request 도구를 시험한다. owner, 저장소 이름, PR 번호를 넣고 실행하면 GitHub API의 JSON 응답이 돌아온다. 도구가 동작하며 GitHub와 올바르게 통신한다는 확인이다.
8. 잘못된 PR 번호나 잘못된 토큰으로 다시 호출해, 서버가 실행 가능한 GitHub API 오류를 돌려주는지 확인한다. 실패가 조용히 모델의 맥락으로 바뀌지 않고 MCP 클라이언트에 드러나는지를 검증하는 것이다.

원서의 그림 6.7부터 6.10은 전용 워크스페이스, 요청 유형 전환, stdio 전송 선택, 명령과 환경 변수 설정, 호출 결과 JSON을 보여 준다. 마지막 그림은 도구 발견, 인자 바인딩, GitHub 인증, JSON 결과 처리가 함께 동작한다는 증거다. 스크린샷은 싣지 않고 글로 풀었다.

## 2. 시험의 단계별 확인 항목

| 확인 | 기대 결과 | 무엇을 검증하나 |
|---|---|---|
| Connect | 터미널이 뜨고 도구 목록이 보임 | 서버 실행과 MCP 세션 협상, 도구 발견 |
| github_get_pull_request 호출 | GitHub의 PR JSON 응답 | 인자 바인딩, GitHub 인증, JSON 결과 처리 |
| 잘못된 번호 또는 토큰 | 상태 코드와 본문이 담긴 오류 | 실패가 클라이언트에 드러나는지 |

## 3. 연결 문제 해결

공백이 들어 있는 경로는 MCP가 금지하지 않는다. 연결 실패는 클라이언트가 명령과 인자를 따옴표 없는 하나의 문자열로 취급할 때 일어난다. 해결 방법은 두 가지다. 앱 호스트 경로를 하나의 명령 값으로 쓰거나, dotnet과 DLL 경로를 각각 명령 값과 인자 값으로 따로 설정한다. 또한 사용 중인 서버 실행 파일을 다시 빌드하려면 먼저 활성 Postman 세션의 연결을 끊어야 한다.

참고(노트 작성자): 마지막 주의는 Windows에서 실행 중인 파일은 덮어쓸 수 없다는 일반 상식과 맞는다. 원서는 이유를 설명하지 않았다.

## 4. 다음 단계

서버가 독립적인 MCP 엔드포인트로 검증되면, 이를 에이전트의 직접 PR 데이터 로딩 경로를 대체하는 데 쓸 수 있다. 이 분리는 결합도를 낮추고 같은 GitHub 도구를 다른 호환 클라이언트도 재사용하게 해 준다. 다음 문서에서 PR 품질 에이전트를 MCP 도구에 연결한다.

## 5. 핵심 정리

- Postman을 MCP 요청으로 바꾸고 전송을 stdio로 골라, 앱 호스트 경로 또는 dotnet과 DLL 경로로 서버를 띄운다.
- 환경 변수는 PR_ANALYSIS_TOKEN. GITHUB_ 접두어는 Actions 예약어라 쓰지 않는다.
- Connect 때의 접근 허용은 로컬 프로세스 실행에 대한 신뢰 결정이므로 명령과 환경 변수를 먼저 확인한다.
- 정상 호출과 잘못된 번호나 토큰 호출을 둘 다 해서, 도구 발견과 인자 바인딩과 인증과 오류 전달을 확인한다.
- 경로의 공백은 클라이언트의 인자 처리 문제로 이해하고, 재빌드 전에는 세션 연결을 끊는다.
