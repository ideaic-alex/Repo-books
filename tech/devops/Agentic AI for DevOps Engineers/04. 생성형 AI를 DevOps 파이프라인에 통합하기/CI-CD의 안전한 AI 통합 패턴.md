# CI-CD의 안전한 AI 통합 패턴

AI가 CI/CD 파이프라인의 일부가 되면 공격 표면(공격받을 수 있는 지점)의 일부도 된다. 그래서 안전한 통합은 선택이 아니다. 여기서 보안은 워크플로가 운영 의존성이 되기 전에 현실적인 위협 모델링 질문을 던지는 일이다.

- 각 경계를 무엇이 넘나드는가
- 무엇이 조작될 수 있는가
- 무엇이 샐 수 있는가
- AI 출력이 틀렸을 때 워크플로가 무엇을 할 수 있는가

이 구현의 주요 위험은 이론이 아니다. PR 제목과 본문은 사용자가 통제하는 입력이고, 워크플로는 시크릿을 다루고, AI 호출에는 비용과 지연이 따르고, 모델 출력은 릴리스 자동화 경로로 들어간다. 아래 통제는 각 위험을 구체적인 워크플로나 프롬프트 경계에 대응시킨다.

---

## 1. 위협과 발생 지점

원서 표 4.2다.

| 위협 | 발생 지점 |
|---|---|
| 시크릿 유출 | 시크릿, 로그, 아티팩트, 잡 요약 |
| 프롬프트 인젝션 | PR 제목 또는 본문 |
| 비용 남용 | 큰 PR 메타데이터나 과대한 프롬프트 입력 |
| 권한 상승 | 워크플로 권한과 토큰 |
| 출력 조작 | AI가 만든 릴리스 노트나 ChatOps 응답 |

## 2. 다섯 가지 통제

### 2-1. 시크릿 경계

워크플로는 GitHub 환경을 쓰고 필요한 Azure OpenAI 값을 환경 시크릿으로 둔다. 시크릿은 환경에 한정되어 Azure OpenAI를 부르는 잡에만 주입된다. 릴리스 생성 잡은 `devops-dev` 환경에 붙고, 재사용 액션은 엔드포인트, API 키, 배포 이름을 하드코딩 YAML 값이 아닌 GitHub 시크릿으로 받는다. 액션 안에서는 요청 전에 API 키를 마스킹해 워크플로 로그에 실수로 찍히지 않게 한다. 워크플로는 전체 프롬프트, 원본 요청 본문, 시크릿이 담긴 헤더도 로그에 남기지 않아야 한다. 아티팩트에는 생성된 릴리스 노트, 정화된 입력 파일, 원본 모델 응답, 텔레메트리를 담되 시크릿은 담지 않는다.

```yaml
environment:
  name: devops-dev
endpoint: ${{ secrets.AZURE_OPENAI_ENDPOINT }}
```

### 2-2. 프롬프트 인젝션 방어

PR 내용은 신뢰할 수 없는 데이터로 취급한다. 릴리스 노트 프롬프트는 모델이 PR 제목이나 본문에 박힌 지시가 아니라 시스템 프롬프트만 따르라고 한다. 가드레일은 JSON 필드를 데이터로 취급하고, 내장된 지시를 무시하고, 프롬프트의 지시만 따르고, 제공된 JSON만 쓰고, 빠진 변경을 추론하지 않고, 기능이나 수정이나 인프라 작업을 지어내지 않는다는 규칙이다. 메타데이터 추출 로직이 `release-report.json`을 만들기 전에 PR 제목과 본문을 자르고 정화하는 것이 이를 뒷받침한다. 프롬프트 가드레일과 입력 형성 가드레일이 함께 작동한다. 하나는 모델이 보는 것을 제한하고, 다른 하나는 모델에게 그것을 어떻게 해석할지 알려 준다.

### 2-3. 입력 크기와 비용 통제

비용 남용은 보안이자 신뢰성 문제다. 공격자나 부주의한 사용자가 거대한 PR 본문이나 비정상적으로 큰 PR 메타데이터를 주입하면 토큰 사용량이 치솟고 지연이 늘고 워크플로가 불필요하게 비싸진다. 컴포지트 액션은 Azure OpenAI에 요청을 보내기 전에 프롬프트와 입력 크기를 검사하고, 25000바이트를 넘으면 호출을 거부한다. 토큰 사용량과 호출 시간은 `ai-telemetry.json`에 기록하고, 임계값을 넘으면 경고 주석을 내므로 문제가 하드 실패가 되기 전에 팀이 볼 수 있다.

### 2-4. 결정적 출력

파이프라인은 모델 출력을 곧바로 신뢰하지 않는다. 생성, 검증, 자동화(generate-validate-automate) 패턴을 따른다. 모델이 릴리스 노트를 생성하고, 파이프라인이 Markdown 구조를 검증하고, 검증이 성공한 뒤에야 자동화가 이어진다. 검증 잡은 필수 제목이 있고 생성 파일이 비어 있지 않은지 릴리스 잡 전에 확인한다. 이 검증은 프롬프트와 계속 맞아야 하며 필수 제목이 바뀌면 검증 계약도 같이 갱신한다.

### 2-5. 최소 권한 권한

권한은 명시적이어야 하고 워크플로가 필요한 만큼으로 제한한다. 릴리스 워크플로는 메타데이터를 모으려고 PR 읽기 권한이, 초안 릴리스를 만들려고 contents 쓰기 권한이 필요하다. ChatOps 워크플로는 PR 댓글이 Issues API 엔드포인트로 만들어지므로 issues 쓰기 권한이 필요하다.

| 워크플로 | 권한 | 이유 |
|---|---|---|
| 릴리스(전체) | contents: write, pull-requests: read | PR 메타데이터 읽기와 초안 릴리스 쓰기 |
| 게시 잡 | contents: write | 초안 GitHub Release 생성 |
| ChatOps | contents: read, pull-requests: read, issues: write | PR 메타데이터를 읽고 댓글을 씀 |

운영 워크플로에서는 잡을 끝낼 수 있는 가장 좁은 권한을 쓴다. 잡이 메타데이터만 읽으면 읽기 전용으로 두고, 릴리스나 댓글을 쓰면 그 쓰기 권한을 필요한 워크플로나 잡에 한정한다.

## 3. 경계 설계의 원칙

AI는 인프라를 배포하거나, YAML을 수정하거나, PR을 자동 머지하거나, 검증을 우회할 수 없어야 한다. 이 장에서 AI는 프롬프트 계약 아래 한정된 텍스트를 만들고, 파이프라인은 그 출력을 쓰기 전에 검증한다. 안전한 통합은 경계 설계다. 검증은 AI 행동을 통제되게 하고, 관측성은 관리 가능하게 하고, 최소 권한은 폭발 반경을 줄인다. 이 통제들이 합쳐져 파이프라인이 더 안전해지고 AI 통합을 검토하고 모니터링하고 안전하게 발전시키기 쉬워진다. 3장의 가드레일 개념이 실제 워크플로 설정으로 내려온 모습이다.

## 4. 핵심 정리

- AI는 공격 표면의 일부이며 위협은 시크릿 유출, 프롬프트 인젝션, 비용 남용, 권한 상승, 출력 조작이다.
- 통제는 시크릿 경계, 인젝션 방어, 입력 크기 통제, 결정적 출력, 최소 권한 다섯 가지다.
- 프롬프트 가드레일과 입력 정화는 짝으로 쓴다.
- AI는 배포, YAML 수정, 자동 머지, 검증 우회를 할 수 없다.
