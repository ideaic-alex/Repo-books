# AI 비용과 성능 관리

이제 파이프라인은 AI가 만든 릴리스 노트를 생성하고 검증할 수 있다. 다음 관심사는 모델을 꼭 필요할 때만 부르는지, 일시적인 API 실패를 책임 있게 다루는지, 토큰 소비를 기록하는지, 실행 뒤 비용과 성능을 검토할 만큼 텔레메트리(실행 중 수집한 측정 기록)를 남기는지다. 이 문서는 비용, 성능, 신뢰성을 챙기는 개선을 다룬다.

완성된 워크플로는 불필요한 AI 호출 건너뛰기, 재시도와 지수 백오프(exponential backoff, 실패할 때마다 대기 시간을 두 배로 늘리는 방식), 호출 시간 추적, 토큰 사용량 추출, `ai-telemetry.json` 작성, 그 파일을 워크플로 아티팩트로 업로드하는 것으로 이 문제를 해결한다.

---

## 1. 실습 단계

### 1-1. 단계 1: PR이 없으면 AI 호출 건너뛰기

릴리스 워크플로는 main으로 푸시될 때 돌기 때문에, 직접 푸시에는 머지된 PR 메타데이터가 없을 수 있다. 요약할 머지된 PR이 없으면 AI 호출을 건너뛰어야 한다. 순서는 세 가지다.

1. 메타데이터 수집 스크립트에서 `release-report.json`의 PR 개수를 계산해 `pr_count` 출력으로 내보낸다.
2. 같은 값을 잡 출력으로도 노출해 하위 잡이 실행 여부를 판단하게 한다.
3. AI 생성 잡에 `if: needs.collect-metadata.outputs.pr_count != '0'`를 건다. 릴리스 보고서에 PR이 적어도 하나 있을 때만 돈다.

```javascript
const prCount = report.pull_requests.length;
core.setOutput('pr_count', String(prCount));
```

단순하지만 효과적인 비용 통제다. 모델이 처리할 PR 메타데이터가 없을 때 빈 요청이나 가치 낮은 요청을 Azure OpenAI에 보내지 않는다.

### 1-2. 단계 2: 재시도와 백오프 추가

`action.yml`에서 HTTP 호출 부분을 다듬는다. 외부 서비스는 속도 제한, 일시적 네트워크 오류, 서비스 쪽 5xx 응답 같은 일시적 실패를 낼 수 있고, 일시적 실패가 곧 워크플로 즉시 실패를 뜻하지는 않는다. 너무 공격적으로 재시도하지 않으면서 AI 호출 성공 확률을 높이도록 재시도와 백오프 로직을 넣는다. 루프 앞에서 재시도 설정을 정의한다. 최대 재시도 3회(`MAX_RETRIES=3`), 현재 시도 1(`ATTEMPT=1`), 대기 2초(`SLEEP_SECONDS=2`)다. HTTP 호출은 루프 안에 둔다. 매 시도마다 시작 시각을 기록하고, 요청을 보내고, 종료 시각을 기록하고, 소요 시간을 계산해 로그에 남긴다.

### 1-3. 단계 3: 성공, 실패, 재시도 처리

루프 안에서 액션은 성공, 최종 실패, 재시도의 세 결과를 처리한다.

| 상황 | 동작 |
|---|---|
| 2xx 응답(성공) | 루프를 빠져나간다(break) |
| 마지막 시도에서도 실패 | 실패 메시지와 응답 JSON을 찍고 액션을 종료한다 |
| 그 밖의 실패 | 대기하고, 시도 번호를 올리고, 대기 시간을 두 배로 늘려 다시 시도한다 |

이 조정으로 워크플로는 호출 시간을 추적하고, 실패한 호출을 재시도하고, 짧은 시간에 너무 공격적으로 재시도하지 않는다. 설정한 재시도 한도 뒤에도 실패하게 두므로 진짜 실패는 눈에 보인다. 이 설정이면 대기가 2초, 4초로 늘어난다(참고(노트 작성자): 최대 3회 시도이면 대기는 두 번 일어나므로 코드의 값에서 계산한 것이다).

### 1-4. 단계 4: 토큰 소비 추적

다음으로 추적할 지표는 토큰 소비다. Azure OpenAI 응답에는 사용량 정보가 들어 있다. 컴포지트 액션은 `jq`로 응답의 `.usage`에서 프롬프트 토큰, 완성 토큰, 총 토큰을 읽어 파이프라인 출력에 기록한다. 이 값은 모델에 얼마나 많은 맥락을 보내고 응답이 얼마나 큰지 팀이 이해하게 돕는다. 프롬프트 크기, 입력 크기, 릴리스 양이 늘 때 비용 회귀를 찾기도 쉬워진다.

### 1-5. 단계 5: 텔레메트리 아티팩트

`ai-telemetry.json`이라는 파일을 만든다. 기록 항목은 타임스탬프, 프롬프트 크기, 입력 크기, 호출 시간, HTTP 상태, 토큰 정보다. 이 파일은 `release-output` 아티팩트에 입력 보고서, 생성된 릴리스 노트, 원본 Azure OpenAI 응답과 함께 넣고, 별도로 `ai-telemetry`라는 아티팩트로도 올려 나머지 릴리스 출력과 따로 내려받을 수 있게 한다. 이렇게 하면 생성된 릴리스 산출물과 모델 사용량, 지연, 응답 행동을 이해하는 데 쓰는 운영 텔레메트리가 분리된다.

### 1-6. 단계 6: 검증과 게시 잡에도 조건

PR이 없으면 검증하거나 게시할 생성 출력도 없으므로 검증 잡과 게시 잡에도 조건이 필요하다. 검증 잡은 수집 잡과 생성 잡에 의존하고 `pr_count`가 0이 아닐 때만 돈다. 게시 잡은 수집 잡과 검증 잡에 의존하고 역시 `pr_count`가 0이 아닐 때만 돈다. 이렇게 main에 직접 푸시된 경우를 처리한다. 직접 푸시 테스트에서는 워크플로가 머지된 PR 0건의 보고서를 쓰고, AI 생성 잡을 건너뛰고, 불필요한 검증과 릴리스 게시를 피한다.

### 1-7. 단계 7: PR로 전체 흐름 테스트

`feature/testing-costing` 브랜치를 만들고 `Program.cs`에 작은 코드 변경을 한다. 커밋하고 푸시한 뒤 PR을 만들고, Copilot으로 PR 요약을 생성한 다음 검사가 통과하면 머지한다. 이번에는 보고할 PR이 하나 이상 있으므로 릴리스 노트 생성 잡이 돌고, 재시도 로직이 유지되고, 토큰 사용량이 기록되고, 텔레메트리 아티팩트가 만들어지고, AI 출력이 검증되고, 초안 릴리스가 게시된다. 워크플로 실행에는 세 아티팩트가 나타난다. AI 텔레메트리, 릴리스 입력, 릴리스 출력이다.

## 2. 결과

이 변경들은 비용 절감 조치를 넣고 AI 호출마다 더 많은 정보를 준다. 파이프라인은 불필요한 모델 호출을 피하고, 일시적 실패를 책임 있게 재시도하고, 모델 사용량을 기록하고, 나중에 검토할 텔레메트리를 보존한다.

## 3. 핵심 정리

- 비용 통제의 첫걸음은 처리할 PR이 없으면 AI 잡을 건너뛰는 pr_count 조건이다.
- 재시도는 최대 3회, 대기 2초에서 시작해 두 배씩 늘리며 한도 뒤에는 실패시킨다.
- 응답의 usage에서 프롬프트, 완성, 총 토큰을 읽어 기록한다.
- ai-telemetry.json은 release-output과 별도 ai-telemetry 아티팩트로 올린다.
- 검증과 게시 잡에도 같은 pr_count 조건을 건다.
