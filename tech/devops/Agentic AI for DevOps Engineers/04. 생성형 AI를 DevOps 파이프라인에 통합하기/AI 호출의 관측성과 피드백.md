# AI 호출의 관측성과 피드백

파이프라인은 이미 텔레메트리를 `ai-telemetry.json`에 쓴다. 감사와 문제 해결에 유용하지만, 워크플로가 끝난 뒤 누군가 파일을 내려받아야 한다는 한계가 있다. 이번 개선은 같은 텔레메트리를 컴포지트 액션의 출력으로 노출하고, 그 출력으로 경고(warning)와 GitHub Actions 잡 요약(job summary)을 보여 준다.

이렇게 하면 Azure OpenAI 호출이 관찰 가능한 파이프라인 의존성이 된다. 워크플로는 모델 호출이 성공했는지, 얼마나 걸렸는지, 토큰을 얼마나 썼는지를 원본 응답 파일을 열어 보지 않고도 보여 줄 수 있다.

---

## 1. 실습 단계

### 1-1. 단계 1: 액션 출력 확장

`.github/azure-openai-chat/action.yml`의 출력을 늘린다. 이전에는 응답 경로, 출력 경로, HTTP 상태만 노출했다. 관측성을 위해 호출 시간과 토큰 사용량도 노출해야 호출하는 워크플로가 읽을 수 있다. 추가하거나 확인할 출력은 `duration_seconds`, `total_tokens`, `prompt_tokens`, `completion_tokens`이며(기존의 `response_path`, `output_path`, `http_status` 포함 모두 일곱 개) 각 값은 `steps.call.outputs.*`에서 온다.

### 1-2. 단계 2: GITHUB_OUTPUT에 기록

액션의 API 호출 부분에서 토큰 값을 응답에서 뽑은 뒤 `$GITHUB_OUTPUT`에 값을 쓴다. 이 줄들이 `release-ai.yml`에서 재사용 액션 단계를 통해 값을 읽게 해 준다.

```bash
echo "duration_seconds=${DURATION}" >> "$GITHUB_OUTPUT"
echo "total_tokens=${TOTAL_TOKENS}" >> "$GITHUB_OUTPUT"
```

### 1-3. 단계 3: 단계 ID 확인

`release-ai.yml`의 생성 잡에서 재사용 액션 단계의 ID가 `aoai`인지 확인한다. 이후 단계가 `steps.aoai.outputs`에서 값을 읽기 때문이다. ID가 바뀌면 경고와 요약 단계도 맞춰 고쳐야 한다.

### 1-4. 단계 4: 예산과 성능 경고

새 단계 이름은 AI budget + performance warnings다. 총 토큰과 호출 시간에 소프트 임계값(soft threshold, 넘어도 실패시키지 않고 알리기만 하는 기준)을 쓴다. 빌드를 실패시키지 않고 경고만 하므로 하드 게이트를 적용하기 전의 초기 모니터링에 유용하다. `if: always()`로 앞 단계 결과와 상관없이 돌고, 예제 임계값은 `MAX_TOKENS=2000`, `MAX_DURATION=10`(초)이며 조직마다 조정한다. 동작은 이렇다.

1. 총 토큰과 호출 시간을 읽어 출력한다.
2. 어떤 이유로든 출력이 비어 있으면 `::warning::AI telemetry outputs missing`을 내고 파이프라인은 실패시키지 않고 끝낸다.
3. 토큰이 소프트 예산을 넘으면 메타데이터 크기를 줄이거나 자르기를 조이라는 경고를 낸다.
4. 호출 시간이 임계값을 넘으면 지연 회귀 가능성 경고를 낸다.

경고는 싸고 신호가 강하다. 배포를 막지 않으면서 비용과 지연 문제를 부각한다. 조직이 예산이나 성능을 더 엄격히 강제하려면 나중에 이 경고를 하드 게이트로 바꿀 수 있다.

### 1-5. 단계 5: 텔레메트리 요약 게시

AI 호출 내용을 GitHub Actions 잡 요약에 쓰는 단계를 하나 더 추가해 워크플로 실행 화면에서 바로 보이게 한다. 요약 제목은 AI Telemetry Summary이며 HTTP 상태, 소요 시간(초), 총 토큰, 프롬프트 토큰, 완성 토큰을 불릿으로 적고 "경고가 보이면 자르기나 임계값을 조정하라"는 메모를 붙인다. 내용은 `$GITHUB_STEP_SUMMARY` 파일에 쓴다. 이 단계도 `if: always()`다.

### 1-6. 단계 6: 테스트와 http_status 누락 수정

`feature/add-observability` 브랜치를 만들고 커밋과 푸시 후 PR을 만들어 검사가 통과하면 머지한다. 워크플로가 호출에 걸린 시간과 소비된 토큰을 보여 주는 미니 보고서를 출력한다.

첫 실행에서는 요약에 HTTP 상태가 빠져 있을 수 있다. 컴포지트 액션이 `http_status` 출력을 선언만 하고 `$GITHUB_OUTPUT`에 값을 쓰지 않으면 그렇게 된다. `action.yml`에서 `http_code` 변수의 값을 `echo "http_status=${http_code}" >> "$GITHUB_OUTPUT"`으로 써서 고친다. 워크플로를 다시 돌리면 요약이 HTTP 상태 코드를 올바르게 출력한다.

## 2. 결과

AI가 관찰 가능한 의존성이 된다. 파이프라인은 AI 통합이 동작하는지, 모델 호출이 얼마나 걸렸는지, 토큰이 얼마나 소비됐는지, 사용량이나 지연이 설정한 경고 임계값을 넘었는지를 보여 줄 수 있다. 결과적으로 이 워크플로는 AI를 부르는 데 그치지 않고, 엔지니어링 팀이 시간이 지나며 이 의존성을 모니터링하고 조정할 만한 텔레메트리를 만들어 낸다. 이것이 이 장이 말하는 피드백이다. 측정하고, 보여 주고, 임계값과 자르기를 다듬는 순환이다.

| 장치 | 보여 주는 것 | 실패 여부 |
|---|---|---|
| 액션 출력 | 호출 시간, 토큰, 상태를 다음 단계에 전달 | 해당 없음 |
| 경고 주석 | 예산 초과, 지연 초과 | 빌드를 막지 않음(소프트) |
| 잡 요약 | 한눈에 보는 호출 기록 | 해당 없음 |

## 3. 핵심 정리

- 텔레메트리를 파일에만 두지 않고 액션 출력, 경고, 잡 요약으로 노출한다.
- 단계 ID aoai가 후속 단계의 참조 기준이므로 바꾸면 함께 수정한다.
- 소프트 임계값(토큰 2000, 10초 예)은 경고만 하고 나중에 하드 게이트로 올릴 수 있다.
- 출력을 선언만 하고 GITHUB_OUTPUT에 쓰지 않으면 값이 비는데, http_status가 그 사례였다.
