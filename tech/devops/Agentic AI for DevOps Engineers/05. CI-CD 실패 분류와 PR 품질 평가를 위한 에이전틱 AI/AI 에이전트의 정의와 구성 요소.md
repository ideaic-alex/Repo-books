# AI 에이전트의 정의와 구성 요소

5장은 에이전틱 AI(스스로 판단하고 도구를 써서 목표를 이루는 AI)를 DevOps에 적용하는 첫 단계다. 핵심 원칙은 범위를 좁게 정한 에이전트를 CI/CD 워크플로 안에서 쓰되, 코드와 배포와 운영 시스템에 대한 무제한 권한은 주지 않는다는 것이다. 이 문서는 에이전트가 무엇이고 어떤 부품으로 이루어지는지, 그리고 실습을 따라 하려면 무엇이 필요한지 정리한다.

이 장이 노리는 것은 DevOps 엔지니어를 대체하는 일이 아니다. 사람이 직접 조사하는 수고를 줄이면서도 사람의 검토, 검증, 거버넌스(통제와 책임 체계)는 그대로 두는 것이다. 장은 두 가지 안전한 자동화 패턴, 즉 CI 로그로 하는 실패 분류와 코드 변경으로 하는 풀 리퀘스트(PR) 품질 평가를 만든다.

## 1. 이 장에서 다루는 주제

원서가 예고하는 순서는 다음과 같다. 이 노트의 문서도 같은 순서로 나뉜다.

- AI 에이전트란 무엇인가
- CI/CD 파이프라인에서 에이전트를 안전하게 쓰기
- 실습: DevOps 실패 분류 에이전트 만들기
- 에이전트가 운영에서 실패하는 이유
- 점진적 자율성
- DevOps 워크플로의 에이전트 패턴
- 실습: PR 품질 평가 에이전트 만들기
- 실습: 에이전트를 PR 분석 워크플로에 통합하기

## 2. 실습 준비물

코드는 원서 저장소(PacktPublishing/Agentic-AI-for-DevOps-Engineers)의 start 폴더와 finish 폴더에 있다. start는 실습을 시작하는 기준 프로젝트이고, finish는 완성본이라 비교와 검증에 쓴다. 워크플로 예제의 경로는 start 폴더를 저장소 루트로 복사하거나 연 것으로 가정하고 적혀 있다.

- .NET 10 SDK. 데모는 .NET 10의 파일 기반 C# 앱을 쓰며 워크플로가 `dotnet run file`로 실행한다.
- Git, 그리고 git, dotnet, jq 명령을 돌릴 터미널.
- C# 개발을 지원하는 편집기(VS Code, Visual Studio 등). VS Code라면 C# Dev Kit 확장을 설치한다.
- GitHub 계정과 GitHub Actions가 켜진 저장소. 브랜치 생성, PR 열기, 저장소 시크릿 추가, 워크플로 파일 수정 권한이 필요하다.
- Azure 구독과 Azure OpenAI 또는 Azure AI Foundry 접근 권한, 그리고 gpt-4o-mini 같은 배포된 채팅 모델.
- 저장소 시크릿 세 개: AZURE_OPENAI_ENDPOINT, AZURE_OPENAI_API_KEY, AZURE_OPENAI_DEPLOYMENT.
- PR 품질 평가 워크플로에서는 GitHub 토큰을 MCP 서버(에이전트가 쓸 도구를 표준 방식으로 노출하는 서버, 자세한 설명은 6장)에 PR_ANALYSIS_TOKEN이라는 이름으로 넘긴다. 워크플로 권한 범위를 제대로 좁혔다면 secrets.GITHUB_TOKEN을 여기에 연결하면 된다.
- MCP를 쓰는 PR 에이전트용 환경 변수: MCP_PR_OWNER, MCP_PR_REPO, MCP_PR_NUMBER, MCP_SERVER_PROJECT.
- 저장소 내용 읽기, PR 파일 읽기, PR 대화 댓글 쓰기를 허용하는 워크플로 권한.
- 워크플로 스크립트에서 JSON을 검증할 jq. GitHub 호스티드 Ubuntu 러너에는 들어 있지만 자체 호스팅 러너에는 따로 설치해야 할 수 있다.

선택 도구로는 AI 리뷰 결과를 Copilot이 만든 리뷰 댓글과 비교해 볼 GitHub Copilot, 워크플로를 커밋하기 전에 파일 기반 에이전트를 돌려 볼 로컬 터미널이 있다.

참고(노트 작성자): 시크릿 값은 실제 값을 쓰지 말고 저장소 시크릿에만 넣는다. 이 노트에는 값을 적지 않는다.

## 3. AI 에이전트의 정의

원서는 에이전트를 환경을 인식하고, 추론하고, 계획하고, 도구를 써서 행동하며, 사람이 계속 지켜보지 않아도 특정 목표를 달성하는 자율 소프트웨어 시스템이라고 정의한다. 특정한 결과를 내고 업무 과정을 효율적으로 만들도록 설계된다.

비유를 하나 들면, 질문에 답만 하는 일반 AI 어시스턴트가 상담 창구 직원이라면 에이전트는 창구 직원에게 업무 시스템 접근권을 주고 "이 건을 처리해 달라"고 맡긴 담당자에 가깝다. 그래서 권한 설계가 중요해진다.

## 4. DevOps에서 에이전트를 적용하는 영역

| 영역 | 에이전트가 하는 일 |
|---|---|
| 코드 생성과 리뷰 | 구조화된 요구에서 구현 가능한 코드를 만들고, 검증과 인수 확인을 하며, 여러 파일과 서비스에 걸쳐 아키텍처 일관성을 유지 |
| IaC(코드형 인프라) 개발 | IaC 템플릿을 작성하고 성능, 비용, 보안 면에서 최적화하며 요구가 바뀌면 구성을 조정 |
| CI/CD 자동화 | 파이프라인 실행과 테스트 결과를 분석하고 실패 패턴과 병목을 찾아 맞춤 조치를 권고 |
| 인시던트 대응 | 로그와 모니터링 신호를 엮어 인시던트(장애 사건)를 분류하고, 근본 원인을 가설로 세우며, 정해 둔 완화 조치를 권고하거나 실행 |
| 성능 최적화 | 런타임 텔레메트리로 비효율을 찾고, 서비스 중단 없이 스케일링과 구성 개선을 권고 |
| 보안과 컴플라이언스 | 코드와 인프라의 취약점을 스캔 |

원서는 이 책 앞부분에서 코드 작성에 썼던 GitHub Copilot의 에이전트 모드가 이미 쓰이고 있는 에이전트적 동작의 예라고 짚는다.

## 5. 에이전트의 구성 요소

해부학적으로 보면 에이전트는 추론에 LLM(대규모 언어 모델)을 쓴다. 맥락을 유지하고, 외부 도구를 호출하며, 계획 루프 안에서 움직이고, 자기 출력을 스스로 평가한다. 다섯 가지 부품으로 이루어진다.

| 구성 요소 | 역할 |
|---|---|
| 추론 엔진 | 구조화되었거나 아닌 입력을 해석하고 분류하며, 구조화된 출력을 만들고, 필요하면 조치 단계를 제안 |
| 계획 계층 | 어떤 맥락을 모을지, LLM을 언제 부를지, 도구를 언제 쓸지, 출력을 검증할지 거부할지 결정. LLM의 예측 불가능성으로부터 시스템을 보호하는 층 |
| 메모리 | 단계 사이에 맥락을 유지해 같은 일을 반복하지 않게 함 |
| 도구 연동 | GitHub REST API, 로깅 시스템의 로그 조회, 테스트 실행, Bicep이나 Terraform 같은 IaC 템플릿 검증 등 |
| 자기 비판 | 자기 출력을 다시 평가해 정책과 비교하고 구조적 무결성을 확인 |

각 부품에서 놓치기 쉬운 점은 다음과 같다.

- 메모리는 실행 범위(execution-scoped)와 영속(persistent)의 두 종류다. 전부 저장하면 위험이 커지므로 꼭 필요한 정보만 담도록 의도적으로 설계해야 한다. 메모리는 6장에서 자세히 다룬다.
- 자기 비판의 예는 JSON 스키마 검증, 위험 분류 임계값 적용, 빠뜨린 것이 없는지 확인하는 두 번째 추론 패스다. 이 장의 실습에서는 이 자기 비판을 모델에게 맡기지 않고 코드로 강제한다.
- 계획 계층이 따로 있다는 점이 중요하다. 모델이 알아서 하게 두지 않고, 맥락 수집과 검증 여부를 시스템이 결정한다.

## 6. 자율 DevOps AI가 하는 일

자율적인 쪽에서 에이전트는 CI/CD 파이프라인 안의 문제를 감지하고, 분석하고, 해결할 수 있다. 로그를 해석하고 지표를 분석하고 인시던트를 예측하는 도구와 연동되며, IaC 코드 생성, 환경 구성, 로그 분석 같은 반복 작업을 자동화한다. 다만 CI/CD는 위험이 큰 자동화라서, 다음 문서에서 보듯 무엇을 허용하고 무엇을 막을지부터 정해야 한다.

## 7. 핵심 정리

- 에이전트는 인식, 추론, 계획, 도구 사용을 하는 자율 시스템이며 LLM은 그중 추론 부품이다.
- 구성 요소는 추론 엔진, 계획 계층, 메모리, 도구 연동, 자기 비판이다.
- 이 장의 실습은 .NET 10 파일 기반 C# 앱, GitHub Actions, Azure OpenAI 배포 모델, jq를 쓴다.
- 코드는 원서 저장소의 start와 finish 폴더로 대조한다.
- 참고(노트 작성자): 원서 PDF 추출본에는 `idx_...` 같은 색인 표식이 본문 사이에 끼어 있었다. 의미가 없는 찌꺼기라 무시하고 읽었다.
