# 실패 분류 에이전트 구현 실습

CI에서 테스트가 실패하면 로그를 읽고 원인을 분류해 구조화된 JSON으로 알려 주는 에이전트를 만든다. 이름은 DevOpsFailureTriageAgent다. 이 에이전트는 어떤 수정도 자동으로 하지 않는다. 가능성 높은 실패 유형과 근거 정보를 담은 제안만 내놓는다. 안전한 사용 사례의 전형인 읽기와 제안 전용 에이전트다.

구현은 .NET 10의 파일 기반 앱이다. .NET 10부터는 필요한 참조와 패키지를 한 개의 .cs 파일에 담아 한 번에 실행할 수 있어서, 프로젝트를 새로 만드는 번거로움이 없다. 다른 언어나 프레임워크를 쓰는 사람도 같은 개념을 자기 언어로 옮기면 된다고 원서는 말한다.

---

## 1. 전체 흐름

1. CI에서 테스트를 돌리고 로그를 파일로 남긴다.
2. 테스트가 실패하면 에이전트가 로그를 읽는다.
3. 에이전트가 먼저 도구로 실패 신호를 추출한다.
4. 신호로 실패를 분류해 JSON으로 출력한다.
5. 코드가 JSON을 검증하고, 잘못됐으면 안전한 대체 JSON을 낸다.

완성 스크립트는 원서 저장소 finish/ai/agents/DevOpsFailureTriageAgent.cs에 있다.

## 2. 에이전트 파일 만들기

ai 폴더 안에 agents 폴더를 만들고 DevOpsFailureTriageAgent.cs를 만든다. 단계는 원서의 번호를 따랐다.

1. 파일 맨 위에 .NET 10 대상 선언을 둔다. `#:property`로 TargetFramework는 net10.0, Nullable과 ImplicitUsings는 enable, TreatWarningsAsErrors는 true, PublishAot는 false로 정한다.
2. `#:package`로 Azure.AI.OpenAI 2.8.0-beta.1, Azure.Identity 1.13.2, Microsoft.Agents.AI.OpenAI 1.0.0-rc3, Microsoft.Extensions.AI 10.3.0을 추가한다. 이 패키지들이 LLM과 통신하는 Microsoft Agent Framework를 제공한다.
3. 원서 주의: 이 장 데모는 집필 시점의 최신 버전을 쓰며 릴리스 후보와 베타 빌드가 섞여 있다. 실행 전에 지원되는 최신 버전과 릴리스 노트의 호환성 깨짐 여부를 확인하라고 한다.
4. 환경 변수를 읽는다. 이름은 CI/CD 파이프라인에 이미 정해진 것과 같아야 한다. 엔드포인트와 API 키는 없으면 예외를 던지고, 배포 이름은 없으면 gpt-4o-mini를 기본값으로 쓴다.
5. 취소 토큰을 만든다. 2분 이상 멈추면 작업이 자동 취소된다.
6. 로그 파일 경로(인자가 없으면 failure.log)에서 내용을 읽는다. 최대 글자 수를 100,000자로 정해 모델의 컨텍스트 창을 넘지 않게 하고, 넘으면 잘라 내고 끝에 truncated 표시를 붙인다.
7. Microsoft Agent Framework로 에이전트를 정의한다. OpenAI 클라이언트에 엔드포인트와 API 키를 넘기고, 배포 이름으로 채팅 클라이언트를 얻어 에이전트를 만든다.

에이전트에는 이름과 지시문(instructions)과 JSON 스키마를 준다. 지시문의 핵심 규칙은 세 가지다. 먼저 ExtractFailureSignals 도구를 쓸 것, 출력은 JSON만(마크다운과 서술 금지), 파괴적인 명령은 제안하지 말 것.

```csharp
.AsAIAgent(name: "DevOpsFailureTriageAgent",
    instructions: "...Use the tool ExtractFailureSignals first. Output MUST be JSON only...",
    tools: [AIFunctionFactory.Create(LogTools.ExtractFailureSignals)])
```

JSON 스키마의 필드는 failureCategory(문자열), severity(low, medium, high), likelyCause, recommendedNextStep, confidence(숫자)다.

도구 목록에는 이 데모에서 로컬 도구가 하나뿐이다. 도구 목록을 작고 초점 있게 유지하는 것은 의도된 설계다. 뒤의 PR 분석 데모에서 MCP 기반 조회 경계가 등장하고, MCP는 다음 장에서 도구 표준화 패턴으로 확장된다.

## 3. 결정론적 도구 LogTools

8. 같은 파일에 정적 클래스 LogTools를 만들고, CI 로그에서 실패 신호를 결정론적으로 추출한다는 설명을 붙인다.
9. 추출 메서드는 로그 내용이 비었으면 곧바로 돌아간다.
10. 흔한 실패 표지(마커) 키워드 목록을 정한다. ERROR, FAIL, FATAL, Unhandled exception, Build FAILED, Test Run Failed, Exited with code, MSB1, NETSDK, NU1이다. 로그의 각 줄을 이 마커에 대조해 대소문자 구분 없이 일치하면 기록한다. 최대 줄 수 기본값은 30이다. 일치하는 줄이 하나도 없으면 로그의 마지막 줄들을 대신 돌려준다.
11. 신호를 하나의 문자열로 합쳐 요청에 실을 맥락을 정제한다. 결과 문자열은 `=== Failure Signals ===`로 시작한다.

핵심은 LLM이 아니라 일반 코드가 신호를 뽑는다는 점이다. 같은 로그면 항상 같은 줄이 나오므로 모델이 볼 입력의 일부가 예측 가능해진다.

참고(노트 작성자): MSB1은 MSBuild, NETSDK는 .NET SDK, NU1은 NuGet 계열 오류 코드의 접두어다. 원서는 이 설명을 하지 않았고 일반 지식으로 보충했다.

## 4. 프롬프트와 실행, 자기 비판

12. 프롬프트를 만든다. CI 워크플로가 실패했다고 알리고, 원본 로그를 BEGIN LOG와 END LOG 표지 사이에 넣고, 해야 할 단계를 적는다. 1) ExtractFailureSignals를 호출하고 2) 그 신호로 실패를 분류하고 3) JSON만 반환한다.
13. 에이전트를 실행해 응답을 받는다(`agent.RunAsync`, 취소 토큰 전달).
14. 자기 비판 단계를 둔다. 응답이 유효한 JSON인지 파싱하고, 다섯 개 속성이 모두 있고 자료형이 맞는지 확인하며, 원본 출력을 콘솔에 보여 준다.

예외가 나면 같은 형식의 기본 JSON과 예외 메시지를 낸다. 값은 failureCategory가 unknown, severity가 medium, likelyCause가 "Agent returned invalid JSON", confidence가 0.0이고 다음 조치는 로그를 직접 보고 지시문을 조이라는 내용이다. 대체 JSON도 결정론적이라는 점이 포인트다.

원서는 에이전트가 자기 평가를 할 수 있으며 위 단계가 그 동작을 코드에 직접 적용한 예라고 말한다. 코드 주석에는 이것이 코드로 강제하는 자기 비판이라고 적혀 있다.

## 5. CI 워크플로 구성

새 워크플로 이름은 CI (with Agent Failure Triage)이고 파일은 .github/workflows/ci-with-agent-triage.yml이다. 테스트 실패가 일어날 때마다 분류 에이전트가 돈다.

| 단계 | 설정 |
|---|---|
| 트리거 | workflow_dispatch(수동). pull_request는 주석 처리된 선택지 |
| 작업 | build_test_triage, ubuntu-latest에서 실행. Checkout(actions/checkout@v4)과 Setup .NET(actions/setup-dotnet@v4, 버전 10.0.x) |
| 테스트 | id는 tests, continue-on-error를 true로 둔다. 실패해도 워크플로가 이 단계에서 멈추지 않게 하려는 것이다. 로그는 artifacts/failure.log에 tee로 저장 |
| 에이전트 실행 | 조건 `steps.tests.outcome == 'failure'`일 때만 `dotnet run --file ai/agents/DevOpsFailureTriageAgent.cs -- ./artifacts/failure.log` |
| 환경 변수 | 엔드포인트, API 키, 배포 이름을 시크릿에서 주입 |
| 업로드 | `always()`로 결과와 관계없이 artifacts/를 ci-artifacts 이름으로 올림. 파일이 없으면 경고 |
| 마무리 | 테스트가 실패했다면 `exit 1`로 워크플로 실행을 실패로 표시 |

테스트 단계의 핵심 두 줄은 다음과 같다.

```yaml
continue-on-error: true
run: |
  set -o pipefail
```

continue-on-error를 쓰는 이유와 마지막 단계의 이유가 짝을 이룬다. 테스트 실패로 중간에 멈추면 에이전트가 돌 기회가 없으므로 일단 계속 진행시키고, 맨 끝에서 따로 실패 처리를 해서 최종 상태는 정직하게 실패로 남긴다.

## 6. 검증하기

1. 테스트 하나를 일부러 실패시킨다. 예로 단언의 기대값을 `Assert.Equal (10, users.Count);`처럼 10으로 바꾼다.
2. 푸시하기 전에 워크플로 jobs 섹션에 세 개의 환경 변수(엔드포인트, API 키, 배포 이름)가 시크릿으로 설정되게 한다.
3. main 브랜치에 푸시하고, workflow_dispatch가 있으므로 GitHub의 Actions 탭에서 해당 CI 워크플로를 수동 실행한다.

원서에 따르면 초기 실행은 기대한 테스트 단계에서 멈추지 않았다. 원인은 테스트 단계 설정이었다. pipefail을 켜고, artifacts 디렉터리를 만들고, 솔루션 경로(src/GenAIDevOps.sln)를 올바르게 쓰도록 고쳐야 했다. 고친 뒤에는 기대한 대로 테스트 작업이 실패하고 로그가 의도한 실패를 확인해 주었다.

참고(노트 작성자): pipefail은 파이프(`|`)로 이은 명령 중 하나라도 실패하면 전체를 실패로 보게 하는 셸 옵션이다. 이게 없으면 `dotnet test`가 실패해도 뒤의 tee가 성공해서 단계가 성공으로 처리될 수 있다. 원서에는 이 설명이 없다.

분류 에이전트의 출력은 테스트 실패로 분류하고 심각도 high, 가능성 높은 원인, 권장 다음 단계, 신뢰도 점수를 담은 JSON이었다. 이로써 CI 실패에서 로그를 수집하고, LLM에 보내고, 가능성 높은 원인 요약을 돌려받는 전체 순환이 확인되었다.

## 7. 핵심 정리

- 에이전트는 읽고 제안만 하며, 어떤 수정도 자동으로 하지 않는다.
- 로그는 100,000자로 제한하고, 실패 마커 10종으로 신호를 결정론적으로 추출한다.
- 출력은 다섯 필드의 JSON이고, 코드가 파싱과 필드 검증을 하며 실패하면 안전한 대체 JSON을 낸다.
- 워크플로는 continue-on-error로 테스트를 계속 진행시키고, 실패 시에만 에이전트를 돌리고, 마지막에 exit 1로 실패를 확정한다.
- 원서 코드 일부는 줄바꿈이 깨져 들어가 있었다. 문맥으로 복원해 해석했다. 특히 YAML 들여쓰기는 추출 과정에서 사라져 있어 구조는 원서 설명의 단계 순서로 복원했다.
