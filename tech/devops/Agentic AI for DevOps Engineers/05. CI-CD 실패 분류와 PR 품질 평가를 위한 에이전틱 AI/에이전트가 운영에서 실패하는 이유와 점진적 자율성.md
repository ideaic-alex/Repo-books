# 에이전트가 운영에서 실패하는 이유와 점진적 자율성

실패 분류 에이전트가 동작하는 것을 확인했다면, 다음 질문은 이것을 운영에 오래 두어도 안전한가다. 원서는 에이전트가 운영에서 왜 실패하는지 다섯 가지 유형으로 정리하고, 그 위험을 다루는 방법으로 점진적 자율성(작게 시작해 신뢰가 쌓이면 권한을 넓히는 방식)을 제시한다.

핵심은 신뢰를 먼저 주지 않는다는 것이다. 에이전트는 관찰과 제안에서 시작하고, 성과가 입증된 뒤에만 안전한 행동을 자율로 할 권한을 받는다.

---

## 1. 에이전트가 운영에서 실패하는 이유

원인은 크게 네 가지로 묶인다. 불완전한 맥락에서 동작하고, 확률적으로 추론하고, 깨지기 쉬운 도구 인터페이스에 의존하고, 프롬프트 구조에 민감하다. 이 중 여러 개가 겹치기도 한다. 이를 구체적인 실패 모드로 나누면 다음 다섯 가지다.

| 실패 모드 | 무슨 일이 생기나 | 결과 |
|---|---|---|
| 맥락 손실 | 큰 로그나 큰 데이터가 컨텍스트 창을 넘고, 줄이는 과정에서 중요한 신호가 잘림 | 잘못된 분류, 오해를 부르는 조치, 신뢰 상실 |
| 약한 계획 | 여러 단계의 해결 추론, 일관된 실행 전략 유지, 긴 상호작용의 상태 추적이 어려움 | 부분 수정, 일관성 없는 권고, 지나치게 단순한 근본 원인 |
| 도구 취약성 | API 계약 변경, 권한 부족, 잘못된 입력 형식 등으로 도구가 실패하는데 LLM은 성공했다고 가정 | 거짓 확신, 유효하지 않은 자동화 단계 |
| 프롬프트 민감성 | 프롬프트가 조금 달라져도 처리 방식이 바뀜 | 출력 예측과 자동화 디버깅이 어려워짐 |
| 과신 | 그럴듯하지만 틀린 근본 원인을 높은 확신으로 말하고 안전하지 않은 조치를 권고 | 비결정적 동작 |

### 1-1. 맥락 손실의 사례

5,000줄짜리 로그에서 오류가 4,850번째 줄에 있는데 로그를 50% 잘라 넣는다고 하자. 에이전트가 오류를 잘못 분류하거나, 실제로는 테스트가 실패했는데 오류가 없었다고 단정할 수 있다. 근본 원인은 맥락 누락이다. 너무 많이 보내는 것과 딱 필요한 만큼만 보내는 것 사이에서 균형을 잡아야 하는 미묘한 문제다.

참고(노트 작성자): 앞 실습의 로그 100,000자 제한과 실패 마커 추출은 이 문제를 줄이려는 장치다. 다만 앞 실습 코드는 100,000자를 넘으면 앞부분만 남기고 뒤를 잘라 내므로, 오류가 로그 끝에 있는 경우를 원서도 위험 사례로 든다고 읽을 수 있다. 이 연결은 노트 작성자의 해석이다.

### 1-2. 약한 계획의 사례

원서는 직접 관찰한 일을 든다. 에이전트가 한동안 돌았다며 잠시 멈췄다가 나중에 이어서 할지 묻는 경우가 있다. 이어서 하면 동작은 하지만, 시간이 지날수록 출력 품질이 떨어진다. 약한 계획이 일으키는 일종의 부식이라고 설명한다.

### 1-3. 도구 취약성의 사례

GitHub API와 연동한 에이전트가 이슈를 만들려 하는데 GitHub 토큰에 권한이 없어 403 응답이 돌아온다고 하자. 그대로 두면 에이전트는 이슈가 만들어졌다고 가정하고, 인시던트는 추적되지 않은 채 남는다. 도구가 조용히 실패했는데 에이전트는 계속 성공을 보고하는 거짓 확신의 경우다.

### 1-4. 정리

에이전트는 컨텍스트 한계, 계획 약점, 도구 취약성, 프롬프트 불안정, 과신 때문에 실패한다. AI와 에이전트를 DevOps 파이프라인에 넣으려면 각 단계에서 의도적인 결정이 필요하다.

## 2. 점진적 자율성

점진적 자율성은 에이전트가 관찰과 제안으로 시작하고, 잘 수행하면 범위가 통제된 행동으로 넓어지며, 그 사이에 검증 계층이 더해지는 방식이다. 안전한 행동을 자율로 수행할 권한은 신뢰성이 입증된 뒤에만 준다.

### 2-1. 네 가지 자율성 수준

| 수준 | 이름 | 에이전트가 할 수 있는 것 | 할 수 없는 것 |
|---|---|---|---|
| 0 | 관찰(Observe) | 로그 분석, 실패 분류, 구조화된 결과 출력 | PR 댓글, 이슈 생성, 파이프라인 변경 |
| 1 | 제안(Suggest) | PR 댓글 게시, 권고 초안, 이슈 라벨링 | 코드 변경, 배포, 병합 확정 |
| 2 | 통제된 행동 | 초안 PR 열기, 테스트 재실행 트리거, 비프로덕션 구성 수정 | 정해진 경계 밖의 결정 |
| 3 | 준자율 실행 | 조건부로 조치 적용, 구성 값 갱신, PR 병합 | 게이트 없이 하는 것 |

각 수준의 목적과 요구는 다음과 같다.

- 수준 0은 기준이 되는 추론 신뢰도를 세우는 진단 모드다. 실제 워크플로에 영향을 주는 출력을 허용하기 전에 지표를 모은다.
- 수준 1은 큰 위험 없이 눈에 보이는 참여를 시작한다.
- 수준 2는 정책 아래 제한된 자동 실행을 허용한다. 검증 검사를 통과해야 하고 정해진 범위를 지켜야 한다. 범위 제한이 결정적이다. 분명하게 정한 경계 밖의 일은 에이전트가 결정하면 안 된다.
- 수준 3은 신뢰와 확신이 높을 때 엄격히 감시되는 자율을 허용한다. 다층 검증, 결정론적 검증, 감사 로그가 필요하다. 드문 수준이며 텔레메트리 검증과 정책 집행이 요구된다. 대부분의 구현은 수준 2에서 멈춘다.

## 3. 수준 사이에서 승격하기

에이전트를 언제 다음 수준으로 올릴지는 측정 가능한 신호로 정한다. 원서가 드는 다섯 가지 신호는 제안 수락률, 오탐률(false positive rate), 조치 후 테스트 통과율, 평균 해결 시간, 개발자의 재정의(override) 빈도다. 이 측정으로 에이전트의 판단을 믿을 수 있는지, 더 튜닝이 필요한지, 작은 일에서만 낮은 수준에 머물고 큰 결정은 사람에게 남겨야 하는지 판단한다.

자율성을 더 주려면 더 많은 게이트가 필요하다. 브랜치 제한, 환경 승인, 필수 리뷰어 검사와 결합할 수 있다. 게이트 로직의 예는 단계 출력의 신뢰도가 임계값을 넘는지 보는 것이다.

```yaml
if: steps.classify.outputs.confidence >= 0.85
```

앞의 분류 예에서 실패는 90% 신뢰도로 분류되었다. 임계값을 85%로 정하면, 에이전트가 최소 85% 확신할 때 이슈 생성, PR 초안 작성, 코드 수정 제안 같은 다음 단계로 갈 수 있다. 원서의 결론은 자율성이 파이프라인 정책에 부호화되어야 한다는 것이다.

참고(노트 작성자): 위 `if` 줄은 원서가 개념을 보이려고 든 한 줄이며, 완결된 워크플로가 아니다. 실제로 쓸 때는 출력이 문자열이라는 점과 숫자 비교 방식을 따로 확인해야 한다. 이 지적은 원서에 없다.

## 4. 점진적 자율성 패턴

원서의 그림 5.5가 보여 주는 흐름은 이렇다. GitHub 이벤트가 에이전트 실행을 트리거하고, 검증이 신뢰도 임계값을 충족하는지 판단한다. 충족하면 에이전트가 행동을 할 수 있고, 아니면 제안만 할 수 있다.

사람의 감독은 내내 필수다. 행동 전의 수동 승인이나, 환경 보호 규칙에 대한 코드 오너의 리뷰가 그 형태다. 사람이 고리 안에 있는 자율성은 자동화의 속도를 살리면서 위험을 줄인다. 원서의 결론 문장은 자율성은 단계적이고, 측정되고, 통제되고, 철회 가능해야 한다는 것이다. 통제되지 않은 자율성은 불안정으로 이어진다.

## 5. 핵심 정리

- 운영 실패의 다섯 유형은 맥락 손실, 약한 계획, 도구 취약성, 프롬프트 민감성, 과신이다.
- 도구가 조용히 실패하면 에이전트가 성공을 가정하는 거짓 확신이 생긴다. 도구 호출 결과를 코드로 확인해야 한다는 교훈으로 읽을 수 있다(해석은 노트 작성자).
- 자율성은 관찰, 제안, 통제된 행동, 준자율 실행의 네 수준이며 대부분은 수준 2에서 멈춘다.
- 승격 기준은 수락률, 오탐률, 조치 후 테스트 통과율, 평균 해결 시간, 재정의 빈도다.
- 신뢰도 임계값은 파이프라인 정책에 코드로 넣고, 사람의 승인과 병행한다.
