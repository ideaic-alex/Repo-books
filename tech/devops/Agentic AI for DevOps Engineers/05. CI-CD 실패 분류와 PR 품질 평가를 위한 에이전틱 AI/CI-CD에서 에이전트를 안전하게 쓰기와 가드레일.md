# CI/CD에서 에이전트를 안전하게 쓰기와 가드레일

에이전트가 DevOps 작업의 중심에 가까워질수록, 특히 자율적인 AI를 CI/CD 파이프라인에 넣을 때는 조심해야 한다. 원서의 출발점은 CI/CD가 위험이 큰 자동화라는 사실이다. 그래서 에이전트를 붙이는 방식은 가능한 한 안전해야 한다.

이 문서는 왜 CI/CD가 위험한지, 에이전트에게 맡겨도 되는 일과 안 되는 일이 무엇인지, 그리고 에이전트를 감싸야 하는 가드레일(안전 울타리)이 무엇인지 정리한다.

---

## 1. CI/CD가 위험한 이유

원서가 드는 이유는 네 가지다. CI/CD는 자동으로 실행되고, 프로덕션에 영향을 줄 수 있으며, 자주 실행되고, 보호된 브랜치에 영향을 준다. 이런 환경에서 에이전트가 안전하지 않은 행동을 하면 한 번의 실수로 끝나지 않고 시스템 전체의 위험(systemic risk)이 된다.

비유하면 매일 수십 번 자동으로 돌아가는 컨베이어 벨트에 사람 대신 새 작업자를 세우는 일과 같다. 한 번 잘못 놓은 부품이 벨트를 타고 계속 흘러간다.

## 2. 안전한 사용 사례와 안전하지 않은 사용 사례

| 구분 | 사례 |
|---|---|
| 안전 | 실패 분류(파이프라인 실패를 분류하고 무엇이 잘못됐을지 쉬운 말로 설명), 테스트 결과 요약, PR 제안 또는 초안 작성, 문서 생성 |
| 위험 | 보호된 브랜치에 자동 병합, 프로덕션 자동 배포, 막힌 파이프라인을 넘기려고 실패하는 테스트 비활성화, 보안 정책 수정 |

안전한 쪽의 공통점은 결과가 사람에게 보이는 제안이나 설명에 그친다는 것이다. 위험한 쪽은 에이전트가 직접 상태를 바꾼다.

## 3. 왜 위험한가: 원서의 설명

### 3-1. 자동 병합

원서는 AI 보조 코딩을 주니어 개발자의 기여처럼 다루라고 한다. 주니어든 동료든 보호된 브랜치에 병합하기 전에는 코드 리뷰가 있어야 한다. 에이전트의 자동 병합은 명백한 적신호다. 보호된 브랜치로 병합되면 CI/CD 파이프라인이 프로덕션 자동 배포까지 이어 갈 가능성이 크고, 그러면 평소의 프로덕션 배포 단계를 건너뛰게 될 수 있기 때문이다.

### 3-2. 실패하는 테스트 비활성화

에이전트는 해결책을 찾으려는 최선의 노력 중에 실패를 일으키는 테스트를 꺼 버리려 할 수 있다. 문제를 푼 것처럼 보이지만 실은 문제를 묻어서 파이프라인만 통과시킨 것이다. 원서는 에이전트에게 이런 권한을 절대 주지 말고, 보안 정책도 수정하지 못하게 하라고 못박는다.

## 4. DevOps 에이전트의 가드레일

안전한 DevOps 에이전트는 워크플로 결과에 영향을 주기 전에 결정론적(같은 입력이면 같은 결과가 나오는) 가드레일로 감싸야 한다. 최소한 다음 네 가지를 쓴다.

1. 모델 출력에 대한 스키마 검증
2. 도구에 대한 최소 권한 접근
3. 지원하는 동작을 명시한 허용 목록(allowlist)
4. 코드, 배포, 보안 정책이 바뀌기 전의 사람 검토

실용적인 가드레일의 예는 다음과 같다.

| 가드레일 | 하는 일 |
|---|---|
| 관련성 검사 | 모델에 맥락을 보내기 전에 관련 있는 내용인지 확인 |
| 안전성 검사 | 파괴적이거나 월권하는 권고를 거부 |
| 비밀과 개인정보 필터 | 로그와 diff(변경 내용)에서 비밀 값과 개인 식별 정보를 걸러냄 |
| 최종 정책 게이트 | 워크플로를 통과시킬지, 실패시킬지, 사람 검토를 요구할지 결정 |

핵심은 최종 판단을 모델이 아니라 결정론적 정책 게이트가 내린다는 점이다. 모델의 출력은 권고일 뿐이고, 통과 여부는 코드가 정한 규칙이 가른다. 이 구조는 뒤의 두 실습에서 그대로 구현된다. 실패 분류 실습에서는 JSON 검증이, PR 분석 실습에서는 위험도와 신뢰도로 판정하는 리스크 게이트가 그 역할을 한다.

참고(노트 작성자): 원서는 비밀과 개인정보 필터와 관련성 검사를 가드레일로 열거하지만, 이 장의 실습 코드에는 그 둘을 구현한 부분이 없다. 실습이 보여 주는 가드레일은 스키마 검증, 도구 범위 제한, 로그 길이 제한, 최종 게이트다.

## 5. 핵심 정리

- CI/CD는 자동, 고빈도, 프로덕션 영향, 보호 브랜치 영향 때문에 위험이 큰 자동화다.
- 실패 분류, 테스트 요약, PR 초안 제안, 문서 생성은 안전한 사용이다.
- 자동 병합, 프로덕션 자동 배포, 테스트 비활성화, 보안 정책 수정은 금지한다.
- 에이전트는 스키마 검증, 최소 권한, 허용 목록, 사람 검토로 감싼다.
- 최종 통과 여부는 결정론적 정책 게이트가 정한다.
