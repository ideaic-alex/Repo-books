# DevOps 수명주기에 AI 대응시키기

생성형 AI와 LLM의 성질을 정리했으면 다음은 그것을 실제 DevOps 일에 대응시킬 차례다. 목적은 효과가 작거나 위험한 용도를 피하는 것이다. 원문은 이를 위해 DevOps 수명주기를 먼저 되짚고, 단계마다 AI가 얼마나 도움이 되는지 가치를 매긴다.

핵심 판단 기준은 하나다. AI는 엔지니어가 정보를 해석하고 결정하는 지식 중심 단계에서 잘 맞고, 일관성과 결정론이 최우선인 실행 중심 단계에서는 맞지 않는다. 모든 곳에 AI를 쓰는 것이 목표가 아니라, 변동성이 도움이 되는 곳에만 쓰고 예측 가능성이 필요한 곳에서는 피하는 것이 목표다.

---

## 1. DevOps 수명주기 되짚기

DevOps 사이클은 소프트웨어를 계획(plan), 코딩(code), 빌드(build), 테스트(test), 릴리스(release), 배포(deploy), 운영(operate), 모니터링(monitor)하는 끊임없는 흐름이다. 각 단계가 다음 단계를 먹이고, 운영 환경에서 얻은 피드백이 다음 계획과 개선에 반영된다. 이 순환은 팀이 품질, 신뢰성, 통제를 지키면서 변경을 빠르게 내놓도록 설계된 것이다. 원서의 그림 1.1이 이 흐름을 보여 주지만 이 노트에는 싣지 않는다.

원문은 두 가지를 덧붙인다. 첫째, 의사결정은 언제나 사람의 책임으로 남아야 한다. 둘째, 각 단계에서 AI의 가치는 프로젝트, 팀, 여러 요인에 따라 상대적이므로 저자의 설명이 독자의 상황에 그대로 들어맞지 않을 수 있다.

---

## 2. 단계별 AI 가치 평가

원문이 매긴 가치를 단계별로 정리하면 다음과 같다.

| 단계 | AI 가치 | AI가 할 수 있는 일 |
|---|---|---|
| Plan | 높음 | 요구사항과 티켓 요약, 아이디어를 기술 작업으로 번역, 아키텍처 노트와 아키텍처 결정 기록(ADR) 초안, 위험과 미해결 질문 식별 |
| Code | 높음 | 보일러플레이트 패턴 초안, 리팩터링 제안, 잠재 이슈 강조, 풀 리퀘스트(PR) 리뷰 보조 |
| Build | 낮음 | 거의 없음. 빌드는 결정론적이어야 하고 실패도 예측 가능해야 하므로 AI는 빌드 로직에 영향을 주면 안 되고 실행 경로 밖에 둔다 |
| Test | 높음 | 테스트 케이스 제안, 빠진 커버리지 식별, 테스트 데이터 시나리오 초안, 실패한 테스트 설명 |
| Release | 중간 | 릴리스 노트 초안, 변경 요약, 깨지는 변경(breaking change) 강조, 릴리스 준비 상태 리뷰 생성 |
| Operate | 높음(강한 지원 영역) | 로그 요약, 오류 패턴 탐지, 인시던트 타임라인 초안, 사후 검토 |
| Monitor | 중간 | 지표 추세 해석, 알림을 쉬운 말로 설명, 시스템 간 이벤트 연관 분석, 지속적 개선 지원 |

원문은 상위 요약에서 가치가 높은 곳을 계획, 코딩, 테스트, 운영, 중간인 곳을 릴리스와 모니터링, 낮은 곳을 빌드, 실행, 배포로 묶는다. 표의 Build와 Operate, 배포 항목은 이 요약과 단계별 본문을 합쳐 정리했다.

참고(노트 작성자): 원문은 배포(deploy)를 단계별 항목으로 따로 설명하지 않고 요약 문장에서 '낮은 가치' 영역으로만 언급한다. 표에는 Deploy 행을 넣지 않았다.

### 2-1. 단계별로 눈여겨볼 점

- Code 단계에서도 AI가 사려 깊은 코드 리뷰나 아키텍처 판단을 대신할 수는 없다. 반복 작업, 뼈대 만들기, 초기 리뷰를 돕지만 엔지니어링 판단의 필요를 없애지 않는다.
- Test 단계에서는 AI가 시나리오를 제안하고 실패를 설명해도 무엇을 테스트 스위트에 넣을지는 사람이 정한다. 코드를 AI에게 리뷰·감사시켜 엣지 케이스를 찾는 것이 유용한데, 사람이 놓치기 쉬운 부분이고 찾는 데 머리를 많이 써야 하기 때문이다.
- Operate 단계는 특히 로그처럼 데이터가 엄청나게 쏟아져서 AI 지원이 강한 영역이다. AI가 모니터링 도구나 당직자의 판단을 대체하지는 않지만, 방대한 운영 데이터를 처리하는 인지 과부하를 줄여 준다.
- Release 단계에서는 조율, 소통, 확신을 돕는다. 사람이 읽을 수 있는 산출물을 빨리 만들어 주는 것이 핵심이다.
- Monitor 단계에서 모니터링 도구는 신호를 내보내지만 해석은 여전히 사람의 몫이다. AI는 그 해석을 거든다.

---

## 3. AI를 피하거나 넣지 말아야 할 영역

AI가 거의 가치를 더하지 못하거나 위험 때문에 피해야 하는 영역도 분명히 있다. 원문이 나열한 것은 다음 다섯 가지다.

1. 운영 환경으로의 직접 배포
2. 비밀 값(secrets) 관리
3. 승인과 승인 우회
4. 보안 집행 결정
5. 되돌릴 수 없는 작업이 걸린 모든 일

AI를 이런 영역의 책임자로 앉히면 안 되고, 경우에 따라서는 아예 관여시키지도 말아야 한다. 결국 AI는 생각을 돕지 실행을 돕지 않는다. 이해를 가속하지만 책임을 가속하지는 않는다.

---

## 4. 이 장의 판단 틀 정리

단계별 평가와 금지 영역을 하나의 기준으로 묶으면 이렇다.

- 해석과 판단이 필요하고, 틀려도 사람이 검토해서 잡을 수 있는 일은 AI를 넣는다.
- 같은 입력에 같은 결과가 나와야 하거나 되돌릴 수 없는 일은 AI를 넣지 않는다.
- 어느 쪽이든 마지막 결정은 사람이 한다.

참고(노트 작성자): 이 판단 틀은 원문의 서술을 세 줄로 줄여 정리한 것이다. 원문에 이런 형태의 표현이 그대로 있지는 않다.

원서의 그림 1.1은 수명주기 개요도다. 위 표는 그림이 전달하는 단계 순서에 AI 가치를 겹쳐 놓은 것에 해당한다.
