# 요약과 핵심 개념

이 장은 세 덩어리로 이뤄진다. 생성형 AI와 LLM이 무엇인지, DevOps 수명주기의 어디에 AI를 쓸지, AI 지원과 자율의 차이 및 그에 따르는 위험이다. 이 문서는 세 덩어리를 한 번에 되짚고 핵심 용어를 정리한다.

원서의 요약은 이렇게 이어진다. 생성형 AI가 무엇이고 무엇이 아닌지, 어디에서 가치를 더하는지, 지원이 자율보다 나은 이유, AI 위험을 알아보고 관리하는 법을 살폈다. AI 지원은 DevOps 엔지니어의 인지 부하와 반복 작업을 줄여 주지만 AI 도구도 실수를 하므로 작업 수행의 결정 요소는 여전히 엔지니어링 전문성이어야 한다. 이론을 깔았으니 다음 장은 실무 활용으로 넘어간다.

---

## 1. 장 전체 흐름

| 순서 | 주제 | 결론 |
|---|---|---|
| 1 | 생성형 AI와 LLM | 학습한 패턴으로 새 출력을 만드는 확률적 시스템. 자동화와 성질이 다르다 |
| 2 | 자동화와 LLM의 역할 구분 | 자동화는 실행하고 LLM은 제안한다. 파이프라인에서 AI는 보조자다 |
| 3 | 수명주기별 AI 가치 | 계획, 코딩, 테스트, 운영은 높음. 릴리스, 모니터링은 중간. 빌드, 실행, 배포는 낮음 |
| 4 | AI 지원 대 AI 자율 | 지원은 전문성을 확장하고 자율은 위험을 확장한다 |
| 5 | 세 가지 위험 | 환각, 드리프트, 월권 |
| 6 | 안전 설계 | 사람을 루프에 두고 AI 권한을 제한하며 승인 게이트, 관측성, 감사 추적을 둔다 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 생성형 AI | 정해진 명령을 실행하지 않고 텍스트, 코드, 설정, 요약 같은 새 내용을 만드는 시스템 |
| LLM | 방대한 텍스트와 코드로 학습한 생성형 AI 모델. 대부분 트랜스포머 기반 |
| 토큰 | 모델이 처리하는 작은 텍스트 단위(단어, 단어 일부, 문장부호, 코드 한 줄 등) |
| 컨텍스트 윈도우 | 모델이 한 번에 참고할 수 있는 입력 범위. 필요한 정보가 빠지면 출력이 불완전하거나 낡거나 위험해질 수 있다 |
| 결정론적 | 출력이 예측 가능해서 같은 상황이면 같은 결과가 나오고 실패도 예측 가능한 성질 |
| AI 지원 DevOps | AI가 제안하고 사람이 검토해 결정하며 변경이 추적·감사되는 방식 |
| AI 자율 DevOps | AI가 변경을 시작하고 실행하고 스스로 승인하며 사람 검토가 최소이거나 없는 방식 |
| 피해 반경(blast radius) | 한 번의 잘못된 결정이 미치는 범위. 자율일수록 커진다 |
| 환각 | 맞는 듯하지만 사실이 아닌 출력. 확신에 차 있어 더 위험하다 |
| 드리프트 | 모델이 아니라 환경이 변해 시간이 지날수록 출력이 낡는 현상 |
| 월권 | AI가 자문 역할을 넘어 되돌릴 수 없는 작업을 실행하거나 검토를 우회하는 것. 시스템 설계의 실패다 |
| 승인 게이트 | 실행 전에 사람의 승인을 요구하는 지점 |

## 3. 자주 놓치는 점

- 생성형 AI를 자동화의 다른 이름으로 오해하면 안 된다. 같은 입력에 같은 결과를 보장하지 않는다.
- AI 출력은 그럴듯해도 검증 전에는 틀린 것으로 취급한다. 복구 절차도 미리 준비한다.
- 빌드처럼 결정론이 필요한 실행 경로에는 AI를 넣지 않는다. 다만 가치 평가는 팀과 프로젝트에 따라 달라질 수 있다고 원문도 단서를 단다.
- 드리프트는 모델이 바뀌어서가 아니라 세상이 바뀌어서 생긴다. 폐기된 문법과 낡은 기본값을 특히 조심한다.
- 월권은 모델의 결함이 아니라 권한을 너무 준 시스템의 결함이다. AI에는 읽기 전용이나 자문 권한부터 준다.
- 위험을 이유로 AI를 아예 피하는 것도 답이 아니다. 인정하고 설계로 관리한다.
- 책임은 어떤 도구를 쓰든 엔지니어링 팀에 남는다.
