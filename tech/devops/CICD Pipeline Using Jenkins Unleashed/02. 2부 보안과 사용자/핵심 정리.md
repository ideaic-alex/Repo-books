# 핵심 정리

이 문서는 2부(7장부터 9장)의 요점을 한곳에 모은 복습용 정리다. 각 요점 끝의 **→ 자세히** 링크를 따라가면 해당 장으로 이동한다. 책의 화면은 2021년경 Jenkins 기준이다.

---

## 1. 한눈에 보는 요점

- **인증과 인가는 `Configure Global Security`에서 정한다**: Security Realm으로 사용자 출처를, Authorization으로 허용 범위를 고른다.
  - *쉽게 말하면*: "누가 들어오나"와 "들어와서 무엇을 하나"를 한 화면에서 정한다.
  - → 자세히: [7장 보안 관리](07%EC%9E%A5%20%EB%B3%B4%EC%95%88%20%EA%B4%80%EB%A6%AC.md)
- **권한이 너무 넓은 기본 옵션은 피한다**: 익명에게 전체 권한을 주는 `Anyone can do anything`과 `Legacy mode`는 비권장이고, 자체 DB의 가입 허용도 켜 두지 않는 것이 좋다.
  - *쉽게 말하면*: 문을 활짝 열어 두는 설정은 신뢰된 환경에서도 조심한다.
  - → 자세히: [7장 보안 관리](07%EC%9E%A5%20%EB%B3%B4%EC%95%88%20%EA%B4%80%EB%A6%AC.md)
- **포트와 토큰 설정에도 보안 의미가 있다**: 에이전트·SSH 포트는 방화벽 규칙을 만들기 쉬운 `Fixed`가 선호되고, 안 쓰면 `Disable`로 둔다. CSRF는 crumb으로 막고, 레거시 API 토큰은 2.129 이후 deprecated다.
  - *쉽게 말하면*: 안 쓰는 통로는 닫고, 쓰는 통로는 위치를 고정해 관리한다.
  - → 자세히: [7장 보안 관리](07%EC%9E%A5%20%EB%B3%B4%EC%95%88%20%EA%B4%80%EB%A6%AC.md)
- **LDAP은 도메인 계정으로 로그인해야 할 때 쓴다**: 플러그인을 설치한 뒤 Security Realm에서 LDAP을 선택하고 세부 값은 조직 IT와 정한다.
  - *쉽게 말하면*: 회사 계정 그대로 Jenkins에 로그인하게 연결하는 방법이다.
  - → 자세히: [7장 보안 관리](07%EC%9E%A5%20%EB%B3%B4%EC%95%88%20%EA%B4%80%EB%A6%AC.md)
- **자격 증명은 ID로만 꺼내 쓰는 금고다**: 기본 인증, SSH, API 토큰, 인증서 정보를 Jenkins에 저장하고 작업 코드에는 비밀을 평문으로 적지 않는다.
  - *쉽게 말하면*: 비밀번호를 코드에 쓰지 않고 이름표만 쓴다.
  - → 자세히: [8장 자격 증명 관리](08%EC%9E%A5%20%EC%9E%90%EA%B2%A9%20%EC%A6%9D%EB%AA%85%20%EA%B4%80%EB%A6%AC.md)
- **Scope와 Domain이 사용 범위를 좁힌다**: Global은 작업과 시스템 모두, System은 시스템과 노드 전용이다. Domain의 Hostname 조건은 접속 대상에 맞는 항목만 후보에 올린다.
  - *쉽게 말하면*: 누가, 어디서 이 열쇠를 쓸 수 있는지를 열쇠마다 제한한다.
  - → 자세히: [8장 자격 증명 관리](08%EC%9E%A5%20%EC%9E%90%EA%B2%A9%20%EC%A6%9D%EB%AA%85%20%EA%B4%80%EB%A6%AC.md)
- **Credentials Provider로 공용과 개인을 나눈다**: Jenkins Credentials Provider는 공용, User Credentials Provider는 만든 사용자 전용이며, Types로 만들 수 있는 종류도 제한한다.
  - *쉽게 말하면*: 공용 금고와 개인 서랍을 따로 둔다.
  - → 자세히: [8장 자격 증명 관리](08%EC%9E%A5%20%EC%9E%90%EA%B2%A9%20%EC%A6%9D%EB%AA%85%20%EA%B4%80%EB%A6%AC.md)
- **역할 기반 권한은 역할을 만들고 배정한다**: 플러그인 설치 후 `Manage Roles`에서 전역 역할과 `Item Roles`(Pattern으로 작업 범위 지정)를 만들고 `Assign Roles`에서 사용자에게 배정한다. 전역 역할의 Overall 접근도 필요하다.
  - *쉽게 말하면*: 직책별 권한 세트를 먼저 만들고 사람에게 붙인다.
  - → 자세히: [9장 사용자 관리](09%EC%9E%A5%20%EC%82%AC%EC%9A%A9%EC%9E%90%20%EA%B4%80%EB%A6%AC.md)
- **Matrix 방식은 권한 표에 직접 체크한다**: 전역 Matrix는 사용자별 표이고, Project-based Matrix는 작업별 표를 더해 `Build`와 `Read`만 허용하는 식의 세밀한 제한이 가능하다.
  - *쉽게 말하면*: 누구에게 무슨 버튼을 열어 줄지 표에서 직접 고른다.
  - → 자세히: [9장 사용자 관리](09%EC%9E%A5%20%EC%82%AC%EC%9A%A9%EC%9E%90%20%EA%B4%80%EB%A6%AC.md)

## 2. 2부를 관통하는 질문

| 질문 | 2부가 보여 주는 답 |
|------|-------------------|
| 로그인 사용자는 어디서 오나? | Security Realm: 자체 DB, 서블릿 컨테이너, LDAP, None |
| 로그인한 사람은 무엇을 할 수 있나? | Authorization: 기본 옵션, 역할 기반, Matrix, 프로젝트 기반 Matrix |
| 외부 도구 접속 정보는 어디에 두나? | 자격 증명 항목(ID로 참조), Scope와 Domain으로 범위 제한 |
| 특정 작업만 보게 하려면? | Item Roles의 Pattern, 또는 작업별 Matrix와 Inheritance Strategy |

> **2부 한 줄 요약**
> Jenkins는 출입 규칙을 정하고(7장), 외부에 접속할 비밀을 금고에 두며(8장), 팀원마다 필요한 만큼만 권한을 나눠 주는(9장) 순서로 안전하게 운영한다.
