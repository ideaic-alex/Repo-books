# 500라인 가이드라인

출처에서 제시하는 **500라인 가이드라인(The 500-Line Guideline)**은 단순한 문서 분량 제한이 아니라, 에이전트의 주의력(Attention)과 컨텍스트 예산을 효율적으로 배분하기 위한 **핵심 성능 요구사항(Performance Requirement)**입니다.

---

## 1. 500라인 가이드라인의 핵심 이유와 메커니즘

- **주의력 분산 및 지침 경합 (Attention Dilution)**: `CLAUDE.md` 파일이 500라인을 초과하면 지침들이 서로 경합하기 시작합니다. Claude Code가 비대한 파일을 무시하는 것은 아니지만, 수많은 지침으로 인해 모델의 주의력(attention)이 분산되면서 정작 가장 중요한 규칙이 거의 중요하지 않은 규칙과 동일한 비중으로 처리되는 현상이 발생합니다.
- **성능 및 이행률 저하의 신호**: 명확한 금지 규칙이 존재함에도 에이전트가 이를 무시하고 실수를 반복하거나, `CLAUDE.md`에 이미 명시된 내용을 자꾸 되물어본다면 파일이 너무 길어져 핵심 지침이 묻혔음을 의미합니다.
- **코드 형태의 유지보수 (Pruning & Tuning)**: `CLAUDE.md`는 소스 코드처럼 취급되어야 합니다. 문제 발생 시 정기적으로 가치를 잃은 지침을 가지치기(pruning)해야 하며, 반드시 준수해야 하는 핵심 규칙에는 `IMPORTANT` 또는 `YOU MUST` 같은 강조어를 사용하여 이행률을 높입니다.

---

## 2. `CLAUDE.md`와 컨텍스트 엔지니어링의 더 큰 맥락

500라인 가이드라인은 Claude Code의 전체 컨텍스트 엔지니어링(Context Engineering) 체계 속에서 다음과 같은 구조적 역할을 갖습니다.

1. **상시 로드(Always-On)에 따른 컨텍스트 비용**
   - `CLAUDE.md`는 대화 요청(turn)이 일어날 때마다 **매번 전체 내용이 시스템 프롬프트로 주입**됩니다.
   - 따라서 파일 내의 모든 줄은 세션이 진행되는 내내 컨텍스트 윈도우(에이전트의 RAM) 공간을 계속 점유하는 고정 비용을 발생시킵니다.
2. **Strict Filtering: 포함할 정보 vs 제외할 정보**
   - 500라인 예산을 유지하기 위한 핵심 기준은 **"Claude가 코드를 스스로 읽고 추론할 수 없는 정보인가?"**입니다.
   - **포함 (Include)**: 빌드/테스트 특정 명령어, 기본 표준과 다른 서식/스타일 예외, 리포지토리 에티켓, 아키텍처 결정 배경, 개발 환경 특이점(예: 포트 번호), 알려진 데이터 이상점 등.
   - **제외 (Exclude)**: 코드 파싱으로 알 수 있는 언어/프레임워크 정보, 표준 언어 컨벤션, 장황한 외부 라이브러리 문서, 일반적인 개발 절차 설명 등.
3. **`@path` 임포트 구문을 통한 가독성 분산**
   - 루트 `CLAUDE.md`를 500라인 이내로 슬림하게 유지하면서도 상세 아키텍처 가이드나 API 규격을 제공하기 위해 `@docs/architecture.md` 형태의 파일 참조 임포트 시스템을 활용합니다.
4. **자동 축소(Auto-Compaction)와 `Compact Instructions`**
   - 대화량이 많아져 컨텍스트 윈도우가 한계(약 95%)에 도달하면 대화 이력이 자동으로 요약·축소(Auto-compaction)됩니다.
   - 이 과정에서 손실되면 안 되는 핵심 규칙은 `CLAUDE.md` 내의 `Compact Instructions` 헤더 하위에 작성하여 축소 후에도 온전히 보존되도록 보호합니다.
5. **스킬(Skills) 및 서브에이전트(Subagents)와의 자원 분담**
   - 매 turn마다 필요한 지침만 `CLAUDE.md`에 남기고, 특정 작업(예: DB 마이그레이션, 배포 체크리스트)에만 필요한 참조 지침은 **스킬(Skills)**로 전환하여 호출 시에만 맥락을 소비하도록 분리합니다.

---
