# 세션 관리와 사용자 정의 도구

`query` 함수는 단발성 작업에 알맞다. 그러나 실제 애플리케이션은 여러 턴이 필요한 경우가 많다. 사용자가 먼저 문제 분석을 시키고, 결과를 본 뒤 고칠 방향을 정하고, 수정이 끝나면 검증을 시키는 식이다. 또 Claude가 기본으로 가진 Read, Write, Bash, Grep 같은 도구만으로는 데이터베이스 조회, 사내 API 호출, 알림 전송 같은 업무 기능을 다룰 수 없다.

이 문서는 세션을 이어 쓰고 갈라 쓰는 방법, 그리고 Claude의 능력 범위를 넓히는 사용자 정의 도구(Custom Tools)를 만드는 방법을 다룬다.

---

## 1. session_id로 이어 가기

첫 호출에서 스트림의 `system/init` 메시지에서 `session_id`를 꺼내 저장한다. 두 번째 호출에서는 `ClaudeAgentOptions`의 `resume`에 그 값을 넣는다. 그러면 Claude는 앞 대화의 전체 맥락, 즉 이미 읽은 파일, 거친 분석 단계, 낸 결론을 "기억"한 채로 이어 간다.

```python
if isinstance(message, SystemMessage) and message.subtype == "init":
    session_id = message.session_id          # 핵심: 세션 ID 확보
resume_options = ClaudeAgentOptions(**options.__dict__, resume=session_id)
# 두 번째 query(prompt="앞서 찾은 첫 SQL 인젝션 위험에 집중해 줘", options=resume_options)
```

원서 예제는 먼저 "src/auth의 보안 문제 분석"을 시키고, 이어서 "방금 찾은 첫 번째 SQL 인젝션 위험을 파고들어라"를 시킨다. 두 번째 프롬프트가 "방금 찾은"이라고만 해도 통하는 것은 맥락이 이어져 있기 때문이다. 맥락을 다시 설명하는 것보다 효율적이고 분석의 정확성과 일관성도 높다.

참고(노트 작성자): 원서의 `resume_options` 생성 코드는 `options.__dict__`를 펼쳐 쓰는 방식이다. 실제 사용 시에는 사용하는 SDK 버전에서 이 방식이 통하는지 확인이 필요하다. 원서가 검증 방법까지 밝히지는 않는다.

## 2. 대화 분기(fork)

`fork_session=True`를 `resume`과 함께 주면 지정한 세션의 특정 시점에서 새 세션 사본을 "갈라" 만든다. 원래 세션의 상태는 변하지 않는다. 같은 분석 결과를 출발점으로 서로 다른 방향을 탐색하되 가지끼리 독립을 유지하고 싶을 때 쓴다.

| 방향 | 분기에서 던진 질문 |
|---|---|
| A | 마이크로서비스 아키텍처로 리팩터링한다면 어떤 컴포넌트를 고쳐야 하나 |
| B | 기존 아키텍처를 유지한다면 보안을 어떻게 강화해야 하나 |

같은 `session_id`에서 두 번 분기하므로 두 방향은 완전히 독립이다. "가정 분석"이나 여러 기술안을 비교할 때 매우 유용하다. 비유하면 게임의 저장 지점에서 두 갈래 선택을 각각 해 보는 것이다.

## 3. 사용자 정의 도구의 정체

Agent SDK의 사용자 정의 도구는 본질적으로 프로세스 내(in-process) MCP 서버다. 6장에서 본 독립 배포 MCP 서버와 달리 별도 프로세스를 띄우지 않고 애플리케이션 프로세스 안에서 바로 돈다. 프로세스 간 통신 비용이 없으니 도구 호출 효율과 응답 속도가 좋아진다.

### 3-1. @tool 데코레이터로 정의하기

원서 예제는 두 가지 업무 기능을 안전한 도구로 감싼다.

| 도구 | 하는 일 | 핵심 안전장치 |
|---|---|---|
| `query_database` | 앱 DB에 읽기 전용 SQL 실행 (`query`, `limit` 입력) | SQL을 대문자로 바꿔 `SELECT`로 시작하지 않으면 `isError: True`로 거절 |
| `send_notification` | 팀 Slack 채널에 알림 전송 (`channel`, `message` 입력) | (예제에는 별도 검증 없음) |

그 뒤 `create_sdk_mcp_server(name="app-tools", version="1.0.0", tools=[...])`로 도구들을 한 서버에 묶는다. 반환값은 `{"content": [{"type": "text", "text": ...}]}` 형태이며, 오류는 `"isError": True`를 붙인다.

```python
@tool(name="query_database", description="...", input_schema={"query": str, "limit": int})
async def query_database(args):
    if not args["query"].strip().upper().startswith("SELECT"):
        return {"content": [{"type": "text", "text": "Error: Only SELECT queries allowed"}], "isError": True}
```

참고(노트 작성자): 원서의 이 예제는 `startswith("SELECT")` 검사만으로 읽기 전용을 보장한다고 보기에는 허술하다. `SELECT 1; DROP ...` 같은 문장을 막지 못할 수 있다. 원서는 이를 "보안 핵심 검증"의 예시로만 제시하며, 위 지적은 노트 작성자의 견해다. 아래 Pydantic 절의 매개변수 검증과 함께 읽는 편이 좋다.

### 3-2. 등록과 활성화

서버를 `mcp_servers={"app-tools": tools_server}`로 등록하고, 쓸 도구 이름을 `allowed_tools`에 적는다. 이름은 반드시 `mcp__{서버이름}__{도구이름}` 형식이다. 예를 들어 `mcp__app-tools__query_database`다. 이 접두어 규칙은 내장 도구(Read, Bash)와의 이름 충돌을 막고, 로그 감사나 모니터링 대시보드에서 자연스러운 분류 표지가 된다.

### 3-3. Pydantic 모델로 매개변수 검증

납작한 문자열 몇 개를 넘어서면 딕셔너리 대신 Pydantic 모델(Python의 데이터 검증 라이브러리)로 매개변수를 정의하는 것이 낫다. 딕셔너리가 표현하지 못하는 네 가지가 있다. 중첩 객체, 기본값이 있는 선택 필드, 값을 고정 집합으로 묶는 enum, 숫자 범위다. 원서의 `DatabaseQueryParams`는 `table`(필수), `columns`(기본 `["*"]`), `where`(기본 None), `limit`(기본 100, `ge=1`, `le=1000`)를 가진다. 각 제약은 Claude가 보는 스키마의 일부가 되므로, 잘못된 호출은 함수가 실행되기도 전에 거절된다. `@tool(..., input_schema=DatabaseQueryParams)`로 모델을 통째로 넘긴다.

원서 코드에는 `table` 필드 정의의 닫는 괄호가 빠져 있다. 추출 또는 조판 오류로 보고 복원해 읽었다.

## 4. 사용자 정의 도구 설계 원칙 (Kage's notes)

Claude는 도구를 예상 밖의 방식으로 부를 수 있다. 극단적인 매개변수 값을 넣거나, 짧은 시간에 수십 번 호출하거나, 한 도구의 출력을 다른 도구의 입력으로 쓰기도 한다. 그래서 세 원칙을 지킨다.

- 단일 책임: 도구 하나는 한 가지 일만 한다.
- 명확한 설명: `description`은 Claude가 읽는 "사용 설명서"다. 언제 쓸 수 있고 언제 쓰면 안 되는지를 분명히 쓴다.
- 제로 트러스트 검증: Claude가 넘긴 매개변수를 절대 믿지 말고, 도구 안에서 모든 입력을 엄격히 검증한다.

또 하나, 좋은 설명보다 권한 게이트가 필요한 도구는 다시 실행해도 결과를 되돌릴 수 없는 도구다. 삭제, 운영 환경 쓰기, 이메일이나 Slack 메시지 발송, 돈이 나가는 작업이 그렇다.

---

## 5. 핵심 정리

- `resume`에 `session_id`를 넣으면 맥락을 그대로 이어 간다. `fork_session=True`를 더하면 원본을 보존한 채 독립 가지를 만든다.
- 사용자 정의 도구는 프로세스 내 MCP 서버이며 `@tool`과 `create_sdk_mcp_server`로 만든다.
- 도구 이름은 `mcp__{server_name}__{tool_name}`이고 `allowed_tools`에 명시해야 쓸 수 있다.
- 단일 책임, 명확한 description, 제로 트러스트 검증을 지키고, 되돌릴 수 없는 작업은 권한 게이트로 막는다.
