# 메시지 유형 해석

`query`가 돌려주는 스트림은 순서가 있는 메시지의 나열이고, 각 메시지는 `type` 필드로 종류가 구분된다. Kage는 이것을 HTTP API의 상태 코드에 비유한다. HTTP를 다루는 개발자가 상태 코드를 알아야 하듯, Agent SDK 개발자는 각 메시지가 무엇을 뜻하는지 정확히 알아야 한다.

이 문서는 네 가지 메시지(system/init, assistant, user, result)와 `result`의 `subtype` 값, 그리고 이를 받아 처리하는 실용 패턴을 정리한다.

---

## 1. system/init: 세션 초기화

스트림의 첫 메시지다. 이번 세션의 설정 상태를 알려 준다.

```json
{"type": "system", "subtype": "init", "session_id": "550e8400-...",
 "model": "claude-sonnet-4-6", "tools": ["Read","Grep","Glob"], "mcp_servers": []}
```

담긴 정보는 `session_id`, 사용 모델, 쓸 수 있는 도구 목록, MCP 서버 상태다. 디버깅에서 특히 중요하다. Claude가 기대한 도구를 부르지 않는다면 가장 먼저 그 도구가 init 메시지의 `tools`에 있는지 확인한다. 정의조차 안 되어 있으면 호출될 수 없다. 또한 이 메시지의 `session_id`는 뒤에서 세션을 이어 쓸 때 열쇠가 된다.

## 2. assistant: Claude의 응답

Claude의 한 차례 응답마다 하나씩 온다. 핵심은 `message.content`가 배열이라는 점이다. 이 배열에는 두 종류의 블록이 섞여 들어간다.

| 블록 | 의미 |
|---|---|
| `text` | Claude의 사고 과정 또는 최종 출력 |
| `tool_use` | Claude가 하기로 한 행동. `id`, `name`, `input`을 가진다 |

한 assistant 메시지에 `tool_use`가 여러 개 들어 있을 수 있다. 즉 Claude는 여러 파일을 동시에 읽는 식의 병렬 작업을 한 번에 요청할 수 있다. 예를 들어 `{"type": "tool_use", "id": "toolu_xxx", "name": "Glob", "input": {"pattern": "src/auth/**/*"}}`는 "이 패턴의 파일을 찾겠다"는 요청이다.

## 3. user: 도구 실행 결과

도구가 실행되면 그 결과가 `type: "user"` 메시지로 돌아온다. 역할이 user인 이유는 모델 입장에서 도구 결과가 "바깥에서 들어온 입력"이기 때문이다(참고(노트 작성자): 이 이유 설명은 원문에 없는 풀이다). 내용은 `tool_result` 블록이며 `tool_use_id`와 `content`를 가진다.

`tool_use_id`는 assistant 메시지의 도구 호출 ID와 정확히 대응해야 한다. 이 대응은 SDK가 자동으로 관리하므로 개발자가 직접 맞출 일은 보통 없다.

## 4. result: 작업 종료

작업이 끝날 때 오는 마지막 메시지다. 담긴 값은 다음과 같다.

- `subtype`: 종료 상태
- `session_id`, `num_turns`(턴 수), `duration_ms`(전체 시간), `duration_api_ms`(API 시간)
- `total_cost_usd`: 비용. 원서 예시는 0.0342달러
- `usage`: `input_tokens`, `output_tokens`, `cache_read_input_tokens`(캐시에서 읽은 토큰)
- `result`: 최종 텍스트
- `structured_output`: 구조화된 출력을 요청했을 때 채워진다(요청하지 않으면 null)

`subtype`은 종료 상태를 판정하는 핵심 필드다(원서 표 8.1).

| subtype | 의미 |
|---|---|
| `success` | 정상 완료 |
| `error_max_turns` | 최대 턴 제한(`--max-turns`)에 도달 |
| `error_max_budget_usd` | 비용 한도에 도달 |
| `error_during_execution` | 실행 중 오류 발생 |
| `error_max_structured_output_retries` | 구조화된 출력 검증 실패(재시도 횟수 초과) |

원서 표에서는 마지막 값이 줄바꿈으로 `error_max_structured_outp / ut_retries`처럼 끊겨 인쇄되어 있다. 본문 뒤쪽(구조화된 출력 절)에 같은 값이 온전히 나와 그 철자로 복원했다.

## 5. 메시지 처리 패턴

원서는 비동기 스트림에서 텍스트 수집, 도구 호출 기록, 세션 메타데이터 저장을 한 번에 하는 함수 `process_query`를 보여 준다. 구조는 다음과 같다.

1. 결과 상자 `{"text": [], "tools": [], "metadata": {}, "error": None}`를 만든다.
2. 스트림을 돌며 `AssistantMessage`이면 블록을 훑는다. `text`가 있으면 텍스트 목록에, `name`이 있으면(도구 호출이면) 도구 이름과 입력을 도구 목록에 넣는다.
3. `ResultMessage`이면 `session_id`, 비용, 턴 수, 소요 시간을 `metadata`에 넣는다. `message.is_error`가 참이면 `subtype`을 `error`에 기록한다.
4. 결과 상자를 반환한다.

이 패턴의 가치는 "화면 출력"과 "기록"을 분리한다는 데 있다. 웹 서비스라면 텍스트는 사용자에게 흘려 보내고, 도구 목록과 비용은 로그나 과금 시스템으로 보낼 수 있다. 참고(노트 작성자): 원서 코드의 마지막 `return result`는 들여쓰기가 함수 밖으로 인쇄되어 있다. 추출 또는 조판 오류로 보고 함수 안으로 복원해 이해했다.

---

## 6. 핵심 정리

- 스트림은 system/init, assistant, user, result 순서로 흐른다. 한 번의 작업 중 assistant와 user가 여러 번 번갈아 나온다.
- 도구가 동작하지 않으면 init 메시지의 `tools`부터 본다.
- assistant의 `content`는 text와 tool_use가 섞인 배열이고, tool_use는 한 메시지에 여러 개일 수 있다.
- 종료 판정은 result의 `subtype`으로 한다. 턴 초과, 예산 초과, 실행 오류, 구조화 출력 실패를 구분해서 대응한다.
