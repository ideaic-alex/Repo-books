# 4계층 구조 모델

Claude Code 전체를 하나의 지도로 보려면 네 개의 층으로 나누어 보면 된다. 아래에서 위로 메모리 계층, 확장 계층, 통합 계층, 프로그래밍 계층이다. 그 위에 층을 가로지르는 더 근본적인 관점으로 하니스(harness)와 에이전틱 루프(agentic loop)가 있다. 이 문서는 각 층이 무엇이고 어디서 끝나는지, 그리고 하니스 개념이 왜 중요한지를 정리한다.

Kage는 네 층을 고층 건물에 비유한다. 메모리 계층은 땅속 기초, 확장 계층은 일상 기능을 떠받치는 본 층들, 통합 계층은 눈에 띄지 않지만 건물을 바깥 인프라와 잇는 수도와 전기망, 프로그래밍 계층은 꼭대기 층의 건축가 작업실이다. 아래에서 위로 보면 건설자의 관점(기초와 지지), 위에서 아래로 보면 사용자의 관점(기능과 경험)이라는 점도 기억해 둘 만하다.

---

## 1. 메모리 계층: CLAUDE.md 시스템

Claude는 상태를 갖지 않는(stateless) 모델이다. 새 대화가 열릴 때마다 프로젝트 배경, 기술 스택, 코드 표준, 팀 규칙을 전혀 모른다. 설정이 없으면 "JavaScript 말고 TypeScript", "npm 말고 pnpm", "테스트는 Vitest" 같은 기본 설정을 매번 다시 말해야 한다.

해법이 CLAUDE.md 파일이다. 'AI를 위한 직원 안내서'에 해당하며 대화가 시작될 때마다 컨텍스트에 자동으로 실린다. 이 기억은 한 덩어리가 아니라 5단계 계층이고, 단계마다 적용 범위가 다르다. 설계 철학은 CSS의 캐스케이딩 우선순위나 '전역-사용자-프로젝트-로컬' 4단계 덮어쓰기 설정 모델과 비슷하다. 각 단계는 앞 단계 설정을 덮어쓸 수 있고, 구체적일수록(로컬일수록) 우선순위가 높다. 5단계의 구체 내용은 2장에서 다룬다.

원서가 보여 주는 프로젝트 수준 CLAUDE.md의 항목은 다음과 같다.

| 절 | 담긴 내용 |
|---|---|
| Tech Stack | TypeScript 5.x(strict), Fastify + Prisma, Vitest(공개 함수는 단위 테스트 필수), pnpm(npm과 yarn 금지) |
| Code Standards | 함수형 컴포넌트 선호(클래스 컴포넌트 금지), 오류는 Result 타입으로 반환(예외 직접 throw 엄금), 커밋 형식 `<type>(<scope>): <description>` |
| Common Commands | `pnpm dev`, `pnpm test`, `pnpm lint` |

Xiaoxue는 "CLAUDE.md를 만든 뒤로는 pnpm을 쓰지 npm이 아니라고 매번 일러 줄 필요가 없다"고 말한다. 이 단순한 장치가 전체 프레임워크의 주춧돌이다. 스킬, 커맨드, 훅 같은 위층 설정은 모두 Claude가 프로젝트 맥락을 정확히 이해한다는 전제 위에 서 있다.

## 2. 확장 계층: 네 가지 확장 구성 요소

확장 계층은 건물의 본체다. 커맨드(Commands, 슬래시 명령), 스킬, 서브에이전트, 훅 네 가지가 독립적으로 작동하면서도 자유롭게 조합된다.

### 2-1. 커맨드

`/review`, `/commit`, `/deploy`처럼 입력하면 미리 정한 템플릿대로 표준 워크플로를 실행한다. 자주 쓰는 고정 절차를 '원클릭' 단축키로 묶은 것이다. 설계 패턴으로는 요청을 객체로 캡슐화하는 커맨드 패턴의 교과서적 적용이다. 정의 파일은 `.claude/commands/` 디렉터리에 두며 마크다운 파일 하나가 명령 하나다. 예를 들어 `review.md`에 점검 목록과 출력 형식을 적어 두면 `/review` 입력만으로 항목별 리뷰가 진행된다.

Kage의 노트에 따르면 현재 Claude Code에서는 사용자 정의 커맨드도 스킬 시스템으로 구현된다. 책은 그래도 '수동으로 부르는 슬래시 워크플로'(의미로 자동 발동하는 스킬과 대비되는)를 개념상 별도 트리거 방식으로 따로 언급한다.

### 2-2. 스킬

스킬은 `.claude/skills/<skill-name>/SKILL.md`에 있다(예전 `.claude/commands/` 위치도 여전히 동작). 서브에이전트 정의는 `.claude/agents/<agent-name>.md`에 있다. 스킬은 사용자가 손으로 호출하지 않아도 Claude가 현재 작업의 의미 맥락을 보고 관련 스킬을 알아서 판단해 불러온다. 스킬은 SKILL.md를 담은 디렉터리이며, 파일 맨 위의 YAML 프런트매터(메타데이터)에 이름, 설명, 허용 도구 목록을 선언한다. Claude는 description 필드를 보고 '이 작업에 이 스킬을 켤지'를 동적으로 정한다. 이 암묵적 트리거 덕분에 금융 분석법, API 설계 표준, 특정 프레임워크의 모범 사례 같은 도메인 지식을 담는 그릇으로 적합하다.

금융 지표를 이야기하면 '금융 스킬'이 자동으로 로드되고, 주제가 코드 구조로 넘어가면 그 스킬은 조용히 물러난다. 필요할 때 로딩하고 쓰이지 않을 때는 침묵하는 방식이다. 원서의 SKILL.md 예시는 name이 `code-reviewing`, description이 "모범 사례와 잠재 문제를 리뷰한다. 사용자가 코드 리뷰를 요청하거나 변경 검토를 언급할 때 쓴다", allowed-tools가 Read, Grep, Glob이며, 본문은 'Code Review Guidelines'로 시작한다.

### 2-3. 서브에이전트

서브에이전트(sub-agent)는 더 깊은 병목인 컨텍스트 윈도 한계를 겨냥한다. 컨텍스트 윈도는 크기가 정해진 책상과 같아서 파일을 쌓을수록 어지러워진다. PR 전체의 변경분을 리뷰하듯 파일이 아주 많은 작업을 본 대화에 몰아 넣으면 책상이 넘쳐 Claude가 중요한 정보를 놓친다.

해법은 특정 작업용으로 독립된 컨텍스트 공간을 만드는 것이다. 주 책상 옆에 새 작업대를 놓고 전문가에게 하위 작업을 맡기는 셈이다. 끝나면 초안 전체가 아니라 결론(간결한 보고)만 주 책상으로 돌려보낸다. 관리자가 코드 줄 하나하나를 보지 않고 리뷰 결론과 개선 제안만 받는 것과 같다.

정의 파일은 `.claude/agents/`에 두며 파일 하나마다 역할, 권한 범위, 행동 지침을 적는다. 서브에이전트에는 엄격한 도구 권한을 줄 수 있다. 예컨대 '코드 리뷰어'는 파일 읽기만 허용하고 수정은 절대 금지한다. 이는 AI 에이전트 설계의 핵심인 최소 권한 원칙을 잘 드러낸다.

### 2-4. 훅

훅은 네 구성 요소 중 '가로채기' 능력이 있는 유일한 요소다. 커맨드가 Claude가 '무엇을' 하는지를 정하고, 스킬이 '어떻게' 하는지를 안내한다면, 훅은 '해도 되는지'를 정한다.

훅은 특정 이벤트 지점에서 자동 발동한다. 가장 자주 쓰는 것은 도구 호출 전(PreToolUse), 도구 호출 후(PostToolUse), 응답 생성이 끝나기 전(Stop)이다. 전체 이벤트 목록은 Claude Code의 훅 레퍼런스 문서에 있다. 웹 프레임워크의 미들웨어와 매우 닮았다. `.claude/settings.json`에 훅을 걸어 두면, 예컨대 Claude가 `git commit`을 실행하려 할 때 린트 검사를 자동으로 돌리고 실패하면 커밋을 막을 수 있다.

원서의 설정 예시는 아래와 같다. Bash 도구를 호출하려 할 때마다 `safety_check.py`가 먼저 돈다는 뜻이다.

```json
{ "hooks": { "PreToolUse": [ { "matcher": "Bash",
  "hooks": [ { "type": "command",
               "command": "python .claude/hooks/safety_check.py" } ] } ] } }
```

항목의 모양에 주의해야 한다. `matcher`와 `hooks` 배열이 짝을 이루고 각 원소가 자기 `type`과 `command`를 선언한다. '차단(blocking)' 필드는 따로 없다. 훅은 종료 코드 2로 끝나는 방식으로 도구 호출을 막고, stderr에 쓴 내용이 이유로 Claude에게 되돌아간다. 이 규약은 5장에서 상세히 다룬다. 원서는 훅의 정체를 Git 훅, 데이터베이스 트리거, 메시지 큐 소비자와 같은 '이벤트가 일어나면 미리 정한 논리를 실행한다'는 통일된 패턴이라고 짚는다.

### 2-5. 직교성과 학습 순서

네 요소는 직교(orthogonal)한다. 각자 따로 배우고 따로 쓸 수 있으면서 조합하면 더 강한 워크플로가 된다. 이는 소프트웨어 공학의 단일 책임 원칙(SRP)을 따른 설계다. 각 요소가 한 가지 문제를 잘 풀고, 유기적으로 결합하면 능력이 거의 무한해진다.

Kage의 학습 순서 조언은 이렇다. 처음에는 네 가지를 한꺼번에 익히려 하지 말고 다음 순서를 밟는다.

1. 탄탄한 CLAUDE.md를 쓴다.
2. 가장 직관적인 확장 방법인 커맨드를 익힌다.
3. 스킬로 의미 기반 자동 트리거를 경험한다.
4. 훅으로 안전과 품질의 안전망을 세운다.
5. 마지막으로 서브에이전트에 도전해 대규모 복잡한 작업을 처리한다.

각 요소를 익힐 때마다 실제 프로젝트에서 2주는 써 본 뒤 다음 단계로 넘어갈 것을 권한다. 욕심내어 한꺼번에 씹으면 체한다는 것이다.

## 3. 통합 계층: 바깥 세계와 연결

통합 계층은 건물의 수도와 전기망이다. 핵심은 헤드리스(Headless)와 MCP 두 기둥이다.

### 3-1. 헤드리스

헤드리스는 대화형 터미널 없이 사람이 없는 환경에서 자동 실행하게 한다. `-p`로 작업 설명을 넘기고 `--output-format json`으로 출력 형식을 정하면 GitHub Actions, Jenkins, GitLab CI 같은 어떤 CI/CD 파이프라인에도 끼워 넣을 수 있다. 대표 사례는 PR 자동 리뷰다. 개발자가 PR을 올리면 CI가 Claude Code를 호출해 리뷰하고 결과를 PR 페이지에 댓글로 남긴다. 사람 개입이 전혀 없다. 원서의 호출 예는 다음과 같다.

```bash
claude -p "Review the most recent code changes, focusing on security risks and performance issues" \
  --output-format json --max-turns 10 --allowedTools Read,Grep,Glob
```

| 옵션 | 공학적 의도 |
|---|---|
| `-p` | 헤드리스 모드를 켜 비대화형으로 실행한다 |
| `--output-format json` | 출력을 스크립트가 자동으로 파싱할 수 있게 한다 |
| `--max-turns` | 상호작용 최대 횟수를 제한해 비용을 정밀하게 통제한다 |
| `--allowedTools` | 허용 목록(화이트리스트)으로 Claude가 부를 수 있는 도구 범위를 엄격히 좁혀 강한 보안 장벽을 세운다 |

### 3-2. MCP

MCP는 통합의 다른 차원을 연다. 헤드리스가 Claude를 '밖으로 나가' 파이프라인에 들어가게 한다면, MCP는 외부 능력을 '안으로 들여' 모델을 강하게 만든다. 프로젝트 루트의 `.mcp.json`에 MCP 서버(외부 도구나 데이터를 Claude에 노출하는 프로그램)를 설정하면 데이터베이스 접근, 타사 API 호출, GitHub 이슈 조작, Jira 티켓 조회가 한 번의 설정으로 연결된다. Anthropic은 MCP를 'AI 시대의 USB-C'에 비유한다.

원서의 GitHub MCP 서버 설정은 `mcpServers.github`에 `command: "npx"`, `args: ["-y", "@modelcontextprotocol/server-github"]`, `env.GITHUB_TOKEN`을 두는 모양이다. 토큰 자리에는 반드시 자리표시자(`your-token-here`)만 쓰고 실제 값을 파일에 적어 넣지 않는다.

MCP 이전에는 외부 시스템마다 맞춤 어댑터 코드를 많이 짜야 했다. MCP는 Tools, Resources, Prompts라는 세 가지 핵심 능력을 표준 프로토콜로 정의해 도구 제공자와 AI 소비자 사이의 인터페이스를 통일한다. 웹 시대에 REST API가 프런트와 백엔드 통신을 통일한 것과 닮았고, 표준화는 제약이 아니라 생태계를 키운다는 것이 책의 논지다.

| 기둥 | 지향 | 방향 |
|---|---|---|
| 헤드리스 | 자동화 파이프라인 | Claude Code를 기존 CI/CD 시스템에 심는다 |
| MCP | 도구 생태계 | 외부 데이터와 서비스를 Claude Code의 도구함에 들여온다 |

확장 계층이 Claude Code의 핵심 기능을 '안에서' 강화한다면 통합 계층은 '밖으로' 연결망을 짠다. 둘은 서로 보완하며 어느 쪽도 빠질 수 없다.

## 4. 프로그래밍 계층: Agent SDK

꼭대기 층의 Agent SDK는 중요한 분수령이다. 아래 세 계층에서는 설정 파일과 명령줄로 Claude의 행동 경계를 넓힐 뿐, 개발자는 본질적으로 사용자다. Agent SDK를 넘으면 Python이나 TypeScript로 코드를 쓰며 Claude Code의 핵심 능력을 직접 호출해 새 AI 에이전트를 처음부터 짓는 건축가가 된다.

원서 예제는 코드 건강 점검 에이전트다. 핵심 구조만 옮기면 이렇다.

```python
options = ClaudeAgentOptions(allowed_tools=["Read","Grep","Glob"], max_turns=15)
async for message in query(prompt="Analyze the code quality of all Python files under src/ ...",
                           options=options):
    ...  # AssistantMessage면 text를 출력, ResultMessage면 total_cost_usd를 출력
```

의미는 이렇다. 개발자가 Claude Code의 터미널 화면에 갇히지 않고 자기 애플리케이션 안에서 Claude를 직접 구동한다. 예약 작업, 웹 서비스, 데이터 처리 파이프라인처럼 코드가 닿는 곳이면 어디든 Claude의 능력이 닿는다. 대부분의 개발자에게는 앞의 세 계층이면 일상 개발에 충분하다. 팀 수준의 AI 개발 플랫폼이나 다중 에이전트 협업 자동화를 만들 생각이라면 Agent SDK가 필수 경로다. 일괄 코드 리뷰 도구, 프로젝트 건강 대시보드, 테스트 보고서 생성기를 만들 수 있고, 코드를 읽는 에이전트, 테스트를 쓰는 에이전트, 리뷰하는 에이전트를 이어 완전 자동 파이프라인을 짤 수도 있다.

흥미로운 사실이 하나 있다. Claude Code와 Agent SDK는 같은 에이전트 루프, 같은 도구, 같은 컨텍스트 관리를 돌린다. SDK는 그 런타임을 라이브러리로 포장해 개발자가 Claude Code를 구동하는 하니스와 같은 것을 자기 애플리케이션에 심게 한 것이다. 터미널에서 보는 파일 읽기, 코드 쓰기, 명령 실행은 본질적으로 SDK 층의 도구 호출이다. 이것을 이해하면 Claude Code를 '제품'이 아니라 '아키텍처 패턴의 구체적 구현'으로 보게 된다. 설정 주도에서 코드 주도로 넘어가는 출발점이 이 계층이다.

## 5. 밑바탕의 관점: 하니스와 에이전틱 루프

Anthropic 공식 문서는 간결하게 정의한다. Claude Code는 Claude를 둘러싼 에이전틱 하니스로, 언어 모델을 유능한 코딩 에이전트로 바꿔 주는 도구, 컨텍스트 관리, 실행 환경을 제공한다. 순수한 모델은 텍스트만 생성한다. 파일을 읽고, 코드를 쓰고, 코드베이스를 검색하고, 터미널 명령을 돌리는 '손발'을 주는 것이 하니스다. 하니스가 없으면 Claude는 지능은 있으나 행동하지 못하는 '두뇌'일 뿐이다.

harness의 원뜻은 말에 채우는 마구(고삐와 끈)다. 말은 힘이 있어도 마구의 인도가 없으면 마차를 끌지 못한다. 마구는 말의 힘 자체를 바꾸지 않고 그 힘이 전달되고 제어되는 방식을 바꾼다. 공식으로 쓰면 다음과 같다.

**Agent = Model + Harness**

모델이 엔진이라면 하니스는 엔진을 둘러싼 모든 기반 시설이다. 도구 체계, 권한 통제, 컨텍스트 관리, 세션 지속, 이벤트 훅, 그리고 이 모두를 구동하는 핵심 루프인 에이전틱 루프(Agentic Loop)가 그것이다.

### 5-1. 에이전틱 루프

원서의 그림 1.4가 보여 주는 에이전틱 루프의 핵심은 '관찰, 가설, 검증'의 반복이다. 버그를 제출하면 Claude Code는 한 번 훑어보고 답을 짐작하지 않는다. 오류 로그를 먼저 보고, 관련 코드를 검색하고, 맥락을 깊이 이해한 다음에야 수정에 들어간다.

루프가 끝나는 조건은 두 가지다.

| 종료 조건 | 설명 |
|---|---|
| 모델이 스스로 멈춤 | 작업이 끝났다고 판단하고 더 이상 도구 호출을 하지 않는다 |
| 최대 턴 수 도달 | `--max-turns` 매개변수로 정한 상한에 닿아 무한 루프를 막는다 |

### 5-2. 하니스가 모델보다 중요하다는 근거

책은 최근 벤치마크를 근거로 든다. 모델을 그대로 두고 하니스만 바꿔도 에이전트 성능이 크게 달라진다는 것이다. Terminal-Bench 2.0에서 하니스 최적화만으로 같은 모델이 30위권에서 상위 5위권으로 올랐고, 점수는 52.8%에서 66.5%로 13.7포인트 올랐다. 출처로 LangChain의 'improving deep agents with harness engineering' 글이 인용된다. 그래서 책은 하니스가 모델 자체보다 중요하다고 말한다.

앞서 배운 4계층의 모든 고리, 곧 CLAUDE.md 작성, 도구 권한 설정, 훅 연동, MCP 연결은 본질적으로 하니스를 정교하게 다듬는 일이다. Xiaobing는 "Claude Code가 그저 Claude 모델의 껍데기인 줄 알았는데, 그 껍데기가 진짜 가치가 있는 곳이었다"고 깨닫는다.
