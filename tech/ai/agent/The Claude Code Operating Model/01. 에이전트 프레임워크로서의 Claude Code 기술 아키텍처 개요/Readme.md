# 에이전트 프레임워크로서의 Claude Code 기술 아키텍처 개요

이 장은 Claude Code를 '명령줄 채팅 도구'가 아니라 프로그래밍 가능하고 확장 가능하고 조합 가능한 에이전트 프레임워크로 보는 관점을 세운다. Xiaobing가 겪은 기억 상실, 스타일 흔들림, 맥락 넘침이라는 세 문제에서 출발해, 이를 해결하는 장치를 메모리, 확장, 통합, 프로그래밍의 4계층 지도에 올려 놓는다.

이어서 모든 계층을 가로지르는 개념인 하니스와 에이전틱 루프를 설명하고, 구성 요소의 트리거 차이와 요청이 흐르는 경로, 플러그인의 위치, 상황별 기술 선택 기준을 정리한다. 책 전체의 지도 역할을 하는 장이다.

---

## 1. 핵심 요점

- 세 문제(기억 상실, 스타일 흔들림, 긴 작업의 맥락 넘침)는 모두 Claude Code를 채팅 도구로 오해한 데서 나온다. 해법은 사용 습관이 아니라 구성(configuration)이다.
- 4계층은 아래부터 메모리(CLAUDE.md 5단계 계층), 확장(커맨드, 스킬, 서브에이전트, 훅), 통합(헤드리스 모드와 MCP), 프로그래밍(Agent SDK)이다.
- 확장 구성 요소 네 가지는 직교하며 단일 책임을 진다. 커맨드는 무엇을, 스킬은 어떻게, 훅은 해도 되는지, 서브에이전트는 누가 하는지를 맡는다.
- 커맨드와 훅은 결정적 트리거, 스킬과 서브에이전트는 AI 판단 트리거다. 보안이 중요하면 훅을, 유연성이 필요하면 스킬을 우선한다.
- Agent = Model + Harness. 하니스가 모델에게 손발(도구), 컨텍스트 관리, 실행 환경을 준다. 에이전틱 루프는 관찰, 가설, 검증을 반복하며 모델이 멈추거나 `--max-turns`에 닿으면 끝난다.
- 같은 모델에서 하니스만 최적화해도 Terminal-Bench 2.0 점수가 52.8%에서 66.5%로 올랐다는 사례로 하니스의 중요성을 보인다.
- 플러그인은 새 능력이 아니라 `plugin.json`으로 묶는 포장과 배포 방식이다. 개인에게는 선택, 팀 리더에게는 표준화 도구다.
- 선택 원칙은 '가장 단순한 해법으로 지금 문제를 푼다'이다. 과잉 설계와 과소 설계는 똑같이 해롭다.
