# 요약과 핵심 개념

1장은 관점을 바꾸는 장이다. Claude Code를 대화창으로 쓰던 사용자가 그 밑의 4계층 구조와 하니스를 보게 되고, 요구에 따라 알맞은 구성 요소를 고르는 사람으로 바뀐다. 이 문서는 장 전체 흐름과 핵심 개념을 한 번에 되짚고, 원서가 남긴 반성 질문 세 가지를 정리한다.

원서의 요약은 이렇게 이어진다. Claude Code는 명령줄판 ChatGPT가 아니라 프로그래밍, 확장, 조합이 가능한 에이전트 프레임워크이며, 4계층이 전체 시스템의 청사진을 준다. 구성 요소의 관계를 분명히 하는 것이 이 장에서 내면화할 핵심 지식이고, 다음 장은 모든 것의 주춧돌인 메모리 시스템(CLAUDE.md)을 다룬다.

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | Xiaobing의 세 문제 | 기억 상실, 스타일 흔들림, 맥락 넘침의 뿌리가 '채팅 도구로 오해'임을 확인 |
| 2 | 빙산 비유 | 수면 위(대화)와 물 밑(CLAUDE.md, 스킬, 서브에이전트, 훅, MCP, 헤드리스, SDK, 플러그인)의 구분 |
| 3 | 4계층 모델 | 메모리, 확장, 통합, 프로그래밍 계층 각각의 역할과 설정 형태 파악 |
| 4 | 하니스와 에이전틱 루프 | Agent = Model + Harness, 관찰-가설-검증의 반복 루프, 종료 조건 두 가지 |
| 5 | 구성 요소 관계 | 트리거 비교, 요청 한 건의 흐름, 관심사 분리 |
| 6 | 플러그인 | 능력이 아니라 배포 형태임을 정리 |
| 7 | 기술 선택 | 결정 트리와 시나리오 표로 최소 해법 고르기 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 에이전트 프레임워크 | 기억, 스킬, 위임, 훅, 외부 도구 연결을 갖춘 틀. Claude Code가 여기에 해당한다 |
| 프로그래밍/확장/조합 가능 | 코드로 구동, 설정으로 능력 주입, 블록처럼 엮기라는 세 가지 성질 |
| 4계층 모델 | 아래부터 메모리, 확장, 통합, 프로그래밍. 고층 건물 비유 |
| CLAUDE.md | 매 세션 자동으로 컨텍스트에 실리는 'AI용 직원 안내서'. 5단계 계층이며 구체적일수록 우선 |
| 커맨드 | `.claude/commands/`의 마크다운으로 정의하는 수동 슬래시 명령. 현재는 스킬로 구현된다 |
| 스킬(Skills) | `.claude/skills/<name>/SKILL.md`. description을 보고 Claude가 자동으로 로드한다 |
| 서브에이전트 | `.claude/agents/<name>.md`. 독립 컨텍스트에서 일하고 결론만 돌려보내며 도구 권한을 제한한다 |
| 훅(Hooks) | PreToolUse, PostToolUse, Stop 등 이벤트에서 발동. 종료 코드 2로 차단하고 stderr가 이유로 전달된다 |
| 헤드리스 모드 | `claude -p`로 비대화형 실행. `--output-format json`, `--max-turns`, `--allowedTools`와 함께 쓴다 |
| MCP | Tools, Resources, Prompts를 표준화한 프로토콜. `.mcp.json`에 서버를 설정하며 'AI 시대의 USB-C' |
| Agent SDK | Python/TypeScript로 Claude Code의 런타임을 라이브러리로 쓰는 계층. 설정 주도에서 코드 주도로 넘어가는 분수령 |
| 하니스(harness) | 모델 밖의 모든 기반 시설(도구, 권한, 컨텍스트, 세션, 훅, 루프) |
| 에이전틱 루프 | 관찰, 가설, 검증을 반복하는 핵심 루프. 모델이 멈추거나 최대 턴에 닿으면 종료 |
| 플러그인 | `plugin.json`으로 구성 요소를 묶어 한 번에 설치하게 하는 포장 방식 |

## 3. 반성 질문 정리

원서의 반성 질문(Reflection questions) 세 가지를 풀어 쓰면 다음과 같다. 정답이 있는 문제가 아니라 자기 환경에 대입해 보는 질문이다.

1. 지금 Claude Code(또는 다른 AI 프로그래밍 도구) 습관 중 아직 '빙산 위'의 수동 상호작용에 머문 것은 무엇인가. 이 장의 구성 요소를 들이면 어떤 단계를 자동화하거나 구조적으로 고칠 수 있는가.
2. 팀의 일상 개발 흐름에서 훅으로 자동 경비를 세우기 좋은 단계(코드 표준 검사, 민감 정보 차단 등)와 커맨드로 굳혀 명시적으로 부르기 좋은 단계는 각각 무엇인가. 구체적 시나리오 3~5개를 적고 각각 가장 알맞은 구성 요소를 짝지어 본다.
3. 네 구성 요소가 단일 책임 원칙을 따른다고 했다. 만약 스킬과 커맨드를 하나로 합쳐(수동 호출과 자동 반응을 모두 지원) 보면 어떤 편의가 생기고 어떤 문제가 생길 수 있는가. 이는 소프트웨어 설계의 '단순함 대 직교성' 고전적 트레이드오프를 보여 준다.

참고(노트 작성자): 3번 질문에서 현재 Claude Code는 이미 커맨드를 스킬 시스템으로 구현한다는 책의 노트(Kage's notes)가 있다. 질문은 개념 수준에서 두 트리거 방식을 합칠 때의 득실을 생각해 보라는 취지로 읽으면 된다.

## 4. 자주 놓치는 점

- 플러그인을 '고급 스킬'로 착각하기 쉽다. 스킬은 능력의 종류, 플러그인은 배포 형태다.
- 훅 설정에는 '차단(blocking)' 필드가 없다. 종료 코드 2와 stderr가 차단 규약이다.
- 커맨드와 훅은 결정적, 스킬과 서브에이전트는 AI 판단이라는 구분을 잊으면 보안 요구에 스킬을 잘못 쓰게 된다.
- 에이전틱 루프는 `--max-turns`가 없으면 모델이 멈추기만을 기다리게 된다. 헤드리스 자동화에는 반드시 상한이 필요하다.
- 구성 요소는 다 쓰는 것이 목표가 아니다. 단순한 작업은 CLAUDE.md와 스킬이면 충분하고, 일상 커밋은 훅 하나로도 된다.
- 네 계층은 서로 쌓이지만 한꺼번에 익힐 필요는 없다. 권장 순서는 CLAUDE.md, 커맨드, 스킬, 훅, 서브에이전트이며 단계마다 2주 실습이다.
- MCP 설정의 토큰 같은 비밀 값은 자리표시자로만 쓰고 실제 값을 파일에 커밋하지 않는다.
- 원서의 표 1.1과 1.2는 PDF 추출에서 칸이 뒤섞여 있다. 이 노트의 표는 내용에 맞춰 복원한 것이다.
