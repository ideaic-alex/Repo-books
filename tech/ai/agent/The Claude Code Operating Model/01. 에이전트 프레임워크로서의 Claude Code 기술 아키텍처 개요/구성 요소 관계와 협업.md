# 구성 요소 관계와 협업

각 부품을 따로 이해한 다음에는 더 중요한 질문이 남는다. 부품들은 어떻게 함께 일하는가, 상황마다 무엇을 골라야 하는가, 실제 작업 하나는 이 체계를 어떻게 통과하는가. 이 문서는 네 가지 확장 구성 요소의 트리거(작동 계기) 비교, 요청 하나가 흘러가는 경로, 그리고 플러그인의 위치를 다룬다.

핵심 한 줄은 '플러그인은 새 능력이 아니라 포장 방식'이라는 것이다. 트리거를 구분하는 법을 먼저 익히면 이 말이 자연스럽게 이해된다.

---

## 1. 트리거 방식 비교

네 가지 확장 구성 요소에서 가장 헷갈리는 부분이 트리거다. 원서의 표 1.1은 다섯 항목으로 비교한다. 이 표는 PDF 추출 과정에서 칸이 뒤섞여 있어, 아래는 내용을 맞춰 복원한 것이다. 복원이 불확실한 칸은 표시했다.

| 비교 항목 | 커맨드 | 스킬 | 서브에이전트 | 훅 |
|---|---|---|---|---|
| 누가 일으키나 | 사람이 수동 입력 | AI가 의미를 보고 자동 매칭 | 사용자 지정 또는 Claude가 능동적으로 위임 | 시스템 이벤트가 자동 발동 |
| 이름을 외워야 하나 | 예(명령 이름을 알아야 함) | 아니오(자동 발견) | 예(에이전트 이름을 알아야 함) | 아니오(설정하면 바로 유효) |
| 대표 예 | `/review`, `/deploy` | 금융 분석, API 설계 | 코드 리뷰, 로그 분석 | 커밋 전 점검, 저장 후 포매팅 |
| 공학적 비유 | CLI 명령 | 전략 패턴(알고리즘 자동 선택) | 스레드 풀(격리 실행) | 미들웨어, Git 훅 |

참고(노트 작성자): 원서 표 1.1의 마지막 행인 '추천 구성 요소'와 '적용 시나리오'는 추출본에서 칸이 흩어져 있어 위 표에서 뺐다. 적용 시나리오는 '기술 선택 가이드' 문서의 표 1.2 정리에서 따로 정리했다. 또 '대표 예'와 '공학적 비유' 칸의 열 정렬은 문맥으로 맞춘 것이다.

기억하기 쉬운 표어는 다음과 같다.

| 요소 | 표어 |
|---|---|
| 커맨드 | "네가 시킨다" (사용자 명령에 응답) |
| 스킬 | "스스로 알아서 한다" (자율적으로 판단하고 실행) |
| 서브에이전트 | "남에게 맡긴다" (하위 에이전트를 조율해 완수) |
| 훅 | "누가 하든 이 단계에서 점검은 실행된다" (특정 워크플로 지점에서 자동 가로채기나 처리) |

### 결정적 트리거와 AI 판단 트리거

Xiaoxue가 핵심을 짚는다. 커맨드와 훅은 결정적(deterministic) 트리거다. 하나는 사용자 명령으로, 다른 하나는 특정 이벤트로 분명하게 발동한다. 스킬과 서브에이전트는 AI의 자율 판단이 끼어든다. AI가 필요하다고 보면 스킬이 켜지고, 위임하기로 결정하면 서브에이전트가 일한다. Kage도 이 이분법이 네 구성 요소의 차이를 이해하는 또 하나의 열쇠라고 인정한다. 실무 지침은 이렇다.

- 보안 요구가 아주 높은 경우(민감 정보 차단 등)에는 결정적인 훅을 우선한다.
- 유연성이 더 필요한 경우(도메인 지식 매칭 등)에는 AI 판단으로 트리거되는 스킬이 맞다.

## 2. 데이터 흐름: 요청 하나의 여정

각 구성 요소가 어떻게 협업하는지 보려고 원서는 구체적인 요청 하나를 따라간다. 개발자가 터미널에 이렇게 입력했다고 하자. "src/payment/ 디렉터리의 최근 코드 변경을 리뷰해서 보안 위험이 없는지 확인해 줘." 원서의 그림 1.5가 보여 주는 처리 흐름에서 메모리 계층과 확장 계층의 구성 요소는 각자 역할을 한다.

| 구성 요소 | 이 요청에서의 역할 |
|---|---|
| 메모리 계층(CLAUDE.md) | 프로젝트 맥락을 세운다 |
| 스킬 | 도메인 지식을 주입한다 |
| 서브에이전트 | 격리된 실행 환경을 제공한다 |
| 훅 | 품질 검문소를 엄격히 지킨다 |

사용자가 자연어 한 줄을 입력한 뒤에는 추가 개입이 필요 없고 모든 것이 자동으로 조율된다. 이것이 '조합 가능성'의 본질이다. 각 구성 요소는 독립된 블록이고, 합치면 완결된 자동화 파이프라인이 된다. 소프트웨어 공학의 고전 원칙인 관심사 분리(Separation of Concerns)와도 맞는다. 모듈마다 책임이 하나이고 명확한 인터페이스로 협업한다는 뜻이다. 책이 정리한 책임 분담은 다음과 같다.

- CLAUDE.md는 '무엇을 아는가(know-what)'에 집중한다.
- 스킬은 '어떻게 하는가(know-how)'에 집중한다.
- 서브에이전트는 '누가 하는가(who-does-it)'에 집중한다.
- 훅은 '가드레일(guard-rails)'에 집중한다.

경계가 분명하기에 서로 간섭하지 않고 자유롭게 조합된다. 다만 위 예는 '올인원' 협업 장면이라는 점에 유의한다. 실제로 대부분의 작업은 모든 구성 요소를 쓰지 않는다. 단순한 코드 생성은 메모리와 스킬 협력이면 충분하고, 일상적인 커밋은 훅만 개입할 수도 있다. 구성 요소의 가치는 '모두 쓰는 것'이 아니라 '필요할 때 불러 쓸 수 있게 준비되어 있는 것'에 있다.

## 3. 플러그인: 조합의 포장과 배포

Xiaobing가 "스킬과 플러그인은 무슨 관계예요?"라고 물은 적이 있었다. Kage는 화이트보드에 커다란 상자를 그리며 답한다. 플러그인은 새 능력이 아니라 패키징 메커니즘이다.

상황을 상상해 보자. 팀을 위해 3주를 들여 확장 체계를 정성껏 만들었다. 스킬 두 개(코드 리뷰, API 설계), 서브에이전트 한 개(보안 감사), 훅 세 개(커밋 전 린트, 저장 후 포매팅, 민감 정보 차단)가 들어 있다. 새 동료가 합류해 이 구성을 바로 써야 하는데 파일을 손으로 복사하면 '어느 파일이 어느 디렉터리로 가는지'만 알아내는 데도 반나절이 걸릴 수 있다.

플러그인(Plugin)은 이 문제를 푼다. 표준화된 포장 형식으로서 `plugin.json` 매니페스트 파일을 통해 스킬, 커맨드, 서브에이전트, 훅, MCP 설정을 한꺼번에 담는다. 포장한 뒤에는 설치 명령 한 번으로 모든 설정이 제자리에 배치된다. Node.js의 npm이나 컨테이너 이미지의 Docker와 같은 역할이며, 핵심 가치는 새로운 능력의 차원이 아니라 배포와 재사용에 있다.

초보자는 플러그인을 '더 고급스러운 스킬'로 오해하기 쉽다. 그러나 둘은 다른 차원에 있다. 스킬은 능력의 종류를 정의하고 플러그인은 배포의 형태를 정의한다. 플러그인은 스킬, 커맨드, 훅, 서브에이전트를 담을 수 있는 용기이며, 관심사는 '무슨 작업을 실행할까'가 아니라 '어떻게 포장해서 공유할까'다.

| 사용자 | 플러그인의 필요성 |
|---|---|
| 개인 개발자 | 일부러 만들 필요가 없을 수 있다. 프로젝트에 로컬로 구성해도 충분하다 |
| 팀 리더 | 모범 사례를 표준화하고 새 팀원에게 원클릭 구성을 주는 강력한 도구다 |

플러그인의 구조, `plugin.json` 필드, 사설 마켓플레이스는 9장에서 다룬다.
