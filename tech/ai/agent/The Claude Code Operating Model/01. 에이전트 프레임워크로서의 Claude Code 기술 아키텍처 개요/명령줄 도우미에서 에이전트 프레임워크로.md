# 명령줄 도우미에서 에이전트 프레임워크로

1장은 Xiaobing이라는 엔지니어가 겪은 곤란에서 시작한다. Claude Code를 쓰면 처음에는 코드가 놀랄 만큼 빨리 나오는데, 2주쯤 지나자 문제가 한꺼번에 터진다. 이 문서는 그 세 가지 문제가 어디서 왔는지, 그리고 책이 내놓는 첫 번째 관점 전환, 곧 'Claude Code는 채팅 도구가 아니라 에이전트 프레임워크'라는 주장을 정리한다.

비유는 하나로 통일된다. Claude Code는 빙산이다. 물 위에 보이는 것은 터미널 대화와 코드 생성, 명령 실행뿐이고, 문제를 해결해 줄 장치는 모두 물 밑에 있다. 에이전트 프레임워크(agent framework)란 AI가 도구를 쓰고 기억하고 일을 나누도록 짜 놓은 틀을 말한다.

---

## 1. Xiaobing의 세 가지 문제

Xiaobing는 AI 에이전트 프로젝트를 이끌며 Claude Code를 핵심 개발 도구로 골랐다. 2주 뒤에 나타난 문제는 다음과 같다.

| 증상 | 구체적 모습 | 근본 원인 |
|---|---|---|
| 기억 상실 | 새 세션을 열 때마다 기술 스택(FastAPI + SQLAlchemy)을 기억하지 못해 배경을 반복 설명해야 한다 | 프로젝트 맥락이 저장되어 있지 않다 |
| 스타일 흔들림 | Black 포매팅 표준이 들쭉날쭉 적용되어 풀 리퀘스트(PR) 세 건이 리뷰에서 반려됐다 | 표준이 말로만 전달되고 제도화되어 있지 않다 |
| 긴 작업에서의 맥락 넘침 | 파일 여섯 개를 고치는 리팩터링에서 네 번째 파일쯤 가면 앞의 논리를 잊어 결과가 어긋난다 | 컨텍스트 윈도(모델이 한 번에 볼 수 있는 입력 한도)의 한계 |

Xiaobing는 "매일 기억을 잃는 인턴을 관리하는 느낌"이라고 푸념했다. 선임 멘토 Kage는 위로 대신 세 가지 질문을 던졌다.

1. 프로젝트 루트에 CLAUDE.md를 설정했는가?
2. 여섯 파일 리팩터링을 왜 서브에이전트에게 나눠 맡기지 않았는가?
3. 코드 표준이 중요하다면 왜 말로만 전하고 스킬(Skills)로 묶어 자동 로딩되게 하지 않았는가?

Xiaobing는 하나도 답하지 못했다. Kage의 진단은 이렇다. 문제의 뿌리는 모델이 똑똑하지 않아서가 아니라 기본 대화 능력만 쓰고 있어서다. Claude Code는 기억 시스템, 스킬 모듈, 서브에이전트 위임, 이벤트 훅, 외부 도구 프로토콜을 갖춘 완전한 에이전트 프레임워크이고, 겪은 문제마다 프레임워크 수준의 해법이 이미 있다. 두 시간 대화 끝에 Xiaobing는 "AI 비서를 부린다고 생각했는데 사실은 화려한 채팅창을 쓰고 있었다"고 탄식한다.

세 증상은 서로 다른 버그처럼 보이지만 같은 원인, 곧 에이전트 프레임워크를 단순 채팅 도구로 오해한 데서 나온다. 책은 Claude Code의 본질을 세 단어로 압축한다.

| 성질 | 의미 |
|---|---|
| 프로그래밍 가능(Programmable) | Python이나 TypeScript 코드로 직접 구동해 CI/CD 파이프라인이나 자동화 스크립트에 넣을 수 있다. 사람이 터미널 앞에서 지켜보지 않아도 된다 |
| 확장 가능(Extensible) | 핵심 코드를 건드리지 않고 설정 파일만으로 메모리, 스킬, 훅 같은 능력을 주입한다 |
| 조합 가능(Composable) | 확장 모듈을 레고 블록처럼 엮어 복잡하고 효율적인 워크플로를 만든다 |

세 성질이 합쳐지면 도구 하나가 아니라, 자기만의 AI 작업 체계를 쌓는 토대가 되는 인프라 프레임워크가 된다.

## 2. 빙산 아래의 구성 요소

수면 위에는 터미널 대화, 코드 생성, 명령 실행이 있다. 물 밑의 구조는 Xiaobing의 문제를 하나씩 겨냥한다.

| 구성 요소 | 해결하는 문제 |
|---|---|
| CLAUDE.md | '기억 상실'을 고친다. 프로젝트 표준을 설정 파일에 한 번 적으면 매 세션 자동으로 불러온다 |
| 스킬(Skills) | 스타일 흔들림을 끝낸다. 코드 리뷰 기준을 설정으로 제도화해 말로 하는 당부의 불확실성을 없앤다 |
| 서브에이전트 | 맥락 넘침을 해결한다. 여섯 파일 리팩터링을 여섯 개의 독립된 컨텍스트 단위로 쪼개 병렬 처리와 논리적 격리를 얻는다 |
| 훅(Hooks) | 도구를 호출하는 순간에 보안 점검이나 기록을 자동으로 걸어 방어적 프로그래밍 장치를 만든다 |
| MCP(Model Context Protocol) | 데이터 사일로를 깨고 외부 데이터베이스와 API를 호출하게 한다 |
| 헤드리스 모드 | CI/CD 파이프라인에서 사람 없이 돌아가게 해 진짜 자동 전달을 가능하게 한다 |
| Agent SDK | 복잡한 다단계 에이전트 워크플로를 코드로 오케스트레이션해 실행 유연성을 높인다 |
| 플러그인 생태계 | 위 능력을 묶어 팀 안에서 효율적으로 배포하고 재사용한다 |

여기서 헤드리스 모드(headless mode)는 대화형 터미널 없이 `-p` 같은 인자로 일회성 작업을 돌리는 방식을 말한다. 자세한 내용은 7장의 몫이다.

### 수동 스크립팅에서 시스템 구성으로

Xiaobing는 자신의 예전 방식을 '비효율적인 수동 스크립팅'이라고 되돌아본다. 같은 정보를 Claude에게 거듭 먹이고, 작업을 손으로 쪼개고, 스타일을 눈으로 확인했다는 것이다. Kage는 이를 구체적으로 짚는다. 새 대화마다 기술 스택을 다시 말하고, 리뷰할 때마다 기준을 손으로 설명하고, 커밋할 때마다 개인 기억에 기대어 점검하는 일은 모두 수동 스크립팅이다. 프레임워크 방식은 다음과 같다.

- 기술 스택은 CLAUDE.md에 한 번 굳혀 놓는다.
- 리뷰 기준은 스킬로 묶어 자동 로딩한다.
- 커밋 점검은 훅으로 설정해 빠뜨리는 일이 없게 한다.

'단계별 지시'에서 '시스템 구성'으로의 전환은 효율만이 아니라 사람과 AI의 협업 품질도 바꾼다. 한 번 만든 설정은 잊히지 않고, 소홀해지지 않고, 야근에 흔들리지도 않는다. 개인의 지혜를 제도적 표준으로 증류하는 것, 책은 이것을 엔지니어링의 본질이라고 부른다.

## 3. 이 장이 남기는 관점

이 문서에서 가져갈 것은 세 가지다.

- 증상은 여럿이어도 원인은 하나다. Claude Code를 채팅창으로만 쓰고 있다는 것이다.
- 해법은 사용 습관이 아니라 구성(configuration)에 있다. 한 번 설정해 두면 모든 세션에서 같은 품질이 나온다.
- 모든 부품을 처음부터 다 익힐 필요는 없다. 이 장의 뒷부분(4계층 구조 모델 문서)에서 각 부품의 위치와 역할을 더 자세히 본다.

참고(노트 작성자): 원서의 서두에는 "We shape our tools, and thereafter our tools shape us."라는 마셜 매클루언(Marshall McLuhan)의 인용이 놓여 있다. 도구를 만들고 나면 도구가 우리를 만든다는 뜻이며, 설정을 통해 일하는 방식 자체가 바뀐다는 이 장의 취지와 이어진다.
