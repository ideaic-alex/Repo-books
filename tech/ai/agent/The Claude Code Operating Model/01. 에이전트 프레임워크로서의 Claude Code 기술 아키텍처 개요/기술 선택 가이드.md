# 기술 선택 가이드

구성 요소가 많으면 핵심 질문이 생긴다. 내 요구에는 무엇을 골라야 하는가. 1장은 이를 위해 결정 트리 한 장과 적용 시나리오 비교표를 준다. 이 문서는 둘을 글과 표로 풀고, 이 장의 마무리인 요약과 원칙을 함께 정리한다.

가장 중요한 원칙은 하나다. 지금의 문제를 가장 단순한 해법으로 푼다. 아는 것이 망치라고 해서 모든 것을 못으로 보지 말라는 경고가 이 문서의 끝에 붙는다.

---

## 1. 결정 트리를 따라 묻는 순서

원서의 그림 1.6(구성 요소 선택 결정 트리)은 다음 질문 순서로 읽는다.

| 단계 | 질문 | 답에 따른 선택 |
|---|---|---|
| 1 | 이 작업은 어떻게 트리거되는가? | 사람이 시작하면 2번으로, Claude가 자동으로 일으키면 3번으로 |
| 2 | 논리가 얼마나 복잡한가? | 단계가 고정이면 커맨드, Claude의 판단이 필요하면 스킬 |
| 3 | 특정 이벤트 지점에서인가, CI/CD 파이프라인에서인가? | 이벤트 지점이면 훅, CI/CD 파이프라인이면 헤드리스 모드 |
| 4 | 실행 환경은 어떤가? | 작업량이 무겁거나 컨텍스트 격리가 필요하면 서브에이전트를 더한다 |
| 5 | 외부 시스템(도구, 데이터)에 접근해야 하나? | MCP를 더한다 |
| 6 | 코드 수준의 프로그래밍 제어가 필요한가? | Agent SDK를 쓴다 |

4~6번은 앞 단계 선택에 '추가'하는 요소라는 점에 유의한다. 구성 요소는 서로 배타적인 선택지가 아니라 함께 쓰는 경우가 많다.

## 2. 적용 시나리오와 구성 요소

원서의 표 1.2는 시나리오마다 추천 구성 요소와 핵심 이유를 짝짓는다. 이 표도 추출 과정에서 칸이 흩어져 있어 내용을 맞춰 복원했다.

| 시나리오 | 추천 구성 요소 | 핵심 이유 |
|---|---|---|
| 릴리스 때마다 정해진 점검 목록을 실행 | 커맨드 | 단계가 분명하고 고정이라 수동 명령으로 원클릭 트리거하기에 알맞다 |
| 금융 문제를 논할 때 전문 가이드를 자동으로 받기 | 스킬 | 도메인 지식이 의미에 따라 자동 매칭되어 필요할 때만 로딩된다. 사용자가 명령을 따로 지정하거나 외울 필요가 없다 |
| 큰 PR을 리뷰하되 컨텍스트 넘침을 피하기 | 서브에이전트 | 독립 서브에이전트로 컨텍스트를 격리하고 간결한 결론만 주 세션에 돌려줘 토큰 소비를 효과적으로 관리한다 |
| 코드 제출 전에 민감 정보 유출을 자동 차단 | 훅(PreToolUse) | 이벤트 기반 장치로 특정 작업(도구 호출 등) 전에 강제 가로채기와 점검을 보장하며 빠짐이 없다 |
| PR 제출 뒤에 자동으로 코드 리뷰 실행 | 헤드리스 | 무인 환경에 알맞고 CI/CD 파이프라인에 넣어 명령으로 리뷰 작업을 자동 실행한다 |
| Claude가 GitHub 이슈를 조작하게 하기 | MCP | 표준 프로토콜로 외부 시스템(GitHub API 등)에 매끄럽게 연결해 모델의 도구 경계를 넓힌다 |

참고(노트 작성자): 표 1.2의 원문 헤더는 '파일 유형, MCP, 경로'처럼 어긋나게 추출되어 있다. 위 표의 세 열 이름은 내용에 맞춰 노트 작성자가 붙인 것이다.

## 3. 성숙한 팀 구성과 비유

요소들은 흔히 조합해 쓴다. 성숙한 팀은 보통 모든 구성 요소를 조율해 튼튼한 자동화 체계를 만든다.

- CLAUDE.md는 기초 맥락을 깐다.
- 스킬은 도메인 전문성을 주입한다.
- 커맨드는 수동 작업을 위한 표준 진입점을 제공한다.
- 훅은 자동 보안 방어선을 세운다.
- 서브에이전트는 매우 복잡한 작업을 쪼개 처리한다.
- MCP는 외부 시스템과의 데이터 장벽을 허문다.
- 헤드리스 모드는 능력을 CI/CD 파이프라인에 매끄럽게 통합한다.

책은 이를 효율적인 기업에 비유한다. 역할(구성 요소)마다 책임과 경계가 분명하면서도 최종 목표를 위해 긴밀히 협력한다는 것이다.

### Kage의 노트: 단순함이 기준이다

기술 선택의 핵심 원칙은 항상 '가장 단순한 해법으로 현재 문제를 푼다'이다. 서브에이전트를 배웠다고 모든 작업을 위임하지 말고, 훅을 익혔다고 사소한 동작마다 경비를 세우지 않는다. 과잉 설계와 과소 설계는 똑같이 해롭다. 좋은 설계자는 균형의 기술을 안다. 확장성을 위해 추상화 층을 도입할 때와 간단한 CLAUDE.md 파일 하나로 완벽한 해법이 될 때를 구분한다.

## 4. 장의 마무리

원서의 요약을 이 장의 논지에 맞춰 풀면 다음과 같다.

- 관점 전환: Claude Code는 명령줄판 ChatGPT가 아니라 프로그래밍 가능하고 확장 가능하고 조합 가능한 에이전트 프레임워크다. 수면 위의 대화 인터페이스는 입구일 뿐이고 기술적 깊이는 메모리 시스템, 네 가지 확장 구성 요소, 통합 장치, Agent SDK에 있다. 이를 이해하는 것이 '수동적 사용'에서 '능동적 오케스트레이션'으로 가는 첫걸음이다.
- 4계층: 메모리 계층은 기초이고 맥락 이해 능력을 준다. 확장 계층은 본체로 커맨드, 스킬, 서브에이전트, 훅 네 가지 직교하는 확장 방법을 준다. 통합 계층은 헤드리스와 MCP로 바깥과 잇는다. 프로그래밍 계층은 꼭대기이며 사용자에서 건설자로 넘어가게 한다. 네 층은 서로 쌓이지만 따로 공부할 수도 있어서 한꺼번에 다 익히지 않아도 실습을 시작할 수 있다.
- 관계: 커맨드는 명시적 지시, 스킬은 암묵적 지식, 서브에이전트는 격리된 위임, 훅은 자동 수호자다. 수동 개입에서 자동 실행까지, 명시적 호출에서 암묵적 반응까지 전 범위를 덮으며 독립 또는 조합해 쓸 수 있다. 플러그인은 표준화된 포장 메커니즘으로 조합의 배포와 재사용을 돕는다.
- 다음 장 예고: 4계층의 주춧돌인 메모리 시스템(CLAUDE.md)을 다룬다. 잘 쓴 CLAUDE.md 하나가 반복되는 말 열 마디보다 값지다는 것이 이 장의 마지막 문장이다.
