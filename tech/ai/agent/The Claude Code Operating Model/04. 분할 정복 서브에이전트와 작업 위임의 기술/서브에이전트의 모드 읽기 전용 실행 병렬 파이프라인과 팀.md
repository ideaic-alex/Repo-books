# 서브에이전트의 모드: 읽기 전용, 실행, 병렬, 파이프라인, 팀

기본 개념과 설정법을 익혔으니 이 장의 핵심으로 들어간다. 책은 서브에이전트의 모드를 단순한 분류 목록이 아니라 근본적으로 다른 아키텍처 패러다임이라고 소개하며, 각각이 특정한 작업 특성에 정확히 대응하고 소프트웨어 공학 원리에 뿌리를 둔다고 말한다. 이 장 요약은 이를 읽기 전용, 실행, 병렬, 파이프라인, 팀의 다섯 가지 패턴이라고 부른다.

참고(노트 작성자): 이 절의 도입부 문장은 "다섯 가지 모드"라고 쓰면서 바로 이어서 카게가 화이트보드에 "네 개의 상자"를 그린다고 적고, 팀 모드는 "앞의 네 가지 모드"와 구별해 따로 설명한다. 그래서 이 문서는 앞의 네 모드(읽기 전용, 실행, 병렬, 파이프라인)를 한 묶음으로, 팀 모드를 확장판 다섯째로 다룬다.

---

## 1. 모드 한눈에 보기

| 모드 | 핵심 가치 | 대표 작업 | 대응 공학 개념 |
|---|---|---|---|
| 읽기 전용 | 안전한 관찰자 | 코드 리뷰, 보안 감사, 아키텍처 분석, 의존성 점검 | 최소 권한 원칙 |
| 실행 | 신호 대 잡음 최적화 | 테스트 실행, 로그 분석, 대량 포맷팅 | 파사드 패턴, 벌크헤드 |
| 병렬 | 다중 전문가 동시 작업 | 독립된 여러 관점의 분석 | MapReduce |
| 파이프라인 | 직렬 처리 사슬 | 버그 위치 추적에서 수정, 검증, 영향 분석 | 책임 연쇄, 유닉스 파이프 |
| 팀 | 자율 조직형 협업 | 경쟁 가설, 모듈 소유 등 | 실험적 기능 |

## 2. 읽기 전용: 안전한 관찰자

가장 기본적이고 안전한 모드이며 핵심 특징은 "읽기만 하고 쓰지 않는다"로 요약된다. 코드 리뷰, 보안 감사, 아키텍처 분석, 의존성 점검에 쓴다. 이런 작업은 본질적으로 방대한 정보를 읽고 깊이 분석하는 "관찰" 활동이어서 시스템에 부작용을 일으켜서는 안 된다. 리뷰어는 코드를 직접 고치지 않고 문제를 지적하며, 감사자는 장부를 조작하지 않고 재무상의 허점을 드러낸다.

도구 권한은 Read, Grep, Glob 세 가지로 엄격히 제한된다. Read는 파일 내용을, Grep은 특정 패턴 검색을, Glob은 규칙에 맞는 파일 경로 찾기를 맡아 코드 분석에 필요한 능력을 모두 덮고, 어떻게 호출해도 파일 시스템을 바꾸지 못한다는 공통점이 있다. 이는 최소 권한 원칙의 구현이다. 전통 시스템에서 데이터베이스 복제본(ReadReplica)에 읽기 전용 권한을 주거나 리눅스 chmod로 권한을 세밀히 통제하는 것의 자연스러운 확장이다. 책은 이 설계가 아키텍처 차원에서 쓰기 위험을 줄이며, 실제로 의존하는 경계는 tools 화이트리스트라고 다시 강조한다.

## 3. 실행: 고잡음 작업 처리기

일상 개발에서 가장 널리 쓰이는 모드이며 핵심 가치는 "신호 대 잡음 최적화"다. 방대한 데이터(예: 500줄)를 넣고 간결한 결론(예: 5줄)만 내놓는다. 수천 줄 로그를 만드는 테스트 스위트, 수만 건의 기록을 분석하는 일, 수백 개 파일을 바꾸는 포맷팅이 모두 해당한다. 개발자는 대개 어떤 테스트가 실패했는지, 근본 원인이 무엇인지, 어떤 파일이 바뀌었는지만 알면 된다. 이 잡음을 메인 대화에 흘려보내면 신호 대 잡음 비가 급락하지만, 격리 공간에서 처리하면 "격벽(bulkhead)" 밖에 잡음을 막아 둘 수 있다.

앞서 정의한 test-runner가 대표 예다. Bash를 호출해야 하므로 읽기 전용보다 권한이 넓지만 그 "넓음"도 엄격히 제한된다. 예를 들어 `Bash(npm test:*)`로 설정하면 `npm test`로 시작하는 명령만 실행할 수 있어서, 실행 능력이 있어도 임의의 셸 작업은 근본적으로 막힌다.

실행 서브에이전트 설계의 핵심은 출력 형식이 아니라 구조적 격리다. 메인 에이전트는 서브에이전트의 최종 메시지만 받으므로, 장황한 로그와 중간 도구 출력은 출력 형식 지시 없이도 자동으로 서브에이전트의 컨텍스트에 남는다. 출력 형식 제약은 2차 안전장치로서, 반환되는 요약을 하류 소비자가 예측할 수 있게 해 준다.

공학적으로는 파사드 패턴(Facade Pattern, 복잡한 내부를 단순한 창구로 감싸는 설계)의 전형이다. 복잡한 하위 시스템은 테스트 프레임워크가 만드는 상세 로그와 저수준 상호작용이고, 단순화된 인터페이스는 서브에이전트가 밖으로 내는 구조화된 요약이며, 클라이언트인 메인 대화는 내부를 몰라도 이 "정면"을 통해 간결하고 쓸 수 있는 결과를 얻는다.

## 4. 병렬: 다중 전문가 워크플로

같은 문제를 여러 독립 차원에서 깊이 분석해야 할 때 병렬 모드가 힘을 발휘한다. 형사 세 명을 파견해 각자 다른 증거(물증, 증인 면담, 감시 영상)를 맡기는 것과 같다. 서브에이전트 셋이 각자의 격리된 공간에서 서로 간섭 없이 동시에 일하면 전체 분석 시간이 크게 줄고, 마지막에 시스템이 각자의 발견을 모아 다각도의 종합 보고서를 만든다.

### 4-1. 엄격한 전제 조건

하위 작업이 완전히 독립적이어야 하며 공유 상태나 의존 관계가 없어야 한다. 보안 감사는 코드 품질 평가 결과를 기다릴 필요가 없고, 성능 분석은 보안 감사 결론에 의존하지 않는다. 반대로 작업 사슬에 논리적 의존이 있으면(예: "버그를 먼저 찾아야 고칠 수 있다") 병렬은 맞지 않는다. 억지로 병렬로 돌리면 선행 입력이 없어 후속 작업이 실패하거나 틀린 결과를 낸다. 이런 순서가 분명한 흐름에는 다음 절의 파이프라인을 쓴다.

### 4-2. MapReduce와의 대응

Map 단계에서 메인 에이전트는 "오케스트레이터"로서 크고 복잡한 문제를 여러 독립 하위 작업으로 쪼개 서브에이전트(워커 노드)에게 분배하고, 각 서브에이전트는 격리된 환경에서 병렬로 자기 몫을 처리한다. Reduce 단계에서 모든 서브에이전트가 끝나면 메인 에이전트가 다시 나서서 각 출력을 모으고 통합, 증류해 통일된 완전한 답을 낸다. 서브에이전트는 전역 상태나 다른 노드의 결과를 신경 쓰지 않고, 메인 에이전트는 분해와 집계라는 오케스트레이션에 전념한다.

### 4-3. 전문화와 동시성의 구분

병렬 모드의 큰 장점은 전문화다. 서브에이전트마다 좁은 임무(예: security-auditor)를 줄 수 있다고 책은 말하며, 역할 스케치는 측정값이 아니라 예시라는 단서를 단다. 참고(노트 작성자): 이 대목의 추출본은 security-auditor 설명 뒤가 끊겨 있어 구체적인 역할 예시 내용을 확인할 수 없다.

두 개념을 혼동하지 말라고 책은 당부한다.

- 진짜 동시성: 메인 에이전트가 한 턴 안에서 서브에이전트 여럿을 띄우면 하니스(harness, 모델을 감싸 도구 호출과 실행 환경을 제공하는 실행 틀)가 동시에 실행한다.
- 백그라운딩: 오래 걸리는 서브에이전트를 백그라운드로 보내 메인 스레드가 막히지 않게 하는 편의 기능은 별개다. 키 바인딩은 플랫폼과 Claude Code 버전마다 다르므로 인쇄된 단축키를 믿지 말고 자기 환경의 키 바인딩을 확인한다.
- 세션 안에서 Agent 도구로 띄우는 서브에이전트는 에이전트 보기(agent view)에 나타나는 백그라운드 세션과 다른 메커니즘이다.

## 5. 파이프라인: 직렬 처리 사슬

병렬이 독립 작업용이라면 파이프라인은 단계 간 의존이 분명한 작업용이다. 대표 예시는 버그 수정 파이프라인이다. 문제의 근본 원인을 찾고, 진단에 따라 수정하고, 수정이 효과 있는지 검증하고, 마지막으로 수정의 영향을 분석한다. 각 단계의 출력이 다음 단계의 입력이며 순서를 뒤집을 수 없다.

### 5-1. 단계마다 다른 도구 권한

이 파이프라인에는 미묘하지만 중요한 설계 특징이 있다. 단계별로 도구 권한이 뚜렷이 다르다.

| 단계 | 서브에이전트 | 권한 | 이유 |
|---|---|---|---|
| 1 | bug-locator | 읽기 전용(Read, Grep, Glob, permissionMode: plan) | 진단 중에 아무것도 수정되지 않게 한다 |
| 2 | bug-fixer | 읽기와 쓰기, Bash(Read, Grep, Glob, Edit, Write, Bash) | 코드를 고치고 빌드 명령을 돌린다 |
| 3 | bug-verify | 읽기 전용 + Bash | 수정 효과를 검증하려 테스트만 돌리며 코드 변경은 엄격히 금지 |
| 4 | bug-report | 순수 읽기 전용 | 영향 분석은 코드와 변경 이력을 보기만 하면 된다 |

이 권한의 동적 조정은 파이프라인 모델 특유의 보안 메커니즘으로, 각 단계가 자기 책임을 수행하는 데 필요한 최소 권한만 갖게 한다.

### 5-2. 인수인계 계약

파이프라인의 핵심 기술은 인수인계 계약(handoff contract)이다. 각 단계의 출력 형식이 다음 단계의 입력 요구와 엄격히 맞아야 한다. 책의 예에서 bug-locator의 출력은 다음 네 항목이다.

```
Root Cause File: [file_path:line_number]
Problem Description: [원인 한 문장 요약]
Call Chain: [진입점에서 오류 위치까지의 전체 경로]
Fix Direction: [수정 아이디어 요약]
```

여기서 "근본 원인 파일"과 "수정 방향"은 bug-fixer가 일을 시작하는 데 꼭 필요한 입력이다. bug-fixer의 출력은 "Modified files"(수정 파일), "Reason for each modification"(수정 이유), "Potential side effects"(잠재 부작용), "Suggested test commands"(검증 명령 제안)이며, 이것이 다시 bug-verify의 검증 근거가 된다. 상하류 간의 이 엄격한 형식 계약이 신뢰할 수 있는 파이프라인의 초석이다. 유닉스 파이프(`cat log.txt | grep ERROR | sort | uniq -c | sort -rn`)도 같은 사상이다.

### 5-3. 실제 실행 흐름

"issue #123에 보고된 결제 실패를 고쳐라"라는 지시를 받으면 메인 에이전트는 다음 순서로 조율한다.

1. bug-locator에 위임해(독립 컨텍스트) 근본 원인을 분석하고 "src/payment/charge.ts:89의 null 검사 누락"이라는 결론을 얻는다.
2. 이 결론을 입력으로 bug-fixer에 넘겨(독립 컨텍스트) 코드를 수정하고 charge.ts:89에 null 검사 로직이 추가되었다는 결론을 얻는다.
3. 수정된 파일과 제안된 테스트 명령을 bug-verify에 넘겨(독립 컨텍스트) 테스트를 돌린다. 결과는 결제 모듈 테스트 12건 모두 통과다.
4. 수정과 검증의 전체 기록을 bug-report에 넘겨(독립 컨텍스트) 영향 범위를 분석하고 보고서를 만든다. 결론은 수정 범위가 통제되어 있고 부작용이 없으며 향후 null 경계 테스트를 추가하길 권한다는 것이다.

결과적으로 서브에이전트 넷이 각자 격리된 컨텍스트에서 깊이 있는 작업을 마치고, 메인 대화는 간결하고 구조화된 핵심 결론 네 개만 받아 표시한다.

## 6. 팀: 자율 조직형 협업

가장 복잡하고 강력한 서브에이전트 패턴이다. 주의할 점이 있다. Agent Teams는 실험적 기능이며 기본적으로 꺼져 있고, 환경 변수 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS로 켠다. 켜지 않고 시도하면 쓸 수 없다.

앞의 네 모드에서 서브에이전트는 작업을 수행하는 동안만 활동하다 끝나면 종료되는 "일회성"이다. 팀 모델에서는 서브에이전트가 장기적으로 지속되어 실제 팀처럼 계속 협업하고, 실시간으로 소통하고, 자율적으로 일을 나눈다. 구성 요소는 셋이다.

- 팀 리드(Team Lead): 작업 분해, 자원 조율, 진행 추적을 맡는 프로젝트 매니저 격.
- 팀원(Teammates): 서로 다른 전문 분야의 서브에이전트들로 각자 특정 기능 모듈을 맡는다.
- 공유 인프라: 두 가지 메커니즘이다. 작업 목록(Task List)은 모든 구성원이 전체 진행과 자기 할 일을 실시간으로 파악하게 하고, 메일박스(Mailbox)는 구성원 간 비동기 소통을 지원한다(예: 프런트엔드 개발자가 백엔드 개발자와 API 명세를 확인).

### 6-1. 네 가지 협업 패턴

| 패턴 | 설명 |
|---|---|
| 경쟁 가설 | 원인이 불확실한 복잡한 문제(성능 병목이 DB 쿼리인가 네트워크 IO인가)에서 서브에이전트 여럿이 서로 다른 가설로 병렬 조사하고, 팀 리드가 조사 보고서를 비교해 증거가 가장 강한 결론을 고른다 |
| 병렬 리뷰 | 같은 코드 변경에 보안 리뷰와 기능 리뷰를 동시에 진행한다. 리뷰어들은 독립적으로 일하고 의견은 마지막에 합친다. 직렬 리뷰보다 효율적일 뿐 아니라 여러 관점의 독립성이 리뷰 품질을 높인다 |
| 모듈 소유 | 대규모 리팩터링에서 코드베이스를 모듈별로 나눠 맡긴다. 프런트엔드는 UI 컴포넌트, 백엔드는 API 계층, 데이터 계층은 DB 마이그레이션을 맡고, 모듈 간 인터페이스 변경은 메일박스로 조율한다 |
| 제안 승인 | 한 서브에이전트가 리팩터링 방안을 제안하고 다른 서브에이전트가 "악마의 대변인"으로서 도전과 반대를 제기한다. 팀 리드가 양쪽 논거로 최종 결정한다. 이런 대립 설계가 방안의 사각지대를 막는다 |

### 6-2. 팀 모델을 쓸 시점

실용적 기준은 협업의 복잡도다. 서브에이전트들이 여러 차례 소통하고 깊은 조율이 필요하면 팀 모델을, 각자 한 번 작업을 끝까지 수행하면 되면 단순 병렬이나 파이프라인으로 충분하다. 팀 모델은 운영 비용이 높다. 장기 컨텍스트 윈도를 유지하는 것은 토큰을 계속 소모한다는 뜻이므로, 정말 복잡한 협업이 필요한 시나리오에서만 가성비가 맞는다.

## 7. 핵심 정리

- 읽기 전용은 Read, Grep, Glob만 쓰는 관찰자, 실행은 잡음이 많은 작업을 요약으로 바꾸는 파사드, 병렬은 독립 하위 작업을 동시에 돌리는 MapReduce, 파이프라인은 의존 있는 단계를 계약으로 잇는 사슬이다.
- 병렬의 전제는 완전한 독립이다. 선행 결과가 필요하면 파이프라인으로 간다.
- 파이프라인은 단계마다 최소 권한을 다르게 주고, 상하류 출력과 입력 형식을 맞추는 인수인계 계약이 신뢰성의 초석이다.
- 팀 모드는 실험적이며 기본 비활성이고(CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS), 장기 컨텍스트로 토큰을 많이 쓰므로 복잡한 협업에만 쓴다.
