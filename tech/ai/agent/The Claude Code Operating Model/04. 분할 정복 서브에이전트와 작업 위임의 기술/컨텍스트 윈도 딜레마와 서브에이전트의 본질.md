# 컨텍스트 윈도 딜레마와 서브에이전트의 본질

4장은 목요일 오후 3시, 스택이 넘치기 직전 같은 표정의 샤오빙(Xiaobing)을 보여 주며 시작한다. 그녀는 결제 모듈의 운영 버그를 잡으려고 한 시간 넘게 Claude와 대화했다. 먼저 500줄이 넘는 오류 로그를 분석시켰고, 회귀 테스트를 돌려 200줄 넘는 출력이 대화창에 쏟아졌고, 관련 소스 파일 예닐곱 개를 읽혔다. 그 상태에서 앞선 분석을 토대로 수정안을 달라고 하자 Claude의 답이 이상해졌다. 로그 분석에서 찾은 핵심 오류 코드를 "잊어버리고", 테스트 출력의 무관한 실패를 핵심 문제로 오인하고, 수정안에 존재하지도 않는 함수 이름을 끌어다 썼다.

샤오쉐(Xiaoxue)는 화면을 보자마자 원인을 짚었다. 모든 정보를 하나의 채팅창에 쑤셔 넣었고, 로그와 테스트 결과와 코드 리뷰를 합치면 수만 토큰일 것이다. Claude는 잊은 것이 아니라 정보의 홍수에 빠진 것이다. 이 문서는 그 문제(컨텍스트 윈도 딜레마)와, 해법인 서브에이전트(subagent, 독립된 컨텍스트 윈도를 가지고 메인 에이전트의 위임을 받아 일하는 별도의 Claude 인스턴스)의 정의와 세 가지 가치를 정리한다.

---

## 1. 컨텍스트 윈도 딜레마

### 1-1. 책상 비유와 컨텍스트 오염

두 사람이 이 문제를 카게(Kage)에게 가져가자 그는 대답 대신 화이트보드에 책상을 그린다. 책상 크기는 고정이어서 파일 약 20개만 올라간다. 여기에 20쪽짜리 재무 보고서 검토, 시스템 로그 더미 분석, 기술 제안서 작성이라는 세 가지 작업의 파일을 전부 올리면 어떻게 될까. 책상은 엉망이 되어 필요한 것을 찾지 못한다.

문제는 그것만이 아니다. 기술 제안서를 쓰려는 순간 눈에 들어오는 것이 재무 수치와 로그 더미뿐이다. 이 무관한 정보는 가만히 있지 않고 계속 사고를 방해해서, 무의식중에 기술 제안서에 재무 보고서의 문체를 쓰게 만든다. 이것이 컨텍스트 오염(context pollution)이다.

### 1-2. 유한한 창과 신호 대 잡음

Claude Code의 기본 컨텍스트 윈도(모델이 한 번에 볼 수 있는 텍스트 범위)는 200,000토큰으로 크고, Amazon Bedrock 같은 클라우드 제공자를 통하면 최대 100만 토큰까지 더 큰 창을 쓸 수 있다. 그래도 유한하다.

- 로그 500줄을 컨텍스트에 넣어도 진짜 가치 있는 것은 오류 스택 3줄일 수 있다.
- 테스트 출력 200줄에서 필요한 것은 "3개 실패, 47개 통과"라는 요약뿐일 수 있다.
- 나머지 수백 줄은 잡음이다. 귀한 공간을 차지하고 진짜 중요한 신호를 희석해서 Claude가 핵심 문제에 집중하기 어렵게 만든다.

### 1-3. 소프트웨어 공학에서 이미 낯익은 문제

책은 이 문제가 낯설지 않다고 말한다. 운영체제에 프로세스 격리가 필요한 이유는 모든 프로그램이 같은 메모리 공간을 쓰면 한 프로그램의 엉뚱한 포인터가 시스템 전체를 죽일 수 있어서다. 마이크로서비스가 모놀리식 애플리케이션을 대체한 이유는 모든 비즈니스 로직이 한 프로세스에 몰려 있으면 어느 모듈의 메모리 누수든 전체를 끌어내리기 때문이다. 관심사 분리, 프로세스 격리, 장애 구획은 모두 "서로 다른 작업이 서로를 방해하지 않게 하려면 어떻게 하나"라는 같은 질문에 답한다. 대형 모델 시대에 Claude가 겪는 컨텍스트 오염은 "메모리 누수", "프로세스 간섭"에 해당한다.

### 1-4. 새 대화는 너무 거친 해법

"작업마다 새 대화를 시작하면 되나요?"라는 샤오빙의 물음에 카게는 그것이 너무 거칠다고 답한다. 새 대화는 진짜 가치 있는 배경 정보와 프로젝트 규범까지 포함해 모든 컨텍스트를 잃는다. 책상을 치우려고 책상째, 문서째 분쇄기에 던지는 격이다. 올바른 방법은 작업을 서브에이전트에게 위임하는 것이다.

## 2. 서브에이전트의 본질: CEO 위임 모델

카게는 이번에는 어수선한 책상 대신 깔끔하게 정돈된 현대식 사무실을 그린다. 당신이 이제 작업에 묻힌 실무자가 아니라 회사의 CEO라고 하자. 책상 위에 재무제표 감사, 시스템 장애 조사, 분기 전략 수립 세 건이 급하다. 혼자 방에 틀어박혀 세 건을 다 처리하겠는가? 샤오쉐의 답은 CFO에게 재무제표 감사를, SRE(Site Reliability Engineer, 서비스 안정성을 맡는 엔지니어)에게 장애 조사를 맡기고 자신은 사무실에서 간결한 보고를 기다렸다가 최종 결정만 내리겠다는 것이다. 이것이 서브에이전트의 핵심 발상이다. Claude에게 원자료를 통째로 삼키게 하지 말고, CEO 역할을 맡겨 구체적인 업무를 전문 "직원"에게 쪼개 위임하게 한다.

### 2-1. 정의

서브에이전트는 독립된 컨텍스트 윈도, 제한된 도구 권한, 명확하게 정의된 작업 범위를 가진 Claude 인스턴스다. 메인 에이전트가 필요할 때 서브에이전트를 띄우고 작업 설명을 건넨다. 서브에이전트는 자기만의 격리된 컨텍스트 안에서 작업을 수행하고, 중간 과정 전부가 아니라 결론만 메인 에이전트에게 돌려준다.

### 2-2. 세 가지 핵심 가치

| 가치 | 의미 | 대응하는 공학 원리 |
|---|---|---|
| 격리(Isolation) | 서브에이전트가 읽은 파일, 실행한 명령의 출력, 중간 추론은 모두 자기 컨텍스트 안에 갇히고 메인 대화로 흘러가지 않는다. 로그 500줄의 "잡음"이 서브에이전트 안에 갇히고 메인은 정제된 장애 진단만 받는다 | 운영체제의 프로세스 격리 |
| 제약(Constraint) | 서브에이전트마다 도구 권한을 엄격한 화이트리스트로 설정할 수 있다. 코드 리뷰 서브에이전트에 Read, Grep, Glob만 주면 Claude가 의도를 잘못 이해해도 파일을 수정할 수 없다. "파일을 수정하지 마세요"라는 놓치기 쉬운 프롬프트가 아니라 물리적 경계를 세우는 것이다 | 최소 권한 원칙 |
| 재사용(Reuse) | 서브에이전트는 마크다운 파일로 정의되어 팀 공유와 프로젝트 이전이 된다. 한 개발자가 공들여 설계한 리뷰 서브에이전트를 신입이 바로 쓸 수 있다 | 컴포넌트화 |

### 2-3. 실제로 일어나는 일

메인 에이전트가 위임을 결정하면 Claude Code는 내장 Agent 도구로 새 Claude 인스턴스를 만든다. 책은 이것이 운영체제의 프로세스 포크가 아니라고 분명히 한다. 독자적인 컨텍스트 윈도, 시스템 프롬프트, 도구 권한을 가진 별도의 에이전트 인스턴스이고, 부모의 작업 설명이 그 인스턴스의 첫 메시지로 도착하며, 최종 텍스트만 부모에게 돌아간다. 프로세스 격리 비유는 여전히 유용하지만 비유로만 쥐고 있어야 한다.

깨끗한 컨텍스트 안에서 서브에이전트는 파일 읽기, 명령 실행, 결과 분석을 독립적으로 수행하고, 끝나면 결과 요약만 돌려준다. 서브에이전트 내부의 모든 중간 상호작용은 종료와 함께 해제된다.

샤오빙의 상황에 적용하면 이렇다. 로그 분석을 log-analyzer라는 서브에이전트에 맡기면 중복된 로그 500줄은 서브에이전트 안에서 소화되고, 메인 대화에는 "원인 확인: src/payment/charge.ts:89에 null 검사 누락으로 NullPointerException 발생" 같은 간결한 결론만 보인다. 이후 수정안을 요청할 때 컨텍스트에 로그 잡음이 없고 정확한 장애 진단만 의사결정의 근거로 남는다.

## 3. 핵심 정리

- 컨텍스트 윈도는 유한하며, 무관한 정보가 쌓이면 Claude가 잊는 것이 아니라 신호가 잡음에 묻힌다(컨텍스트 오염).
- 새 대화를 여는 것은 가치 있는 배경까지 버리는 거친 해법이다.
- 서브에이전트는 독립 컨텍스트, 제한된 도구, 명확한 작업 범위를 가진 인스턴스이며 결론만 돌려준다.
- 가치는 격리, 제약, 재사용이다. 제약은 프롬프트의 부탁이 아니라 도구 화이트리스트라는 물리적 경계다.
- 참고(노트 작성자): 이 문서의 "유한한 창" 수치(기본 200,000토큰, 최대 100만 토큰)는 책이 인쇄된 시점 기준이며, 모델과 제공자에 따라 달라질 수 있다.
