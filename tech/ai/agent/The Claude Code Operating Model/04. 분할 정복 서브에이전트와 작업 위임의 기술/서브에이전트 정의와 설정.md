# 서브에이전트 정의와 설정

서브에이전트가 좋다는 것은 알겠는데 실제로 어떻게 만드는가. 카게의 답은 단순하다. 프로젝트의 `.claude/agents/` 디렉터리에 마크다운 파일 하나를 만들면 된다. 코드 리뷰 담당 code-reviewer.md, 테스트 실행 담당 test-runner.md, 로그 분석 담당 log-analyzer.md, 버그 위치 추적 담당 bug-locator.md처럼 역할마다 파일을 하나씩 둔다.

이 문서는 정의 파일의 구조, 읽기 전용 리뷰어와 실행형 테스트 러너 두 예시, YAML front matter(파일 맨 앞에서 `---`로 감싼 설정 영역) 필드 하나하나의 설계 의도, 그리고 서브에이전트를 부르는 두 가지 방법을 다룬다.

---

## 1. 정의 파일의 구조

각 정의 파일은 두 부분으로 이뤄진다.

| 부분 | 역할 |
|---|---|
| YAML front matter 메타데이터 | 서브에이전트가 "무엇인가"를 정한다. 정체성, 능력 경계(도구 권한 화이트리스트 등), 실행 설정 매개변수 |
| 마크다운 본문 지침 | 서브에이전트가 "어떻게 일하는가"를 정한다. 실행 절차, 표준화된 출력 형식, 필요한 전문 지식 |

## 2. 예시 1: 읽기 전용 리뷰어(code-reviewer)

설계 의도는 엄격한 읽기 전용 리뷰어다. 코드를 관찰할 수만 있고 어떤 파일도 수정할 수 없으며, 리뷰 결과는 고정된 구조화 형식으로 출력해서 메인 에이전트가 핵심 정보를 효율적으로 뽑게 한다.

```yaml
---
name: code-reviewer
description: |
  An expert in reviewing code quality, security vulnerabilities, and performance issues
  Use when the user requests code review, security audit, or quality assessment
tools:
- Read
- Grep
- Glob
model: sonnet
permissionMode: plan
---
```

본문은 "10년 넘는 경력의 시니어 코드 리뷰 전문가"라는 역할 선언으로 시작해 세 가지 리뷰 관점을 둔다.

- 보안: 하드코딩된 자격 증명(API 키, 비밀번호, 토큰), SQL 인젝션, XSS, CSRF 같은 주입 취약점, 입력 검증의 완전성, 민감 데이터 처리(암호화 여부, 로그 기록 여부).
- 코드 품질: 함수의 단일 책임 준수, 명확하고 일관된 이름, 중복 코드(DRY), 적절한 오류 처리(예외 삼키기와 빈 catch 블록 금지).
- 성능: 불필요한 중첩 루프(O(n^2) 초과), 데이터 구조 선택의 합리성, 데이터베이스 쿼리의 N+1 문제, 닫지 않은 자원(파일 핸들, DB 연결).

출력 형식은 엄격히 정해져 있다. "Review Summary"(전반 품질 요약과 장점, 주요 문제), "Issues Found"(`[Critical/Major/Minor] 설명 at file_path:line_number` 형태), "Improvement Suggestions"(우선순위를 매긴 구체적 개선 제안) 세 부분이다.

## 3. front matter 필드별 설계 의도

| 필드 | 별명 | 설명 |
|---|---|---|
| name | 고유 식별자("신분증") | 시스템 로그, 디버깅 추적, 내부 호출 체인에서 유일한 키로 쓰인다 |
| description | 트리거 설명, 라우팅 근거("광고판") | 메인 에이전트가 작업을 라우팅하는 핵심 근거. 스킬의 description과 비슷하게 동작한다 |
| tools | 도구 화이트리스트 | 서비스에서 가장 보안 가치가 큰 기능. 시스템 차원에서 최소 권한을 세운다 |
| model | 사용 모델 지정 | 비용 최적화의 과소평가된 지렛대 |
| permissionMode | 권한 모드 | plan이면 읽기 전용 계획 모드로 실행 |

### 3-1. description: 자동 위임의 근거

사용자가 "이 PR 리뷰해 줘"라고 말하면 다음 세 단계가 일어난다.

1. 의미 매칭: 메인 에이전트가 등록된 모든 서브에이전트의 description을 훑는다.
2. 의도 인식: 사용자 의도와 description 텍스트의 의미 유사도를 비교해 현재 작업이 그 서브에이전트의 능력 범위에 드는지 판단한다.
3. 자동 위임: code-reviewer의 description이 "code review", "security audit" 같은 요구와 높게 일치하면, 사용자가 서브에이전트 이름을 지정하지 않아도 작업 맥락을 포장해 위임한다.

### 3-2. tools: 보이지도 접근하지도 못하는 도구

예시의 화이트리스트에는 Read(파일 내용 읽기), Grep(파일 내 패턴 검색), Glob(파일 이름 경로 매칭) 세 가지 읽기 전용 작업만 있다. 목록에 없는 도구(Edit, Write, Bash 등)는 이 서브에이전트에게 보이지도 접근 가능하지도 않다.

### 3-3. model: 비용 조절

패턴화된 단순 작업(형식 검사, 로그 필터링)에는 Haiku 같은 가볍고 빠른 모델을 쓰고, 깊은 이해와 복잡한 추론이 필요한 작업(아키텍처 설계, 보안 감사)에는 Sonnet이나 Opus 같은 고성능 모델을 고른다. 올바른 모델 선택은 작업 품질을 지키면서 비용을 효과적으로 통제한다.

### 3-4. permissionMode: plan은 보강일 뿐

plan으로 설정하면 서브에이전트는 읽기 전용 계획 모드로 실행된다. 책은 이것을 tools 화이트리스트를 대체하는 층이 아니라 강화하는 층으로 다루라고 말한다. 부모 세션이 auto 모드로 실행 중이면 서브에이전트가 부모의 모드를 상속하고 자기 front matter의 permissionMode는 무시된다. 믿을 수 있는 물리적 경계는 tools 화이트리스트다. Edit, Write, Bash를 빼면 서브에이전트는 스스로 어떤 모드라고 믿든 쓸 수 없다.

### 3-5. 고급 필드: skills와 hooks

Kage의 메모는 front matter가 두 가지 고급 필드를 더 지원한다고 소개한다.

- skills: 서브에이전트에 특정 스킬 지식 묶음을 미리 로드한다. 예를 들어 impact-analyzer 서브에이전트에 chain-knowledge 스킬을 미리 로드하면 시작할 때부터 시스템 의존 관계 지식을 갖는다.
- hooks: 이벤트 훅(Hooks, 특정 시점에 자동 실행되는 처리 로직)을 구성해 특정 시점에 점검이나 동작을 자동 수행한다.

이 두 필드의 구체적 활용은 뒤 장들에서 다룬다고 책은 예고한다. skills는 이 장 뒷부분에서 곧 나온다.

## 4. 예시 2: 실행형 테스트 러너(test-runner)

앞 예시와 가장 큰 차이는 Bash 도구를 호출해 명령을 실행해야 한다는 점이다. 그래서 도구 권한(Read, Grep, Glob, Bash)은 넓어지지만 출력 형식 요구는 더 엄격하다. 모델은 haiku다. 설명은 "프로젝트 테스트 스위트를 실행하고 결과를 분석한다"이며 테스트 실행, 커버리지 확인, 실패 원인 분석을 요청받을 때 쓴다.

본문의 핵심 가치는 방대한 테스트 출력에서 핵심 정보를 증류해 메인 대화에 정확한 테스트 요약을 주는 것이다. 실행 절차는 네 단계다.

1. 프로젝트의 테스트 명령을 확인한다(package.json이나 CLAUDE.md 참조).
2. 테스트 스위트를 실행한다.
3. 출력을 분석해 통과와 실패를 구분한다.
4. 실패한 테스트는 구체적 원인을 짚는다.

출력 형식은 "Test Summary"(총 개수, 통과, 실패, 건너뜀), "Failure Details"(실패한 테스트만, 한 문장 원인과 `file_path:line_number`), "Suggestions"(뚜렷한 실패 패턴이 있을 때 수정 방향)다. 출력에 전체 테스트 로그를 넣지 말고 이 형식의 요약만 넣으라는 주의가 붙는다.

Haiku를 고른 이유는 테스트 실행, 출력 파싱, 실패 정보 추출이 최고 수준의 추론을 요구하지 않기 때문이다. Haiku는 충분히 해내면서 속도와 비용에서도 유리하다. 단위 테스트를 돌리려고 수석 아키텍트를 고용하지 않는 것과 같다.

## 5. 사용법 두 가지

| 방식 | 설명 |
|---|---|
| 자동 위임 | 사용자가 평소처럼 요청하면 Claude가 작업 성격을 보고 특정 서브에이전트에 위임할지 스스로 판단한다 |
| 명시적 요청 | 사용자가 Claude에게 특정 서브에이전트를 호출해 작업을 하라고 직접 지시한다 |

자동 위임 예시에서 사용자가 "src/payment/ 디렉터리의 코드 변경을 리뷰해 줘"라고 하면 Claude는 리뷰 전문가에게 위임한다. 그 과정에서 code-reviewer가 수십 개 파일을 읽고 여러 코드 패턴을 검색했을 수 있지만 세부 사항은 모두 격리된 컨텍스트에 남고, 메인 대화에는 두 가지 간결한 결론만 나온다. 예를 들어 `[Critical]` src/payment/processor.ts:45의 SQL 인젝션 위험, `[Minor]` src/payment/validator.ts:23의 경계값 검사 누락이다.

## 6. 핵심 정리

- 서브에이전트는 `.claude/agents/`의 마크다운 파일이며, front matter는 "무엇인가", 본문은 "어떻게 일하는가"를 정한다.
- description은 자동 위임의 라우팅 근거, tools는 보안 장벽, model은 비용 레버다.
- permissionMode: plan은 tools 화이트리스트를 강화할 뿐이며, 부모가 auto 모드면 무시된다. 믿을 경계는 tools다.
- 실행형은 Bash가 필요하므로 권한이 넓지만, 출력 형식은 더 엄격하게 요약만 돌려주도록 한다.
- skills와 hooks 필드는 고급 설정이다.
