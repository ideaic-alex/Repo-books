# 토큰 경제학

"카게, 서브에이전트를 쓰면 API 호출 비용이 늘어나나요?" 샤오빙이 매우 현실적인 질문을 던진다. 답은 의외다. 대부분의 상황에서 서브에이전트를 합리적으로 쓰면 비용이 늘기는커녕 전체 토큰 소비가 의미 있게 줄 수 있다. 책은 이 원리를 "토큰 경제학"이라 부르며 숫자로 보여 준다.

이 문서는 서브에이전트를 쓰지 않을 때와 쓸 때의 토큰 계산을 따라가 보고, 프롬프트 캐싱이 이 이점을 얼마나 깎는지, 그럼에도 서브에이전트가 가치 있는 이유(컨텍스트 윈도 보호와 응답 품질), 그리고 도입 여부를 가르는 기준을 정리한다.

---

## 1. 비용의 원리: 잡음은 매 라운드 다시 전송된다

Claude의 API는 보통 상태를 유지하지 않는다(stateless). 그래서 호출할 때마다 전체 컨텍스트 이력을 다시 보내야 한다. 메인 Claude가 테스트를 직접 실행해 10,000토큰의 출력이 나왔다면, 이 내용이 메인 대화 컨텍스트에 들어간 순간부터 이후 모든 상호작용 라운드에서 반복 전송된다. 대화를 다섯 번 더 하면 테스트의 "잡음" 데이터가 다섯 번 더 중복 전송된다.

## 2. 계산 비교

가정은 다음과 같다. 시스템 프롬프트는 5,000토큰, 기존 대화 이력은 8,000토큰, 테스트 출력(잡음)은 10,000토큰이고, 이후 5라운드는 라운드마다 약 1,000토큰씩 늘어난다.

### 2-1. 서브에이전트가 없을 때

| 라운드 | 계산 | 합계 |
|---|---|---|
| 5 | 5,000(시스템) + 8,000(이력) + 10,000(테스트) | 23,000 |
| 6 | 5,000 + 9,000 + 10,000 | 24,000 |
| 7 | 5,000 + 10,000 + 10,000 | 25,000 |
| 8 | 5,000 + 11,000 + 10,000 | 26,000 |
| 9 | 5,000 + 12,000 + 10,000 | 27,000 |

5~9라운드 총 소비는 125,000토큰이다.

### 2-2. 서브에이전트가 있을 때

테스트 출력은 서브에이전트의 독립 컨텍스트 안에 엄격히 격리되고, 메인 대화는 약 100토큰의 테스트 요약만 받는다.

| 위치 | 라운드별 계산 | 소계 |
|---|---|---|
| 서브에이전트 내부 | 1라운드 5,500(시스템 5,000 + 작업 설명 500), 2라운드 8,500(부분 출력 3,000 포함), 3라운드 11,500(누적 출력 6,000), 4라운드 15,500(전체 출력 10,000) | 41,000 |
| 메인 대화 | 5라운드 13,100, 6라운드 14,100, 7라운드 15,100, 8라운드 16,100, 9라운드 17,100(각각 시스템 5,000 + 이력 + 요약 100) | 75,500 |

합계는 41,000 + 75,500 = 116,500토큰이다. 절약량은 125,000 - 116,500 = 8,500토큰이고 절감률은 약 6.8%다.

### 2-3. 추세

후속 대화 라운드가 늘수록 대량 잡음 데이터의 반복 전송을 피한 덕에 절감률이 크게 오른다. 이 예는 후속 대화 5라운드만으로 6.8%를 아끼며, 10~20라운드로 늘면 절감률은 더 커진다. 대량 로그 분석 뒤 여러 라운드의 깊은 논의를 이어 가는 극단적 시나리오에서는 토큰 절감률이 50%를 넘을 수도 있다고 책은 말한다.

## 3. 프롬프트 캐싱의 영향

Anthropic의 프롬프트 캐싱(Prompt Caching, 반복되는 앞부분 입력을 저장해 두고 싸게 재사용하는 기능) 메커니즘은 위의 비용 이점을 어느 정도 깎는다. 캐시에 적중한 토큰은 표준 가격의 10%만 청구되므로, 메인 대화에서 반복 전송되는 테스트 출력도 캐시되면 실제 비용이 훨씬 낮아진다. 캐싱을 반영해 다시 계산하면 이 예의 절감은 6.8%에서 1~2%로 떨어진다.

## 4. 그래도 가치 있는 이유: 비용은 핵심이 아니다

비용 최적화는 서브에이전트 가치의 한 차원일 뿐 핵심 가치도 아니다. 프롬프트 캐싱이 대체하지 못하는 두 가지 핵심 이점이 있다.

- 컨텍스트 윈도 보호: 대형 모델의 컨텍스트 윈도 용량은 유한하다. 잡음 데이터가 공간을 차지하면 Claude가 컨텍스트 압축(compaction)을 일찍 발동할 수 있고, 그 과정에서 핵심 정보가 "우선순위가 낮다"고 판단되면 쉽게 사라진다. 잡음을 독립 컨텍스트에 격리하면 메인 대화를 위한 귀한 공간이 보존되어 핵심 정보의 온전함이 유지된다.
- 응답 품질 향상: 깨끗한 컨텍스트는 Claude의 집중력을 크게 높인다. 대화 이력이 무관한 로그와 테스트 출력으로 가득하면 Claude의 "어텐션 메커니즘"이 분산되어 생성 품질이 떨어진다. 샤오빙이 처음에 겪은 전형적 딜레마다. 서브에이전트의 격리 구조는 이 "주의력 희석" 문제를 근본적으로 풀어, 메인 모델이 늘 질 높고 관련도 높은 정보로 추론하게 한다.

## 5. 언제 쓰면 오히려 손해인가: 입력 대 출력 비율

간결한 결정 규칙은 입력량 대 출력량의 비를 보는 것이다.

| 구분 | 상황 | 판단 |
|---|---|---|
| 고가치(입력 >> 출력) | 시스템 로그 수백 줄을 분석해 핵심 결론 다섯 개만 뽑는 경우처럼 입력이 최종 출력을 크게 웃돈다 | 서브에이전트의 가치가 특히 크다 |
| 저가치(입력 ≈ 출력) | 함수 하나를 고치거나 코드 주석을 쓰는 경우처럼 입력과 출력이 비슷하고 중간 데이터가 적다 | 서브에이전트의 격리 오버헤드가 아깝다. 메인 대화에서 바로 처리하는 편이 더 단순하고 효율적이며, 불필요한 아키텍처 복잡성과 소통 비용도 없다 |

## 6. 서브에이전트 도입을 정하는 네 가지 차원

Kage의 메모는 도입 판단을 네 가지 핵심 차원으로 요약한다.

1. 대규모 파일 읽기(입력 잡음 격리): 작업이 보통 다섯 개 넘는 많은 파일을 읽거나 방대한 데이터 소스를 처리해야 할 때, 서브에이전트로 파일을 읽는 동안 생기는 "입력 잡음"을 독립 환경에 완전히 가둘 수 있다. 메인 대화 컨텍스트가 중복 파일 내용으로 빨리 차는 것을 막는다.
2. 고빈도 출력 생성(출력 잡음 필터링): 종합 테스트 보고서, 상세 시스템 로그, 전체 빌드 과정 기록처럼 중간 출력이 많이 나올 것으로 예상되면 서브에이전트가 "필터"로서 간결한 요약이나 핵심 오류 정보만 돌려준다. 긴 출력이 메인 모델의 주의력을 희석하고 토큰을 낭비하는 것을 막는다.
3. 컨텍스트 무결성 보호(장기 작업 계획): 현재 작업이 복잡한 워크플로의 일부일 때 메인 대화에 후속의 깊은 상호작용과 추론을 뒷받침할 컨텍스트 공간이 충분히 남아 있어야 한다. 소모가 큰 하위 작업을 덜어내면 메인 대화의 컨텍스트 윈도가 한꺼번에 고갈되는 것을 막고 장기 작업 정보의 일관성과 완전성을 지킨다.
4. 운영 권한과 보안 경계(위험 관리): 작업이 민감한 연산(파일 시스템 쓰기, 네트워크 요청, 외부 명령 실행)을 포함하거나 엄격한 권한 통제가 필요할 때, 서브에이전트를 권한이 제한된 독립 샌드박스로 구성할 수 있다. 하위 작업이 실패하거나 악의적으로 동작해도 영향이 국소 범위에 갇혀 메인 시스템의 자연스러운 보안 방화벽이 된다.

## 7. 핵심 정리

- 잡음이 메인 컨텍스트에 들어가면 이후 모든 라운드에서 다시 전송되므로, 격리하면 라운드가 쌓일수록 이득이 커진다. 예시에서는 5라운드에 125,000토큰에서 116,500토큰으로 약 6.8% 절감이다.
- 프롬프트 캐싱을 고려하면(적중분은 표준 가격의 10%) 이 예의 절감은 1~2%로 줄어든다.
- 진짜 가치는 컨텍스트 윈도 보호와 응답 품질이다.
- 입력이 출력보다 훨씬 클 때 쓰고, 입력과 출력이 비슷하면 메인 대화에서 직접 처리한다.
- 참고(노트 작성자): 위 계산은 책의 가정 수치를 그대로 쓴 설명용 예이며 실제 요금이나 측정값이 아니다. 책도 극단적 시나리오에서 50% 초과 절감이 "가능하다"고만 말한다.
