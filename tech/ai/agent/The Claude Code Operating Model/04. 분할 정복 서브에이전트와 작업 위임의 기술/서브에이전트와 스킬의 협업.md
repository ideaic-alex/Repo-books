# 서브에이전트와 스킬의 협업

앞의 모드들은 작업 분해와 격리 능력을 잘 보여 주지만 한 가지 핵심 질문을 피해 갔다. 서브에이전트의 "전문 지식"은 어디서 오는가? 파이프라인의 bug-fixer를 보자. null 검사 버그를 고치는 임무를 맡았고 Read, Edit, Write, Bash 등 도구는 다 갖췄지만, 프로젝트의 코딩 표준은 모른다. 오류 처리는 Result 패턴인가 try-catch인가, 로깅은 console.log인가 프로젝트 전용 logger인가, 변수 이름은 camelCase인가 snake_case인가.

이 규범을 프로젝트의 CLAUDE.md에 적어 두면 서브에이전트가 자동으로 상속하기는 한다. 그러나 CLAUDE.md는 대개 일반 규범만 다루고 "버그 수정용 보안 코딩 체크리스트" 같은 깊은 도메인 지식까지 담기 어렵다. 그런 지식은 스킬의 영역이다. 이 문서는 스킬과 서브에이전트를 결합하는 두 방향, 두 예제, 역할 분담 원칙, 선택 기준을 정리한다.

---

## 1. 결합의 두 가지 원자 모드

스킬과 서브에이전트를 결합하는 원자적 모드는 두 가지뿐이며, 핵심 차이는 포함 관계다.

| 구분 | 방향 A: 서브에이전트가 스킬을 미리 로드 | 방향 B: 스킬이 서브에이전트를 띄움 |
|---|---|---|
| 포함 관계 | 서브에이전트가 스킬을 포함 | 스킬이 서브에이전트를 포함 |
| 설정 | 서브에이전트 정의의 skills 필드 | 스킬의 context: fork 설정 |
| 역할 | 서브에이전트는 실행자, 스킬은 그의 매뉴얼 | 스킬은 배차 담당(dispatcher), 서브에이전트는 실행 인스턴스 |
| 시스템 프롬프트 | 서브에이전트 정의 파일 본문이 시스템 프롬프트가 되고 스킬 전문은 도메인 지식 컨텍스트로 주입 | agent 필드로 지정한 에이전트 유형이 시스템 프롬프트를 제공하고 SKILL.md 내용은 구체적 작업 지시로 전달 |
| 적합한 상황 | 파이프라인에서 특정 도메인 지식이 필요한 역할(보안 코딩 표준을 읽는 bug-fixer, 문서 생성 절차를 읽는 doc-generator) | 엄격한 격리와 일회성 완료가 필요한 무거운 작업(깊은 코드 분석, 대량 문서 생성) |

책은 두 방식의 밑바닥 메커니즘은 완전히 같지만 호출 관계가 근본적으로 반대라고 요약한다. 시스템 프롬프트를 누가 쥐느냐가 핵심 차이다.

## 2. 방향 A 예제 1: bug-fixer와 secure-coding

개선된 bug-fixer는 front matter에 `skills:` 필드로 secure-coding 스킬을 미리 로드한다.

```yaml
# .claude/agents/bug-fixer.md
tools: [Read, Grep, Glob, Edit, Write, Bash]
skills:
- secure-coding       # 보안 코딩 스킬 미리 로드

# .claude/skills/secure-coding/SKILL.md
name: secure-coding
description: Secure coding checklist for bug fixes and new features.
  Use when fixing bugs, writing new code, or reviewing security aspects.
user-invocable: false
```

참고(노트 작성자): 위 코드는 책의 두 파일에서 필드만 추려 한 블록으로 합친 것이다. 원문에서는 각각 별도의 front matter다.

bug-fixer 본문은 secure-coding 스킬이 정의한 체크리스트를 엄격히 따르되 null 검사, 입력 검증, 오류 처리 패턴에 특별히 유의하라고 지시한다. 수정 원칙은 최소 변경, 부작용 없음, 표준 준수, 방어적 프로그래밍이고, 출력에는 수정 파일과 이유 외에 스킬 체크리스트 중 통과 확인된 항목(Security checklist items)이 추가된다.

secure-coding 스킬의 본문은 세 영역으로 이뤄진다.

- Null 방어: 외부 입력은 모두 null이 아님을 검사한다. 중첩 속성 접근에는 옵셔널 체이닝(?.)을 우선하고 non-null 단언(!)은 엄격히 금지한다. 데이터베이스 조회 결과는 비즈니스 로직에 쓰기 전에 null 여부를 명시적으로 확인한다.
- 오류 처리: 비즈니스 예외는 프로젝트의 통합 AppError 클래스를 쓰고 네이티브 예외나 문자열을 직접 던지는 것을 금지한다. 빈 catch 블록은 엄격히 금지하며 예외를 잡았으면 최소한 오류 로그를 남기거나 재시도 메커니즘을 둔다. 모든 비동기 작업에는 명확한 타임아웃을 둔다.
- 로깅: 운영 환경에서 console.log() 사용을 엄격히 금지하고 프로젝트가 감싼 logger 객체(logger.error() 등)를 쓴다. 오류 로그에는 고유한 오류 코드와 완전한 스택 트레이스를 넣는다. 데이터 마스킹으로 비밀번호나 API 토큰 같은 민감 정보를 로그에 찍는 것을 금지한다.

여기서 `user-invocable: false`는 이 스킬이 사용자의 `/` 메뉴에 나타날 필요가 없다는 뜻이다. 순수한 "참고 매뉴얼" 성격이며 서브에이전트가 시작될 때 자동으로 미리 로드된다.

## 3. 방향 A 예제 2: api-doc-generator와 api-generating

두 번째 예는 영역이 다른 API 문서 생성기다. api-doc-generator 서브에이전트는 도구로 Read, Grep, Glob, Write, Bash를 갖고, `skills: [api-generating]`으로 "문서 생성 스킬"을 미리 로드해 전문성을 키운다. 이 설정은 본질적으로 서브에이전트에게 "작업 매뉴얼"을 건네는 것이다. 역할(API 문서 전문가)이 분명하고 스킬에 구체적인 단계, 템플릿, 스크립트가 담긴 전문 워크플로가 들어 있으므로, 서브에이전트는 만능 일반 에이전트에서 전문 기술을 가진 도메인 전문가로 바뀐다.

## 4. 역할 분담 원칙: 정체성은 서브에이전트, 방법은 스킬

두 예제(bug-fixer + secure-coding, api-doc-generator + api-generating)는 명확한 책임 분담 원칙을 드러낸다. 서브에이전트는 "정체성과 목표"를, 스킬은 "방법과 표준"을 정의한다.

| 담당 | 질문 | 내용 예 |
|---|---|---|
| 서브에이전트(.md 파일, 전략 수준) | Who(정체성) | "당신은 취약점 수정 전문가다", "API 문서 전문가다" 같은 역할 설정 |
| 서브에이전트 | What(작업) | "취약점을 고친다", "API 문서를 생성한다" 같은 핵심 목표 |
| 서브에이전트 | Where(범위) | "docs/api/ 디렉터리에 쓴다" 같은 작업 경계 |
| 서브에이전트 | Output(산출물) | "수정 내역 요약을 반환한다", "라우트 개수를 센다" 같은 출력 형식 |
| 스킬(SKILL.md와 관련 파일, 전술 수준) | How(절차) | "1단계: detect-routes.py 실행, 2단계: 결과 분석" 같은 운영 단계 |
| 스킬 | With What(도구) | scripts/detect-routes.py 스크립트, templates/api-doc.md 템플릿 같은 필요한 자원 |
| 스킬 | By What Standard(규범) | "인증 미들웨어를 확인해 잠금 표시" 같은 실행 기준 |
| 스킬 | Quality(품질) | "모든 라우트가 기록되고 스키마가 코드와 정확히 일치" 같은 합격 기준 |

이 분리는 강력한 재사용성을 준다. 같은 secure-coding 스킬을 bug-fixer가 미리 로드해 취약점 수정에 쓸 수도, code-reviewer가 호출해 코드 규정 준수를 감사할 수도 있다. api-generating 스킬도 새 문서를 만드는 서브에이전트를 돕거나 기존 문서의 규정 준수를 검증하는 API 리뷰 서브에이전트에 힘을 줄 수 있다. 요컨대 스킬은 재사용 가능한 지식 모듈이고 서브에이전트는 그 지식의 유연한 소비자다.

## 5. 방향 B 예제: codebase-health-check

방향 B의 예는 스킬 자체가 격리된 서브에이전트를 띄우는 경우다.

```yaml
# .claude/skills/codebase-health-check/SKILL.md
name: codebase-health-check
description: Perform comprehensive code health analysis
context: fork
agent: general-purpose
allowed-tools: [Read, Grep, Glob]
```

사용자가 `/codebase-health-check src/`를 입력하면 시스템이 격리된 컨텍스트에서 서브에이전트를 자동으로 띄운다. 이 서브에이전트는 모든 파일을 스캔하고, 문제를 분석하고, 보고서를 생성할 수 있으며, 메인 대화는 간결한 최종 결과만 받는다. 그 과정의 방대한 파일 내용과 추론은 메인 컨텍스트를 전혀 오염시키지 않는다.

## 6. 어느 쪽을 고르나: 누가 주인공인가

판단 기준은 단순하다. 주인공이 누구인가.

| 구분 | 방법 A: 역할 중심(서브에이전트가 주인공) | 방법 B: 지식/프로세스 중심(스킬이 주인공) |
|---|---|---|
| 핵심 논리 | 작업의 열쇠가 구체적 역할 정체성과 협업 과정에 있다 | 작업의 열쇠가 표준화된 지식 프로세스의 실행에 있고 실행자는 중요하지 않거나 오히려 격리되어야 한다 |
| 예 | 파이프라인의 bug-fixer가 취약점 수정에 전문성을 계속 적용한다. 서브에이전트는 장기적 "전문가", 스킬은 도구함의 "렌치" | codebase-health-check는 표준화된 점검 절차다. 스킬이 "어떻게"를 정하고 서브에이전트는 컨텍스트를 격리하려 만든 임시 "실행 컨테이너" |
| 선택 | 역할 상태를 유지하거나, 다회 상호작용이나 복잡한 협업을 할 때 | 작업이 일회성이거나, 엄격한 컨텍스트 격리가 필요하거나, 표준 프로세스를 재사용하는 데 초점이 있을 때 |

## 7. 핵심 정리

- 서브에이전트에게 도메인 지식을 주는 길은 CLAUDE.md 상속과 스킬이다. 깊은 전문 지식은 스킬로 준다.
- 방향 A는 서브에이전트가 skills 필드로 스킬을 미리 로드하고, 방향 B는 스킬이 context: fork와 agent 필드로 서브에이전트를 띄운다.
- 시스템 프롬프트의 주인이 다르다. A는 에이전트 정의 본문, B는 agent 필드의 에이전트 유형이다.
- 서브에이전트는 정체성, 목표, 범위, 산출물을, 스킬은 절차, 자원, 규범, 품질 기준을 맡는다.
- 주인공이 역할이면 A, 표준 프로세스나 일회성 격리면 B를 고른다.
