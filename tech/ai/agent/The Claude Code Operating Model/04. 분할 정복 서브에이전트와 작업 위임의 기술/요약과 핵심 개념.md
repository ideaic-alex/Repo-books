# 요약과 핵심 개념

이 장은 하나의 대화창에 모든 정보를 쑤셔 넣어 Claude가 "정보의 홍수에 빠지는" 문제에서 출발했다. 해법은 독립된 컨텍스트에서 일하고 결론만 돌려주는 서브에이전트다. 정의와 설정, 다섯 가지 모드, 스킬과의 두 가지 결합 방향, 토큰 경제학, 소프트웨어 공학 패턴과의 대응, 실무 고려 사항을 차례로 다뤘다.

원서의 요약은 이렇게 말한다. 서브에이전트는 Claude Code 확장 시스템에서 아키텍처 면에서 가장 중요한 기능이다. CLAUDE.md가 Claude에게 기억하는 능력을, 스킬이 도메인 전문성을 준다면, 서브에이전트는 더 근본적인 능력, 곧 복잡성을 분해하는 능력을 준다. 여러 차원에 걸쳐 있고 잡음이 많으며 다단계 처리가 필요한 복잡한 작업에서, 전체 작업을 초점이 분명한 하위 작업들로 쪼개 격리된 컨텍스트에서 독립적으로 실행하고 정제된 핵심 결론만 메인 대화로 모아 오라는 구조적 전략을 준다. 그 가치는 기술적 차원(컨텍스트 격리, 권한 제약, 토큰 활용 효율 최적화)뿐 아니라 더 깊게는 "위임하는 사고방식"을 기른다는 데 있다. 모든 세부 사항을 한 대화에 밀어 넣지 않고, 노련한 관리자처럼 각 작업의 책임 경계, 능력 요건, 납품 기준을 분명히 해 알맞은 실행자에게 맡기는 것이다. 책은 이것이 모듈 설계, 마이크로서비스 아키텍처, 관심사 분리와 맞닿은 "복잡성을 어떻게 효과적으로 관리하는가"라는 영원한 과제의 답이라고 한다. 다음 5장은 훅 기반의 이벤트 구동 자동화다. 스킬과 서브에이전트가 주로 Claude의 "인지 수준"에서 작동한다면, 훅은 "시스템 실행 수준"으로 통제를 넓혀 Claude가 어떻게 생각할지가 아니라 물리적 실행 단계에서 행동을 직접 가로채 제약한다.

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | 컨텍스트 윈도 딜레마 | 잡음이 쌓이면 신호가 묻히는 컨텍스트 오염 이해, 서브에이전트를 CEO 위임 모델로 파악 |
| 2 | 정의와 설정 | `.claude/agents/`의 마크다운 파일, front matter 필드별 의도, 자동 위임과 명시적 요청 |
| 3 | 모드 | 읽기 전용, 실행, 병렬, 파이프라인, 팀(실험적) |
| 4 | 스킬과의 협업 | 방향 A(skills 필드로 미리 로드)와 방향 B(context: fork)의 역할 분담 |
| 5 | 토큰 경제학 | 예시 계산에서 약 6.8% 절감, 캐싱 반영 시 1~2%, 진짜 가치는 컨텍스트 보호와 품질 |
| 6 | 소프트웨어 공학 관점 | 단일 책임, 벌크헤드, MapReduce, 책임 연쇄와의 대응 |
| 7 | 실무 고려 사항 | CLAUDE.md 상속, 메시지 전달, 중단 복구, 중첩 두 층 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 컨텍스트 오염 | 무관한 정보가 컨텍스트에 쌓여 신호를 희석하고 사고를 방해하는 현상 |
| 서브에이전트 | 독립 컨텍스트, 제한된 도구, 명확한 작업 범위를 가진 Claude 인스턴스. 결론만 돌려준다 |
| 격리, 제약, 재사용 | 서브에이전트의 세 가치. 프로세스 격리, 최소 권한, 컴포넌트화에 각각 대응 |
| tools 화이트리스트 | 서브에이전트가 쓸 수 있는 도구를 정하는 필드. 진짜 물리적 경계 |
| permissionMode: plan | 읽기 전용 계획 모드. tools를 강화할 뿐이며 부모가 auto 모드면 무시된다 |
| model | 작업 난이도에 맞춰 Haiku, Sonnet, Opus를 고르는 비용 레버 |
| 읽기 전용 모드 | Read, Grep, Glob만 쓰는 관찰자(리뷰, 감사, 분석) |
| 실행 모드 | 잡음 많은 작업을 요약으로 바꿈. 파사드 패턴, 구조적 격리가 핵심 |
| 병렬 모드 | 완전히 독립된 하위 작업을 동시에 실행. MapReduce |
| 파이프라인 모드 | 의존 있는 단계의 직렬 사슬. 단계별 최소 권한과 인수인계 계약 |
| 팀 모드 | 팀 리드, 팀원, 작업 목록, 메일박스로 구성. 실험적이고 기본 비활성이다(CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS) |
| skills 필드 / context: fork | 서브에이전트가 스킬을 미리 로드 / 스킬이 서브에이전트를 띄움 |
| 정체성은 서브에이전트, 방법은 스킬 | Who, What, Where, Output은 서브에이전트가, How, With What, Standard, Quality는 스킬이 정의 |
| 입력 대 출력 비율 | 입력이 출력보다 훨씬 클 때만 서브에이전트가 가치 있다 |
| 메시지 전달 | 서브에이전트는 서로 직접 통신하지 못하고 메인 에이전트가 넘긴 것만 본다 |

## 3. 자주 놓치는 점

- 서브에이전트는 OS 프로세스 포크가 아니라 별도의 컨텍스트, 시스템 프롬프트, 도구 권한을 가진 새 에이전트 인스턴스다. 프로세스 격리는 비유로만 쓴다.
- 읽기 전용을 보장하는 것은 permissionMode가 아니라 tools 화이트리스트다. Edit, Write, Bash를 빼야 쓸 수 없다.
- 병렬은 하위 작업이 완전히 독립일 때만 쓴다. "찾은 뒤에 고친다"처럼 의존이 있으면 파이프라인이다.
- 파이프라인의 신뢰성은 상류 출력과 하류 입력 형식을 맞추는 인수인계 계약에서 나온다.
- 병렬 실행(동시성)과 백그라운딩은 다른 것이다. 단축키는 버전과 플랫폼마다 다르니 자기 환경에서 확인한다.
- 실행 모드의 핵심은 출력 형식 지시가 아니라 구조적 격리다. 형식은 2차 안전장치다.
- 토큰 절감은 프롬프트 캐싱을 고려하면 작아진다. 하지만 컨텍스트 보호와 응답 품질이라는 이점은 남는다.
- 일회성이고 입력과 출력이 비슷한 작은 작업은 메인 대화에서 직접 하는 편이 낫다.
- 팀 모드는 비용이 크고 실험적이므로 복잡한 협업에만 쓴다. 대부분은 읽기 전용과 실행 모드로 충분하다.
- 중첩은 두 층 정도로 유지한다. 강제 한도가 아니라 유지보수성 때문이다.

## 4. 생각해 볼 질문 (원서의 Discussion Questions)

1. 팀에서 자동화된 PR 리뷰 프로세스를 만들어야 한다. 코드 품질 점검, 보안 취약점 스캔, 성능 분석을 동시에 수행하고 결과를 종합 리뷰 보고서로 통합해야 한다. 서브에이전트 아키텍처를 설계해 보자. 서브에이전트는 몇 개를 배치하는가? 병렬과 파이프라인 중 어느 패턴을 쓰는가? 각 서브에이전트의 도구 권한은 어떻게 구성하는가?
2. 토큰 경제학에서는 "후속 대화 5라운드"를 가정했다. 작업 실행 뒤 후속 상호작용이 전혀 없는 일회성 실행이라면 서브에이전트 아키텍처가 여전히 비용 이점을 주는가? 어떤 구체적 조건에서 서브에이전트 도입이 오히려 토큰 소비를 급증시켜 전체 비용을 높일 수 있는가?
3. 이 장에서 다섯 가지 서브에이전트 설계 패턴과 그 밑의 소프트웨어 공학 원리를 살펴보았다. 실제 프로젝트에서 서브에이전트 아키텍처로 풀기에 특히 알맞은 문제 상황이 있는가? 있다면 어느 패턴에 맞는가? 구체적인 비즈니스 로직에 비춰 그 패턴을 고른 깊은 이유를 설명해 보자.

참고(노트 작성자): 1번 질문의 실마리는 본문에 있다. 세 점검은 서로 결과를 기다릴 필요가 없는 독립 작업이므로 병렬 모드(MapReduce 구조)가 맞고, 읽기 전용 권한(Read, Grep, Glob)만 주어도 충분하며, 종합 보고서 작성은 메인 에이전트의 Reduce 단계가 맡는다. 2번의 실마리는 토큰 경제학 문서의 "입력 대 출력 비율" 기준, 그리고 서브에이전트가 자기 컨텍스트에서 입력을 읽는 비용(예시의 41,000토큰)이 별도로 든다는 계산이다. 정답은 책에 없으며 이 힌트는 노트 작성자의 해석이다.
