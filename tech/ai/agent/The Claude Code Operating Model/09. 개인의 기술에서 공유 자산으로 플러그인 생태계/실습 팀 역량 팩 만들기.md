# 실습 팀 역량 팩 만들기

이론만으로는 몸에 붙지 않는다. 이 실습은 React, TypeScript, PostgreSQL 기술 스택을 쓰는 팀의 일원이 되어, 코드 리뷰, 보안 스캔, 자동 포맷팅을 한데 묶은 내부 플러그인 `team-toolkit`을 만들고 배포하는 과정이다.

순서는 디렉터리 구조 설계, `plugin.json`, 보안 스캔 서브에이전트, 훅 보안 검사 스크립트, 릴리스다. 마지막에 이 플러그인이 "내부용"인 이유가 무엇인지 짚는다.

---

## 1. 전체 디렉터리 구조

```
team-toolkit/
├── .claude-plugin/plugin.json
├── commands/   review.md (코드 리뷰), test.md (테스트 실행)
├── agents/     security-scanner.md, quick-fix.md
├── skills/react-patterns/SKILL.md   (React 모범 사례 지식)
├── hooks/      hooks.json, check-bash.sh, auto-format.sh
├── .mcp.json   (데이터베이스와 GitHub 연결)
└── README.md
```

앞 문서의 규칙대로 매니페스트만 `.claude-plugin/` 안에 있고 나머지는 루트에 있다. 구성 요소는 다섯 종류가 모두 들어간다. 명령 2개, 에이전트 2개, 스킬 1개, 훅 설정 1벌, MCP 설정 1개다.

## 2. plugin.json

`name`은 `team-toolkit`, `version`은 `2.0.0`, `description`은 팀 표준 개발 도구 모음(코드 리뷰, 자동 테스트, 보안 스캔 통합), `author`는 `Platform Team`, `repository`는 `https://github.com/our-company/team-toolkit`, `license`는 `MIT`, `keywords`는 team, devops, code-review, security다. 필수 필드 세 가지(name, version, description)와 선택 필드가 모두 채워져 있다. 이름에 `team-` 접두어를 붙여 구체성을 확보했다.

## 3. 보안 스캔 서브에이전트

`agents/security-scanner.md`는 프런트매터에서 `tools: Read, Grep, Glob`로 읽기 전용 도구만 주고 `model: sonnet`을 지정한다. 본문은 네 부분이다.

| 부분 | 내용 |
|---|---|
| 스캔 범위 | 주입 취약점(SQL 인젝션, 명령 주입, XSS), 인증 문제(약한 비밀번호 정책, 하드코딩된 자격 증명, 세션 관리 결함), 데이터 노출(로그에 남은 민감 정보, 안전하지 않은 전송), 접근 제어(권한 검사 누락, 경로 순회) |
| 작업 흐름 | 1) Glob으로 소스 파일 전체 수집 2) Grep으로 `eval`, `dangerouslySetInnerHTML`, `exec` 같은 의심 패턴 검색 3) Read로 의심 코드 문맥을 보고 진짜 취약점인지 확인 4) 파일명, 줄 번호, 위험 수준을 담은 구조화 보고서 출력 |
| 실행 원칙 | 확실한 증거: 구체적 코드 근거가 있는 문제만 보고하고 주관적 추측은 금지 |
| | 해결 지향: 문제 지적에 그치지 않고 구체적이고 실행 가능한 수정안 제시 |
| | 엄밀한 표시: 완전히 확인할 수 없는 잠재 위험은 "의심(suspected)"으로 분명히 표시 |

도구가 Read, Grep, Glob뿐이므로 이 에이전트는 코드를 고칠 수도 명령을 실행할 수도 없다. 다음 문서에서 다룰 최소 권한 원칙을 실제로 구현한 사례다. 원서의 작업 흐름 첫 항목은 번호 "1."이 빠져 인쇄되어 있어 순서대로 복원했다.

## 4. 훅: Bash 보안 검사 스크립트

`hooks/check-bash.sh`는 Claude Code가 위험한 명령을 실행하기 전에 막는다. 동작은 다음과 같다.

1. 표준 입력으로 들어온 JSON에서 `jq`로 `.tool_input.command`를 꺼낸다(없으면 빈 값).
2. 위험 패턴 배열 `rm -rf /`, `rm -rf ~`, `sudo rm`, `> /dev/`, `chmod 777`을 하나씩 명령에 포함됐는지 `grep -qF`로 검사한다.
3. 걸리면 `{"decision": "deny", "reason": "Blocked dangerous pattern: ..."}`를 출력하고 종료한다.
4. 아무것도 안 걸리면 `{"decision": "allow"}`를 출력한다.

```bash
INPUT=$(cat)
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command // empty')
# DANGEROUS_PATTERNS 각각에 대해 grep -qF 로 검사
#   걸리면: {"decision": "deny", "reason": "Blocked dangerous pattern: $pattern"} 출력 후 exit 0
echo '{"decision": "allow"}'
```

참고(노트 작성자): 위 코드는 원서 스크립트의 반복문 부분을 주석으로 줄인 것이다. 원서에서 이 스크립트가 쪽 경계에서 갈라져 있고 heredoc(`cat << EOF`) 구간이 나오지만 내용은 위 흐름과 같다. 이 스크립트가 쓰려면 `jq`가 설치되어 있어야 한다. 또한 8장의 SDK 훅이 `permissionDecision`을 쓰는 반면 이 셸 스크립트는 `decision`을 쓰는데, 원서는 이 차이를 따로 설명하지 않는다.

## 5. 릴리스 절차

플러그인은 본질적으로 표준 Git 저장소다. 새 버전 릴리스는 코드를 커밋하고, 태그를 달고, 원격 저장소에 푸시하는 과정이다. 플러그인 루트(`team-toolkit`)에서 한다.

```
git init
git add .
git commit -m "v2.0.0: Integrated security scanning and auto-formatting features"
git tag v2.0.0
git remote add origin https://github.com/our-company/team-toolkit
git push -u origin main --tags
```

팀원은 `/plugin install github.com/our-company/team-toolkit`로 설치한다.

### 5-1. 무엇이 이 플러그인을 "내부용"으로 만드는가

플러그인 시스템 안에는 내부용이라는 개념이 따로 없다. 내부용으로 만드는 것은 저장소 권한이다. 설치하는 사람은 이미 그 저장소에 읽기 권한이 있어야 한다. 저장소가 공개이면 그 플러그인은 전혀 내부용이 아니다. 비공개 저장소로 두고 권한을 관리하는 것이 곧 배포 범위 관리다.

---

## 6. 핵심 정리

- `team-toolkit`은 명령, 에이전트, 스킬, 훅, MCP 설정을 모두 담은 팀 표준 도구 모음이다.
- 보안 스캔 에이전트는 Read, Grep, Glob만 쓰고, 증거 있는 문제만 보고하며 불확실하면 "의심"으로 표시한다.
- 훅 스크립트는 표준 입력 JSON을 `jq`로 읽어 위험 패턴이면 deny, 아니면 allow를 출력한다.
- 릴리스는 커밋, 태그, 푸시이고, 내부용 여부는 저장소 권한이 정한다.
