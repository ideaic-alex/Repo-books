# 개인의 기술에서 공유 자산으로 플러그인 생태계

이 장은 개인이 애써 만든 스킬, 훅, MCP 설정, 명령을 팀과 조직이 한 번에 설치할 수 있는 자산으로 바꾸는 플러그인을 다룬다. 플러그인의 폴더 구조와 `plugin.json`, 구성 요소별 파일 형식을 보고, 설치와 수명주기와 이름 충돌을 막는 네임스페이스를 익힌다.

이어서 `team-toolkit` 실습으로 만들고 릴리스하는 과정을 따라가고, 비공개 마켓플레이스와 조직 수준 관리를 살핀다. 끝으로 설계 원칙과 패키징 시점, LSP 지원이 가리키는 미래를 정리한다.

---

## 1. 핵심 요점

- 플러그인은 새 기능이 아니라 흩어진 확장 장치를 한 꾸러미로 묶어 명령 한 줄로 설치하게 하는 배포 형식이다.
- 정체성 파일 `plugin.json`만 `.claude-plugin/` 안에 두고, commands, agents, skills, hooks 폴더와 `.mcp.json`은 루트에 둔다.
- `name`은 네임스페이스를 정한다. 설치 후 구성 요소는 `플러그인이름:구성요소이름`으로 유일해진다.
- 설치 출처는 마켓플레이스, GitHub 저장소, 로컬 디렉터리이고, 개발 중에는 `claude --plugin-dir`로 설치 없이 시험한다.
- 내부용 플러그인은 비공개 저장소의 읽기 권한으로 범위가 정해지며, 여러 팀에는 비공개 마켓플레이스(`.claude-plugin/marketplace.json`)를 쓴다.
- 기업용 조직 수준 관리는 통일 배포, 버전 고정, 감사 가시성을 준다.
- 설계 원칙은 단일 책임, 점진적 반복, 최소 권한, 문서화다. 단일 프로젝트는 `.claude/` 커밋으로 충분하다.
- LSP 지원은 플러그인이 Claude에게 코드의 실시간 상태를 보여 주는 방향이다.
