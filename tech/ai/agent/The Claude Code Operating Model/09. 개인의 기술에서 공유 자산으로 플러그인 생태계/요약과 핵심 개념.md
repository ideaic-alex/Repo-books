# 요약과 핵심 개념

9장은 흩어진 확장 장치를 한 꾸러미로 묶어 배포하는 플러그인 생태계를 다뤘다. 플러그인의 물리 구조와 `plugin.json`, 설치와 수명주기와 네임스페이스, 팀 도구 모음 실습, 비공개 마켓플레이스와 조직 관리, 설계 원칙과 패키징 시점, LSP 지원이 내용이다. 이 문서는 전체 흐름과 용어를 되짚는다.

원서의 요약은 이렇게 이어진다. 플러그인은 다른 네 가지 장치를 배포 가능하게 만든다. 새 기능은 없다. 손으로 쓸 수 있는 명령, 에이전트, 스킬, 훅과 같은 내용이지만, 애써 쌓은 설정 폴더를 동료가 재구성하지 않고 명령 한 줄로 설치하게 한다. 구조상 플러그인은 특정 디렉터리 관례를 따르는 Git 저장소이며 핵심은 `.claude-plugin/`의 `plugin.json`이다. 설치는 `/plugin install`이고 출처는 커뮤니티 마켓플레이스, GitHub 저장소, 로컬 디렉터리 세 가지이며, 네임스페이스가 공존을 보장한다. 팀 실무에서 플러그인의 가치는 기술의 복잡함보다 지식에 하는 일에 있다. 누군가 한 주 걸려 맞춘 코드 리뷰 기준, 보안 훅, 포맷팅 설정이 포장되면 팀 전체가 1초 만에 설치하는 자산이 된다. 다음 10장은 마지막 장으로, 지금까지의 메커니즘이 엔지니어링 실무에서 어떻게 함께 작동하는지, 디버깅과 비용 통제와 팀 단위 확대 방법론을 본다.

---

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | 플러그인의 역할과 물리 구조 | 다섯 구성 요소를 한 꾸러미로. 매니페스트만 `.claude-plugin/`, 나머지는 루트 |
| 2 | 설치와 수명주기, 네임스페이스 | `/plugin` 명령 관리, 완전 되돌림, `플러그인:구성요소` 이름 |
| 3 | 실습 팀 역량 팩 | `team-toolkit` 작성, Git 태그 릴리스, 저장소 권한으로 내부용 유지 |
| 4 | 비공개 마켓플레이스와 조직 관리 | `marketplace.json`, `이름@마켓플레이스`, 통일 배포·버전 고정·감사 |
| 5 | 설계 원칙, 패키징 시점, LSP | 단일 책임·점진 반복·최소 권한·문서화, 범위별 배포 방식, 실시간 진단의 방향 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 플러그인 | 명령, 에이전트, 스킬, 훅, MCP 설정을 담은 Git 저장소 형태의 배포 단위 |
| `plugin.json` | `.claude-plugin/` 안의 매니페스트. 필수는 name, version, description |
| 플러그인 루트 | commands, agents, skills, hooks 폴더와 `.mcp.json`이 놓이는 곳 |
| `name` | 네임스페이스를 정하는 필드. 구체적으로 지어야 한다 |
| `/plugin install` | 마켓플레이스, GitHub, 로컬 디렉터리 세 출처에서 설치 |
| `--plugin-dir` | 로컬 디렉터리를 설치 없이 로드하는 개발용 옵션 |
| `CLAUDE_PLUGIN_ROOT` | 플러그인 자신의 설치 디렉터리를 가리키는 런타임 변수. 저장 위치 설정이 아니다 |
| 네임스페이스 | `plugin-name:component-name` 형태의 전역 고유 이름. 충돌 시에만 필수 |
| 마켓플레이스 | 플러그인 카탈로그 역할을 하는 Git 저장소. `.claude-plugin/marketplace.json` |
| 조직 수준 플러그인 | 관리자가 배포하고 버전을 고정하며 감사하는 기업용 방식 |
| 시맨틱 버전 | major는 깨지는 변경, minor는 구성 요소 추가, patch는 인터페이스 불변 수정 |
| LSP | 에디터의 코드 진단 표준 프로토콜. 플러그인이 Claude에게 실시간 상태를 제공할 수 있다 |

## 3. 자주 놓치는 점

- 모든 파일을 `.claude-plugin/` 안에 넣지 않는다. 매니페스트만 그곳에 둔다. `marketplace.json`도 같은 폴더에 두어야 발견된다.
- `plugin.json`은 사용자 프로젝트의 `.claude/`나 저장소 루트에 두는 것이 아니다.
- 플러그인 저장 위치 `~/.claude/plugins/`는 바꿀 수 없다. `CLAUDE_PLUGIN_ROOT`는 그 위치를 바꾸는 설정이 아니다.
- 마켓플레이스는 먼저 추가해야 설치할 수 있다.
- 내부용 플러그인을 만드는 것은 플러그인 시스템이 아니라 저장소 권한이다. 저장소가 공개이면 내부용이 아니다.
- 단일 프로젝트에 한정된 설정은 굳이 플러그인으로 만들지 않고 `.claude/`를 커밋하는 편이 간단하다.
- 읽기 전용이면 충분한 에이전트에 Write나 Bash를 주지 않는다.
- 첫 릴리스를 "완전한 기능"을 기다리며 미루지 않는다.

## 4. 생각해 볼 질문 (원서 Discussion Questions)

1. 현재 팀에서 Claude Code 관련 설정(스킬, 훅, MCP 등)이 흩어져 있는 곳은 어디인가. 하나의 플러그인으로 합친다면 디렉터리 구조를 어떻게 계획하겠는가.
2. 조직 수준 플러그인과 프로젝트 수준 `.claude/` 설정은 각각 장단점이 있다. 어떤 상황에서 전자를 우선하겠는가. 생각의 실마리는 보안 훅처럼 표준을 강제해야 하는 경우, 버전 고정과 감사가 필요한 경우다.
3. 자기 분야에 맞춘 전용 플러그인을 설계해 본다. 이름은 무엇이고, 어떤 핵심 구성 요소(Commands, Agents, Skills, Hooks, MCP)를 넣을지, 주 사용자 집단은 누구인가.
