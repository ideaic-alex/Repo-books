# 플러그인의 역할과 물리 구조

이 문서는 플러그인(Plugin)이 왜 필요한지, 어떤 폴더 모양을 가지는지, 정체성 파일인 `plugin.json`에 무엇을 적는지, 그리고 구성 요소별 파일 형식을 정리한다. 책의 도입 장면은 이렇다. 샤오쉐가 오픈소스 저장소 "React 풀스택 팀을 위한 Claude Code 모범 사례"를 발견했다. 코드 리뷰, 컴포넌트 문서 생성, 테스트 작성 스킬(Skills)과 자동 포맷팅 훅(Hooks), GitHub와 Linear를 미리 연결한 `.mcp.json`까지 갖춘 알찬 저장소였다.

그러나 스킬은 한 폴더에, 훅 스크립트는 다른 폴더에, `.mcp.json`은 따로, 사용자 정의 명령 파일은 또 다른 곳에 흩어져 있었다. 쓰려면 파일을 일일이 제자리로 복사하고 각 부분의 설치법을 알아내야 했다. 설치 순서를 파악하는 데만 오후가 다 갔고 결국 포기했다. Kage는 "바로 이 문제를 풀려고 플러그인이 있다"고 말한다. JavaScript의 npm, Python의 pip처럼 Claude Code 능력의 표준 배포 수단이라는 것이다.

---

## 1. 플러그인의 역할: 능력의 캡슐화와 배포

지금까지 여섯 가지 확장 장치를 따로 배웠다. CLAUDE.md(프로젝트 기억), 서브에이전트(작업 위임), 스킬(도메인 워크플로 캡슐화), 훅(이벤트 기반 제어), MCP(외부 서비스 연결), 헤드리스 모드와 Agent SDK(프로그램 호출)다. 각각 쓸모가 있지만 서로 따로 놀고 통째로 배포하기 어렵다는 공통 약점이 있다.

몇 주 걸려 다듬은 팀의 개발 워크플로를 다른 팀에 주려 하면 현실은 이렇다.

- 스킬은 `.claude/skills/`에 복사한다.
- 훅 설정은 `settings.json`에 합쳐 넣는다.
- MCP 서버는 따로 설정한다.
- 사용자 정의 명령은 `.claude/commands/`로 옮긴다.
- 서브에이전트 정의는 또 다른 곳에 둔다.

받는 쪽은 구성 요소마다 설치법을 파악하고 이름 충돌까지 처리해야 한다. 지식 공유가 아니라 지루한 이삿짐 작업이 된다.

플러그인은 새 기능을 만들지 않는다. 통일된 포장 형식과 설치 방법을 줄 뿐이다. 스킬, 훅, 명령(Commands), 에이전트(Agents), MCP 설정을 한 꾸러미에 담고 명령 한 줄로 모든 구성 요소를 제자리에 놓는다.

```
/plugin install team-toolkit@our-company
```

### 1-1. 담을 수 있는 구성 요소

| 구성 요소 | 기능 | 해당 장 |
|---|---|---|
| Commands | 사용자 정의 슬래시 명령 | 3장 |
| Agents | 미리 설정한 서브에이전트 | 3장 |
| Skills | 도메인 지식 꾸러미 | 4장 |
| Hooks | 자동화된 동작 | 5장 |
| MCP server | 외부 도구 연동 | 6장 |

앞에서 따로 배운 확장 능력이 모두 플러그인의 구성 요소로 묶여 함께 배포된다.

## 2. 플러그인의 물리 구조

플러그인은 본질적으로 정해진 디렉터리 구조를 따르는 폴더이며, 보통 Git 저장소로 호스팅한다. 핵심은 `.claude-plugin/` 하위에 있는 `plugin.json` 매니페스트(manifest, 꾸러미의 신상 명세 파일)다. 원서의 `react-workflow` 예시는 다음과 같다.

```
react-workflow/
├── .claude-plugin/plugin.json   ← 필수
├── commands/    (review.md, deploy.md)
├── agents/      (security-scanner.md, quick-fix.md)
├── skills/react-patterns/  (SKILL.md, chapters/hooks.md, performance.md)
├── hooks/       (hooks.json, check-bash.sh, auto-format.sh)
├── .mcp.json
└── README.md
```

### 2-1. 꼭 지킬 물리 제약

`plugin.json`만 `.claude-plugin/` 안에 둔다. 나머지 기능 폴더(commands, agents, skills, hooks)와 설정 파일(`.mcp.json`)은 모두 플러그인 루트에 바로 둔다. 흔한 실수는 모든 것을 `.claude-plugin/` 안에 넣는 것이다.

이 구조의 이점은 플러그인 루트 폴더 자체가 유효한 Claude Code 프로젝트 디렉터리라는 점이다. 개발자는 특별한 개발 모드로 바꿀 필요 없이 그 폴더에서 바로 개발하고 테스트할 수 있다.

## 3. plugin.json: 플러그인의 신분증

`plugin.json`은 플러그인 자체 저장소의 `.claude-plugin/`에 둔다. 사용자 프로젝트의 `.claude/`에도, 저장소 루트에도 두지 않는다.

```json
{ "name": "react-workflow", "version": "1.2.0",
  "description": "Complete React/TypeScript development workflow for Claude Code",
  "author": "YourName", "repository": "https://github.com/yourname/react-workflow",
  "license": "MIT", "keywords": ["react", "typescript", "workflow", "code-review"] }
```

원서 코드는 `description` 값이 줄바꿈된 채 인쇄되어 있어 한 줄로 이어 복원했다.

| 필드 | 필수 | 설명 |
|---|---|---|
| `name` | 예 | 플러그인의 고유 식별자. 설치 명령과 내부 참조에 쓴다 |
| `version` | 예 | 시맨틱 버전(SemVer) |
| `description` | 예 | 플러그인 목록에 표시되는 짧은 설명 |
| `author` | 아니오 | 작성자나 팀 이름 |
| `repository` | 아니오 | 소스 저장소 주소 |
| `license` | 아니오 | 오픈소스 라이선스 |
| `keywords` | 아니오 | 검색용 키워드 |

### 3-1. name은 이름표가 아니라 네임스페이스

`name`은 표시 이름이 아니라 네임스페이스를 결정한다. 플러그인이 내놓는 모든 명령, 에이전트, 스킬 앞에 이 이름이 붙어 충돌을 막는다. 그래서 구체적으로 지어야 한다. `tools`처럼 흔한 이름은 마켓플레이스 항목이 몇 개만 넘어도 아무것도 구분하지 못한다. 팀이 통째로 설치하는 넓은 내부 도구 모음에는 쓸 수 있지만, 그때도 팀 접두어를 붙이는 편이 읽기 좋다.

## 4. 구성 요소별 파일 형식

### 4-1. 명령 파일 (commands/)

마크다운 형식이며 규칙은 세 가지다.

- 파일 이름이 명령 이름이다. `review.md`는 `/review` 명령이 된다.
- 파일 맨 위에 YAML 형식의 프런트매터(front matter, 파일 머리의 메타데이터)로 `name`, `description`을 적는다.
- 본문이 AI에게 보내는 실제 지시다.

원서의 `review.md` 예는 사용자가 `/review [target]`을 실행하면 코드 리뷰 절차를 따르게 한다. 검토 초점은 코드 품질(네이밍, DRY 원칙), 보안 문제(입력 검증 누락, SQL 인젝션과 XSS 같은 주입 위험), 성능 문제(불필요한 반복, 메모리 누수, 비효율 알고리즘)다. 출력은 Critical(즉시 수정), Warning(수정 권장 잠재 위험), Suggestion(선택적 개선)의 세 단계로 분류하도록 지시한다.

### 4-2. 서브에이전트 파일 (agents/)

역시 마크다운이지만 프런트매터가 더 강력해서 에이전트의 도구 권한과 기반 모델을 정밀하게 제어한다. 예: `security-scanner.md`의 프런트매터는 `name: security-scanner`, `description`, `tools: Read, Grep, Glob`, `model: sonnet`이다. 본문은 에이전트의 역할을 서술한다. 숙련된 보안 전문가로서 주입 공격, 크로스 사이트 스크립팅(XSS), 자격 증명 유출(하드코딩된 API 키, 비밀번호, 개인 키), 접근 제어를 점검하라는 내용이다.

### 4-3. 훅 설정 파일 (hooks/hooks.json)

플러그인이 특정 수명주기 이벤트에서 할 자동 동작을 정의한다. 형식은 5장의 전역 `settings.json` 훅 설정과 완전히 호환된다고 원서가 설명한다. 예시는 PreToolUse에서 Bash에 `check-bash.sh`를, PostToolUse에서 Write에 `auto-format.sh`를 걸고 있다.

```json
{"hooks": [
  {"event": "PreToolUse",  "matcher": "Bash",  "command": ["bash", "./hooks/check-bash.sh"]},
  {"event": "PostToolUse", "matcher": "Write", "command": ["bash", "./hooks/auto-format.sh"]}]}
```

참고(노트 작성자): 원서가 "5장 설정과 완전 호환"이라고 하지만 이 예시의 키 구성(`event`, `command` 배열)은 이 노트가 확인한 5장의 형식과 같은지 다시 대조하지 않았다. 실제 적용 때는 사용 중인 Claude Code 버전의 훅 스키마를 확인해야 한다.

### 4-4. MCP 설정 파일 (.mcp.json)

플러그인 루트에 `.mcp.json`이라는 이름으로 두며, 프로젝트 수준 MCP 설정과 형식이 똑같다. 플러그인이 필요로 하는 외부 서비스 연결을 선언한다. 원서 예시는 `mcpServers` 아래에 `postgres` 서버를 두고 `command: npx`, `args: ["-y", "@anthropic/mcp-server-postgres"]`로 띄우며, 접속 정보는 `env`의 `DATABASE_URL: "${DATABASE_URL}"`처럼 환경 변수로 받는다. 비밀 값을 파일에 적지 않고 환경 변수에서 읽는 방식이다.

---

## 5. 핵심 정리

- 플러그인은 새 기능이 아니라 스킬, 훅, 명령, 에이전트, MCP 설정을 한 번에 설치하게 하는 포장 형식이다.
- 정체성 파일 `plugin.json`만 `.claude-plugin/` 안에 두고, 나머지 폴더와 `.mcp.json`은 루트에 둔다.
- 필수 필드는 `name`, `version`, `description`이다. `name`은 네임스페이스를 정하므로 구체적으로 짓는다.
- 명령과 에이전트는 프런트매터가 있는 마크다운, 훅은 `hooks.json`, MCP는 `.mcp.json`이다.
