# 설계 원칙, 패키징 시점, LSP 지원과 미래

플러그인을 만들 줄 아는 것과 잘 만드는 것은 다르다. 이 문서는 플러그인 설계의 네 가지 원칙(단일 책임, 점진적 반복, 최소 권한, 문서화), 모든 것을 플러그인으로 만들 필요는 없다는 판단 기준인 패키징 시점, 그리고 플러그인의 미래로 제시되는 LSP(Language Server Protocol) 지원과 생태계 전망을 다룬다.

---

## 1. 플러그인 설계 원칙

### 1-1. 단일 책임

플러그인 하나는 특정 종류의 문제에 집중한다. 이것저것 다 담은 비대한 "만능 도구 상자"를 피한다. 기능이 좁을수록 유지 비용이 줄고 사용 경험이 좋아진다.

- 권장: `react-workflow`(React 개발 워크플로 최적화), `security-scanner`(코드 보안 스캔), `db-tools`(데이터베이스 작업 보조)
- 나쁜 예: `everything-plugin`. 모든 걸 하려 하지만 깊이가 없고, 정체성이 불분명하고 유지가 어렵다.

### 1-2. 점진적 반복

최소 기능 제품(MVP) 철학을 따른다. 핵심 능력으로 시작해 작게 빠르게 개선한다. 시맨틱 버전으로 관리하되 단계별 의미를 분명히 한다.

| 버전 단계 | 올리는 때 |
|---|---|
| major | 명령의 인터페이스나 훅의 계약이 깨지는 변경 |
| minor | 구성 요소가 추가될 때 |
| patch | 인터페이스를 바꾸지 않는 수정 |

원서가 드는 진행 예는 다음과 같다.

| 버전 | 내용 |
|---|---|
| v1.0.0 | 핵심 기능 출시(예: 효율적인 코드 리뷰 명령 하나) |
| v1.1.0 | 하위 능력 확장(예: 보안 스캔 서브에이전트 통합) |
| v1.2.0 | 도메인 전문성 강화(예: React 모범 사례 가이드 추가) |
| v2.0.0 | 자동화 심화(예: MCP 연동과 자동화 훅 워크플로 도입) |

"완전한 기능"을 기다리며 첫 출시를 미루지 않는다. 효율적인 명령 하나뿐인 플러그인이 반쯤 끝난 기능 열 개를 가진 비대한 플러그인보다 훨씬 낫다. 쓸 만한 버전을 일찍 내고 사용자 피드백으로 다음 반복을 이끈다.

### 1-3. 최소 권한

서브에이전트는 핵심 작업에 꼭 필요한 권한만 요청해야 한다. 코드 리뷰와 분석만 맡는 서브에이전트라면 권한을 읽기 전용(Read, Grep, Glob)으로 엄격히 제한한다. 이런 에이전트에 파일 쓰기(Write)나 시스템 명령 실행(Bash) 권한을 주는 것은 엄격히 금지다. 권한 범위가 지나치면 사용자의 신뢰 비용이 크게 올라간다. 사용자는 고권한 플러그인을 설치하기 전에 개발자를 충분히 믿어야 하므로 설치 전환율이 직접 떨어진다.

### 1-4. 문서화는 필수

문서가 없는 플러그인은 채택되지 않는다. README는 팀원이 설치할지 결정하는 곳이다. 소스를 읽지 않고도 세 가지에 답해야 한다. 구성 요소가 각각 무엇을 하는지, 어떻게 호출하는지, 설치될 프로젝트에 대해 무엇을 가정하는지다. 이를 위해 다음 네 요소를 둔다.

| 요소 | 내용 |
|---|---|
| 빠른 설치 | 한 줄 설치 명령으로 진입 장벽을 낮춘다 |
| 기능 목록 | 모든 Commands, 서브에이전트, Skills를 짧은 설명과 함께 나열 |
| 설정 안내 | 필요한 환경 변수(특히 MCP 서버 연결 설정)를 자세히 설명해 누락 때문에 막히지 않게 한다 |
| 변경 이력 | 버전별 변경, 신기능, 버그 수정을 기록해 업그레이드 영향을 가늠하게 한다 |

## 2. 언제 플러그인으로 패키징할까

모든 스킬이나 훅을 플러그인으로 만들 필요는 없다. 배포 방식을 고르는 핵심 기준은 대상 사용자의 범위다(원서 표 9.3).

| 배포 범위 | 권장 방식 | 핵심 장점 |
|---|---|---|
| 단일 프로젝트 | 프로젝트 수준 설정(`.claude/`) | 코드와 같은 자리: 설정이 코드와 함께 버전 관리되고 변경이 추적된다 |
| 개인의 여러 프로젝트 | 사용자 수준 설정(`~/.claude/`) | 개인화: 개인 취향에 맞고 다른 팀원에게 영향이 없다 |
| 팀·조직 간 | 공개/비공개 플러그인 | 표준화: 한 번에 설치, 프로젝트 간 재사용이 쉽다 |
| 전사 롤아웃 | 조직 수준 플러그인 | 강제 관리: 관리자가 중앙 배포, 직원의 수동 작업이 필요 없다 |

현재 프로젝트의 팀원만 대상이라면 가장 간단한 해법은 스킬과 훅 설정 파일을 프로젝트의 `.claude/`에 직접 두고 Git에 커밋하는 것이다. 저장소를 복제하는 순간 설정이 자동으로 따라와 "마찰 없는" 온보딩이 된다. 더 중요한 이점은 설정이 코드와 같은 자리에 있어 수정 과정이 자연히 코드 리뷰 흐름에 들어가고 이력이 분명히 남는다는 것이다.

요구가 단일 프로젝트를 넘으면 플러그인이 맞는 수단이다. 조직 내 다른 팀과 공유하거나, 오픈소스 커뮤니티에 공개하거나, 전사 표준 도구 체인으로 보급하는 경우다.

## 3. LSP 지원과 미래

### 3-1. Kage의 한마디

플러그인의 가치는 효용에 사용자 수를 곱한 값이다. 개인만 쓰는 스킬은 개인 효율만 높이지만, 플러그인으로 포장해 20명 팀에 보급하면 같은 개발 노력이 만드는 가치가 스무 배가 된다. 플러그인은 지식을 재사용 가능한 자산으로 바꾸는 핵심 단계이며, 개인이 쌓은 모범 사례를 조직 전체를 돕는 자산으로 만든다.

### 3-2. LSP란

스킬, 훅, MCP 외에 플러그인은 더 고급 확장 유형인 LSP(Language Server Protocol, 언어 서버 프로토콜)도 지원한다. LSP는 VS Code 같은 현대 에디터가 문법 검사, 코드 자동 완성, 정의로 이동 같은 기능을 구현하는 표준 프로토콜이다. 플러그인에 LSP 지원이 들어가면 Claude에게 실시간 코드 진단 능력을 줄 수 있다.

예를 들어 TypeScript 플러그인이라면, 사용자가 Claude와 코드를 쓰는 동안 플러그인이 TypeScript 컴파일러를 불러 실시간 타입 오류 정보를 Claude의 컨텍스트에 직접 넣어 줄 수 있다. 그러면 Claude는 코드를 생성하면서 잠재적 타입 오류를 알아채고 바로 고친다.

이 변화는 플러그인 능력의 차원을 "Claude에게 어떻게 행동할지 알려 주는 것"에서 "Claude가 코드의 실시간 상태를 감지하게 하는 것"으로 끌어올린다. 원서는 LSP 통합이 아직 초기 단계라고 밝히면서도, 플러그인이 지식을 담는 그릇일 뿐 아니라 Claude가 코드 세계를 감지하는 감각 확장이라는 방향은 이미 분명하다고 말한다.

### 3-3. 생태계 전망

거시적으로 플러그인 생태계는 npm과 비슷한 분산 배포 네트워크를 만들어 가고 있다. 원서가 드는 그림은 세 층이다.

- 커뮤니티 마켓플레이스(예: claude-plugins.dev)에는 이미 수천 개의 공개 플러그인이 모여 있다.
- 기업은 비공개 마켓플레이스로 사내 도구 체인을 조율한다.
- 개인 개발자는 GitHub 저장소로 모범 사례를 공유한다.

이 생태계의 성숙도가 Claude Code가 "효율적인 도구"에서 "번성하는 플랫폼"으로 진화할지를 직접 결정한다고 원서는 본다. 참고(노트 작성자): 마켓플레이스의 공개 플러그인 수 등은 책 집필 시점의 서술이므로 현재 값은 다를 수 있다.

---

## 4. 핵심 정리

- 설계 원칙은 단일 책임, 점진적 반복(SemVer 의미 구분), 최소 권한, 문서화(설치, 기능, 설정, 변경 이력)다.
- 단일 프로젝트는 `.claude/`를 Git에 커밋, 개인 공통은 `~/.claude/`, 팀·조직 간은 플러그인, 전사는 조직 수준 플러그인이다.
- LSP 지원은 플러그인이 Claude에게 코드의 실시간 상태를 보여 주는 방향이며 아직 초기 단계다.
- 플러그인은 개인의 노하우를 조직의 재사용 자산으로 바꾸는 핵심 단계다.
