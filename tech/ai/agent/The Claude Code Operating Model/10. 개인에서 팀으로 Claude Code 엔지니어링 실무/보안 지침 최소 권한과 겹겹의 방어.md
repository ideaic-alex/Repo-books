# 보안 지침 최소 권한과 겹겹의 방어

"Claude Code는 강력하지만 위험한 작업도 실행할 수 있다. 어떻게 효과적으로 제약하고 무단 행동을 막나?" 샤오빙의 질문에 원서의 답은 만능 영구 해법은 없고 엄격한 엔지니어링 규율만이 돕는다는 것이다. 보안은 단순한 스위치가 아니라 층층이 쌓은 심층 방어 체계다. 바닥에 놓는 원칙은 최소 권한(필요한 만큼만 권한을 주는 원칙)이다.

이 문서는 권한 모드, 도구 권한 규칙, `.claudeignore`와 파일 접근 통제, 훅 보안 스캔, MCP 서버 신뢰 평가, API 키 수명주기 관리를 다룬다.

---

## 1. 권한 모드: 첫 번째 방어선

Claude Code에는 다섯 가지 권한 모드가 있다(원서 표 10.3).

| 모드 | 동작 | 적합한 상황 | 제한 수준 |
|---|---|---|---|
| `plan` | 읽기 전용. 파일 수정과 명령 실행 금지 | 코드 리뷰, 아키텍처 분석 | 매우 엄격 |
| `default` | 각 도구를 처음 쓸 때 승인을 요청(기본값) | 일상 개발 | 엄격 |
| `acceptEdits` | 파일 편집 요청은 자동 수락, 나머지는 확인 요구 | 코딩 단계 집중 | 비교적 엄격 |
| `dontAsk` | 미리 승인된 작업만 실행 | 제한된 환경 | 느슨 |
| `bypassPermissions` | 모든 권한 프롬프트 생략 | 컨테이너나 가상 머신 환경에서만 | 매우 느슨 |

참고(노트 작성자): 8장은 SDK 권한 모드를 네 가지(default, acceptEdits, plan, bypassPermissions)로 소개했고 이 장은 `dontAsk`를 더한 다섯 가지다. 원서 표에서 `acceptEdits`의 제한 수준 칸은 "Relativ / ely / strict"로 쪼개져 인쇄되어 "비교적 엄격"으로 복원했다.

CI/CD 파이프라인, 예약 작업, 헤드리스 호출 같은 모든 자동화 환경에서는 권한 모드를 반드시 명시한다. CI/CD에서 `bypassPermissions`를 쓴다면 실행 환경이 완전히 격리된 컨테이너나 가상 머신이어야 한다. 개발자의 로컬 머신에서는 절대 켜지 않는다. 통제 불가능한 보안 위험을 피하기 위해서다.

## 2. 도구 권한: 세밀한 통제

`--allowedTools`와 `--disallowedTools`는 패턴 매칭을 지원해 도구 단위의 세밀한 통제를 한다. 원서의 두 장면은 다음과 같다.

- CI/CD 코드 리뷰(읽기 전용): `claude -p "Review PR changes" --allowedTools "Read" "Grep" "Glob" --max-turns 5`
- 특정 Bash 패턴만 허용: `--allowedTools "Read" "Grep" "Bash(npm run test *)" "Bash(npm run lint)"`

팀이 공유하는 `.claude/settings.json`에서는 `permissions` 아래에 `deny`, `allow`, `ask` 세 단계 규칙으로 통제한다.

| 규칙 | 원서 예시 |
|---|---|
| `allow` | `Bash(npm run lint)`, `Bash(npm run test *)`, `Bash(git commit *)` |
| `deny` | `Bash(curl *)`, `Bash(wget *)`, `Read(./.env)`, `Read(./.env.*)`, `Read(./secrets/**)`, `Bash(git push --force *)` |
| `ask` | `Bash(git push *)` |

평가 순서는 deny, ask, allow다. deny가 가장 우선이라서 어떤 작업이 allow 규칙에 맞더라도 deny 규칙에도 맞으면 곧바로 거부된다. "보안 우선"이라는 핵심 설계 철학이다.

## 3. .claudeignore와 파일 접근 통제

`.claudeignore`는 Claude가 특정 파일을 색인하지 못하게 하지만 알려진 한계가 있다. 일부 상황에서 우회될 수 있다. 그래서 더 믿을 만한 전략은 `permissions.deny`에서 민감 파일의 읽기를 명시적으로 금지하는 것이다. 권장 구성은 `Read(./.env)`, `Read(./.env.*)`, `Read(./secrets/**)`, `Read(**/*.pem)`, `Read(**/*.key)`다.

두 장치는 함께 써서 이중 보호를 만든다. `.claudeignore`는 불필요한 파일 색인 부담을 줄이는 첫 번째 최적화 층이고, `permissions.deny`는 색인이 우회되더라도 민감 파일이 읽히지 않게 하는 두 번째 단단한 방어선이다.

## 4. 훅 보안 스캔

5장에서 본 PreToolUse 훅은 도구가 실제로 실행되기 전에 위험한 작업을 가로채 동적 보안 장벽을 더한다. 원서의 `.claude/hooks/security-check.sh`는 표준 입력 JSON에서 `tool_name`과 `tool_input`을 꺼내고, 도구가 Bash이면 `command`를 정규식으로 검사한다. 걸리는 고위험 패턴은 `rm -rf /` 계열, `sudo rm`, `chmod 777`, `curl ... | bash`다. 걸리면 표준 오류에 `{"decision": "block", "reason": ...}`를 쓰고 `exit 2`로 막는다. 통과하면 `exit 0`이다.

```bash
if [ "$TOOL" = "Bash" ]; then
    COMMAND=$(echo "$TOOL_INPUT" | jq -r '.command')
    if echo "$COMMAND" | grep -qE 'rm\s+-rf\s+/|sudo\s+rm|chmod\s+777|curl.*\|\s*bash'; then
        echo '{"decision": "block", "reason": "Dangerous command blocked by security policy"}' >&2
        exit 2
    fi
fi
exit 0
```

원서의 정규식은 쪽 경계 근처에서 줄바꿈되어 있어 한 줄로 이어 복원했다. 규칙 기반 스크립트 외에 프롬프트형 훅(`type: "prompt"`로 설정)도 있다. 대규모 언어 모델을 불러 현재 도구 호출의 맥락과 의도를 평가하며, 단순 정규식이 덮지 못하는 복잡한 보안 위협이나 논리적 취약점을 식별할 수 있다.

## 5. MCP 서버 신뢰 평가

MCP 서버는 Claude가 외부 시스템과 상호작용하는 대리인이다. 악의가 있거나 취약점이 있으면 공격자가 Claude의 도구 호출 능력을 내부망 자원에 대한 무단 접근으로 키울 수 있다. 그래서 MCP 서버를 도입할 때는 엄격한 점검 목록을 강제한다.

| 점검 항목 | 확인할 것 |
|---|---|
| 출처의 신뢰성 | 공식이거나 평판 있는 개발자에게서 왔는가 |
| 코드의 투명성 | 오픈소스라서 감사할 수 있는가 |
| 권한의 합리성 | 요청하는 권한 범위가 최소 권한 원칙에 맞는가 |

자주 간과되는 위험이 있다. MCP 서버가 한 번 승인되면 이후 업데이트에는 시스템이 사용자 동의를 다시 구하지 않는다. 처음에는 안전했던 서버가 자동 업데이트 중에 악성 코드를 심을 수 있다는 뜻이다. 버전 고정이 필수 방어책이다. 검증된 특정 버전을 강제로 쓰게 해서 신뢰할 수 없는 버전으로의 자동 업그레이드를 막는다.

CI/CD 같은 자동화 환경에서는 항상 `--strict-mcp-config`를 준다. 명령줄에서 지정한 MCP 설정만 로드하고 다른 출처는 모두 무시하게 해서, 개발자 로컬 서버가 파이프라인에 섞일 가능성을 없앤다. 설정은 인라인 플래그로 조립하지 말고 체크인된 파일(CI 작업이 명시적으로 참조하는 프로젝트 `.mcp.json`)에 두어, 파이프라인이 쓰는 도구 범위를 코드와 같은 풀 리퀘스트에서 검토할 수 있게 한다.

## 6. API 키 수명주기 관리

Claude Code가 개발 워크플로에 깊이 들어올수록 프로젝트에서 `ANTHROPIC_API_KEY`를 참조하는 곳이 늘어난다. 키 수명주기 관리 원칙은 세 가지다.

- 격리: 프로젝트와 환경(개발, 테스트, 운영)마다 별도 키를 둔다. "하나의 키로 전부" 방식을 피한다.
- 정기 교체: 일정을 정해 주기적으로 갱신해 장기 유출 위험을 줄인다.
- 비상 대응: 키 유출이 의심되거나 확인되면 즉시 폐기하고 재발급할 수 있는 신속 대응 체계를 갖춘다.

어떤 단일 조치로도 충분하지 않으므로 네 겹의 보호를 동시에 구현한다.

| 층 | 내용 |
|---|---|
| 저장 격리 | 키는 `.env` 파일에만 보관 |
| 버전 관리 제외 | `.gitignore`에 `.env`를 명시적으로 제외 |
| 런타임 차단 | `.claude/settings.json`의 `permissions.deny`로 Claude가 `.env` 등을 못 읽게 명시 |
| 커밋 전 차단 | PreToolUse 훅으로 커밋이나 관련 명령 실행 전 스캔해 키를 실수로 커밋하려는 시도를 감지하고 차단 |

비밀 값은 이 노트 어디에도 실제 값을 적지 않고 `<API_KEY>` 같은 자리표시자로만 쓴다.

## 7. 핵심 정리

- 권한 모드 다섯 가지(plan, default, acceptEdits, dontAsk, bypassPermissions)를 자동화 환경에서는 반드시 명시하고, bypass는 격리된 컨테이너나 VM에서만 쓴다.
- 규칙 평가는 deny, ask, allow 순이며 deny가 이긴다.
- `.claudeignore`는 우회될 수 있으니 `permissions.deny`와 함께 이중으로 건다.
- PreToolUse 훅은 정규식으로, 프롬프트형 훅은 LLM 판단으로 위험을 거른다.
- MCP 서버는 출처, 투명성, 권한을 점검하고 버전을 고정하며, CI에서는 `--strict-mcp-config`를 쓴다.
- API 키는 격리, 정기 교체, 비상 대응 원칙에 저장 격리, git 제외, 런타임 차단, 커밋 전 차단 네 겹으로 지킨다.
