# 요약과 핵심 개념

10장은 책 전체의 마무리로, 도구 기능이 아니라 엔지니어링 실무를 다룬다. 비용, 디버깅, 보안, 규모(대규모 코드베이스), 지침(프롬프트 엔지니어링), 협업(팀 도입)이라는 여섯 낱말에 맞춰 구성되고, 끝에 SDD 생태계와 아홉 가지 메커니즘의 종합이 붙는다. 이 문서는 전체 흐름과 용어를 되짚는다.

원서의 요약은 이렇게 이어진다. 비용 통제는 세 차원이다. 작업 복잡도에 따라 Haiku, Sonnet, Opus를 유연하게 배치하고, 서브에이전트 컨텍스트 격리와 CLAUDE.md 간소화와 캐싱 최적화로 토큰 소비를 줄이고, `--max-budget-usd`로 넘을 수 없는 예산 상한을 둔다. 확장 사고(Extended Thinking) 모드는 간과되기 쉬운 숨은 비용 원천이므로 필요할 때만 켠다. 디버깅의 첫 원칙은 실행 과정을 투명하게 만드는 것이다. `--debug`, `stream-json`, PostToolUse 훅 감사 기록, 세션 파일 보존이 관측 체계를 이루고, 이상 동작의 원인은 컨텍스트 누락, 지침 충돌, 권한 부족 세 범주로 모인다. 보안은 최소 권한 원칙을 지키는 겹겹의 방어다. 다섯 권한 모드, deny/allow/ask 규칙, PreToolUse 훅, 덮어쓸 수 없는 managed settings, MCP 서버의 버전 고정과 엄격한 코드 검토가 그것이다. 대규모 코드베이스는 "전체 읽기"를 "유도된 검색"으로 바꾼다. 팀 도입은 개인 탐색, 프로젝트 통일, 자동화 통합, 조직 확대로 차근차근 나아간다.

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 토큰 비용 | 호출마다 (입력 + 출력 토큰) × 모델 단가. 출력이 더 비싸다 |
| 프롬프트 캐싱 | 접두부가 같으면 일반 입력의 10분의 1 가격으로 재사용 |
| `--max-budget-usd` | 비용 상한 옵션. CI에서는 표준으로 강제 |
| 진짜 비용 | API 비용 + 사람 시간 비용 |
| `--debug` | 컨텍스트, 도구 입출력, 토큰, 시점을 보여 주는 X선. 카테고리 필터 지원 |
| `stream-json` | 사고와 도구 호출을 NDJSON으로 실시간 출력 |
| 세션 jsonl | `~/.claude/projects/{project}/{sessionId}.jsonl`. 사후 분석의 원본 증거 |
| 권한 모드 5종 | plan, default, acceptEdits, dontAsk, bypassPermissions |
| deny → ask → allow | 규칙 평가 순서. deny 우선 |
| `--strict-mcp-config` | 명령줄에 지정한 MCP 설정만 로드. CI에서 필수 |
| 계층형 CLAUDE.md | 상위는 누적 로드, 하위는 온디맨드 로드 |
| `.claude/rules/` | `paths:` 프런트매터로 경로별 규칙 활성화 |
| `/compact` | 보존할 정보를 지시하며 직접 압축. 자동 압축은 약 95%에서 발동 |
| managed settings | IT가 배포하는 덮어쓸 수 없는 조직 정책 |
| 스펙 주도 개발(SDD) | 명세를 먼저 정하고 코드를 쓰는 방법론 |

## 3. 자주 놓치는 점

- 비용 상한이 하드인지 소프트인지 장마다 표현이 다르다. 10장은 `--max-budget-usd`를 하드 리밋, 8장 SDK의 `max_budget_usd`는 턴 사이 검사하는 소프트 한도로 설명한다.
- 모델 가격은 책 시점 스냅샷이다. 최신 값은 공식 가격 페이지로 확인한다.
- CLAUDE.md는 200줄 아래로 유지하고, 자주 바꾸면 캐시가 깨진다.
- `.claudeignore`만 믿지 않는다. 우회될 수 있어 `permissions.deny`를 같이 건다.
- 한 번 승인된 MCP 서버는 업데이트 때 재동의를 구하지 않으므로 버전을 고정한다.
- `bypassPermissions`는 격리된 컨테이너나 VM에서만, 개발자 로컬 머신에서는 쓰지 않는다.
- managed settings는 모든 충돌에서 이기므로 선호 사항을 거기에 넣지 않는다.
- 로드맵은 한 팀씩 진행한다. 한꺼번에 배포하면 좋은 사용 방식을 물어볼 사람이 없다.
- 원서 그림 10.2(CLAUDE.md 6단계 로딩 순서)와 10.3(온보딩 4단계)의 상세 내용은 추출본에 없어 이 노트에 실리지 않았다.

## 4. 생각해 볼 질문 (원서 Reflection Questions)

1. 지금까지 Claude Code를 쓰며 가장 큰 고통(비용 폭주, 일관성 없는 동작, 신뢰성 부족, 기타)은 무엇이었나. 이 장의 실무 중 어떤 메커니즘을 먼저 개선하겠는가. 실마리는 비용은 모델 티어링과 `--max-budget-usd`, 일관성은 CLAUDE.md 거버넌스, 신뢰성은 진단 3분류와 감사 로그다.
2. Claude Code를 처음 쓰는 10명 팀의 "첫 달" 엔지니어링 로드맵을 만든다면 어떤 세 가지를 우선하겠는가. 왜 그 셋이고 다른 것은 아닌가. 실마리는 개인 탐색에서 프로젝트 표준화로 넘어가는 1~2단계다.
3. "진짜 비용 = API 비용 + 시간 비용"의 균형점은 우리 팀에서 어디인가. 어떤 상황에서 더 높은 모델 비용을 치르고 귀한 개발자 시간을 아끼는 것이 가치 있는가.
