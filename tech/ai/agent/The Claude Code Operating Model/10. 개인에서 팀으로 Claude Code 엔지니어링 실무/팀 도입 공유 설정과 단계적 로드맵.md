# 팀 도입 공유 설정과 단계적 로드맵

개인 수준에서는 Claude Code 도입 문턱이 낮다. 효율 향상을 직접 겪으면 엔지니어들은 스스로 계속 쓴다. 그러나 팀 수준에서는 자연 발생에 기댈 수 없다. 팀의 사용 표준, 설정 규격, 워크플로를 통일하려면 능동적인 엔지니어링 설계와 제도화된 관리가 필요하다.

이 문서는 `.claude/` 디렉터리의 공유 전략, CLAUDE.md 거버넌스(통제 체계), 조직 수준 관리 정책(managed settings), 4단계 성숙도 로드맵, 신규 팀원 온보딩 교육 프로그램을 다룬다.

---

## 1. 공유 설정: 팀 통일의 초석

`.claude/` 디렉터리는 팀 협업의 핵심 기반이다. 팀 표준은 통일하되 개인의 유연성은 남기려면 Git 버전 관리에 넣을 파일(공유)과 로컬에만 둘 파일(개인)을 분명히 구분해야 한다(원서 표 10.4).

| 파일 경로 | Git 공유 | 용도 |
|---|---|---|
| `.claude/settings.json` | 예 | 팀 공유 설정: 팀 전체의 모델 매개변수, 도구 권한 등 |
| `.claude/settings.local.json` | 아니오 | 개인 덮어쓰기 설정: 선호 모델 등 개인 습관에 맞춰 일부 설정을 덮어씀 |
| `.claude/agents/*.md` | 예 | 팀 서브에이전트: 코드 리뷰어, 테스트 전문가 같은 팀 공유 전문 역할 |
| `.claude/skills/*.md` | 예 | 팀 스킬 라이브러리: 프로젝트 고유 도메인 지식과 복잡한 조작 안내(온디맨드 로드) |
| `.claude/rules/*.md` | 예 | 모듈형 규칙: 큰 규칙을 모듈로 쪼개 유지와 조합을 쉽게 함 |
| `CLAUDE.md` | 예 | 프로젝트 기억: 핵심 컨텍스트, 아키텍처 개요, 주요 제약 |
| `CLAUDE.local.md` | 아니오 | 개인 선호: 구성원의 개인 프롬프트 선호나 임시 메모 |

Claude Code는 프로젝트 루트 `.gitignore`에 `.claude/settings.local.json`과 `CLAUDE.local.md`를 제외하는 규칙을 자동으로 추가한다. 참고(노트 작성자): 표의 스킬 경로는 원서에 `.claude/skills/*.md`로 적혀 있다. 9장의 플러그인 구조에서는 스킬이 `skills/<이름>/SKILL.md` 형태였으므로 두 표기가 다르다. 원서 표기를 그대로 옮겼으며 실제 배치는 사용 버전의 스킬 문서를 따라야 한다.

## 2. CLAUDE.md 거버넌스

CLAUDE.md는 핵심 코드처럼 다루어 엄격한 코드 리뷰 과정에 넣어야 한다. CLAUDE.md 변경은 반드시 PR로 올리고 합치기 전 최소 한 명의 시니어 엔지니어가 승인해야 한다. 이유는 간단하다. CLAUDE.md의 모든 줄이 팀원 전체가 Claude를 쓸 때의 행동 양식을 직접 결정한다. 팀의 최상위 "AI 행동 표준"으로서 중요성과 영향이 핵심 업무 코드에 못지않으니 같은 수준의 검증을 받아야 한다.

Claude Code의 `ConfigChange` 훅을 쓰면 세션 중 설정 파일(settings 파일 등) 변경을 감시해 자동 감사하거나 무단 수정을 아예 막을 수 있다. 원서 예시는 `hooks.ConfigChange`에 matcher `"*"`, `type: "command"`를 걸어 `echo '[AUDIT] Config changed: $CONFIG_FILE' >> ~/.claude/config-audit.log`로 변경을 기록한다. 이 명령도 지면 때문에 줄이 나뉘어 있어 한 줄로 복원했다.

## 3. 조직 수준 정책 관리

조직 전체를 통제하려면 managed settings(관리 설정)를 쓴다. 개발자가 덮어쓸 수 없는 정책이다. IT가 머신에 배포하는 managed-settings 파일에 두며, 협상 불가 사항, 즉 권한 모드, 금지 도구 목록, MCP 서버를 아예 추가할 수 있는지 여부를 정하는 자리다. 팀이 스스로 정할 수 있어야 하는 사항은 프로젝트 설정에 둔다. managed settings는 모든 충돌에서 이기므로 선호 사항을 거기에 두면 설계상 덮어쓸 수 없게 된다.

원서의 Linux 배포 예시(`/etc/claude-code/managed-settings.json`)는 다음과 같다.

```json
{ "disableBypassPermissionsMode": "disable",
  "allowManagedPermissionRulesOnly": true,
  "allowManagedHooksOnly": true,
  "permissions": { "deny": ["Bash(curl *)", "Bash(wget *)", "Read(./.env)", "Read(./.env.*)"] } }
```

관리 설정은 사용자 로컬 설정, 프로젝트 수준 설정, 심지어 명령줄 매개변수보다 우선한다. `disableBypassPermissionsMode`를 `disable`로 두면 사용자가 로컬에서 `--dangerously-skip-permissions` 플래그를 쓰는 것이 완전히 금지되어 권한 우회 위험이 근본적으로 사라진다. `allowManagedPermissionRulesOnly`를 `true`로 두면 시스템은 조직이 정의한 권한 규칙만 적용하고 다른 출처의 규칙 정의는 무시한다. 원서는 이 구성을 보안팀을 위한 단단한 "방어선"이라고 부른다. 원서 예시의 `allowManagedHooksOnly: true`에 대한 별도 설명은 없으나 이름대로 관리 훅만 허용한다는 취지로 읽힌다(노트 작성자의 해석이다).

## 4. 단계적 역량 구축 로드맵

한꺼번에 모두에게 Claude Code를 배포하면 실패하기 쉽다. 도구와는 무관한 이유로, 이 코드베이스에서 좋은 사용이 무엇인지 아직 아무도 배우지 못해 물어볼 사람이 없기 때문이다. 한 팀씩 가면 다음 팀이 시작하기 전에 그 답이 나온다. 팀은 보통 네 단계의 성숙을 거친다.

| 단계 | 시기 | 전략 목표 | 활동 |
|---|---|---|---|
| 1. 개인 탐색 | 도입 후 첫 2주 | 경험 사례 축적 | 엔지니어가 독립적으로 고가치 활용 장면을 탐색한다. 아직 체계적 규범은 없다. 자유로운 실험을 장려해 진짜 사용자 피드백과 성공 패러다임을 모으고, 혁신적 사고를 억누를 조기 표준화를 피한다 |
| 2. 프로젝트 수준 표준화 | 첫 달 | 자산 공유화 | 검증된 모범 사례(CLAUDE.md 규칙, 자주 쓰는 스킬, 기본 훅)를 프로젝트 `.claude/`에 모아 Git 버전 관리 아래 둔다. 흩어진 "사적 경험"을 "팀 공유 자산"으로 바꾼다 |
| 3. 자동화 통합 | 둘째 달 | 프로세스 자동화 | 훅과 헤드리스 모드로 코드 리뷰, 테스트 실행, 포맷 검사 같은 품질 게이트를 CI/CD에 깊이 통합한다. Claude Code가 "사람을 돕는 도구"에서 "개발 워크플로의 자동화 구성 요소"로 진화한다 |
| 4. 조직 수준 확대 | 셋째 달 | 전사 확장 | 통일된 플러그인 배포, 조직 수준 MCP 서버 배치, 관리 정책 시행으로 성숙한 능력을 여러 팀, 나아가 전체 엔지니어링 조직에 확산한다. 팀 사일로를 허물고 기술 스택, 보안 정책, 협업 표준을 그룹 차원에서 통일한다 |

각 단계는 앞서 다룬 도구와 맞물린다. 2단계는 `.claude/` 공유와 CLAUDE.md 거버넌스, 3단계는 8장 이전의 훅과 헤드리스 모드, 4단계는 9장의 플러그인과 이 문서의 managed settings다.

## 5. Claude Code 온보딩 교육 프로그램

첫 팀이 돌아가기 시작하면 다음 병목은 나머지 모두의 온보딩이다. 원서 그림 10.3은 이미 Claude Code를 쓰는 팀에 합류한 신규 팀원이 경험이 없는 상태에서 한 달 안에 팀 워크플로에 기여하고 개선하는 수준까지 가는 구조화된 프로그램을 네 개의 점진적 단계로 제시한다. 참고(노트 작성자): 이 그림의 내용은 추출본에 텍스트로 들어 있지 않아 각 단계의 구체적 제목과 활동은 옮기지 못했다. 원서 PDF의 그림 10.3을 직접 확인해야 한다.

## 6. 핵심 정리

- `.claude/settings.json`, agents, skills, rules, `CLAUDE.md`는 Git으로 공유하고, `settings.local.json`과 `CLAUDE.local.md`는 개인용으로 제외한다.
- CLAUDE.md는 핵심 코드처럼 PR과 시니어 승인으로 관리하고, `ConfigChange` 훅으로 설정 변경을 감사한다.
- managed settings는 사용자, 프로젝트, 명령줄보다 우선하는 조직 정책이며 권한 모드, 금지 도구, bypass 차단을 강제하는 자리다.
- 로드맵은 개인 탐색(2주), 프로젝트 표준화(1개월), 자동화 통합(2개월), 조직 확대(3개월)다. 한 팀씩 진행해 답을 먼저 얻는다.
- 온보딩은 신규 팀원을 한 달 안에 기여자로 만드는 4단계 프로그램이다.
