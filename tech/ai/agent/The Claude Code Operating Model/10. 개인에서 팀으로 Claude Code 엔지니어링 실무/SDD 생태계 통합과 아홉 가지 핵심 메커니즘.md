# SDD 생태계 통합과 아홉 가지 핵심 메커니즘

앞에서 본 독립 메커니즘들을 어떻게 이어 하나의 완전한 워크플로로 만들까. 오픈소스 커뮤니티는 지금 워크플로 층에서 폭발적으로 성장하고 있다. GitHub에는 Claude Code 기반 플러그인과 프레임워크가 쏟아지고, 모두 같은 질문에 답하려 한다. AI 시대의 소프트웨어 공학 방법론은 어떤 모습이어야 하는가. 접근은 달라도 답은 스펙 주도 개발(SDD, Specification-Driven Development, 명세를 먼저 정하고 코드를 쓰는 개발 방식)로 모인다.

이 문서는 SDD 생태계의 4계층 구조, 워크플로 도구 조합 추천, 그리고 책 전체의 아홉 가지 메커니즘을 한 장으로 묶는 종합 정리와 책의 결론을 다룬다.

---

## 1. SDD 생태계의 4계층 구조

이 도구들은 자연스럽게 네 층으로 나뉘고, 층마다 핵심 문제 하나를 푼다.

| 계층 | 해결하는 문제 | 대표 도구와 특징 |
|---|---|---|
| 1. 원자적 스킬 | 작은 마크다운으로 AI 행동 패턴 바꾸기 | Matt Pocock의 `grill-me`. 마크다운 여섯 줄뿐이지만 Claude를 "순종하는 실행자"에서 "집요한 면접관"으로 바꾼다. 사용자가 해결되지 않은 모든 쟁점과 암묵적 가정을 따져 보게 만든다 |
| 2. 컨텍스트 지속 | 긴 작업에서 컨텍스트가 사라지는 문제 | Planning with Files: 계획을 `task_plan.md`, `findings.md`, `progress.md` 같은 파일에 적는다. 대화 컨텍스트가 비워져도 파일을 다시 읽어 진행을 복원한다. Trellis: `.trellis/` 디렉터리 구조로 크로스 플랫폼 표준화를 이뤄 같은 명세를 Claude Code, Cursor, OpenCode 등 10개 이상의 플랫폼에서 쓰게 한다 |
| 3. 명세 생성 프레임워크 | 명세 정의에서 코드 생성까지 완전한 파이프라인 | Spec-Kit(GitHub 공식 프로젝트, 별 7만 개 이상): "헌법(constitution)"에서 코드까지 전 과정을 정의하고 명령 9개가 개발 전 수명주기를 덮는다. 작은 프로젝트에는 무거울 수 있다. OpenSpec(Fission AI): 더 가볍고 핵심 명령 4개로 한 단계 과정. cc-sdd: EARS(Easy Approach to Requirements Syntax) 요구사항 문법을 도입해 극도로 단순한 SDD 워크플로를 이룬다 |
| 4. 완전한 방법론 | 종합 엔지니어링 실천 체계 | Superpowers(집필 시점 별 4만 개 이상, Anthropic 공식 플러그인 마켓플레이스에 등재): 조합 가능한 스킬 14개를 묶고 7개 표준 단계(브레인스토밍, Git Worktree 생성, 계획, 계획 실행, 테스트 주도 개발(TDD), 코드 리뷰, 최종 병합)를 정의한다. TDD 원칙을 강제해 사용자가 테스트보다 코드를 먼저 쓰면 시스템이 코드를 자동으로 삭제한다. 서브에이전트로 작업을 병렬 분배한다. Compound Engineering: 다른 프레임워크가 놓치는 "학습" 차원에 집중한다. 매 반복 뒤 `/ce:compound` 명령으로 경험을 `docs/solutions/`에 쌓고, 비슷한 문제가 나오면 에이전트가 과거 해법을 먼저 찾아 지속적으로 진화한다 |

원서는 `grill-me`를 3장의 스킬 힘을, Superpowers의 서브에이전트 분배를 4장의 서브에이전트 메커니즘을 적용한 사례로 언급한다. 참고(노트 작성자): 9장 표(Table 9.1)는 에이전트와 명령을 3장, 스킬을 4장으로 대응시켜 놓아서 원서 안에서 장 번호 참조가 서로 어긋난다. 어떤 쪽이 맞는지는 확인하지 못했다.

## 2. 추천 워크플로 조합

원서 표 10.5가 드는 세 가지 조합이다.

| 적용 상황 | 추천 조합 | 핵심 흐름 |
|---|---|---|
| 개인 개발자 | grill-me + OpenSpec + Planning with Files | 요구 심문, 명세 생성, 진행 영속화, 구현 검증. grill-me로 요구를 깊이 파고, OpenSpec으로 빠르게 명세를 만들고, 파일 기록으로 긴 작업이 컨텍스트를 잃지 않게 한다 |
| 소규모 팀 협업 | Superpowers + Trellis | 표준화, 전 과정 인수. Trellis는 플랫폼 간 명세 일관성을, Superpowers는 표준화된 개발 프로세스를 강제 |
| 장기 진화 프로젝트 | OpenSpec + Compound Engineering + grill-me | 명세 강제, 지식 복리. 엄격한 표준 위에 Compound Engineering이 과거 해법을 쌓아 팀 역량이 계속 갱신 |

추천하지 않는 조합은 Superpowers + Spec-Kit이다. 둘 다 무거운 프레임워크이고 단계 정의가 충돌해 섞으면 프로세스가 혼란스러워진다. 도구를 모두 통째로 설치한다고 효율이 오르지 않고 오히려 인지 부담이 늘어, 일을 단순하게 하려고 도구를 도입했다는 본래 취지에 어긋난다.

### 2-1. SDD의 핵심은 습관 (Kage's notes)

SDD의 핵심은 어떤 플러그인을 쓰느냐가 아니라 개발에서 "행동 전에 생각하는" 습관을 세우는 데 있다. Claude Code를 띄우기 전 5분만 "목표 범위(할 것과 하지 않을 것)"와 "검증 기준"을 분명히 해도, 플러그인 없이 직관에 따르는 프로그래밍(바이브 코딩 같은 것)의 90%를 넘어선다고 원서는 말한다. 플러그인의 본질은 이 중요한 습관을 자동화하는 데 있을 뿐이다.

## 3. 전체 조망: 아홉 가지 핵심 메커니즘의 오케스트레이션

Claude Code 엔지니어링의 아홉 가지 핵심 메커니즘을 거시 관점에서 한눈에 정리한 표다(원서 표 10.6).

| 메커니즘 | 핵심 가치 | 주요 적용 상황 |
|---|---|---|
| CLAUDE.md | 프로젝트 기억과 컨텍스트 지속 | 모든 상황 공통(항상 설정 권장) |
| 서브에이전트 | 병렬 실행과 컨텍스트 격리 | 복잡한 다단계 작업 분해 |
| 스킬 | 도메인 지식 재사용과 워크플로 표준화 | 빈도 높은 반복 전문 작업 |
| 명령(Commands) | 표준화된 조작 캡슐화 | 팀이 합의한 고정 조작 순서 |
| 훅 | 이벤트 기반 안전 게이트와 자동화 | 품질 보증, 보안 방어 |
| MCP | 외부 데이터 소스와 도구 통합 | 실시간 데이터나 외부 API 호출이 필요한 상황 |
| 헤드리스 모드 | CI/CD 통합, 자동화 파이프라인 구축 | 비대화형 자동화 프로세스 |
| Agent SDK | 맞춤 에이전트 애플리케이션 개발 | 제품화 개발(도구 사용을 넘어) |
| 플러그인 | 능력 포장과 팀 간 배포 | 커뮤니티 공유와 전사 보급 |

어느 하나도 만능이 아니고 어느 하나도 군더더기가 아니다. 이 표를 서술형으로 풀면 구조가 보인다.

- CLAUDE.md는 시스템 전체의 초석으로 Claude의 "작업 맥락"을 정한다.
- 스킬과 서브에이전트는 그 맥락 안에서 능력을 넓히는 두 차원이다. 스킬은 도메인 지식을 깊게, 서브에이전트는 실행 경계를 돌파한다.
- 훅은 실행 중의 품질과 보안 방어선이다.
- MCP는 외부 세계로 가는 다리다.
- 헤드리스 모드와 Agent SDK는 Claude Code를 대화형 도구에서 프로그램 가능한 능력 부품으로 끌어올린다.
- 플러그인은 이 모든 능력을 이전과 재사용이 가능한 지식 자산으로 포장한다.

이 아홉 가지를 필요에 따라 조합해 협력시키면 완전하고 효율적인 AI 보조 개발 엔지니어링 체계가 된다.

## 4. 책의 결론: 도구 사용자에서 엔지니어로

"이걸 다 배우고 나면 Claude Code로 실제로 무엇을 할 수 있나요?" 샤오빙의 질문에 Kage는 이렇게 답한다. Claude Code로 할 수 있는 일은 석 달 전과 본질적으로 다르지 않다. 늘 코드를 읽고, 쓰고, 리뷰하고, 문서를 만들고, 테스트를 돌릴 수 있었다. 진짜로 배운 것은 이 흩어진 능력들을 체계적으로 통합하는 법이다.

도구 사용자는 필요할 때 도구를 부르고 쓰고 나면 버린다. 엔지니어는 도구를 워크플로에 깊이 통합해 적절한 순간에, 올바른 방식으로, 미리 정한 제약 아래 알아서 개입하게 만든다. 후자는 도구 자체에 능숙해야 할 뿐 아니라 프로세스에 대한 깊은 이해, 제약 장치의 세심한 설계, 잠재 실패 양상에 대한 예측에 달려 있다. 이것이 "엔지니어링"의 핵심 본질이다. 강력하지만 본질적으로 불확실한 도구가 질서 있는 체계 안에서 믿을 만하게 가치를 만들게 하는 일이다.

Claude Code의 능력은 계속 진화하고 컨텍스트 창은 계속 커지고 추론 정확도는 계속 오르며 새 도구와 API가 빠르게 나올 것이다. 그러나 엔지니어링 사고는 변하지 않는다. 밑바닥 메커니즘을 이해하고, 적절한 층에서 결정하고, 제약을 신뢰성과 맞바꾸고, 개인의 모범 사례를 팀의 공유 자산으로 바꾸는 것이다. 샤오쉐의 한 줄 정리는 "처음의 구조 개관에서 마지막 엔지니어링 실천까지, 이 여정의 본질은 '도구를 아는 것'에서 '도구를 다루는 것'으로의 전환이다"이다.

## 5. 핵심 정리

- SDD의 답은 명세를 먼저 정하는 것이고, 생태계는 원자적 스킬, 컨텍스트 지속, 명세 생성 프레임워크, 완전한 방법론의 4계층이다.
- 상황별 추천은 개인(grill-me + OpenSpec + Planning with Files), 소규모 팀(Superpowers + Trellis), 장기 프로젝트(OpenSpec + Compound Engineering + grill-me)이며 Superpowers + Spec-Kit은 피한다.
- SDD의 본질은 행동 전에 목표 범위와 검증 기준을 정리하는 습관이고, 도구는 그 자동화다.
- 아홉 메커니즘은 CLAUDE.md를 초석으로 스킬, 서브에이전트, 훅, MCP, 헤드리스·SDK, 플러그인이 각자의 층에서 맞물린다.
- 엔지니어링은 불확실한 도구가 질서 있는 체계 안에서 믿을 만한 가치를 만들게 하는 일이다.
