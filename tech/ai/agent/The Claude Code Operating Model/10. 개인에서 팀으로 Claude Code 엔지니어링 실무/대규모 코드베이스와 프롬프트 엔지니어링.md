# 대규모 코드베이스와 프롬프트 엔지니어링

코드베이스가 커질수록 Claude Code에는 도전이 된다. Claude의 능력이 모자라서가 아니라 컨텍스트 창(한 번에 볼 수 있는 입력의 한도)이 유한하기 때문이다. 또 같은 일을 시켜도 어떤 사람은 한 번에 완벽한 답을 얻고 어떤 사람은 몇 번씩 오간다. 샤오빙의 이 질문에 원서의 답은 Claude의 능력 차이가 아니라 지침의 질이라는 것이다. 훌륭한 지침은 완벽한 요구사항 문서처럼 분명하고, 구체적이며, 모호하지 않다.

이 문서는 컨텍스트 한도의 계산, 계층형 CLAUDE.md와 `.claude/rules/`, 탐색 유도 전략, Explore 서브에이전트, 모듈별 서브에이전트, 컨텍스트 압축, 그리고 CLAUDE.md 작성 원칙과 프롬프트 표현 기법을 다룬다.

---

## 1. 컨텍스트 창은 생각보다 작다

표준 컨텍스트 창은 20만 토큰이지만 그만큼의 코드를 채울 수 있다는 뜻은 아니다. 원서의 계산은 이렇다.

| 항목 | 토큰(약) |
|---|---|
| 시스템 프롬프트 | 5,000 |
| CLAUDE.md 설정 파일 | 2,000 |
| 대화 이력 | 20,000 |
| 도구 정의와 반환 결과 | 10,000 |
| 필요한 안전 여유 | 20,000 |
| 남는 공간(코드용) | 143,000 |

143,000토큰은 코드로 3만 5천~4만 줄에 해당한다. 그런데 중형 전자상거래 백엔드는 5만 줄을 쉽게 넘고, 기업용 SaaS는 20만 줄을 자주 넘는다. 결론은 대형 프로젝트는 코드베이스 전체를 한 번에 컨텍스트에 올릴 수 없으므로 쪼개 다루는 전략이 필요하다는 것이다.

## 2. 계층형 CLAUDE.md와 rules 디렉터리

모노레포(여러 프로젝트를 한 저장소에 둔 구조)에서 계층형 CLAUDE.md 배치는 대형 코드베이스 관리의 핵심 기반이다. Claude Code는 설정 파일을 불러올 때 엄격한 우선순위 순서를 따른다(원서 그림 10.2는 6단계 계층 로딩 순서를 보여 주지만, 추출본에는 그림 내용이 없어 단계의 구체적 항목은 옮기지 못했다).

로딩 규칙은 두 가지다.

- 하위 디렉터리의 CLAUDE.md는 Claude가 그 디렉터리의 파일을 처리할 때만 트리거되어 로드된다(온디맨드 로딩).
- 상위 디렉터리의 CLAUDE.md는 현재 작업 디렉터리에서 위쪽으로 재귀 검색해 각 단계마다 누적해서 로드한다.

덕분에 모노레포 설정 관리가 유연해진다. 루트 CLAUDE.md는 전체 아키텍처와 모듈 간 공통 규약을, 하위 모듈의 CLAUDE.md는 모듈 내부 세부 사항을 맡고, 실행 시 자동으로 합쳐져 전역 일관성과 지역 구체성을 모두 얻는다.

`.claude/rules/` 디렉터리는 경로 필터링 기반의 모듈형 규칙을 지원한다. 규칙 파일 맨 위 프런트매터에 `paths:`로 `"src/api/**/*.ts"` 같은 패턴을 적으면 그 경로의 파일을 다룰 때만 규칙이 켜진다.

```
---
paths:
- "src/api/**/*.ts"
---
# API Development Standards
- All API endpoints must include input validation logic.
```

원서 예시의 나머지 규칙은 오류 응답에 `ErrorResponse` 타입을 일관되게 쓸 것, 인증 미들웨어는 전역 설정이라 엔드포인트마다 import하지 않아도 된다는 것이다. 이 방식으로 규칙이 "필요할 때 활성화"된다. API 관련 파일을 고치면 API 표준이, 프런트엔드 컴포넌트를 다루면 프런트엔드 표준이 자동으로 로드된다.

## 3. 통째로 읽지 말고 검색을 유도하라

대형 코드베이스 관리의 핵심 전략은 "맹목적으로 읽게 하지 말고 검색하도록 유도하는 것"이다. 방향이 없으면 Claude는 관련 파일을 전부 읽으려 해서 비효율적이고 비용도 크게 는다. 그래서 CLAUDE.md에 분명한 탐색 전략을 둔다. 원서의 "코드베이스 탐색 원칙" 예는 다음과 같다.

1. Grep으로 핵심 함수 이름, 클래스 이름, 오류 코드를 검색해 관련 파일을 정확히 찾는다.
2. Glob으로 대상 디렉터리의 파일 구조를 나열해 전체 조직을 빠르게 훑는다.
3. 가장 관련 있는 핵심 파일 2~3개의 구체적 내용만 읽는다.
4. 명확한 목적 없는 대규모 파일 읽기는 엄격히 금지한다.

출력이 많이 나올 작업(로그 분석, 큰 파일 검색)은 서브에이전트에 위임한다. Claude Code에는 코드베이스 탐색 전용 Explore 서브에이전트가 내장되어 있다. 가장 저렴한 Haiku 모델을 쓰고, 읽기 전용 도구 권한을 가지며, quick, medium, very thorough 세 가지 탐색 모드를 제공한다. 모든 검색과 읽기는 서브에이전트의 독립 컨텍스트에서 끝나고 메인 대화는 최종 요약만 받는다. 메인 대화의 귀한 컨텍스트 공간을 지키고 운영 비용도 크게 줄이는 방식이다.

## 4. 서브에이전트로 모듈별 컨텍스트 경계 만들기

3장에서 다룬 서브에이전트의 컨텍스트 격리는 대형 코드베이스에서 더 중요해진다. 큰 작업을 모듈별로 쪼개 서로 다른 서브에이전트에 맡기고, 각자 맡은 모듈의 컨텍스트만 갖게 한다. `.claude/agents/`에서 에이전트별로 전용 도구 집합, 모델 버전, 지속 메모리까지 지정할 수 있다.

원서의 결제 모듈 전용 리뷰어는 프런트매터가 `name: payment-reviewer`, `description`(결제 모듈의 코드 변경 리뷰), `tools: Read, Grep, Glob`, `model: sonnet`, `memory: project`다. 본문 심사 기준은 세 가지다. 금액 계산에는 반드시 `Decimal` 타입을 쓰고 부동소수점은 엄격히 금지한다. 결제 상태 변경은 데이터베이스 트랜잭션 안에서 원자적으로 끝낸다. 외부 결제 게이트웨이를 부를 때는 재시도 메커니즘과 타임아웃 제어를 구현한다.

## 5. 컨텍스트 압축과 세밀한 관리

대화 턴이 늘수록 컨텍스트 창이 한도에 가까워진다. Claude Code에는 자동 압축 기능이 있고 보통 용량이 약 95%에 이르면 발동한다. 정보 보존을 더 정밀하게 통제하려면 `/compact`를 직접 실행하면서 꼭 남길 정보를 지시한다. 원서 예시는 `/compact preserves the full paths of all modified files and the test commands`다.

압축 규칙은 CLAUDE.md에 미리 적어 두어 서브에이전트가 압축 중에도 핵심 상태를 잃지 않게 할 수도 있다. 원서의 "압축 전략" 절은 항상 남길 것으로 수정한 모든 파일의 전체 경로 목록, 실패한 테스트와 구체적 오류 스택 정보, 진행 중인 작업의 남은 단계를 든다.

환경 변수 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`로 자동 압축 시점을 바꾼다. 기본은 약 95%이고 50으로 설정하면 더 일찍 압축된다. 컨텍스트가 거의 바닥났을 때 대량 데이터를 처리하느라 생기는 성능 저하나 응답 지연을 피하는 데 도움이 된다.

## 6. CLAUDE.md 작성 원칙

CLAUDE.md는 Claude Code에서 가장 중요한 설정 파일이다. 이 파일을 다듬으면 일반 코딩 성능이 측정 가능하게 개선된다고 원서는 말한다. 저자들 자체 테스트에서 수 퍼센트 수준이고 일부 저장소에서는 더 컸다는 표현이다.

| 넣을 것 | 피할 것 |
|---|---|
| 핵심 명령: 빌드, 테스트, 배포의 구체적 명령(Claude가 스스로 추론하지 못함) | 추론 가능한 정보: 코드를 읽으면 알 수 있는 내용 |
| 사용자 정의 표준: 기본값과 다른 코드 스타일 규칙 | 일반 규약: 표준 언어 규범(Claude가 이미 알고 있음) |
| 아키텍처 제약: 프로젝트 고유의 설계 결정과 한계 | 변동성 정보: 자주 바뀌는 내용(캐시 무효화 유발) |
| 환경 요구: 필요한 환경 변수, 비표준 도구 체인 | 파일 설명: 파일별 코드 설명(검색 도구가 할 일) |
| 함정 안내: 흔한 함정, 미묘한 시스템 동작 | 모호한 조언: "깨끗한 코드를 써라" 같은 자명한 원칙 |

직관에 어긋나는 원칙은 "적을수록 좋다"다. 간결할수록 효과적이다. 긴 설정 파일은 API 호출마다 전체를 올려야 해서 비용이 늘고, 핵심 규칙이 정보 소음 속에 묻힌다. 상세한 도메인 지식은 온디맨드로 로드되는 스킬(Skills) 쪽으로 옮긴다.

## 7. 정밀한 표현 기법

지침의 핵심은 가장 적은 토큰으로 가장 완전한 정보를 전하는 것이다. 실용 기법은 네 가지다.

| 기법 | 내용과 예 |
|---|---|
| 모두 수량화 | "대량 데이터 처리"는 "100만 건 처리", "응답이 빨라야 함"은 "P99 응답 시간 200ms 미만", "코드는 간결하게"는 "함수는 20줄 이하, 매개변수 4개 이하" |
| 예시 주도 | 복잡한 요구는 예 하나가 설명 열 개보다 낫다. 예: camelCase를 snake_case로 변환. `getUserName`은 `get_user_name`, `HTTPRequest`는 `http_request` |
| 경계 명확화 | "금지 사항"을 정하는 것이 "해야 할 일"만큼 중요하다. 범위 제한(auth 모듈만 수정), 도구 제약(기존 로거 사용, `console.log` 금지), 의존성 관리(새 의존성 추가 엄금), 실패 처리(풀 수 없는 문제는 즉시 보고하고 멈춤, 재시도 반복 금지) |
| 단계별 확인 | 복잡한 작업은 한 번에 제출하기보다 단계적으로. 큰 요구를 독립된 검증 고리로 쪼개 이탈 위험을 줄인다 |

단계별 확인의 원서 예는 세 단계다. 1단계에서는 "버그의 근본 원인을 분석하되 아직 코드는 고치지 마라"고 한다. 분석 논리가 맞는지 확인한 뒤 2단계에서 "위 분석에 따라 필요한 코드만 수정해 고쳐라"고 한다. 수정이 맞는지 확인한 뒤 3단계에서 "이 수정에 대응하는 테스트를 써라"고 한다. 단계마다 독립 검증이 가능해 Claude가 잘못된 방향으로 과하게 실행하는 일을 막는다. 헤드리스 모드에서는 `--max-turns`로 단계별 턴 수를 제한해 폭주를 막을 것을 권한다.

## 8. 핵심 정리

- 20만 토큰 창에서 실제 코드 공간은 약 14.3만 토큰(3.5만~4만 줄)이므로 대형 프로젝트는 쪼개 다룬다.
- 계층형 CLAUDE.md는 상위는 누적, 하위는 온디맨드 로드이고, `.claude/rules/`의 `paths:`로 경로별 규칙을 켠다.
- 읽게 하지 말고 검색하게 한다. Grep, Glob, 핵심 파일 2~3개 읽기, 무거운 일은 Explore나 모듈별 서브에이전트로 격리한다.
- `/compact`와 CLAUDE.md 압축 규칙, `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`로 압축을 통제한다.
- CLAUDE.md는 짧게, 수량화와 예시와 경계 명시와 단계별 확인으로 쓴다.
