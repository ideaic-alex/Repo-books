# 요약과 핵심 개념

이 장의 중심 생각은 하나다. CLAUDE.md와 스킬은 Claude가 "알아서 따르길 바라는" 제안이고, 훅은 도구가 실행되려는 순간 시스템이 "강제하는" 규칙이다. 그래서 훅은 Claude가 더 많은 일을 하게 만드는 장치가 아니라, Claude가 하는 모든 일을 더 믿을 만하게 만드는 실행 기반이다. 이 문서는 장 전체를 한 번에 되짚고 용어와 흔한 오해를 정리한다.

원서의 요약은 이렇게 이어진다. 훅은 CLAUDE.md와 스킬이 비워 둔 틈을 메워 도구 실행 시점에 규칙을 강제한다. 일부는 팀 규약이고 일부(파괴적 명령 차단, 자격 증명 파일 보호)는 혼자 하는 프로젝트에도 해당하는 안전의 문제다. 확장 메커니즘 중 인지 층이 아니라 실행 층에 있는 유일한 구성 요소라 Claude의 이해에 기대지 않는다. 이벤트는 스물네 개 이상이고(최신 목록은 공식 레퍼런스), 처리기 세 종류는 command, prompt, agent 순의 사다리이며, Frontmatter 훅은 전역 설정보다 정밀하고, 비동기 훅은 오래 걸리는 작업의 지연을 해결한다. 방법론은 "먼저 관찰, 그다음 통제"이고 stop_hook_active는 훅이 일으키는 무한 호출을 막으며 종료 코드 2는 "의도적 차단"을 시스템 오류와 구분한다. 다음 장(6장)은 시선을 밖으로 돌려 MCP를 다룬다.

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 훅(Hooks) | 도구 호출 전후 같은 시점에 자동 실행되어 Claude의 행동을 가로채는 스크립트 |
| 정책과 메커니즘 | CLAUDE.md와 스킬은 정책(무엇을 할지), 훅은 어긴 순간 막는 메커니즘 |
| PreToolUse | 도구 실행 전 문지기. allow, deny, ask, defer 결정과 updatedInput 재작성 |
| PostToolUse | 실행 후 피드백과 후처리. 되돌릴 수 없고 additionalContext, updatedToolOutput을 쓴다 |
| Stop | 응답 한 사이클이 끝나는 순간의 품질 관문. decision: "block"으로 종료를 막는다 |
| 차단 가능 이벤트 | 통제용(PreToolUse, Stop 등). 나머지(PostToolUse, Notification, SubagentStart 등)는 관찰용 |
| matcher | 훅을 적용할 도구(또는 서브에이전트 유형)를 정하는 필드. `Bash`, `Write\|Edit`, `*` |
| 종료 코드 2 | 의도적 차단. stderr가 Claude에게 간다. 그 밖의 비정상 코드는 스크립트 오류 알림 |
| command / prompt / agent | 결정성 높음에서 낮음, 유연성 낮음에서 높음의 처리기 사다리. 강등 원칙으로 선택 |
| additionalContext | Claude의 컨텍스트에 주입되는 추가 정보. lint 피드백 순환의 열쇠 |
| continue: false | 이벤트 단계와 무관하게 Claude 처리를 즉시 끝내는 비상 브레이크 |
| stop_hook_active | Stop 훅이 이미 한 번 막았음을 알리는 표식. 무한 루프를 끊는 종료 조건 |
| Frontmatter 훅 | 서브에이전트 정의 파일에 적는 훅. 서브에이전트와 수명주기를 같이한다 |
| async: true | command 훅을 백그라운드로 돌린다. 차단은 못 하고 결과는 다음 턴에 전달 |
| 점진적 퇴화 | 포맷 도구가 없으면 조용히 건너뛰는 식으로, 훅의 예외가 핵심 흐름을 막지 않게 하는 원칙 |

## 3. 자주 놓치는 점

- 훅이 막는 것은 과업이 아니라 개별 도구 호출이다.
- stdout은 JSON 결정 전용이다. 디버그 출력은 stderr로 보내고, 셸 설정 파일의 무조건 echo도 stdout을 오염시킨다.
- 종료 코드 2는 "막음", 다른 코드는 "스크립트 고장"이다. 고장은 흐름을 멈추지 않는다.
- Stop과 SubagentStop 훅에는 stop_hook_active 검사를 넣지 않으면 "수정, 실패, 수정"의 무한 루프에 빠진다.
- 비동기 훅은 막을 수 없으므로 SQL 인젝션 방어 같은 실시간 보안 차단에는 쓰지 않는다. prompt와 agent 유형은 비동기가 안 된다.
- settings.json을 고쳐도 시작 시점 스냅샷 때문에 바로 적용되지 않는다. /hooks 메뉴에서 확인하거나 세션을 다시 시작한다.
- 처음부터 차단하지 말고, 감사 로그로 며칠 관찰한 뒤 위험 패턴에 맞춰 차단 규칙을 만들고 점차 조인다. 로깅은 계속 둔다.
- 팀 저장소의 훅은 모두에게 적용된다. 커밋 전에 합의하고 차단 사유를 분명히 적는다.
- 원서 코드 예시 일부(lint 스크립트의 `|| true`, 보안 스크립트의 따옴표 패턴 비교)는 의도대로 안 움직일 수 있어 그대로 복사해 쓰지 말고 시험해 본다(각 실습 문서의 참고 참조).

## 4. 토론 질문 (원서 Discussion questions)

1. 일상 개발에서 "절대 일어나서는 안 되지만 부주의로 가끔 일어나는 오류" 중 하나를 골라, 트리거 이벤트, 훅 유형, matcher 규칙, 스크립트가 확인할 조건을 포함한 완전한 훅 설계를 해 본다.
2. Stop 훅의 "품질 관문" 방식과 CI/CD 파이프라인의 자동 테스트는 어떤 점이 같고 다른가. 어떤 상황에서 Stop 훅을, 어떤 상황에서 CI/CD를 우선해야 하는가.
3. PreToolUse는 차단이 되고 PostToolUse는 피드백만 가능한 비대칭 설계의 공학적 의미는 무엇인가. PostToolUse에 차단 능력(이미 실행한 조작을 취소하는 능력)을 주면 어떤 문제가 생기는가.
4. 전역 settings.json과 서브에이전트 Frontmatter, 두 설정 방식을 비교해 보자. 내 프로젝트에서 어떤 훅은 전역에, 어떤 훅은 특정 서브에이전트의 Frontmatter에 두는 게 좋은가.
