# 환경 변수, 디버깅, 함정, 설계 방법론

훅을 실제로 굴릴 때 필요한 실무 지식을 모았다. 훅 스크립트가 쓸 수 있는 환경 변수, 디버깅하는 세 가지 방법, 자주 밟는 함정 두 가지, 그리고 요구 사항을 훅 설계로 바꾸는 방법론과 "관찰 먼저, 통제는 나중"이라는 세 단계 전략을 다룬다. 끝에는 훅이 팀 인프라라는 케이지의 당부가 붙는다.

---

## 1. 훅이 쓸 수 있는 환경 변수

원서의 표 5.2는 훅에서 쓸 수 있는 환경 변수를 적용 범위와 핵심 용도로 정리한다. 다만 추출본에서 표의 열이 뒤섞여 변수 이름과 설명의 짝이 어긋나 있다. 아래는 본문 다른 곳의 설명으로 확인되는 것을 우선하고, 짝이 불확실한 것은 그렇게 표시했다.

| 변수 | 범위 | 용도 | 확실도 |
|---|---|---|---|
| CLAUDE_PROJECT_DIR | 모든 훅 | 현재 프로젝트 루트의 절대 경로. 감사 로그 경로와 Stop 훅의 `cd`에 쓰였다 | 본문 코드로 확인됨 |
| CLAUDE_ENV_FILE | SessionStart | 환경 변수 export 문을 적어 넣는 파일 경로 | 1번 문서 본문으로 확인됨 |
| CLAUDE_PLUGIN_ROOT | 플러그인 훅 전용 | 플러그인이 설치된 루트 디렉터리 경로 | 표의 설명으로 추정 |
| CLAUDE_CODE_REMOTE | (표에서 범위가 뒤섞임) | 원서가 이름만 나열하고 설명은 확인되지 않음 | 불확실 |

표 안에는 이 밖에 "현재 세션의 고유 식별자"(범위 모든 훅)와 "구체적인 알림 메시지 내용"(Notification 전용)이라는 두 설명이 남아 있으나, 대응하는 변수 이름은 추출본에서 읽히지 않았다. 이름을 짐작해 적지 않는다.

## 2. 디버깅 기법 세 가지

1. **디버그 정보는 stderr로**: stdout은 JSON 결정 결과 전용이므로 모든 디버그 출력은 stderr로 돌린다.

```bash
echo "DEBUG: Checking file $FILE_PATH" >&2   # 디버그 정보
echo '{"decision": "allow"}'                 # JSON 결정
```

2. **훅 스크립트를 수동으로 시험**: 모의 입력을 직접 만들어 파이프로 넣고 종료 코드까지 확인한다.

```bash
echo '{"tool_name":"Bash","tool_input":{"command":"rm -rf /"}}' | ./.claude/hooks/block-dangerous.sh
echo "Exit code: $?"
```

3. **`claude --debug`로 실행 정보 보기**: 일치한 훅 목록, 각 스크립트의 실행 시간, 반환 결과가 표시된다.

참고(노트 작성자): 원서 예시의 `{"decision": "allow"}`는 3번 문서의 새 규격에서 보면 `permissionDecision` 형태가 아니라 옛 최상위 형식이다. 디버그 출력 위치를 설명하려는 예시로 읽으면 된다.

## 3. 자주 밟는 함정 두 가지

- **셸 설정 파일의 무조건 echo**: `~/.zshrc`나 `~/.bashrc`에 환영 메시지 같은 echo가 무조건 실행되도록 들어 있으면, 그 출력이 stdout을 오염시켜 JSON 파싱이 실패한다. 해결책은 그 echo를 `[[ $- == *i* ]]` 조건으로 감싸 대화형 셸에서만 실행되게 하는 것이다.
- **settings.json 직접 수정 후 반영 안 됨**: Claude Code는 시작할 때 설정의 스냅샷을 한 번 잡아 두고, 실행 중 파일이 바뀌어도 자동으로 동기화하지 않는다. 변경을 적용하려면 /hooks 메뉴에서 확인하거나 현재 세션을 재시작해야 한다.

## 4. 엔지니어링 설계 방법론: 세 가지 차원

구체적인 자동화 요구 사항을 만나면 세 가지를 먼저 정해야 한다.

| 차원 | 질문 | 선택 기준 |
|---|---|---|
| 개입 시점(이벤트 선택) | 언제 개입할까 | 실행 전 차단은 PreToolUse 또는 UserPromptSubmit, 실행 후 피드백은 PostToolUse, 완료 점검은 Stop 또는 SubagentStop, 수명주기 관리는 SessionStart 또는 SessionEnd |
| 판단 방법(유형 선택) | 무엇으로 판단할까 | 규칙이 분명(패턴 매칭, 파일 검사)하면 command, 의미 판단이 필요하나 입력이 충분하면 prompt, 깊은 코드 분석이 필요하면 agent |
| 설정 범위(위치 선택) | 어디에 둘까 | 팀 전체 표준은 `.claude/settings.json`, 개인 취향은 `~/.claude/settings.json`, 서브에이전트 전용 검사는 Frontmatter |

## 5. 세 단계 전략: 관찰 먼저, 통제는 나중

설계는 보통 다음 세 단계로 진행한다.

1. 먼저 PostToolUse 이벤트와 matcher `"*"`로 감사 로그 훅을 설정해, Claude가 실제로 도구를 어떻게 호출하는지 관찰하고 며칠치 실제 운영 데이터를 쌓는다.
2. 감사 데이터를 근거로 위험도가 높은 조작 패턴을 가려내고, 겨냥한 PreToolUse 차단 규칙을 설계한다.
3. 차단 규칙을 점차 조이되 로깅 기능은 항상 유지한다. 오탐이 나도 원인을 바로 추적할 수 있게 하기 위해서다.

요약에서 원서는 이 원칙을 "먼저 관찰하고 그다음 통제한다"로 부르고, 로그로 훅의 발동 빈도를 실시간 감시해 오탐을 즉시 발견·교정하라고 덧붙인다.

## 6. 케이지의 노트: 훅은 팀 인프라다

`.claude/settings.json`에 둔 훅은 저장소를 clone하는 모든 팀원에게 적용된다. 영문도 모르고 막힌 팀원은 작업 흐름이 심하게 끊기고 짜증이 쌓인다. 그래서 두 가지를 지켜야 한다.

- 훅 설정을 커밋하기 전에 팀과 충분히 논의해 합의한다.
- 모든 차단 규칙에는 사용자가 막힌 구체적 이유를 알 수 있도록 명확한 사유 문구를 넣는다.

---

## 7. 핵심 정리

- CLAUDE_PROJECT_DIR(프로젝트 루트), CLAUDE_ENV_FILE(SessionStart의 변수 주입), CLAUDE_PLUGIN_ROOT(플러그인 훅)가 확인되는 환경 변수다. 표 5.2는 추출이 깨져 나머지는 확인하지 못했다.
- 디버깅은 stderr 출력, 모의 입력 수동 시험, `claude --debug`의 세 가지다.
- 함정은 셸 설정 파일의 echo가 stdout을 오염시키는 것과, 설정을 고쳐도 스냅샷 때문에 /hooks 확인이나 재시작이 필요한 것이다.
- 설계는 이벤트, 유형, 위치의 세 차원으로 정하고, 관찰(감사 로그)에서 통제(차단)로 단계적으로 진행한다.
- 팀 설정의 훅은 합의와 명확한 차단 사유가 필수다.
