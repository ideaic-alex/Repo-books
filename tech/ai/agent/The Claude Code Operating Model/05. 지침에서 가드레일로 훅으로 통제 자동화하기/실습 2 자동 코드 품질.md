# 실습 2 자동 코드 품질

보안 보호가 "문제가 생기기 전에 막는" 일이라면, 자동 코드 품질은 "훌륭한 결과물을 보장하는" 일이다. 이 실습은 PostToolUse와 Stop 훅이 협력하는 방식을 보여 준다. 파일을 쓸 때마다 자동으로 포맷하고(미관), lint로 오류를 잡아 Claude에게 되먹이고(정확성), 끝내려는 순간 테스트를 돌려 실패하면 못 끝내게 막는다(관문). 세 단계는 각각 별도 스크립트다.

---

## 1. PostToolUse: 자동 포맷 (auto-format.sh)

Claude가 파일에 쓸 때마다 포맷 도구를 자동으로 돌린다. 이 훅의 묘미는 관심사의 분리다. Claude는 프로젝트가 어떤 포맷 규칙을 쓰는지 몰라도 되고 코드 논리에만 집중하면 되며, 포맷은 뒤에서 조용히 끝난다.

스크립트는 `.tool_input.file_path`를 꺼내 비었거나 파일이 없으면 `{}`를 내고 끝낸다. 그다음 확장자로 도구를 고른다.

| 확장자 | 사용 도구 | 성공 시 additionalContext |
|---|---|---|
| js, jsx, ts, tsx, json, md, css, scss, html | `npx prettier --write` | Formatted with Prettier |
| py | `black` | Formatted with Black |
| go | `gofmt -w` | Formatted with gofmt |
| 그 외 | 없음 | `{}` |

각 도구는 실행 전에 `command -v 도구명`으로 설치 여부를 확인한다. 설치되어 있지 않으면 오류를 내지 않고 조용히 건너뛴다. 이것이 점진적 퇴화(graceful degradation)라는 설계 원칙이다. 훅 자체의 예외가 핵심 작업 흐름을 막아서는 안 된다는 뜻이다.

```bash
case "$EXTENSION" in
    py)
        if command -v black &> /dev/null; then
            black "$FILE_PATH" 2>/dev/null
            echo '{"hookSpecificOutput":{"additionalContext":"Formatted with Black"}}'
        fi
        ;;
esac
```

## 2. PostToolUse: lint 피드백 순환 (lint-check.sh)

자동 포맷이 코드의 "미관"을 맡는다면 lint는 "정확성"을 보증한다. 핵심은 additionalContext로 lint 결과를 Claude에게 되먹여 "수정, 검사, 피드백, 교정"의 자동 폐쇄 루프를 만드는 것이다.

스크립트는 파일이 .js, .ts, .jsx, .tsx일 때만 `npx eslint`를 돌린다. 결과의 앞 30줄(`head -30`)을 jq의 `-Rs`로 JSON 문자열로 이스케이프해 "ESLint found problems:" 뒤에 붙여 additionalContext로 낸다. 문제가 없으면 "ESLint check passed"를 낸다. 대상이 아닌 파일은 `{}`를 낸다.

참고(노트 작성자): 원서 코드는 `LINT_RESULT=$(npx eslint ... 2>&1) || true` 바로 다음 줄에서 `$?`를 검사한다. `|| true` 때문에 `$?`는 항상 0이어서 이 코드대로면 항상 "통과" 분기로 가는 것으로 읽힌다. 원서가 의도한 동작(오류가 있으면 문제 목록을 되먹임)을 구현하려면 종료 코드를 따로 저장하는 식의 보완이 필요하다. 이는 원서에 없는 관찰이며, 원서 코드의 줄바꿈이 추출 중 일부 깨져 있어 정확한 원형은 확신할 수 없다. 또 원서는 이 스크립트 설명으로 앞 절의 `command -v` 문단을 거의 그대로 되풀이하는데, 스크립트에는 `command -v`가 없어 중복 서술로 보인다.

## 3. Stop 훅: 테스트 품질 관문 (run-tests.sh)

Stop 훅은 품질 보증의 방어선이다. Claude가 "작업을 마쳤다"고 선언하는 순간 테스트 스위트를 자동으로 돌리고, 실패하면 세션 종료를 막아 계속 고치게 한다.

### 3-1. 무한 루프 방지: stop_hook_active

스크립트 맨 앞에서 입력 JSON의 `stop_hook_active`를 확인한다. 이 값이 true면 이미 한 번 재시도가 일어났다는 뜻이므로 이번에는 통과시켜(exit 0) 교착을 피한다. 재귀 함수에 종료 조건이 있어야 하는 것과 같다. 훅이 실패해 막으면 Claude가 고친 뒤 다시 멈추려 하고 그때 훅이 또 발동하는데, 이때 stop_hook_active가 true가 되므로 스크립트가 이 표식을 보고 흐름을 놓아 준다. 이 검사가 없으면 "수정, 테스트 실패, 또 수정"의 무한 루프에서 스스로 빠져나올 수 없다.

### 3-2. 프로젝트 유형 감지와 테스트 실행

`CLAUDE_PROJECT_DIR`가 있으면 그 디렉터리로 이동하고, 파일로 프로젝트 유형을 판별한다.

| 감지 파일 | 실행 명령 |
|---|---|
| package.json (안에 "test" 스크립트가 있을 때) | `npm test` |
| pyproject.toml 또는 pytest.ini | `pytest` |
| go.mod | `go test ./...` |
| 모두 없음 | additionalContext "No test framework detected"를 내고 통과 |

각 명령은 `2>&1`로 출력을 모으고, 실패하면 TEST_PASSED를 false로 바꾼다. 통과하면 "All tests passed"를 additionalContext로 낸다. 실패하면 오류 로그의 앞 50줄을 이스케이프해 다음 JSON으로 낸다.

```json
{ "decision": "block",
  "reason": "Test failed, please fix before stopping",
  "hookSpecificOutput": { "additionalContext": "<앞 50줄 오류 로그>" } }
```

원서 코드는 `[ -f "package.json"]&&grep-q'"test"'package.json`처럼 띄어쓰기가 사라진 채 추출되었고 heredoc 종결 표식도 보이지 않는다. 문맥으로 `[ -f "package.json" ] && grep -q '"test"' package.json`로 복원해 읽었다.

---

## 4. 세 훅이 만드는 순환

흐름은 이렇게 이어진다. Claude가 파일을 쓰면 PostToolUse가 포맷하고 lint 결과를 알려 준다. Claude가 끝내려 하면 Stop 훅이 테스트를 돌려 실패 시 막고 오류 로그를 돌려준다. 그러면 Claude가 고치고, 다시 멈추려 하면 stop_hook_active가 true이므로 이번에는 통과한다. 모든 단계에 사람이 끼지 않는다.

토론 질문 2번(요약 문서 참조)이 짚듯 이 Stop 훅은 CI/CD의 자동 테스트와 닮았지만, 위치가 개발자 로컬 세션의 마지막 순간이라는 점이 다르다.

---

## 5. 핵심 정리

- 포맷은 PostToolUse에서 확장자별 도구(prettier, black, gofmt)를 돌리고, 도구가 없으면 조용히 건너뛴다.
- lint 결과는 additionalContext로 Claude에게 되먹여 스스로 고치게 한다. 원서 코드의 `|| true` 부분은 의도대로 동작하지 않는 것으로 보인다.
- Stop 훅은 테스트가 실패하면 decision: "block"으로 종료를 막고, stop_hook_active로 무한 루프를 끊는다.
- 테스트 명령은 npm test, pytest, go test ./...이며 오류 로그는 앞 50줄만 되돌린다.
