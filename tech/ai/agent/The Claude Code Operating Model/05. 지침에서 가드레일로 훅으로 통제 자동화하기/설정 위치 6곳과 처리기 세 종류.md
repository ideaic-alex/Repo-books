# 설정 위치 6곳과 처리기 세 종류

훅을 어디에 적고(설정 위치), 걸린 이벤트에서 무엇이 실행되는지(처리기, 원서 표현으로 handler)를 정하는 방법을 다룬다. 설정은 겹겹이 덮어쓰는 층 구조이고 JSON으로 쓴다. 처리기는 command, prompt, agent 세 종류가 "결정성은 줄고 유연성은 늘어나는" 사다리를 이루며, 고르는 원칙은 가능하면 낮은 단계(command)를 쓰는 것이다.

---

## 1. 설정 위치: 6곳, 6가지 용도

Claude Code의 설정은 위에서 아래로 우선순위가 낮아지는 층 구조이며, 훅 설정은 여섯 단계 우선순위 구조를 따른다(원서 그림 5.1). 범위에 맞춰 자동화 로직을 배치할 수 있게 한 설계다.

원서 본문이 구체적으로 설명하는 위치는 아래 셋이다.

| 위치 | 성격 |
|---|---|
| `.claude/settings.json` (프로젝트 설정) | 팀 협업의 핵심. Git 저장소에 커밋하면 팀원 모두가 clone할 때 팀이 합의한 보안 검사와 자동화 규칙을 그대로 받는다 |
| `.claude/settings.local.json` (로컬 프로젝트 설정) | .gitignore로 제외된다. 팀 기본값을 개인적으로 덮어써야 할 때 적합하다 |
| `~/.claude/settings.json` (사용자 전역 설정) | 프로젝트를 가로지르는 개인 취향 관리용. 로그 형식, 데스크톱 알림 방식 등 |

참고(노트 작성자): 그림 5.1은 PDF 텍스트 추출본에서 비어 있어(해당 쪽에 본문이 없음) 나머지 세 위치의 이름은 확인할 수 없다. 이 장의 다른 대목에서 서브에이전트 Frontmatter에 훅을 정의할 수 있고(6번 문서 참조), 설계 방법론에서도 팀 전체는 `.claude/settings.json`, 개인은 `~/.claude/settings.json`, 서브에이전트 전용은 Frontmatter에 둔다고 정리한다. 이 노트는 원서가 확인해 주지 않은 위치명을 지어내지 않는다.

## 2. 설정 구조: 세 단계 중첩

훅 설정은 이벤트 유형, 매처 그룹(matcher group), 훅 처리기 목록의 세 단계로 중첩한다. 아래는 원서 예시에서 핵심만 추린 것이다. 원서 코드 중 PostToolUse의 command 문자열이 줄바꿈으로 깨져 있어 한 줄로 복원했다.

```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [ { "type": "command",
                     "command": "./.claude/hooks/block-dangerous.sh",
                     "timeout": 30 } ] }
    ],
    "PostToolUse": [
      { "matcher": "Write|Edit",
        "hooks": [ { "type": "command",
          "command": "INPUT=$(cat); FILE=$(echo \"$INPUT\" | jq -r '.tool_input.file_path'); prettier --write \"$FILE\"" } ] }
    ]
  }
}
```

### matcher 필드

이 훅 그룹을 적용할 도구 범위를 정한다.

- `"Bash"`: 모든 Bash 호출에 일치한다.
- `"Write|Edit"`: Write 또는 Edit 도구에 일치한다. 파이프 기호 `|`는 논리합(또는)이다.
- `"*"`: 모든 도구에 일치한다.

Stop, Notification, UserPromptSubmit 같은 수명주기 이벤트는 특정 도구를 대상으로 하지 않으므로 matcher가 무시된다. 반대로 SubagentStart와 SubagentStop에서는 matcher가 도구 이름이 아닌 서브에이전트 유형 이름에 일치한다.

## 3. 처리기 유형: 결정성의 사다리

원서에 따르면 훅 처리기는 다섯 종류다. 그중 command, prompt, agent 세 가지가 "결정성이 줄고 유연성이 느는" 사다리를 이루고, 어느 것을 쓸지는 검사가 얼마나 엄격해야 하느냐로 정한다. 나머지 둘은 사다리의 칸이 아니라 연동용 통로다. http는 이벤트 JSON을 사용자가 관리하는 URL로 POST하고, mcp_tool은 이미 연결된 MCP 서버의 도구를 호출한다. /hooks 메뉴에 다섯 가지가 모두 나온다. 이 장은 세 가지만 자세히 다룬다.

### 3-1. command 유형: 결정적 규칙

셸 명령이나 스크립트를 실행한다. 가장 많이 쓰고 가장 믿을 만하다. 결정적 규칙은 언제나 대형 모델의 판단보다 신뢰할 수 있기 때문이다.

command 훅은 stdin으로 JSON 컨텍스트(session_id, tool_name, tool_input 등)를 받고, stdout으로 JSON 결정을 내보내며, 종료 코드로 최종 의도를 표현한다.

| 종료 코드 | 의미 |
|---|---|
| 0 | 성공. 시스템이 stdout의 JSON을 파싱해 결정의 근거로 삼는다 |
| 2 | 의도적 차단. stderr 내용이 오류 사유로 Claude에게 전달된다 |
| 그 밖의 값 | 스크립트 오류. 실행은 중단되지 않지만 더는 조용히 넘어가지 않는다. 대화 기록에 "<hook name> hook error" 알림과 stderr 첫 줄이 보이고 전체 stderr는 디버그 로그로 간다 |

종료 코드 2 설계가 핵심이다. "의도적으로 작업을 막는 것"과 "스크립트가 고장난 것"을 엄격히 구분한다. 스크립트 고장이 정상 작업 흐름을 막아서는 안 된다. 고장 난 화재 경보기가 사람의 출입을 막지 않는 것과 같다.

### 3-2. prompt 유형: 대형 모델 한 번 평가

검증 논리에 어느 정도 판단이 필요하지만 여러 단계 작업은 필요 없을 때 권한다. 가벼운 대형 모델(보통 Haiku)을 한 번 불러 현재 상황을 평가하게 한다.

```json
{ "type": "prompt",
  "prompt": "Evaluate whether this code modification introduces security vulnerabilities. $ARGUMENTS",
  "model": "claude-haiku-4-5",
  "timeout": 30 }
```

`$ARGUMENTS`는 실행 시 훅이 받은 입력 JSON 전체로 치환되는 자리표시자다. 모델의 응답은 정해진 JSON 형식이어야 한다. 허용은 `{"ok": true, "reason": "..."}`, 거부는 `{"ok": false, "reason": "..."}`다. 원서의 거부 예시는 사용자 입력이 이스케이프 없이 쿼리 문자열에 바로 이어 붙어 SQL 인젝션 위험이 감지됐다는 사유를 든다.

### 3-3. agent 유형: 여러 턴의 지능적 검증

결론을 내리려면 실제 코드 파일을 열어 보거나 검색하거나 여러 단계를 거쳐야 할 때 쓴다. 서브에이전트를 띄워 Read, Grep, Glob 같은 도구로 여러 턴에 걸쳐 깊이 검증하게 한다.

```json
{ "type": "agent",
  "prompt": "Check whether all modified files have passed unit tests. Run the test suite and verify the results. $ARGUMENTS",
  "timeout": 120 }
```

agent 유형의 서브에이전트는 최대 50회의 대화·작업 라운드 안에 결정을 반환해야 한다. 응답 형식은 prompt 유형과 같아서 ok(불리언)와 reason(문자열)이 든 JSON 객체다.

## 4. 선택 원칙: 강등 원칙

처리기를 고를 때는 "가능하면 prompt보다 command를, 가능하면 agent보다 prompt를" 쓰라는 강등 원칙을 따른다(원서 그림 5.2). 패턴 매칭, 파일명 검사, 정규식 같은 결정적 규칙은 속도와 신뢰성에서 대형 모델 판단을 언제나 앞선다. 검증에 정말로 이해(의미 분석)나 코드 점검 능력(여러 파일의 컨텍스트 검색)이 필요할 때만 prompt나 agent로 올린다.

| 유형 | 결정성 | 유연성 | 제한 | 쓰는 때 |
|---|---|---|---|---|
| command | 가장 높음 | 가장 낮음 | 종료 코드와 JSON | 규칙이 분명할 때 |
| prompt | 중간 | 중간 | 모델 1회 평가, ok/reason | 의미 판단이 필요하나 입력이 충분할 때 |
| agent | 가장 낮음 | 가장 높음 | 최대 50라운드, ok/reason | 코드를 열어 봐야 판단될 때 |

## 5. 핵심 정리

- 설정은 층 구조이며 프로젝트(`.claude/settings.json`)가 팀 공유, 로컬(`.claude/settings.local.json`)이 개인 덮어쓰기, 전역(`~/.claude/settings.json`)이 개인 전반 취향이다. 여섯 곳 중 나머지는 그림이 추출되지 않아 확인하지 못했다.
- 구조는 이벤트 유형, 매처 그룹, 처리기 목록의 3단 중첩이고, matcher는 `Bash`, `Write|Edit`, `*`처럼 쓴다. 수명주기 이벤트는 matcher를 무시하고, 서브에이전트 이벤트는 유형 이름과 일치시킨다.
- 처리기는 command, prompt, agent 외에 http, mcp_tool까지 다섯 종류다.
- command는 stdin JSON 입력, stdout JSON 출력, 종료 코드 0(성공)과 2(의도적 차단)로 동작한다. 그 밖의 코드는 알림이 보이는 스크립트 오류다.
- prompt는 Haiku 같은 가벼운 모델 한 번, agent는 최대 50라운드이며 둘 다 ok와 reason을 반환한다. 선택은 command 우선의 강등 원칙이다.
