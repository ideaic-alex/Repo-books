# 실습 1 보안 보호 체계

장 첫머리의 .env 유출 사고로 돌아가, 훅으로 세 겹의 방어선을 만든다. 첫째는 위험한 명령 차단, 둘째는 민감한 파일 보호, 셋째는 모든 조작의 감사 기록이다. 앞의 둘은 PreToolUse로 "실행 전에 막고", 셋째는 PostToolUse로 "실행 후에 남긴다". 세 스크립트를 `.claude/settings.json`에 묶으면 사전 차단, 실시간 보호, 사후 감사의 폐쇄 루프가 된다.

---

## 1. 1선 방어: 위험한 명령 차단 (block-dangerous.sh)

Claude가 재앙을 부를 수 있는 Bash 명령을 막는 스크립트다. 원서가 짚는 설계 포인트는 세 가지다.

- 디버그 정보는 stdout이 아니라 stderr(`>&2`)로 낸다. stdout은 JSON 결정 결과 전용으로 엄격하게 남겨 둬야 하기 때문이다.
- 입력 JSON은 jq로 파싱한다. 문자열을 손으로 매칭하는 방식은 깨지기 쉽다.
- 차단할 때마다 구체적인 사유를 붙인다.

동작은 단순하다. stdin의 JSON에서 `.tool_input.command`를 꺼내고(`// ""`로 비어 있을 때를 대비), 위험 패턴 배열을 돌며 명령에 패턴이 들어 있는지 본다. 하나라도 걸리면 stderr에 `BLOCKED: <패턴>`을 쓰고, permissionDecision이 deny인 JSON을 낸 뒤 exit 2로 끝낸다. 아무것도 안 걸리면 allow JSON을 내고 exit 0으로 끝낸다.

```bash
INPUT=$(cat)
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command // ""')
echo "DEBUG: Checking command: $COMMAND" >&2
for pattern in "${DANGEROUS_PATTERNS[@]}"; do
    if [[ "$COMMAND" == *"$pattern"* ]]; then
        echo "BLOCKED: $pattern" >&2
        # deny JSON 출력 후
        exit 2
    fi
done
echo '{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"allow"}}'
```

원서의 위험 패턴 목록은 다음과 같다.

| 분류 | 패턴 |
|---|---|
| 루트·홈 삭제 | `rm -rf /`, `rm -rf ~`, `rm -rf $HOME` |
| 디스크·권한 파괴 | `> /dev/sd`, `mkfs.`, `chmod -R 777 /` |
| 포크 폭탄 | `:(){:|:&};:` |
| 원격 이력 파괴 | `git push --force origin main`, `git push --force origin master`, `git reset --hard origin` |
| 데이터베이스 파괴 | `DROP DATABASE`, `DROP TABLE`, `TRUNCATE` |
| 위험한 파이프 실행 | `curl.*| sh`, `curl.*| bash` |

참고(노트 작성자): 원서 스크립트는 `[[ "$COMMAND" == *"$pattern"* ]]`처럼 패턴을 따옴표로 감싸 비교한다. 이 경우 패턴은 글자 그대로 비교되므로 `curl.*| sh`의 `.*`는 정규식이 아니라 그냥 글자로 취급된다. 실제 `curl ... | sh` 명령을 잡으려면 정규식 비교 등 다른 방식이 필요하다. 이는 원서에 없는 관찰이므로 참고로만 둔다. 또 원서는 포크 폭탄 줄에 주석을 인용 부호 밖에 붙였는데 추출 과정에서 들여쓰기가 깨진 것으로 보인다.

## 2. 2선 방어: 민감한 파일 보호 (protect-files.sh)

민감한 파일이 실수로 수정되는 것을 막는다. matcher를 `"Write|Edit"`로 두어 파일 쓰기·편집 때만 발동하게 하며, 위험을 발생원에서 차단한다. 장 첫머리의 사고(.env 커밋)는 이 2선 방어가 있었다면 완전히 피할 수 있었다는 것이 원서의 평가다.

스크립트는 `.tool_input.file_path`에서 경로를 꺼내 비어 있으면 allow로 통과시키고, 그렇지 않으면 세 가지를 순서대로 검사한다.

| 검사 | 대상 |
|---|---|
| 보호 디렉터리(경로에 포함 여부) | `.git/`, `.ssh/`, `node_modules/` |
| 보호 파일명(basename 일치) | `.env`, `.env.local`, `.env.production`, `credentials.json`, `secrets.yaml`, `secrets.json`, `id_rsa`, `id_ed25519` |
| 보호 확장자(`${FILENAME##*.}`) | `pem`, `key`, `p12`, `pfx` |

어느 하나에 걸리면 각각 "보호 디렉터리 안의 파일 수정은 허용되지 않음", "민감한 파일 수정은 허용되지 않음", "키 파일 수정은 허용되지 않음(`*.확장자`)"이라는 사유와 함께 deny JSON을 내고 exit 2로 끝난다. 모두 통과하면 allow다.

원서 코드는 이 스크립트에서 heredoc 종결 표식(EOF)이 빠져 있고, "Check file extensions" 주석이 이름 검사 블록 한가운데에 들어가 있는 등 추출·조판이 깨져 있다. 위 설명은 변수 정의(디렉터리, 파일명, 확장자 순)와 문맥에 따라 논리 순서를 복원한 것이다.

참고(노트 작성자): 이 훅은 Write와 Edit 도구에만 걸려 있다. 원서는 Bash로 파일을 건드리는 경우(예: `cat > .env`)까지 막는다고는 하지 않았다. 필요하면 1선 방어의 Bash 패턴을 보강해야 한다는 점은 원서에 없는 보충이다.

## 3. 3선 방어: 전체 조작 감사 (audit-log.sh)

matcher를 `"*"`로 두어 모든 도구 호출을 기록한다. 엄격한 컴플라이언스가 필요한 기업 환경에서는 필수에 가깝다. "언제 Claude가 어떤 대상에 무슨 조작을 했는가"라는 감사의 핵심 질문에 답해 주기 때문이다.

동작은 이렇다. 로그 디렉터리는 `${CLAUDE_PROJECT_DIR:-.}/.claude/logs`, 파일은 날짜별 `audit-YYYY-MM-DD.log`다. 한 줄은 `[ISO 시각] 도구이름: 도구입력(JSON 한 줄)` 형식이다. 끝에는 `echo '{}'`와 `exit 0`으로 아무 결정도 내리지 않고 흘려보낸다.

```bash
LOG_FILE="$LOG_DIR/audit-$(date +%Y-%m-%d).log"
TIMESTAMP=$(date -Iseconds)
TOOL_NAME=$(echo "$INPUT" | jq -r '.tool_name // "unknown"')
TOOL_INPUT=$(echo "$INPUT" | jq -c '.tool_input // {}')
echo "[$TIMESTAMP] $TOOL_NAME: $TOOL_INPUT" >> "$LOG_FILE"
```

## 4. 전체 설정

세 스크립트를 `.claude/settings.json`에 이렇게 묶는다. 원서 설정의 구조 그대로다.

| 이벤트 | matcher | 스크립트 |
|---|---|---|
| PreToolUse | Bash | `./.claude/hooks/block-dangerous.sh` |
| PreToolUse | Write\|Edit | `./.claude/hooks/protect-files.sh` |
| PostToolUse | * | `./.claude/hooks/audit-log.sh` |

각 항목은 `{"type": "command", "command": "<경로>"}` 형태의 처리기 하나다. 이 구성이 "사전 차단, 실시간 보호, 사후 감사"의 폐쇄 루프이며 흐름은 위험 명령 차단, 민감 파일 보호, 전체 조작 감사 순이다. 사람의 조심성에 기대던 취약한 과정을 "코드가 곧 법"인 자동 보안 체계로 끌어올린 것이다.

---

## 5. 핵심 정리

- 1선 PreToolUse(Bash) 위험 명령 차단, 2선 PreToolUse(Write|Edit) 민감 파일 보호, 3선 PostToolUse(*) 감사 기록이다.
- 스크립트 규칙은 jq 파싱, 디버그는 stderr, stdout은 JSON 결정 전용, 차단에는 구체적 사유를 쓰는 것이다.
- 차단은 deny JSON과 exit 2의 조합이고, 통과는 allow JSON과 exit 0이다.
- 감사 로그는 날짜별 파일에 시각, 도구 이름, 입력을 남긴다. 이 기록은 7번 문서의 "관찰 먼저, 통제는 나중" 방법론의 출발점이 된다.
