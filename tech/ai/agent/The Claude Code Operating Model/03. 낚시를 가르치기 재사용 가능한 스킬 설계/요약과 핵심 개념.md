# 요약과 핵심 개념

이 장은 "매번 같은 설명을 되풀이하는 비용"에서 출발해, 전문 지식을 폴더로 묶어 필요할 때만 불러오는 스킬(Skills)의 구조와 설계법을 다뤘다. 지식의 두 차원(CLAUDE.md와 스킬), 스킬의 해부, 점진적 공개와 description 예산, 트리거와 두 가지 스킬 철학, SKILL.md 본문과 권한, 인자와 동적 주입, 실습과 설계 패턴 순으로 이어졌다.

원서의 요약은 이렇게 정리한다. 스킬은 개발자가 겪는 일상의 불편, 곧 Claude가 전문적인 작업 방식을 영구히 간직하게 하는 문제를 해결한다. Claude Code의 5층 구조에서 스킬은 지식 층에 있고, 도구 층("무엇을 할 수 있는가")을 토대로 에이전트 층("누가 하는가")을 돕는다. 아래로는 allowed-tools로 도구 행동을 제약하고, 위로는 skills 필드로 서브에이전트에게 전문 지식을 주입하며, CLAUDE.md와는 병렬적이고 상호 보완적인 관계다(전자는 항상 활성, 후자는 필요할 때 호출). 다음 4장은 서브에이전트를 다룬다. 스킬이 Claude에게 전문 "지식"을 준다면 서브에이전트는 복잡한 작업을 쪼개 독립된 컨텍스트를 가진 여러 전문가에게 맡기고 정제된 결론만 메인 대화로 돌려주는 더 근본적인 "능력"이다.

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | CLAUDE.md와 스킬 비교 | 상시 적용되는 규칙(벽)과 필요할 때 꺼내는 절차(서류함)의 구분 |
| 2 | 디렉터리 구조와 frontmatter | SKILL.md, scripts/, reference/, templates/ 구성과 이름 규칙, 세 묶음의 필드 |
| 3 | 점진적 공개와 description 예산 | 3층 로딩으로 토큰 50~98% 절감, 입구 예산은 사용 빈도 순으로 저하 |
| 4 | 트리거와 스킬 철학 | description 공식, 과소/과다 트리거 처방, 참조 스킬 대 작업 스킬 |
| 5 | SKILL.md 본문과 allowed-tools | 라우터 사고, 500줄 규칙, 유형별 최소 권한 설계 |
| 6 | 인자, 동적 주입, 범위 | `$ARGUMENTS`, `!`command``, 기업 > 개인 > 프로젝트 > 플러그인 우선순위 |
| 7 | 실습 3개와 설계 패턴 | code-reviewing, committing, financial-analyzing, 4가지 패턴과 테스트 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 스킬 | 지침과 자원을 담은 폴더. Claude에게 특정 작업 방식을 "가르친다" |
| SKILL.md | 필수 주 파일. 이름은 대문자 그대로여야 하고 라우터 역할을 한다 |
| kebab-case | 소문자, 숫자, 하이픈만 쓰는 이름 규칙. 64자 이하 |
| 점진적 공개 | description 상주, 본문은 트리거 시, 참조 파일은 필요 시 로드하는 3층 구조 |
| description | 의미 매칭의 유일한 신호. 기능 + "Use when..." + 핵심 능력(+ "Not for...") |
| 참조 스킬 | 기본 설정. Claude가 맥락에 따라 자동 로드하는 지식 |
| 작업 스킬 | disable-model-invocation: true. 사용자가 `/이름`으로만 실행하는 부작용 있는 작업 |
| 계약형 참조 | 언제, 어디, 무엇을 얻는지 밝히는 보조 파일 참조 |
| 500줄 규칙 | SKILL.md는 500줄(약 2,000~3,000토큰) 이내. 넘으면 분리 |
| allowed-tools | 스킬 활성 중 허용되는 도구. `Bash(prefix:*)`로 명령을 좁힌다 |
| `$ARGUMENTS`, `$0` | 호출 인자 변수 |
| `!`command`` | 프롬프트 전달 전에 셸 명령을 실행해 출력을 끼워 넣는 동적 주입 |
| 네 가지 패턴 | 템플릿 주도, 스크립트 강화, 지식 계층화, 도구 격리 |
| 개방형 표준 | 2025년 12월 18일 공개, 2026년 중반 약 40개 제품이 호환(시점 수치) |

## 3. 자주 놓치는 점

- 파일 이름은 정확히 SKILL.md여야 한다. 소문자나 혼합 표기는 모두 무효다.
- allowed-tools는 도구를 허용하고 자동 승인하는 필드이고, 제거하는 필드는 disallowed-tools다. user-invocable: false도 보안 경계가 아니라 메뉴 숨김일 뿐이며, 진짜 경계는 권한 설정과 훅(5장)이다.
- 스킬을 많이 설치해도 스킬이 사라지지는 않는다. 예산이 모자라면 덜 쓰는 스킬의 설명 텍스트부터 줄어들 뿐이다. Claude가 스킬을 못 찾는다면 글자 수 제한이 아니라 description 품질을 의심한다.
- 예산과 한도 수치(약 1%, 항목당 1,536자, description 1,024자)는 릴리스마다 바뀌어 왔다. 규모 감각으로만 쓰고 실제 버전에서 확인한다.
- 위험한 작업은 최악의 경우를 먼저 따져 작업 스킬로 만든다. `Bash(*)` 같은 전역 와일드카드는 쓰지 않는다.
- `!`command`` 실행 전에 인자가 먼저 치환되므로 셸 주입 위험이 있다.
- SKILL.md 안에 계산식을 쓰고 있다면 스크립트로 옮길 때다.
- 같은 오류를 손으로 반복 교정하고 있다면 SKILL.md를 고쳐야 할 신호다.

## 4. 생각해 볼 질문 (원서의 Reflection Questions)

1. 일상 업무에서 Claude에게 반복해서 설명하는 도메인 지식이나 작업 규약은 무엇인가? 그것을 스킬의 description으로 증류해 보자. 1,024자 제한에서 어떤 핵심 정보를 우선하겠는가?
2. `/deploy`라는 작업 스킬을 설계해 보자. disable-model-invocation이 필요한 이유, allowed-tools의 정밀한 권한 범위, `!`command`` 실행 전에 미리 불러올 맥락(현재 브랜치, 최근 빌드 상태 등), 완전한 오류 처리 경로를 반영해 frontmatter 전체와 SKILL.md 뼈대를 출력해 본다.
3. 프로젝트에 스킬 25개가 설치되어 있고 description 글자 예산이 총 16,000자라고 하자. 예산을 엄수하면서 각 스킬의 트리거 정확도를 최대화하려면 어떻게 해야 하는가? 어떤 종류의 스킬에 disable-model-invocation: true를 설정해 귀한 설명 공간을 비울 수 있는가?

참고(노트 작성자): 3번 질문의 힌트는 본문에 있다. 비슷한 스킬은 합치고, 사용자가 직접 실행하는 작업 스킬은 description이 Claude의 컨텍스트에 주입되지 않으므로 예산을 쓰지 않는다는 점(트리거 문서 참조), 그리고 설명을 짧게 쓸수록 예산 압박에서 살아남는다는 점이다.
