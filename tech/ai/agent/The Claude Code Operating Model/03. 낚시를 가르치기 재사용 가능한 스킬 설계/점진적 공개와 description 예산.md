# 점진적 공개와 description 예산

스킬 구조를 이해한 샤오빙이 곧바로 날카로운 질문을 던진다. 스킬이 20개이고 각각 수천 토큰이라면, 대화할 때마다 Claude Code가 전부 로드해야 하는가? 그러면 모든 것을 CLAUDE.md에 밀어 넣는 것과 무엇이 다른가? 카게는 이것이 스킬 시스템의 가장 영리한 핵심, 점진적 공개(progressive disclosure, 정보를 한꺼번에 주지 않고 필요한 만큼 단계적으로 드러내는 방식)를 정확히 짚은 질문이라고 답한다.

이 문서는 세 층 구조와 그 절감 효과를 수치로 살펴보고, 첫 층인 description이 공유하는 "예산"이 어떻게 관리되는지, 그래서 왜 스킬을 "적게, 그러나 정제해서" 만들어야 하는지를 정리한다.

---

## 1. 도서관 모델과 세 층

카게의 비유는 도서관이다. 도서관에 가서 모든 책을 한꺼번에 읽는 사람은 없다. 먼저 목록을 훑어 분류를 찾고, 목표한 책을 꺼내 목차를 보고, 마지막으로 필요한 부분만 정독한다. 스킬 시스템은 같은 3단계 구조를 쓴다.

| 층 | 로드되는 것 | 시점 |
|---|---|---|
| 1층 | 모든 스킬의 description(이름과 설명) | 컨텍스트에 항상 상주 |
| 2층 | SKILL.md 본문 | 스킬이 트리거되었을 때 |
| 3층 | SKILL.md가 가리키는 참조 파일 | 실행 중 필요할 때 읽음 |

참고(노트 작성자): 이 구분은 책 3장 요약에 나온 설명("컨텍스트에 상주하는 description, 트리거 시 로드되는 SKILL.md 본문, 실행 중 동적으로 읽는 참조 파일")을 표로 정리한 것이다. 원서의 그림 3.3은 추출본에서 내용이 비어 있어 확인할 수 없었다.

## 2. 재무 분석 스킬로 본 절감 효과

책은 총 5,300토큰짜리 재무 분석 스킬을 예로 든다. 파일 구성은 SKILL.md 800토큰(주 로직과 라우팅 안내), reference/revenue.md 1,500, reference/costs.md 1,200, reference/profitability.md 1,000, templates/report.md 800이다. 합계가 5,300이다.

요청 유형별로 전통적인 전체 로드와 점진적 공개를 비교하면 다음과 같다.

| 상황 | 전체 로드 | 점진적 공개 | 절감률 |
|---|---|---|---|
| 스킬 미활성 | 0 | 0 | 없음 |
| 스캔 단계(관련성 판단만) | 5,300 | 약 100 | 98% |
| 단순 요청(주 파일만) | 5,300 | 800 | 85% |
| 중간 요청(참조 파일 1개 필요) | 5,300 | 2,300 | 57% |
| 복잡한 요청(전체 자원 필요) | 5,300 | 5,300 | 0% |

사용자가 "매출총이익률은 어떻게 계산하나요?"라고 물으면 Claude Code는 SKILL.md(라우팅용)와 profitability.md(공식) 두 개만 읽는다. 합계는 약 1,800토큰이고, 나머지 세 파일(약 3,500토큰)은 디스크에 그대로 남아 비용이 0이다. 대부분의 요청이 자원의 일부만 필요로 한다는 점이 "최소한의 컨텍스트 비용으로 최대한의 지식 범위를 확보한다"는 이점의 핵심이다. 책은 장 요약에서 대부분의 상황에서 토큰 소비를 50~98% 줄일 수 있다고 말한다.

## 3. description의 예산 메커니즘

1층, 즉 모든 스킬의 description은 상주 방식으로 Claude의 컨텍스트에 주입된다. 그래서 모두가 한정된 토큰 예산을 나눠 쓰며, 이것이 시스템의 "입구 병목"이 된다.

### 3-1. 예산의 크기와 한도

- Claude Code는 스킬 목록의 크기를 컨텍스트 윈도 크기에 비례하는 글자 수 예산으로 정하며, 기본값은 대략 1%다.
- 예산과 별개로 각 항목의 합산 텍스트는 1,536자로 제한된다.
- 책은 이 수치가 릴리스마다 바뀌어 왔으니 대략의 규모 감각으로만 받아들이고, 실제로 배포하는 Claude Code 버전에서 확인하라고 당부한다.

참고(노트 작성자): description 필드 자체의 상한은 앞 절(frontmatter)에서 본 것처럼 1,024자이고, 위의 1,536자는 목록에 올라가는 항목 하나의 합산 한도다. 책은 두 수치의 관계를 더 설명하지 않는다.

### 3-2. 예산은 균등 분배가 아니다

스킬 이름은 항상 목록에 나온다. 설명들의 합이 예산을 넘으면 Claude Code는 가장 적게 호출한 스킬부터 설명을 줄이고, 이어서 아예 뺀다. 그래서 자주 쓰는 스킬은 설명 전문을 유지한다. 즉 저하는 사용 빈도 순으로 일어나며 스킬마다 같은 몫이 주어지는 것이 아니다.

책에는 "스킬당 사용 가능한 글자 수 = 전체 예산 / 전체 스킬 수"라는 식이 나오는데, 바로 뒤 문단은 균등 분배가 아니라고 설명한다. 식은 개념적 평균을 보여 주는 것으로 읽는 것이 맞아 보인다.

결론은 이렇다.

- 스킬을 많이 설치했다는 이유만으로 스킬이 사라지지는 않는다. 예산이 부족하면 가장 덜 쓰는 스킬의 설명 텍스트가 줄어들 뿐이고 이름은 모두 보인다.
- 설명이 길다고 목록에서 조용히 빠지는 일도 없다.
- 따라서 Claude가 어떤 스킬을 "못 보는 것 같다"면 숨은 글자 수 제한이 아니라 description 품질 문제다.
- 처음부터 설명을 간결하게 쓰는 것이 좋다. 몫이 나뉘어서가 아니라 짧은 설명이 예산 압박에서 온전히 살아남기 때문이다.

## 4. 철학: 적게, 그러나 정제해서

책은 예산 메커니즘에서 설계 철학을 끌어낸다. 스킬을 무작정 만들지 말고 "소수 정예" 구조를 지향하라는 것이다. 20개 넘게 설치해야 한다는 느낌이 들면 아키텍처 전략을 다시 점검하라는 신호다. 세 가지 대응이 제시된다.

- 비슷한 것을 합친다. 조각난 여러 스킬을 하나의 종합 스킬로 묶는다.
- 내부 도구를 숨긴다. 순수한 내부 하위 작업은 disable-model-invocation: true로 표시해 예산 사용을 줄인다.
- "토큰 투자" 수익률 관점을 채택한다. description의 글자 하나하나를 비싼 투자로 본다. 정확한 검색과 실행에 정밀하게 투자해야 하며, 낭비하면 자기 예산을 쓸 뿐 아니라 다른 스킬의 생존 공간까지 밀어낸다.

### 4-1. 예산 늘리기

Kage의 팁 3은 예산을 올리려면 skillListingBudgetFraction 설정을 쓰라고 한다(예: 2%에 해당하는 0.02). SLASH_COMMAND_TOOL_CHAR_BUDGET 환경 변수는 고정 글자 수로 덮어쓰는 용도로 여전히 쓸 수 있다.

## 5. 핵심 정리

- 점진적 공개는 description 상주, SKILL.md 트리거 시 로드, 참조 파일 필요 시 로드라는 3층 구조다.
- 5,300토큰 스킬이 요청 유형에 따라 100~5,300토큰으로 로드되고, 가장 복잡한 요청에서는 절감이 없다.
- description은 모두가 나눠 쓰는 입구 예산이며, 넘치면 사용 빈도가 낮은 스킬부터 설명이 줄어든다.
- 한도 수치는 버전에 따라 변하므로 규모 감각으로만 기억하고 실제 버전에서 확인한다.
- 스킬은 합치고, 내부용은 자동 호출을 끄고, 설명 한 글자도 투자로 여긴다.
