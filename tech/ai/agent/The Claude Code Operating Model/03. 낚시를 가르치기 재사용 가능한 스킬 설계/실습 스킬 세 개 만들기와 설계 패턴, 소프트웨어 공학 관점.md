# 실습: 스킬 세 개 만들기와 설계 패턴, 소프트웨어 공학 관점

이론을 마쳤으니 책은 복잡도가 점점 올라가는 세 가지 사례를 단계별로 만든다. 세 사례는 우연히 고른 것이 아니라 앞서 설명한 세 가지 전형적 응용 장면, 곧 참조 스킬, 작업 스킬, 점진적 공개를 모두 쓰는 종합 스킬에 정확히 대응한다. 이어서 책은 실무에서 걸러 낸 네 가지 설계 패턴과 스킬 테스트 방법, 그리고 소프트웨어 공학의 고전 원칙으로 스킬을 다시 보는 관점을 제시한다.

---

## 1. 참조 스킬 실습: 코드 리뷰(code-reviewing)

샤오빙의 팀은 매일 많은 코드 리뷰를 한다. 팀의 내부 규약은 세 가지다. 우선순위는 보안 문제가 최우선이고 성능 문제, 코드 스타일이 그다음이다. 문제만 지적하고 해법을 주지 않는 것은 엄격히 금지한다. 모든 이슈에는 심각도 등급을 표시한다. 지침이 여러 문서에 흩어져 있어 신입이 한 번에 익히기 어렵기 때문에 스킬로 정리했다.

디렉터리는 단출하다. SKILL.md(핵심 리뷰 절차와 기준)와 reference/severity-guide.md(상세 심각도 분류 기준)다. frontmatter는 이렇다.

```yaml
name: code-reviewing
description: Performs structured code reviews following team standards. ...
  Use when user asks to "review code", "do a code review", "check this PR",
  "audit this function", or provides code and asks for feedback.
allowed-tools:
- Read
- Grep
- Glob
```

본문은 우선순위별 점검 항목과 출력 형식 규정으로 이뤄진다.

| 우선순위 | 점검 항목 |
|---|---|
| 1순위 보안 | SQL 인젝션(문자열 직접 연결, 매개변수화 쿼리 미사용), XSS(이스케이프하지 않은 사용자 입력의 HTML 출력), 하드코딩된 민감 정보(비밀번호, 키, 토큰, DB 연결 문자열), 인가 검증 결함(인증 미들웨어 누락, 권한 상승 가능 로직) |
| 2순위 성능 | N+1 쿼리, 인덱스 누락, 중복 계산(루프 안의 불변 계산), 메모리 누수 위험(닫지 않은 연결, 계속 커지는 캐시) |
| 3순위 품질 | 과도하게 긴 함수(정당한 사유 없이 50줄 초과), 모호한 이름, 오류 처리 누락(빈 catch 블록, 삼킨 예외), 코드 중복(DRY 위반) |

출력 규정은 발견한 이슈마다 심각도(Critical / Major / Minor), 이슈 설명, 파일 위치(`file_path:line_number`), 권고 사항(구체적 코드 수정이나 해결 전략) 네 요소를 넣는 것이다. 문제가 없으면 "Review Passed"라고 답하고 점검한 주요 측면을 간단히 요약한다. 상세 심각도 기준은 reference/severity-guide.md를 보도록 안내한다.

이 스킬의 세 가지 설계 원칙은 읽기 전용 권한 보장(Read, Grep, Glob만 열어 리뷰 중 우발적 코드 수정을 원천 차단), 우선순위 순서 전략(보안 > 성능 > 품질), 구조화된 출력 규격(일관성과 추적성 보장)이다.

## 2. 작업 스킬 실습: 지능형 커밋(committing)

샤오빙은 하루에 열두 번 넘게 커밋하고, 커밋 메시지를 손으로 쓰는 일은 시간을 먹고 일관성도 없다. 이 작업은 Git 이력을 직접 바꾸는 부작용이 있으므로 사용자가 명시적으로 시작할 때만 실행하게 하고 자동 실행은 엄격히 금지한다.

```yaml
name: committing
description: Quickly perform a git commit with an auto-generated or user-specified message
argument-hint: "[optional: commit message]"
disable-model-invocation: true
allowed-tools:
- Bash(git status:*)
- Bash(git add:*)
- Bash(git commit:*)
- Bash(git diff:*)
model: haiku
```

본문은 네 부분이다.

- 입력 처리: `$ARGUMENTS`로 메시지가 오면 그것을 쓰고, 없으면 `git diff --staged`(스테이징된 게 없으면 `git diff`)로 변경을 분석해 간결한 메시지를 생성한다.
- 현재 상태 자동 감지: `!`command``로 `git status --short`와 `git diff --staged --stat`의 결과를 미리 주입한다(저장소가 아니거나 스테이징된 것이 없을 때의 대체 문구 포함).
- 절차: status 확인, 스테이징된 게 없으면 `git add .`, diff 검토, 적절한 메시지로 커밋, 간단한 확인 출력 순이다.
- 메시지 형식: feat, fix, docs, refactor, test, chore 같은 유형으로 시작하고 첫 줄은 최대 72자, 예는 `feat: add user authentication with JWT`다.

이 스킬은 여러 고급 기능이 통합된 모습이다. 책의 정리는 다음과 같다. disable-model-invocation: true는 모델 호출을 강제로 막아 사전 정의된 절차에만 의존하게 하고, `$ARGUMENTS`는 메시지를 직접 주거나 비워서 자동 생성을 유도하는 유연한 인자 전달을 맡는다. `!`command``는 실행 직전에 Git 상태를 주입해 추가 도구 호출 없이 변경 사항을 인지하게 한다. model: haiku는 커밋이 복잡한 추론보다 규칙 매칭에 가까운 일이므로 정확성을 유지하면서 지연과 자원 소비를 줄인다. 사용은 `/committing`(메시지 자동 생성) 또는 `/committing fix: resolve login validation bug`(메시지 지정)다.

## 3. 종합 스킬 실습: 재무 분석(financial-analyzing)

점진적 공개를 모두 활용하는 사례로, 층을 분리해 복잡한 작업을 효율적으로 관리한다.

| 층 | 파일 | 역할 |
|---|---|---|
| 제어 층 | SKILL.md | 의도 인식과 절차 라우팅 |
| 지식 층 | reference/revenue.md, costs.md, profitability.md | 공식, 업계 벤치마크, 평가 기준 같은 심층 도메인 지식 |
| 규격 층 | templates/analysis_report.md | 산출물 서식을 균일하게 하는 구조화된 템플릿 |
| 실행 층 | scripts/calculate_ratios.py | 정확한 재무 비율 계산. 환각(hallucination, 모델이 그럴듯하지만 틀린 값을 만들어 내는 현상) 위험 제거 |

SKILL.md의 구성은 이렇다. allowed-tools는 Read, Grep, Glob, `Bash(python:*)`이고, 본문에 Quick Reference 표, 4단계 분석 절차, 출력 지침이 들어간다. 절차는 질문 이해, 데이터 수집(사용자에게 요청하거나 제공된 파일에서 읽기), 지표 계산(유형별 reference 파일을 참조하고 `python scripts/calculate_ratios.py <data_file>`로 계산), 보고서 생성(templates/analysis_report.md 사용)이다. 출력 지침은 계산 과정을 항상 보여 줄 것, 각 지표의 의미를 쉬운 말로 설명할 것, 업계 벤치마크 같은 맥락을 줄 것, 실행 가능한 권고를 줄 것, 재무 데이터를 지어내지 말고 불완전하면 되물을 것이다.

이 SKILL.md는 약 200줄로 500줄 규칙을 충분히 지킨다. Claude가 "gross margin"을 식별하면 revenue나 costs 관련 파일을 불필요하게 로드하지 않고 곧장 profitability.md의 공식을 찾는다. 또 calculate_ratios.py가 결정적인 계산 로직을 캡슐화하므로 Claude는 오류 나기 쉬운 부동소수점 연산을 스스로 하지 않고 스크립트를 호출해 정확한 결과를 얻는다. 최소한의 토큰 투자로 최대한의 작업 품질을 얻는, 점진적 공개의 전형이다.

## 4. 네 가지 스킬 설계 패턴

실무에서 검증된 네 가지 패턴이다. 서로 배타적이지 않고 성숙한 스킬 시스템은 보통 여러 패턴을 조합한다.

| 패턴 | 핵심 | 적합한 경우 |
|---|---|---|
| 템플릿 주도 | 미리 정의된 템플릿으로 출력 형식을 엄격히 제약 | 주간 보고서, 장애 보고서, 리뷰 보고서처럼 표준화된 출력. 결과가 예측 가능하고 비교 가능하며 자동 후처리가 가능하다 |
| 스크립트 강화 | 결정적 계산 로직을 스크립트로 캡슐화해 Claude가 직접 도출하지 않고 호출 | 재무 계산, 정규식 매칭, 데이터 변환. 모델 추론보다 정확하고 토큰을 아끼며 재현성이 높다 |
| 지식 계층화 | 사용 빈도에 따라 지식을 층으로 조직(80/20 법칙) | 자주 쓰는 지식은 SKILL.md에 넣고 드문 지식은 참조 파일로 빼서 필요 시 로드. 점진적 공개를 패턴화한 것 |
| 도구 격리 | allowed-tools로 스킬의 능력 경계를 엄격히 정의 | 보안 설계. "무엇을 금지하는가"를 정하는 것이 "무엇을 허용하는가"보다 중요한 경우가 많다 |

스크립트 강화 패턴에는 경험칙이 붙는다. SKILL.md에 Claude가 계산할 공식을 쓰고 있다면 즉시 멈추고 그 로직을 스크립트로 옮기라는 것이다. 도구 격리 패턴에서는 리뷰형 스킬에 쓰기 권한을 주지 않고, 생성형 스킬에 수정 권한을 주지 않고, 테스트형 스킬이 소스 코드를 수정하는 것을 엄격히 금한다.

## 5. 스킬은 살아 있는 문서다: 테스트와 개선

"스킬을 쓰면 끝인가요?"라는 샤오빙의 질문에 카게는 아니라고 답한다. 책은 공식 사이트가 권하는 세 가지 테스트를 소개한다.

- 트리거 테스트: 트리거되어야 할 질문 10개와 되지 말아야 할 질문 10개로 판단 정확도를 검증한다. 관련 작업 트리거율 90% 초과, 무관 작업 오트리거율 5% 미만이 목표다.
- 기능 테스트: 스킬이 로드된 뒤의 실행 품질을 본다. 출력 형식이 기대와 맞는지, 체크리스트 항목을 모두 다루는지, 경계 사례가 제대로 처리되는지가 체크포인트다.
- 성능 비교: 같은 작업을 "스킬 있음"과 "스킬 없음"에서 각 5회 실행해 토큰 소비, 사용자 수정 횟수, 최종 품질을 비교한다.

Claude의 출력을 손으로 반복해서 고치고 있다면(예: 늘 "인증 요건 표시를 잊지 마"라고 일러 줘야 한다면) SKILL.md 본문을 갱신하라는 분명한 신호다. 교정 논리를 SKILL.md에 직접 쓰면 같은 오류가 재발하지 않는다. 이 과정은 전통적인 버그 수정 루프와 같다. 문제 발견, 원인 파악(설명이 부정확한가, 단계가 빠졌는가, 형식 정의가 모호한가), 문서 수정, 효과 검증이다.

Claude Code에는 skill-creator라는 전용 스킬도 있어 자연어 설명으로 SKILL.md 초안을 만들어 준다. 예시 지시는 "Use the skill-creator skill to help me build a skill for [your use case]"이다. 책은 이 도구의 존재 자체가 스킬 시스템이 스킬로 새 스킬을 만드는 "부트스트래핑"이 가능할 만큼 성숙했다는 증거라고 말한다.

## 6. 소프트웨어 공학 관점

책은 스킬이 서브에이전트처럼 새로운 개념이지만, 본질은 소프트웨어 공학의 오래 검증된 지혜를 AI 에이전트의 지식 아키텍처로 옮겨 적용한 것이라고 말한다.

| 원칙 | 스킬에서의 모습 |
|---|---|
| 관심사 분리 | 문제 해결 방법과 경험을 재사용 가능한 구조화 자산으로 증류한다. CLAUDE.md는 전역 규칙, 스킬은 전문 워크플로, 서브에이전트는 작업 실행(동적 계획과 실시간 작업)을 맡는다. 모든 로직을 CLAUDE.md에 넣는 것은 main 함수에 코드를 전부 쓰는 것과 같아 컨텍스트 중복, 유지보수 곤란, 확장성 저하를 낳는다 |
| 의존성 역전 | 구현이 아니라 인터페이스에 맞춰 프로그래밍한다. Claude는 스킬 내부(스크립트, 프롬프트 세부)가 아니라 추상 인터페이스(description과 출력 계약)에 의존한다. 계약이 같으면 내부를 언제든 교체, 리팩터링, 업그레이드할 수 있고 결합도가 크게 낮아진다 |
| 캐시 최적화와 지연 로딩 | 점진적 공개는 전형적인 지연 로딩(lazy loading)이다. 시작할 때 모든 지식을 미리 올리지 않고 특정 스킬이 처음 필요할 때 관련 자원을 올린다. 웹의 코드 분할이나 데이터베이스의 지연 로딩과 같다 |
| 최소 권한 원칙 | allowed-tools는 고전 보안 원칙을 AI 영역에 옮긴 것이다. 리눅스의 chmod, AWS의 IAM 정책처럼 책임을 다하는 데 딱 필요한 권한만 준다. "할 수 없는 일"을 정의하는 것이 악성 코드나 환각으로 인한 월권을 막는 데 더 효과적이다 |
| 개방형 표준 | 선언적이고, 자기완결적이며, 지식 중심이다 |

개방형 표준 항목은 부연이 필요하다. 이 사양은 2025년 12월 18일 개방형 표준으로 공개되었고, 이후 OpenAI Codex CLI, Google Gemini CLI, Cursor, GitHub Copilot을 비롯한 수십 개 에이전트 플랫폼이 채택해 2026년 중반 기준 약 40개 호환 제품이 있다. 책은 이 개수를 고정값이 아니라 해당 시점의 수치로 보라고 한다. 성공의 세 속성은 다음과 같다.

- 선언적: 순수 마크다운 형식이라 어떤 대형 모델도 읽고 이해하며, 블랙박스 바이너리가 없다.
- 자기완결적: 필요한 구성 요소가 폴더 하나에 모두 들어 있어 복사만 하면 설치되고 복잡한 의존성 관리가 필요 없다.
- 지식 중심: 핵심 가치는 특정 형식이 아니라 내용에 있으며 하나의 플랫폼에 묶이지 않는다.

그래서 Claude Code에서 잘 설계한 스킬은 이론상 이 표준을 지원하는 어떤 AI 플랫폼으로도 옮겨 갈 수 있다("write once, run anywhere"). 책은 이것이 단순한 제품 기능이 아니라 업계 표준의 이야기이며, 독자가 배우는 것은 Claude Code의 기능 설정법을 넘어 AI 에이전트 생태계를 위한 표준화된 지식 패키지를 만드는 법이라고 맺는다.

## 7. 핵심 정리

- 참조 스킬(code-reviewing)은 읽기 전용 권한과 우선순위, 출력 규격으로, 작업 스킬(committing)은 자동 호출 금지, 인자, 사전 주입, 가벼운 모델로, 종합 스킬(financial-analyzing)은 제어, 지식, 규격, 실행 4개 층으로 설계한다.
- 설계 패턴은 템플릿 주도, 스크립트 강화, 지식 계층화, 도구 격리 네 가지이며 조합해서 쓴다.
- 스킬은 트리거, 기능, 성능 비교로 테스트하고, 반복되는 수정은 SKILL.md에 반영한다.
- 스킬의 뼈대에는 관심사 분리, 의존성 역전, 지연 로딩, 최소 권한, 개방형 표준이라는 공학 원칙이 깔려 있다.
