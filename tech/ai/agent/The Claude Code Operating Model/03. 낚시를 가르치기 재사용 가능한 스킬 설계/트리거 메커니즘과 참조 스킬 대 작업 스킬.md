# 트리거 메커니즘과 참조 스킬 대 작업 스킬

책은 스킬 트리거 메커니즘을 시스템 전체에서 가장 깊이 이해해야 할 부분이라고 못 박는다. 제때 활성화되지 못하면 아무리 훌륭한 내용도 쓸모가 없으므로, 트리거는 내용의 품질보다 더 중요하다는 주장이다.

이 문서는 스킬이 불려 나오는 두 경로, 그 열쇠인 description을 쓰는 법, 과소 트리거와 과다 트리거를 다루는 법, 그리고 disable-model-invocation 하나로 갈리는 두 가지 스킬 철학(참조 스킬과 작업 스킬)을 정리한다.

---

## 1. 이중 채널 활성화

스킬마다 활성화 경로가 두 개 있다.

- 명시적 호출: 사용자가 대화에 `/skill-name`을 입력하면 Claude Code가 즉시 해당 스킬을 로드해 실행한다. 터미널 명령처럼 명확하고 모호함이 없다. 스킬이 argument-hint를 정의했다면 `/commit fix login bug`나 `/review src/auth/login.ts`처럼 인자도 줄 수 있다.
- 의미 매칭: Claude가 사용자 의도를 이해한 뒤 현재 작업에 가장 알맞은 스킬을 스스로 판단해 자동으로 로드한다. 일상 사용에서 스킬의 핵심 가치는 여기에 있다. 사용자는 필요를 말하기만 하고, 어떤 스킬을 어떻게 쓸지는 Claude가 뒤에서 결정한다.

## 2. description이 스킬의 영혼인 이유

의미 매칭은 전적으로 description 필드에 의존한다. 이 필드는 사람이 읽는 설명이 아니라 Claude가 특정 스킬을 호출할지 판단하는 유일한 신호다. 권장 공식은 다음과 같다.

> [기능 정의](무엇을 하는가) + [트리거 상황](언제 쓰는가) + [핵심 능력](무엇을 할 수 있는가)

### 2-1. 나쁜 예와 좋은 예

| 유형 | 예(원문의 영어 표현) | 문제 |
|---|---|---|
| 너무 모호함 | Helps with projects. | 언제 쓸지 판단할 수 없다 |
| 지나치게 기술적 | Implements the Project entity model with hierarchical relationships. | 사용자 관점의 트리거 단어가 없다 |
| 기능만 서술 | Generates API documentation. | 트리거 상황이 없다 |

좋은 예는 이런 모양이다. 명확한 진술, 구체적 트리거 상황, 핵심 능력 세부 내용이 모두 들어 있다.

```yaml
description: Generate API documentation from Express, FastAPI, or Spring Boot source code.
  Use when user asks to "write API docs", "document endpoints", "create OpenAPI specs",
  or mentions "Swagger". Supports route detection, request/response schema extraction,
  and authentication requirement marking.
```

### 2-2. 쓰는 3단계

description은 1,024자 제한이 있어 단어를 신중히 골라야 한다. 책이 제시하는 효율적인 전략은 세 단계다.

1. 핵심 능력(What)을 한 문장으로 요약한다.
2. 트리거 상황(When)을 "Use when user..." 문형으로 나열한다. 사용자가 쓸 법한 명령, 구절, 키워드를 상세히 적을수록 의미 매칭 적중률이 오른다.
3. 제외 조건(Not For)을 정의한다. 선택 사항이지만, 잘못 트리거되기 쉬운 스킬이라면 "Not for..." 절로 쓰지 말아야 할 상황을 분명히 한다.

Kage의 메모에 따르면 description의 주 독자는 사람이 아니라 Claude다. 사람은 제목을 훑고 구조를 탐색하지만 Claude는 깊은 의미 매칭을 하며 사용자 의도의 미묘한 차이를 포착해야 한다. 그래서 가능한 모든 사용자 표현을 빠짐없이 넣어야 한다. "API 문서 생성" 하나에도 "generate API docs", "write interface documentation", "output OpenAPI specs", "help me write a Swagger"처럼 말이 다양하며, 동의어 집합이 풍부할수록 매칭 범위가 넓어지고 정확도가 오른다.

## 3. 과소 트리거와 과다 트리거

트리거 실패는 두 가지 전형적인 모습으로 나타난다.

| 구분 | 현상 | 원인 | 처방 |
|---|---|---|---|
| 과소 트리거 | 호출되어야 할 스킬이 호출되지 않음 | description이 지나치게 기술적, 학술적이어서 사용자의 자연스러운 구어체와 의미 간극이 큼 | 사용자 언어로 "번역"한다. 도메인 용어의 동의어, 구어체, 흔한 부정확한 표현도 추가한다(Swagger와 OpenAPI를 혼동하는 사용자가 많으니 둘 다 넣는다) |
| 과다 트리거 | 호출하면 안 되는 상황에서 활성화됨 | description이 너무 넓고 흔한 일반 용어가 많아 매칭 문턱이 낮음 | 부정 제약을 도입한다. "Not for..." 문형으로 경계를 정한다. 예: "Not for general code questions or debugging. Only for structured documentation generation." |

과소 트리거의 근거로 책은 Vercel의 Next.js 16 평가를 인용한다. 에이전트에게 명시적 안내를 주지 않았을 때, 평가 대상이던 단일 스킬이 56%의 경우에 호출되지 않았다(Vercel Engineering, "AGENTS.md outperforms skills in our agent evals"). 책은 이 결과가 그 평가와 하나의 스킬에 한정된 것이라고 단서를 단다. 모든 상황의 확률이 아니라 스킬 발견의 어려움에 대한 경고로 읽으라는 뜻이다.

### 3-1. 트리거 검증 세트

정확히 트리거되는지 확인하려면 "트리거되어야 할 것"과 "트리거되지 말아야 할 것"을 아우르는 10~20개 검증 사례를 만든다. 책의 템플릿 예시는 다음과 같다.

- 트리거되어야 함: "src/api/의 인터페이스 문서를 만들어 줘", "OpenAPI 명세를 써 줘", "REST 엔드포인트를 문서화해 줘", "Swagger를 써 줘".
- 트리거되지 말아야 함: "이 API 호출을 디버깅해 줘", "이 엔드포인트가 왜 500을 반환하지?", "이 API 성능을 최적화해 줘".
- 합격 기준: 관련 작업의 트리거율 90% 이상, 무관한 작업의 오트리거율 5% 미만.

## 4. 참조 스킬 대 작업 스킬

disable-model-invocation은 단순한 스위치가 아니라 두 가지 근본적으로 다른 상호작용 방식을 정의한다.

### 4-1. 참조 스킬(Reference Skills)

- 설정: 기본 동작이다.
- 핵심 논리: "온디맨드 지식 베이스". Claude가 대화 맥락에 따라 이 스킬이 필요한지 자동 판단한다. description이 트리거 조건으로서 Claude의 컨텍스트에 직접 주입되어 의미 매칭에 쓰인다.
- 용도: 지식, 지침, 프레임워크, 표준을 제공한다. 사용자는 스킬의 존재를 알 필요가 없고, Claude가 알맞은 때 알아서 "매뉴얼을 펼친다".
- 예: API 설계 지침, 코드 리뷰 체크리스트, 업계 표준 문서.

### 4-2. 작업 스킬(Task Skills)

- 설정: disable-model-invocation: true를 명시한다.
- 핵심 논리: "통제된 실행 도구". Claude가 자동으로 트리거할 수 없고 사용자가 `/skill-name`으로 수동 호출해야 한다. description은 Claude의 컨텍스트에 주입되지 않고, 명령줄에서 스킬을 고를 때 사용자가 식별하는 용도로만 쓰인다.
- 용도: 사용자의 명시적 승인이 필요한 부작용 있는 작업.
- 예: `/commit`(코드 커밋), `/deploy`(애플리케이션 배포), `/notify`(알림 발송).

| 차원 | 참조 스킬 | 작업 스킬 |
|---|---|---|
| Claude 자동 트리거 | 가능(의미 매칭) | 불가(수동 호출만) |
| 사용자의 이름 호출 | 가능 | 가능 |
| description의 기능 | 트리거 조건(Claude 컨텍스트에 주입) | 사용자 식별용(주입되지 않음) |
| 토큰 예산 소비 | 있음(자동 로드 시 소비) | 없음(수동 호출 때만 소비) |
| 전형적 장면 | 지식 제공, 표준 조회 | 행동 실행, 부작용 있는 작업 |
| 대표 사례 | API 표준, 리뷰 체크리스트 | /commit, /deploy |

### 4-3. 부작용이란

Kage의 메모는 여기서 말하는 부작용이 약의 부작용이 아니라고 짚는다. 소프트웨어 공학에서 부작용(side effect)은 결과를 돌려주는 데서 그치지 않고 시스템의 외부 상태까지 바꾸는 동작이다. 코드를 커밋하면 Git 저장소 이력이 바뀌고, 앱을 배포하면 운영 서비스 상태가 바뀌고, 알림을 보내면 실제로 누군가에게 메시지가 전달된다. 이런 동작은 실행되는 순간 현실에 영향을 주며 대개 되돌릴 수 없다. 그래서 이런 스킬은 모델이 스스로 실행 시점을 정하게 하지 않고 사용자의 명시적 개시를 요구하도록 설계한다.

## 5. 어느 쪽으로 설계할지 정하는 "최악의 경우 테스트"

샤오빙이 "작업을 참조 스킬로 만들어야 할지 작업 스킬로 만들어야 할지" 묻자 카게는 간단한 기준을 준다. "Claude가 이 작업을 자동으로 실행하면 최악의 경우 무슨 일이 생기는가?"

- 답이 불안하게 만든다면 작업 스킬을 택하고 disable-model-invocation: true를 붙인다. 불안한 사례로는 테스트하지 않은 코드를 자동 커밋하는 것, 버그 있는 버전을 자동 배포하는 것, 운영 데이터를 자동 삭제하는 것, 틀린 알림을 자동 발송하는 것이 있다. 통제권을 사용자에게 두고, 사용자가 `/skill-name`을 입력했을 때만 실행되게 한다.
- 답이 대수롭지 않다면(참조 문서를 하나 더 보여 주거나, 제안을 하나 더 하거나, 토큰 소비가 조금 늘어나는 정도) 참조 스킬로 둔다. 맥락에 맞게 Claude가 알아서 로드하게 한다.

핵심 원칙은 "부작용이 클수록 통제는 더 엄격해야 한다"이다. 시스템 상태를 바꾸거나 되돌릴 수 없는 결과를 낳을 수 있는 작업에서는 Claude의 자동 판단을 믿어서는 안 된다.

## 6. 핵심 정리

- 활성화 경로는 명시적 호출(`/skill-name`)과 의미 매칭 두 가지이고, 후자는 description에만 의존한다.
- description은 기능, "Use when..." 트리거 문구, 핵심 능력, 선택적 "Not for..." 제외 조건으로 쓴다.
- 과소 트리거는 사용자 표현을 늘려, 과다 트리거는 부정 제약을 넣어 고친다. 검증 세트는 10~20개, 기준은 트리거율 90% 이상과 오트리거율 5% 미만이다.
- 참조 스킬은 자동 로드되는 지식, 작업 스킬은 사용자만 실행하는 통제된 행동이다.
- "자동 실행되면 최악의 경우 어떻게 되나"에 대한 답이 불안하면 작업 스킬로 만든다.
