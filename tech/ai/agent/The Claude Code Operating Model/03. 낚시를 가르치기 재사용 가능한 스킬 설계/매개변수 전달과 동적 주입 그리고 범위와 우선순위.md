# 매개변수 전달과 동적 주입, 범위와 우선순위

스킬은 고정된 지침서에 그치지 않는다. 실행할 때 인자를 받아 쓰고, 실행 직전에 현재 상태를 읽어 와 프롬프트에 끼워 넣을 수도 있다. 또 스킬 파일은 기업, 개인, 프로젝트, 플러그인(plugin, 스킬과 확장을 묶어 배포하는 꾸러미) 같은 여러 층에 둘 수 있고, 이름이 겹치면 우선순위 규칙이 적용된다.

이 문서는 세 가지를 다룬다. `$ARGUMENTS`로 받는 매개변수, `!`command`` 구문으로 하는 동적 컨텍스트 주입과 그 보안 주의점, 그리고 스킬의 저장 위치별 범위와 우선순위다.

---

## 1. $ARGUMENTS와 위치 매개변수

사용자가 `/skill-name arg1 arg2`로 스킬을 호출하면 SKILL.md 본문에서 다음 변수를 쓸 수 있다.

| 변수 | 의미 |
|---|---|
| $ARGUMENTS | 모든 인자를 이은 전체 문자열 |
| $ARGUMENTS[0], $ARGUMENTS[1] | 첫 번째, 두 번째 인자(인덱스는 0부터) |
| $0, $1, $2 | 위치 매개변수의 줄임 표기 |

책의 예는 컴포넌트를 한 프레임워크에서 다른 프레임워크로 옮기는 스킬이다.

```yaml
---
name: migrate-component
description: Migrate a component between frameworks
argument-hint: "[component] [from] [to]"
disable-model-invocation: true
---
Migrate the $0 component from $1 to $2.
Preserve all existing behavior and tests.
```

`/migrate-component SearchBar React Vue`를 실행하면 Claude가 실제로 받는 지시는 "SearchBar 컴포넌트를 React에서 Vue로 마이그레이션하라. 기존 동작과 테스트를 모두 보존하라."가 된다.

## 2. 동적 컨텍스트 주입

책은 이것을 스킬 시스템에서 가장 강력하고 독특한 기능이라고 부른다. `!`command`` 구문을 쓰면 SKILL.md가 Claude에게 보내지기 전에 지정한 명령을 셸 환경에서 실행하고, 그 출력을 프롬프트 안에 그대로 끼워 넣는다. 참고로 이 구문의 백틱은 마크다운 서식이 아니라 문법의 일부이므로 SKILL.md 안에 글자 그대로 입력해야 한다(책 3장 뒤쪽의 설명이다).

### 2-1. 동작 예시

SKILL.md에 이렇게 적었다고 하자.

```markdown
Current branch:
!`git branch --show-current`
Recent commits:
!`git log origin/main..HEAD --oneline 2>/dev/null || echo "No commits"`
```

`/pr-create "Add auth"`를 실행하면 명령이 이미 실행되어 Claude가 받는 프롬프트는 이런 모습이 된다. 현재 브랜치 자리에는 feature/auth가, 최근 커밋 자리에는 "a1b2c3d Add JWT middleware", "d4e5f6g Add login endpoint"가 들어가고, 변경된 파일 통계 자리에도 실제 diff 요약이 채워진다. 책의 예에서는 src/auth/middleware.ts와 src/auth/login.ts 두 파일에 127줄이 추가된 것으로 나온다.

### 2-2. 공학적 가치

책은 이 기능이 있을 때와 없을 때를 비교한다(책 표 3.7, 본문에서는 번호가 3.6으로 겹쳐 인쇄되어 있다).

| 차원 | 없을 때 | 있을 때 |
|---|---|---|
| Claude 시작 컨텍스트 | 비어 있어 여러 턴 탐색이 필요 | 핵심 정보가 미리 주입됨 |
| 첫 응답의 도구 호출 수 | 3~5회(정보 수집용) | 0~1회(바로 행동) |
| 토큰 소비 | 높음 | 낮음 |
| 응답 속도 | 느림 | 빠름 |
| 결과 일관성 | 낮음(정보 누락 위험) | 높음(같은 정보가 고정 주입됨) |

### 2-3. 실행 경계: 셸 주입 주의

Kage의 메모는 실행 순서를 못 박는다. 먼저 `$ARGUMENTS` 변수를 치환하고 그다음에 셸 명령을 실행한다. 사용자 입력이 셸 명령에 그대로 이어 붙는다는 뜻이므로, 적절한 통제가 없으면 셸 주입(shell injection, 입력 문자열에 섞인 명령이 그대로 실행되는 공격) 공격으로 이어지기 쉽다. 그래서 `!`command``를 쓰는 모든 스킬은 allowed-tools로 실행 가능한 명령 범위를 엄격히 제한해 보안 경계를 세워야 한다.

## 3. 스킬의 범위: 어디에 두는가

스킬 파일은 위치에 따라 영향 범위와 적합한 용도가 다르다.

| 저장 위치 | 영향 범위 | 대표 용도 |
|---|---|---|
| 기업 설정 센터 | 모든 구성원 | 기업 차원의 필수 개발 표준과 보안 정책 |
| `~/.claude/skills/<name>/` | 개인의 모든 프로젝트 | 개인 코딩 습관, 범용 도구 모음, 프로젝트 공통 보조 스크립트 |
| `<project>/.claude/skills/<name>/` | 현재 프로젝트만 | 프로젝트 고유 워크플로, 비즈니스 로직 맞춤, 팀 협업 규범 |
| 플러그인 내장 자원 | 플러그인이 활성화되었을 때 | 커뮤니티가 공유한 능력 팩, 특정 프레임워크 전용 지침 모음 |

## 4. 같은 이름의 우선순위

여러 출처에 같은 이름의 스킬이 있으면 시스템은 우선순위 내림차순으로 파싱하고 로드한다.

> 기업 정책 > 개인 설정(~/.claude/) > 프로젝트 설정(.claude/) > 플러그인 내장

이 순서는 기업 거버넌스 구조를 그대로 따라 "강제 기준선"에서 "개인 취향"으로 질서 있게 넘어가게 한다. 책은 각 층의 성격을 다음처럼 설명한다.

- 기업 정책(깰 수 없는 기준선): 최고 권한을 가지며 전사 보안과 규정 준수를 강제한다. 예를 들어 보안 리뷰 스킬은 OWASP Top 10 취약점 점검을 반드시 수행해야 하고, 이런 핵심 규칙은 프로젝트나 개인 설정이 덮어쓸 수 없어야 조직의 보안 레드라인이 지켜진다.
- 개인 설정(개인화된 효율 도구): 개발자 개인의 습관에 맞춘다. 예를 들어 `/commit` 명령을 정의해 conventional commit 규칙에 따라 커밋 메시지를 자동 생성할 수 있다. 개인 환경에만 적용되고 남에게 영향을 주지 않는다.
- 프로젝트 설정(업무 시나리오 맞춤): 특정 코드베이스에 맞춘다. 예를 들어 프런트엔드 프로젝트가 자기 기술 스택과 문서 구조에 맞는 컴포넌트 문서 생성 스킬을 따로 정의할 수 있다.

### 4-1. 프로젝트 스킬을 Git에 포함하기

책은 프로젝트의 `.claude/skills/` 디렉터리를 Git 버전 관리에 포함하는 것이 비용 없이 팀 지식을 공유하는 최적의 방법이라고 한다.

- 꽂으면 바로 동작: 새 팀원이 저장소를 클론하면 관련 스킬이 자동으로 활성화된다. 수동 설치나 설정이 필요 없다.
- 함께 진화: 프로젝트가 반복되면서 스킬 라이브러리도 코드와 함께 갱신되어 팀이 항상 최신 워크플로 표준을 쓴다.

## 5. 핵심 정리

- 인자는 `$ARGUMENTS`, `$ARGUMENTS[n]`, `$0`~`$2`로 받는다. `argument-hint`는 `/` 메뉴 안내용이다.
- `!`command``는 Claude가 보기 전에 셸 명령을 실행해 출력을 프롬프트에 넣어, 첫 응답의 도구 호출을 3~5회에서 0~1회로 줄인다.
- 인자 치환이 먼저이고 셸 실행이 나중이므로 셸 주입에 주의하고 allowed-tools로 명령 범위를 제한한다.
- 스킬은 기업, 개인, 프로젝트, 플러그인 층에 둘 수 있고, 같은 이름이면 기업 > 개인 > 프로젝트 > 플러그인 순으로 우선한다.
- 프로젝트 스킬을 Git에 넣으면 팀 공유가 공짜로 된다.
