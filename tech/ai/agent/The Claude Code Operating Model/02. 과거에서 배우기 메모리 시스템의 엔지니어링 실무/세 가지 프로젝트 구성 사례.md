# 세 가지 프로젝트 구성 사례

이론을 실제 CLAUDE.md로 엮어 보는 단계다. 원서는 세 가지 전형적 프로젝트, 곧 React 프런트엔드, Node.js 백엔드, Python 데이터 프로젝트의 예시를 든다. 세 파일은 강조점이 다르다. 프런트엔드는 컴포넌트 규약과 상태 관리 전략, 백엔드는 계층형 아키텍처 설계와 API 규약, 데이터 프로젝트는 데이터 처리 흐름의 엄밀함과 실험의 재현성 기준이다.

이 차이는 우연이 아니라 기술 영역마다 '가장 자주 틀리는 지점'의 분포가 다르다는 사실을 반영한다. 좋은 CLAUDE.md는 정밀 유도 무기처럼 문제가 생기기 쉬운 핵심 영역에 화력을 집중해야 한다.

---

## 1. React 프런트엔드 프로젝트

React 프런트엔드에서는 컴포넌트 입도, 상태의 소유권, 스타일링 방식 선택이 의견 충돌의 온상이고, Claude가 가장 '주도적으로' 나서서 코드 스타일을 조각내기 쉬운 곳이다. 상태 관리 전략을 명시하지 않으면 한 프로젝트 안에서 Redux, Context API, 로컬 상태를 뒤섞어 아키텍처가 혼란에 빠질 가능성이 높다.

원서 예시(전자상거래 플랫폼 프런트엔드)의 구성은 다음과 같다.

| 절 | 내용 |
|---|---|
| Tech Stack | React 18 + TypeScript(strict), Vite 5 + pnpm, 서버 상태는 TanStack Query(React Query), 전역 클라이언트 상태는 Zustand, 스타일은 Tailwind CSS(CSS Modules와 styled-components 엄금) |
| Component Guidelines | 함수 컴포넌트 + Hooks만(클래스 컴포넌트 금지), 파일명은 PascalCase(`ProductCard.tsx`), props 타입은 컴포넌트명 + Props(`ProductCardProps`), 공용 UI 원자 컴포넌트는 `src/components/ui/`, 비즈니스 도메인 컴포넌트는 `src/components/features/` |
| State Management Decision Tree | 서버 데이터(API 응답, 캐싱, 동기화)는 TanStack Query, 전역 클라이언트 상태(테마 전환, 로그인 상태, 임시 장바구니)는 Zustand, 컴포넌트 지역 상태(폼 입력값, 드롭다운 펼침, 모달 표시)는 `useState` |
| Common Commands | `pnpm dev`(5173 포트), `pnpm build`, `pnpm test`(vitest), `pnpm lint`(ESLint) |

'상태 관리 결정 트리' 절에 주목해야 한다. 기술 스택 이름을 나열하는 데 그치지 않고 '시나리오에서 도구로의 매핑 논리'를 만들었다. 이런 '결정 지침'은 단순한 도구 목록보다 훨씬 효과적이다. 구체적 문제를 만났을 때 '어느 열쇠를 골라야 하는지'를 Claude에게 직접 알려 주어 아키텍처 스타일의 표류를 처음부터 막는다.

## 2. Node.js 백엔드 프로젝트

백엔드 프로젝트의 생명줄은 계층형 아키텍처에서 책임 경계가 분명한 것과 데이터 형식의 통일이다. 백엔드 코드의 '옳음'은 각 계층이 의존성 규칙을 엄격히 지키는지에 달려 있다. 라우트 계층이 서비스와 리포지터리를 건너뛰고 Prisma를 직접 부르면 비즈니스 로직이 인프라 계층으로 새어 훗날 유지보수 수렁이 된다.

원서 예시(주문 마이크로서비스)는 다음과 같다.

| 절 | 내용 |
|---|---|
| Technology Stack | Node.js 20 + TypeScript 5.3, Fastify 4(Express 엄금), Prisma ORM + PostgreSQL 15, 도구 체인은 pnpm과 Zod |
| Layered Architecture(엄격한 단방향 의존) | `routes/`는 요청 파라미터 파싱, 입력 검증, 컨트롤러 호출, HTTP 응답 구성. `controllers/`는 서비스 호출 조율, HTTP 의미 처리, 예외 포착과 변환. `services/`는 핵심 비즈니스 규칙, 트랜잭션 관리, 여러 리포지터리 조율. `repositories/`는 Prisma 쿼리와 데이터 매핑을 캡슐화하며 다른 계층의 Prisma 직접 호출은 엄금 |
| API Response Standards | 모든 엔드포인트가 `{ success, data?, error?: { code, message } }` 형식을 반환. 페이징은 `page`(1부터), `limit`(기본 20, 최대 100). 오류 코드는 UPPER_SNAKE_CASE |
| Common Commands | `pnpm dev`(3000), `pnpm test`, `pnpm build`(tsc), `pnpm db:migrate`, `pnpm db:studio`(Prisma Studio) |

이 설정에서 가장 핵심인 규칙은 '다른 계층에서 Prisma를 직접 호출하는 것을 엄금한다'이다. 단순한 코딩 스타일 취향이 아니라 프로젝트의 유지보수성과 수명을 좌우하는 침범 불가의 아키텍처 원칙이다.

## 3. Python 데이터 프로젝트

Python 데이터 프로젝트는 웹 개발과 근본적으로 다른 풍경이다. Claude가 데이터 과학 분야의 엔지니어링 관례에 익숙하지 않으면 모범 사례를 어기는 코드를 만들기 쉽다. 예를 들어 `inplace=True`를 남용해 DataFrame을 제자리에서 바꾸면 데이터 흐름의 추적 가능성이 무너지고, `None`과 `pd.NA`를 섞어 쓰면 결측치 처리 논리가 혼란스러워진다.

원서 예시(사용자 행동 분석 시스템)는 다음과 같다.

| 절 | 내용 |
|---|---|
| Tech Stack | Python 3.11 + uv(의존성과 가상환경 관리), pandas 2.x, scikit-learn, matplotlib + seaborn, 타입 힌트는 `typing` 모듈을 엄격히, docstring은 Google Style 필수 |
| Project Structure | `notebooks/`(탐색적 분석, 이름 형식 "번호-설명.ipynb" 예: `01-data-exploration.ipynb`), `src/data/`(로딩, 정제, 파이프라인), `src/features/`(피처 엔지니어링), `src/models/`(모델 정의, 학습, 평가 지표), `tests/`(pytest) |
| Data Processing Conventions | 결측치는 `pd.NA`만 쓰고 `None`이나 맨 `np.nan` 금지. 날짜 열은 항상 `datetime64`로 변환하고 출력과 저장 형식은 YYYY-MM-DD. 카디널리티가 낮은 범주형 변수는 `category` 타입으로 명시 변환. `inplace=True` 금지, 모든 변환 연산은 새 DataFrame 복사본을 반환 |
| Common Commands | `uv sync`, `uv run pytest`, `uv run jupyter lab`, `uv run python -m src.train` |

## 4. Kage의 총평: 한 줄 한 줄이 알짜

세 파일은 각각 20~30줄밖에 안 되지만 모든 줄이 알맹이다. React가 무엇인지, Python의 들여쓰기 규칙이 어떤지처럼 Claude가 이미 잘 아는 일반 지식은 버리고, 해당 영역과 이 프로젝트만의 고유한 관례와 결정에 정밀하게 집중한다.

여기서 CLAUDE.md 작성의 핵심 규칙이 나온다. Claude가 반드시 알아야 하지만 스스로 추론할 수 없는 핵심 정보만 기록한다. 책이 강조하는 황금 시험은 이것이다. 어떤 규칙을 지워도 Claude가 올바르게 행동한다면 그 규칙은 CLAUDE.md에 속하지 않는다.

| 확인 항목 | 질문 |
|---|---|
| 일반 지식인가 | Claude가 이미 아는 내용이면 뺀다 |
| 추론 가능한가 | 코드나 설정 파일에서 스스로 알아낼 수 있으면 뺀다 |
| 결정 지침인가 | '시나리오에서 도구로' 연결하는 결정 트리는 넣는다 |
| 영역 특유의 함정인가 | 그 영역에서 Claude가 흔히 어기는 지점(예: `inplace=True`)을 겨냥한다 |

참고(노트 작성자): 위 표의 네 항목은 책이 든 사례를 점검 질문으로 다시 정리한 것이며 원서에 이런 표가 있는 것은 아니다.
