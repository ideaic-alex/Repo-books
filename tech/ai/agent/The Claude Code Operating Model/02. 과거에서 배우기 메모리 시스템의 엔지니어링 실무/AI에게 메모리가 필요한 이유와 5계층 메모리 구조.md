# AI에게 메모리가 필요한 이유와 5계층 메모리 구조

2장은 Xiaobing이 주문 서비스 프로젝트에서 처음 로그인 API를 부탁하는 장면으로 시작한다. Claude는 Express 기반의 JavaScript 코드에 `npm install`까지 곁들여 한 번에 내놓았다. 그녀가 "우리는 Fastify와 TypeScript를 쓴다"고 바로잡아 원하는 코드를 얻었지만, 다음 날 새 세션에서 주문 생성 API를 부탁하자 프레임워크는 다시 Express, 패키지 관리자는 다시 npm이었고 디렉터리 구조마저 팀 규약과 달랐다.

이 문서는 그 'AI 건망증'의 정체와, 해법인 CLAUDE.md가 어디에 놓이고 어떻게 겹쳐 쌓이는지를 다룬다. 비유는 회사 규정 문서의 계층이다.

---

## 1. AI에게 메모리가 필요한 이유

### 1-1. 매 대화는 '입사 첫날'

Kage는 입사 첫날을 떠올려 보라고 한다. 저장소가 어디인지, 브랜치 전략이 무엇인지, CI는 어떻게 도는지 모두 동료에게 물어야 했다. 그런데 매일 아침 어제 배운 것을 전부 잊고 다시 첫날이 된다면 어떨까. Claude가 바로 그 처지다. 매 대화가 '입사 첫날'이어서, 기술력은 있는 신입이 회사의 기술 스택을 모른 채 개인 경험과 업계 관례로 짐작하는 셈이다. 짐작은 논리적일 수 있어도 정확하다는 보장이 없다.

이것은 대형 모델의 근본 특성이다. 세션 사이에 지속되는 상태가 없다. 세션을 닫고 새로 열면 모델 앞에는 백지가 놓인다. 프로젝트의 프레임워크도, 팀의 코드 스타일도, 5분 전에 고쳐 준 실수도 기억하지 못한다. 특정 모델의 결함이 아니라 현재 모든 대형 모델의 공통 성질이다.

### 1-2. Claude의 기본값은 훈련 데이터에서 온다

소프트웨어 공학에는 '설정보다 관례(Convention over Configuration)' 원칙이 있다. Ruby on Rails가 높은 생산성을 주는 이유는 합리적인 기본값 덕분이다. 테이블 이름은 복수형, 모델 이름은 단수형, 컨트롤러는 `app/controllers`에 둔다는 식이라 개발자는 관례에서 벗어나는 예외만 신경 쓰면 된다.

그런데 Claude의 기본 '관례'는 프로젝트 표준이 아니라 훈련 데이터, 곧 인터넷에 공개된 모든 코드의 통계 패턴에서 온다. 그 분포에서는 Express가 Fastify보다, npm이 pnpm보다, JavaScript 샘플이 TypeScript보다 많다. 그래서 구체적 맥락이 없으면 가장 '주류'인 해법으로 쏠린다. 일반 상황에서는 합리적이어도 특정 팀 표준에는 맞지 않을 수 있다. 책의 결론은 한 줄이다. Claude에게 부족한 것은 능력이 아니라 맥락이다.

### 1-3. 해법: 입사 안내서 CLAUDE.md

매 대화가 입사 첫날이라면 시작할 때마다 자동으로 읽게 할 '입사 안내서'를 준비하면 된다. 그것이 CLAUDE.md다. 평범한 마크다운 텍스트 파일을 정해진 프로젝트 디렉터리에 두면 Claude Code가 시작할 때 자동으로 스캔해 읽는다. 이때 내용은 시스템 프롬프트 안에 들어가는 것이 아니라 시스템 프롬프트 바로 뒤에 우선순위 높은 사용자 메시지로 주입된다. 그래서 CLAUDE.md는 강제 설정이 아니라 지침(guidance)으로 작동한다는 설명이 따라붙는다.

이 발상은 이미 익숙하다. `.editorconfig`는 편집기 동작을, `.eslintrc`는 코드 스타일을, `tsconfig.json`은 TypeScript 컴파일 옵션을, `.prettierrc`는 포매팅 규칙을 고정한다. 모두 사람 머릿속의 암묵적 '팀 관례'를 기계가 읽는 선언적 규칙으로 꺼내는 것이다. CLAUDE.md도 같은 논리이고 다른 점은 읽는 쪽이 컴파일러가 아니라 자연어를 이해하는 대형 모델이라는 것뿐이다. 책은 이를 설정 주도 사고의 AI 시대 진화형이라고 부른다.

### 1-4. Kage의 노트: package.json을 읽으면 되지 않나

Claude Code도 프로젝트 파일을 읽을 수 있으니 `package.json`만 보고 기술 스택을 추론하면 되지 않느냐는 반문이 있을 수 있다. 맞지만 '능동 탐색'은 귀중한 도구 호출 횟수와 컨텍스트 윈도 공간을 쓰고, `package.json`은 의존성 목록만 담을 뿐 아키텍처 결정이나 팀 규칙 같은 깊은 정보를 담지 못한다. CLAUDE.md의 핵심 가치는 흩어진 암묵지를 명시적 지침 문서로 모아, 코딩을 시작하기 전에 Claude가 프로젝트에 대한 정확한 정신 모형을 갖추게 하는 데 있다.

## 2. 5계층 메모리 구조

CLAUDE.md는 한 곳에만 있지 않다. Claude Code의 메모리 시스템은 전역에서 지역까지 다섯 단계로 나뉜 층 구조다. 리눅스가 `/etc/`의 전역 설정, 홈 디렉터리의 사용자 설정, 현재 디렉터리의 프로젝트 설정을 차례로 겹쳐 읽는 방식과 같은 설계 철학이다.

참고로 책의 NOTE에 따르면 이 5단계 모델은 이 책이 메모리를 정리하는 자체 방식이다. 공식 문서는 Managed Policy, User, Project, Local의 네 가지 메모리 범위를 정의한다. 여기서 별도 층으로 뽑은 규칙 디렉터리(`.claude/rules/`)는 그 분류에서는 독립 범위가 아니라 프로젝트 범위 안의 모듈식, 경로 지정형 기능이다. 조건부 규칙 장치를 부각하려고 별도 층으로 세운 것이라고 한다.

### 2-1. 회사 규정 문서 비유

| 계층 | 비유 | 성격 |
|---|---|---|
| 1. 엔터프라이즈 정책 | 본사가 내리는 '그룹 행동 강령' | 모든 자회사가 지켜야 하고 고칠 수 없는 철칙 |
| 2. 사용자 | 부서 운영 매뉴얼(원서 비유) 자리이나 실제로는 개인 취향 프로필 | 이 머신의 모든 프로젝트에 적용 |
| 3. 프로젝트 | 프로젝트 팀의 '개발 규격서' | 기술 선택, 코딩 스타일 같은 핵심 관례 |
| 4. 규칙 디렉터리 | 특정 상황용 '특수 작업 지침서' | 해당 작업에서만 참조되는 시나리오별 규칙 |
| 5. 로컬 | 각자 책상 위 개인 포스트잇 | 본인만 보는 임시 디버깅 팁이나 선호 |

참고(노트 작성자): 원서의 비유는 본사(그룹 강령), 부서(운영 매뉴얼), 프로젝트팀(개발 규격서), 특정 시나리오(특수 작업 지침), 개인 포스트잇의 다섯 단계로 서술된다. 바로 뒤에 나오는 실제 계층 설명은 엔터프라이즈 정책, 사용자, 프로젝트, 규칙 디렉터리, 로컬 순이어서 비유의 두 번째 칸(부서 매뉴얼)이 사용자 계층과 정확히 맞지 않는다. 위 표는 실제 계층 순서에 맞추어 정리했다. 위에서 아래로 갈수록 적용 범위는 좁아지고 내용의 입도는 세밀해지며 관리 유연성은 올라간다는 점만 기억하면 된다.

### 2-2. 계층별 책임과 위치

**엔터프라이즈 정책 계층.** 시스템 전체의 '천장'이며 보통 개발자는 접근하지 못한다. 회사 IT 관리자가 시스템 수준 설정 파일이나 Anthropic 엔터프라이즈 관리 콘솔로 일괄 설정한다. 위치는 운영체제별로 다르다.

| 운영체제 | 경로 |
|---|---|
| macOS | `/Library/Application Support/ClaudeCode/CLAUDE.md` |
| Linux/WSL | `/etc/claude-code/CLAUDE.md` |
| Windows | `C:\Program Files\ClaudeCode\CLAUDE.md` |

전형적인 정책은 코드를 외부 API로 보내지 못하게 하기, 모든 DB 작업을 ORM으로 하게 하기, 비밀 값을 코드에 하드코딩하지 못하게 하기 같은 보안 레드라인이다. 아래 네 계층을 어떻게 설정하든 이 강제 제약은 우회할 수 없다. 개인 개발자와 소규모 팀에서는 보통 비어 있어 신경 쓸 필요가 없다.

**사용자 계층.** 사용자의 '개인 선호 프로필'로 홈 디렉터리의 `~/.claude/CLAUDE.md`에 있고 이 머신에서 여는 모든 프로젝트에 적용된다. 특정 비즈니스 로직과 무관한 개인 작업 습관을 담기에 알맞다. 소통 언어(한국어나 영어), Git 커밋 메시지 형식, 자주 쓰는 단축 명령 매핑 등이다. 원서 예시는 응답은 중국어로 코드 주석은 영어로, 커밋 형식은 `type(scope): 중국어 설명`, 함수형 스타일 선호, "테스트 실행"이라고 하면 `pnpm test`를, "서비스 시작"이라고 하면 `pnpm dev`를 실행하라는 식이다. 프로젝트를 바꿔도 변하지 않는 안정적 선호만 둔다.

**프로젝트 계층.** 일상 개발에서 가장 자주 쓰이며 2장의 주 무대다. 프로젝트 루트의 `CLAUDE.md`이고, 반드시 Git 저장소에 커밋해 프로젝트 코드 자산의 일부로 만든다. 새 동료가 프로젝트를 클론하면 Claude Code가 이 파일을 자동으로 읽으므로 추가 설정 없이 즉시 프로젝트 맥락 전체를 얻는다. 입사 환영 키트에 '프로젝트 개발 매뉴얼'이 들어 있는 것과 같다. 기술 스택, 디렉터리 구조, 코딩 표준, 자주 쓰는 명령이 한눈에 보인다.

**규칙 디렉터리 계층.** 'CLAUDE.md 하나로는 복잡한 규칙을 다 담을 수 없다'는 문제를 풀려는 고급 설계다. `.claude/rules/` 아래에 주제별(DB 규약, API 설계 스타일, 테스트 전략 등) 마크다운 파일을 여러 개 둔다. 특정 파일을 다루거나 특정 맥락에 들어갈 때만 동적으로 불러오는 조건부 트리거를 지원해 무관한 정보가 컨텍스트를 어지럽히지 않게 한다. 자세한 내용은 '조건부 규칙 시스템' 문서에 있다.

**로컬 계층.** 개발자의 '개인 메모'로 `CLAUDE.local.md`에 해당한다. Git에 커밋하지 않는다. 주의할 점은 `/init`을 실행해 개인용 옵션을 골랐을 때만 Claude Code가 `CLAUDE.local.md`를 `.gitignore`에 넣어 준다는 것이다. 파일을 손으로 만들었다면 `.gitignore`에 직접 추가해야 한다. 테스트 서버의 주소와 포트, 개인 디버깅 중 쌓은 고유한 통찰, 임시 작업 메모처럼 개인에게는 가치가 크지만 공유하기엔 맞지 않는 정보를 둔다. 개발 DB가 특정 시간에 점검에 들어간다는 정보는 팀 전체에 알리지 않고 로컬 계층에만 적으면 정보 소음을 피한다.

원서의 로컬 메모 예시는 DB 접속 주소, 수요일 22시~23시 DB 점검 시간(이 시간 마이그레이션 엄금), CORS 오류가 나면 Nginx 설정부터 확인, 프런트 서비스가 5173 포트에서 돌아 수동 프록시 설정이 필요하다는 내용이다. DB 접속 문자열에 비밀번호가 들어 있다는 점은 주의할 부분이며 이 노트에서는 값을 옮기지 않는다.

### 2-3. 메모리 범위 표(표 2.1)

원서의 표 2.1은 `/memory` 명령이 보여 주는 파일들의 적용 범위다. 추출본에서 칸이 흩어져 있어 아래와 같이 복원했다.

| 구분 | 파일 | 적용 범위 |
|---|---|---|
| 프로젝트 메모리 | `./CLAUDE.md` 또는 `./.claude/CLAUDE.md` | 팀 공유. 버전 관리 가능하며 팀 표준 통일에 알맞다 |
| 사용자 메모리 | `~/.claude/CLAUDE.md` | 개인 전역. 현재 사용자의 모든 프로젝트에 유효한 개인 선호 설정 |
| 프로젝트 로컬 메모리 | `./CLAUDE.local.md` | 개인 로컬. 현재 프로젝트에만 적용되는 개인 선호로 보통 `.gitignore`로 제외해 저장소에 커밋되지 않게 한다 |
| 시스템 파일 | 엔터프라이즈 정책 경로 | 위 2-2의 운영체제별 경로(추출본에는 '운반하는 내용' 같은 조각만 남아 정확한 칸은 확인할 수 없다) |

## 3. 계층이 충돌할 때와 @ 참조

Xiaobing이 날카로운 질문을 던진다. 사용자 계층에는 '들여쓰기 4칸', 프로젝트 계층에는 '2칸'이라고 적혀 있으면 어느 쪽을 따르는가. Kage의 답은 '누적이지 덮어쓰기가 아니다'이다. Claude Code는 모든 계층의 내용을 읽어 하나의 완전한 컨텍스트로 합친다. 충돌이 생기면 Claude 모델이 스스로 판단하되 핵심 논리는 구체적인 쪽이 우선이다. 들여쓰기 예에서는 현재 프로젝트에 더 구체적인 프로젝트 계층의 '2칸'이 사용자 계층의 일반 선호 '4칸'보다 앞선다.

단 엔터프라이즈 정책 계층은 예외로 절대 권한을 갖는다. 아래 계층을 어떻게 설정하든 제약은 우회되지 않는다. 회사의 법무나 보안 레드라인처럼 어떤 프로젝트 관리자나 개인 선호도 넘을 수 없다.

참고(노트 작성자): 1장은 'CSS의 캐스케이딩처럼 각 단계가 앞 단계를 덮어쓴다'고 비유했다. 2장은 정확히는 '모든 계층을 합쳐 읽고 충돌 시 구체적인 쪽을 따른다'고 설명한다. 두 설명의 핵심은 같지만 2장의 표현이 더 정확하다.

### @ 참조 문법

어느 계층의 메모리 파일에서든 `@path/to/file` 문법으로 다른 파일의 내용을 포함할 수 있어 설정을 모듈식으로 정리할 수 있다. 프로젝트 계층 CLAUDE.md에 `@docs/api-conventions.md`라고 쓰면 Claude가 그 API 규약 문서를 자동으로 불러와 해석한다. 이 장치는 최대 5단계의 중첩 재귀를 지원하며 대부분의 복잡한 프로젝트를 정리하기에 충분하다.

대형 프로젝트에는 우아한 문서 거버넌스 해법이 된다. CLAUDE.md가 모든 세부를 직접 짊어지지 않고 여러 전문 문서를 가리키는 '마스터 색인' 역할을 하며, 거대한 단일 파일에 정보를 쌓는 폐단을 피해 구조가 명료해지고 유지보수가 쉬워진다.
