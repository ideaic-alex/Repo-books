# 조건부 규칙 시스템

프로젝트가 자라면 CLAUDE.md 하나는 결국 용량의 한계에 부딪힌다. 프런트엔드 컴포넌트 규약, 백엔드 API 설계, DB 마이그레이션 절차, 테스트 전략(커버리지와 목), 인프라(Docker와 CI/CD)까지 모든 규칙을 한 파일에 쌓으면 두 가지 문제가 생긴다. 이 문서는 그 해법인 `.claude/rules/` 디렉터리와 `paths` 필드를 이용한 조건부 로딩을 다룬다.

핵심 비유는 직무별 맞춤 조작 설명서다. 접수 담당은 안내 데스크 절차를, 창고 직원은 창고 규정을 따르고 아무도 회사 전체 규정을 외울 필요가 없다. 창고 일을 하게 될 때에야 '창고 관리 매뉴얼'을 펼치면 된다.

---

## 1. 왜 규칙을 나누는가

한 파일에 모두 쌓을 때의 문제는 두 가지다.

| 문제 | 설명 |
|---|---|
| 유지보수 악몽 | 파일이 극단적으로 길어져 특정 규칙을 찾고 고치기 어렵다 |
| 주의력 희석 | 단순한 프런트엔드 컴포넌트를 쓰는 중에도 DB 마이그레이션 규범과 CI 설정 요구 같은 무관한 정보가 컨텍스트에 강제로 실린다. 이 소음이 모델의 주의를 흩어 현재 작업의 효율을 떨어뜨리고 심하면 환각을 부르거나 핵심 프런트 제약이 무시되게 한다 |

`.claude/rules/` 디렉터리는 메모리 시스템을 '하나의 무겁고 모든 것을 담은 매뉴얼'에서 '필요할 때 꺼내 보는 모듈식 지식 베이스'로 진화시킨다. 장점은 두 가지다.

- 영역 분할: 큰 규칙 묶음을 주제별 파일로 쪼개 파일마다 한 영역에 집중하게 해 유지보수성을 크게 높인다.
- 지능적 활성화: 각 파일 맨 위에 YAML 프런트매터를 넣고 `paths` 필드에 글롭(Glob) 패턴을 선언한다. Claude Code가 다루는 파일 경로가 패턴과 맞을 때만 해당 규칙이 활성화되어 컨텍스트에 주입된다. 맞지 않으면 규칙 파일은 디스크에 조용히 있을 뿐 토큰도 컨텍스트 공간도 쓰지 않는다.

## 2. 규칙 파일 예시

### 2-1. 테스트 규칙

`.claude/rules/testing.md`는 `paths`로 `**/*.test.ts`, `**/*.spec.ts`, `tests/**`를 선언하고 본문(Testing Guidelines)에 다음을 적는다.

```markdown
---
paths:
  - "**/*.test.ts"
  - "**/*.spec.ts"
  - "tests/**"
---
# Testing Guidelines
- Use vitest as the testing framework; jest is prohibited.
```

본문의 규칙은 이렇다. 테스트 프레임워크는 vitest이며 jest는 금지, 모든 테스트 파일에는 대상 모듈 이름과 같은 `describe` 블록 필수, 모듈 목킹은 `vi.mock()`으로 통일하고 수동 목은 엄금, 비동기 테스트는 `async/await`만 쓰고 `done` 콜백 금지, 테스트 데이터는 팩토리 함수로 만들고 하드코딩 엄금.

이 설정에서는 Claude가 `src/services/order-service.ts`를 고칠 때는 위 규칙이 로드되지 않는다. 그러나 `tests/order-service.test.ts`를 쓰는 순간 자동으로 적용된다. 프로그래밍 언어의 지연 로딩(lazy loading) 개념과 같다. 시작할 때 모든 잠재 자원을 미리 올릴 필요 없이 정말 필요할 때 동적으로 부른다.

### 2-2. DB 규칙과 API 설계 규칙

같은 방식을 다른 영역으로 확장한다.

| 규칙 파일 | paths | 담긴 규칙 |
|---|---|---|
| `.claude/rules/database.md` | `prisma/**`, `src/repositories/**` | 메인 브랜치에 커밋된 마이그레이션 파일은 수정 엄금하고 필요하면 새 마이그레이션만 만든다. 모든 쿼리는 리포지터리 계층을 거치며 서비스 계층이 Prisma 클라이언트를 직접 부르지 않는다. 배치 작업은 트랜잭션으로 감싸고 한 번에 100건 넘게 쓸 때는 배치 처리가 필수다 |
| `.claude/rules/api-design.md` | `src/routes/**`, `src/schemas/**` | 모든 라우트에는 입력 검증용 Zod 스키마를 붙인다. 목록 엔드포인트는 `page`(1부터 시작)와 `limit`(기본 20, 최대 100) 페이징을 통일해 지원한다. 오류 응답에는 기계가 읽는 `code` 필드와 사람이 읽는 `message` 필드를 둔다 |

즉 DB 규칙은 Prisma 파일이나 데이터 접근 계층을 다룰 때만, API 설계 규칙은 라우트나 스키마 파일을 고칠 때만 적용된다.

## 3. 협업에서의 이점과 주의점

Kage는 모듈식 규칙의 실무 이점을 하나 더 든다. 협업 환경에서 도메인 전문가가 자기 규칙 파일을 독립적으로 관리할 수 있어 Git 병합 충돌 가능성이 크게 줄어든다. 프런트엔드 엔지니어는 `frontend.md`를, 백엔드 엔지니어는 `api-design.md`를, DBA는 `database.md`를 맡아 서로 간섭 없이 각자 영역에 집중한다. 팀이 커질수록 이 '분할 정복' 전략의 가치가 뚜렷해진다.

### 주의: paths가 없으면 전역 규칙이 된다

규칙 파일에 `paths` 프런트매터가 설정되어 있지 않으면 시스템은 그것을 전역 무조건 규칙으로 취급해 모든 세션에서 강제 로딩한다. 사실상 메인 CLAUDE.md에 직접 적은 것과 같다. 따라서 규칙 파일마다 정밀한 `paths` 제한을 설정해야 메모리 시스템의 핵심 장점인 '필요할 때만 로딩'을 누릴 수 있다.

참고(노트 작성자): 원서는 규칙 파일을 `.claude/rules/` 아래 마크다운으로 두고 `paths`로 활성 조건을 거는 방식만 설명한다. 하위 폴더 구성이나 파일 이름 규칙처럼 원문에 없는 세부는 여기서 다루지 않았다. 정확한 지원 범위는 공식 문서를 확인한다.

## 4. 5계층 안에서의 위치

규칙 디렉터리 계층은 앞 문서의 5계층 중 4번째이며, 책의 NOTE가 밝히듯 공식 분류에서는 프로젝트 범위 안의 모듈식 기능이다. 이 층의 존재 이유는 '조건부 로딩'이다. 요약하면 다음과 같다.

- 프로젝트 CLAUDE.md는 항상 필요한 핵심 규칙(스택, 구조, 명령)만 담는다.
- 특정 영역에서만 필요한 규칙은 `paths`를 건 규칙 파일로 뺀다.
- 큰 문서는 `@` 참조로 연결하되, 항상 로딩되는 분량을 가볍게 유지한다.

이렇게 하면 '적절한 정보를 정확한 시점에 컨텍스트에 전달하는' 지능적 장치가 된다. 모든 규칙을 Claude 앞에 쏟아 붓는 거친 방식을 버리고 컨텍스트를 깨끗하고 효율적으로 유지한다는 것이 2장 요약의 평가다.
