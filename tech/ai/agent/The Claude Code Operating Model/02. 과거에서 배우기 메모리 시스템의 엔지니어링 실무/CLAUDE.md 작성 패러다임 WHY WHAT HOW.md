# CLAUDE.md 작성 패러다임 WHY WHAT HOW

CLAUDE.md가 어디에 놓이는지 알았다면 이제 어떻게 써야 하는가가 남는다. Kage는 화이트보드에 세 단어를 적는다. Less is more. CLAUDE.md의 내용은 전역으로 지속되어서, 매 대화 시작 때 컨텍스트 윈도에 통째로 주입된다. 한 줄 한 줄이 모든 상호작용에서 귀한 토큰 한도를 쓴다는 뜻이다.

이 문서는 간결함이 왜 기술적 이유가 있는 원칙인지, 무엇을 적을지 가르는 세 질문 틀(WHY, WHAT, HOW), 나쁜 예와 좋은 예의 대비, 그리고 작성을 돕는 `/init`과 `/memory` 명령을 정리한다.

---

## 1. 왜 짧아야 하는가

컨텍스트 윈도는 면적이 정해진 책상이다. Claude Code가 실제 작업을 하기 전에 두꺼운 참고 자료(긴 규칙 파일)를 책상 위에 쌓아 놓으면 정작 처리할 코드, 파일, 임시 초안이 놓일 자리가 줄어든다. 책상이 차면 Claude Code는 공간을 만들려고 초기의 핵심 정보를 '버려야' 하고, 그래서 중요한 지시나 맥락을 '잊는' 일이 생긴다.

Anthropic 공식 지침은 CLAUDE.md 파일 하나를 200줄 미만으로 목표하라고 권한다. 더 길면 컨텍스트를 더 먹고 준수율이 떨어진다. 밑바닥 논리는 지시의 밀도가 준수 확률에 반비례한다는 것이다. 지시가 장황하고 복잡할수록 각 규칙이 모델의 '깊은 주의'와 '엄격한 실행'을 받을 확률이 낮아진다. 너무 두꺼워서 아무도 끝까지 읽지 못하는 직원 안내서보다 핵심만 추린 A4 한 장 요약이 실제로 더 잘 먹히는 '정보 과부하' 원리와 같다. 간결함은 토큰 절약을 넘어 지시가 실제로 이행되게 하는 핵심 전략이다.

## 2. 세 질문 틀: WHY, WHAT, HOW

무엇을 CLAUDE.md에 적을지 가르는 기준으로 Kage는 세 질문을 준다.

| 질문 | 핵심 가치 | 성격과 효과 |
|---|---|---|
| WHY(왜 하는가) | 모델에게 '유추하는 능력'을 준다 | 결정 뒤의 논리를 드러내 프로젝트의 핵심 관심사를 이해시킨다 |
| WHAT(무엇을 하고 하지 않는가) | 넘어선 안 될 '행동 경계'를 정한다 | 가장 직접적이고 단단한 지시. 설명이 필요 없고 절대 준수를 요구한다 |
| HOW(어떻게 단계별로 하는가) | '표준 운영 절차'를 규격화한다 | 자주 쓰는 명령, 고정 절차에 알맞다. 원리를 이해시킬 필요 없이 정해진 단계를 정확히 실행하게 한다 |

### 2-1. WHY

원리를 아는 모델은 명시되지 않은 경계 사례를 만나도 원칙에 따라 올바르게 추론한다. 원서의 예시는 "Fastify의 스키마 기반 검증이 프로젝트의 '타입 안전 우선' 전략과 맞기 때문에 Express 대신 Fastify를 골랐다"이다. Claude가 '타입 안전'이 최우선임을 이해하면 라이브러리를 따로 지정하지 않은 곳에서도 타입 정의가 더 좋은 해법을 알아서 선호한다. 키워드를 기계적으로 맞추지 않는다.

### 2-2. WHAT

프로젝트 규격의 대다수가 여기에 속한다. 예: "패키지 관리자는 반드시 pnpm을 쓴다. npm이나 yarn은 금지." 명확한 '레드라인'이 되어 도구 선택의 불확실성을 없애고 기술 스택의 일관성을 보장한다.

### 2-3. HOW

팀의 모범 사례를 모델의 '근육 기억'으로 바꿔 명령어 오타나 매개변수 누락에서 오는 저수준 실수를 줄인다. 예: "DB 마이그레이션은 `pnpm db:migrate`, 테스트 데이터 시딩은 `pnpm db:seed`."

### 2-4. 세 질문을 쓰는 요령

모든 정보가 세 질문에 한꺼번에 답할 필요는 없다. 대부분의 규칙은 WHAT 수준에서 한 문장으로 분명히 하면 충분하다. 오해하기 쉬운 핵심 결정이나 모델이 '선의의 실수'를 하기 쉬운 곳만 WHY로 깊이 보충할 가치가 있다. 규칙마다 긴 배경 설명이나 감정 표현이 붙어 있다면 대개 내용이 과적재라는 신호다.

## 3. 나쁜 예와 좋은 예

### 3-1. 나쁜 예: 그럴듯하게 들리는 무의미

원서의 나쁜 예는 "이 프로젝트는 전자상거래 플랫폼 백엔드다, 팀원은 5명이고 2024년 3월에 개발을 시작했다, Node.js의 RESTful API 서비스다, 코드를 잘 써야 하고 성능에 신경 써야 한다, 테스트는 포괄적이어야 한다, 모범 사례를 따르라" 같은 문서다. 사람 사이의 사교적 표현과 모호한 지시가 가득해 AI에게는 거의 쓸모없는 정보다.

| 표현 | 무엇이 문제인가 |
|---|---|
| "잘 써라" | 어느 정도? Prettier 포매팅인가, 디자인 패턴인가 |
| "포괄적" | 어떤 시나리오? 단위, 통합, E2E 중 무엇인가, 커버리지는 80%인가 100%인가 |
| "모범 사례" | 누구의 모범 사례인가 |

가장 치명적인 것은 '모범 사례를 따르라'다. 옳은 듯 보이지만 비어 있다. Claude는 이미 기본적으로 자신이 아는 '모범 사례'(인터넷 대규모 데이터의 통계 패턴)를 따르려 하는데, 모델이 아는 일반적 모범 사례와 팀의 구체적 기술 관례는 흔히 다르기 때문이다. 또 '팀원 5명', '2024년 3월 시작' 같은 메타데이터는 코드 생성에 아무 지침이 되지 못하면서 귀한 컨텍스트만 차지한다.

### 3-2. 좋은 예: 정밀한 조작 설명서

좋은 예(주문 서비스 API)의 뼈대는 네 절이다.

| 절 | 담긴 내용 |
|---|---|
| Technology Stack | Node.js 20 + TypeScript 5.3(strict), Fastify 4(Express 사용 금지), Prisma ORM + PostgreSQL 15, pnpm 8(npm/yarn 금지) |
| Project Structure | `src/routes/`(파라미터 파싱과 응답 구성만), `src/services/`(비즈니스 로직), `src/repositories/`(Prisma 호출 캡슐화), `src/schemas/`(Zod 검증 스키마, 라우트와 일대일) |
| Key Conventions | 통일된 API 응답 형식 `{ success, data?, error?: { code, message } }`, 오류 코드는 UPPER_SNAKE_CASE(예: `ORDER_NOT_FOUND`), DB 테이블명은 snake_case 복수형, 기본 키는 UUID, `created_at`과 `updated_at` 필수 |
| Common Commands | `pnpm dev`(3000 포트), `pnpm test`(vitest), `pnpm build`(TypeScript 컴파일과 타입 검사), `pnpm db:migrate`(Prisma 마이그레이션) |

두 문서의 차이는 한눈에 보인다. 좋은 쪽은 간결하고 구체적이며 즉시 실행 가능해서 모든 규칙이 Claude의 행동 논리를 직접 고정한다.

- 기술 스택 고정: "Fastify 4 (Express 사용 금지)"를 보면 Claude는 Express 관련 해법을 즉시 배제하고 Fastify로 코드를 생성한다.
- 아키텍처 표준화: 디렉터리 구조를 읽으면 새 라우트 파일이 `src/routes/`에 가야 함을 정확히 판단해 흩어 놓지 않는다.
- 무오류 실행: 명령과 주석이 있어 빌드와 테스트를 정확히 돌리고 `npm run build`와 `yarn build` 사이의 추측을 없앤다.

## 4. 작성을 돕는 두 가지 명령

### 4-1. /init

프로젝트 루트에서 실행하면 Claude Code가 디렉터리 구조와 의존성 설정 파일(`package.json`, `pyproject.toml`, `Cargo.toml` 등)을 자동으로 스캔해 CLAUDE.md 초안을 만든다. 보통 기술 스택 식별, 디렉터리 구조 개요, 자주 쓰는 스크립트 명령을 담아 좋은 출발점이 된다. 하지만 `/init`이 자동으로 추론하지 못하는 내용은 사람이 검토하고 보충해야 한다. 계층형 아키텍처의 구체 제약, 통일된 API 응답 형식, 팀 고유의 명명 규칙 같은 것이다. 이 '암묵지'는 팀원 머릿속에만 있고 설정 파일만으로는 뽑아낼 수 없어, 사람이 명시해야 AI의 행동이 팀 기대와 일치한다.

### 4-2. /memory

대화 중 메모리를 동적으로 고치는 명령이다. 실행하면 현재 쓸 수 있는 메모리 파일 목록이 파일 선택기로 뜨고, 고르면 편집기에서 바로 열린다. 예컨대 프로젝트 규격은 `date-fns`를 요구하는데 Claude가 또 `moment.js`를 썼다면 다음 순서로 고친다.

1. `/memory`를 입력한다.
2. 프로젝트 수준 CLAUDE.md를 고른다.
3. "날짜 처리는 항상 date-fns를 쓴다. moment.js 금지" 규칙을 추가한다.
4. 저장하고 닫는다.

다음 대화부터 새 규칙이 즉시 적용된다. 개인 습관일 뿐 팀에 영향을 주기 싫다면 `CLAUDE.local.md`에 적으면 된다. 이 파일은 기본적으로 `.gitignore`로 제외된다는 원서 설명이 있으나, 앞 문서에서 보았듯 손으로 만든 경우는 직접 추가해야 한다. 이 장치는 '실수, 교정, 메모리 갱신, 실수 방지'의 선순환을 만들며, 시간이 지날수록 메모리 파일은 더 정밀해지고 프로젝트 안에서 Claude Code의 성능은 계속 좋아진다.
