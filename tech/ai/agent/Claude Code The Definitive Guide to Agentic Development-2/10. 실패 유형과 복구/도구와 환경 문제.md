# 도구와 환경 문제

이 문서는 Claude Code를 둘러싼 도구와 실행 환경에서 생기는 실패를 다룬다. bash 환경이 명령마다 초기화되는 문제, MCP 서버 연결이 조용히 끊기는 문제, 스톱 훅이 무한 루프에 빠지는 문제, 에이전트 팀 기능의 한계를 설명한다.

이 실패들도 에러 메시지로 드러나지 않는 경우가 많다. 무엇이 어떻게 조용히 틀어지는지 알아 두면, 결과가 이상할 때 어디부터 의심해야 하는지 빨리 정할 수 있다.

---

## 1. bash 환경은 명령 사이에 유지되지 않는다

이 문제는 누구나 한 번은 당하고, 잊어버려서 또 당한다.

Claude가 실행하는 bash 명령은 매번 새 셸 환경에서 돌아간다. 명령 사이에 유지되는 것은 작업 디렉터리뿐이다. 환경 변수, 셸 별칭(alias), 함수 정의, 활성화한 가상 환경은 명령이 끝나면 모두 사라진다.

실패 방식이 조용하다는 점이 위험하다. Claude가 한 명령에서 환경 변수를 설정하고 다음 명령에서 그 변수를 쓴다고 하자. 두 번째 명령은 "변수를 찾을 수 없다"는 에러를 내지 않는다. 변수가 비어 있는 채로 실행되고, 빈 문자열 때문에 엉뚱한 동작을 조용히 할 수 있다. 예를 들어 Claude가 테스트하려고 NODE_ENV=production을 설정해도, 다음 명령의 테스트는 기본값인 개발 모드로 돈다. 에러는 없는데 결과는 틀린다.

### 대응 방법

잘못된 결과가 조용히 나온 경우에는 복구 수단이 따로 없고, 직접 발견해야 한다. 그래서 예방이 핵심이다.

- 공유 상태에 의존하는 bash 명령을 이어서 실행할 때는 명령마다 그 상태를 다시 만들어 준다.
- 변수 설정과 실행을 한 줄에 쓴다.

```bash
NODE_ENV=production npm test
```

- 또는 매 명령 시작에 설정 스크립트를 source한다.
- 또는 settings.json의 환경 변수 설정을 쓴다. 이 설정은 모든 bash 명령에 변수를 자동으로 넣어 준다.

특히 다음 상황에서 조심한다.

- 가상 환경 활성화: `source venv/bin/activate`는 다음 명령까지 유지되지 않는다.
- 한 번만 source하는 디렉터리별 환경 파일
- 명령에 걸쳐 쓰는 셸 함수 정의
- "이걸 실행하고 저걸 실행해"가 상태 공유를 전제로 하는 모든 워크플로

## 2. MCP 연결 끊김: 사라지는 도구

MCP 서버는 세션을 시작할 때 연결되고, 언제든 끊어질 수 있다. 끊어지면 그 서버가 제공하던 도구가 Claude의 사용 가능한 도구 목록에서 그냥 사라진다. 알림도 에러도 없다. 1분 전까지 할 수 있던 일을 Claude가 갑자기 못 하게 될 뿐이다.

겉으로는 잘 하던 작업을 Claude가 갑자기 해내지 못하는 모습으로 나타난다. MCP 도구로 데이터베이스를 조회하다가 서버가 끊어졌다고 하자. Claude는 "데이터베이스 도구를 잃었다"고 말하지 않는다. 대안을 찾아 시도하다 실패하고, 없어진 능력을 자기가 잃은 줄 모른 채 우회하려다 점점 더 혼란스러운 출력을 낸다.

### 대응 방법

- `/mcp` 명령으로 연결된 MCP 서버의 상태를 확인한다. 연결이 끊긴 서버가 있으면 그 화면에서 다시 시작할 수 있다.
- Claude의 행동이 예상치 못하게 바뀌면 미리 MCP 상태를 점검한다. 특히 외부 도구를 잘 쓰던 중이었다면 더 그렇다.
- MCP 신뢰성에 관한 자세한 내용은 5장에 있다. 원인이 무엇이든 복구 방법은 같다. 서버를 다시 연결하거나 세션을 다시 시작한다.

## 3. 스톱 훅 무한 루프

훅(hook, 정해진 시점에 자동으로 실행되는 사용자 정의 동작)은 생명주기 이벤트에 맞춰 작동한다. 그중 스톱 훅(stop hook)은 Claude가 작업이 끝났다고 판단하고 멈추려 할 때 실행된다. 예를 들어 테스트가 아직 실패 중이라서 Claude가 멈추면 안 된다고 훅이 판단하면, Claude에게 계속하라고 지시할 수 있다.

실패 방식은 항상 "계속해"라고 말하는 스톱 훅이다. Claude가 끝내면 훅이 발동해 "계속해"라고 하고, Claude가 더 작업하고 또 끝내면 훅이 또 "계속해"라고 한다. 멈추는 조건이 영원히 충족되지 않으니 무한 루프가 된다.

시스템에는 폭주 루프를 막기 위한 `stop_hook_active` 필드가 있다. 하지만 설계상의 위험은 여전히 크다. 훅의 "계속" 조건이 Claude가 실제로 만족시킬 수 없는 기준에 기대고 있으면, 수렴하기 전에 토큰 예산이 바닥난다. 대표적인 예는 다음과 같다.

- Claude의 변경과 무관한 이유로 실패하는 테스트
- 통과가 불가능한 린트 규칙
- 다운된 외부 서비스

### 예방 방법

- 스톱 훅에 반복 횟수 제한을 넣는다. 예를 들어 "세 번 시도한 뒤에도 테스트가 실패하면 멈추고 남은 실패를 보고한다"처럼 쓴다.
- 일부러 실패하는 조건으로 훅을 테스트해서 결국 끝나는지 확인한다.
- 스톱 훅을 처음 쓸 때는 토큰 사용량을 지켜본다.

## 4. 에이전트 팀의 한계

에이전트 팀(agent teams, 4장)은 실험적인 기능이고, 한계도 그 상태에서 비롯된다.

| 한계 | 내용 | 영향 |
|---|---|---|
| 세션 재개 불가 | 팀원의 세션이 중단되거나 비정상 종료되면 재개할 수 없고 작업이 사라진다. | 오래 걸리는 작업에서 90% 지점에 중단되면 처음부터 다시 해야 한다. |
| 태스크 상태 지연 | 공유 태스크 목록의 갱신이 즉시 반영되지 않는다. | 다른 에이전트가 이미 시작한 태스크를 또 집어서 중복 작업이 생길 수 있다. |
| 세션당 팀 하나 | 조율을 맡은 세션은 활성 팀을 하나만 가질 수 있다. | 독립적인 팀이 여러 개 필요하면 조율 세션도 여러 개 필요하다. |
| 중첩 팀 불가 | 팀원이 자기 하위 팀을 만들 수 없다. | 구조가 평평해서(조율자 하나, 팀원 여러 명) 표현할 수 있는 작업 분해의 복잡도가 제한된다. |

### 대응 방법

현실적인 대응은 다음과 같다.

- 팀 태스크를 하나쯤 잃어도 감당할 수 있을 만큼 작게 쪼갠다.
- 느슨한 협업의 대가로 약간의 중복 작업은 받아들인다.
- 정확한 조율이 필요할 때는 태스크 상태를 직접 확인한다.
