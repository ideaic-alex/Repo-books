# 실수 반복과 작업 복구

Claude가 같은 실수를 되풀이하거나, 되돌린 줄 알았던 파일이 그대로이거나, 터미널을 닫았더니 작업이 사라지는 일은 모두 "상태가 어디에 저장되는가"를 오해해서 생긴다. 이 문서는 세션을 넘나드는 기억, 체크포인트의 한계, 세션 복구, 그리고 방향이 틀어졌을 때 판단 기준을 다룬다.

마지막에는 Claude가 지나치게 복잡한 해법을 내놓을 때 다루는 방법도 정리한다.

---

## 1. Claude가 같은 실수를 반복할 때

**증상.** 세션이 바뀌어도 같은 실수가 나온다. 잘못된 import 경로, 틀린 테스트 명령, 폐기된 API 사용, 잘못된 모듈 참조 같은 것이다.

**원인.** 그 오류 패턴이 계속 유지되는 컨텍스트(CLAUDE.md 등)에 기록되어 있지 않다. 세션은 매번 이전 실패에 대한 지식 없이 새로 시작한다.

**해결 방법.**

- 해당 오류를 겨냥한 지시를 CLAUDE.md에 추가한다.
- 잘못된 행동과 올바른 행동을 모두 구체적으로 쓴다.
- 프로젝트 수준 CLAUDE.md에 넣어 팀원 모두가 혜택을 보게 한다.

예를 들면 다음과 같은 지시다. 폐기된 경로를 밝히고 올바른 경로를 함께 적는다.

```text
Always import from @app/db/utils, never @app/utils/db (deprecated path)
```

---

## 2. 체크포인트 복원이 변경을 되돌리지 못할 때

**증상.** `Esc-Esc` 되감기(rewind)를 했는데 기대한 파일 상태로 돌아가지 않는다. `rm`, `mv`, `cp`, `sed` 같은 bash 명령으로 바뀐 파일이 원래대로 복구되지 않는다.

**원인.** 체크포인트는 Claude Code의 Write와 Edit 도구로 한 파일 수정만 추적한다. bash 명령, 외부 편집기, 동시에 도는 다른 세션이 바꾼 내용은 추적하지 않는다.

**해결 방법.**

- 완전한 복구는 git으로 한다. `git checkout -- <file>` 또는 `git stash`를 쓴다.
- 위험한 작업 전에 자주 커밋한다.
- 가능하면 bash보다 Claude Code의 내장 파일 도구로 파일을 수정한다.
- 파괴적인 작업은 Claude에게 먼저 백업을 만들라고 요청한다.

체크포인트는 편리한 되감기 장치지만 안전망의 전부가 아니다. git 커밋이 진짜 안전망이다.

---

## 3. 세션이 충돌이나 터미널 종료로 사라질 때

**증상.** 이전 세션의 작업이 없어졌다. Claude가 하던 일을 기억하지 못한다.

**원인.** 세션은 서로 독립적이다. 컨텍스트는 세션 안에만 존재한다. 터미널을 닫거나 충돌하면 저장하지 않은 컨텍스트를 잃는다.

**해결 방법.**

- 이전 세션을 이어서 쓴다. `claude -c`는 가장 최근 세션을 이어가고, `claude -r <session-id>`는 지정한 세션을 다시 연다.
- `claude --resume`을 실행하면 최근 세션 목록에서 골라 열 수 있다.
- 여러 세션에 걸치는 중요한 작업은 상태를 파일로 남긴다. 명세, 작업 목록(`.claude/tasks/`), CLAUDE.md 갱신이 해당한다.
- 중요한 세션은 `/rename`으로 이름을 붙여 두면 나중에 찾기 쉽다.

---

## 4. 처음부터 다시 할까, 중간에 고칠까

**증상.** Claude가 엉뚱한 방향으로 가거나 틀린 코드를 만들거나 잘못된 계획을 따른다. 방향을 바로잡을지 아예 다시 시작할지 판단이 서지 않는다.

**처음부터 다시 시작해야 하는 경우.**

- Claude가 컨텍스트를 잘못된 탐색으로 채웠다.
- 세부 사항이 아니라 근본 접근 방식이 틀렸다.
- 여러 번 고쳐 달라고 했는데도 수렴하지 않는다.
- 컨텍스트가 압축 기준에 가깝다.

**중간에 바로잡아야 하는 경우.**

- 접근은 맞고 세부만 틀렸다.
- 고칠 내용을 간결하게 설명할 수 있다.
- 컨텍스트에 여유가 많다.
- Claude가 쌓은 유용한 이해를 잃고 싶지 않다.

**권장 패턴.** 결정하기 전에 현재 상태를 git에 커밋한다. 다시 시작하면 그 커밋이 쓸 만한 조각을 보존해 준다. 중간에 고치기로 하면 그 커밋이 되돌아갈 지점이 된다. 어느 쪽을 택해도 손해가 없는 장치다.

---

## 5. Claude가 지나치게 복잡한 해법을 내놓을 때

**증상.** 단순한 문제에 정교한 추상화, 불필요한 디자인 패턴, 복잡한 아키텍처를 만든다.

**원인.** 기본 성향이 포괄적인 해법 쪽으로 기운다. 제약이 없으면 유연성, 확장성, 추상화 계층을 덧붙인다.

**해결 방법.**

- CLAUDE.md에 "요구 사항을 만족하는 가장 단순한 해법을 선호한다. 불필요한 추상화는 하지 않는다"는 취지의 지시를 넣는다. 영문으로는 "Prefer the simplest solution that meets requirements. No unnecessary abstractions."이다.
- 범위를 분명히 말한다. 예를 들어 "라이브러리가 아니라 일회용 스크립트다"라고 알려 준다.
- 제약을 명시한다. 예를 들어 `No new dependencies`(새 의존성 금지), `Single file`(파일 하나), `Under 100 lines`(100줄 미만)처럼 쓴다.
- 복잡한 구조가 나오면 그렇게 한 이유를 설명하라고 요청한다.
- 실행 도중 끼어들어 "왜 이렇게 하는가? 더 단순하게 해 보라"고 말한다.

---

## 6. 요약

| 증상 | 핵심 대응 |
|------|-----------|
| 같은 실수가 세션마다 반복된다 | CLAUDE.md에 틀린 방식과 맞는 방식을 함께 기록 |
| 되감기가 안 먹힌다 | git으로 복구, 자주 커밋, 내장 파일 도구 선호 |
| 세션이 사라졌다 | `claude -c`, `claude -r`, `claude --resume`, 상태를 파일로 보존 |
| 다시 할지 고칠지 모르겠다 | 먼저 커밋한 뒤 근본 접근이 틀렸으면 새로 시작 |
| 해법이 과하게 복잡하다 | 단순함 지시, 범위와 제약 명시, 이유 설명 요청 |
