# MCP와 실시간 시스템 한계

이 문서는 두 종류의 문제를 다룬다. 하나는 세션 중간에 MCP 서버 연결이 끊기는 문제이고, 다른 하나는 Claude Code가 만든 코드가 특정 영역, 즉 대규모 WebSocket과 FIX 프로토콜에서 한계를 보이는 문제다.

뒤의 두 가지는 Claude Code의 버그가 아니라 "뼈대는 잘 만들지만 운영 수준의 세부까지는 자동으로 챙기지 않는다"는 성격의 한계다. 따라서 해결의 핵심은 요구를 명시하고 사람이 검토하는 것이다.

---

## 1. MCP 서버 연결이 끊겼을 때

**증상.** 세션 도중 MCP 도구가 동작하지 않는다. 도구 호출이 조용히 실패하거나 에러를 반환한다. 서버 연결이 끊어졌다는 경고는 없다.

**원인.** MCP 서버 연결은 알림 없이 끊어질 수 있다. 끊기면 Claude가 쓸 수 있는 도구 목록에서 그 도구가 사라진다.

**해결 방법.**

- `/mcp`를 실행해 서버 상태와 토큰 비용을 확인한다.
- 서버가 죽었다면 다시 시작한다. 프로세스와 로그를 확인한다.
- 새 Claude Code 세션을 열어 연결을 다시 만든다.
- 문제가 계속되면 MCP 서버 로그에서 타임아웃이나 메모리 에러를 찾는다.
- 직접 만든 MCP 서버에는 상태 점검(health-check) 로직을 넣는다.
- 중요한 작업 전에 MCP가 살아 있는지 확인하는 PreToolUse 훅을 고려한다.

---

## 2. WebSocket 확장성 한계

**증상.** Claude Code가 만든 실시간 기능(채팅 화면, 라이브 대시보드, 스트리밍 피드)이 부하가 걸리면 실패하거나 연결이 끊긴다.

**원인.** Claude Code는 올바른 WebSocket 뼈대(scaffolding)를 만들지만, 운영 규모에서 필요한 사항을 자동으로 처리하지는 않는다. 연결 풀링(connection pooling), 백프레셔(backpressure, 받는 쪽이 못 따라갈 때 보내는 속도를 조절하는 장치), 재연결 로직, 하트비트(heartbeat) 유지 신호가 그 예다.

**규모별 권장 스택.**

| 동시 접속 규모 | 권장 스택 |
|----------------|-----------|
| MVP (50 미만) | Python + FastAPI로 충분하다 |
| 확장 단계 (100 초과) | Go 또는 Node.js가 필요하다. 이 수준에서 Python은 버거워한다 |
| 대규모 (1000 이상) | Go를 강하게 권장한다 |

표에서 50~100 구간은 원 자료에도 기준이 없다. 이 구간은 서비스 특성에 맞게 직접 판단해야 한다.

**해결 방법.**

- 프롬프트에서 연결 풀링과 재연결 로직을 명시적으로 요청한다.
- 완료 기준(acceptance criteria)에 부하 테스트 요구를 넣는다.
- 생성된 WebSocket 코드를 직접 검토한다. 최대 연결 수 제한, 하트비트 간격, 점진적 성능 저하(graceful degradation), 닫지 않은 연결로 인한 메모리 누수를 본다.
- 백프레셔 처리를 검토한다. Claude가 뼈대는 만들 수 있지만, 지연 시간 SLA 기준으로 직접 검증해야 한다.
- 원시 WebSocket을 직접 다루기보다 전용 실시간 메시징 라이브러리 사용을 고려한다.

---

## 3. FIX 프로토콜 한계

**증상.** Claude가 만든 FIX 메시지 빌더는 컴파일되지만 잘못되거나 불완전한 메시지를 만든다. 적합성 테스트(conformance test)에서 실패한다.

**원인.** FIX 프로토콜은 매우 복잡하고 도메인 고유의 의미 체계가 있다. Claude Code는 FIX 메시지 빌더를 만들 수는 있지만 운영 수준 구현에 필요한 깊은 도메인 지식이 부족하다.

**해결 방법.**

- Claude가 만든 FIX 코드는 뼈대로만 취급한다.
- 생성된 모든 메시지 빌더를 FIX 도메인 전문가가 검토하게 한다.
- 운영에 쓰기 전에 FIX 적합성 테스트 스위트로 검증한다.
- 가능하면 표준 REST나 WebSocket 브로커 API를 감싸는 작업에 Claude Code를 쓴다.

컴파일이 된다는 것과 프로토콜 규격에 맞는다는 것은 전혀 다른 문제다. 이 영역은 사람의 전문 검토와 외부 테스트가 필수다.

---

## 4. 요약

| 문제 | 핵심 대응 |
|------|-----------|
| MCP 도구가 조용히 사라진다 | `/mcp`로 확인, 서버 재시작, 새 세션, PreToolUse 훅 |
| 실시간 기능이 부하에서 무너진다 | 요구 명시, 부하 테스트, 코드 직접 검토, 규모에 맞는 언어 선택 |
| FIX 메시지가 틀린다 | 뼈대로만 사용, 전문가 검토, 적합성 테스트 |
