# MCP와 에이전트 시대의 보안

권한, 샌드박스, 훅이 도구 하나하나의 안전을 다룬다면, 이 문서는 더 넓은 질문을 다룬다. 외부 서비스는 어떤 경로로 연결하는 것이 안전한가, 에이전트 도구가 공격자에게도 같은 힘을 준다는 사실에 어떻게 대응할 것인가, 그리고 프로덕션에 에이전트를 풀어 놓기 전에 어떻게 신뢰를 쌓을 것인가다.

---

## 1. 외부 서비스 접근: CLI보다 MCP

Claude Code가 외부 서비스와 상호작용하는 길은 두 가지다. bash로 CLI 명령을 실행하거나, MCP 서버(Model Context Protocol, 에이전트가 외부 도구에 접근하는 표준 인터페이스)를 쓰는 것이다. 원문은 보안 측면에서 MCP 쪽이 낫다고 본다.

MCP 서버는 입력과 출력이 정의된 구조화된 도구 인터페이스를 제공한다. 모든 호출이 권한 시스템을 거치고, 훅이 가로챌 수 있고, 구조화된 로그를 남긴다. 반면 자격 증명을 넣은 `curl`을 bash로 실행하면 이런 가시성이 하나도 없다. 자격 증명이 명령 문자열에, 대화 컨텍스트에, 경우에 따라서는 모델 제공자로 가는 API 호출에까지 나타난다.

보안을 의식한 접근법은 이렇다. 민감한 데이터 소스에는 MCP 서버를 만든다. Claude에게 프로덕션 데이터베이스에 대한 bash 접근을 주지 않는다. 대신 적절한 인증, 로깅, 쿼리 제한으로 데이터베이스 접근을 감싼 MCP 도구를 준다. MCP의 전체 구조와 CLI 대비 MCP의 보안 논거는 원문 5장에서 자세히 다룬다.

## 2. 연동이 깊어질수록 커지는 마찰

Anthropic 내부의 한 법무 팀은 제품 법무 관점에서 중요한 우려를 제기했다. MCP 연동이 민감한 시스템 깊숙이 들어갈수록 보수적인 보안 태세가 장벽을 만든다는 것이다. 도구가 강력해질수록 더 많은 접근이 필요하고, 보안 정책이 만드는 마찰도 커진다.

원문의 조언은 이 긴장을 예상하고 미리 계획하라는 것이다. 사후 대응이 아니라 선제적으로 컴플라이언스 도구를 만들고, 연동이 본격적으로 늘어나기 전에 MCP 접근 거버넌스 체계를 세워 두라는 의미다.

## 3. 이중 용도(dual-use) 위험

에이전트 코딩 도구는 이중 용도 기술이다. 보안 팀이 코드를 감사하고 패치를 만드는 데 도움이 되는 바로 그 능력이, 공격자가 취약점을 찾고 익스플로잇을 만드는 데도 도움이 된다. 코드베이스 전체를 읽고, 구조를 이해하고, 정확한 변경을 하는 Claude Code의 능력은 방어에도 공격에도 똑같이 쓸모가 있다.

가정이 아니라 현실이다. 보안 연구자들은 Claude Code로 버그를 찾는다. 공격자도 같은 방식으로 쓸 수 있다. 보안 전문가가 아닌 개발자가 안전한 코드를 쓰게 해 주는 전문성의 민주화가, 보안 전문가가 아닌 사람이 취약한 코드를 찾아내게 해 주기도 한다.

## 4. 에이전트 사이버 방어

흐름은 두 방향으로 동시에 움직인다.

**방어 쪽.** 에이전트 시스템 덕분에 이전에는 전문 지식이 필요했던 보안 리뷰, 하드닝(hardening, 시스템의 약점을 줄이는 작업), 모니터링을 어떤 엔지니어든 할 수 있게 된다. 보안 배경이 없는 엔지니어도 Claude Code로 코드 경로를 감사하고, 흔한 취약점 패턴을 찾고, 강화된 구현을 만들 수 있다.

**공격 쪽.** 공격자들은 같은 도구로 공격 규모를 키울 것이다. 원문이 인용한 업계 분석의 예측은 분명하다. 자동화된 에이전트 시스템이 기계 속도의 보안 대응을 가능하게 하고, 자율적인 위협의 속도에 맞춰 탐지와 대응을 자동화한다는 것이다. 보안을 나중에 덧붙이지 않고 처음부터 에이전트 워크플로에 녹이는 조직이 같은 기술을 쓰는 공격자를 상대로 유리한 위치에 선다.

## 5. 일상이 되는 보안 리뷰

Anthropic의 보안 엔지니어링 팀은 실용적인 패턴을 보여 주었다. 인프라 코드(infrastructure-as-code) 계획을 Claude Code에 붙여 넣고 "이게 무엇을 하게 되는지, 나중에 후회할 일은 없는지"를 묻는 것이다. 배포 설정, 네트워크 정책 변경, 접근 제어 수정처럼 보안 승인이 필요한 인프라 변경이 보안 팀 대기열에서 기다리는 대신 몇 초 안에 Claude의 검토를 받는다. 피드백 고리가 짧아지고, 개발자가 보안 리뷰를 기다리며 막히는 일이 사라진다.

이것은 보안 리뷰의 대체가 아니라 보안 리뷰를 상시화하는 것이다. 파이프라인 끝에 놓인 병목 대신 만들어지는 순간에 보안 분석이 일어난다. 보안 팀은 여전히 최종 설정을 검토하지만, 뻔한 문제는 거기까지 가기 전에 Claude가 잡는다.

조직의 대응은 Claude Code를 제한하는 것이 아니다. 그러면 방어의 이점은 놓치면서 공격적 사용에는 아무런 영향도 주지 못한다. 대응은 보안 구조가 공격자가 허술하다는 가정에 의존하지 않게 하는 것이다. 공격자도 나만큼 성능 좋은 도구를 쓴다고 가정하고 방어를 세워야 한다.

## 6. 페이퍼 트레이딩: 안전한 실험 경계

페이퍼 트레이딩(paper trading)은 실제 결과 없이 실제 운영을 모의로 해 보는 것이다. 원문은 이 개념이 Claude Code 도입에 그대로 적용된다고 본다. 에이전트에게 프로덕션 시스템, 프로덕션 데이터베이스, 프로덕션 자격 증명을 주기 전에, 위험 없이 자유롭게 움직일 수 있는 경계를 먼저 만들라는 것이다.

구체적으로는 다음 환경을 쓴다.

- 합성(synthetic) 데이터를 담은 샌드박스 환경
- 프로덕션과 토폴로지는 같지만 민감한 것이 없는 스테이징 시스템
- 외부 서비스를 목(mock)으로 대체한 로컬 개발 환경

이런 곳에서는 에이전트가 자율적으로 돌고, 실수하고, 엣지 케이스를 발견하고, 죽어도 결과가 없다. 에이전트를 자율 루프로 오래 돌려 본 실무자들의 경험은 한결같다. 페이퍼 트레이딩부터 시작하고, 안전한 환경에서 동작을 검증하고, 경계를 점진적으로 넓히라는 것이다.

신뢰 구조는 이런 진행을 뒷받침한다. 최대한 제한한 상태로 시작해서 확신이 쌓이는 만큼 제약을 푼다.

## 7. 신뢰의 기울기

권한 시스템, 샌드박스 격리, 훅, Managed 설정이 합쳐져 하나의 기울기(gradient)를 만든다. 한쪽 끝은 "Claude Code가 묻지 않고는 아무것도 할 수 없다"이고, 반대쪽 끝은 "이 격리된 환경 안에서는 무엇이든 할 수 있다"이다. 어느 지점이 맞는지는 내 상황, 위험 감수 수준, 그리고 안전한 환경에서 얼마나 검증했는지에 달려 있다.

장 첫머리의 목표로 돌아가면, 이 장을 읽은 뒤에는 Claude Code가 기본으로 내놓은 설정도, 확인창이 귀찮아서 바꾼 전부 열린 설정도 아닌, 실제 위험 감수 수준에 맞는 권한 구성을 설계할 수 있어야 한다.

## 8. 정리

- 민감한 시스템은 bash CLI 대신 MCP 도구로 감싸서 권한, 훅, 로그의 대상이 되게 한다.
- 에이전트 도구는 이중 용도다. 방어자도 공격자도 쓴다고 가정한다.
- 보안 리뷰는 파이프라인 끝의 병목이 아니라 만드는 순간의 일상 작업으로 만든다.
- 프로덕션 접근 전에 합성 데이터와 스테이징에서 먼저 검증하고, 경계를 점진적으로 넓힌다.
