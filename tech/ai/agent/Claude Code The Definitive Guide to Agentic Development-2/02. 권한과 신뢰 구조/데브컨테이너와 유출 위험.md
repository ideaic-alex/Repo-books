# 데브컨테이너와 유출 위험

사람이 명령마다 승인하지 않아도 CI에서 Claude Code를 자율적으로 돌리려면 어떻게 해야 할까. 원문이 내놓는 기업용 답은 권한 시스템을 없애는 것이 아니라, 실행 환경을 네트워크 격리로 감싸는 것이다.

이 문서는 데브컨테이너(devcontainer, 개발 환경을 컨테이너로 정의해 두는 방식) 모델이 무엇을 막아 주고, 설정으로도 완전히 해결되지 않는 자격 증명 유출 문제가 왜 남는지 설명한다.

---

## 1. 데브컨테이너의 보안 모델

데브컨테이너는 기본 거부(default-deny) 방화벽으로 네트워크 수준의 격리를 제공한다. 설정으로 Claude Code가 닿을 수 있는 호스트를 제한하면, `--dangerously-skip-permissions` 옵션을 쓰더라도 덜 위험해진다. 컨테이너 자체가 피해 범위를 제한하기 때문이다.

`--dangerously-skip-permissions`는 이름 그대로 권한 확인을 모두 건너뛰는 옵션이다. 보통은 위험해서 피하지만, 격리된 컨테이너 안이라면 이야기가 달라진다.

이 방식의 사고방식은 다음과 같다.

- 권한 시스템을 걷어내지 않는다.
- 대신 실행 환경에 네트워크 격리를 입힌다.
- 그러면 제약 없이 동작하더라도 닿아서는 안 되는 곳에는 닿지 못한다.

## 2. Anthropic의 참조 구현

Anthropic은 참조용 데브컨테이너 구현을 제공한다. 구성은 다음과 같다.

- 네트워크 접근을 제한하는 맞춤 방화벽
- 세션 유지(session persistence)
- 에디터 연동이 미리 설정되어 있음

CI 파이프라인, 보안에 민감한 프로젝트, 헤드리스(headless, 화면 없이 돌아가는) 자율 워크플로처럼 격리된 환경에서 Claude Code를 돌려야 하는 조직이 출발점으로 쓰도록 만들어졌다.

## 3. 유출 주의점

원문은 문서 자체가 직접 인정하는 불편한 사실을 말한다. 데브컨테이너는 악의적인 프로젝트로 인한 자격 증명 유출을 막지 못한다.

시나리오는 이렇다. 프로젝트 코드 안에 Claude Code가 자격 증명을 읽어 출력에 인코딩하도록 유도하는 지시가 들어 있고, 그 출력이 허용된 엔드포인트에 닿는다고 하자. 컨테이너 방화벽은 이를 막지 못한다. 데이터가 승인된 통로로 나가기 때문이다.

이것은 이론에 그치지 않는다. 코드 주석이나 README 파일에 지시를 심는 공급망(supply chain) 공격은 이미 알려진 경로다. 데브컨테이너는 우발적인 네트워크 접근은 막지만, 에이전트가 실행하는 프로젝트 코드가 의도적으로 벌이는 악용은 막지 못한다.

## 4. 해법은 겹겹의 방어

원문이 제시하는 완화책은 층을 겹치는 것이다.

1. `permissions.deny`로 민감 파일을 제외해서, 자격 증명을 읽는 것 자체를 막는다.
2. 컨테이너 격리로, 데이터가 나갈 수 있는 곳을 제한한다.

어느 한쪽만으로는 충분하지 않지만 둘을 함께 쓰면 공격의 문턱이 크게 높아진다. 읽지 못하게 하는 층과 나가지 못하게 하는 층이 서로의 빈틈을 메우는 구조다.

## 5. 정리

- 컨테이너 방화벽은 에이전트가 의도치 않게 외부로 접속하는 사고에 강하다.
- 허용된 통로를 이용한 의도적 유출에는 방화벽이 무력하다.
- 그래서 읽기 제한과 네트워크 격리를 함께 적용한다.
- 신뢰할 수 없는 프로젝트를 에이전트에게 실행시킬 때는 특히 이 점을 의식한다.
