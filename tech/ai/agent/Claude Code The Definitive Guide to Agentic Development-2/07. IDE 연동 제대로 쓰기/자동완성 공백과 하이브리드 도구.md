# 자동완성 공백과 하이브리드 도구

Claude Code에는 한 가지 분명한 빈자리가 있다. 타이핑하는 동안 에디터에 회색 제안이 떠오르는 인라인 자동완성이다. 책은 이것을 결함이 아니라 설계의 결과로 설명하고, 해법으로 도구를 나눠 쓰는 하이브리드 구성을 권한다. 이 문서는 자동완성 공백의 이유, IDE와 터미널을 고르는 기준, 디자인 도구와 같이 쓰는 방식, 스킬(skills)의 에이전트 간 표준, 그리고 하이브리드 구성이 앞으로도 유지될 것이라는 전망을 정리한다.

---

## 1. 자동완성 공백

Claude Code에는 스트리밍 인라인 자동완성이 없다. 몇 글자를 치면 제안될 완성 문장이 회색 유령처럼 나타나고, 키를 누를 때마다 갱신되는 경험은 Claude Code가 하는 일이 아니다.

이것은 실수로 빠진 것이 아니라 구조에서 나온 결과다. Claude Code의 강점은 여러 파일과 도구에 걸친 에이전트형 다단계 작업이다. 인라인 자동완성은 완전히 다른 상호작용 방식이다. 지연이 아주 짧아야 하고, 한 줄 단위이며, 글자 하나씩 예측한다. 이 둘을 한 도구에서 잘 만들려면 모델 구성, 인프라, UX가 모두 달라야 한다.

그래도 이 공백은 의미가 있다. 인라인 자동완성은 실제로 유용하기 때문이다. 상용구 코드(boilerplate)를 쓰고, 함수 시그니처를 채우고, 변수 이름을 완성하는 등 프롬프트를 쓰고 실행시킬 만큼은 아닌 수많은 작은 편집에서 좋은 자동완성 도구는 시간을 실제로 줄여 준다.

## 2. 권장하는 하이브리드 구성

책이 권하는 방식은 도구를 섞어 쓰는 것이다.

- **Claude Code**: 저장소 전체 리팩터링, 복잡한 구현, 코드베이스 탐색, 아키텍처 계획, 자동화된 작업 흐름처럼 에이전트형 다단계 다중 파일 작업.
- **인라인 자동완성 전문 도구**: 함수 시그니처, 변수 이름, 상용구 코드 같은 글자 단위 편집.

두 도구는 충돌하지 않는다. 상호작용의 규모가 다를 뿐이다. 책은 하나는 숲을, 다른 하나는 나뭇잎 하나하나를 맡는다고 비유한다.

책은 이 구성이 임시방편이 아니라고 강조한다. 모든 상호작용 규모를 지배하는 도구는 없고, 그렇다고 믿으면 단순한 도구가 더 잘할 일에 강력한 도구를 서툴게 쓰게 된다. 에이전트형 코딩과 인라인 완성은 서로 최적화 목표가 달라서 한 도구에서 둘 다 훌륭하게 만들면 반드시 한쪽을 희생하게 된다는 것이다.

### 앞으로의 전망

책은 Claude Code의 인라인 IDE 경험이 앞으로 더 적극적으로 바뀔 것이라고 예측한다. 파일 단위 편집 모드, 영역 단위 재작성, 더 촘촘한 에디터 연동 같은 것이다. 하지만 화면이 서로 비슷해져도 안쪽 구조는 계속 서로 다른 규모의 상호작용에 맞춰 최적화된다. 그래서 하이브리드 방식은 일시적인 타협이 아니라 안정된 최종 형태라고 본다.

## 3. IDE를 쓸 때와 터미널로 내려갈 때

기준은 보이는 것보다 단순하다.

| IDE 확장을 쓰는 경우 | 터미널로 내려가는 경우 |
|---|---|
| 여러 파일의 diff를 시각적으로 검토해야 할 때 | IDE 확장에 없는 CLI 플래그가 필요할 때 |
| @-멘션으로 특정 코드 위치를 가리킬 때 | 병렬 세션을 여러 개 돌릴 때 |
| 파일 안의 변경을 일부만 수락하거나 거절하고 싶을 때 | 입출력을 다른 도구와 파이프로 연결할 때 |
| 플랜 검토에서 인터랙티브 체크리스트를 쓰고 싶을 때 | 자동화나 스크립트 연동이 필요할 때 |
| IDE가 더 편한 팀원과 함께 일할 때 | 피드백 루프를 가장 빠르게 돌리고 싶을 때 |
| | diff 검토보다 대화 흐름이 중요한 탐색 작업을 할 때 |

대부분의 세션은 터미널에서 시작한다. 일부는 검토를 위해 IDE로 옮겨 간다. IDE에서 시작해 거기에 머무는 경우는 드물다. 책은 이것이 IDE의 품질에 대한 평가가 아니라고 한다. 에이전트형 코딩은 본질적으로 대화이고, 대화는 터미널에서 가장 자연스럽게 흐르기 때문이다.

## 4. 디자인 도구와 같이 쓰는 방식

팀들은 시각적인 디자인 도구와 Claude Code를 약 80%의 시간 동안 동시에 열어 둔다고 보고한다. 디자인 도구는 시각적 기준(목업, 레이아웃, 컴포넌트 디자인)을 주고, Claude Code는 그 디자인이 보여 주는 것을 구현한다.

이것은 전통적인 의미의 IDE 연동이 아니다. 두 도구가 서로 연결되지 않은 채 상호 보완하는 작업 방식이다. 사람이 연동 계층이 되어 디자인을 보고 무엇을 만들어야 하는지 Claude Code에게 말한다.

이 방식이 통하는 이유는 Claude Code가 이미지를 입력으로 받기 때문이다. 디자인 목업의 스크린샷을 대화에 붙여 넣으면 Claude가 레이아웃, 색상, 간격, 컴포넌트 구조를 해석할 수 있다. 말로 디자인을 설명하는 것보다 빠르다. 다만 명시적인 구현 요구사항을 대신하지는 못한다.

디자인에서 코드로 가는 흐름은 1장의 4단계 패턴을 따른다. 기존 코드베이스의 컴포넌트를 탐색하고, 구현 방법을 계획하고, 디자인을 구현하고, 커밋한다. 디자인 도구는 탐색 단계에 시각적 기준을 더해서 뒤 단계가 더 탄탄하게 이어지게 한다.

## 5. 스킬은 에이전트 사이의 공통 표준

스킬은 Claude Code만의 기능이 아니다. 여러 AI 코딩 에이전트가 지원하는 공통 표준이다. Claude Code용으로 쓴 스킬이 표준을 지원하는 다른 에이전트에서도 동작하고, 지원하는 에이전트는 계속 늘고 있다. 스킬을 만드는 투자가 한 도구에 묶이지 않는다는 뜻이다.

설치는 에이전트에 상관없이 쓸 수 있는 패키지 러너 명령으로 한다.

```
npx skills add <repository-url> --skill <skill-name>
```

이 명령은 다음을 순서대로 한다.

1. 저장소를 복제한다.
2. 사용할 수 있는 스킬을 찾는다. 보통 저장소 하나에 열두 개 이상 들어 있다.
3. 호환되는 에이전트를 감지한다.
4. 설치 범위가 프로젝트인지 사용자인지 묻는다.
5. 스킬 디렉터리 구조를 만든다.

이렇게 설치한 스킬은 심볼릭 링크로 걸거나 복사할 수 있고, Claude Code를 재시작하지 않아도 바로 동작한다.

실용적인 결과도 있다. AI 코딩 도구를 여러 개 쓰는 팀은 도구별 설정을 따로 만들지 않고 스킬로 작업 방식을 표준화할 수 있다. 코드 리뷰 스킬, 배포 작업 흐름, 문서 생성기가 어느 에이전트에서 돌든 똑같이 동작한다. 여러 도구를 시험하는 비용이 줄고, 작업 방식이 한 도구에 묶이는 것도 막을 수 있다.

## 6. 정리: 터미널을 중심에 두고 도구를 겹쳐 쓰기

지금까지의 내용을 한 줄로 줄이면 이렇다. 터미널에서 Claude Code를 본거지로 삼고, 검토가 필요할 때 IDE나 데스크톱 앱을 꺼내 쓰고, 글자 단위 편집은 인라인 자동완성 도구에 맡긴다. 오래 걸리는 일은 클라우드에 보내고 휴대폰으로 지켜본다. 디자인이 있다면 디자인 도구를 옆에 열어 두고 스크린샷을 붙여 넣는다. 도구 하나가 모든 규모의 작업을 다 해 주리라 기대하지 않는 것이 이 장이 말하는 성숙한 방식이다.
