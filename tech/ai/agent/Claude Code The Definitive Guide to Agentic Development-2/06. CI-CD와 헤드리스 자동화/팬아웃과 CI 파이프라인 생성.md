# 팬아웃과 CI 파이프라인 생성

헤드리스 모드의 활용법 중 두 가지를 다룬다. 하나는 파일 하나마다 Claude Code를 한 번씩 부르는 팬아웃(fan-out) 패턴이고, 다른 하나는 CI 설정 파일 자체를 Claude Code에게 만들게 하는 방식이다. 보안 스캔을 CI에 넣을 때 무엇을 Claude에게 맡기고 무엇을 사람이 정해야 하는지도 함께 정리한다.

두 주제 모두 결과를 바로 검증할 수 있다는 점에서 헤드리스 자동화에 잘 맞는다.

---

## 1. 팬아웃 패턴

팬아웃은 파일 집합을 순회하면서 파일마다 범위를 좁힌 권한으로 Claude Code를 한 번씩 호출하는 방식이다. AI로 하는 일괄 처리라고 보면 된다.

```bash
for file in $(find src -name '*.ts' -type f); do
  claude -p "Review $file for security vulnerabilities" \
    --allowedTools "Read,Grep,Glob" \
    --output-format json >> reviews.jsonl
done
```

열쇠는 `--allowedTools` 플래그다. 이번 실행에서 Claude Code를 읽기 전용 도구로 제한한다. 파일을 읽고, 코드베이스를 검색하고, 패턴을 grep할 수는 있지만 아무것도 수정하지 못한다. 위험할 수 있는 일괄 작업이 안전한 분석 작업으로 바뀐다.

팬아웃이 잘 맞는 작업은 다음과 같다.

- 수백 개 파일에 대한 보안 감사
- 모듈별 문서 생성
- 컴포넌트별 테스트 커버리지 분석
- 코딩 표준 준수 여부 점검

호출할 때마다 새로운 컨텍스트에서 시작하고, 파일 하나에 집중하며, 그 작업에 딱 필요한 만큼만 권한을 받는다. 파일이 많아도 컨텍스트 윈도가 서로 오염되지 않는다는 장점이 있다.

결과가 줄바꿈으로 구분된 JSON이기 때문에 표준 유닉스 도구와 조합하기 좋다. 분석 도구에 파이프로 넘기거나 걸러 내거나 집계할 수 있다. 팬아웃을 돌리고, 심각도가 높은 결과만 걸러서, 항목마다 이슈를 여는 CI 작업은 셸 스크립트와 CLI만으로 충분히 만들 수 있다.

---

## 2. CI 파이프라인 생성

Claude Code는 CI 설정을 만드는 데 효과적이다. 프로젝트 구조를 읽고, 빌드 도구를 이해하고, 올바른 YAML(또는 그에 준하는 형식)을 만들어 내는 능력이 합쳐져서, 원하는 바를 설명하면 동작하는 파이프라인이 나온다. 대상은 CI 워크플로 정의, 컨테이너 이미지 설정, 인프라 as 코드(IaC) 템플릿, 보안 스캔 설정까지 넓다. 프로젝트의 의존성, 테스트 설정, 배포 대상을 읽고 거기에 맞는 파이프라인 정의를 만든다.

잘 되는 이유는 CI 설정이 구조는 뚜렷하고 모호함은 적은 일이기 때문이다. 스키마가 명확하고, 관례가 안정적이며, 결과를 테스트할 수 있다. 커밋하기 전에 생성된 YAML을 CI 시스템의 스키마로 검증해 볼 수 있다.

평범한 프로젝트에 CI/CD 파이프라인을 요청하면 다음과 같은 결과가 나온다(일부 발췌).

```yaml
name: CI/CD Pipeline
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Install dependencies
        run: npm ci
      - name: Lint
        run: npm run lint
      - name: Type check
        run: npm run type-check
      - name: Unit tests
        run: npm test
```

전체 파이프라인에는 이어서 `Build` 단계가 있고, 그다음 `deploy` 작업이 `needs: test`와 `if: github.ref == 'refs/heads/main'` 조건으로 붙는다. deploy 작업은 체크아웃 후 Docker 이미지를 `myapp-api:${{ github.sha }}` 태그로 빌드하고, 레지스트리에 푸시하고, `kubectl set image`로 staging 네임스페이스의 `deployment/app-api`에 배포한다.

Claude Code는 lint, type-check, test, build, deploy 단계를 의존 순서까지 맞춰 전체 구조를 한 번에 만든다. 사용자는 검토하고, 자격 증명과 환경별 세부 사항만 조정하고, 머지하면 된다. 생성된 설정은 대폭 고쳐야 하는 초안이 아니라, 프로젝트의 실제 빌드 단계를 반영한 동작하는 파이프라인이다. 생성 전에 Claude Code가 프로젝트 설정을 읽었기 때문이다.

---

## 3. 반복하며 다듬기

더 흥미로운 점은 반복적 개선이다. 초기 파이프라인을 만들고, 돌려 보고, 실패를 관찰하고, 에러 출력을 다시 Claude Code에 넘기면 설정을 고쳐 준다. 이 피드백 루프는 YAML 들여쓰기 오류나 문서화되지 않은 설정 옵션을 손으로 디버깅하는 것보다 빨리 동작하는 파이프라인에 수렴한다.

실전 예를 보자. 서비스 세 개가 들어 있는 모노레포가 있고, 서비스마다 테스트 스위트, 컨테이너 이미지, 배포 대상이 따로 있다. 바뀐 경로에 따른 조건부 빌드, 병렬 테스트 실행, 롤백 관문이 있는 단계별 배포까지 포함한 CI 설정을 손으로 쓰면 하루가 걸리는 일이다. Claude Code는 저장소 구조를 읽고 서비스 경계를 파악해서 한 세션에 전체 파이프라인 설정을 만든다. 방금 읽은 프로젝트 구조를 이해하고 있기 때문에 조건부 로직, 병렬 처리, 배포 순서가 함께 처리된다.

컨테이너 이미지 생성도 같은 방식이다. 애플리케이션 코드를 읽고 의존성을 파악해서 적절한 베이스 이미지를 고르고, 레이어 캐싱이 올바르게 걸린 멀티 스테이지 빌드 파일을 만든다. 인프라 as 코드 도구라면 설명한 아키텍처에 맞는 리소스 정의를 만들어 준다.

---

## 4. 보안 스캔 통합

보안 스캔 설정은 특별히 짚어 둘 만하다. Claude Code가 단계를 만들고, 규칙은 사람이 정하는 영역이기 때문이다.

스캔 범주마다 방식이 다르다. 정적 애플리케이션 보안 테스트(SAST) 도구는 CI 워크플로에 바로 들어가며, Claude Code가 스캔 단계를 추가하면 결과가 PR 코멘트로 나타난다. 의존성 감사 도구(패키지 관리자용, 언어 생태계용 모두)는 빌드 단계에서 추가 검증으로 들어간다. 컨테이너 이미지 스캔 도구는 레지스트리에 올라가기 전에 빌드된 이미지를 검사한다.

| 범주 | Claude가 만드는 것 | 사람이 정하는 것 |
|---|---|---|
| 정적 분석 | 스캐너를 호출하는 CI 워크플로 단계 | 룰셋과 심각도 임계값 |
| 의존성 감사 | 취약점 점검을 하는 빌드 단계 명령 | 허용할 권고 목록과 예외 정책 |
| 컨테이너 스캔 | 빌드 후 이미지를 검사하는 스캔 단계 | 수용 가능한 위험 수준과 베이스 이미지 정책 |
| 런타임 규정 준수 | 맞춤 점검 스크립트 | 준수 규칙과 집행 정책 |
| 시크릿 탐지 | 플랫폼의 기본 기능 사용 | 저장소 수준 설정 |

권장 사항은 CI 워크플로에 처음부터 보안 스캔을 넣으라는 것이다. Claude Code가 통합 단계를 만들고, 스캔 도구가 결과를 내고, 결과가 임계값을 넘으면 CI 시스템이 머지를 막는다. 시크릿 탐지만은 예외다. 직접 만든 구현보다 플랫폼 자체의 시크릿 스캔이 더 믿을 만하다.

---

## 5. 핵심 통찰

CI 설정은 헤드리스 Claude Code의 투자 대비 효과(ROI)가 가장 높은 용도 중 하나다. 결과를 즉시 테스트할 수 있기 때문이다. 파이프라인을 돌리면 되거나 안 되거나 둘 중 하나다. 품질을 두고 주관적으로 판단할 일이 없다. 피드백 루프가 짧고 모호함이 없다.
