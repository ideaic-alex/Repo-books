# 맡길 일과 직접 할 일 구분

Claude Code가 모든 일을 똑같이 잘하는 것은 아니다. 어떤 부분은 지금 바로 맡겨서 운영 환경에 올려도 되고, 어떤 부분은 사람이 함께 봐야 하고, 어떤 부분은 조심해서 다가가야 한다. 이 문서는 그 경계를 컴포넌트 단위로 나눠 보고, 판단용 체크리스트와 시점별 도구 선택 기준을 정리한다.

뒤에서는 같은 직관을 비동기와 동기라는 작업 분류로 풀어서, Anthropic 제품 개발 팀이 만든 분류 기준을 소개한다.

---

## 1. 70~80% 커버리지 격차

원문은 Claude Code가 오늘날 프로덕션 스택의 약 70~80%를 만들 수 있다고 본다. 나머지 20~30%에서 경험 많은 개발자가 제 몫을 한다.

실수하기 쉬운 지점은 이 격차를 추상적으로 생각하는 것이다. 격차는 컴포넌트마다 다르고, 무엇을 만드느냐에 따라 적합도가 크게 달라진다. 프런트엔드, 백엔드, 인프라 계층을 가진 일반적인 프로덕션 애플리케이션을 놓고 컴포넌트별로 보면 다음과 같다.

## 2. Claude Code가 잘하는 영역 (지금 만들어서 운영에 올린다)

| 영역 | 이유 |
|------|------|
| 프런트엔드 스캐폴딩 | 컴포넌트 구조, 폼, 대시보드, 상태 관리. 컨벤션이 잘 확립된 표준 패턴이다 |
| API 스캐폴딩 | CRUD 엔드포인트, 라우트 정의, 미들웨어, 요청 검증. 패턴이 예측 가능하고 검증하기 쉽다 |
| 데이터베이스 스키마 설계 | 마이그레이션, 모델, 인덱싱 전략, 관계 정의. 적절한 제약과 불변성(immutability) 패턴을 갖춘 스키마를 만든다 |
| 테스트 생성 | 단위·통합 테스트, 픽스처. 성공 기준이 분명해 에이전트 루프에 이상적이다 |
| DevOps 설정 | 컨테이너 정의, CI 파이프라인 정의, 배포 스크립트. 템플릿 중심이고 결과를 검증할 수 있다 |
| 문서화 | API 문서, README, 코드 주석, 변경 이력. 코드를 읽고 하는 일을 설명하는 작업이다 |

## 3. 사람과 함께 해야 하는 영역 (하이브리드)

- **연결 관리가 필요한 실시간 시스템**: Claude가 구조는 잡아 주지만, 연결 생명주기, 백프레셔(backpressure) 처리, 장애 조치(failover) 로직은 사람이 검토한다.
- **성능이 중요한 경로**: 올바른 코드는 만들어 주지만 빡빡한 지연 시간 예산에 맞추는 최적화는 측정과 반복이 필요하고, 여기서는 사람의 판단이 도움이 된다.
- **보안에 민감한 로직**: 인증 흐름, 암호화, 접근 제어. 보일러플레이트는 Claude가 처리하지만 보안 검토는 사람 몫이다.
- **도메인 특화 프로토콜과 표준**: 전문 프로토콜은 도메인 지식이 필요하다. Claude가 비슷하게 흉내 낼 수는 있어도 보장하지는 못한다.

## 4. 조심해서 진행할 영역

- 확립된 패턴이 없는 새로운 알고리즘. Claude는 무언가를 내놓겠지만 참고할 구현이 없으면 미묘하게 틀릴 수 있다.
- 마이크로초가 중요한 초저지연 컴포넌트. Claude는 프로파일링을 하지 않는다. 사람이 한다.
- 실패 양상이 "동작은 하는데 틀렸고, 그 사실을 나중에야 비싸게 알게 되는" 모든 것.

## 5. 빠른 판단 체크리스트

특정 컴포넌트를 Claude Code로 만들지 평가할 때는 다음 질문을 순서대로 짚는다.

| 질문 | 판단 |
|------|------|
| 성공 기준이 분명한가? 테스트 통과, 타입 체크, 린터 만족 | 바로 만든다 |
| 실시간 데이터 처리가 필요한가? | Claude가 컴포넌트를 만들고, 연결 관리는 사람이 맡는다 |
| 지연 시간 예산이 빡빡한가? | Claude가 뼈대를 만들고, 프로파일링과 최적화는 사람이 한다 |
| 확립된 패턴이 있는가? | 있으면 Claude가 잘한다. 없으면 신중히 진행한다 |
| 정확성이 필수인데 검증이 어려운가? | 사람의 검토가 선택이 아니라 필수다 |

어느 범주인지 알아보는 것 자체가 기술이다. 이 분류에 직관이 생긴 개발자는 더 빨리 출시한다. 사람의 판단이 꼭 필요한 일을 두고 Claude와 씨름하느라 시간을 쓰지 않고, Claude가 몇 초 만에 만들 코드를 손으로 쓰느라 시간을 쓰지도 않기 때문이다.

## 6. 지금 만들 것과 기다릴 것

아직 현재 도구에서는 프로덕션 수준이 아닌 기능도 곧 나온다. 현실적인 접근은 그 차이를 아는 것이다.

- **지금 Claude Code로 만든다**: 저장소 전체 리팩터링, API 스캐폴딩, 테스트 생성, 데이터베이스 마이그레이션, 배포 설정, 문서화, 컴포넌트 구조, 그리고 검증이 자동화된 모든 작업.
- **당분간 하이브리드 도구 체인을 쓴다**: 타이핑하면서 받는 인라인 코드 제안(IDE에 통합된 자동완성 도구를 Claude Code와 함께 쓴다), 브라우저 기반 end-to-end 테스트(Claude Code가 테스트 스크립트를 작성하고, 실행과 검증은 사람이 한다), 더 성숙한 UI가 필요한 복잡한 멀티 에이전트 조율.
- **개선을 기다린다**: 네이티브 CI 자동 수정 파이프라인(통합이 나올 예정), 이슈에서 풀 리퀘스트까지 자동화하는 봇(워크플로가 조각으로는 있지만 아직 다듬어지지 않았다), 병렬 에이전트 작업을 시각적으로 관리하는 더 풍부한 멀티 에이전트 조율 UI.

가장 빨리 출시하는 개발자는 오늘 잘하는 일에는 Claude Code를 공격적으로 쓰고, 현재의 빈틈은 다른 도구로 보완하고, 몇 달 안에 기본 기능이 될 것을 위해 깨지기 쉬운 임시 우회책을 만들지 않는 사람이다.

## 7. 비동기 작업과 동기 작업

모든 작업에 같은 수준의 주의를 쏟을 필요는 없다. 경험 많은 팀은 어떤 작업을 비동기(asynchronous, 맡겨 놓고 잊기)로 돌리고 어떤 작업을 동기(synchronous, 실시간 감독)로 할지 직감을 키운다.

**비동기 후보.** 기존 코드의 테스트 생성, 문서 갱신, 보일러플레이트 스캐폴딩, 패턴이 분명한 마이그레이션 스크립트, 의존성 업데이트, 코드 포맷팅과 린트 수정. 성공 기준이 명확하고 미묘한 오류의 위험이 낮은 작업이다. 자동 수락 모드로 돌려 놓고 끝나면 결과를 확인한다.

**동기 후보.** 핵심 비즈니스 로직, 보안에 민감한 변경, 아키텍처 결정, 성능 최적화, 그리고 실패가 조용히 일어나는 모든 일(코드는 돌아가는데 결과가 틀리는 경우). 이런 작업은 사람이 지켜보고, 반응하고, 실시간으로 방향을 바로잡아야 한다.

### 제품 팀의 분류 기준표

Anthropic의 제품 개발 팀은 이 직관을 기준표로 만들었다.

- 제품 주변부 작업(새 설정 패널, 프로토타입 기능, 주변 UI 컴포넌트)은 자동 수락 모드로 보낸다.
- 개발자가 낯설어하는 추상적인 문제도 좋은 후보다. 자율 모드에서 Claude가 시도해 보는 탐색이 사람의 추측보다 빨리 올바른 접근을 찾아내는 경우가 많다.
- 핵심 비즈니스 로직, 사용자에게 중요한 핵심 기능, 스타일 가이드 준수와 아키텍처 일관성이 중요한 작업은 동기 감독으로 한다. 개발자가 지켜보다가 필요하면 끼어들어 Claude가 전체 설계 의도에서 벗어나지 않게 한다.

이 분류는 고정되어 있지 않다. 비동기로 시작한 작업이 Claude가 예상치 못한 엣지 케이스를 만나면 동기로 바뀔 수 있다. 동기로 시작한 작업도 접근법이 마음에 들고 여러 파일에 적용만 하면 되는 단계가 되면 비동기로 바뀔 수 있다. 내 주의와 Claude의 권한 설정, 양쪽에서 모드를 오갈 수 있어야 워크플로가 유연해진다.
