# 자율 실행과 80퍼센트 인계

권한 모드를 높이면 Claude Code는 사람의 개입 없이 코드를 쓰고, 테스트를 돌리고, 실패를 읽고, 고치는 일을 반복할 수 있다. Anthropic의 제품 개발 팀과 보안 엔지니어링 팀은 이 자율 루프를 실무에 적용했다. 이 문서는 그 방식과 전제 조건을 정리한다.

이어서 "AI를 쓴다"와 "AI에게 맡긴다"가 얼마나 다른지 보여 주는 숫자, 그리고 완전 위임이 어려운 이유를 설명한다. 마지막으로 코드가 아닌 일에서도 Claude Code를 반복적인 사고 파트너로 쓰는 모델을 다룬다.

---

## 1. 자율 루프와 80퍼센트 인계

Anthropic의 제품 개발 팀은 자동 수락 워크플로를 한 단계 더 밀고 나갔다. 엔지니어들이 전체 자동 수락 모드를 켜고, Claude가 코드를 쓰고, 테스트 스위트를 돌리고, 실패를 읽고, 계속 반복하는 자율 루프를 구성한다. 익숙하지 않은 추상적인 문제를 Claude에게 던져 놓고 알아서 일하게 한 다음, 대략 80% 완성된 시점에 결과를 검토한다. 마지막 20%는 직접 마무리한다. 판단이 필요한 결정, 설계 다듬기, 도메인 지식이 필요한 엣지 케이스가 거기에 속한다.

### 이 방식의 두 가지 전제

- **깨끗한 git 상태에서 시작한다.** 실행이 엉뚱한 방향으로 흘러가도 전체를 되돌릴 수 있어야 한다.
- **Claude가 일하는 중에 커밋하게 한다.** 중간 체크포인트가 생긴다.

Anthropic의 보안 엔지니어링 팀은 이를 자율 세션을 시작할 때 Claude에게 주는 한 줄 지시로 압축했다. "commit your work as you go"다. 코드 조각을 얻으려고 좁은 질문을 던지는 대신 Claude가 중간중간 확인만 받으며 자율적으로 일하게 하고, 점진적인 커밋이 남기는 기록을 보면서 필요할 때 검토하고, 골라서 가져오고(cherry-pick), 되돌린다.

## 2. 협업의 역설

불편한 숫자가 하나 있다. 연구에 따르면 개발자는 업무의 약 60%에서 AI 보조 도구를 쓴다. 그런데 문제를 넘기고 자리를 떠나도 될 만큼 완전히 위임할 수 있는 비율은 0~20%에 그친다.

이것은 도구의 실패가 아니라 일의 성격이다. 소프트웨어 엔지니어링은 판단 집약적인 활동이다. 구현을 Claude Code가 맡아도 사람은 여전히 해야 할 일이 있다.

- 문제를 올바르게 정의한다.
- 해법이 적절한지 평가한다.
- 어떤 트레이드오프를 받아들일지 정한다.
- 기술적으로는 맞지만 전략적으로는 틀린 코드를 잡아낸다.

60%라는 수치는 Claude가 하루 대부분 곁에서 도움이 된다는 뜻이다. 일의 60%가 자동화된다는 뜻이 아니다. AI는 상시 협업자이지만, 제대로 쓰려면 신중한 준비, 적극적인 감독, 검증, 사람의 판단이 필요하고, 위험도가 높은 일일수록 더 그렇다.

## 3. 반복형 파트너 모델

가장 힘들어하는 사람은 완전 위임을 기대했다가 그렇게 되지 않아 좌절하는 사람이다. 잘 쓰는 사람은 반복형 파트너 모델을 받아들인다. Claude가 제안하고, 내가 반응하고, Claude가 조정하고, 내가 승인한다. 이건 인계가 아니라 대화다.

한 작업 안에서도 마찬가지다. 초기 구현은 맡기고, 디버깅은 지켜보고, 까다로운 엣지 케이스는 직접 넘겨받고, 테스트 커버리지는 다시 맡길 수 있다. 사람의 일과 기계의 일 사이의 경계는 깨끗한 선이 아니다. 계속 오가는 협상이고, 그 협상 자체가 일의 일부다.

## 4. 사고 파트너 모델: 코드가 아닌 일

Claude Code의 쓰임은 코드 작성에 그치지 않는다. 원문은 소프트웨어가 아니라 재무 계획을 세우는 데 Claude Code를 쓴 사례를 든다. 사용자는 여러 계좌에서 내려받은 스프레드시트를 넣고, 목표와 제약을 설명하고, 여러 세션에 걸쳐 반복적으로 작업해 단계별 최적화 계획을 만들었다. 세금 영향 분석, 펀드 추천, 전후 자산 배분 표까지 포함된 결과물로, 전문 자문가에게 돈을 내고 받을 만한 수준이었다.

상호작용은 "질문하고 답을 얻는" 방식이 아니었다. 데이터는 다 갖고 있지만 그 계좌들과 함께 살아 본 적은 없는 분석가와 일하는 것과 비슷했다. 사용자가 설명을 보태고 제약을 다시 잡으면 Claude는 모든 계산과 표와 추천을 실시간으로 갱신한다. 코드가 아니라 분석에 적용한 반복적 사고 파트너십이다.

이 모델, 즉 한 번에 정답을 내놓는 도구가 아니라 반복하며 다듬는 분석가로서의 Claude는 데이터를 처리하고, 제약을 적용하고, 피드백으로 결과물을 다듬는 모든 영역에 통한다. 코드가 가장 흔한 사례일 뿐이고, 데이터 분석, 기술 문서 작성, 인프라 계획처럼 결과물의 품질이 대화의 품질에 달린 일이면 이 사고방식이 그대로 옮겨 간다.

## 5. 백지 말고 초안을 준다

핵심 통찰은 이렇다. 잘 쓰는 사람은 Claude에게 백지가 아니라 거친 제안을 출발점으로 준다. 접근 방식의 스케치, 임시로 세운 아키텍처, 덜 다듬어진 아이디어도 좋다. Claude는 아무것도 없는 데서 만들어 내는 것보다 제안을 다듬는 쪽이 더 빠르고 정확하다. 의견이 있으면 말하고, 의심 가는 게 있으면 공유한다. 출력 품질은 입력의 구체성에 정비례한다.

## 6. 정리

| 항목 | 내용 |
|------|------|
| 자율 루프 | 코드 작성, 테스트, 실패 읽기, 반복. 약 80%에서 사람이 검토하고 나머지 20%는 직접 마무리 |
| 전제 | 깨끗한 git 상태, 작업 중 커밋("commit your work as you go") |
| 협업의 역설 | AI 사용은 업무의 약 60%, 완전 위임 가능은 0~20% |
| 올바른 모델 | 제안, 반응, 조정, 승인의 반복. 인계가 아니라 대화 |
| 적용 범위 | 코드 외에도 분석, 문서, 인프라 계획 등 대화로 다듬는 모든 일 |
