# 프롬프트 제안과 단순함의 원칙

이 문서는 Claude의 응답 아래에 흐릿하게 나타나는 후속 제안을 어떻게 활용할지, 그리고 Claude가 지나치게 복잡한 해법으로 흐르는 경향을 어떻게 다룰지 정리한다. 둘 다 사소해 보이지만 일상적인 효율에 직접 영향을 준다.

둘을 관통하는 원칙은 Claude Code가 자유보다 제약에 더 잘 반응한다는 점이다.

---

## 1. 프롬프트 제안: 무시하고 있던 힌트

Claude가 응답을 마치면 출력 아래에 회색으로 흐릿하게 후속 제안이 나타난다. 대부분의 개발자는 이를 무시한다. 원문은 그게 실수라고 말한다.

이 제안은 무작위가 아니다. 현재 대화 컨텍스트와 코드베이스 상태를 보고 Claude가 판단한 논리적인 다음 단계다. 내가 원하긴 하지만 요청할 생각을 못 했을 만한 행동을 드러내 준다.

- 리팩터링 후에 테스트를 돌리기
- 구현 후에 엣지 케이스 점검하기
- 공유 인터페이스를 바꾼 뒤 관련 파일 업데이트하기

특히 세션 초반, 아직 문제에 적응 중일 때 가치가 크다. Claude가 알아챘지만 시키지 않아서 하지 않은 일의 가벼운 체크리스트 역할을 한다. Tab 키로 제안을 수락하는 것은 다음 프롬프트를 직접 만드는 것보다 빠르다. 또 Claude가 방금 한 일의 전체 컨텍스트를 갖고 있으므로 내가 직접 쓸 문장보다 범위가 더 잘 잡힌 경우가 많다.

### 맹목적 수락은 안티패턴

제안을 무조건 받아들이는 것은 안티패턴이다. 제안은 힌트이지 명령이 아니다. 읽어 보고, 내가 다음에 하려던 것과 같으면 수락하고, 아니면 무시하고 직접 지시한다. 가치는 제안이 맞을 때 아낀 시간에 있고, 판단을 통째로 넘기는 데 있지 않다.

## 2. 단순함이 정교함을 이길 때

Claude는 과하게 설계된(over-engineered) 해법으로 가는 경향이 있다. 이 실패 양상은 10장에서 자세히 다룬다. 짧게 요약하면 이렇다.

1. Claude에게 단순하게 하라고 말한다.
2. 직관적인 구현 쪽으로 명시적으로 제약한다.
3. 단순함 지침을 CLAUDE.md에 넣는다.

## 3. 자유보다 제약

이는 더 넓은 원칙으로 이어진다. Claude Code는 자유보다 제약에 더 잘 반응한다. 모호한 프롬프트는 모호한 출력을 만든다. 구체적인 제약이 있는 프롬프트는 집중되고 적절한 코드를 만든다. 제약의 예는 다음과 같다.

| 제약 | 예 |
|------|-----|
| 건드릴 파일 | 어떤 파일만 수정할지 지정 |
| 따를 패턴 | 기존 코드의 어떤 패턴을 따를지 지정 |
| 트레이드오프 | 어떤 선택을 할지 미리 정함 |
| 피할 프레임워크 | 쓰지 말아야 할 것을 명시 |

프롬프트 작성법은 8장에서 더 다룬다.

## 4. 정리

- 후속 제안은 Claude가 보기에 논리적인 다음 단계다. 세션 초반에 특히 쓸모 있다.
- Tab으로 수락하면 빠르지만 읽어 보고 판단한다. 힌트이지 명령이 아니다.
- 과설계 경향에는 단순하게 하라는 지시, 명시적 제약, CLAUDE.md의 단순함 지침으로 대응한다.
- 구체적 제약이 구체적 결과를 만든다.
