# 실제 사례로 보는 경제성

경제성은 숫자보다 개별 사례로 볼 때 더 와닿는다. 이 문서는 원문이 소개하는 네 가지 사례를 풀어서 정리한다. 금융 전문가 없이 포트폴리오를 최적화한 이야기, 3년 걸려 만든 UI를 버리고 다시 만든 이야기, 백엔드 개발자가 10시간 만에 풀스택 앱을 만든 이야기, 8주 만에 프로덕션 플랫폼을 만든 이야기다. 마지막에는 기능 하나를 추가하는 작업 흐름이 어떻게 줄어드는지도 다룬다.

---

## 1. 포트폴리오 최적화 사례

금융 계획 분야의 전문 배경은 없지만 일반적인 기술 소양과 도메인 지식이 있는 사람이 Claude Code로 포트폴리오 최적화를 했다.

### 입력 세 가지

- 여러 증권 계좌에서 내려받은 CSV 파일. 보유 종목, 취득 원가(cost basis), 펀드 데이터가 들어 있다.
- 내보내기 기능이 없는 비정형 정보를 적은 보조 텍스트 파일. 은행 잔고, 회사 퇴직연금 정보, 자동 투자 설정 같은 것이다.
- 원하는 결과물, 제약, 선호를 적은 정성 들인 목표 프롬프트.

### 목표 프롬프트가 가장 중요했다

이 프롬프트에는 다음이 들어 있었다.

- 어떤 데이터가 어디에 있는지
- 원하는 출력 형식
- 투자 선호: 수익 쫓기보다 세금 효율, 가장 싼 수수료의 펀드, 단순함
- 알려진 제약: 건드리지 않을 계좌
- 사용자가 무엇이 잘못됐다고 의심하는지. 단, Claude가 반박해도 좋다는 단서를 붙였다.
- 임시 목표 배분안(strawman). 처음부터 만들게 하는 대신 Claude가 반응할 구체적인 대상을 주기 위한 것이다.
- 결론으로 뛰어들기 전에 확인 질문을 빠짐없이 하라는 요청

### 진행 과정

Claude Code는 Python 스크립트를 써서 CSV를 파싱하고, 모든 보유 종목을 목표 범주로 분류하고, 인코딩 문제를 처리하고, 겹치는 내보내기를 중복 제거하고, 표준에서 벗어난 항목을 다뤘다. 모든 계좌와 범주에 걸친 전체 갭 분석이라는 기준안이 나왔고, 바로 반복 작업을 시작할 만큼 탄탄했다.

반복 단계는 데이터는 다 가졌지만 그 계좌들과 함께 살아 보지는 않은 애널리스트와 협업하는 느낌이었다. 제약을 고칠 때마다 모든 계산, 표, 권고안이 자동으로 갱신됐다. 자기 계획을 1~10점으로 스스로 비평하게 하자 Claude는 개선점 일곱 가지를 찾아냈다. 그중에는 비과세 퇴직 계좌에서 비중이 과다한 종목이 있었다. 거기서 팔면 세금이 정말 0원인데, 원래 계획은 이를 건드리지 않았다.

최종 결과물은 부록이 붙은 10개 섹션짜리 계획 문서였다. 사용자가 요청하지 않은 섹션도 있었다.

- 퇴직 연금 납입 최적화
- 신규 납입만으로 비중이 과다한 범주가 목표에 도달하는 데 걸리는 시간을 추정한 자연 희석(natural dilution) 타임라인
- 추천 종목마다 짝이 되는 세금 손실 확정(tax-loss harvesting) 상대 종목

전체 계획 문서는 다시 실행용 체크리스트로 줄여서 재구성했다.

CLAUDE.md 파일에는 세션이 지나는 동안 데이터의 특이점, 전략 결정, 목표 배분이 쌓였다. 며칠 뒤 사용자가 돌아오자 Claude는 정확히 중단했던 곳에서 이어서 일했다. 결과물도 복리로 쌓였다. 같은 프로젝트 디렉터리를 이후 이 과정을 쓰는 블로그 글에도 썼고, Claude가 세션 기록과 계획 문서를 맥락으로 읽었다.

1년 전이었다면 일주일치 스프레드시트 작업이거나, 금융 자문사에 몇 천 달러를 내는 일이었을 것이다. 이번에는 Claude Code와 며칠 저녁 주고받은 것이 전부였고, 나온 계획은 실제로 실행 중인 계획이었다.

## 2. 3년 걸린 UI를 다시 만든 사례

대체의 경제성은 창조의 경제성과 다르고, 감정의 궤적도 다르다.

한 개발자가 알고리즘 트레이딩 플랫폼의 설정 인터페이스를 3년 동안 만들었다. 트리 구조가 복잡하게 이어지는 형태로 매매 조건을 설정하게 했다. 탐색하려면 머릿속에 모델이 잘 잡혀 있어야 했다. 그래도 동작했고 개발자는 자랑스러워했다.

그러던 중 Claude Code가 더 나은 설계를 만들었다. 조금 나은 정도가 아니라 근본적으로 나았다. 개발자는 Claude가 자신보다 더 나은 UX 디자이너이자 프론트엔드 개발자임을 인정했고, 대부분의 개발자가 거부할 결정을 내렸다. 처음부터 다시 만들기로 한 것이다.

새로운 방식은 손으로 다듬은 트리 구조 인터페이스를 자연어 방식으로 바꾸었다. 사용자가 영어 평문으로 전략을 설명한다. 예를 들면 "마지막 매수로부터 20일이 지났고 RSI가 35 미만이면 사는 전략을 만들어라" 같은 식이다. Claude가 이 문장을 포트폴리오, 전략, 액션, 조건 같은 구조화된 객체로 분해한다. 3년의 수작업 UI 개발이 만들던 것과 같은 구조화 데이터를, 사용자가 설정 미로를 헤매지 않고 자연어 입력으로 얻게 된 것이다.

그 위에 수동 미세 조정용 노코드 UI 계층을 추가했다. 주목할 패턴은 AI가 자연어로 초안을 만들고, 사람이 시각적 인터페이스로 다듬는다는 점이다. 이 민주화된 인터페이스로 현재 2만 5천 명이 넘는 사람이 고급 트레이딩 도구를 쓸 수 있다.

원문은 서사의 흐름이 중요하다고 말한다. 옛 작업에 대한 자부심, AI가 자기 전문 기술을 넘어섰다는 인정, 다시 시작하겠다는 결정이다. 게으름이나 지름길의 이야기가 아니다. 더 나은 방법이 나타나서 이전의 노력이 무의미해졌음을 알아보고, 그에 따라 행동하는 규율의 이야기다.

## 3. 백엔드 개발자의 풀스택 스프린트

프론트엔드 프레임워크 경험도, 디자인 배경도, 금융 데이터 시각화 전문성도 없는 백엔드 개발자가 10시간도 안 되어 완전한 주식 거래 분석 애플리케이션을 만들었다.

장난감이 아니었다. 구성은 이랬다.

- 여러 주식 API에서 데이터를 가져와 정규화하는 모듈
- 기술적 지표 15개 이상
- 뉴스 출처 기반 감성 분석
- value-at-risk(VaR) 계산과 스트레스 테스트를 포함한 리스크 평가
- 성과 기여도 분석이 있는 포트폴리오 추적
- 캔들스틱 표시와 지표 오버레이가 있는 차트

구조도 깔끔했다. 새 지표나 데이터 소스를 추가하기 쉬울 만큼 모듈화되어 있었다.

어려운 점은 개별 구성요소가 아니라, 개발자가 다루지 못하는 세 영역의 교차점이었다. 프론트엔드 프레임워크 패턴, 금융 데이터 시각화, 디자인 감각이다. Claude Code가 세 가지를 동시에 메웠다. 개발자는 트레이딩 개념을 알았고, Claude Code는 프론트엔드 패턴과 금융 UI 관례를 알았다. 둘이 함께 그 시간 안에 어느 쪽도 혼자서는 못 만들 것을 만들었다.

## 4. 8주 만에 만든 프로덕션 플랫폼

주 단위 타임라인을 기록한 사례는 평균 단축률보다 더 정확한 그림을 준다. 한 팀이 Claude Code를 주 개발 도구로 써서 완전한 프로덕션 트레이딩 플랫폼을 8주 만에 만들었다.

| 기간 | 작업 | 산출물 |
|---|---|---|
| 1~2주 | 설계와 DB 설계. 스키마, ER 다이어그램, 마이그레이션 스크립트 생성 | 기술 스택 결정을 담은 CLAUDE.md, 준비된 DB와 테이블, 초안 컨테이너 정의 |
| 2~3주 | 백엔드 API. 서버 뼈대, 주문·포지션·체결 엔드포인트, 실시간 통신 서버 | 로컬에서 도는 백엔드 |
| 3~4주 | 프론트엔드 UI. 폼, 차트, 표, 상태 관리, API 응답 타입 정의 | 로컬에서 도는 프론트엔드. 와이어프레임에서 인터랙티브 프로토타입으로 진행 |
| 4~5주 | 브로커 연동과 전략 엔진. 브로커 API 래퍼, 주문 로직, 백테스팅 엔진 | 모의 거래 계좌로 시험한 "실주문 전송" 기능 |
| 5~6주 | 테스트와 문서화. 단위 테스트, E2E 시나리오, API 문서 | 테스트 커버리지 80% 초과, CI 파이프라인 통과 |
| 6~7주 | DevOps와 배포. 컨테이너 이미지, CI/CD 워크플로, 스테이징 인프라 | 스테이징에서 스모크 테스트를 돌리는 자동 파이프라인 |
| 7~8주 | 프로덕션 하드닝. 보안 스캔, 컴플라이언스 점검, 부하·스트레스 테스트, 프로덕션 배포, 모니터링 | 운영 배포 |

UI, 백엔드, 브로커 연동, 전략 엔진, 테스트 묶음, 배포 인프라를 갖춘 프로덕션급 플랫폼을 8주에 끝냈다. 같은 일의 전통적인 견적은 3~6개월이다. 플랫폼 안의 개별 기능도 비슷하게 줄었다. 새 전략 유형을 추가하는 일은 데이터 모델 변경, 백엔드 로직, API 엔드포인트, 프론트엔드 UI, 테스트, 문서화를 모두 포함하는데, 전통적으로 2~3주 걸리던 것이 2~3일에 끝났다.

## 5. 기능 개발 워크플로의 압축

주 단위 타임라인이 거시적인 이야기라면 기능 단위 타임라인은 미시적인 이야기다. 기존 플랫폼에 새 기능을 추가하는 일은 여섯 단계로 흐른다.

1. 데이터 모델 업데이트: DB 마이그레이션, 검증 모델, 타입 정의
2. 백엔드 로직 구현: 신호 평가, 실행 로직, 청산 조건, 테스트
3. API 엔드포인트 작성: 생성, 조회, 수정, 삭제와 특수 작업
4. 프론트엔드 UI 제작: 폼, 표시 화면, 결과 시각화
5. 테스트 작성과 CI 설정: 단위, 통합, E2E
6. 문서 업데이트

각 단계에서 Claude Code가 산출물을 만들면 전체가 2~3일 걸린다. 같은 기능을 전통적으로 개발하면 2~3주 걸린다.

단축은 단계마다 고르지 않다.

- 데이터 모델 변경과 API 엔드포인트는 첫 시도부터 거의 완벽에 가까운 품질로 나온다.
- 프론트엔드 UI와 백엔드 비즈니스 로직은 더 많은 반복이 필요하다.
- 테스트 생성은 빠르지만, 커버리지가 충분한지는 사람이 검토해야 한다.
- 문서는 거의 즉시 생성된다.

압축이 어디서 가장 강하고 약한지 알면 팀은 검토 시간을 가장 중요한 곳에 배분할 수 있다.
