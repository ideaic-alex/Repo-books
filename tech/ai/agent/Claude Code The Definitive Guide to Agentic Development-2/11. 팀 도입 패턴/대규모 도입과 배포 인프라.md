# 대규모 도입과 배포 인프라

회사 전체로 Claude Code를 넓힐 때는 결제 방식 선택, 네트워크 구성, 조직 정책 수립이 필요하다. 이 단계의 결정이 도입을 매끄럽게 확장시킬지, 보안 심사에서 멈추게 할지를 좌우한다.

이 문서는 대규모 도입 사례의 성과와 도입 곡선, 배포 방식 선택지, LLM 게이트웨이와 프록시 설정, 조직 전체 CLAUDE.md, 개발 컨테이너, SSO까지 엔터프라이즈 배포에 필요한 요소를 차례로 설명한다.

---

## 1. 대규모 도입의 성과

대규모로 Claude Code를 도입한 조직들은 일관된 수치를 보고한다. 원문이 소개하는 사례는 다음과 같다.

| 조직 | 보고된 성과 |
| --- | --- |
| 한 대형 통신 기술 기업 | 팀들이 맞춤 AI 솔루션을 1만 3천 개 넘게 만들었고, 엔지니어링 코드를 30% 더 빨리 출시했으며, 누적 50만 시간 넘게 절약 |
| 한 대형 핀테크 플랫폼 | 조직 전체에서 AI 도입률 89%, 내부에 800개가 넘는 AI 에이전트 배치 |
| 사용자 1,500만 명 이상의 다른 핀테크 플랫폼 | 개발 수명 주기 전반에서 실행 속도가 2배 |
| 한 대형 금융 기술 기업 | 엔지니어의 75%가 SQL 쿼리 생성 같은 작업에 Claude Code를 써서 주당 8~10시간 이상 절약 |

이것은 시범 운영 수치가 아니다. 조직 규모의 결과다.

### 도입 곡선

엔터프라이즈 규모의 도입 곡선은 예측 가능한 모양을 띤다.

- **초기 도입자**: 첫 주 안에 성과를 낸다.
- **다수의 중간층**: 동료들의 생산성 향상을 보면서 2~3개월에 걸쳐 도입한다.
- **늦게 합류하는 사람**: 팀의 속도 기대치가 Claude Code 사용을 전제로 바뀌었을 때 합류한다.

도입하지 않는 것의 조직적 위험도 눈에 띄기 시작했다. AI 보조 개발을 도입하지 않은 팀은 도입한 팀과 점점 불리하게 비교된다. 엔지니어의 실력이 떨어져서가 아니라, 기본 생산성 기대치가 달라졌기 때문이다.

## 2. 배포 방식 선택

Claude Code는 여러 배포 경로로 쓸 수 있고, 경로마다 결제, 인증, 지역별 이용 가능 여부, 비용 추적에서 장단점이 다르다.

- **좌석당 구독 플랜**: 셀프서비스 방식이며 협업 기능, 관리자 도구, 결제 관리가 들어 있다.
- **엔터프라이즈 플랜**: 위 기능에 더해 싱글 사인온(SSO), 도메인 캡처, 역할 기반 권한, 컴플라이언스 API 접근, 조직 전체 관리 정책 배포 기능이 있다.
- **클라우드 제공업체 경유**: 자체 클라우드 인프라를 거쳐야 하는 조직을 위해, 주요 클라우드 제공업체가 각자의 AI 서비스 플랫폼을 통해 Claude Code를 제공한다. 인프라 쪽에서 결제를 관리하고, 지역별 배포, 프롬프트 캐싱 지원, 기존 클라우드 인증과 비용 추적 시스템과의 연동이 따라온다.

선택은 순수하게 경제적인 문제만은 아니다. 데이터 거주 요건이 엄격한 조직은 지역 통제를 위해 클라우드 제공업체 배포가 필요할 수 있다. 가장 간단한 길을 원한다면 좌석당 플랜으로 시작하고, 인프라 요건이 요구할 때만 클라우드 제공업체 경유로 옮기는 것이 좋다.

## 3. LLM 게이트웨이

LLM 게이트웨이는 Claude Code와 클라우드 제공업체 사이에 놓여 인증과 라우팅(요청 경로 지정)을 맡는다. 조직이 게이트웨이를 쓰는 이유는 다음과 같다.

- 팀별 사용량을 중앙에서 추적하려고
- 맞춤형 호출 제한(rate limit)과 예산을 정하려고
- 인증을 중앙에서 관리하려고

설정은 간단하다. Claude Code가 제공업체 대신 게이트웨이를 가리키도록 알맞은 기본 URL(base URL) 환경 변수를 지정한다. 게이트웨이가 인증과 라우팅을 투명하게 처리하므로 Claude Code는 평소처럼 동작한다. 직접 API 접근, 클라우드 제공업체 경유, 표준 API 인터페이스를 지원하는 모든 제공업체에서 이 방식이 통한다.

---

## 4. 사내 프록시

보안 모니터링, 컴플라이언스, 네트워크 정책 때문에 모든 외부 트래픽이 프록시 서버를 지나야 하는 조직은 표준 환경 변수인 `HTTPS_PROXY`나 `HTTP_PROXY`를 설정한다.

사내 프록시와 LLM 게이트웨이는 서로 다른 설정이며 함께 쓸 수 있다. 트래픽이 사내 프록시를 거쳐 LLM 게이트웨이에 닿고, 게이트웨이가 인증과 제공업체까지의 라우팅을 처리하는 구조다.

---

## 5. 조직 전체 CLAUDE.md

프로젝트 수준 CLAUDE.md 외에, 조직은 시스템 디렉터리에도 CLAUDE.md를 배포할 수 있다. macOS에서는 `/Library/Application Support/ClaudeCode/CLAUDE.md`에 두면 조직 전체 표준이 적용된다. Linux에서는 같은 역할을 하는 경로가 `/etc/claude-code/` 아래에 있다. 이런 시스템 수준 파일은 그 컴퓨터의 모든 Claude Code 세션에 적용되며, 프로젝트 수준 설정으로는 덮어쓸 수 없는 조직의 코딩 표준, 보안 정책, 아키텍처 제약을 정한다.

그 결과 CLAUDE.md는 3단계 계층이 된다.

| 계층 | 위치 | 예시 |
| --- | --- | --- |
| 조직 전체 표준 | 시스템 수준 | "never commit secrets" |
| 팀 고유 관례 | 저장소 수준 | "always use our internal auth library" |
| 개인 취향 | 사용자 수준 | "I prefer tabs to spaces" |

## 6. 배포를 단순하게 만드는 두 가지 방법

대규모 도입에 성공한 조직에서 나온 모범 사례는 두 가지다.

1. **설치 경로를 단순하게 만든다.** 커스텀 개발 환경이 있다면 "원클릭" 설치 방식이 도입을 키우는 핵심이다. 초기 설정에 마찰이 클수록 그 단계를 넘기는 사람이 줄어든다. 인증 설정, 프록시 설정, 관리 정책, 기본 플러그인을 하나의 설치 단계로 묶는다.
2. **안내된 사용부터 시작한다.** 새 사용자는 코드베이스 Q&A로 시작하고, 작은 버그 수정과 기능 요청으로 넘어가고, Claude Code에게 계획을 세우게 한 다음 그 계획을 점검하고, 그 뒤에 에이전트의 자율성을 점차 높인다. 앞서 본 단계별 도입 경로와 같지만, 개인 조언이 아니라 조직 정책의 형태로 제시한 것이다.

## 7. 개발 컨테이너로 환경 표준화

일관되고 안전한 환경이 필요한 팀을 위해 참고용 개발 컨테이너(development container) 구성이 있다. Node.js가 설치된 사전 구성 컨테이너에, 승인된 도메인으로만 네트워크 접근을 제한하는 맞춤 방화벽이 들어 있다. 컨테이너 격리와 네트워크 제한 같은 보안 기능이 프롬프트 인젝션 등의 위협에 대한 다층 방어(defense in depth)를 제공한다.

개발 컨테이너는 특히 세 가지 상황에서 유용하다.

- 고객 프로젝트별로 코드와 자격 증명이 환경 사이에서 섞이지 않도록 격리할 때
- 신규 팀원이 일관된 환경에서 바로 일을 시작해야 할 때
- 개발 환경을 그대로 본뜬 일관된 CI/CD 환경을 만들 때

---

## 8. SSO와 도메인 캡처

엔터프라이즈 플랜은 SSO와 도메인 캡처를 지원한다. 회사 이메일 도메인으로 인증하는 모든 직원이 자동으로 조직의 결제와 정책 구조 안으로 들어온다. 개발자가 개인 계정으로 가입해서 조직의 통제를 피해 가는 상황을 없애 준다.

---

## 9. 정리

- 가장 간단한 길은 좌석당 플랜으로 시작하는 것이다. 데이터 거주 같은 요건이 생길 때 클라우드 제공업체 경유로 옮긴다.
- 게이트웨이는 사용량과 예산, 인증을 중앙에서 다루고, 사내 프록시는 외부 트래픽 통제를 맡는다. 둘은 함께 쓸 수 있다.
- CLAUDE.md는 조직, 저장소, 사용자 3단계로 쌓는다.
- 설치는 원클릭으로 만들고, 사용은 안내된 단계로 시작한다.
- 개발 컨테이너와 중앙 MCP 설정, SSO와 도메인 캡처가 환경 일관성과 통제를 받쳐 준다.
