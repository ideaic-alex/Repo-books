# 공유 CLAUDE.md와 프로젝트 설정

팀이 Claude Code를 같이 쓸 때 가장 값진 공유 자산은 버전 관리에 커밋한 CLAUDE.md다. CLAUDE.md는 Claude가 코드베이스와 나누는 모든 대화에 항상 깔리는 맥락(3장에서 다룬 내용)인데, 팀 단위로 쓰면 가치가 누적된다.

이 문서는 CLAUDE.md가 팀에서 어떻게 복리로 쌓이는지, 무엇을 커밋하고 무엇을 커밋하지 말아야 하는지, 그리고 `.claude/settings.json`과 플러그인 범위를 통해 팀 전체가 같은 환경을 쓰게 만드는 방법을 설명한다.

---

## 1. CLAUDE.md가 복리로 쌓이는 방식

개발자 A가 Claude가 자꾸 폐기 예정 모듈에서 import한다는 것을 발견했다고 하자. A는 CLAUDE.md에 한 줄을 적는다.

```text
Never import from src/legacy/utils. Use src/core/utils instead.
```

개발자 B는 이 문제를 겪을 일이 없다. C, D, 그리고 앞으로 들어올 모든 팀원도 마찬가지다. 한 번 적은 수정이 같은 오류를 영원히 막는 것이다.

몇 주, 몇 달이 지나면 CLAUDE.md에는 팀이 어렵게 얻은 코드베이스 지식이 쌓인다. 예를 들면 이런 것들이다.

- 관례에서 벗어난 빌드 명령
- 코드만 봐서는 알기 어려운 테스트 패턴
- 구현 선택지를 제한하는 아키텍처 결정
- 조용히 실패를 일으키는 환경상의 함정

항목 하나를 추가하는 데는 30초면 된다. 하지만 몇 달 동안 팀 전체에 쌓이는 가치는 상당하다. 원문은 며칠짜리 프로젝트에서 다섯 번 이상의 개발 세션에 걸쳐 CLAUDE.md를 관리한 팀들이 Claude Code의 효과가 눈에 띄게 좋아졌다고 보고한다고 적는다.

---

## 2. 무엇을 커밋하고 무엇을 빼야 하나

프로젝트 수준의 CLAUDE.md는 버전 관리에 커밋한다. 이 파일의 변경도 다른 코드 변경처럼 리뷰한다. 그래야 Claude가 받는 지시를 팀이 합의했다고 말할 수 있다. 팀의 관행과 어긋나는 항목이 몰래 들어가면, 모든 개발자의 Claude 세션에서 혼란이 생긴다.

개인 취향은 커밋하지 않는다. 개인 취향은 사용자 수준 설정이나 gitignore 처리한 로컬 CLAUDE.md에 둔다. 공유 CLAUDE.md는 팀의 합의를 담는 곳이고, 개인의 의견을 담는 곳이 아니다.

| 종류 | 둘 곳 | 커밋 여부 |
| --- | --- | --- |
| 팀이 합의한 규칙 | 프로젝트 CLAUDE.md | 커밋하고 코드처럼 리뷰 |
| 개인 취향 | 사용자 수준 설정, 로컬 CLAUDE.md | 커밋하지 않음(gitignore) |

---

## 3. .claude/settings.json으로 같은 환경 공유하기

버전 관리에 커밋한 `.claude/settings.json`은 권한만 공유하는 파일이 아니다. 훅, 플러그인 활성화 여부, 환경 변수 기본값, 도구 설정까지 팀에 같이 퍼진다.

그래서 프로젝트에서 일하는 모두가 같은 Claude Code 경험을 하게 된다. 같은 훅이 모든 개발자에게 실행되고, 같은 권한이 적용되고, 같은 플러그인이 켜진다. 새 팀원의 온보딩 비용은 "모든 것을 직접 설정하기"에서 "저장소를 clone하기"로 줄어든다.

---

## 4. 프로젝트 범위와 로컬 범위의 플러그인

플러그인은 설치하는 범위(scope)에 따라 공유 여부가 갈린다.

- **프로젝트 범위(project scope)**: 버전 관리를 통해 팀 전체가 공유한다.
- **로컬 범위(local scope)**: gitignore 대상이라 그 컴퓨터에서만 보인다.

이 구분은 개발자마다 취향이 다른 팀에서 쓸모가 있다. 팀은 코드 품질 훅과 MCP 서버 연결을 담은 플러그인을 프로젝트 범위로 표준화할 수 있다. 개별 개발자는 개인 생산성 도구, 다른 언어 서버, 실험적 기능 같은 것을 로컬 범위로 추가할 수 있다.

프로젝트 범위는 팀의 표준이고 로컬 범위는 개인의 확장이다. 두 가지는 충돌 없이 함께 쓸 수 있다.

---

## 5. 중앙에서 관리하는 MCP 설정

조직은 한 팀이 승인된 MCP 서버를 설정하고 그 `.mcp.json` 파일을 코드베이스에 체크인하게 하면 이득을 본다. 그러면 프로젝트에 붙는 모든 개발자가 같은 MCP 서버를 같은 승인된 연결로 받는다. 개발자가 각자 데이터베이스, API, 사내 서비스 연결을 따로 설정하는 일이 없어진다. 여기에 허용할 MCP 서버를 제한하는 관리 설정(다음 문서에서 설명한다)을 합치면, 통제되면서도 쓸 만한 연동 계층이 만들어진다.

---

## 6. 팀 도입 관점의 정리

- CLAUDE.md는 한 번 적으면 팀 전체가 계속 이득을 보는 자산이다. 짧게 자주 추가하는 습관이 핵심이다.
- 프로젝트 CLAUDE.md는 코드처럼 리뷰하고, 개인 취향은 팀 파일에 넣지 않는다.
- `.claude/settings.json`을 커밋하면 훅, 권한, 플러그인이 모두에게 같아져서 온보딩이 clone 한 번으로 끝난다.
- 팀 표준은 프로젝트 범위, 개인 확장은 로컬 범위로 나눈다.
- MCP 연결은 한 팀이 `.mcp.json`으로 중앙 관리하면 개발자마다 제각각 설정하는 일을 막을 수 있다.
