# 엔지니어링 팀 일곱 곳의 사용 사례

백엔드, 프론트엔드, DevOps 같은 일반 분류는 실제 모습을 가린다. 한 대형 엔지니어링 조직 안의 여러 팀이 Claude Code를 어떻게 쓰는지 들여다보면 워크플로가 크게 갈린다. 원문은 한 대형 AI 기업의 팀별 도입 사례를 정리한 것이며, 세부 정보를 가리기 위해 일반화했다고 밝힌다.

이 문서는 열 개 팀 중 엔지니어링 성격이 강한 일곱 팀(데이터 인프라, 프로덕트 개발, 보안 엔지니어링, 추론, 데이터 과학과 ML 엔지니어링, API 지식, RL 엔지니어링)을 다룬다. 나머지 세 팀(그로스 마케팅, 프로덕트 디자인, 법무)은 다음 문서에서 다룬다.

---

## 1. 데이터 인프라

데이터 인프라 팀은 조직 전체의 비즈니스 데이터 파이프라인을 관리한다. 이 팀의 가장 놀라운 기여는 기술적인 것이 아니었다. 재무 팀 동료들에게 데이터 워크플로를 설명하는 평문(plain-text) 파일을 쓰는 법을 가르치고, 그 파일을 Claude Code에 불러와 완전 자동으로 실행하게 한 것이다. 코드를 모르는 사람이 자연어로 쓴 워크플로 설명을 Claude Code가 처음부터 끝까지 실행한다. 개발자 중심 도입 계획으로는 예상할 수 없던 사례다.

팀 안에서는 CLAUDE.md를 전통적인 데이터 카탈로그와 탐색 도구의 대용으로 쓴다. 신입 데이터 과학자에게는 Claude Code에게 코드베이스 탐색을 시키라고 안내한다. Claude는 CLAUDE.md 파일들을 읽고, 작업에 관련된 파일을 찾고, 데이터 파이프라인의 의존 관계를 설명하고, 어떤 상위 데이터 소스가 대시보드로 흘러가는지 신입이 이해하도록 돕는다.

그 밖의 특징적인 실천은 다음과 같다.

- 긴 작업을 위해 여러 저장소에서 Claude Code 인스턴스를 병렬로 돌린다. 몇 시간 또는 며칠 뒤에 돌아와도 각 인스턴스는 전체 맥락을 유지한다.
- 대규모 모니터링을 한다. 대시보드 200개를 훑으며 이상 징후를 찾는 것처럼, 사람이 직접 검토할 수 없는 양의 데이터를 Claude Code가 처리한다.
- 팀 내부 사용 세션을 열어 서로의 워크플로를 시연하며 모범 사례를 퍼뜨린다.
- 각 세션이 끝날 때 Claude에게 끝낸 작업을 요약하게 하고 워크플로 자체의 개선안도 제안받는다. 이렇게 하면 프로젝트 지식뿐 아니라 팀의 업무 방식까지 다듬는 지속적 개선 고리가 만들어진다.

## 2. 프로덕트 개발

프로덕트 개발 팀은 핵심 플랫폼 기능과 에이전트 기능을 맡는다. 두 가지 모드로 일하며, 어느 모드를 고를지는 의식적으로 정한다.

- **프로토타입과 주변 기능**: 자동 수락 모드로 자율 루프를 만든다. Claude가 코드를 쓰고, 테스트를 돌리고, 계속 반복한다. 엔지니어는 대략 80% 완성된 결과를 검토한 뒤 마무리 다듬기를 넘겨받는다.
- **핵심 비즈니스 로직과 중요 기능**: 동기식(synchronous)으로 일한다. 자세한 프롬프트를 주고 Claude의 출력을 실시간으로 지켜보면서 코드 품질, 스타일 가이드 준수, 올바른 아키텍처를 확인한다.

이 구분이 중요하다. 이 팀에서 가장 성공적이었던 비동기 프로젝트는 복잡한 기능 구현이었는데, 최종 코드의 약 70%가 Claude의 자율 작업에서 나왔고 몇 번의 반복만으로 끝났다. 이 팀의 작업 분류 기준은 그대로 따라 해 볼 만하다. 제품의 가장자리에 있는 작업(주변 기능, 프로토타입, 탐색용 코드)은 자동 수락 모드에 맡긴다. 핵심 기능을 건드리는 작업은 자세한 프롬프트와 동기식 감독으로 진행한다. 이 구분을 빠르게 하는 능력도 몇 주에 걸쳐 길러지는 기술이다.

---

## 3. 보안 엔지니어링

보안 팀은 소프트웨어 개발 수명 주기와 공급망 보안에 집중한다. 이 팀은 조직 전체 모노레포에 있는 커스텀 슬래시 명령의 절반을 차지한다. Claude Code가 실무에 얼마나 깊이 들어와 있는지 보여 주는 이례적인 밀도다.

인프라 코드 계획을 Claude Code에 붙여 넣고 사실상 "이게 무슨 일을 하게 되고, 나중에 후회할 일은 없나"를 묻는다. 그 덕분에 인프라 변경의 보안 검토에서 피드백 고리가 짧아졌고, 개발자가 보안 팀 승인을 기다리던 병목이 사라졌다. 또한 Claude에게 여러 문서 자료를 읽혀서 마크다운 런북(runbook, 운영 절차서)과 장애 대응 가이드로 합치게 하고, 그렇게 압축한 문서를 실제 장애를 디버깅할 때 맥락으로 쓴다.

가장 큰 변화는 일하는 방식이었다. 예전에는 기능을 설계하고, 대충 코드를 쓰고, 리팩터링하다가, 결국 테스트를 포기하는 패턴이었다. 이제는 테스트 주도 개발(TDD) 방식을 쓴다. Claude가 먼저 의사 코드(pseudocode)를 쓰고, 팀원이 Claude를 TDD 흐름으로 이끌며, 가끔 진행 상황을 확인한다. 명세는 마크다운으로 코드베이스에 저장하며, Claude가 쓰고, 리뷰하고, 실행한다. 덕분에 이전에는 맥락을 쌓는 데 몇 주가 걸렸을 프로젝트에 며칠 만에 의미 있게 기여할 수 있다.

이 팀의 운영 철학도 독특하다. 좁은 질문을 던지는 대신 Claude Code에게 자율적으로 일하면서 중간중간 커밋하라고 지시하고, 가끔 점검한다. 이 "일하면서 커밋" 패턴이 일일이 간섭하는 상호작용보다 더 포괄적인 결과를 낸다.

---

## 4. 추론(Inference)

추론 팀은 메모리 시스템과 모델 서빙을 담당한다. 머신러닝 배경이 없는 팀원들이 Claude Code로 모델 특화 함수와 설정을 설명받아서 조사 시간을 80% 줄였다. 문서를 뒤지고 논문을 읽는 데 한 시간 걸리던 일이 10~20분이면 끝난다.

여러 프로그래밍 언어에 걸쳐 기능을 테스트할 때는, 테스트하려는 내용을 말로 설명하면 Claude가 필요한 언어로 로직을 작성한다. 테스트하려고 새 언어를 배울 필요가 없어진다. 이 팀은 Claude Code를 자신들의 도메인 전문성과 구현에 필요한 어떤 언어 사이의 만능 통역사로 쓰는 셈이다.

## 5. 데이터 과학과 ML 엔지니어링

이 팀은 모델 성능과 학습 데이터를 이해하기 위한 정교한 시각화 도구가 필요하다. 프론트엔드 웹 개발은 거의 모르지만, 깊이 알지 못하는 언어로 5,000줄짜리 애플리케이션을 처음부터 Claude Code로 만든다. 이것이 가능한 이유는 시각화 앱이 맥락이 비교적 적게 필요하고 모노레포 전체를 이해할 필요가 없기 때문이다. 프론트엔드 개발자를 따로 채용해야 했을 도구를 빠르게 프로토타이핑할 수 있다.

일회용에서 영구적인 도구로 바뀐 점이 크다. 한 번 분석하고 버리는 노트북 대신, 이후 모델 평가에서 계속 재사용할 수 있는 상설 인터랙티브 대시보드를 만든다. 모델 성능을 이해하는 것이 이 팀의 핵심 업무이므로, 영구적인 도구는 그 이해의 질을 바꾼다.

반복적인 리팩터링에서는 2~4배의 시간 절약을 보고한다. 불확실한 개발 작업에서는 실용적으로 접근한다. 상태를 커밋하고, Claude가 30분 동안 자율적으로 일하게 한 뒤, 결과를 받아들이거나 처음부터 다시 시작한다. 결함이 있는 첫 시도를 고치는 것보다 깨끗한 세션으로 다시 시작하는 편이 더 나은 결과를 낸다고 한다.

## 6. API 지식

이 팀은 어떤 작업이든 Claude Code를 가장 먼저 찾는다. 다른 일을 하기 전에 어떤 파일을 봐야 하는지부터 묻는다. 저장소를 직접 검색하거나 동료에게 묻는 대신, 특정 기능을 호출하는 파일을 Claude에게 물어 몇 초 안에 답을 얻는다.

이 팀에게 가장 중요한 도입 결과는 자신감이다. 이제는 코드베이스의 낯선 영역에서 생긴 버그도 남에게 도움을 청하지 않고 혼자 처리한다. 예전 워크플로의 맥락 전환 부담은 사라졌다. 코드 조각을 별도 인터페이스에 복사하고, 파일을 끌어다 놓고, 문제를 길게 설명하던 일이 없어졌다. 팀은 일상 업무의 마찰이 줄어 눈에 띄게 더 행복하고 생산적이라고 말한다.

---

## 7. RL 엔지니어링

강화 학습(reinforcement learning, RL) 팀은 "시도해 보고 롤백"하는 방식을 쓴다. 체크포인트를 자주 커밋해 두고 Claude의 자율 구현을 시험하다가, 필요하면 되돌린다. 이 팀은 Claude가 첫 시도에서 성공하는 경우가 약 3분의 1 정도라고 인정한다.

단계적 대응 방식은 현실적이다. 먼저 짧은 프롬프트로 Claude에게 전체 구현을 시도하게 한다. 성공하면(대략 세 번에 한 번) 상당한 시간을 번다. 실패하면 더 협업적이고 안내하는 방식으로 전환한다. 성공하는 3분의 1에서 절약한 시간이 실패하는 3분의 2의 비용을 충분히 상쇄한다.

## 8. 일곱 팀에서 뽑는 공통 교훈

| 팀 | 핵심 패턴 |
| --- | --- |
| 데이터 인프라 | 평문 워크플로 파일, CLAUDE.md를 데이터 카탈로그로 활용, 세션 끝 개선 요청 |
| 프로덕트 개발 | 주변 기능은 자동 수락, 핵심 로직은 동기식 감독 |
| 보안 엔지니어링 | 슬래시 명령 다수, TDD, "일하면서 커밋" |
| 추론 | 언어 장벽 제거, 조사 시간 80% 단축 |
| 데이터 과학과 ML | 영구 대시보드, 30분 시도 후 수락 또는 재시작 |
| API 지식 | 모든 작업의 첫 단계로 Claude에게 파일 위치 질문 |
| RL 엔지니어링 | 자주 커밋하고 시도, 실패하면 롤백 |

- 자율 실행과 동기식 감독을 작업의 중요도로 나누는 팀이 많다.
- 자주 커밋하고, 안 되면 되돌리거나 새 세션으로 다시 시작하는 방식이 여러 팀에서 반복된다.
- 지식을 CLAUDE.md, 마크다운 명세, 슬래시 명령에 남겨서 신입이 빨리 기여하게 만든다.
