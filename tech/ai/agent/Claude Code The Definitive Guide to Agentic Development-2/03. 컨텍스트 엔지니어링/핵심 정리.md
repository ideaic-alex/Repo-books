# 핵심 정리

이 문서는 장 끝의 Key Takeaways를 한곳에 모아 풀어 쓴 것이다. 앞선 문서들에서 따로 다룬 내용을 열 가지 요점으로 다시 묶어, 장을 다 읽은 뒤 빠르게 복습할 때 쓰도록 했다.

각 요점 끝의 **→ 자세히** 링크를 따라가면 해당 내용을 다룬 문서로 이동한다.

## 1. 한눈에 보는 요점

- **CLAUDE.md는 매 요청마다 비용이 든다**: 500줄 이내로 유지하고, `/init`으로 초안을 만든 뒤 코드에서 Claude가 스스로 알아낼 수 없는 정보만 남긴다. 줄이 늘수록 컨텍스트 윈도가 줄어들기 때문이다.
  - *쉽게 말하면*: 매일 아침 읽는 업무 수칙은 짧을수록 좋다.
  - → 자세히: [CLAUDE.md 기본기](CLAUDE.md%20%EA%B8%B0%EB%B3%B8%EA%B8%B0.md)
- **비용 비교표가 예산 기준이다**: CLAUDE.md와 MCP는 매 요청마다 비용이 들고, 스킬은 설명만 올라가서 낮고, 서브에이전트는 따로 분리되며, 훅은 비용이 없다. 기능을 고를 때 이 표부터 보면 낭비를 막는다.
  - *쉽게 말하면*: 고정 지출(늘 켜진 것)과 변동 지출(쓸 때만 드는 것)을 구분하라.
  - → 자세히: [컨텍스트 비용과 기능 선택](%EC%BB%A8%ED%85%8D%EC%8A%A4%ED%8A%B8%20%EB%B9%84%EC%9A%A9%EA%B3%BC%20%EA%B8%B0%EB%8A%A5%20%EC%84%A0%ED%83%9D.md)
- **항상 필요한 규칙은 CLAUDE.md, 작업별 참고 자료는 스킬에 둔다**: 사람이 직접 부를 때만 쓰는 스킬은 `disable-model-invocation: true`로 두면 컨텍스트 비용이 0이다. 쓰지 않을 때 자리를 차지하지 않게 하려는 것이다.
  - *쉽게 말하면*: 수칙은 책상에, 매뉴얼은 서랍에, 위험한 작업 매뉴얼은 잠긴 서랍에.
  - → 자세히: [컨텍스트 비용과 기능 선택](%EC%BB%A8%ED%85%8D%EC%8A%A4%ED%8A%B8%20%EB%B9%84%EC%9A%A9%EA%B3%BC%20%EA%B8%B0%EB%8A%A5%20%EC%84%A0%ED%83%9D.md)
- **`@path/to/import`로 CLAUDE.md를 가볍게 유지한다**: 깊은 참고 자료는 별도 파일로 빼고 필요할 때 연결한다. 본문은 짧게 두면서 정보 접근은 막지 않는 방법이다.
  - *쉽게 말하면*: 다 베껴 적지 말고 "자세한 건 ○○ 문서 참고"라고 적는다.
  - → 자세히: [CLAUDE.md 기본기](CLAUDE.md%20%EA%B8%B0%EB%B3%B8%EA%B8%B0.md)
- **압축에서 살아남을 내용을 직접 정한다**: CLAUDE.md의 Compact Instructions는 자동 압축 후에도 남고, 초점 지시를 붙인 `/compact`는 보존 대상을 지정하며, `/rewind`의 "Summarize from here"는 필요한 구간만 정리한다. 압축 때문에 중요한 규칙을 잃는 일을 줄여 준다.
  - *쉽게 말하면*: 칠판을 지우기 전에 "지우지 마시오" 칸을 정해 두고, 지울 범위도 내가 고른다.
  - → 자세히: [자동 압축과 컨텍스트 관리](%EC%9E%90%EB%8F%99%20%EC%95%95%EC%B6%95%EA%B3%BC%20%EC%BB%A8%ED%85%8D%EC%8A%A4%ED%8A%B8%20%EA%B4%80%EB%A6%AC.md)
- **`/context`로 먼저 점검한다**: 컨텍스트 예산이 어디에 쓰이는지 확인하고 나서 Claude가 공간이 모자라다고 탓해야 한다. 원인 대부분은 내가 채운 내용에 있다.
  - *쉽게 말하면*: 휴대폰 저장 공간이 부족하면 무작정 지우기 전에 "무엇이 공간을 먹는지" 화면부터 본다.
  - → 자세히: [자동 압축과 컨텍스트 관리](%EC%9E%90%EB%8F%99%20%EC%95%95%EC%B6%95%EA%B3%BC%20%EC%BB%A8%ED%85%8D%EC%8A%A4%ED%8A%B8%20%EA%B4%80%EB%A6%AC.md)
- **CLAUDE.md는 코드 밖에서도 쓸 수 있다**: 재무 분석, 데이터 과학, 기술 문서 작성처럼 작업이 여러 세션에 걸치고 맥락이 이어져야 하는 분야라면 어디서나 쓸 수 있다.
  - *쉽게 말하면*: "다음에 다시 설명하기 싫은 것"을 적어 두는 곳이라면 분야는 상관없다.
  - → 자세히: [세션을 넘어 쌓이는 지식](%EC%84%B8%EC%85%98%EC%9D%84%20%EB%84%98%EC%96%B4%20%EC%8C%93%EC%9D%B4%EB%8A%94%20%EC%A7%80%EC%8B%9D.md)
- **서브에이전트 격리의 효과는 크다**: 서브에이전트 열네 개를 돌려도 작업이 각자의 컨텍스트 윈도에 머물러 메인 세션이 바닥나지 않는다. 무거운 탐색은 위임하는 것이 기본이라는 뜻이다.
  - *쉽게 말하면*: 팀장은 보고서만 받고, 자료 더미는 팀원 책상에 둔다.
  - → 자세히: [AGENTS.md와 서브에이전트 격리](AGENTS.md%EC%99%80%20%EC%84%9C%EB%B8%8C%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%20%EA%B2%A9%EB%A6%AC.md)
- **세션 종료 시 CLAUDE.md를 갱신하면 기억이 복리로 쌓인다**: 지식뿐 아니라 워크플로 개선점도 함께 기록하면 지속적인 개선 루프가 된다. 다음 세션이 이전보다 나은 상태로 시작한다.
  - *쉽게 말하면*: 퇴근 전 업무 일지를 쓰면 내일의 내가 어제보다 똑똑하게 출근한다.
  - → 자세히: [세션을 넘어 쌓이는 지식](%EC%84%B8%EC%85%98%EC%9D%84%20%EB%84%98%EC%96%B4%20%EC%8C%93%EC%9D%B4%EB%8A%94%20%EC%A7%80%EC%8B%9D.md)
- **관찰한 오류를 겨냥한 추가가 일반 지시보다 낫다**: 실제로 본 실수에 맞춰 한 줄을 덧붙이는 편이 막연한 당부보다 효과가 크다. 스펙 문서는 압축과 세션 재시작을 견디므로 여러 세션에 걸친 프로젝트에 꼭 필요하고, 세션 포크(`--fork-session`)는 쌓인 컨텍스트를 살린 채 다른 방향으로 작업을 이어 가게 해 준다.
  - *쉽게 말하면*: "조심해"보다 "이 칸에는 이 형식으로"가 낫다. 긴 공사에는 설계도를 걸어 두고, 다른 길을 시험할 땐 세이브 파일을 복사해서 한다.
  - → 자세히: [세션을 넘어 쌓이는 지식](%EC%84%B8%EC%85%98%EC%9D%84%20%EB%84%98%EC%96%B4%20%EC%8C%93%EC%9D%B4%EB%8A%94%20%EC%A7%80%EC%8B%9D.md), [자동 압축과 컨텍스트 관리](%EC%9E%90%EB%8F%99%20%EC%95%95%EC%B6%95%EA%B3%BC%20%EC%BB%A8%ED%85%8D%EC%8A%A4%ED%8A%B8%20%EA%B4%80%EB%A6%AC.md)

## 2. 스스로 점검해 보기

장을 다 읽었다면 아래 질문에 답해 보자. 막히는 질문이 있으면 괄호 안의 문서로 돌아가면 된다.

1. CLAUDE.md에 "이 프로젝트는 Python을 쓴다"라고 적는 것은 좋은 선택일까? 왜 그런가? (CLAUDE.md 기본기)
2. 한 달에 한 번 하는 배포 절차는 CLAUDE.md와 스킬 중 어디에 두어야 할까? Claude가 멋대로 배포를 시작하지 않게 하려면 무엇을 더해야 할까? (컨텍스트 비용과 기능 선택)
3. 자동 압축을 기다리지 않고 80%쯤에서 직접 `/compact`를 하는 이유는? (자동 압축과 컨텍스트 관리)
4. 서브에이전트에게 일을 맡겼는데 결과를 아주 길게 돌려받았다. 무엇이 문제일까? (AGENTS.md와 서브에이전트 격리)
5. Claude가 같은 import 실수를 세 번째 반복했다. CLAUDE.md에 어떻게 적어야 효과가 좋을까? (세션을 넘어 쌓이는 지식)

1. 좋지 않다. Claude는 프로젝트 파일만 봐도 Python을 쓴다는 것을 알 수 있다. CLAUDE.md에는 Claude가 스스로 알아낼 수 없는 것만 적는다.
2. 스킬에 둔다. 매번 필요하지 않기 때문이다. 사람만 실행하게 하려면 frontmatter에 `disable-model-invocation: true`를 넣는다.
3. 여유 공간이 있을 때 압축해야 요약이 잘 되고, 무엇을 남길지 초점을 직접 지정할 수 있기 때문이다.
4. 긴 결과가 메인 컨텍스트를 채워 격리의 의미가 사라진다. 돌려받을 형식을 짧게 정해 주어야 한다.
5. 막연한 당부("경로 조심") 대신 정확한 규칙("○○는 `@app/db/utils`에서 import한다. `@app/utils/db`는 deprecated다")을 적는다.
