# 자동 압축과 컨텍스트 관리

세션이 길어지면 컨텍스트 윈도가 차오르고, 어느 시점에는 Claude Code가 대화를 압축한다. 이때 무엇이 남고 무엇이 사라지는지를 이해해야 긴 작업에서 중요한 지시를 잃지 않는다.

이 문서는 자동 압축의 동작, 압축에서 살아남게 하는 Compact Instructions, /compact와 /rewind를 이용한 직접 제어, PreCompact 훅, /context 진단, 그리고 세션을 포크(fork)하는 복구 방법을 정리한다.

---

## 1. 자동 압축은 언제 일어나는가

컨텍스트 용량이 약 95%에 이르면 Claude가 자동 압축(auto-compaction)을 시작한다. 이것은 충돌이 아니라 관리되는 과정이다. 그래도 무엇이 살아남는지를 결정하므로 동작 방식을 알아야 한다.

압축 중에 Claude는 오래된 도구 출력을 지우고 대화 기록을 요약한다. 스무 턴 전에 읽은 파일 내용, 앞서 탐색하며 얻은 명령 출력, 중간 추론이 모두 요약본으로 압축된다. 컨텍스트 공간은 확보되지만 세부 내용은 잃는다.

## 2. Compact Instructions: 압축을 견디는 구간

CLAUDE.md 안에서 "Compact Instructions"라는 제목 아래의 내용만 특별 대우를 받는다. 이 섹션의 내용은 압축 중에도 명시적으로 보존된다. 대화 기록이 압축된 뒤에도 Claude가 반드시 기억해야 할 것을 지정하는 자리다.

다음과 같은 내용에 쓴다.

- 세션이 아무리 길어져도 어기면 안 되는 핵심 제약.
- 현재 작업의 설명. 복잡해서 요약하면 중요한 뉘앙스가 빠질 수 있는 경우에 해당한다.
- 세션 앞부분에서 내린 결정 중 이후 모든 작업에 영향을 주는 것.

## 3. /compact로 초점을 지정해 압축하기

`/compact`로 압축을 직접 실행할 수 있고, 초점 지시를 붙여서 무엇을 살릴지 방향을 줄 수 있다. 예를 들어 `/compact Focus on the API changes`라고 하면, 압축 과정이 요약할 때 대화의 어떤 측면을 우선할지 알게 된다. 초점을 주지 않으면 압축이 스스로 중요도를 판단하는데, 대체로 합리적이지만 가끔 엉뚱한 것을 버린다.

95%에서 자동 압축이 오기를 기다리기보다 80% 정도에서 직접 압축하는 편이 대개 낫다. 제어권이 더 있고, 압축이 작업할 여유 공간이 더 있으며, 대화 내용이 아직 생생할 때 방향을 줄 수 있기 때문이다.

압축이 시작되는 기준은 환경 변수 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`로 바꿀 수 있다. 80으로 설정하면 압축이 더 일찍 일어나서 윈도가 꽉 차기 전에 공간을 확보한다. 더 높게 설정하면 압축이 늦어지지만, 압축이 발동하기 직전 구간에서 성능이 떨어질 위험이 있다.

## 4. /rewind로 일부만 요약하기

대화 전체가 아니라 일부만 압축하고 싶을 때가 있다. Escape를 두 번 누르거나 `/rewind` 명령을 쓰면 되감기 메뉴가 열린다. 내가 보낸 프롬프트가 체크포인트로 스크롤 목록에 나타난다. 메시지를 하나 고르면 네 가지 선택지가 나온다.

1. **코드와 대화 모두 복원**: 그 시점으로 모든 것을 되돌린다.
2. **대화만 복원**: 대화는 되감고 현재 코드는 유지한다.
3. **코드만 복원**: 대화는 유지하고 파일 변경만 되돌린다.
4. **여기서부터 요약(Summarize from here)**: 선택한 지점부터 이후 내용을 요약으로 줄이고, 그 이전 대화는 원본 그대로 둔다.

"여기서부터 요약"은 필요한 부분만 정밀하게 도려내는 압축이다. 막다른 길을 서른 턴 동안 탐색하다가 올바른 접근법을 찾았다면, 그 탐색 부분만 요약해서 컨텍스트를 확보하고 쓸모 있는 작업은 세부까지 보존할 수 있다. 대화 전체를 압축하는 것보다 훨씬 정밀하다.

## 5. PreCompact 훅

PreCompact 훅 이벤트는 수동이든 자동이든 압축이 시작되기 직전에 발생한다. 훅은 트리거 종류(`manual` 또는 `auto`)와 `/compact`에 넘긴 사용자 지정 지시를 전달받는다. 압축을 막을 수는 없지만, 세션 상태 저장, 컨텍스트 사용량 기록, 압축 요약에 영향을 줄 컨텍스트 주입 같은 준비 작업은 할 수 있다. 컨텍스트 관리를 프로그램으로 확장하는 지점이다.

## 6. /context 명령

`/context`는 현재 컨텍스트 사용량을 색깔 격자로 보여 준다. 시스템 프롬프트, CLAUDE.md 내용, MCP 도구 정의, 대화 기록, 진행 중인 작업이 각각 얼마나 차지하는지 나타난다. 컨텍스트 엔지니어링의 진단 도구로, 성능이 떨어질 때 이유를 알려 준다. 질문을 하나도 하기 전에 MCP 서버가 컨텍스트의 30%를 쓰고 있다면 무엇을 고쳐야 할지 바로 알 수 있다.

실무적인 결론은 이렇다. 세션이 자주 압축 단계에 도달한다면, 한 세션에서 너무 많은 일을 하고 있거나 항상 켜져 있는 컨텍스트 비용이 너무 높은 것이다. 둘 다 해결할 수 있는 문제다.

## 7. 세션 포크로 컨텍스트 복구하기

세션의 컨텍스트가 오염되었을 때가 있다. 막다른 길이 너무 많거나, 더는 상관없는 탐색이 쌓였거나, 자동 압축이 중요한 지시를 잃어버린 경우다. 이때 처음부터 다시 시작하는 것 말고도 복구 방법이 있다.

`--fork-session` 플래그는 기존 세션의 전체 기록을 가진 채 시작하되 그 지점부터 갈라지는 새 세션을 만든다. 원래 세션은 그대로 보존되고, 포크된 세션은 새 세션 ID와 별도의 대화 흐름을 가진다.

```bash
claude --continue --fork-session
```

보존하고 싶은 가치 있는 컨텍스트가 있지만 작업을 다른 방향으로 끌고 가야 할 때 쓴다. 프로젝트 설정, 이미 내린 결정, 취하고 있는 접근법을 다시 설명하는 대신 세션을 포크하고 그 모든 컨텍스트를 유지한 채 새 방향을 시작한다.

다만 세션 포크는 좋은 컨텍스트 관리를 대체하지 못한다. 최선을 다했는데도 세션 컨텍스트가 필요와 어긋나 버렸을 때 쓰는 비상구다.
