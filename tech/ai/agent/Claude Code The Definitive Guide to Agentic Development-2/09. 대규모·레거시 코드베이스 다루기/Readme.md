# 대규모·레거시 코드베이스 다루기

작고 구조가 잘 잡힌 프로젝트는 쉽다. 진짜 시험대는 파일이 이백만 개인 모노레포, 프레임워크 세 개가 섞이고 문서가 없는 레거시, 한 사람이 전체를 이해할 수 없는 거대한 시스템이다. 이 장은 컨텍스트에 다 들어가지 않을 만큼 크고, 현대적 관례를 따르지 않을 만큼 오래되었고, 함부로 다시 쓰기에는 너무 중요한 코드베이스를 다루는 기법을 설명한다.

워크트리로 병렬 작업을 하는 법, Explore 서브에이전트와 병렬 리서치, 작업 의존성 관리, 파일시스템 기반 분석, 레거시 언어 장벽의 붕괴, 스펙 기반 리팩터링, 온보딩, 기술 부채 해소를 차례로 다룬다.

---

## 1. 핵심 요점

- **워크트리**: 브랜치마다 작업 디렉터리를 나누면 Claude Code 세션을 병렬로 돌릴 수 있다. 세션끼리 컨텍스트와 파일이 독립이고, 한계는 컴퓨터 자원과 API 예산이다.
- **Explore와 병렬 서브에이전트**: 읽기 전용에 저비용인 Explore와 여러 서브에이전트의 병렬 조사로, 메인 컨텍스트를 아끼면서 큰 시스템을 빠르게 파악한다.
- **작업 의존성**: `blocks`와 `blockedBy`로 선후 관계를 선언하면 웨이브 순서로 실행된다. 순서는 Claude의 추측이 아니라 명시적으로 강제되는 구조가 보장한다.
- **고치기 전에 이해하기**: 지저분한 데이터와 설정 디렉터리를 먼저 분석하게 하고, 그 결과를 스펙 문서나 CLAUDE.md로 남긴다. 원본 내보내기, 보충 텍스트, 목표 프롬프트의 3입력 패턴이 효과적이다.
- **레거시 재작성의 세 조건**: 목표 아키텍처가 분명하고, 기존 코드를 스펙으로 삼고, 모듈 단위로 진행한다. 이때 3년 걸린 작업이 몇 주로 줄 수 있다.
- **선택적 로딩**: 천이백만 줄 코드베이스에서도 필요한 부분만 불러와 작업한다. 한계는 코드 크기가 아니라 작업 정의와 컨텍스트의 질이다.
- **스펙 기반 리팩터링**: 조사, 디스크 위의 스펙, 사전 질문, 서브에이전트별 원자적 커밋 순서로 진행하고 오케스트레이터는 가볍게 유지한다.
- **온보딩과 기술 부채**: 잘 가꾼 CLAUDE.md와 Claude Code의 탐색이 데이터 카탈로그와 온보딩 시간을 대신하고, 에이전트가 기술 부채의 경제성을 바꾼다.
