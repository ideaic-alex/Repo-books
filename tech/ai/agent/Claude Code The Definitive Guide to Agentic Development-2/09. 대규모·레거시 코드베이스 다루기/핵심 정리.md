# 핵심 정리

이 문서는 9장 끝에 실린 요점 목록을 풀어 쓴 것이다. 장 전체를 한 번 더 훑고 싶을 때, 각 요점이 왜 중요한지 확인하는 용도로 본다.

---

## 1. 한눈에 보는 요점

- **워크트리로 병렬 세션을 돌린다.** git 워크트리를 쓰면 같은 저장소의 서로 다른 브랜치에서 Claude Code 세션을 동시에 돌려도 서로 간섭하지 않는다. 기다리는 시간 없이 여러 작업을 한꺼번에 진행할 수 있어서 중요하다.
- **Explore 서브에이전트는 아끼지 않고 쓴다.** Haiku 모델로 돌고, 읽기 전용이며, 컨텍스트가 격리되어 있어 비용이 낮다. 낯선 코드를 둘러보는 일을 맡기면 메인 컨텍스트 윈도가 깨끗하게 유지된다.
- **병렬 리서치 서브에이전트로 여러 관점의 이해를 얻는다.** 큰 시스템을 사람이 몇 시간 걸려 파악할 일을 몇 분 만에 여러 각도에서 볼 수 있다. 고치기 전에 이해하는 속도가 곧 전체 속도를 좌우한다.
- **작업 의존성을 명시해 웨이브로 실행한다.** `blocks`와 `blockedBy`로 선후 관계를 적으면 복잡한 마이그레이션과 리팩터링이 순서대로 안전하게 진행된다. 순서를 추측에 맡기지 않아도 된다.
- **레거시 재작성은 세 조건이 맞을 때 성공한다.** 목표 아키텍처가 분명하고, 기존 코드가 스펙 역할을 하고, 작업이 모듈 단위로 나뉘어야 한다. 조건이 빠지면 재작성은 방향을 잃기 쉽다.
- **한계는 코드베이스 크기가 아니라 작업의 명확함과 컨텍스트의 질이다.** 원문이 든 사례는 1,250만 줄 코드베이스에서 수치 정확도 99.9%를 달성한 것이다. 코드가 크다는 이유로 포기할 필요가 없다는 뜻이다.
- **오래된 언어의 장벽이 사라지고 있다.** 에이전트는 요즘 개발자 대부분이 읽지 못하는 언어의 업무 로직도 읽고, 이해하고, 옮길 수 있다. 사람이 없어 방치되던 레거시 시스템을 다시 다룰 수 있게 된다.
- **3입력 워크스페이스 패턴으로 분석을 반복 가능하게 만든다.** 원본 데이터 내보내기, 보충 텍스트 파일, 상세한 목표 프롬프트를 함께 주면 파일시스템 기반 분석이 구조를 갖춘 재현 가능한 과정이 된다.
- **스펙 기반 리팩터링이 바로 코드부터 쓰는 것보다 낫다.** 먼저 조사하고, 정확히 명세하고, 병렬로 실행하는 순서다. 개발자가 직접 짤 수 있는 작업이라도 이 순서가 더 좋은 결과를 낸다.
- **CLAUDE.md가 데이터 카탈로그를 대신할 수 있다.** 세션이 끝날 때마다 내용을 개선하는 루프를 돌리면 온보딩 자료가 늘 최신으로 유지된다.
- **기술 부채를 체계적으로 없앨 수 있다.** 에이전트가 경제성을 바꿔서 "엔지니어 3주를 쓸 가치가 없다"던 일이 "3시간에 리뷰 정도"로 줄어든다. 쌓아 두기만 하던 백로그를 실제로 줄일 수 있게 된다.
