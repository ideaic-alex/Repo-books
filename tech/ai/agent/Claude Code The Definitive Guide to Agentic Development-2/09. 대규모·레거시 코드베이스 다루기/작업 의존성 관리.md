# 작업 의존성 관리

대규모 작업은 서로 의존하는 일들로 이루어진다. 스키마 마이그레이션이 끝나야 API를 고칠 수 있고, 둘 다 끝나야 통합 테스트를 쓸 수 있고, 테스트가 통과해야 배포할 수 있다. 이 문서는 Claude Code의 작업(task) 시스템이 이런 순서를 어떻게 다루는지 설명한다.

핵심은 순서를 Claude의 눈치에 맡기지 않고 명시적인 구조로 선언한다는 점이다.

---

## 1. 왜 의존성이 필요한가

대규모 코드베이스에서 복잡한 작업을 하다 보면 이런 선후 관계가 계속 나온다.

- 데이터베이스 스키마가 마이그레이션되기 전에는 API 엔드포인트를 갱신할 수 없다.
- API와 데이터베이스 변경이 모두 끝나기 전에는 통합 테스트를 쓸 수 없다.
- 테스트가 통과하기 전에는 배포할 수 없다.

## 2. blocks와 blockedBy

Claude Code의 작업 시스템은 `blocks`와 `blockedBy` 관계로 의존성을 명시적으로 선언할 수 있다. 이를 바탕으로 웨이브(wave) 기반 실행이 가능하다. 의존성이 없는 작업이 먼저 돌고, 그 작업에 의존하는 작업이 다음에 돌며, 모든 작업이 끝날 때까지 이어진다.

## 3. 진행 순서

1. **계획**: 작업을 경계가 분명한 개별 작업으로 쪼갠다.
2. **의존성 선언**: 작업 A가 작업 B를 막는다(block)고 선언한다. 작업 C는 A와 B 둘 다에 막힌다(blockedBy).
3. **실행**: Claude Code(또는 에이전트 팀)가 의존성 순서대로 작업을 처리한다. 독립적인 작업은 병렬로, 의존적인 작업은 순차로 돈다.

## 4. 예시: ORM 교체

모듈 오십 개에 걸쳐 ORM 하나를 다른 ORM으로 바꾸는 마이그레이션을 생각해 보자. 손으로 조율하면 악몽 같은 일이지만, 웨이브로 나누면 구조화된 실행 계획이 된다.

| 웨이브 | 내용 | 실행 방식 |
|---|---|---|
| 1 | 핵심 데이터베이스 계층을 마이그레이션한다 | 웨이브 안에서 병렬 가능 |
| 2 | 그 계층에 의존하는 모듈을 갱신한다 | 웨이브 안에서 병렬 가능 |
| 3 | 테스트를 갱신한다 | 웨이브 안에서 병렬 가능 |

웨이브 안에서는 병렬로 돌릴 수 있지만 웨이브끼리는 순차로 실행된다.

## 5. 프롬프트 요령이 아니라 인프라다

이것은 영리한 프롬프트 요령이 아니라 인프라 수준의 프로젝트 관리다. 잘 동작하는 이유는 Claude Code가 "순서를 알아서 알아낼 만큼 똑똑해서"가 아니다. 의존성 시스템이 명시적이고 강제되기 때문이다. 구조는 사람이 정의하고, 실행은 Claude Code가 한다.

## 6. 정리

- 작업을 쪼개고 `blocks`/`blockedBy`로 선후 관계를 선언하면 웨이브 순서로 실행된다.
- 의존성이 없는 작업은 병렬로, 의존하는 작업은 순차로 처리된다.
- 순서를 보장하는 것은 명시적으로 강제되는 의존성 시스템이다.
- 모듈 수십 개에 걸친 ORM 마이그레이션 같은 작업에서 효과가 크다.
