# 워크트리와 파일 제안 설정

코드베이스가 커지면 가장 먼저 부딪히는 문제는 "한 번에 한 가지 일밖에 못 한다"는 점이다. 같은 디렉터리에서 브랜치를 바꿔 가며 에이전트 여러 개를 돌릴 수는 없다. 이 문서는 git worktree(워크트리: 저장소를 다시 복제하지 않고 브랜치마다 별도 작업 디렉터리를 만드는 기능)로 Claude Code 세션을 여러 개 병렬로 돌리는 방법을 설명한다.

함께 다루는 주제는 모노레포(monorepo: 여러 프로젝트를 한 저장소에 담은 구조)에서 `@` 자동완성이 느리거나 파일을 놓칠 때 쓰는 파일 제안 커스터마이징이다. 둘 다 규모가 큰 저장소에서 작업 속도를 올리는 기본기다.

---

## 1. 가장 단순하고 가장 덜 쓰이는 확장 기법

대규모 저장소를 다루는 기법 중 가장 단순한 것이 워크트리다. 그런데 의외로 잘 쓰이지 않는다. 워크트리는 브랜치 하나를 위한 별도의 작업 디렉터리를 만들어 준다. 저장소 전체를 다시 clone하지 않아도 된다.

워크트리마다 다음이 따로 있다.

- 체크아웃된 파일
- 자기만의 인덱스(index)
- 독립적으로 실행되는 Claude Code 세션

중요한 점은 세션끼리 컨텍스트를 공유하지 않는다는 것이다. 서로 간섭하지 않는다. 같은 저장소를 쓰지만 디렉터리는 완전히 분리되어 있다.

## 2. 사용 방법

워크트리는 브랜치마다 디렉터리를 하나씩 만드는 방식으로 쓴다.

```bash
git worktree add ../feature-auth feature/auth
git worktree add ../feature-payments feature/payments
```

이렇게 만들어 두면 `../feature-auth`에서는 인증 기능을, `../feature-payments`에서는 결제 시스템을 각각 다른 Claude Code 세션으로 동시에 작업할 수 있다. 두 세션 모두 저장소 히스토리 전체에 접근할 수 있다. 하지만 파일 변경, 컨텍스트 윈도, 대화 기록은 완전히 독립적이다.

## 3. 왜 필요한가

대규모 코드베이스에서 가장 큰 병목은 순차 작업인 경우가 많다. 같은 디렉터리에서 서로 다른 브랜치를 맡은 Claude Code 세션 두 개를 돌리면 서로 파일을 덮어쓰게 된다. 워크트리는 이 제약을 없앤다.

이 방식은 선형으로 늘어난다. 브랜치 세 개면 워크트리 세 개, 세션 세 개다. 한계는 구조가 아니라 내 컴퓨터의 자원과 API 예산이다. 독립적인 기능 여러 개가 동시에 진행 중인 모노레포 팀이라면, 워크트리 덕분에 Claude Code 하나가 병렬 세션 여러 개로 바뀌는 셈이다.

| 항목 | 같은 디렉터리에서 세션 여러 개 | 워크트리마다 세션 하나 |
|---|---|---|
| 파일 충돌 | 서로 덮어쓸 위험이 있다 | 디렉터리가 분리되어 없다 |
| 컨텍스트 | 같은 작업 공간을 공유한다 | 세션마다 독립이다 |
| 히스토리 접근 | 가능하다 | 가능하다 |
| 한계 | 구조상 사실상 불가능하다 | 컴퓨터 자원과 API 예산 |

## 4. 워크트리별 .claude 디렉터리

실무에서 알아 둘 점이 하나 있다. 저장소에 `.claude/` 디렉터리가 있으면 워크트리마다 그 디렉터리가 따로 생긴다. 그래서 프로젝트 수준의 CLAUDE.md와 설정이 워크트리마다 독립적으로 적용된다. 3장에서 다룬 CLAUDE.md 내용이 워크트리를 가로질러 충돌 없이 쌓인다는 뜻이다.

## 5. 모노레포용 파일 제안 커스터마이징

Claude Code에서 `@`를 입력하면 파일 자동완성이 뜬다. 일반적인 저장소에서는 잘 동작한다. 하지만 모노레포처럼 큰 저장소에서는 기본 파일 인덱싱이 느리거나, 깊이 중첩된 디렉터리 안의 파일을 놓칠 수 있다.

해법은 직접 만든 인덱싱이다. `@`를 입력할 때 Claude Code가 보여 주는 파일 제안을 만들어 내는 스크립트를 직접 제공할 수 있다. 이 스크립트에는 어떤 로직이든 넣을 수 있다.

- 최근에 수정한 파일을 우선한다.
- 빌드 산출물을 제외한다.
- 내가 관심 있는 패키지만 인덱싱한다.
- 완전히 새로운 정렬 순서를 쓴다.

패키지가 수백 개인 모노레포라면 지금 작업과 관련된 패키지만 걸러 내는 인덱싱 스크립트가 `@` 경험을 확 바꿔 준다. 수천 개 파일을 스크롤하는 대신 정말 필요한 스무 개 정도만 본다.

## 6. 작은 기능이지만 효과가 큰 이유

파일이 만 개 정도인 모노레포에서는 올바른 파일을 빨리 가리키는 것만으로 두 가지를 아낄 수 있다.

- **컨텍스트 절약**: Claude가 알아서 검색하게 두는 대신 정확한 코드를 직접 가리킨다.
- **시간 절약**: 어디를 봐야 하는지 이미 알고 있으니 탐색 단계를 건너뛴다.

## 7. 정리

- 워크트리는 브랜치마다 작업 디렉터리를 나누어 세션을 병렬로 돌리게 해 주는 가장 단순한 확장 기법이다.
- 세션은 컨텍스트와 파일 변경이 모두 독립이라 서로 간섭하지 않는다.
- 한계는 구조가 아니라 컴퓨터 자원과 API 예산이다.
- 큰 모노레포에서는 `@` 파일 제안을 스크립트로 직접 만들어 관련 파일만 보이게 하면 효과가 크다.
