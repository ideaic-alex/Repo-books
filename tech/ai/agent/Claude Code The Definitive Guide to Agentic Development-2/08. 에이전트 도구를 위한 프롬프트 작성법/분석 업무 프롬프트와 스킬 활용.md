# 분석 업무 프롬프트와 스킬 활용

앞에서 다룬 패턴은 범용이다. 하지만 재무 분석, 기술 감사, 데이터 사이언스 같은 분석 업무에서는 일반 패턴이 주지 못하는 구조적인 깊이가 프롬프트에 필요하다. 이 문서는 자기 비평이 실제로 어떤 결과를 냈는지, 분석용 목표 프롬프트를 어떻게 구성하는지, 반복해서 쓰는 프롬프트 흐름을 스킬(skill)로 묶는 방법을 다룬다. 개발자가 아닌 팀원과 일할 때의 흐름과 글쓰기 샘플을 주는 방법도 함께 다룬다.

---

## 1. 자기 비평 사례

한 실무자가 Claude Code에게 재무 최적화 계획을 만들게 한 뒤 "이 계획에 1에서 10까지 점수를 매기고 무엇을 개선하겠는지 말해라"라고 요청했다.

Claude는 자기 계획에 10점 만점에 7.5점을 줬고, 구체적인 개선점 일곱 가지를 짚었다. 그중에는 중요한 발견이 있었다. 계획이 일부 자산을 배분하면서 특정 은퇴 계좌가 세금이 면제된다는 점을 무시했다는 것이다. 그 계좌 안에서 팔고 재배분하면 세금이 전혀 들지 않는데, 처음 계획은 이를 활용하지 않았다. 자기 비평이 놓친 최적화를 찾아냈고, 수정된 계획에 반영됐다.

교훈은 자기 비평이 항상 일곱 가지를 찾는다는 것이 아니다. 처음 생성에서는 분명하지 않은 개선점을 찾아낸다는 것이다. 생성 과정은 프롬프트의 가장 흔한 해석에 맞춰 최적화되므로 이런 최적화는 처음에 들어가지 않는다. 자기 비평 단계는 첫 번째 패스가 놓친 것을 잡는 두 번째 패스를 강제한다.

분석 작업에서 특히 효과적인 프롬프트는 이렇다. 자기 비평 섹션을 포함하고, 계획에 1에서 10까지 점수를 매기고, 개선할 모든 점을 나열하게 한다. 자기 비평을 사후 점검이 아니라 결과물에 반드시 들어가는 섹션으로 만들면 충분한 주의를 받는다.

## 2. 목표 프롬프트의 구조

복잡한 분석 작업에서 자세한 목표 프롬프트는 다음 일곱 가지 요소로 구성된다.

1. **어떤 데이터가 어디에 있는지.** 예를 들어 `/data/accounts/`에 계좌 세 개의 CSV 내보내기 파일이 있고, `/data/notes.txt`에는 내보낼 수 없었던 보충 정보가 있다고 알려 준다.
2. **원하는 출력 형식.** 자산, 현재 비중, 목표 비중, 격차, 우선순위, 조치를 열로 하는 표를 만들고, 요약 섹션과 방법론 부록을 포함하라고 한다.
3. **선호와 원칙.** 순수 수익률보다 세금 효율을 우선하고, 수수료를 최소화하고, 단순함을 선호하라고 한다.
4. **알려진 제약.** 은퇴 계좌 납입은 자동이므로 건드리지 말고, 증권 계좌에는 최소 잔고 10,000달러 조건이 있다고 말한다.
5. **무엇이 잘못됐다고 의심하는지.** 포트폴리오가 대형 성장주에 쏠려 있다고 생각하지만, 다른 견해가 있다면 듣고 싶다고 쓴다. 이 단서가 있어야 Claude가 내 의심에만 끌려가서 반대 증거를 무시하는 일을 막을 수 있다.
6. **초안 제안.** 대략적인 목표 배분안을 준다. 예를 들면 국내 주식 40퍼센트(대형주와 중형주 60 대 40), 해외 20퍼센트, 채권 30퍼센트, 대체 자산 10퍼센트이고, 틀렸을 수도 있다는 단서를 붙인다.
7. **철저한 질문 지시.** 마지막에 "진행하기 전에 확실하지 않은 모든 것에 대해 철저하게 질문해라"를 넣는다. 끝에 두면 Claude가 결론으로 달려가기 전에 확인 질문부터 한다.

이 구조는 금융 밖에서도 통한다. 도메인 맥락, 출력 기대치, 미묘한 선호를 한꺼번에 전달해야 하는 모든 분석 작업에 쓸 수 있다.

### 동적 제약 재구성

프로젝트 도중에 제약을 다시 틀 지어서 Claude가 분석 틀 전체를 다시 짜는 모습을 볼 수 있다. 예를 들어 "은퇴 계좌를 고정 제약으로 취급해라. 이상적인 전체 포트폴리오를 계산하고, 은퇴 계좌가 제공하는 몫을 빼고, 남은 계좌들을 최적화해서 빈 곳을 채워라"라고 말한다. Claude는 새 틀에 맞춰 모든 목표, 격차, 권고를 다시 계산한다. 고정된 부분은 주어진 값이 되고 변하는 부분이 최적화된다.

이 방식은 새 프롬프트로 처음부터 다시 하는 것보다 강력하다. Claude가 분석의 전체 컨텍스트를 유지한 채 재구성된 제약 위에서 다시 쌓기 때문이다.

## 3. 스킬로 프롬프트 흐름 묶기

스킬은 복잡한 프롬프트 패턴을 재사용 가능한 작업 흐름으로 담을 수 있다. 커뮤니티가 만든 스킬 두 가지가 좋은 예다.

### 워크스루(walkthrough) 스킬

"walkthrough how does authentication work in this codebase" 같은 질의로 워크스루 스킬을 부르면 네 단계 파이프라인이 실행된다.

1. 서브에이전트를 두 개에서 네 개 띄워 코드베이스의 관련 부분을 병렬로 탐색한다.
2. 발견한 내용을 서로 연결된 다섯 개에서 열두 개의 핵심 개념으로 종합한다.
3. 상호작용하는 다이어그램이 들어간 독립형 HTML 파일을 만든다.
4. 다이어그램을 브라우저에서 연다.

다이어그램의 각 노드는 클릭할 수 있다. 클릭하면 쉬운 말로 된 설명, 파일 경로, 코드 조각이 담긴 상세 패널이 나타난다. 시스템에 대한 머릿속 모델이 2분 안에 만들어진다.

이 스킬이 보여 주는 패턴은 모든 복잡한 프롬프트 흐름에 적용된다. 병렬 조사, 종합, 산출물 생성 같은 여러 단계를 스킬에 담아서 단일 명령으로 만든다. 프롬프트는 한 번 잘 만들어 시험해 두면 계속 재사용할 수 있다.

### /learn 스킬 패턴

학습 스킬은 다섯 단계를 따른다.

| 단계 | 내용 |
|---|---|
| 1 | 현재 대화를 깊이 분석한다 |
| 2 | 통찰을 패턴, 함정(gotcha), 아키텍처 결정으로 분류한다 |
| 3 | 배운 내용을 문서로 초안 작성한다 |
| 4 | 사용자 승인을 받는다. 스킬이 멈추고 확인을 기다리는 차단 단계다 |
| 5 | 알맞은 문서 파일에 저장한다 |

이 패턴은 대화에서 조직의 지식을 뽑아내서 남긴다. Claude가 찾아낸 유용한 발견이 세션이 끝나면서 사라지는 대신, 이후 세션과 이후 개발자에게 도움이 되는 문서로 남는다. 차단 승인 단계가 있어서 사람의 검토 없이 저장되는 내용은 없다.

### 스킬의 점진적 공개

잘 설계된 스킬은 점진적 공개(progressive disclosure)로 컨텍스트 비용을 최소화한다. 분석 컨설턴트 스킬을 예로 들면, 스킬 디렉터리에는 스킬 정의와 빠른 시작 안내가 든 `skill.md` 파일, 실행 가능한 도구가 든 `scripts/` 디렉터리, 상세 문서가 든 `references/` 디렉터리가 있다.

사용자의 프롬프트가 스킬 설명과 맞으면 `skill.md`만 컨텍스트에 올라온다. 스킬이 실행되면 `scripts/`의 CLI 도구를 호출한다. 도구가 자세한 안내를 필요로 할 때만 `references/`를 읽는다. 전체 참고 자료는 필요하지 않으면 컨텍스트에 들어오지 않는다. 이 설계는 기본 컨텍스트 비용을 거의 0으로 유지하면서도 아무리 복잡한 작업도 지원한다.

## 4. 개발자가 아닌 팀원과 일하는 방식

### 두 인터페이스 계획

비기술 구성원이 있는 팀은 독특한 흐름을 쓴다고 한다. 먼저 클라우드 AI 채팅 인터페이스에서 브레인스토밍하고, 구현은 Claude Code로 옮겨서 한다. 클라우드 인터페이스는 열린 탐색에 더 낫다. 작업 흐름을 생각하고, 대안을 따져 보고, 접근법을 스케치하기 좋다. 계획이 분명해지면 채팅 인터페이스에서 포괄적인 프롬프트를 만들고 Claude Code에 붙여 넣어 시작점으로 쓴다.

핵심은 클라우드 인터페이스에게 한 번에 전부 내놓지 말고 속도를 늦춰 한 단계씩 하라고 요청하는 것이다. 계획 단계의 결과물은 코드도 설계 문서도 아니고, Claude Code가 실제로 받을 입력인 구조화된 프롬프트다. 이 두 인터페이스 방식은 비개발자가 창의적인 작업에는 익숙한 인터페이스를 쓰고, 기술적인 실행은 그 일을 위해 설계된 도구에 맡기게 해 준다.

### 글쓰기 샘플 제공

Claude가 문서나 보고서 같은 글을 쓸 때 글쓰기 샘플을 주면 스타일이 훨씬 잘 맞는다. 한 팀은 문서 작업을 시작할 때 서식 선호와 예시 문서를 함께 준다. 예를 들어 "이것이 우리가 런북(runbook)을 쓰는 방식의 예시다. 제목 구조, 불릿 밀도, 문제 해결 단계의 상세 수준까지 이 스타일에 맞춰라"라고 말한다.

Claude는 추상적인 스타일 설명을 따를 때보다 예시에서 규칙을 뽑아낼 때 더 믿을 만하다. "간결하고 직접적인 스타일로 써라"는 모호하다. 내 실제 글의 세 문단 샘플은 정확하다. 비용은 예시 입력 몇백 토큰이다. 이득은 다시 쓰지 않고 바로 쓸 수 있는 결과물이다.

## 5. 정리

- 분석 업무의 목표 프롬프트는 데이터 위치, 출력 형식, 원칙, 제약, 의심, 초안, 철저한 질문의 일곱 요소로 구성한다.
- 의심을 말할 때는 다른 견해도 듣고 싶다는 단서를 붙여서 Claude가 내 생각에만 끌려가지 않게 한다.
- 자기 비평은 결과물에 필수 섹션으로 넣을 때 가장 잘 동작한다. 처음 생성이 놓친 최적화를 찾아낸다.
- 반복되는 다단계 프롬프트는 스킬로 묶는다. 워크스루 스킬은 병렬 조사와 시각화를 한 명령으로 만든다. `/learn` 패턴은 사람의 승인을 거쳐 지식을 문서로 남긴다.
- 스킬은 점진적 공개로 컨텍스트 비용을 줄인다. 글쓰기 샘플은 스타일 설명보다 정확하다.
