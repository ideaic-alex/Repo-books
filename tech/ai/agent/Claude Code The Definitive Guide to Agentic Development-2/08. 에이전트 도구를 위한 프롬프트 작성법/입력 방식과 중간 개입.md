# 입력 방식과 중간 개입

Claude Code는 글로 쓴 프롬프트만 받는 도구가 아니다. 파일 참조, 이미지, URL, 파이프 입력까지 다양한 입력을 받고, 작업 도중에 끼어들어 방향을 바꿀 수도 있다. 이 문서는 이런 입력 방식과 중간 개입(interrupt and steer), 그리고 Claude에게 역할을 정해 주는 방법을 정리한다. 스크린샷을 활용한 작업 방식도 함께 다룬다.

입력 방식을 폭넓게 쓰면 결과가 꾸준히 좋아진다. 입력마다 컨텍스트가 늘고 컨텍스트는 토큰을 쓰지만, 알맞은 입력은 오히려 비용이 적다. 문단으로 설명하는 대신 스크린샷을 한 장 붙이고, 파일을 말로 설명하는 대신 파일을 직접 참조하는 식이다.

---

## 1. 풍부한 입력 방식

### 파일 참조(`@`)

`@` 뒤에 경로를 쓰면 파일 내용이 컨텍스트에 바로 들어간다. Claude에게 파일을 읽으라고 시키는 것보다 싸고 확실하다. 내용이 프롬프트 안에 이미 있고, 도구 호출로 가져오는 과정이 없기 때문이다.

### 이미지

UI 목표 화면, 에러 메시지, 디자인 시안, 화이트보드 스케치를 붙여 넣는다. Claude는 이미지를 해석하고 시각적인 목표에 맞춰 구현할 수 있다. 화면 구성을 세 문단으로 설명하는 것보다 "대시보드를 이 모양으로 만들어 줘"라는 말과 스크린샷 한 장이 더 정확하다.

### URL

Claude는 웹 콘텐츠를 가져와 해석할 수 있다. API 문서, 스타일 가이드, 참고 구현의 주소를 알려 주면 복사해서 붙여 넣는 수고를 덜 수 있다.

### 파이프 입력

Claude Code는 유닉스 도구처럼 동작한다. 데이터를 파이프로 넘기면 기존 명령줄 작업 흐름에 바로 연결된다.

```bash
cat error.log | claude "what's causing these failures?"
git diff HEAD~5 | claude "summarize these changes"
```

## 2. 중간에 끼어들어 방향 바꾸기

Claude Code는 한 번 돌리면 끝나는 배치(batch) 처리가 아니다. 작업 중에 끼어들 수 있다. 잘못된 방향으로 가고 있다면, 예를 들어 원하지 않는 해법을 구현하거나, 쓰지 않는 라이브러리를 고르거나, 엉뚱한 파일을 고치고 있다면, 수정할 내용을 입력하고 Enter를 누른다. Claude는 하던 일을 멈추고 수정 내용을 읽은 뒤 방향을 조정한다.

이 실시간 조정 루프가 에이전트 도구를 "한 번에 생성하는 도구"와 질적으로 다르게 만든다. 전체 출력이 나오기를 기다렸다가 검토하고 거절하는 것이 아니라, 작업이 진행되는 모습을 보면서 그 자리에서 방향을 바꾼다.

### 효과적인 끼어들기

끼어들기는 구체적이어야 한다. 예를 들어 "멈춰. 새로 만들지 말고 `config/db.ts`에 있는 기존 데이터베이스 연결을 써"는 좋은 개입이다. "그거 아니야"처럼 모호하게 말하면 Claude는 무엇이 문제인지 추측해야 한다.

이 방식은 복잡한 작업을 시작하고 처음 몇 분 동안 가장 가치가 크다. 초기 접근 방식에 Claude의 가정이 드러나기 때문이다. 가정을 일찍 바로잡으면 나머지 구현이 올바른 방향으로 따라온다.

### 단순함을 요구하는 끼어들기

Claude는 복잡한 해법으로 기우는 경향이 있다. 추상화를 만들고, 층을 더하고, 패턴을 끌어들인다. 문제가 복잡하면 이것이 장점이지만, 단순한 방법이 맞는 상황에서도 지나치게 나아가는 경우가 있다.

이럴 때는 작업 도중에 멈추고 "왜 이렇게 하고 있어? 더 단순하게 해 봐"라고 말한다. Claude는 단순함 요청에 잘 반응해서 불필요한 추상화와 층을 걷어내고 더 직접적인 해법을 내놓는다.

앞에서 말한 일반적인 끼어들기는 방향을 바로잡는 것이고, 이 패턴은 복잡도를 바로잡는 것이다. 필요 없어 보이는 새 파일, 호출 하나만 감싸는 추상화, 가치 없이 간접 단계만 늘리는 패턴이 보이면 바로 끼어든다.

## 3. 역할 지정 프롬프트

Claude에게 역할을 정해 주면 행동이 달라진다. 신비로운 프롬프트 기법이 아니라, 협업에서 기대하는 바를 맞춰 두는 일이다.

대표적인 예가 조율자(orchestrator) 역할이다. 여러 에이전트를 나누어 맡기고 조율하는 일(오케스트레이션)을 하게 하려면 이런 식으로 말한다. "너는 조율자다. 서브에이전트들이 너의 개발팀이다. 각자에게 분명하고 범위가 정해진 작업을 맡기고, 결과를 합치기 전에 검토해라." 이렇게 말하면 Claude는 모든 것을 메인 컨텍스트에서 직접 구현하지 않고 서브에이전트에게 위임한다. 행동하기 전에 계획하고, 결과를 검토한다.

이런 역할 설정이 없으면 Claude는 한 컨텍스트 안에서 혼자 모든 일을 처리하는 경향이 있다. 작은 작업이라면 괜찮다. 하지만 여러 파일에 걸친 리팩터링이나 서비스를 넘나드는 변경에서는 컨텍스트가 바닥나고 세부 사항이 빠진다. 조율자 역할은 다른 작업 패턴을 끌어낸다.

### 그 밖의 역할 설정

| 역할 | 프롬프트 방향 | 효과 |
|---|---|---|
| 조사자(Investigator) | 이해하는 것이 임무이고 바꾸지 않으며 발견한 내용만 보고하라고 한다 | 탐색 작업에서 Claude를 읽기 전용 상태로 유지한다 |
| 리뷰어(Reviewer) | 시니어 엔지니어로서 PR을 보되 정확성, 보안, 유지보수성에 집중하라고 한다 | 코드 변경 대신 구조화된 리뷰 결과가 나온다 |
| 전문가(Specialist) | 데이터베이스 마이그레이션 전문가로서 스키마 변경과 데이터 무결성만 신경 쓰라고 한다 | 초점이 좁아져서 관련 없는 변경이 줄어든다 |

## 4. 이미지와 스크린샷 활용법

Claude Code는 여러 경로로 이미지를 받고, 경로마다 잘 맞는 용도가 있다.

- **드래그 앤 드롭.** 데스크톱 앱에서는 이미지 파일을 프롬프트 영역에 끌어다 놓는다. 지원하는 터미널에서도 드래그 앤 드롭이 된다.
- **복사해서 붙여넣기.** `Ctrl+V`로 클립보드의 이미지를 붙여 넣는다. 맥에서도 `Cmd+V`가 아니라 `Ctrl+V`를 쓴다는 점이 자주 틀리는 부분이다. 시스템 스크린샷 도구로 찍은 화면은 클립보드에 들어가므로 바로 붙여 넣을 수 있다.
- **파일 경로.** 경로로 이미지를 가리킨다. 예를 들어 "`./screenshots/bug.png`에 있는 스크린샷을 보고 레이아웃 문제를 찾아줘"라고 한다. Claude가 이미지 파일을 읽고 내용을 해석한다.
- **참조된 이미지 열기.** Claude가 답변에서 이미지 경로를 언급하면 `Ctrl+Click`(맥은 `Cmd+Click`)으로 시스템 뷰어에서 열 수 있다. Claude가 이미지를 만들었거나 기존 스크린샷을 가리킬 때 유용하다.

### 스크린샷으로 디버깅하기

한 인프라 팀은 이미지 입력을 UI 작업 밖으로 넓혔다. 컨테이너 오케스트레이션 클러스터가 멈추고 새 파드(pod)를 스케줄하지 못하자, 모니터링 대시보드 스크린샷을 Claude Code에 넣었다. Claude는 대시보드 시각화를 해석해서 IP 주소가 고갈됐다는 경고를 찾아냈다. 그리고 클라우드 제공자의 관리 화면을 메뉴 단위로 안내하며 문제를 풀 명령어를 알려 줬다. 대시보드 상태를 말로 설명하는 것보다 스크린샷이 더 정확했다.

이 패턴은 증상은 눈에 보이는데 해결책은 기술적인 모든 곳에 쓸 수 있다. 인프라 대시보드, 에러 메시지 캡처, 로그 뷰어 화면, 네트워크 구성도가 그런 예다. Claude는 이미지를 해석해서 코드베이스의 기술적 맥락에 연결한다.

### 개발자가 아닌 사람의 시각 중심 반복

디자이너, 기획자, 법무 담당자 같은 비개발 직군은 스크린샷을 Claude Code와 소통하는 주된 수단으로 쓰는 경우가 많다. 원하는 화면의 스크린샷을 붙이면 Claude가 구현한다. 결과를 보고 무엇이 틀렸는지 다시 스크린샷으로 보여 주면 Claude가 고친다. 반복 과정 전체가 시각적이어서 코드 이야기가 전혀 없다.

이것은 개발자의 작업 흐름과 다른 상호작용 방식이다. 개발자는 변경을 코드 용어로 설명하고, 비개발자는 겉모습으로 설명한다. 둘 다 올바른 입력이다. 스크린샷 방식은 한 번 반복하는 데 시간이 더 걸리지만 기술 용어가 하나도 필요 없다.

---

## 5. 정리

- 입력은 텍스트에 한정되지 않는다. `@` 파일 참조, 이미지, URL, 파이프 입력을 상황에 맞게 쓴다.
- 작업 중에 끼어들어 방향을 바꿀 수 있다. 개입은 구체적으로, 특히 초반에 하는 것이 효과가 크다.
- 역할을 정해 주면 작업 방식이 바뀐다. 조율자 역할은 서브에이전트 위임과 계획, 검토를 끌어낸다.
- 증상이 눈에 보이는 문제는 스크린샷이 말보다 정확하다. 비개발자와 협업할 때도 시각 중심 반복이 통한다.
