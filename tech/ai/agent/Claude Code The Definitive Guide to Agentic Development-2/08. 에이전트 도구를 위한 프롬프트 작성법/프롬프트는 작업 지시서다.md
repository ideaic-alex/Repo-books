# 프롬프트는 작업 지시서다

에이전트(agent) 도구에 쓰는 프롬프트는 챗봇에 던지는 질문과 성격이 다르다. 챗봇은 글을 만들어 주는 데서 끝나지만, Claude Code 같은 에이전트는 파일을 읽고, 코드를 쓰고, 테스트를 돌리고, 파일 시스템까지 바꾸면서 수십 가지 작업을 이어서 처리한다. 그래서 프롬프트는 질문이라기보다 작업 지시서에 가깝다.

깔끔하게 구현되는 프롬프트와 세 시간짜리 뒷정리를 만드는 프롬프트의 차이는 문장력이 아니라 엔지니어링에서 나온다. 이 문서는 그 중에서도 가장 효과가 큰 검증 기준, 구체성의 수준, 위임하는 태도를 다룬다.

---

## 1. 무엇보다 중요한 한 가지: 검증 기준

이 장 전체에서 하나만 가져간다면 이것이다. Claude가 자기 작업을 스스로 확인할 방법을 알려 준다. 영리한 표현이나 긴 시스템 프롬프트보다 이 한 가지가 훨씬 효과가 크다.

검증 기준이 없으면 Claude는 "만들고 기대하는" 방식으로 움직인다. 코드를 쓰고, 스스로 맞아 보인다고 판단하고, 다음으로 넘어간다. 버그는 사람이 찾아야 하고, 출력 형식이 틀려도 사람이 알아채야 하고, 예외 상황은 운영 환경에서 터진 뒤에야 알게 된다.

검증 기준이 있으면 "만들고, 시험하고, 고치는" 방식으로 바뀐다. 코드를 쓰고, 검증을 실행하고, 결과를 보고, 통과할 때까지 반복한다. 피드백 루프가 자동으로 돌아간다. 성공 조건은 내가 정하고, 그 조건을 쫓아가는 일은 Claude가 한다.

### 검증 기준의 종류

| 종류 | 예시 |
|---|---|
| 테스트 명령 | 변경할 때마다 `npm test`를 실행하고 전부 통과하는지 확인하라고 지시한다 |
| 기대 출력 | 입력이 `[1, 2, 3, 4]`일 때 함수가 `[1, 4, 9, 16]`을 돌려줘야 한다고 적는다 |
| 시각 확인 | 목표 UI의 스크린샷을 붙이고 결과가 이렇게 보여야 한다고 말한다 |
| 동작 설명 | 인증 헤더 없이 호출하면 API가 400 상태 코드를 돌려줘야 한다고 적는다 |
| 기존 테스트 묶음 | 전체 테스트를 돌려서 기존 기능이 깨지지 않았는지(회귀가 없는지) 확인하라고 한다 |

### 핵심 통찰: 한 번에 맞힐 필요가 없다

검증 기준은 "한 번에 생성하고 끝나는 작업"을 "반복하는 루프"로 바꾼다. Claude는 처음부터 정답을 낼 필요가 없고, 멈추기 전에 정답에 도달하면 된다. 검증 기준이 곧 "멈추기 전"이 무엇인지 정의해 준다.

## 2. 기준이 없을 때와 있을 때

"API에 사용자 인증을 추가해 줘"라고만 쓰면 Claude는 그럴듯해 보이는 구현을 내놓는다. 동작할 수도 있고 아닐 수도 있다. 이때는 내가 검증 단계가 되는데, 코드 리뷰만으로는 미묘한 문제를 놓치기 쉽다.

같은 요청에 다음을 덧붙이면 상황이 달라진다.

```text
API에 사용자 인증을 추가해 줘. 구현이 끝나면 pytest tests/auth/ 를 실행해.
테스트는 모두 통과해야 해. /api/protected 엔드포인트는
토큰이 없으면 401, 유효한 토큰이 있으면 200을 돌려줘야 해.
```

이제 Claude에게 목표가 생겼다. 테스트를 돌리고, 엔드포인트를 직접 호출해 보고, 기준을 만족할 때까지 반복한다. 끝내 못 맞추면 막힌 이유를 알려 준다. 이런 문장을 덧붙이는 데 드는 시간은 30초 정도이고, 안 붙였을 때의 비용은 디버깅 시간으로 계산된다.

---

## 3. 구체적인 프롬프트와 모호한 프롬프트

모호한 프롬프트를 써야 할 때가 있고 구체적인 프롬프트를 써야 할 때가 있다. 이 구분을 아는 것이 위임을 잘하는 사람과 시간을 낭비하는 사람의 차이다.

**탐색에는 모호한 프롬프트가 맞다.** 예를 들어 "이 코드베이스에서 인증 흐름은 어떻게 생겼어?", "에러 처리는 어떤 구조야?", "다국어 지원을 넣으려면 뭐가 필요해?" 같은 질문이다. 답을 모르고 Claude가 넓게 읽어서 알아내 주기를 바라는 상황이므로, Claude가 넓게 읽고 종합하는 능력을 그대로 쓰는 편이 낫다.

**구현에는 구체적인 프롬프트가 맞다.** 예를 들면 이런 식이다. `src/auth/middleware.ts`의 `validateToken` 함수에 속도 제한(rate limiting)을 추가한다. IP당 분당 100건의 슬라이딩 윈도(sliding window)를 쓴다. 횟수 저장에는 `src/config/cache.ts`에 이미 있는 인메모리 저장소 연결을 쓴다. 테스트는 `tests/auth/rate-limit.test.ts`에 추가한다.

### 흔한 실패: 구현 작업을 모호하게 시키는 것

"속도 제한 추가해 줘"처럼 어디에, 어떻게, 무엇에 적용할지 빼고 말하면 Claude에게 선택의 자유가 너무 많이 간다. 엉뚱한 파일을 고르고, 이미 있는 캐시 연결 대신 새 연결을 만들고, 공유 캐시에 둘 상태를 로컬 메모리에 저장하기도 한다. 각각의 가정은 따로 보면 합리적이지만 우리 코드베이스에는 맞지 않는다.

---

## 4. 구체성을 높이는 세 가지: 파일, 제약, 예시

결과를 꾸준히 좋게 만드는 구체성은 세 갈래로 나뉜다.

- **특정 파일을 지목한다.** `@` 멘션이나 명시적인 경로를 쓴다. 예를 들어 "우리가 쓰는 패턴은 `@src/utils/validation.ts`를 봐"라고 하면 Claude가 맞는 파일을 찾느라 헤맬 필요가 없다. 이미 가리켜 줬기 때문이다.
- **제약을 말한다.** 바꾸면 안 되는 것, 감수할 수 있는 트레이드오프, 움직여도 되는 범위를 알려 준다. 예를 들면 "데이터베이스 스키마는 건드리지 마. 여기서는 코드 가독성보다 성능이 중요해. 새 파일은 추가해도 되지만 기존 디렉터리 구조는 바꾸지 마" 같은 식이다.
- **예시를 준다.** 특정 형식의 출력을 원하면 그 형식을 보여 주고, 특정 패턴을 따르는 코드를 원하면 그 패턴을 보여 준다. Claude는 추상적인 설명을 따를 때보다 예시에서 규칙을 뽑아낼 때 더 잘 맞춘다.

---

## 5. 위임하는 태도

에이전트에게 프롬프트를 쓰는 일은 스크립트에 지시를 적는 일이 아니라, 유능한 동료에게 일을 맡기는 일이다. 이 구분이 프롬프트에 무엇을 넣을지를 바꾼다.

스크립트에는 모든 단계를 적는다. "이 파일을 열고, 이 함수를 찾고, 이 줄을 추가하고, 저장해라" 같은 식이다. 동료에게는 목표와 맥락을 말한다. "봇이 계속 몰려와서 인증 미들웨어에 속도 제한이 필요하다. 캐시 연결은 이미 있다. 결제 엔드포인트에 썼던 슬라이딩 윈도 방식을 똑같이 쓰자" 정도면 된다. 동료는 단계를 스스로 찾고, 스크립트는 내가 적은 단계만 실행한다. Claude Code는 동료 쪽이다.

위임하는 태도는 프롬프트를 세 가지 방향으로 바꾼다.

1. **단계보다 목표.** 어떻게 하라고 쓰기보다, 작업이 끝났을 때 무엇이 참이어야 하는지를 쓴다.
2. **지시보다 맥락.** 이 변경이 왜 필요한지, 이미 무엇이 있는지, 제약이 무엇인지를 설명한다.
3. **통제보다 신뢰.** 구현 방식은 Claude가 고르게 둔다. 미리 막지 말고, 잘못 고르는 것이 보일 때 개입한다.

개발자에게는 불편한 태도다. 우리는 정확하게 명세하도록 훈련받았기 때문이다. 하지만 에이전트를 과하게 명세하면 내가 떠올린 방식에 묶이게 되고, 그 방식이 최선이 아닐 수 있다. 목표를 말하고, 맥락을 주고, 일하게 둔다.

---

## 6. 정리

- 가장 효과가 큰 습관은 검증 기준을 프롬프트에 넣는 것이다. 테스트 명령, 기대 출력, 스크린샷, 동작 설명 모두 쓸 수 있다.
- 탐색은 모호하게, 구현은 구체적으로 시킨다. 구현을 모호하게 시키면 Claude가 코드베이스와 맞지 않는 합리적인 가정을 쌓는다.
- 구체성은 파일 지목, 제약 명시, 예시 제공으로 만든다.
- 스크립트가 아니라 동료에게 맡기듯 목표, 맥락, 신뢰를 중심으로 쓴다.
