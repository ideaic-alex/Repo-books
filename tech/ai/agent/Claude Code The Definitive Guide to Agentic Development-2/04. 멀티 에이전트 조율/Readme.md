# 멀티 에이전트 조율

작업이 컨텍스트 윈도 하나를 넘어서면 한계와 씨름하거나 일을 나눠야 한다. 이 장은 여러 에이전트를 나누어 맡기고 조율하는 일(오케스트레이션)을 다룬다. 서로 구조가 다른 두 가지 방식인 서브에이전트와 실험 기능인 에이전트 팀을 비교하고, 각각의 비용과 실패 유형, 알맞은 자리를 설명한다.

기본 제공 서브에이전트 여섯 종류, 영속 메모리와 훅과 턴 제한을 갖춘 커스텀 서브에이전트, 팀의 일곱 가지 기본 도구와 작업 시스템, 실제 사례를 함께 다룬다. 장 전체의 결론은 가장 싼 조율 전략이 거의 언제나 정답이라는 것이다.

---

## 1. 핵심 요점

- **두 단계 계층**: 서브에이전트는 세션 안의 세션이며 다른 서브에이전트를 만들 수 없다. 이는 의도한 설계다.
- **격리가 병렬보다 중요**: 서브에이전트의 가장 큰 가치는 컨텍스트 격리다. 장황한 작업은 서브에이전트에 맡기고 메인 컨텍스트는 가볍게 유지한다.
- **포그라운드와 백그라운드**: 백그라운드는 병렬이 되지만 MCP 도구, 되묻기, 즉석 권한 승인이 안 된다.
- **에이전트 팀은 독립 세션**: 팀원은 각자 완전한 세션이고, 작업 파일과 `SendMessage`로만 조율한다. 비용이 높아서 팀원끼리 직접 대화해야 할 때만 쓴다.
- **선택의 위계**: 단일 에이전트, 서브에이전트, 팀 순으로 단순한 쪽에서 올라간다.
- **계획 먼저**: 플랜 모드 약 10,000 토큰이 500,000 토큰 이상의 낭비를 막는다. 작업 경계, 인터페이스 계약, 의존 순서, 완료 기준을 계획에 담는다.
- **비싼 두뇌, 싼 손발**: 오케스트레이터는 유능한 모델, 서브에이전트는 싼 모델로 돌려 비용을 크게 줄인다.
- **역할은 작업으로 정의**: 성격 중심의 역할은 예측 못 한 충돌을 낳는다. 트레이딩 사례에서 에이전트 넷이 하나로 단순화됐다.
