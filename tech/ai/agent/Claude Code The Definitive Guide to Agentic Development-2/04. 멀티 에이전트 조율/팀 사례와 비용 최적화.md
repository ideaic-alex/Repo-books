# 팀 사례와 비용 최적화

멀티 에이전트의 가치는 구체적인 사례와 비용 계산으로 봐야 선명해진다. 이 문서는 책이 소개하는 에이전트 팀 사례 두 가지(블로그 QA와 인증 모듈 리팩터링), 계획을 먼저 세우고 병렬로 실행하는 방식, 비싼 두뇌와 싼 손발을 나누는 비용 전략을 다룬다.

---

## 1. 사례 1: 블로그 QA 스웜

한 실무자가 에이전트 팀에게 자신의 블로그를 겨냥해 프롬프트 하나만 줬다. 프로덕션 배포 전에 에이전트 팀으로 블로그를 QA하라는 내용이다. 리드는 작업 다섯 개를 만들고, 더 싼 모델에서 도는 병렬 에이전트 다섯 개를 띄웠다.

| # | 작업 | 에이전트 | 점검 내용 |
|---|---|---|---|
| 1 | 핵심 페이지 응답 | qa-pages | URL 16개의 HTTP 상태 코드가 맞는지 |
| 2 | 블로그 글 렌더링 | qa-posts | 글 83개의 제목 구조, 메타 태그, 이미지 동작 |
| 3 | 내비게이션과 링크 무결성 | qa-links | 내부 URL 146개의 깨진 링크 |
| 4 | RSS, 사이트맵, SEO 메타데이터 | qa-seo | RSS 유효성, robots.txt, Open Graph 태그 |
| 5 | 접근성과 HTML 구조 | qa-a11y | 제목 계층, ARIA 속성, 테마 토글 |

에이전트들은 각자 독립적으로 일을 끝내고 `SendMessage`로 구조화된 보고서를 보냈다. 이들은 bash와 curl로 페이지를 가져와 HTML을 직접 파싱했다. 브라우저 자동화도 테스트 프레임워크도 쓰지 않았다. 다섯 개가 모두 끝나자 리드가 결과를 종합해 심각도(major, medium, minor) 순으로 우선순위를 매긴 보고서를 만들었다. 그다음 리드가 종료 요청을 보내고, 팀원들이 확인 응답을 했고, `TeamDelete`가 정리했다.

프롬프트에서 최종 보고서까지 전 과정이 약 3분 걸렸다. 에이전트 5개, 146개가 넘는 URL 테스트, 블로그 글 83개 점검이다. 같은 일을 단일 세션이 순차로 했을 때보다 비용은 더 들었지만 실제 걸린 시간(wall-clock time)은 훨씬 짧았다.

---

## 2. 사례 2: 인증 모듈 리팩터링

조율이 더 많이 필요한 예다. 인증 모듈을 리팩터링하는데 팀원 한 명은 API 계층, 한 명은 프론트엔드 컴포넌트, 한 명은 테스트를 계속 돌리는 역할을 맡았다.

서브에이전트와의 핵심 차이는 이렇다. API 팀원이 타입 정의를 끝내고 UI 팀원에게 직접 "인터페이스 준비됐고 이렇게 바뀌었다"고 메시지를 보냈다. 테스트 팀원은 API 팀원에게 개발 서버를 띄워 달라고 요청할 수 있었다. 모든 상호작용을 리드를 거치지 않고 스스로 조율한 것이다.

이 패턴이 에이전트 팀이 비용을 정당화하는 지점이다. 에이전트들이 서로의 작업에 실시간으로 반응해야 했기 때문이다. 서브에이전트였다면 오케스트레이터가 병목이 된다. 작업자가 부모에게 보고하고, 부모가 다음 작업자에게 전달하고, 이것이 빙빙 돈다. 팀에서는 작업자들이 직접 대화한다.

---

## 3. 먼저 계획하고, 그다음에 병렬화

가장 효과적인 에이전트 팀 패턴은 두 단계다. 플랜 모드로 먼저 계획하고, 그 계획을 팀에 넘겨 병렬로 실행한다.

### 3.1 1단계: 플랜 모드에서 시작

오케스트레이터가 코드베이스를 탐색하고, 대상 파일을 찾고, 단계별 구현 계획을 만들게 한다. 그 계획을 검토하고 다듬는다. 플랜 모드는 파일만 읽기 때문에 비용이 싸다. 오케스트레이터가 만드는 계획은 이런 모습일 수 있다.

```
Plan:
1. Create src/auth/jwt.ts -- extract token signing/verification
2. Create src/auth/sessions.ts -- extract session logic
3. Create src/auth/middleware.ts -- extract Express middleware
4. Update src/auth/index.ts -- re-export public API
5. Update 12 import sites across the codebase
6. Update tests in src/auth/__tests__/
```

### 3.2 2단계: 팀으로 실행

계획에 이미 작업 분해가 들어 있다. 리드는 의존성 그래프를 보고 팀원을 물결(wave) 단위로 띄운다.

- **Wave 1 (병렬)**: jwt.ts, sessions.ts, middleware.ts. 팀원 세 명.
- **Wave 2 (Wave 1 이후)**: index.ts 배럴(barrel) 파일과 import 갱신. 팀원 한두 명.
- **Wave 3 (Wave 2 이후)**: 테스트 갱신. 팀원 한 명.

### 3.3 왜 이익인가

플랜 모드는 대략 10,000 토큰이 든다. 잘못된 방향으로 간 팀은 500,000 토큰 이상이 든다. 병렬 실행을 시작하기 전에 계획을 잠깐 검토하는 것만으로, 스웜이 한창 돌 때 비싼 방향 수정을 하는 일을 피할 수 있다.

## 4. 비용 최적화: 비싼 두뇌, 싼 손발

가장 비용 효율적인 멀티 에이전트 패턴은 개념이 단순하다. 조율에는 비싸고 유능한 모델을, 실행에는 싸고 빠른 모델을 쓴다.

- **오케스트레이터(메인 세션)**: 계획, 분해, 품질 평가를 맡는다. 추론 품질이 가장 중요한 곳이므로 쓸 수 있는 가장 유능한 모델로 돌린다.
- **서브에이전트**: 구현, 탐색, 잡일을 맡는다. 상당수는 품질이 눈에 띄게 떨어지지 않으면서 더 작은 모델로 돌릴 수 있다.

Explore 서브에이전트가 기본값으로 더 작고 빠른 모델을 쓰는 것이 이미 이 패턴이다. 커스텀 에이전트도 정의에 모델 선호를 적어서 같은 방식으로 확장할 수 있다.

### 4.1 경제성 계산

조율이 전체 토큰 사용량에서 차지하는 비중이 작기 때문에 이 방식이 성립한다. 리팩터링을 계획하는 데 10,000 토큰이 들 수 있다. 그 리팩터링을 파일 스무 개에 걸쳐 실행하는 데는 500,000 토큰이 들 수 있다. 실행을 토큰당 비용이 5분의 1인 모델에서 돌리면 계획 품질은 그대로 두고 전체 비용을 약 80% 줄인다.

### 4.2 조직에 빗댄 설명

시스템을 설계하는 시니어 아키텍트와 구현하는 주니어 개발자의 관계와 같다. 아키텍트의 시간은 비싸고 결정은 영향력이 크다. 구현자의 시간은 더 싸고 작업은 아키텍트의 계획이 이끌어 준다. 보일러플레이트를 쓰는 사람에게 아키텍트 단가를 줄 이유가 없듯이, 서브에이전트의 잡일에 오케스트레이터의 토큰 단가를 쓰지 않는다.

---

## 5. 계획 먼저 병렬화: 가장 비싼 실수를 피하는 법

멀티 에이전트 조율에서 가장 비싼 실수는 계획 없이 병렬 에이전트를 먼저 띄우는 것이다.

계획이 없으면 에이전트마다 목표를 독자적으로 해석한다. 서로 다른 가정을 세우고, 충돌하는 코드를 쓰고, 겹치는 문제를 호환되지 않는 방식으로 푼다. 그러면 병렬화로 아낀 시간보다 충돌을 푸는 시간이 더 든다. 책은 이것이 이론상의 걱정이 아니라 순진한 병렬화의 기본 결과라고 경고한다.

계획 먼저 방식은 거의 공짜로 이를 막는다. 오케스트레이터가 약 10,000 토큰을 들여 상세한 계획을 만든다. 각 에이전트가 무엇을 할지, 어떤 파일을 각자 소유할지, 지켜야 할 인터페이스가 무엇인지, 통합 지점이 어디인지를 적는다. 그다음에야 작업을 에이전트에게 넘겨 병렬로 실행한다.

이 선행 투자는 실행 비용에 비하면 미미하다. 에이전트 열 개가 한 시간 도는 팀은 수십만 토큰을 쓸 수 있고, 계획 단계는 반올림 오차 수준이다. 그런데 계획이 실행을 혼란스러운 스웜에서 조율된 노력으로 바꿔 준다.

계획에는 네 가지가 있어야 한다.

- **작업 경계**: 어느 에이전트가 어느 파일을 소유하는가.
- **인터페이스 계약**: 어떤 함수나 API가 서로 호환되어야 하는가.
- **의존 순서**: 무엇이 끝나야 무엇을 시작하는가.
- **완료 기준**: 각 에이전트가 끝났음을 어떻게 아는가.

이런 구조를 미리 받은 에이전트는 호환되는 코드를 만든다. 받지 못한 에이전트는 머지 충돌을 만든다.

---

## 6. 정리

- QA 스웜은 독립 작업 다섯 개를 병렬로 돌려 약 3분 만에 끝냈고, 비용은 더 들었지만 시간은 크게 줄었다.
- 인증 리팩터링은 팀원끼리 직접 대화해야 해서 팀의 비용이 정당화된 예다.
- 플랜 모드 약 10,000 토큰으로 500,000 토큰 이상의 낭비를 막는다.
- 오케스트레이터는 비싼 모델, 서브에이전트는 싼 모델로 돌리면 전체 비용을 약 80% 줄일 수 있다는 계산이다.
- 계획에는 작업 경계, 인터페이스 계약, 의존 순서, 완료 기준을 넣는다.
