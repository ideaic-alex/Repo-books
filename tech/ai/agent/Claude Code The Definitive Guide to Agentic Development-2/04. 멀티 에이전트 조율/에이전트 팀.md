# 에이전트 팀

에이전트 팀(agent teams)은 서브에이전트와는 아예 다른 구조다. 서브에이전트가 한 세션 안의 일꾼이라면, 에이전트 팀은 독립된 Claude Code 세션들이 공유 인프라를 통해 서로 조율하는 방식이다. 아직 실험 단계의 기능이라 제약도 분명하다. 이 문서는 팀을 켜는 법, 일곱 가지 기본 도구, 팀 리드의 역할, 표시 모드, 작업 의존성, 계획 승인, 팀 전용 훅, 서브에이전트와의 비교, 한계를 정리한다.

---

## 1. 에이전트 팀 켜기

에이전트 팀은 기본적으로 꺼져 있다. 환경 변수 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`를 `1`로 설정하면 켜진다. 셸에서 설정해도 되고 설정 파일로 해도 된다.

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

그다음에는 원하는 것을 자연어로 설명하면 된다. 프롬프트를 바탕으로 Claude가 팀을 만들고, 팀원을 띄우고, 일을 조율한다.

---

## 2. 일곱 가지 팀 기본 도구

팀 조율의 전 과정은 일곱 개 도구가 맡는다.

### 2.1 TeamCreate

팀을 초기화한다. 디스크에 팀 디렉터리와 설정 파일이 만들어진다. `team_name` 파라미터는 모든 것을 묶는 네임스페이스라서, 작업, 메시지, 설정이 전부 이 이름 아래에 놓인다.

```
TeamCreate({ "team_name": "auth-refactor", "description": "Refactor authentication module" })
```

### 2.2 TaskCreate

작업 단위를 정의한다. 작업 하나가 디스크의 JSON 파일 하나가 된다. 리드는 팀원을 띄우기 전에 작업을 먼저 만든다. 설명(description)을 충분히 자세히 적어서, 그 작업을 집어 드는 에이전트의 프롬프트 역할을 하게 한다.

```
TaskCreate({
  "subject": "Extract JWT handling into jwt.ts",
  "description": "Move all token signing and verification logic from auth.ts to a new jwt.ts module...",
  "team_name": "auth-refactor"
})
```

### 2.3 TaskUpdate

작업을 파이프라인 위에서 앞으로 보낸다. 팀원은 이 도구로 작업을 가져가고(상태를 `in_progress`로, owner를 지정) 완료 처리를 한다. 상태 필드 덕분에 두 에이전트가 같은 작업을 동시에 하지 않는다.

```
TaskUpdate({ "taskId": "1", "status": "in_progress", "owner": "jwt-agent" })
TaskUpdate({ "taskId": "1", "status": "completed" })
```

### 2.4 TaskList

모든 작업과 현재 상태를 돌려준다. 팀원은 작업 하나를 끝낼 때마다 이것을 불러 다음 할 일을 찾는다. 중앙 스케줄러는 없다. 팀원마다 `TaskList`를 확인하고, 주인 없는 대기(pending) 작업을 찾아 하나를 가져간다. 이것이 공유 조율 장치의 전부다.

### 2.5 Task (team_name과 함께)

팀원을 만든다. 핵심은 팀원 한 명이 컨텍스트 윈도를 따로 가진 완전한 Claude Code 세션이라는 점이다. 팀원은 같은 프로젝트 컨텍스트(CLAUDE.md, MCP 서버, 스킬)를 불러오지만 리드의 대화 기록은 물려받지 않는다. 팀원마다 모델을 따로 지정할 수 있다.

```
Task({
  "subagent_type": "general-purpose",
  "name": "jwt-agent",
  "team_name": "auth-refactor",
  "model": "sonnet"
})
```

### 2.6 SendMessage

팀을 서브에이전트와 다르게 만드는 도구다. 어느 팀원이든 다른 팀원에게 직접 메시지를 보낼 수 있다. 메시지 유형은 네 가지다.

- **message**: 두 에이전트 사이의 직접 대화. 팀원이 리드에게 결과를 보고하거나, 한 팀원이 다른 팀원에게 정보를 묻는다.
- **broadcast**: 모든 팀원에게 한꺼번에 보낸다. 팀원 모두가 그 메시지를 처리하므로 비용이 팀 규모에 비례해 늘어난다. 아껴서 써야 한다.
- **shutdown_request / shutdown_response**: 정상 종료 절차. 리드가 종료 요청을 보내면 팀원이 응답으로 확인한다. 끝내지 못한 일이 있으면 팀원이 이유를 달아 종료를 거절할 수 있다.
- **plan_approval_response**: 품질 확인 단계. 리드가 팀원의 구현 계획을 승인하거나 거절한다.

```
// Teammate reports findings to lead
SendMessage({
  "type": "message",
  "recipient": "lead",
  "content": "JWT extraction complete. Created jwt.ts with signToken and verifyToken exports."
})
```

```
// Lead requests graceful shutdown
SendMessage({
  "type": "shutdown_request",
  "recipient": "jwt-agent",
  "content": "All tasks complete, shutting down team."
})
```

### 2.7 TeamDelete

팀 설정과 모든 작업 파일을 디스크에서 지운다. 팀원이 모두 종료된 뒤에 호출한다.

---

## 3. 팀 리드의 역할

에이전트 팀을 단순한 병렬 서브에이전트 이상으로 만드는 것이 팀 리드(team lead)의 조율 역할이다. 리드는 팀을 만든 세션이며 다음을 맡는다.

- 작업을 만들고 일의 분해 구조를 정한다.
- 알맞은 역할로 팀원을 띄운다.
- 작업 목록으로 진행 상황을 지켜본다.
- 여러 에이전트의 결과를 종합한다.
- 정상 종료를 처리한다.

조율 채널은 디스크의 작업 파일과 `SendMessage` 둘뿐이다. 공유 메모리는 없다. 팀원은 각자 대화 기록과 컨텍스트 윈도를 따로 가지며, 리드나 다른 팀원과 독립되어 있다. 이 독립성이 구조의 강점(완전한 컨텍스트 격리 속의 진짜 병렬 작업)이면서 동시에 비용의 원인이다. 팀원 하나하나가 따로 토큰을 태우는 완전한 Claude Code 세션이기 때문이다.

### 3.1 위임 모드(delegate mode)

팀을 시작한 뒤 `Shift+Tab`으로 리드를 위임 모드에 둘 수 있다. 이 모드의 리드는 작업을 직접 구현하지 못하고 조율만 한다. 팀원 생성, 메시지, 종료, 작업 관리만 가능하다. 팀원에게 분산해야 할 일을 리드가 직접 해 버리는 것은 놀랄 만큼 흔한 실패 유형인데, 위임 모드가 이를 막아 준다.

---

## 4. 표시 모드 세 가지

표시 모드는 `teammateMode` 설정이나 `--teammate-mode` 플래그로 정한다.

- **auto** (기본값): 이미 tmux 세션 안에서 실행 중이면 분할 창을, 아니면 in-process를 쓴다.
- **in-process**: 모든 팀원을 내 메인 터미널 안에서 실행한다. `Shift+Up/Down`으로 팀원을 선택하고 입력하면 그 팀원에게 바로 메시지가 간다. `Enter`로 팀원의 세션을 보고, `Escape`로 현재 턴을 중단시키고, `Ctrl+T`로 작업 목록을 켜고 끈다. 추가 설정 없이 어느 터미널에서나 동작한다.
- **tmux**: 팀원마다 터미널 창(pane)을 하나씩 준다. 모두의 출력을 동시에 보면서 창을 클릭해 직접 상호작용할 수 있다. 분할 창 모드는 tmux나 iTerm2가 필요하고, 코드 에디터의 통합 터미널에서는 동작하지 않는다.

한 세션만 in-process로 강제하려면 다음처럼 실행한다.

```bash
claude --teammate-mode in-process
```

## 5. 작업 의존성과 파일 잠금

작업은 다른 작업에 의존할 수 있다. 해결되지 않은 의존성이 있는 대기 작업은 그 의존성이 끝나기 전에는 가져갈 수 없다. 다른 작업이 의존하던 작업을 팀원이 끝내면 막혀 있던 작업이 자동으로 풀린다. 그 결과 자연스러운 물결(wave) 패턴이 생긴다. 서로 독립적인 작업이 먼저 병렬로 돌고, 의존하는 작업이 뒤따른다.

작업을 가져갈 때는 경쟁 상태(race condition)를 막기 위해 파일 잠금(file locking)을 쓴다. 잠금이 없으면 같은 순간에 `TaskList`를 확인한 두 에이전트가 같은 작업을 동시에 가져가려 해서 일이 중복된다. 잠금 덕분에 작업마다 정확히 한 에이전트만 주인이 된다.

---

## 6. 계획 승인(plan approval)

복잡하거나 위험한 작업에서는 팀원이 구현에 들어가기 전에 먼저 계획하도록 요구할 수 있다. 팀원은 리드가 접근 방식을 승인할 때까지 읽기 전용 플랜 모드로 일한다. 프롬프트는 예를 들어 이런 식이다.

```
Spawn an architect teammate to refactor the authentication module.
Require plan approval before they make any changes.
```

팀원이 계획을 마치면 리드에게 계획 승인 요청을 보낸다. 리드는 계획을 검토해서 승인하거나(팀원이 플랜 모드를 벗어나 구현 시작) 피드백과 함께 거절한다(팀원은 플랜 모드에 남아 계획을 고쳐서 다시 제출). 프롬프트에 기준을 적어 리드의 판단을 유도할 수도 있다. "테스트 커버리지가 포함된 계획만 승인하라", "데이터베이스 스키마를 바꾸는 계획은 거절하라" 같은 식이다.

이 절차는 "에이전트가 알아서 잘하겠지" 하고 믿는 것과 "구현에 토큰을 쓰기 전에 접근 방식을 확인하는 것"의 차이다. 에이전트 다섯 개가 병렬로 분당 수천 토큰씩 태우는 상황이라면 계획 승인은 싼 보험이다.

---

## 7. 팀 전용 훅 이벤트

에이전트 팀에만 있는 훅 이벤트가 두 개 있다.

- **TeammateIdle**: 팀원이 유휴 상태로 들어가려 할 때(현재 일을 끝내고 멈출 준비가 됐을 때) 발생한다. 이 훅이 종료 코드 2를 내면 팀원이 계속 일하게 강제된다. 예를 들어 예상 출력 디렉터리에 빌드 산출물이 있는지 확인한 뒤에야 멈추게 하는 훅을 쓸 수 있다. 산출물이 없으면 훅이 유휴를 거부하고 팀원은 계속 일한다.
- **TaskCompleted**: `TaskUpdate`로 작업이 완료 처리될 때, 또는 진행 중인 작업이 남은 채로 팀원이 턴을 마칠 때 발생한다. 종료 코드 2는 완료를 막는다. 품질 확인 단계로 쓸 수 있다. 작업이 완료로 표시될 때 테스트 스위트를 돌리고 테스트가 실패하면 완료를 막는 훅이 그 예다. 팀원은 실패 출력을 보고 스스로 고친다.

---

## 8. 에이전트 팀과 서브에이전트 비교

| 항목 | 서브에이전트 | 에이전트 팀 |
|---|---|---|
| 컨텍스트 | 자기 윈도, 결과는 호출자에게 반환 | 자기 윈도, 완전히 독립 |
| 소통 | 메인 에이전트에게만 결과 보고 | 팀원끼리 직접 메시지 |
| 조율 | 메인 에이전트가 모든 일을 관리 | 공유 작업 목록에서 스스로 가져감 |
| 토큰 비용 | 낮음(결과가 요약되어 메인으로 돌아옴) | 높음(팀원이 각각 완전한 세션) |
| 적합한 일 | 결과만 중요한 집중된 작업 | 토론과 협업이 필요한 복잡한 작업 |

차이가 가장 크게 드러나는 때는 에이전트끼리 대화해야 할 때다. API 팀원이 타입 정의를 끝내고 UI 팀원에게 직접 메시지를 보내 통합 작업을 시작하게 하는 것이 에이전트 팀다운 패턴이다. 각 작업자가 그냥 오케스트레이터에게 보고만 한다면 서브에이전트가 더 싸고 단순하다.

---

## 9. 한계

에이전트 팀은 실험 기능이라 현실적인 제약이 있다.

- in-process 팀원은 세션 재개가 안 된다. 팀원이 크래시하면 그 작업과 컨텍스트를 잃는다.
- 작업 상태가 늦게 갱신될 수 있다. 팀원이 작업 완료 표시를 깜빡하는 일이 있고, 그러면 의존하는 작업이 막힌다.
- 세션당 팀은 하나다. 중첩된 팀이나 한 리드 세션에서 여러 팀을 돌릴 수 없다.
- 분할 창은 tmux나 iTerm2가 필요하고 코드 에디터의 통합 터미널에서는 안 된다.
- 모든 팀원은 리드의 권한 설정으로 시작한다. 리드보다 넓은 권한을 한 팀원에게만 줄 수 없다.

---

## 10. 정리

- 에이전트 팀은 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`로 켜는 실험 기능이며, 팀원은 각각 독립된 완전한 세션이다.
- 일곱 개 도구(TeamCreate, TaskCreate, TaskUpdate, TaskList, Task, SendMessage, TeamDelete)와 작업 파일이 조율의 전부다. 공유 메모리는 없다.
- 의존성과 파일 잠금이 작업 충돌을 막고, 계획 승인과 훅이 품질 확인 역할을 한다.
- 팀원끼리 직접 대화해야 할 만큼 협업이 필요할 때만 서브에이전트 대신 팀을 쓴다.
