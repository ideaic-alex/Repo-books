# 설정 범위와 우선순위

settings.json은 한 곳에만 있지 않다. 조직이 배포하는 파일, 명령줄 플래그, 프로젝트 폴더의 파일, 홈 디렉터리의 파일까지 다섯 군데에서 설정이 들어온다. 이 문서는 각 범위(scope)가 어디에 있고, 서로 부딪히면 무엇이 이기는지, 어떤 내용을 어느 범위에 두면 좋은지를 정리한다.

---

## 1. 범위 계층

우선순위 숫자가 작을수록 강하다.

| 우선순위 | 범위 | 위치 | 공유 여부 | 덮어쓸 수 있는가 |
|---|---|---|---|---|
| 1 (최고) | Managed | 시스템 디렉터리 또는 서버 관리(IT 배포) | 조직 전체 | 불가 |
| 2 | CLI | 명령줄 플래그 | 공유 안 함 | 세션 동안만 적용 |
| 3 | Local | `.claude/settings.local.json` | 공유 안 함 (gitignore 대상) | managed와 CLI가 덮어씀 |
| 4 | Project | `.claude/settings.json` | 공유함 (버전 관리) | managed, CLI, local이 덮어씀 |
| 5 (최저) | User | `~/.claude/settings.json` | 공유 안 함 | 위의 모든 범위가 덮어씀 |

표를 읽는 법은 이렇다. 가장 아래의 User는 개인 기본값이라서 나머지가 전부 덮어쓸 수 있다. 반대로 맨 위의 Managed는 누구도 바꿀 수 없다. Project는 저장소에 커밋되어 팀이 함께 쓰고, Local은 같은 프로젝트 안에서 내 컴퓨터에만 적용된다.

## 2. 범위별 용도

| 범위 | 두기 좋은 내용 |
|---|---|
| Managed | 조직 전체에 강제할 보안 정책, API 키 헬퍼, 로그인 방식 강제, MCP 허용/거부 목록, 샌드박스 요구 사항 |
| User | 개인 취향(모델, 언어, 스피너 동사, 움직임 줄이기), 개인 API 키, 사용자 수준 권한 |
| Project | 팀이 함께 지킬 표준(권한, 훅, MCP 서버), 코딩 규칙, 어트리뷰션 설정 |
| Local | 특정 프로젝트에서만 쓰는 개인 덮어쓰기, 실험용 설정, 커밋하고 싶지 않은 자격 증명 |

판단 기준은 두 가지다. 팀이 같이 지켜야 하는가, 그리고 저장소에 올려도 되는가. 팀 규칙이면 Project, 올리면 안 되는 개인 값이면 Local이나 User로 간다. 조직이 반드시 강제해야 하는 값은 Managed다.

## 3. 범위가 서로 영향을 주는 방식

설정은 범위를 가로질러 병합된다. 대부분의 키는 우선순위가 높은 범위가 낮은 범위의 값을 덮어쓴다. 예를 들어 User에서 `model`을 정했어도 Project에 같은 키가 있으면 Project 값이 쓰인다.

권한 규칙만은 다르게 동작한다. 높은 범위가 낮은 범위를 덮어쓰는 방식이 아니라, 정해진 평가 순서를 따른다. 먼저 deny 규칙, 다음 ask, 마지막으로 allow를 보고, 모든 범위를 통틀어 처음 일치한 규칙이 이긴다. 그래서 User 범위에서 deny로 막은 도구는 Project가 allow로 열어도 막힌 채 남는다.

## 4. 서버 관리 설정

장치 관리 인프라가 없는 조직도 서버 관리(server-managed) 설정을 쓸 수 있다. 이 방식은 Anthropic 서버가 설정을 내려보내 주며, Claude for Enterprise 고객이 대상이다. 동작은 파일로 배포하는 managed 설정과 똑같고, 사용자나 프로젝트 설정으로 덮어쓸 수 없다.

즉 각 PC의 시스템 디렉터리에 파일을 배포하는 장치 관리 체계가 없는 조직도, 서버 쪽에서 같은 수준의 강제력을 가진 정책을 걸 수 있다.
