# 대규모 MCP 구성과 아키텍처 패턴

MCP 서버를 어떤 언어로 만들지, 무거운 계산은 어디서 할지, 도구가 40개를 넘으면 무엇을 지켜야 하는지는 실제로 운영하는 팀에게 가장 현실적인 질문이다. 이 문서는 Go와 JavaScript를 나눠 쓰는 구조, 개발 바깥 영역(마케팅)으로 확장한 사례, 그리고 도구 41개 이상으로 규모를 키울 때 쓰는 다섯 가지 운영 규칙을 설명한다.

---

## 1. Go + JavaScript 패턴

운영 중인 MCP 배포에서 자주 보이는 구조는 무거운 계산을 Go로, MCP 서버 인터페이스를 JavaScript로 맡기는 것이다. 이유는 실용적이고 실무자 경험에서 나온 것이다.

- Go는 동시성 데이터 처리, 복잡한 알고리즘, 성능에 민감한 작업을 맡는다.
- JavaScript는 Claude Code가 MCP 서버 코드를 만들 때 가장 유창하게 쓰는 언어다.

한 실무자는 이유를 직설적으로 설명했다. 기존 인프라 전문성이 있어서 무거운 일은 Go로 하고, MCP 서버는 Claude가 가장 쉽게 쓰는 언어라서 JavaScript로 만든다는 것이다.

### 동작 구조

1. Go 백엔드가 로컬 API(HTTP 또는 gRPC)를 노출한다.
2. JavaScript MCP 서버가 MCP 프로토콜과 Go API 사이를 번역한다.
3. Claude는 MCP 서버와 상호작용하고, MCP 서버는 Go로 위임한다.

### 토큰 절약 효과

이 구조로 만든 코드베이스 분석 도구는 Claude가 코드를 직접 분석할 때보다 토큰을 80~90% 아꼈다고 보고했다. Go 백엔드가 무거운 파싱과 분석을 하고 구조화된 결과를 MCP 서버를 통해 돌려준다. Claude는 원본 소스 파일 대신 미리 소화된 정보를 받으므로 컨텍스트를 아주 조금만 쓴다.

### 유일한 정답은 아니다

Python MCP 서버도 되고 Rust MCP 서버도 된다. 다만 Go + JavaScript 분리는 한 가지 강점을 노린다. Claude Code에게 MCP 서버를 만들거나 고치게 하면 Go보다 JavaScript를 더 깔끔하게 만든다는 점이다. MCP 서버가 얇은 번역 계층이라면, AI가 생성한 코드의 품질은 계산 부분보다 인터페이스 부분에서 더 중요하다.

## 2. 개발 바깥의 MCP: 마케팅 캠페인 분석

MCP는 개발자 도구와 데이터 API에만 쓰는 것이 아니다. 그로스 마케팅 팀이 대형 소셜 미디어 광고 플랫폼의 API와 연동한 MCP 서버를 만든 사례가 있다. 캠페인 성과, 지출 데이터, 광고 효과를 Claude 안에서 바로 조회한다. 광고 플랫폼 대시보드와 Claude를 오가며 분석하는 대신 한 곳에서 모두 조회한다.

구성은 이렇다.

- MCP 서버가 광고 API를 감싼다.
- 캠페인 지표를 가져오는 도구를 노출한다.
- Claude가 추론할 수 있는 구조화된 데이터를 돌려준다.

팀은 이 서버로 "이번 주에 획득당 비용이 가장 높았던 캠페인은 무엇인가", "진행 중인 모든 캠페인에서 헤드라인 A안과 B안의 성과를 비교해 줘" 같은 질문에 답한다. 모든 질의는 훅으로 감사할 수 있고, API 자격 증명은 Claude의 컨텍스트에 들어가지 않는다.

이 사례는 MCP 패턴이 엔지니어링을 넘어 일반화된 모습이다. 외부 서비스를 조회하고, 응답을 분석하고, 분석에 근거해 결정하는 워크플로라면 무엇이든 MCP 연동의 후보가 된다. 서버를 만드는 노력은 한 번만 들이면 된다. 이후에는 Claude의 추론 루프 안에서 외부 데이터에 구조적이고 안전하며 감사 가능하게 접근하는 장점이 계속 이어진다. 이 서버도 며칠 만에 만들어졌다.

## 3. 도구 41개 이상으로 키우기

도구가 40개를 넘는 운영 배포가 여러 서버에 걸쳐 존재한다. 이 규모에서는 설정 규율을 지키는 일이 선택이 아니다. 대규모 연동이 돌아가게 하는 다섯 가지 패턴은 다음과 같다.

### 3-1. 도메인별 서버 분리

데이터 영역이나 서비스마다 MCP 서버를 하나씩 둔다. 분석 도구는 한 서버, 포트폴리오 도구는 다른 서버, 백테스팅 도구는 세 번째 서버에 둔다. 이렇게 하면 장애가 격리된다. 분석 서버가 죽어도 포트폴리오 관리가 같이 멈추지 않는다.

### 3-2. 기본값은 지연 로딩

도구가 40개 이상이면 즉시 로딩이 컨텍스트의 감당하기 어려운 비중을 차지한다. 도구 검색을 반드시 켜 둬야 한다.

### 3-3. 이름 규칙

모든 도구 이름 앞에 도메인을 붙인다.

```
analytics_price_history
portfolio_current_holdings
backtest_run_strategy
```

이름이 스스로 설명이 되면 Claude가 도구를 고르는 판단도 나아진다.

### 3-4. 최소한의 스키마

각 도구의 파라미터 스키마에는 필요한 것만 정확히 적는다. 풍부한 설명은 스킬이나 CLAUDE.md 참조 문서에 두고, 매 세션 컨텍스트에 올라가는 스키마에는 넣지 않는다.

### 3-5. 상태 점검

시작 훅이나 스크립트로 작업을 시작하기 전에 모든 MCP 서버가 응답하는지 확인한다. 30초의 확인이 도구가 왜 없는지 한 시간 동안 디버깅하는 일을 막는다.

## 4. 정리 표

| 규칙 | 해결하는 문제 |
|---|---|
| 도메인별 서버 분리 | 한 서버 장애가 다른 기능으로 번지는 것 |
| 지연 로딩 | 컨텍스트 고갈 |
| 도메인 접두어 이름 | 도구 선택 혼동, 이름 충돌 |
| 최소 스키마 | 매 세션 반복되는 토큰 낭비 |
| 시작 시 상태 점검 | 조용한 연결 실패 |
