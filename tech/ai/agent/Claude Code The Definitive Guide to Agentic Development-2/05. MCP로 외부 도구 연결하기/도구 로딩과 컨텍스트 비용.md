# 도구 로딩과 컨텍스트 비용

MCP(Model Context Protocol)는 Claude Code가 파일 시스템 바깥의 세계와 대화하는 표준 통로다. 데이터베이스, API, 클라우드 서비스, 시세 피드, 사내 도구 같은 것들이 모두 이 통로로 연결된다. MCP가 없으면 Claude Code는 파일을 읽고 bash 명령을 돌리는 똑똑하지만 고립된 프로세스에 머문다. MCP가 있으면 인프라 안의 한 지점(노드)이 된다.

다만 MCP는 꽂기만 하면 되는 기능이 아니다. 서버를 연결할 때마다 세션 시작 시점에 컨텍스트 윈도의 토큰을 쓴다. 연결이 세션 도중에 조용히 끊기기도 하고, 도구가 말없이 사라지기도 한다. 백그라운드 서브에이전트는 MCP를 아예 쓰지 못한다. MCP 연동이 잘 돌아가느냐, 세션 품질을 슬금슬금 깎아 먹느냐는 설정을 꼼꼼히 관리하고, 구조를 이해하고, 프로토콜이 어떤 비용을 요구하는지 솔직하게 아는 데서 갈린다. 이 문서는 그중 첫 단계인 도구 로딩 방식과 비용을 다룬다.

---

## 1. 세션이 시작되면 무슨 일이 일어나는가

Claude Code 세션이 시작되면 설정된 MCP 서버가 모두 연결되고, 각 서버가 자기 도구 정의를 내놓는다. 도구 정의에는 도구 이름, 설명, 파라미터 스키마가 들어 있다. 이 정의들은 곧바로 컨텍스트 윈도에 올라간다.

여기서 MCP의 비용이 생긴다. 도구를 한 번도 쓰지 않아도 정의를 올리는 것만으로 컨텍스트 토큰을 낸다. 서버를 많이 붙일수록 프롬프트를 한 줄 치기 전에 이미 윈도가 차 있는 상태로 시작한다.

## 2. 도구 검색(tool search)으로 비용 줄이기

이 부담을 덜어 주는 장치가 도구 검색(tool search)이다. 기본으로 켜져 있고, 동작 방식은 다음과 같다.

- 컨텍스트 용량의 약 10%까지는 도구 정의를 그대로 올린다.
- 나머지 도구는 미뤄 둔다(deferred). 설명은 색인에만 들어 있고, 전체 스키마는 필요해지기 전까지 컨텍스트에 올라가지 않는다.
- Claude가 어떤 작업에 미뤄 둔 도구가 필요할 수 있다고 판단하면 색인을 검색해서 해당 스키마를 불러오고 작업을 이어 간다.

이 지연 로딩 덕분에 MCP 서버를 수십 개 붙여도 컨텍스트 윈도가 바로 바닥나지 않는다.

### 지연 로딩에도 대가가 있다

검색 단계 자체가 컨텍스트를 쓰고 지연 시간도 늘린다. 그래서 상황에 따라 선택이 달라진다.

| 상황 | 알맞은 방식 |
|---|---|
| 매 세션 반드시 쓰는 도구 | 즉시 로딩(eager loading) |
| 도구가 40개인데 세션마다 5개 정도만 쓴다 | 지연 로딩이 필수 |
| 서버가 몇 개 안 되고 검색 지연이 싫다 | 도구 검색을 꺼도 괜찮다 |

### ENABLE_TOOL_SEARCH 환경 변수

도구 검색은 `ENABLE_TOOL_SEARCH` 환경 변수로 제어한다. 이 기능을 끄면 모든 도구 정의가 즉시 로딩된다. MCP 서버가 적고 검색 지연을 아예 없애고 싶다면 문제없다. 하지만 서버가 많고 도구 목록이 방대하다면 치명적이다. 세션을 열자마자 컨텍스트가 도구 정의로 가득 차기 때문이다.

## 3. 내 MCP 컨텍스트 비용 측정하기

`/mcp` 슬래시 명령은 서버별로 토큰 비용을 보여 준다. 한 번은 꼭 돌려 봐야 한다. 프롬프트를 입력하기도 전에 MCP 서버가 컨텍스트 윈도의 15%를 쓰고 있다면 설정에 문제가 있는 것이다. 이때 해결책은 두 가지다.

1. 연결한 서버 수를 줄인다.
2. 도구 검색이 대부분의 도구를 미루도록 되어 있는지 확인한다.

### 스키마가 비용의 정체다

비용은 도구 이름만이 아니라 도구마다 붙은 JSON 스키마에서 나온다. 파라미터 타입, 설명, enum, 중첩된 객체가 전부 쌓인다. 파라미터 설명을 정성껏 쓴 도구는 간결한 도구보다 컨텍스트를 더 많이 먹는다.

팀에서 쓸 MCP 서버를 직접 만든다면 스키마를 정확하되 짧게 유지해야 한다. 파라미터 설명에 쓴 단어 하나하나가 모든 요청마다 Claude가 치르는 토큰이다.

## 4. MCP 리소스: 도구가 아니라 데이터를 참조하기

MCP 서버는 도구뿐 아니라 리소스(resource)도 내놓을 수 있다. 리소스는 구조화된 데이터이고, 파일을 참조할 때 쓰는 `@` 멘션과 같은 방식으로 가리킨다. 문법은 `@server:protocol://resource/path` 형태다.

```
> Can you analyze @github:issue://123 and suggest a fix?
> Please review the API documentation at @docs:file://api/authentication
> Compare @postgres:schema://users with @docs:file://database/user-model
```

프롬프트에 `@`를 입력하면 연결된 모든 MCP 서버의 리소스가 자동 완성 메뉴에 파일과 나란히 뜬다. 리소스를 참조하면 자동으로 가져와서 대화에 첨부 자료로 포함시킨다. 한 프롬프트에 여러 리소스를 함께 걸어도 된다.

### 왜 리소스 참조가 더 나은가

외부 데이터가 로컬 파일과 같은 위치에 놓이기 때문이다. "데이터베이스 MCP 도구로 users 테이블 스키마를 가져와 줘"라고 시키는 대신 `@postgres:schema://users`로 직접 참조하면 그 스키마가 곧바로 컨텍스트에 들어온다.

모델은 이 데이터를 도구 호출의 결과물이 아니라 구조화된 입력으로 받는다. 추론을 시작하기 전에 데이터가 이미 눈앞에 있고, 대화 중간에 가져오는 것이 아니다. 이 차이가 대체로 더 좋은 답변으로 이어진다.

## 5. 정리

- MCP 서버를 붙이면 도구 정의가 세션 시작 시 컨텍스트에 올라가고, 그만큼 토큰을 쓴다.
- 도구 검색은 기본으로 켜져 있으며, 컨텍스트 용량의 약 10%까지만 즉시 로딩하고 나머지는 필요할 때 불러온다.
- 매번 쓰는 소수의 도구는 즉시 로딩이 낫고, 쓰는 비율이 낮은 대규모 도구 목록은 지연 로딩이 필수다.
- `ENABLE_TOOL_SEARCH`로 켜고 끈다. 서버가 많은데 끄면 컨텍스트가 순식간에 찬다.
- `/mcp`로 서버별 비용을 확인한다. 시작 전부터 15%를 쓰고 있다면 서버를 줄이거나 지연 로딩을 점검한다.
- 스키마는 정확하고 짧게 쓴다. 설명 한 단어도 매 요청마다 비용이 된다.
- 데이터 조회는 `@server:protocol://resource/path` 리소스 참조를 쓰면 대화 중 호출보다 깔끔하게 컨텍스트에 들어간다.
