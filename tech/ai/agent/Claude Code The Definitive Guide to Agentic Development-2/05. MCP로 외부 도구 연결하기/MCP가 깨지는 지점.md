# MCP가 깨지는 지점

MCP 연결은 로컬 도구 호출만큼 믿을 만하지 않다. 서버는 별도의 프로세스이거나 외부 서비스라서 시작에 실패할 수도, 도중에 끊길 수도 있다. 더 까다로운 것은 이런 실패가 대부분 조용히 일어난다는 점이다. 이 문서는 자주 만나는 실패 유형, 서브에이전트에서의 제약, 플러그인과 MCP의 관계를 정리한다. 원인을 알아 두면 "갑자기 Claude가 이상해졌다"는 상황에서 헤매는 시간을 크게 줄일 수 있다.

---

## 1. 조용한 연결 끊김

MCP 서버는 세션 도중에 연결이 끊길 수 있다. 그러면 그 서버가 제공하던 도구가 그냥 사라진다. Claude Code는 오류를 던지지 않고 알림도 주지 않는다. 도구가 없어졌을 뿐이다. Claude가 그 서버의 도구에 의존하고 있었다면 도구를 찾지 못해 실패하거나, 사용자가 원하지 않았을 수도 있는 대체 방법을 시도한다.

증상은 미묘하다.

- Claude가 방금까지 쓰던 기능을 갑자기 쓰지 않는다.
- 도구로 하던 일을 수작업 방식으로 하기 시작한다.
- 예를 들어 API 커넥터를 쓰던 Claude가 갑자기 원시 HTTP 요청을 직접 작성한다면 MCP 연결부터 의심해야 한다.

현재 연결 상태는 `/mcp` 명령으로 확인한다. 행동이 예상 밖으로 바뀌었을 때 `/mcp`를 먼저 치는 것을 반사적인 습관으로 만들어 두는 것이 좋다.

## 2. 서버 시작 실패

세션이 시작될 때 MCP 서버가 뜨지 못하는 경우도 있다. 의존성이 빠졌거나, 환경 변수가 잘못됐거나, 포트가 충돌하는 식이다. 어느 하나만 어긋나도 서버가 초기화되지 못한다. 이때 Claude Code는 그 도구들 없이 세션을 시작한다. 그래서 그 도구가 필요해지는 순간까지 없다는 사실을 모를 수 있다.

진단 방법은 간단하다. 세션을 시작할 때 `/mcp`를 실행해서 기대한 서버가 모두 연결됐는지, 도구 개수가 예상과 맞는지 확인한다. 5초면 끝나는 확인이 30분의 혼란을 막는다.

## 3. 이름이 같은 도구

두 MCP 서버가 같은 이름의 도구를 내놓으면 동작이 정의되어 있지 않다. 한쪽이 다른 쪽을 가려 버리고(shadow), 어느 쪽이 이길지는 서버 초기화 순서에 좌우될 수 있다. 그 순서는 사용자가 통제할 수 없다. 충돌을 피하려면 도구 이름에 서버별 접두어를 붙인다.

## 4. 서브에이전트에서의 MCP

MCP 도구는 포그라운드(foreground) 서브에이전트에서는 쓸 수 있지만 백그라운드(background) 서브에이전트에서는 쓸 수 없다. 설정으로 바꿀 수 있는 옵션이 아니라 구조적으로 정해진 제약이다.

이유는 백그라운드 서브에이전트의 성격에 있다. 백그라운드 서브에이전트는 동시에 돌고, 사용자와 상호작용할 수 없다. 그런데 MCP 서버는 대화형 인증을 요구할 수 있고, 병렬로 접근하면 호출 횟수 제한(rate limit)과 부딪힐 수 있으며, 사람의 검토가 필요한 출력을 낼 수도 있다. 일부만 지원해서 예측하기 어려운 동작을 만드느니, 포그라운드는 MCP를 쓰고 백그라운드는 못 쓴다는 이분법으로 정했다.

### 실무에 미치는 영향

- 서브에이전트가 외부 서비스를 조회해야 하는 워크플로를 설계한다면, 그 서브에이전트는 포그라운드로 돌아야 한다.
- 4장에서 다룬 것처럼 포그라운드 서브에이전트는 메인 대화를 막는다. 그래서 병렬화 전략에 영향이 있다.
- 백그라운드 서브에이전트에 외부 데이터가 필요하다면 우회로가 있다. 메인 에이전트가 먼저 MCP로 데이터를 가져온 뒤, 그 결과를 백그라운드 서브에이전트의 작업 설명에 넣어 넘긴다. 실시간 데이터 접근을 포기하는 대신 병렬성을 얻는 거래다.

## 5. 플러그인 속의 MCP

플러그인은 MCP 서버 설정을 함께 묶어 둘 수 있고, 플러그인을 켜면 그 서버가 자동으로 시작된다. 사용자 입장에서는 플러그인의 MCP 도구가 내장 기능과 구별되지 않는 표준 도구처럼 보인다.

플러그인은 MCP의 배포 수단이다. 팀원마다 MCP 서버를 손으로 설정하라고 요구하는 대신, 플러그인이 서버 실행 파일, 설정, 자동 시작 로직을 한 묶음으로 담아 한 번의 활성화로 켜지게 한다.

### 컨텍스트 주의

자동 시작은 플러그인이 활성화된 순간부터 그 MCP 서버가 컨텍스트를 쓴다는 뜻이다. 안 쓰는 플러그인을 비활성화하면 그만큼 컨텍스트가 돌아온다. 컨텍스트 예산이 빠듯하다면 어떤 플러그인이 켜져 있는지, 그 플러그인의 MCP 도구를 실제로 쓰는지 점검해 보는 것이 좋다.

## 6. 점검 체크리스트

| 증상 | 의심할 것 | 확인 방법 |
|---|---|---|
| 쓰던 기능을 Claude가 갑자기 안 쓴다 | 세션 중 연결 끊김 | `/mcp`로 연결 상태 확인 |
| 도구가 처음부터 없다 | 서버 시작 실패(의존성, 환경 변수, 포트) | 세션 시작 때 `/mcp`로 서버와 도구 수 확인 |
| 엉뚱한 서버의 도구가 호출된다 | 같은 이름의 도구 충돌 | 서버별 접두어로 이름 변경 |
| 백그라운드 서브에이전트가 MCP를 못 쓴다 | 구조적 제약 | 포그라운드로 전환하거나 메인 에이전트가 데이터를 미리 전달 |
| 시작 컨텍스트가 크다 | 플러그인의 자동 시작 MCP | 쓰지 않는 플러그인 비활성화 |
