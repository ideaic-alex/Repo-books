# 부록 D 용어집 (Appendix D: Glossary of Key Terms)

부록 D는 책에 쓰인 기술 용어와 사업 용어를 알파벳순으로 풀어 둔 사전이다. 저자는 이 정의가 학문적 정밀함보다 실제 응용을 위한 것이라고 밝힌다. 이 노트는 정의를 그대로 번역하지 않고 쉬운 우리말로 다시 풀었으며, 이 노트가 쓰는 번역어(프롬프트 시스템, 워크플로, 파이프라인, 인지 자본, 승수, 청사진 등)를 함께 맞췄다. 책 본문에서 처음 만난 낯선 말을 찾아볼 때 쓴다.

> **쉽게 말하면**
> 용어집은 외우는 목록이 아니라 막힐 때 펼치는 사전이다. 특히 "워크플로"와 "파이프라인"의 차이만 잡아도 뒤의 자동화 장이 쉬워진다.

> **참고(노트 작성자)** 용어의 영어 표기는 책 기준이다. 요금이나 한도 같은 수치성 정보는 용어집에 포함하지 않았다.

## 이 부록의 흐름

1. 기술 용어(A에서 M까지)
2. 기술 용어(N에서 Z까지)
3. 헷갈리기 쉬운 짝 정리
4. 용어를 쓰는 요령

## 1. A에서 M까지

| 용어 | 쉬운 풀이 |
|------|-----------|
| API(Application Programming Interface) | 프로그램끼리 말을 주고받게 하는 약속. Claude API를 쓰면 채팅 화면 없이 코드나 자동화 도구가 Claude에게 일을 시키고 답을 받는다 |
| 자동화 파이프라인(automation pipeline) | 어떤 사건이 방아쇠가 되어 여러 도구를 거쳐 결과를 목적지에 전달하는 연쇄. 사람이 시작 버튼을 누르지 않아도 돈다 |
| 단계적 사고 프롬프트(chain-of-thought) | 결론 전에 문제를 한 걸음씩 풀게 하는 요청 방식. 복잡한 분석에서 품질이 오른다 |
| 인지 레버리지(cognitive leverage) | 혼자 하는 사고, 분석, 창작의 규모를 지렛대처럼 키우는 힘. Claude가 구조화된 생성을 맡고 사람은 전략과 품질 판단을 맡는다. 노트에서는 인지 자본의 승수 효과로 부르기도 한다 |
| 컨텍스트 윈도(context window) | 한 번의 상호작용에서 Claude가 다룰 수 있는 글의 총량(요청과 답변 합). 큰 문서를 처리하는 시스템에서 한계를 고려해야 한다 |
| CRAFT 프레임워크 | 맥락, 역할, 행동, 형식, 어조의 다섯 요소로 프롬프트를 짜는 틀 |
| 맞춤 제작 서비스(done-for-you) | 가르치는 대신 완성된 결과물을 고객에게 직접 전달하는 서비스 |
| 퓨샷 프롬프트(few-shot) | 원하는 결과의 예시를 두세 개 넣어 스타일과 품질 기준을 보여 주는 방식. 문체가 중요한 일에서 설명보다 효과가 크다 |
| 단계적 품질 저하(graceful degradation) | 입력이 부족하거나 이상해도 아예 멈추지 않고, 경고 표시와 함께 부분적이지만 쓸모 있는 결과를 내는 설계 원칙 |
| 입력 층(input layer) | 3층 워크플로의 첫 층. 시스템 프롬프트, 자료, 사용자 입력, 예시처럼 Claude가 답하기 전에 받는 모든 것 |
| 마이크로 SaaS(micro SaaS) | 좁은 용도에 맞춘 작은 구독형 소프트웨어. 비용이 낮고 반복 매출이 있으며 소규모 팀이 운영한다 |
| MRR(Monthly Recurring Revenue, 월간 반복 매출) | 구독이나 리테이너에서 매달 예측 가능하게 들어오는 매출. 구독형 사업의 핵심 지표 |
| 멀티 스테이지 파이프라인(multi-stage pipeline) | 한 프롬프트의 출력이 다음 프롬프트의 입력이 되도록 이은 구조. 복잡한 일을 단계별로 나눠 따로 다듬는다 |

## 2. N에서 Z까지

| 용어 | 쉬운 풀이 |
|------|-----------|
| n8n | 오픈소스 워크플로 자동화 플랫폼. 직접 설치할 수 있어 개인정보와 비용 면에서 유리하며 대량 처리에 어울린다 |
| 출력 층(output layer) | 3층 워크플로의 마지막 층. 결과의 형식, 구조, 도착지를 정한다 |
| PAVED 프레임워크 | 문제 구체성, 청중 접근성, 검증된 수요, 실행 가능성, 유통 명확성으로 마이크로 SaaS 아이디어를 심사하는 틀 |
| 프롬프트 엔지니어링 | AI에게 줄 입력을 설계해 믿을 만한 고품질 출력을 얻는 기술. 프롬프트 하나의 최적화부터 다단계 시스템 설계까지 아우른다 |
| 프롬프트 팩(prompt pack) | 특정 직무용으로 골라 모은 실전 프롬프트 묶음. 디지털 상품으로 판매한다 |
| 프롬프트 스택(prompt stack) | 영구적인 기반 프롬프트에서 실행별 맥락 주입까지 층층이 쌓은 구조. 모듈식 관리가 쉬워진다 |
| 리테이너(retainer) | 고객이 정해진 범위의 지속 업무에 월 정액을 내는 계약. 안정적이고 키우기 쉬운 서비스 사업의 핵심 청구 방식 |
| 직접 설치(self-hosted) | 업체 클라우드 대신 내 서버에서 소프트웨어를 돌리는 것. 고객 정보를 제3자 플랫폼에 넘기기 어려울 때 쓴다 |
| 시스템 프롬프트(system prompt) | 한 세션이나 API 호출 내내 유지되는 상시 지시. 역할, 제약, 출력 형식, 고정 맥락을 정하며 Claude 시스템에서 효과가 가장 큰 요소다 |
| 토큰(token) | AI 모델이 처리하는 글의 기본 단위. 영어로는 대략 단어의 4분의 3 정도이고, API 요금과 컨텍스트 윈도가 토큰으로 표시된다 |
| 워크플로(workflow) | 일을 끝내는 정해진 단계의 순서. 보통 사람이 시작하고 단계마다 확인한다 |

## 3. 헷갈리기 쉬운 짝

책은 워크플로와 자동화 파이프라인을 구분한다. 워크플로는 사람이 시작하고 지켜보는 절차이고, 파이프라인은 사건에 반응해 혼자 달린다. 새 예시로 보면, 월요일 아침에 내가 Claude에게 보고서 초안을 부탁하고 읽어 보는 것은 워크플로이고, 새 고객이 양식을 제출하면 자동으로 환영 메일 초안이 만들어져 대기함에 쌓이는 것은 파이프라인이다. 같은 일도 시작 버튼을 사람이 누르면 전자이고, 사건이 대신 누르면 후자다.

| 짝 | 차이 |
|----|------|
| 워크플로와 파이프라인 | 사람이 시작하는가, 사건이 시작하는가 |
| 시스템 프롬프트와 프롬프트 스택 | 하나의 상시 지시와 여러 층의 구조 |
| 프롬프트 엔지니어링과 프롬프트 팩 | 기술 분야와 그 결과를 담은 상품 |

## 4. 용어를 쓰는 요령

- 고객에게 보내는 글에서는 약어(MRR, API)를 처음 쓸 때 풀어 쓴다.
- 팀이나 고객과 같은 말을 같은 뜻으로 쓰도록 자기 용어집을 한 쪽 만든다.
- 새 용어가 나올 때마다 정의를 적고 이 부록처럼 알파벳순으로 정리하면 지식이 쌓인다.

## 핵심 정리

- 용어집의 정의는 학문적 엄밀함이 아니라 일에 쓰기 위한 풀이다.
- 입력 층, 처리 층, 출력 층과 시스템 프롬프트, 프롬프트 스택은 시스템 설계의 말이다.
- 리테이너, MRR, 맞춤 제작 서비스, 마이크로 SaaS는 사업 모델의 말이다.
- 워크플로는 사람이 시작하고 파이프라인은 사건이 시작한다는 구분을 기억하면 된다.
- 정의가 낯설면 장 본문으로 돌아가 예시와 함께 다시 읽는 것이 좋다.
