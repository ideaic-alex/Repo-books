# 컨텍스트 엔지니어링

Claude Code 환경에서 **컨텍스트 윈도우(Context Window)**는 단순한 대화 버퍼가 아니라 에이전트의 **CPU, RAM, 하드드라이브 역할을 모두 수행하는 가장 결정적인 제약 자원**입니다. 파일 내용, CLI 실행 결과, 도구 호출 기록, 대화 메시지 등 모든 작업 내역이 이 고정 크기의 버퍼에 누적되며, 공간이 가득 차면 지침을 잊어버리거나 이미 해결한 문제를 다시 푸는 **성능 절벽(Performance Cliff)** 현상이 발생합니다.

따라서 클로드 코드에서 뛰어난 성과를 내는 핵심은 프롬프트 다듬기가 아니라, 제한된 메모리 예산을 효율적으로 배분하고 관리하는 '컨텍스트 엔지니어링(Context Engineering)' 시스템을 구축하는 데 있습니다.

---

## 1. 핵심 지속성 레이어: `CLAUDE.md`의 구조적 역할

`CLAUDE.md`는 단순한 설명 문서나 README가 아니라, 매 대화 요청(turn)마다 프롬프트에 자동으로 로드되는 **상시 로드 지침(Always-On File)**입니다.

- **상시 비용(Always-On Cost)**: 작성된 모든 문장은 대화가 지속되는 내내 컨텍스트 윈도우 점유 비용을 발생시킵니다.
- **500줄 가이드라인 (500-Line Guideline)**: 파일이 500줄을 넘어가면 규칙 간 주의력(attention) 경합이 발생하여 에이전트가 중요 지침을 무시하게 되므로, 간결함 유지는 **성능 요구사항**입니다.
- **엄격한 정보 필터링**: *"Claude가 코드를 읽고 스스로 추론할 수 없는 정보인가?"*를 기준으로 작성합니다.
  - **포함**: 빌드/테스트 특정 명령, 기본 가이드라인과 다른 코딩 스타일 예외, 아키텍처 결정 배경, 개발 환경 특이점/트랩, 알려진 데이터/코드 버그 이력
  - **제외**: 코드나 의존성 파일에서 스스로 파악 가능한 정보, 표준 언어 컨벤션, 장황한 외부 라이브러리 문서
- **모듈화 및 에러 패치**: `@path` 임포트 구문(`@docs/architecture.md`)을 활용해 루트 파일을 슬림하게 유지하고, 세션 종료 시 새로 배운 내용을 `CLAUDE.md`에 지속적으로 업데이트하여 프로젝트 지식을 **복리로 성장(Compounding)**시킵니다.

## 2. 컨텍스트 예산 배분 및 확장 수단 비교 (Decision Matrix)

출처에서는 컨텍스트 예산을 최적화하기 위해 각 메커니즘의 로딩 방식과 비용 구조를 다음과 같이 비교합니다:

- **`CLAUDE.md`**: 매 turn 상시 소비되는 채널이므로 빌드 명령, 필수 가이드라인 등 **상시 필요한 규칙**만 최소한으로 배치합니다.
- **스킬 (Skills)**: 세션 시작 시 요약 설명만 로드되고 실제 호출 시에만 본문이 로드되므로 **특정 작업 시에만 필요한 참조 지침**을 저장하기에 적합합니다. 프런트매터에 `disable-model-invocation: true`를 지정하면 수동 호출 전까지 **컨텍스트 비용을 제로(0)**로 절감할 수 있습니다.
- **서브에이전트 (Subagents)**: 독립된 별도의 컨텍스트 윈도우에서 실행되어, 대량의 파일 읽기나 장황한 CLI 출력이 메인 세션의 컨텍스트를 오염시키는 것을 완전 격리(Context Isolation)합니다. 오직 요약 결과만 메인 맥락으로 전달됩니다.
- **훅 (Hooks)**: 외부 프로세스로 실행되므로 컨텍스트 소모가 전혀 없는 **가장 효율적인 확장 메커니즘**입니다. `SessionStart` 훅을 통해 동적 환경 상태를 주입할 수도 있습니다.
- **MCP 서버**: 외부 서비스와 연동되는 도구 규격으로 세션 시작 시 지연 로딩(Deferred Tool Search) 및 자원 모니터링(`/mcp`)을 통해 예산을 제어합니다.

## 3. 수술적 맥락 관리 및 손실 방지 메커니즘

컨텍스트 오염 및 가득 참으로 인한 성능 저하를 방지하기 위해 다음과 같은 진단 및 제어 기능을 활용합니다:

- `/context`: 현재 컨텍스트 점유율(시스템 프롬프트, `CLAUDE.md`, MCP, 대화 이력 등)을 색상 그리드로 시각화하여 예산 낭비 요소를 진단합니다.
- **자동 축소 보호 (`Compact Instructions`)**: 컨텍스트가 약 95%에 도달해 자동 축소(Auto-compaction)가 실행될 때, `CLAUDE.md` 내의 `Compact Instructions` 헤더 하위에 작성된 지침은 요약 손실 없이 온전히 보존됩니다.
- **선제적 및 수술적 요약 (`/compact`, `/rewind`)**: 80% 수준에서 `/compact Focus on...` 명령으로 의도된 수동 요약을 실행하거나, Esc 두 번(`/rewind`)을 눌러 "Summarize from here"를 통해 탐색 과정의 불필요한 대화만 선택적으로 축소합니다.
- **스펙 문서 (`spec.md`)**: 세션 축소나 재시작에도 변하지 않는 단일 진실 원천(Source of Truth)으로 스펙 문서를 작성해 맥락 오염을 방지합니다.

---

## 4. 워크플로우적 연계 (Explore-Plan-Implement-Commit)

컨텍스트 엔지니어링은 **4단계 워크플로우**의 기반이 됩니다. 컨텍스트 관점에서 **탐색(Explore)과 계획(Plan)**은 비용이 저렴한 읽기 전용 작업이며, **구현(Implement)과 디버깅**은 수많은 파일 수정과 테스트 출력을 수반하는 비싼 작업입니다. 사전 탐색과 계획으로 저렴한 작업을 전면에 배치(Front-loading)함으로써, 오답 구현 및 되돌리기(Revert)로 발생하는 컨텍스트 윈도우 낭비를 근본적으로 줄이는 경제학적 가치를 가집니다.

---

💡 컨텍스트 엔지니어링 관점에서 점유 비용을 제로(0)로 최적화해 주는 `disable-model-invocation: true` **스킬 작성 패턴**이나, 자동 축소 시 지침을 보호해 주는 `Compact Instructions` **헤더 작성 예시**에 대해서도 구체적으로 다뤄볼까요?
