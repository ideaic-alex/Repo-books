# 맞춤 코드 생성 지침

Copilot이 코드를 만들 때마다 "주석을 꼭 달아 줘", "private 필드는 밑줄로 시작해 줘" 같은 말을 매번 적는 건 비효율적이다. 맞춤 지침(custom instructions)을 설정해 두면 채팅이 코드를 생성하는 방식을 미리 길들일 수 있다.

2장에서는 코드 리뷰용 맞춤 지침을 소개했다. 이 문서는 같은 방식을 코드 생성 응답에 적용하는 세 가지 방법과 그 효과를 정리한다. 이 지침은 에디터의 인라인 코드 제안에는 적용되지 않는다는 점이 중요하다.

---

## 1. 설정 방법 세 가지

| 방법 | 어디에 | 형태 |
| --- | --- | --- |
| 1. settings.json | 사용자 설정 파일 | `github.copilot.chat.codeGeneration.instructions` 아래 `text` 항목 |
| 2. 지침 파일 | 저장소 또는 프로젝트의 `.github/copilot-instructions.md` | Markdown 불릿 목록 |
| 3. 다른 경로의 파일 | 원하는 경로의 Markdown 파일 + settings.json에서 `file` 키로 참조 | 파일 경로 지정 |

읽는 법은 간단하다. 개인 설정이면 1번, 저장소와 함께 공유하고 싶으면 2번, 파일 위치나 이름을 바꾸고 싶으면 3번이다.

### 1.1 settings.json에 직접 쓰기

`settings.json`을 편집해서 `github.copilot.chat.codeGeneration.instructions` 아래에 지침을 넣는다. 책의 규칙 예시는 다음과 같다.

```json
"github.copilot.chat.codeGeneration.instructions": [
    {
        "text": "Always add comments to generated code describing its purpose."
    },
    {
        "text": "Use underscores for private field names in TypeScript."
    }
]
```

이렇게 사용자 설정 파일에 규칙을 넣은 뒤에는, 같은 코드를 Copilot에게 다시 검토시켜 보면 설정 파일에 적은 조건을 짚어 낸다고 책은 설명한다(책은 2장의 그림 2-24를 가리킨다).

### 1.2 저장소의 Markdown 파일

저장소나 프로젝트에 경로와 이름을 정확히 `.github/copilot-instructions.md`로 해서 Markdown 파일을 만든다. 같은 규칙을 담은 파일의 모양은 이렇다.

```markdown
# Custom Instructions for Code Generation
- Always add comments to generated code describing its purpose.
- Use underscores for private field names in TypeScript.
```

### 1.3 다른 경로나 이름의 파일

다른 경로나 이름의 Markdown 파일을 쓰고 싶으면 그 파일을 만든 뒤 `settings.json`에서 `file:` 키로 가리킨다. 예를 들어 파일 이름이 `.docs/code-style.md`라면 설정에 다음 항목을 넣어 Copilot이 찾도록 한다.

```json
"github.copilot.chat.reviewSelection.instructions": [
    {
        "file": ".docs/code-style.md"
    }
]
```

원서의 이 예시는 설정 키로 `reviewSelection.instructions`를 쓰고 있다. 앞의 1.1이 `codeGeneration.instructions`인 것과 다르므로, 실제로 쓸 때는 지침을 적용하려는 용도(코드 생성인지 리뷰인지)에 맞는 키를 쓰는지 확인한다.

## 2. 적용 전후 비교

책은 최소한의 TypeScript 클래스를 만들면서 private 변수를 하나 두라고 프롬프트를 주는 예를 들었다. 맞춤 지침이 없을 때와 있을 때를 비교하면 다음과 같다.

| 항목 | 지침 없음 | 지침 있음 |
| --- | --- | --- |
| 주석 | 규칙이 반영되지 않는다 | 목적을 설명하는 주석이 붙는다 |
| private 변수 이름 | 규칙이 반영되지 않는다 | 밑줄로 시작한다 |

같은 프롬프트를 다시 실행했더니 코드에 주석이 달리고 private 변수 이름이 밑줄로 시작했다. 위 세 가지 방법 가운데 하나로 지정한 지침을 따른 결과다. 지침 하나를 적어 두면 이후 프롬프트마다 같은 요구를 반복할 필요가 없다는 점이 이 기능의 효용이다.

## 3. 알아 둘 점

| 대상 | 지침이 적용되는가 |
| --- | --- |
| 채팅의 코드 생성 응답 | 적용된다 |
| 에디터의 인라인 코드 제안 | 적용되지 않는다 |
| 코드 리뷰 | 2장의 리뷰용 지침을 따로 설정한다 |

설정 경로는 2장의 리뷰용 지침과 같은 세 가지(설정 파일, 지침 파일, 다른 경로 지정)다. 지침 파일을 저장소 안에 두면 같은 저장소를 쓰는 팀원도 같은 규칙을 받게 된다는 점은 파일 위치에서 짐작한 장점이다.
