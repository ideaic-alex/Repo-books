# 슬래시 명령과 채팅 참여자

자주 하는 요청마다 긴 문장을 쓰는 건 번거롭다. Copilot Chat은 흔한 요청을 짧게 부르는 슬래시 명령(`/`)과, 질문의 범위를 정해 주는 채팅 참여자(`@`)를 제공한다. 둘은 같은 입력창에서 나란히 쓰이고, 슬래시 명령은 대개 기본으로 연결된 참여자가 있다.

이 문서는 슬래시 명령의 목록과 호출 방법, 참여자의 종류와 쓰임, 그리고 둘의 대응 관계를 정리한다.

---

## 1. 슬래시 명령

슬래시 명령은 흔한 상호작용을 위한 지름길이다. `/`로 시작해서 이런 이름이 붙었다. 메인 채팅 창과 인라인 채팅(`Meta-I`) 어디서든 쓸 수 있다. 다만 IDE마다 가능한 명령이 다를 수 있어서, 아래 표는 책을 쓸 당시 쓸 수 있던 명령의 전체 집합이다. 인라인 채팅에서는 일부 명령이 빠진다.

### 1.1 명령 목록

| 명령 | 용도 |
| --- | --- |
| `/clear` | 현재 대화를 지운다 |
| `/doc` | 선택하거나 지정한 코드에 주석을 단다 |
| `/edit` | 활성 에디터에서 선택한 코드를 편집한다 |
| `/explain` | 코드가 어떻게 동작하는지 설명을 만든다 |
| `/fix` | 문제에 대한 수정안을 제안한다 |
| `/fixTestFailure` | 실패한 테스트의 수정안을 제안한다 |
| `/generate` | 특정 요청에 맞는 코드를 생성한다 |
| `/help` | Copilot 사용 도움을 얻는다 |
| `/new` | 새 워크스페이스용 코드를 뼈대로 만든다(scaffold) |
| `/newNotebook` | 새 Jupyter 노트북을 만든다 |
| `/search` | VS Code에서 내용을 검색한다 |
| `/startDebugging` | 실행 설정(launch config)을 만들고 VS Code에서 디버깅을 시작한다 |
| `/tests` | 코드에 대한 단위 테스트를 만든다 |

기능 일치 정도가 IDE마다 다르다는 점에 주의한다. IDE에 따라 일부만 있거나 표에 없는 명령이 있을 수 있고, 지원되는 명령은 자주 바뀐다. 쓰는 IDE의 Copilot 문서를 확인하는 것이 안전하다.

### 1.2 부르는 방법

채팅창에서 `/`를 입력하면 쓸 수 있는 명령 목록이 뜨고, 거기서 고르면 된다. 메인 채팅 창에서도 같은 방식이다. 이 책은 여기서 간단히 소개만 하고, 개별 명령은 뒤 장들에서 하나씩 자세히 다룬다.

### 1.3 코드 설명 기능이 잘 되는 조건

코드 설명 기능은 IDE에 해당 언어의 확장이 설치되어 있을 때 가장 잘 작동한다. 책을 쓸 당시 VS Code 확장 기준으로 다음 언어가 해당된다.

| 언어 |
| --- |
| TypeScript/JavaScript |
| Python |
| Java |
| C# |
| C++ |
| Go |
| Ruby |

## 2. 채팅 참여자

슬래시 명령 목록 옆에 `@`로 시작하는 이름이 함께 나온다. 이것이 채팅 참여자다. 참여자는 특정 영역(domain)을 가리키는 포인터에 가깝다. 프롬프트에 참여자를 적으면 AI에게 "이 영역으로 범위를 좁히고, 그 영역에 대한 참여자의 지식을 써서 답해 달라"고 말하는 셈이다. 쓰는 법은 `@` 다음에 참여자 이름을 적는 것이다.

### 2.1 참여자 목록

책을 쓸 당시 GitHub 문서에 있던 참여자는 다음과 같다.

| 참여자 | 아는 것 | 쓰는 때 |
| --- | --- | --- |
| `@workspace` | 워크스페이스에 있는 코드 | 프로젝트 구조, 코드 각 부분의 상호작용, 디자인 패턴을 고려하게 하고 싶을 때 |
| `@vscode` | VS Code의 명령과 기능 | VS Code 사용에 도움이 필요할 때 |
| `@terminal` | VS Code 터미널 셸과 그 내용 | 터미널 명령을 만들거나 디버깅할 때 |
| `@vision` | 이미지 파일을 붙여 질문을 이해하게 한다 (preview) | 이미지를 곁들여 질문할 때 |
| `@github` | 저장소 전반의 이슈, 풀 리퀘스트(PR) 등 | GitHub 관련 질문. 모든 인터페이스에서 되지는 않는다 |
| `@project` | JetBrains IDE용. `@workspace`처럼 프로젝트 코드를 안다 | JetBrains에서 프로젝트 전체를 물을 때 |

Copilot 확장을 설치하면 확장이 제공하는 맞춤 참여자도 쓸 수 있다. 확장은 10장에서 다룬다. 아래에서 자주 쓰는 세 가지를 더 살펴본다.

### 2.2 @workspace

워크스페이스의 모든 코드를 응답의 잠재적 출처로 삼게 하고 싶을 때 쓴다. 다만 모든 코드를 보내서 답을 만든다는 뜻은 아니다. Copilot 확장이 워크스페이스의 파일 전체를 훑어서, 컨텍스트로 쓸 만한 파일이나 그 일부를 가려낸다. 앞에서 말한 자동 인덱싱이 이 일을 쉽게 해 준다.

예를 들어 `@workspace`에게 "import를 쓰는 파일이 어느 것인가"를 물으면, Copilot은 먼저 워크스페이스에서 관련 내용을 모으고, 응답 맨 앞에 최종적으로 참고한 참조 목록을 보여 준다. "Used references" 줄을 펼치면 그 목록이 보이며, `@workspace`를 쓰면 참조가 더 많이 잡힌다. 응답은 워크스페이스 전반에 걸쳐 여러 파일을 나열한다.

`@workspace`로 할 만한 일반 질문은 다음과 같다. 익숙하지 않은 코드의 정보를 알아낼 때 특히 유리하다.

| 질문 예 |
| --- |
| What kind of backend is used in this project? |
| How do I run this code? |
| Where do I use X? |
| What service do I use to do Y? |
| Which frameworks are being used? |

두 가지를 기억해 둔다.

- `@workspace`는 코드베이스에 저장된 내용을 참조한다. 고친 내용이나 새로 만든 내용을 반영하려면 프롬프트를 실행하기 전에 먼저 저장한다.
- 채팅 입력을 보낼 때 Enter 대신 `Meta-Enter`를 누르면 프롬프트에 `@workspace`가 자동으로 붙는다.

### 2.3 @vscode

`@vscode`는 VS Code 전용이며, VS Code의 명령과 사용자 설정에 대한 전문가 역할을 한다. 자연어로 VS Code에 관해 물을 수 있고, 애플리케이션의 모든 설정과 명령의 색인에 접근할 수 있다.

| 질문 예 |
| --- |
| How can I open a project in VS Code? |
| How can I install extensions in VS Code? |
| How can I create a new file in VS Code? |
| How can I change the theme in VS Code? |

VS Code 기본값을 바꾸는 방법을 물은 예에서는, 답에 다른 인터페이스인 명령 팔레트(Command Palette)로 가는 링크 버튼이 함께 나왔다. 그 버튼을 누르면 해당 항목이 명령 팔레트에 열린다. 디버깅 방법이 궁금하면 이렇게 쓴다.

```text
@vscode how do I debug
```

### 2.4 @terminal

`@terminal`은 통합 터미널 셸, 그 버퍼, 터미널에서 현재 선택한 내용에 대해 묻게 해 준다. 터미널에서 무슨 일이 있었는지 이해하고, 문제를 풀고, 필요한 명령을 알아내는 데 편리하다.

| 질문 예 |
| --- |
| What did the last command do? |
| Explain the command |
| How do I...? |

출력된 명령 위에 마우스를 올리면 오른쪽에 팝업 컨트롤이 나타나 응답을 터미널에 바로 넣을 수 있다. 터미널에서 자주 쓰는 작업 흐름을 묻는 데도 쓴다. 예를 들면 명령줄에서 Git으로 코드를 커밋하는 방법이다.

## 3. 슬래시 명령과 참여자의 짝

대부분의 슬래시 명령은 기본으로 연결된 참여자가 있어서 그 영역에서 실행된다. 예를 들어 `@vscode`에는 `/startDebugging`이 연결되어 있다. 입력창에 `/startDebugging`만 써도 `@vscode`가 앞에 자동으로 붙는다. 이는 `/startDebugging`이 현재 VS Code를 대상으로 할 때만 의미가 있다는 뜻이다.

| 명령 | 참여자 | Copilot의 기능 |
| --- | --- | --- |
| `/explain` | `@terminal` | 터미널에서 일어난 일을 설명한다 |
| `/search` | `@vscode` | 검색(Search) 뷰에 넣을 쿼리 매개변수를 만든다 |
| `/startDebugging` | `@vscode` | 실행 설정을 만들고 VS Code에서 디버깅을 시작한다 (실험적) |
| `/explain` | `@workspace` | 활성 코드가 어떻게 동작하는지 설명한다 |
| `/fix` | `@workspace` | 코드의 버그에 대한 수정안을 제안한다 |
| `/fixTestFailure` | `@workspace` | 실패한 테스트의 수정안을 제안한다 |
| `/new` | `@workspace` | 새 워크스페이스나 새 파일의 뼈대를 만든다 |
| `/newNotebook` | `@workspace` | 자연어로 새 Jupyter 노트북의 뼈대를 만든다 |
| `/setupTests` | `@workspace` | 프로젝트의 테스트 설정을 한다 (실험적) |
| `/tests` | `@workspace` | 코드의 단위 테스트를 만든다 |
| `/help` | 없음 | GitHub Copilot 사용법을 안내한다 |
| `/clear` | 없음 | 새 채팅 세션을 시작한다 |

같은 `/explain`이라도 짝이 `@terminal`이면 터미널 내용을, `@workspace`면 활성 코드를 설명한다. `/help`와 `/clear`는 참여자와 짝이 없다. 이 표에는 앞의 명령 목록에 없던 `/setupTests`가 들어 있다는 점도 눈여겨본다.

참여자는 넓은 수준으로 컨텍스트를 다듬는다. 더 정밀하게 파일이나 선택 영역을 지정하고 싶다면 채팅 변수를 쓴다. 이는 [채팅 변수와 조합하기](%EC%B1%84%ED%8C%85%20%EB%B3%80%EC%88%98%EC%99%80%20%EC%A1%B0%ED%95%A9%ED%95%98%EA%B8%B0.md)에서 다룬다.
