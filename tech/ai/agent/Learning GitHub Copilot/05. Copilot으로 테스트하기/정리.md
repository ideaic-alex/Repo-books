# 정리

이 장은 Copilot의 코드 완성과 채팅 기능을 코드 테스트 생성에 적용하는 법을 다뤘다. 이 문서는 장 전체의 결론을 한곳에 모아 어떤 상황에 어떤 방법이 맞는지, 지켜야 할 태도가 무엇인지 정리한다.

---

## 1. 방법 선택 기준

작업 공간의 코드에 맞는 테스트를 만드는 방법은 여러 가지다. 코드 완성과 인라인 제안을 쓸 수도 있고 채팅 기능을 쓸 수도 있다. 대부분의 방법은 요청을 어떤 형태로든 채팅 화면에 넘긴다. 슬래시 명령을 쓰거나, 인라인 채팅 또는 별도 채팅에 프롬프트를 입력하는 식이다.

| 상황 | 알맞은 방법 |
|---|---|
| 길고 복잡하거나 분량이 큰 테스트 | 채팅 기능 |
| 빠른 틀(boilerplate) 단위 테스트, 간단한 테스트 함수 | 구체적인 인라인 주석을 프롬프트로 사용 |
| 통합 테스트 | 구성 요소 상호작용, 목, 기대 결과 검증을 프롬프트에 포함 |
| TDD 같은 모범 사례 | 테스트를 먼저 만들고, 이후 그것을 통과하는 구현을 생성 |
| 팀의 프레임워크와 규칙 맞추기 | 사용자 지정 테스트 지침 설정 |

기본 명령으로 만든 테스트는 대부분 단위 테스트다. 통합 테스트를 얻으려면 프롬프트에 구성 요소 사이의 상호작용, 목, 예상 결과 검증을 다루는 부분을 넣어야 한다.

## 2. 지켜야 할 태도

- 어떤 접근이든 결과가 쓸 만하고 의도와 맞는지 검토한다. Copilot의 제안이나 코드는 얼마든지 버리거나 프롬프트를 다시 짜서 더 정확한 결과를 구해도 된다.
- Copilot이 고려할 컨텍스트를 더 명확히 지정할 수 있다.
- 구현 코드처럼 테스트 코드도 가능하면 주석을 자세히 달아 읽고 이해하기 쉽게 하는 것이 이상적이다.

## 3. 다음 장으로

테스트 케이스나 구현을 설명하고 문서화하는 일은 다른 일에 쓸 시간을 뺏고 알고리즘도 바뀔 수 있어서 미뤄 두기 쉽다. 다음 장에서는 Copilot이 이런 작업을 거의 힘들이지 않고 끝내도록 돕는 방법을 다룬다.
