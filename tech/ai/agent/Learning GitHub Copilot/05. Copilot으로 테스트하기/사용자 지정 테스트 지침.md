# 사용자 지정 테스트 지침

팀마다 선호하는 테스트 프레임워크와 코딩 규칙이 있다. Copilot이 만드는 테스트를 이런 기준에 맞추려면 테스트 생성용 지침(instruction)을 직접 줄 수 있다. 그러면 원하는 프레임워크, 코딩 표준, 작업 방식에 맞는 테스트가 나온다.

이 문서는 지침을 어디에 어떻게 적는지, 설정 키와 예시, 별도 파일로 빼는 방법, 아직 실험 단계라는 점을 정리한다.

---

## 1. 두 가지 수준

테스트 생성 지침은 사용자 수준과 작업 공간(workspace) 수준에서 설정한다.

| 수준 | 어디에 적나 | 적용 범위 |
|---|---|---|
| 작업 공간 | 프로젝트의 `.vscode/settings.json` | 저장해 두면 그 프로젝트에서 일하는 모든 사람에게 Copilot의 동작이 맞춰진다 |
| 사용자(전역) | VS Code의 전역 설정 | 내가 다루는 모든 프로젝트에 적용된다 |

어느 수준이든 더 자세한 지침을 별도의 Markdown 파일에 쓰고, 설정에서 그 파일을 가리키게 할 수도 있다. 복잡하거나 계속 바뀌는 표준을 여러 프로젝트에서 재사용할 때 편리하다.

## 2. 설정 키와 예시

설정 파일에 지침을 넣을 때는 `github.copilot.chat.testGeneration.instructions` 키 아래에 둔다. 아래는 직접 쓴 지침과 파일 참조를 함께 보여 주는 예다.

```json
"github.copilot.chat.testGeneration.instructions": [
  {
    "text": "Prefer Mocha and Chai for testing Node.js modules."
  },
  {
    "text": "Use Pytest for all Python test cases."
  },
  {
    "file": "test-guidelines.md" // import instructions from file
  }
]
```

각 항목은 `text`로 지침 문장을 직접 적거나 `file`로 파일 경로를 가리킨다.

| 항목 키 | 값 | 용도 |
|---|---|---|
| `text` | 지침 문장 | 짧고 분명한 규칙 |
| `file` | 지침이 담긴 파일 | 길거나 자주 바뀌는 규칙 |

참조한 `test-guidelines.md`의 내용은 이런 식이다.

```text
Ensure all test functions have descriptive names.
Mock external API calls in integration tests.
```

## 3. 효과와 한계

지침의 형태를 다듬느라 몇 번 반복해야 할 수 있다. 하지만 한번 자리를 잡으면 `@workspace /tests` 같은 일반적인 작업에서 Copilot이 지침을 따른다.

| 설정 위치 | 예시 효과 |
|---|---|
| `text`: Mocha와 Chai | Node.js 모듈 테스트에 Mocha, Chai를 우선 사용 |
| `text`: Pytest | Python 테스트는 Pytest로 작성 |
| `file`: test-guidelines.md | 테스트 함수 이름을 설명적으로, 통합 테스트에서는 외부 API 호출을 목으로 |

글을 쓴 시점에 이 사용자 지정 테스트 지침 기능은 아직 실험적(experimental) 기능이라고 표시되어 있었다. 따라서 동작이 바뀌거나 기대와 다를 수 있다.

## 4. 언제 쓰면 좋은가

- 팀이 한 가지 프레임워크로 통일해서 쓸 때는 작업 공간 수준에 적어 저장소와 함께 공유한다.
- 개인 취향이나 여러 프로젝트에 공통인 규칙은 전역 설정에 둔다.
- 규칙이 길어지면 Markdown 파일로 빼서 `file`로 가리킨다.
