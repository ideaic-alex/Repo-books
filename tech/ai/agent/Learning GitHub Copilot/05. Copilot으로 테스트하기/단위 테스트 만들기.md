# 단위 테스트 만들기

CI(지속적 통합)나 테스트 주도 개발을 하려면 테스트를 많이 써야 하고, 손으로 쓰면 프로젝트 시간의 상당 부분이 여기에 들어간다. Copilot으로는 여러 방식으로 테스트 생성을 자동화할 수 있고, 복잡도도 고를 수 있다.

Copilot이 만드는 테스트는 대부분 함수나 절차 하나를 기본적으로 검사하는 단위 테스트(unit test)다. 다만 범위와 깊이는 프롬프트와 화면(인터페이스)에 따라 달라진다. 이 문서는 `/tests` 명령, 직접 쓴 프롬프트, 주석, 입력값 검증, 프롬프트 템플릿을 차례로 다룬다. 예제는 숫자가 소수인지 판별하는 함수다. 구현 방식은 중요하지 않고, 이런 버전이 쓰였다.

```python
def is_prime(number):
    if number <= 1:
        return False
    for n in range(2, int(number**0.5) + 1):
        if number % n == 0:
            return False
    return True
```

---

## 1. 접근 방법 한눈에 보기

| 방법 | 어디서 | 장점 | 단점 |
|---|---|---|---|
| `/tests` 명령 | 인라인 채팅, 채팅 보기 | 가장 쉽고 빠르다 | 기본 범위의 테스트만 나온다 |
| 컨텍스트 메뉴 Copilot > Generate Tests | 에디터 우클릭 | 마우스로 바로 실행 | 내부적으로 `/tests`를 쓴다 |
| 직접 쓴 프롬프트 | 채팅 | 원하는 케이스를 짚어 요청 | 프롬프트를 고민해야 한다 |
| 주석 지시 | 에디터 인라인 | 흐름을 끊지 않는다 | 제안을 여러 번 수락해야 하거나 평범한 제안이 나온다 |
| 입력 검증 요청 | 채팅 | 함수 안에 검사 코드를 넣는다 | 테스트 파일이 아니라 구현 코드가 바뀐다 |

글이 길어도 요점은 하나다. 빠르고 간단하게는 `/tests`나 주석, 길고 복잡한 테스트에는 채팅을 쓰는 것이 낫다.

## 2. /tests 명령 사용하기

가장 쉬운 방법은 에디터에서 쓰는 슬래시 명령 `/tests`다. IDE에서 선택하거나 참조한 코드에 대해 기본적인 단위 테스트를 만들어 준다. IDE가 제공하는 어느 채팅 화면에서든 입력할 수 있다.

가장 간단한 사용법은 테스트할 코드를 드래그해 선택하고 채팅창에 `/tests`를 입력하는 것이다. 예제에서 인라인 채팅으로 실행하자 Copilot은 소수, 소수 아닌 수, 1, 0, 큰 소수, 큰 합성수에 대한 assert 기반 테스트를 만들었다. 인라인 채팅에서는 `test_is_prime.py`라는 새 파일로 변경을 제안하고, 마음에 들면 Accept 버튼을 누른다.

에디터 컨텍스트 메뉴에서 Copilot > Generate Tests를 골라도 같은 결과가 나온다. 사실 Copilot은 대부분 `/tests` 단축 명령을 쓰려고 한다.

별도 채팅 보기에서 `/tests`를 실행하면 결과는 비슷하지만, 채팅 영역에 접근 방식, 선택한 프레임워크, 만들 테스트의 종류에 대한 설명이 더 많이 붙는다. 입력창 바로 위에는 변경된 파일 목록이 나오고, 모든 파일에 Keep/Undo 버튼이 있다.

| 컨트롤 | 모양 | 역할 |
|---|---|---|
| 유지(keep) | 체크 표시 | 제안된 파일을 받아들인다 |
| 되돌리기(undo) | 왼쪽으로 굽은 화살표 | 제안을 취소한다 |
| diff 보기 | +와 -가 든 문서 아이콘 | 제안된 변경의 차이를 에디터에 보여 준다 |

개별 파일은 첫 줄로 표시되고, 파일마다 자기 컨트롤이 있다. 읽는 법은 간단하다. 체크는 받기, 화살표는 버리기, 문서 아이콘은 먼저 비교하기다.

## 3. 아이콘이 바뀌어도 변하지 않는 것

Copilot은 화면의 컨트롤을 자주 바꾸고 위치도 옮긴다. 이 책을 읽는 시점에는 다시 바뀌었을 가능성이 크다. 그래도 제안된 편집에 대해서는 대체로 다음이 유지된다.

- 변경을 받아들이는(accept/keep) 컨트롤과 거부하는(reject/undo) 컨트롤이 있다.
- 체크 표시는 keep 컨트롤을 겸한다.
- 제안된 diff를 에디터의 파일로 보거나 파일에 적용하는 컨트롤이 있다.
- diff 컨트롤이 파일 이름을 알맞게 정해 준다는 보장은 없다. 검토하고 남길 변경을 고른 뒤에는 직접 저장해야 한다.

## 4. 명시적인 프롬프트로 테스트 만들기

채팅에 프롬프트를 직접 쓰는 방법도 있다. "선택한 코드의 테스트를 만들어 줘" 같은 간단한 문장은 보통 `/tests`가 다시 실행되는 결과가 된다(그 명령을 IDE가 지원한다면). 하지만 더 방향이 분명한 프롬프트를 쓰면 다른 케이스의 테스트도 제안받을 수 있다.

이미 생성한 테스트를 반영했다면, 현재 테스트 파일과 구현 파일을 컨텍스트로 선택하고 이렇게 물어본다.

```text
are there any other edge cases that should be tested
```

Copilot은 추가 케이스를 이유와 함께 알려 준다. 예제에서 나온 여섯 가지는 다음과 같다.

| 번호 | 케이스 | 확인하려는 것 |
|---|---|---|
| 1 | 가장 작은 소수 | 2를 소수로 판별하는지 |
| 2 | 2보다 큰 짝수 | 10 같은 수가 소수가 아닌지 |
| 3 | 매우 큰 합성수 | 10^6 같은 큰 비소수 |
| 4 | 부동소수점 입력 | 3.5 같은 정수가 아닌 값을 어떻게 처리하는지 |
| 5 | 문자열 입력 | "seven" 같은 잘못된 타입의 처리 |
| 6 | 음의 짝수 | -4가 소수가 아닌지 |

Copilot은 이 케이스를 위한 코드도 준다. 핵심 줄만 보면 다음과 같다.

```python
def test_smallest_prime(self):
    self.assertTrue(is_prime(2))
def test_very_large_composite_number(self):
    self.assertFalse(is_prime(10**6))
def test_floating_point_input(self):
    with self.assertRaises(TypeError):
        is_prime(3.5)
def test_negative_even_number(self):
    self.assertFalse(is_prime(-4))
```

부동소수점과 문자열 테스트는 "함수가 정수가 아니면 TypeError를 낸다고 가정한다"는 주석이 달려 있다. 이 가정이 실제 함수에 맞는지는 사람이 확인해야 한다.

더 지시적으로 요청할 수도 있다. `add test cases for other kinds of inputs`라고 하면 `is_prime(7.1)`과 `is_prime("7")`에 대해 TypeError를 기대하는 테스트가 추가된다.

여기서 얻을 점은, 기본 프롬프트나 명령이 만드는 범위를 넘어서 계속 추가로 질문하는 것이 Copilot에서 가치를 뽑아내는 핵심이라는 것이다. Copilot을 팀에 새로 들어온 사람에 비유하면, 일반적인 테스트 너머의 상황도 생각해 보라고 한 번 더 떠밀어 줘야 한다.

## 5. 주석으로 테스트 만들기

채팅을 켜지 않고, 에디터에서 작업하던 흐름 그대로 "여기에 간단한 테스트를 넣어 줘"라고 하고 싶을 때가 있다. 이럴 때는 Copilot에게 주는 지시를 주석으로 쓴다. 그러면 Copilot이 돌려주는 개별 테스트나 테스트 함수 제안을 수락하면 된다. 수락, 편집 같은 흐름은 2장과 같다.

- 장점: 단순하든 복잡하든 코드 안의 주석 한 줄로 시작할 수 있다.
- 단점: 제안의 일부를 계속 반복해서 수락해야 하거나, 덜 유용한 일반적 제안이 나올 수 있다.

`is_prime` 함수 뒤에 다음 주석을 넣은 예다.

```python
# Generate 10 simple test cases for the is_prime function
```

Copilot은 간단한 assert 묶음으로 이루어진 인라인 함수를 제안했다. 예제에서 9번째 줄이 주석이었고 10~23번째 줄이 전부 자동 생성되었다. 더 일반적인 주석도 가능하다.

```python
# Create tests for the code above
```

이 경우에도 비슷한 테스트가 나오지만 같은 파일 안에 만들어진다. 이 예제에서 직접 입력한 줄은 첫 주석뿐이었고 나머지는 모두 제안을 받아서 생성되었다.

## 6. 입력값 검증 코드 만들기

테스트와는 다른 각도로, 함수에 들어오는 입력이 유효한지 검사하는 코드도 Copilot이 만들어 준다. 먼저 assert를 쓰도록 요청한다.

```text
generate asserts to ensure that the inputs to the function are valid
```

Copilot은 함수 시작 부분에 입력이 정수인지, 음수가 아닌지 확인하는 assert를 넣는 방법을 제안한다.

```python
def is_prime(num):
    assert isinstance(num, int), "Input must be an integer"
    assert num >= 0, "Input must be a non-negative integer"
    if num < 2:
        return False
```

assert라는 말을 빼고 "checks"로 요청할 수도 있다.

```text
generate checks to ensure that the inputs to the function are valid
```

이번에는 더 표준적인 코딩 방식으로 문제를 드러낸다. 정수가 아니면 `TypeError`, 음수이면 `ValueError`를 발생시키는 `if` 문이 들어간다.

```python
def is_prime(num):
    if not isinstance(num, int):
        raise TypeError("Input must be an integer")
    if num < 0:
        raise ValueError("Input must be a non-negative integer")
    if num < 2:
        return False
```

| 방식 | 결과 | 어울리는 때 |
|---|---|---|
| assert 요청 | `assert`로 간단히 검사 | 결과를 단순하게 두고 싶을 때 |
| checks 요청 | `raise TypeError`, `raise ValueError` | 더 넓은 범위의 표준적인 오류 처리가 필요할 때 |

AI와 상호작용하고 있으므로 프롬프트와 컨텍스트 설정이 명확한 결과를 얻는 열쇠다. 일반적인 결과나 인라인에서 빨리 나온 결과와 구분된다. 프로젝트 진행 상황, 언어와 프레임워크 경험에 따라 여러 방식을 섞어 쓰면 잘 맞는다.

## 7. 단위 테스트 프롬프트 템플릿

Copilot 문서를 바탕으로 한 범용 템플릿은 다음과 같다. `<`와 `>`로 감싼 부분은 자기 상황에 맞게 바꾼다.

```text
Develop a comprehensive suite of unit tests for the
<method/function> in <language/framework>. Write multiple test
methods that cover a wide range of scenarios, including edge
cases, exception handling, and data validation.
```

| 요소 | 의미 |
|---|---|
| 범위(Scope) | 포괄적인 단위 테스트 묶음을 요청해서 기본 테스트 이상으로 다양한 사용 사례를 다루게 한다 |
| 경계 케이스(edge cases) | 경계 조건을 확인한다 |
| 예외 처리(exception handling) | 잘못된 동작이 일어났을 때 발생해야 하는 오류를 확인한다 |
| 데이터 검증(data validation) | 입력이 메서드에서 제대로 검증되고 처리되는지 확인한다 |

이 템플릿의 효과는 "여러 테스트 메서드로, 넓은 시나리오를"이라고 명시하는 데서 나온다. 단위 테스트 방식은 여기까지이고, 다음은 통합 테스트를 다룬다.
