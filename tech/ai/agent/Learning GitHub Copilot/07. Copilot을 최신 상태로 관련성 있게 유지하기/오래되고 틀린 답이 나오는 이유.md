# 오래되고 틀린 답이 나오는 이유

Copilot 채팅을 처음 열면 AI가 만든 결과라 놀랄 만한 일이나 실수가 있을 수 있으니 생성된 코드와 제안을 꼭 확인하라는 안내가 나온다. 생성형 AI는 부정확하거나 문제가 있을 수 있고, 결과가 맞고 관련 있는지 확인하는 책임은 결국 사용자에게 있다는 뜻이다. 테스트와 코드 리뷰 같은 표준 검증 절차를 AI가 만든 코드에도 똑같이 적용해야 하는 이유다.

이 문서는 응답의 시의성(최신성)과 관련성을 해치는 요인 가운데 학습 시점의 한계, 환각, 실시간 검증의 부재를 다룬다. 마지막 요인인 잘못된 컨텍스트는 다음 문서에서 다룬다.

---

## 1. 네 가지 요인 한눈에 보기

| 요인 | 한 줄 설명 | 눈에 띄는 증상 |
| --- | --- | --- |
| 학습 시점 한계(training cutoff) | 모델은 학습이 끝난 시점까지의 정보만 안다 | 폐기된 코드, 이전 버전 기준 코드 |
| 환각(hallucination, 그럴듯하지만 틀린 답) | 진짜처럼 보이지만 존재하지 않는 내용을 만든다 | 없는 함수, 없는 라이브러리 |
| 실시간 검증 부재 | 생성한 데이터를 확인할 방법이 없다 | 틀린 값이 섞인 생성 데이터 |
| 잘못된 컨텍스트 | 의도와 다른 내용을 근거로 답한다 | 엉뚱한 언어나 파일 기준의 답 |

네 가지는 서로 다른 원인이지만, 겉으로는 모두 "그럴듯한데 안 맞는 답"으로 나타난다. 어떤 요인인지 알아야 대응 방법을 고를 수 있다.

## 2. 학습 시점 한계

대규모 언어 모델(LLM)은 학습이 이루어진 시점까지의 데이터로 만들어진다. 그 날짜 이후에 바뀐 것은 모델이 알 방법이 없다. 학습 시점에서 멀어질수록 응답이 낡았을 가능성이 커진다. 폐기(deprecated)된 코드가 나오거나, 이전 버전의 프레임워크와 언어에 맞는 코드가 나오는 식이다. 어떤 모델을 쓰느냐에 따라 결과도 달라진다.

모델을 자주 새로 학습시키지 않는 이유는 단순하다. 모델에는 수십억 개의 파라미터가 있고 처리할 데이터도 방대해서, 학습에 막대한 계산 비용과 시간이 든다. 그래서 기반 학습을 갱신하는 일은 여러 면에서 비싸다.

### Go의 rand.Seed 예시

책이 쓰인 시점의 Copilot으로 실험한 사례가 있다. Go에서 난수 생성기의 시드를 설정하는 함수를 써 달라고 요청하면, 문법상 문제없어 보이는 코드가 나온다. 그런데 Seed 함수는 Go 1.20부터 폐기되었다. 그래서 채팅에 "Is the Seed function deprecated in Go?"라고 물어보면, 모델의 학습 내용에는 그 정보가 없어서 폐기되었다고 답하지 못한다.

여기서 알 수 있는 점은 두 가지다. 코드가 문법적으로 맞아도 최신 권장 방식이라는 보장은 없다. 그리고 Copilot에게 폐기 여부를 되물어도 학습 시점에 없던 내용은 모른다. 이 예시는 이후 문서에서 모델 변경과 예시 제공으로 해결하는 과정에 계속 쓰인다.

### 다른 도구가 알려 주는 경우

일부 IDE에서는 설치된 다른 도구가 폐기된 코드를 감지해 경고해 준다. 이럴 때는 Copilot의 Fix 기능을 써서 대체 코드를 만들게 할 수 있다.

## 3. 환각

LLM은 그럴듯해 보이지만 실제로는 사실이 아닌 데이터로 응답을 만들기도 한다. 이를 환각이라 한다. 일반 채팅에서는 존재하지 않는 대상을 언급하거나 사실이 아닌 것을 사실처럼 말하는 모습으로 나타난다. 위협 탐지처럼 중요한 시스템에서는 위협이 아닌 것을 위협으로 표시하기도 한다.

코딩에서 환각은 아래와 같은 형태를 띤다.

| 환각 유형 | 예 |
| --- | --- |
| 없는 식별자와 코드 참조 | 존재하지 않는 이름, 변수, 상수, 관련 코드를 참조 |
| 부정확한 생성 데이터 | 값이 틀린 데이터 |
| 없는 함수와 메서드 | 실제로 정의되지 않은 호출 |
| 잘못된 라이브러리나 API 사용 | 사용법이 틀리거나, 아예 없는 라이브러리와 API를 사용 |
| 만들어 낸 타입이나 클래스 | 존재하지 않는 타입 |
| 그럴듯하지만 틀린 비즈니스 로직 | 맞아 보이는 흐름이지만 실제 요구와 다름 |
| 주변 코드에 대한 잘못된 가정 | 실제와 다른 전제 위에서 작성 |
| 의도한 동작을 검증하지 않는 테스트 | 테스트가 있어도 핵심을 확인하지 못함 |

위 표의 첫 번째 범주, 즉 없는 식별자나 코드를 참조하는 환각은 모델이 좋아지면서 Copilot 초창기보다 줄어든 것으로 보인다. 이런 환각은 눈에 잘 띄어서 사용자가 검토하다 빨리 잡는 경우가 많다. 놓친 채 수락했다 해도 컴파일러, 린터, 문법 검사 도구가 결국 걸러 낼 가능성이 높다. 반면 두 번째 유형인 생성 데이터의 부정확함은 훨씬 눈에 안 띈다. 자동으로 실시간 검증할 방법이 없기 때문이다.

## 4. 실시간 검증이 없다는 것

Copilot이 만든 데이터는 부정확할 수 있고, Copilot 스스로도 그렇게 알려 줄 때가 있다. 예를 들어 지역 번호와 주를 매핑하는 데이터를 만들어 달라고 했더니, 작업을 마친 뒤 위 코드는 자리 표시자일 뿐이며 실제 주별 지역 번호를 나타내지 않을 수 있다는 단서를 붙인 사례가 있다.

이런 일이 생기는 이유는 네 가지다.

1. Copilot이 학습한 데이터에 정확한 실제 값이 있을 수도 있고 없을 수도 있다.
2. Copilot은 문법과 구조에 맞는 결과를 만드는 데 집중한다.
3. Copilot은 자기가 생성한 코드를 실행하지 않고 논리를 검증하지도 않는다.
4. 생성한 데이터가 정확한지, 최신인지 찾아서 확인할 장치가 없다.

앞의 세 가지는 이해하기 쉽다. 네 번째는 Copilot이 만든 결과를 웹 같은 다른 출처와 대조하는 기능이 없다는 의미다. 도구를 활용해 이를 하는 AI 기법도 있지만, 모델 응답을 검증하는 용도로 Copilot에 통합된 것은 아니다. 데이터가 맞을 수도 있으나 보장은 없다. 한마디로 Copilot은 무엇이 참이고 거짓인지 알 방법이 없다.

그래서 Copilot이 만든 정보가 정확하다고 가정하면 안 된다. 데이터 생성은 값이 정확할 필요 없이 형식만 맞으면 되는 내용, 예를 들어 테스트 시나리오용 데이터에 더 잘 맞는다.

> 참고: Copilot Extensions(확장)을 만들면 API나 다른 도구를 호출해 특정 용도에 더 최신이고 관련성 높은 정보를 가져올 수 있다. 이미 있는 확장을 찾아 쓰거나 직접 만들면 된다. 확장은 10장에서 자세히 다룬다.
