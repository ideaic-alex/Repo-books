# 정리

이 장은 Copilot이 코드 제안과 응답을 위해 컨텍스트를 어떻게 정하는지, 그 응답이 왜 최신이 아니거나 부정확할 수 있는지, 그런 상황에서 사용자가 쓸 수 있는 대응법을 다루었다. 이 문서는 장의 결론을 다시 묶어 정리한다.

---

## 1. 장 전체 요약

Copilot의 핵심 컨텍스트는 사용하는 모델의 학습에서 나온다. 모델은 마지막으로 학습된 시점까지만 최신이므로, 그 뒤에 일어난 언어와 프레임워크의 갱신이나 변경은 알지 못한다. 학습에 쓰인 내용도 도구의 옛 버전을 사용하고 있어서, 거기서 나온 제안과 응답은 상당히 낡았을 수 있다. 이 점은 꼭 인지하고 주의해야 한다. 빠르게 쓸 수 있는 해결책 하나는, 더 나은 모델이 있으면 그쪽으로 바꾸는 것이다.

다행히 Copilot은 사용 중인 에디터와 워크스페이스에 있는 내용에서도 컨텍스트를 가져온다. 이 컨텍스트는 지금 하는 일과 쓰는 것을 반영하므로 학습 데이터보다 우선한다. 그래서 IDE와 워크스페이스에 관련 내용을 직접 넣어 더 최신이고 관련성 높은 컨텍스트를 줄 수 있다. 대개는 관련 정보가 담긴 파일을 IDE에서 열어 두면 된다. 더 분명하게 지시하려면 필요한 동안 현재 파일에 그 정보를 추가해 Copilot이 참고하게 한다.

## 2. 지정 수단 정리

GitHub Copilot에는 특정 내용에 AI를 집중시키는 수단도 있다.

| 수단 | 역할 | 예 |
| --- | --- | --- |
| 채팅 참여자(@) | 질문과 응답의 전체 컨텍스트 영역을 정한다 | VS Code, 활성 터미널, 워크스페이스 |
| 채팅 변수(#) | 워크스페이스 안의 특정 항목으로 컨텍스트를 좁힌다 | 에디터의 현재 선택 영역, 에디터에 열린 내용, 터미널의 마지막 명령 등 |

## 3. 문제와 대응 한눈에 보기

| 문제 | 대응 |
| --- | --- |
| 폐기된 코드나 이전 버전 기준 코드 | 더 최신 모델로 전환, 최신 코드 예시를 컨텍스트로 제공 |
| 컨텍스트가 엉뚱하거나 없음 | @workspace 같은 채팅 참여자와 #file 같은 채팅 변수로 지정 |
| 프로젝트에 맞지 않는 일반적인 제안 | 스키마 같은 정의 파일을 워크스페이스에 두고 열어 둠 |
| 생성된 데이터를 신뢰하기 어려움 | 정확성을 가정하지 않고 테스트와 코드 리뷰로 검증 |
