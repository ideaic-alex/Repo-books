# 개인정보와 보안

Copilot은 열린 파일 같은 여러 정보를 읽어 웹을 통해 보내고 처리한다. 그래서 내 데이터가 어떻게 다뤄지는지, 라이선스가 걸린 코드와 비슷한 제안이 나오면 어떻게 되는지, 결과가 안전한지가 현실적인 걱정거리다. 이 문서는 고려할 점 여섯 가지 중 마지막 둘인 개인정보와 보안을 다루고, Copilot을 어떤 태도로 대해야 하는지까지 정리한다.

---

## 1. 개인정보

앞에서 본 것처럼 현재 파일, 열린 파일 등 여러 정보 출처를 읽어 Copilot을 통해 LLM용 프롬프트에 넣는다. 일부 데이터가 웹을 건너 내 통제 밖에서 처리된다는 뜻이라 보안 위험처럼 보일 수 있다.

그러나 Copilot은 가입할 때 선택 옵션을 둔다. 내 컨텍스트 정보를 GitHub가 Copilot을 개선하는 데이터로 쓰도록 허용할지 정하는 것이다. 허용하지 않으면 정보는 수집되지만 보관되지 않는다. 프롬프트를 만들려고 모았다가 버린다. GitHub에는 개인정보 관련 콘텐츠 문제를 다루는 Trust Center도 있다.

### 데이터가 닿는 세 영역

| 영역 | 내용 |
|---|---|
| 사용자 참여(User engagement) | 텔레메트리, 즉 Copilot을 어떻게 쓰는지에 관한 사용 데이터. 제안을 수락했는지 무시했는지, 채팅 UI를 어떻게 쓰는지, 지연 시간과 오류 메시지 같은 지표 |
| 프롬프트(Prompts) | 환경에서 가져온 컨텍스트 정보나 GitHub로 되돌려 보내는 채팅 질의 |
| 제안(Suggestions) | Copilot이 돌려주는 코드 완성 제안이나 채팅 질의에 대한 응답 |

사용자 참여 데이터는 기본적으로 추적되고 익명화된 데이터가 포함될 수 있다. 다만 쓰는 Copilot 요금제에 따라 세부 사항이 다르므로 Trust Center 문서를 봐야 한다. 데이터는 전송 중과 저장 중 모두 암호화하는 장치가 있고, GitHub 쪽에서 데이터에 접근할 수 있는 사람을 엄격하게 제한하는 통제도 있다.

## 2. 공개 코드 일치와 라이선스

공개 저장소로 일부 LLM을 훈련하는 것이 합법인지는 여론과 법정에서 의문이 제기되어 왔다. 책은 이 문제를 다른 이들에게 맡기고 초기 훈련 과정의 그런 측면은 논평하지 않는다.

Copilot에 대해 흔히 제기되는 또 다른 우려가 있다. 라이선스가 걸린 저장소로 훈련된 모델을 쓰면 그 코드베이스의 내용과 아주 비슷한 제안이 나올 수 있다는 점이다. 그러면 사용자가 모르는 사이에 복제된 코드가 작업에 들어가 라이선스 조건과 지식재산권을 위반할 수 있다.

이에 대비해 Copilot에는 개인과 관리자가 공개 코드 일치를 차단하는 옵션이 있다(위 가입 옵션 화면의 위쪽에 해당). 이 옵션을 선택하면 일치가 생겼을 때 Copilot이 상황을 알려 주고 공개 코드베이스와 일치하는 내용을 걸러 낸다.

| 설정 | 일치하는 코드가 나오면 |
|---|---|
| 차단 선택 | 알림을 주고 공개 코드와 일치하는 제안을 걸러 낸다 |
| 허용 | 제안이 그대로 나온다 |

### 일치 허용 옵션은 왜 있나

일치 콘텐츠는 GitHub 저장소의 코드와 Copilot이 제안한 코드 사이의 정확한 또는 거의 정확한 일치를 말한다. 허용 옵션의 가치는 사실 크지 않을 수 있다. 다만 어떤 일을 하는 방법을 일반적으로 조사 중이고, 일치하는 게 있으면 쓸 생각이 없거나, 그것이 최선의 접근이라면 라이선스 조건에 따라 쓸 생각인 경우에는 받아들일 만한 사용 사례가 될 수 있다.

## 3. 보안

마지막이지만 중요한 것이 Copilot이 돌려주는 결과의 보안이다. 보안은 오늘날 모든 제품과 애플리케이션에서 항상 걱정거리이고, 해결은 안전한 코딩 관행에서 시작한다.

앞서 Copilot이 LLM의 잠재 결과를 받으면 GitHub가 추가 처리를 한다고 했다. 이 처리에는 가능한 취약점을 빨리 찾는 알고리즘 실행이 들어간다. 보안 스캔 애플리케이션을 결과에 돌리는 것은 아니다. 그러면 시간이 너무 오래 걸린다. 대신 취약점이나 안전하지 않은 코딩 관행을 가리키는 패턴을 빠르게 훑는다. 그런 것이 확인되면 해당 제안에 표시를 붙인다.

| 비교 | Copilot의 빠른 패턴 스캔 | 취약점 전용 스캔 도구 |
|---|---|---|
| 방식 | 취약하거나 위험한 코딩 패턴을 빠르게 찾음 | 전체 스캔 |
| 속도 | 빠름 | 오래 걸림 |
| 보장 | 빠져나가는 것이 없다고 보장하지 못함 | 목적에 맞는 전체 검사 |

이런 조치가 있어도 놓친 것이 없다는 보장은 없다. 처리 방식이 취약점 전용 도구로 전체 스캔을 돌리는 것과 같지 않으므로, Copilot의 결과에도 다른 코드에 적용하던 보안 점검을 그대로 적용해야 한다.

## 4. 신입 개발자처럼 대하기

생성형 AI를 쓸 때의 분명하고 상시적인 요구는, 돌려받은 제안을 항상 검토하고 평가해야 한다는 것이다. 컨텍스트를 완전히 올바르게 해석했을 것이라고 가정하면 안 된다. 아주 단순한 경우를 빼면 결과가 완벽하다고 볼 수도 없다.

Copilot은 흔히 AI 페어 프로그래머라고 불리지만 실제 사람 페어 프로그래머만큼 내 코드를 이해하거나 익숙하지 않다. 프로젝트에 새로 들어온 숙련된 프로그래머로 생각하는 편이 낫다. 그런 사람은 관찰하고 공유받은 것을 바탕으로 쓸 만한 코드를 만들 수 있지만, 더 큰 컨텍스트, 프로젝트 이력, 배경 이야기까지 갖고 있지는 못하다. 그래서 그가 만든 코드가 정확하고 안전하며 병합하기에 적합한지 꼼꼼히 확인해야 한다. Copilot의 답과 제안도 똑같이 다뤄야 한다.

팀 신입을 대할 때처럼 자세히 알려 줄수록 결과가 좋아진다. 컨텍스트로 쓸 코드든 구체적인 지시든 마찬가지다. 참고할 코딩 예제를 더 주고 채팅 프롬프트에 구체적인 내용을 담으면 AI에서 더 나은 결과를 얻는 데 큰 도움이 된다.

| 신입 개발자에게 하는 일 | Copilot에게 하는 일 |
|---|---|
| 프로젝트 배경과 예제 코드를 보여 준다 | 열린 파일과 주석으로 컨텍스트를 준다 |
| 구체적으로 지시한다 | 채팅 프롬프트에 구체적인 내용을 담는다 |
| 낸 코드를 리뷰하고 병합 전에 확인한다 | 정확성, 보안, 병합 적합성을 직접 검토한다 |
