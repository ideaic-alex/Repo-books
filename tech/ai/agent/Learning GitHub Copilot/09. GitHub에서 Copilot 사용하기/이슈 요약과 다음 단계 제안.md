# 이슈 요약과 다음 단계 제안

GitHub 이슈는 버그, 작업, 논의를 기록하는 흔한 도구다. 오래된 이슈일수록 댓글이 길게 쌓여서 핵심을 파악하는 데 시간이 든다. Copilot에는 이슈를 요약해 주는 기능이 기본으로 들어 있다.

이 문서는 Copilot이 이슈를 어떤 재료로 요약하는지, 요약이 주는 이점, 채팅에서 요약과 다음 단계 제안을 받는 방법, 그리고 결과를 믿고 쓸 때 주의할 점을 정리한다.

---

## 1. Copilot이 이슈를 읽는 방식

Copilot은 GitHub 자체 API 같은 도구를 써서 이슈의 내용을 분석한다. 읽는 대상은 다음과 같다.

| 읽는 재료 | 설명 |
|---|---|
| 본문(body) | 이슈를 설명한 글 |
| 제목(title) | 이슈 제목 |
| 댓글(comments) | 이슈에 달린 토론 |
| 연결된 PR | 있다면 포함 |

목표는 알아야 할 요점을 모은 요약 개관을 만드는 것이다. 이슈에 담긴 정보가 얼마나 많은가에 따라 달라지지만 요약에는 보통 다음이 들어간다.

- 핵심 문제
- 영향을 받는 구성 요소
- 기대하는 동작(있어야 할 기능)
- 가능한 해결 방법

## 2. 요약의 이점

| 이점 | 내용 |
|---|---|
| 시간 절약 | 긴 토론을 일일이 읽지 않고도 이슈의 핵심을 빨리 이해한다 |
| 더 나은 소통 | 관련 작업이나 업데이트에 붙일 명확한 요약을 모든 수준에서 제공한다 |
| 효율적인 분류(triage) | 요약에서 드러나는 심각도, 영향, 수정 난이도를 근거로 이슈의 우선순위를 더 잘 정한다 |

분류는 이슈가 많이 쌓인 프로젝트에서 어느 것부터 처리할지 정하는 일이다. 요약이 명확하면 판단이 쉬워진다.

## 3. 채팅으로 이슈 다루기

앞 코드 스캔 예시에서 만든 데이터베이스 쿼리 보안 이슈로 이어서 해 보자. 이슈 화면에서 Copilot 채팅을 열고 프롬프트를 보내서 정보나 도움을 얻는다.

이슈 화면에서 새 채팅을 열면 이슈에 맞는 질문이 미리 채워진다는 점은 앞서 채팅 문서에서 설명했다. 아래는 책이 보여 준 두 가지 프롬프트다.

| 프롬프트 | 얻는 것 |
|---|---|
| Summarize this issue | 이슈 요약 |
| Suggest next steps for this issue | 다음에 할 일 제안 |

그 밖에 더 자세한 내용을 달라고 하거나 주요 요점을 묻는 식으로 이어 갈 수 있다.

## 4. 결과를 믿기 전에

AI의 출력은 늘 그렇듯 요약이 정확한지 확인할 책임은 사용자에게 있다. Copilot의 이슈 요약은 중요할 수 있는 미묘한 차이나 세부 사항을 놓칠 수 있다.

또 생성형 AI는 결정적이지 않아서 같은 요청이어도 응답의 상세 수준이 크게 달라질 수 있다. 어떤 때는 일반적인 안내가 오고, 어떤 때는 훨씬 구체적인 안내가 온다.

| 주의할 점 | 대응 |
|---|---|
| 세부 사항 누락 가능 | 중요한 이슈는 원문과 대조한다 |
| 응답 상세도가 들쭉날쭉 | 부족하면 더 자세히 달라고 다시 묻는다 |

## 5. 쓰는 요령

- 긴 이슈를 처음 받으면 요약부터 시킨다.
- 다음 단계 제안은 방향을 잡는 참고로 쓰고, 최종 판단은 사람이 한다.
- 요약을 팀에 공유할 때는 원문과 맞는지 한 번 확인한다.
