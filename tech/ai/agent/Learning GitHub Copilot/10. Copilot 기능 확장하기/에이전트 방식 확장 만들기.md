# 에이전트 방식 확장 만들기

에이전트 방식은 요청을 어떻게 처리하고 응답을 어떻게 만들지 직접 통제하고 싶을 때 고르는 구현이다. 사용자 지정 로직을 넣고, 다른 LLM이나 Copilot API와 연동하고, 채팅 대화의 컨텍스트(문맥)를 돕고, 상호작용 전체를 관리할 수 있다. 대신 만들고 유지하기가 더 복잡하다. 이 문서는 @meta-files라는 예제 확장을 통해 코드의 핵심, 서버 띄우기, GitHub App 설정, 첫 사용 승인까지의 전 과정을 정리한다.

---

## 1. 예제: @meta-files

프롬프트에 프로그래밍 언어 이름을 쓰면 그 언어에 맞는 .gitignore와 .gitattributes 예시 파일을 만들어 주는 확장이다. 오픈 소스 라이선스 이름을 쓰면 그 라이선스 예시 파일을 만든다. 라이선스에 이름과 현재 연도를 넣는 자리가 있으면 채워 넣으려고 시도하고, 그 라이선스가 어떤 경우에 유용한지에 대한 안내도 함께 준다.

| 호출 | 결과 |
| --- | --- |
| `@meta-files Python` | Python용 .gitignore, .gitattributes 예시 |
| `@meta-files MIT` | MIT 라이선스 예시와 사용 안내 |

코드는 Copilot 확장 예제를 바탕으로 했고 책의 GitHub 저장소에서 볼 수 있다.

### 에이전트 확장의 동작 흐름

| 순서 | 일어나는 일 |
| --- | --- |
| 1 | 사용자가 채팅에서 프롬프트를 보낸다 |
| 2 | GitHub App을 거쳐 서버의 엔드포인트로 페이로드(payload)가 들어온다 |
| 3 | 코드가 프롬프트에 지시를 덧붙여 AI가 무엇을 찾아야 할지 알려 준다 |
| 4 | 덧붙인 프롬프트를 기반 LLM에 보내 응답을 받는다 |
| 5 | 응답을 채팅 창으로 돌려준다 |

---

## 2. 프로젝트 파일 구성

예제는 JavaScript로 작성했지만, 확장은 거의 모든 최신 언어로 만들 수 있다. 이 단순한 예제의 핵심 파일은 package.json과 index.js 두 개뿐이다. package.json의 내용은 다음과 같다(핵심 줄만).

```json
{
  "name": "metafiles-extension",
  "private": "true",
  "scripts": {
    "start": "node index.js",
    "dev": "node --watch index.js"
  },
  "type": "module",
  "dependencies": {
    "@octokit/core": "^6.1.2",
    "express": "^4.19.2"
  }
}
```

구조는 이런 파일의 표준 틀이다. 설명이 필요한 것은 의존성(dependencies) 둘뿐이다.

| 의존성 | 역할 |
| --- | --- |
| Express | 간단한 백엔드 웹 애플리케이션 프레임워크. Node.js로 웹 앱과 API를 쉽게 만들게 해 준다. 에이전트 확장은 사실상 GitHub App을 통해 노출되는 엔드포인트를 가진 웹 앱을 만드는 일이다 |
| Octokit | GitHub가 제공하는 라이브러리 모음으로, 코드에서 GitHub의 REST API와 GraphQL API를 쓰게 해 준다. 작업 자동화와 저장소 관리, 풀 리퀘스트(PR)나 이슈 같은 자원을 코드로 다룰 수 있다. 여기서는 사용자 정보를 얻는 토큰을 가져와 다루는 데 쓴다 |

---

## 3. index.js의 핵심: 프롬프트 덧붙이기

주 로직은 index.js에 있다. 위쪽에서 필요한 모듈을 가져오고, Express 앱을 시작하고, 환영 메시지를 게시한 다음 본 처리로 들어간다. 본 처리는 Octokit으로 토큰을 얻은 뒤 표준 순환을 따른다.

1. 채팅 창에서 (GitHub App을 거쳐) 들어온 페이로드를 받는다.
2. AI에게 무엇을 찾아야 하는지 알려 주도록 프롬프트를 보강한다.
3. 보강한 프롬프트를 기반 LLM에 보내 응답을 받는다.
4. 응답을 채팅 창에 넘긴다.

기계적인 부분은 어렵지 않다. 진짜 핵심은 두 번째 단계, 프롬프트 보강이다. 코드는 다음과 같은 형태로 시스템 메시지를 앞에 끼워 넣는다(줄여서 옮긴 것이다).

```javascript
const messages = payload.messages;
messages.unshift({
  role: "system",
  content: "Search for a programming language name ... generate
   example .gitignore and .gitattributes files ...",
});
messages.unshift({
  role: "system",
  content: "Search for an open source software license name ...
   replace [YEAR] with the current year.",
})
```

첫 번째 시스템 메시지는 사용자 글에서 프로그래밍 언어 이름을 찾고, 있으면 그 언어의 .gitignore와 .gitattributes 예시를 만들라고 지시한다. 두 번째는 오픈 소스 라이선스 이름, 종류, 약어를 찾아서, 있으면 라이선스의 핵심 요점과 쓰면 좋은 경우와 쓰지 말아야 할 경우를 알려 주고, 예시 LICENSE 파일을 만들라고 한다. 파일에 [NAME]이나 [YOUR NAME]이 있으면 사용자 이름(코드에서는 user.data.name)으로, [YEAR]가 있으면 현재 연도로 바꾼다.

핵심은 에이전트 확장이 잘 동작하느냐가 LLM에게 주는 상세한 프롬프트에 달렸다는 것이다. 무엇에 주목하고 어떤 출력을 원하는지 알려 주는 일인데, ChatGPT 같은 모델과 직접 대화할 때와 비슷하다. 프롬프트가 구체적일수록 응답도 좋아진다. 결국 에이전트 코드의 논리는 좋은 프롬프트를 만드는 일로 귀결된다.

좋은 프롬프트를 쓰는 안내서는 많다. 결국 가장 좋은 프롬프트는 의도한 대로 알맞은 정보를 뽑아내고 의미 있는 응답을 돌려주는 프롬프트다. 간단한 방법은 먼저 Copilot Chat(또는 AI 모델)에서 직접 프롬프트를 시험하고 다듬은 뒤, 잘 되는 것을 확장 코드에 넣는 것이다.

## 4. 프로덕션으로 가려면: Copilot extensions SDK

여기까지가 확장에 필요한 핵심 코드다. 다만 이 코드는 비프로덕션 환경에서 만든 것이고, 실제 서비스에 올리려면 더 많은 구현이 필요하다. 이를 줄이기 위해 GitHub는 프로덕션 확장에 필요한 핵심 기능 일부를 구현한 SDK를 내놨다. 책을 쓰던 시점에는 알파 릴리스였고, 에이전트로 구현한 확장에만 쓸 수 있었다. 프리뷰 SDK(Preview SDK)라고도 부른다.

| SDK가 자동화하는 일 | 설명 |
| --- | --- |
| 요청 페이로드 검증 | 들어오는 요청이 유효하고 안전한지 확인한다 |
| 페이로드 파싱 | 요청에서 필요한 데이터를 쉽게 뽑는다 |
| 응답 구성 | Copilot Chat과 호환되는 형식으로 응답을 만든다 |
| API 상호작용 간소화 | 반복되는 연동 코드 없이 외부 도구, API, 데이터 소스를 Copilot Chat에 연결하게 돕는다 |

이런 반복 작업을 SDK가 맡아 주면 개발자는 확장의 핵심 기능에 집중할 수 있다. SDK 코드는 GitHub의 Copilot 확장 영역에 있다. 아직 개발 초기라서 이 책은 사용법까지 다루지 않고, 프로젝트의 README.md에 흔한 작업의 기본 예제가, examples 폴더에 기본 예제 몇 개가 있다고만 안내한다.

## 5. 서버 띄우기: Codespace 활용

완성하려면 서버와 앱이 필요하다. 이 예제는 GitHub Codespace를 런타임 환경 겸 엔드포인트 서버로 쓴다. 프로덕션에서 쓸 방법은 아니지만 데모와 테스트에는 과정이 많이 단순해진다. ngrok 같은 서비스를 써도 된다. 저장소에서 codespace를 만드는 절차는 문서에 나와 있고, codespace가 시작되면 서버를 띄우는 데 필요한 명령은 둘뿐이다.

```bash
npm install
npm start
```

이 코드는 node 앱이고 npm은 이를 실행하는 node 도구다. 이렇게 하면 codespace에서 포트 3000으로 서버가 돌아간다. GitHub App을 설정하기 전에 두 가지를 해 둔다.

| 순서 | 할 일 | 방법 |
| --- | --- | --- |
| 1 | 포트를 비공개에서 공개로 바꾸기 | codespace의 Ports 탭에서 목록의 포트를 우클릭해 Port Visibility를 Public으로 바꾼다(그림 10-14) |
| 2 | 서버 주소 복사하기 | 같은 위치에서 포트 주소를 복사한다(그림 10-15) |

codespace가 어떻게 구성되고 서버가 어떻게 시작되고 포트가 어떻게 정해지는지 궁금하면 저장소의 .devcontainer/devcontainer.json과 .vscode/launch.json 파일을 보면 된다.

이 장의 예제는 코드 작성, 간단한 서버 구성, 사용자별 에이전트 구현이 모두 데모용이다. 프로덕션 수준으로 바꾸려면 보안, 호스팅 등의 기능을 더해야 한다.

## 6. GitHub App 만들고 설정하기

코드와 서버가 준비됐으니 대응하는 GitHub App을 만들어 설정한다.

### 앱 등록(General 페이지)

codespace를 실행한 계정과 같은 ID로 GitHub에 로그인한 다음 개발자 설정에서 새 앱을 만든다. 바로 가기 주소는 `https://github.com/settings/apps/new`이다. 필수 항목은 다음과 같다.

| 항목 | 입력할 내용 |
| --- | --- |
| App Name | 고유한 이름. Copilot Chat에서 확장을 부를 때 쓰는 이름이다. 예를 들어 my-app이라고 하면 채팅에서 @my-app으로 부른다 |
| Homepage URL | 앱이나 확장을 소개하는 웹 페이지 주소. 없으면 확장 저장소 링크나 `https://github.com`도 된다 |
| Callback URL | codespace에서 공개로 바꾼 포트의 공개 URL. 확장이 코드와 응답을 주고받으려면 꼭 있어야 하며, URL 끝에 /callback을 덧붙인다 |
| Webhooks 등 기타 선택 항목 | 이 예제에서는 끈다 |
| 공개 범위 | 개발과 테스트 동안은 본인만 쓰게 하고, 공유할 준비가 되면 공개로 바꾼다(그림 10-16) |

입력을 마치고 Create GitHub App을 눌러 등록을 끝낸다.

### 개인 키 만들기

앱을 설치하고 액세스 토큰에 서명하려면 개인 키(private key)가 필요하다. GitHub가 키를 만들고 내려받는 링크를 제공하며, 키는 앱 설정에 자동으로 추가된다(그림 10-17).

### 권한 설정(Permissions & Events 페이지)

General 페이지에서 앱을 만든 뒤에는 왼쪽 메뉴로 설정을 더 해야 한다. 개발과 테스트용으로 반드시 설정할 것은 Account Permissions 구역의 Copilot Chat을 읽기 전용(read-only)으로 주는 것 하나뿐이다. 변경 사항을 저장한다(그림 10-18).

### Copilot 설정 페이지

| 항목 | 설정 |
| --- | --- |
| App Type | Disabled에서 Agent로 바꾼다(에이전트로 구현하므로) |
| URL | codespace의 공개 URL을 붙여 넣는다 |
| Inference description | 에이전트의 목적을 사용자가 이해하도록 짧게 설명한다. 채팅 영역에서 확장의 슬러그(slug)에 마우스를 올리면 표시된다 |

작성하고 저장하면 된다(그림 10-19). 이상이 앱이 에이전트와 함께 동작하는 데 필요한 모든 필수 설정이다. 나머지 페이지는 다음과 같다.

| 페이지 | 용도 |
| --- | --- |
| Optional Features | 토큰 만료를 쓰지 않도록 선택하는 것만 있다 |
| Advanced | 소유권 이전, 앱 삭제, 공개 전환 같은 위험 구역(Danger Zone) 옵션을 다룬다 |
| Install App | 개인 또는 조직 계정에 테스트용으로 앱을 설치한다 |

## 7. 첫 사용 승인

앱을 설치한 뒤 확장을 처음 쓰려 하면 계속하려고 접근을 승인하라는 안내가 나온다(그림 10-20). Connect 버튼을 누르면 앱이 관련 자원에 접근하는 것을 승인하라는 화면이 이어진다(그림 10-21). 승인이 끝나면 앞서 본 것처럼 확장을 쓸 수 있다.

에이전트 외에 확장을 만드는 다른 방법이 스킬셋이다. 실시간의 특정 정보를 가져오거나 간단한 API 처리를 쉽게 하는 데 적합하다. 코드 구현은 더 단순하지만 앱 설정은 더 복잡하다. 다음 문서에서 자세히 본다.
