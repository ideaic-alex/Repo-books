# 멀티 클라우드 모델 제공자 전략

기업 안에서도 팀마다 처한 제약이 다르다. Codex CLI는 모델 호출 경로를 정책 등급별로 달리 줄 수 있어서, 별도의 프록시 인프라 없이도 멀티 클라우드 라우팅이 된다. 이 문서는 제공자 구성 방법, 인증, 온프레미스 선택지, 클라우드와 자체 호스팅의 득실을 다룬다.

---

## 1. 어떤 제공자를 쓸 수 있나

Codex CLI에는 직접 OpenAI API 제공자와 함께 `amazon-bedrock` 제공자가 내장되어 있고, Azure OpenAI는 사용자 정의 제공자로 연결한다. 이 조합이 서드파티 프록시를 세우지 않고도 진짜 멀티 클라우드 모델 라우팅 계층을 만들어 준다.

눈에 띄는 빈자리는 Google Cloud다. Vertex AI는 OpenAI 모델이 아니라 Gemini와 Anthropic 모델을 서비스하므로 Codex CLI용 Vertex 제공자는 없다. Google Cloud로 표준화한 팀은 직접 OpenAI API로 가거나, 사용자 정의 제공자로 정의한 OpenAI 호환 엔드포인트를 쓴다.

## 2. 왜 멀티 클라우드가 필요한가

사업 부문마다 제약이 다르기 때문이다.

- EU 데이터 거주 요건 아래에서 일하는 팀은 계약상 Azure의 유럽 리전에 묶일 수 있다.
- 청구를 통합한 AWS 팀은 Bedrock을 선호할 수 있다.
- 연구 그룹은 최신 모델을 첫날부터 쓰려고 직접 OpenAI API를 원할 수 있다.

## 3. 정책 등급별 라우팅

관리형 `requirements.toml` 인프라는 그룹별 모델 엔드포인트 설정을 지원한다. 각 정책 등급이 `model_provider` 하나를 정한다.

```toml
model_provider = "amazon-bedrock"   # AWS 중심 팀: 내장 Bedrock 제공자
# model_provider = "azure"          # EU 규제 팀: Azure OpenAI(아래에서 정의하는 사용자 정의 제공자)
# model_provider = "openai"         # 연구 팀: 최신 모델을 위한 직접 OpenAI API
```

내장된 `openai`와 `amazon-bedrock`은 따로 정의할 필요가 없다. Bedrock은 중첩된 AWS 덮어쓰기 값만 받는다. Azure OpenAI는 사용자 정의 제공자로 연결한다.

```toml
[model_providers.amazon-bedrock.aws]
region = "eu-central-1"
[model_providers.azure]
name = "Azure OpenAI"
base_url = "https://YOUR_RESOURCE.openai.azure.com/openai"
env_key = "AZURE_OPENAI_API_KEY"
query_params = { api-version = "2025-04-01-preview" }
wire_api = "responses"
```

그림의 왼쪽이 `requirements.toml`의 정책 등급이고, 오른쪽이 팀별로 연결되는 제공자다. AWS 중심 팀은 청구 통합 때문에 내장 `amazon-bedrock`으로, EU 규제 팀은 EU 데이터 거주 때문에 Azure OpenAI 사용자 정의 제공자로, 연구 팀은 최신 모델을 첫날부터 쓰려고 직접 OpenAI API로 간다. 엄격한 데이터 주권 요건을 가진 팀은 `base_url`로 지정한 온프레미스 로컬 엔드포인트로 가서 데이터가 네트워크 밖으로 나가지 않는다.

## 4. 인증

제공자마다 고유한 인증 방식을 쓴다.

| 제공자 | 인증 |
|---|---|
| Azure OpenAI | API 키 또는 Entra ID 토큰 |
| Bedrock | IAM 역할(AWS 프로필과 리전 경유) |
| 직접 OpenAI API | API 키 또는 OAuth |

CLI는 각 제공자의 표준 자격 증명 체인을 따라 환경에서 자격 증명을 찾는다.

## 5. 온프레미스 선택지

데이터 주권 요건이 엄격한 조직에는 호환 하드웨어(예를 들어 NVIDIA GB10 기반 시스템)에서 돌리는 온프레미스 추론이 길을 열어 준다. 데이터가 기업 네트워크 경계를 벗어나지 않는다. Codex CLI는 사용자 정의 제공자 정의의 `base_url` 키로 로컬 엔드포인트를 가리키게 설정한다.

## 6. 클라우드 대 자체 호스팅

흔한 "직접 만들까, 살까"의 축에 데이터 거주라는 차원이 하나 더 붙는다.

| 구분 | 내용 |
|---|---|
| 클라우드의 장점 | 인프라를 관리하지 않고 가장 높은 성능의 모델을 쓴다. 업데이트가 투명하고 운영 부담이 없다. 데이터 처리 계약을 맺은 규제 산업을 포함해 대부분의 조직에서는 이쪽이 맞는 기본값이다 |
| 자체 호스팅의 장점 | 데이터가 네트워크 경계를 떠나지 않는다. 모델 버전을 완전히 통제한다. 가장 엄격한 데이터 거주 규제를 만족한다 |
| 자체 호스팅의 비용 | GPU 인프라는 비싸다. 오픈 웨이트 모델의 품질은 대부분의 소프트웨어 엔지니어링 작업에서 아직 최전선 모델에 못 미친다. 모델 서빙 스택과 그 의존성, 업데이트 주기를 직접 떠안는다 |

"자체 호스팅"이 곧 "규정 준수"는 아니다. 클라우드 제공자의 GPU 인스턴스에서 자체 호스팅 모델을 돌리면 데이터는 여전히 그 제공자에게 간다. 자체 호스팅을 근거로 배포를 확정하기 전에 법무와 컴플라이언스 팀과 먼저 상의해야 한다.
