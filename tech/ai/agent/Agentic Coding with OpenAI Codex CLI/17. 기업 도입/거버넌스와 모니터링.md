# 거버넌스와 모니터링

파일럿에서 전사 배포로 넘어가면 질문이 "이게 되나?"에서 "잘못했을 때 누가 책임지나?"로 바뀐다. 이 문서는 거버넌스를 이루는 세 요소, 3단계 가드레일 파이프라인, 그리고 데이터를 세 층으로 나누는 모니터링 모델을 정리한다.

---

## 1. 거버넌스 체계의 세 요소

쓸 만한 거버넌스 체계는 세 가지 구성 요소로 이뤄진다.

**코드로서의 정책(policy as code).** 조직의 Codex CLI 정책은 버전 관리되는 파일(`config.toml`, `AGENTS.override.md`)로 두고, 인프라 코드와 같은 리뷰와 승인 절차를 거치게 한다. 그러면 정책 변경을 감사할 수 있고, 되돌릴 수 있고, 적용되기 전에 리뷰할 수 있다.

**감사 추적(audit trail).** 세션마다 실행한 명령, 수정한 파일, 시도한 네트워크 요청의 기록이 남는다. 최소한 다음은 기록해야 한다.

- 세션 시작 시각과 사용자 신원
- 모든 셸 명령과 그 종료 코드
- 모든 파일 쓰기와 대상 경로
- 시도된 모든 네트워크 연결

**승인 워크플로(approval workflow).** 운영에 치명적인 경로를 건드리는 작업에는 작업을 시작한 개발자와 독립된 사람 검토 지점이 필요하다. 특정 경로를 건드리는 PR에 두 번째 승인자를 요구하거나(CODEOWNERS 이용), 가장 위험한 범주에는 정식 변경 자문 위원회(CAB) 절차를 쓴다.

## 2. 3단계 가드레일 파이프라인

에이전트 거버넌스의 참조 아키텍처는 세 단계로 이뤄진다.

| 단계 | Codex CLI에서의 대응 | 강제 계층 |
|---|---|---|
| 사전 점검(Pre-flight) | `requirements.toml` 제약 | 관리자가 관리하며 변경 불가 |
| 입력(Input) | `UserPromptSubmit`과 `PreToolUse` 훅 | 절차적, 스크립트 기반 |
| 출력(Output) | `PostToolUse` 훅과 감사 추적 | 관찰 중심, 감사 가능 |

그림은 왼쪽에서 오른쪽으로 흐르는 세 단계를 보여 준다. 사전 점검 단계는 관리자가 관리하는 변경 불가능한 `requirements.toml` 제약으로 넓은 범위의 위반을 정적 정책으로 잡는다. 입력 단계는 `UserPromptSubmit`과 `PreToolUse` 훅으로 런타임 위반을 잡는다. 출력 단계는 `PostToolUse` 훅과 감사 추적으로 관찰을 담당하고, 마지막에는 조사를 위한 증거 기록이 남는다.

이 파이프라인은 거버넌스를 여러 계층에 나눠 맡긴다. 정적 정책은 넓은 위반을 걸러 내고, 훅은 실행 중에 생기는 위반을 잡고, 감사 추적은 사후 조사의 증거가 된다.
## 3. 3계층 모니터링 모델

기업 배포는 성격이 다른 세 가지 데이터 흐름을 만든다.

| 계층 | 수단 | 담당 | 목적 |
|---|---|---|---|
| 셀프 서비스 가시성 | 분석 대시보드 | 엔지니어링 리드 | 도입 지표, 팀별 사용량 |
| 자동 보고 | Analytics API | 플랫폼 팀 | 일 단위 시계열, 데이터 웨어하우스 적재 |
| 감사와 조사 | Compliance API | 보안/법무 | 변경 불가능한 로그, SIEM 적재 |

세 데이터는 답하는 질문이 다르다. 분석 이벤트는 누가 Codex CLI를 얼마나 쓰는지 알려 준다. OpenTelemetry로 내보내는 실시간 관측 추적은 지금 무슨 일이 벌어지는지 알려 준다. 컴플라이언스 내보내기는 정확히 무슨 일이 있었는지를 기록으로 남겨 준다. 마지막 것은 고칠 수 없다.

실시간 관측을 위한 OpenTelemetry 추적 내보내기는 `config.toml`에 이렇게 켠다.

```toml
# 실시간 관측을 위한 OpenTelemetry 추적 내보내기 켜기
[otel]
environment = "prod"
exporter = "otlp-grpc"
[otel.exporter.default]
endpoint = "https://otel-collector.internal:4317"
```

각 계층에 담당자를 정해 두는 것이 이 모델의 핵심이다. 대시보드, API, 이벤트 파이프라인의 주인이 없으면 데이터는 쌓여도 아무도 보지 않는다.
