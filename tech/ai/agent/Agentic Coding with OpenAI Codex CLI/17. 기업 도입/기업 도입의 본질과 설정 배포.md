# 기업 도입의 본질과 설정 배포

16장은 보안을 개발자 한 사람의 작업 환경과 프로젝트 경계 단위로 다뤘다. 개발 조직이 수십 개 팀, 수백 개 저장소, 모든 커밋에 걸친 컴플라이언스 의무를 가지는 단계가 되면 그것만으로는 모자란다. 기업 도입은 보안 위에 세 가지 고민을 더 얹는다. 설정을 대규모로 배포하고 강제하는 일, 에이전트가 할 수 있는 일을 통제하고 나중에 증명하는 일, 이 모든 것이 들인 돈만큼 값어치가 있는지 재는 일이다.

이 문서는 장 전체의 관점을 잡고, 그중 가장 쉬운 부분인 `config.toml` 배포 방식을 정리한다.

---

## 1. 이 장의 학습 목표

이 장을 읽고 나면 다음을 할 수 있어야 한다.

- 여러 팀에 걸쳐 설정을 배포하고 관리형 정책을 강제한다.
- 관찰에서 시작해 자율 사용까지 안전하게 넘어가는 3단계 온보딩 프로그램을 짠다.
- 과장 없이 엔지니어링 리더십을 설득할 수 있는 ROI 지표를 정의한다.
- 멀티 클라우드 제공자 라우팅 전략을 설계한다.
- 감사 추적과 승인 워크플로를 갖춘 거버넌스 체계를 세운다.
- 기업 도입이 흔히 실패하는 방식을 진단하고 각각에 구조적인 해법을 적용한다.

## 2. 기업 도입이 실제로 다루는 문제

이 장을 설정 작업으로만 읽고 싶은 유혹이 있다. 알맞은 `config.toml`을 뿌리고, `requirements.toml`을 쓰고, SCIM을 연결하고 끝내는 식이다. 이런 장치는 중요하고 뒤에서 모두 다루지만 쉬운 쪽이다. MDM 프로필이나 Ansible 인벤토리를 이미 갖고 있다면 설정 배포는 사실상 풀린 문제다.

어려운 쪽은 28장이 팀(pod) 단위로 짚은 문제와 같다. 에이전트가 예전보다 훨씬 많은 변경을 만들어 내면 병목은 코드를 만드는 일에서 코드를 믿는 일로 옮겨 간다. 기업 규모에서 이 병목은 정책 파일 하나로는 답할 수 없는 세 질문으로 나타난다.

| 질문 | 따져 볼 내용 |
|---|---|
| 책임 | 에이전트가 만든 결함이 운영에 나갔을 때 누가 책임지는가 |
| 증거 | 에이전트가 무엇을 요청받았고 무엇을 했는지 사후에 증명할 수 있는가 |
| 리뷰 용량 | 리뷰 용량이 생성 용량만큼 빠르게 늘고 있는가, 아니면 리뷰되지 않은 에이전트 산출물의 위험이 조용히 쌓이고 있는가 |

관리형 정책, RBAC, 감사 추적은 목표가 아니라 도구다. 조직이 위 세 질문(책임, 증거, 리뷰 용량)에 규모 있게 답하기 위한 수단이다. 설정은 완벽하게 해 놓고 세 질문을 무시하는 배포가, 시범 운영 뒤에 에이전트 프로그램이 멈추는 가장 흔한 경로다. 이어지는 문서를 읽을 때 이 세 질문을 계속 머리에 두면 좋다.

## 3. 설정을 대규모로 배포하기

`config.toml`은 설정이 없는 Codex CLI 설치본에 조직의 모양을 입힌다. 모델, 승인 정책, 네트워크 샌드박스, 토큰 예산, 신뢰하는 도구 제공자가 여기 들어간다. 혼자 쓸 때는 한 번 고치면 끝이다. 기업에서는 모든 개발자의 파일이 같은 기준선을 반영해야 하고, 변경 사항이 머신마다 지원 요청을 받지 않고도 퍼져 나가야 한다.

대부분의 조직은 세 가지 배포 방식 중에서 고른다.

| 방식 | 동작 | 강점과 한계 |
|---|---|---|
| MDM(모바일 기기 관리) | 첫 로그인 때 `~/.codex/config.toml`을 쓰는 패키지를 배포한다 | 강제력이 있지만 입자가 거칠다. 승인 정책, 네트워크 샌드박스 규칙, 모델 엔드포인트처럼 타협할 수 없는 기준선에 쓴다 |
| 도트파일 저장소 | 공유 dotfiles 저장소에 `codex/config.toml` 템플릿을 둔다 | 부담이 적고 버전 관리가 되지만 강제가 아니라 권고에 그친다 |
| 구성 관리(Ansible, Chef, Puppet) | 대상 머신에 `config.toml`을 템플릿으로 찍어 낸다 | OS가 섞인 환경에서 유연성과 감사 가능성의 조합이 가장 좋다. 팀, 환경, 컴플라이언스 등급별로 값을 매개변수화한다 |

어떤 방식을 고르든 원칙은 하나다. 기준선은 최소로 유지한다. 반드시 잠가야 하는 것만 잠근다. 네트워크 외부 통신(egress), 파괴적 작업에 대한 승인 정책, 데이터 거주(residency) 때문에 정해야 하는 모델 엔드포인트가 그 예이고, 나머지는 팀의 재량에 맡긴다. 설정을 지나치게 중앙에 모으면 사람들이 우회로를 만든다. 이 우회로 문제는 뒤의 "다섯 가지 실패" 문서에서 섀도 AI로 다시 나온다.
