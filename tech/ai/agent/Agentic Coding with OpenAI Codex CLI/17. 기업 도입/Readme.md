# 기업 도입

혼자 쓰던 Codex CLI를 수십 개 팀과 수백 개 저장소를 가진 조직에 넓힐 때는 보안 말고도 세 가지가 더 필요하다. 설정을 대규모로 배포하고 강제하는 일, 에이전트가 할 수 있는 일을 통제하고 사후에 증명하는 일, 들인 비용이 값어치가 있는지 재는 일이다. 이 장은 그 세 가지를 차례로 다루고, 확대 배포 전에 쓸 점검표로 끝난다.

다만 설정 배포는 쉬운 부분이다. 진짜 어려움은 에이전트가 만든 변경을 조직이 믿을 수 있느냐에 있다. 누가 책임지는지, 무슨 일이 있었는지 증명할 수 있는지, 리뷰 용량이 생성 속도를 따라가는지가 이 장 전체를 꿰는 질문이다.

---

## 1. 핵심 요점

- 기업 도입의 병목은 설정이 아니라 신뢰다. 책임, 증거, 리뷰 용량 세 질문에 답하는 도구로서 정책과 감사 장치를 쓴다.
- 설정은 MDM, 도트파일 저장소, 구성 관리로 배포한다. 기준선은 최소로 두고 꼭 잠가야 하는 것만 잠근다.
- 클라우드 관리형 `requirements.toml`은 로컬 `config.toml`이 덮어쓸 수 없다. `AGENTS.override.md`는 강한 기본값일 뿐 강제 경계가 아니다.
- IdP의 Codex Admins 그룹을 SCIM으로 동기화해 접근 등급을 자동화하고, 10~20명 파일럿에서 30~50명 단위로 넓힌다.
- 온보딩은 관찰, 안내된 자율, 자율 운영의 3단계로 하고 단계마다 회고한다.
- ROI는 절약 시간 대신 개입 없이 끝난 작업 비율, 리뷰 통과율, 저작 방식별 결함 유출률로 잰다.
- 정책 등급별 `model_provider`로 Bedrock, Azure OpenAI, 직접 OpenAI API, 온프레미스 엔드포인트를 나눠 라우팅한다.
- 거버넌스는 코드로서의 정책, 감사 추적, 승인 워크플로이고, 섀도 AI, 정책 연극, 리뷰 병목, 라이선스 낭비, 책임 공백은 구조로 푼다.
