# 기업 도입이 실패하는 다섯 가지 방식과 점검표

앞에서 본 장치들은 필요하지만 충분하지는 않다. 도중에 멈추는 프로그램은 설정 때문에 실패하는 일이 드물다. 대개 다섯 가지 반복되는 방식으로 실패하고, 각각에는 도구가 아니라 구조로 푸는 해법이 있다. 문서 끝에는 확대 배포 전에 훑어볼 점검표를 붙였다.

---

## 1. 섀도 AI

공식 도구를 너무 세게 잠그면 개발자들은 우회한다. 개인 챗봇에 코드를 붙여 넣거나, 사이드 프로젝트에서 승인받지 않은 CLI를 돌린다. 이쪽이 느슨한 정책보다 나쁘다. 조직이 보지도, 통제하지도, 감사하지도 못하는 에이전트 지원 코드가 생기기 때문이다.

해법은 더 강한 통제가 아니라, 공식 경로가 진짜로 가장 편한 길이 되게 하는 것이다. 금지 사항 하나하나를 승인된 대안을 내놓으라는 신호로 읽는다. `curl` 대신 egress 프록시, 아무 데서나 설치하는 대신 사내 패키지 미러를 주는 식이다. 그러면 규정을 지키는 길이 곧 쉬운 길이 된다.

## 2. 정책 연극(policy theatre)

겉보기에 완벽한 `requirements.toml`이 있어도 실제로는 집행되지 않을 수 있다. `AGENTS.override.md`는 권고일 뿐이고, 훅은 우회할 수 있고, 감사 로그를 읽는 사람이 없는 경우다. 서류상의 컴플라이언스는 실제 컴플라이언스가 아니다.

해법은 통제마다 어느 계층이 집행하는지 아는 것이다. 변경 불가능한 관리형 정책인지, 절차적 훅인지, 사후 감사인지 구분한다. 이것이 거버넌스 문서에서 본 파이프라인의 세 단계다. 통제를 갖췄다고 말하기 전에, 집행하는 계층이 실제로 동작하는지 확인한다.

## 3. 리뷰 병목

25장의 벤치마크가 수치로 보여 주는 실패다. 에이전트를 쓰면 풀 리퀘스트가 나오기까지의 시간은 크게 줄지만, 리뷰어 용량은 생성 용량만큼 늘지 않아서 PR이 리뷰에서 훨씬 오래 머문다. 도입률과 속도만 재는 기업은 빨라진 것을 자축하는 동안 리뷰되지 않은 물량과 그 안에 든 위험이 복리로 불어난다.

해법은 리뷰 처리량을 관리 대상 제약으로 삼는 것이다(28장). 생성한 변경과 리뷰를 마친 변경의 비율을 추적한다. 생산성에서 얻은 여유는 더 많은 산출물에만 쓰지 말고 검증에도 쓴다.

## 4. 라이선스 낭비

대부분의 기업 도입에서 구매한 좌석의 상당 부분이 쓰이지 않는다. 구매는 조직 전체 기준으로 하는데 실제 사용은 몇몇 팀에 몰린다(수치는 25장에서 인용한다).

해법은 라이선스를 밀어 넣지 말고 도입이 끌어당기게 하는 것이다. 3단계 온보딩을 마친 팀에 좌석을 주고, 분석 대시보드를 보면서, 인원 수 예측이 아니라 실제 사용 실적을 보고 넓힌다.

## 5. 책임 공백

에이전트가 쓴 변경이 사고를 일으켰을 때 "누구 책임인가?"에 깔끔한 답이 없는 경우가 많다. 변경이 사람이 아니라 도구의 것으로 기록됐기 때문이다. 코딩 에이전트는 책임을 질 수 없다. 지시하고 머지한 엔지니어가 진다.

해법은 구조적이다. 에이전트가 관여한 모든 변경에 저작 메타데이터를 남기고(ROI 측정에서 본 커밋 트레일러나 PR 라벨), 운영에 치명적인 경로를 건드리는 변경에는 기록상의 담당 사람 리뷰어를 지정한다. 그리고 에이전트 산출물을 머지하는 행위는 저작 행위이고 그에 따른 책임이 따른다는 원칙을 분명히 한다.

## 6. 롤아웃 점검표

확대 배포 전에 아래 항목이 준비됐는지 확인한다.

| 영역 | 준비 상태 지표 |
|---|---|
| RBAC 구성 | IdP에 관리자 그룹을 만들고 SCIM으로 동기화했다 |
| 관리형 정책 | `requirements.toml` baseline을 작성하고 파일럿 그룹에서 테스트했다 |
| TLS 구성 | TLS 프록시 환경을 위한 CA 인증서를 설정했다 |
| 권한 잠금 | 제한 대상 팀에 `request_permissions = false`를 설정했다 |
| 멀티 클라우드 제공자 | 정책 등급별로 제공자 라우팅을 구성하고 모델 버전을 고정했다 |
| 설정 덮어쓰기 | `AGENTS.override.md`를 작성해 MDM/Ansible로 배포했다 |
| 컴플라이언스 파이프라인 | 감사 로그를 SIEM에 적재하도록 구성했다 |
| 분석 담당 | 대시보드, API, 이벤트 파이프라인의 담당자를 정했다 |
| 온보딩 프로그램 | 3단계 계획과 회고 일정을 문서로 남겼다 |
| ROI 지표 | 저작 태깅 규칙을 세우고 기준선 측정값을 정의했다 |
