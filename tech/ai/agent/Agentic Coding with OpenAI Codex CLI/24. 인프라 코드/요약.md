# 요약

24장은 Run or Relax를 Cloud Run과 Cloud Storage에 올리면서, 인프라 코드를 다룰 때 에이전트를 어디까지 믿고 어디서 멈추게 할지 정리한 장이다. 열세 가지 요점을 주제별로 풀어 둔다.

---

## 1. 경계와 안전장치

1. **인프라에는 더 엄격한 제약이 필요하다.** 인프라 저장소의 AGENTS.md는 애플리케이션용보다 촘촘해야 하고, 무엇보다 `apply`, `destroy`, 직접적인 `gcloud run deploy`를 명시적으로 금지해야 한다.
2. **기본값은 읽기 전용이다.** 계획 검토에는 읽기 전용 샌드박스 모드를, 작성에는 `untrusted` 승인과 `workspace-write`를 써서 모든 파일 쓰기에 관문을 둔다.
3. **계획 검토가 가장 가치 큰 패턴이다.** 계획을 만들고, 에이전트가 위험을 검토하게 하고, 사람이 적용한다. 에이전트가 적용 경계의 안전한 쪽에만 머무른다.
4. **에이전트는 제안하고 사람이 적용한다.** 이것이 장 전체가 지키는 경계다. AGENTS.md의 금지는 이를 말로 밝히지만 프롬프트 지시는 권고일 뿐이다. `terraform apply`, `terraform destroy`, `gcloud run deploy`를 막는 `PreToolUse` 훅이 구속력을 주고, 뒤에서 샌드박스 모드와 사람이 거치는 파이프라인 단계가 받친다.
5. **GitOps는 경계를 구조로 만든다.** 에이전트의 유일한 출력이 Git 커밋이고, 적용은 컨트롤러나 머지로 트리거되는 `terraform apply`가 한다면, 자격 증명이 없는 에이전트는 프롬프트가 어떻든 적용할 수 없다.

## 2. 작업 방식

6. **리팩터링은 변경 없는 계획을 목표로 한다.** 운영에서 리소스 재생성을 일으키는 구조 변경은 리팩터링이 아니다. 리소스 주소를 보존해서 `terraform plan`이 변경 없음을 보이게 하고, Cloud Run URL도 지킨다.
7. **결정적 도구로 루프를 닫는다.** 에이전트가 세션 안에서 tflint와 checkov를 돌려 깨끗하게 종료될 때까지 반복하게 하고, 정당화할 수 있는 예외(웹사이트 버킷과 공개 보드 API가 정당하게 필요로 하는 공개 읽기)만 남긴다. 깨끗한 스캐너 실행은 Goal Mode가 필요로 하는 외부 검증 수단이기도 하므로 루프를 `/goal`(12장)로 자연스럽게 감쌀 수 있다.
8. **배포에는 에이전트가 짐작하지 못하는 전제 조건이 있다.**
   - 사람이 인증하고, 첫 `terraform init` 전에 테라폼 상태 버킷을 만든다(백엔드는 자기 상태가 담길 버킷을 스스로 만들 수 없다).
   - Cloud Run에는 `$PORT`에 바인딩된 시작 명령(한 줄짜리 Procfile)이 필요하다.
   - 첫 이미지 푸시에는 API 활성화와 Artifact Registry 저장소가 필요하므로, 부트스트랩을 별도 단계로 먼저 적용하고 이미지를 빌드한 뒤 나머지를 적용한다.
   - `.gcloudignore`가 빌드 컨텍스트가 불어나는 것을 막는다.
   - 빌드팩 빌더는 프로젝트의 파이썬 버전과 맞아야 한다.
   - 초록색 `terraform validate`가 `init` 성공을 뜻하지 않고, 깨끗한 checkov 실행은 지적 0건이 아니라 설명되지 않은 지적 0건을 뜻한다(표 24-1).
9. **프로바이더 변동에 맞서 생성을 단단히 한다.** 인프라 코드는 에이전트가 가장 많이 환각하는 곳이고, Google 프로바이더의 잦은 변경(`google_cloud_run_v2_service` 이름 변경이 대표적)이 좋은 예다. 동작하는 길을 만든 뒤에 더하는 Terraform MCP 서버가 검증된 프로바이더, 모듈, 정책 문서를 공급하고, `enabled_tools`가 무인 에이전트를 읽기 전용 레지스트리 조회로 묶어 둔다.

## 3. 파이프라인과 운영

10. **CI/CD는 계획에서 멈춘다.** 파이프라인 통합은 풀 리퀘스트의 계획 검토를 중심으로 하며 자동 apply는 하지 않는다. 드리프트 감지는 별도의 정기 2일차 작업으로 돈다.
11. **2일차 운영은 읽고 보고하는 일이다.** 드리프트 감지, 인증서 점검, 컴플라이언스 스캔은 구조화된 보고서를 내는 정기 읽기 전용 `codex exec` 파이프라인으로 돌고, 수정은 사람이 승인하는 별도 단계다.
12. **README로 마무리한다.** 완성된 스택에도 아키텍처, 두 도구 체인의 로컬 설정과 실행 명령, 환경 변수, 시드 데이터, 테라폼 검증 워크플로, 적용 금지 경계를 기록한 루트 `README.md`가 하나 필요하다. 세션이 끝난 뒤에도 프로젝트를 실행할 수 있어야 한다. 마지막 빌드 단계로 생성한다.
13. **이야기는 적용 경계에서 끝난다.** 22장부터 이어진 장들은 Run or Relax API를 만들고, 보드를 얹고, Cloud Run에 올렸다. 에이전트는 스택의 모든 테라폼 줄을 쓸 수 있다. Cloud Run 서비스, 정적 사이트 버킷, 서비스 계정과 IAM, 보드의 origin을 API의 CORS에 이어 주는 배포 환경 변수까지다. 하지만 같은 경계가 유지된다. 에이전트는 제안하고 사람이 적용한다.
