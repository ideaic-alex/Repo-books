# 테라폼 작업 흐름

Codex CLI로 테라폼 작업을 할 때 반복되는 세 가지 패턴이 있다. 모듈 생성, 계획 검토, 리팩터링이다. 이 문서는 각 패턴에서 프롬프트에 무엇을 넣어야 하는지, 왜 그런 제약을 거는지를 Run or Relax 예제로 설명한다.

---

## 1. 모듈 생성

Codex CLI는 자연어 설명으로 테라폼 모듈을 만들어 준다. 보드(정적 웹 화면)용 버킷은 Run or Relax 배포에서 가장 작은 조각이라 첫 모듈로 알맞다. 원서의 프롬프트는 다음을 요구한다.

- uniform bucket-level access 켜기.
- `public_access_prevention`은 `"enforced"`가 아니라 `"inherited"`로 둔다. 공개 웹사이트 버킷에는 이 설정이 필요하므로, 이유를 설명하는 인라인 checkov 예외를 붙인다.
- 웹사이트 설정: 인덱스 페이지 `index.html`, 404 페이지 `404.html`.
- 객체 버저닝. 잘못 올린 보드를 롤백하기 위해서다.
- `allUsers`에게 `roles/storage.objectViewer`를 주는 IAM 바인딩으로 공개 읽기를 허용하고, 의도된 공개 사이트라는 인라인 checkov 예외를 붙인다.
- 버킷 이름은 프로젝트와 환경으로 만든다(예: `${project}-${env}-rr-board`). 버킷 이름은 전역에서 유일해야 하고 63자 제한이 있다.
- 프로젝트, 환경, 위치 변수.
- 출력은 세 가지다. 버킷 이름, 사이트 URL(`index.html` 주소), 그리고 API의 CORS 설정에 쓸 origin(스킴과 호스트만).

에이전트는 AGENTS.md의 관례를 따라 `main.tf`, `variables.tf`, `outputs.tf`를 만든다. 커밋하기 전에 `terraform validate`, tflint, checkov로 검증한다. 직접 돌려도 되고, 앞 문서의 결정적 도구 루프처럼 에이전트에게 통과할 때까지 돌리게 해도 된다.

## 2. 계획 검토(plan review)

계획 검토는 인프라 팀에 가장 가치가 큰 패턴이다. 전부 적용 경계의 안전한 쪽에서 일어나기 때문이다. 순서는 이렇다.

1. `terraform plan -out=tfplan`을 돌려 출력을 모은다.
2. Codex CLI에게 위험, 의도하지 않은 변경, 보안 우려를 검토하게 한다.
3. 에이전트는 삭제, 수정, 생성되는 리소스를 구분하고 예상 밖의 것을 표시한다.

```bash
terraform plan -out=tfplan -no-color > plan-output.txt
codex exec -a untrusted -s read-only "Review the Terraform plan in
plan-output.txt for risks and unintended changes. Flag any resource
deletions, IAM binding changes, or Cloud Run revisions that would
shift traffic."
```

`-a untrusted -s read-only` 조합이라 에이전트는 읽고 평가하기만 한다. 눈여겨볼 항목은 리소스 삭제, IAM 바인딩 변경, 트래픽을 옮기는 Cloud Run 리비전이다.

## 3. 리팩터링

인프라 리팩터링은 21장의 애플리케이션 리팩터링과 같은 방식으로 하되 제약이 더 촘촘하다. 흔한 작업은 거대한 구성을 모듈로 쪼개기, 프로바이더 버전 올리기, 폐기된 리소스에서 옮겨 가기다. 에이전트가 근거 없이 쓰다가 걸려 넘어지는 `google_cloud_run_service`에서 `google_cloud_run_v2_service`로의 이전이 바로 그 예다.

```text
Refactor the Cloud Run configuration in `main.tf` into a separate module
under `modules/cloud_run/`.
Preserve all resource addresses so that `terraform plan` shows no changes
after the refactoring.
Run `terraform validate` after each change to verify syntax.
```

핵심 제약은 변경 없음(zero-diff)이다. 운영에서 리소스 재생성을 일으키는 리팩터링은 리팩터링이 아니다. Cloud Run 서비스가 업데이트되지 않고 재생성되면 URL과 트래픽을 잃는다. 리소스 주소를 보존해야 계획이 비어 있게 유지된다.
