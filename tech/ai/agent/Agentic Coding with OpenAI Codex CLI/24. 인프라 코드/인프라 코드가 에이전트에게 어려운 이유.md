# 인프라 코드가 에이전트에게 어려운 이유

앞의 두 장에서 Run or Relax 예제의 백엔드(22장)와 프런트엔드(23장)를 만들었다. 둘 다 아직 노트북 안에서만 돈다. 출퇴근하는 사람이 쓰려면 어딘가에 올려야 하고, 그 일이 인프라 작업이다. 이 장은 그 스택을 운영 환경까지 올리면서, 여느 장처럼 Codex CLI에게 코드 작성을 맡긴다.

다만 인프라 코드는 애플리케이션 코드와 다룰 때의 마음가짐이 다르다. 애플리케이션 코드의 잘못된 한 줄은 테스트에서 실패하고 끝난다. 인프라의 잘못된 한 줄은 운영 환경을 내리거나, 서비스가 올라갈 자리 자체를 지워 버릴 수 있다. 그래서 에이전트의 역할은 계획하고, 초안을 쓰고, 제안하는 데까지로 좁히고, 검토와 적용(apply)은 사람이 한다. 이 장 전체가 에이전트를 그 선의 제안하는 쪽에 붙잡아 두는 방법을 다룬다.

---

## 1. 이 장의 배포 대상과 범위

배포 대상은 Google Cloud Run이다. GCP 기반 클라우드 네이티브 프로젝트가 실제로 쓰는 기법과 같다. 하지만 이 장의 주제는 Google Cloud 설정이 아니다. 인프라 작업을 할 때 Codex CLI를 어떻게 설정해야 "에이전트는 제안만 한다"는 경계가 지켜지는지가 주제다.

원서는 Cloud Run, Cloud Storage, 테라폼(Terraform) 기법을 일부러 가볍게만 다룬다고 밝히고, 더 깊은 내용은 《Cloud Native Development with Google Cloud》를 참고하라고 안내한다. 그 책은 빌드팩으로 여러 서비스를 배포하는 방법, GCS에 올리는 정적 사이트, 서비스별 서비스 계정, GCS 원격 백엔드를 쓰는 테라폼을 다룬다.

## 2. 학습 목표

이 장을 읽고 나면 다음을 할 수 있어야 한다.

1. 인프라 저장소에 맞춘 AGENTS.md를 쓴다.
2. 인프라 변경에 맞는 승인 모드와 샌드박스 설정을 고른다.
3. Codex CLI로 Cloud Run 서비스와 Cloud Storage 정적 사이트를 배포하는 테라폼을 생성, 검토, 리팩터링한다.
4. 결정적 도구(tflint, checkov)로 루프를 닫고, 이를 `/goal`(12장)로 감싼다.
5. 검토 없는 인프라 변경을 막는 안전장치를 적용한다.
6. Codex CLI를 인프라 CI/CD 파이프라인에 붙인다.
7. Terraform MCP 서버로 에이전트가 최신 프로바이더 문서를 근거로 삼게 한다.
8. GitOps로 적용 경계를 정책이 아니라 구조로 강제한다.
9. 드리프트 감지 같은 2일차 운영 작업을 읽기 전용 `codex exec` 파이프라인으로 돌린다.

## 3. 인프라 코드가 에이전트에게 유독 어려운 이유

폭발 반경(blast radius, 잘못됐을 때 피해가 번지는 범위) 말고도 이유가 더 있다.

**환각이 치명적이다.** 대규모 언어 모델은 테라폼의 리소스 타입과 속성 이름을 지어내는 경우가 있다. 파이썬에서는 사소한 짜증거리지만 리소스 정의에서는 피해가 크다. 원인은 구조적이다.

- HCL(HashiCorp Configuration Language, 테라폼을 쓰는 언어)은 파이썬이나 타입스크립트에 비해 학습 데이터가 적다.
- 프로바이더 스키마는 릴리스마다 바뀐다. Google 프로바이더는 리소스 타입이 수백 개이고 인자도 자주 고쳐진다. 6개월 전에 학습한 모델은 이제 없는 속성을 자신 있게 써 낸다.

대표 사례가 Cloud Run이다. 리소스가 `google_cloud_run_service`에서 `google_cloud_run_v2_service`로 이름과 구조가 바뀌었는데, 옛 모양을 배운 모델은 새 리소스에 없는 필드를 쓴다. 원서는 테라폼 합성 연구(TerraFormer, arXiv:2601.08734)에서도 강한 모델조차 리소스 타입과 속성 이름을 지어내는 것이 가장 흔한 기본 실패였다고 인용한다.

**지도 없이 쓰면 뻔한 방식으로 실패한다.** 에이전트가 쓴 인프라는 대체로 다음 문제를 보인다.

| 실패 유형 | 설명 |
| --- | --- |
| 하드코딩 | 변수여야 할 값이 코드에 박혀 있다 |
| 거대한 단일 파일 | 모듈로 나눠야 할 구성이 한 파일에 몰려 있다 |
| 과한 IAM 권한 | 필요 이상으로 넓은 바인딩을 준다 |
| 암호화 누락 | 저장소 암호화가 빠진다 |
| 테스트·정책 검사 부재 | 자동 검증이 없다 |

이 중 어느 것도 `terraform validate`로는 걸러지지 않고, 몇몇은 운영에 가장 올리고 싶지 않은 변경이다.

## 4. 대응의 순서: 피하지 말고 제약한다

해법은 에이전트를 안 쓰는 것이 아니라 제약하는 것이다. 이 장은 세 단계를 이 순서로 쌓는다.

1. **기반**: 팀의 관례와 금지 사항을 적은 AGENTS.md.
2. **결정적 검사**: 에이전트와 커밋 사이에 두는 린터와 보안 스캐너.
3. **강화**: 모델이 낡은 학습 데이터 대신 검증된 최신 프로바이더 문서를 보게 하는 MCP(Model Context Protocol) 서버.

앞의 두 가지만으로도 스택을 만들어 배포할 수 있다. 세 번째는 이미 서 있는 길을 더 단단하게 만드는 보강이다.
