# 흔한 실수와 정리

AGENTS.md는 대개 서너 줄로 시작해서 서서히 부풀고, 그 과정에서 오히려 에이전트 성능을 해친다. 이 문서에서는 규칙이 안 먹을 때 원인을 찾는 진단법, 파일이 끝없이 커지는 이유와 연구 결과, 가지치기 점검표와 네 가지 포함 기준, 탐색 실패를 줄이는 파일 맵 패턴을 다룬다.

---

## 1. 규칙이 적용되지 않을 때의 진단

제약을 적었는데 Codex CLI가 무시한다면 버그를 의심하기 전에 지침 체인부터 확인한다. 원문이 권하는 방법은 Codex CLI에게 직접 물어보는 것이다.

```bash
codex --ask-for-approval never \
 "List the AGENTS.md files you loaded this session, in order, with their full paths."
```

불러온 파일의 목록과 순서, 전체 경로를 알려 달라고 하는 요청이다. 아래 표는 증상별 원인을 정리한 것이다.

| 증상 | 가능성 높은 원인 |
|---|---|
| override가 적용되지 않는다 | 파일 이름이 틀렸다. `AGENTS-override.md`가 아니라 `AGENTS.override.md`여야 한다 |
| 고친 뒤에도 옛 규칙이 남는다 | 더 가까운 `AGENTS.override.md`가 수정한 `AGENTS.md`를 계속 이기고 있다 |
| 파일이 조용히 무시된다 | 파일이 비어 있거나, 체인 전체가 이미 `project_doc_max_bytes`에 닿았다 |
| 엉뚱한 디렉터리에서 규칙이 적용된다 | Codex CLI는 git 루트에서부터 해석한다. 대상 디렉터리에서 실행해야 한다 |
| 제약이 들쭉날쭉 지켜진다 | 규칙이 잘림 지점 아래에 묻혀 있다 |

## 2. 파일이 끝없이 커지는 이유

AGENTS.md는 작게 시작한다. 문제는 성장 곡선이다. 에이전트가 뭔가 잘못할 때마다 규칙을 하나 더 적고 싶어지고, 하나하나는 합리적이지만 합쳐 놓으면 전혀 다른 문제가 된다.

원문은 ETH Zurich SRI Lab의 연구(Gloaguen 외, arXiv:2602.11988, 2026)를 인용한다. 결과는 다음과 같다.

| 컨텍스트 파일 | 작업 성공률 | 추론 비용 |
|---|---|---|
| LLM이 생성한 파일 | 파일이 없을 때보다 3퍼센트 감소 | 20퍼센트 넘게 증가 |
| 사람이 쓴 파일 | 4퍼센트 향상에 그침 | 최대 19퍼센트 증가 |

긍정적인 효과를 낸 내용은 표준에서 벗어난 도구 사용법과, 코드에서 추론할 수 없는 팀의 결정이었다. 아키텍처 개요나 프레임워크 관례는 효과가 없었다.

그래서 `/init` 같은 자동 생성 명령의 결과를 한 줄씩 사람이 검토하지 않고 커밋하면 안 된다. 생성된 파일은 그럴듯하게 들리지만, 중복된 내용을 쳐내기 전까지는 에이전트 성능에 실제로 해롭다.

## 3. 가지치기 점검표

AGENTS.md를 한 번에 앉아서 다음 질문으로 훑는다.

1. 저장소 구조, 아키텍처, 레이아웃에 관한 내용인가. 지운다. 에이전트는 저장소를 읽으면서 길을 찾는다.
2. 일반적인 모범 사례인가. 지운다. 모델이 이미 안다.
3. 프레임워크 관례를 설명하는가. 지운다. 모델이 안다.
4. README와 겹치는가. 지운다. 같은 내용에 두 번 비용을 내는 셈이다.
5. 중첩된 AGENTS.md로 옮길 수 있는가. 특정 하위 디렉터리에만 해당하면 아래로 내린다.
6. 스킬로 옮길 수 있는가. 특정 워크플로에서만 필요하다면 필요할 때 불러오는 스킬 파일이 맞다.

## 4. 포함 기준 네 가지

지침은 다음 네 가지를 모두 통과해야 들어갈 자격이 있다.

- 실패에 근거한다: 이 지침이 없을 때 에이전트가 반복 가능한 패턴으로 실패하는 것을 직접 봤다.
- 추론할 수 없다: 코드베이스를 직접 읽어서는 알아낼 수 없는 정보다.
- 항상 관련 있다: 이 디렉터리의 대부분 작업에 적용된다.
- 발동 장면을 말할 수 있다: 지침을 따랐을 때 결과가 측정 가능하게 달라지는 구체적 상황을 설명할 수 있다.

## 5. 파일 맵 패턴

원문은 코딩 에이전트 실패의 가장 큰 원인이 탐색이라고 말한다. 전체 실패의 27~52퍼센트를 차지한다는 연구(AAR, The Amazing Agent Race, arXiv:2604.10261, 2026년 4월)를 근거로 든다. 다만 각주에 따르면 이 벤치마크는 퍼즐과 검색 기반 탐색을 측정하므로 코드베이스 탐색에 적용하는 것은 비유다.

해결책이 파일 맵이다. 어디에 무엇이 있는지 디렉터리별 목록으로 알려 준다.

```markdown
## File Map
### Core Application
- `src/api/routes/` --- HTTP route handlers; one file per API resource
- `src/services/` --- Business logic; no direct DB access
- `src/models/` --- Sequelize model definitions; one file per table
### Generated (DO NOT MODIFY)
- `src/generated/` --- OpenAPI codegen output; regenerated on build
- `prisma/client/` --- Prisma client; regenerated from schema
```

원문의 전체 예시에는 `src/api/middleware/`(auth, rate-limit, error-handler용 Express 미들웨어)도 있고, 테스트 섹션에는 `tests/unit/`(`src/` 구조를 그대로 따르며 `npm test`로 실행)과 `tests/integration/`(Docker 의존, `npm run test:integration`으로 실행)이 들어 있다.

파일 맵은 탐색 문제를 조회 문제로 바꾸어 준다. 토큰을 잡아먹는 디렉터리 읽기가 줄어드는 효과도 있다. 이 패턴은 가지치기 점검표의 첫 항목(구조 설명은 지운다)과 얼핏 부딪히는 것처럼 보인다. 점검표가 겨냥하는 것은 일반적인 구조 설명이고, 파일 맵은 간결한 위치 안내와 건드리면 안 되는 영역을 표시하는 데 쓴다는 점이 다르다. 원문은 이 두 가지의 관계를 따로 설명하지 않으므로, 여기서는 독자가 두 규칙을 함께 적용할 때의 해석으로 덧붙인다.
