# 함께 쓰는 Markdown 파일들

AGENTS.md가 잘 되는 이유는 에이전트가 자동으로 읽는 일반 Markdown이기 때문이다. 이 공식은 다른 용도로도 쓸 수 있다. 파일 이름만 바꾸고 "오래 가야 하는 맥락을 Markdown에 못박아 에이전트가 집어 가게 한다"는 발상은 같다. 이 문서에서는 AGENTS.md와 짝으로 쓰이는 PLANS.md, SKILL.md, DESIGN.md, SOUL.md, WORKFLOW.md를 살펴보고, 1부를 마무리하는 이야기를 정리한다.

---

## 1. 한눈에 보기

생태계는 비공식적이다. 무엇이 표준인지 정하는 위원회는 없다. 그래도 실무에서 자리를 잡은 파일이 몇 개 있다.

| 파일 | 목적 | 범위 | 수명 |
|---|---|---|---|
| AGENTS.md | 상시 규칙과 관례 | 명령, 제약, 금지 파일 | 프로젝트 전체 기간 |
| PLANS.md | 실행 로드맵 | 현재 진행 중인 과제의 마일스톤 | 며칠에서 몇 주 |
| SKILL.md | 절차 지식 | 에이전트가 수행할 수 있는 특정 작업 | 여러 프로젝트에서 재사용 |
| DESIGN.md | 시각, UX 관례 | 토큰, 컴포넌트, 상호작용 패턴 | 프로젝트 전체 기간 |
| SOUL.md | 에이전트 페르소나 | 어조, 말투, 거절 방식 | 에이전트나 역할별 |
| WORKFLOW.md | 여러 에이전트를 나누어 맡기고 조율하는 일(오케스트레이션) | 서브에이전트가 일을 넘기는 방법 | 워크플로별 |

## 2. PLANS.md: 가장 자리 잡은 확장

3장에서 소개한 패턴의 규율을 여기서 정리한다. OpenAI에서 Codex 제품을 이끄는 Alex Embiricos는 코드를 쓰기 전에 PLANS.md에 마일스톤 단위 계획을 먼저 만들라고 권한다(Lenny's Newsletter의 How I AI 팟캐스트, 2026). 한 번에 마일스톤 하나씩 실행하고, 매 단계 전에 Codex CLI에게 PLANS.md를 읽게 하고, 넘어가기 전에 알게 된 점을 PLANS.md에 업데이트하게 한다.

역할 분담은 이렇다. AGENTS.md는 모든 세션에 적용되는 상시 규칙이고, PLANS.md는 지금 진행 중인 과제의 실행 로드맵이다. 하나는 프로젝트의 헌법, 다른 하나는 지금 해야 할 일을 적은 작업 지시서다.

```markdown
# PLANS.md — Auth migration
## Goal
Move auth from session cookies to JWT without downtime.
## Milestones
- [x] M1 — JWT verifier middleware behind a feature flag
- [ ] M2 — Issue JWT alongside session cookie on login
- [ ] M3 — Switch default to JWT; cookies become fallback
- [ ] M4 — Remove session-cookie path after one week green
## Decision log
- 2026-05-02: Rejected refresh tokens for v1
```

원문의 결정 기록 항목은 "v1에서는 리프레시 토큰을 채택하지 않았다. 아직 필요 없는 키 순환 작업이 늘어나기 때문"이라는 내용이다. 마일스톤 목록과 결정 기록을 같은 파일에 두면, 다음 세션의 에이전트가 왜 그렇게 정했는지까지 읽을 수 있다.

## 3. SKILL.md: 필요할 때만 불러오는 절차

그다음으로 구체적인 것이 SKILL.md다. Codex CLI의 스킬 형식은 YAML 머리말이 달린 Markdown 파일이고, 매 세션 로드되지 않고 필요할 때 발견되어 쓰인다. 원문 예시의 머리말은 `name: docstring-pass`와 `description`이다. 설명은 공개 함수에 Google 스타일 docstring이 없을 때 쓰고, 이미 있으면 건너뛰라는 내용이다. 본문은 밑줄로 시작하지 않는 모든 공개 함수에 Args, Returns, Raises 섹션을 가진 Google 스타일 docstring을 추가하고, `src/services/auth.py`의 패턴을 따르며, 구현 코드는 바꾸지 말라는 지시다. 스킬은 10장에서 자세히 다룬다.

## 4. DESIGN.md: 디자인 시스템 지키기

DESIGN.md는 표준화 정도가 낮지만, 에이전트가 존중해야 할 디자인 시스템이 있는 프로젝트에서 유용하다. 원문 예시에는 세 부분이 있다.

- 팔레트: 토큰은 `src/ui/tokens.css`에 있고, 주색은 `#0F62FE`, 밝은 표면은 `#FFFFFF`, 어두운 표면은 `#161616`
- 간격: 기본 4px, `--space-1`부터 `--space-8`까지 쓰고 픽셀 값을 직접 쓰지 않는다
- 컴포넌트: 버튼은 `src/ui/Button.tsx`의 variant 패턴을 따르고, 새 버튼은 새 모양을 만들지 말고 기존 variant를 확장한다

## 5. SOUL.md와 WORKFLOW.md

두 파일은 덜 흔하고 관례도 아직 자리를 잡는 중이다. 반복되는 필요가 있을 때 쓴다. SOUL.md는 어조가 뚜렷한 에이전트 역할용이다(원문의 예는 얼버무리는 말투를 쓰지 않는 코드 리뷰 에이전트). WORKFLOW.md는 여러 서브에이전트가 정해진 순서로 일을 넘기는 조율 상황용이다. 27장에서 WORKFLOW.md를 실제 하니스에 적용한다.

SOUL.md는 역할, 말투, 거절 방식, 경계의 네 부분으로 정리되는 것이 아직 비공식 관례다. 원문의 보안 집착형 리뷰 에이전트 예시를 요약하면 이렇다.

- 역할: 편집증적인 애플리케이션 보안 엔지니어로서 리뷰한다. 침입 경로를 찾고, 잘된 점은 칭찬하지 않으며, 모든 diff를 안전이 증명될 때까지 적대적으로 본다.
- 말투: 직설적이고 구체적이다. "어쩌면 이럴 수도"식 얼버무림과 칭찬 샌드위치를 쓰지 않는다. 취약점, 영향, 수정 방법 순으로 파일과 줄 번호를 붙여 말하고, 확신이 없으면 부드럽게 포장하지 말고 그대로 말한다.
- 거절 방식: 분류하지 않은 발견이 남아 있으면 승인하지 않는다. 비위를 맞추려고 승인하지 않는다. 점검을 건너뛰라는 요청을 받으면 떠안게 될 위험을 말하고 명시적 확인을 받은 뒤에만 진행한다.
- 경계: 시크릿, 인젝션, 인증 허점, 안전하지 않은 역직렬화를 먼저 표시한다. 발견을 입증하는 데 필요한 최소한의 증명만 쓰고 무기화된 익스플로잇은 쓰지 않는다. 범위는 페르소나와 태도에 한정하며, 작업을 쉽게 하려고 프로젝트의 승인 정책이나 샌드박스 설정을 약화하지 않는다.

SOUL.md는 어조와 판단을 다듬는 용도이지 지시를 몰래 끼워 넣는 곳이 아니다. 이런 파일을 불러오는 도구들은 프롬프트 인젝션 패턴을 점점 더 검사한다. 그래서 위 예시의 마지막 경계가 실제로 중요한 역할을 한다. 페르소나가 슬쩍 신뢰 모델을 느슨하게 만들지 못하게 막기 때문이다. 이 신뢰 모델은 6장에서 명시적으로 다룬다.

## 6. 두 번째 파일을 만들 때의 기준

어느 파일이든 패턴은 같다. 에이전트가 스스로 읽는 설정 표면으로서의 Markdown이다. 대부분의 팀은 AGENTS.md 하나면 충분하다. 두 번째 파일을 만드는 것은 같은 시험이 적용될 때만이다. 실패에 근거하고, 추론할 수 없고, 그 파일의 범위 안에서 항상 관련 있어야 한다.

## 7. 1부를 마치며

1부는 여기서 끝난다. 이제 Codex CLI를 설치하고, 세션을 실행하고, 몇 분 걸리는 실행을 보람 있게 만드는 프롬프트를 쓰고, 그 뒤를 받쳐 줄 지속적인 맥락을 AGENTS.md에 두는 법을 안다. 이것이 신뢰 모델의 부드러운 쪽, 곧 에이전트가 읽고 따르는 지침이다.

하지만 지침은 제안일 뿐이다. Codex CLI가 하는 경향을 바꿀 수는 있어도 원하지 않는 일을 하지 못하게 막지는 못한다. 신뢰 모델의 단단한 쪽은 승인 정책과 샌드박스 모드다. 에이전트가 애초에 어떤 행동을 할 수 있는지, 에이전트가 시도해도 운영체제가 무엇을 막는지를 정하는 설정이다. 이것이 5장이고, 2부의 시작이다.
