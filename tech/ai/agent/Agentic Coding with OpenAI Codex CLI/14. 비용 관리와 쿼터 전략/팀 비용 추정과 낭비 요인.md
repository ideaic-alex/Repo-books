# 팀 비용 추정과 낭비 요인

추상적인 가격표보다 구체적인 계산 예시가 더 쓸모 있다. 이 문서는 현실적인 팀 배포를 가정한 계산 과정을 따라가고, 사용자가 체감하는 비용과 실제 소모량이 왜 어긋나는지, 에이전트가 만든 PR이 실패할 때 돈이 어떻게 새는지, 리뷰 루프 비용을 어떻게 줄이는지를 정리한다.

---

## 1. 시나리오: 엔지니어 5명, 조율자/작업자 구조

가정은 다음과 같다.

1. 엔지니어 5명이 각자 근무일마다 Codex CLI를 약 3시간 동안 활성 세션으로 돌린다.
2. 조율자/작업자 구조: 작업 하나마다 조율자 호출 1회(gpt-5.4)가 작업자 에이전트 2~3개(gpt-5.4-mini)를 띄운다.
3. 조율자 세션 평균: 입력 40,000토큰, 출력 4,000토큰.
4. 작업자 세션 평균: 입력 25,000토큰, 출력 3,000토큰.
5. 작업당 작업자 평균 2.5개.
6. 엔지니어 한 명이 하루 15개 작업을 처리한다(짧은 것과 긴 것 혼합).

엔지니어 한 명의 하루 비용은 이렇게 계산한다.

```text
조율자(gpt-5.4): 15 x (40,000 x $2.50/1M + 4,000 x $15.00/1M)
              = 15 x ($0.10 + $0.06) = 15 x $0.16 = $2.40
작업자(gpt-5.4-mini): 15 x 2.5 x (25,000 x $0.75/1M + 3,000 x $4.50/1M)
              = 37.5 x ($0.01875 + $0.0135) = 37.5 x $0.03225 = $1.21
합계: $2.40 + $1.21 = $3.61 (엔지니어 1명, 하루)
```

한 달 팀 비용(근무일 22일)은 다음과 같다.

```text
$3.61 x 5명 x 22일 = 약 $397/월
```

대략적인 추정이지만 규모감을 잡아 준다. 엔지니어 5명 팀이 조율자/작업자 구조로 쓰는 Codex CLI API 비용은 클라우드 서비스 인스턴스 하나 정도와 비슷한 수준이다.

이 계산은 모델 라우팅의 위력도 보여 준다. 작업자를 전부 gpt-5.4-mini 대신 gpt-5.4로 돌리면 작업자 비용이 엔지니어당 하루 $1.21에서 약 $4.03으로 3.3배 뛰고, 월 총액은 $397에서 약 $707로 오른다. 캐싱 다음으로 가장 큰 비용 레버가 모델 라우팅이다.

---

## 2. 추정값을 크게 흔드는 변수

추정치에서 가장 민감한 변수는 세 가지다.

1. 세션 깊이: 조율자 입력 40,000토큰은 보수적인 가정이다. 파일을 많이 읽는 대형 레거시 코드베이스에서는 입력이 100,000토큰 이상으로 갈 수 있다. `--debug` 출력으로 실제 세션을 재서 조정한다.
2. 작업당 작업자 수: 병렬이 늘면 비용도 늘어난다. 작업자 3명은 2.5명보다 20% 더 들고, 5명이면 두 배가 든다.
3. 작업 빈도: 탐색 위주(짧은 세션이 많음)와 깊은 작업 완료 위주(긴 세션이 적음)는 비용 구조가 다르다. 탐색 세션은 짧지만 세션당 고정 오버헤드의 비중이 높다.

---

## 3. 청구 투명성 문제

사용자들이 반복해서 보고하는 문제는 두 가지다. 하나는 토큰이 직관보다 5~10배 빨리 줄어든다는 것이고, 다른 하나는 에이전트가 시작한 API 요청과 사용자가 시작한 요청을 구분하기 어렵다는 것이다. 후자 때문에 작업별 비용 귀속이 힘들다. 기업 팀은 세션별, 작업별로 세밀하게 비용을 나눠 보고 싶어 하지만 대시보드는 아직 그 수준을 제공하지 않는다.

뿌리는 앞서 말한 누적 기록 문제다. API 호출 때마다 전체 기록을 다시 처리하기 때문에, "질문 몇 개"처럼 느껴지는 세션도 열 번째 API 호출쯤이면 입력 토큰을 20만 개 이상 썼을 수 있다.

구체적인 사례가 있다. 7,000줄짜리 코드베이스에 "이 코드베이스를 훑어서 macOS에 맞게 문제를 미리 고쳐라" 같은 넓은 프롬프트 하나를 GPT-5.4, xHigh 추론 강도로 던졌더니 7분 동안 34번의 API 요청에서 약 400만 토큰을 쓰고, 프롬프트 하나에 대략 $3.50가 나왔다. 범위가 넓고 끝이 열린 프롬프트가 사소하지 않은 코드베이스에서 최대 추론 강도의 유능한 모델을 만나면 의외로 큰 청구서가 나온다.

기대와 실제의 간극은 세 가지 요인으로 더 커진다.

- 구독 한도 화면이 토큰 수가 아니라 남은 비율만 보여 준다.
- 세션별 비용 내역이 없다.
- 멀티 에이전트 워크플로에서는 서브에이전트마다 자기만의 컨텍스트 누적 곡선이 있어 효과가 겹친다.

현실적인 대응은 모니터링이다. 이 장 뒤에서 다루는 Stop 훅(hook)으로 세션별 토큰 수를 기록하고, 매주 예상치와 비교한다. 실제 소모가 예상을 꾸준히 2배 넘게 웃돈다면 세션 깊이 가정을 고쳐야 한다.

Codex CLI는 `codex_compaction_event`라는 분석 레코드를 내보낸다. `/compact`가 얼마나 자주 발동하고 토큰을 얼마나 줄였는지 기록한다. PreCompact/PostCompact 훅과 함께 쓰면 사용량 대시보드가 제공하기 전에 로컬에서 압축 빈도를 볼 수 있다.

## 4. 낭비되는 돈: 에이전트 PR 실패율

에이전트가 작성한 풀 리퀘스트(PR) 33,000개를 조사한 연구에서 에이전트 PR의 28.5%가 머지되지 못했다. 가장 큰 실패 원인은 코드가 나빠서가 아니라 사회적, 워크플로상 어긋남이다.

- 리뷰어가 포기함: 실패의 38%
- 중복 제출: 23%
- 원치 않는 기능: 4%

실패한 PR 하나하나가 결국 배포되지 않을 일에 쓴 토큰이다. 다른 연구에서는 에이전트가 도입한 심볼의 생존 기간 중앙값이 3일로, 사람이 도입한 심볼의 34일에 비해 훨씬 짧았다. 에이전트 코드의 변경 이탈률(churn)도 7.33%로 사람 코드의 4.10%보다 높았다. 머지된 에이전트 코드조차 더 빨리 고쳐지므로, 살아남는 줄당 실제 토큰 비용이 더 커진다.

더 작은 PR, 제출 전 CI 검증, AGENTS.md의 명시적인 범위 제약으로 실패율을 28.5%에서 15%로 낮추면 에이전트 지출 낭비의 절반 정도가 사라진다. 15장에서 이 연구 결과를 반영한 CI/CD 파이프라인 설계를 다룬다.

## 5. 리뷰 루프의 비용과 SLM 선별 계층

12장의 교차 모델 리뷰 루프는 구조적으로 다른 모델을 비평가 자리에 앉힌다. 프런티어(frontier) 모델만으로 구성하면 경제성이 나쁘다. 프런티어 추론 모델 하나에 플래그십 리뷰어 둘을 붙인 3개 제공자 리뷰 루프는 머지 리퀘스트(MR) 하나에 대략 $0.47~$0.50가 든다. 개발자 한 명이 한 달에 MR 40개를 올리면 리뷰에만 월 $20, 50명 팀이면 연 약 $12,000이다.

작은 언어 모델(SLM)을 심사자로 쓰는 최근 연구는, 파인튜닝한 SLM이 5~25배 큰 모델과 겨룰 만한 판정 성능을 낸다고 보여 준다. 이를 이용해 gpt-5.4-mini(Codex 권장 모델 중 가장 작은 모델)로 모든 MR을 먼저 거르는 선별 계층을 둔다. 문제 소지가 있다고 표시된 MR(보통 일상적 MR의 25~35%)만 프런티어 모델의 정식 리뷰로 넘긴다. 이렇게 하면 MR당 평균 리뷰 비용이 약 $0.27(2개 모델)에서 약 $0.09로 줄어 3배 절감된다.

한 모델로 구현하고 다른 모델로 리뷰하는 2개 모델 리뷰 루프가 비용 대비 품질의 최적점이다. 세 번째 리뷰어는 품질보다 비용을 더 빨리 늘리고, 독립 리뷰어가 둘을 넘으면 효과가 줄어든다는 연구도 있다. 세 번째 프런티어 리뷰어를 붙이기보다 SLM 선별 계층과 프롬프트 캐싱에 투자하는 편이 낫다.

## 6. 스킬 평가 비용

스킬(skill)을 개발하는 팀은 평가 비용을 따로 예산에 잡아야 한다. 10장의 스킬 벤치마크 하니스(harness)는 벤치마크 1회에 약 74,000토큰을 쓴다. 5번 반복하면 약 370,000토큰이고, gpt-5.4 입력 단가로 $0.93, gpt-5.4-mini로 $0.28에 해당한다. 합리적인 기본값은 전체 Codex CLI 지출의 5%를 스킬 개발과 평가에 배정하는 것이다.
