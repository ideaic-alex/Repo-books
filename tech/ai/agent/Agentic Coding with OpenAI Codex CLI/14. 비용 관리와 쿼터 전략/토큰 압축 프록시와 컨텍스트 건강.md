# 토큰 압축 프록시와 컨텍스트 건강

이 문서에서 다루는 기법은 Codex CLI의 기능이 아니라 커뮤니티 도구다. 배포를 권하는 추천이 아니라 자기 작업에 맞춰 조사해 볼 만한 제안으로 받아들여야 한다. 계산상으로는 솔깃하지만 실패 유형도 실제로 있으므로, 측정을 동반한 시험 적용이 합당한 다음 단계다.

---

## 1. 프록시의 개념

토큰 압축 프록시는 Codex CLI와 모델 API 사이, 또는 Codex CLI와 도구 출력을 만드는 셸 사이에 놓인다. 어디에 놓이든 일하는 방식은 같은 네 가지 동작이다.

1. 거르기(filter): 신호가 없는 줄, 필드, 토큰을 버린다. 모델이 짐작할 수 있는 경고, ANSI 이스케이프, 반복되는 스택 프레임, 패키지 설치 소음 같은 것들이다.
2. 묶고 요약하기: 반복되는 줄을 "N x 메시지"로 접고, 장황한 진행 상황 스트림을 최종 상태로 바꾼다.
3. 구조 단위로 자르기: 임의의 바이트 수가 아니라 의미 있는 경계(모델이 이미 이해한 함수 본문, 큰 diff의 중간)에서 자른다.
4. 턴 사이 중복 제거: 같은 파일 경로, 오류 메시지, 트리 조각이 되풀이되는 것을 찾아 반복하지 않고 참조한다.

긴 셸 출력을 채팅에 붙여넣기 전에 손으로 하던 일과 같다. 프록시는 모델이 원본 출력을 읽는 비용을 치르기 전에 이를 일관되게 적용한다.

가장 구체적인 커뮤니티 사례는 RTK(Rust Token Killer)다. 로컬 래퍼로 설치되어 관찰 위주의 셸 명령(`git status`, `pytest`, 큰 파일 읽기)을 압축된 요약으로 다시 쓴다. 이 프로젝트 문서는 흔한 개발 명령에서 60~90% 절감을 보고한다. 같은 이슈 트래커에는 실패 사례도 있다. 말 없이 다시 쓴 출력 때문에 입력 토큰은 줄었지만 모델이 출력 토큰을 약 50% 더 내놓아서, 해당 작업의 총비용이 약 18% 올랐다는 것이다.

교훈은 늘 같다. 압축 계층을 자주 쓰는 경로에 넣기 전에, 입력 절감이라는 겉보기 숫자가 아니라 작업당 총비용을 처음부터 끝까지 측정해야 한다.

## 2. 원시인 모드: 모델의 출력을 압축하기

대화의 반대편, 곧 모델의 문장을 압축하는 패턴도 있다. 커뮤니티 도구 squeez는 Codex CLI 훅으로 설치되어 세션 시작 때 간결한 페르소나를 주입한다. 관례상 이름은 원시인 모드(caveman mode)다. 이 페르소나는 모델에게 관사, 군더더기, 인사말을 빼고, 기술 용어는 정확히 유지하고, 코드 블록과 오류 메시지는 그대로 보존하라고 요청한다. 출력 토큰을 줄이는 것이 목적이다. 출력은 입력보다 토큰당 단가가 높다.

개념적으로는 프롬프트 맨 앞에 훅이 주입하는 지시 한 줄이다. 대략 이런 내용이다.

```text
Respond in caveman mode: terse. Drop articles, filler, and pleasantries.
Preserve code blocks, file paths, error messages, and technical terms exactly.
Use normal prose only for commit messages and PR descriptions.
```

이는 SessionStart나 UserPromptSubmit 훅(9장)이 지시를 stdout으로 내보내 주입하는 방식으로 구현할 수 있다. squeez 같은 커뮤니티 구현은 페르소나와 몇 가지 관련 조정을 묶어 제공하고, 직접 만든다면 bash 몇 줄이면 된다.

레버는 작지만 부작용은 눈에 띈다. 도구 출력 압축보다 주의가 더 필요하다. 모델 출력은 독자나 다음 턴의 에이전트가 보는 내용이므로, 문장의 연결 조직을 잘라 내면 품질 위험이 생긴다. 공개된 "원시인 말투" 실험에서는 토큰은 아꼈지만 품질이 크게 나빠져서, 글쓴이가 진지한 코드에는 믿고 쓰지 못하겠다고 했다.

시도해 볼 만한 곳은 일상적인 구현 루프, 상태 보고, 간결한 소통이 괜찮은 탐색 작업이다. 맞지 않는 곳은 교육 자료, 아키텍처 설명, 안전이 걸린 리뷰, 연결 조직이 빠지면 독자의 이해가 달라지는 모든 곳이다.

## 3. 두 계층을 조사하는 방법

운영에 바로 넣지 않고 평가하려면 이렇게 한다.

1. 작업 하나를 고른다. 반복되는 작업 종류여야 하며 가장 중요한 PR은 피한다.
2. 기준 세션을 돌리고 앞서 만든 Stop 훅으로 세션별 합계를 기록한다.
3. 프록시나 훅을 그 작업에만 켠다. 전용 프로필(6장)을 쓰면 영향 범위가 한정된다.
4. 같은 작업을 다시 돌리고 총 토큰 비용, 총 소요 시간, 결과물의 질적 차이를 비교한다.

두 계층은 모두 각자 릴리스 주기와 버그를 가진 독립 커뮤니티 프로젝트다. 도입한다면 버전을 고정하고, 명령이나 훅 경로에 있는 신뢰할 수 없는 코드로 취급해야 한다. 개발자 세션과 같은 호스트에서 실행하고, 원본 출력으로 되돌아갈 비상구를 두며, 정확한 출력 자체가 산출물인 명령(마이그레이션, 배포, 보안 스캔, 생성 파일, 장애 보고서나 감사 기록으로 갈 모든 것)에서는 압축을 끈다.

---

## 4. 비용 관측으로서의 컨텍스트 건강

컨텍스트 저하는 품질 문제가 되기 전에 비용 문제다. 세션이 압축 루프에 들어가는 경우를 보자. 모델이 압축하고, 곧바로 컨텍스트가 다시 차고, 또 압축하기를 반복하면 이미 처리한 파일을 다시 읽고 이미 만든 요약을 다시 생성하느라 토큰이 낭비된다. 앞에서 다룬 압축 관련 키 세 개(`tool_output_token_limit`, `model_auto_compact_token_limit`, `compact_prompt`)가 설정 쪽 방어선이고, 압축 훅이 텔레메트리 쪽 방어선이다.

실무 규칙은 컨텍스트 사용량 95%가 아니라 60%에서 압축하라는 것이다. 자동 트리거를 기다리면 압축이 압박 속에서 일어나 고품질 요약을 만들 여유가 적다. 하위 작업을 끝내고 새 파일을 시작하기 전 같은 자연스러운 작업 경계에서 수동으로 압축하면, 요약기가 더 여유롭게 일하고 세션 전체의 토큰 지출이 줄어든다.
