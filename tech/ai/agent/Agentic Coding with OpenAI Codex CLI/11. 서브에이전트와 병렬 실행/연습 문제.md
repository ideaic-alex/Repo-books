# 연습 문제

11장 끝에 있는 연습 문제 세 개를 풀이 방향과 함께 정리한다. 문제마다 취지를 풀어 쓰고, 어떻게 접근하면 좋을지 한두 문장으로 덧붙인다.

---

## 1. test-runner 에이전트 정의하기

`.codex/agents/test-runner.toml`에 커스텀 에이전트를 만든다. 이 에이전트는 테스트 파일 하나를 실행하고 JSON 보고서를 돌려줘야 한다. 모델은 gpt-5.4-mini, 샌드박스는 read-only로 하고, 지침에는 지시문으로 받은 경로에 대해 `pytest --json-report`를 실행하라고 적는다. 그 다음 테스트 파일 세 개에 대해 직접 호출해 보고, 실행할 때마다 구조화된 출력이 일관된지 확인한다.

풀이 방향: name, description, developer_instructions 세 필수 필드에 `model`과 `sandbox_mode`를 더하면 된다. 지침에는 출력 형식(어떤 키를 가진 JSON인지)을 구체적으로 적어 두어야 실행마다 모양이 흔들리지 않는다. 읽기 전용 샌드박스에서 보고서 파일을 쓰려 할 수 있으니, 보고서를 파일이 아니라 응답으로 돌려주도록 지침을 짜는 점도 확인한다.

## 2. 순차 워크플로를 팬아웃으로 바꾸기

마크다운 파일 목록을 한 번에 하나씩 처리하는 순차 부모 에이전트 워크플로를 `spawn_agents_on_csv` 팬아웃으로 바꾼다. worker 출력 모양은 `output_schema`로 고정한다. 파일 20개 목록으로 변환 전후의 실제 소요 시간(wall-clock)을 재고, 병렬 버전이 몇 개 파일부터 더 빨라지는지 찾는다.

풀이 방향: 파일 경로를 담은 CSV와 `{path}` 같은 자리표시자를 쓴 지시문을 만들고, 결과를 담을 스키마의 필수 키를 정한다. 측정할 때는 병렬 쪽의 컨텍스트 준비와 취합 오버헤드를 포함해서 재야 한다. 파일 수가 적으면 오버헤드 때문에 순차가 이길 수 있으므로, 파일 수를 바꿔 가며 교차점을 찾는다.

## 3. 내 작업의 병렬화 가능성 점검하기

표 11-1의 작업 종류(린트, 테스트 생성, 번역, PR 요약 등)를 내가 일하는 실제 코드베이스나 프로젝트에 대어 본다. 지금은 순차로 하고 있지만 병렬화로 이득을 볼 작업 두 가지를 찾는다. 코드를 쓰기 전에, 각 작업마다 입력, 에이전트 정의, 취합 전략, 실패 처리를 담은 짧은 분해 계획을 쓴다.

풀이 방향: 항목끼리 독립인지, 끝나는 순서가 바뀌어도 결과가 같은지 먼저 확인한다. 계획에는 worker가 서로 다른 출력에 쓰도록 하는 방법과, 실패한 행을 최대 몇 번 재시도할지를 반드시 넣는다.
