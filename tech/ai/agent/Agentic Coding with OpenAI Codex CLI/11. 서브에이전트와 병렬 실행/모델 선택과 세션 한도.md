# 모델 선택과 세션 한도

서브에이전트를 쓰면 모델 선택과 동시 실행 수가 곧 비용과 속도, 사용 한도(쿼터)에 직결된다. 이 문서는 서브에이전트에 어떤 모델을 붙일지, 그리고 `config.toml`의 `[agents]` 아래 세션 전체 한도 세 가지를 설명한다.

---

## 1. 서브에이전트용 모델 고르기

기본 원칙은 역할을 나누는 것이다.

- 린트, 포맷, 구조화된 데이터 추출처럼 기계적인 일을 하는 worker에는 더 싸고 빠른 모델을 쓴다.
- 부모의 더 강력한 모델은 계획 세우기와 결과 취합에 아껴 둔다.

worker 역할에는 플래그십 모델보다 gpt-5.4-mini가 더 나은 선택인 경우가 많다. worker가 직접 상당한 추론을 해야 한다면 gpt-5.5가 어울린다. `model`을 생략하면 부모 모델을 그대로 물려받는다.

## 2. 세션 전체 한도: [agents] 설정

`config.toml`의 `[agents]` 아래 세 설정이 세션 안의 모든 서브에이전트를 한꺼번에 제한한다.

| 키 | 기본값 | 역할 |
|---|---|---|
| max_threads | 6 | 동시에 열려 있을 수 있는 에이전트 스레드의 최대 수 |
| max_depth | 1 | 중첩 깊이. 1이면 부모의 직접 자식까지만 허용하고 손자는 안 된다 |
| job_max_runtime_seconds | 없음 | `spawn_agents_on_csv` 작업의 worker별 기본 타임아웃 |

이 값들은 에이전트마다 따로 정하는 것이 아니라 **세션 전체**에 적용된다.

## 3. 기본값이 보수적인 이유

기본값은 일부러 조심스럽게 잡혀 있다.

- 동시 스레드 6개면 대부분의 팬아웃(fan-out, 한 작업을 여러 갈래로 퍼뜨려 동시에 돌리는 것)을 사용 한도에 걸리지 않고 처리할 수 있다.
- 중첩을 한 단계로 막아 두면, 넓게 퍼뜨리라는 지시가 반복적인 팬아웃으로 번지는 일을 막는다. 그런 연쇄 팬아웃은 토큰 사용량, 지연 시간, 로컬 자원 소모를 한꺼번에 불린다.

두 한도 중 어느 쪽이든 올리려면 분명한 이유가 있어야 하고, 내 사용 한도와 토큰 예산이 감당할 수 있는지 먼저 따져야 한다.

## 4. 모델과 슬롯 수를 맞추기

서브에이전트 하나하나는 자기가 쓰는 모델의 계정 단위 사용 한도(rate limit)에 합산된다. 그래서 gpt-5.5 worker 6개를 동시에 돌리면 gpt-5.4-mini worker 6개보다 먼저 한도에 걸린다. 모델 선택은 쓸 수 있는 슬롯 수와 함께 정해야 한다.

정리하면 다음과 같다.

- 슬롯을 많이 쓰고 싶다면 가벼운 모델을 worker에 배정한다.
- 무거운 추론이 필요한 worker는 수를 줄인다.
- 부모는 계획과 취합만 하므로 상대적으로 강한 모델을 유지한다.
