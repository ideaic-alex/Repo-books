# 운영상 주의점과 병렬화가 해로운 경우

서브에이전트를 길게 돌리면 두 가지 문제가 생길 수 있다. 하나는 MCP 서버 프로세스가 정리되지 않고 쌓이는 문제이고, 다른 하나는 애초에 병렬화가 맞지 않는 작업에 병렬화를 적용하는 문제다. 이 문서는 두 문제와 대응 방법을 정리한다.

---

## 1. 서브에이전트와 MCP 서버 프로세스 누수

서브에이전트가 MCP 도구를 부를 때, MCP 서버 프로세스가 바로 정리되지 않는 경우가 있다. 특히 stdio 전송 방식 MCP 서버(url이 아니라 command로 설정한 서버)는 자식 프로세스를 만든다. 이 프로세스가 자기를 띄운 서브에이전트보다 오래 살아남아, 긴 세션 동안 계속 쌓일 수 있다.

영향은 곱셈으로 불어난다.

> 서브에이전트 수 × MCP 서버 수 × 서버당 프로세스 수 × 프로세스당 메모리

무거운 세션의 예로 worker 40개, MCP 서버 5개, 서버당 프로세스 2개를 들 수 있다. 이 경우 부모 세션이 끝나기 전에 프로세스가 수백 개 새고 수 GB의 메모리를 쓸 수 있다.

## 2. 방어 방법 네 가지

**1) 긴 세션에서는 MCP 프로세스 수를 감시한다.** 프로세스 수를 세어 임계치를 넘으면 알려 주는 워치독(watchdog) 스크립트가 있으면, 문제가 심각해지기 전에 잡을 수 있다.

```bash
#!/usr/bin/env bash
# mcp-watchdog.sh — alert when MCP process count exceeds threshold
THRESHOLD=${1:-50}
COUNT=$(pgrep -f 'mcp' | wc -l)
if [ "$COUNT" -gt "$THRESHOLD" ]; then
  echo "WARNING: $COUNT MCP processes detected (threshold: $THRESHOLD)"
fi
```

**2) 서버가 지원하면 HTTP 전송을 쓴다.** command 대신 url로 설정한 MCP 서버는 로컬 자식 프로세스를 만들지 않는다.

```toml
[mcp_servers.my-server]
url = "https://mcp.example.com/sse"
```

**3) 큰 배치 사이에는 재시작한다.** CI에서는 지속적으로 떠 있는 에이전트 파드보다 작업 하나당 Codex CLI 호출 하나를 쓰는 편이 낫다. 누수는 한 프로세스 안에서 일어난 서브에이전트 생성 횟수에 비례하므로, 새 프로세스로 시작하면 카운트가 초기화된다.

**4) MCP를 많이 쓰는 작업은 max_threads를 낮춘다.** max_threads를 6에서 3으로 줄이면 stdio MCP 서버를 쓰는 팬아웃의 프로세스 최대치가 절반이 된다.

stdio MCP 서버를 쓰지 않는다면 이 걱정은 해당되지 않는다. HTTP 호출과 기본 제공 도구(파일 편집, 셸, 웹 가져오기)에서는 이런 현상이 나타나지 않는다.

## 3. 서브에이전트가 도움이 안 되는 경우

병렬화가 오히려 해가 되는 패턴이 두 가지 있다.

**정답이 하나뿐인 작업.** 특정 패치로 고치는 버그 수정, 린트와 포맷 정리, 결정적인 마이그레이션, 보안 취약점 수정은 맞는 출력이 하나다. worker 여러 개가 서로 다른 해법을 탐색해도 비용만 늘고 가치는 늘지 않는다. 하나만 남기고 전부 버릴 것이기 때문이다. 이런 작업은 추론 강도를 높인 에이전트 하나로 돌린다.

**출력의 다양성 자체가 목표인 작업.** 브레인스토밍, 탐색적 아키텍처 스케치, 여러 관점의 코드 리뷰, 문서 초안은 갈라지는 것이 이득이다. worker마다 다른 시각으로 쓰는 것이 핵심이므로, 이런 경우에 팬아웃이 오버헤드 값을 한다. 내 작업이 이 선의 어느 쪽에 있는지 아는 판단력이 병렬화가 도움이 될지 토큰 낭비가 될지를 가른다.

## 4. 메트릭 자유도(Metric Freedom)

Xu 등은 이 직관에 공식 이름을 붙였다. 메트릭 자유도(Metric Freedom)는 F = 1 − ρ(D_out, D_score)로 정의되며, worker 출력의 다양성과 평가 점수의 다양성 사이의 순위 상관(ρ)을 가리킨다. 출처는 "From Multi-Agent to Single-Agent: When Is Skill Distillation Beneficial?"(arXiv:2604.01608)이고, 멀티 에이전트 워크플로를 단일 에이전트 스킬 하나로 합치는 것이 이득인지 미리 예측하는 지표로 소개된다.

- **F가 높다**(출력이 다양해도 점수가 다양하게 갈리지 않음): 유효한 답이 많다는 뜻이므로 병렬화가 가치를 더한다.
- **F가 낮다**(벗어나면 감점되는 엄격한 지표): 정답이 하나라는 뜻이므로 추론 강도를 높인 에이전트 하나가 팬아웃을 이긴다.

원서는 같은 작업이라도 지표에 따라 스킬로 인한 향상이 +28%에서 -2% 사이로 흔들렸다고 소개한다. 정기적으로 병렬화할 작업이라면 F를 계산해 볼 만하다는 것이 원서의 조언이다.
