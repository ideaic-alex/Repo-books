# 작업 결과 병합하기

작업마다 복잡도가 달라서 에이전트들은 서로 다른 시각에 끝난다. 완료된 브랜치가 제각각 도착하는 상황을 다룰 병합 전략이 필요하다. 이 문서는 순차 병합, 리베이스 병합, 머지 큐 세 가지를 비교하고 어떤 기준으로 고르는지 정리한다.

---

## 1. 병합 전략 고르기

원서의 그림 13.1은 승인된 작업 브랜치를 어떻게 main에 합칠지 고르는 결정 트리다. 먼저 동시에 끝나는 에이전트가 많은지를 묻는다. 동시성이 높으면 머지 큐로 간다. 동시성이 낮으면 프로젝트가 선형 히스토리를 강제하는지를 한 번 더 묻는다. 강제하면 리베이스 병합, 아니면 순차 병합이다. 세 갈래 모두 마지막에는 "main에 병합됨"으로 끝난다.

| 상황 | 선택 |
|---|---|
| 동시성 높음 | 머지 큐 |
| 동시성 낮음 + 선형 히스토리 강제 | 리베이스 병합 |
| 동시성 낮음 + 선형 히스토리 불필요 | 순차 병합 |

## 2. 순차 병합 (단순한 경우)

동시성이 낮으면 승인된 작업 브랜치를 끝나는 대로 바로 main에 합친다.

```bash
git checkout main
git merge --no-ff codex/task-a3f9c1
git worktree remove .codex/worktrees/task-a3f9c1
git branch -d codex/task-a3f9c1
```

`--no-ff`를 붙이면 작업 브랜치마다 별도의 병합 커밋이 남아서 히스토리를 읽기 쉽다.

## 3. 리베이스 병합 (선형 히스토리)

프로젝트가 선형 히스토리를 강제한다면 병합하기 전에 작업 브랜치를 현재 main 위로 리베이스한다.

```bash
git -C .codex/worktrees/task-a3f9c1 rebase main
git checkout main
git merge --ff-only codex/task-a3f9c1
```

리베이스 중에 충돌이 날 수 있다. 이때 Codex에게 맡길 수 있다. `codex --cd .codex/worktrees/task-a3f9c1 "resolve any rebase conflicts against main"`을 실행하면 에이전트가 충돌을 해석해서 풀어 준다. 두 에이전트가 서로 다른 이유로 같은 함수를 고친 의미상 충돌(semantic conflict)에서 특히 도움이 된다.

## 4. 머지 큐 (동시성이 높은 경우)

많은 에이전트가 한꺼번에 끝나면, 오래된 main을 기준으로 테스트한 브랜치들 때문에 통합 단계에서 실패가 날 수 있다. 머지 큐는 이를 막는다. GitHub의 머지 큐는 저장소 설정에서 켜며, CI를 통과한 브랜치에 대해 이 과정을 자동으로 처리한다. 푸시와 PR 생성은 표준 도구로 한다.

```bash
git -C .codex/worktrees/auth-oauth push origin codex/auth-oauth
gh pr create --head codex/auth-oauth --title "feat: add OAuth2 PKCE support"
```

머지 큐가 켜져 있으면 CI가 통과하는 순간 PR이 자동으로 큐에 들어간다. 워크트리는 PR이 병합되거나 닫힐 때까지 남겨 두고, 그 뒤에 `git worktree remove`와 `git branch -d`로 정리한다.

## 5. 낡은 워크트리 정리

이미 main에 반영된 브랜치의 워크트리를 치우려면 `git worktree prune`을 야간 cron 작업이나 병합 후 훅으로 돌린다. 방치하면 낡은 워크트리가 파일 사본을 쌓아 디스크를 차지한다. 다만 저장소의 정확성에는 영향이 없다.
