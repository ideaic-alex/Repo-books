# 런타임 격리의 빈틈

앞 문서에서 짚은 예외 사례는 병렬 에이전트 워크트리를 확장하는 팀이 가장 흔하게 겪는 실패 유형이라서 따로 깊게 다룰 가치가 있다. git 워크트리가 격리하는 것은 코드 상태(파일, 인덱스, 브랜치 포인터)이고, 실행 상태는 격리하지 못한다. 이 문서는 어떤 충돌이 조용히 일어나는지와 그 대응법을 정리한다.

---

## 1. 조용히 일어나는 다섯 가지 충돌

여러 에이전트가 각자의 워크트리에서 애플리케이션 스택을 동시에 띄우면 다음 충돌이 소리 없이 발생한다.

1. 포트 충돌. 두 워크트리가 모두 `localhost:3000`을 기대한다. 두 번째 에이전트의 개발 서버가 포트를 못 잡고 실패하거나, 더 나쁘게는 엉뚱한 인스턴스에 접속한다.
2. 데이터베이스 충돌. 공유 데이터베이스 인스턴스에 여러 브랜치의 마이그레이션이 동시에 들어와 스키마 상태가 망가진다.
3. 환경 변수 번짐. 한 브랜치용 자격 증명이나 설정이 공유 셸이나 dotenv 상태를 타고 다른 브랜치로 새어 나간다.
4. Docker 데몬 공유. 하나의 Docker 데몬을 공유하는 워크트리끼리 컨테이너 이름과 포트가 겹친다.
5. 브라우저 상태. 공유된 세션, 캐시된 인증 토큰, 쿠키 때문에 에이전트가 엉뚱한 애플리케이션 인스턴스를 대상으로 테스트한다.

## 2. 에이전트가 문제를 키우는 이유

에이전트는 사람보다 빠르게 움직이므로 포트 충돌을 알아채고 멈추는 시간이 없다. 또 자동으로 반복하기 때문에 잘못된 상태에서 나온 오류가 계속 쌓인다. 마지막으로 테스트 결과가 어느 브랜치에서 나왔는지를 믿을 만하게 구분하지 못한다. 엉뚱한 인스턴스를 상대로 통과한 테스트는 코드가 맞다는 거짓 증거가 된다. 원서는 이 문제를 2026년 3월 Penligent의 글에서 구조적 빈틈으로 짚었다고 인용한다.

## 3. 실무 대응 표

| 자원 | 격리 방법 |
|---|---|
| 포트 | 워크트리마다 고유한 포트 범위를 준다. 예: `BASE_PORT=$((3000 + TASK_INDEX * 100))` |
| 데이터베이스 | 워크트리별 SQLite 파일, 또는 브랜치별 PostgreSQL 스키마를 쓴다. |
| 환경 변수 | 워크트리 전용 `.env.$TASK_ID` 파일을 불러온다. |
| Docker 컨테이너 | 컨테이너 이름 앞에 작업 ID를 붙인다. 예: `docker run --name ${TASK_ID}-api` |
| 브라우저 세션 | 에이전트마다 별도 브라우저 프로필이나 시크릿 모드를 쓴다. |

## 4. 도구의 도움: Coasts와 Codexia

병렬 에이전트가 3개 이상이 되면 포트와 데이터베이스 이름 나누기를 손으로 관리하다 실수하기 쉽다. 원서는 이 빈틈을 다루는 도구로 Coasts를 소개한다. 주요 기능은 다음과 같다.

- 정규 포트 미러링을 곁들인 동적 포트 배정
- 서비스별 재배정 정책(브랜치를 바꿀 때 데이터베이스는 그대로 두고 프런트엔드만 핫 리로드)
- 인스턴스별 데이터 격리
- 워크트리 전체의 실행 중 인스턴스를 보는 로컬 관측 UI(Coast Guard)

다른 각도에서 접근하는 도구도 있다. 원서가 쓰인 시점에 Codexia는 GUI로 격리된 작업 디렉터리를 만들어 주는 git 워크트리 관리 기능을 내장하고 있었다. 규모가 커질 때 "한 에이전트 한 워크트리" 원칙을 지키려고 셸에서 손으로 하던 일을 줄여 준다.

## 5. 운영 격리이지 보안 격리가 아니다

Coasts 같은 런타임 격리 도구는 워크트리끼리 실수로 서로 오염되는 것을 막아 줄 뿐이다. 신뢰할 수 없는 코드, 컨테이너 탈출, 프롬프트 인젝션은 막지 못한다. 따라서 런타임 조율을 넘어서 커널 샌드박싱, 네트워크 정책 같은 계층별 보안 통제가 여전히 필요하다.
