# 하나의 에이전트 하나의 워크트리

이 장의 설계 규칙은 한 문장으로 줄일 수 있다. 에이전트 하나는 한 시점에 정확히 워크트리 하나에서만 일하고, 활성 상태인 두 에이전트가 같은 워크트리를 쓰지 않는다. 이 문서는 이 격리 원칙이 주는 보장과, 원칙이 닿지 않는 경계를 설명한다.

---

## 1. 원칙이 주는 세 가지 보장

| 보장 | 의미 |
|---|---|
| 파일 격리 | 에이전트가 작업 중에 쓴 내용은 커밋하고 명시적으로 병합(또는 cherry-pick)하기 전까지 다른 에이전트에게 보이지 않는다. |
| 인덱스 격리 | 워크트리마다 스테이징 영역이 따로라서, 한 에이전트의 `git add`와 `git commit`이 다른 에이전트의 스테이징 상태를 건드리지 못한다. |
| 브랜치 잠금 | 다른 워크트리에서 이미 체크아웃한 브랜치는 git이 체크아웃을 거부한다. 에이전트끼리 브랜치 포인터를 실수로 덮어쓸 수 없다. |

이 원칙은 에이전트를 로컬에서 돌리든, 원격 머신에서 돌리든, 컨테이너 안에서 돌리든 똑같이 성립한다. 워크트리마다 디렉터리가 서로 다르기만 하면 파일 시스템 수준의 보장이 유지된다.

## 2. 원칙이 닿지 않는 곳

워크트리 격리는 git 작업 트리 안쪽만 보호한다. 작업 트리 밖에 있는 공유 자원은 보호 대상이 아니다. 예를 들면 다음과 같다.

- SQLite 데이터베이스 파일
- 로컬 `.env` 파일
- 공유 캐시 디렉터리

이런 자원에는 에이전트 단위로 이름을 나누거나(에이전트마다 별도 데이터베이스 파일을 쓰는 식), 파일 잠금 같은 조율 장치를 따로 둬야 한다. 워크트리가 해결해 주는 것은 소스 코드 격리일 뿐이고, 범용 샌드박스가 아니라는 점을 기억해야 한다.

## 3. 빌드 도구가 만드는 바깥 쓰기

빌드 도구가 생성 파일을 워크트리 밖 디렉터리에 쓰는 경우도 같은 문제다. 저장소 루트에 있는 공유 `node_modules`나 전역 Gradle 캐시가 대표적이다. 이런 쓰기는 격리되지 않는다. 도구 캐시 경로를 워크트리 안쪽으로 고정하거나, 에이전트 ID별로 캐시 디렉터리를 나눠서 서로 오염되지 않게 해야 한다.
