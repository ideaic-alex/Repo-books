# 요약

13장의 여섯 가지 결론과, 다음 장으로 이어지는 연결을 정리한다. 앞의 문서들에서 풀어 쓴 내용을 한 번에 확인하는 용도로 쓰면 된다.

---

## 1. 여섯 가지 핵심

1. 워크트리는 클론 비용 없이 격리한다. Codex 에이전트마다 저장소의 체크아웃 화면을 따로 주면서 객체 데이터베이스는 공유한다. 중복 다운로드도, 전체 클론을 기다리는 시간도 없다.
2. 에이전트당 워크트리 하나가 핵심 규칙이다. 이 격리 원칙이 병렬 실행 중의 파일 충돌, 인덱스 손상, 브랜치 덮어쓰기를 막는다. git의 워크트리당 브랜치 하나 제약이 이를 강제한다.
3. 워크트리는 코드 상태를 격리할 뿐 실행 상태는 격리하지 못한다. 포트 충돌, 데이터베이스 충돌, 환경 변수 번짐은 워크트리 격리를 넘어 살아남는다. 워크트리별 포트 범위, 별도 데이터베이스 인스턴스, Coasts 같은 전용 도구로 런타임 격리를 더해야 한다.
4. CLI 흐름은 `git worktree add`와 `codex --cd`의 조합이다. 전용 워크트리 하위 명령은 없다. git으로 워크트리를 만들고 `--cd`로 각 에이전트를 그 안에 보낸다.
5. 병합 전략은 세 가지가 대부분을 덮는다. 순차 병합, 리베이스 병합, CI가 받쳐 주는 머지 큐 중에서 팀 규모와 히스토리 선호에 따라 고른다.
6. 동시성이 커질수록 수명주기를 자동화한다. CI에서는 작업 전에 워크트리를 만들고, 작업 뒤에 `trap ... EXIT`로 지우고, 시작할 때 prune한다. 그러면 러너 워크스페이스가 깨끗하게 유지되고 낡은 등록 정보가 쌓이지 않는다.

## 2. 더 보기와 다음 장으로의 연결

27장(하니스 엔지니어링)에서는 Symphony 하니스 구조가 대규모에서 이슈마다 git 워크트리를 격리 작업 공간으로 쓴다고 설명한다. Linear 이슈 하나에 워크트리 하나와 전용 Codex 에이전트 하나를 두고, PR이 병합된 뒤 정리하는 방식이다. 그 장에서는 WORKFLOW.md 정책, 작업 증명 요구 사항, 체크포인트 기반 상태 보존이 여기서 다룬 워크트리 격리와 어떻게 결합하는지 전체 하니스 패턴으로 보여 준다.

병렬 워크트리로 에이전트를 많이 돌리면 처리량뿐 아니라 비용도 곱절이 된다. 동시에 도는 에이전트마다 API 호출이 늘어나기 때문이다. 다음 장은 이 두 번째 예산을 다룬다. Codex CLI 사용 한도(쿼터)가 어떻게 동작하는지, 팀 워크플로의 비용을 어떻게 추정하는지, 병렬 실행이 청구서 폭탄으로 번지지 않게 하는 통제와 모니터링을 어떻게 만드는지를 살펴본다.
