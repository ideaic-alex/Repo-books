# 팀 규모별 워크트리 패턴

팀이 커지고 동시에 돌리는 에이전트가 늘수록 워크트리 운영 방식도 달라진다. 원서의 표 13-1은 그 흐름을 규모별로 요약한다. 이 문서는 표의 내용을 새로 구성해 보여 주고, 표가 말하려는 공통 주제를 풀어 쓴다.

---

## 1. 규모별 패턴 표

| 팀 규모 | 동시 에이전트 | 워크트리 전략 | 병합 전략 | 정리 방식 |
|---|---|---|---|---|
| 1인 개발 | 1~3개 | 직접 `git worktree add` 후 `codex --cd` | 순차 `git merge --no-ff` | 직접 `git worktree remove` |
| 소규모 (2~5명) | 3~10개 | CLI의 `git worktree add`와 래퍼 스크립트 | 워크트리마다 PR, 사람이 리뷰 | PR을 닫을 때 스크립트 실행 |
| 중규모 (5~20명) | 10~30개 | CLI와 셸 fan-out | 워크트리마다 PR, 머지 큐 | 각 CI 작업 안의 정리 단계 |
| 대규모 (20명 이상) | 30개 이상 | CI 매트릭스 작업 | 머지 큐와 자동 리베이스 | `trap EXIT`와 `git worktree prune` |

## 2. 표가 말하는 것

동시성이 커질수록 수명주기를 더 많이 자동화한다는 것이 일관된 주제다. 혼자 쓸 때는 손으로 만들고 손으로 지워도 충분하다. 팀이 커지면 래퍼 스크립트와 PR 단위 리뷰가 붙고, 중규모부터는 머지 큐와 CI 정리 단계가 들어간다. 대규모에서는 CI 매트릭스, 자동 리베이스, `trap EXIT`, `git worktree prune`이 기본이 된다.

그런데 밑바탕 원시 요소는 모든 규모에서 같다. 브랜치 하나, 워크트리 하나, 에이전트 하나다.

## 3. 활용 방법

- 지금 팀이 어느 줄에 있는지 확인하고, 다음 줄에서 새로 생기는 자동화(예: 정리 단계, 머지 큐)를 미리 준비한다.
- 규모가 커져도 원칙을 바꾸지 않는다. 바뀌는 것은 사람이 하던 일을 자동화하는 정도다.
- 5명에서 20명으로 확장하는 설계는 연습 문제 5번에서 다룬다.
