# 접근성 점검 자동화

프런트엔드에서는 접근성 부채가 조용히 쌓인다. 눈으로 보는 점검은 눈에 띄는 문제를 잡고, 자동 린터는 그것과 일부 겹치지만 다른 문제를 잡는다. 어느 쪽도 전부를 잡지 못하고, 어느 쪽도 재현 가능한 점검 기록을 남기지 않는다. axe-core를 Codex CLI와 묶으면 넓은 커버리지, 반복 가능성, diff로 비교하기 좋은 보고서를 얻는다. 이 문서는 Vitest 수준과 브라우저 수준의 두 가지 점검, 그리고 이를 스킬로 만드는 방법을 정리한다.

---

## 1. axe-core란

axe-core는 Deque Systems가 관리하는 접근성 테스트 엔진으로, 위반 사항을 WCAG 2.1과 2.2 기준에 연결해 준다. 2015년에 오픈소스가 됐고 WCAG 2.0, 2.1, 2.2의 A, AA, AAA 수준을 다루며, 구글 Lighthouse의 접근성 점검이 쓰는 엔진이기도 하다. 연동은 두 가지다. `jest-axe`는 이름과 달리 Vitest에서 동작하고, `@axe-core/playwright`는 브라우저 수준 점검에 쓴다.

## 2. Vitest 수준 점검

컴포넌트를 렌더링하고 axe를 돌려 위반이 없는지 단언한다.

```tsx
import { render } from '@testing-library/react'
import { axe, toHaveNoViolations } from 'jest-axe'
import { expect } from 'vitest'
import { DepartureBoard } from '../components/DepartureBoard'
expect.extend(toHaveNoViolations)
it('DepartureBoard has no accessibility violations', async () => {
  const { container } = render(
    <DepartureBoard departures={mockDepartures} /> )
  const results = await axe(container)
  expect(results).toHaveNoViolations()
})
```

참고로 원서의 이 예시는 DepartureBoard에 departures props를 넘기는데, 앞 절에서 만든 DepartureBoard는 station을 받는 컨테이너다. 원서 코드를 그대로 옮긴 것이므로 실제로 적용할 때는 컴포넌트 시그니처에 맞춰야 한다.

## 3. accessibility-audit 스킬

이 패턴을 반복 가능하게 만들려면 `.agents/skills/accessibility-audit/SKILL.md`를 만든다. 스킬이 시키는 일은 여섯 단계다.

1. 요청에 이름이 나온 컴포넌트 파일마다 /tests/에 axe-core 테스트가 이미 있는지 확인한다.
2. 없으면 /tests/DepartureBoard.test.tsx의 패턴대로 하나 만든다.
3. `pnpm test --reporter=verbose`를 돌려 axe 위반을 수집한다.
4. 위반마다 어긴 WCAG 기준, 문제를 일으킨 구체적 요소, 권장 수정을 보고한다.
5. 심각도가 "critical"이나 "serious"인 위반은 고친다.
6. 점검을 다시 돌려 위반이 해결됐는지 확인한다.

컴포넌트나 디렉터리를 대상으로 부른다. 예를 들면 `codex "$accessibility-audit — audit all components in /components/forms/"`다.

## 4. 브라우저 수준 점검

jsdom 기반 테스트가 놓치는 문제가 있다. 색 대비와 포커스 트랩 동작이 대표적이다. 이런 것은 스킬에 `@axe-core/playwright`를 쓰는 Playwright 단계를 더해 잡는다.

```ts
// e2e/accessibility.spec.ts
import { test, expect } from '@playwright/test'
import AxeBuilder from '@axe-core/playwright'
test('settings page has no critical accessibility violations', async ({ page }) => {
  await page.goto('/settings')
  const results = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa'])
    .analyze()
  expect(results.violations.filter(v => v.impact === 'critical')).toHaveLength(0)
})
```

이 예에서는 WCAG 2 A와 AA 태그만 검사하고 영향도가 critical인 위반이 0건이어야 통과한다.

## 5. CI와 경로 전체 점검

릴리스에 들어가는 모든 페이지에 대해 axe-core Playwright 점검을 CI에서 돌린다. 라우트 트리 전체의 초기 테스트 묶음도 프롬프트 하나로 Codex CLI가 만들어 줄 수 있다. 책이 드는 문장은 "`$accessibility-audit`로 /app/ 아래 모든 페이지의 Playwright axe 테스트를 쓰고 개발 서버를 대상으로 돌려라"다.
