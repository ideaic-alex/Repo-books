# 연습 문제

23장 끝의 연습 문제 다섯 개를 취지 중심으로 풀어 쓰고, 풀이 방향을 덧붙였다. 모두 직접 손으로 해 보는 실습이다.

---

## 1. 내 프로젝트용 프런트엔드 AGENTS.md

직접 관리하는 React 프로젝트를 하나 고른다. 이 장의 다섯 질문에 답하는 AGENTS.md를 쓰고, 명령이 최소 세 개 들어간 완료 기준 섹션을 더한다. 그런 다음 Codex에게 스캐폴딩 작업을 시키고, AGENTS.md가 막아 준 관례 위반과 놓친 관례 위반을 구분해서 기록한다.

풀이 방향: 놓친 위반은 AGENTS.md에 없는 규칙일 가능성이 높다. 기록한 놓친 항목을 다음 판에 규칙으로 되돌려 넣으면 문서가 점점 정확해진다.

## 2. 탐색자/작업자 패턴

새 UI 화면과 새 API 엔드포인트가 함께 필요한 기능을 하나 찾는다. 탐색자 하나(데이터 모양과 제약 보고), 프런트엔드와 백엔드를 병렬로 구현하는 작업자 둘, e2e 테스트를 쓰는 작업자 하나로 서브에이전트 프롬프트를 작성한다. Codex 세션에서 실제로 돌려도 되고, 각 작업자가 어떤 컨텍스트를 필요로 하고 탐색자 보고서를 어떻게 구성해야 하는지 분석해도 된다.

풀이 방향: 탐색자 보고서에 "응답 모양, 타입, 레이아웃 제약"처럼 작업자가 그대로 입력으로 쓸 항목을 정해 두고, e2e 작업자는 앞의 둘이 끝난 뒤에 돌도록 순서를 명시한다.

## 3. 접근성 점검 파이프라인

이 장의 `$accessibility-audit` 스킬을 만들어 컴포넌트 세 개에 돌린다. 컴포넌트마다 Vitest(jsdom) 실행에서 axe-core가 잡는 위반과 Playwright(브라우저) 실행에서 잡는 위반을 나눠 적는다. 브라우저 수준에서만 잡힌 위반을 하나 골라, jsdom이 왜 놓쳤는지 설명한다.

풀이 방향: 색 대비나 포커스 트랩처럼 실제 렌더링과 레이아웃, 스타일 계산이 필요한 문제는 jsdom이 그리지 못해서 놓친다는 점을 근거로 삼는다.

## 4. 디자인에서 코드로

만들어야 할 UI 컴포넌트의 스크린샷을 찍는다. Codex CLI의 비전 입력으로 초기 구현을 만들게 한 뒤, 원본과 세 가지 축으로 비교한다. 구조 정확도(계층과 중첩), 시각 충실도(간격, 색, 타이포그래피), 접근성(ARIA 속성, 키보드 탐색)이다. 어느 축이 가장 정확했고 어느 축이 가장 많은 수정을 필요로 했는지 가려낸다.

풀이 방향: 본문이 구조적 레이아웃은 정확하고 간격 토큰은 수동 확인이 필요하다고 했으므로, 결과가 그 말과 맞는지 확인해 본다. 접근성은 이미지에 안 보이는 상태라 보통 약하다.

## 5. TypeScript 가드레일

파일을 쓸 때마다 `pnpm tsc --noEmit`을 돌리는 PostToolUse 훅을 TypeScript 프로젝트에 추가한다. 매처는 파일 편집 도구에 맞춘다. 일부러 타입 오류가 있는 함수를 Codex에게 쓰게 해서 시험한다. 훅이 실행되는지, 오류가 에이전트에게 보이는지, Codex가 작업을 마치기 전에 스스로 고치는지 확인한다. 훅 설정과, 그 훅이 막는 실패 패턴을 문서로 남긴다.

풀이 방향: 9장의 훅 설정 방식을 따르고, 훅의 출력이 에이전트에게 돌아가야 수정 루프가 닫힌다는 점을 확인한다. 막는 실패 패턴은 "타입 오류가 있는 채 완료로 보고하는 것"이다.
