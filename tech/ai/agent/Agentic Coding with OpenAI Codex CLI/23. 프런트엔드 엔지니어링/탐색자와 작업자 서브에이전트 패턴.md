# 탐색자와 작업자 서브에이전트 패턴

UI와 API에 걸친 기능은 기존 관례를 먼저 이해한 뒤 새 코드를 만들어야 한다. 이때 읽는 일과 쓰는 일을 서로 다른 서브에이전트에게 나눠 맡기는 것이 탐색자/작업자(explorer/worker) 패턴이다. 서브에이전트 전반은 11장에서 다루고, 이 문서는 프런트엔드 기능에 적용하는 방식과 원서의 그림을 설명한다. Codex의 서브에이전트(멀티 에이전트 워크플로)는 부모 세션이 자식 에이전트를 띄워 작업을 병렬로 돌리고, 결과를 조율하는 쪽이 돌려받는 기능이다.

---

## 1. 풀려는 문제는 컨텍스트 오염

낯선 코드베이스에 설정 페이지를 새로 만든다고 하자. Codex CLI는 레이아웃, 인증 모델, API 모양, 컴포넌트 관례를 알려고 기존 파일을 읽고, 같은 컨텍스트 윈도 안에서 새 코드를 만든다. 읽는 단계가 남긴 잡음이 생성에 쓸 수 있는 유효 컨텍스트를 줄인다. 탐색자/작업자 패턴은 이 두 단계를 서로 다른 에이전트로 가른다.

## 2. 프롬프트 예: 전광판 기능

책은 전광판 기능을 이렇게 나눈다. 기능은 "역에서 출발하는 다음 열차를 RUN 또는 relax 판정과 함께 보여 주고, 폴링으로 갱신하는 페이지"다.

| 역할 | 실행 시점 | 맡은 일 |
| --- | --- | --- |
| 탐색자 | 먼저 | 22장의 Departure 타입과 `GET /departures`, `/lib/departures.ts`, 기존 `/components/DepartureRow.tsx`를 읽는다. 응답 모양, verdict 유니온, 이미 있는 행 props를 보고한다. |
| 작업자 1 | 탐색자 다음 | 탐색자의 결과를 받아 `/app/departures/page.tsx`, 폴링하는 `<DepartureBoard>` 컨테이너, DepartureRow를 조합하는 `<DepartureBoardView>`를 만든다. |
| 작업자 2 | 작업자 1과 병렬 | 탐색자의 결과를 받아 `/lib/departures.ts`의 타입 데이터 계층을 쓴다. Departure 타입, API 기본 주소, 쿼리 인코딩과 선택 인자 now를 갖춘 fetchDepartures다. |
| 작업자 3 | 작업자 1과 2 다음 | 전광판 흐름의 Playwright e2e 테스트를 쓴다. RUN 상태, relax 상태, API에 닿지 못할 때의 에러 상태, "no more trains today" 빈 상태를 다룬다. |

## 3. 그림 23.1 읽기

> 원서 그림 설명(약 486쪽, 글로 풀어 씀): 그림 23.1 탐색자/작업자 서브에이전트 패턴. 맨 위 탐색자 상자에서 구조화된 보고서가 아래로 내려가 병렬로 도는 작업자 1, 작업자 2로 갈라지고, 두 작업자에서 화살표가 모여 맨 아래 작업자 3으로 이어진다.

그림 23.1은 위 표를 흐름도로 그린 것이다. 그림 속 글자는 영어 그대로다. 읽는 방법은 다음과 같다.

- 맨 위 상자는 탐색자다. `GET /departures` 계약, 데이터 계층, DepartureRow를 읽고 응답 모양, verdict 유니온, 행 props를 보고한다고 적혀 있다.
- 탐색자 아래 선에 "structured report as clean input"이라는 말이 붙어 있다. 구조화된 보고서가 작업자들에게 깨끗한 입력으로 전달된다는 뜻이다.
- 가운데 줄에는 병렬로 도는 작업자 둘이 나란히 있다. 왼쪽 작업자 1은 전광판 페이지와 DepartureBoard(행을 조합하고 폴링)를 만든다. 오른쪽 작업자 2는 타입이 붙은 데이터 계층과 "API proxy route"를 맡는다고 적혀 있다.
- 두 작업자에서 나온 화살표가 맨 아래 작업자 3으로 모인다. 작업자 3은 작업자 1과 2가 끝난 뒤 전광판 흐름의 Playwright e2e 테스트를 쓴다.

참고로 그림 속 작업자 2 상자의 "API proxy route"는 본문과 맞지 않는다. 본문과 AGENTS.md는 전광판이 백엔드를 브라우저에서 직접 호출한다고 설명하고 프록시 라우트를 만들지 않기 때문이다. 그림 아래 원서의 대체 설명도 작업자 2를 타입 데이터 계층(Departure 타입과 fetchDepartures)으로만 적고 있어서, 그림 쪽 문구가 앞선 판의 흔적으로 보인다. 이 노트는 본문 기준을 따랐다.

## 4. 왜 이 순서인가

탐색자는 구조화된 보고서(응답 모양, verdict 유니온, 기존 행 props)를 낸다. 작업자 1과 2는 그 보고서를 깨끗한 입력으로 받는다. 두 작업자는 UI와 데이터 계층이라는 서로 다른 관심사를 맡으므로 병렬로 돌려 걸리는 시간을 줄인다. 작업자 3은 마지막에 돈다. 의미 있는 테스트를 쓰려면 실제 구현이 있어야 하기 때문이다.

## 5. 언제 쓰고 언제 쓰지 않는가

단순한 컴포넌트 추가에는 과하다. 다음 경우에 쓴다.

- 작업이 여러 하위 시스템(UI, API, 데이터베이스 스키마)에 걸칠 때
- 관례를 읽는 데 컨텍스트를 많이 쓸 때
- 병렬 실행이 테스트할 수 있는 결과까지 가는 시간을 크게 줄일 때

탐색자의 결과물은 질문의 질만큼 쓸모가 있다. "코드베이스를 읽고 뭐가 있는지 알려 줘"는 요약을 낳는다. "인증 레이아웃과 사용자 타입을 읽고 데이터 모양과 레이아웃 제약을 보고해"는 명세를 낳는다. 뒤쪽이 작업자에게 한 번에 제대로 생성할 구조화된 입력을 준다.
