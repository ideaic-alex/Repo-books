# 프로젝트 만들기와 막힘 해결

22장에서 만든 run-or-relax/ 저장소에는 src/ 아래 FastAPI 서비스가 있다. 전광판은 같은 저장소의 frontend/ 디렉터리에 둔다. 파이썬이 아닌 Node 프로젝트이므로 두 툴체인이 부딪치지 않는다. 이 문서는 스캐폴드(뼈대 생성) 명령, 에이전트에게 맡기는 설정 프롬프트, 도구 변화 때문에 막혔을 때의 복구표를 정리한다.

---

## 1. 툴체인 확인과 스캐폴드

최근 Node에서는 Corepack을 켜기 전까지 pnpm이 PATH에 안 잡힐 수 있다. 그래서 먼저 확인한다.

```bash
node --version
corepack enable pnpm
pnpm --version
```

그다음 저장소 루트에서 프로젝트를 만든다.

```bash
cd run-or-relax
pnpm create next-app@latest frontend --typescript --app --tailwind --eslint --use-pnpm
cd frontend
pnpm dlx shadcn@latest init --defaults --yes
pnpm add -D vitest @testing-library/react @testing-library/user-event jsdom @vitejs/plugin-react
pnpm add -D @playwright/test jest-axe @axe-core/playwright
```

이 명령들은 빠르게 변하는 도구를 따라가므로 어긋남이 생길 수 있다는 점을 염두에 둔다.

- `@latest`가 AGENTS.md의 스택 줄에 적은 것보다 새로운 Next 메이저를 설치할 수 있다. 버전을 고정하지 말고 스캐폴드가 깐 버전을 그대로 쓰고 스택 줄을 맞춰 고친다. 이 장의 관례는 정확한 버전에 의존하지 않는다.
- shadcn init의 비대화형 플래그도 릴리스마다 바뀐다. 그래도 질문이 뜨면 `--force`를 붙이거나 현재 `--help`를 확인한다.
- create-next-app은 자기 AGENTS.md와 CLAUDE.md를 프로젝트에 넣는다. 덮어쓰지 말고, 앞에서 만든 설정에 그쪽의 버전별 주의사항을 합쳐 넣는다.

오프라인이나 제한된 세션이라 create-next-app을 못 돌리고 구조를 손으로 만든다면, 스캐폴드가 대신 깔아 주던 타입 패키지를 직접 추가해야 한다.

```bash
pnpm add -D @types/react @types/node
```

이게 없으면 `pnpm tsc --noEmit`이 바로 실패한다. 또 `next build`가 빌드 도중 자동으로 설치하게 두면 pnpm 스토어 설정과 충돌한다. 스캐폴드가 숨겨 주던 의존성을 수동 경로에서는 직접 적어야 한다는 얘기다.

## 2. 설정 파일 만들기를 에이전트에게 맡기기

병합한 AGENTS.md를 frontend/AGENTS.md에 둔다. 그러면 Codex CLI가 여기서 실행하는 모든 명령이 이 관례를 물려받는다. 같은 세션에서 테스트 설정도 만들게 하는데, 두 테스트 도구가 충돌하지 않도록 러너 경계를 프롬프트에 명시한다.

- vitest.config.ts: jsdom 환경, tests/setup.ts 설정 파일, 그리고 e2e/**, node_modules/**, .next/**, out/**를 제외해서 Vitest가 Playwright 스펙을 읽지 않게 한다.
- playwright.config.ts: e2e/**만 실행한다.
- package.json: "test"는 Vitest, "test:e2e"는 Playwright를 돌린다.

전광판은 서버 런타임이 없으므로 같은 세션에서 정적 내보내기도 설정한다.

- next.config.ts: `output: "export"`로 두어 `pnpm build`가 정적 out/ 디렉터리를 만들게 한다. 그리고 `turbopack.root`를 이 frontend/ 디렉터리로 지정해서, 빌드가 상위의 락파일을 워크스페이스 루트로 잘못 추정하지 않게 한다.
- app/layout.tsx: 스캐폴드가 넣은 next/font/google(Geist) 임포트를 시스템 폰트 스택으로 바꿔서, 빌드 때 구글에서 폰트를 받아 오지 않게 한다. 빌드 중 네트워크 호출이 없어야 한다는 조건이다.

이렇게 하면 `pnpm build`가 전광판을 out/에 쓴다. 이 out/은 24장이 정적 자산으로 서빙하는 디렉터리다. 결과 트리는 AGENTS.md의 아키텍처 섹션이 설명한 모양이다.

```text
run-or-relax/
├── src/departures/   # 22장 FastAPI 서비스
├── data/             # 시드 시간표와 지연 정보
└── frontend/
    ├── AGENTS.md, app/departures/page.tsx
    ├── components/ (DepartureRow, DepartureBoard,
    │                DepartureBoardView)
    ├── lib/departures.ts   # 타입 계약과 fetch
    └── tests/, e2e/        # Vitest, Playwright
```

DepartureBoard는 데이터 가져오기와 폴링을 맡는 컨테이너이고, DepartureBoardView는 화면만 그리는 프레젠테이션 컴포넌트다.

## 3. 막힘 복구표

위 프롬프트대로 따라 하면 사람 손 없이 초록불 `pnpm build`에 닿아야 한다. 그래도 프런트엔드 스캐폴드는 이 스택에서 도구 변화에 가장 취약한 부분이라 어딘가에서 안 먹힐 수 있다. 플래그가 릴리스 사이에 바뀌거나, 선행 조건 전에 명령이 돌기도 한다. 아래 표는 눈에 보이는 증상에서 에이전트에게 건넬 한 줄 처방을 찾게 만든 복구표다.

| 증상 | 원인 | 처방 |
| --- | --- | --- |
| `pnpm: command not found` | Corepack이 아직 pnpm 실행 파일을 연결하지 않았다 | 첫 명령 전에 `corepack enable pnpm` |
| shadcn init이 계속 질문한다 | 비대화형 플래그가 릴리스마다 바뀐다 | `--force`를 붙이거나 `--help`로 현재 플래그 확인 |
| `pnpm test`가 "Playwright Test did not expect test() to be called here"로 실패 | Vitest가 e2e/ 스펙을 읽고 있다 | vitest.config.ts에서 `e2e/**` 제외 |
| 빌드가 상위 락파일을 워크스페이스 루트로 추정했다고 경고 | frontend/ 위에 락파일이 여러 개 있다 | next.config.ts에서 `turbopack.root`를 frontend/ 디렉터리로 지정 |

스캐폴드를 설정하고 관례를 적고, 알려진 함정을 프롬프트로 미리 막았거나 표로 답할 수 있게 되면, 프로젝트는 초록불 `pnpm build` 상태이고 에이전트는 추측 없이 일할 재료를 갖춘 셈이다. 이 장의 나머지는 이 트리에, 이어지는 프롬프트들이 하나씩 생성해 넣는다. 첫 번째는 전광판이 그리는 데이터 계약이다.
