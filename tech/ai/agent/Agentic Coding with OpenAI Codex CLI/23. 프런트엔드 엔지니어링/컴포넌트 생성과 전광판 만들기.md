# 컴포넌트 생성과 전광판 만들기

AGENTS.md가 갖춰지면 컴포넌트 스캐폴딩은 Codex CLI가 가장 믿을 만하게 해내는 작업 중 하나가 된다. 이 문서는 컴포넌트 하나를 만드는 프롬프트의 구조, 반복 패턴을 스킬로 굳히는 방법, 그리고 전광판을 뷰와 컨테이너 두 컴포넌트로 나눠 만드는 과정을 다룬다.

---

## 1. 프롬프트에 넣을 것

프롬프트에는 에이전트가 추측으로 채울 만한 맥락을 모두 넣는다. 파일 위치, props, 상태, 같이 만들 테스트다. 책의 예는 DepartureRow 컴포넌트다.

- 위치는 `/components/DepartureRow.tsx`, props는 `Departure` 하나다(타입은 lib/departures.ts).
- 출발 시각, 승강장, 지연(0이면 숨김), 남은 분을 보여 준다.
- 판정은 배지로 그린다. verdict가 "RUN"이면 눈에 띄고 대비가 큰 `run` 변형, "relax"면 `calm` 변형이다.
- verdict가 "RUN"이면 행을 강조한다. 문 앞에서 승강장까지 가는 규칙은 백엔드가 이미 판정에 담았으므로, 행이 임계값을 다시 계산하면 안 된다.
- shadcn/ui 기본 부품을 쓰고, 키보드만으로 완전히 쓸 수 있어야 하며, 판정 배지에는 접근 가능한 레이블을 단다. TypeScript strict에 `any`는 쓰지 않는다.
- `/tests/DepartureRow.test.tsx`에 Vitest 테스트를 쓴다. RUN 행, relax 행, 지연 0인 경우, 접근 가능한 레이블을 다룬다.

구체성이 결과를 가른다. "판정을 보여 줘"와 "verdict가 "RUN" | "relax"일 때 각각 run 변형과 calm 변형을 쓰는 배지"는 다른 결과를 낳는다. 뒤쪽은 틀리게 추측하면 후속 수정이 필요했을 결정 지점을 미리 없앤다. 그리고 그 props가 22장에서 온 판별 유니온이므로 컴포넌트는 구성상 빠짐없이 처리하고, 세 번째 판정이 생기면 여기서 타입 검사가 실패한다.

## 2. 반복 패턴은 스킬로

폼 필드, 모달 대화상자, 데이터 가져오기 래퍼처럼 같은 모양의 컴포넌트를 되풀이해 만드는 팀이라면, 패턴을 스킬에 넣어 프롬프트마다 관례를 다시 적는 수고를 없앤다. `.agents/skills/new-component/SKILL.md`는 이렇게 쓴다.

```markdown
---
name: new-component
description: Scaffold a new React component with co-located test file
---
# New Component Skill
1. `/components/<Name>.tsx` — props interface, Tailwind, named export
2. `/tests/<Name>.test.tsx` — Vitest + Testing Library test
3. Add named export to `/components/index.ts`
4. Follow all AGENTS.md conventions
Do not create a Storybook story unless the user explicitly asks.
```

호출은 프롬프트를 거의 쓰지 않고 한다. 예를 들어 `codex "$new-component — BirthdayBanner component that takes a name and an age and renders a celebratory message"`처럼 이름과 입력만 준다. 책 예시는 이름과 나이를 받아 "Happy 4th Birthday Alex" 같은 축하 문구를 그리는 BirthdayBanner다.

스킬의 마지막 줄, Storybook 스토리를 요청 없이 만들지 말라는 문장은 잔소리가 아니다. 이 줄이 없으면 Codex CLI는 학습 데이터에 그 패턴이 자주 나오기 때문에 시키지 않은 스토리를 가끔 만들어 낸다. 스킬에 부정 지시를 명시해 두면 이런 선의의 범위 이탈을 막는다.

## 3. 전광판을 두 컴포넌트로 나누기

lib/departures.ts에 계약이 있으니 전광판을 두 컴포넌트로 만든다. 렌더링만 하는 순수 뷰와, 가져오고 폴링하는 컨테이너다. 이렇게 나누면 뷰는 테스트하기 아주 쉽고, 까다로운 비동기(로딩, 에러, 폴링 타이머)는 한곳에 격리된다.

**DepartureBoardView** (`/components/DepartureBoardView.tsx`)

- `departures: Departure[]`를 받는다.
- 출발 하나마다 DepartureRow를 하나씩 그린다.
- 빈 목록이면 빈 상태 문구("no more trains today")를 보여 준다.
- 순수하고 표현만 담당한다. 가져오기도 상태도 없다.

**DepartureBoard** (`/components/DepartureBoard.tsx`, `"use client"`)

- `station: string`을 받는다.
- `fetchDepartures(station)`을 호출하고 30초마다 다시 폴링한다.
- 처음에는 로딩 스켈레톤, fetch가 던지면 에러 상태, 데이터가 오면 눈에 보이는 마지막 갱신 시각을 보여 준다.
- 결과를 DepartureBoardView에 넘긴다.
- shadcn/ui 기본 부품, TypeScript strict, 키보드 접근성을 따른다.

테스트도 같은 프롬프트에서 시킨다. 뷰는 RUN 행, relax 행, 빈 상태를 다룬다. 컨테이너는 mock한 fetchDepartures로 로딩 후 로드 경로, 거부된 fetch에서의 에러 상태, 폴링 간격에 따라 마지막 갱신 시각이 넘어가는지를 다룬다. fireEvent 대신 Testing Library의 userEvent와 가짜 타이머(fake timers)를 쓰고, 고정된 `now`를 넘겨서 어떤 테스트도 실제 시계에 기대지 않게 한다.

## 4. 왜 이렇게 나누는가

컨테이너가 잘못될 수 있는 모든 것(로딩, 폴링, 실패)을 맡고, 뷰는 departures props의 순수 함수로 남는다. 그래서 RUN 배지가 그려지는지 증명하는 테스트가 fetch mock을 세울 필요가 없다. 컨테이너를 일부러 클라이언트 컴포넌트로 둔 이유도 있다. 정적 내보내기에는 서버 런타임이 없어서 폴링과 `NEXT_PUBLIC_DEPARTURES_API_URL` 읽기가 모두 브라우저에서 일어난다. 판정 타입을 22장과 공유하므로 뷰의 경우의 수는 두 상태에서 그대로 나오고, 백엔드가 나중에 세 번째 판정을 내놓으면 아무것도 안 그리는 대신 `pnpm tsc --noEmit`이 여기서 실패한다. 한 가지 모양을 네트워크 양쪽에서 거울처럼 맞춰 두는 계약이 프런트엔드에서 일을 하는 순간이다.

## 5. 페이지와 실행

전광판을 올리는 페이지는 얇은 껍데기다. `/app/departures/page.tsx`가 `<DepartureBoard station="audley-end" />`를 렌더링하게 시킨다.

두 쪽을 함께 돌리려면 백엔드 저장소에서 `uv run uvicorn departures.app:app --reload`, frontend/에서 `pnpm dev`를 실행한다. 그러면 localhost:3000/departures에 Audley End 전광판이 뜨고, 열차마다 RUN 또는 relax가 붙으며 30초마다 새로고침된다.

주의할 점이 있다. 시드 시간표에는 아침 출발만 들어 있어서, 오후에 돌리면 전광판이 "no more trains today"를 정상적으로 보여 준다. 일정을 모르면 데이터 경로가 고장 난 것처럼 보인다. 어느 시간대에든 RUN과 relax 행을 보고 싶으면, 데이터 계층이 이미 받는 결정적 `now` 덮어쓰기(테스트가 쓰는 것과 같은 ISO 8601 훅)에 아침 시각을 넘겨 전광판이 그 시각을 기준으로 삼게 한다.
