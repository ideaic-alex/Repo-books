# 요약

23장의 핵심을 여덟 가지로 정리한다. 앞의 문서들에서 풀어 쓴 내용을 한 번에 훑어보는 용도로 쓴다.

---

## 1. 여덟 가지 요점

1. **프런트엔드 AGENTS.md는 다섯 질문에 답한다.** 패키지 매니저, React 버전과 허용 패턴, 컴포넌트 라이브러리 설치 방법, 테스트 프레임워크, 파일 시스템 경계다. 이게 없으면 Codex는 그럴듯하지만 틀린 가정으로 돌아간다.
2. **완료 기준은 에이전트를 스스로 고치게 만든다.** `pnpm build`, `pnpm test`, `pnpm tsc --noEmit`을 적어 두면 Codex CLI가 셋 다 통과할 때까지 반복한다.
3. **반복 패턴은 스킬에 담는다.** `$new-component`나 `$playwright-check` 같은 스킬은 프롬프트마다 관례를 다시 적는 수고를 없애고, 범위 이탈을 줄인다.
4. **탐색자/작업자 패턴은 발견과 생성을 나눈다.** 여러 하위 시스템에 걸친 기능이나, 컨텍스트 오염이 생성 품질을 떨어뜨릴 만한 기능에 쓴다.
5. **axe-core는 접근성 점검을 재현 가능하게 한다.** Vitest에서는 jest-axe, 종단 간 테스트에서는 @axe-core/playwright로 연동하며, WCAG에 연결된 점검을 Codex CLI가 한 세션에서 만들고, 돌리고, 고칠 수 있다.
6. **디자인에서 코드로 가는 길은 두 가지다.** Figma의 MCP 서버는 책을 쓰던 시점에 베타다. 비전 기반 흐름은 구조적 레이아웃을 정확히 다루지만 간격 토큰은 수동 확인이 필요하다. 작업 유형별 권장 패턴은 표 23-2에 정리돼 있다.
7. **Codex 브라우저 사용은 빌드와 검증 루프를 닫는다.** 시각 QA를 자율화하지만, 백엔드만 다루는 작업에서는 지연과 토큰 비용이 값을 못 하므로 골라서 쓴다.
8. **프런트엔드는 22장 백엔드의 얼굴이다.** `<DepartureBoard>` 컨테이너가 `GET /departures`를 직접 호출하고(기본 주소는 `NEXT_PUBLIC_DEPARTURES_API_URL`, 백엔드는 CORS 허용), 순수한 `<DepartureBoardView>`가 공유된 `"RUN" | "relax"` 유니온으로 분기한다. 그래서 계약이 양쪽에서 거울처럼 맞는다. 전광판은 정적 내보내기로 나가고, 24장이 이를 API와 함께 배포한다.

## 2. 이 장을 관통하는 생각

프런트엔드의 실수는 조용하다. 컴파일은 되는데 관례와 어긋나고, 테스트는 통과하는데 아무것도 증명하지 못하고, 화면은 뜨는데 접근성이 무너져 있다. 그래서 이 장의 모든 장치(AGENTS.md, 완료 기준, 스킬, 타입 계약, userEvent, axe-core, 브라우저 검증)는 같은 목적을 가진다. 조용한 실패를 일찍, 에이전트가 스스로 알아챌 수 있는 신호로 바꾸는 일이다.
