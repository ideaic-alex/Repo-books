# 보안 강화

에이전트가 저장소 전체를 읽고, 외부 API를 부르고, 셸 명령을 실행하게 되면 실수 한 번의 피해 범위는 에이전트에게 열어 준 권한 전체로 커진다. 이 장은 공격자가 에이전트 시스템을 어떻게 보는지, Codex CLI의 어떤 기능이 에이전트가 건드릴 수 있는 범위를 좁혀 주는지, 컴플라이언스와 사고 대응이 요구하는 감사 기록을 어떻게 만드는지 다룬다.

원서의 그림 두 장(프롬프트 인젝션 방어 계층, 운영체제 수준 샌드박스 구조)도 해당 문서에 함께 실었다. 핵심 발상은 에이전트의 판단을 믿기보다, 시스템 쪽에서 에이전트의 권한을 겹겹이 제한하라는 것이다.

---

## 1. 핵심 요점

- 에이전트는 자산이 넓고, 공격이 요청이 아니라 읽는 콘텐츠로 들어오며, 설정 실수로 스스로 위협이 되기도 한다.
- 프롬프트 인젝션은 단일 방어로 막을 수 없다. PreToolUse 훅, 출력 리뷰, 좁은 컨텍스트, 경로 허용 목록을 겹쳐 쌓되 확률적인 마찰로 본다.
- 샌드박스는 macOS, Linux, Windows에서 각각 커널 수준으로 강제된다. 다만 읽기 제한은 커널이 아니라 도구 계층의 deny_read가 맡는다.
- 자동 리뷰는 L0(관찰)에서 시작해 한 주기에 한 단계씩 L3(강제)까지 올린다. 이 사다리는 저자의 제안이며 Codex 기능이 아니다.
- CI에서는 `--ignore-user-config`와 `--ignore-rules`로 재현 가능한 실행을 만들고, 관리형 설정은 그대로 적용된다.
- 네트워크는 관리형 허용 목록으로 기본 거부하고, MCP 서버는 소스를 검토한 뒤 필요한 호스트만 연다.
- 시크릿은 설정 파일에 넣지 않고 환경 변수나 시크릿 매니저로 주입하며, shell_environment_policy와 PostToolUse 스캐너로 새는 것을 막는다.
- 감사 로그와 통제 대응표는 SOC 2, GDPR, ISO 27001 검토의 출발점이고, 열두 항목 체크리스트로 배포 전에 점검한다.
