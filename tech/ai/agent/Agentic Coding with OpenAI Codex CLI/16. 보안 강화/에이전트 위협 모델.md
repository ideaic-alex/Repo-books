# 에이전트 위협 모델

15장에서 Codex CLI는 CI/CD 파이프라인 안으로 들어가 사람 없이 돌게 됐다. 이 변화는 어느 실행 방식에나 있던 문제를 더 날카롭게 만든다. 에이전트가 저장소의 모든 파일을 읽고, 외부 API를 부르고, 셸 명령을 대신 실행하는 상황에서는 실수 하나가 미치는 피해 범위가 에이전트에게 열어 준 권한 전체로 커진다.

이 문서는 보안 논의의 출발점인 위협 모델을 다룬다. 일반 웹 애플리케이션과 에이전트 시스템이 어떻게 다른지, 위협 종류마다 어떤 방어 수단이 대응하는지를 정리한다.

---

## 1. 위협 모델이 묻는 세 가지

보안 위협 모델링은 세 가지를 묻는다. 무엇이 위험에 놓여 있는가(자산), 누가 공격할 수 있는가(공격자), 어떤 경로로 들어오는가(경로)이다.

전통적인 웹 애플리케이션이라면 자산은 데이터베이스의 데이터이고, 공격자는 바깥의 클라이언트이며, 경로는 HTTP 엔드포인트다. Codex CLI를 쓰는 에이전트 환경은 이 그림이 세 군데에서 달라진다.

## 2. 달라지는 세 가지

**자산이 훨씬 넓다.** 에이전트는 소스 코드를 읽을 수 있고, 파일 시스템에 쓸 수 있고, 셸에서 명령을 실행할 수 있다. MCP 서버를 연결했다면 사내 API, 클라우드 제공자, 외부 서비스까지 네트워크로 닿는다. 공격이 성공하면 코드베이스 전체가 밖으로 빠져나가거나, 악성 커밋이 푸시되거나, 클라우드 자격 증명으로 번져 갈 수 있다.

**공격이 요청이 아니라 콘텐츠로 들어온다.** 웹 앱에서는 공격자가 조작한 HTTP 요청을 보낸다. 에이전트에게는 에이전트가 읽는 모든 글이 공격 표면이다. 악의적인 기여자가 쓴 README, 의존 패키지의 CHANGELOG, 외부 패키지 레지스트리에서 받은 테스트 픽스처, GitHub 이슈 본문이 모두 해당한다. 에이전트는 이런 글을 신뢰하는 컨텍스트로 받아들이기 때문에, 소스 파일 속에 교묘하게 심은 문자열이 곧 명령이 될 수 있다.

**에이전트 자신이 위협이 될 수 있다.** 권한을 잘못 설정했거나, 도구 구현에 버그가 있거나, 모델이 예상 밖의 응답을 하면 운영자가 의도하지 않은 행동을 하게 된다. 파일을 지우고, 환경 변수를 밖으로 내보내고, 개발용 샌드박스에서 운영 API를 호출하는 식이다.

## 3. 위협과 방어 대응표

위협 종류별로 공격 경로와 1차 방어를 짝지으면 다음과 같다.

| 위협 | 공격 경로 | 주된 방어 |
|---|---|---|
| 프롬프트 인젝션 | 파일, 이슈, 도구 출력에 숨은 악성 내용 | 입력 검증 훅, 출력 리뷰 패턴 |
| 자격 증명 유출 | 에이전트가 .env를 읽고 시크릿을 stdout에 출력 | 시크릿 관리, 파일 시스템 범위 제한 |
| 권한 상승 | 높은 권한을 가진 셸 훅이나 MCP 서버 | 최소 권한 도구 부여, 네트워크 허용 목록 |
| 횡적 이동 | 침해된 MCP 서버가 내부 API를 호출 | 네트워크 허용 목록, MCP 서버 검토 |
| 감사 회피 | 에이전트의 행동이 기록되지 않음 | PostToolUse 감사 훅, 구조화된 로깅 |
| 데이터 거주지 위반 | 에이전트가 개인정보(PII)를 외부 모델이나 서비스로 전송 | 네트워크 허용 목록, 데이터 흐름 검토 |

이 표의 방어 수단은 이어지는 문서에서 하나씩 풀어 쓴다. 프롬프트 인젝션은 따로 다루고, 파일 시스템과 네트워크 제한, 시크릿, 감사는 각각 별도 문서에서 설명한다.

## 4. 읽는 순서 잡기

이 장의 학습 목표는 다섯 가지다. 위협 범주를 Codex CLI의 방어 수단과 연결하기, 파일 시스템 제한과 읽기 거부 정책과 네트워크 허용 목록 설정하기, 입력을 검증하고 시크릿을 가리고 구조화된 감사 이벤트를 내보내는 훅 작성하기, 자동 리뷰와 단계별 신뢰 사다리로 보안을 점진적으로 강제하기, 에이전트 워크로드용 CI/CD 파이프라인을 컴플라이언스 프레임워크에 비추어 평가하기다.

핵심 감각은 하나다. 에이전트의 판단을 믿고 맡기는 대신, 에이전트가 건드릴 수 있는 범위를 시스템 쪽에서 좁혀 두어야 한다.
