# 시크릿 관리

API 키, 데이터베이스 비밀번호, 개인 키, 토큰 같은 시크릿은 자격 증명 유출 공격의 가장 흔한 표적이다. 이 문서는 Codex CLI 환경에서 지킬 세 가지 규칙, 환경 변수가 하위 프로세스로 새는 것을 막는 설정, 훅으로 실수로 드러난 시크릿을 찾아내는 방법을 설명한다.

---

## 1. 세 가지 규칙

**규칙 1. AGENTS.md나 config.toml에 시크릿을 넣지 않는다.** 두 파일은 보통 버전 관리에 커밋된다. AGENTS.md에 시크릿이 있으면 git log를 볼 때마다, 그리고 에이전트가 처리하는 모든 컨텍스트 윈도에 그 값이 나타난다.

**규칙 2. 시크릿은 실행 시점에 환경 변수로 주입한다.** CI 환경의 시크릿 저장소에 넣어 두고 디스크에는 쓰지 않는다.

```yaml
# .github/workflows/codex.yml
- name: Run Codex agent
  env:
    OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
    DATABASE_URL: ${{ secrets.DATABASE_URL }}
  run: codex exec "run the migration and report results"
```

**규칙 3. 오래 떠 있는 배포에는 시크릿 매니저를 쓴다.** 환경 변수는 잠깐 도는 CI 작업에는 충분하다. 상주하는 에이전트 서비스라면 HashiCorp Vault, AWS Secrets Manager 같은 도구를 쓴다. 작업을 시작할 때 짧은 TTL(유효 시간)로 자격 증명을 동적으로 가져온다.

```bash
DB_PASS=$(vault kv get -field=password secret/agent/database)
export DB_PASS
codex exec "generate the weekly report"
unset DB_PASS
```

작업이 끝나면 `unset`으로 변수를 치우는 것까지가 한 세트다.

## 2. 환경 변수 유출 막기

config.toml의 `shell_environment_policy` 섹션은 에이전트가 띄우는 하위 프로세스에 어떤 환경 변수가 전달될지 정한다.

```toml
[shell_environment_policy]
inherit = "core"  # PATH/HOME/TERM만 상속
exclude = [
  "*_API_KEY", "*_SECRET", "*_TOKEN",
  "PASSWORD", "AWS_*", "DATABASE_URL",
]
[shell_environment_policy.set]
NODE_ENV = "development"
LANG = "en_GB.UTF-8"
```

`inherit = "core"`이면 셸에 .env 파일을 source해 둔 상태라도, Codex CLI는 그 변수를 자신이 실행하는 명령에 넘기지 않는다. 핵심 변수(PATH, HOME, TERM)만 상속하고, exclude 패턴이 자격 증명 모양의 변수를 한 번 더 걸러 낸다. `[shell_environment_policy.set]`은 NODE_ENV나 LANG처럼 명시적으로 지정하고 싶은 값을 넣는 자리다.

한계도 있다. shell_environment_policy는 하위 프로세스를 보호할 뿐, 에이전트가 .env 파일을 텍스트로 읽어 그 내용을 모델 컨텍스트에 넣는 것까지 막지는 못한다. 그래서 도구 계층에서 .env 접근을 막는 deny_read 규칙과 함께 써야 한다. deny_read는 '샌드박스와 파일 시스템 제한' 문서에서 설명했다.

## 3. 실수로 드러난 시크릿 탐지

PostToolUse 훅으로 도구 출력에서 자격 증명처럼 생긴 문자열을 검사할 수 있다.

```python
# hooks/secret_scanner.py
import json, re, sys
output = json.load(sys.stdin).get("tool_response", "")
SECRET_PATTERNS = [
    r"(?:AKIA|ASIA)[A-Z0-9]{16}",  # AWS access key
    r"-----BEGIN (?:RSA |EC )?PRIVATE KEY-----",
    r"sk-[a-zA-Z0-9]{20,}",  # OpenAI API key pattern
    r"ghp_[a-zA-Z0-9]{36}",  # GitHub PAT
]
for pattern in SECRET_PATTERNS:
    if re.search(pattern, output):
        print(json.dumps({"alert": "credential_detected",
            "pattern": pattern, "action": "redact_and_warn"}),
            file=sys.stderr)
        break
```

패턴은 순서대로 AWS 액세스 키, RSA 또는 EC 개인 키 머리말, OpenAI API 키 모양, GitHub 개인 액세스 토큰(PAT)을 찾는다. 하나라도 걸리면 경고 JSON을 stderr로 내보내고 멈춘다.

운영에서는 손으로 만든 패턴보다 관리되는 스캐너를 권한다. MIT 라이선스의 시크릿 스캐너인 Gitleaks는 stdin에서 입력을 읽고, 엔트로피 분석을 포함한 수백 개의 탐지 규칙을 갖추었으며, 시크릿을 찾으면 0이 아닌 종료 코드를 돌려준다. 그래서 PostToolUse 훅이 도구 출력을 gitleaks의 stdin으로 파이프해서 결과에 따라 행동하게 할 수 있다. 위의 패턴은 아이디어를 보여 주는 용도이고, 실제 운영에서 돌릴 것은 gitleaks다.

대가는 에이전트의 런타임이나 컨테이너에 바이너리 의존성이 하나 더 생긴다는 점이다. 같은 부류의 대안으로는 찾아낸 자격 증명이 아직 유효한지까지 검증해 주는 TruffleHog와 detect-secrets가 있다.
