# 컨텍스트 윈도 관리

컨텍스트 윈도는 지시문, 대화 기록, 도구 결과, 코드가 함께 쓰는 고정 크기의 메모리다. 모델이나 추론 강도를 잘 골라도 이 한계는 그대로이고, 파일을 읽고 도구를 부를 때마다 남은 공간이 줄어서 창이 차면 정보를 잃거나 세션이 멈춘다.

이 장은 컨텍스트가 어떻게 차는지, 채워지는 속도를 어떻게 늦추는지, 서브에이전트 위임이 어떻게 시계를 되돌리는지를 다룬다. 압축, 프롬프트 캐싱, 세션을 넘는 메모리, 컨텍스트가 일으키는 실패 유형까지 함께 정리한다.

---

## 1. 핵심 요점

- 매 턴이 전체 기록을 다시 보내므로 누적 전송량은 턴 수에 대해 대략 이차로 늘어난다. 한 세션에는 한 가지 일만 맡기고 단계 경계에서 컨텍스트를 리셋한다.
- 고정 접두부에서는 MCP와 커넥터 도구 스키마가 가장 큰 소비처다. `codex debug prompt-input`과 `/status`로 직접 재고, 안 쓰는 것은 끈다.
- `/compact`는 손실 압축이다. 꼭 지켜야 할 규칙은 AGENTS.md에 두고, 상태 보존은 PreCompact/PostCompact 훅으로 자동화한다.
- 서브에이전트 위임은 컨텍스트 전략이다. 무거운 작업은 별도 창에서 돌고 부모는 짧은 요약만 받는다. Plan Mode는 계획과 구현의 컨텍스트를 분리한다.
- 프롬프트 캐싱으로 입력 비용을 크게 줄일 수 있다. AGENTS.md와 시스템 지시를 세션 중에 바꾸지 않고, 압축은 필요할 때만 한다.
- 2단계 메모리 파이프라인(추출, 통합)이 세션을 넘는 지식을 나르고, MCP 메모리 서버가 의미 검색을 더한다. 팀 메모리는 아직 빈틈이다.
- 오염, 산만, 혼란, 충돌의 네 가지 컨텍스트 실패 유형이 있으며, 도구와 문서를 줄이는 것이 공통 처방이다.
