# 컨텍스트 실패 유형

컨텍스트가 모자라서만 문제가 생기는 것은 아니다. 컨텍스트에 무엇이 들어 있느냐에 따라서도 모델의 답이 흔들린다. 이 문서는 실제 세션에서 반복되는 네 가지 컨텍스트 실패 유형과 각각의 증상, 대응책을 정리하고, 도구를 줄이면 정확도가 오른다는 "도구 역설"을 컨텍스트 관점에서 짚는다.

---

## 1. 실패 유형 네 가지

네 가지는 각자 증상이 다르고 대응도 다르다.

### 1) 컨텍스트 오염(poisoning)

낡은 정보 때문에 모델이 자신 있게 틀린 답을 낸다. 흔한 출처는 이름이 바뀐 명령을 가리키는 오래된 AGENTS.md, 리팩터링 이전의 캐시된 파일 내용, 서버 API와 더는 맞지 않는 MCP 도구 설명이다.

대응: AGENTS.md를 정기적으로 가지치기하고(4장), 큰 리팩터링 뒤에는 세션을 다시 시작하며, 메모리 파이프라인의 diff 기반 망각을 활용한다.

### 2) 컨텍스트 산만(distraction)

관련 없는 정보가 주의를 흐린다. 모델은 모든 토큰에 주의를 대체로 고르게 나누므로, 무관한 내용이 핵심 내용과 경쟁한다.

대응: 컨텍스트 표면적을 줄인다. 좁은 작업에는 `project_doc_max_bytes = 0`을 쓰고, MCP 서버는 필요한 것으로 한정하며, 4장의 가지치기 체크리스트를 적용한다.

### 3) 컨텍스트 혼란(confusion)

서로 모순되는 정보가 들어오면 모델이 충돌을 해소해야 하고, 종종 잘못 해소한다. 가장 흔한 출처는 부모와 자식 AGENTS.md가 상충하는 지시를 주는 계층 구조다.

대응: 4장의 AGENTS.md 진단 명령으로 충돌을 찾는다. `AGENTS.override.md`를 써서 우선순위를 명시한다.

### 4) 컨텍스트 충돌(clash)

프롬프트나 AGENTS.md에 참고 구현을 넣어 두면 모델이 원칙부터 추론하지 않고 예시에 지나치게 매달릴 수 있다. 추론 모델 평가에서는 풀이가 컨텍스트에 보이면, 그 풀이가 기술적으로 맞더라도 정확도가 눈에 띄게 떨어지는 결과가 나왔다.

대응: AGENTS.md에 예시 풀이나 참고 구현을 넣지 않는다. 꼭 예시를 줘야 한다면 '참고용, 복사 금지'라고 분명히 표시하고 작업 설명과 분리한다.

## 2. 정리표

| 유형 | 증상 | 주요 대응 |
|---|---|---|
| 오염 | 낡은 정보로 자신 있게 틀림 | AGENTS.md 가지치기, 리팩터링 후 세션 재시작, diff 기반 망각 |
| 산만 | 무관한 내용이 핵심과 경쟁 | `project_doc_max_bytes = 0`, MCP 서버 한정, 가지치기 체크리스트 |
| 혼란 | 모순된 지시를 잘못 해소 | AGENTS.md 진단 명령, `AGENTS.override.md` |
| 충돌 | 예시에 과하게 매달림 | 예시 풀이를 넣지 않거나 '복사 금지'로 격리 |

## 3. 도구 역설

관련된 관찰이 하나 있다. 쓸 수 있는 도구 집합을 줄이면 에이전트의 정확도가 실질적으로 오른다. 이 도구 역설(tool paradox)은 도구 선택의 문제만큼이나 컨텍스트 관리의 문제다. MCP 서버 설명은 가장 큰 고정 비용 소비처 중 하나이고, 불필요한 서버는 하나하나가 신호 대 잡음비를 떨어뜨린다.

플랫폼 수준에서는 Codex CLI가 지연 도구(deferred tool)를 걸러 낸다. 등록은 되었지만 아직 로드되지 않은 MCP 도구는 모델의 도구 목록에 나타나지 않는다. 그래서 준비되지 않은 도구를 부르느라 토큰을 낭비할 수 없다.
