# 프롬프트 캐싱

이차 증가 문제는 실제로 존재하지만 비용이 이차로 늘어나는 것으로 곧바로 이어지지는 않는다. Codex CLI가 Responses API의 접두부 캐싱(prefix caching)을 쓰기 때문이다. 이 문서는 캐시가 어떻게 비용 구조를 바꾸는지, 어떤 습관이 캐시 적중률을 높이는지 정리한다.

---

## 1. 접두부 캐싱의 원리

특정 프롬프트 접두부가 처음 전송되면 모델은 그 접두부의 내부 키-값 상태를 계산해 캐시에 저장한다. 같은 접두부를 공유하는 다음 턴들은 캐시된 부분의 재계산을 건너뛰고, 캐시된 토큰은 캐시되지 않은 토큰보다 훨씬 싸다.

캐시가 잘 되는(적중률이 높은) 것은 다음과 같다.

1. 시스템 프롬프트(같은 세션에서는 매 턴 내용이 같다)
2. 대화 기록의 대부분(턴 사이에 바뀌지 않는 부분)

캐시가 안 되는 것은 다음과 같다.

1. 가장 최근의 사용자 메시지(항상 새것이다)
2. 가장 최근의 도구 호출 결과(항상 새것이다)

설계상의 시사점은, 세션 중에는 AGENTS.md를 안정되게 유지하라는 것이다. 세션 도중에 바꾸면 시스템 프롬프트 캐시가 무효가 되는데, 이는 보통 가장 큰 캐시 접두부이고 비용 절감의 가장 큰 몫을 담당한다. 다음 세션을 위해 AGENTS.md를 고치고 싶다면 긴 실행 도중이 아니라 세션과 세션 사이에 한다.

## 2. 캐시에 유리한 프롬프트 구조

Codex CLI의 프롬프트 구조는 캐시 가능한 접두부를 최대로 늘리도록 일부러 짜여 있다. 가장 안정적인 내용을 맨 앞에 둔다. 시스템 지시, 도구 정의, 샌드박스 설정, 환경 컨텍스트, config의 개발자 지시, 합쳐진 AGENTS.md 내용이 먼저 오고, 그다음 사용자 질의, 그다음 늘어나는 대화 기록이 온다. 턴마다 새 메시지를 뒤에 덧붙이기만 하고 앞부분은 건드리지 않으므로, 시스템 지시부터 직전 턴의 출력까지의 접두부 전체가 바이트 단위로 동일하게 유지되어 캐시 재사용 자격을 얻는다.

가격 면에서 캐시된 입력 토큰은 현재 GPT-5 계열에서 표준 입력 토큰 가격의 약 10%로 청구된다. 90% 할인이다. 시스템 프롬프트와 도구 구성이 일관된 잘 짜인 세션이라면 첫 턴 이후 턴들의 입력 토큰 중 80~90%가 캐시에 적중한다. 세션 길이와 턴마다의 고정 접두부 대 새 내용의 비율에 따라 다르지만, 전형적인 세션에서 입력 토큰 비용의 총 70~80% 정도가 절약된다.

원서가 각주로 단 가격 예시(표준 처리 모드, 2026년 6월 기준)는 다음과 같다.

| 모델 | 입력(100만 토큰당) | 캐시된 입력(100만 토큰당) |
|---|---|---|
| GPT-5.5 | $5.00 | $0.50 |
| GPT-5.4 | $2.50 | $0.25 |
| GPT-5.4 mini | $0.75 | $0.075 |

## 3. 높은 적중률을 유지하는 습관

1. `project_root_markers`를 `config.toml`에 명시한다. 그러면 AGENTS.md 탐색이 세션 사이에 알려진 디렉터리에서 멈춘다. 예를 들어 `project_root_markers = [".git", "pyproject.toml", "package.json"]`은 프로젝트가 실제로 가진 것에 맞춰 탐색을 고정한다. 조립된 접두부가 세션마다 바이트 단위로 같아져 캐시 재사용 대상이 된다.
2. MCP 서버는 세션 중에 추가하지 말고 처음에 모두 선언한다. 비활성화한 서버도 접두부 공간을 차지하지만 캐시 안정성은 유지하므로, 제거보다 비활성화를 택한다.
3. 시스템 지시에 동적 내용을 넣지 않는다. 타임스탬프, 빌드 번호, 생성된 내용을 `config.toml` 지시에 넣으면 세션마다 캐시가 무효가 된다.
4. 압축은 현실적으로 가능한 한 늦춘다. 압축할 때마다 접두부가 리셋되어 그다음 턴에 캐시 미스가 나기 때문이다.

이 마지막 항목은 압축을 일찍 하라는 앞 문서의 조언과 균형을 잡아야 한다. 압축은 컨텍스트 공간과 캐시 적중을 맞바꾸는 일이므로, 작업의 경계에서 꼭 필요할 때 하는 것이 좋다.
