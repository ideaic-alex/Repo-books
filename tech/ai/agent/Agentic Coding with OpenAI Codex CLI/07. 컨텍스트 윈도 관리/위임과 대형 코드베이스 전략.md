# 위임과 대형 코드베이스 전략

컨텍스트 압력을 줄이는 방법은 압축만이 아니다. 이 문서는 서브에이전트 위임을 컨텍스트 관리 기법으로 보는 관점, 대형 코드베이스에서 예산을 지키는 전략, `/status`로 사용량을 지켜보는 습관, 그리고 Plan Mode로 계획과 구현의 컨텍스트를 분리하는 방법을 다룬다.

---

## 1. 위임은 컨텍스트 리셋이다

서브에이전트 오케스트레이션(여러 에이전트를 나누어 맡기고 조율하는 일) 전체는 별도 장에서 다룬다. 여기서는 위임을 의도적인 컨텍스트 관리 기법으로 본다.

하위 작업을 위해 서브에이전트를 띄우면 별도의 컨텍스트 윈도에서 돈다. 서브에이전트는 깨끗한 상태로 시작하며 내 세션이 쌓은 기록, 읽은 파일, 도구 결과를 물려받지 않는다. 위임 지시에 담아 건넨 것만 받는다. 끝나면 부모 세션에 요약을 돌려주는데, 서브에이전트가 내부에서 몇 토큰을 썼든 대개 200~800토큰이다.

서비스 파일 20개를 네 개 패키지에 걸쳐 리팩터링한다고 해 보자. 모두 인라인으로 처리하면 작업 도중에 80,000토큰에 이를 수 있다. 패키지마다 서브에이전트를 보내면 계산이 달라진다. 각자 자기 파일을 읽고, 수정하고, 테스트를 돌리고, 짧은 요약을 돌려준다. 부모는 요약 네 개를 합쳐 2,000토큰쯤 받고, 토큰을 많이 쓰는 일은 고립된 하위 창에서 일어난다.

위임 경계를 정할 때는 부모 세션이 "알아야 할 것"과 "기억해야 할 것"을 구분해서 생각한다. 부모에게 필요한 것은 결과이지 과정 기록이 아니다. 위임 지시를 쓸 때 단계마다의 장황한 설명이 아니라 간결하고 구조화된 요약을 요청하는 것이 좋다.

위임에도 오버헤드가 있다. 호출마다 지시문(100~400토큰)이 필요하고, 돌아온 요약이 부모의 컨텍스트를 쓴다. 대략의 판단 기준은 다음과 같다. 하위 작업이 상당한 크기의 파일을 서너 개 넘게 읽어야 하거나, 셸 명령을 대여섯 번 넘게 돌려야 하거나, 오류 수정 사이클을 두 번 넘게 돌아야 하면 위임한다. 그 아래에서는 오버헤드가 인라인 비용과 비슷하다.

## 2. 대형 코드베이스 전략

큰 코드베이스에서 예산 안에 머무르는 데 도움이 되는 전략이 몇 가지 있다.

- 대상 파일만 읽기(targeted file inclusion): 작업에 직접 관련된 파일만 읽는다. 디렉터리 구조와 grep 결과를 먼저 보고, 관련 있다고 확인된 파일만 연다. 짐작으로 읽은 파일은 쓸모가 있든 없든 토큰 비용을 낸다.
- 단계마다 직접 압축하기(rolling summarisation): 자동 압축을 기다리지 말고 주기적으로 `/compact`를 실행한다. 한 모듈의 변경을 모두 끝내고 다음 모듈에 들어가기 전처럼 큰 단계를 마칠 때마다 수동으로 압축하면, 작업 중간의 임의 지점이 아니라 앞뒤가 맞는 경계를 요약에 담을 수 있다.
- 프로젝트 문서 파일: 잘 쓴 AGENTS.md는 디렉터리 구조, 쓰는 관례, 빌드/테스트/린트 명령, 눈에 띄지 않는 제약을 미리 알려 줘서 수십 번의 탐색용 파일 읽기를 대신한다. 이 절약은 프로젝트의 모든 세션에 걸쳐 쌓인다. AGENTS.md는 중첩할 수 있다. 루트 AGENTS.md는 프로젝트 전반의 맥락을 주고, 하위 디렉터리의 AGENTS.md는 에이전트가 그 디렉터리에 들어갈 때만 로드되는 모듈별 맥락을 준다. 이 계층을 활용해 루트 파일은 간결하게 두고 모듈 세부사항은 각 위치의 파일에 미룬다.
- `project_doc_max_bytes` 설정: 좁은 작업에서 AGENTS.md 오버헤드가 작업 자체의 토큰 비용보다 크다면 `config.toml`로 로드를 제한하거나 끈다.
- 범위를 좁힌 MCP 서버 로딩: 현재 작업에 필요한 서버만 올린다. 파일 시스템과 셸만 쓰는 작업이면 데이터베이스 점검이나 브라우저 자동화 서버를 올릴 이유가 없다.

```toml
# AGENTS.md 로딩을 완전히 끄기
project_doc_max_bytes = 0
```

호출 한 번에 한해서만 덮어쓸 수도 있다.

```bash
codex -c project_doc_max_bytes=0 "run the payment-service unit tests and report failures"
```

작업이 프롬프트에 완전히 명시된 자동 호출에서 가장 유용하다. 낯선 코드베이스에서 하는 대화형 세션이라면 거의 언제나 AGENTS.md를 로드하는 편이 낫다.

## 3. /status로 사용량 감시하기

`/status`는 활성 세션의 설정과 현재 컨텍스트 윈도 사용량을 출력한다. 원서의 예시 출력에서 보이는 항목은 모델(gpt-5.5, reasoning medium), 작업 디렉터리, 권한, 읽은 AGENTS.md 경로, 계정, 협업 모드, 세션 ID, 그리고 컨텍스트 윈도다. 예시에서는 `73% left (77.6K used / 258K)`로 표시되었다.

핵심 줄은 Context window이다. 남은 비율과 사용량/전체 토큰 수를 절대값으로 함께 보여 준다. 다만 `/status`는 이 합계를 범주별로 쪼개 주지 않는다. 앞 문서 표의 범주별 수치는 각 소비처가 기여하리라 기대되는 값일 뿐 `/status`가 출력하는 값이 아니다. 특정 소비처의 비용을 재려면 그것을 켜기 전후로 `/status`를 실행해 Context window 줄의 차이를 읽는다. 접두부를 구성 요소별로 보고 싶을 때는 앞서 본 `codex debug prompt-input`을 쓴다.

출력에는 `5h limit`과 `Weekly limit` 막대도 있다. 이것은 컨텍스트 예산이 아니라 사용 한도(rate limit) 예산이다. 컨텍스트 윈도가 아무리 남았어도 둘 중 하나가 소진되면 세션이 끝나므로 장시간 작업에서는 중요하다.

습관으로 만들 만한 것은 단계 경계에서 `/status`를 보는 일이다. 큰 파일 조사 전, 긴 편집 연속 뒤, 출력이 장황할 것 같은 작업 전이 그 시점이다. 압박을 일찍 알아챌수록 선택지가 많다.

셸 명령이 긴 출력을 낼 것 같다면(전체 테스트 스위트, 경고가 많은 빌드, 로그 덤프) 에이전트에게 돌려주기 전에 필터를 거친다. 예를 들어 `make 2>&1 | tail -50`은 빌드 명령의 컨텍스트 비용을 마지막 50줄로 제한한다. 관련 오류는 보통 그 안에 있다.

사용량 감시는 위임 판단에도 쓴다. 남은 작업이 상당한데 용량이 60%에 이르렀다면 서브에이전트에 위임하는 편이 오버헤드를 감수할 가치가 크다. 30% 수준에 남은 작업이 적다면 인라인으로 계속하는 것이 간단하다.

## 4. Plan Mode와 새 컨텍스트에서의 구현

계획은 코드 한 줄을 쓰기도 전에 컨텍스트를 쓴다. Plan Mode는 계획과 구현을 서로 다른 컨텍스트 수명으로 나누어 이 문제를 다룬다. 계획 단계가 끝나면 Plan Mode가 컨텍스트 사용률을 보여 준다. 계획이 30%를 썼다면 같은 세션에서 진행하고, 70%를 썼다면 구현은 새 세션에서 시작한다.

```bash
# 1단계: 전용 세션에서 계획. TUI 안에서 /plan 실행
codex "refactor the payment module to use the new gateway abstraction"
# /plan 결과 예: Context usage: 67% (85,760 / 128,000 tokens)

# 2단계: 깨끗한 컨텍스트에서 구현
codex "implement the following plan: [paste or reference the plan]"
```

원서 예시에서 Plan Mode는 "계획 완료, 컨텍스트 사용 67%, 구현은 새 세션에서 시작하길 권장"이라고 안내한다. 컨텍스트 경계를 넘는 산출물은 계획(무엇을, 어떤 순서로, 왜 바꾸는가) 하나뿐이고 나머지는 모두 뒤에 남는다. 이는 서브에이전트 위임과 잘 어울린다. 구현 세션이 모듈마다 서브에이전트를 보내면, 각자 깨끗한 상태로 시작해서 계획 중 자기 몫만 받는다.

같은 세션에서 계속할 생각이어도 Plan Mode의 사용률 표시는 도움이 된다. 진행 전에 비율을 보면 구현 중간에 컨텍스트가 거의 바닥난 것을 뒤늦게 발견하는 대신 정보에 근거한 선택을 할 수 있다.
