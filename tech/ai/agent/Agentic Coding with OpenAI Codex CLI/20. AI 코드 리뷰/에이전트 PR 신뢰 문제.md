# 에이전트 PR 신뢰 문제

AI가 리뷰를 얼마나 정확히 하는가와는 별개로, AI가 쓴 PR의 품질은 어떤가 하는 질문이 있다. 이 문서는 에이전트가 만든 PR에 대해 리뷰어가 직관적으로 느끼던 불신을 수치로 보여 주는 연구 두 건과, Codex CLI로 이 문제를 줄이는 두 가지 설정을 정리한다.

---

## 1. 메시지와 코드의 불일치 연구

한 연구는 AI 코딩 에이전트 다섯 종이 만든 PR 23,247건을 분석했다. 그중 974건은 사람이 직접 주석을 달아, 자동 탐지 파이프라인인 PR-MCI(PR Message-Code Inconsistency, PR 설명과 코드의 불일치) 검출 결과를 검증했다. 결과는 다음과 같다.

| 항목 | 수치 |
| --- | --- |
| 설명과 코드가 크게 어긋난(high-MCI) PR 비율 | 1.7% |
| high-MCI 사례 중 가장 흔한 유형 | 45.4%, 구현되지 않은 변경을 설명이 주장함 |
| high-MCI PR의 수락률 | 28.3% (일반 PR은 80.0%), 51.7% 낮음 |
| 머지까지 걸린 시간 | 55.8시간 (일반 PR은 16.0시간), 3.5배 |

1.7%는 규모가 커지면 반올림 오차가 아니다. 일주일에 에이전트 PR을 50건 머지하는 팀이라면 거의 매 근무일 하나씩 오해를 부르는 설명을 만나게 된다.

## 2. CodeRabbit의 분석

CodeRabbit은 오픈소스 PR 470건을 분석해 다른 각도에서 같은 방향의 결과를 냈다. AI가 공동 작성한 PR은 사람만 쓴 PR보다 이슈가 약 1.7배 많았다(PR당 10.83건 대 6.45건). 격차는 모든 주요 범주에 걸쳐 있다.

| 범주 | AI PR 대 사람 PR 비율 |
| --- | --- |
| 로직과 정확성 | 1.75배 |
| 보안 지적 | 2.74배 |
| 가독성 | 3.0배 |

수치 출처는 2025년 12월 CodeRabbit 보고서다.

## 3. 왜 설명이 코드와 어긋나는가

원인은 시간 순서에 있다. 대부분의 에이전트는 구현 전이거나 구현 초반에 PR 설명을 만든다. 구현 중에 오류가 나고, 도구 호출을 재시도하고, 접근 방식을 바꿔도 설명은 거의 갱신되지 않는다. 연구는 에이전트가 변경 묶음을 계획하고, 그것을 설명하고, 컨텍스트 윈도 한계나 도구 실패 때문에 일부만 구현하는 일이 잦다고 지적한다.

## 4. 대응 1: 계획이 아니라 diff에서 설명 만들기

구현이 끝난 뒤에 `codex exec`에 `--output-schema`를 줘서 PR 설명을 만들면, 설명이 의도한 변경이 아니라 실제 변경을 반영하게 된다.

```bash
git diff main...HEAD | codex exec \
  "Analyse this diff and produce an accurate PR description. \
List only changes that actually appear in the diff." \
  --output-schema pr-description-schema.json --json
```

핵심은 프롬프트에서 diff에 실제로 나타나는 변경만 나열하라고 못박는 것이다.

## 5. 대응 2: 훅으로 설명과 코드 일치 검증하기

PostToolUse 훅이 `git commit` 동작을 가로채서, 스테이징된 diff가 PR 설명 파일과 맞는지 확인할 수 있다. 설명이 diff에 없는 파일을 언급하면 커밋을 막는 식이다. 훅 자체의 구성은 9장에서 다룬다.

## 6. 머지 관문으로 쓰지 말 것

AI 리뷰를 사람 승인 단계 없이 머지 관문으로 설정하면 안 된다. 거짓 음성(모델이 놓친 P0 이슈)은 곧 운영 장애가 된다. AI의 발견 사항은 사람 리뷰를 보강하는 1차 필터이지, 사람 리뷰를 대신하는 장치가 아니다.
