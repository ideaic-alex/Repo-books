# AI 리뷰가 잘하는 일과 못하는 일

코드 리뷰는 개발팀이 매일, 가장 자주 하는 일 가운데 가치가 큰 편에 속한다. 지식이 퍼지고, 버그가 커지기 전에 잡히고, 코드베이스가 커져도 팀의 기준이 유지된다. 문제는 이 일이 끝도 없이 반복된다는 점이다. Codex CLI의 리뷰 기능은 로컬 터미널, 풀 리퀘스트(PR), CI 파이프라인이라는 세 층에서 동작한다.

이 문서는 설정으로 들어가기 전에, AI 리뷰를 어디까지 믿어도 되는지부터 정리한다. 너무 낙관('다 잡아 주겠지')하거나 너무 깎아내리는('맥락을 모르니 쓸모없다') 두 극단 사이에서 현실적인 기준점을 잡는 것이 목표다.

---

## 1. AI 리뷰가 믿을 만하게 잡는 것

AI 리뷰가 안정적으로 잡아내는 문제는 비교적 한정되어 있다.

- **보안 안티패턴**: 문자열을 이어 붙여 만든 SQL, `eval()` 호출, 빠진 인증 미들웨어, 코드에 새어 나온 자격 증명 등. 이런 유형은 OWASP Top 10에 잘 정리되어 있다.
- **린터는 못 보지만 언어 모델은 바로 보이는 정확성 문제**: 하나 어긋난 경계값(off-by-one), 생각하지 못한 경로에서의 null 참조, 비동기 체인에서 빠진 에러 처리.
- **코드베이스와 AGENTS.md에서 배운 패턴과의 어긋남**: 일관되지 않은 이름, 문서 없이 바뀐 공개 API, 동작이 아니라 구현 방식을 검증하는 테스트.

이 영역은 사람 리뷰어가 오히려 약한 곳이다. 아침에 네 번째 PR을 읽고 나면 47번째 줄의 SQL 인젝션을 놓치기 쉽다. 모델은 지치지 않는다.

## 2. AI 리뷰가 판단하지 못하는 것

반대로 다음은 AI가 약하다.

- 이 아키텍처가 팀이 풀려는 문제에 맞는지
- 지난 화요일 설계 회의에서 무엇을 결정했는지
- 기술적으로는 돌아가지만 제품의 사용자 멘탈 모델과 어긋나서 사용자를 혼란스럽게 하는 기능
- 조직 안에서만 아는 지식이 필요한 트레이드오프. 예를 들어 "성능이 떨어져 보이지만, 이 모듈은 코드가 단순한 편이 낫다고 판단해서 감수한 것"

결론은 대체가 아니라 역할 배분(캘리브레이션)이다. 자주 반복되고 피로에 민감한 항목은 AI에게 맡기고, 사람의 리뷰 시간은 아키텍처, 의도, 그 코드가 왜 존재하는지 알아야 내릴 수 있는 판단에 집중시킨다.

## 3. 벤치마크로 본 현실: c-CRAB

싱가포르 국립대학교의 c-CRAB(Code Review Agent Benchmark)는 코드 생성이 아니라 코드 리뷰 능력을 평가하는 벤치마크다. PR-agent, Devin, Claude Code, Codex CLI 네 에이전트를 실제 PR 리뷰와 그에 대응하는 테스트로 평가했다.

핵심 결과는 네 에이전트를 합쳐도 c-CRAB 과제의 약 40%만 풀었다는 것이다. 사람 리뷰어가 아키텍처 적합성과 의미상의 정확성에 집중하는 동안, 에이전트는 리뷰 피로 때문에 사람이 건너뛰는 기계적 결함을 잘 잡았다. 빠진 에러 처리, 잘못된 타입 변환, 테스트되지 않은 경계 사례 같은 것들이다.

이 결과는 보완적인 운영 방식을 뒷받침한다. 같은 PR에 에이전트를 여럿 돌리면 각자 사각지대가 달라서 커버리지가 넓어진다. 한 에이전트의 리뷰 결과를 두 번째 에이전트의 맥락으로 넘기는 교차 모델 적대적 리뷰 패턴은 이 차이를 의도적으로 활용한다(자세한 내용은 '구조화 출력과 교차 모델 리뷰' 문서에서 다룬다).

## 4. 체크리스트로 격차 줄이기

명시적인 체크리스트가 없으면 에이전트는 리뷰에서 많은 문제를 놓친다. 가장 직접적인 방법은 AGENTS.md에 구조화된 리뷰 체크리스트를 넣는 것이다. 체크리스트는 모델이 기본 주의 분포대로 움직이지 않고 항목별로 하나씩 따져 보게 만든다. 기본 상태의 모델은 견고성(robustness)에 치우치고 유지보수성과 설계는 덜 본다.

원문이 제시하는 AGENTS.md 체크리스트는 일곱 항목이다.

| 번호 | 영역 | 볼 것 |
| --- | --- | --- |
| 1 | 로직 정확성 | 하나 어긋난 경계, 뒤집힌 조건, 빠진 return, 도달할 수 없는 코드 |
| 2 | 에러 처리 | 처리되지 않은 예외, 삼켜진 에러, 일시적 실패에 대한 재시도 누락 |
| 3 | 보안 | 인젝션 경로, 인증 우회, 코드 속 비밀 값, 안전하지 않은 역직렬화 |
| 4 | 유지보수성 | 불분명한 이름, 3단계를 넘는 깊은 중첩, 빠진 추상화, 중복 |
| 5 | 테스트 커버리지 | 경계 사례 테스트 여부, 새 코드 경로 커버 여부(19장의 과도한 모킹 문제 참고) |
| 6 | API 설계 | 일관된 이름, 알맞은 HTTP 메서드, 합리적인 에러 응답 |
| 7 | 문서화 | 공개 API의 문서 주석, CHANGELOG의 호환성 깨짐 표기 |

```markdown
## Review Checklist
When reviewing code, evaluate each category explicitly:
1. **Logic correctness** — off-by-one, inverted conditions
2. **Error handling** — unhandled exceptions, swallowed errors
3. **Security** — injection vectors, auth bypass, secrets in code
4. **Maintainability** — unclear naming, deep nesting (>3 levels)
```

가이드가 없으면 Codex CLI는 견고성보다 유지보수성과 설계 코멘트에서 점수가 낮다. 체크리스트를 쓰면 이 격차가 줄어든다. 완전히 없애지는 못하지만 의미 있는 개선이라고 원문은 평가한다.
