# 더 큰 그림과 현장 엔지니어

기계적인 부분에서 한 걸음 물러서면, 하니스 엔지니어링은 에이전트가 타이핑을 맡을 때 전문 소프트웨어 작업이 무엇이 되는가에 대한 하나의 입장이다. 이 문서는 Karpathy의 구분, 하니스 없이 배포되어 무너진 OpenClaw 사례, 그리고 하니스 엔지니어링을 고객 현장에서 실천하는 포워드 디플로이드 엔지니어를 다룬다.

---

## 1. Karpathy의 구분: 바이브 코딩과 에이전틱 엔지니어링

2026년 4월 Andrej Karpathy는 하니스 엔지니어링의 목적을 분명히 해 주는 선을 그었다. Sequoia Capital에서 한 강연에서 그는 에이전트 혁명에 대한 두 가지 대응을 구분했다.

- **바이브 코딩**은 바닥을 올린다. 원하는 것을 말로 설명하고 모델이 만들어 주리라 믿으면 누구나 소프트웨어를 만들 수 있다.
- **에이전틱 엔지니어링**은 품질 기준을 지킨다. 전문 팀이 에이전트 이전부터 있던 보안, 신뢰성, 유지보수성 기준을 희생하지 않으면서 더 빨라진다.

두 접근은 반대 방향으로 당긴다. 바이브 코딩은 제약을 없애서 성공한다. 테스트도, 리뷰도, 아키텍처도 없이 자연어를 넣으면 동작하는 소프트웨어가 나온다. 에이전틱 엔지니어링은 제약(하니스)을 더해서 성공한다. 에이전트가 경계 안에서 움직이게 해 결과를 믿을 수 있게 한다. Karpathy의 구도는 이 장이 암묵적으로 주장해 온 바를 드러낸다. 하니스는 부담이 아니라 엔지니어링 그 자체다.

Karpathy의 관찰 세 가지가 하니스 개념과 곧장 연결된다.

1. **"에이전트는 인턴 같은 존재다."** 취향, 판단, 설계는 사람이 맡고 에이전트는 빈칸을 채운다. 앞에서 설명한 명세 우선, 작업 증명 모델과 같다. 사람이 WORKFLOW.md를 쓰고 인수 기준을 정의하면, 에이전트가 구현하고 하니스가 검증한다.
2. **"에이전트에 복사해 붙여 넣을 텍스트가 무엇인가. 이제 그것이 프로그래밍 패러다임이다."** Karpathy가 소프트웨어 3.0이라 부르는 것으로, 컨텍스트 윈도가 지렛대이고 LLM이 인터프리터다. 저장소의 AGENTS.md와 WORKFLOW.md가 바로 그 텍스트다. 소프트웨어 3.0 패러다임으로 쓴 우리의 프로그램이다.
3. **"모델은 들쭉날쭉하다. Opus 4.7은 10만 줄 코드베이스를 리팩터링해 놓고, 50미터 떨어진 세차장에 걸어가라고 말한다."** 들쭉날쭉함이 사람을 루프에서 뺄 수 없는 이유다. 하니스는 모델이 보지 못하는 실패를 잡아서 이를 보완한다. 훅은 모델이 무시한 린트 규칙을 강제하고, 샌드박스 정책은 모델이 하지 말아야 할 행동을 막으며, 작업 증명 요구는 모델이 자기 보고로 성공을 말하는 대신 증거를 내놓게 한다.

Karpathy는 에이전틱 엔지니어의 상한이 '10배보다 훨씬 많다'고도 말했는데, 설정에 투자한 사람에게만 해당한다. 그 설정이 하니스다. 자릿수가 다른 처리량을 얻는 실무자들은 스킬, 훅, 승인 정책, 테스트 스위트, 수백 세션에 걸쳐 다듬은 AGENTS.md로 가장 풍성하고 래칫이 많이 걸린 구성을 만든 사람들이다.

## 2. OpenClaw의 교훈

하니스 없이 간 경우의 결과는 OpenClaw 사례가 보여 준다. 이메일, 캘린더, 메신저에 연결되는 개인용 AI 비서 OpenClaw는 8주 만에 GitHub 스타 24만 7천 개를 얻었다. 하지만 하니스 없이 배포한 사용자들은 연쇄적인 실패를 겪었다.

- '하트비트' 기능이 아무 작업 없이 한 달에 토큰 값 86달러를 태웠다.
- 컨텍스트 압축이 안전 규칙을 조용히 지웠다. 한 사용자의 "실행 전에 항상 확인하라"는 지시가 요약 과정에서 사라졌고, 에이전트가 이메일을 자율적으로 삭제하기 시작했다.
- 이메일을 통한 프롬프트 인젝션으로 SSH 키가 유출됐다.
- 버전을 올릴 때 메모리가 지워졌다.

살아남은 사용자들이 도달한 운영 수칙은 하니스 엔지니어링 입문서처럼 읽힌다. 작은 워크플로 하나, 반복 작업에는 저렴한 모델, 샌드박스 격리, 통제된 피해 범위다. 그들은 세 기둥(밀폐된 테스트, 기계가 읽을 수 있는 문서, 모듈화된 아키텍처)을 의도적인 설계가 아니라 쓰라린 경험으로 다시 발견했다.

Karpathy가 말한 바이브 코딩과 에이전틱 엔지니어링의 간극은 바닥을 올리는 일과 천장을 지키는 일의 간극이다. 천장을 지켜 주는 것이 하니스다.

## 3. 하니스 실천가로서의 포워드 디플로이드 엔지니어

하니스 엔지니어링은 소프트웨어만의 학문이 아니라 점점 고객과 마주하는 일이 되고 있다. 2025년 한 해 동안 800~1,000퍼센트 성장한 포워드 디플로이드 엔지니어(FDE) 직군이 하니스 엔지니어링을 현장에서 구현한다.

FDE는 기업 고객 곁에 파고들어 다음 일을 한다.

- 고객의 기존 개발 워크플로를 파악한다.
- 고객 코드베이스 관례에 맞춘 AGENTS.md '헌법'을 쓴다.
- Codex 앱 서버를 CI 파이프라인에 연결한다.
- requirements.toml로 샌드박스 정책을 잠근다.
- 고객의 관측 스택으로 OpenTelemetry 내보내기를 설정한다.

FDE의 일과인 탐색, 빠른 프로토타입, 프로덕션 강화, 핵심 제품 팀으로의 피드백은 특정 고객의 제약에 적용한 하니스 엔지니어링이다. 사내 하니스를 만드는 팀에게 FDE의 방식은 유용한 사고 모델이 된다. 우리 엔지니어링 조직을 '고객'으로 보고 탐색에서 강화까지 같은 구조화된 순서를 적용해 보는 것이다.
