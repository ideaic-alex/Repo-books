# 연습 문제

장에서 배운 내용을 자기 프로젝트에 적용해 보는 실습 다섯 개다. 각 문제에 취지와 풀이 방향을 덧붙인다.

---

## 1. 에이전트용으로 테스트 스위트 단단하게 만들기

프로젝트의 테스트 스위트가 밀폐성 기준을 만족하는지 점검한다. 모든 테스트가 오프라인에서, 명령 하나로 돌아가고, 결과가 결정적인가? 기준을 통과하지 못하는 테스트마다 외부 의존성이 무엇인지 찾고, 목이나 시드 데이터로 대체한 뒤, 네트워크 없이 로컬에서 10번 연속 돌려도 안정적인지 확인한다.

풀이 방향: 먼저 네트워크를 끊고 전체 테스트를 돌려 실패하는 항목을 목록으로 만든다. 실패 원인이 외부 API인지, 공유 DB인지, 시간이나 난수 같은 비결정 요소인지 분류하면 대체 방법이 정해진다.

## 2. 실제 작업을 위한 WORKFLOW.md 쓰기

프로젝트에서 반복되는 작업 하나를 고른다. 특정 종류의 버그 수정, 표준적인 기능 유형 구현, 의존성 업데이트가 후보다. 모델, 턴 제한, 필요한 작업 증명 산출물을 담은 YAML 프런트 매터와, 작업별 맥락을 매개변수로 받는 Liquid 템플릿 본문으로 WORKFLOW.md를 쓴다. 렌더링한 프롬프트를 Codex CLI exec 세션에 넣고, 에이전트의 행동이 의도한 정책과 맞는지 평가한다.

풀이 방향: 개념 문서의 예시처럼 프런트 매터 다섯 항목에서 시작하고, 본문에는 이슈 제목과 설명, 금지 파일 같은 자리 표시자만 둔다. 평가할 때는 정책에 쓴 규칙(예: 완료 전 테스트 실행)을 에이전트가 실제로 따랐는지를 기준으로 삼는다.

## 3. 체크포인트 기반 재개 구현하기

기존에 쓰던 여러 단계의 Codex CLI 파이프라인을 가져오거나, 뚜렷한 단계가 세 개 이상인 새 파이프라인을 설계한다. 하니스에 체크포인트 파일 쓰기와 읽기 로직을 구현한다. 각 단계가 시작되기 전에 체크포인트를 읽어 이미 끝난 단계인지 확인하고, 각 단계가 끝나면 누적된 상태를 체크포인트에 쓴다. 실행 도중 일부러 파이프라인을 중단시키고, 처음부터 다시 하지 않고 올바른 단계에서 재개되는지 확인한다.

풀이 방향: 체크포인트는 단계 이름 목록과 산출물을 담은 JSON으로 시작한다. 스키마 버전 필드를 처음부터 넣고, 단계 중간에 중단된 경우에도 해당 단계를 다시 하게 되는지 확인한다.

## 4. 팀의 작업 증명 기준 정의하기

Symphony의 작업 증명 모델을 참고해서, 팀의 워크플로에서 작업이 완료로 인정되려면 에이전트가 어떤 산출물을 만들어야 하는지 정의한다. 최소한 다음 셋은 다룬다.

1. 어떤 기능 검증이 필요한가(테스트 통과율, CI 상태)
2. 어떤 검토 가능성 산출물이 필요한가(diff 요약, 설명 메모)
3. 어떤 문서 산출물이 필요한가(갱신된 AGENTS.md, CHANGELOG 항목, 결정 기록 항목)

이 기준을 프로젝트의 AGENTS.md에 적고, 다음에 나오는 에이전트 생성 PR 세 개에 적용한다.

풀이 방향: 항목마다 사람이 확인할 수 있는 형태(링크, 파일, 숫자)로 적는다. 세 개의 PR에 적용한 뒤 기준이 지나치게 느슨하거나 빡빡했던 곳을 고쳐 두면 래칫 원칙에도 맞는다.

## 5. 하니스 신뢰도 벤치마크

지금 쓰는 Codex CLI 워크플로로 대표 작업 5~10개를 돌려, 사람의 개입 없이 끝나고 모든 관문을 통과한 작업의 비율을 성공률로 기록한다. 그다음 이 장의 하니스 개선 한 가지를 적용한다. 더 나은 밀폐 테스트, WORKFLOW.md 정책, 체크포인트 기반 재개 중 하나가 후보다. 같은 작업을 다시 돌려 성공률 향상 폭을 계산하고, 한 달 치 평소 사용량으로 환산해 가치를 추정한다. 엔지니어링 리더십에 공유할 구체적인 투자 대비 효과(ROI) 수치가 나온다.

풀이 방향: 개선 전후에 같은 작업, 같은 모델, 같은 설정을 유지해야 비교가 의미가 있다. 한 번에 개선 하나만 바꿔서 어떤 변경이 효과를 냈는지 분리한다.
