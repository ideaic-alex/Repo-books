# 하니스가 모델을 이기는 근거

이 장은 "루프를 소유하는 것은 모델이 아니라 하니스"라는 주장으로 시작했다. 2026년 중반에 이 명제는 더 이상 직관이 아니다. 서로 조율하지 않았는데도 같은 결론에 이른 네 가지 관점이 이를 뒷받침한다. 통제된 벤치마크, 동료 검토를 거친 재현 결과, 실무자의 작업 이론, 그리고 기업 현장에서 나온 OpenAI 내부의 경험이다. 숫자 하나보다 이 수렴 자체가 논거다. 이 장에서 운영 규칙 하나만 가져간다면 이것이다. 에이전트 성능이 부족하면 모델을 바꾸기 전에 하니스를 바꾼다.

---

## 1. 측정된 격차와 그 재현

가장 깔끔한 결과는 통제 실험에서 나왔다. 모델을 gpt-5.2-codex로 고정하고 하니스만 바꿨을 때 LangChain의 deepagents-cli는 Terminal Bench 2.0에서 30위에서 5위로 올랐다. 올린 요인은 독점 기술이 아니라 옮겨 쓸 수 있는 것들이다. 미들웨어 패턴 다섯 가지이고, 각각 이미 가진 Codex CLI 기능이나 만들 수 있는 것에 대응한다.

| 미들웨어 패턴 | 하는 일 | Codex CLI 대응 |
|---|---|---|
| PreCompletionChecklistMiddleware | 에이전트가 '끝'을 선언하기 전에 가로채 계획, 구축, 검증, 수정 네 단계 검증을 강제 | PostToolUse 훅 + 완료 전 테스트 검증을 요구하는 AGENTS.md 지시 |
| LocalContextMiddleware | 디렉터리 구조, 쓸 수 있는 도구, 언어 감지 같은 환경 맥락을 시작할 때 주입해 시행착오로 알아내지 않게 함 | AGENTS.md 맥락 주입(세션 시작 때 자동 로드) |
| LoopDetectionMiddleware | 파일별 수정 횟수를 세어, 같은 파일을 N번 고치면 다시 생각하게 유도해 실패한 전략을 되풀이하는 '파멸 루프'를 끊음 | 내장 대응 없음. 맞춤 PostToolUse 훅으로 채울 수 있음 |
| 추론 샌드위치(Reasoning Sandwich) | 계획과 검증에는 추론 연산을 많이, 구현 중에는 적게 배분 | --reasoning-effort 플래그와 빠른 조절키(Alt+,/Alt+.)로 수동 조절. 단계별 자동 예산은 아직 없음 |
| 환경 인지 프롬프팅 | 테스트 가능성 기준과 시간 예산을 강조하는 시스템 프롬프트 | 표준적인 AGENTS.md 작성 관행 |

벤치마크 하나는 우연일 수 있지만 이 결과는 혼자가 아니다. 하니스 엔지니어링에 대한 첫 동료 검토 서베이도 같은 구조를 정리했고, 한 걸음 더 나간 결과 둘을 인용한다. Meta-Harness는 하니스 변경만으로 6배의 성능 격차를 측정했다. CAAF 프레임워크는 결정적인 하니스 제약이 모델 규모를 이기는 모습을 보였다. 제약이 잘 걸린 작은 모델이 제약 없는 큰 모델을 앞섰다. 서베이는 산업계의 기원도 기록한다. OpenAI가 이 용어를 만들 당시 3~7명 규모의 팀이 5개월에 걸쳐 약 100만 줄의 프로덕션 코드를 냈다. 벤치마크 팀, 학계 프레임워크 둘, 프로덕션 팀이 서로 다른 길로 같은 결론에 닿았다.

## 2. 격차가 생기는 이유와 대응

측정된 격차에는 설명이 필요하고, Addy Osmani가 2026년에 쓴 두 편의 글이 가장 쓸모 있는 설명을 준다.

「Factory Model」 글은 변화를 이렇게 명명한다. 소프트웨어는 세 세대를 거쳤다. 자동 완성, 동기식 에이전트, 그리고 독립적으로 일하고 산출물을 검토용으로 돌려주는 자율 에이전트다. 병목도 따라 옮겨 갔다. "이제 병목은 생성이 아니라 검증이다." 하니스가 원시 출력이 아니라 작업 증명을 보장해야 하는 이유가 이 한 문장에 있다. Osmani의 권고 세 가지는 필수 red/green TDD, 지렛대로서의 명세 명확성, 증폭기로서의 깔끔한 아키텍처인데, 실무자 자리에서 다시 말한 세 기둥이다.

후속 글 「Agent Harness Engineering」은 하니스가 실제로 담고 있는 것을 정리한다. 파일시스템과 git 연동, 코드 실행, 샌드박스, 메모리와 지식 연동, 컨텍스트 관리, 강제 훅이다. 이 책의 독자라면 모두 아는 요소이며, 이들이 잡다한 요령 모음이 아니라 하나의 학문이라고 주장한다. 두 아이디어가 특히 중요하다.

- **래칫 원칙(Ratchet Principle)**: 에이전트의 모든 실패는 영구적인 하니스 변경이 되어 다시는 같은 실패가 나지 않게 해야 한다. 새 AGENTS.md 한 줄, 새 훅, 더 촘촘한 샌드박스 규칙이 각각 뒤로 풀리지 않는 톱니 한 칸이다. "좋은 AGENTS.md의 모든 줄은 잘못됐던 구체적인 사건으로 거슬러 올라갈 수 있어야 한다." 설정 쪽에서 본 작업 증명 고리, 즉 증거가 정책으로 쌓이는 과정이다.
- **'Skill Issue' 관점 전환**(Osmani는 HumanLayer의 것이라고 밝힌다): 이 장의 명제를 진단으로 바꾼다. 에이전트 실패의 대부분은 능력의 한계가 아니라 설정 문제다. 증명 방식은 LangChain과 같다. Claude Opus 4.6이 기본 환경에서 맞춤 하니스로 옮기기만 했는데 Terminal Bench 2.0 점수가 크게 올랐다. 모델은 그대로고 하니스만 달라졌다.

산업이 가는 방향도 읽힌다. Osmani는 서비스형 하니스(Harness-as-a-Service, HaaS)를 꼽는다. 실행 루프, 도구 체계, 컨텍스트 관리를 제품으로 제공하는 완성형 런타임이다. Claude Agent SDK, Codex SDK, OpenAI Agents SDK가 초기 사례다. 기업 팀(17장)은 성능 좋은 하니스 API로 조율 계층을 사내에서 만드는 수고를 덜 수 있다. 대가는 모델 종속보다 깊은 종속이다. 하니스에는 우리 팀만의 실패 이력, 곧 하니스를 값지게 만든 바로 그 래칫이 새겨져 있기 때문이다.

## 3. 공급사 내부에서 나온 같은 발견

벤치마크와 프레임워크는 열성 팬끼리의 대화일 수도 있다. 이를 가장 강하게 검증해 주는 것은 공급사 내부의 증언이고, 유럽·중동 지역을 맡은 OpenAI의 현장 개발 엔지니어링(포워드 디플로이드 엔지니어링) 책임자 Arnaud Fournier가 이를 제공한다. 그의 핵심 관찰은 OpenAI 엔지니어들이 '순수 코드 작성에서 멀어져' 하니스 엔지니어링으로 옮겨 갔고, 이 패턴이 John Deere, Amgen, 반도체 기업 등 기업 고객으로 퍼지고 있다는 것이다. 두 수치가 근거다.

- 기업 고객의 약 20퍼센트가 API를 직접 호출하는 대신 에이전트 프레임워크를 도입하고 있다. 18개월 전에는 없던 범주에서 나온 초기 다수 채택 단계의 수치다.
- 결과가 가장 좋은 고객은 프롬프트 최적화만 하지 않고 하니스 인프라(컨텍스트 관리, 승인 파이프라인, 도구 조율)에 투자한 고객이다.

Meta-Harness의 격차와 LangChain의 순위가 리더보드가 아니라 프로덕션 환경에서 다시 관찰된 것이다.

네 증언은 방법론을 공유하지 않고, 서로 맞춰 줄 이유도 없다. 그래서 일치한다는 사실에 무게가 실린다. 통제된 벤치마크, 학술 서베이, 실무자의 현장 기록, 공급사의 기업 사례가 모두 같은 지침에 도달한다. 더 큰 모델을 찾기 전에 하니스를 개선하라. 이 장의 앞부분 전체가 그 방법이다.
