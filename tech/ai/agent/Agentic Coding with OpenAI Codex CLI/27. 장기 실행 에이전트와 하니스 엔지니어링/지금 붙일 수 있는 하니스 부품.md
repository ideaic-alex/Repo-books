# 지금 붙일 수 있는 하니스 부품

앞에서 다룬 패턴이 설계 수준의 이야기였다면, 이 문서의 부품은 Codex CLI 하니스에 지금 바로 끼워 넣을 수 있는 구체적인 요소다. 각각 운영상의 빈틈 하나를 메운다. 모델이 어디서 돌고, 도구가 어떻게 격리되고, 변경이 어떻게 리뷰되고, 하니스를 프로그램으로 어떻게 구동하고, 부품이 생태계 사이를 어떻게 옮겨 다니고, 에이전트를 제품에 넣으면 무엇이 달라지는지를 차례로 본다.

---

## 1. 로컬 모델 제공자

클라우드 모델 엔드포인트에만 기대는 하니스는 단일 장애점을 떠안고, 에이전트 동시 실행 수에 비례해 커지는 비용 바닥도 함께 안는다. Ollama, vLLM, llama.cpp 같은 로컬 모델 제공자를 config.toml의 [model_providers]에 설정하면 특정 구간에서 대안이 된다.

- `wire_api = "responses"` 설정이 로컬 제공자가 클라우드 엔드포인트와 같은 API 규약을 쓰게 한다. 그래서 프롬프트, 도구, 승인 정책 같은 나머지 하니스는 그대로 둔다.
- `--profile local`과 `--profile cloud`처럼 프로필을 바꿔서, 하니스 자체를 고치지 않고 실행마다 백엔드를 고른다.

로컬 제공자는 Tier 1과 Tier 2 작업에 가장 잘 맞는다. 기계적인 수정, 코드베이스 탐색, 포매팅처럼 로컬 모델과 최상위 모델의 품질 차이가 가장 작은 작업이다. 깊은 추론이나 긴 호흡의 계획이 필요한 Tier 3 작업은 클라우드 엔드포인트가 맞다. 이 선택은 하니스 정의가 아니라 하니스 운영자의 프로필 선택에 속한다. 로컬 계층을 빌리지 않고 하드웨어를 사서 쓸 때 수지가 맞는지는 14장의 온프레미스 손익분기 분석을 보면 된다.

## 2. Docker MCP Toolkit: 하니스 수준 격리

MCP 도구 서버를 개발자 PC에서 npx나 pip 프로세스로 그냥 띄우면 의존성 충돌, 자격 증명 난립, 에이전트와 호스트 사이의 격리 전무라는 문제가 생긴다. Docker의 MCP Toolkit은 이를 하니스 수준에서 푼다. 검증된 MCP 서버 200개 이상을 컨테이너 이미지로 묶고, 하나의 게이트웨이 프로세스가 라우팅, 자격 증명 주입, 자원 제한을 맡는다.

게이트웨이는 stdio 프로세스 하나다. 내부에서는 도구 호출을 필요할 때 띄우는 컨테이너 서버로 보낸다. 서버마다 자기 네임스페이스에서 제한된 권한으로 돈다(호스트 파일시스템 없음, CPU 1개, 메모리 2GB 상한). 응답은 클라이언트로 돌아가기 전에 비밀 값 유출 여부를 검사받는다.

하니스 관점의 핵심은 프로필 관리다.

- Docker 프로필은 한 워크플로에 쓰는 MCP 서버를 묶고, OCI 산출물로 공유할 수 있다.
- 프로필을 가리키는 .codex/config.toml을 커밋하면 모든 개발자가 똑같이 격리된 도구 접근을 얻는다.
- CI에서는 게이트웨이를 GitHub Actions의 서비스 컨테이너로 띄워, codex exec가 헤드리스 모드에서 같은 도구를 쓴다.
- startup_timeout_sec는 최소 30초로 설정한다. 전체 카탈로그를 띄우는 시간이 Codex의 기본 핸드셰이크 제한인 10초를 넘을 수 있기 때문이다.

선택 기준은 이렇다. 네이티브 MCP 서버는 도구 하나에 신뢰도가 높은 단순한 환경에 맞고, 하니스가 격리, 자격 증명 관리, 팀 표준화를 요구하면 Docker MCP Toolkit이 맞다.

## 3. 내장 코드 리뷰 스킬

Codex CLI에는 코드 리뷰 스킬이 내장되어 있어 별도의 리뷰 도구를 만들 필요가 줄어든다. 이게 없으면 하니스 작성자는 정적 분석용 MCP 서버를 따로 붙이거나, 리뷰 에이전트를 부르는 훅을 직접 만들거나, 서드파티 GitHub Action을 써야 한다.

내장 스킬은 스테이징했거나 커밋한 변경을 AGENTS.md 규칙과 대조해 분석하고 구조화된 피드백을 낸다. 하니스 엔지니어에게는 외부 의존 하나가 줄어든다는 뜻이다. 작업 증명 파이프라인의 리뷰 단계가 Codex CLI에 함께 오는 기능을 가리키면 된다. 도메인에 특화된 규칙이나 규정 준수 검사에는 전용 도구가 여전히 필요할 수 있다. 하지만 사람의 최종 승인 전에 일반적인 코드 품질을 거르는 관문으로는 내장 스킬이 더 단순하고 유지하기 쉽다.

## 4. 앱 서버 JSON-RPC: 맞춤형 하니스 클라이언트

Codex 앱 서버는 에이전트 핵심부를 클라이언트 화면과 분리한다. CLI TUI, VS Code 확장, 데스크톱 앱, 웹, IDE 연동까지 모든 Codex CLI 경험이 하나의 양방향 JSON-RPC 2.0 API로 통신한다. 하니스 엔지니어에게 이곳이 맞춤 프런트엔드와 조율 계층을 붙이는 접점이다.

프로토콜은 세 가지 기본 요소로 상호작용을 구성한다.

| 요소 | 뜻 |
|---|---|
| Item | 입출력의 원자 단위 |
| Turn | 에이전트 작업 한 단위에서 나온 Item의 연속 |
| Thread | 스레드(대화 기록 한 묶음). 생성, 재개, 포크, 보관을 지원하는 영속 세션 컨테이너 |

전송 방식은 둘이다. 로컬 연동용 stdio(`codex app-server`)가 지원되는 기본값이다. 원격 시나리오용 WebSocket(`codex app-server --listen ws://127.0.0.1:4500`)은 원서 집필 시점에 실험 단계이고, /readyz와 /healthz로 상태 확인을 한다.

활용 예는 다음과 같다.

- turn/completed 알림을 구독해 토큰 사용량을 추적하는 대시보드
- 샌드박스 격리와 함께 command/exec를 호출하는 CI/CD 조율기
- requestApproval 알림을 가로채는 기업용 승인 게이트웨이

타입 안전한 클라이언트 바인딩은 `codex app-server generate-ts`나 `codex app-server generate-json-schema`로 만든다. codex exec를 감싼 셸 스크립트가 한계에 이른 하니스 작성자에게 앱 서버 프로토콜은 안정적이고 언어에 구애받지 않는 기반이다.

## 5. 도구 사이 이식성

26장에서 본 cc-plugin-to-codex 역방향 브리지 덕분에 하니스 부품을 에이전트 생태계 사이에서 부분적으로 옮길 수 있다. Claude Code 플러그인에 들어 있는 PostToolUse 비밀 값 스캔 훅을 cc2codex로 Codex 네이티브 훅으로 바꿀 수 있고, 반대 방향은 codex-plugin-cc가 맡는다. CI/CD에는 Codex, 디버깅에는 Claude Code를 쓰는 식의 멀티 에이전트 하니스를 운영하는 조직은 부품을 중복해서 만들지 않고 공유할 수 있다. 변환에는 손실이 있어 검증이 필요하지만, 부품 수준에서 도구에 구애받지 않는 하니스 엔지니어링의 방향을 보여 준다.

## 6. SaaS 준비도와 제품 내장

하니스가 한 엔지니어링 팀을 돕는 데 그치지 않고 멀티 테넌트 SaaS 제품 안에 Codex CLI를 내장하려는 것이라면 요구 사항이 달라진다. CLI 에이전트 11종을 여섯 가지 제품 내장 기준(아키텍처, SDK 제공, 세션 관리, MCP 확장성, 에어갭 지원, 라이선스)으로 평가한 결과에서 Codex CLI는 Tier 2(주의할 점이 있지만 내장 가능)에 놓였다. 내장 세션 저장소와 관대한 라이선스를 가진 OpenCode나 Pi/OpenClaw 같은 도구에 뒤진다.

하니스 작성자에게 가장 큰 빈틈은 두 가지다. 하나는 세션 영속성으로, Codex CLI의 JSONL-over-stdio 방식에서는 영속 계층을 직접 만들어야 한다. 다른 하나는 에어갭 기업 환경을 위한 오프라인 모델 지원이다.

내장 아키텍처를 확정하기 전에, 멀티 테넌트 부하에서 깨지기 쉬운 다섯 가지를 확인해야 한다.

1. 서브프로세스 방식과 라이브러리 방식 중 어느 쪽으로 연동할지
2. 구조화된 이벤트 스트리밍
3. 동시 요청에서의 테넌트 격리
4. 모델 BYOK(자체 키 지참) 지원
5. 샌드박스 탈출 경계
