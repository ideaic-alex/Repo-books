# 하니스 엔지니어링의 개념

도구, 핸드오프, 가드레일, 컨텍스트 윈도 같은 기본 부품을 알아도 곧바로 쓸 만한 시스템이 되지는 않는다. 망치와 수평계만으로 집을 지을 수는 없다. 작업자를 지켜 주는 비계, 현장에 부딪혀도 버티는 계획, 실수가 구조물이 되기 전에 잡아내는 검사 지점이 있어야 공사가 끝까지 간다. 에이전트 엔지니어링에서 이 역할을 하는 것이 하니스(harness, 에이전트를 감싸는 실행 환경 전체)다.

이 문서는 하니스가 무엇인지, 학계가 제안한 세 계층 틀이 무엇인지, 그리고 하니스를 받치는 세 기둥이 무엇인지 설명한다. 이 장 전체의 출발점이 되는 개념 문서다.

---

## 1. 하니스 엔지니어링이란

하니스 엔지니어링이라는 말은 2026년 2월 Ryan Lopopolo가 처음 썼다. 실무자들이 이미 하고 있던 일에 공통 이름을 붙인 셈이다. 세 가지 일을 나란히 놓으면 위치가 분명해진다.

| 분야 | 설계 대상 |
|---|---|
| 전통 소프트웨어 엔지니어링 | 코드 |
| 프롬프트 엔지니어링 | AI에게 줄 지시문 |
| 하니스 엔지니어링 | AI 에이전트가 안정적으로 일하게 하는 인프라, 제약, 피드백 고리 |

하니스 엔지니어링은 앞의 둘보다 한 단계 위에 있다. Lopopolo는 이를 "에이전트는 어렵지 않다. 어려운 것은 하니스다"라는 한 문장으로 요약했다. 그가 쓴 글은 작은 팀이 5개월 동안 약 100만 줄의 프로덕션 코드를 사람이 직접 한 줄도 쓰지 않고 만들어 배포한 내부 실험을 다룬다. 이 팀은 한 사람당 엔지니어 3~10명 몫의 처리량을 냈다고 한다.

하니스는 에이전트를 감싸는 모든 것이다.

- 프로젝트를 설명하는 AGENTS.md
- 결정적인(매번 같은) 피드백을 주는 테스트 스위트
- 피해 범위를 제한하는 샌드박스
- 산출물을 검증하는 CI 파이프라인
- 사람이 언제 개입해야 하는지 정하는 승인 정책
- 여러 시간짜리 작업이 일시적 장애를 견디게 하는 체크포인트 로직

하니스가 잘 설계되어 있으면 유능한 모델이 높은 확신으로 작업을 혼자 끝낸다. 그렇지 않으면 가장 좋은 모델도 같은 자리에서 헛돈다.

Part IV까지 따라온 독자는 이미 하니스 엔지니어링을 해 온 셈이다. AGENTS.md를 다듬은 일, 외부 의존 없는 테스트 스위트를 만든 일, PostToolUse 린트 훅을 단 일, codex exec CI 프로필을 만든 일이 모두 하니스 작업이다. 이 장이 더하는 것은 체계다. 모든 하니스가 만족해야 하는 세 기둥, 특정 실패 유형에 맞는 패턴, 에이전트 정책을 감사하고 버전 관리할 수 있게 해 주는 파일 형식을 차례로 다룬다.

## 2. 학술적 토대: 세 계층 틀

2026년 5월, 저자 42명이 참여한 서베이 논문 'Code as Agent Harness'(arXiv 2605.18747)가 코딩 에이전트를 세 계층 구조로 분석하며 하니스 엔지니어링을 처음으로 학술적으로 정리했다. 논문의 중심 주장은 "하니스가 루프를 소유한다"이다. 모델은 하나의 부품일 뿐이고 결과 품질을 정하는 쪽은 하니스라는, 현장에서 경험으로 알게 된 사실을 뒷받침한다.

세 계층은 다음과 같다.

1. **인터페이스 계층**: 에이전트가 지시를 받고 결과를 보여 주는 방식. Codex CLI에서는 AGENTS.md, TUI, 시스템 프롬프트, 승인 대화창이 여기에 속한다. 모델이 "무엇을 해야 한다고 믿는가"를 만든다.
2. **메커니즘 계층**: 에이전트의 행동을 제한하고 가능하게 하는 장치. 훅, 권한 프로필, 샌드박스 정책, 실행 정책 규칙, 승인 모드 사다리가 해당한다. 모델이 무엇을 해야 한다고 믿든 상관없이 "실제로 무엇을 할 수 있는가"를 정한다.
3. **멀티 에이전트 확장 계층**: 에이전트들이 경계를 넘어 협력하는 방식. MCP 서버, 서브에이전트, A2A 프로토콜, 그리고 여러 에이전트를 나누어 맡기고 조율하는 일(오케스트레이션)의 패턴인 Symphony의 WORKFLOW.md가 여기에 든다. 한 에이전트가 다른 에이전트에게 일을 맡길 수 있는지, 상태가 그들 사이에서 어떻게 흐르는지를 정한다.

위 그림은 원서의 그림 27.1이다. 위에서 아래로 인터페이스, 메커니즘, 멀티 에이전트 확장 계층이 쌓여 있고, 각 계층 옆의 점선 화살표가 그 계층이 결정하는 것을 가리킨다. 인터페이스는 모델의 믿음("믿음을 만든다"), 메커니즘은 모델의 가능한 행동("능력을 정한다"), 확장 계층은 에이전트 사이의 상태 흐름("위임을 가능하게 한다")이다. 계층 사이의 실선 화살표는 위 계층이 아래 계층을 제약한다는 뜻이다. 인터페이스에서 메커니즘으로 가는 화살표에는 "모델이 해야 할 일을 정한다", 메커니즘에서 확장 계층으로 가는 화살표에는 "모델이 할 수 있는 일을 제약한다"라고 적혀 있다.

Codex CLI의 구성 요소를 이 틀에 맞추면 이 책의 장 구성이 곧 하니스 엔지니어링 교육 과정으로 읽힌다.

| 틀의 계층 | Codex CLI 구성 요소 | 이 책의 장 |
|---|---|---|
| 인터페이스 | AGENTS.md, 시스템 프롬프트, TUI, 계획 모드 | 3, 4, 7장 |
| 메커니즘 | 훅, 권한 프로필, 샌드박스, 승인 모드 | 5, 9, 16장 |
| 멀티 에이전트 확장 | MCP 서버, 서브에이전트, 스킬, exec 파이프라인 | 8, 10, 11, 12, 15장 |

원서는 dev.to에 올라온 실무자 비교 분석도 함께 언급한다. 여러 플랫폼을 여러 평가 항목으로 비교해 보니, 실제 결과의 차이를 만드는 것은 모델 선택보다 하니스 설계 결정이었다. 같은 모델에 하니스만 다른 두 에이전트는 결과가 크게 달랐고, 다른 모델이라도 하니스 구조가 비슷하면 품질이 비슷한 수준으로 수렴했다. 하니스가 독립 변수라는 이야기다.

이 발견은 도구를 평가하는 질문 자체를 바꾼다. "어떤 모델이 최고인가"가 아니라 "내 제약 조건에서 가장 좋은 엔지니어링 선택을 해 주는 하니스는 무엇인가"를 물어야 한다. 경쟁 도구 지형에 이 시각을 적용한 내용은 26장에 있다.

## 3. 세 기둥

뒤에 나오는 여러 패턴이 Symphony를 끌어다 쓰므로, 먼저 Symphony가 무엇인지 짚고 가자. Symphony는 OpenAI가 공개한 오픈소스 참조 하니스다. 이슈 트래커에서 이슈를 가져와, 이슈마다 격리된 작업 공간에서 Codex CLI 에이전트를 돌리고, 에이전트가 검증 가능한 작업 증명을 만든 뒤에야 사람에게 풀 리퀘스트를 올린다. 구조는 뒤의 「참조 구현과 패턴 선택」 문서에서 자세히 다룬다. 지금은 지금 논의하는 원칙을 보여 주는 실제 예로 생각하면 된다.

프로덕션 수준의 하니스는 모두 세 기둥 위에 서 있다. Symphony 문서가 이를 분명히 밝혀 두었다.

**밀폐된 테스트(hermetic testing)**는 테스트 스위트가 로컬에서, 안정적으로, 외부 의존 없이 돈다는 뜻이다. 에이전트가 npm test를 실행해 매번 같은 결과를 받으면 혼자 반복 개선할 수 있다. 반대로 스테이징 데이터베이스나 실서비스 API에 기대는 테스트라면 에이전트는 진짜 회귀(regression)인지 환경이 잠깐 흔들린 건지 구분하지 못해 헛돈다. 해법은 익숙하다. 외부 서비스는 목(mock)으로 대체하고, 테스트 DB는 시드 데이터로 채우고, 모든 테스트를 명령 하나로 오프라인에서 돌릴 수 있게 만든다.

**기계가 읽을 수 있는 문서**는 에이전트가 프로젝트를 빌드, 테스트, 린트, 배포하는 방법을 물어보지 않고도 찾아낼 수 있다는 뜻이다. 대표 수단은 AGENTS.md(4장 참고)지만 원칙은 더 넓다. 이름이 붙은 타깃이 있는 Makefile, 예측 가능한 이름의 package.json 스크립트, 일정한 형식을 따르는 README 절 같은 구조화된 자료가 모두 포함된다. 에이전트가 추측해야 하면 토큰이 들고 오류가 생긴다.

**모듈화된 아키텍처**는 부수 효과가 한 곳에 갇히고 경계가 분명하다는 뜻이다. 결제 모듈을 고치는 에이전트가 알림 서비스를 엉겁결에 망가뜨려서는 안 된다. 결합도가 높으면 정확성이 불확실해지고, 낮으면 에이전트가 정해진 범위 안에서 자신 있게 일한다. 좋은 아키텍처가 늘 해 온 도메인 분리 논리와 같지만, 되물을 수 있는 사람 개발자보다 자율 에이전트가 이 문제에 더 민감하다. Codex CLI 자체가 큰 멀티 크레이트 워크스페이스로 구성되어 있어서, 크레이트마다 컴파일 단위, 의존성 그래프, 테스트 스위트를 따로 가진다. 원서는 Codex CLI가 아직 1.0 이전이어서 정확한 크레이트 수는 릴리스에 따라 달라진다고 덧붙인다. 도구 자신에게 하니스 엔지니어링을 적용한 사례로, 모듈화를 극단까지 밀어 병렬 컴파일, 격리된 테스트, 더 깔끔한 의존성 감사를 얻는다. 에이전트 작업을 다루기 쉽게 만드는 원칙이 하니스 도구 체인의 유지보수성도 높인다.

세 기둥 중 하나라도 약하면 에이전트는 추측하게 되고, 추측은 토큰 낭비와 오류로 돌아온다. 자기 코드베이스를 이 세 기준으로 점검해 보는 일이 하니스 개선의 첫걸음이다.
