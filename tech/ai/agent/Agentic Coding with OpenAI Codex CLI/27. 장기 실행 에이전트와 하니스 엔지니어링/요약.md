# 요약

27장의 핵심 열 가지를 정리한다. 각 항목은 해당 주제를 다룬 문서에서 자세히 설명한다.

---

## 1. 장 요약 열 가지

1. **하니스 엔지니어링은 하나의 학문이다.** AI 에이전트가 안정적으로 생산성을 내도록 인프라, 제약, 피드백 고리를 설계한다. 프롬프트 엔지니어링과 전통 소프트웨어 엔지니어링보다 한 단계 위에 있다.
2. **세 기둥이 하니스에 맞는 코드베이스를 받친다.** 밀폐된 테스트, 기계가 읽을 수 있는 문서, 모듈화된 아키텍처다. 어느 기둥이든 약하면 에이전트가 추측하게 되고, 추측은 토큰을 쓰고 오류를 만든다.
3. **WORKFLOW.md가 에이전트 정책을 버전 관리한다.** YAML 프런트 매터(실행 설정)와 Liquid 템플릿 Markdown 본문(에이전트 프롬프트)을 하나의 버전 관리 산출물로 합친다. 에이전트 정책이 저장소의 1급 구성원이 되어 애플리케이션 코드와 같은 리뷰와 롤백 절차를 받는다.
4. **상태 저장이 중단을 견디게 한다.** 세션 ID, 체크포인트 파일, 데이터베이스 기반 상태로 오래 도는 에이전트가 끝난 작업을 되풀이하지 않고 재개한다. 어느 단계가 맞는지는 작업의 길이와 비용에 달려 있다.
5. **오류 복구는 실패 유형 셋에 맞춘다.** 일시적 실패에는 백오프 재시도, 판단이 필요한 경우에는 사람에게 에스컬레이션, 일부만 적용된 변경은 재시도 전에 롤백한다.
6. **작업 증명이 에이전트를 책임지는 행위자로 만든다.** CI 통과, 코드 리뷰 피드백, 변경 요약, 설명 영상 같은 검증 가능한 증거로 완료를 보여 주어야 하고, 자기 보고에 기대면 안 된다. 에이전트가 블랙박스가 아니라 책임지는 행위자가 된다.
7. **Symphony가 참조 구현이다.** OpenAI의 오픈소스 하니스가 이 패턴들을 규모 있게 보여 준다. WORKFLOW.md 형식, 작업 증명 강제, Elixir/BEAM 아키텍처는 도구를 쓰지 않더라도 공부할 가치가 있다.
8. **NanoClaw가 상주형 조율을 보여 준다.** 항상 켜진 스케줄링, 컨테이너 격리, 채널 기반 통신이 Symphony의 배치 지향, 이슈 주도 방식을 보완한다. 프로덕션에서는 작업 종류에 따라 두 패턴을 함께 쓸 수 있다.
9. **생태계가 하니스 부품을 이미 제공한다.** Docker MCP Toolkit은 MCP 서버를 컨테이너 이미지로 묶어 단일 게이트웨이 뒤에 두고, 프로필을 OCI 산출물로 공유한다. 내장 코드 리뷰 스킬은 맞춤 도구 없이 Codex CLI가 직접 제공하는 리뷰를 준다. Codex 앱 서버의 JSON-RPC 프로토콜은 stdio나 WebSocket으로 대시보드, 조율기, 승인 게이트웨이를 구동한다. 모두 만들지 않고 가져다 쓸 수 있는 부품이다.
10. **이 분야는 수렴하고 있고, 기술은 오래간다.** 독립된 신호들이 같은 방향을 가리킨다. Cursor의 2026년 4월 글은 '모델 중심 자랑에서 하니스 중심 엔지니어링으로의 이동'을 말하고, Altman은 하니스와 모델이 점점 분리할 수 없게 되고 모델을 감싼 런타임이 제품 표면의 일부가 되었다고 설명했다. 하니스 엔지니어링은 모델의 한계를 임시로 때우는 작업이 아니라 스택의 영구적인 층이므로, 하니스 기술은 다음 모델이 쓸모없게 만들 비계가 아니라 오래가는 투자다.
