# 장기 실행 에이전트와 하니스 엔지니어링

도구, 핸드오프, 가드레일, 컨텍스트 윈도 같은 기본 부품만으로는 실제로 쓸 만한 시스템이 되지 않는다. 시간이 지나도 공사가 무너지지 않게 붙들어 주는 비계, 현장에 부딪혀도 버티는 계획, 실수를 미리 잡아내는 검사 지점이 필요하다. 에이전트 엔지니어링에서 이 역할을 하는 것이 하니스다. 이 장은 하니스가 무엇인지, 처음부터 어떻게 만드는지, Codex CLI 하니스에 지금 붙일 수 있는 부품이 무엇인지 설명한다.

또 OpenAI의 오픈소스 하니스 Symphony 같은 참조 구현이 이 패턴을 어떻게 규모 있게 보여 주는지, 그리고 결과의 품질을 정하는 것이 모델이 아니라 하니스라는 증거를 정리한다.

---

## 1. 핵심 요점

- 하니스 엔지니어링은 AI 에이전트가 안정적으로 일하게 하는 인프라, 제약, 피드백 고리를 설계하는 일이며, 프롬프트 엔지니어링보다 한 단계 위에 있다.
- 하니스는 인터페이스, 메커니즘, 멀티 에이전트 확장의 세 계층으로 볼 수 있고, 결과 품질은 모델보다 하니스가 좌우한다.
- 밀폐된 테스트, 기계가 읽을 수 있는 문서, 모듈화된 아키텍처 세 기둥이 약하면 에이전트는 추측하게 된다.
- WORKFLOW.md는 YAML 실행 설정과 Liquid 프롬프트 템플릿을 합쳐 에이전트 정책을 버전 관리되는 저장소 산출물로 만든다.
- 세션 ID, 체크포인트 파일, 데이터베이스로 상태를 저장하고, 백오프 재시도, 사람 에스컬레이션, 롤백으로 실패에 대응한다.
- 작업 증명 원칙은 에이전트가 자기 보고가 아니라 CI 통과, 리뷰 피드백, 변경 요약 같은 검증 가능한 증거로 완료를 보이게 한다.
- Symphony(배치형)와 NanoClaw(상주형)는 서로 다른 지점의 참조 구현이며, Docker MCP Toolkit, 내장 코드 리뷰 스킬, 앱 서버 같은 부품은 직접 만들지 않고 가져다 쓸 수 있다.
- 벤치마크, 학술 연구, 실무자 이론, OpenAI 내부 사례가 모두 같은 결론을 가리킨다. 성능이 부족하면 모델을 바꾸기 전에 하니스를 고친다.

---

## 학습 목표

- 하니스가 무엇인지, 세 계층 틀과 세 기둥으로 보았을 때 왜 모델이 아니라 하니스가 결과 품질을 정하는지 설명한다.
- 코드베이스를 세 기둥(밀폐된 테스트, 기계가 읽을 수 있는 문서, 모듈화된 아키텍처) 기준으로 점검해 에이전트가 추측하게 만드는 곳을 찾는다.
- 실행 설정과 행동 정책을 함께 담는 WORKFLOW.md를 설계한다.
- 체크포인트 기반 상태 저장을 구현해 중단된 에이전트가 끝낸 일을 되풀이하지 않고 재개하게 한다.
- Symphony를 쓰든 안 쓰든 자기 파이프라인에 작업 증명 원칙을 적용한다.
- 규모에 맞는 하니스 부품과 조율 패턴을 고르고, 모델을 바꾸기 전에 하니스부터 개선해야 하는 이유를 댄다.
