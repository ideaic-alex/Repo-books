# WORKFLOW.md 패턴

AGENTS.md는 프로젝트와 규칙을 설명하는 정적인 문서다. 실행마다 바뀌지 않는다. Symphony가 도입한 WORKFLOW.md는 한 파일에 두 가지를 합쳐서 훨씬 강력한 패턴이 된다. 이 문서는 파일 구조, 에이전트 정책을 저장소 산출물로 다룰 때 생기는 이점, Symphony 없이 이 형식을 쓰는 방법을 설명한다.

---

## 1. 파일 구조

WORKFLOW.md는 두 부분으로 이루어진다.

- **YAML 프런트 매터**: 실행 환경 설정이다. 모델 선택, 턴 제한, 연동 엔드포인트, 반드시 만들어야 하는 작업 증명 산출물을 적는다.
- **Markdown 본문**: 에이전트의 시스템 프롬프트다. Liquid 호환 템플릿으로 쓴다.

실행 시점에 하니스가 이슈별 정보(티켓 제목, 저장소, 브랜치, 수정 금지 파일)를 템플릿에 채워 넣어 렌더링하고, 그 결과를 첫 지시로 에이전트에 넘긴다. 원서의 예시는 프런트 매터가 다음과 같다.

```yaml
---
model: gpt-5.5
max_turns: 40
issue_tracker: linear
workspace_mode: isolated
proof_of_work: [ci, review, complexity]
---
```

본문은 일반 Markdown이고, 중간중간 {{ issue.title }}, {{ issue.description }}, {{ repo.name }}, {{ branch_name }}, {{ protected_files }} 같은 Liquid 자리 표시자가 들어간다. 원서의 본문 예시는 "이 이슈를 구현하라"는 도입, 이슈 설명과 저장소와 브랜치 같은 맥락, 그리고 세 가지 규칙으로 이루어진다. 규칙은 완료 표시 전에 전체 테스트를 돌릴 것, 보호 파일은 수정하지 말 것, 새 함수에는 테스트를 쓸 것이다.

프런트 매터의 proof_of_work 항목은 뒤에서 다룰 작업 증명 원칙과 직접 연결된다. 어떤 증거가 있어야 일이 끝난 것으로 보는지를 설정으로 못 박는 것이다.

## 2. 에이전트 정책이 저장소 산출물이 된다

이 패턴의 구조적 의미는 곱씹을 가치가 있다. 에이전트의 행동이 버전 관리되는 저장소 산출물이 된다. 그래서 다음이 가능해진다.

- 릴리스 사이에 에이전트 정책을 diff로 비교한다.
- 버그를 만든 행동 변경을 되돌린다.
- 프로덕션에 반영하기 전에 풀 리퀘스트 리뷰를 요구한다.

에이전트의 지시문이 애플리케이션 코드와 같은 저장소에 있으니 같은 거버넌스를 받는다. 에이전트가 이상하게 행동했을 때 원인을 찾으려면 이 파일의 이력을 먼저 보면 된다.

## 3. Symphony 없이 쓰는 방법

Symphony의 전체 조율 계층을 쓰지 않아도 이 파일 형식은 자기 파이프라인에 가져올 수 있다. Codex CLI의 exec 호출 앞단에서 다음 세 단계를 하면 된다.

1. 아무 YAML 파서로 프런트 매터를 읽는다.
2. Liquid 호환 엔진으로 본문을 렌더링한다. 파이썬이라면 python-liquid를 쓸 수 있고, 템플릿을 Jinja로 다시 쓴다면 jinja2도 된다.
3. 렌더링 결과를 시스템 프롬프트로 넘긴다.

이렇게 하면 Symphony가 요구하는 Elixir 의존성 없이 버전 관리의 이점을 모두 얻는다.

파일 위치는 저장소 루트에 AGENTS.md와 나란히 두기를 권한다. 두 파일 모두 에이전트 정책을 담고 있으므로, 에이전트가 예상 밖으로 행동한 이유를 따질 때 둘을 함께 검토해야 한다.

## 4. AGENTS.md와 WORKFLOW.md 비교

| 구분 | AGENTS.md | WORKFLOW.md |
|---|---|---|
| 성격 | 정적 문서 | 실행마다 렌더링되는 템플릿 |
| 담는 내용 | 프로젝트 설명, 규칙 | 실행 설정(YAML)과 작업별 프롬프트(Liquid 본문) |
| 변하는 정도 | 실행 간에 안 바뀜 | 이슈마다 채워지는 값이 다름 |
| 위치 | 저장소 루트 | 저장소 루트(AGENTS.md 옆) |
