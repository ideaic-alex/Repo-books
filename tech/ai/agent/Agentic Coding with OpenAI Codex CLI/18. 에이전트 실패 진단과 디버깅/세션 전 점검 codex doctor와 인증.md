# 세션 전 점검 codex doctor와 인증

세션을 시작한 뒤에 설정 오류를 발견하면 이미 토큰을 쓴 뒤다. `codex doctor`는 세션을 열기 전에 설정과 환경 문제를 미리 잡아내는 진단 명령이다. 이 문서는 `codex doctor`가 무엇을 확인하는지, 언제 돌려야 하는지, 결과를 어떻게 읽어야 하는지, 그리고 인증 문제를 따로 떼어 보는 방법을 정리한다.

---

## 1. codex doctor가 확인하는 항목

```bash
codex doctor
```

명령은 일곱 가지를 점검한다.

1. API 키의 유효성과 권한. 인증이 되는가.
2. 모델 접근. 설정해 둔 모델에 닿을 수 있는가.
3. 네트워크 연결. 필요한 제공자 엔드포인트에 HTTP로 닿고, chatgpt.com에 WebSocket을 열 수 있는가.
4. MCP 서버 연결. 선언한 서버가 모두 응답하는가.
5. `config.toml`의 문법과 키 유효성. 오타나 폐기된 키가 없는가.
6. 샌드박스 호환성. 현재 OS와 커널이 요청한 샌드박스 모드를 지원하는가.
7. AGENTS.md 파일 탐색. 어떤 지침 파일이 로드될 것인가.

책이 쓰인 시점 기준으로는 진단 범위가 더 넓다. 설치된 Codex 버전을 보고하고, 새 릴리스가 있는지 확인하며, 환경 변수, Git 설정, 터미널 기능, app-server 상태, 스레드 목록까지 다룬다. 이 중 스레드 목록은 기존 스레드 전체와 각각의 상태, 디스크 사용량을 보여 주기 때문에, 쌓인 세션이 예상보다 많은 저장 공간을 차지하는 문제를 찾을 때 특히 유용하다.

## 2. 언제 돌리나

설치한 직후, 설정을 바꾼 뒤, 프로필을 바꿀 때, 그리고 뭔가 이상하다고 느껴질 때마다 돌린다. 5초짜리 진단 한 번이, 비싼 세션이 몇 턴 지난 뒤에야 나타나는 영문 모를 에러를 20분 동안 붙잡고 씨름하는 일을 막아 준다.

`codex doctor`는 점검이 하나라도 실패하면 0이 아닌 종료 코드로 끝난다. 그래서 CI/CD 파이프라인 앞단의 사전 점검 관문(pre-flight gate)으로 끼워 넣을 수 있다.

## 3. 결과를 읽을 때 주의할 점

실패가 떴다고 해서 곧바로 설치가 망가졌다고 결론내리면 안 된다. 네트워크가 제한된 환경에서는 연결 점검이 줄줄이 실패할 수 있다. DNS 해석, 제공자 엔드포인트 HTTP 접속, chatgpt.com WebSocket, 그리고 api.github.com에 대한 업데이트 확인이 그렇다. 이때도 설치, 설정, 인증, MCP 항목은 모두 OK로 나올 수 있다.

판단 기준은 이렇다. 로컬 점검은 모두 정상인데 네트워크 해석만 실패한다면, 원인은 Codex가 아니라 샌드박스나 프록시다.

출력 형식은 두 가지 옵션으로 바꿀 수 있다.

| 옵션 | 효과 |
|---|---|
| `--json` | 민감 정보를 가린(redacted) 지원용 보고서를 기계가 읽는 형식으로 내보낸다 |
| `--summary` | 그룹별 점검 행과 마지막 개수 요약만 보여 준다 |

## 4. 인증 실패 분리하기

세션이 인증 오류로 시작되지 않을 때는 다시 시작하기 전에 문제를 먼저 분리해 본다.

```bash
# 로그인 절차를 띄우지 않고 현재 인증 상태만 확인
codex login status
# 토큰 만료 시각을 직접 확인
cat ~/.codex/auth.json | jq '.expires_at'
```

`codex login status`는 인증이 되어 있는지, 어떤 방식(브라우저 OAuth, 디바이스 코드, API 키)을 썼는지, 토큰이 유효한지를 알려 준다. 흔한 실패 패턴은 `auth.json` 파일이 손상되었거나 만료된 경우다. 이때는 `codex logout`을 한 뒤 `codex login`을 다시 하면 해결된다.

## 5. 정리

점검은 싼 것부터 한다. 설치와 설정과 인증은 `codex doctor` 한 번으로 거의 다 걸러지고, 그 뒤에 남는 문제만 세션 기록이나 로그 추적 같은 비싼 방법으로 파고든다. 이 순서는 뒤쪽 "진단 체크리스트" 문서에서 다시 정리한다.
