# 세션 기록으로 원인 찾기

에이전트가 엉뚱한 결과를 내놓았을 때 가장 먼저 할 일은 "어느 지점에서 의도와 어긋났는지"를 찾는 것이다. Codex CLI는 세션에서 일어난 일을 전부 파일로 남기므로, 이 기록을 거꾸로 따라가면 대부분의 원인을 짚을 수 있다.

이 문서는 세션 기록(롤아웃 파일)을 읽는 법, 실행 없이 계획만 들여다보는 진단용 승인 모드, 그리고 TUI 안에서 바로 쓰는 진단 슬래시 명령 세 가지를 다룬다.

---

## 1. 세션 기록은 어디에 있나

세션 기록은 `~/.codex/sessions/` 아래에 JSONL 형식의 롤아웃(rollout) 파일로 저장된다. JSONL은 한 줄에 JSON 객체 하나가 들어가는 형식이고, 줄 하나가 이벤트 하나다. 파일 안에는 타입이 붙은 `RolloutItem` 이벤트가 쌓인다. `SessionMeta`, `UserMessage`, `ResponseItem`, `EventMsg`, `ApprovalDecision` 같은 종류가 있고, 이것들을 이어 붙이면 세션에서 일어난 일의 완전한 기록이 된다.

도구 호출 한 쌍은 대략 이런 모양이다. 호출(`tool_call`)이 먼저 적히고, 이어서 결과(`tool_result`)가 `call_id`로 짝지어 적힌다.

```json
{"type":"tool_call","id":"call_def456","name":"run_shell","args":{"cmd":"npm test -- --testPathPattern=auth"},"ts":1710510123}
{"type":"tool_result","call_id":"call_def456","ok":false,"output":"FAIL tests/auth.test.ts ...","ts":1710510126}
```

위 예시에서는 앞서 `read_file`로 `src/handlers/auth.ts`를 읽고, 이어서 인증 테스트를 돌렸더니 `ok: false`로 실패한 장면이 이어진다. 이런 식으로 "무엇을 읽고, 무엇을 실행했고, 결과가 어땠는지"가 시간순으로 남는다.

## 2. 어긋난 지점을 찾는 요령

에이전트가 의도에서 벗어나는 지점은 거의 항상 세 가지 중 하나다.

| 유형 | 설명 |
|---|---|
| 예상 밖의 결과를 돌려준 도구 호출 | 읽은 내용이나 출력이 기대와 다르다 |
| 조용히 실패한 명령 | `ok: true`인데 출력 안에는 에러가 들어 있다 |
| 잘못 추론한 추론 단계 | 도구 결과는 맞았는데 에이전트가 그릇된 결론을 냈다 |

요령은 끝에서부터 거꾸로 올라가며 "내가 기대한 결과가 마지막으로 나온 곳"을 찾는 것이다. 그 바로 다음 단계가 어긋난 지점일 가능성이 높다.

실패한 도구 결과만 한 번에 뽑으려면 `jq`를 쓴다.

```bash
jq -s 'map(select(.type == "tool_result" and .ok == false))' transcript.jsonl
```

실패 결과만으로는 부족할 때를 위해, 세션 전체의 도구 호출 분포를 세거나 승인 결정을 전부 뽑는 방법도 있다.

```bash
# 가장 최근 세션 롤아웃 찾기
ls -t ~/.codex/sessions/*.jsonl | head -1
# 도구 호출 종류별 횟수 세기
cat ~/.codex/sessions/<session>.jsonl | \
  jq 'select(.type == "ResponseItem") | .item.type' | \
  sort | uniq -c | sort -rn
# 승인 결정만 모두 추출
cat ~/.codex/sessions/<session>.jsonl | \
  jq 'select(.type == "ApprovalDecision")'
```

호출 종류별 횟수를 보면 같은 파일을 반복해서 읽는 식의 루프가 있었는지 한눈에 드러난다. 승인 결정 목록은 어떤 명령을 누가 허용했는지 점검하는 감사 용도로도 쓴다.

기록을 눈으로 보기 편하게 해 주는 도구도 있다. 커뮤니티가 만든 codex-replay는 JSONL 파일을 브라우저에서 볼 수 있는 HTML로 바꿔 주고, ccusage 프로젝트는 롤아웃에 담긴 토큰 카운터를 읽어 일별·월별 비용 보고서를 만들어 준다.

## 3. 승인 모드를 진단 도구로 쓰기

이전 세션이 뜻밖의 행동을 했는데 그 계획을 실제로 돌리기 전에 먼저 보고 싶다면, 승인 모드를 가장 엄격하게 잡는다.

```bash
codex -a untrusted -s read-only "refactor the authentication module to use JWT"
```

`-a untrusted -s read-only` 조합은 순수한 점검 모드다. 에이전트는 파일을 읽을 수만 있고, 쓰거나 실행하지 못한다. 에이전트가 하려는 모든 행동이 상세한 내용과 함께 승인 요청으로 뜨기 때문에, 계획을 한 단계씩 확인할 수 있다.

untrusted 모드에서 요청을 거절할 때는 이유나 수정 방향을 바로 적어 줄 수 있다. 예를 들어 `src/auth/jwt.ts`에 쓰겠다는 요청에 `reject: use the jose library, not new-jwt-library`라고 답하면, 에이전트는 이 교정을 받아 계획을 그 자리에서 고친다. 세션을 끊고 다시 시작하지 않아도 되는 것이 장점이다.

## 4. TUI 슬래시 명령 세 가지

TUI를 떠나지 않고도 진단 정보를 얻는 슬래시 명령이 세 개 있다.

**/status**는 현재 세션 설정과 토큰 사용량을 보여 준다. 뭔가 이상하다고 느꼈을 때 가장 먼저 쳐 볼 명령이다. 지금 활성인 모델, 추론 강도, 토큰 소모량, 실제 적용 중인 샌드박스 모드를 확인할 수 있다.

**/debug-config**는 설정이 어떤 순서로 해석됐는지 전체 계층을 펼쳐 보여 준다. 낮은 우선순위에서 높은 우선순위까지의 레이어 순서, 키마다의 유효 값과 그 값을 정한 레이어, 그리고 `allowed_approval_policies`, `allowed_sandbox_modes`, `mcp_servers`, `rules` 같은 정책 내용이 나온다. 관리형 `requirements.toml`이 사용자의 `config.toml`을 조용히 덮어쓰는 기업 환경에서 특히 쓸모가 있다. 예를 들어 `sandbox_mode = "danger-full-access"`를 적었는데 무시되는 것 같다면, `/debug-config`에서 관리 정책이 `workspace-write`를 강제하고 있다는 사실이 드러난다.

**/feedback**은 요청 ID, 세션 ID, 연결 상태, 마지막 에러 메시지, 활성 도구 수, MCP 서버 상태 같은 진단 정보를 모아 OpenAI 메인테이너에게 바로 제출한다. 예상 밖으로 동작한 세션은 닫기 전에 `/feedback`을 실행해 두는 것이 좋다. GitHub에 이슈를 올릴 때 가장 쓸모 있는 단서가 요청 ID이기 때문이다.
