# 샌드박스와 실행 정책 오프라인 검증

빌드 도구나 테스트 러너가 에이전트 세션에서만 실패하는 일이 있다. 원인이 샌드박스 제한인지 실행 정책 규칙인지 확인하려고 매번 에이전트 세션을 띄우면 토큰과 시간이 든다. Codex CLI에는 세션을 시작하지 않고 두 가지를 따로 검증하는 명령이 있다. `codex sandbox`는 명령을 실제 샌드박스 아래에서 돌려 보고, `codex execpolicy check`는 `.rules` 파일이 어떤 결정을 내리는지 미리 보여 준다.

---

## 1. codex sandbox로 샌드박스 아래에서 명령 돌리기

`codex sandbox` 하위 명령은 에이전트 세션에서 적용되는 것과 똑같은 샌드박스 제한을 걸고 임의의 명령을 실행한다. 세션은 시작하지 않는다.

```bash
# macOS: Seatbelt 제한 아래에서 실행
codex sandbox macos -- npm run build
# macOS: workspace-write 권한과 거부 로그
codex sandbox macos --permissions-profile workspace-write --log-denials -- cargo test
# Linux: bubblewrap/seccomp 제한 아래에서 실행
codex sandbox linux -- pytest tests/
# Linux: workspace-write 모드
codex sandbox linux --permissions-profile workspace-write -- make install
```

macOS에서 `--log-denials`를 붙이면 Seatbelt가 거부한 모든 동작이 stderr로 찍혀, 어떤 파일 시스템 경로나 네트워크 동작이 막혔는지 정확히 알 수 있다. macOS는 Seatbelt, Linux는 bubblewrap과 seccomp가 제한을 맡는다.

## 2. 사례: Codex 밖에서는 되는데 안에서는 실패하는 Rust 빌드

Rust 프로젝트가 평소엔 빌드되는데 에이전트의 샌드박스 안에서만 실패한다고 하자. 다음 세 단계로 원인을 좁힌다.

```bash
# 1단계: 샌드박스 아래에서 빌드해 거부 흔적 찾기
codex sandbox linux -- cargo build 2>&1 | grep -i denied
# 2단계: 실패하면 workspace-write로 다시 시도
codex sandbox linux --permissions-profile workspace-write -- cargo build
# 3단계: 그래도 실패하면 네트워크 접근이 원인
# (예: crates.io 다운로드가 샌드박스에 막힘)
```

1단계에서 쓰기 거부가 보이면 쓰기 권한 문제이고, 2단계에서 해결되면 권한 프로필로 풀 수 있다. 그래도 안 되면 의존성 내려받기 같은 네트워크 접근이 막힌 것이다. 이 흐름의 이점은 샌드박스 제한을 디버깅하려고 완전한 에이전트 세션을 띄우는 비용을 아낄 수 있다는 점이다.

## 3. 실행 정책 규칙(.rules)이란

15장에서 CI의 결정성을 위해 `--ignore-rules`를 소개했는데, 그 옵션이 무시하는 대상이 바로 이 규칙이다. 실행 정책 규칙은 에이전트가 샌드박스 밖에서 실행할 수 있는 명령을 결정한다. OS가 허용하는 범위(5장의 샌드박스 모드)와 에이전트가 건드릴 수 있는 파일(권한 프로필) 사이에 놓이는 계층이다. 샌드박스가 명령이 피해를 주지 못하게 막는다면, 규칙은 그 명령을 아예 실행해도 되는지를 정한다.

규칙은 Starlark로 쓴 `.rules` 파일에 담긴다. Starlark는 파이썬과 비슷하지만 부수 효과가 없는 작은 설정 언어다. Codex는 시작할 때 여러 레이어에서 규칙을 읽는다. 팀 설정, 사용자 레이어 `~/.codex/rules/`, 프로젝트 로컬 `<repo>/.codex/rules/`가 그것이다. 프로젝트 레이어는 해당 `.codex/` 디렉터리를 신뢰했을 때만 로드된다. 책이 쓰인 시점에는 실험적 기능이다.

핵심 구문은 `prefix_rule()`로, 명령의 앞부분 토큰으로 일치 여부를 판단해 결정을 부여한다.

```python
prefix_rule(
    pattern = ["gh", "pr", ["view", "list"]],
    decision = "prompt",
    justification = "Reading PRs is fine, but flag it for visibility.",
    match = ["gh pr view 7888", "gh pr list --state open"],
    not_match = ["gh pr merge 7888"],
)
```

- `pattern`의 각 요소는 글자 그대로의 토큰이거나, 그 자리에서 허용할 대안들의 목록이다. 위 규칙은 `gh pr view`와 `gh pr list`는 잡고 `gh pr merge`는 잡지 않는다.
- `decision`은 `allow`(기본값), `prompt`(사람이 승인한 뒤에만 실행), `forbidden`(절대 실행하지 않음) 중 하나다.
- `justification`은 선택 항목으로, 승인 프롬프트와 감사 출력에 이유로 표시된다.
- `match`와 `not_match`는 규칙이 잡아야 할 명령과 잡지 말아야 할 명령의 예시이며, 다음 절의 오프라인 검증기가 사용한다.

여러 규칙이 한 명령에 동시에 걸리면 가장 엄격한 결정이 이긴다. 순서는 `forbidden`, `prompt`, `allow` 순으로 강하다. 또 Codex는 안전한 연산자(`&&`, `||`, `;`, `|`)로 이어진 셸 체인을 쪼개 각 명령을 따로 평가한다. 반면 리다이렉션, 명령 치환, 변수가 들어간 호출은 쪼개지 않고 하나의 명령으로 취급한다.

## 4. codex execpolicy check로 규칙 검증하기

`.rules` 파일을 배포하기 전에 오프라인으로 검증한다.

```bash
codex execpolicy check \
  --pretty \
  --rules ~/.codex/rules/default.rules \
  -- gh pr view 7888 --json title,body,comments
```

출력에는 유효 결정(일치한 모든 규칙 중 가장 엄격한 수준, `forbidden > prompt > allow`)과, 접두사가 일치한 모든 규칙, 그리고 실제로 일치한 `matchedPrefix`가 나온다. `--rules`를 여러 번 주면 규칙 파일을 합쳐서 검증할 수 있다.

```bash
codex execpolicy check \
  --pretty \
  --rules ~/.codex/rules/default.rules \
  --rules .codex/rules/project.rules \
  -- rm -rf node_modules
```

이 명령은 "사용자 규칙과 프로젝트 규칙을 합치면 `rm -rf node_modules`가 어떻게 판정되는가"를 세션 없이 알려 준다. 팀 규칙을 넣기 전에 의도한 대로 막히고 허용되는지 확인하는 용도다.
