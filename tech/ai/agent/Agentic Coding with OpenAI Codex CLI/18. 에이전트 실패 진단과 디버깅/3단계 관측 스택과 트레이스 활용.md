# 3단계 관측 스택과 트레이스 활용

로컬 롤아웃 파일은 Codex CLI 디버깅의 토대지만, 관측(observability) 체계의 한 층일 뿐이다. 관측은 세 단계로 나뉘고, 단계마다 풀 수 있는 문제가 다르다. 이 문서는 세 단계의 역할, 각 단계 설정 방법, 터미널에서 롤아웃을 직접 훑는 방법, 그리고 트레이스로 풀 수 있는 실전 문제 네 가지를 정리한다.

---

## 1. 세 단계 한눈에 보기

위에서 아래로 쌓인 세 단계 구조다. 1단계는 `~/.codex/sessions`의 로컬 롤아웃 JSONL 파일로, 감사와 재생에 쓴다. API 키로 돌린 세션은 자동으로 2단계인 OpenAI Platform Traces로 올라가며, 여기서는 도구 호출, 핸드오프(서브에이전트 인계), 소요 시간이 스팬 트리(span tree) 형태로 보인다. 팀은 여기서 더 나아가 3단계로, 자기 백엔드(Jaeger, Grafana Tempo, SigNoz 등)에 OTLP/gRPC 방식의 OpenTelemetry 스팬을 내보낼 수 있다.

| 단계 | 저장 위치 | 쓰임새 |
|---|---|---|
| 1단계 | 로컬 `~/.codex/sessions/*.jsonl` | 감사 기록, 규정 준수, 세션 재생 |
| 2단계 | OpenAI Platform Traces (platform.openai.com/traces) | 시각적 탐색 |
| 3단계 | OTLP로 내보낸 외부 백엔드 | 팀 전체 대시보드와 알림 |

## 2. 1단계: 로컬 롤아웃 파일

이 장 처음에 설명한, 추가만 되는(append-only) 전체 JSONL 기록이다. 감사 추적, 규정 준수, 세션 재생에 가장 알맞다.

## 3. 2단계: OpenAI Platform Traces

Codex CLI의 롤아웃 추적은 도구 호출, 코드 모드 전환, 세션 간 관계, 멀티 에이전트의 부모-자식 연결을 자동으로 기록한다. ChatGPT 요금제가 아니라 API 키로 Codex CLI를 쓰면, 이 트레이스가 OpenAI 플랫폼의 Logs 아래 Traces에 나타난다. 각 트레이스에는 다음이 담긴다.

- 모델 호출: 프롬프트, 소모 토큰, 추론 강도, 응답
- 도구 호출: 도구 이름, 인자, 출력
- 핸드오프: 서브에이전트 생성과 스레드 관계
- 가드레일 평가: 승인 결정, 정책 검사
- 시간 정보: 실제 경과 시간, 대기 시간, 생성 지연

대시보드는 세션을 스팬 트리로 보여 주고, 펼치면 정확한 도구 인자, stdout/stderr 출력, 승인 결과를 볼 수 있다. ChatGPT 요금제 세션은 이 대시보드에 나타나지 않는다. 플랫폼 수준의 가시성이 필요하면 API 키가 있어야 한다.

## 4. 3단계: OTLP 외부 백엔드 내보내기

자체 관측 스택에 트레이스가 필요한 팀을 위해 Codex CLI는 OTLP/gRPC로 OpenTelemetry 스팬을 내보낸다. 설정은 `~/.codex/config.toml`에 쓴다.

```toml
[otel]
log_user_prompt = true
exporter = { otlp-grpc = { endpoint = "https://ingest.eu.signoz.cloud:443", headers = { "signoz-ingestion-key" = "your-key-here" } } }
```

Jaeger, Grafana Tempo, SigNoz 같은 자체 호스팅 백엔드라면 로컬 엔드포인트를 쓴다.

```toml
[otel]
log_user_prompt = true
exporter = { otlp-grpc = { endpoint = "http://localhost:4317" } }
```

세션마다 만들어지는 스팬은 `codex.session`, `codex.turn.N`, `codex.model_call` 또는 `codex.tool.<name>` 계층을 따른다. 주요 속성은 `codex.session_id`, `codex.model`, `codex.tool.name`, `codex.tool.exit_code`와, 턴별 토큰 소모량인 `codex.tokens.input`, `codex.tokens.cached_input`, `codex.tokens.output`이다. OTLP 내보내기는 일반적인 환경에서 세션 경과 시간에 한 자릿수 퍼센트 수준의 낮은 오버헤드를 더한다.

## 5. 롤아웃 트레이스 리듀서

터미널 중심 디버깅에서는 표준 셸 도구로 롤아웃 JSONL을 직접 볼 수 있다. 책이 쓰인 시점에는 실험적인 `codex debug trace-reduce` 도우미도 제공되지만, JSONL을 직접 쿼리하는 쪽이 버전이 바뀌어도 그대로 쓸 수 있다고 한다.

```bash
jq '.items[] | select(.type == "tool_call") | {tool: .name, status, duration_ms}' \
  ~/.codex/sessions/2026/05/07/rollout-*.jsonl
```

이러면 도구 호출, 종료 상태, 소요 시간을 간결하게 볼 수 있다. 실패만 보거나, 오래 걸린 명령, 롤아웃 스키마에 담긴 토큰 필드를 보려면 `jq` 필터를 바꾸면 된다.

## 6. 트레이스로 푸는 실전 문제

**잘못된 파일을 수정한 경우.** platform.openai.com/traces에서 세션 ID로 거르고, 잘못된 파일이 수정된 턴을 펼친다. `apply_patch` 앞에 어떤 `read_file` 호출이 있었는지 본다. 관련 파일이 컨텍스트에 있었는지, 아니면 에이전트가 이름 규칙만 보고 짐작했는지 확인한다.

**느린 세션 찾기.** 가장 오래 걸린 도구 호출 다섯 개는 JSONL 쿼리로 뽑는다.

```bash
jq '[.items[] | select(.type == "tool_call")
  | {tool: .name, duration_ms: .duration_ms}]
  | sort_by(-.duration_ms) | .[0:5]' <rollout-file>
```

**토큰 비용 귀속.** 작업별 비용을 추적하는 팀이라면 OTLP 스팬이 턴마다 토큰 수를 싣고 있다. Grafana에서 `sum by (codex.model)(rate(codex_tokens_output_total[5m]))` 같은 쿼리를 쓰면 모델별 출력 토큰 소모 속도를 볼 수 있다.

**멀티 에이전트 관계 파악.** 플랫폼 트레이스 대시보드는 `codex.parent_session_id`로 서브에이전트 스레드 사이의 부모-자식 관계를 보여 준다. 이를 통해 위임한 지시가 제대로 전달됐는지 확인하고, 깊이 한도를 넘긴 서브에이전트를 찾고, 서브에이전트의 실패를 부모의 재시도 결정과 연결해서 볼 수 있다.
