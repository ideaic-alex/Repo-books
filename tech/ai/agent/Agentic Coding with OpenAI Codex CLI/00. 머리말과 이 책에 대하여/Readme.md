# 머리말과 이 책에 대하여

이 문서는 책 'Agentic Coding with OpenAI Codex CLI'의 머리말을 정리한 학습 노트이다. 저자가 왜 이 책을 쓰게 되었는지, 누구를 위해 썼는지, 책을 어떻게 읽으면 좋은지를 다룬다.

머리말은 본격적인 기술 내용에 들어가기 전의 안내문이지만, 이 책 전체를 관통하는 관점이 여기에 담겨 있다. 핵심은 "AI 코딩 도구를 자동완성기로 쓰는 것"과 "에이전트로 쓰는 것"은 다르다는 점이다. 이 차이를 먼저 이해하고 나면 뒤에 나오는 승인 모드, 컨텍스트 관리, 서브에이전트 같은 주제가 왜 필요한지 자연스럽게 보인다.

---

## 1. 저자가 이 책을 쓰게 된 계기

저자는 2025년 11월의 어느 화요일 아침, 런던으로 가는 통근 열차 안에서 Codex CLI를 처음 제대로 써 보았다. 기차는 약 58분이 걸리는 구간이었고, 노트북과 그리 좋지 않은 모바일 데이터 연결이 전부였다. Codex CLI는 몇 주 전에 설치해 명령 몇 개만 돌려 보고 시큰둥하게 넘어간 상태였다.

그날은 실제 문제가 있었다. 6개월 전에 직접 만든 Node 서비스가 스테이징 환경에서 이상하게 동작하기 시작했는데, 저자는 그 저장소의 내용이 머릿속에 거의 남아 있지 않았다. 프로젝트 디렉터리에서 Codex CLI를 실행하고 증상만 설명한 뒤 지켜보았다.

Codex CLI가 한 일은 단순히 고칠 만한 코드를 제안하는 데 그치지 않았다.

- 소스 파일을 직접 읽고 실행 경로를 따라가며 원인을 추적했다.
- 테스트 스위트를 돌렸다.
- 저자가 언급하지 않은 두 번째 문제를 스스로 찾아냈다.
- 그 문제를 재현하는, 실패하는 테스트를 먼저 작성했다.
- 두 문제를 모두 고친 뒤 풀 리퀘스트를 열지 물어왔다.

열차가 중간 역(여기서도 실제로 무슨 문제가 생겼다고 한다)에 닿을 즈음 저자 손에는 깔끔한 diff와 근본 원인 설명이 있었고, 방금 본 것에 대한 약간의 불안감도 남았다.

저자는 초기 Copilot 시절부터 AI 코딩 도구를 써 왔다. 브라우저 탭의 ChatGPT, 사이드바의 Claude, 여러 종류의 Copilot, Cursor, Windsurf 등을 거쳤고, 모두 자동완성이 유용한 정도로는 유용했다고 평가한다. 그런데 이번 경험이 달랐던 이유는 모델이 더 똑똑해서가 아니라 "동작(operating)"했기 때문이다. 질문에 답하는 데 그치지 않고 컨텍스트를 읽고, 행동을 취하고, 상태를 관리하고, 오류에서 스스로 복구했다. 저자는 이 차이가 미묘하게 들리지만 실제로는 결코 미묘하지 않다고 말하며, 이때부터 이 책이 필요해졌다고 적는다.

참고로 저자는 각주에서 GitHub Copilot이 2021년에 기술 프리뷰로 처음 나온 최초의 AI 페어 프로그래밍 도구이며, GitHub, OpenAI, Microsoft가 개발한 생성형 AI 모델로 동작한다고 밝힌다.

## 2. 저자의 생각을 바꾼 것: 에이전트 루프라는 구조

저자의 생각을 바꾼 것은 어느 한 번의 인상적인 결과물이 아니라 구조를 이해한 일이었다.

### 2.1 반응형 도구와 에이전트의 차이

대부분의 AI 코딩 도구는 본질적으로 컨텍스트 윈도(모델이 한 번에 볼 수 있는 입력 범위)를 가진 고급 텍스트 완성기이다. 코드를 주면 코드를 더 만들어 준다. 컨텍스트 윈도는 계속 커지고 통합 기능은 매끄러워지지만, 근본 방식은 반응형이다. 프롬프트를 쓰면 답이 오고, 받아들이거나 거절하고, 다시 프롬프트를 쓴다.

Codex CLI는 전제가 다르다. 이 도구는 에이전트 루프다. 목표를 주면 계획하고, 실행하고, 결과를 관찰하고, 조정하고, 끝나거나 막힐 때까지 계속한다. 구체적인 특징은 다음과 같다.

- 실제 도구 사용 능력이 있다. 파일을 읽고 쓰고, 임의의 셸 명령을 실행하고, 테스트를 돌리고, 외부 API를 호출한다. (저자는 각주에서 공식 Codex CLI 문서가 이런 도구 사용 능력을 설명한다고 안내한다.)
- 서로 독립적인 하위 작업은 서브에이전트를 띄워 병렬로 처리할 수 있다.
- 한 세션 안에서 여러 단계에 걸쳐 컨텍스트를 이어 간다.
- 물어봐야 할 때와 그냥 진행해도 될 때를 구분한다.

### 2.2 도구마다 잘하는 일이 다르다

저자는 세 가지 방식이 각각 잘하는 영역이 다르다고 정리한다.

| 방식 | 잘하는 일 |
| --- | --- |
| 자동완성 | 한 줄 단위의 코드 작성 |
| 채팅 | 질문과 답변 |
| 에이전트 실행 | 시작, 중간, 끝이 있는 "작업" 단위의 일 |

에이전트 실행이 맞는 일은 여러 파일을 읽고, 여러 명령을 실행하고, 중간에 여러 판단을 내려야 하는 작업이다. 모듈 리팩터링, 기능 하나를 처음부터 끝까지 추가하기, 실패하는 빌드 진단하기 같은 일이 그렇다. 예전에는 이런 일이 오후 한나절을 잡아먹었고, Codex CLI는 바로 이런 일을 위해 만들어졌다.

### 2.3 흔한 평가가 놓치는 점

AI 코딩 도구에 대한 과장된 논평은 많은데, 저자는 대부분이 이 구분을 놓친다고 본다. 자동완성의 품질을 벤치마크하거나 모델이 맞는 함수 이름을 얼마나 자주 제안하는지를 재는 식이다. 저자는 이것이 엉뚱한 것을 재는 일이라고 말한다. 정말 흥미로운 질문은 모델이 정렬 알고리즘을 쓸 수 있느냐가 아니라, 도구가 실제 작업 흐름 안에서, 즉 내 저장소와 테스트와 CI 시스템과 팀 관례 속에서 상당한 자율성을 갖고 쓸모 있는 일을 할 수 있느냐이다. 그리고 그 질문에 대한 Codex CLI의 답이 지금까지 본 것 중 가장 흥미롭다고 한다. 이 책은 왜 그런지 설명하고, 제대로 쓰는 법을 가르치려는 시도이다.

## 3. 이 책의 대상 독자와 다루지 않는 것

### 3.1 대상 독자

저자는 AI 지원 개발에 이미 익숙한 중급에서 시니어 수준의 소프트웨어 엔지니어를 염두에 두고 썼다. GitHub Copilot을 오래 써 왔거나 Claude Code 같은 에이전트형 도구를 이미 쓰고 있어서, 이런 도구가 어디에 강하고 어디에 약한지 아는 독자이다. 그리고 에이전트 방식에서 더 많은 것을 끌어내고 싶은 사람이 이 책의 독자이다.

필요한 조건은 다음과 같다.

- 터미널이 편해야 한다. Codex CLI는 명령줄 도구이고, 책도 그렇게 다룬다. GUI도, 플러그인도, 사이드바도 없이 모든 것이 셸에서 일어난다. 이 점이 부담이 아니라 매력으로 느껴지면 맞는 독자이다.
- 머신러닝이나 대규모 언어 모델(LLM)의 깊은 지식은 필요 없다. Codex CLI를 효과적으로 쓰는 데 필요한 정도의 모델 동작 원리는 책에서 설명하지만, ML 교재는 아니다.
- 대신 엔지니어링 경험을 전제한다. 코드베이스를 읽는 능력, 시스템 동작을 추론하는 능력, 불확실한 상황에서 디버깅하는 능력이다. 이런 기술은 에이전트를 다룰 때 그대로 통한다.

관리자가 AI 동향을 파악하려는 경우나 소프트웨어 개발의 미래가 궁금한 비기술 독자는 대상이 아니다. 그런 독자를 위한 좋은 책은 따로 있고, 이 책은 엔지니어에게 유용하도록 구체적이고 실무적으로 썼다.

### 3.2 저자의 관점

저자는 이 도구를 매일 쓰는 사람의 관점에서 쓴다고 밝힌다. 기업 납품 프로젝트, 리서치, 엔지니어링 팀을 넘나들며 일했고, 운영 중인 코드베이스, 새로 시작하는 프로젝트, CI 파이프라인, 로컬 개발 환경에서 Codex CLI를 돌려 보았다. 책의 의견은 벤치마크나 데모가 아니라 이런 실사용에 근거한다.

### 3.3 이 책에 없는 것

저자는 범위를 솔직히 밝히는 것이 독자에 대한 예의라고 말하며 다음 세 가지를 책에서 다루지 않는다고 못 박고, 마지막에 이 책이 무엇을 다루는지 밝힌다.

- 프롬프트 엔지니어링 일반 입문서가 아니다. 괜찮은 프롬프트는 쓸 수 있다고 가정하고, Codex CLI의 에이전트 방식에서 잘 먹히는 패턴과 관용구에 집중한다.
- LLM 교재가 아니다. 어텐션 메커니즘, 트랜스포머 구조, 최신 모델의 학습 방식은 설명하지 않는다. 모델 특성이 중요한 부분에서는 필요한 만큼만 설명한다. 신경망을 이해하는 것이 Codex CLI를 잘 쓰는 전제 조건은 아니라고 한다.
- 시장 조사서가 아니다. Cursor, Devin, Aider, Claude Code 등 여러 도구를 장마다 비교하지 않는다. 그런 비교는 책이 인쇄되기 전에 낡아 버린다. 대신 에이전트 방식이 다른 방식과 무엇이 다른지 설명하고, 독자가 이미 쓰는 도구에 대해 스스로 결론을 내리게 한다.
- 이 책이 다루는 것은 한 가지 도구를 깊이 파고든 내용이다. 몇 달간 매일 써 온 사람이 무엇이 되고 무엇이 안 되는지에 대해 분명한 의견을 갖고 쓴 책이다.

## 4. 책의 구성: 여섯 개 부

책은 모두 여섯 개 부로 나뉜다. 머리말에는 장별 제목이 나오지 않으므로, 아래는 머리말이 각 부에 대해 밝힌 주제를 정리한 것이다. 장별 세부 내용은 이 노트의 각 장 폴더에서 확인하면 된다.

| 부 | 제목 | 다루는 내용 |
| --- | --- | --- |
| 1부 | 기초 다지기(Grounding) | Codex CLI가 무엇이고 어디서 왔는지, 설치와 프롬프트 작성, 에이전트가 항상 읽는 지속적인 컨텍스트인 AGENTS.md에 무엇을 담을지 |
| 2부 | 안전장치(Guardrails) | 실행을 이끌고 제한하는 설정 요소인 승인 모드, 모델 선택, 컨텍스트 관리, MCP 연동, 훅 시스템 |
| 3부 | 규모 키우기(Scaling Up) | 기본 설정을 넘어서는 방법인 스킬, 서브에이전트, 여러 에이전트를 나누어 맡기고 조율하는 일(오케스트레이션), 비용 관리, CI/CD 연동 |
| 4부 | 실전 운영(Production) | 개인 사용에서 팀 사용으로 넘어갈 때 생기는 문제인 보안 강화, 기업용 설정, 디버깅, 테스트 전략 |
| 5부 | 실무자 가이드(Practitioner Guides) | 코드 리뷰, 코드베이스 마이그레이션, 코드형 인프라(IaC), 프론트엔드 엔지니어링, 파이썬 팀, 워크트리 기반 격리를 실제 작업 하나씩 처음부터 끝까지 따라가는 실습형 장 |
| 6부 | 더 큰 그림(The Bigger Picture) | 개별 작업 흐름에서 한 걸음 물러나 구조를 살피는 부분. 벤치마크, 경쟁 도구, 하니스 엔지니어링, 새로 떠오르는 에이전트 엔지니어링 팟(pod)의 역할 |

각 부에 대한 저자의 부연은 다음과 같다.

- 1부는 도구를 처음 접하는 독자라면 여기서 시작하라고 권한다. 이미 한동안 써 본 독자는 1부를 훑어보고, 필요할 때 특정 장으로 돌아오면 된다. 이 부에서 첫 장은 "Codex CLI란 무엇인가"로 시작해 에이전트형 도구의 계보와 설계 결정을 짚는다.
- 2부는 가장 자주 되돌아오게 될 참고서 같은 부분이다. 각 장이 단독으로 읽히도록 썼다.
- 3부는 기본값을 넘어 특정한 작업 흐름이나 제약이 있을 때 흥미로워지는 부분이다.
- 4부는 개인에서 팀 단위로 옮겨 갈 때 마주치는 질문에 답한다.
- 5부의 각 장은 실제 과제를 시작부터 끝까지 따라간다.
- 6부는 앞의 부들을 거쳐 온 독자가 더 넓은 그림을 생각할 준비가 되었다고 가정한다.

## 5. 버전 변화에 대한 안내

Codex CLI는 매주, 때로는 더 자주 새 버전이 나온다. 지금 설치한 도구는 저자가 특정 장을 쓸 때 쓰던 버전과 다르게 동작할 수 있다. 그렇다고 책을 불신할 이유는 아니다. 구조, 사고 모델, 핵심 작업 흐름은 안정적이기 때문이다. 다만 구체적인 플래그와 설정 옵션은 확정된 정답이 아니라 출발점으로 받아들여야 한다. `codex --help`의 출력이 책에 인쇄된 어떤 내용보다 항상 더 믿을 만하다.

최신 상태를 따라가는 실용적인 방법으로 저자는 변경 기록(changelog)을 읽으라고 권한다. Codex CLI의 changelog는 유난히 잘 쓰여 있고, 개발팀이 무엇이 왜 바뀌었는지 투명하게 밝힌다고 한다.

## 6. 읽는 법

독자의 상황에 따라 저자가 권하는 방법이 다르다.

| 상황 | 권장하는 읽는 법 |
| --- | --- |
| 처음 읽는 경우 | 처음부터 끝까지, 적어도 3부까지는 순서대로 읽는다. 책은 앞의 내용 위에 쌓이는 구조여서, 앞에서 소개한 개념을 뒤에서는 다시 설명하지 않고 쓴다. 1부와 2부에서 잡은 사고 모델이 있으면 3부와 4부가 훨씬 쉬워진다. |
| 참고서로 다시 찾는 경우 | 2부, 3부, 4부의 각 장은 독립적으로 읽히게 설계되었다. 색인이 상세하고 상호 참조도 넉넉히 달아 두었으므로 주변 장을 다시 읽지 않고도 필요한 내용을 얻을 수 있다. |
| 팀을 이끌고 읽는 경우 | 워크숍을 열거나 엔지니어들에게 에이전트 도구를 익히게 하려는 경우에는 5부를 쓰면 된다. 5부의 실무자 가이드는 각각 직접 따라 해 보는 실습 형태로 짜여 있다. |

머리말은 "자, 시작해 보자"라는 짧은 말로 끝난다.

---

## 7. 코드 예제와 그림에 대해

이 머리말과 이어지는 1부 표지 부분에는 코드 예제도, 별도로 정리할 그림이나 표도 없다. 중간에 낀 빈 쪽과 1부 표지가 전부이고 그림 캡션도 남아 있지 않다. 그래서 이 노트에 옮길 원서의 그림은 없다. 머리말 본문에서 코드와 관련해 직접 언급되는 것은 `codex --help` 명령 하나뿐이며, 이는 위 5절에 정리했다.

저자가 머리말에서 코드 예제의 사용 허락이나 저작권에 관해 따로 안내하는 내용은 이 범위의 원문에서 확인되지 않는다. 책 속 예제를 쓰려는 독자는 원서의 판권 안내를 직접 확인하기 바란다.
