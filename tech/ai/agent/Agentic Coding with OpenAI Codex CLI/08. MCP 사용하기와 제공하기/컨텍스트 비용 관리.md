# 컨텍스트 비용 관리

MCP 서버를 연결하면 그 서버의 도구 정의가 모델의 컨텍스트 윈도에 올라간다. 편리함의 대가가 이 비용이다. 이 문서는 비용이 얼마나 드는지, MCP 대신 CLI를 쓰는 편이 나은 경우는 언제인지, MCP를 쓰기로 했을 때 비용을 줄이는 네 가지 방법은 무엇인지 설명한다.

---

## 1. 서버를 연결하면 얼마나 드나

연결된 MCP 서버는 모두 도구 정의를 컨텍스트에 추가한다. 도구 20개에 설명이 자세한 서버라면 에이전트가 프롬프트를 하나 처리하기도 전에 수천 토큰이 나간다. 도구가 60개 넘게 들어 있는 GitHub MCP 서버를 통째로 켜면 수만 토큰까지 간다. 내 환경에서 서버별로 정확히 얼마인지는 7장에서 다룬 측정 방법, 즉 `codex debug prompt-input` 출력을 토크나이저에 넣어 세는 방법으로 확인할 수 있다.

## 2. 가장 싼 도구는 이미 컨텍스트에 있는 도구

Codex CLI는 셸 실행이 기본 내장이다. 그래서 PATH에 설치된 CLI는 도구 스키마를 하나도 추가하지 않고도 에이전트가 쓸 수 있다. 이슈 목록, PR 생성, 특정 커밋의 파일 읽기, 검색 결과 거르기 같은 일상적인 GitHub 작업은 MCP보다 `gh`가 나은 경우가 많다. 모델은 학습 데이터에서 gh 사용 예를 엄청나게 많이 봐서 호출법을 이미 안다. 게다가 셸 명령은 grep, jq, head로 파이프를 걸어 출력을 미리 걸러서 컨텍스트에 넣을 수 있다.

이 원칙은 앞에서 소개한 서버들에 모두 적용된다.

1. **GitHub**: 이슈, PR, 파일 읽기, 코드 검색은 gh로 된다. 승인 어노테이션으로 보호되는 더 풍부한 워크플로가 필요할 때 MCP 서버가 이긴다.
2. **문서 조회**: Context7을 쓰기 전에 curl, `gh api`, 프로젝트 자체 CLI로 먼저 해결할 수 있다. 모델이 학습 때 못 본 최신 버전별 문서가 필요하면 Context7이 이기고, 모델이 이미 잘 아는 인기 라이브러리에는 오히려 손해다.
3. **브라우저 자동화**: 방법이 세 가지다. 읽기 전용 가져오기와 가벼운 스크래핑은 curl이면 된다. 코딩 에이전트에서 프로그램으로 브라우저를 자동화할 때는 Microsoft가 MCP 서버보다 playwright-cli 워크플로를 명시적으로 권한다. CLI 호출이 토큰 효율이 더 좋기 때문이다. Playwright MCP 서버는 탐색형 자동화, 스스로 고치는(self-healing) 테스트, 오래 걸리는 자율 워크플로처럼 브라우저 상태를 계속 유지하는 것이 스키마 비용만큼 값어치를 하는 경우에 알맞다.
4. **데이터베이스**: psql, mysql, 프로젝트 ORM의 CLI로 된다. 관례가 아니라 런타임이 강제하는 구조화된 도구 어노테이션(readOnlyHint, 승인 제어)이 필요하면 MCP 서버가 이긴다.

원서는 이 판단 기준을 인용으로 뒷받침한다. Playwright MCP 저장소의 README는 최근의 코딩 에이전트가 스킬로 노출된 CLI 워크플로를 MCP보다 선호하는 추세이고 그 이유가 토큰 효율이라고 밝히며, 최신 코딩 에이전트 방식으로는 microsoft/playwright-cli를 안내한다. MCP 서버는 지속 상태, 풍부한 내부 관찰, 페이지 구조에 대한 반복 추론이 필요한 특수한 에이전트 루프용으로 자리매김한다.

**결정 규칙은 이렇다.** 구조화된 도구 스키마, 타입이 있는 입출력, 런타임이 강제하는 안전 어노테이션이 필요하면 MCP 서버를 쓴다. 모델이 학습에서 충분히 접한 익숙한 작업이고 스키마 비용을 내도 셸이 이미 주는 것 이상을 못 얻으면 CLI를 쓴다.

## 3. 비용을 줄이는 네 가지 방법

MCP 서버가 맞는 선택일 때 컨텍스트 비용을 다루는 방법은 네 가지다. 셋은 ~/.codex/config.toml에 있고, 하나는 서버 소스 코드에 있다.

1. **enabled_tools 허용 목록.** 각 `[mcp_servers.<name>]` 블록에 둔다. 서버가 노출하는 도구를 워크플로에 필요한 것으로 제한한다. 앞의 GitHub 예시가 서버 기본값인 수십 개 대신 네 개만 나열한 이유가 이것이다. 목록에 없는 도구는 컨텍스트에 올라가지 않는다.
2. **서버 단위 enabled 토글.** 같은 블록에 둔다. `enabled = false`로 두면 설정은 그대로 두되 시작할 때 서버를 불러오지 않는다. 가끔 쓰는 서버에 유용하고, 다시 쓰고 싶을 때는 값만 바꾸면 된다.
3. **프로필 범위 설정.** 프로필 파일 `~/.codex/<name>.config.toml` 안에 `[mcp_servers.<id>]`로 서버를 선언한다. `codex --profile <name>`으로 그 프로필을 켤 때만 로드되므로, 필요 없는 세션은 비용을 내지 않는다. 프로필 구조는 6장에서 자세히 다룬다.
4. **도구 설명을 짧게.** 서버 소스에서 각 도구 정의의 description 인자로 정한다. 직접 서버를 만들 때는 설명을 간결하게 쓴다. 긴 설명도 다른 글과 똑같이 토큰으로 세어지고, 매 턴마다 고정 앞부분(static prefix)에 실려 간다.

세 가지는 사용자가 설정으로 조절하고, 마지막 하나는 서버를 만드는 사람이 코드로 조절한다는 점이 다르다.
