# 운영 환경의 MCP

연결까지는 이 장 앞부분만으로 충분하다. 운영 환경에서 MCP를 돌리면 서로 겹치지 않고 쌓이는 네 가지 걱정이 더해진다. 쓰기 작업은 읽기보다 위험해서 명시적 통제가 필요하고, 서버는 죽거나 멈출 수 있어서 견디는 설정이 필요하며, 배포가 로컬 밖으로 나가면 다른 전송 방식이 필요하고, 문제가 생기면 이유를 설명해 줄 진단 수단이 필요하다. 이 문서는 이 순서대로 정리한다.

---

## 1. 쓰기 작업의 안전

읽기 전용 MCP 연동은 기본적으로 안전하다. 에이전트가 데이터를 조회하고 그 위에서 추론할 뿐이다. 쓰기(write-back) 연동은 다르다. 이슈 생성, 메시지 게시, 데이터베이스 갱신은 사용자가 승인하지 않은 행동을 에이전트가 하거나, 같은 행동을 두 번 하게 될 위험을 만든다. 쓰기가 가능한 MCP 연동에는 네 가지 안전 원칙을 지킨다.

1. **명시적 도구 어노테이션.** 쓰기 도구에는 `readOnlyHint: false`를 달고, 해당되면 `destructiveHint: true`도 단다. 그래야 승인 시스템이 알맞은 경로로 보낸다.
2. **승인을 거치는 호출.** 가장 신뢰하는 환경이 아니라면 쓰기 도구는 명시적 승인을 요구하게 한다. 쓰기 가능한 MCP 도구를 파일 시스템 쓰기와 똑같이 취급하도록 승인 정책을 설정한다.
3. **가능하면 멱등성(idempotency).** 쓰기 도구는 안전하게 재시도할 수 있게 설계한다. 에이전트 세션이 끊겼다가 이어져 같은 쓰기 도구가 다시 호출되어도 중복 레코드가 생기면 안 된다.
4. **감사 로그.** 모든 쓰기 도구 호출은 인자 전체와 결과를 감사 기록에 남긴다. 9장에서 다루는 PostToolUse 훅으로 MCP 쓰기 작업을 파일 작업과 함께 기록한다.

실무에서 자주 보이는 패턴 세 가지는 다음과 같다.

| 영역 | 에이전트가 하는 일 | 지킬 점 |
|---|---|---|
| 티켓 관리(Jira, Linear) | 코드 분석에서 이슈 생성, CI 결과로 상태 갱신, PR과 이슈 연결 | 쓰기 범위를 좁게. 생성과 댓글은 허용하되 담당자 변경이나 닫기는 막는다 |
| 커뮤니케이션(Slack, Teams) | 요약, 알림, 상태 공지 게시 | 조직 전체 권한 대신 특정 채널로 한정된 토큰을 쓴다 |
| 데이터베이스 | 마이그레이션 스크립트 작성, 테스트 픽스처 삽입, 설정 테이블 갱신 | 필요한 최소 권한만 가진 전용 서비스 계정을 쓰고, 개발자 개인 DB 자격 증명은 쓰지 않는다 |

## 2. 장애에 견디기

쓰기 안전이 에이전트가 해도 되는 일을 다룬다면, 복원력(resilience)은 의존하는 서버가 이상하게 동작할 때 무슨 일이 일어나는지를 다룬다. MCP 서버는 외부 프로세스라서 실패하거나, 멈추거나, 예상 밖의 결과를 돌려줄 수 있다. 설정은 서버가 늘 잘 동작한다고 가정하면 안 된다.

- **기능을 줄여서라도 계속하기(graceful degradation).** MCP 서버를 쓸 수 없으면 에이전트는 작업 전체를 실패시키지 않고 내장 기능으로 계속해야 한다. Codex CLI는 대체로 MCP 서버 시작 실패에 너그럽지만, 운영에서 의존하기 전에 쓰는 버전에서 동작을 확인한다. 프롬프트도 MCP 도구가 항상 있다고 가정하지 않게 쓴다.
- **타임아웃 설정.** tool_timeout_sec는 도구 호출 하나가 얼마나 오래 돌 수 있는지 제한한다. 큰 저장소 검색, 브라우저 이동, 큰 테이블 쿼리처럼 정당하게 느린 서버에는 값을 늘린다. 나머지는 짧게 두어, 멈춘 서버가 에이전트를 무한정 막지 못하게 한다. 짝이 되는 키 startup_timeout_sec는 처음 핸드셰이크를 다스리며 아래 디버깅 항목에서 다룬다.
- **테스트용 더미 도구.** MCP 서버에 의존하는 워크플로를 개발할 때는 정해진 응답만 돌려주는 가벼운 더미 서버를 만든다. 외부 서비스 없이도 프롬프트 설계와 승인 흐름을 시험할 수 있다.

## 3. 원격과 컨테이너 서버

서버가 로컬 밖에 있으면 실패 모양도 달라진다. MCP는 서버를 로컬 자식 프로세스가 아니라 원격 인프라에서 돌리는 HTTP 전송을 지원한다.

```toml
[mcp_servers.remote_tools]
enabled = true
url = "https://mcp.internal.company.com/tools"
bearer_token_env_var = "MCP_REMOTE_TOKEN"
```

원격 전송은 플랫폼 팀이 관리하는 공용 인프라로 MCP 서버를 돌리는 기업 배포에 유용하다. 개발자 노트북마다 서버를 따로 두는 대신, GitHub 서버를 자격 증명 한 벌로 정식 인스턴스 하나만 둘 수 있다.

더 강한 격리가 필요하면 Docker MCP Toolkit을 쓴다. MCP 서버마다 자기 컨테이너 안에서 돌리고, 필요한 네트워크 접근과 파일 시스템 마운트만 준다. 서드파티 MCP 서버에 대해 기업 배포에서 쓸 수 있는 가장 강한 격리 모델이며, 컨테이너별 자격 증명 경계 덕분에 비밀 관리도 단순해진다.

## 4. 문제가 생겼을 때 디버깅

서버가 로컬이든 원격이든 컨테이너든 진단 동작 네 가지로 대부분의 실패를 잡는다.

1. **자세한 로그 켜기.** `RUST_LOG=debug`를 설정하면(codex 크레이트만 보려면 `RUST_LOG=codex=debug`) MCP 프로토콜 교환 전체를 볼 수 있다.
2. **서버 상태 확인.** Codex CLI REPL에서 `/mcp` 명령으로 연결된 서버와 상태를 확인한다.
3. **단독 테스트.** Codex CLI 밖에서 서버를 stdio로 직접 호출하거나(더 풍부한 디버깅은 MCP Inspector로) 제대로 응답하는지 확인한다.
4. **도구 정의 점검.** 서버가 돌려주는 도구 스키마가 에이전트가 기대하는 것과 맞는지 살펴본다.

가장 흔한 실패 네 가지는 위 동작에 대응된다.

| 증상 | 점검과 해결 |
|---|---|
| 서버가 시작되지 않음 | config의 command와 args를 확인하고 실행 파일이 PATH에 있는지 본다. TUI에 `MCP client for '<name>' timed out after 30 seconds`가 뜨면 핸드셰이크가 기본 startup_timeout_sec를 넘긴 것이다. `npx -y`의 첫 실행 때 패키지를 내려받고 연결하느라 첫 tools/list 요청에 바로 답하지 못해 흔히 생긴다. 해결은 두 가지다. 해당 `[mcp_servers.<name>]` 블록의 startup_timeout_sec를 늘리거나(보통 60~120초면 패키지 내려받기를 충분히 덮는다), 서버를 전역 설치해 다음부터 바로 뜨게 한다. 예: `npm i -g @modelcontextprotocol/server-github` |
| 도구가 보이지 않음 | enabled_tools가 서버가 노출하는 도구 이름과 정확히 같은지 확인한다 |
| 자격 증명 오류 | MCP 서버 프로세스가 기대하는 토큰 변수를 실제로 보는지 확인한다. 토큰이 `gh api`에선 되는데 MCP에서 실패하면 Codex CLI를 재시작하고, 설정이 `${GITHUB_TOKEN}` 같은 자리 표시자 문자열을 그대로 넘기지 않는지 본다 |
| 컨텍스트 사용량이 높음 | 도구가 너무 많이 노출된 것이다. enabled_tools로 필요한 것만 허용한다 |

## 5. 다음 장으로 이어지는 이야기

MCP는 에이전트가 외부 시스템에 손을 뻗게 해 준다. 이 장은 컨텍스트 비용과 쓰기 쪽 위험을 놓치지 않고 그 능력을 더하는 방법을 보였다. 9장은 반대 방향이다. 에이전트에게 능력을 더 주는 대신, 에이전트가 이미 가진 능력을 가로챈다. 훅은 에이전트 수명 주기의 정해진 지점(도구 호출 전, 호출 후, 세션 시작, 컴팩션 발생 등)에서 스크립트를 실행해, 에이전트가 하는 일을 검증하고 기록하고 변형하고 거부하게 해 준다. 이 장의 수단들과 다음 장의 수명 주기 훅을 합하면 운영 수준의 Codex CLI 배포에 필요한 부품 대부분이 갖춰진다.
