# 스킬 찾기와 설치와 관리

스킬을 쓰는 입장에서 알아야 할 실무 내용을 모았다. 공식 카탈로그와 커뮤니티 레지스트리에서 스킬을 가져오는 방법, Codex CLI가 스킬을 어느 디렉터리에서 어떤 순서로 찾는지, 스킬을 지우지 않고 끄는 방법, 자동 호출을 막는 정책을 다룬다. 끝에서는 스킬을 AGENTS.md, 훅, MCP 같은 다른 설정 수단과 견주어 언제 무엇을 골라야 하는지 정리한다.

---

## 1. 카탈로그와 설치 방법

기준이 되는 카탈로그는 OpenAI의 공식 저장소 github.com/openai/skills다. 눈에 보이는 층이 두 개 있다.

- 시스템 스킬: Codex CLI에 처음부터 들어 있다. `$skill-creator`, `$skill-installer`, 그리고 codex-auto-review 모델이 받쳐 주는 내장 Code Review 스킬이 여기에 속한다.
- 선별(curated) 카탈로그: OpenAI의 내부 검토를 통과한 설치형 스킬이다. `gh-address-comments`, `gh-fix-ci`, 여러 Notion 연동 스킬, 그리고 `$define-goal`이 예로 나온다. `$define-goal`은 코드를 쓰기 전에 막연한 의도를 구체적이고 측정 가능한 목표로 다듬어 준다.

시스템 스킬은 `$` 접두사로 바로 쓸 수 있고, 선별 스킬은 설치를 한 번 해야 한다. 공식 카탈로그에서 가져오는 표준 방법은 내장 `$skill-installer`다.

```
$skill-installer gh-fix-ci
```

명시적인 URL이나 로컬 경로를 줄 수도 있다. 개발 중인 스킬을 여러 머신에 퍼뜨릴 때 쓸 만하다.

```
$skill-installer install https://github.com/openai/skills/tree/main/skills/.curated/gh-fix-ci
```

공식 카탈로그 밖의 커뮤니티 스킬은 agentskills.io, skills.sh, Tessl 레지스트리 같은 서드파티 레지스트리에 있다. skills.sh의 크로스 플랫폼 CLI인 `npx skills`는 여러 에이전트 제품에 커뮤니티 스킬을 한 줄로 설치해 준다.

```
npx skills add vercel-labs/agent-skills --skill frontend-design -a codex
```

## 2. 스코프와 디렉터리 탐색 순서

Codex CLI는 아래 디렉터리를 우선순위가 높은 것부터 낮은 것 순으로 훑는다.

```
$CWD/.agents/skills        # 프로젝트 수준
$CWD/../.agents/skills     # 상위 디렉터리
$REPO_ROOT/.agents/skills  # 저장소 루트
$HOME/.agents/skills       # 사용자 수준
/etc/codex/skills          # 시스템/관리자
(내장 시스템 스킬)          # 가장 낮음
```

이름이 같으면 프로젝트 수준 스킬이 사용자 수준 스킬을 가리고(shadow), 사용자 수준 스킬이 시스템 수준 스킬을 가린다. 스코프별로 누가 관리하는지는 다음과 같다.

| 스코프 | 위치 | 관리 주체 |
| --- | --- | --- |
| 프로젝트 | `$REPO_ROOT/.agents/skills/` | 저장소(소스 관리에 커밋) |
| 사용자 | `$HOME/.agents/skills/` | 개발자 개인 |
| 관리자 | `/etc/codex/skills/` | 조직의 플랫폼 팀 |
| 시스템 | 내장 | OpenAI |

팀에게 가장 쓸모 있는 것은 프로젝트 행이다. 팀 고유의 스킬을 `$REPO_ROOT/.agents/skills/`에 커밋해 두면, 저장소를 클론한 개발자 모두가 따로 설치하지 않아도 같은 에이전트 동작을 얻는다.

## 3. 지우지 않고 끄기

스킬 디렉터리를 지우지 않고 로딩만 막고 싶으면 `~/.codex/config.toml`에 항목을 추가한다.

```toml
[[skills.config]]
name = "gh-address-comments"
enabled = false
```

config.toml을 고친 뒤에는 Codex CLI를 다시 시작해야 한다. 스킬이 예상치 못한 자동 활성화를 일으킬 때 쓰기 좋다. 일단 끄고, description을 살펴 손본 다음, 다시 켜면 된다.

## 4. 호출 정책

기본적으로 Codex CLI는 프롬프트가 description과 맞으면 스킬을 암묵적으로 활성화한다. 이를 바꾸려면 스킬 디렉터리 안에 `agents/openai.yaml` 파일을 두고 다음을 적는다.

```yaml
policy:
  allow_implicit_invocation: false
```

암묵적 호출을 끄면 스킬은 사용자가 이름으로 부를 때만 켜진다. 민감하거나 비용이 큰 스킬에서, 패턴 매칭에 맡기지 않고 명시적인 의도를 요구하고 싶을 때 쓴다.

## 5. 어떤 수단을 고를까

스킬은 Codex CLI가 제공하는 여섯 가지 설정 수단 중 하나이며, 각각 다른 질문에 답한다.

1. AGENTS.md: 정적인 프로젝트 컨텍스트. 관례, 명령어, 파일 경계(4장).
2. 훅: 생애 주기 가드레일. 에이전트가 실행되는지 자체를 제어한다(9장).
3. 스킬: 절차 지식. X를 어떻게 하는가.
4. MCP 서버: 실시간 연동. 에이전트에게 Y에 대한 실시간 접근을 준다(8장).
5. 서브에이전트: 실행 위임. 격리된 컨텍스트 윈도에서 병렬로 일한다(11장).
6. 플러그인: 나머지를 배포 가능한 단위로 묶는다(이 장 뒷부분).

이 층들은 서로 겹쳐 쌓인다. 성숙한 설정은 보통 프로젝트 컨텍스트용 AGENTS.md, 팀 워크플로용 스킬 두세 개, 외부 연동용 MCP 서버 한두 개, 여러 에이전트를 나누어 맡기고 조율하는 일(오케스트레이션)을 위한 서브에이전트, 배포용 플러그인으로 이루어진다. 문제를 풀 수 있는 가장 낮은 층에서 시작하고, 아래 층이 모자랄 때만 위로 올라간다.

이 중 가장 헷갈리는 선택은 스킬, MCP, 훅이다. 같은 일을 하는 대안처럼 보이기 때문이다. 아래 표로 비교한다.

| 비교 항목 | 스킬 | MCP 서버 | 훅 |
| --- | --- | --- | --- |
| 정체 | 에이전트 컨텍스트에 올라가는 텍스트 | 타입이 있는 도구 엔드포인트를 노출하는 실행 중 서버 | 생애 주기 이벤트에서 부르는 셸 콜백 |
| 로딩 방식 | 점진적. 시작 시 이름과 설명, 활성화 시 본문 | 즉시 로딩. 시작 시 모든 도구 스키마 | 이벤트 기반. SessionStart, Stop, 프롬프트 제출 때 실행 |
| 실행 방식 | 에이전트가 지시문을 읽고 자기 도구로 행동 | 에이전트가 실행 중인 프로세스의 구조화된 엔드포인트를 호출 | 내 스크립트가 돌고, 출력과 종료 코드가 에이전트에 돌아감 |
| 잘 맞는 일 | 절차 지식, 팀 관례, 워크플로 패턴 | 실시간 데이터, 인증이 필요한 API, 상태가 있는 작업 | 컨텍스트 주입, 프롬프트 차단, 세션 경계의 부수 효과 |
| 배포 | 저장소에 커밋하거나 레지스트리에서 설치 | 데몬으로 실행. 설정에 호스트와 포트를 적음 | `.codex/`에 커밋한 스크립트 |
| 플랫폼 간 호환 | SKILL.md 하나가 여러 에이전트 제품에서 동작 | 플랫폼이 MCP를 지원하면 가능, 아니면 플랫폼 전용 | Codex 전용 |
| 한마디로 | "X를 하는 법을 가르친다" | "Y에 실시간으로 접근하게 한다" | "에이전트가 실행되는지, 언제 되는지를 제어한다" |

AGENTS.md가 너무 불어서 다루기 힘들다면 스킬이 리팩터링 목적지가 되는 경우가 많다. 자세한 비대화 분석은 4장에 있다. 두 형식이 모두 AAIF 관리 아래 있어서 이행 경로도 표준에 근거한다. 프로젝트 컨텍스트는 AGENTS.md에 남기고, 재사용 가능한 절차 지식은 이식 가능한 스킬로 옮긴다.
