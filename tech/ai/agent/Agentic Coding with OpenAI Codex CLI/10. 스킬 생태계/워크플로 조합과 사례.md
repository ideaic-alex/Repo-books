# 워크플로 조합과 사례

스킬과 플러그인은 반복 가능한 에이전트 워크플로로 엮을 때 가장 큰 힘을 낸다. 이 문서는 조합 패턴 세 가지와 설계 원칙, 플러그인에 번들되는 훅, 확장 우선 구조, 그리고 네 가지 실제 사례(Nx, codex-pr-body, Elves, Google Agent Skills)를 다룬다.

---

## 1. 조합 패턴

조합 워크플로란 스킬 활성화, 플러그인 호출, MCP 도구 호출을 이어 붙여 팀의 표준 운영 절차를 담은 것이다.

패턴 1, 리뷰 후 수정 루프: 코드 리뷰 스킬이 diff에서 문제를 찾는다. 수정 스킬(또는 에이전트 자체의 코딩 능력)이 각 지적을 고친다. 두 번째 리뷰 패스가 수정이 맞는지 확인한다. 이 루프는 순서를 조율하는 지시문을 가진 하나의 복합 스킬로 짤 수도 있고, 상위 AGENTS.md 지시가 이어 주는 세 개의 별도 스킬로 짤 수도 있다.

패턴 2, 스캐폴드-테스트-배포 파이프라인: 스캐폴딩 스킬이 상용구 코드(새 서비스, 새 마이그레이션, 새 API 엔드포인트)를 만든다. 테스트 스킬이 프로젝트 테스트 스위트를 돌려 실패를 보고한다. 배포 스킬이 테스트를 통과한 뒤 staging에 푸시한다. 각 스킬은 따로도 쓸모 있고, 합치면 기능을 만들어 배포하기까지의 워크플로 전체를 담는다.

패턴 3, 워크플로 번들로서의 플러그인: 지시문만이 아니라 인증된 API 접근과 외부 도구까지 필요한 워크플로라면 플러그인이 전체 스택을 묶는다. 예를 들어 Terraform 드리프트(실제 인프라와 코드의 어긋남) 복구 워크플로를 조율하는 스킬, 클라우드 제공자 상태를 읽는 MCP 서버, 결과를 Slack에 올리는 앱 커넥터를 한 플러그인에 넣을 수 있다. 개발자는 플러그인 하나만 설치하고 완전한 기능을 얻는다.

일반 원칙은 이렇다. 지시문만으로 되는 워크플로는 독립 스킬로 시작한다. 워크플로에 MCP 서버, 앱 커넥터, 팀 전체 거버넌스 통제가 필요해지면 플러그인으로 올린다. 커밋된 SKILL.md로 충분한데 전부 플러그인에 넣고 싶은 충동은 누른다.

조합 워크플로를 설계할 때는 스킬 하나가 책임 하나에 집중하게 한다. 코드를 리뷰하는 스킬이 배포까지 해서는 안 된다. 조합은 개별 스킬 안이 아니라 조율 계층, 즉 AGENTS.md 지시문, 상위 스킬, 플러그인 매니페스트에서 일어난다.

## 2. 플러그인에 번들되는 훅

플러그인은 스킬, MCP 서버와 함께 자체 생애 주기 훅을 실어 보낼 수 있다. 9장에서 다룬 핵심 훅 체계를 확장하는 기능이다. 번들된 훅은 사용자가 정의한 훅과 같은 생애 주기 시점(PreToolUse, PostToolUse 등)에 발동하지만 범위는 그 플러그인의 맥락으로 한정된다. 보안 플러그인이 위험한 셸 명령을 막는 PreToolUse 훅을 번들하면, 사용자는 훅 스크립트를 직접 쓰지 않아도 된다. 훅의 활성화 상태는 플러그인별로 추적되므로, 플러그인을 켜거나 끄면 번들된 훅도 같이 켜지고 꺼진다.

## 3. 확장 우선 아키텍처

Codex CLI는 확장 우선(extension-first) 구조를 따른다. 핵심 기능이 런타임에 고정된 부품이 아니라 갈아 끼울 수 있는 확장이라는 뜻이다. 제안된 변경의 안전성과 정확성을 점검하는 모델인 자동 리뷰어(automated reviewer)도 그 자체로 교체, 맞춤화, 보강할 수 있는 확장이다. 규제 환경에는 더 엄격한 정책 엔진을, 내부 도구 프로젝트에는 더 가벼운 검사를 붙일 수 있다.

두 가지가 더 있다. 플러그인 ID 정규화(canonicalisation)는 공유 워크스페이스를 정돈해서, `my-org/linter`와 `My-Org/Linter`가 두 개가 아니라 하나의 플러그인으로 등록되게 한다. 플러그인 발견 가능성(discoverability) 분리는 관리자가 마켓플레이스 브라우저에 어떤 플러그인이 보이는지를, 어떤 플러그인이 설치 가능한지와 별개로 통제하게 해 준다. 스킬과 플러그인 작성자가 얻을 실용적 교훈은, 거버넌스, 리뷰, 정책 집행 스킬이 핵심 기능과 같은 확장 지점에 꽂힌다는 점이다.

## 4. 사례 1: Nx 모노레포 에이전트 스킬

Nx 빌드 시스템의 공식 Codex CLI 연동은 스킬과 MCP를 나눠 쓰는 방식을 잘 보여 준다. `@nx/codex` 패키지는 핵심 스킬 여섯 개를 제공한다. `nx-project-details`, `nx-affected`, `nx-generators`, `nx-dependency-graph`, `nx-migrate`, `nx-ci-pipeline`이다. 각각 Nx CLI 명령을 부르는 보조 스크립트를 붙인 SKILL.md로 되어 있다. 스킬 옆에는 MCP 서버(`nx-mcp`)가 있어 프로젝트 그래프, 태스크 파이프라인, 생성기 스키마 같은 실시간 워크스페이스 메타데이터를 노출한다.

스킬은 절차 지식을 담는다("새 라이브러리를 추가하려면 이런 관례로 `nx g @nx/js:library`를 실행한다"). MCP 서버는 실시간 데이터를 준다("이 워크스페이스에는 프로젝트가 47개 있고 의존 관계는 이렇다"). 둘을 같이 쓰는 에이전트는 모노레포 구조를 MCP로 추론하고 스킬로 올바르게 행동하며, 개발자가 프롬프트마다 Nx 관례를 설명할 필요가 없다. 큰 Nx 모노레포에서는 AGENTS.md가 담던 몇 페이지 분량의 지시를, 설치된 스킬을 가리키는 몇 줄로 줄일 수 있다.

## 5. 사례 2: codex-pr-body

codex-pr-body는 Codex CLI 저장소 자체에 커밋된, OpenAI 팀이 직접 쓴 첫 공식 프로젝트 수준 스킬이다. `$skill-installer`나 `$skill-creator` 같은 내장 시스템 스킬과 달리 `.agents/skills/codex-pr-body/`에 있고 이 장이 권하는 관례를 그대로 따른다. 목적은 프로젝트 고유의 워크플로 패턴을 반영한 풀 리퀘스트 설명을 만드는 것이다. 참고할 만한 설계 선택이 세 가지다.

- 코드베이스와 함께 배포: 외부에 따로 공개하지 않고 저장소에 커밋했다. 저장소를 클론한 기여자 모두가 설치 단계 없이, 버전 드리프트 없이 일관된 PR 설명 동작을 얻는다. 구조화된 지시가 필요할 만큼은 복잡하지만 외부 배포 인프라까지는 필요 없는 3단계 팀 관례 패턴이 맞다는 것을 보여 준다.
- 읽기 전용 Sapling CLI 접근: 스킬은 `sl`을 읽기 전용 작업(`sl log`, `sl status`, `sl diff`)으로 제한하고 쓰기를 명시적으로 금지한다. 정확한 설명을 만들려면 저장소 이력이 필요하지만 부수 효과로 작업 트리를 바꾸면 안 되기 때문이다. 의도치 않은 변경 위험 없이 버전 관리 상태를 들여다보는 모든 스킬에 일반화되는 패턴이다.
- 스택형 PR을 아는 설명: Codex CLI 팀은 Sapling과 Graphite로 스택형 풀 리퀘스트를 쓰며, 기능 하나가 서로 의존하는 여러 PR에 걸치기도 한다. 이 스킬은 main과 무작정 diff하지 않고 현재 스택 계층에 해당하는 커밋 범위를 살펴, 각 PR의 증분 변경을 반영한 설명을 만든다. 스택 diff 워크플로를 쓰는 팀은 같은 문제를 겪는데, codex-pr-body는 스택 인식을 이식 가능한 스킬 형식에 담는 방법을 보여 준다.

의미를 요약하면, 에이전트를 만드는 팀이 이 장이 권하는 패턴을 스스로 채택했다는 것이다. 팀 고유 스킬에 투자할지 고민할 때 codex-pr-body는 참조 구현이자 이 패턴이 확장된다는 증거다.

## 6. 사례 3: aigorahub/elves

지금까지 본 스킬은 단일 작업(마이그레이션 절차, PR 설명 형식, 리뷰 체크리스트)의 지식을 담았다. Elves(aigorahub/elves)는 완전히 다른 범주다. 자체 메모리 관리, 거버넌스 모델, 전략적 망각까지 갖추고 여러 배치(batch)에 걸친 자율 개발 워크플로 전체를 조율하는 스킬이다.

Elves는 두 번 호출하는 핸드오프 패턴으로 동작한다. 먼저 Stage 호출이 작업 계획을 준비한다(요구 사항 파싱, 배치 정의 생성, 거버넌스 구조 생성). 이어 Launch 호출이 자율 실행을 시작한다. 이렇게 나눈 데는 이유가 있다. 에이전트가 몇 시간짜리 자율 작업에 들어가기 전에 사람이 검토할 체크포인트를 주는 것이다. 스킬 설계자에게 의미 있는 구조적 혁신은 네 가지다.

- 계층형 메모리: 배치 경계를 넘어 네 개의 지식 층을 유지한다. Plan(전체 작업 명세), Survival Guide(이전 배치에서 얻어 반드시 남겨야 하는 교훈), Learnings(버려도 되는 가벼운 관찰), Execution Log(수행한 행동의 진행 기록)이다. 층마다 보존 규칙이 다르다. Plan은 불변이고, Survival Guide는 추가만 가능하며, Learnings는 배치 사이에 검토해 솎아 내고, Execution Log는 배치가 끝날 때마다 보관한다.
- 헌법적 판단: 매 배치가 끝나면 사람이 쓴 '절대 안 됨(deal-breaker)' 규칙, 즉 어기면 워크플로를 중단하고 사람에게 올리는 강한 제약에 비추어 자기 출력을 평가한다. 훅 수준이 아니라 스킬 수준의 거버넌스다. 규칙이 외부 집행 인프라가 아니라 스킬의 지식에 속한다.
- 전략적 망각: 컨텍스트 윈도가 가득 차서 압축이 품질을 떨어뜨릴 때까지 기다리지 않고, 끝난 배치 이력을 선제적으로 보관하고 오래 남을 지식만 `.ai-docs/` 디렉터리로 올린다. 작업 집합은 아무리 긴 워크플로에서도 가볍게 유지된다. 7장에서 다룬 모델 수준 압축 전략의 애플리케이션 수준 짝이다.
- 프로덕션 자율성 비율: 여러 배치에 걸친 개발 작업에서 에이전트 시간 대 사람 시간의 비율을 높게 잡도록 설계했다. 사람은 준비와 검토에 몇 분을 쓰고 에이전트는 몇 시간 자율로 일한다. 스킬의 메모리와 거버넌스 계층이 원래라면 사람 개입이 필요했을 실패 유형을 처리하기에 가능한 비율이다.

Elves는 스킬이 지시문 모음 이상일 수 있음을 보여 준다. 메모리 관리, 거버넌스, 자율성, 자기 정리를 이식 가능한 SKILL.md 하나에 담은 완전한 운영 프레임워크일 수 있다. 야심찬 자율 워크플로를 만드는 팀에게 Elves는 5단계 프로덕션 스킬이 어떤 모습인지 보여 주는 현재의 참조 구현이다.

## 7. 사례 4: Google Agent Skills

개별 저작자에서 플랫폼이 유지하는 패키지로의 이동을 가장 잘 보여 주는 것이 Google Agent Skills(google/skills)다. 테스트, 코드 리뷰, API 설계, 성능, 보안 등을 아우르는 공식 카탈로그이며, 표준 배포 방식으로 설치한다.

```
npx skills add google/skills
```

의미는 내용(이미 잘 알려진 엔지니어링 관행)이 아니라 배포 모델에 있다. 대형 플랫폼 업체가 스킬 패키지를 유지하고 버전 관리하며, 그 패키지가 Agent Skills 표준을 지원하는 어떤 에이전트에든 설치된다. 개인 커뮤니티 저작자가 쓰는 SKILL.md 형식이 공식 플랫폼 배포에도 그대로 통한다는 점에서 생태계의 이식성 약속이 입증된다.

기업 팀에게 Google Agent Skills는 기준선 역할을 한다. 공식 패키지를 깔아 엔지니어링 모범 사례를 폭넓게 덮고, 그 위에 조직 고유의 관례를 담은 팀 스킬을 얹는다. 이 조합이 플랫폼이 유지하며 정기적으로 갱신되는 폭과, 팀이 직접 쓴 맥락 특화의 깊이를 함께 준다.
