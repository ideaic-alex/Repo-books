# 빌드 시스템과 실증 연구 그리고 패턴 표

이 문서는 장의 마지막 묶음이다. Bazel과 Dagger 같은 빌드 시스템과 Codex CLI를 잇는 방법, 에이전트가 만든 PR 수만 건을 분석한 연구가 파이프라인 설계에 주는 교훈, Microsoft의 에이전트 시대 DevOps 플레이북, 그리고 장 전체 패턴을 한 표로 모은 카탈로그를 다룬다.

---

## 1. 빌드 시스템 통합

### Bazel 모노레포

Bazel을 쓰는 모노레포 팀에서는 Codex CLI를 원격 실행, 빌드 그래프 분석, 테스트 타깃 선택과 엮을 수 있다. 실용적인 패턴은 CI 단계에서 `bazel query`로 영향받는 타깃을 찾고, 구현이나 수정 작업을 그 타깃으로만 한정해서 Codex에 맡기는 것이다. 에이전트가 무관한 패키지를 건드리지 못하고, 맥락도 좁게 유지된다.

### Dagger Container-Use MCP

Dagger의 Container-Use MCP 서버는 Codex CLI가 셸 스크립트 없이 컨테이너 파이프라인 안에서 빌드, 테스트, 배포를 하게 해 준다. 에이전트가 Dagger 함수를 MCP 도구로 호출해 빌드 단계를 프로그램으로 조립한다. 재현 가능한 컨테이너 빌드가 필요한 CI에 특히 유용하다. 에이전트가 Dagger 파이프라인 정의를 고치고, 실행하고, 결과를 보고, 반복하는 일을 모두 샌드박스된 MCP 맥락 안에서 할 수 있다.

## 2. 에이전트 PR 33,000건이 알려 주는 것

MSR 2026에서 발표된 연구 다섯 편이 AIDev 데이터셋(61,000개 저장소에 걸친 933,000건 이상의 에이전트 PR)을 분석했고, 결과는 CI/CD 파이프라인 설계에 바로 쓸 만하다.

### 실패율 28.5퍼센트는 코드 품질보다 워크플로 문제가 크다

Ehsani 등은 에이전트 PR의 28.52퍼센트가 머지되지 못한다는 것을 발견했다. 분석 대상은 33,596건이었고, 실패 분류는 대부분의 팀이 예상하는 것과 다르다.

| 실패 범주 | 비율 | 주된 원인 |
| --- | --- | --- |
| 리뷰어 이탈 | 38퍼센트 | 사람의 의미 있는 상호작용이 없음 |
| PR 수준 문제 | 31퍼센트 | 중복(23퍼센트), 원치 않는 기능(4퍼센트) |
| 코드 수준 실패 | 22퍼센트 | CI/테스트 실패(17퍼센트), 잘못된 구현(3퍼센트) |
| 에이전트 불일치 | 2퍼센트 | 에이전트가 리뷰어 피드백을 무시 |

가장 큰 실패 원인은 사회적·워크플로 어긋남이다. 아무도 요청하지 않은 PR을 올리거나, 기존 작업과 겹치거나, 리뷰어 관심을 못 받는 경우다. 그래서 모델 선택보다 파이프라인 설계가 더 중요하다. 중복 자동 감지, 오래된 PR 확인, 리뷰어 지정이 생성 품질을 높이는 것보다 효과가 큰 개입이다.

### 심볼 생존 기간: 에이전트 코드 3일 대 사람 코드 34일

Pham과 Ghaleb는 에이전트가 도입한 심볼(함수·변수 등)이 수정되거나 삭제되기까지 중앙값 3일 생존하고, 사람이 쓴 심볼은 34일 생존한다고 밝혔다. CI/CD 쪽 시사점은 에이전트가 만든 코드는 잠정적인 것으로 봐야 한다는 점이다. 에이전트가 작성한 변경이 일주일 안에 수정 없이 살아남았다면 더 깊은 리뷰 후보로 표시하는 식이 가능하다.

### CI 실패 한 번이 머지 확률을 약 15퍼센트 깎는다

반려된 PR은 성공한 PR보다 코드 줄이 17퍼센트 더 많고 파일을 10퍼센트 더 많이 건드린다. 설계 쪽 시사점은 작고 원자적인 변경 묶음을 강제하고, 에이전트 PR을 연 뒤가 아니라 열기 전에 전체 테스트를 돌리는 것이다.

### 직접 대응하는 파이프라인 추가 세 가지

1. 중복 감지: PR을 열기 전에 같은 이슈를 다루는 열린 PR이 이미 있는지 본다. `gh pr list --search` 단계 하나로 23퍼센트의 중복률을 막을 수 있다.
2. 방치 모니터링: 에이전트가 만든 PR에 48시간 동안 리뷰어 활동이 없으면 표시하고 팀 리드에게 올리는 예약 워크플로다. 38퍼센트 리뷰어 이탈률을 겨냥한다.
3. 원자적 변경 강제: 줄 수나 파일 수 임계값(설정 가능)을 넘는 PR을 실패시키는 CI 단계를 둔다. 에이전트가 큰 변경을 쪼개게 만든다.

## 3. Microsoft의 에이전트 시대 DevOps 플레이북

David Sanchez의 「DevOps Playbook for the Agentic Era」는 이 장의 파이프라인 패턴이 기업 환경에서도 타당하다는 근거를 준다. 핵심 주장은 에이전트가 망가진 엔지니어링 관행을 마법처럼 고치지 않고 오히려 키운다는 것이다. 그래서 에이전트를 도입하기 전에 여섯 영역을 점검해야 한다. CI/CD 파이프라인, 자동화된 테스트, 코드형 인프라(IaC), 보안 스캔, 브랜치 보호, 관측성이다.

### 네 가지 협업 영역

| 영역 | 사람의 역할 | 에이전트의 역할 | Codex CLI 대응 |
| --- | --- | --- | --- |
| IDE/에디터 | 의도를 정한다 | 코드 완성을 만든다 | 대화형 CLI 세션 |
| Pull Request | 변경을 리뷰한다 | PR을 열고 피드백에 반복 대응한다 | codex-action GitHub Action |
| CI/CD 파이프라인 | 규칙을 정한다 | 빌드를 트리거하고 실패를 수정한다 | 워크플로 안의 `codex exec` |
| 운영 | 모니터링하고 승인한다 | 이상을 감지하고 사전 승인된 동작을 실행한다 | Symphony(등장 중) |

### 3계층 파이프라인 검증

Sanchez는 파이프라인이 관문지기에서 검증자로 진화해야 한다고 주장하며 세 가지 검증 층을 제시한다.

1. 구조(Structural): 아키텍처 패턴을 검증한다. 커밋 전 단계에서 코드 구조를 강제하는 Codex CLI 훅에 대응한다.
2. 의미(Semantic): 명세와의 부합을 확인한다. 에이전트가 따라야 할 프로젝트 관례를 담은 AGENTS.md 지시에 대응한다.
3. 출처(Provenance): 산출물의 정당성을 검증한다. 플러그인 공급망 보안, 그리고 승인된 도구와 서버를 허용 목록에 올리는 `requirements.toml` 강제 계층에 대응한다.

### 성숙도 모델

반응적인 1단계(IDE 코파일럿만 사용)부터 최적화된 4단계(리뷰 관문에서만 사람이 감독하는 완전 자율 파이프라인 에이전트)까지 4단계다. 이 장 앞에서 본 자가 치유 모델(Observer, Gatekeeper, Healer)을 더 넓은 기업 도입 맥락에 놓아 보완한다.

Sanchez가 말하는 역할 변화는 엔지니어가 코드를 만드는 사람에서 시스템 설계자, 에이전트 운영자, 품질 관리자로 옮겨 가는 것이다. 12장의 조율 패턴과 11장의 서브에이전트 구조를 쓰는 팀에서는 이미 눈에 보인다.

## 4. CI/CD 패턴 카탈로그 (표 15-1)

이 표는 장의 패턴을 한곳에 모은 것이다. 메뉴가 아니라 의사 결정 도구로 읽는다. 각 행은 트리거(잡을 시작시키는 파이프라인 이벤트)와, 피해 범위를 정하는 두 설정을 짝짓는다. 승인 모드는 에이전트의 자율성을 정한다. `untrusted`(읽기 전용 분석)에서 `on-request`(파일 수정)를 거쳐 `never`(격리된 러너의 완전 자율)까지다. 권한 열은 그 패턴에 필요한 최소 GitHub 토큰 범위다. 댓글만 다는 리뷰어는 `pull-requests: write`와 `contents: read`면 되고, 브랜치와 PR을 여는 패턴은 `contents: write`도 필요하다. GitLab 행은 인증이 플랫폼을 통해 흐르므로 다르다. Duo Agent는 GitLab 관리 자격 증명을 쓰고, 파이프라인 잡은 토큰 범위 대신 아티팩트(`codequality`, SAST)로 결과를 낸다. 일이 일어나길 원하는 시점과 맞는 트리거의 행을 고르고, 잡이 할 일을 하기에 충분한 가장 좁은 승인 모드와 권한 집합을 택한다.

| 패턴 | 트리거 | 승인 모드 | 권한 |
| --- | --- | --- | --- |
| PR 리뷰 (GitHub) | `pull_request` | `untrusted` | `pull-requests: write`, `contents: read` |
| 테스트 생성 (GitHub) | `push` to main | `on-request` | `contents: write`, `pull-requests: write` |
| 의존성 업데이트 (GitHub) | `schedule` | `on-request` | `contents: write`, `pull-requests: write` |
| 보안 스캔 (GitHub) | `pull_request` | `untrusted` | `pull-requests: write`, `contents: read` |
| 코드 품질 (GitLab) | `merge_request_event` | `never` | `codequality` 아티팩트 |
| 보안 수정 (GitLab) | `merge_request_event` | `never` | SAST 리포트 + 패치 아티팩트 |
| Duo Agent (GitLab) | `@codex` 멘션 | GitLab 관리 | AI Gateway 자격 증명 |
| Pipeline Doctor | `workflow_run`(실패) | `on-request` | `contents: write`, `pull-requests: write` |
| CI 자동 수정 | `workflow_run`(실패) | `never` | `contents: write`, `pull-requests: write` |
| 스택 설명 | `pull_request` | `untrusted` | `pull-requests: write`, `contents: read` |
