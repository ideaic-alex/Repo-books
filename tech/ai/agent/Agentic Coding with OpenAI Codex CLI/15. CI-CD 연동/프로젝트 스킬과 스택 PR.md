# 프로젝트 스킬과 스택 PR

자동화 설정이 코드와 따로 놀면 코드베이스가 바뀔 때 자동화가 낡는다. 이 문서는 자동화를 자동화 대상 코드와 함께 버전 관리하는 두 가지 패턴을 다룬다. 하나는 PR 설명을 만들어 주는 프로젝트 수준 스킬(codex-pr-body)이고, 다른 하나는 작은 PR을 사슬처럼 이어 붙이는 스택 PR(stacked PR)에 에이전트가 만든 설명을 결합하는 방식이다.

---

## 1. codex-pr-body 스킬

`codex-pr-body`는 Codex CLI 코드베이스에 함께 들어 있는 프로젝트 수준 스킬이다. diff, 커밋 이력, 연결된 이슈를 보고 PR 설명을 만들어 준다. CI에 붙이는 스킬을 설계할 때 본보기로 삼을 만한 결정이 세 가지 있다.

### 스킬이 코드베이스와 함께 간다

스킬 정의는 `.agents/skills/` 아래에 있고, 설명하는 코드와 같이 버전 관리된다. PR 템플릿이 바뀌면 같은 커밋에서 스킬도 바뀐다. 문서와 코드가 어긋나는 일을 구조적으로 막는 셈이다.

### Sapling CLI는 읽기 전용으로 제한

스킬은 Meta의 Sapling(`sl`)을 diff와 스택 분석에 쓴다. 다만 읽기 전용 작업으로만 쓰게 한다. `sl push`도 `sl rebase`도 하지 않는다. 이 제한은 AGENTS.md 지시로 걸려 있는데, 이는 권고 수준이지 커널이 강제하는 것이 아니다. 실제 운영에서는 `-s read-only -c approval_policy=untrusted`를 함께 써서 OS 수준으로 막는다.

### 스택 PR을 이해하는 설명

스킬은 스택 PR, 곧 서로 의존하는 여러 PR이 사슬을 이룬 구조를 이해한다. 그래서 부모 PR과 자식 PR을 언급하는 설명을 만들고, 의존 관계 그래프가 리뷰어에게 분명히 보이게 한다.

## 2. 스택 PR이 가진 문제

스택 PR은 큰 변경을 리뷰하기 쉬운 작은 조각으로 쪼갠다. 대신 비용이 따라온다.

- PR마다 사슬 안에서 자기 역할을 설명하는 설명문이 필요하다.
- 스택이 리베이스(rebase)될 때마다 설명이 서로 맞게 유지되어야 한다.

`gh stack` 확장이 브랜치 사슬, 리베이스, PR 메타데이터 같은 기계적인 부분을 자동화한다. 여기에 에이전트가 만든 설명을 더하면 남은 부담이 거의 사라진다.

## 3. 스택 설명 자동 갱신 워크플로

PR이 열리거나 동기화(`opened`, `synchronize`)될 때 도는 워크플로다. 핵심은 프롬프트와 샌드박스다.

- 체크아웃은 `fetch-depth: 0`으로 전체 이력을 받는다. 부모 브랜치와 비교해야 하기 때문이다.
- 프롬프트는 "이 PR은 스택 PR 사슬의 일부다. 부모 브랜치 대비 diff를 분석하고, 이 조각이 이루는 일을 찾아서 설명을 만들라"는 내용이다. 설명에는 세 가지가 들어간다. 이 PR이 하는 일(2~3문장), 부모·자식 PR과의 관계, 리뷰어가 집중할 지점이다. 형식은 GitHub 마크다운이다.
- `sandbox: read-only`로 읽기만 하고 `OPENAI_API_KEY`는 시크릿에서 가져온다.

```yaml
- name: Generate stack-aware description
  uses: openai/codex-action@v1
  with:
    sandbox: read-only
  env:
    OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
```

## 4. 얻는 효과

이 조합은 스택 PR을 고급 사용자의 기법에서 기본 워크플로로 바꾼다. PR 하나가 한자리에서 읽을 만큼 작아져서 리뷰 처리량이 늘고, 에이전트가 만든 설명 덕분에 각 조각이 전체에서 어디에 들어맞는지 파악하려고 맥락을 오가는 비용이 없어진다.
