# CLI 에이전트 비교

터미널에서 도는 에이전트들을 하나씩 살펴본다. Codex CLI의 강점, 가장 가까운 경쟁자인 Claude Code, 무료 티어가 특징인 구글의 터미널 에이전트, 오픈소스 에이전트, 그리고 설계 철학이 아예 다른 스펙 기반과 병렬 조율 에이전트까지 다룬다. 각 도구를 이기고 지는 것으로 나누기보다 어떤 트레이드오프를 택했는지 이해하는 데 초점을 둔다.

---

## 1. Codex CLI의 강점

Codex CLI의 장점은 하니스의 메커니즘 층에 몰려 있다. 서베이 논문이 오래가는 차이는 그 층에 있다고 예측한 바로 그 자리다.

1. **커널 수준 샌드박스**: macOS에서는 Apple Seatbelt, Linux에서는 seccomp와 함께 bubblewrap을 쓴다. 애플리케이션 계층의 제한이 아니라 OS가 강제한다. 시스템 호출(syscall) 수준에서 동작하므로 에이전트가 무슨 시도를 하도록 설득당하든 막힌다. 보안 영향은 16장에서 깊게 다룬다.
2. **토큰 효율**: 헤드리스 터미널 운영은 IDE 연동 에이전트가 짊어지는 IDE 프로토콜 계층(에디터 상태 동기화, 완성 스트림, UI 갱신 메시지)의 토큰 부담이 없다. 이 차이가 팀 규모에서는 예산 항목이 되는 이유는 14장에 나온다.
3. **CI/CD 친화**: codex exec는 작업을 하나 받아 실행하고, 결과를 돌려주고, 끝난다. 파이프라인에 넣기에 자연스럽다. 15장에서 길게 다룬다.
4. **단계적 승인 모델**: 신뢰 수준이 여러 단계로 나뉘고 그 뒤에서 커널 수준 강제가 받쳐 준다. 신뢰만으로 켜고 끄는 이분법 스위치와 구조가 다르다. 이름 붙은 프로필(5장)로 이 프리셋을 재사용하고 버전 관리할 수 있다.

## 2. Claude Code: 가장 가까운 경쟁자

Claude Code는 CLI 에이전트 범주의 대표 경쟁자이자 Codex CLI와 가장 닮은 상대다. 가장 널리 쓰이는 터미널 에이전트 중 하나이며, 추론 품질이 결정적 제약일 때 강한 선택이다. 여러 파일에 걸쳐 미묘한 버그를 찾아 고치는 작업에서 꾸준히 좋은 수정을 내놓고, 집필 시점에 공개된 SWE-bench Verified 점수가 가장 높은 축에 든다. 다만 구체적인 벤치마크 수치는 스냅샷일 뿐이고 실시간 리더보드가 기준이라고 원서는 단서를 단다.

원서는 외우기보다 이해해 둘 구조적 차이를 두 가지 꼽는다.

**첫째, 정책 표현력.** Claude Code는 풍부한 훅 이벤트를 제공해서 셸 스크립트로 아무리 복잡한 정책 로직도 코드로 적을 수 있다. 훅은 설정이 아니라 프로그램이므로 표현력이 사실상 무제한이다. 반면 Codex CLI의 안전 모델은 커널 수준 샌드박스에 기댄다. 격리에는 더 강하지만 맞춤형 컴플라이언스 절차에는 덜 유연하다. 어느 쪽이 일방적으로 낫지 않다. 프로그램 가능한 훅은 샌드박스가 표현하지 못하는 정책을 쓸 수 있고, 샌드박스는 같은 신뢰 영역 안에서 도는 훅이 보장하지 못하는 경계를 강제할 수 있다.

**둘째, 강제의 기본값.** Claude Code도 자체 OS 수준 샌드박스를 갖고 있다. 에이전트가 띄우는 셸 하위 프로세스에 대해 macOS는 Seatbelt, Linux와 WSL2는 bubblewrap을 쓴다. 따라서 차이는 강제가 있느냐 없느냐가 아니라 범위와 기본값이다.

- 그 샌드박스는 Bash 하위 프로세스를 덮는다. 파일 읽기와 편집은 권한 계층을 통해 처리된다.
- 네트워크 필터링은 호스트 이름 기반이고 TLS 검사는 하지 않는다.
- 샌드박스는 선택해서 켜는(opt-in) 방식이다. Codex CLI는 커널 수준 격리를 구조상 기본값으로 둔다.

정리하면, 추론 품질과 프로그램 가능한 정책이 핵심 요구라면 Claude Code가 훌륭한 선택이고, 기본 상태의 강한 격리와 토큰 효율이 핵심이라면 Codex CLI가 우위다.

일대일로 붙었을 때 Codex CLI가 이기는 쪽은 토큰 효율과 비용이다. 독립 테스트에서 Codex CLI는 IDE 연동 에이전트보다 훨씬 적은 토큰을 쓰는 결과가 반복해서 나왔고, 일부 CLI끼리의 비교에서는 같은 작업에 Claude Code보다 몇 배 적게 쓰기도 했다. 개인이 쓸 때는 차이가 미미하지만, 팀 규모에서는 비용 절감이나 사용 한도 여유로 바뀌어 계획 수립의 입력값이 된다. 배수는 작업에 따라 달라지므로, 자기 대시보드에서 직접 확인하라고 원서는 당부한다. 실용적인 방법은 같은 작업을 두 도구에서 돌려 토큰 수를 직접 확인하는 것이고, 이것이 이 장의 첫 번째 연습 문제다.

## 3. 구글의 터미널 에이전트

구글도 같은 범주에 터미널 에이전트를 내놓았고, 가장 큰 특징은 큰 컨텍스트 윈도를 가진 진짜 무료 티어다. 이 무료 티어는 어떤 벤치마크보다 사용 습관을 크게 바꾼다. 질문 하나에 몇 센트가 들면 간단한 코드베이스 파악 질문은 잘 안 하게 되지만, 공짜면 편하게 묻는다. 그래서 코드를 고치는 일꾼보다는 탐색과 문서화 동반자 역할이 된다. 실시간 웹 검색으로 근거를 보강하는 기능도 있어서, 최근 버전의 라이브러리나 모델 학습 시점 이후 바뀐 API를 다룰 때 쓸모가 있다.

트레이드오프는 이 범주의 전형이다. 샌드박스는 커널 수준이 아니라 컨테이너 기반이고, 복잡한 추론이나 여러 파일에 걸친 리팩터링에서는 최전선 CLI 에이전트의 벤치마크 성능을 따라잡지 못했다. 비용이 제약이 아니고 작업 품질이 가장 중요한 팀이라면 최전선 에이전트가 더 나은 결과를 낸다. 반대로 탐색, 파악, 코드베이스에 대한 빠른 질문에는 무료 티어가 실제 가치를 만든다. 집필 시점에 이 분야의 구글 제품 계보는 유동적이어서 터미널 제품이 더 큰 플랫폼으로 흡수되는 중이다. 브랜드 이름은 그 범주보다 덜 안정적이라고 보면 된다(종료 일정은 이식 도구를 다루는 문서에서 설명한다).

## 4. 오픈소스와 벤더 중립 에이전트

OpenCode, Aider, Continue 같은 오픈소스 CLI 에이전트는 생태계의 깊이를 내주고 제공사로부터의 독립을 얻는다. Codex CLI는 OpenAI의 모델 스택과 강하게 결합돼 있지만, 이 도구들은 모든 제공사를 동등하게 대한다. 하나의 인터페이스 뒤에 수십 개의 모델 백엔드를 지원하고, 보통 관대한 라이선스 덕에 조달 심사 없이 내장할 수 있다. 로컬 모델을 쓰는 망 분리 환경이나 상용 도구를 쓰기 힘든 조달 절차를 가진 조직에서는 종속 걱정이 아예 사라진다.

대가는 상용 도구를 여러 개발자 팀에서 쓸 만하게 만드는, 의견이 담긴 설정 계층이다. 이런 에이전트에는 대체로 커널 수준 샌드박스, 이름 붙은 권한 프로필, 관리형 엔터프라이즈 기능이 없고 벤치마크 성능도 독립적으로 검증되지 않은 경우가 많다. 벤더 중립, 망 분리 운영, 모델 무관이 최우선 요구일 때는 강한 선택이다. 팀 전체 규칙과 강한 격리를 처음부터 갖춰 쓰려면 설득하기 어렵다.

## 5. 스펙 기반 에이전트와 병렬 조율 에이전트

철학이 실제로 다른 두 범주도 알아 둘 만하다. 기능 몇 개 차이가 아니기 때문이다.

**스펙 기반 에이전트**는 코드베이스가 아니라 구조화된 명세(스펙)를 주된 산출물로 삼는다. Codex CLI는 터미널 중심이고 최소주의라서 프롬프트를 받아 실행하고 샌드박스로 감싸는 데서 끝나지만, 스펙 기반 에이전트는 자연어 요청을 먼저 에이전트와 사람이 함께 참조하는 공식 명세로 바꾼 뒤에야 코드를 만든다. 이미 문서로 된 스펙으로 일하는 팀이 에이전트의 계획을 검토 가능한 문서로 원할 때 어울린다. 반면 파일 하나 고치는 빠른 작업에는 불필요한 의식이 된다. Codex CLI도 비슷한 자리에 PLANS.md 파일이라는 수동 관례(3장의 계획 방식)로 갈 수 있지만, 일급 스펙 객체는 없다.

**병렬 조율 에이전트**는 다른 쪽에 건다. 여러 에이전트를 나누어 맡기고 조율하는 일(오케스트레이션)에 무게를 두어, 깊은 추론 사슬 하나 대신 여러 서브에이전트로 갈라지고, 라우터가 이들을 조율하며, 때로는 사람이 보기 전에 경쟁하는 결과물끼리 점수를 매긴다. 그럴듯한 구현이 여럿인 탐색적 작업에서는 너비 우선 탐색이 에이전트 하나가 시도하지 않을 선택지를 드러낼 수 있다. 대신 통제와 검증 가능성을 잃는다. 품질 높은 단일 에이전트 한 번의 실행은 읽기 쉬운 기록을 남기고, 명세가 잘 된 티켓에는 비용 효율도 더 좋다. 이 범주 신규 진입자들이 스스로 발표한 벤치마크 수치는 독립 평가를 늘 통과하지는 못했다.

그래서 어떤 벤더든 자체 보고 벤치마크 수치는 독립 평가가 나올 때까지 조심해서 봐야 한다. 다른 스캐폴드로 재거나 독립 평가 기관 같은 제3자가 재면 헤드라인 수치보다 한참 낮게 나오는 일이 흔하다. 하니스 관점은 양쪽으로 작동한다. 강한 모델이라도 약한 공개 하니스에 담기면 자기 홍보 문구보다 못한 성능을 낼 수 있다.

## 6. 이 문서에서 기억할 것

- Codex CLI는 커널 샌드박스, 토큰 효율, CI/CD 친화성, 단계적 승인에서 강하다.
- Claude Code는 추론 품질과 훅의 프로그램 표현력에서 강하고, 샌드박스는 범위와 기본값이 다르다. 둘은 순위가 아니라 트레이드오프다.
- 구글 터미널 에이전트는 무료 티어가 핵심이며 탐색용에 어울린다.
- 오픈소스 에이전트는 종속이 없는 대신 팀 기능과 격리가 약하다.
- 스펙 기반과 병렬 조율 에이전트는 설계 철학이 다르며, 자체 보고 벤치마크는 독립 검증 전까지 의심한다.
