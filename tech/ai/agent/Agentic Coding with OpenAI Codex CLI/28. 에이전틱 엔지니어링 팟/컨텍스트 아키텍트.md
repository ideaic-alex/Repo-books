# 컨텍스트 아키텍트

컨텍스트 아키텍트(Context Architect)는 팟에서 왜와 무엇을 맡는 사람이다. 개별 기능 세션을 직접 몰기보다 재사용 가능한 맥락, 스킬, 가드레일을 만들어 레버리지를 낸다. 이 문서는 이 역할이 맡는 영역, 자율성 사다리, 주 산출물인 AGENTS.md 계층, 그리고 에이전트 쌍둥이 설정을 정리한다.

---

## 1. 이 역할이 맡는 것

컨텍스트 아키텍트는 성과와 환경을 책임진다. 팟이 약속한 것을 실제로 내놓는지, 에이전트가 정확한 맥락에서 일하는지, 전략 방향이 사업 의도와 맞는지가 그의 몫이다. 책임 영역은 네 가지다.

- **공장 관리(Factory Stewardship)**: 팟의 재사용 가능한 생산 체계, 즉 맥락, 스킬, 가드레일을 관리한다. 신호가 높은 브리프의 기준을 세우고 리뷰 루프를 설계한다. 반복되는 마찰은 맥락 층을 고치는 쪽으로 되먹인다.
- **성과 정의와 가치 실현**: 사업 후원자와 만나는 주 창구다. 막연한 사업 피드백을 실행 가능한 맥락으로 옮기고, 제품 서사를 책임지며, 전달 트레이드오프를 비용 대비 가치로 설명한다. 여기에는 원서가 말하는 '에이전시의 경제학'이 포함된다.
- **컨텍스트 엔지니어링**: 패턴, 문서, 의사결정 기록을 가꿔 에이전트가 낮은 수준의 결정을 올바르게 내리는 감각을 갖게 한다. 신호 대 잡음비를 가차 없이 관리한다. 서로 모순되거나 낡은 맥락은 모순되거나 낡은 결과물을 낳기 때문이다.
- **전략적 가드레일과 정책**: 법률, 윤리, 안전 가드레일을 정한다. 컴플라이언스 요구를 구조화된 정책으로 옮기고, 무엇이 자동으로 돌아도 되고 무엇이 사람 승인을 받아야 하는지 에스컬레이션 기준을 정한다.

## 2. 자율성 사다리

에이전트에게 얼마나 맡길지를 네 단계로 나눈 것이 자율성 사다리다.

| 단계 | 이름 | 의미 |
|---|---|---|
| 1 | Assist(보조) | 에이전트는 제안만 하고, 사람이 모든 변경을 검토해 직접 적용한다 |
| 2 | Approval-required(승인 필요) | 에이전트가 실행하되 사람이 각 동작을 실행 전에 승인한다 |
| 3 | Policy-bounded(정책 한정) | 정해진 경계 안에서 에이전트가 실행하고, 예외는 위로 올린다 |
| 4 | Self-remediating(자가 치유) | 가드레일 안에서 에이전트가 문제를 찾고, 진단하고, 고친다 |

단계를 올릴 때는 확신이 아니라 증거(테스트 커버리지, 리뷰 이력, 감사 로그)가 필요하다. 단계는 모듈 단위가 아니라 변경 범주 단위로 매긴다. 예를 들어 결제 모듈이라도 스키마 변경은 영구히 2단계로 두고, 읽기 경로 최적화는 3단계로 둘 수 있다.

## 3. AGENTS.md는 이 역할의 주 산출물

AGENTS.md는 여러 설정 파일 중 하나가 아니라 컨텍스트 아키텍트의 핵심 납품물이다. 밸류 엔지니어가 돌리는 모든 Codex 세션과 퀄리티 엔지니어가 발동하는 모든 자동 게이트가 이 계층을 읽는다. 팟 결과물의 품질은 이 문서의 품질을 넘을 수 없다.

(AGENTS.md 계층, 파일 로딩 순서, 덮어쓰기 방식은 4장에서 자세히 다룬다. 팟에서 중요한 성질은 Codex가 계층의 AGENTS.md를 자동으로 읽는다는 점이다. 그래서 따로 불러오라고 지시하지 않아도 모든 팟 에이전트 세션의 공유 컨텍스트 층이 된다.)

운영용 팟의 계층은 다음과 같다.

```
~/.codex/AGENTS.md                # 개인 선호, 커밋하지 않음
AGENTS.md                         # 저장소 수준, 팟의 단일 진실 공급원
src/payments/AGENTS.md            # 바운디드 컨텍스트의 도메인 제약
src/auth/AGENTS.md                # 인증용으로 더 엄격한 보안 제약
.codex/roles/value-engineer.md    # 역할별 지침
.codex/roles/quality-engineer.md  # QE용 역할별 지침
```

저장소 수준 AGENTS.md에는 제품 설명, 인수 조건 기준, 아키텍처 제약, 승인된 의존성 목록, 완료의 정의가 들어간다. 모든 에이전트가 이 파일을 제일 먼저 읽는다. 하위 디렉터리의 AGENTS.md는 스프린트가 바뀌어도 유지되는 도메인 제약을 담는다. 더 구체적인 파일이 더 일반적인 파일을 덮어쓰므로, src/auth/ 안에서 일하는 에이전트는 따로 지시하지 않아도 더 엄격한 제약을 자동으로 물려받는다.

잘 쓴 저장소 수준 AGENTS.md는 대략 다음 뼈대를 가진다(원문의 핵심 줄만 옮겼다).

```markdown
# Product Context
This service is the authoritative source for user subscription state.
# Acceptance Criteria Standard
1. A user-facing outcome statement ("A user with [state] can [action]...")
2. At least one failure scenario with expected behaviour
3. A performance bound for any user-facing path (<200ms p95)
# Architectural Constraints
- All external data validated with zod at the boundary
- No cross-module database queries; each module owns its schema
- All state changes must emit an audit event before returning
# Approved Dependencies
See .codex/approved-deps.json. Adding an unlisted dependency requires ADR approval.
```

원문은 이 뒤에 자율성 수준 절도 둔다. 읽기 경로 변경은 정책 한정(3단계), 쓰기 경로 변경과 스키마 변경은 승인 필요(2단계), 인프라 변경은 보조(1단계)로 적는다. 또 제품 맥락에는 구독 상태를 둘 이상의 진실 공급원에서 파생하는 경로를 만들지 말라는 규칙이, 인수 조건 기준에는 기능마다 사용자 관점의 결과 문장, 실패 시나리오 하나 이상, 성능 상한을 요구한다는 규칙이 들어 있다. 승인 목록에 없는 의존성은 ADR(아키텍처 결정 기록) 승인 없이 쓸 수 없다.

## 4. 명세를 강제하는 장치 - 오피스 아워 스킬

유용한 패턴으로 오피스 아워(office-hours) 스킬이 있다. 코드를 쓰기 전에 구조화된 제품 대화를 먼저 열고 네 질문에 명시적으로 답하게 하는 스킬이다. 어떤 문제를 푸는가, 성공은 관찰 가능한 말로 어떤 모습인가, 범위 밖은 무엇인가, 타협할 수 없는 제약은 무엇인가. 이렇게 설계한 Codex 스킬은 범위와 성공 기준이 확인되기 전에는 세션을 진행시키지 않는다. 이 답이 글로 적히기 전에는 해당 기능의 AGENTS.md 항목도 만들지 않는 것이 원칙이다.

## 5. 플러그인으로 이 역할의 기술 배포하기

컨텍스트 아키텍트의 명세 스킬, 오피스 아워 스코핑 대화, AGENTS.md 상태 점검, ADR 작성 템플릿은 한 사람 머릿속에만 있으면 안 되는 조직의 지식이다. 플러그인 시스템은 스킬을 훅, MCP 서버, 앱 커넥터와 함께 설치 가능한 하나의 단위로 묶는다. 다만 원서가 쓰인 시점에 문서화된 플러그인 명세는 커스텀 에이전트 역할 TOML이나 AGENTS.md 템플릿을 정식 구성 요소로 나열하지 않는다. 그래서 이것들은 자동 연결되는 요소가 아니라 같이 담겨 가는 파일로 취급한다. 가장 경험 많은 컨텍스트 아키텍트가 스킬을 개선하거나 컨텍스트 드리프트 점검을 추가하면, 버전을 올리는 것만으로 모든 팟이 그 갱신을 받는다. 기술이 특정 사람만 아는 지식이 아니라 배포 가능한 인프라가 된다. 이 패턴은 세 역할 모두에서 반복되며 뒤의 플러그인 배포 문서에서 다시 정리한다.

## 6. 컨텍스트 아키텍트의 TOML 설정

컨텍스트 아키텍트가 Codex를 부르는 일은 명세와 아키텍처 작업이다. ADR 작성, AGENTS.md 갱신, 인수 조건 검증, 컨텍스트 드리프트 평가가 대표적이다. 이 세션은 추론 강도가 높은 모델을 쓰고 완전 자동으로는 돌리지 않는다. 컨텍스트 아키텍트는 구현이 아니라 정책을 정하기 때문이다.

```toml
# .codex/agents/context-architect.toml
name = "context-architect"
description = "Specification, ADR authoring, AGENTS.md maintenance, context quality review."
developer_instructions = """ ...(아래 규칙 요약)... """
model = "gpt-5.4"
model_reasoning_effort = "xhigh"
approval_policy = "untrusted"
sandbox_mode = "workspace-write"
```

`developer_instructions`의 내용은 말로 옮기면 이렇다. 처리할 일은 계층 어느 수준의 AGENTS.md든 작성하거나 갱신하기, ADR 쓰기와 검토, 인수 조건을 검증 가능하고 구체적인 형태로 바꾸기, 기존 맥락 문서가 최신이고 정확한지 평가하기, 맥락 층의 빈틈이나 모순 찾기다. 규칙은 기능 구현 코드를 쓰지 말 것, `.codex/`나 `docs/` 밖의 소스 파일을 고치지 말 것, ADR은 `.codex/adr-template.md` 형식을 따를 것, 에이전트가 진행하기 전에 사람의 결정이 필요한 맥락 공백은 표시할 것, 문서 묶음이 팟에서 쓸 준비가 되면 `CONTEXT_COMPLETE`를 출력할 것이다.

`approval_policy = "untrusted"`는 의도된 선택이다. 컨텍스트 아키텍트는 맥락 층에 제안된 모든 변경을 커밋 전에 직접 검토하고 승인한다. 맥락 오류는 이후 모든 에이전트 세션으로 퍼지므로, 작성하는 시점에 사람이 꼼꼼히 봐야 한다.
