# 플러그인으로 팟 배포하기

팟이 하나일 때 생기는 문제는 안에서 곪는 방식이다. 규모가 커지면 다른 압력이 생긴다. 범위 팽창의 해결책이 팟을 키우지 말고 병렬 팟을 띄우라는 것이었는데, 새 팟마다 같은 구조를 충실히 재현해야 한다. 손으로 설정해야 하는 구조는 복사하는 순간부터 어긋나기 시작한다. 팟을 배포한다는 것은 수많은 팟을 수작업 없이 구조적으로 동일하게 유지하는 문제다.

---

## 1. 설정 문제

운영 수준의 팟에는 다음이 필요하다. 역할 TOML 세 개, AGENTS.md 계층, 정책 강제와 세션 후 검증을 위한 훅 스크립트, 검증 스킬, MCP 서버 설정, 브리핑 템플릿이다. 기업이 팟을 열 개 운영하면 이 설정이 열 번 복제되고 어긋남이 불가피하다. 세 번째 팟의 훅이 일곱 번째 팟의 훅과 달라진다. 한 컨텍스트 아키텍트가 AGENTS.md 구조를 발전시켜도 다른 사람들은 따라가지 않는다. 설정 드리프트는 팟 모델이 기대는 구조적 보장을 갉아먹는다.

## 2. 팟 인프라로서의 플러그인

Codex 플러그인 시스템은 스킬, 훅, MCP 서버, 앱 커넥터를 설치 가능한 하나의 단위로 묶는다. 이것이 팟의 필요와 곧바로 맞는다. 팟 플러그인은 플러그인 시스템이 자동으로 활성화하는 스킬, 훅 스크립트, MCP 설정을 묶고, 팟이 쓰는 역할 TOML과 AGENTS.md 템플릿도 함께 담는다. 다만 원서가 쓰인 시점에 문서화된 플러그인 명세는 커스텀 에이전트 역할 TOML이나 AGENTS.md 템플릿을 자동 연결되는 구성 요소로 나열하지 않는다. 플러그인 시스템이 알아서 등록해 주는 것이 아니라, 자동으로 활성화되는 부분과 함께 설치되는 동봉 파일로 보아야 한다. 원서가 보여 주는 디렉터리 구성은 다음과 같다.

```
agentic-pod/
├── .codex-plugin/plugin.json
├── skills/   (context-architect, value-engineer, quality-engineer,
│              office-hours, pod-health 각각의 SKILL.md)
├── hooks/    (pre-prompt-policy.sh, post-tool-scope.sh,
│              post-session-verify.sh)
├── roles/    (context-architect.toml, value-engineer.toml,
│              quality-engineer.toml)
└── templates/ (agents-md-repo.md, agents-md-domain.md,
               brief-template.md)
```

스킬은 각각 명세와 AGENTS.md 유지, 브리핑 엔지니어링과 구현, 검증 게이트 실행, 구현 전 스코핑(office-hours), 컨텍스트 드리프트와 역할 붕괴 탐지(pod-health)를 맡는다. 훅 세 개는 `pre-prompt-policy.sh`(UserPromptSubmit, 인젝션 검사), `post-tool-scope.sh`(PostToolUse, 파일 범위 강제), `post-session-verify.sh`(Stop, 테스트 스위트·범위·감사 이벤트)다. 템플릿은 저장소 수준 AGENTS.md, 하위 디렉터리 AGENTS.md, 높은 신호의 브리프용이다.

설치는 `codex plugin add agentic-pod` 한 줄이 된다. 모든 개발자가 같은 역할 설정, 훅, 검증 게이트를 받는다. 드리프트를 원천에서 없앤다.

## 3. 단일형과 조합형

패키징 전략은 두 가지가 통한다. 모든 것을 플러그인 하나에 넣는 단일형은 더 단순하고 일관성을 보장한다. 역할별 플러그인 세 개(`pod-context-architect`, `pod-value-engineer`, `pod-quality-engineer`)로 나누는 조합형은 더 유연하다. 전담 퀄리티 엔지니어가 없는 팀은 자동 게이트용으로 QE 플러그인만 설치하면 된다. 조합형은 버전 주기도 독립시킨다. 보안 팀이 VE 브리핑 템플릿을 건드리지 않고 QE의 적대적 테스트를 갱신할 수 있다.

원서의 조언은 단일형으로 시작하고, 갈라져야 할 압력이 실제로 생기면 쪼개라는 것이다. 너무 일찍 쪼개면 팟 모델이 없애려는 조율 비용이 되살아난다.

## 4. 마켓플레이스를 통한 기업 거버넌스

플러그인 시스템의 3단 마켓플레이스 계층은 기업의 팟 거버넌스와 대응한다. 저장소 마켓플레이스, 즉 저장소 루트의 `.agents/plugins/` 아래 `marketplace.json`이 기업의 통제 지점이다. 원서의 예는 `pod-quality-engineer`와 `pod-value-engineer` 두 항목을 둔다.

```json
{ "plugins": {
  "pod-quality-engineer": {
    "source": { "source": "git", "url": "https://github.com/acme/codex-pod-qe.git" },
    "policy": { "installation": "INSTALLED_BY_DEFAULT", "authentication": "ON_INSTALL" }
  }
} }
```

`pod-value-engineer`도 같은 형식으로 `https://github.com/acme/codex-pod-ve.git`를 가리키고 같은 정책을 쓴다. `INSTALLED_BY_DEFAULT`는 퀄리티 엔지니어의 훅이 설정을 기억하는 팀뿐 아니라 기업 전체의 모든 세션에서 발동하게 한다. 플랫폼 팀이 검증 훅을 개선해서 API 계약 검증 같은 새 Tier 2 검사를 더하면, 팟들은 마켓플레이스를 새로 고쳐(`codex plugin marketplace upgrade`) 변경을 받는다. 그러면 `INSTALLED_BY_DEFAULT` 정책이 다음 세션에서 갱신된 훅이 있도록 보장한다.

## 5. 플러그인이 바꾸지 못하는 것

플러그인이 배포하는 것은 인프라이지 판단이 아니다. 세 질문은 여전히 세 사람에게 있다. 플러그인이 바꾸는 것은 그 질문 주위의 구조를 운영하는 데 드는 비용이다. 플러그인이 있는 팟은 시간을 판단에 쓰고, 없는 팟은 상당한 비중을 설정, 동기화, 드리프트 복구에 쓴다. 플러그인 시스템은 에이전틱 팟을 개념 모델에 그치지 않고 배포 가능한 조직 패턴으로 만든다.
