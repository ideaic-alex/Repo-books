# 기능 하나의 생애 주기

앞에서 세 역할을 따로 봤다면, 이 문서는 기능 하나가 팟을 통과하는 과정을 처음부터 끝까지 따라간다. 예로 드는 기능은 '구독이 만료된 사용자가 결제 정보를 다시 입력하지 않고 갱신할 수 있다'이다. 컨텍스트 아키텍트가 틀을 잡고, 밸류 엔지니어가 구현을 조율하고, 퀄리티 엔지니어의 자동 게이트가 검증하는 세 단계로 흐른다.

---

## 1. 1단계 - 컨텍스트 아키텍트가 기능의 틀을 잡는다

컨텍스트 아키텍트는 AGENTS.md가 갱신 흐름을 이미 다루고 있는지 살핀다. 구독 모듈에 빠진 인수 조건을 추가하고 브리프를 쓴다. 브리프의 내용은 다음과 같다.

- **사용자 결과**: `status=expired`인 사용자가 `POST /subscriptions/renew`를 호출하면 결제 정보를 다시 입력하지 않고 `status=active`를 받는다.
- **실패 시나리오**: `status=active`인 사용자는 409와 `{"error": "already_active"}`를 받는다. Stripe 실패는 502와 `{"error": "payment_failed"}`를 반환하고 구독 상태는 바뀌지 않는다. 연속 두 번 호출하면 두 번째는 현재 상태와 함께 200을 반환하고 두 번째 청구는 없다.
- **성능 상한**: 정상 부하에서 p95 200ms 미만.
- **자율성 수준**: 쓰기 경로 변경이므로 승인 필요(2단계).

## 2. 2단계 - 밸류 엔지니어가 구현을 조율한다

결제와 얽힌 쓰기 경로 변경이라서 밸류 엔지니어는 전용 워크트리에서 승인 필요 정책으로 Codex 세션을 띄운다.

```bash
git worktree add ../worktrees/feature-subscription-renewal -b feature/subscription-renewal
cd ../worktrees/feature-subscription-renewal
codex --profile value-engineer
```

첫 프롬프트는 신호가 높은 브리프다. 요지는 이렇다. `src/subscriptions/AGENTS.md`의 인수 조건대로 `POST /subscriptions/renew`를 구현한다. 의도는 expired 사용자가 저장된 결제 수단으로 active가 되는 것이다. 제약은 멱등이어야 하고(두 번 호출해도 Stripe 청구가 두 번 생기면 안 됨), 200을 돌려주기 전에 `subscription.renewed` 이벤트를 발행하며, Stripe 실패면 502를 돌려주고 오류를 기록하되 상태를 바꾸지 않고, 결제 수단 저장 로직은 고치지 않는 것이다. 그리고 코드를 쓰기 전에 `/plan`으로 영향받는 파일과 의존 순서를 먼저 보여 달라고 요구한다.

에이전트가 `/plan`을 실행하면 밸류 엔지니어는 실행을 승인하기 전에 계획을 검토한다. 여기서 전문가 판단이 가장 크게 작용한다. 에이전트의 첫 멱등성 구현에는 동시 호출에서 터지는 경쟁 상태가 있었다. 밸류 엔지니어는 이렇게 방향을 바로잡는다. 애플리케이션 수준의 읽기-확인-쓰기가 아니라 `(user_id, renewal_date)`에 대한 데이터베이스 수준 유니크 제약을 써야 하며, 멱등성 패턴 요구는 `src/subscriptions/AGENTS.md`에 있으니 접근을 고치라는 것이다.

## 3. 3단계 - 퀄리티 엔지니어의 자동 게이트가 발동한다

퀄리티 엔지니어의 세션 후 훅이 발동해 테스트 스위트를 돌리고, 범위 준수를 확인하고, 결과를 `.codex/tasks/subscription-renewal/verification.md`에 쓴다. 퀄리티 엔지니어는 적대적 테스트도 따로 실행한다. 요청의 요지는 갱신 엔드포인트 구현을 레드팀하라는 것이고, 시험할 것은 세 가지다.

1. 같은 `user_id`에서 오는 동시 호출(경쟁 상태)
2. 갱신 요청이 처리 중일 때 도착하는 Stripe 웹훅
3. 같은 사용자에게 두 번째 Stripe 청구가 생길 수 있는 모든 경로

결과는 `.codex/tasks/subscription-renewal/security-review.md`에 보고한다. 적대적 세션은 우회를 찾지 못했고 데이터베이스 수준 제약이 버텼다. `VERIFICATION_PASSED`가 나왔으므로 기능은 병합 준비가 됐다.

결제와 얽힌 쓰기 경로 변경이라면 팟은 병합 전에 다학제 게이트를 돌린다. 엔지니어링 리뷰, 보안 리뷰(OWASP Top 10과 STRIDE), QA 검증을 순차 체크포인트로 거친다. 자율성 사다리와 게이트 순서는 같은 분류표를 쓰며, 둘 다 퀄리티 엔지니어가 관리한다.

## 4. 사람의 판단이 들어가는 지점

이 생애 주기에서 사람의 판단은 네 곳에서 나타난다. 기능의 틀 잡기, 구현 계획 검토, 경쟁 상태에 대한 방향 수정, 최종 병합 승인이다. 나머지는 모두 팟의 에이전트 층이 실행한다.

> 원서 그림 설명(약 616쪽, 글로 풀어 씀): 그림 28.2. 팟을 통과하는 기능의 생애 주기. 사람이 기능의 틀을 승인하면 컨텍스트 아키텍트가 AGENTS.md와 인수 조건을 갱신해 신호가 높은 브리프를 밸류 엔지니어에게 넘기고, 밸류 엔지니어는 워크트리에서 /plan을 실행해 영향받는 파일과 의존 순서를 사람에게 보여 준다. 이어 구현을 퀄리티 엔지니어에게 넘기면 세션 후 훅이 테스트, 범위, 레드팀 검사를 돈다. VERIFICATION_PASSED이면 병합 승인을 사람에게 요청하고, 문제가 발견되면 수정을 위해 밸류 엔지니어에게 작업을 되돌리는 점선 피드백 고리가 있다.

그림을 읽는 요령은 다음과 같다. 위에서 아래로 시간이 흐르고, 가로 화살표가 인계와 보고다. 사람이 처음(틀 잡기)과 끝(병합 승인)을 쥐고 있고, 중간에 밸류 엔지니어가 계획을 사람에게 보여 승인과 방향 수정을 받는다. 퀄리티 엔지니어의 검증에서 문제가 발견되면 점선을 따라 밸류 엔지니어에게 돌아가 수정 작업이 이어진다.
