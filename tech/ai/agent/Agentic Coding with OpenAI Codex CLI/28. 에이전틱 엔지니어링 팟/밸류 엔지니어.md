# 밸류 엔지니어

밸류 엔지니어(Value Engineer)는 팟에서 어떻게를 맡는다. 에이전트에게 일을 어떻게 시킬지, 결과가 좋은 구현인지를 판단하는 사람이다. 이 문서는 이 역할의 책임, 좋은 브리프를 쓰는 법, 병렬화 판단 기준, 리뷰 깊이, 그리고 에이전트 쌍둥이 설정을 정리한다.

---

## 1. 이 역할이 맡는 것

밸류 엔지니어는 처음부터 끝까지 전달을 조율한다. 이 역할에는 탄탄한 소프트웨어 엔지니어링 기초가 필요하다. AI 도구를 우연히 쓰게 된 프로젝트 매니저로는 안 된다. 에이전트 결과물을 검증하고, 아키텍처가 어긋나는 것을 알아채고, 정확성 실패를 잡고, 에이전트가 혼자서는 지키게 할 수 없는 구현 기준을 유지할 기술 깊이가 있어야 하기 때문이다. 책임 영역은 네 가지다.

- **시스템 조율과 기술 탐색**: 기술 분야 전문가를 만나는 주 창구다. 복잡한 업무 규칙을 실행 가능한 시스템 동작으로 옮기는 깊은 탐색을 맡는다.
- **브리핑 엔지니어링**: 신호가 높은 브리프를 만든다. 브리프는 의도, 제약, 예시, 엣지 케이스를 갖춘 구조화된 프롬프트로, 에이전트가 모호함 없이 실행할 만큼 충분해야 한다. 브리프의 품질이 이 역할의 핵심 기술이다.
- **에이전틱 루프 엔지니어링**: 수렴 기준, 병렬도, 중단 조건을 설계한다. 속도, 토큰 비용, 확신 사이에서 의도적으로 균형을 잡는다. 에이전트를 끝까지 돌리게 둘 때, 방향을 바꿀 때, 더 나은 맥락으로 다시 시작할 때를 안다.
- **전문가 판단과 구현 기준**: 모든 로직에 대한 최종 검증을 한다. 에이전트가 놓칠 수 있는 아키텍처 이탈, UX 결함, 정확성 실패를 짚는다.

## 2. 브리핑 엔지니어링 실전

낮은 신호의 브리프('구독 서비스에 갱신 엔드포인트를 추가해 줘')와 높은 신호의 브리프를 가르는 것은 길이가 아니라 구체성이다. 원서의 예를 간추리면 다음과 같다.

- **과제**: 구독 갱신 엔드포인트
- **의도**: `subscription.status = "expired"`인 사용자가 결제 정보를 다시 입력하지 않고 `POST /subscriptions/renew`로 구독을 갱신할 수 있어야 한다.
- **제약**: `user.paymentMethodId`에 저장된 결제 수단을 재사용한다. 갱신은 멱등(idempotent)이어야 해서 엔드포인트를 두 번 불러도 청구가 두 번 생기면 안 된다. 200을 돌려주기 전에 `subscription.renewed` 이벤트를 발행한다.
- **인수 조건**: expired 사용자는 성공 호출 뒤 active가 된다. active 사용자는 `{"error": "already_active"}` 본문과 함께 409를 받는다. Stripe 실패는 오류를 로그에 남기고 502를 반환하며 구독 상태는 그대로다. 정상 부하에서 응답 시간은 p95 200ms 미만이다.
- **범위 밖**: 결제 수단 저장 로직을 건드리지 않는다. 새 구독 등급을 추가하지 않는다.
- **참조**: 멱등성 요구와 이벤트 스키마는 `src/subscriptions/AGENTS.md`와 `src/events/types.ts`를 본다.

이 브리프에는 명시된 실패 시나리오, 분명한 멱등성 요구, 범위 밖 경계, 도메인 AGENTS.md 참조가 들어 있다. 각각은 에이전트가 추측으로 풀어야 했을 결정 지점을 하나씩 없애 준다.

## 3. 밸류 엔지니어의 Codex 세션 패턴

전형적인 기능 세션은 이렇게 흐른다. 과제 명세와 관련 AGENTS.md 맥락을 읽는다. `/plan`으로 접근 방식을 검증한다. 워크트리의 workspace-write 샌드박스 안에서 실행한다. 결과를 인수 조건과 대조해 검토한다. 어긋나면 방향을 바로잡는다. 구현이 깨끗해지면 퀄리티 엔지니어의 게이트로 넘긴다. 기능마다 자기 워크트리를 가지며, main에는 검토를 거쳐 게이트를 통과한 결과만 들어간다.

워크트리는 병렬 에이전트 세션을 구조적으로 가능하게 하는 수단이며 13장에서 다룬다. 밸류 엔지니어의 기능 세션은 각자 전용 워크트리에서 돌리고, main 브랜치는 완료된 워크트리의 검토 완료·게이트 통과 결과만 받는다. 에이전트가 직접 커밋하는 일은 없다.

## 4. 병렬화 판단 - Metric Freedom

11장에서 소개한 Metric Freedom은 병렬 서브에이전트를 띄울지 한 세션에 둘지 정하는 원칙적 기준이다. `F = 1 − ρ(D_out, D_score)`라는 숫자 하나로, 작업이 다양한 출력의 이득을 보는지(F가 높음) 하나의 정답을 요구하는지(F가 낮음)를 잰다. 기능을 에이전트 과제로 쪼갤 때 이렇게 쓴다.

- **F가 높은 하위 작업**(코드 리뷰, 문서화, 테스트 생성)은 병렬 서브에이전트에 맡긴다. 다양성이 자산이므로 여러 멀티 에이전트 역할로 퍼뜨려 여러 접근을 탐색하게 한다.
- **F가 낮은 하위 작업**(버그 수정, 마이그레이션, 스키마 변경)은 추론 강도를 높인 단일 에이전트에 맡긴다. 다양성보다 정밀함이 중요하다. 병렬화의 조율 비용을 치르기보다 작업에 맞는 지식을 집중된 프롬프트에 담는다.

퀄리티 엔지니어도 같은 숫자로 검증을 맞춘다. F가 높은 결과물은 접근 선택에 대한 사람의 리뷰가 필요하다(유효한 접근이 많은 가운데 좋은 것을 골랐는가). F가 낮은 결과물은 자동화된 정확성 검사가 필요하다(유일한 정답을 냈는가).

## 5. 비례형 리뷰 깊이

리뷰 깊이는 diff 크기에 비례해야 한다. 작고 독립적인 diff(대략 50줄 미만, 논리 단위 하나)에서는 세 가지를 본다. 주장대로 동작하는가, 눈에 띄는 정확성 문제가 있는가, 금지된 의존성을 들이지 않았는가. 여러 모듈에 걸치거나 핵심 로직을 다시 쓰는 더 큰 diff는 네 번 훑을 가치가 있다. 의도 일치, 정확성(경쟁 상태, 엣지 케이스, 실패 경로), 부작용, 완결성(테스트가 있는가, 인수 조건을 보여 줄 수 있는가)이다. 밸류 엔지니어는 이를 리뷰 스킬로 만들어 `git diff --stat` 출력에 따라 빠른 검토와 전체 검토 중 하나로 보낼 수 있다.

## 6. 밸류 엔지니어의 TOML 설정

```toml
# .codex/agents/value-engineer.toml
name = "value-engineer"
description = "Feature implementation, orchestration, and agent supervision sessions."
developer_instructions = """ ...(아래 규칙 요약)... """
model = "gpt-5.4-mini"
model_reasoning_effort = "high"
approval_policy = "on-request"
sandbox_mode = "workspace-write"
```

지시문의 내용은 세 단계다. 시작 전에는 AGENTS.md와 과제에 관련된 하위 디렉터리 AGENTS.md를 읽고, 과제 브리프를 읽어 인수 조건을 이해했는지 확인하고, 모호한 제약이 있으면 코드를 쓰기 전에 드러낸다. 구현 중에는 논리적인 변경 묶음마다 테스트를 돌리고, 테스트가 실패하면 넘어가지 않고 고치며(건너뛰기 금지), 브리프가 다루지 않은 아키텍처 결정을 만나면 `.codex/clarifications.md`에 적고 검토를 위해 멈추며, 브리프의 인수 조건을 추적해 각 항목이 입증된 뒤에만 완료를 알린다. 완료 신호는 `IMPLEMENTATION_COMPLETE`이며, 인수 조건별 충족 여부, 브리프를 넘어 처리한 엣지 케이스, 퀄리티 엔지니어 검토로 미룬 항목의 요약을 붙인다.

`approval_policy = "on-request"`는 밸류 엔지니어의 워크트리 세션에 알맞다. 에이전트가 범위가 정해진 워크트리 안에서 실행되고, 인수 조건이 명확하며, main에 닿기 전에 퀄리티 엔지니어의 게이트가 돌기 때문이다. 모델이 승인을 요청할 시점을 스스로 판단하므로 일상적인 파일 편집은 막힘없이 흐르고, 이상해 보이는 일만 사람에게 올라온다.
