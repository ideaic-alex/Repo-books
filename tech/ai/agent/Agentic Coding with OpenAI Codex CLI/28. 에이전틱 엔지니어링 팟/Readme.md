# 에이전틱 엔지니어링 팟

에이전트가 실행 대부분을 맡으면 사람에게는 세 가지 질문이 남는다. 왜 만드는가, 어떻게 만들 것인가, 만든 것을 믿어도 되는가다. 이 장은 이 세 질문에 사람 셋(컨텍스트 아키텍트, 밸류 엔지니어, 퀄리티 엔지니어)을 붙이고 하나의 컨텍스트 층을 공유하게 하는 팀 구조, 에이전틱 엔지니어링 팟을 설명한다.

각 역할의 TOML 설정, AGENTS.md 계층, 훅과 게이트, 기능 하나가 팟을 통과하는 과정, 팟이 무너지는 방식, 플러그인으로 여러 팟을 같은 구조로 유지하는 방법을 차례로 다룬다. 원서는 이 팟이 정답이 아니라 출발점이라고 못 박는다.

---

## 1. 핵심 요점

- 에이전트가 생성을 싸게 만들어 병목이 검증으로 옮겨 갔다. 검증되지 않은 결과물은 가치가 아니라 재고다.
- 팟의 세 역할은 사람이 맡는다. 컨텍스트 아키텍트는 왜와 무엇, 밸류 엔지니어는 어떻게, 퀄리티 엔지니어는 신뢰를 책임지며, 에이전트는 각자가 쓰는 도구다.
- 세 사람 규칙은 인원수가 아니라 책임의 분리다. 수요가 늘면 팟을 키우지 말고 병렬 팟을 띄운다.
- 각 역할에는 이름이 같은 에이전트 쌍둥이 설정이 있고, 역할의 장기 과제는 자기 판단을 쌍둥이에게 옮겨 심는 것이다.
- AGENTS.md 계층이 공유 컨텍스트 층이고, 변경 범주별 자율성 사다리(4단계)는 증거가 있어야 오른다.
- 퀄리티 엔지니어는 검증 처리량으로 속도를 정하고 구조적인 거부권을 쥔다. 훅과 3단계 비용 게이트로 검증 노력을 위험에 맞춘다.
- 컨텍스트 부채, 게이트 우회, 단일 지점 품질 실패, 역할 붕괴, 범위 팽창이 팟의 대표적인 실패 방식이다.
- 플러그인과 마켓플레이스 정책(INSTALLED_BY_DEFAULT)으로 구조와 게이트를 배포하지만 판단은 사람에게 남는다.
