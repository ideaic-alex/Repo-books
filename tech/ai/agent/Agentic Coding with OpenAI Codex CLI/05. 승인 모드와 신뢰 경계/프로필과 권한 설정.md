# 프로필과 권한 설정

Codex CLI에는 이름이 비슷하지만 서로 다른 프로필(profile) 체계가 둘 있다. 이를 구분하지 못하는 것이 이 영역에서 가장 흔한 설정 실수다. 이 문서는 두 체계의 차이, TUI의 권한 선택 메뉴가 실제로 무엇을 바꾸는지, 기본 제공 프로필, 상속(extends), 그리고 항목별 승인 설정(granular)을 차례로 설명한다.

---

## 1. 프로필 체계 두 가지

첫째, 이름 붙인 프로필(named profile)은 세션 수준 설정(모델, 승인 정책, 샌드박스 모드, MCP 서버)을 `~/.codex/<name>.config.toml` 파일 하나에 묶는다. 실행할 때 `--profile <name>`(별칭 `-p`)로 켠다. 이 플래그를 주면 `~/.codex/config.toml`을 먼저 읽고, 그 위에 `~/.codex/<name>.config.toml`을 덮어쓴다.

둘째, `[permissions.<name>]`은 파일 시스템과 네트워크 규칙 묶음을 정의하며 `default_permissions` 키로 활성화한다. 기본 제공되는 `:read-only`, `:workspace`, `:danger-full-access` 프리셋이 이 쪽 이름 공간에 있다.

## 2. 이름 붙인 프로필 예시

아래는 모델, 승인 정책, 샌드박스 모드를 재사용 가능한 설정 묶음으로 만든 예다.

```toml
# ~/.codex/strict.config.toml
model = "gpt-5.5"
model_reasoning_effort = "high"
approval_policy = "untrusted"
sandbox_mode = "read-only"
```

```toml
# ~/.codex/auto.config.toml
approval_policy = "never"
sandbox_mode = "workspace-write"
```

```bash
codex --profile strict "audit this PR for security issues"
codex -p auto "fix all lint warnings"
```

프로필은 각자 자기 `<name>.config.toml` 파일에 산다. `--profile`은 config.toml 안의 `[profiles.<name>]` 표를 읽지 않는다. 우선순위는 이렇다. 프로필 값은 사용자 수준 설정을 덮어쓰고, 프로필 값 자체는 명시한 CLI 플래그에 덮어쓰인다.

## 3. TUI 권한 선택 메뉴

대화형 TUI에는 세션 도중 권한을 바꾸는 단순화된 선택 메뉴가 있다. 메뉴에 보이는 이름은 새로운 모드가 아니다. 권한 프로필 하나에 기존 설정 키 두 개를 합친 표시용 프리셋이다. 그 두 키는 `approval_policy`와, 승인 질문에 누가 답할지를 정하는 `approvals_reviewer`다.

`approvals_reviewer`는 값을 두 개 받는다.

- `user`(기본값)는 모든 승인 질문을 사용자에게 보낸다.
- `auto_review`는 질문을 먼저 에이전트에게 보낸다. 에이전트가 그 행동이 위험해서 사용자에게 넘길 만한지 판단한다.

메뉴 세 항목이 실제 설정으로 어떻게 대응하는지는 아래와 같다.

| TUI 이름 | 권한 프로필 | approval_policy | approvals_reviewer |
|---|---|---|---|
| Ask for approval | `:workspace` | on-request | user |
| Approve for me | `:workspace` | on-request | auto_review |
| Full Access | 전체 접근(샌드박스 해제) | never | 해당 없음 |

"Ask for approval"과 "Approve for me"는 샌드박스와 `approval_policy`가 같다. 다른 것은 검토자뿐이다. "Approve for me"는 첫 판단을 에이전트에게 맡기며, 그래서 설명 문구가 잠재적으로 안전하지 않다고 감지된 행동에만 묻는다고 되어 있다. 메뉴의 현재 기본 동작을 config.toml로 똑같이 만들려면 다음과 같이 쓴다.

```toml
default_permissions = ":workspace"
approvals_reviewer = "auto_review"
```

메뉴는 상황에 따라 일부 프리셋을 숨긴다. 예를 들어 workspace-write 세션에서는 내부 프리셋 목록에 있어도 "Read Only" 항목이 보이지 않는다. 메뉴가 숨기는 설정이 필요하면 config.toml을 고치거나 `-c` 덮어쓰기를 쓴다.

## 4. 기본 제공 프로필

Codex CLI는 콜론으로 시작하는 기본 프로필 세 개를 제공한다.

- `:read-only`는 쓰기와 명령 실행이 없다. 리뷰와 탐색에 맞다.
- `:workspace`는 프로젝트 작업 공간 안에서 읽기와 쓰기, 명령 실행이 가능하고 네트워크는 기본으로 꺼져 있다. 보호 경로인 `.git/`, `.agents/`, `.codex/`는 계속 읽기 전용이다. 권장 기본값이다.
- `:danger-full-access`는 모든 제약을 푼다. 운영 환경에는 권장하지 않는다.

기본 제공 프로필은 `~/.codex/config.toml`의 `default_permissions` 키로 켠다. `--profile` 플래그로 켜는 것이 아니다. `--profile`은 사용자가 만든 `~/.codex/<name>.config.toml`을 설정 위에 덮을 뿐이다.

```toml
default_permissions = ":workspace"
```

한 번만 바꾸고 싶으면 범용 `-c` 설정 덮어쓰기로 키를 명령줄에 넘긴다.

```bash
codex -c default_permissions=':read-only' "audit this PR for security issues"
```

명시한 `-a`, `-s` 플래그는 프로필보다 우선하므로, 설정을 고치지 않고도 `-a never -s danger-full-access` 같은 일회성 실행은 언제든 가능하다.

## 5. 프로필 상속

프로필은 설정 계층을 조합하는 방식으로 상속을 지원한다. 플랫폼 팀이 시스템 계층에 제한적인 기반을 정의하고, 프로젝트 팀은 자기 서비스에 필요한 것만 얹어 확장한다.

```toml
# /etc/codex/config.toml (시스템 계층)
[permissions.secure-base]
description = "Restrictive baseline for hosted runners"
[permissions.secure-base.filesystem]
":workspace_roots"."." = "write"
":workspace_roots"."**/*.env" = "deny"
[permissions.secure-base.network]
enabled = true
[permissions.secure-base.network.domains]
"api.openai.com" = "allow"
"registry.npmjs.org" = "allow"
```

```toml
# .codex/config.toml (프로젝트 계층)
[permissions.payments]
extends = "secure-base"
[permissions.payments.network.domains]
"api.stripe.com" = "allow"
```

`payments` 프로필은 `secure-base`의 모든 규칙을 물려받고, 그 위에 Stripe 도메인만 더한다. `extends` 키가 계층형 권한 묶음을 합성하는 문서화된 방법이다. 시스템 계층 기반을 확장하는 프로젝트 프로필은 기반 규칙을 다시 적지 않아도 전부 받는다. 기반에서 `deny`로 선언한 규칙은 확장하는 프로필이 다시 허용으로 돌릴 수 없다. 그래서 상위 계층이 그 아래 모두에 대해 `.env` 접근을 잠글 수 있다. 앞의 샌드박스 문서에서는 네트워크가 켜짐과 꺼짐뿐이라고 했지만, 이 권한 프로필 층에서는 위 예처럼 `network.domains`로 도메인별 허용을 적을 수 있다.

## 6. 항목별 승인 설정

전부 막는 never 대신 항목별로 제어하고 싶은 파이프라인에는 granular 설정이 있다.

```toml
[approval_policy.granular]
sandbox_approval    = true
rules               = true
mcp_elicitations    = false
request_permissions = false
skill_approval      = true
```

각 키는 해당 항목이 실행을 멈추고 승인을 요청할 수 있는지를 켜고 끈다. 위 설정에서는 스킬과 규칙은 여전히 승인을 물을 수 있다. MCP 엘리시테이션(서버가 사용자에게 입력을 요청하는 일)과 권한 요청은 파이프라인을 막지 않고 처리된다.
