# 운영체제별 샌드박스

`sandbox_mode`는 이식 가능한 추상 설정이다. 같은 값을 써도 실제로 막아 주는 방식은 운영체제마다 다르다. 이 문서는 macOS, Linux, Windows에서 샌드박스가 어떻게 강제되는지, 그리고 어느 쪽이 더 단단한지를 정리한다. 요점은 커널 수준에서 강제되기 때문에 사용자 공간(user space)에서 도는 프로그램은 이를 뚫을 수 없다는 것이다.

---

## 1. macOS: Seatbelt

macOS에서 Codex CLI는 실행할 때 SBPL(Sandbox Profile Language) 스크립트를 만들어 `sandbox-exec`에 넘긴다. `sandbox-exec`는 Apple이 제공하는 커널 수준 샌드박스 기능이다. 강제가 커널의 시스템 호출 단계에서 일어나므로, Codex CLI 자신을 포함해 사용자 공간에서 돌아가는 어떤 것도 이를 우회할 수 없다.

## 2. Linux: bubblewrap과 seccomp

Linux 샌드박스는 두 단계로 이루어진다.

- 바깥 단계는 `bwrap`(bubblewrap)으로 파일 시스템의 네임스페이스를 분리한다. 시스템 경로는 읽기 전용으로 바인드 마운트하고, 쓰기는 설정된 루트에만 허용한다.
- 안쪽 단계는 `PR_SET_NO_NEW_PRIVS`와 `seccomp` 시스템 호출 필터를 적용한다. 권한 상승이나, 미리 정해 둔 허용 목록 밖의 시스템 호출을 막는다.

원문은 대부분의 위협 모델에서 Linux 샌드박스가 macOS보다 확연히 더 강하다고 평가한다. 네임스페이스 격리, 파일 접근 제어, 시스템 호출 필터링이 겹쳐 다층 방어(defence in depth)를 이루기 때문이다. 단단하게 굳힌 자동화 파이프라인에는 제대로 설정한 컨테이너 위의 Linux가 더 성숙한 선택이다.

## 3. Windows: 제한된 토큰과 ACL

Windows 샌드박스는 권한이 낮은 전용 사용자 계정과 Win32 보안 기능을 쓴다. 하위 모드는 두 가지다.

| 모드 | 방식 | 조건 |
|---|---|---|
| elevated(권장) | 전용 샌드박스 계정에 파일 시스템 ACL과 방화벽 규칙을 적용 | 한 번은 관리자 설정이 필요하다 |
| unelevated(대체 수단) | 현재 사용자로부터 만든 제한된 토큰(restricted token)을 사용 | 관리자 설정이 필요 없다 |

관리형 기업 배포에서는 elevated를 강하게 권장한다.

## 4. 한눈에 보기

| 운영체제 | 강제 수단 | 한 줄 평가 |
|---|---|---|
| macOS | Seatbelt(`sandbox-exec`, SBPL) | 커널 수준이라 사용자 공간에서 우회 불가 |
| Linux | `bwrap` + `PR_SET_NO_NEW_PRIVS` + `seccomp` | 다층 방어, 대부분의 위협 모델에서 macOS보다 강함 |
| Windows | 전용 저권한 계정 또는 제한된 토큰, ACL | elevated 모드를 권장 |
