# 다중 공급자 복원력과 모델 폐기 점검

깊게 집중해서 돌리는 에이전트 세션을 가장 조용히 망가뜨리는 것은 속도 제한(rate limit)이다. 복잡한 리팩터링을 40분쯤 진행했는데 HTTP 429가 떠서 세션이 멈추면, 프롬프트 캐시가 무효화되고 컨텍스트를 처음부터 다시 데워야 한다. 이런 일을 막으려면 의도적으로 구조를 짜 두어야 한다. 이 문서는 재시도 설정, 프로필 기반 전환, AI 게이트웨이 자동 전환, 그리고 모델 폐기(deprecation) 점검을 정리한다.

---

## 1. 내장 재시도와 백오프

런타임은 일시적인 속도 제한 오류를 지수 백오프(exponential backoff, 재시도 간격을 점점 늘리는 방식)로 자동 처리한다. 공급자별로 횟수를 조정할 수 있다.

```toml
[model_providers.openai]
request_max_retries = 4
stream_max_retries = 10
```

`request_max_retries`는 요청 재시도 횟수, `stream_max_retries`는 스트림 재시도 횟수다. 이 값을 넘는 장애는 더 위쪽 구조가 받아 줘야 한다.

## 2. 프로필로 공급자 바꾸기

상위 공급자마다 `~/.codex/<이름>.config.toml` 파일을 하나씩 만들어 두면, `--profile` 플래그 하나로 그 실행의 공급자를 고를 수 있다. 전체 배치는 그림 6-3에 나와 있다.

그림에서 사용자 세션은 먼저 Codex CLI(재시도와 백오프)를 지난다. 거기서 두 갈래로 나뉜다. 위쪽은 `--profile`로 사람이 직접 고르는 경로이고 OpenAI 직접(primary), Azure OpenAI(azure), Amazon Bedrock(bedrock) 셋 중 하나로 간다. 아래쪽은 AI 게이트웨이(LiteLLM, Bifrost)를 거치는 경로이고, 게이트웨이에서 세 공급자로 점선 화살표(auto-failover)가 뻗는다.
### 왜 진짜 이중화가 되는가

Azure와 Bedrock의 속도 제한은 각자 클라우드 계정 단위로 걸린다. Azure OpenAI 쿼터는 Azure 구독, 리전, 모델별로 정해지고, Amazon Bedrock 쿼터는 AWS 계정 단위다(원서 각주 1, 2: 마이크로소프트와 AWS 공식 문서). OpenAI 직접 호출에서 받은 429는 이 두 풀에서 쿼터를 빼 가지 않는다. 따라서 Azure나 Bedrock으로 프로필을 돌려 쓰면 이름만 다른 같은 쿼터가 아니라 실제로 독립된 여유분이 생긴다.

사람이나 스크립트가 실행 전에 대체 공급자를 고르는 방식은 이런 모양이다.

```bash
codex --profile azure "continue the refactor"
```

## 3. AI 게이트웨이 프록시

자동 전환이 필요하면 Codex CLI와 상위 공급자 사이에 AI 게이트웨이(LiteLLM, Bifrost 등)를 둔다.

```toml
[model_providers.gateway]
name = "AI Gateway (auto-failover)"
base_url = "http://localhost:4000"
env_key = "GATEWAY_API_KEY"
wire_api = "responses"
```

게이트웨이가 라우팅, 재시도, 장애 전환(failover)을 맡는다. 대가는 모든 요청에 붙는 지연이다. 같은 내부 네트워크에서는 보통 한 자릿수 밀리초이고, 광역망(WAN)을 건너면 더 늘어난다.

### 게이트웨이가 하는 일

Codex는 모든 모델 요청을 게이트웨이라는 엔드포인트 하나로만 보낸다. 그 요청을 다음에 어디로 보낼지는 게이트웨이가 정한다. Codex 입장에서는 Responses 호환 공급자 하나와 말하고 있을 뿐이다. 상위 목록, 상태 점검, 재시도 규칙, 모델 이름 매핑, 대체 순서는 모두 게이트웨이 소유다. 흔한 정책은 이렇다. OpenAI 직접을 먼저 시도하고, 일시적 실패는 몇 번 재시도하고, 오류가 속도 제한이나 타임아웃이나 일시적 5xx 응답이면 다음 시도를 Azure OpenAI나 Bedrock으로 보낸다.

### 프로필 전환과의 차이

프로필 전환은 실행을 시작하기 전에 사람이나 스크립트가 대체 공급자를 고른다. 게이트웨이 전환은 요청 경로 안에서 선택이 일어나고, Codex 설정은 그대로다.

```toml
model_provider = "gateway"
model = "gpt-5.5"
```

설정이 변하지 않는다는 점은 CI/CD와 긴 대화형 세션에서 유용하다. 호출하는 쪽이 지금 어느 상위 공급자가 건강한지 몰라도 된다. 정책도 한곳에 모인다. 팀은 라우팅 가중치를 조절하거나, 상태가 나쁜 공급자를 끄거나, 백업 계정을 추가할 때 개발자마다 `config.toml`을 고칠 필요가 없다.

### 자동 전환은 마법이 아니다

- 스트림이 이미 시작된 뒤 응답 중간에 실패하면 게이트웨이가 그 턴을 안전하게 다시 재생하지 못할 수 있다.
- 도구 호출을 만들어 내는, 같은 결과를 보장하지 못하는(비멱등) 요청을 다른 모델로 재시도하면 다른 계획이나 다른 도구 호출이 나올 수 있다.
- 위험이 큰 작업이라면 생성이 시작되기 전에 전환하는 쪽을 택하고, 깨끗한 재시도를 보장하지 못할 때는 게이트웨이가 닫힌 채 실패하도록(fail closed) 만든다.

### 전환 풀에서 맞춰야 할 것

같은 프롬프트가 어느 상위 공급자에서든 동작하려면 서로 충분히 호환되어야 한다. 다음 여섯 가지를 풀 안에서 일치시킨다.

1. 모델 능력과 컨텍스트 윈도
2. Responses API 호환성과 스트리밍 동작
3. 도구 호출과 구조화된 출력 지원
4. 안전 정책과 데이터 보존 요건
5. 인증, 쿼터, 청구 소유권
6. 어느 공급자가 각 요청을 처리했는지 설명할 수 있는 로깅 필드

### 전환을 일부러 시험하기

스테이징 게이트웨이에서 주 공급자의 429나 타임아웃을 일부러 일으켜, Codex가 백업 공급자에게서 정상 응답을 받는지 확인한다. 로그도 점검한다. 원래 요청, 실패한 상위 공급자, 대체 공급자, 최종 상태를 로그만으로 재구성할 수 있어야 한다.

## 4. 모델 폐기 점검

OpenAI는 주기적으로 오래된 모델을 폐기한다. 인증 방식에 따라 영향이 다르다.

1. ChatGPT 로그인으로 쓰는 사용자는 폐기가 적용되는 즉시 그 모델을 쓸 수 없다. Codex 모델 페이지에 해당 이름이 올라오고 현재 기본 모델로 갈아타라고 안내한다.
2. API 키 사용자는 대체로 더 오래 쓸 수 있다. 모델 페이지에는 ChatGPT 로그인에서 폐기된 모델 중 일부가 API에서는 계속 쓸 수 있을 수 있다고 적혀 있다. 그래서 ChatGPT 쪽에서 폐기된 모델에 고정해 둔 파이프라인도 OpenAI가 API에서 완전히 내릴 때까지는 돌아갈 수 있다.

둘 다 믿을 만한 보험은 아니다. ChatGPT 경로는 폐기가 닿는 순간 끊기고, API 경로는 끊기는 시점이 미뤄질 뿐이다. 그래서 설정을 정기적으로 점검한다. 원서가 제시한 명령은 다음과 같다.

```bash
grep -rn --include='*.toml' 'model = ' ~/.codex .codex
```

사용자 설정 폴더와 프로젝트의 `.codex` 폴더 안 TOML에서 `model = ` 줄을 찾아 낡은 모델 참조가 없는지 훑는 명령이다. CI/CD 파이프라인에서는 모델을 명시적으로 고정하고, 대체 동작에 기대지 말고 일정을 정해 의도적으로 갱신한다.

## 5. 정리

- 속도 제한 429는 세션을 멈추고 프롬프트 캐시를 날리므로 미리 구조로 대비한다.
- `request_max_retries`와 `stream_max_retries`로 공급자별 재시도를 조절한다.
- Azure와 Bedrock은 쿼터 풀이 OpenAI 직접과 독립이라 프로필 전환이 진짜 이중화가 된다.
- AI 게이트웨이는 자동 전환을 주지만 지연이 늘고, 중간 실패나 다른 모델 재시도의 위험이 남는다. 전환 풀의 호환성과 로그를 챙기고 시험해 본다.
- 모델 폐기는 인증 방식에 따라 시점이 다르다. 정기적으로 grep으로 점검하고 CI/CD는 모델을 고정한다.
