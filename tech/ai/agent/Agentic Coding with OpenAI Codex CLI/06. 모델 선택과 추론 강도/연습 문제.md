# 연습 문제

6장 끝에는 직접 설정을 만들고 비교해 보는 실습 세 문제가 있다. 이 문서는 각 문제의 취지를 풀어 쓰고, 어떻게 접근하면 좋을지 짧은 방향을 덧붙인다.

---

## 1. 연습 6-1. 세 가지 프로필로 같은 작업 비교하기

세 개의 프로필을 만든다. daily는 범용 모델에 medium 강도, deep은 플래그십 모델에 high 강도와 읽기 전용 샌드박스, quick은 빠른 모델에 low 강도다. 같은 리팩터링 작업을 세 프로필로 각각 실행하고, 결과물의 품질, 토큰 사용량, 걸린 시간을 비교한다.

풀이 방향: `~/.codex/daily.config.toml`, `deep.config.toml`, `quick.config.toml` 세 파일을 만들고 `codex -p <이름>`으로 같은 프롬프트를 돌린다. 조건을 공정하게 맞추려면 매번 같은 브랜치 상태에서 시작한다. deep은 읽기 전용이라 파일을 고치지 못하므로, 코드를 직접 바꾸게 하기보다 제안한 변경 계획의 품질을 비교하는 쪽이 맞다.

## 2. 연습 6-2. 조율자-작업자 서브에이전트 구성

조율자는 범용 모델, 작업자는 빠른 모델로 하는 다중 모델 서브에이전트 워크플로를 구성한다. 여러 파일을 고쳐야 하는 작업을 시키고, 역할별 토큰 소비량을 관찰한다.

풀이 방향: `agents.<이름>.config_file`로 조율자와 작업자 설정 파일을 각각 가리키고, 파일 안에 서로 다른 `model`과 `model_reasoning_effort`를 넣는다. 작업 후 조율자 쪽 토큰은 계획과 통합에, 작업자 쪽 토큰은 개별 수정에 얼마나 쓰였는지 비교해 보면 역할 분담의 효과가 드러난다. 전체 서브에이전트 설정은 11장에서 다룬다.

## 3. 연습 6-3. 로컬 모델 프로필과 한계점 찾기

Ollama 같은 로컬 모델 공급자를 설정하고 로컬 프로필을 정의한다. 범위가 정해진 작업(예: TODO 목록 뽑기, 파일 하나 포매팅)을 로컬 프로필과 클라우드 프로필에서 모두 돌린다. 그러고 나서 로컬 모델의 결과 품질이 부족해지는 작업 복잡도의 경계가 어디인지 찾아낸다.

풀이 방향: `oss_provider = "ollama"`와 `--oss`, 또는 `[model_providers.local]`과 `model_catalog_json`으로 로컬 프로필을 만든다. `model_context_window`를 서버 설정과 맞추는 것을 잊지 않는다. 작업을 단순한 것에서 점점 복잡한 것으로(한 파일, 여러 파일, 설계 판단이 들어가는 일) 올려 가며 같은 프롬프트로 비교하면 경계를 찾기 쉽다.
