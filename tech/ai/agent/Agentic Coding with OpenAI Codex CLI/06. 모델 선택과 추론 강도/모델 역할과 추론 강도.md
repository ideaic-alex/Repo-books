# 모델 역할과 추론 강도

Codex CLI에서 승인 모드와 샌드박스로 에이전트가 할 수 있는 일의 경계를 정했다면, 그다음에 정할 것은 두 가지다. 어떤 모델이 일을 맡을지, 그리고 그 모델이 답하기 전에 얼마나 깊이 생각할지다. 이 두 설정이 작업 품질과 한 번 실행하는 데 드는 비용을 좌우한다.

이 문서는 모델을 이름이 아니라 역할로 나누어 보는 방법과, 추론 강도(reasoning effort) 다섯 단계를 설정하고 바꾸는 방법을 정리한다.

---

## 1. 왜 모델과 추론 강도를 따로 봐야 하나

모델 선택은 쓸 수 있는 능력의 천장을 정한다. 추론 강도는 요청 하나하나에서 모델이 그 천장에 얼마나 가까이 가서 일할지를 정한다. 둘은 서로 독립된 손잡이다.

둘 중 하나라도 잘못 잡으면 사용 한도(쿼터)가 샌다. 단순한 조회 작업에 가장 비싼 대형 모델을 쓰면 답을 괜히 복잡하게 만든다. 반대로 어려운 설계 문제에 가벼운 모델을 쓰면 얕은 결과가 나오고, 그 비용은 나중에 몰래 더 크게 돌아온다.

## 2. 모델 이름 대신 역할로 생각하기

OpenAI는 자기 일정에 맞춰 새 모델을 내고 옛 모델을 없앤다. 원서가 쓰던 시점의 예로 gpt-5.5, gpt-5.4-mini, gpt-5.3-codex-spark 같은 이름이 있었지만, 이런 이름은 책이 따라갈 수 있는 속도보다 빨리 바뀐다. 그래서 이 장은 특정 이름에 기대지 않고 역할 단위로 모델을 분류한다. 지금 그 역할을 맡은 모델이 무엇인지만 그때그때 확인하면 된다.

| 역할 | 특징 | 주로 쓰는 곳 |
|---|---|---|
| 플래그십(flagship) | 컨텍스트 윈도가 가장 크고 능력이 가장 높지만 비용도 가장 높다 | 리서치, 복잡한 추론, 최고 성능이 필요한 작업 |
| 범용(general-purpose) | 능력과 비용의 균형이 좋고 API 키로 쓸 수 있다 | 매일 쓰는 기본 모델, CI/CD, 조율(오케스트레이션), 일반 개발 |
| 빠른 모델 / 미니(fast / mini) | 컨텍스트가 작고 비용이 가장 낮으며 처리 속도가 가장 빠르다 | 서브에이전트 작업자, 일괄 작업, 쿼터를 아껴야 하는 세션 |
| 코딩 특화(coding-specialist) | 코드 생성에 맞춰 다듬었고 처리량이 높다 | 대량의 터미널 코딩, 보안 감사, 오래 이어지는 세션 |

현재 역할과 모델 이름의 대응은 OpenAI 문서(developers.openai.com/codex/models)에서 확인한다. `codex --help` 출력에도 쓸 수 있는 모델 목록이 나온다.

### 모델을 지정하는 세 가지 방법

- 실행할 때 `--model` 플래그(줄여서 `-m`)로 지정한다.
- `config.toml`의 `model` 키에 적어 기본값으로 둔다.
- 대화형 세션 안에서 `/model` 슬래시 명령으로 바꾼다.

```bash
codex -m gpt-5.5 "refactor the authentication module"
```

```toml
# ~/.codex/config.toml
model = "gpt-5.5"
```

### 능력과 비용이 꼭 비례하지는 않는다

빠른/미니 모델은 범용 모델의 약한 버전이 아니다. 다른 종류의 일에 맞게 만든 별개의 모델이다. 범위가 정해진 하위 작업, 파일 단위 분석, 코드 탐색 같은 일에서는 비용의 일부만 들이고도 충분한 품질을 낸다. 이 모델을 그냥 "싸지만 못한 모델"로 보면 설계 의도를 놓치게 된다.

## 3. 추론 강도

추론 강도는 모델이 답하기 전에 얼마나 깊이 생각하는지를 정한다. 단계는 다섯 개이고, 3장에서 프롬프트 설계를 다룰 때 본 표와 같은 내용이다.

| 단계 | 동작 | 잘 맞는 일 |
|---|---|---|
| minimal | 사고 과정(chain-of-thought)을 거의 쓰지 않는다 | 포매터, 일괄 이름 바꾸기, CI 템플릿 생성 같은 단순 변환 |
| low | 사고 과정을 최소로 쓰고 빠르게 답한다 | 간단한 수정, 이름 바꾸기, 조회 |
| medium | 균형 잡힌 깊이이고 기본값이다 | 일반 개발, 중간 정도 복잡도 |
| high | 더 길게 생각해서 느리지만 꼼꼼하다 | 설계 결정, 복잡한 디버깅, 보안 감사 |
| xhigh | 추론 예산을 최대로 쓴다 | 위험이 큰 설계 결정, 보안 리뷰, 어려운 근본 원인 분석 |

### 설정하는 방법

추론 강도는 `config.toml`에 기본값으로 적거나, 실행할 때 `-c` 옵션으로 덮어쓰거나, 세션 중에 바꿀 수 있다.

```toml
model_reasoning_effort = "medium"
```

```bash
codex -c model_reasoning_effort=high "design the database schema for the new billing module"
```

### 세션 중 빠른 조절 단축키

대화형 세션을 껐다 켜지 않고도 추론 강도를 바꿀 수 있다.

- `Alt+,` : 추론 강도를 한 단계 낮춘다(예: medium에서 low).
- `Alt+.` : 추론 강도를 한 단계 높인다(예: medium에서 high).

코드 구조를 훑어보는 탐색 단계에서는 낮게 두고, 복잡한 구현 결정을 내릴 때는 높였다가 다시 낮추는 식으로 쓴다. 바꾼 값은 다음 모델 호출부터 적용된다.

## 4. 정리

- 모델은 능력의 천장을, 추론 강도는 그 천장에 얼마나 다가갈지를 정한다.
- 이름은 자주 바뀌므로 플래그십, 범용, 빠른/미니, 코딩 특화 네 가지 역할로 기억한다.
- 빠른/미니 모델은 싸구려 버전이 아니라 범위가 정해진 작업에 맞춘 다른 모델이다.
- 추론 강도는 `config.toml`, `-c` 옵션, `Alt+,` / `Alt+.` 단축키 세 곳에서 조절한다.
