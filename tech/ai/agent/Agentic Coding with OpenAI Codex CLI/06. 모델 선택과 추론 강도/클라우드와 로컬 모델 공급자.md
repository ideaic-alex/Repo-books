# 클라우드와 로컬 모델 공급자

Codex CLI는 OpenAI 모델만 쓰도록 묶여 있지 않다. `config.toml`의 `[model_providers]` 항목으로 Responses API 규약에 맞는 공급자라면 직접 등록해서 쓸 수 있다. 이 문서는 Azure, AWS, GCP 같은 클라우드 공급자 설정과, Ollama 같은 로컬 추론 서버를 연결하는 방법을 정리한다.

---

## 1. 클라우드 공급자

| 클라우드 | 연결 방식 | 쓰임새 |
|---|---|---|
| Azure | Azure OpenAI 모델 공급자 | Azure 계약이 있는 기업 팀 |
| AWS | Amazon Bedrock 기본 제공 공급자 | AWS를 우선하는 조직 |
| GCP | 직접 정의하는 커스텀 공급자(Vertex AI) | Google Cloud 환경 |

Azure를 예로 든 설정은 이렇다. 공급자 이름을 `model_provider`에 적고, 같은 이름의 `[model_providers.<이름>]` 표에 접속 정보를 넣는다.

```toml
model_provider = "azure-openai"

[model_providers.azure-openai]
name = "Azure OpenAI"
base_url = "https://your-org.openai.azure.com"
env_key = "AZURE_OPENAI_API_KEY"
wire_api = "responses"
```

각 키의 뜻은 다음과 같다. `base_url`은 접속할 주소이고, `env_key`는 API 키가 들어 있는 환경 변수 이름이다(키 자체를 파일에 쓰지 않는다). `wire_api = "responses"`는 이 공급자가 Responses API 규약으로 통신한다는 선언이다.

## 2. 로컬 모델 공급자

Ollama, vLLM, llama.cpp 같은 로컬 추론 서버도 같은 틀로 모델 공급처가 될 수 있다. 로컬 모델은 지연 시간과 비용 면의 이점이 능력 격차보다 클 때, 즉 범위가 정해진 기계적인 작업에 가장 잘 맞는다.

```toml
[model_providers.local]
name = "Local Ollama"
base_url = "http://localhost:11434"
wire_api = "responses"
```

### --oss 단축 플래그

Ollama나 LM Studio를 쓸 때는 `[model_providers.*]` 블록을 직접 만들지 않아도 `--oss` 플래그가 지름길 역할을 한다. 이 플래그는 실행을 로컬 오픈소스 백엔드로 보내라는 뜻이다. 다만 어느 백엔드인지는 알려 줘야 하므로 `config.toml`에 `oss_provider`를 한 번 지정해 둔다.

```toml
oss_provider = "ollama"   # 또는 "lmstudio"
```

이렇게 해 두면 `codex --oss "..."`가 Ollama로 연결된다. 한 번만 다른 로컬 백엔드를 쓰고 싶으면 `--local-provider lmstudio`(또는 `ollama`)를 붙인다.

## 3. 로컬 프로필과 모델 카탈로그

로컬 환경을 더 세밀하게 제어하려면 `[model_providers.*]`를 계속 쓴다. 모델 슬러그(slug, 모델 식별 이름)가 Codex 내장 카탈로그에 없으면, `model_catalog_json` 파일을 추가해 Codex가 그 모델을 어떻게 보여 주고 다룰지 알려 줘야 한다.

```toml
# ~/.codex/local.config.toml
model = "qwen3:32b"
model_provider = "local"
model_context_window = 131072
model_catalog_json = "~/.codex/models/local-models.json"
```

### model_context_window를 맞추는 이유

`model_context_window`는 로컬 서버에 실제로 설정된 컨텍스트 윈도 크기와 같아야 한다. 너무 크게 적으면 Codex가 백엔드가 받을 수 있는 양보다 많은 컨텍스트를 보내 버릴 수 있다. 너무 작게 적으면 Codex가 필요 이상으로 일찍 컨텍스트를 압축(compact)한다.

원서의 예로, Ollama는 qwen3:32b를 기본 40K 윈도로 서빙한다. 모델의 최대치인 128K(131072 토큰)까지 늘리려면 Ollama Modelfile에서 컨텍스트를 확장해야 하고, 그만큼을 받쳐 줄 VRAM도 있어야 한다.

### 카탈로그 JSON 형식

카탈로그 파일은 내장 카탈로그와 같은 스키마를 쓴다. 최소한 배포한 모델 이름과 맞는 `slug`, 사람이 읽을 `display_name`, 짧은 `description`, 토큰 단위의 `context_window`, Codex가 제시할 추론 강도 목록이 필요하다.

```json
{
  "models": [
    {
      "slug": "qwen3:32b",
      "display_name": "Qwen3 32B",
      "description": "Local Qwen3 32B served via Ollama",
      "context_window": 131072,
      "supported_reasoning_levels": ["medium"],
      "default_reasoning_level": "medium"
    }
  ]
}
```

세 필드는 따로 짚어 볼 가치가 있다.

- `slug`는 상위 공급자가 기대하는 이름과 정확히 같아야 한다. qwen3:32b는 `ollama pull`과 `ollama run`이 받는 이름 그대로여서 Codex가 그대로 넘긴다.
- `context_window`는 로컬 배포가 실제로 서빙하는 윈도 크기(토큰)여야 한다.
- `supported_reasoning_levels`는 Codex가 선택 목록에 보여 줄 추론 강도다. Qwen3는 프롬프트의 `/think`와 `/no_think`, 또는 `enable_thinking=True`로 쓰는 켜고 끄는 방식의 생각 모드뿐이고 단계별 강도가 없다. 그래서 `medium` 하나만 적으면 Codex가 이 모델에서는 `Alt+,` / `Alt+.` 조절을 숨긴다. 반면 GPT-5 계열이라면 minimal부터 xhigh까지 다섯 단계를 모두 적는다.

도구 지원 여부, 노출 여부, 요금제별 사용 가능 여부 같은 추가 필드는 Codex 소스의 실제 카탈로그를 참고하라고 원서는 안내한다.

## 4. 활용 방식

원서의 제안은 탐색용 로컬 프로필과 구현용 클라우드 프로필을 따로 정의하고 `--profile`로 오가는 것이다. 탐색처럼 단순하고 양이 많은 작업은 로컬에서 싸게 처리하고, 품질이 중요한 구현은 클라우드 모델로 돌린다.

## 5. 정리

- `model_provider`와 `[model_providers.<이름>]` 표로 Azure, Bedrock, Vertex AI 같은 클라우드 공급자를 연결한다.
- 로컬 추론 서버도 같은 구조로 연결하며, Ollama나 LM Studio는 `--oss`와 `oss_provider`로 간단히 쓸 수 있다.
- 내장 카탈로그에 없는 모델은 `model_catalog_json`으로 등록하고, `model_context_window`는 서버의 실제 윈도와 맞춘다.
- `supported_reasoning_levels`에 한 단계만 적으면 `Alt+,` / `Alt+.` 조절이 사라진다.
