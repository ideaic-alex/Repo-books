# 조율의 출발점, 랄프 루프

11장에서 서브에이전트의 기본 부품을 익혔다. 내장 에이전트, TOML로 만드는 사용자 정의 에이전트, `spawn_agents_on_csv` 팬아웃(CSV 한 줄을 일꾼 하나에게 맡기는 병렬 처리), `[agents]` 세션 한도 같은 것들이다. 이 부품이 있으면 전문화된 스레드 하나를 띄우거나 CSV 수백 줄을 일꾼들에게 나눠 줄 수 있다. 그런데 이 부품들을 어떻게 엮어 여러 단계 파이프라인을 만드는지, 바깥에서 Codex CLI 세션을 어떻게 몰고 가는지, 에이전트에게 장기 목표를 쥐여 주고 여러 턴에 걸쳐 끝까지 가게 하려면 어떻게 하는지는 아직 다루지 않았다.

12장은 그 "엮는 방법"을 다룬다. 현장에서 반복해서 나타나는 네 가지 조율 패턴(순차 게이트 체인, 웨이브 기반 혼합, 교차 모델 리뷰 루프, 반복 수리 루프), 대화를 갈라 개발자를 가벼운 감독자로 만들어 주는 `/fork`와 `/side`, 어떤 패턴이든 감싸는 지속 목표 `/goal`, 외부 스크립트가 세션을 몰게 해 주는 `codex remote-control`, 그리고 다단계 결과를 조용히 망가뜨리는 안티패턴을 차례로 설명한다. 이 문서는 그중 출발점이 되는 관점과 랄프 루프를 정리한다.

---

## 1. 이 장에서 할 수 있게 되는 것

원문이 제시한 학습 목표는 일곱 가지다.

1. 작업의 의존 구조와 품질 요구에 맞춰 네 패턴 중 하나를 고른다.
2. 부모 에이전트가 서브에이전트를 조율하고, 넘기는 지점마다 `output_schema`로 검증하는 게이트 파이프라인을 짠다.
3. `codex exec -m <model> -s read-only --output-schema`로 교차 모델 리뷰 루프를 만든다.
4. JSON으로 이어진 `codex exec` 호출 세 개로 반복 수리 루프를 구현한다.
5. `/fork`, `/side`, `/btw`로 병렬 작업 흐름을 감독자처럼 조율한다.
6. 토큰 예산과 감사(audit) 기반 완료 확인을 갖춘 `/goal` 목표 안에 어떤 패턴이든 넣는다.
7. 게이트 없는 넘김, 집계 없는 팬아웃, 끝이 없는 반복, 쓰기 권한을 가진 리뷰어 같은 안티패턴을 알아본다.

## 2. 새 부품이 아니라 조합이다

11장은 세 층의 풍경으로 끝났다. 프로세스 안의 서브에이전트, 워크트리를 가로지르는 로컬 셸 팬아웃(13장), 그리고 Codex Cloud Tasks다. 12장은 네 번째 층을 더하지 않는다. 대신 층과 층 사이의 "연결 조직"을 다룬다.

- 파이프라인의 각 단계가 결과를 어떻게 넘기는가
- 리뷰어가 빌더와 의견이 다를 때 빌더가 어떻게 반응하는가
- 긴 목표가 컨텍스트 압축(compaction)을 어떻게 견디는가
- 외부 스크립트가 돌고 있는 세션을 어떻게 조종하는가

쓰는 부품은 이미 아는 것들이다. 이 장의 주제는 그 부품들이 서로 어떻게 맞물리는가이다. 여러 에이전트를 나누어 맡기고 조율하는 일(오케스트레이션)은 새 기능이 아니라 설계 습관이라는 뜻이다.

## 3. 랄프 루프: 모든 것의 출발점

네 패턴을 소개하기 전에, 이 패턴들이 갈라져 나온 커뮤니티 패턴부터 보자. Geoffrey Huntley가 2025년 7월에 "랄프 루프(Ralph loop)"라는 이름을 붙였다. 심슨 가족의 랄프 위검에서 따온 이름이다. 단순하고 고집스러운 행동으로 뜻밖의 결과를 만들어 낸다는 뜻을 담았다.

패턴의 모양은 이름처럼 단순하다. 에이전트 호출을 `while` 루프로 감싸고, 무언가가 멈출 때까지 같은 작업에 같은 프롬프트를 계속 다시 넣는다. Huntley의 원래 한 줄을 Codex CLI로 옮기면 이렇다.

```bash
while :; do cat PROMPT.md | codex exec - ; done
```

Huntley의 관점에서 LLM은 한 번에 한 가지 일만 하는 단일 작업 처리기다. 사람은 명세, 계획 파일, 표준 라이브러리, `PROMPT.md` 같은 구조적 울타리를 마련하고, 모델은 그 안에서 우선순위를 알아서 고른다. 그는 이 방식을 "예측 불가능한 세상에서 결정적으로 나쁘다"고 표현했다. 실패 양상이 예측 가능하니 그에 맞춰 프롬프트를 조율할 수 있다는 뜻이고, 성공은 "결국엔 수렴할 것이라는 믿음"에 기댄다고 했다.

작고 경계가 분명한 수렴 작업에는 실제로 잘 통하고 쓸모도 있다. 한 턴을 넘겨서 에이전트가 계속 시도하게 만들어야 할 때 대부분의 개발자가 처음 떠올리는 방법이기도 하다.

### 3.1 랄프 루프의 세 가지 약점

작업이 어려워질수록 다음 세 가지 약점이 겹쳐서 커진다.

| 약점 | 무슨 일이 생기는가 |
|---|---|
| 성공 판정과 작업이 한 몸 | 에이전트가 무엇이 "끝"인지 스스로 정하고 루프는 그 말을 믿는다. |
| 감사 기록이 없음 | 최종 diff는 보이지만 각 단계에서 왜 그렇게 했는지는 남지 않는다. |
| 한 모델이 모든 단계를 처리 | 싼 모델로도 잡을 문제를 찾으려고 최상위 모델 요금을 내고, 깊은 추론이 필요한 수정에 오히려 싼 요금을 쓰는 식의 낭비가 생긴다. |

### 3.2 네 패턴은 그 대안이다

이 장의 네 패턴은 위 약점 중 하나 이상을 해결하려고 설계한 대안이다. 순수한 루프보다 구조가 많고, 그 구조의 대가로 감사 가능성, 복구 가능성, 비용에 맞춘 모델 배정을 얻는다. 구조가 오히려 부담일 만큼 작은 작업에는 랄프 루프가 여전히 맞는 도구다. 그보다 큰 작업은 네 패턴 중 어딘가에 속한다.
