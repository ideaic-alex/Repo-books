# 패턴 1. 순차 게이트 체인

가장 단순한 구조는 사슬(체인)이다. 단계 A의 출력이 단계 B의 입력이 되고, B의 출력이 C로 이어진다. 각 단계에는 위쪽 생산자가 하나, 아래쪽 소비자가 하나 있고, 마지막 단계가 최종 산출물을 내면 끝난다. 이 문서는 사슬의 각 연결 지점에 검증을 끼워 넣는 "게이트 체인"이 왜 필요한지, 그리고 Codex CLI에서 어떻게 표현하는지 설명한다.

---

## 1. 게이트 없는 사슬이 위험한 이유

서브에이전트는 미묘한 방식으로 실패한다. 요약기는 원본이 바이너리면 빈 문자열을 돌려준다. 분류기는 약속한 어휘 밖의 라벨을 내놓는다. 번역기는 입력 언어를 알아보지 못하면 원문을 그대로 돌려준다. 이런 결과를 확인 없이 다음 단계로 넘기면 실패가 아래로 계속 번져서, 마지막 산출물이 틀렸을 때는 사슬 전체를 다시 돌려 보지 않고는 원인을 찾기 어렵다.

게이트 체인은 모든 넘김 지점에 검증 단계를 넣는다. 이 게이트는 또 다른 LLM 호출이 아니다. 위쪽 출력이 아래로 흐르기 전에 거치는 결정적(deterministic) 검사다. Codex CLI에서 가장 싼 게이트는 위쪽 단계에 `output_schema`를 거는 것이다(11장). 일꾼의 구조화된 출력이 스키마를 통과하지 못하면, 런타임은 깨진 산출물을 만들지 않고 그 행을 실패로 기록한다.

## 2. 예시: 릴리스 브랜치 커밋으로 변경 이력 만들기

릴리스 브랜치의 원시 커밋을 공개할 수 있는 changelog로 바꾸는 파이프라인을 생각해 보자. 단계는 셋이다.

1. 분류(Classify): 팬아웃으로 브랜치의 모든 커밋을 장(chapter)과 수정 종류별로 분류해 `commit-review.csv`에 쓴다.
2. 그룹(Group): 부모가 결과 CSV를 읽어 성공한 행만 장별로 나누고, 장마다 한 행인 `chapter-summaries.csv`를 만든다.
3. 작성(Compose): 일꾼 에이전트가 묶인 요약을 받아 Markdown changelog 초안을 쓴다.

1단계와 2단계 사이의 게이트는 팬아웃에 선언한 `output_schema`다. `result_json`이 스키마에 맞지 않는 행은 다음 단계로 넘어가지 않고 실패로 기록된다. 2단계와 3단계 사이의 게이트는 부모가 자연어로 수행하는 구조 검사다. "요약을 작성기에 넘기기 전에 모든 장에 불릿이 최소 하나는 있는지 확인하라" 같은 지시다.

## 3. 부모에게는 번호 붙은 계획으로 전달한다

Codex CLI의 부모 에이전트는 조건 로직을 산문으로 잘 처리한다. 단, 각 단계가 어떤 모양의 출력을 내야 하는지를 분명히 적어야 한다. 원문의 지시 예시는 다음과 같다.

```text
Stage 1: spawn_agents_on_csv fan-out over commits.csv with output_schema
(sha, chapter, edit_kind, note) writing to commit-review.csv.
Concurrency 3, timeout 120 seconds.
Stage 2: read commit-review.csv, drop any row whose status is not
completed, group by chapter, write chapter-summaries.csv with one row
per chapter and a bullets column. Fail the pipeline if any expected
chapter has zero rows after grouping.
Stage 3: spawn a worker against chapter-summaries.csv to write a
Markdown changelog draft. Save to CHANGELOG-draft.md.
```

핵심은 세 가지다. 1단계는 동시성 3, 타임아웃 120초로 한도를 명시했다. 2단계는 `completed`가 아닌 행을 버리고, 기대한 장이 비면 파이프라인을 실패시킨다. 3단계는 정리된 CSV만 입력으로 받는다.

*그림 12.1. commits.csv가 분류 단계를 거쳐 스키마 게이트를 지나고, 그룹 단계를 거쳐 구조 게이트를 지나, 작성 단계를 거쳐 CHANGELOG-draft.md가 된다. 스키마를 어긴 행은 실패로 기록되어 빠지고, 구조 게이트에서 막히면 파이프라인 전체가 멈춘다.*

## 4. 이 구조가 주는 이점

- 조합하기 쉽다. 단계마다 역할이 분명하다.
- 감사할 수 있다. 각 단계의 중간 파일이 디스크에 남는다.
- 복구할 수 있다. 3단계가 실패해도 1, 2단계를 다시 돌릴 필요가 없다.

## 5. 언제 쓰고, 무엇을 감수하는가

단계 N이 단계 N-1의 검증 가능한 산출물 없이는 진짜로 시작할 수 없을 때 순차 체인이 맞다. 대가는 지연 시간이다. 전체 소요 시간이 단계별 지연의 합이 되고, 사슬 안에서는 병렬성이 없다. 다만 위 예시의 1단계처럼 한 단계 자체가 팬아웃일 수는 있다.

게이트는 표현할 수 있는 가장 엄격한 것이 가장 싸다. JSON을 내는 단계라면 `output_schema` 한 줄로 모든 모양 오류를 공짜로 잡는다. "모든 장에 불릿이 있는지 확인하라" 같은 자연어 단언은 내가 통제할 수 없는 단계를 데이터가 지나갈 때의 차선책이다.
