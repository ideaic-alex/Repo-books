# 패턴 3. 교차 모델 리뷰 루프

앞의 두 패턴은 모든 단계가 같은 모델을 쓴다고 가정했다. 실무에서 품질이 가장 크게 오르는 지점은 빌더(만드는 쪽)와 리뷰어(검토하는 쪽)에 서로 다른 모델을 배정하는 것이다. 이 문서는 그 이유와 셸 스크립트로 구성하는 방법, 그리고 반드시 피해야 할 함정을 정리한다.

---

## 1. 왜 다른 모델을 비평자로 앉히는가

모델이 자기 출력을 검토하면 아첨 편향(sycophancy bias)이 생긴다. 버그를 만든 추론 지름길이 리뷰 때도 똑같이 작동해서 그 버그를 합리화한다. 구조적으로 다른 모델은 학습 데이터, 사각지대, 판단이 독립적이다. 둘 다 같은 문제를 지적하면 확신이 높다. 한쪽만 지적하면 그 의견 불일치 자체가 신호가 된다.

Codex CLI는 플러그인 없이도 이 구성을 짤 수 있게 해 준다. `codex exec -m <model> -s read-only --output-schema <reviewer-schema>` 한 줄이 어떤 산출물에든 일회성, 샌드박스, 구조화 출력으로 리뷰를 돌린다. 오케스트레이터(부모 에이전트나 셸 스크립트)가 리뷰어의 지적을 빌더에게 되먹이고, 반복 횟수에 상한을 두고, 끝낸다.

## 2. 셸로 짠 최소 리뷰 루프

원문의 `cross-review.sh`는 모델과 라운드 수를 변수로 잡고 루프를 돈다. 핵심은 리뷰어 호출과 빌더 호출 두 개다.

```bash
MAX_ROUNDS=3
BUILDER_MODEL=gpt-5.5
REVIEWER_MODEL=gpt-5.4
for round in $(seq 1 "$MAX_ROUNDS"); do
  codex exec -m "$REVIEWER_MODEL" -s read-only \
    --output-schema reviewer-schema.json \
    -o "review-$round.json" \
    "Review $ARTEFACT. Return findings per schema."
  verdict=$(jq -r '.verdict' "review-$round.json")
  [ "$verdict" = "PASS" ] && exit 0
```

리뷰 결과가 `PASS`가 아니면 빌더를 호출한다.

```bash
  codex exec -m "$BUILDER_MODEL" -s workspace-write \
    "Address findings in review-$round.json and update $ARTEFACT."
done
echo "Failed to converge after $MAX_ROUNDS rounds. Escalate to human review."
exit 1
```

원문 스크립트는 `PASS`일 때 "Converged after N round(s)"를 출력하고 `exit 0`으로 끝낸다. 라운드를 모두 쓰고도 수렴하지 못하면 사람 리뷰로 넘기라는 메시지와 함께 `exit 1`로 종료한다. 반복 상태는 스크립트가 쥐고 있다. Codex CLI는 그 상태를 들고 있지 않기 때문이다.

리뷰어는 `-s read-only`, 빌더는 `-s workspace-write`로 샌드박스를 다르게 준 점을 눈여겨보자. 리뷰어에게는 쓰기 권한이 아예 없다.

*그림 12.3. 산출물과 reviewer-schema.json에서 시작한다. 읽기 전용 리뷰어가 verdict를 내고, PASS면 수렴하며 종료한다. CONCERNS면 라운드 수가 상한 미만인지 확인해, 아니면 사람 리뷰로 올리고, 맞으면 지적 사항을 빌더에게 넘긴다. 빌더가 산출물을 고치면 다시 리뷰어로 돌아간다.*

## 3. 함정: 재진입(re-entrancy)

재진입이 가장 큰 함정이다. 리뷰어가 끝날 때마다 또 다른 리뷰가 시작되도록 걸려 있으면 루프는 끝나지 않는다. 반복 상태는 오케스트레이터가 가져야 한다. 카운터, `--max-rounds` 플래그, `state.json` 파일 같은 것이다. Codex CLI는 임의의 오케스트레이터 스크립트에 대한 재진입 방지 장치를 기본 제공하지 않는다. 그 가드는 직접 써야 한다.

## 4. 리뷰어의 output_schema가 수렴을 만든다

리뷰어가 산문으로 "괜찮아 보이지만 이런 것도 고려해 보세요"라고 답하면 빌더가 손댈 구체적인 대상이 없다. 반대로 타입이 있는 지적의 정렬된 목록을 내놓으면 빌더는 우선순위가 매겨진 작업 목록을 받는다. 원문의 예는 이렇다. `severity: high, file: src/auth.py, line: 47, issue: token is logged before being hashed`. 이러면 라운드마다 구체적 지적을 처리하게 되고, 정의되지 않은 기준을 더듬어 가는 일이 없어진다.

## 5. 언제 쓰고 언제 건너뛰는가

처리량보다 독립적인 판단이 중요한 고위험 산출물에 쓴다. 보안에 민감한 코드, 공개 API 변경, 데이터베이스 마이그레이션처럼 배포된 버그의 비용이 에이전트 시간 5분 더 쓰는 비용보다 큰 경우다. 반대로 린트나 타입 검사처럼 값싸고 결정적인 검증이 가능한 산출물에는 건너뛴다. 그런 검사가 이미 독립적인 판단 역할을 하기 때문이다.
