# 요약

12장의 핵심을 여덟 가지로 간추린 문서다. 각 항목은 앞 문서들에서 자세히 설명한 내용을 다시 모은 것이다. 이 장의 결론은 새 기능이 아니라 규율이라는 점이다. 항상 게이트를 두고, 항상 상한을 걸고, 항상 격리하고, 누가 무엇을 결정했는지 항상 기록한다.

---

## 1. 여덟 가지 요점

1. 네 가지 조율 패턴. 순차 게이트 체인은 넘김 지점마다 검증 게이트를 둔 선형 파이프라인이다. 웨이브 기반 혼합은 의존하는 작업을 병렬 가능한 웨이브로 묶고 웨이브 경계를 품질 게이트로 쓴다. 교차 모델 리뷰 루프는 구조적으로 다른 모델을 비평자 자리에 앉혀 구조화된 지적을 빌더에게 되먹인다. 반복 수리 루프는 검토, 수리, 검증을 기계가 읽는 JSON으로 이어진 별개의 `codex exec` 단계로 나눈다.
2. 패턴은 조합된다. 웨이브가 체인을 품을 수 있고, 체인이 어느 단계에서든 리뷰 루프를 부를 수 있으며, 수리 루프는 단계가 검토, 수리, 검증인 체인이다. 독립 대 의존 작업, 단일 대 복수 모델, 결정적 대 LLM 검증이라는 제약을 이름 붙이면 패턴이 대개 저절로 정해진다.
3. 대화 분기는 더 가벼운 조율 수단이다. `/fork`는 병렬 스레드를 만들고 `/side`와 `/btw`는 일시적인 곁가지를 연다. 감독자가 사람이거나 부모 에이전트 하나이고 하위 작업이 서로 다를 때 쓴다.
4. 규모가 커지면 프로그램적 조율로 간다. 작업 단위가 많거나, 균질하거나, 자동 스케줄링이 사람의 감독보다 잘 표현하는 의존 그래프가 있을 때다.
5. `/goal`은 어떤 패턴이든 지속 목표로 감싼다. 토큰 예산과 감사 기반 완료 확인이 붙는다. 목표는 모호한 "다 했다"로 뭉개지지 않고 `unmet`이나 `budget_limited`로 쓸모 있게 실패할 수 있다. Goal Mode는 기본으로 켜져 있고, 제약이 있는 CI 환경에서는 `[features]`의 `goals = false`로 끈다.
6. `codex remote-control`은 외부 조율 표면이다. CI 파이프라인, 셸 스크립트, 에이전트가 아닌 하니스가 app-server 프로토콜로 상태를 가진 Codex CLI 세션을 여러 단계에 걸쳐 몬다. 1층(프로세스 안 서브에이전트)과 2층(독립 프로세스 셸 팬아웃) 사이에 놓인다. 명령과 프로토콜 표면은 아직 바뀌는 중이므로 CI에서 Codex 버전을 고정한다.
7. 피해야 할 안티패턴 다섯 가지. 게이트 없는 넘김, 집계 계획 없는 팬아웃, 끝이 없는 반복, 쓰기 권한 있는 리뷰어, 병렬 일꾼 간 공유 가변 상태다. 네 패턴 안에 중첩되면 각각 조용히 증폭된다.
8. 중요한 것은 부품이 아니라 엄밀함이다. 항상 게이트를 두고, 항상 상한을 걸고, 항상 격리하고, 누가 무엇을 결정했는지 항상 기록한다.

## 2. 다음 장 예고

원문은 14장이 여러 단계 작업의 비용 측면을 다룬다고 예고한다. 조율자, 서브에이전트, 리뷰 루프가 커질 때 API 지출을 어떻게 예측하고, 모니터링하고, 통제하는지다. 바로 이어지는 13장은 워크트리와 격리 실행이다. 12장이 에이전트가 어떤 순서로 도는지를 답했다면, 13장은 에이전트가 어디서 도는지를 답한다.
