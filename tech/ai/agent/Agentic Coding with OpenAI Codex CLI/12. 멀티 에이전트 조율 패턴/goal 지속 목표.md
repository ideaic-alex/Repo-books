# /goal: 지속 목표

앞의 패턴들은 시작과 끝이 있는 개별 작업을 다룬다. `/goal`은 다른 추상화를 도입한다. 턴, 세션, 터미널 충돌, 기기 재부팅을 넘어 살아남는 지속 목표(persistent objective)다. 에이전트가 목표를 달성했다고 선언하거나, 토큰 예산이 바닥나거나, 외부 장애물이 진행을 막을 때까지 완료를 향해 일한다. 이 문서는 명령, 생명주기, 완료 감사, 토큰 예산, 목표 문장 쓰는 법을 정리한다.

---

## 1. 켜고 끄는 법

Goal Mode는 Codex CLI에서 기본으로 켜져 있다. CI 같은 환경에서 끄려면 `config.toml`에 `[features]`의 `goals = false`를 쓴다.

## 2. 명령 다섯 개

```text
/goal "<objective>"  # set a new goal; Codex begins pursuing immediately
/goal                # view current goal summary and status
/goal pause          # pause; preserves audit context
/goal resume         # resume; picks up where it left off
/goal clear          # clear the goal; revert to single-turn behaviour
```

목표 문장은 비어 있으면 안 되고 최대 4,000자다. `/goal status` 하위 명령은 없다. 인자 없이 `/goal`만 치면 상태가 나온다. `/goal budget` 하위 명령도 없다. 예산은 `config.toml`에서 설정한다.

## 3. 핵심은 생명주기

목표는 서로 구분되는 다섯 가지 상태를 거친다. 상태 전이는 자유로운 글이 아니라 모델이 부르는 구조화된 `update_goal` 도구 호출이 구동한다.

| 상태 | 뜻 |
|---|---|
| `pursuing` | 적극적으로 일하며 다음 단계를 계획하는 중 |
| `paused` | 사용자 조작으로 중단. `/goal resume`을 기다림 |
| `achieved` | 완료 감사를 통과. 작업 중단 |
| `unmet` | 외부 의존이 완료를 막음. 에이전트가 해결 못 한 것을 보고 |
| `budget_limited` | 토큰 예산 소진. 에이전트가 진행 상황과 남은 일을 요약 |

`achieved`, `unmet`, `budget_limited`를 구분하는 것이 설계의 핵심 이득이다. 목표는 쓸모 있게 실패할 수 있다. 진행 내용을 보존하고, 남은 일을 설명하고, 깔끔한 이어하기 지점을 건넨다. 일반적인 대화형 프롬프트 루프였다면 셋 모두 모호한 "다 했다"로 뭉개졌을 것이다.

*그림 12.5. 목표를 세우면 pursuing 상태에 들어간다. `/goal pause`로 paused로 갔다가 `/goal resume`으로 되돌아올 수 있다. pursuing에서는 세 종착 상태 중 하나로 간다. 완료 감사를 통과하면 achieved, 외부 의존이 막으면 unmet, 토큰 예산이 소진되면 budget_limited다.*

## 4. 완료 감사

Goal Mode에서 가장 중요한 설계 결정은 이어가기 프롬프트가 에이전트에게 간접 신호(proxy signal, 테스트 통과처럼 완료를 대신 보여 주는 지표)를 완료의 증거로 받아들이지 못하게 막는다는 점이다. 목표에 테스트 커버리지 이상의 요구가 들어 있다면 테스트 통과만으로는 목표 달성이 증명되지 않는다. `update_goal`로 완료 상태를 부르기 전에 에이전트는 다음을 해야 한다.

1. 목표를 구체적인 산출물로 바꾼다.
2. 각 요구사항을 증거에 대응시키는 체크리스트를 만든다.
3. 실제 산출물(디스크의 파일, 명령 출력, 테스트 결과)을 직접 확인한다.
4. 커버리지를 빠짐없이 검증한다.

이것이 셸 스크립트로 감싼 랄프 루프와 런타임이 관리하는 목표 루프의 차이다. 랄프 루프는 자기 "다 했다" 신호를 믿는다. Goal Mode는 믿지 않는다.

## 5. 토큰 예산

토큰 예산은 하나의 목표가 주간 사용 한도(쿼터) 전체를 삼키는 일을 막는다. 기본값은 `~/.codex/config.toml`에 설정한다.

```toml
[goals]
default_token_budget = 500000  # 500k tokens per goal
```

예산이 거의 소진되면 런타임이 예산 한계 프롬프트를 주입해, 새 일을 시작하지 말고 진행 상황을 요약하라고 에이전트에게 지시한다. 예산 소진은 `achieved`가 아니라 `budget_limited`로 이어진다. 범위가 분명한 목표라면 20만에서 50만 토큰으로 시작하고, 복잡한 마이그레이션은 더 필요할 수 있으니 처음 몇 번은 실행을 지켜보며 조정하라는 것이 원문의 권고다.

## 6. 네 패턴과의 관계

Goal Mode는 네 패턴을 감싸는 바깥 루프이며 대체하지 않는다. 목표 안에서도 게이트 체인, 웨이브 계획, 교차 모델 리뷰 루프, 반복 수리 루프를 돌릴 수 있다. Goal Mode가 더하는 것은 세 가지다.

1. 에이전트가 매 턴 경계에서 다시 확인하는 지속 목표
2. 사람 검토 전에 얼마나 일할지 묶는 토큰 예산
3. 완료 주장을 받아들이기 전의 감사 단계

랄프 루프 용어로는 Goal Mode가 Codex 내장의 장시간 에이전트 루프다. 스레드 하나가 잘 명세된 일 하나를 끝낼 수 있을 때 `/goal`을 쓴다. 여러 에이전트, 반복마다 새 세션, 컨테이너 격리, 작업마다 커밋하는 워크플로, 단계마다 교차 모델 리뷰가 필요하면 외부 하니스를 쓴다.

## 7. 좋은 목표 문장 쓰는 법

약한 목표는 예산을 조용히 태운다. 성공을 가르는 가장 큰 요인은 목표 문장이다. 좋은 문장은 다섯 가지를 담는다.

1. 결과(outcome)
2. 검증 방법: 정확성을 증명하는 단일 명령
3. 쓰기 범위
4. 정지 조건
5. 에이전트가 멈추고 물어야 하는 트리거

다섯 개에 모두 답할 수 없다면 목표가 준비되지 않은 것이다.

### 7.1 예시: React 클래스 컴포넌트 변환

코드베이스의 모든 React 클래스 컴포넌트를 훅을 쓰는 함수형 컴포넌트로 바꾸는 일을 두 가지로 써 보자. 약한 버전은 `/goal "Modernise our React components"` 한 줄이다. 측정 가능한 결과도, 검증 명령도, 경계도, 정지 조건도 없다. 에이전트가 다른 스타일로 다시 쓰거나, API 계약을 바꾸거나, 피상적인 작업 뒤에 성공을 선언할 수 있다. 더 나쁘게는 언제 멈출지 아무 데도 적혀 있지 않아서 토큰 예산이 끝날 때까지 계속 돈다.

강한 버전은 다섯 질문을 한 문장에 담는다. 원문은 `src/components/`의 클래스 컴포넌트 23개를 변환하고, `src/__tests__/components/`의 기존 테스트를 모두 보존하며, 변환마다 `npm test -- --watch=false`를 돌려 종료 코드 0일 때만 계속하고, `src/components/` 밖 파일은 건드리지 않으며, 매 턴 `converted_count`와 `remaining_count`를 추적하고, `remaining_count`가 0이 되면 멈추되 공개 prop 타입을 바꿔야 하는 컴포넌트는 손대지 않고 수동 검토 대상으로 보고하라고 쓴다.

| 질문 | 이 예시의 답 |
|---|---|
| 결과 | 23개 컴포넌트 변환, 모든 테스트 통과 유지 |
| 검증 명령 | 변환마다 `npm test -- --watch=false` |
| 쓰기 범위 | `src/components/`만 |
| 정지 조건 | `remaining_count`가 0 |
| 멈춤 트리거 | 공개 prop 타입을 바꿔야 할 때 |

### 7.2 다른 장기 작업에도 같은 모양

"더 좋게"를 관찰 가능한 증거로 바꿔야 하는 장기 작업이면 같은 모양이 통한다. 안전장치 정지 조건을 둔 커버리지 목표, N번 시도해도 개선이 없으면 끊는 회로 차단기를 둔 벤치마크 임계값, 각 요구사항을 `npm run spec:validate` 스위트로 검증하는 명세 대 구현 작업이 그 예다.

### 7.3 검증 수단은 에이전트 밖에 있어야 한다

목표에는 에이전트 바깥에 있는 검증 수단이 필요하다. 자기 출력을 다시 읽어서 스스로 검증하는 목표는 런타임으로 감싼 랄프 루프일 뿐이다. 종료 코드나 구조화된 출력이 "끝났는가"에 답해 주는 명령을 가리킬 수 없다면, 그 작업은 아직 목표로 걸 준비가 되지 않은 것이다.
