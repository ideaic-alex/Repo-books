# 워크플로 테스트와 평가 전략

에이전트 작업에서 테스트 실행은 가장 중요한 피드백 수단이다. 하지만 테스트가 느리거나 가끔 깨지거나 네트워크에 의존하면, 에이전트는 가짜 실패를 쫓으며 엉뚱한 곳을 고친다. 이 장은 테스트 스위트를 믿을 만한 신호로 만드는 방법과, 이미 있는 스위트를 감사하는 방법, 그리고 단위 테스트를 넘어 에이전트 역량을 평가하는 방법을 다룬다.

코드량이 사람의 10~100배로 늘어난 지금, 에이전트가 에이전트를 검수하는 구조만으로는 문제가 사라지지 않는다. 기계가 판정할 수 있는 신호를 주는 테스트 스위트가 마지막 보루이며, 그 위에 게이트 명령, TDD, 평가 하니스, CI 연동, 벤치마크 기반 점검을 쌓아 가는 것이 이 장의 흐름이다.

---

## 1. 핵심 요점

- 에이전트 친화적 테스트는 격리돼 있고, 결정적이며, 명령 하나(종료 코드 0 또는 아님)로 돌릴 수 있어야 한다.
- 시드 픽스처, 메모리 내 서비스, 트랜잭션 롤백, 환경 변수 자동 주입으로 테스트를 서로 독립시킨다.
- 린트, 타입 검사, 테스트를 `make gate` 같은 단일 게이트 명령으로 묶고, 줄 커버리지보다 분기 커버리지를 기준으로 삼는다.
- Codex CLI를 읽기 전용으로 돌려 테스트의 네트워크 호출, 절대 경로, sleep(), 전역 상태를 감사하고 영향이 큰 순서로 고친다.
- TDD는 에이전트에게 실행 가능한 완료 기준을 준다. AGENTS.md에 '테스트를 수정하지 말 것'을 적고, 버그 수정은 재현 테스트부터 쓴다.
- 단위 테스트 너머로는 통합 테스트, 속성 기반 테스트, 표본 추출 평가, 최소 평가 하니스를 쓰고, 하니스는 에이전트 루프 밖에 둔다.
- 에이전트는 모킹을 과하게 쓰므로 AGENTS.md 모킹 정책과 훅으로 비율을 관리하고, 리뷰 체크리스트로 유지보수성 공백을 메운다.
- 여러 세션에 걸친 긴 작업은 PLAN, PROGRESS, DISCOVERIES, DECISIONS 네 파일로 상태를 보존하고 과정까지 채점한다.
