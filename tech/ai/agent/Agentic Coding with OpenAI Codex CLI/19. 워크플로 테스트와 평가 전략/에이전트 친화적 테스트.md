# 에이전트 친화적 테스트

이 책 전체에서 Codex CLI의 가장 중요한 피드백 수단은 테스트 실행이었다. 그런데 이 전제는 테스트가 믿을 만한 신호일 때만 성립한다. 느리거나, 가끔 깨지거나, 네트워크에 기대는 테스트는 에이전트(스스로 계획하고 도구를 쓰며 작업하는 AI)를 엉뚱한 곳으로 이끈다. Codex CLI가 내놓는 결과의 품질은 결국 테스트 스위트의 품질을 넘지 못한다.

이 문서는 왜 테스트가 그렇게 중요한지, 그리고 에이전트가 다루기 좋은 테스트가 갖춰야 할 세 가지 성질을 설명한다.

---

## 1. 왜 테스트가 마지막 보루인가

개발자 한 명이 에이전트에게 시켜서 한 세션에 수천 줄을 만들어 내는 시대다. 직접 짤 때보다 10배에서 100배 많은 코드가 나오니, 그 안에 버그가 섞여 있을 확률은 통계적으로 거의 확실하다. 원서는 GitHub 시니어 엔지니어 출신의 한 비평을 인용한다. 코드량이 100배가 되면 사람이 그 결과물을 의미 있게 리뷰할 수 없게 되고, 발견되지 않는 버그가 쌓일 수밖에 없다는 주장이다.

업계의 흔한 반응은 에이전트를 더 쌓는 것이다. 에이전트가 테스트를 쓰고, 에이전트가 리뷰하고, 에이전트가 평가하게 한다. 하지만 이는 문제를 없애는 것이 아니라 흩뿌릴 뿐이다. 불완전한 시스템이 불완전한 시스템을 평가한다고 해서 완전해지지는 않는다.

테스트 스위트는 기계가 검증할 수 있는 신호를 주는 거의 유일한 산출물이다. 코드를 사람이 썼든 에이전트가 썼든 상관없이 통과와 실패가 똑같이 판정된다. 그래서 이 장은 테스트 스위트를 믿을 만한 신호로 만드는 법, 이미 있는 스위트를 점검하는 법, 단위 테스트 너머의 평가 방법을 차례로 다룬다.

## 2. 이 장에서 얻는 것

- 에이전트 실행에서 오탐(거짓 실패)을 만드는 흔한 테스트 문제를 찾아 고친다.
- 린트, 타입 검사, 테스트를 하나로 묶은 단일 게이트 명령을 설계한다.
- 에이전트 결과물을 작업 명세에 비춰 채점하는 최소한의 평가 하니스(실행·채점을 묶는 틀)를 만든다.
- 에이전트 평가를 CI 파이프라인에 끼워 넣는다.

## 3. 에이전트 친화적 테스트의 세 가지 조건

좋은 테스트 스위트가 갖는 일반적인 장점 위에, 에이전트용으로는 세 가지가 더 필요하다. 격리돼 있을 것(hermetic), 결과가 늘 같을 것(deterministic), 명령 하나로 돌릴 수 있을 것이다.

### 격리성(hermetic)

격리된 테스트는 외부에 의존하지 않는다. 실제 API 호출도, 실제 데이터베이스 연결도 없다. 샌드박스 안에서 도는 에이전트는 네트워크가 막혀 있을 수 있다. 그러면 HTTP를 부르는 테스트는 코드가 틀려서가 아니라 네트워크가 막혀서 실패한다.
외부 호출은 테스트 경계에서 가짜로 바꾼다. 언어별로 쓸 만한 도구는 다음과 같다.

| 대상 | Node.js | Python | Go |
|---|---|---|---|
| HTTP 호출 | msw | responses | httptest |
| 데이터베이스 | 메모리 내 구현 또는 트랜잭션 롤백 | 같음 | 같음 |

### 결정성(deterministic)

가끔 깨지는(flaky) 테스트는 에이전트가 가짜 실패를 쫓게 만든다. 더 나쁜 경우에는 근본 원인은 두고 불안정함만 가려 버리는 '수정'을 내놓는다. 흔한 원인은 다음과 같다.

- 시간에 의존하는 단언. 테스트용 날짜를 고정해서 푼다.
- 데이터베이스 행의 순서를 가정하는 코드.
- 정리(teardown) 없이 공유하는 전역 상태.
- 비동기 타이밍을 맞추려고 넣은 sleep() 호출.
- 고정하지 않은 난수 시드.

모든 테스트는 언제, 어떤 순서로 돌려도 같은 결과를 내야 한다.

### 단일 명령 실행

작업 지시에 "테스트를 돌려라"라고 적었다면, 그것이 종료 코드가 분명한 명령 하나로 이어져야 한다. 0이면 통과, 0이 아니면 실패다. 대화형 질문도, 출력 해석을 방해하는 진행 막대도, 사전 준비가 필요한 러너도 없어야 한다.

```bash
# 좋은 예: 명령 하나, 종료 코드 명확
npm test
pytest
make test
go test ./...

# 나쁜 예: 실행 전에 준비가 필요
npm install && npm test
source .env.test && pytest
```

사전 준비가 꼭 필요하다면 Makefile 타깃이나 래퍼 스크립트 안에 넣는다. 에이전트가 만나는 창구는 깔끔한 명령 하나여야 한다.

### 병렬 실행은 괜찮다

병렬 실행 자체는 에이전트에게 문제가 아니다. 빠를수록 좋다. 문제는 비결정성이다. 병렬로 돌려도 늘 같은 결과가 나오면 에이전트 친화적이고, 순차로 돌리는데도 가끔 통과와 실패가 뒤바뀌면 그렇지 않다.
