# 에이전트 테스트 품질과 벤치마크

에이전트가 만든 테스트의 품질과 에이전트 코드 리뷰의 성능에 대해, 원서는 연구 결과 몇 가지를 근거로 든다. 이 문서는 과도한 모킹 문제, 코드 리뷰 에이전트 벤치마크(c-CRAB), 팀이 평가 체크리스트로 가져다 쓸 수 있는 벤치마크 세 가지(CocoaBench, HiL-Bench, AAR), 그리고 MCP 서버 테스트를 정리한다.

---

## 1. 과도한 모킹 문제

MSR 2026에 채택된 실증 연구는 2,168개 저장소의 커밋 120만 건 이상(에이전트 커밋 48,563건 포함)을 분석했다. 결과는 이렇다.

| 항목 | 에이전트 | 사람 |
|---|---|---|
| 커밋에서 모킹을 추가하는 비율 | 36% | 26% |
| 커밋에서 테스트 파일을 수정하는 비율 | 23% | 13% |

에이전트는 테스트 파일도 훨씬 자주 건드리므로, 모킹의 격차는 몇몇 파일에 머물지 않고 코드베이스 전체로 번진다.

더 걱정스러운 것은 종류의 쏠림이다. 사람은 목(mock), 페이크(fake), 스파이(spy), 더미(dummy) 같은 여러 테스트 대역을 골라 쓰지만, 에이전트는 목에 크게 기대고 나머지는 덜 쓴다. 에이전트가 무엇이든 `jest.fn()`이나 `unittest.mock.patch`로 처리하면, 테스트는 '이 함수를 불렀는가'라는 상호작용 패턴만 확인하고 동작이 올바른지는 확인하지 못한다.

왜 문제일까. 목이 지배하는 스위트는 함수가 예상한 순서로 호출됐는지만 확인하기 쉬워서, 실제 회귀가 빠져나가는 중에도 초록불을 유지할 수 있다. 테스트 파일이 페이크나 실제 경계 대신 목에 기댈수록 신호는 약해진다.

## 2. 현실적인 테스트를 위한 Codex CLI 설정

세 층에서 설정해 에이전트가 만드는 테스트를 현실적으로 유지한다.

### AGENTS.md 모킹 정책

무엇을 어떤 대역으로 처리할지 나눠 적는다.

- **Mock**: 외부 HTTP API, 서드파티 서비스, 시스템 시계, 난수 생성기.
- **Fake**: 데이터베이스(testcontainers나 SQLite 메모리), 메시지 큐, 캐시.
- **Spy**: 이벤트 발행기, 로깅, 메트릭. 동작을 대체하지 않고 호출만 확인한다.
- **Never mock**: 순수 함수, 값 객체, 자기 도메인 로직.
- 파일별 모킹 비율은 50% 미만으로 유지한다. 단언보다 모킹 설정이 많은 테스트 파일은 페이크나 통합 경계를 쓰도록 리팩터링한다.

### 모킹 비율을 지키는 PostToolUse 훅

`~/.codex/hooks/check-mock-ratio.sh`는 도구 이름과 파일 경로를 JSON에서 읽는다. 도구가 write_file이고 파일 이름에 test가 들어 있으면, 파일 안에서 mock, jest.fn, patch, MagicMock이 나온 줄 수와 assert, expect, should가 나온 줄 수를 grep으로 센다. 모킹 수가 단언 수보다 크면 경고를 출력한다. 핵심 비교 부분만 옮기면 이렇다.

```bash
if [ "$MOCK_COUNT" -gt "$ASSERT_COUNT" ]; then
  echo "WARNING: Mock count ($MOCK_COUNT) exceeds assertion count ($ASSERT_COUNT) in $FILE"
fi
```

### 게이트 명령에서 통합 테스트 강제

게이트에 단위 테스트와 통합 테스트를 모두 넣어서 최소한 일부 테스트는 실제 경계를 건드리게 한다. 원서의 예는 `npm run test:unit`, `npm run test:integration`을 차례로 돌린 뒤 "GATE PASSED"를 찍는 형태다.

## 3. 코드 리뷰 에이전트 벤치마크 c-CRAB

2026년에 나온 c-CRAB은 코드 리뷰 에이전트를 위한 실행 가능한 벤치마크다. 결과는 냉정하다. 오픈소스 PR-agent와 Devin, Claude Code, Codex의 상용 에이전트를 시험했더니, 다 합쳐도 c-CRAB 작업의 약 40%만 풀었고 약 60%의 문제는 발견하지 못했다. 에이전트끼리 겹치는 부분도 적어서, 각자 다른 문제를 잡아낸다.

잘하는 영역은 견고성과 경계 사례(위험한 인덱싱, null 검사, 경계 조건)이고, 가장 약한 영역은 유지보수성과 설계 문제(API 설계, 추상화 경계, 이름 일관성)다.

### 더 나은 리뷰를 위한 설정

AGENTS.md에 명시적인 리뷰 체크리스트를 넣는다. `/review`나 `@codex review`로 리뷰할 때 다음 여섯 가지를 확인하게 한다.

1. 논리 오류: off-by-one, 뒤집힌 조건, 빠진 반환.
2. 에러 처리: 처리되지 않은 예외, 삼켜진 에러, 빠진 재시도.
3. 보안: 인젝션, 인증 우회, 코드 속 비밀값, 안전하지 않은 역직렬화.
4. 유지보수성: 불분명한 이름, 깊은 중첩, 빠진 추상화.
5. 테스트 커버리지: 경계 사례를 테스트했는가, 새 경로를 다뤘는가.
6. 문서화: 공개 API에 문서 주석이 있는가, 호환성을 깨는 변경을 적었는가.

원서는 체크리스트를 c-CRAB이 가리키는 지렛대라고 본다. 체크리스트를 따라 하는 리뷰는 에이전트가 이미 잘하는 영역의 성능은 떨어뜨리지 않으면서 유지보수성 격차를 좁힌다.

## 4. 평가 프레임워크 CocoaBench, HiL-Bench, AAR

세 벤치마크는 기업 팀이 곧바로 가져다 쓸 수 있는 평가 틀이다. 학술적 연습이 아니라 에이전트 워크플로의 테스트 공백을 찾는 구체적 체크리스트로 쓴다(전체 분석은 26장).

### 실패 유형을 테스트 커버리지 체크리스트로

가장 실용적인 교훈은 실패 유형 분류에서 얻는 체크리스트다. 대부분의 팀은 도구 사용을 열심히 테스트하지만, 벤치마크 데이터에서 도구 사용이 병목인 경우는 드물고 에이전트 실패의 작은 일부만 차지한다. 지배적인 실패 유형은 오히려 테스트가 부족하다.

- **탐색 테스트(실패의 27~52%).** 평가 스위트에 낯선 코드 영역에서 파일을 찾아야 하는 작업이 있는가. 대부분의 내부 벤치마크는 에이전트가 전에 본 파일만 시험한다. 평소 작업 영역 밖을 탐색하는 작업을 넣고, 에이전트가 이를 못 하면 AGENTS.md의 파일 지도(4장)를 늘려야 한다.
- **도움 요청 판단 테스트.** 진행하지 않고 되물어야 맞는 작업이 있는가. 대부분의 스위트는 완료를 보상하고 미완료를 감점해서, 제안(Suggest) 모드가 더 나은 결과를 낼 작업에도 Full Auto를 쓰도록 팀을 길들인다. 모호한 작업을 넣고, 불확실함을 알아채 상위로 넘기는 에이전트에게 가점을 준다.
- **멀티모달 조합 테스트(작업의 약 55%가 실패).** 코드, 문서, 테스트, 설정 등 여러 형태에 걸친 작업이 있는가. 대부분의 평가 작업은 한 형태뿐이다. 이들을 아울러 고쳐야 하는 작업을 넣고 형태 간 일관성으로 채점한다.

### CocoaBench를 평가 틀로

CocoaBench의 작업 구조(멀티모달 조합 작업을 형태 간 일관성으로 채점)는 내부 평가에 그대로 적용할 수 있다. 팀에 평가 하니스가 있다면 CocoaBench식 작업 범주를 더한다. 에이전트가 코드를 고치고, 대응하는 테스트를 갱신하고, 관련 문서까지 한 번의 일관된 작업으로 바꾸게 한다. 한 결과물의 기능 정확성만이 아니라 세 결과물 사이의 일관성을 채점한다.

### HiL-Bench로 승인 모드 보정하기

HiL-Bench는 승인 모드를 원칙 있게 조정하는 방법을 준다. 모호한 작업을 Full Auto와 Suggest 모드로 모두 돌려 본다. 에이전트가 적절히 되묻는 Suggest 쪽 결과가 확연히 좋다면, Full Auto 설정이 품질을 깎고 있는 것이다. 도움을 구한 경우와 구하지 않은 경우의 성능 차이를 재는 HiL-Bench 채점 방식을 승인 모드 결정의 정량 입력으로 쓴다.

### AAR로 AGENTS.md 효과 재기

AAR 연구의 탐색 정확도 지표(기준선 37.2%)로 AGENTS.md 파일 지도의 효과를 잰다. 특정 함수 찾기, 모듈의 테스트 위치 찾기, 서비스 설정 파일 식별 같은 탐색 위주 작업을 파일 지도 섹션이 있을 때와 없을 때 각각 돌린다. 정확도가 얼마나 오르는지가 파일 지도의 가치를 직접 보여 준다. 참고로 원서의 각주에 따르면 AAR 최고 에이전트의 정확도는 37.2%이고 탐색 오류가 시도의 27~52%를 차지하며, 이 벤치마크는 퍼즐·검색 기반 탐색을 쓰므로 코드베이스 탐색에 적용하는 것은 유추다.

## 5. MCP 서버 테스트

MCP 서버를 쓰는 Codex CLI 워크플로에서 MCP 서버는 핵심 의존성이므로 자체 테스트 전략이 필요하다. MCP 서버를 따로 떼어 테스트하는 방법은 8장에서 다룬다. 이 장의 원칙은 MCP 서버 장애를 데이터베이스 장애처럼 대하라는 것이다. 에이전트는 있어야 할 데이터를 잃고도 눈에 보이는 에러 대신 그럴듯하지만 틀린 답을 내놓기 때문에 출력 품질이 조용히 나빠진다.

CI에 MCP 서버 상태 점검을 넣는다. 설정된 MCP 서버를 하나씩 띄우고, 도구가 등록됐는지 확인하고, 각 도구를 알려진 입력으로 호출하고, 종료가 제대로 되는지 보는 단순한 통합 테스트면 대부분의 팀에 충분하다. 에이전트 수준 평가에 앞서 이 테스트를 돌려 인프라가 멀쩡한지부터 확인한다.
