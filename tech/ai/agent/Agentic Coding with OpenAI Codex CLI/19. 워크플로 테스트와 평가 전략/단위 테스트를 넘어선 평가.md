# 단위 테스트를 넘어선 평가

단위 테스트는 에이전트 결과물을 평가하기에는 한계가 뚜렷하다. 기능이 맞는지만 보고 결과물의 품질은 보지 못하며, '맞는 답'이 판단의 문제인 긴 작업은 판정할 수 없다. 이 문서는 통합 테스트, 속성 기반 테스트, 표본 추출 평가, 그리고 이를 모아 돌리는 평가 하니스와 CI 연동을 다룬다.

---

## 1. 통합 테스트 전략

에이전트가 개발하는 동안에는 빠른 단위 테스트 스위트를 돌린다. 그 결과로 올라온 PR에서는 단위 테스트와 통합 테스트를 함께 돌린다. 통합 테스트는 에이전트의 변경이 끝에서 끝까지 동작하는지 확인한다. 진짜지만 시드를 심어 둔 서비스를 Docker Compose로 띄우고, 에이전트가 개발 중에 쓰는 빠른 단위 테스트와는 분리해 둔다.

## 2. 속성 기반 테스트

속성 기반 테스트는 어떤 유효한 입력에 대해서든 항상 성립해야 하는 불변식을 검증한다. 테스트 작성자가 모든 입력을 미리 떠올릴 필요 없이 구조적 정확성을 확인할 수 있어, 에이전트 결과물에 특히 쓸모가 크다. 아래는 문서를 파싱했다가 직렬화한 뒤 다시 파싱해도 같아야 한다는 속성이다(Python의 hypothesis 방식).

```python
@given(st.text(alphabet=st.characters(whitelist_categories=('L', 'N', 'P'))))
def test_parse_serialise_roundtrip(content):
    parsed = parse_document(content)
    serialised = serialise_document(parsed)
    re_parsed = parse_document(serialised)
    assert parsed == re_parsed
```

에이전트가 parse_document나 serialise_document를 고치면, 이 테스트는 작성자가 생각지 못한 입력에서 왕복 불변식이 깨지는 것까지 잡아낸다. 예시 기반 테스트보다 쓰기 어렵지만, 구조를 바꾸는 작업에는 훨씬 강력한 피드백이 된다.

## 3. 긴 작업을 위한 표본 추출 평가

코드 품질, 아키텍처 결정, 문서의 명확성처럼 '맞다'가 판단의 문제인 작업은 표본 추출로 평가한다. 같은 작업을 서로 다른 난수 시드로 여러 번 돌려서 결과물을 채점하는 방식이다. 채점 방법은 세 가지다.

1. **자동 채점.** 각 결과물에 린트·타입·테스트 게이트를 돌린다. 표본 전체에서 통과한 비율이 점수다.
2. **LLM 심사(LLM-as-judge).** 별도의 모델 호출로 결과물을 평가 기준표에 비춰 본다. 이 방식은 자체 편향이 있지만 규모를 키우기 쉽다.
3. **사람 검토.** 소수의 결과물을 뽑아 사람이 채점한다. 비싸지만 정확하다.

CI에서는 자동 채점으로 게이트 통과율 80~90퍼센트(M개 표본 중 N개가 모든 검사를 통과)를 기준으로 삼는 것이 현실적이다. 결과가 어느 정도 흔들릴 수밖에 없는 긴 작업에 알맞은 기준이다.

## 4. 평가 하니스 만들기

최소한의 평가 하니스는 에이전트에게 작업을 시키고, 결과를 모으고, 채점한다. SWE-bench 방식 평가 뒤에 있는 인프라와 같은 구조이며, 자기 코드베이스용으로 만들 수 있다.

### 구조

```text
eval/
├── tasks/
│   └── task-001/
│       ├── prompt.txt    # 작업 설명
│       ├── setup.sh      # 준비(저장소 복제, 데이터 시드)
│       ├── teardown.sh   # 정리
│       └── grade.sh      # 채점(0/1 반환)
├── run_eval.sh           # 준비, 에이전트, 채점을 조율
└── results/              # 평가 실행 결과
```

### run_eval.sh의 흐름

스크립트는 작업 폴더를 받아 결과 폴더를 시각 기반 이름으로 만든 뒤 네 단계를 밟는다.

1. 준비: setup.sh를 실행하고 로그를 남긴다.
2. 에이전트 실행: `codex exec "$(cat "$TASK_DIR/prompt.txt")" --json`으로 돌리고 출력은 agent.json, 에러는 agent.log에 저장한다.
3. 채점: grade.sh를 실행하고 종료 코드를 GRADE에 보관한다.
4. 정리: teardown.sh를 실행하고 score.txt에 점수를 쓴다. 마지막에 PASS 또는 FAIL을 출력하고 GRADE로 종료한다.

```bash
codex exec "$(cat "$TASK_DIR/prompt.txt")" \
  --json > "$RESULTS_DIR/agent.json" 2>"$RESULTS_DIR/agent.log"
bash "$TASK_DIR/grade.sh" > "$RESULTS_DIR/grade.log" 2>&1
GRADE=$?
```

코드 작업의 grade.sh는 보통 테스트 스위트를 돌려 그 종료 코드를 그대로 돌려준다. 문서 작업이라면 링크 검사기, 맞춤법 검사기, LLM 평가를 돌릴 수 있다.

### SWE-bench와의 연결

SWE-bench는 실제 GitHub 이슈로 코딩 에이전트를 평가하는 표준 벤치마크다. 위 구조(프롬프트, 준비, 정리, 채점)는 일부러 SWE-bench의 작업 형식과 맞춰 두었기 때문에, 내 설정을 공개된 기준선과 비교해 볼 수 있다. 다만 대부분의 팀에는 자기 백로그에서 뽑은 내부 벤치마크가 더 유익하다. 공개 벤치마크는 공개 저장소에서의 성능을 재는 것이지 우리 코드베이스와 관례에서의 성능을 재는 것이 아니기 때문이다.

## 5. CI 연동

원서의 표 19-1을 새로 정리하면 전략별 성격은 다음과 같다.

| 전략 | 속도 | 검증 범위 | 에이전트 친화도 | 용도 |
|---|---|---|---|---|
| 단위 테스트 | 빠름(2분 미만) | 함수 수준 | 높음 | 에이전트 피드백 루프 |
| 속성 기반 테스트 | 중간(2~5분) | 불변식 수준 | 높음 | 구조적 정확성 |
| 통합 테스트 | 느림(5~30분) | 시스템 수준 | 중간 | 머지 전 게이트 |
| 평가 하니스 | 가변 | 작업 수준 | 낮음 | 벤치마킹, 회귀 확인 |
| LLM 심사 | 빠름(API) | 품질 수준 | 중간 | 긴 작업 |

권장하는 CI 연동 순서는 다음과 같다.

1. 에이전트가 커밋할 때마다 단위 테스트를 돌린다. 빠른 게이트이며 에이전트 루프가 여기에 달려 있다.
2. PR마다 단위 테스트, 통합 테스트, 타입 검사, 린트를 돌린다. 사람이 리뷰하기 전의 포괄적인 게이트다.
3. 밤마다 대표 작업 묶음으로 평가 하니스를 돌리고 통과율을 시간에 따라 추적한다.
4. 모델을 바꾸기 전에는 평가 하니스 전체를 돌린다. 통과율이 떨어지면 에이전트 역량이 퇴보했다는 신호다.

평가 하니스를 에이전트의 피드백 루프에 넣지 않는다. 하니스는 에이전트의 역량을 바깥에서 재는 도구다. 에이전트가 하니스에 접근할 수 있으면 본래 작업을 푸는 대신 하니스를 통과하도록 결과를 맞출 수 있다. 에이전트 시스템에 적용된 굿하트의 법칙(지표가 목표가 되면 좋은 지표가 아니게 된다는 원리)이다.
