# 내 코드베이스로 벤치마크 만들기

공개 벤치마크가 아무리 좋아도, 정말로 중요한 벤치마크는 내 코드베이스에서 내 작업을 내 제약 조건 아래 돌려 본 결과다. 이 문서는 Terminal-Bench 2.0의 구조를 본떠 5~10개 작업으로 구성한 마이크로 벤치마크를 만드는 절차, 디렉터리 구조, 기록 항목, 그리고 이것이 왜 공개 점수보다 더 현실적인지를 정리한다.

---

## 1. 다섯 단계 절차

1. **대표 작업 5~10개를 고른다.** Codex CLI에 실제로 시키는 일의 범위를 아우르게 버그 수정, 기능 추가, 인프라 변경을 섞는다. 너무 쉽거나 끝이 없이 열린 작업은 피한다.
2. **결정적인 성공 기준을 쓴다.** 작업마다 사람의 판단 없이 통과/실패를 출력하는 테스트 스크립트가 필요하다. 벤치마크 설계에서 가장 어려운 부분이며, 합성 벤치마크가 실제 업무의 복잡성을 덜 반영하는 이유이기도 하다. 실제 작업은 유효한 해법이 여러 개인 경우가 많지만, 신뢰할 수 있는 자동 테스트는 검증 가능한 결과가 하나여야 하기 때문이다.
3. **환경을 컨테이너로 만든다.** Docker 환경이면 실행 사이의 오염을 막고 결과를 재현할 수 있다. 매번 같은 베이스 이미지를 쓰고 의존성 버전을 고정한다.
4. **여러 설정으로 돌린다.** 최소한 현재의 모델과 AGENTS.md 설정을 대안 하나와 비교한다. 대안은 다른 모델일 수도, 다른 AGENTS.md 구조일 수도, 다른 훅 묶음일 수도 있다.
5. **해결률과 함께 비용을 기록한다.** 작업당 0.50달러로 80%를 해결하는 설정이 4.00달러로 85%를 해결하는 설정보다 낫다는 판단이 처리량 요구에 따라 나올 수 있다.

## 2. 디렉터리 구조

작은 벤치마크 디렉터리를 두면 작업이 반복 가능한 모양을 갖는다.

```text
.benchmarks/
  task-001/
    README.md        # 자연어 작업 설명
    setup.sh         # 저장소를 시작 상태로 되돌림
    test.sh          # 성공하면 0, 실패하면 1로 종료
    expected.md      # 의도한 동작에 관한 메모
  results/
    2026-04-23-gpt-5.5-default.json
```

결과는 매번 같은 항목으로 기록한다.

| 항목 | 의미 |
|---|---|
| Task | 어떤 작업인가 |
| Config | 모델, AGENTS.md, 훅 등 설정 |
| Pass/fail | 통과 여부 |
| Turns | 걸린 턴 수 |
| Tokens | 사용한 토큰 |
| Cost | 비용 |
| Notes | 특이 사항 |

## 3. 내 코드베이스가 더 어려울 수 있다

지속적 진화를 겨냥한 SWE-EVO 벤치마크는 한 번에 끝나는 패치가 아니라 기존 시스템이 계속 발전하는 과정을 시험한다. 여기서 OpenHands를 쓴 GPT-5는 21%를 기록했는데, 같은 모델이 SWE-bench Verified에서는 65%다. 상업용·기업용 코드베이스에서는 최고 모델도 20% 아래다. 내 사내 코드베이스는 어떤 공개 벤치마크보다 어려울 가능성이 높다. 그 현실을 전제로 만들어야 한다.

## 4. 목표와 관리

목표는 공개할 만한 리더보드 점수가 아니다. 모델과 스캐폴딩이 바뀔 때 설정을 결정하고 성능 후퇴를 추적하는 데 쓸, 일관되고 반복 가능한 신호다. 작업이 다섯 개뿐인 묶음이라도 내 실제 문제 영역을 재기 때문에 어떤 공개 벤치마크보다 실행에 옮기기 좋은 데이터를 준다.

작업 정의와 결과는 전용 디렉터리(예를 들어 `.benchmarks/`)에 두고 AGENTS.md와 함께 버전 관리한다. 그러면 Codex CLI 설정을 바꿔 가면서 성능이 언제 왜 달라졌는지 정확히 볼 수 있다.
