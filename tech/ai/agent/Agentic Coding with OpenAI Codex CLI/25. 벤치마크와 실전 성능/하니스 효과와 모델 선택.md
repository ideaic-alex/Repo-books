# 하니스 효과와 모델 선택

벤치마크 점수는 모델만의 성적이 아니다. 모델을 감싸는 조율 계층, 곧 스캐폴딩(여기서는 하니스와 같은 뜻)이 점수를 크게 좌우한다. 이 문서는 그 효과를 설명하고, 벤치마크 점수를 내 팀의 도구 선택으로 옮길 때 필요한 보정 방법과 Codex CLI에서의 모델 선택 요령을 다룬다.

---

## 1. 스캐폴딩 효과

스캐폴딩은 메모리 관리, 도구 사용 규약, 재시도 로직을 맡는 조율 계층이다. 이 계층이 기반 모델만큼 중요할 수 있다. 예를 들어 Confucius Code Agent는 Claude 4 Sonnet으로 SWE-bench 74.6%를 기록해서, 더 뛰어난 Claude 4.5 Sonnet을 쓴 mini-SWE-Agent 변형을 앞질렀다. 더 나은 조율이 한 세대 모델 격차를 따라잡고 추월한 것이다. SWE-bench Pro 리더보드 논의에서도 같은 모델을 다른 에이전트 프레임워크로 돌리면 4~12점씩 달라진다.

이는 Codex CLI 설정에 직접 의미가 있다. CLI가 기본 제공하는 서브에이전트 지원, AGENTS.md 컨텍스트 로딩, 훅 시스템이 합쳐져 나만의 스캐폴딩 계층이 된다.

- AGENTS.md를 잘 쓰면 코드베이스 범위, 테스트 실행 관례, 건드리면 안 되는 디렉터리를 알려 줄 수 있다. 이것이 세션 내내 모델이 기댈 지속적인 컨텍스트가 된다.
- SessionStart 훅으로 관련 문서나 최근 git 이력을 미리 불러오면 근거(grounding)가 보강된다. 벤치마크에서 무난한 성적을 내는 것과 실제 작업을 끝내는 것을 가르는 차이가 여기서 생긴다.

Codex CLI를 설정할 때 우리는 모델만 고르는 것이 아니라 스캐폴드를 구성하고 있다. 벤치마크 숫자는 천장을 보여 주고, 내 AGENTS.md와 훅이 내 작업에서 그 천장에 얼마나 가까이 가는지를 정한다.

## 2. 내 작업에 맞는 벤치마크 고르기

가장 흔한 실수는 엉뚱한 벤치마크의 높은 점수를 적합하다는 증거로 받아들이는 것이다. 점수를 평가하기 전에 어떤 벤치마크가 내 실제 업무와 가장 닮았는지부터 물어야 한다.

| 내 주된 용도 | 가장 예측력 있는 벤치마크 |
|---|---|
| 파이썬 저장소의 버그 수정 | SWE-bench Pro (Verified 아님) |
| 터미널 자동화, 데브옵스, ML 파이프라인 | Terminal-Bench 2.0 |
| 여러 언어와 여러 파일에 걸친 기능 개발 | SWE-bench Pro 비공개 부분 |
| 처음부터 새로 만드는 개발 | 이를 잘 담은 현재 벤치마크는 없음 |

팀이 주로 Rust 마이크로서비스를 짠다면 파이썬 전용 벤치마크는 신호가 약하다. 업무가 인프라 자동화, 곧 셸 스크립트, 서비스 설정, 파이프라인 디버깅 같은 플랫폼 엔지니어링이라면 그런 일을 닮은 공개 벤치마크는 Terminal-Bench 2.0뿐이다.

## 3. 스캐폴드 부풀림 감안하기

벤더가 자체 스캐폴딩으로 낸 점수는 표준화 평가보다 4~12점 부풀려진다. 사기라는 뜻은 아니다. 맞춤 스캐폴딩이 실제로 결과를 개선하기 때문이다. 다만 두 벤더가 같은 하니스로 측정되지 않았다면 벤더 간 비교는 믿을 수 없게 된다.

같은 조건 비교를 하려면 SWE-bench 작업은 SEAL 리더보드 수치를, 그 외에는 에이전트 프레임워크가 명시된 Terminal-Bench 결과를 보는 게 낫다. 벤더가 "SWE-bench Pro에서 X%"라고 주장하면 첫 질문은 "어떤 스캐폴딩이냐"가 되어야 한다.

## 4. Codex CLI에서 모델 고르기

현재 벤치마크 데이터를 토대로 한 실용적인 순서는 유효한 로컬 기본값에서 시작하는 것이다.

```toml
# config.toml - 로컬 기본 모델
model = "gpt-5.5"
```

- 계획, 컴퓨터 사용, 여러 세션에 걸친 긴 컨텍스트가 필요한 넓은 에이전트 작업에는 gpt-5.5가 출발점으로 알맞다.
- 전문적인 코딩 작업에는 gpt-5.4를 명시적으로 써 보고 내 벤치마크 묶음으로 비교한다.
- 넓게 탐색하느라 토큰 비용이 많이 드는 서브에이전트 작업에는 더 저렴한 후보로 gpt-5.4-mini를 시험해 본다.

Codex는 config.toml의 `[model]` 표로 작업 종류별 모델을 자동 분기하지 않는다. 설정을 비교하고 싶으면 모델을 명시적으로 바꿔 실행한다.

```bash
codex -m gpt-5.5
codex -m gpt-5.4
codex exec --model gpt-5.4-mini "map this repository and identify the test commands"
```

중요한 습관은 벤치마크를 돌릴 때마다 어떤 모델을 썼는지 기록하는 것이다. CLI가 작업 종류를 보고 알아서 맞는 모델을 고르리라고 가정하면 안 된다.
