# 품질 벤치마크와 보완 평가

지금까지의 벤치마크는 대부분 작업을 끝냈는지만 본다. 이 문서는 그 맹점을 메우는 평가들을 정리한다. 코드 품질을 재는 SlopCodeBench, 코드 리뷰 능력, 명세서에서 코드를 만드는 PRDBench, 멀티 에이전트 조율을 평가하는 MAESTRO를 다루고, 마지막으로 벤치마크들이 이루는 신뢰도 위계를 정리한다.

---

## 1. SlopCodeBench: 완료가 아니라 품질

2026년 3월에 나온 SlopCodeBench는 기존 벤치마크의 맹점을 직접 겨냥한다. SWE-bench는 패치가 테스트를 통과했는지를, Terminal-Bench는 작업 흐름을 마쳤는지를 묻는다. SlopCodeBench는 코드가 커지는 동안에도 구조가 좋고 유지보수 가능한 상태로 남는지를 묻는다.

방식은 에이전트가 변하는 명세 아래에서 자기가 앞서 만든 해법을 반복해서 확장하게 하는 것이다. 그러면서 궤적 수준의 품질 신호 두 가지를 추적한다.

- **장황함(verbosity)**: 중복되거나 불필요한 코드의 비율
- **구조 침식(structural erosion)**: 복잡도가 소수의 함수에 몰리는 현상

원 논문 주석에 따르면 문제 20개와 체크포인트 93개로 구성되며, 가장 높은 체크포인트 해결률이 17.2%다. 품질은 꾸준히 나빠져서 구조 침식은 궤적의 80%에서, 장황함은 89.8%에서 증가한다.

초기 결과는 작업 완료 벤치마크에서 점수가 좋은 에이전트가 반드시 품질 좋은 코드를 내지는 않는다는 것을 보여 준다. 무작정 대입하는(brute-force) 방법으로 테스트만 통과시키는 모델은 SWE-bench에서는 점수가 좋아도 SlopCodeBench에서는 나쁘다. 처리량보다 코드베이스의 건강을 더 중시하는 팀이라면, 내 모델이 잘하는 벤치마크가 정말 신경 쓰는 것을 예측해 주지 않을 수 있다.

Codex CLI 사용자에게 시사점은, 작업 완료 벤치마크가 개선되더라도 훅 기반 품질 검사(린터, 스타일 강제, 작성 후 분석)가 여전히 필수라는 것이다. 모델이 문제를 풀 수는 있다. 그 해법이 내 코드베이스에 들어올 자격이 있는지는 별개의 질문이다.

## 2. 코드 리뷰 평가와 도입 데이터

OpenAI가 보고한 코드 리뷰 평가는 최상위 모델도 코드를 리뷰할 때 실제 결함의 상당 부분을 놓친다는 정성적 경고를 준다. Codex CLI의 내장 코드 리뷰 스킬이나 CodeRabbit 플러그인을 쓰는 팀은 이를 기대치 보정에 쓰면 된다. 자동 리뷰는 쓸모 있는 1차 점검이지 사람 리뷰의 대체물이 아니다.

## 3. PRDBench: 요구사항 문서에서 코드까지의 격차

PRDBench는 상하이 교통대와 메이퇀(Meituan) 팀이 만들었고(2025년 10월 arXiv 공개, AAMAS 2026 채택), 기존 벤치마크와 근본적으로 다른 능력을 잰다. 기존 버그를 고치거나 부분 구현을 마무리하는 것이 아니라, 제품 요구사항 문서(PRD)에서 소프트웨어를 만들어 내는 능력이다. 20개 분야의 실제 파이썬 프로젝트 50개로 구성되고 프로젝트마다 구조화된 PRD가 있다.

핵심 결과는 PRD에서 코드로 가는 격차가 버그 수정 격차보다 훨씬 크다는 것이다. 집필 시점에 리더보드 결과는 가장 강한 모델이 60%대 초중반, 약한 모델은 30%를 한참 밑돌았다. 명세서로 만드는 일에는 설계 결정, 의존성 선택, 통합 계획이 필요한데 수정 중심 벤치마크는 이를 시험하지 않기 때문이다. 모델별 순위는 프로젝트의 실시간 AGI-Eval 리더보드에 있고 논문에 고정돼 있지 않으니, 구체적 점수는 특정 시점의 값으로 보아야 한다.

Codex CLI 사용자에게는 새로 만드는 개발 작업의 기대치를 보정해 준다. 명세에서 새 서비스나 기능을 만드는 일(기업에서 흔한 패턴)이 업무라면 SWE-bench보다 PRDBench 점수가 에이전트 성능을 더 잘 예측한다. 또 구조화된 PRD를 주는 것이 모호한 프롬프트보다 해결률을 의미 있게 높인다는 점에서 명세 주도 개발 방식을 뒷받침한다.

## 4. MAESTRO: 멀티 에이전트 평가

MAESTRO(Multi-Agent Evaluation Suite for Testing, Reliability, and Observability)는 단일 에이전트 벤치마크의 공백, 곧 여러 에이전트를 나누어 맡기고 조율하는 일(오케스트레이션)의 품질을 평가한다. 핵심 발견은 멀티 에이전트 성능에서는 모델 선택보다 아키텍처 선택이 더 중요하다는 것이다. 에이전트를 어떻게 구성하는지, 어떤 상태를 공유하는지, 실패가 어떻게 전파되는지가 결정적이다. 조율이 잘된 시스템은 약한 모델로도 조율이 엉망인 강한 모델 시스템을 앞설 수 있다.

이 결과는 12장의 오케스트레이션 패턴을 뒷받침한다. 패턴 자체가 단순한 조직상의 편의가 아니라 성능 레버라는 뜻이다. MAESTRO는 내 오케스트레이션 구조가 실제로 도움이 되는지, 아니면 병렬화의 이득을 넘는 조율 비용을 만들고 있는지 측정하는 평가 방법을 제공한다.

## 5. 벤치마크 신뢰도 위계

2026년의 벤치마크 지형은 내 실제 업무에 얼마나 적용되는지에 따라 아래에서 위로 올라가는 위계를 이룬다.

| 위치 | 벤치마크 | 성격 |
|---|---|---|
| 맨 아래 | SWE-bench Verified | 약한 모델을 구별하는 데는 쓸모가 있으나 최상위에서는 변별력을 잃었다 |
| 그 위 | SWE-bench Pro | 여러 파일, 여러 언어 추론을 더 정직하게 재며 비공개 부분이 가장 오염에 강한 신호다 |
| 나란히 | Terminal-Bench 2.0 | Codex CLI 사용자에게 가장 관련 깊은 도메인 벤치마크. 터미널 중심이고 Docker 샌드박스이며 암기에 구조적으로 강하다 |
| 맨 위 | 내 벤치마크 묶음 | 실제 워크플로에서 나온 것으로, 내가 던지는 질문에 직접 답하는 유일한 평가다 |

공개된 숫자는 선택지를 좁히는 출발점이다. 최종 결정은 내 평가로 내린다.
