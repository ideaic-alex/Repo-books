# 공식 워크플로 레시피 여덟 가지

OpenAI 개발자 문서에는 Workflows 페이지가 있고, 소프트웨어 개발 생명주기 전반에서 Codex CLI를 쓰는 정석 패턴 여덟 가지가 정리되어 있다. 이 레시피들은 이 장 앞부분의 네 요소 프롬프트를 공식화한 공통 뼈대를 갖는다. 목표(Goal), 맥락(Context), 제약(Constraints), 완료 조건(Done-when)이다.

이 문서는 여덟 레시피를 표로 정리하고, 레시피를 오갈 때 프로필로 마찰을 줄이는 방법을 설명한다.

---

## 1. 여덟 가지 레시피

각 레시피는 알맞은 샌드박스 모드와 핵심 기법이 정해져 있다.

| 번호 | 레시피 | 샌드박스 모드 | 핵심 기법 |
|---|---|---|---|
| 1 | 코드베이스 설명 | read-only | @ 파일 퍼지 검색과 /plan 모드 |
| 2 | 버그 수정 | workspace-write | 오류 출력을 붙여 넣고 통과 기준을 정한다 |
| 3 | 테스트 작성 | workspace-write | 참고할 구현과 기존 테스트 규약을 지정한다 |
| 4 | 스크린샷으로 프로토타입 만들기 | workspace-write | -i 이미지 입력과 높은 추론 강도 |
| 5 | 리팩터링을 클라우드에 맡기기 | workspace-write | 로컬에서 /plan 후 클라우드로 제출 |
| 6 | 로컬 코드 리뷰 | read-only | /review 슬래시 명령 |
| 7 | GitHub PR 리뷰 | read-only | PR 댓글의 @codex 또는 codex exec |
| 8 | 문서 갱신 | workspace-write | 코드와 문서를 교차 참조하고 PostToolUse 린터 훅 |

### 표에서 읽을 수 있는 규칙

- 읽고 분석만 하는 레시피(설명, 로컬 리뷰, PR 리뷰)는 샌드박스를 read-only로 둔다. 코드를 바꿀 필요가 없으니 쓰기 권한을 주지 않는 쪽이 안전하다.
- 코드나 문서를 실제로 바꾸는 레시피(버그 수정, 테스트, 프로토타입, 리팩터링, 문서 갱신)는 workspace-write를 쓴다.
- 버그 수정은 오류 출력을 붙이고 통과 기준을 정한다는 점에서 버그 수정 패턴과 같고, 테스트 작성은 본보기 구현을 가리킨다는 점에서 맥락 요소의 활용이다.
- 문서 갱신 레시피의 PostToolUse 린터 훅(hook, 특정 시점에 자동 실행되는 스크립트)은 도구 사용 직후 린터가 돌아가게 하는 장치다.

## 2. 프로필로 레시피 전환하기

레시피를 바꿀 때마다 샌드박스 모드와 승인 정책을 손으로 바꾸면 번거롭다. 레시피별 프로필을 만들어 두면 이 마찰이 사라진다.

```toml
# ~/.codex/explore.config.toml
sandbox_mode = "read-only"
model_reasoning_effort = "high"

# ~/.codex/fix.config.toml
sandbox_mode = "workspace-write"
approval_policy = "on-request"
```

```toml
# ~/.codex/review.config.toml
sandbox_mode = "read-only"
approval_policy = "never"
```

| 프로필 | 샌드박스 | 승인 정책 | 추론 강도 |
|---|---|---|---|
| explore | read-only | 지정 없음 | high |
| fix | workspace-write | on-request | 지정 없음 |
| review | read-only | never | 지정 없음 |

리뷰 프로필은 읽기 전용이어서 승인 정책을 never로 두어도 위험이 작다고 볼 수 있다. 수정 프로필은 쓰기가 가능하므로 on-request를 둔다. 이 해석은 위 설정 값에서 도출한 것이며, 원서가 각 값의 이유를 따로 설명하지는 않는다.
