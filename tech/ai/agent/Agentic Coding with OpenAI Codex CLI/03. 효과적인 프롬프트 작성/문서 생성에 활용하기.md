# 문서 생성에 활용하기

Codex CLI는 코드만 쓰는 도구가 아니다. 저장소 전체를 읽고 코드 구조를 파악할 수 있어서, 프로젝트 문서를 만들고 최신 상태로 유지하는 일에도 잘 맞는다. 이 문서는 코드 주석, ADR, README, 문서 신선도 점검까지 네 가지 활용법을 정리한다.

---

## 1. 코드 문서 주석

코드베이스 전체에 언어에 맞는 문서 주석을 달 수 있다. JavaScript나 TypeScript라면 JSDoc 방식으로 이렇게 지시한다.

```text
Add JSDoc comments to all exported functions in src/api/.
Follow the existing style in src/api/users.ts.
Include @param, @returns, and @throws tags.
Do not change any implementation code.
```

Python 프로젝트에서는 같은 패턴을 docstring(함수 설명 문자열)에 적용한다.

```text
Add Google-style docstrings to all public functions in src/services/.
Include Args, Returns, and Raises sections.
Follow the pattern in src/services/auth.py.
```

핵심은 문서 스타일(JSDoc, Google 스타일, NumPy 스타일, rustdoc 등)을 지정하고, 기존에 잘 쓴 예시 파일을 가리키는 것이다. 스타일 기준이 없으면 Codex CLI는 내용은 맞지만 일관성이 없는 문서를 만든다. 또 마지막 줄의 '구현 코드는 바꾸지 말 것' 같은 제약이 주석 작업이 로직을 건드리는 사고를 막는다.

## 2. 아키텍처 결정 기록(ADR)

ADR(Architecture Decision Record, 중요한 기술 결정의 이유를 남기는 문서)은 결정의 배경을 기록한다. Codex CLI는 코드 맥락과 짧은 프롬프트를 합쳐 초안을 쓸 수 있다.

```text
Write an ADR for the decision to migrate from Express to Fastify.
Read the current Express routes in src/api/ and the new Fastify
routes in src/api-v2/. Include the context, decision, consequences,
and alternatives considered. Save to docs/adr/0012-fastify-migration.md.
Follow the format in docs/adr/0001-template.md.
```

이 프롬프트에서 눈여겨볼 점은 다음과 같다.

- 읽을 코드 위치를 두 곳(기존 Express 라우트, 새 Fastify 라우트)으로 정확히 알려 준다.
- 담을 항목을 정한다. 배경, 결정, 결과, 검토한 대안이다.
- 저장 경로와 파일 이름을 정한다.
- 기존 템플릿 파일을 형식의 기준으로 준다.

## 3. README와 온보딩 문서

새 프로젝트이거나 문서가 코드를 따라가지 못한 프로젝트에서는, 저장소 구조와 의존성과 설정을 읽게 해서 온보딩(신규 합류자용 안내) 문서를 만들 수 있다.

```text
Generate a README.md for this project. Read the package.json, the
src/ directory structure, and the existing AGENTS.md. Include:
- Project overview (one paragraph)
- Prerequisites and installation steps
- Development workflow (build, test, lint)
- Project structure overview
- Contributing guidelines
Do not include badges or shields.
```

읽을 파일과 담을 항목을 정해 주고, 원치 않는 요소(배지)는 제약으로 막아 둔 것이 특징이다. 이미 있는 AGENTS.md를 입력으로 넣으면 빌드와 테스트 명령 같은 정보를 다시 설명하지 않고 가져올 수 있다.

## 4. 문서 신선도를 CI에서 점검하기

문서 부패(documentation rot)는 문서가 이미 사라진 코드를 설명하는 흔한 문제다. Codex CLI로 이를 탐지할 수 있다. 원서의 예는 codex exec(비대화형으로 한 번 실행하는 명령)를 읽기 전용 샌드박스로 돌려, 문서와 실제 공개 API를 비교하게 한다.

```bash
codex exec --sandbox read-only \
 "Compare the public API documented in docs/api.md with the actual
 exports in src/index.ts. List any functions that are documented
 but no longer exist, and any functions that exist but are not
 documented." \
 -o /tmp/doc-audit.md
```

이 명령은 두 방향의 불일치를 찾는다. 문서에는 있지만 코드에서 사라진 함수, 코드에는 있지만 문서에 없는 함수다. 결과는 -o 옵션이 지정한 파일에 저장된다. 읽기 전용 샌드박스라서 점검 과정에서 파일이 바뀔 걱정은 없다.

이 점검을 주기적인 CI 작업으로 돌리면, 문서가 코드와 어긋나는 현상이 쌓이기 전에 잡을 수 있다.
