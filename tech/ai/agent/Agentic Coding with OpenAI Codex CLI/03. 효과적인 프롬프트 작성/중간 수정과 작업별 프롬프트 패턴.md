# 중간 수정과 작업별 프롬프트 패턴

에이전트가 엉뚱한 방향으로 갈 때 어떻게 개입하는지, 그리고 버그 수정, 리팩터링, 병렬 작업처럼 자주 하는 일에는 프롬프트를 어떻게 짜는지 정리한다. 앞 문서의 네 요소(목표, 맥락, 제약, 완료 기준)를 실제 작업 유형에 적용한 모습이라고 보면 된다.

---

## 1. 세션 도중에 바로잡기

Codex CLI가 잘못된 방향으로 가면 바로 끊는다. Esc를 누르면 지금 진행 중인 단계가 멈춘다. 단계가 실행되는 동안에는 REPL 아래쪽 상태 표시줄에 `esc to interrupt`라고 뜬다. 멈춘 뒤에 정정 지시를 입력한다.

정정 지시도 첫 프롬프트와 같은 구조로 쓴다. 원서의 예는 다음과 같다. 멈추라고 말하고, 무엇을 되돌릴지 정하고, 대신 어디에서 처리할지 알려 준다.

```text
Stop. Revert the changes to src/db/schema.ts and instead handle the
migration in src/db/migrations/.
```

### 컨텍스트 관리 명령

- `/compact`: 쌓인 기록이 최근 결정을 밀어낼 때 쓴다. 대화 기록을 압축해 컨텍스트 윈도(context window, 모델이 한 번에 볼 수 있는 입력 범위)를 비운다.
- `/fork`: 같은 출발점에서 두 가지 접근을 따로 탐색하고 싶을 때 쓴다.

두 명령은 7장에서 자세히 다룬다. 컨텍스트 윈도가 어떻게 차는지, 압축이 무엇을 남기고 무엇을 버리는지, 위험한 작업 전에 언제 fork 하는지가 거기에 나온다.

### 고치지 말고 다시 쓸 때

프롬프트에 두 가지 해석이 가능했던 탓에 세션이 엉뚱한 결과를 냈다면, 정정을 거듭하지 말고 멈춘 뒤 프롬프트를 다시 쓴다. 원인이 애초의 모호함이기 때문에 정정 위에 정정을 쌓아도 같은 모호함이 남는다.

## 2. 버그 수정 패턴

버그 수정 프롬프트에는 관찰된 동작, 기대하는 동작, 재현 단계를 넣는다. 거기에 수정 위치, 회귀 테스트 요구, 건드리면 안 되는 파일까지 적는다.

```text
Bug: Checkout page throws unhandled promise rejection with expired card.
Observed: "CardError: card_expired" in server logs. User sees 500 page.
Expected: User sees "Your card has expired. Please update your payment
method."
Reproduce: Run __tests__/checkout/payment.test.ts "handles expired card"
case.
Fix in src/checkout/payment.ts. Include regression test.
Do not change src/payments/stripe.ts.
```

재현 단계를 실행 가능한 테스트 하나로 주면, 에이전트가 고친 뒤에 같은 테스트로 스스로 확인할 수 있다. 이것이 곧 완료 기준이 된다.

## 3. 리팩터링 패턴

리팩터링에서는 동작을 보존한다는 점을 명시적으로 밝힌다. 리팩터링은 겉으로 드러나는 동작이 바뀌지 않아야 하는 작업인데, 이를 말해 주지 않으면 에이전트가 '겸사겸사' 시그니처나 구조를 바꿔 버릴 수 있다.

```text
Refactor src/notifications/sender.ts: replace .then()/.catch() with async/
await.
Public API must not change. Run npm test after each function. Do not
change other files.
```

이 예시는 변경 범위(파일 하나), 보존 대상(공개 API), 검증 주기(함수마다 npm test)를 모두 정해 준다.

## 4. 병렬로 할 수 있는 작업

서로 독립적인 작업이라면 독립적이라고 분명히 말해 준다. 그러면 Codex CLI가 병렬로 처리할 여지를 얻는다. 원서의 예시는 세 모듈의 단위 테스트를 동시에 쓰게 하는 프롬프트다.

```text
Write unit tests for these three modules in parallel:
- src/auth/validate.ts
- src/payments/process.ts
- src/notifications/sender.ts
Use helpers in __tests__/helpers.ts and patterns in __tests__/auth/
token.test.ts.
```

세 모듈 모두 같은 도우미 파일과 같은 본보기 테스트를 참고하도록 경로를 지정한 점도 눈여겨볼 만하다. 맥락을 한 번에 주고 작업만 나누는 방식이다. 연습 문제 3-4에서는 이렇게 독립 작업을 표시한 프롬프트와 순차 실행의 소요 시간을 비교해 본다.

## 5. 패턴 요약

| 작업 유형 | 프롬프트에 꼭 넣을 것 |
|---|---|
| 버그 수정 | 관찰된 동작, 기대 동작, 재현 단계, 수정 위치, 회귀 테스트, 건드리지 말 파일 |
| 리팩터링 | 동작 보존 선언, 공개 API 불변, 검증 명령과 주기, 범위 제한 |
| 병렬 작업 | 작업이 독립적이라는 표시, 공통 도우미와 본보기 경로 |
| 모호한 대형 작업 | 직접 실행하지 말고 플랜 모드나 PLANS.md로 시작 |
