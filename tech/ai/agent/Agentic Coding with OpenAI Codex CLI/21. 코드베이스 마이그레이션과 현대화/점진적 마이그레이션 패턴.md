# 점진적 마이그레이션 패턴

현실의 마이그레이션은 대부분 세 가지 패턴으로 설명된다. 어떤 패턴을 고를지는 모듈 사이의 결합도와, 옛 코드와 새 코드가 함께 있는 기간을 얼마나 견딜 수 있느냐에 달려 있다. 여기에 병렬 서브에이전트를 더해 선택지를 표와 결정 트리로 정리한다.

---

## 1. 세 가지 패턴

**파일 단위(file-by-file).** 가장 단순하다. 파일 하나를 세션 하나로 처리하고, 테스트를 돌리고, 통과하면 커밋한다. 느리지만 변경 이력을 추적하기(auditable)가 가장 좋다. 커밋 하나가 변환된 파일 하나에 대응하므로 git bisect를 하면 항상 특정 변경을 가리킨다.

**모듈 단위(module-by-module).** 응집된 단위(패키지, 디렉터리, 기능 조각)를 세션 하나에 묶어 처리한다. 에이전트가 모듈의 파일을 한꺼번에 보기 때문에 파일 간 참조를 추측하지 않고 풀 수 있다. 대신 배치가 실패하면 원인을 좁히기 어렵다. 파일끼리 강하게 얽혀서 에이전트가 안전하게 하나를 바꾸려면 여러 파일을 읽어야 할 때 쓴다.

**스트랭글러 피그(strangler fig).** 코드베이스가 너무 크거나, 마이그레이션이 너무 파괴적이거나, 사업 쪽에서 기능 개발을 멈출 수 없을 때 쓴다. 새 구현을 옛 구현 옆에 두고, 새 코드는 새 구현으로 보내고, 옛 경로를 조금씩 없앤다. Codex CLI는 새 구현 생성, 호출 지점 갱신, 남은 사용처 감사의 모든 단계를 돕는다.

원문 각주에 따르면 이 패턴은 새 시스템을 기존 시스템 옆에서 점진적으로 지어 가며 기능을 하나씩 옮기다가, 마지막에 원래 시스템을 폐기하는 전략이다. 마틴 파울러는 한 번에 갈아엎는 빅뱅 재작성보다 이 방식을 낫다고 본다. 가치를 계속 내놓을 수 있고 되돌릴 길이 남기 때문이다. 이름은 숙주 나무를 감싸 자라다가 결국 대체하는 스트랭글러 피그 나무에서 왔다. 전환기 동안은 숙주가 구조를 지탱해 준다. 파울러는 2004년 글에서 이 용어를 대중화했고, 지금도 소프트웨어 공학에서 가장 쓸모 있는 마이그레이션 비유 중 하나로 꼽힌다.

## 2. 패턴 선택표

| 패턴 | 언제 쓰나 | 배치 크기 | 롤백 비용 |
|---|---|---|---|
| 파일 단위 | 결합도가 낮고 감사 요구가 높을 때 | 파일 1개 | 최소. 커밋 하나를 되돌린다 |
| 모듈 단위 | 모듈 내부 결합도가 높고 경계가 분명할 때 | 5~30개 파일 | 중간. 배치 하나를 되돌린다 |
| 스트랭글러 피그 | 코드가 크고 기능 개발을 멈출 수 없거나 부분 마이그레이션이 허용될 때 | 계속 진행 | 낮음. 옛 경로가 항상 살아 있다 |
| 병렬 서브에이전트 | 모듈이 독립적이고 일정이 급할 때 | 여러 모듈 동시 | 중간. 병합 전에 검증한다 |

## 3. 결정 트리

원서의 그림 21.1은 패턴을 고르는 결정 트리다.

> 원서 그림 설명(약 438쪽, 글로 풀어 씀): 그림 21.1 마이그레이션 패턴 고르기. 기능 개발을 멈출 수 있는지, 모듈이 독립적이고 일정이 급한지, 모듈 내부 결합이 높은지를 차례로 묻는 흐름도.

그림을 글로 풀면 이렇다.

1. 먼저 코드베이스에서 기능 개발을 멈출 수 있는지 묻는다. 멈추기에 너무 크다면 스트랭글러 피그를 고른다. 새 경로를 옛 경로 옆에 두고 옛 경로를 점진적으로 걷어낸다.
2. 멈출 수 있다면 다음 질문은 모듈이 서로 독립적이고 시간에 쫓기는가이다. 그렇다면 병렬 서브에이전트로 여러 모듈을 동시에 처리하고, 병합 전에 검증한다.
3. 아니라면 마지막 질문은 모듈 내부 결합이 높은가이다. 높으면 모듈 단위로, 세션마다 5~30개 파일 한 묶음을 처리한다. 높지 않고 감사 가능성을 최대로 원하면 파일 단위로, 세션마다 파일 하나를 처리하고 문제가 생기면 커밋 하나만 되돌린다.
