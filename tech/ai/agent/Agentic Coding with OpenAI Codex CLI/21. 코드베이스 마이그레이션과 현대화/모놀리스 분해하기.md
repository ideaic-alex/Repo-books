# 모놀리스 분해하기

모놀리스(하나로 뭉친 큰 애플리케이션)를 서비스로 쪼개는 일은 스트랭글러 피그 패턴을 가장 큰 규모로 적용하는 것이다. 지켜야 할 규율도 같다. 먼저 이해하고, 조금씩 추출하고, 새 경로가 검증될 때까지 옛 경로를 살려 둔다. Codex CLI는 사람이 지루해하는 양 끝, 즉 이음새를 찾는 일과 동작이 같음을 증명하는 일에서 가장 큰 도움이 된다. 중간의 아키텍처 판단은 사람의 몫이다.

---

## 1. 의존성 분석으로 이음새 찾기

에이전트를 읽기 전용 모드로 두고 모듈 수준 의존성을 그리게 한 뒤, 결합도 기준으로 서비스 후보의 순위를 매기게 한다. 볼 항목은 다음과 같다.

- 들어오는 의존성과 나가는 의존성의 개수
- 공유하는 데이터 테이블
- 순환 의존성

첫 시범 대상은 가장 골치 아픈 모듈이 아니라, 결합도가 낮고 데이터 경계가 깨끗한 모듈이어야 한다. 다른 모듈 세 개도 건드리는 테이블을 읽고 쓰는 모듈은 서비스 경계가 아니라 함정이다. 가장 날카로운 시험은 데이터베이스 소유권이다. 서비스 후보 두 개가 같은 테이블에 써야 한다면 경계가 잘못된 곳에 그어진 것이다.

## 2. 구현보다 계약을 먼저

추출할 서비스의 API 계약, 즉 OpenAPI 문서를 에이전트가 서비스 코드를 쓰기 전에 먼저 만들게 한다. 검토할 수 있는 계약은 경계 실수를 아직 값쌀 때 잡아 준다. 또 구현과 테스트를 대조할 명세가 된다. 이 장 앞에서 말한 계획 규율을 서비스 수준에 적용한 것이다. 여기서는 계약이 곧 계획이다.

## 3. 뒤집을 수 있는 이음새로 라우팅

서비스를 라우팅 계층 뒤에 추출한다. API 게이트웨이나 리버스 프록시가 시범 서비스의 엔드포인트는 새 서비스로, 나머지는 모놀리스로 보낸다. 이 전환 스위치를 기능 플래그 뒤에 두면 트래픽 일부만 넘기고, 지켜보고, 재배포 없이 즉시 되돌릴 수 있다. 새 서비스가 트래픽을 받을 자격을 얻을 때까지는 모놀리스가 진실의 원천(source of truth)으로 남는다.

## 4. 검증은 더 엄격해진다

검증 규율은 그대로이거나 오히려 강해진다. 추출된 엔드포인트는 실제 트래픽을 받기 전에, 모놀리스의 기존 통합 테스트를 새 서비스에 대고 돌려서 통과해야 한다. 분해는 움직이는 부품을 늘린다. 부품이 늘어난다고 사고까지 늘어나지 않게 막아 주는 것이 이 테스트 관문이다.

## 5. 정리

| 단계 | 할 일 | 에이전트의 역할 |
|---|---|---|
| 이음새 찾기 | 결합도 분석, 후보 순위 | 읽기 전용으로 분석 |
| 계약 정의 | OpenAPI 문서 작성 | 초안 생성, 사람이 검토 |
| 라우팅 | 게이트웨이와 기능 플래그 | 설정과 호출 지점 갱신 |
| 검증 | 기존 통합 테스트를 새 서비스에 실행 | 반복 실행과 결과 보고 |
