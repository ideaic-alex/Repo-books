# 마이그레이션에 에이전트가 맞는 이유

마이그레이션 작업은 사람이 손으로 하면 지루하고 실수하기 쉽다. 파일 이름 하나를 바꾸고 세 디렉터리 건너에 있는 참조를 놓쳐서, 오후 내내 뒷수습만 하는 일이 흔하다. 이 문서는 왜 마이그레이션이 Codex CLI 같은 에이전트형 도구와 특히 잘 맞는지, 그 네 가지 성질을 정리한다.

에이전트는 지치지 않고, 테스트 파일에 있는 import를 깜빡하지도 않는다. 수십 개 모듈에 병렬로 돌릴 수도 있다. 그동안 사람은 계획을 검토하는 일에 집중하면 된다.

---

## 1. 이 장이 다루는 범위

이 장은 마이그레이션을 한 번의 배치 작업부터 모놀리스 분해, 언어 전체를 갈아엎는 재작성까지 단계별로 다룬다. 크게 다섯 가지를 익히는 것이 목표다.

- 레거시 시스템을 건드리기 전에 읽기 전용 탐색을 돌려 현대화 보고서와 위험 목록(risk register)을 만든다.
- Codex CLI 계획 세션으로 우선순위가 매겨지고 검증된 마이그레이션 계획을 만든다.
- 현재 배치가 테스트를 통과하기 전에는 다음으로 넘어가지 못하게 막는 배치 검증 루프를 구현한다.
- 결합도 분석, 계약 우선 추출, 기능 플래그 라우팅으로 모놀리스를 쪼갠다.
- 큰 재작성은 테스트만 보지 않고 동작 일치, 건전성, 관용구, 보안, 성능의 층으로 나누어 검증한다.

## 2. 마이그레이션이 에이전트에 맞는 네 가지 성질

**기계적이고 규칙이 분명하다.** 마이그레이션은 변환 규칙으로 정의된다. React.Component를 함수 컴포넌트로 바꾸기, CLAUDE.md를 AGENTS.md로 바꾸기, print 문을 print()로 바꾸기 같은 식이다. 에이전트는 이미 정해진 규칙을 넓은 범위에 일관되게 적용하는 데 강하다. 이 작업에서는 패턴 매칭이 장점이고 창의적인 즉흥 대응은 오히려 위험하다. 그래서 좋은 마이그레이션 프롬프트는 창의성을 억누른다. "이 변환만 적용하고 다른 건 리팩터링하지 마라" 같은 식이다.

**범위를 나누기 쉽다.** 마이그레이션에는 파일, 모듈, 패키지처럼 자연스러운 작업 단위가 있고, 이 단위가 Codex CLI 세션 하나와 잘 맞는다. 파일 스무 개를 묶어 에이전트를 돌리고, 테스트를 돌리고, 커밋하고, 다음으로 넘어가면 된다. 범위가 정해져 있으니 컨텍스트 윈도를 감당할 만한 크기로 유지할 수 있고, 검토와 롤백을 할 수 있는 체크포인트도 자연스럽게 생긴다.

**테스트로 검증할 수 있다.** 의미 있는 마이그레이션은 대부분 기존 테스트 스위트로 검증된다. 배치 전후에 테스트가 모두 통과하면 변환이 동작을 보존했다는 뜻이다. 이 원리가 뒤에 나오는 검증 전략의 바탕이다.

**병렬로 돌릴 수 있다.** 모듈끼리 변경 가능한 상태(mutable state)를 공유하지 않으면 동시에 옮길 수 있다. 11장의 서브에이전트가 이 방법을 구체화해 준다. 패키지마다 에이전트 하나를 띄우고, 결과를 모아 검증한 뒤 병합하는 식이다. 순차로 하면 2주 걸릴 일이 몇 시간짜리 병렬 실행과 집중된 사람 검토로 줄어든다.

## 3. 역할 분담

마이그레이션에는 새로운 발상이 거의 필요 없다. 어떻게 옮길지는 사람이 정하고, 에이전트는 그 결정을 엣지 케이스를 잊지 않고 큰 규모로 실행한다. 이 분담이 장 전체를 관통한다. 규칙을 정의하고, 에이전트가 표시해 둔 애매한 경우를 검토하고, 규칙이 처리하지 못하는 판단을 내리는 것이 사람의 몫이다.
