# 훅 운영 도구

훅 스크립트를 만들고 나면 다음 문제는 운영이다. 훅이 실제로 어떻게 동작하는지 보고, 파일을 고치지 않고 켜고 끄고, 팀 전체에 배포하고, 위임된 결정을 TUI에서 눈으로 확인할 수 있어야 한다. 이 문서는 `/hooks` 브라우저, OpenTelemetry 지표, 플러그인에 묶은 훅, 위임된 패치 승인 표시를 다룬다.

---

## 1. /hooks 브라우저

세션에서 `/hooks`를 입력하면 런타임 브라우저가 열린다. 이벤트별로 설치된 훅 수와 현재 활성인 훅 수를 보여 준다. 원서의 예시 화면을 요약하면 다음과 같다.

| 이벤트 | Installed | Active |
|---|---|---|
| PreToolUse | 1 | 1 |
| PermissionRequest | 0 | 0 |
| PostToolUse | 3 | 2 |
| PreCompact | 1 | 1 |
| PostCompact | 1 | 1 |
| SessionStart | 1 | 1 |
| UserPromptSubmit | 2 | 1 |
| SubagentStart | 1 | 1 |
| SubagentStop | 1 | 0 |
| Stop | 1 | 1 |

두 열이 중요하다. Installed는 모든 설정 출처에서 발견된 훅 정의의 수다. 프로젝트 `hooks.json`, `config.toml`의 인라인 `[[hooks]]` 블록, 관리형 `requirements.toml`, 플러그인 번들이 모두 포함된다. Active는 그중 지금 켜져 있는 수다.

위 화면의 상황은 이렇게 읽는다. 개발자가 PostToolUse 훅 세 개(테스트 러너, 비밀 값 검사, MITM 검사)를 설치해 뒀는데, 디버깅하는 동안 테스트 러너를 꺼 놓았다. 또 느린 SubagentStop 품질 관문은 아예 꺼져 있다.

### 1.1 훅 켜고 끄기

브라우저에서 훅을 설정에서 지우지 않고 개별적으로 켜고 끌 수 있다. 느린 PostToolUse 훅을 로컬 개발에서는 돌리되 헤드리스 `codex exec` 실행에서는 건너뛰고 싶을 때 유용하다.

토글 상태는 영구적이다. 켜고 끈 결정이 `$CODEX_HOME` 아래에 저장돼 세션 재시작, 샌드박스 초기화, 기기 재부팅 뒤에도 남는다. 다만 관리형 `requirements.toml` 정책이 저장된 상태보다 우선한다. 관리자가 의무화한 훅은 개발자가 영구적으로 끌 수 없다.

호출 횟수, 소요 시간, 실패율 같은 호출별 통계는 브라우저가 아니라 다음에 설명하는 OpenTelemetry 파이프라인으로 본다.

## 2. 훅 실행의 OpenTelemetry 지표

훅은 구조화된 OpenTelemetry 스팬(span)을 내보낸다. 호출 하나가 이벤트 종류, 훅 명령, 종료 코드, 실제 소요 시간이 태그로 붙은 스팬 하나를 만든다. 스팬은 OTEL 호환 수집기라면 어디로든 흘러가므로 Datadog, Grafana, Honeycomb 같은 스택을 쓰는 팀은 별도 연결 작업 없이 훅 지연, 실패율, 호출 분포를 모니터링할 수 있다.

시작점은 `[otel]` 아래에 OTLP 익스포터를 설정하는 것이다. 훅 스팬은 다른 모든 것과 같은 익스포터로 나가며, 훅만 따로 켜는 스위치는 없다.

```toml
# .codex/config.toml
[otel]
trace_exporter = { kind = "otlp-http", endpoint = "http://localhost:4317", protocol = "grpc" }
metrics_exporter = { kind = "otlp-http", endpoint = "http://localhost:4317", protocol = "grpc" }
```

스팬이 쌓이면 "어떤 PreToolUse 훅이 지연을 가장 많이 늘리는가", "PostToolUse 호출 중 0이 아닌 종료 코드로 끝나는 비율은 얼마인가" 같은 질문에 답하는 대시보드를 만들 수 있다. 여러 이벤트에 걸쳐 훅이 수십 개 있는 팀에게는 훅 성능이 블랙박스에서 일급 관측 대상으로 바뀐다. 실시간 대시보드와 장기 보관용 기록을 모두 얻으려면 OpenTelemetry 지표를 감사 로그 패턴과 함께 쓴다.

팀 환경에서 훅을 배포할 때는 Codex CLI 버전을 고정하고, 올리기 전에 변경 기록(changelog)을 확인하라는 것이 원서의 당부다.

## 3. 플러그인에 묶은 훅

훅은 독립 스크립트가 아니라 플러그인 안에 담아 배포할 수 있다. 플러그인에 `hooks/` 디렉터리와 훅 정의가 들어 있으면 플러그인을 설치할 때 그 훅이 같이 등록된다. `hooks.json`을 직접 고칠 필요가 없다. 마켓플레이스를 등록(`codex plugin marketplace add owner/repo`)하고 그 안의 플러그인을 설치하면, PostToolUse 비밀 값 검사기와 PreToolUse 명령 정책 검사기를 한 번에 연결할 수 있다.

훅은 플러그인의 생애 주기를 따른다. 플러그인을 제거하면 훅도 사라지고, 업데이트하면 훅도 업데이트된다. 관리형 `requirements.toml`이 특정 플러그인(그리고 거기 딸린 훅)을 의무화할 수 있어서 기업 관리자에게 깔끔한 강제 경로가 생긴다. 플러그인을 요구하면 훅이 따라온다.

## 4. 위임된 패치 승인의 표시

패치 승인을 위임한 경우, 예를 들어 자동 리뷰어(`auto_review`)나 직접 만든 PermissionRequest 훅에 맡긴 경우, TUI가 위임 상세를 보여 준다. 리뷰어가 누구인지, 위험 수준은 어떤지, 승인이 자동이었는지 사람에게 올려졌는지를 표시한다. 낮은 위험 변경은 훅이, 높은 위험 변경은 사람이 보는 복합 승인 방식을 쓰는 팀에게는 이 시각적 구분이 신뢰 경계를 한눈에 보이게 해 준다.

## 5. 운영 도구 요약

| 도구 | 하는 일 | 상태 저장 |
|---|---|---|
| `/hooks` 브라우저 | 이벤트별 Installed/Active 확인, 개별 훅 켜고 끄기 | `$CODEX_HOME`에 영구 저장 |
| OpenTelemetry | 호출별 스팬(이벤트, 명령, 종료 코드, 소요 시간) 수집 | 외부 수집기 |
| 플러그인 번들 | 훅을 설치·제거·업데이트와 함께 배포 | 플러그인 생애 주기 |
| 위임 승인 표시 | 리뷰어, 위험 수준, 자동/에스컬레이션 여부 표시 | TUI 표시 |
