# 튼튼한 훅 작성 원칙

훅은 에이전트가 일하는 길목에 동기로 끼어드는 코드다. 느리거나 불안정한 훅 하나가 세션 전체를 느리게 하거나 멈추게 할 수 있다. 이 문서는 원서가 정리한 훅 작성 원칙을 이유와 함께 풀어 쓴다.

---

## 1. 타임아웃은 짧게 잡는다

훅이 동기로 돌기 때문에 시간이 곧 대기 시간이다. UserPromptSubmit 훅에 30초를 주면 프롬프트를 낼 때마다 30초씩 기다린 뒤에야 모델이 움직인다. 원서가 제시하는 대략의 기준은 다음과 같다.

| 훅의 성격 | 권장 타임아웃 |
|---|---|
| 정책 검사 | 5초 |
| 컨텍스트 주입 | 10~15초 |
| 테스트 러너 | 30~60초 |

## 2. stdout 크기를 지킨다

SessionStart와 UserPromptSubmit의 stdout은 모델 컨텍스트에 들어간다. 제한 없는 로그 덤프는 수천 토큰을 조용히 먹어 치운다. 모델에게 필요한 만큼만 잘라 내보내야 한다. 앞 문서의 예제들이 `tail -5`, `head -20`, `[-2000:]`처럼 출력을 자른 이유가 이것이다.

## 3. 의존성이 없을 때는 조용히 넘어간다

venv가 없거나 Slack 토큰이 없는 것처럼 의존성이 빠졌을 때는 exit 2로 세션을 막지 말고 조용히 exit 0으로 끝내야 한다. exit 2는 의도한 정책 거부에만 쓴다. 비밀 값 검사 스크립트가 `gitleaks`가 없으면 곧바로 `exit 0`하는 것이 그 예다.

## 4. 훅 상태 표시를 이해한다

훅의 상태 메시지는 TUI의 전용 실시간 영역에 표시된다. 동작 방식은 이렇다.

- 표시는 300ms 지연 후에 나타난다. 빨리 끝나는 훅에서 화면이 깜빡이는 것을 막기 위해서다.
- 훅이 끝난 뒤에도 600ms 동안 남아 결과를 읽을 수 있다.
- 여러 훅이 한꺼번에 실행되면 간결한 한 줄 상태로 합쳐진다.

따라서 `statusMessage`는 한눈에 무엇을 하는지 알 수 있게 쓰는 것이 좋다. 화면 공간을 다른 메시지와 나눠 쓰게 된다.

## 5. 훅은 따로 떼어 시험한다

`hooks.json`에 넣기 전에 터미널에서 스크립트를 직접 실행해 본다. 종료 코드, stdout, stderr가 기대와 맞는지 확인한다. stdin JSON을 받는 훅이라면 파이프로 예시 JSON을 넣어 보면 된다.

## 6. 개발 중에는 시끄럽게 실패시킨다

bash 훅에는 개발 중에 `set -euo pipefail`을 넣어 오류를 일찍 잡는다. 운영에 올릴 때는 더 선택적인 오류 처리로 바꾼다. 반복해서 고치는 동안에는 조용한 실패가 시끄러운 실패보다 디버깅하기 어렵기 때문이다. 다만 3번 원칙과 부딪히지 않도록 주의한다. 개발 때는 엄격하게, 운영에서는 의존성 부재 같은 예상 가능한 상황을 골라서 부드럽게 처리한다.

## 7. 종료 코드 규약 다시 보기

| 종료 코드 | 의미 |
|---|---|
| 0 | 성공. 이벤트에 따라 stdout이 주입된다 |
| 2 | 막기. 막을 수 있는 이벤트에서는 stderr 메시지와 함께 차단, 아닌 이벤트에서는 오류 기록 후 진행 |
| 그 밖 | 조용한 실패 |

## 8. 점검 목록

- 이 훅은 정말 동기로 돌려야 하는가. 알림처럼 결과를 기다릴 필요가 없다면 가볍게 만든다.
- 타임아웃이 이벤트 성격에 맞는가.
- stdout이 컨텍스트 윈도를 낭비하지 않는가.
- 의존성이 없을 때 exit 0으로 물러나는가.
- exit 2는 의도한 정책 거부에만 쓰는가.
- `hooks.json`에 넣기 전에 단독으로 시험했는가.
