# 부록 C 스킬 템플릿 (Skill Templates)

부록 C는 복사해 고쳐 쓰라고 만든 스킬 견본 네 개를 싣는다. 책의 설명대로 스킬은 이름과 짧은 설명, 그리고 구체적인 절차가 적힌 파일 하나다. 맨 위 `---` 사이의 이름과 설명을 Claude가 읽고 이 스킬을 쓸지 판단하므로, 설명에는 내가 실제로 쓸 법한 표현을 담아야 한다. 본문 절차는 구체적일수록 결과가 매번 일정해진다. 이 노트는 견본을 옮기지 않고 구조와 고쳐 쓸 곳을 정리한다.

> **쉽게 말하면**
> "무엇을 할 때 작동하고, 어떤 순서로 하며, 무엇은 절대 하지 않는지"를 적어 둔 업무 매뉴얼이다.

## 1. 스킬 파일의 뼈대

| 부분 | 역할 |
|------|------|
| 앞머리(front matter)의 이름 | 스킬을 부르는 짧은 이름 |
| 앞머리의 설명 | 언제 이 스킬이 작동해야 하는지. 판단의 근거가 되는 문장 |
| 본문의 단계(Steps) | 따라야 할 절차와 출력 모양 |
| 본문의 규칙(Rules) | 어기면 안 되는 금지선 |
| "어떻게 고쳐 쓸까" 메모 | 책이 견본마다 붙인, 바꿀 만한 부분 안내 |

## 2. 네 가지 견본

| 견본 | 하는 일 | 핵심 설계 | 책이 권하는 조정 |
|------|---------|-----------|-----------------|
| 회의록 요약 | 녹취나 메모를 항상 같은 모양으로 정리 | 고정된 제목 순서, 결정·할 일·미결 질문 분리 | 팀 방식에 맞춰 제목 변경. 지어내지 말라는 규칙은 그대로 둘 것 |
| 브랜드 보이스 | 회사 말투로 글 작성 | 하는 것·하지 않는 것·실제 글 견본 2~3개 | 견본 선택에 공을 들이고, 금지 목록은 짧고 구체적으로 |
| 주간 보고서 | 매주 같은 보고서 생성 | 고정 구조, 값이 없으면 "미보고", 입력에 없는 성과 금지 | 독자가 실제로 행동하는 항목 중심으로, 위험·요청 항목 추가 |
| 데이터 정리 | 표 데이터를 투명하게 정리 | 점검, 진단, 계획 제시, 승인된 것만 실행, 보고 | 내 데이터의 규칙을 계획 단계에 넣되 "먼저 묻기" 구조는 유지 |

## 3. 대표 예시: 새로 쓴 회의록 스킬 틀

아래는 책의 문장이 아니라 이 노트가 구조만 참고해 새로 쓴 예시다.

```markdown
---
name: meeting-notes
description: 회의 녹취나 메모를 결정, 할 일, 미결 질문으로 정리한다. 사용자가 회의 내용을 붙여넣거나 "회의록 써 줘"라고 할 때 사용.
---
# 회의록 정리
## 절차
1. 입력을 끝까지 읽고 참석자는 적힌 사람만 쓴다.
2. 제목 순서를 고정한다: 회의 주제, 한 줄 요약, 결정 사항, 할 일(담당자 - 내용 - 기한), 미결 질문.
3. 담당자나 기한이 불분명하면 "담당 불명", "기한 없음"으로 적는다.
## 규칙
- 입력에 없는 결정, 담당자, 날짜를 만들지 않는다.
- 입력이 너무 엉망이면 요약하지 말고 더 깨끗한 자료를 요청한다.
```

## 4. 공통 교훈

- 일관성이 스킬의 가치다. 출력 모양을 고정하면 읽는 사람이 찾아 헤매지 않는다.
- "지어내지 않기", "승인 전에는 바꾸지 않기" 같은 금지 규칙이 신뢰를 만든다.
- 값이 없을 때의 표기(미보고, 불명, 플래그)를 미리 정해 두면 추측이 사라진다.
- 같은 틀에 내 용어와 기준을 채워 넣으면 매번 설명하지 않아도 된다.

## 핵심 정리

- 스킬은 이름, 설명, 절차, 규칙으로 이뤄진 지침 파일이며 설명 문장이 작동 시점을 결정한다.
- 견본 네 개(회의록, 브랜드 보이스, 주간 보고서, 데이터 정리)는 복사해 대괄호를 채워 쓰도록 만들어졌다.
- 고쳐 쓸 때도 금지 규칙과 "먼저 보여 주고 승인받기" 구조는 남겨 두라는 것이 책의 조언이다.
