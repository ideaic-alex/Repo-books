# 플러그인으로 설정 묶어 공유하기

MCP 서버를 하나씩 설정하는 데 이어, 4장은 설정을 묶어서 나누는 방법인 Claude Code 플러그인(plugin)으로 마무리한다. 플러그인은 슬래시 명령(스킬), 서브에이전트, MCP 서버, 훅을 하나의 공유 가능한 단위로 묶는다. 이 문서는 플러그인이 해결하는 문제, 마켓플레이스를 추가하고 플러그인을 설치하고 관리하는 절차, feature-dev 플러그인으로 실제 작업을 해 본 사례, 기업에서의 쓰임을 정리한다.

비유하면 이사 후 가구를 하나씩 옮기던 방식에서 조립 키트 한 상자로 바뀐 것이다. 새 팀원에게 키트 한 상자만 건네면 같은 작업대가 차려진다.

---

## 1. 플러그인이 풀어 주는 문제

플러그인이 나오기 전에는 설정을 재사용하려면 수작업이 많이 들었다. 오픈소스 저장소의 슬래시 명령을 쓰려면 그 저장소에 가서 명령 파일을 복사해 내 .claude 폴더에 붙여 넣어야 했다. 서브에이전트와 훅도 같은 과정이었다. MCP 서버는 또 다른 설치 절차를 따랐으므로 전체가 수동적이고 흩어져 있었다.

플러그인은 이 구성 요소들을 하나로 묶어 설치와 통합을 한 번에 한다. 출처는 오픈소스 저장소일 수도 있고 사내 저장소일 수도 있으며 팀 간에 공유할 수 있다. Claude Code는 CLI 기반의 직관적인 플러그인 시스템을 제공한다. 원서가 꼽은 장점은 다음과 같다.

- 팀 전체의 통일된 설정: 새 개발자를 온보딩할 때 같은 도구, 같은 에이전트와 서브에이전트, 같은 MCP 서버를 갖추게 하고 싶을 때 표준화 수단이 된다.
- 세밀한 설치: 플러그인 전체가 아니라 MCP 서버 하나 같은 특정 구성 요소만 설치할 수 있다.
- 마켓플레이스라는 새 기본 단위: 설치 가능한 플러그인을 기술한 JSON 파일이다.

원서는 흥미로운 사실도 적는다. 구글의 Gemini CLI가 비슷한 개념인 Gemini Extensions를 2025년 10월 8일에, Claude Code 플러그인이 10월 9일에 공개됐다. 하루 차이는 개발팀이 아주 빠르게 반복했거나 두 팀이 동시에 같은 아이디어를 구현했다는 뜻일 수 있다. 공식 문서는 `https://code.claude.com/docs/en/plugins`에 있다.

## 2. 공식 마켓플레이스 살펴보기

Claude Code 오픈소스 저장소에는 .claude-plugin 디렉터리가 있고, 그 안의 marketplace.json이 공식 마켓플레이스를 정의한다. 설치 가능한 플러그인 목록과 메타데이터, 소스 경로가 들어 있다. 원서가 든 예는 pr-review-toolkit, commit-commands, agent-sdk-dev, feature-dev, 그리고 보안 지침 플러그인이다. 마켓플레이스는 Claude Code가 불러 와서 플러그인을 찾는 등록부 구실을 한다.

### 마켓플레이스 추가 절차

플러그인을 설치하려면 먼저 마켓플레이스를 Claude Code에 추가해야 한다.

1. Claude Code에서 `/plugin`을 실행한다.
2. "Browse and install plugins"를 고른다.
3. 처음에는 마켓플레이스가 없으므로 "Add Marketplace"를 고른다.
4. GitHub 저장소 URL이나 marketplace.json 직접 링크 중 하나를 준다.

원서는 공식 Claude Code 저장소의 기본 URL을 줬고, Claude Code가 마켓플레이스 파일을 자동으로 감지해 플러그인 목록과 설명이 보였다. 참고(노트 작성자): 메뉴 문구와 명령은 책이 쓰인 시점 기준이며 바뀔 수 있다.

### 설치 전 소스 검토

목록에는 플러그인 설명만 보인다. 플러그인이 실제로 무엇을 설치하는지 알려면 소스를 봐야 한다. marketplace.json의 각 플러그인 항목에는 구현 위치를 가리키는 source 필드가 있다. 보안 면에서 이것은 다른 사람이 쓴 MCP 서버, 시스템 프롬프트, 에이전트를 쓰는 것과 같은 위험이다. 구현을 안 보고 설치하면 위험하다.

검토 순서는 marketplace.json을 열고, 플러그인 항목을 찾고, source 필드를 확인하고, 저장소에서 그 경로로 가는 것이다. agent-sdk-dev 플러그인은 저장소의 plugins/agent-sdk-dev/ 디렉터리를 가리키고, 그 안의 .claude-plugin/plugin.json에 메타데이터와 플러그인이 설치하는 에이전트와 슬래시 명령(스킬) 정의가 있다. feature-dev 플러그인에는 코드 리뷰어, 코드 탐색기, 코드 설계자 에이전트가 들어 있고, 기능 설명과 워크플로 안내용 슬래시 명령이 feature-dev.md에 정의되어 있다.

## 3. 설치와 관리

마켓플레이스를 추가하면 플러그인을 설치하고 관리할 수 있다.

- 설치: `/plugin`을 열고 "Browse and install plugins"에서 commit-commands 플러그인을 찾아 상세 화면에서 Install을 누르고 설치가 끝나길 기다린다. 끝나면 설치된 플러그인 목록에 나타난다.
- 확인: 설치된 목록에서 해당 플러그인이 설치됨, 활성화됨으로 표시되는지 본다.
- 업데이트: 플러그인은 저장소가 뒷받침하므로 시간이 지나며 갱신된다. 설치된 플러그인을 고르고 Update를 찾아 적용한다. 원서는 이것을 저장소 최신 버전에 리베이스하는 것과 개념이 비슷하다고 설명한다.
- 제거: 인터페이스에 Uninstall 항목이 있지만, 책이 쓰인 시점에는 실행해도 플러그인이 지워지지 않았다. 원서는 현재의 한계 또는 버그로 보인다고 적는다.

## 4. feature-dev 플러그인 실습

원서는 feature-dev 플러그인(설치되고 활성화된 상태)으로 전체 워크플로를 시연한다.

1. `/feature-dev`를 실행하고 초기화를 기다린다.
2. Claude가 탐색 단계에 들어가 무슨 기능을 구현할지 이해하려고 질문한다.
3. 브랜치를 바꾸기 전에 저장소의 Git 상태를 점검한다. 커밋하지 않은 로컬 변경이 있으면 바로 브랜치를 바꾸는 것은 충돌이나 작업 손실 위험이 있다고 판단한다. 이 점검은 워크플로의 일부로 자동 진행된다.
4. 안전하게 가려고 `git stash`로 작업 상태를 보존한다. 작업 디렉터리 변경을 스태시하고, 트리가 깨끗한지 확인하고, 브랜치를 전환한다.
5. 기능 브랜치를 살펴본 뒤 원래 브랜치(main)로 돌아와 스태시한 변경을 다시 적용하고, 작업 디렉터리가 복원됐는지 확인한다. 로컬 변경이 그대로인 원래 상태로 돌아간다.

과제는 저장소 README를 갱신하는 것이었다. README에는 강의 레슨 표가 있고, context-engineering-mcp라는 GitHub 브랜치에 새 레슨이 있어 표에 추가해야 했다. 프롬프트에 변경 내용을 설명하고 그 브랜치의 URL을 준다. Claude는 그 브랜치로 가서 README를 살펴 표 구조를 파악하고, main으로 돌아와 변경을 적용할 준비를 하며 새 표 항목을 제안한다.

첫 설명은 거의 맞지만 약간 부정확해서 사람이 검토하고 문구를 다듬어야 했다. 승인하면 Claude가 커밋을 만들고 원격 저장소로 푸시한다. 저장소를 새로 고침하고 README를 열어 새 레슨이 표에 들어갔는지 확인하면 워크플로가 성공했음이 확인된다. 이 시연에서 보듯 플러그인의 슬래시 명령 하나가 탐색, 안전한 Git 처리, 제안, 사람 검토, 커밋과 푸시를 한 흐름으로 이끈다.

## 5. 마켓플레이스와 기업 활용

Claude Code는 서드파티 마켓플레이스를 지원한다. 예컨대 DevOps 자동화 마켓플레이스가 인프라 워크플로용 슬래시 명령, 에이전트, MCP 서버를 담은 플러그인을 줄 수 있다. 조직은 내부용 비공개 마켓플레이스를 만들어 사내 도구나 팀 전용 플러그인을 비공개로 둘 수 있다.

원서는 Supabase 같은 플랫폼 회사가 자체 마켓플레이스와 플러그인을 내놓아 Claude Code와의 통합을 개선할 가능성이 높다고 전망한다. 세밀한 설치 덕분에 슬래시 명령 하나나 MCP 서버 하나만 따로 설치할 수도 있다. 이 플러그인 생태계는 커지고 기업 규모의 Claude Code 도입에서 중요한 역할을 할 것으로 기대된다.

참고(노트 작성자): 마켓플레이스에 올라온 플러그인 이름과 구성은 책이 쓰인 시점의 예시다. 지금 목록과 다를 수 있다.
