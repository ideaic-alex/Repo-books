# 인피니트 프롬프트 해부

함수를 인자로 받아 함수를 돌려주는 고차 함수를 아는 사람이라면 이 문서가 쉽다. 프롬프트도 같은 일을 할 수 있다. 프롬프트를 입력으로 받아 프롬프트를 여럿 만들어 내는 프롬프트다.

앞 문서에서 쓴 `infinite.md` 슬래시 명령 안에는 서브에이전트 여섯을 띄운 프롬프트가 들어 있다. 이 문서는 그 프롬프트를 단계별로 뜯어 본다. 내용은 원서가 설명한 범위이며 원 저장소의 최신 모습과 다를 수 있다.

---

## 1. 고차 프롬프트와 메타 프롬프팅

이 프롬프트는 고차(high-order) 프롬프트다. 프롬프트를 입력으로 받아 프롬프트를 동적으로 생성한다. 함수형 프로그래밍의 고차 함수처럼 함수가 인자로 들어가고 반환값으로 나올 수 있듯이, 여기서는 프롬프트가 같은 일을 한다. 이런 접근을 메타 프롬프팅(meta-prompting)이라 부른다. Infinite Agentic Loop 명령에서 이것이 실제로 쓰인다.

프롬프트는 "이 무한 생성 작업을 깊이 생각하라. 정교한 반복 창작 과정을 시작하려 한다" 같은 문장으로 시작한다. "깊이 생각하라"는 모델의 더 깊은 추론을 일으키려는 지시이며, 메인 Claude Code 에이전트에게 가는 프롬프트다.

## 2. 변수와 파싱

변수 절에서 프롬프트는 `spec_file`, `output_dir`, `count` 세 변수를 선언한다. 각각 임시로 `$ARGUMENTS` 자리표시자에 대응한다. `/infinite`를 호출하면 인자 문자열 전체가 `$ARGUMENTS`로 프롬프트에 들어간다. 그래서 같은 값이 여러 번 나란히 보인다. 이 중복은 슬래시 명령에 준 입력과 같은 값이다.

파싱 역할을 하는 부분도 프롬프트에 있다. 인자를 포함한 프롬프트 전체가 메인 에이전트에게 간다. 이 프롬프트가 메인 에이전트에게 입력을 어떻게 해석할지 가르친다. 해석 결과는 이렇다.

- `spec_file`은 Markdown 스펙 파일의 경로다.
- `output_dir`은 반복 결과를 저장할 디렉터리다.
- `count`는 반복 횟수로, 1부터 N까지의 숫자이거나 "infinite"다.

파싱은 모두 메인 에이전트가 한다. 파싱을 맡는 코드는 없고, 명령을 호출할 때마다 LLM이 동적으로 해석한다.

## 3. 단계 1부터 3: 분석, 정찰, 전략

변수가 정해지면 몇 단계로 실행이 진행된다.

- 1단계, 스펙 분석: 메인 에이전트가 `spec_file`의 스펙을 읽고 깊이 이해한다. 스펙에는 생성할 콘텐츠의 종류, 형식과 구조 요구, 구체적인 매개변수와 제약, 반복 간 진화 패턴이 들어 있다. 스펙의 의도와 각 반복이 이전 작업 위에 어떻게 쌓일지를 신중히 생각하라고 지시한다. 앞선 예에서는 반복이나 진화가 스펙에 적히지 않아서 없었다. 원하면 프롬프트가 이를 지원한다.
- 2단계, 출력 디렉터리 정찰: `output_dir`을 철저히 분석해 현재 상태를 파악한다. 기존 파일과 이름 규칙을 나열하고, 현재 가장 높은 반복 번호를 찾고, 기존 반복의 내용이 어떻게 진화했는지 보고, 이전 생성의 궤적을 이해하고, 새 반복이 채울 빈틈을 정한다. 예제에는 반복 번호가 없고 쓰고 싶은 스타일 이름이 있었다. 이 단계는 이미 한 일이 무엇인지 확인하게 한다.
- 3단계, 반복 전략: 스펙 분석과 기존 반복을 바탕으로 시작 반복 번호나 만들 파일 이름을 정한다. 각 반복이 독특하면서 진화하도록 계획한다. 새로움을 유지하면서 이전 반복 위에 쌓는 방법을 생각한다. `count`가 infinite면 컨텍스트 한도에 이를 때까지 계속 생성할 준비를 한다. 이 단계는 아직 계획이다.

## 4. 단계 4: 병렬 에이전트 조율

4단계에서 비로소 서브에이전트의 병렬 실행으로 넘어간다. 메인 에이전트는 최대한의 효율과 창의적 다양성을 위해 여러 서브에이전트를 배치해 반복을 병렬로 만든다. 분배 전략은 개수에 따라 다르다.

| 개수 | 실행 방식 |
|---|---|
| 1에서 5 | 모든 에이전트를 동시에 띄운다 |
| 6에서 20 | 5개씩 묶어 배치로 띄워 조율을 관리한다 |
| infinite | 3에서 5개씩 파도(wave)로 띄우고, 컨텍스트를 감시하며 새 파도를 이어 간다 |

메인 에이전트는 Claude Code의 태스크 도구로 서브에이전트를 만든다. 프롬프트는 서브에이전트 안에 들어갈 프롬프트를 메인 에이전트가 어떻게 쓸지 설명한다. 각 서브에이전트의 입력은 프롬프트 하나이고, 서브에이전트는 컨텍스트 격리 상태에서 일하며 메인 에이전트에게 메시지 하나를 출력한다.

각 서브에이전트가 받는 내용은 다섯 가지다.

- 스펙 맥락: 스펙 파일 분석 전체
- 디렉터리 스냅샷: 실행 시점의 `output_dir` 상태
- 반복 배정: 구체적인 반복 번호, 시작 번호, 에이전트 순번
- 유일성 지시: 기존 반복의 개념과 겹치지 말라는 명시적 지시
- 품질 기준: 스펙에 적힌 상세 요구사항

디렉터리 스냅샷을 입력으로 주기 때문에 서브에이전트는 지금까지 무슨 일이 있었는지 안다. 그래서 중복된 아이디어와 중복된 구현을 피한다. 앞선 예에서는 반복 번호가 없었으므로 반복 배정이 우리가 쓴 파일 이름에 대응됐다.

## 5. 서브에이전트 작업 구조와 실행 관리

프롬프트에는 각 서브에이전트에게 주는 작업 구조도 들어 있다. 작업은 "[스펙 파일]의 [출력 디렉터리]에 반복 [번호]를 생성하라. 당신은 서브에이전트 [X]이고 반복 [번호]를 만든다"로 구성된다. 서브에이전트 프롬프트에는 스펙 전체 분석, 기존 반복 요약, 자기 반복 번호, 배정된 창의적 방향, 요구사항이 포함된다. 스펙을 완전히 읽고 이해하라, 기존 반복을 분석해 출력이 유일하도록 하라는 지시가 있고 그 밖의 지시도 더해진다.

그다음 프롬프트는 메인 에이전트의 실행 관리 지침으로 돌아온다. 메인 에이전트는 이렇게 한다.

- 태스크 도구로 배정된 서브에이전트를 모두 동시에 띄운다.
- 에이전트의 진행과 완료를 감시한다.
- 실패한 에이전트는 반복 번호를 재배정해 처리한다.
- 반복 번호가 중복되지 않게 한다.
- 완료된 반복을 모아 검증한다.

이 부분이 고차 프롬프트의 중심이다. 프롬프트 하나를 입력받아 서브에이전트마다 다른 프롬프트를 여럿 출력한다. 명령에는 무한 실행 지침, 컨텍스트 최적화, 실행 원칙도 들어 있어 메인 에이전트에게 더 많은 맥락을 준다.

## 6. 저자의 생각

프롬프트를 입력으로 받아 프롬프트를 출력하는 프롬프트를 생각하는 것은 꽤 혁신적이라고 저자는 말한다. 자신은 이것을 읽고 놀랐고, 이 방향을 떠올린 IndieDevDan에게 감사한다고 적었다. 저자는 에이전트 코딩과 소프트웨어 엔지니어링이 이런 프롬프트 쪽으로 가고 있다고 믿는다. 거의 모든 것을 하는 메타 프롬프트이기 때문이다.

참고(노트 작성자): 이 믿음은 저자 개인의 전망이며 검증된 사실로 읽을 필요는 없다. 실습에서는 6개 변형을 만드는 가벼운 규모만 썼다는 점도 함께 기억하자.
