# 서브에이전트의 개념과 구조

식당 주방을 생각해 보자. 주방장 혼자 재료 손질부터 설거지까지 하면 금방 머리가 복잡해진다. 그래서 소스 담당, 굽기 담당처럼 한 가지를 아주 잘하는 전문 요리사에게 일을 맡기고, 주방장은 결과만 받는다. Claude Code의 서브에이전트(subagent, 전문 업무를 맡는 보조 에이전트)가 이 구조다.

이 문서는 7장의 이론 부분이다. 서브에이전트가 무엇이고 메인 에이전트와 어떻게 다른지, 정의 파일이 어떻게 생겼는지, 어디에 두는지를 다룬다. 실습 전에 알아야 할 기초다. 도구 이름과 화면은 책이 쓰인 시점 기준이다.

---

## 1. 7장이 다루는 것

7장은 서브에이전트가 구조적이고 확장 가능한 워크플로를 어떻게 가능하게 하는지 보여 준다. 먼저 서브에이전트가 무엇인지, 메인 Claude Code 에이전트와 어떻게 다른지, 컨텍스트 격리가 왜 설계의 중심인지를 이해한다. 이어서 직접 서브에이전트를 설정하고, 프롬프트와 도구 권한이 실행에 주는 영향과 컨텍스트 흐름을 분석한다. 마지막으로 인피니트 에이전틱 루프 패턴으로 여러 서브에이전트를 동시에 돌려 여러 구현을 탐색하고 가장 좋은 것을 고른다.

장은 이런 순서다. 서브에이전트 소개, 첫 서브에이전트 설정, 시험, 컨텍스트 흐름 유지, 동시 서브에이전트로 확장, 인피니트 프롬프트다.

## 2. 서브에이전트란

한 번에 프롬프트를 수십 개 쓰는 대신 `/cook` 같은 명령 하나로 전문 에이전트 팀을 움직일 수 있다. 각 에이전트는 한 가지 일을 아주 잘하도록 설계된다.

공식 문서의 설명에 따르면 서브에이전트는 Claude Code가 일을 위임할 수 있는 미리 구성된 AI 인격이다. 각자 목적과 전문 분야가 있다. 실제로는 특정 프롬프트 하나로 서브에이전트가 정의된다고 보면 된다. 특징은 네 가지다.

- 각 서브에이전트는 자기만의 시스템 프롬프트를 가진다. 어떻게 동작하고 무엇을 할 수 있는지를 우리가 완전히 정한다.
- 메인 대화와 분리된 자기 컨텍스트 윈도우에서 일한다. 이 격리가 컨텍스트 오염을 막고, 메인 대화가 서브에이전트의 일에 편향을 넣지 못하게 한다. 서브에이전트는 자기 목표에 집중한다.
- 쓸 수 있는 도구를 개별로 설정한다. 최소 권한 원칙(principle of least privilege, 필요한 것만 준다는 원칙)을 지키기 좋다. 예를 들어 코드 리뷰 에이전트는 파일을 읽고 정보를 찾는 도구는 필요하지만, 셸 명령이나 파일 쓰기 도구는 필요 없다. 도구에는 기본 도구와 MCP 서버가 노출하는 통합이 모두 포함된다. 에이전트 스킬은 이와 다른 층에서 구조화된 능력을 정의한다.
- 재사용할 수 있다. 한 번 만들면 여러 프로젝트에서 쓰고 팀과 공유한다.

## 3. 정의 파일 예: code-reviewer

서브에이전트는 Markdown 파일로 적고, Claude Code의 계층 규칙을 그대로 따른다. 책은 특정 프로젝트용 코드 리뷰어 예를 보여 준다. 아래는 앞부분의 골격이다.

```markdown
---
name: code-reviewer
description: 시니어 코드 리뷰 에이전트. 코드 변경의 버그,
  보안 결함, 규칙 위반을 자동 분석한다. 코드 수정 뒤 호출한다.
tools: Read, Grep, Glob, Bash
model: inherit
---
당신은 이 프로젝트에 속한 꼼꼼한 코드 리뷰어다.

## 워크플로
1. diff 수집: git diff 로 변경 사항을 모은다
2. 파일 전체 읽기: 바뀐 줄만이 아니라 전체를 읽는다
3. 의존성 추적: 바뀐 함수의 사용처를 모두 찾는다
4. 프로젝트 규칙 검증: CLAUDE.md 의 규칙을 확인한다
```

원서의 예는 Next.js, Firebase 등 특정 스택의 규칙을 길게 담고 있다. 이어서 심각도를 세 단계로 나눈다. 위험은 병합을 막는 보안 구멍, 데이터 손상 위험, 인증 누락, 하위 호환 파괴다. 경고는 출시 전에 해결할 입력 정제 부족, 비동기 오류 처리 누락, 성능 함정, 약한 타입이다. 제안은 더 나은 이름이나 더 단순한 로직이다. 응답 형식은 위치, 문제, 영향, 권장 수정을 담도록 정해 두었다.

## 4. 어디에 두나

서브에이전트는 두 범위에 둔다.

- 프로젝트 수준은 한 저장소에 한정되며 `.claude/agents/` 디렉터리에 둔다. 그 프로젝트에 관련된 에이전트를 모두 여기에 보관한다.
- 사용자 범위는 모든 프로젝트가 공유하며 홈 디렉터리 아래 `.claude/agents/`에 둔다.

프로젝트 수준 파일은 저장소에 커밋해 팀과 공유할 수 있다.

## 5. 파일 구조

모든 정의는 YAML 머리말(frontmatter, 파일 맨 위의 설정 블록)로 시작한다. 꼭 필요한 항목은 `name`과 `description`이다. 그 밖에 `tools`, `skills`, `mcp`, `model`, `hooks`, `memory` 등을 설정할 수 있다. 전체 형식은 공식 문서를 보라고 책은 안내한다.

`description`은 메인 에이전트가 이 서브에이전트를 언제 부를지 판단하는 근거다. 서브에이전트는 메인 Claude Code 에이전트가 쓰는 도구와 같은 개념으로 작동한다. 그래서 이름과 설명이 필수이고 빠뜨릴 수 없다.

`tools`에는 허용할 도구를 이름으로 나열한다. 이 항목을 비워 두면 서브에이전트는 쓸 수 있는 모든 도구를 받는다. MCP 도구도 여기에 들어갈 수 있다.

마지막 부분이 시스템 프롬프트다. 모든 지침이 여기에 있고, 서식은 자유롭다. 고정 맥락이나 동적 맥락을 넣을 수 있다. 이것은 시스템 프롬프트이지 사용자 프롬프트가 아니며 이 구분이 중요하다. 둘의 차이는 뒤에서 자세히 나온다.

## 6. ReAct 에이전트와의 관계

LLM 애플리케이션을 만들어 본 사람이라면 이 구조가 낯익다. 모델에게 이름과 설명이 붙은 도구 묶음과 전반적인 지침을 주는 ReAct 에이전트 패턴과 닮았다. 원서는 이를 "React agents"로 적는데, 문맥상 추론과 행동을 번갈아 하는 ReAct 패턴으로 읽힌다. 책은 LangGraph로 에이전트를 만드는 짧은 파이썬 예를 보여 주며, 고정 프롬프트와 도구 하나로 구성한다.

참고(노트 작성자): 책 예제의 모델 이름 문자열은 책이 쓰인 시점 기준이며 지금은 달라졌을 수 있다. 여기서는 구조만 참고하면 된다.

차이는 Claude Code의 메인 코딩 에이전트와 서브에이전트가 오래 걸리는 일을 끝까지 수행하고 기능을 처음부터 끝까지 구현할 수 있다는 점이다. 책은 ReAct 에이전트가 더 넓은 범주이고 그 안에 딥 에이전트(deep agent)라는 부분집합이 있다고 설명한다. Claude Code의 코딩 에이전트와 서브에이전트가 이 부분집합에 든다. 딥 에이전트가 되기 위한 조건은 책 뒷부분에서 다룬다. 내부 동작을 이해하면 서브에이전트의 행동을 더 잘 다룰 수 있다.
