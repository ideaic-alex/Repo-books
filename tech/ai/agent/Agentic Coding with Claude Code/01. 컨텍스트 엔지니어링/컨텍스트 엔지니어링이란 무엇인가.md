# 컨텍스트 엔지니어링이란 무엇인가

이 문서는 1장의 첫 절 '컨텍스트 엔지니어링 소개'를 다룬다. 저자는 Cursor나 Claude Code 같은 코딩 에이전트가 'LLM을 감싼 껍데기일 뿐'이라는 말에 일리가 있다고 인정한다. 다만 좋은 껍데기를 만들려면 깊은 지식과 많은 엔지니어링이 필요하다고 덧붙인다. 그 껍데기 안에서 가장 중요한 일이 모델에 무엇을 보낼지 정하는 일이다.

비유로 말하면 컨텍스트는 신입 직원에게 건네는 업무 인수인계 자료다. 자료가 빠지면 일을 못 하고, 너무 많거나 서로 모순되면 오히려 엉뚱한 일을 한다. 컨텍스트 엔지니어링은 이 자료 묶음을 상황마다 알맞게 꾸려 주는 일이다.

---

## 1. 에이전트 하네스와 컨텍스트의 출처

원서는 LLM을 둘러싼 시스템을 에이전트 하네스(Agent Harness, 모델 바깥에서 도구 호출과 루프와 오류와 안전장치를 맡는 조율 계층)라고 부른다. 하네스는 도구 호출을 관리하고, 에이전트 루프를 제어하고, 오류를 처리하고, 가드레일(guardrail, 벗어나지 못하게 막는 안전장치)을 적용한다. 무엇보다 단계마다 모델에 어떤 컨텍스트를 보낼지 정한다.

저자의 요점은 실제 엔지니어링의 대부분이 LLM 호출 안이 아니라 그 주변에 있다는 것이다. 모델을 부르는 코드는 대개 단순하다. 에이전트가 안정적으로 동작하느냐는 상태, 도구, 메모리, 컨텍스트를 둘러싼 시스템이 얼마나 잘 관리하느냐에 달렸다. LLM 호출에는 언제나 컨텍스트가 따라붙기 때문이다.

컨텍스트는 여러 곳에서 온다.

- 애플리케이션 개발자가 넣는 것(시스템 프롬프트 같은 기본 지시)
- 사용자가 넣는 것(요청, 붙여 넣은 파일)
- 이전 상호작용, 도구 호출 결과, 외부 데이터에서 오는 것

새로운 출처가 날마다 늘고 양도 계속 불어난다. 그래서 알맞은 컨텍스트를 골라 보내는 일이 초기에 생각한 것처럼 간단하지 않게 되었다.

## 2. 프롬프트 엔지니어링에서 컨텍스트 엔지니어링으로

초기에는 멋진 프롬프트를 잘 쓰면 문제가 풀린다고 믿었다. 그러나 프롬프트는 정적이고 컨텍스트는 극도로 동적이다. 컨텍스트가 동적이라면 그것을 구성하는 시스템도 동적이어야 한다. 저자는 컨텍스트 엔지니어링을 프롬프트 엔지니어링의 자연스러운 진화이자 훨씬 깊은 개념이라고 정리한다.

예를 들어 코딩 에이전트에서 프롬프트는 '로그인 버그를 고쳐 줘' 한 줄이다. 하지만 모델이 실제로 받는 입력에는 프로젝트 규칙, 방금 읽은 파일, 앞선 도구 결과, 사용 가능한 도구 목록이 함께 들어 있다. 사용자가 쓴 한 줄은 전체 입력의 일부일 뿐이다.

원서는 이 절이 Anthropic 엔지니어링 블로그와 커뮤니티 분석 같은 공개 정보에 기댄 논의이며 Anthropic의 공식 입장이 아니라고 명시한다.

## 3. 컨텍스트가 에이전트에게 중요한 이유

'쓰레기를 넣으면 쓰레기가 나온다'는 말처럼, 에이전트 시스템이 기대대로 동작하지 않는 가장 흔한 이유는 올바른 컨텍스트를 받지 못해서다. LLM은 우리 마음을 읽지 못한다. 정보와 데이터만이 아니라 다른 정보를 가져오고 작업을 수행할 올바른 도구도 줘야 한다.

LLM은 추론 능력이 점점 좋아지고 있다. 도구 호출(tool calling)이 있어서 도구를 실행하고 결과를 받아 작업이 끝날 때까지 반복하는 에이전트를 만들 수 있다. 원서의 그림 1.1과 1.2는 컨텍스트 윈도우의 구성과 이 도구 호출 루프를 보여 준다(LangChain이 논의한 개념을 바탕으로 한 그림이라고 밝힌다).

문제는 오래 걸리고 복잡한 작업에서 생긴다. 루프를 돌 때마다 도구 호출 결과와 중간 출력이 쌓이기 때문이다. 그래서 컨텍스트 윈도우(Context Window, 모델이 한 번에 볼 수 있는 입력 분량)가 계속 커진다. 원서의 그림 1.3은 턴이 거듭될수록 컨텍스트가 늘어나는 모습을 보여 준다. 이렇게 되면 세 가지 문제가 따라온다.

- 컨텍스트 윈도우가 크기 한도를 넘을 수 있다.
- 비용과 지연 시간이 늘어난다.
- 에이전트 성능이 떨어지기 시작한다.

아무 조치도 하지 않으면 이 성능 저하는 피할 수 없다. 원서는 긴 컨텍스트가 현실에서 왜 실패하는지를 다룬 Dan Breunig의 글을 참고하라고 소개한다. 원문 PDF의 제목 표기는 'How Long Contexts'로 끊겨 있는데, 주소(dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html)로 보아 원래 제목은 'How Contexts Fail and How to Fix Them'일 가능성이 높다. 참고(노트 작성자): 이것은 주소에서 추정한 복원이다.

## 4. 컨텍스트가 구조 없이 커질 때의 문제 세 가지

무질서하게 커진 컨텍스트는 다음과 같은 문제를 일으킨다고 원서는 정리한다.

| 문제 | 뜻 | 예 |
|---|---|---|
| 컨텍스트 오염(Context poisoning) | 도구 호출이나 LLM 호출에서 나온 환각(hallucination, 없는 사실을 지어냄)이 컨텍스트에 들어가 이후 출력에 계속 영향을 준다 | 에이전트가 존재하지 않는 함수 이름을 한 번 적으면 이후 코드가 그 이름을 계속 쓴다 |
| 컨텍스트 혼란(Context confusion) | 작업과 관련 없는 컨텍스트가 응답에 영향을 준다 | 결제 코드를 고치는데 오래전 로그 분석 내용이 섞여 들어온다 |
| 컨텍스트 충돌(Context clash) | 컨텍스트의 서로 다른 부분이 모순된다 | 앞에서는 '탭 들여쓰기', 뒤에서는 '공백 들여쓰기'를 지시한다 |

위 표의 예는 개념을 풀기 위해 노트 작성자가 만든 것이다. 원서는 정의만 짧게 준다.

## 5. 개발자와 사용자 모두의 몫

이런 문제를 다루는 기법 중 일부는 Claude Code 같은 도구의 개발자가 구현한다. 나머지는 사용자 쪽에 있다. Claude Code 사용자는 모델로 보내지는 컨텍스트와 받는 답변에 큰 영향을 줄 수 있다. 그래서 개발자가 아닌 사람도 AI 시스템에서 더 나은 답을 얻으려면 컨텍스트 엔지니어링을 이해해야 한다고 저자는 말한다.

Claude Code는 개발자 쪽과 사용자 쪽 기법이 모두 쓰이는 좋은 사례다. 다음 문서는 Claude Code가 이 문제를 네 가지 전략으로 푸는 방식을 본다.
