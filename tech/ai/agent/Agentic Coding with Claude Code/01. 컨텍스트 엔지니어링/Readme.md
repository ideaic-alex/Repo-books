# 컨텍스트 엔지니어링

1장은 이 책 전체를 꿰는 개념인 컨텍스트 엔지니어링을 소개한다. 에이전트가 길고 복잡해질수록 컨텍스트가 불어나고, 관리하지 않으면 성능 저하와 비용 증가와 환각이 생긴다는 점에서 출발한다. Claude Code가 이 문제를 쓰기, 선택, 압축, 격리의 네 전략으로 어떻게 푸는지 보고, 마지막으로 시스템 프롬프트를 어떤 수준으로 써야 하는지 다룬다.

---

## 1. 핵심 요점

- 에이전트의 실제 엔지니어링은 모델 호출이 아니라 그 주변, 곧 상태, 도구, 메모리, 컨텍스트를 관리하는 하네스에 있다.
- 프롬프트는 정적이고 컨텍스트는 동적이다. 그래서 컨텍스트를 구성하는 시스템도 동적이어야 하며, 이것이 컨텍스트 엔지니어링이다.
- 도구 호출 결과가 쌓이면 컨텍스트 윈도우가 한도를 넘고, 비용과 지연이 늘고, 성능이 떨어진다.
- 컨텍스트를 방치하면 오염(환각이 퍼짐), 혼란(관련 없는 정보가 섞임), 충돌(모순된 정보)이 생긴다.
- Claude Code는 쓰기(3층 CLAUDE.md 메모리), 선택(폴더 탐색과 도구별 주의사항), 압축(/clear, /compact), 격리(서브에이전트)를 모두 구현한다.
- 사용자도 /memory와 압축 명령으로 컨텍스트에 직접 영향을 줄 수 있다.
- 시스템 프롬프트는 너무 구체적이거나 너무 모호하면 실패하며, 역할과 범위, 사고 틀, 휴리스틱을 주는 골디락스 지대가 알맞다.
