# 요약과 핵심 개념

11장은 책의 마지막 본문 장으로, Claude Code 같은 코딩 에이전트가 긴 작업을 해내는 원리를 개념적으로 정리한다. 에이전트를 분류하고, 얕은 에이전트의 한계를 보이고, 딥 에이전트를 이루는 네 요소를 설명하는 순서다. 이 문서는 그 흐름과 용어를 한 번에 되짚는다.

---

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | 에이전트 분류 | 에이전트 영역 안에 ReAct 에이전트(얕은)와 딥 에이전트가 있고, 코딩 에이전트는 딥 에이전트의 부분집합 |
| 2 | 얕은 에이전트의 한계 | 반복마다 컨텍스트가 쌓여 컨텍스트 부패와 비용 증가가 생김. 몇 번 안 도는 작업에는 충분 |
| 3 | 딥 에이전트와 하니스 | 장기 과제용. 혁신은 모델보다 응용 계층(하니스 엔지니어링)에서 일어남 |
| 4 | 계획 도구와 서브에이전트 | 마크다운 할 일 목록으로 계획하고, 격리된 컨텍스트의 전문 일꾼에게 위임 |
| 5 | 파일시스템 | 컨텍스트를 외부에 쓰고 glob과 grep으로 골라 읽는 컨텍스트 엔진 |
| 6 | 시스템 프롬프트 | 정체성, 권한, 추론 틀, 휴리스틱, 간결함을 갖춘 인지의 기준선 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 딥 에이전트 | 분, 시간, 며칠 걸리는 복잡한 작업을 품질 있게 해내는 에이전트. 멈췄다가 사용자 입력을 받고 이어 갈 수 있음 |
| ReAct 에이전트 | LLM이 도구를 고르고 관찰을 받는 순환을 답이 나올 때까지 도는 에이전트. 이 책의 분류에서는 얕은 에이전트 |
| 컨텍스트 부패 | 반복으로 컨텍스트가 커지며 혼란, 모순, 오염이 생겨 성능이 떨어지는 현상 |
| 에이전트 하니스 | 기본 프롬프트, 도구 처리, 계획, 파일 접근이 미리 갖춰진 에이전트 제작 환경 |
| 계획 도구 | 대기, 진행 중, 완료 상태의 할 일 목록을 명시적으로 갱신(Claude Code는 TodoWrite와 TodoRead) |
| 서브에이전트 | 자기 시스템 프롬프트, 설명, 도구를 가지고 자기 컨텍스트에서 일해 최종 결과만 돌려주는 일꾼 |
| 컨텍스트 엔진으로서의 파일시스템 | 쓰기(영구 저장)와 선택(glob, grep)으로 컨텍스트 엔지니어링 두 원칙을 구현 |
| 시스템 프롬프트 | 딥 에이전트의 추론, 정체성, 경계를 정하는 구조. 구체적 하드코딩과 모호함 사이의 균형이 중요 |

## 3. 자주 놓치는 점

- 얕다는 것은 나쁘다는 뜻이 아니다. 몇 번 안 도는 작업에서는 ReAct 구조가 충분히 효과적이고 널리 쓰인다.
- 딥 에이전트에는 엄밀한 정의가 없다. 저자는 복잡하고 긴 작업을 품질과 신뢰성 있게 해내면 깊다고 본다.
- 계획은 모델 속의 생각의 사슬이 아니라 명시적인 도구로 만든 할 일 목록이다. 실패한 작업도 맹목적으로 재시도하지 않고 계획으로 조정한다.
- Claude Code의 계획 도구 구현은 직접 열어 볼 수 없다. TodoWrite와 TodoRead 호출로 간접 확인한다.
- 서브에이전트는 중간 추론을 메인에 넘기지 않고 최종 응답만 돌려준다. 그래서 컨텍스트가 오염되지 않는다.
- 파일시스템은 인터페이스다. Firestore나 DynamoDB처럼 저장소 구현은 바꿀 수 있다.
- 검색 실패는 과소, 과다, 어긋남 세 가지이고, 윈도우 한계는 별도의 제약이다.
- 컨텍스트 엔지니어링의 목표는 선택한 컨텍스트를 작게 하되 필요한 정보는 모두 덮는 것이다.
- 프롬프트가 중요하다는 말보다, 규칙이 아니라 추론 틀과 압축된 원칙을 주라는 점이 실무 요점이다.
