# 요약과 핵심 개념

5장은 Claude Code를 GitHub에 연결해 이슈와 PR 작업을 자동화하는 장이다. 설치와 인증을 마치면 이슈에서 Claude를 태그해 문제를 맡기고, PR이 열릴 때 자동 검토까지 받을 수 있다. 그러나 실습의 핵심 교훈은 자동화 자체보다 검토와 맥락이다. 맥락 없이 맡기면 외부 API 계약을 깨는 PR이 나왔고, CLAUDE.md를 커밋하자 올바른 결과가 나왔다.

원서의 장 요약은 이렇다. 필요한 도구 설치, Claude GitHub 앱 구성, 이슈와 PR에 응답하는 GitHub Actions 워크플로 설정을 거쳤다. Claude가 브랜치를 만들고 PR을 열고 자동 검토에 참여하는 방식과 변경을 반드시 검토해야 하는 이유를 보았다. 맥락이 빠지면 틀린 변경이 나오고 CLAUDE.md가 정확도를 높임을 확인했다. 다음 장은 구조화된 에이전트 워크플로, 곧 계획 모드와 스펙 주도 개발과 병렬 에이전트 조율을 다룬다.

---

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | 구조 이해 | 이벤트에 반응하는 GitHub Actions가 Claude Code CLI와 SDK로 일한다 |
| 2 | 사전 준비 | GitHub CLI 설치와 `gh auth login` 인증. GitHub 연결된 저장소에서 시작 |
| 3 | 앱과 워크플로 설치 | `/install-github-app`, Tag Claude와 코드 리뷰 선택, 장기 토큰 또는 API 키 |
| 4 | 설치 PR 병합 | `.github/workflows`에 YAML 두 개, 토큰은 시크릿으로 참조 |
| 5 | 이슈 해결 1차 | `@claude` 태그로 이름 변경 요청, 외부 API 계약을 깬 틀린 PR |
| 6 | CLAUDE.md 추가와 2차 | `/init`, 커밋, 힌트와 함께 재요청해 올바른 PR, 자동 리뷰 승인 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| GitHub Actions | 이벤트에 반응해 워크플로를 실행하는 GitHub의 서버리스 자동화 플랫폼 |
| 워크플로 파일 | 어떤 이벤트에 무엇을 실행할지 적은 YAML 파일. `.github/workflows`에 둔다 |
| `/install-github-app` | GitHub CLI와 Claude GitHub 앱, 워크플로 설치를 안내하는 명령 |
| Tag Claude | 이슈와 PR 댓글에서 Claude를 태그해 실행하는 옵션 |
| Claude Code Review | 새 PR을 자동으로 검토하는 옵션 |
| 장기 토큰과 API 키 | 전자는 구독 범위의 소중규모 사용, 후자는 대규모나 잦은 호출에 쓴다 |
| Actions 시크릿 | 토큰을 워크플로 파일 밖에 저장해 두고 이름으로 참조하는 방식 |
| Claude 작업 브랜치 | Claude는 `claude/issue/<번호>` 같은 새 브랜치에서 작업하며 main을 직접 건드리지 않는다 |
| 컨텍스트 엔지니어링 | CLAUDE.md로 스택, 구조, 규약을 의도해서 공급해 정확도를 높이는 일 |

## 3. 자주 놓치는 점

- 연동은 GitHub에 연결된 저장소 디렉터리에서 시작해야 한다. 아니면 오류가 난다. 내 저장소라면 관리자 권한도 필요하다.
- 비밀 값은 워크플로 파일에 쓰지 않는다. 토큰은 Actions 시크릿에 두고 `secrets.이름`으로 참조한다.
- 원시 Actions 로그는 JSON 덩어리다. 보통은 이슈 화면의 할 일 목록과 PR을 본다.
- PR 설명이 그럴듯해도 안심하지 않는다. 실제 diff를 열어 외부 계약이 유지되는지 본다.
- 맥락이 없는 첫 시도는 틀렸다. 다만 2차 시도에는 함수 위치 힌트도 들어갔으므로 CLAUDE.md만의 효과로 단정할 수는 없다.
- CLAUDE.md는 만들기만 하지 말고 커밋해야 자동화 워크플로에서 쓰인다.
- Claude가 브랜치에서 일한다는 점은 병렬 작업의 기초이며 깃 워크트리로 이어진다.
- 책에 나온 액션 버전, 파일 이름 표기, 설치 화면은 책이 쓰인 시점 기준이다.
