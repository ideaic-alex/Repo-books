# 모바일 클라우드 실행과 병렬 에이전트의 한계

이 문서는 10장의 마지막 두 절을 다룬다. 같은 워크플로를 휴대폰에서 시작하면 어떻게 되는지, 그리고 병렬 에이전트가 오히려 해가 되는 경우는 언제인지를 정리한다. 병렬이 좋다는 이야기 끝에 "언제 쓰지 말아야 하는가"를 짚는 부분이라 실무 판단에 가장 가깝다.

비유하면 이삿짐 센터 직원을 여럿 부르는 일과 같다. 방이 따로 나뉘어 있으면 사람을 늘릴수록 빠르다. 좁은 방 하나에 다 같이 들어가면 서로 걸리적거려 더 느려진다.

---

## 1. 모바일에서 클라우드로 실행하기

Claude Code는 모바일 앱에도 들어와 있다. 데스크톱에서 쓰던 흐름을 휴대폰에서 바로 시작할 수 있다. 책의 예에서는 모바일 화면에서 claude-code-crash-course 저장소를 고르고 거기서 세션을 시작한다.

모바일 환경은 코드를 로컬에서 실행하지 않는다. 그래서 모든 작업이 Anthropic 클라우드에서 돈다. 내 컴퓨터에 의존하지 않으며, 저장소 복제와 브랜치 체크아웃과 커밋이 모두 원격에서 일어난다.

### 1.1 푸터 컴포넌트 구현

Claude에게 project/hookhub 브랜치로 옮겨 Anthropic 스타일 푸터를 구현하라고 시킨다. 흐름은 데스크톱과 같다. 저장소를 복제하고, 대상 브랜치를 체크아웃하고, 프로젝트 구조를 살피고, 기능을 구현하고, 변경을 커밋하고, 풀 리퀘스트를 준비한다.

시스템 안내가 브랜치가 project/hookhub로 바뀌었음을 확인해 준다. 프로젝트 맥락을 파악한 Claude는 이 저장소가 Anthropic풍 브랜딩의 Next.js 앱임을 알아보고 거기에 맞춰 진행한다.

여기서 저자가 짚는 점이 있다. 기본 클라우드 구성에는 MCP 서버, 사용자 지정 훅, 출력 스타일이 들어 있지 않다. 환경은 기본 설정으로 돈다. 사용자 지정 구성은 따로 추가할 수 있지만 이 세션은 그것 없이 진행했다.

Claude는 components 디렉터리 아래에 footer.tsx를 새로 만든다. 푸터는 Anthropic 시각 스타일을 따른다. 컴포넌트를 만든 뒤에는 page.tsx에서 불러와 메인 페이지에 렌더링하도록 연결한다.

버전 관리 작업은 자동으로 이어진다. 변경이 스테이징되고 커밋된다. 요청이 project/hookhub로 푸시하라고 했고 Claude Code가 내부적으로 워크트리를 쓰기 때문에, 워크트리 커밋을 올바른 브랜치에 합치는 추가 깃 작업이 뒤에서 일어난다. 깃 로그에는 앞선 병합과 커밋이 그대로 보이고, 새 푸터와 페이지 수정이 브랜치 이력에 포함된다.

### 1.2 풀 리퀘스트 검토

GitHub에서 저장소를 열면 새 풀 리퀘스트가 보인다. 처음에는 대상이 main이라 의도와 다르다. 기준 브랜치를 project/hookhub로 고친다. 그러면 수정 파일은 page.tsx와 footer.tsx 두 개로 나타나고, diff는 푸터 통합이 기대한 대로임을 보여 준다.

GitHub에서 Claude를 직접 호출해 풀 리퀘스트를 검토하게 할 수도 있다. 다만 이 브랜치에는 GitHub 워크플로가 설정돼 있지 않아 자동 점검이 돌지 않았고, 검토는 수동으로 남았다.

### 1.3 로컬에서 검증

통합을 확인하려면 아래를 실행한다.

```bash
git fetch
git pull
npm run dev
```

개발 서버를 켜면 앱이 새 푸터와 함께 뜨고 맨 아래에 "Built with love for Claude Code powered by Anthropic" 문구가 보인다. 레이아웃에는 약간의 조정이 필요하지만, 이것도 Claude Code에게 되돌려 다듬게 하면 된다.

중요한 결과는 복제부터 풀 리퀘스트 생성까지 전 과정이 모바일에서 시작되어 전부 클라우드에서 실행됐다는 점이다. 저자는 공학 모델이 그대로라고 요약한다. 의도를 말하고, Claude가 저장소를 추론하게 하고, 결과를 검토하고, 반복한다. 인터페이스는 바뀌어도 개발 과정은 바뀌지 않는다.

## 2. 병렬 에이전트가 역효과를 내는 경우

병렬 코딩 에이전트는 유용하지만 늘 옳은 선택은 아니다. 책은 병렬 실행이 오히려 발목을 잡는 상황을 다섯 가지로 든다.

| 상황 | 왜 문제인가 | 대응 |
|---|---|---|
| 강하게 얽힌 기능 | 같은 파일을 고치거나 서로의 결과에 의존하면 충돌하거나 조용히 덮어씀 | 기능 B가 A의 인터페이스를 필요로 하면 순서대로 실행 |
| 공유 상태와 순서 제약 | DB 마이그레이션, 설정 파일, 공유 타입 정의는 숨은 의존성을 만듦 | 같은 설정, 스키마, 라우트 파일에 쓰는 일은 한 에이전트에 몰기 |
| 작은 작업 | 세션마다 맥락 준비, 코드 읽기, 계획 수립의 부담이 있음 | 한 세션에 들어가는 일은 한 세션에서 처리 |
| 높은 조율 비용 | 에이전트끼리 부딪히지 않게 명세를 쓰는 데 시간을 다 씀 | 경계 정의에 쓰는 시간이 늘수록 병렬의 이득은 줄어든다고 판단 |
| 탐색적이거나 불확실한 작업 | 어려운 버그나 모호한 설계 시제품에서는 막다른 길만 늘어남 | 반복하는 집중 세션 하나가 낫다 |

두 가지를 더 풀어 쓴다.

- 공유 상태: 두 에이전트가 같은 설정, 스키마, 라우트 파일에 항목을 추가하면 충돌한다. 책은 이 충돌을 푸는 비용이 병렬로 아낀 시간보다 클 때가 많다고 말한다.
- 작은 작업: 순서대로 하면 2분 걸리는 일을 에이전트에 쪼갠 뒤 결과를 검토하고 병합하면 오히려 더 오래 걸릴 수 있다.

## 3. 장 요약과 체크리스트

장 요약은 이렇다. 데스크톱 앱 안에서 Claude Code를 쓰고, 로컬 워크트리와 클라우드 모드를 오가며, 코딩 에이전트 여럿을 병렬로 돌렸다. 깃 워크트리가 기능 개발을 격리하고, 백그라운드 에이전트가 클라우드에서 돌며, 독립적으로 만든 브랜치를 병합하고 시험해 하나의 코드베이스로 합쳤다. 같은 흐름이 모바일로도 확장되어 실행이 전부 클라우드에서 일어난다.

책의 프로팁(Protip)이 주는 정신 모형은 이렇다. 병렬 에이전트는 작업이 독립적이고, 범위가 분명하며, 코드베이스의 서로 다른 부분을 건드릴 때 가장 잘 맞는다. 확신이 없으면 순차로 시작하고, 작업끼리 상호작용하지 않는다고 확인한 뒤에 병렬로 넓힌다.

병렬 개발 체크리스트(Parallel Development Checklist)는 네 줄이다.

1. 각 작업이 독립된 파일이나 컴포넌트에서 일하는지 확인한다.
2. 각 에이전트의 프롬프트에 올바른 시작 브랜치를 명시했는지 확인한다.
3. 대상 브랜치로 푸시하기 전에 병합 결과를 시험한다.
4. 병합이 끝난 뒤 워크트리 디렉터리를 정리한다.

참고(노트 작성자): 이 체크리스트는 앞 문서의 사례와 하나씩 짝이 맞는다. 클라우드 에이전트가 main에서 시작한 일이 2번과, 푸시 전 로컬 시험이 3번과 연결된다.
