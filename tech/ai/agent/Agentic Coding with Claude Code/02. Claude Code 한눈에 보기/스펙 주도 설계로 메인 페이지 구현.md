# 스펙 주도 설계로 메인 페이지 구현

이 문서는 2장의 마지막 실습이다. 계획 모드에서 Opus 모델로 HookHub의 스펙 파일을 쓰게 하고, 그 스펙을 @로 붙여 Sonnet 모델로 메인 페이지를 구현한다. 코드를 바로 시키지 않고 스펙을 먼저 두면 결과의 품질과 일관성이 올라간다는 점을 몸으로 확인하는 과정이다.

비유하면 건축 의뢰다. 시공사에 '대충 멋진 집을 지어 달라'고 하는 대신 설계도를 먼저 받아 두고, 시공할 때마다 그 설계도를 펼쳐 놓고 짓게 한다.

---

## 1. 스펙 주도 설계란

원서는 앱을 분위기로 짜는 바이브 코딩 대신 스펙 주도 설계(spec-driven design)를 쓴다고 말한다. 원문 PDF에 'pec-driven design'으로 첫 글자가 빠져 있으나 문맥상 spec-driven design이 분명하다. 아이디어는 애플리케이션과 유스케이스 또는 비즈니스 유스케이스, 가능하면 비기능 요구사항까지 설명하는 스펙 파일을 만드는 것이다. 그리고 Claude가 코드를 쓸 때 이 스펙 파일을 참조하게 한다. 이렇게 하면 컨텍스트 윈도우가 최적화되고 결과가 좋아진다. 더 자세한 내용은 뒤에서 다룬다.

## 2. 계획 모드에서 스펙 쓰기

먼저 Shift + Tab을 눌러 Claude Code를 계획 모드(plan mode, 읽기 전용으로 조사하고 계획만 세우는 모드)로 바꾼다. 계획 모드는 이런 작업에 맞게 설계되었다. 읽기 전용 작업을 하며 조사하고 Claude가 무엇을 할지 계획하는 것이다. 저자는 모델도 고른다. 계획 모드에서는 대개 깊은 추론이 되는 무거운 모델을 선호한다. /models 명령으로 가장 최신 Opus가 선택되어 있는지 확인한다. 책이 쓰인 시점에는 Opus가 깊은 추론에 가장 앞선 모델이었다. 참고(노트 작성자): 원서의 명령 표기는 /models이며, 실제 명령 이름과 모델 구성은 바뀔 수 있으므로 공식 문서로 확인한다. 또 긴 프롬프트를 붙여 넣으면 실제 텍스트가 아니라 붙여 넣은 내용을 나타내는 표시만 보인다고 한다.

프롬프트는 이런 내용이다. 내가 만드는 프로젝트 hookhub의 스펙 파일 작성을 도와 달라. 멋진 오픈소스 Claude 훅을 보여 주고 둘러보는 곳이다. Claude 훅을 검색해서 초기 스펙을 써 달라. 지금은 MVP이므로 훅을 보여 주는 기능만 필요하다. 훅은 GitHub 저장소에서 찾고, 이름, 카테고리, 설명, 저장소 링크가 있다. 메인 페이지는 훅을 그리드 형태로 보여 줘야 한다.

저자는 이 프롬프트에 대해 다섯 가지를 짚는다. HookHub를 오픈소스 Claude 훅을 보고 둘러보는 곳으로 설명했고, 훅을 검색해 초기 스펙을 쓰라고 했고, MVP라서 기능이 훅 표시로 한정됨을 밝혔고, 훅이 가진 필드(이름, 카테고리, 설명, 저장소 링크)를 주었고, 메인 페이지를 그리드 뷰로 지정했다. 특별한 것이 없고 프롬프트 엔지니어링 기법도 쓰지 않았다는 점이 요점이다.

제출하면 Claude는 읽기 전용 도구만 쓴다. 이 단계에서는 쓰기나 편집이 일어나지 않는다. Claude는 웹 검색 도구로 오픈소스 Claude Code 훅을 조사하고, Anthropic 문서를 가져와도 되는지 권한을 묻는다. 승인하면 조사가 끝난 뒤 계획을 제시한다. 계획에 담긴 항목은 이렇다.

- 프로젝트 개요
- MVP 범위
- Claude Code 훅의 데이터 모델
- UI와 UX 요구사항
- 기술 아키텍처
- 사용자 스토리
- 향후 고려 사항

## 3. 스펙 파일 저장 위치 바로잡기

계획을 승인하면 Claude가 쓰기 모드로 넘어가 hookhub/SPEC.md에 파일을 쓰겠다고 요청한다. 저자는 이를 거절하고 다음처럼 지시한다. 스펙은 spec 디렉터리 안에 CLAUDE.md 파일로 쓰라는 것이다.

```text
I want you to write it into a spec directory and make this a CLAUDE.md file
```

Claude가 다시 spec/CLAUDE.md로 쓸 준비를 하고, 승인하면 편집을 허용한다. 이때 처음으로 할 일 목록(to-do list)이 나온다. Claude는 목록의 작업을 하나씩 처리하며 승인을 요청하고, 우리는 요청마다 승인한다. 할 일 목록은 뒤에서 자세히 다루지만 결과 품질에 큰 역할을 하며, Claude Code가 코딩 에이전트로 잘 동작하는 이유 중 하나라고 한다. 저자는 Claude Code가 상당한 추론이 필요한 오래 걸리는 다단계 작업을 다루는 딥 에이전트처럼 동작한다고 설명한다. 딥 에이전트는 11장에서 다룬다.

완성된 스펙(CLAUDE.md)에는 프로젝트 개요와 비전, 훅 카테고리, 훅 객체 구조, 앱이 어떻게 보여야 하는지, 만드는 데 필요한 단계 등 구현 때 Claude에게 도움이 될 정보가 많이 들어 있다. LLM에게 스펙을 쓰게 하는 것은 흔한 패턴이며 다른 고급 패턴은 뒤에서 다룬다. 마지막으로 spec 디렉터리를 memory 디렉터리 아래로 옮긴다. 그러면 모든 장기 컨텍스트가 한곳에 모여 필요할 때 재사용된다.

```text
memory/
  frontend/CLAUDE.md
  spec/CLAUDE.md
```

## 4. 모델을 바꾸고 스펙으로 구현하기

구현 전에는 모델을 Sonnet으로 바꾼다. 계획에는 무거운 모델을, 구현에는 가벼운 모델을 쓰는 흐름이다. 프롬프트는 '스펙 파일에 지정된 대로 메인 페이지 그리드를 구현해 달라'이고, @ 기호로 spec/CLAUDE.md를 태그해 컨텍스트에 붙인다.

여기서 컨텍스트 관리 교훈이 나온다. 프롬프트를 내고 결과를 받고 또 프롬프트를 낼 때마다 컨텍스트가 채워진다. 같은 세션을 계속 쓰면 결국 컨텍스트 윈도우가 차고, 그러면 결과가 나빠진다. 대처법은 몇 가지다. 컨텍스트를 비우거나 요약하면서 유용한 부분을 남기는 사용자 정의 명령이 있고, 이는 뒤에서 다룬다. 내장된 /clear와 /compact로도 세션을 다시 시작하지 않고 관리할 수 있다. 지금은 가장 단순한 방법으로, /exit로 세션을 끝내고 Claude를 다시 열어 HookHub 폴더에 들어가 새로 시작해 컨텍스트를 비운다. 그리고 같은 프롬프트를 다시 쓴다.

## 5. 구현 실행과 결과

Claude는 할 일 목록을 만들고 항목을 하나씩 구현한다. Hooks.ts 같은 파일을 쓰려 할 때 승인을 묻고, 승인하면 구현이 이어진다. 시간이 꽤 걸린다. 끝나면 훅 카드 컴포넌트가 만들어지고 나머지 단계가 이어지며, 오류를 잡기 위해 린트(lint, 코드 오류와 스타일 검사)를 실행한다. 마지막에 카드 컴포넌트, 히어로 섹션, 헤더 등 구현한 내용을 요약해 준다. 브라우저를 새로 고치면 Claude Code 훅 카드가 그리드로 나타난다.

이번에는 파일 참조를 찾지 못했다는 문제가 있었다. Claude Code를 HookHub 디렉터리 안에서 열었는데 memory 디렉터리는 프로젝트 루트 위쪽에 있었기 때문이다. 해결은 memory 디렉터리를 hookhub 밑으로 옮기는 것이다. 옮기면 파일 참조가 정상 동작한다.

결과는 기본적인 Next.js 애플리케이션이다. 검색 같은 일부 기능은 아직 없지만 일부는 이미 구현되어 있다. 앞으로 계속 쌓아 갈 단단한 뼈대가 생긴 것이다. 책의 뒷부분은 서브에이전트를 동적으로 여러 개 띄우기, UI 컴포넌트 반복 개선, 메타 프롬프팅(프롬프트를 쓰는 프롬프트) 같은 고급 워크플로를 이 프로젝트 위에서 실험한다.

## 6. 커밋하고 최종 구조 확인

마지막으로 코드를 저장소에 커밋해 공유한다. 절차는 git status를 실행하고, 파일을 모두 추가하고, 비밀 값이나 환경 변수가 포함되지 않았는지 확인한 뒤, 'initial project' 같은 메시지로 커밋하고 푸시하는 것이다. 저장소의 project/hookhub 브랜치에서 파일을 보고 같은 커밋의 코드를 받을 수 있다. 저장소 주소는 머리말의 예제 코드 내려받기 안내를 따르면 된다.

2장 실습을 모두 끝낸 HookHub의 구조는 app, components, memory(frontend와 spec 하위 폴더, 각각 CLAUDE.md), package.json, next.config.js 등이다. 이 구조와 같으면 다음 장을 위한 준비가 올바르게 된 것이다.
