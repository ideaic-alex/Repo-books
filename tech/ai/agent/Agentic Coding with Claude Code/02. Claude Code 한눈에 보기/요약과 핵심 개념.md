# 요약과 핵심 개념

2장은 HookHub 프로젝트를 만들며 Claude Code의 기본 동작을 익히는 실습 장이다. 프로젝트 준비와 CLAUDE.md 생성, 권한 시스템, Playwright MCP와 memory 폴더, 스펙 주도 설계와 메인 페이지 구현의 네 덩어리로 이뤄진다. 이 문서는 네 덩어리를 한 번에 되짚고 핵심 용어를 정리한다.

원서의 장 요약은 이렇다. Claude Code가 프로젝트를 관찰하고, CLAUDE.md로 컨텍스트를 만들고, 명시적 권한으로 안전하게 동작하는 방식을 보았다. MCP로 내장 기능을 넘어 확장하고, Playwright 같은 외부 도구가 워크플로에 들어맞는 모습을 보았으며, 스펙 주도 설계가 더 일관되고 예측 가능한 결과를 내는 이유를 보았다. 결과의 질은 우리가 주는 컨텍스트, 구조, 통제의 질에 직접 달려 있다. 다음 장은 가격과 인증, 슬래시 명령, 사용자·프로젝트 수준 설정, Cursor 연동을 다룬다.

---

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | Next.js 프로젝트 준비 | create-next-app으로 만들고 npm run dev로 localhost:3000에서 확인 |
| 2 | /init과 권한 시스템 | 프로젝트를 훑어 CLAUDE.md 생성. 편집마다 승인을 묻는다 |
| 3 | Playwright MCP | claude mcp add로 연결하고 /mcp로 확인한 뒤 브라우저 열기 시험 |
| 4 | memory 폴더 | Cursor 규칙을 frontend 메모리로 저장. 자동으로 읽히지 않음을 확인 |
| 5 | 스펙 작성 | 계획 모드와 Opus로 HookHub 스펙을 쓰고 spec/CLAUDE.md로 저장 |
| 6 | 구현과 커밋 | Sonnet으로 스펙을 @ 태그해 메인 페이지 그리드 구현. memory를 hookhub 아래로 옮김 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| /init | 코드베이스를 스캔해 기술 스택과 구조를 CLAUDE.md에 담는 첫 명령 |
| CLAUDE.md | 요청을 보낼 때마다 먼저 로드되는 프로젝트 컨텍스트 파일 |
| 권한 시스템 | 파일 생성과 편집, 외부 도구 사용마다 사용자 승인을 묻는 안전장치 |
| Playwright MCP | 브라우저 자동화 능력을 Claude Code에 붙이는 MCP 서버 |
| -s user | MCP를 사용자 범위로 등록해 모든 Claude Code 인스턴스에서 쓰게 하는 플래그 |
| Cursor 규칙 | 마크다운으로 AI에게 페르소나와 지침을 주는 규칙. Claude Code에서도 쓸 수 있다 |
| memory 폴더 | 자동 로드되지 않는 장기 컨텍스트 파일(frontend, spec)을 모아 둔 곳 |
| 계획 모드 | Shift + Tab으로 켜는 읽기 전용 조사와 계획 모드. 깊은 추론용 모델과 어울린다 |
| 스펙 주도 설계 | 코드 전에 스펙 파일을 두고 구현 때 참조하게 해 품질과 일관성을 높이는 방식 |
| 할 일 목록 | Claude가 작업을 쪼개 차례로 처리하는 목록. 결과 품질에 큰 역할을 한다 |

## 3. 자주 놓치는 점

- memory 폴더의 CLAUDE.md는 자동으로 읽히지 않는다. 'What are you expert in?'에 일반적인 답이 나오는 것은 오류가 아니라 의도된 동작이다. 언제 불러올지는 3장 이후에서 설정한다.
- @ 파일 참조는 Claude Code를 연 폴더 기준이다. HookHub 폴더에서 열었는데 memory가 그 바깥에 있으면 참조를 찾지 못하므로 memory를 hookhub 아래로 옮겼다.
- 계획 모드와 구현 모드에 같은 모델을 쓸 필요는 없다. 저자는 계획에 최신 Opus, 구현에 Sonnet을 쓴다. 모델 이름과 명령은 책이 쓰인 시점 기준이다.
- 계획 모드에서 Claude는 읽기 전용 도구만 쓴다. 파일이 써지는 것은 계획을 승인한 뒤이며, 그때도 쓰기마다 승인을 묻는다.
- 한 세션을 계속 쓰면 컨텍스트 윈도우가 차서 결과가 나빠진다. 이 장은 /exit 후 재시작이라는 단순한 방법을 쓰고 /clear와 /compact는 뒤에서 다시 본다.
- 스펙을 만들 때 프롬프트에 정교한 프롬프트 엔지니어링은 필요 없었다. 핵심은 목적, MVP 범위, 데이터 필드, 화면 모양을 분명히 알려 주는 것이다.
- 커밋 전에는 git status로 비밀 값이나 환경 변수가 섞이지 않았는지 확인한다.
- 원서는 서브에이전트를 3장에서 다룬다고 안내하지만 목차상 7장이다. 이 노트는 목차를 따른다.
