# 요약과 핵심 개념

6장은 두 덩어리다. 먼저 계획 모드로 계획과 실행을 분리해 스펙 주도 개발을 하는 방법을 보고, 이어서 Claude Code 여러 개를 병렬로 돌려 독립된 일을 동시에 끝내는 방법을 본다. 이 문서는 두 덩어리를 한 번에 되짚고 용어를 정리한다.

원서의 장 요약은 이렇다. 계획 모드는 분석과 구현을 분리해 스펙 주도 개발을 가능하게 한다. 스펙은 깊은 생각으로 다듬고 프로젝트 기억으로 저장한다. 여러 Claude Code가 공유 코드베이스에서 독립된 일을 병렬로 처리할 수 있다. 다음 장은 서브에이전트를 다룬다.

---

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | 계획 모드의 특성과 작업 순서 | 읽기 전용으로 조사하고 계획을 세워 승인받은 뒤에만 구현한다 |
| 2 | 스펙 주도 개발의 이점 | 계획과 실행이 분리되어 위험, 환각, 부작용이 줄어든다 |
| 3 | HookHub 스펙 실습 | `/plan`으로 스펙을 만들고 피드백으로 고쳐 Markdown 파일로 저장한다 |
| 4 | 병렬 실행 대상 고르기 | 독립 작업은 병렬로, 의존 작업은 순서대로 한다 |
| 5 | HookHub 병렬 실습 | 두 터미널이 HookCard.tsx와 Hero.tsx를 각각 맡아 충돌 없이 끝낸다 |
| 6 | 한계와 다음 단계 | 같은 브랜치 병렬은 깨지기 쉬우니 브랜치나 워크트리로 분리한다 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 계획 모드 | 읽기 전용으로 조사하고 계획이나 스펙을 만드는 단계. 승인 전에는 코드가 바뀌지 않는다 |
| `/plan` | 계획 모드에 들어가는 명령 |
| 스펙 주도 개발 | 구현 전에 풀 문제와 방법을 스펙으로 정의하는 방식 |
| 프로젝트 기억 | 저장해 둔 스펙 파일을 이후 요청의 맥락으로 다시 쓰는 것 |
| 병렬 에이전트 | 같은 프로젝트에서 Claude Code 인스턴스 여러 개를 동시에 실행하는 방식 |
| 독립 작업 | 서로 결과를 기다리지 않아 동시에 해도 되는 일 |
| 의존 작업 | 앞 작업의 결과가 필요해 순서대로 해야 하는 일 |
| 깃 워크트리 | 에이전트마다 별도 브랜치와 작업 폴더를 주는 표준적인 격리 방법 |

## 3. 자주 놓치는 점

- 계획 모드는 계획을 세우는 동안 어떤 파일도 만들거나 지우지 못한다. 참고(노트 작성자): 그렇다면 계획 파일 저장은 승인 뒤 실행 단계에서 이뤄진다고 읽히지만, 책은 이 순서를 따로 밝히지 않는다.
- 계획은 한 번에 끝나지 않는다. 캐러셀을 빼고 이벤트 유형을 더하듯 피드백으로 반복해서 고친다.
- 스펙은 말로 끝내지 말고 Markdown 파일로 저장해야 맥락으로 다시 쓰인다.
- 풀스택 기능처럼 백엔드와 프런트엔드가 이어진 일을 동시에 시키면 목업과 인터페이스 불일치가 생긴다.
- 병렬 프롬프트에는 수정할 파일과 건드리지 말 파일을 함께 적어야 서로의 영역을 침범하지 않는다.
- 같은 브랜치에서 파일만 나눠 쓰는 병렬은 입문용 구성이다. 실무의 표준은 브랜치나 워크트리 분리다.
- 책에 나온 커밋 해시는 자리표시자뿐이라, 실습을 따라 하려면 자신의 저장소에서 기준 커밋을 직접 정해야 한다.
