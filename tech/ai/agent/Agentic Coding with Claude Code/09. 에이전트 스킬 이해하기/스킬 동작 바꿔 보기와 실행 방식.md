# 스킬 동작 바꿔 보기와 실행 방식

복제한 스킬을 가지고 실험하는 부분이다. 스킬을 불러 써 보고, 트리거 문구를 고쳐 보고, 승인 절차를 없애고, 스크립트가 Claude를 부르게 만들고, 일부러 폴더 구조를 망가뜨려 본다. 실험마다 한 가지 교훈이 나온다. 스킬이 어떤 부분으로 선택되고 어떤 부분으로 실행되는지가 드러난다.

자동차 정비로 비유하면, 엔진 덮개를 열고 부품을 하나씩 바꿔 끼우며 어느 부품이 어떤 일을 하는지 확인하는 과정과 같다.

---

## 1. 커스텀 스킬 사용해 보기

프로젝트 디렉터리에서 Claude Code 세션을 열고 "List available skills."를 입력한다. 새로 만든 프로젝트 수준 `git-pushing` 스킬이 이전에 설치한 마켓플레이스 스킬과 함께 보인다. 이어서 "push changes"를 입력한다.

Claude가 git-pushing 스킬을 써도 되는지 묻는다. 승인하면 SKILL.md를 로드하고 `smart_commit.sh`를 실행해야 한다고 판단한다. 깃 명령을 하나씩 내리지 않고 스크립트를 돌린다.

스크립트가 깃 오류로 실패할 때도 있다. 그래도 Claude는 멈추지 않는다. 기본 추론으로 돌아가 저장소 상태를 분석하고, `git add -A` 실행을 제안하고, 자기 판단으로 커밋을 만들고, 변경을 수동으로 푸시한다. 즉 스킬이 에이전트의 추론을 대체하지 않는다. 스킬이 실패하면 Claude는 기본 동작으로 돌아가 작업을 이어 간다. 다만 이때의 커밋은 스킬이 아니라 Claude의 기본 동작으로 만들어진 것이다. 스킬은 구조화된 워크플로를 주지만 에이전트의 일반 추론 능력을 없애지 않는다.

## 2. 트리거 문구 고쳐 보기: 효과가 없는 수정

SKILL.md의 When to Use 항목에 "push to remote"라는 트리거 문구를 추가한다. 그다음 컨텍스트를 비우고 새 세션에서 "push to remote"를 입력하면 Claude는 여전히 git-pushing 스킬을 쓰겠냐고 묻는다. 그런데 이것은 우리가 추가한 문구 때문이 아니다.

이유는 이렇다. When to Use는 YAML 프런트매터가 아니라 본문에 속한다. 닫는 `---` 위쪽만 프런트매터이며 시스템 프롬프트에 주입된다. 그 아래 본문은 스킬이 이미 선택된 뒤에야 에이전트에게 보인다. 그러므로 이 수정은 스킬 선택 판단에 영향을 주지 않는다.

그러면 왜 스킬이 여전히 켜졌을까. 원래의 프런트매터 description이 이미 커밋과 푸시 작업을 다룬다고 적었기 때문이다. "push to remote"는 "push changes"나 "push to GitHub"와 의미가 가까워서 기존 설명만으로도 충분히 일치했다.

정리하면 스킬 선택은 전적으로 프런트매터가 결정한다. 에이전트는 사용자 의도를 그 YAML의 name과 description에 맞춰 본다. 파일의 나머지는 선택 단계에서 아무 역할도 하지 않는다. 선택된 뒤에야 Claude가 SKILL.md의 나머지, 곧 워크플로 지시와 스크립트 참조를 읽는다. 이것이 점진적 공개 모델이다.

1. 에이전트는 늘 프런트매터를 본다.
2. 그것을 근거로 스킬을 활성화할지 정한다.
3. 그다음에야 전체 스킬 컨텍스트와 보조 지침을 불러온다.

트리거를 바꾸고 싶다면 본문이 아니라 프런트매터의 description을 고쳐야 한다.

## 3. 자동 승인 켜기

스킬이 제대로 트리거되는데 쓸 때마다 Claude가 승인을 묻는다면, 스킬로 만든 워크플로에도 마찰이 남는다. 커밋과 푸시마다 수동 확인이 필요하면 간결한 워크플로라는 목적이 무색하다. 바꿔야 할 것은 스킬 선택이 아니라 실행 방식이다.

스킬이 올바르게 트리거되는 것을 확인한 뒤, 승인 없이 이 스킬을 계속 쓰도록 허용하는 선택지를 고른다. 그러면 Claude가 `settings.local.json`을 갱신한다. 스킬 정의는 그대로고, 이 스킬이 선택됐을 때 대화형 확인 없이 실행할 수 있도록 로컬 설정이 바뀔 뿐이다.

따라서 서로 다른 두 가지 권한이 있다.

- 스킬을 활성화할 권한
- 스킬 안에 정의된 스크립트를 실행할 권한

자동 승인을 켜면 이후 실행에서 두 단계 확인이 모두 사라진다. 이제 "push to remote"를 입력하면 Claude가 스킬을 바로 로드하고 `smart_commit.sh`를 묻지 않고 실행한다. 스킬에 정의된 워크플로가 완전히 자동화된다.

## 4. 스크립트에 AI 호출 넣기

실행이 성공한 뒤 생성된 커밋을 살펴보면 메시지가 아주 단순하다. 몇 개의 파일이 갱신됐다고만 적혀 있다. 이것은 AI가 쓴 메시지가 아니다. `smart_commit.sh`를 보면 정적 로직이 수정된 파일 개수를 세어 미리 정한 템플릿에 끼워 넣는 구조다. 스크립트 안에 Claude 호출은 없다.

여기서 중요한 구분이 나온다. 스킬이라고 해서 AI 기반 로직인 것은 아니다. 스킬은 포장 방식일 뿐이고, 결정적 스크립트, AI 호출, 또는 둘 다를 담을 수 있다. 워크플로의 지능 수준은 전적으로 스크립트 구현이 정한다.

이를 개선하기 위해 Claude에게 스크립트를 고치라고 시킨다. 책의 프롬프트는 커밋 메시지를 해적 말투로 만들라는 장난스러운 요구다.

```text
can u please edit @.claude/skills/git-pushing/scripts/smart_commit.sh
to use Claude Code cli to create the commit message like a pirate?
```

변경 후 스크립트는 다음을 한다.

1. `claude -p`에 프롬프트를 넣어 호출한다. `-p` 플래그는 질의를 보내고 응답을 표준 출력에 찍은 뒤 종료하는 프롬프트 모드다.
2. Claude CLI가 커밋 메시지를 동적으로 만든다.
3. 스크립트가 그 출력을 `git commit` 명령에 쓴다.

이렇게 층을 이룬 시스템이 된다. 메인 Claude Code 에이전트가 스킬을 고르고, 스킬이 `smart_commit.sh`를 실행하고, 스크립트가 Claude CLI를 부르고, CLI가 커밋 메시지를 만들고, 스크립트가 커밋과 푸시를 끝낸다. 스킬은 결정적 실행을 조율하고, 스크립트는 AI 호출을 조율하며, AI 호출은 구조화된 출력을 만들고, 스크립트가 그 출력을 소비한다.

"push to remote"를 다시 실행하면 해적풍 커밋 메시지가 나타나 스크립트가 Claude CLI를 내부적으로 잘 부르고 있음이 확인된다. 정적 워크플로에서 결정적 처리와 AI를 섞은 하이브리드 워크플로로 넘어온 것이다.

## 5. 구조를 일부러 망가뜨리기

폴더 구조가 SKILL.md가 기대하는 모양과 달라지면 어떻게 될까. IDE에서 `smart_commit.sh`를 `scripts` 폴더 밖 `git-pushing` 폴더 바로 아래로 옮기고 `scripts` 디렉터리는 통째로 지운다. SKILL.md는 `skills/git-pushing/scripts/`를 기대하는데 파일은 `skills/git-pushing/`에 있다. 스킬에 적힌 경로가 틀린 상태이고 저장소 구조도 기술적으로 어긋난다.

컨텍스트를 비우고 "push to remote"를 입력한다. Claude Code는 git-pushing 스킬을 고르고 스크립트를 실행하며, 경로가 안 맞는데도 성공한다.

이유는 스킬이 결국 에이전트에게 컨텍스트와 지침을 주입하는 것이기 때문이다. SKILL.md의 경로가 틀려도 에이전트가 저장소 구조를 추론해서 `smart_commit.sh`가 옮겨진 위치를 찾는다. 스킬은 정확한 파일 경로에 단단히 묶인 것이 아니라 맥락을 가진 지침이다. 파일이 저장소 어딘가에 있으면 에이전트는 적응한다.

그렇다면 `smart_commit.sh`를 아예 지우면 어떻게 될까. 에이전트가 찾을 파일이 없고 필요한 산출물이 사라졌으므로 워크플로를 실행할 수 없다. 구조가 어긋났더라도 파일이 있으면 에이전트가 복구하지만, 파일이 없으면 실행은 실패한다. 그 경계가 여기다.

## 6. 격리된 서브에이전트 컨텍스트에서 실행

스킬은 기본적으로 현재 대화 컨텍스트 안에서 돈다. 프런트매터에 다음을 넣으면 격리된 서브에이전트 컨텍스트에서 실행할 수 있다.

```yaml
---
context: fork
agent: Explore
---
```

`context`를 `fork`로 두면 Claude가 스킬을 별도의 실행 갈래에서 돌려서, 중간 추론과 도구 사용을 메인 대화와 분리한다. `agent` 필드는 어떤 서브에이전트 종류가 실행을 맡을지 정한다(예: Explore, Plan).

참고(노트 작성자): 이 절의 기능은 책이 쓰인 시점 기준의 설명이며 필드 이름과 동작은 버전에 따라 바뀔 수 있다. 원서는 fork 모드의 세부 설정은 다루지 않는다.
