# 사례 연구와 업무 시스템

보너스의 일곱째와 여덟째 묶음은 사례 연구 30개와 완결된 업무 시스템 10개다. 원서로는 456쪽부터 462쪽까지다. 사례는 원칙 하나를 보이려고 만든 짧은 가상 합성 이야기이고, 업무 시스템은 여러 장의 기법을 하나의 운영으로 묶은 설계도다. 이 문서는 두 묶음을 표로 정리하고, 어떻게 활용하는지 덧붙인다.

저자는 사례가 "실제 이름 있는 기업의 기록이 아니라 이 책을 위해 만든 시나리오"라고 밝힌다. 따라서 사례의 결과(예: 어떤 수치가 35퍼센트였다)는 저자의 서술이며 검증된 통계가 아니다.

---

## 1. 사례 연구 30개

각 사례는 한두 문장이고 끝에 해당 장 번호가 붙는다. 아래 표는 사례의 교훈을 장 번호 순서가 아닌 책의 순서 그대로 요약한다.

| 번호와 사례 | 교훈 | 장 |
|---|---|---|
| 1. 화원의 이메일 시퀀스 | 모호한 지시 대신 실제 브랜드 어조 예시를 붙였더니 세 번의 일반적 시도 뒤 첫 초안이 쓸 만했다 | 5 |
| 2. 법무법인의 정보 장벽 | 의뢰 사건마다 프로젝트를 나눠 기밀을 격리하면서도 신입에게 즉시 맥락을 줬다 | 6, 26 |
| 3. 분석가의 숨은 수수료 | 형식을 지정한 구조적 비교 프롬프트가 "어느 쪽이 좋아?"가 놓친 각주 속 수수료를 잡았다 | 3 |
| 4. 식당 체인의 데이터 정리 | 정리 패스로 저조한 지점의 실체가 판매 기록 누락임을 밝혀 오판을 피했다 | 16 |
| 5. 보조금 작성자의 검증된 통계 | 점검 패스가 단일 연구를 합의처럼 쓴 주장을 제안서 제출 전에 잡았다 | 15 |
| 6. 마케팅 팀의 사실 확인 | 측정한 적 없는 "온보딩 시간 60퍼센트 단축"을 잡았고 실제는 35퍼센트였다 | 13 |
| 7. 컨설팅사의 프롬프트 재구성 | 마스터 프롬프트에 어조 예시, 부정 예시, 구조화된 상품 데이터를 함께 넣자 설명 스무 개가 서로 달라졌다 | 4 |
| 8. 부동산 중개인의 낡은 메모리 | 예전 주거 중심 메모리가 상업용으로 바뀐 뒤에도 대화를 편향시켰고 정기 검토로 발견했다 | 7 |
| 9. 교사의 인터랙티브 퀴즈 | 평문 설명으로 분수 연습 퀴즈 아티팩트를 만들고, 학생에게 주기 전에 직접 시험했다 | 8 |
| 10. 기자의 오독 발견 | 자신 있게 제시된 통계를 독립 검증해 1차 자료의 미묘한 오독을 보도 전에 잡았다 | 18 |
| 11. 제조 임원의 계약 조항 | 절 단위 비교 검토가 일반 요약이 압축해 버렸을 가격 조정 조항의 문구 변경을 잡았다 | 10 |
| 12. 에이전시의 팀 기준 도입 | 공유 프로젝트, 서면 온보딩, 기준 문서로 신입이 첫 주에 고객용 결과를 냈다 | 27 |
| 13. 창업자의 빠진 기준 | 가중 틀의 1위가 어색하던 중 장기 관계 가능성이라는 빠진 기준을 더하자 결과가 바뀌었다 | 17 |
| 14. 웨딩 플래너의 엣지 케이스 | 견적 계산기의 손님 0명 오류와 조용한 기본값 문제를 공개 전 시험에서 잡았다 | 19 |
| 15. 부동산 관리인의 점진적 자동화 | 정비 요청 분류를 사람이 확인하는 제안부터 시작해 몇 달 정확성을 본 뒤 일상 범주만 확대했다 | 20 |
| 16. 개발자의 검토한 차이 | 범위를 정한 Claude Code 기능 구현이 공용 유틸리티 파일을 의도치 않게 바꾼 것을 요약이 아닌 실제 차이를 보고 발견했다 | 23 |
| 17. 독학 개발자의 타이밍 버그 | "간헐적"이라던 재고 스크립트 버그가 분리해 보니 재현 가능한 타이밍 문제였고 이후 선제적으로 살피는 유형이 됐다 | 24 |
| 18. 밀키트 회사의 API 기능 | 개발자가 구현해도 마케팅 리드가 프롬프트 의도와 식이 제한 검증 기준에 관여했다 | 25 |
| 19. 치료사의 민감도 등급 | 운영 정보는 자유롭게 쓰되 실제 내담자 건강 정보는 비밀 유지 의무에 맞춰 철저히 배제했다 | 26 |
| 20. 자문사의 검증 해이 | 연간 검토에서 고객용 숫자 검증이 익숙함 때문에 조용히 느슨해진 것을 발견하고 다시 다잡았다 | 28 |
| 21. 보조금 작성자의 시스템 정리 | 연간 검토에서 몇 달 안 쓴 고객 유형 프로젝트 둘을 정리해 새 고가치 고객 유형에 집중했다 | 29 |
| 22. 사업주의 전체 회고 | 1년 뒤 인터페이스 세부는 바뀌었지만 명확한 프롬프트, 선별한 맥락, 적절한 검증 습관은 그대로 이어졌다 | 30 |
| 23. 비영리의 솔직한 종합 | 단일 연구와 충분히 입증된 발견을 구분 표시한 조사 브리프가 제안서 전에 재맥락화할 주장을 잡았다 | 15 |
| 24. 재무 상담사의 구체성 주입 | 지어낸 예시 대신 익명화한 실제 고객 시나리오를 넣어 은퇴 설계 가이드가 일반론에서 자기 것이 됐다 | 12 |
| 25. 영업 이사의 어조 분리 | 호재와 영업 구역 개편을 섞은 분기 메일이 밋밋하다가, 두 메시지를 따로 구조화하고 어조를 나누자 살아났다 | 11 |
| 26. 스킨케어 브랜드의 잠근 핵심 메시지 | 개별 글 전에 핵심 메시지를 잠가서 이메일, 소셜, 랜딩 페이지가 일관됐다 | 13 |
| 27. 주니어 어소시에이트의 자체 편집 | 구조적 자체 편집이 고객 보고서의 뜸 들이는 서두와 모호한 "상당한 개선" 표현을 잡았다 | 14 |
| 28. 스타트업의 최대 변호 선택지 | 낮은 점수 선택지를 일부러 가장 강하게 변호하자 틀이 놓친 장기 이점이 드러나 제휴 결정이 바뀌었다 | 17 |
| 29. 컨설팅사의 컨텍스트 패킷 효과 | 고객 인사이트 브리프 양식, 예시, 필수 범주를 한 컨텍스트 패킷으로 표준화해 몇 달간의 들쭉날쭉한 형식이 사라졌다 | 5 |
| 30. 독자의 회고 루프 | 1장의 "내가 Claude를 쓰는 방식과 쓰지 않는 방식" 회고를 간직해 다시 본 독자는 습관이 어떻게 성숙했는지 구체적 기록을 얻었다 | 1, 30 |

사례를 읽는 법은 간단하다. 내가 겪는 문제와 같은 교훈이 어느 사례인지 찾고, 장 번호를 따라 본문의 원리로 돌아간다. 예를 들어 "Claude가 일반적인 글만 쓴다"면 1번(실제 어조 예시)과 7번(부정 예시와 구조화 데이터)이 해법을 가리킨다.

## 2. 사례에서 반복되는 네 가지 교훈

- **맥락의 질**이 결과를 정한다(1, 7, 24, 29번). 예시, 부정 예시, 실제 자료가 일반론을 이긴다.
- **검증은 사람의 일**이다(5, 6, 10, 16번). 단일 연구, 측정 안 한 수치, 숨은 변경은 사람이 직접 원문과 차이를 볼 때 잡힌다.
- **점진적으로 넓힌다**(15, 19번). 자동화와 민감 정보 모두 좁게 시작하고 증거로 확대한다.
- **정기 점검**이 낡음을 막는다(8, 20, 21, 22번). 메모리, 검증 습관, 프로젝트 모두 시간이 지나면 조용히 낡는다.

## 3. 업무 시스템 10개

업무 시스템은 한 번 만들어 계속 쓰는 운영이며, 유지는 29장의 리듬대로 한다. 각 시스템은 구성 요소의 흐름, 처음 만드는 방법, 유지 방법으로 설명된다.

| 번호와 시스템 | 구성(장) | 만들기와 유지 |
|---|---|---|
| 1. 고객 온보딩 | 고객별 프로젝트 양식(6) - 접수 컨텍스트 패킷(5) - 환영 자료와 첫 안건 생성(8) - 고객 데이터 민감도 등급(26) - 지식 유지 담당자 | 자리표시 필드가 있는 양식 프로젝트를 복제해 채움. 활성 고객마다 월간 지식 갱신 |
| 2. 콘텐츠 제작 파이프라인 | 브랜드 어조 브리프(13) - 캘린더 - 개요 승인 관문(12) - 절 단위 작성 - 구조적 수정(일관성, 구체성, 어조)(14) - 사실 확인(18) - 게시와 보관 | 어조 브리프를 한 번 만들어 모든 글에 재사용. 분기 어조 브리프 갱신 |
| 3. 조사와 경쟁 정보 | 상시 조사 브리프 양식(15) - 주간 또는 월간 검색 - 이견 표시 종합 - 주장 유형별 검증 등급(18) - 이해관계자 배포 | 반복되는 핵심 질문을 한 번 정의. 분기에 계속 추적할 가치 검토 |
| 4. 데이터 보고 | 표준 정리 체크리스트(16) - 정밀한 분석 프레임 양식 - 네 가지 검증 습관(표본 점검, 과정 노출, 상식 점검, 교차 확인) - 보고서 양식 - 배포 | 데이터셋의 알려진 특이점을 한 번 문서화. 데이터 출처가 바뀔 때마다 정리 목록 재검토 |
| 5. 의사결정 | 결정 유형별 기준 양식(17) - 가중 점수 - 최대 변호 단계 - 결정 기록(11장의 메모 규율을 결정 문서화에 적용) | 가장 흔한 결정 유형 세 가지(공급사, 채용, 프로젝트 진행)의 양식부터. 우선순위가 바뀌면 매년 가중치 재검토 |
| 6. 팀 조율 | 업무 영역별 공유 프로젝트(6, 27) - 문서화된 팀 기준(어조, 검증, 민감도) - 서면 온보딩 자료 - 프로젝트 소유자 지정 - 분기 기준 검토 | 처음 만들기 가장 힘든 시스템이므로 가장 많이 쓰는 공유 자원 하나부터. 분기 검토는 협상 불가이며 가장 빨리 낡는다 |
| 7. 민감 정보 처리 | 단계별 민감도 틀(26) - 프로젝트 지침에 익명화 기본값 - 정기 데이터 처리 설정 점검 - 규제 분야는 실제 전문 의무로 별도 절차 | 한 번 만들어 다른 모든 시스템에 적용. 분기 설정 점검, 규제 의무가 바뀌면 즉시 갱신 |
| 8. 노코드 도구 개발 | 기능 명세 양식(19) - 만들고 시험하고 고치는 순환 - 엣지 케이스 시험 규율 - 시험 후 공유 관문 - 도구 목록(중복 제작 방지) | 첫 도구는 느려도 전체 과정으로. 분기에 도구 목록 검토, 안 쓰는 도구 폐기 |
| 9. 검증과 품질 관리 | 단계별 검증 기준(18) - 자체 편집 점검표(14) - 신뢰하는 작업도 정기 표본 점검(28) - 잡힌 오류를 프로세스 개선으로 되먹임 - 연간 종합 검토 | 모든 시스템의 바탕이므로 일찍 만든다. 연간 종합 검토가 닻이며 괜찮아 보여도 건너뛰지 않는다 |
| 10. 개인 생산성 | 지렛대 큰 용도 파악(29) - 그 용도의 전용 프로젝트와 컨텍스트 패킷 - 통합 유지 리듬(주, 월, 분기, 연) - 복잡도 증식 점검 - 새 기능 정기 평가(30) | 마지막에 만드는 졸업 시스템이다. 다른 아홉 개를 충분히 써 보고 무엇이 지렛대인지 안 뒤에 만든다. 이 시스템의 유지 리듬은 신성하게 지킨다 |

시스템 예시를 하나 보자. 마케팅 컨설팅 회사가 1번을 만든다. 양식 프로젝트에 환영 자료 템플릿과 접수 질문지 자리를 두고, 새 고객이 계약하면 복제해서 접수 답변을 컨텍스트 패킷으로 넣는다. Claude가 환영 자료와 첫 미팅 안건을 아티팩트로 만들면 담당자가 검토해서 보낸다. 고객별 유지 담당자를 정해 매달 지식을 갱신한다.

## 4. 만드는 순서에 대한 조언

시스템 간에 의존이 있다. 책의 설명을 종합하면 다음 순서가 합리적이다.

1. **검증과 품질 관리(9번)와 민감 정보 처리(7번)를 먼저.** 둘 다 다른 시스템의 바탕이다.
2. **가장 자주 하는 일의 시스템을 다음에.** 콘텐츠, 보고, 온보딩 중 내 일상과 가까운 것이다.
3. **팀 조율(6번)은 하나의 공유 자원부터.** 가장 노력이 많이 든다.
4. **개인 생산성(10번)은 마지막에.** 앞의 시스템이 쌓여야 무엇이 지렛대인지 보인다.

참고(노트 작성자): 이 순서는 원문 각 시스템의 설명("바탕이므로 일찍", "졸업 시스템이므로 마지막")을 노트 작성자가 합쳐 정리한 것이다.

## 5. 흔한 실수와 문제 해결

| 실수 | 증상 | 대응 |
|---|---|---|
| 사례의 수치를 기대치로 삼는다 | 내 결과가 못 미치면 실망한다 | 사례는 원칙을 보이는 가상 이야기로 읽는다 |
| 시스템을 한꺼번에 만든다 | 어느 것도 유지되지 않는다 | 하나를 끝까지 만들고 유지한 뒤 다음으로 간다 |
| 유지 리듬을 건너뛴다 | 지식이 낡고 검증이 느슨해진다 | 분기와 연간 점검을 일정에 고정한다 |

## 6. 장 요약

- 사례 30개는 맥락의 질, 사람의 검증, 점진적 확대, 정기 점검이라는 네 교훈을 가상 상황으로 보여 준다.
- 시스템 10개는 여러 장의 기법을 한 번 만들어 계속 쓰는 운영으로 묶은 것이다.
- 9번과 7번이 바탕이고, 10번은 가장 나중에 만드는 졸업 시스템이다.
- 유지 없이는 어떤 시스템도 오래가지 못하며, 특히 팀 조율은 분기 검토가 필수다.
