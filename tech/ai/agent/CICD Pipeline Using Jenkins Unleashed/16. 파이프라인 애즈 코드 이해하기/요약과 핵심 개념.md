# 요약과 핵심 개념

이 장은 세 덩어리로 이뤄진다. 비밀번호 대신 쓰는 API 토큰 인증, 파이프라인을 화면 밖의 젠킨스파일에 두는 파이프라인 애즈 코드, 그리고 푸시 같은 저장소 이벤트로 잡을 자동 실행하는 웹훅이다. 이 문서는 세 덩어리를 한 번에 되짚고 핵심 용어를 정리한다.

원서의 요약은 이렇게 이어진다. API 인증과 비밀번호 대비 장점을 배우고, GitHub와 GitLab에서 토큰을 만들어 git 명령에 썼으며, Jenkins에 토큰이 든 자격 증명 항목을 만들었다. 이어 파이프라인을 코드 파일에 쓰고 애플리케이션 소스와 함께 SCM에 올려 실행했으며, 마지막으로 GitHub와 GitLab 웹훅으로 푸시 이벤트에 잡을 트리거했다. 다음 장은 Jenkins 분산 빌드를 다룬다.

---

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | GitHub/GitLab API 토큰 생성 | 비밀번호 대신 쓸 토큰 확보 |
| 2 | 토큰으로 clone, commit, push | 토큰이 윈도우 자격 증명에 저장됨 |
| 3 | Jenkins 자격 증명(Username with Password) | 프리스타일 잡이 토큰으로 저장소 접근, Nexus에 CalculatorAPI-8.0.jar 릴리스 |
| 4 | 선언형 파이프라인을 젠킨스파일로 작성 | Pipeline script from SCM으로 실행 |
| 5 | GitLab 웹훅 | 푸시하면 잡 자동 실행(pom.xml 9.0) |
| 6 | GitHub 웹훅 | 푸시하면 잡 자동 실행(pom.xml 10.0) |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| API 인증 | 비밀번호 대신 API 액세스 토큰을 써서 Git 원격 저장소에 접근하는 방식 |
| API 액세스 토큰 | 권한 범위를 정해 만든 비밀 문자열. 생성 직후 한 번만 볼 수 있다 |
| repo / write_repository | GitHub, GitLab에서 비공개 저장소 전체 제어를 위해 고르는 권한 범위 |
| Username with Password | 토큰을 Jenkins 자격 증명으로 저장할 때 쓰는 종류. Secret Text는 사용자 이름을 못 넣어서 맞지 않는다 |
| 파이프라인 애즈 코드 | 파이프라인을 UI가 아닌 파일로 관리해 소스와 함께 버전 관리하는 방식 |
| 젠킨스파일 | 파이프라인 스크립트가 든 텍스트 파일. 스크립트형(Groovy)이나 선언형(DSL)으로 쓴다 |
| 스크립트형 / 선언형 | node 블록으로 시작하는 전통 방식 / pipeline 블록으로 시작하는 더 단순한 방식 |
| environment 블록 | 모든 스테이지에서 공유하는 변수 정의 |
| STAGE_NAME | 현재 스테이지 이름을 돌려주는 Jenkins 환경 변수 |
| post 블록 | success, failure, always 조건으로 종료 후 실행할 스텝을 담는 블록 |
| archiveArtifacts | 빌드 결과물을 작업 공간 밖의 ${JENKINS_HOME}에 보존하는 스텝 |
| Pipeline script from SCM | 잡이 SCM의 파일에서 파이프라인을 읽도록 하는 Definition 옵션. Script Path로 위치를 지정 |
| 웹훅 | 이벤트 발생 시 지정한 URL로 POST 요청을 보내는 설정 |
| 공인 IP / 포트 포워딩 | 외부에서 보이는 주소 / 공인 IP로 온 요청을 LAN의 Jenkins로 넘기는 설정 |

## 3. 자주 놓치는 점

- 토큰은 페이지를 벗어나면 다시 볼 수 없으므로 만들자마자 파일에 복사해 둔다.
- 윈도우 자격 증명에 이전 값이 저장되어 있으면 새 토큰을 입력하는 창이 뜨지 않는다. 필요하면 저장된 항목을 지운다.
- Jenkins 자격 증명은 Secret Text가 아니라 Username with Password로 만든다.
- 젠킨스파일의 이름과 위치는 Script Path로 지정하므로 이름이 달라도 된다. 책에서는 루트의 Jenkinsfile.txt와 BuildScript/BuildCalculatorAPI.txt를 썼다.
- post 블록의 위치에 따라 적용 범위가 달라진다. 스테이지 뒤면 그 스테이지, stages 블록 뒤면 전체 파이프라인이 기준이다.
- 웹훅은 외부 서비스가 Jenkins에 닿을 수 있어야 하므로 공인 IP와 포트 포워딩이 필요하다.
- GitLab은 Secret Token을 양쪽에 맞춰 넣고, GitHub는 `/github-webhook/` 경로의 Payload URL을 쓴다.
