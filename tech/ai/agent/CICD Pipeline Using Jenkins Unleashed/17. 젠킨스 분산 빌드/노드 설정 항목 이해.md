# 노드 설정 항목 이해

Jenkins에서 새 노드(에이전트)를 등록하면 입력할 항목이 꽤 많다. 값을 채우기 전에 각 항목이 무엇을 뜻하는지 알아 두면 실습에서 헤매지 않는다. 이 문서는 노드 설정 화면의 기본 항목, 실행 방식(Launch method), SSH 호스트 키 검증 전략, 가용성(Availability) 옵션을 표로 정리한다. 이어지는 실습 문서에서 실제 값을 넣는 과정을 다룬다.

노드 설정 화면은 Manage Jenkins(젠킨스 관리) → Manage Nodes and Clouds(노드와 클라우드 관리)에서 New Node(새 노드)를 만들고 노드 이름과 Permanent Agent(고정 에이전트) 라디오 버튼을 선택한 뒤 OK를 눌러 연다.

---

## 1. 기본 설정 항목

| 항목 | 의미 | 원서의 설명과 조언 |
|---|---|---|
| Name | 노드 이름 | 노드마다 고유해야 한다 |
| Description | 설명 | 선택 항목이지만 적어 두면 팀원에게 도움이 된다 |
| # of executors | 이 에이전트에서 동시에 돌릴 수 있는 최대 빌드 수(실행기 개수) | 서버 상태를 보고 정한다. 원서는 테스트용으로 1을 쓴다 |
| Remote root directory | 에이전트 머신에서 Jenkins 전용으로 쓸 디렉터리 | 절대 경로가 좋다. 예: `c:\jenkins\node1`. 에이전트 로컬 경로이면 되고 컨트롤러에서 보일 필요는 없다. 작업 공간(워크스페이스)이 이 안에 만들어진다 |
| Labels | 여러 에이전트를 하나의 논리 그룹으로 묶는 태그 | 여러 개는 공백으로 구분한다. 예: `linux docker`는 linux와 docker 두 라벨을 붙인다 |
| Usage | 이 노드에 빌드를 어떻게 배정할지 | 기본값은 이 노드를 가능한 한 많이 사용하는 모드다 |
| Launch method | Jenkins가 에이전트를 시작하는 방법 | 아래 2절 참고 |
| Availability | 에이전트를 언제 켜고 끌지 | 아래 4절 참고 |

Remote root directory에서 중요한 점은 에이전트가 이 경로 안에 작업 공간을 만든다는 것이다. 라벨은 뒤에서 잡을 특정 노드에 보낼 때 그대로 쓰이므로 의미 있는 이름으로 짓는 편이 좋다. Usage의 기본값은 Use this node as much as possible이며, 이 모드에서는 Jenkins가 노드를 자유롭게 사용한다.

## 2. 실행 방식 (Launch method)

Launch method 드롭다운은 Jenkins가 에이전트를 어떻게 켤지 정한다. 원서가 소개하는 세 가지 선택지 목록은 다음과 같다.

- Launch agent by connecting to the master
- Launch agent via execution of the command on the controller
- Launch agents via SSH

이와 별도로 원서는 Java Web Start, 명령 실행, SSH, Windows 서비스까지 네 가지 방식을 설명한다. 정리하면 다음과 같다.

| 방식 | 동작 | 쓰는 상황 |
|---|---|---|
| Launch agent via Java Web Start | 에이전트 머신에서 JNLP 파일을 열면 컨트롤러로 TCP 연결을 맺는다. 컨트롤러가 에이전트에 닿을 필요가 없고 에이전트가 컨트롤러에 닿기만 하면 된다 | 컨트롤러가 에이전트에 접근할 수 없을 때. 기본은 GUI가 뜨지만 Windows 서비스처럼 GUI 없이 돌릴 수도 있다 |
| Launch the agent via execution of the command on the master | 컨트롤러가 명령을 실행해 에이전트를 시작한다 | 컨트롤러가 SSH나 RSH로 다른 머신에서 프로세스를 원격 실행할 수 있을 때. 원서는 Psexec.exe 같은 도구를 흔한 예로 든다 |
| Launch the slave agents via SSH | 보안 SSH 연결로 명령을 보내 에이전트를 시작한다 | 에이전트에 컨트롤러가 닿을 수 있고, 대상 머신에 로그인할 계정을 줄 수 있을 때. 루트 권한은 필요 없다. 원서 실습이 이 방식이다 |
| Let Jenkins control this Windows slave as a Windows service | Windows에 내장된 원격 관리 기능으로 시작한다 | Windows 에이전트 관리에 적합. 컨트롤러에서 IP로 닿을 수 있어야 한다 |

Java Web Start 방식에서 Configure Global Security 화면을 켜 두었다면, 컨트롤러가 JNLP 연결을 기다리는 포트를 바꿀 수 있다. 이 방식의 구체적 절차는 JNLP 실습 문서에서 다룬다.

### SSH 방식을 고르면 추가되는 항목

Launch agents via SSH를 고르면 입력란 두 개가 더 나타난다.

| 추가 항목 | 의미 |
|---|---|
| Credentials | 에이전트 노드에서 사용자를 인증할 때 쓸 자격 증명(credential) 항목을 고른다 |
| Host Key Verification Strategy | 접속할 때 원격 호스트가 내미는 SSH 키를 Jenkins가 어떻게 검증할지 정한다 |

## 3. 호스트 키 검증 전략 (Host Key Verification Strategy)

호스트 키 검증은 "내가 접속하려는 서버가 진짜 그 서버인가"를 확인하는 절차다. 택배 기사가 집 주소뿐 아니라 받는 사람 얼굴까지 확인하는 것과 비슷하다. 드롭다운에는 네 가지가 있다.

| 전략 | 동작 | 비고 |
|---|---|---|
| Known hosts file verification strategy | Jenkins를 실행하는 사용자의 `~/.ssh/known_hosts` 파일에서 현재 접속과 일치하는 항목이 있는지 확인한다 | 실습에서 선택하는 값 |
| Manually provided key verification strategy | 원격 호스트가 내민 키가 설정한 사용자가 직접 지정한 키와 같은지 확인한다 | |
| Manually trusted key verification strategy | 처음 접속할 때 Computer.CONFIGURE 권한이 있는 사용자가 키를 승인해야 연결이 열린다 | |
| Non verifying verification strategy | SSH 키를 전혀 검증하지 않고 모든 연결을 허용한다 | 공격자에게 길을 열어 줄 수 있어 선택하지 않는 편이 좋다고 원서가 경고한다 |

네 전략은 엄격한 순서로 놓이지 않는다. 다만 마지막 전략만은 보안 위험 때문에 피하는 것이 원서의 권고다.

### Known hosts 검증 오류가 날 때

Known hosts 전략을 쓰다가 아래와 같은 호스트 키 검증 오류를 만날 수 있다.

```text
No entry currently exists in the Known Hosts file for this host.
Connections will be denied until this new host and its
associated key is added to the Known Hosts file.
Key exchange was not finished, connection is closed.
java.io.IOException: There was a problem while connecting to
node2.scmquest.com
```

원서는 이 오류가 Jenkins가 쓰는 SSH 라이브러리가 `ecdsa-sha2-nistp256` 같은 새 암호 방식을 지원하지 않아서 생길 수 있다고 본다. 해법은 known_hosts에서 해당 항목을 지우고, 아래 명령으로 항목을 새로 만드는 것이다. 호스트 이름 자리에는 슬레이브 서버의 호스트 이름을 넣는다.

```bash
ssh -o HostKeyAlgorithms=ssh-rsa node2.scmquest.com
```

이 명령은 SSH 접속 때 호스트 키 알고리즘을 `ssh-rsa`로 제한해, Jenkins가 이해하는 형식의 키가 known_hosts에 기록되게 한다. 원서는 이렇게 하면 문제가 풀린다고 설명한다.

## 4. 가용성 (Availability)

Availability는 Jenkins가 이 에이전트를 언제 시작하고 멈출지 정한다.

| 옵션 | 동작 |
|---|---|
| Keep this slave online as much as possible | 기본값. 에이전트를 가능한 한 계속 온라인으로 유지한다. 사용자 도움 없이 시작할 수 있으면 에이전트가 내려가 있을 때 주기적으로 다시 시작을 시도하고, 스스로 오프라인으로 돌리지는 않는다 |
| Take this slave online when in demand and offline when idle | 실행을 기다리는 잡이 있는 동안에만 주기적으로 켜기를 시도하고, 그렇지 않으면 에이전트를 오프라인으로 돌린다. 이때도 사용자 도움 없이 켤 수 있는 경우에 한한다 |

항상 켜 두면 빌드를 바로 시작할 수 있고, 필요할 때만 켜면 자원을 아낄 수 있다. 처음 실습에서는 기본값을 그대로 둔다.
