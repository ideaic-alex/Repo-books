# 요약과 핵심 개념

17장은 한 대의 Jenkins로 모든 빌드를 처리할 때 생기는 한계를 분산 빌드로 풀어 간다. 분산 빌드가 무엇이고 어떤 이점이 있는지, 컨트롤러와 에이전트를 잇는 방법이 무엇인지, SSH와 JNLP로 각각 연결하는 구체적인 절차, 그리고 잡을 에이전트에서 실행하도록 설정하는 방법을 다뤘다. 이 문서는 장 끝의 Summary를 중심으로 핵심 개념을 한 번에 복습한다. 다음 장에서는 AWS에 EC2 인스턴스를 만들고 Jenkins 파이프라인으로 웹 애플리케이션을 그 위에 배포하는 방법을 다룬다.

---

## 1. 장의 흐름 정리

| 주제 | 핵심 내용 |
|---|---|
| 분산 빌드의 이유 | 단일 머신은 빌드가 느리고, 소프트웨어를 모두 깔아야 하고, 고장 나면 복구가 힘들고, 다양한 환경을 테스트하기 어렵다 |
| 구조 | 컨트롤러(마스터)가 빌드 단계를 에이전트(슬레이브)에 나눠 실행시킨다 |
| 연결 방식 | 컨트롤러가 접속하는 SSH 방식, 에이전트가 접속하는 JNLP 방식 |
| 노드 설정 | 이름, 실행기 수, 원격 루트 디렉터리, 라벨, 사용 방식, 실행 방식, 가용성 |
| 잡 연결 | 프리스타일 잡의 Restrict where this project can be run과 Label Expression으로 실행 노드를 지정 |

## 2. 핵심 개념 용어집

| 용어 | 뜻 |
|---|---|
| 분산 빌드(distributed build) | 빌드 작업을 여러 머신에 나눠 맡기는 Jenkins 기능 |
| 컨트롤러(마스터) | Jenkins가 설치되어 빌드 단계를 에이전트로 보내는 머신 |
| 에이전트(슬레이브) | 컨트롤러가 맡긴 단계를 실행하는 머신. 컨트롤러에 네트워크로 닿을 수 있다 |
| remoting.jar | SSH 방식에서 컨트롤러가 에이전트의 원격 루트 디렉터리에 복사해 실행하는 에이전트 프로그램 |
| JNLP | 에이전트가 먼저 컨트롤러에 접속하는 방식의 프로토콜(Java Network Launch Protocol) |
| agent.jar | JNLP 방식에서 에이전트 머신이 내려받아 실행하는 프로그램 |
| Labels | 여러 에이전트를 하나의 논리 그룹으로 묶는 태그. 공백으로 구분 |
| Label Expression | 잡이 어느 노드(라벨)에서 실행될지 지정하는 칸 |
| Remote root directory | 에이전트에서 Jenkins가 쓰는 전용 디렉터리. 작업 공간이 여기에 생긴다 |
| 실행기(executor) | 노드에서 동시에 돌릴 수 있는 빌드 슬롯. # of executors로 정한다 |

## 3. 실습 시 놓치기 쉬운 점

- SSH 방식의 자격 증명 Username은 에이전트 머신에 있는 사용자여야 한다. 컨트롤러는 이 이름으로 접속한다.
- Remote Root Directory를 다른 드라이브(D:\ 등)로 잡으면 잡 실행 때 오류가 난다. 원서는 접속 시 SystemRoot 기준으로 들어가기 때문이라고 설명한다.
- 잡이 `mvn` 명령을 쓴다면 노드 속성에 `JAVA_HOME` 환경 변수를 JDK 경로로 지정해야 한다.
- Known hosts 전략을 쓸 때는 컨트롤러에서 `ssh 사용자@IP`로 한 번 접속해 `known_hosts`에 항목을 만들어 둔다. 새 암호 방식 때문에 오류가 나면 `HostKeyAlgorithms=ssh-rsa` 옵션으로 접속해 항목을 다시 만든다.
- Non verifying 전략은 보안상 피하라고 원서가 경고한다.
- JNLP 방식의 Jenkins URL에는 localhost를 쓰지 말고 컨트롤러의 IP 주소를 쓴다.
- JNLP의 `-secret` 값은 노드마다 다르므로 노드 화면의 명령을 복사해 쓴다.

## 4. 한 줄 결론

빌드가 느리거나 환경이 다양해지면 에이전트를 늘려 일을 나눈다. 컨트롤러가 에이전트에 닿으면 SSH, 아니면 JNLP로 잇고, 잡에서는 라벨로 실행할 노드를 고른다.
