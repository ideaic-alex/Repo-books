# 프리스타일 잡으로 릴리스하기

이 문서는 젠킨스 프리스타일 잡(체크박스와 입력 칸으로 설정하는 잡)으로 `CalculatorAPI2.0.jar`를 Nexus에 릴리스하는 전체 흐름을 다룬다. 젠킨스에 Maven을 등록하고, 잡을 만들고, 코드에 기능을 더해 GitLab에서 병합한 뒤, 잡을 실행해 결과를 확인하는 순서다.

---

## 1. 전체 흐름

| 단계 | 할 일 | 도구 |
| --- | --- | --- |
| 1 | 젠킨스에 Maven 등록 | Manage Jenkins, Global Tool Configuration |
| 2 | Git 자격 증명 등록 | Credentials Manager |
| 3 | 프리스타일 잡 생성 | New Item |
| 4 | Subtraction 함수와 단위 테스트 추가, 버전을 2.0으로 변경 | Java, pom.xml |
| 5 | 새 브랜치에 커밋하고 GitLab에 푸시 | Git |
| 6 | Merge Request로 Master에 병합 | GitLab |
| 7 | 잡 실행과 Nexus에서 결과 확인 | Jenkins, Nexus |

---

## 2. 1단계: 젠킨스에 Maven 설정하기

1. 젠킨스 서버를 시작하고 로그인해 대시보드로 간다.
2. Manage Jenkins(젠킨스 관리), Global Tool Configuration(전역 도구 설정)으로 간다.
3. Default Settings Provider 영역의 Use Default Maven Settings는 `${use.homer}\.m2`의 기본 `settings.xml`을 뜻한다. Nexus 로그인 정보를 넣어 둔 바로 그 파일이므로 바꿀 것이 없다.
4. 아래로 스크롤해 Add Maven 버튼을 눌러 Maven 영역을 펼친다.
5. Name 칸에 이름을 넣고, Install Automatically 체크를 해제하고, MAVEN_HOME 칸에 Maven 설치 디렉터리 경로를 적는다.
6. Save를 누른다.

뒤에서 잡 설정에 `MyMaven`을 고르므로, 원서에서는 여기서 Maven 이름을 `MyMaven`으로 지은 것으로 보인다. 원서가 이 칸의 값을 직접 적어 두지는 않았다.

---

## 3. 2단계: Git 자격 증명 등록

Credentials Manager에서 Git 사용자 이름과 비밀번호로 자격 증명 항목을 만든다. 자세한 절차는 원서 8장에 있다. 이 장에서는 항목을 만들었다는 것만 언급한다. 저장소가 Private이라서 이 자격 증명이 있어야 젠킨스가 코드를 가져올 수 있다.

---

## 4. 3단계: 프리스타일 잡 만들기

1. 대시보드에서 New Item 링크를 누른다.
2. Enter an Item Name 칸에 잡 이름을 넣고 Free-style Project를 선택한 뒤 OK를 누른다. 원서의 이름은 `ReleaseCalculatorAPI`다.
3. Source Code Management 영역에서 Git 라디오 버튼을 고른다.
4. Repository URL에 Git 저장소의 HTTPS URL을 넣는다. URL을 얻는 방법은 Git 실습 문서의 푸시 단계와 같다.
5. Credentials 드롭다운에서 GitLab 사용자 이름과 비밀번호 항목을 고른다.
6. Branch Specifier 칸에 브랜치 이름을 `Master`로 적는다. 이 예제의 주 브랜치가 Master이기 때문이다.
7. 아래로 내려가 Add Build Step 드롭다운에서 Invoke Top-Level Maven Targets를 고른다.
8. Maven Version 드롭다운에서 `MyMaven`을 고르고, Goals 칸에 `deploy`를 적는다. 원서 본문에는 `Deploy`로 적혀 있으나 Maven 목표 이름은 소문자 `deploy`다.
9. Save를 누른다.

| 설정 항목 | 넣는 값 | 의미 |
| --- | --- | --- |
| Source Code Management | Git | 코드를 Git에서 가져온다 |
| Repository URL | GitLab HTTPS URL | 가져올 저장소 주소 |
| Credentials | GitLab 계정 항목 | Private 저장소 접근 권한 |
| Branch Specifier | Master | 빌드할 브랜치 |
| Build Step | Invoke Top-Level Maven Targets | Maven 실행 스텝 |
| Maven Version | MyMaven | 1단계에서 등록한 Maven |
| Goals | deploy | 빌드 끝에 Nexus로 배포 |

잡은 `mvn deploy`와 같은 일을 한다. 코드를 가져오고, 컴파일하고, 테스트하고, JAR를 만들고, Nexus에 올린다. 직접 명령 프롬프트에서 하던 일을 젠킨스가 대신하게 된 셈이다.

## 5. 4단계: Subtraction 함수와 단위 테스트 추가

새 릴리스를 만들 변경이 필요하다. `Calculator.java`에 뺄셈 함수를 더한다.

```java
public int Subtraction(int num1,Int num2)
{
      int Res=num1-num2;
      return Res;
}
```

원서 코드에는 `Int num2`로 되어 있는데, 자바에서는 소문자 `int num2`여야 컴파일된다. 원문의 오타로 보인다.

`src/test/java` 폴더의 `Pranodayd.CalculatorAPI` 패키지에 `TestSubtractionFunctionality.java`를 만들고 테스트를 몇 개 넣는다. 핵심은 TestNG 애너테이션으로 준비, 테스트, 정리를 나누는 구조다.

```java
public class TestSubtractionFunctionality
{
      Calculator Cal;
      int Result;
      @BeforeClass
      public void Init() { Cal=new Calculator(); }
      @BeforeMethod
      public void ReInitialise() { Result=0; }
      @Test(priority=1,groups= {"RegressionTest"})
      public void TestSubtractionWithPositiveNumbers()
      {
            Result=Cal.Subtraction(50, 10);
            Assert.assertEquals(Result, 40, "...");
      }
}
```

원서는 이외에 `import` 줄들과 두 번째 테스트 `TestSubtractionWith1Positive1NegativeNumbers`(50에서 -10을 빼면 60), `@AfterClass`로 `Cal=null`을 하는 `Teardown`을 더 담고 있다. 위 코드는 핵심만 줄였고 오류 메시지 문자열은 `...`로 줄였다.

| 애너테이션 | 실행 시점 | 이 코드에서 하는 일 |
| --- | --- | --- |
| @BeforeClass | 클래스에서 한 번, 시작 전 | `Calculator` 객체 만들기 |
| @BeforeMethod | 각 테스트 메서드 전 | `Result`를 0으로 되돌리기 |
| @Test | 테스트 메서드 | 뺄셈 결과 검증. `priority`로 순서, `groups`로 그룹 지정 |
| @AfterClass | 클래스의 모든 테스트 후 | 객체 비우기 |

그다음 `pom.xml`의 버전을 1.0에서 2.0으로 바꾼다. 새 기능이 들어갔고 2.0 릴리스를 계획하기 때문이다.

```xml
<groupId>Pranodayd</groupId>
<artifactId>CalculatorAPI</artifactId>
<version>2.0</version>
```

`pom.xml`과 새로 만든 `.java` 파일을 모두 저장한다. 원서는 커밋과 푸시 전에 개발자가 단위 테스트를 돌려 통과하는지 먼저 확인한다고 덧붙인다.

## 6. 5단계: 로컬 커밋과 GitLab 푸시

1. 명령 프롬프트에서 `cd`로 프로젝트 디렉터리에 들어간다.
2. 변경을 추적할 새 브랜치를 만든다.
3. `git add`로 스테이징 영역에 올린다.
4. 새 브랜치에 커밋한다.
5. GitLab 중앙 저장소로 푸시한다.

```
git checkout -b "SubtractionFunction"
git add
git commit -m "Adding subtraction function in Java API project"
git push -u https://gitlab.com/Pranoday/jenkinsbookcalculatorapi.git SubtractionFunction
```

원서의 `git add`는 인자 없이 적혀 있다. 일반적으로는 `git add .`처럼 대상을 지정한다. 이번에는 Git이 자격 증명을 묻지 않을 수 있다. 지난번 푸시 때 입력한 정보가 Windows 자격 증명 관리자(제어판)에 저장될 수 있기 때문이다. 다시 물으면 지난번처럼 입력하면 된다.

## 7. 6단계: Merge Request로 Master에 병합

GitLab 저장소 페이지를 새로 고치면 상단에 SubtractionFunction 브랜치가 푸시되었다는 알림이 보인다.

1. Create Merge Request 버튼을 누른다. New Merge Request 페이지가 열린다.
2. Description 칸에 구현한 변경을 설명한다. 선택 사항이다.
3. Assignee 칸의 Assign to Me 링크로 병합 요청을 자신에게 배정한다.
4. 아래로 내려가 Delete Source Branch When Merge Request Is Accepted 체크를 켜 둔다. 병합이 끝나면 SubtractionFunction 브랜치가 중앙 저장소에서 삭제된다.
5. Create Merge Request를 누르고, 이어서 Merge 버튼을 눌러 Master에 병합한다.

Merge Request는 "내 변경을 Master에 합쳐 달라는 요청서"다. 병합이 끝나면 GitLab의 Calculator 클래스에서 Subtraction 함수가 보인다. 원서 Figure 12-11이 이 화면이다.

## 8. 7단계: 잡 실행과 결과 확인

1. 대시보드의 잡 항목 옆에 있는 시계 모양 아이콘을 누른다.
2. 왼쪽 Build Executor Status 영역에서 진행 상황을 볼 수 있다.
3. 실행이 끝나면 콘솔 출력(console output)을 확인한다.
4. Nexus 저장소에서 `CalculatorAPI2.0.jar`가 올라왔는지 확인한다.

Nexus의 Browse 목록에서 2.0 버전이 보이면 릴리스에 성공한 것이다. 이 흐름에서 눈여겨볼 점은 `pom.xml`의 버전과 아티팩트 이름이 연결된다는 것이다. 버전을 2.0으로 바꾸었기에 올라온 파일이 `CalculatorAPI2.0.jar`가 되었다.
