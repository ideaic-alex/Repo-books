# 요약과 핵심 개념

이 문서는 1장 전체를 짧게 되짚고, 다음 장으로 이어지는 연결 고리를 정리한다. 1장은 전통적인 개발 방식이 애자일처럼 빠른 개발 모델에서 어떤 문제를 일으키는지 설명하고, CI/CD를 도입하면 애자일의 요구와 잘 맞아떨어져 이점을 얻는다는 점을 보여 준다.

---

## 1. 장 전체 요약

1장의 논리는 네 걸음으로 이어진다.

1. 애자일은 짧은 스프린트마다 기능을 쌓는다. 그래서 하루에도 여러 개발자가 메인 브랜치에 변경을 올린다.
2. 변경을 한꺼번에 합치면 회귀 결함, 통합 결함, 병합 충돌이 생기고 해결에 몇 시간이 든다.
3. CI는 변경을 적게 자주 합쳐서 이런 문제를 일찍 찾고 빨리 고친다.
4. CD는 검증된 변경을 운영 환경에 자주 배포해서 환경 차이로 생기는 문제를 일찍 드러낸다.

## 2. 핵심 개념 표

| 용어 | 뜻 |
|---|---|
| 애자일(Agile) | 요구사항을 우선순위 묶음으로 나눠 반복해서 개발하는 방식 |
| 스프린트(sprint) | 한 요구사항 묶음을 검토부터 구현까지 끝내는 기간. 보통 1~3주 |
| 메인 브랜치 | 빌드의 기준이 되는 브랜치. GitLab은 master, GitHub는 main |
| 지속적 통합(CI) | 개발자의 작업을 메인 브랜치에 자주 합치고 검증하는 방식 |
| 지속적 전달/배포(CD) | 검증된 변경을 정기적으로 빌드에 넣고 운영 환경까지 자주 배포하는 방식 |
| TDD | 테스트를 먼저 쓰고, 그 테스트를 통과하도록 코드를 만드는 방식 |
| 회귀 결함 | 새 변경 때문에 기존 기능이 망가지는 결함 |
| 정적 분석 | 코딩 표준 준수와 죽은 코드 존재 등을 코드 실행 없이 검사하는 것 |
| 아티팩트 | 빌드 결과물. 예는 .WAR, .JAR 파일 |
| E2E 테스트 | 배포된 앱에서 처음부터 끝까지의 흐름을 UI 자동화 도구로 확인하는 테스트 |

## 3. 개발 작업 흐름 요약

| 단계 | 핵심 |
|---|---|
| 로컬 단위 테스트 | 모든 단위 테스트가 통과할 때까지 개발한다 |
| 푸시와 병합 | 중앙 저장소의 메인 브랜치에 합친다 |
| 컴파일 | 병합으로 생긴 컴파일 오류를 찾는다 |
| 테스트 | 단위 테스트와 통합 테스트로 회귀를 찾고, 정적 분석을 더하기도 한다 |
| 아티팩트 배포 | 검증된 코드를 패키지로 만들어 서버에 올린다 |

## 4. 다음 장과의 연결

1장의 끝에서 원서는 이렇게 연결한다. CI/CD 과정을 사람이 손으로 하려면 일이 많고 번거롭다. 다음 장에서는 이 과정을 자동으로 돌려 주는 널리 쓰이는 자동화 서버, Jenkins를 소개한다.

참고로 2장 첫머리에서 원서가 덧붙이는 이유는 다음과 같다. CI/CD는 소스 코드 관리 시스템에서 최신 코드를 받고, 컴파일하고, 단위 테스트를 돌리는 식으로 여러 도구를 거친다. 이 작업을 하루에도 여러 번 손으로 하면 개발자, QA, 지원 엔지니어 모두에게 부담이 된다. 이 내용은 2장의 도입부이므로 여기서는 연결만 짚는다.

## 5. 이 장을 마치고 확인할 것

- 애자일에서 변경을 한꺼번에 합치면 어떤 문제가 생기는지 세 가지로 말할 수 있다.
- CI가 문제를 줄이는 이유를 한 문장으로 설명할 수 있다.
- TDD에서 테스트가 먼저 실패해야 하는 이유를 설명할 수 있다.
- 병합 후 컴파일과 테스트를 하는 이유를 설명할 수 있다.
- CD에서 운영 환경에 자주 배포해야 하는 이유를 설명할 수 있다.
