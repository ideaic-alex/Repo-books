# 데이터 포맷과 정리와 균형 조정

원시 데이터가 좋은 데이터셋이 되려면 형식을 통일하고, 오류를 찾아 고치고, 불균형을 바로잡고, 초기 특성 공학까지 해 두어야 한다. 이 문서는 데이터 포맷의 종류, 데이터 정리(cleaning) 절차와 오류 수정 방법, 균형 문제 해결, 데이터셋 준비 단계의 특성 공학을 정리한다.

---

## 1. 데이터 포맷

데이터셋은 만들어지는 동안 여러 포맷을 거친다. 먼저 서로 다른 출처에서 제각각의 포맷으로 받아 모은다. 그다음 직접 접근 바이너리 형식으로 정리·가공하고, 필요하면 학습용으로 순차 바이너리 형식으로 바꾼다.

- **텍스트 형식**: CSV와 JSON이 대표적이다. 텍스트 에디터로 읽고 고칠 수 있어 단순하지만, 용량이 크고 처리 부담도 크다. 메모리에 다 올릴 수 있는 작은 데이터셋에는 괜찮다. 디스크에서 읽어야 할 만큼 큰 데이터는 바이너리로 먼저 바꾸는 편이 낫다.
- **이미지·오디오 파일**: JPEG, WAV처럼 각자 고유한 형식을 쓰며, 파일마다 따로 디스크에 두는 방식이 흔하다. 가장 빠른 방식은 아니지만 특별한 도구 없이 읽고 수정할 수 있어서 충분한 경우가 많다. 보통 매니페스트 파일과 함께 쓴다. 의료 영상처럼 위치·방향 같은 메타데이터를 담는 전용 형식도 있다.
- **직접 접근 바이너리 형식(direct access binary)**: 문자 인코딩 없이 데이터를 본래의 이진 형태로 저장한다(숫자 1337은 텍스트로 저장하면 훨씬 큰 비트열이 된다). 한 파일에 레코드가 많이 들어 있고, 필드가 무슨 뜻인지 알려 주는 메타데이터도 들어 있다. 덕분에 어떤 레코드든 일정한 시간에 접근할 수 있다. `NPY`(NumPy)와 Apache Parquet이 대표적이며, 둘은 성능 면에서 장단점이 다르다.
- **순차 바이너리 형식(sequential binary)**: `TFRecord` 같은 형식이다. 정해진 순서대로 빠르게 읽도록 학습 등에 최적화돼 있고 매우 컴팩트하지만, 원하는 데이터를 찾아보기는 불편하다. 보통 학습 직전 마지막 단계에서 변환하며, 효율을 크게 높일 수 있는 대규모 데이터셋에서만 쓴다.
- **매니페스트 파일(manifest file)**: 데이터셋의 색인 역할을 하는 파일이다. 이미지 데이터셋이라면 학습에 쓸 이미지 파일 이름 목록이며, CSV가 흔하다. 단순해서 관리하기 편하고, 데이터셋에서 표본을 뽑을 때는 매니페스트에서 행을 무작위로 뽑으면 된다.

## 2. 데이터 정리 절차

오류는 수집과 가공 어느 단계에서든 생길 수 있다. 결함 있는 하드웨어가 만든 이상치, 장치마다 다른 형식, 데이터를 합치는 중에 생긴 결측, 특성 공학 코드의 버그로 생긴 잘못된 값이 그 예다.

1. 샘플링으로 데이터를 감사(audit)해서 오류 유형을 파악한다.
2. 오류를 고치거나 피해 가는 코드를 작성한다.
3. 결과를 평가해서 문제가 해결됐음을 증명한다.
4. 2단계의 코드를 자동화해서 전체 데이터셋과 앞으로 추가될 샘플에 같은 수정을 적용한다.

- 데이터가 작지 않다면(대략 1GB 이상이라면) 표본으로 작업하는 편이 피드백 루프를 줄여 준다. 표본에서 검증한 수정을 전체에 적용하되, 마지막에 전체를 다시 평가해서 놓친 문제가 없는지 확인한다.

### 데이터 감사

- 데이터셋(또는 대표 표본)을 요약해서 보여 주는 도구가 가장 강력하다. 필드별 기술 통계와 자료형 표, 값 분포 차트가 대표적이다. 이를 보고 도메인 전문가가 기대한 모습과 맞는지 판단한다.
- 파이썬 `pandas`의 `DataFrame`과 `Matplotlib`이 탐색에 적합하다.

```python
frame.describe()          # count, mean, std, min, 25%, 50%, 75%, max
plt.hist(frame['value'])  # 값의 히스토그램
```

- 책의 예에서는 값이 평균 약 0.5, 표준편차 약 0.13인 정규분포를 이루는데, 몇 개 값이 1.5 부근에 있다. 전문가가 이것이 센서 문제로 생긴 이상치인지 판단하고, 원인을 파고든다.

## 3. 오류 수정 방법

- **값 수정(amending)**: 형식이 맞지 않으면 올바른 형식으로 변환한다. 결측값은 다른 출처에서 찾아 채우고, 특성 공학 코드의 버그로 생긴 값은 고친다. 완전히 고치려면 원시 데이터가 어딘가에 남아 있어야 한다. 너무 낮은 주파수로 수집했다면 원래 신호는 복구할 수 없고 근사만 할 수 있다.
- **값 대체(substituting)**: 고칠 수 없으면 합리적인 값으로 대체한다. 결측값을 해당 필드 전체의 평균으로 채우거나, 이상치를 합리적인 값으로 클리핑하거나, 저주파·저해상도 데이터를 보간(interpolate)한다. 레코드를 살릴 수는 있지만 잡음이 늘어나므로, 득실은 응용에 따라 판단한다.
- **레코드 제외(excluding)**: 결측 때문에 쓸 수 없는 레코드, 고칠 수 없는 센서 데이터, 보안 기준에 못 미치는 출처의 레코드는 버린다. 그냥 삭제하지 말고 문제 있음으로 표시해 따로 보관하면, 어떤 문제가 어느 레코드에서 생기는지 추적할 수 있다.
- 오류의 상류 원인(upstream cause)도 해결해야 한다. 불량 레코드의 비율이 높다면, 피해를 복구하는 데 시간을 쓰기 전에 원인부터 고치는 것이 낫다.
- 어떤 방법이 맞는지는 맥락에 달려 있으며, 도메인 전문성과 데이터 과학 경험이 함께 필요하다.

### 평가와 자동화

- 수정한 뒤에는 다시 감사한다. 수정 때문에 새로 생긴 문제나 가려져 있던 문제를 잡아내기 위해서다(극단적인 이상치를 제거하자 덜 극단적인 이상치가 드러나는 경우가 그렇다). 검증을 마치면 전체에 적용하고, 규모가 크면 데이터 파이프라인에 넣어 자동화한다.
- 수정 코드는 품질 좋게 작성하고 문서화하며, 의존성 기록과 함께 소스 관리에 둔다. 이 코드는 데이터셋이 어떻게 만들어졌는지 보여 주는 기록이고, 앞으로 자동으로 수정할 때 쓰는 수단이기도 하다.
- 원본(수정 전) 데이터셋의 사본을 보관해서 롤백할 수 있게 한다.
- 오류가 어떤 유형의 레코드에 영향을 줬는지 추적한다. 특정 클래스의 레코드가 많이 버려지면 분류 성능에 영향이 있다. 수정한 뒤에도 데이터셋의 품질 기준이 유지되는지 확인한다.
- 초기 평가 결과를 근거로 자동 단언(assertion)을 만든다. 예를 들어 극단적인 이상치를 제거했다면, 분산이 기대한 수준인지 확인하는 자동 테스트를 만들어 새 레코드를 추가할 때마다 돌린다.

## 4. 균형 문제 해결

- 가장 흔한 문제는 하위 그룹별 레코드 수가 고르지 않은 불균형이다.
- **가장 좋은 방법**: 부족한 하위 그룹의 데이터를 더 수집하는 것이다. 항상 가능하지는 않다.
- **오버샘플링(oversampling)**: 부족한 그룹의 레코드를 복제해서 개수를 맞춘다. **언더샘플링(undersampling)**: 많은 그룹의 레코드 일부를 버린다. 모델 학습은 전체 데이터의 손실을 합산한 값을 기준으로 진행되므로, 레코드가 적은 그룹은 영향력이 작다. 이럴 때 개수를 맞춰 주면 도움이 된다.
- 한계: 그 그룹의 실제 변이를 표현할 데이터 자체가 부족하면 오버샘플링은 소용이 없다(한 종의 이미지가 한 개체뿐인 경우). 또 오버샘플링한 데이터로 시스템을 평가하면 그 그룹의 평가 결과를 덜 믿을 수 있으므로 주의한다.
- **가중치(weighting)**: 하위 그룹마다 학습과 평가에 기여하는 정도를 정하는 가중치를 주고, 부족한 그룹에 더 큰 값을 준다. 객체 인식처럼 객체 영역이 배경보다 본래 작아서 리샘플링하기 어려운 경우에도 흔히 쓴다.

### 이상 탐지와 균형

- 이상 탐지에서는 이상 사례가 한 번도 일어나지 않았을 수 있다. 그래서 데이터셋이 정상(nominal) 운영 샘플로만 구성된다. 정상 조건에도 다양한 모드(일이나 계절에 따라 달라지는 작업)가 있으므로, 이를 폭넓게 담아야 한다.
- 실제 이상 예제가 없으면 테스트하기 어렵다. 장비를 일부러 이상하게 가동하거나, 정상 입력을 변형한 합성 데이터로 변화를 시뮬레이션한다. 이때 전문가의 입력이 필요하다.
- 실제 데이터로 검증하지 않은 시스템을 배포하는 것은 권장되지 않는다. 예지 정비처럼 범위를 엄격하게 제한한 경우에만 배포하고, 이해관계자가 효능이 입증되지 않았음을 인지해야 하며, 배포한 뒤에는 집중적으로 감시해야 한다. 가능하다면 알려진 고장 요인별로 문제를 쪼개서 균형 잡힌 데이터를 얻을 방법을 찾는다.

## 5. 특성 공학의 위치

- 대부분의 엣지 AI 프로젝트는 특성 공학을 포함한다. 값 스케일링 같은 단순한 것부터 복잡한 DSP 알고리즘까지 다양하다. 본격적인 작업은 9장의 반복 개발 흐름에서 하지만, 데이터셋을 준비하는 단계에서도 기준선은 마련해 두어야 한다.
- 초기에 특성 공학을 하는 이유는 다음과 같다.
  - 원시 데이터만이 아니라 특성의 관점에서도 데이터셋을 탐색하고 이해하기 위해서다.
  - 모델 입력에 맞게 값을 스케일링하기 위해서다.
  - 센서 융합(sensor fusion) 등을 위해 값을 결합하기 위해서다.
  - 학습 속도를 높이려고 DSP 결과를 미리 계산해 두기 위해서다. 학습 중에는 같은 데이터를 여러 번 보므로, 캐싱해 두면 반복 계산을 피할 수 있다.
- 나중에 반복해서 개선할 것이지만, 일찍 시작할수록 좋다.
