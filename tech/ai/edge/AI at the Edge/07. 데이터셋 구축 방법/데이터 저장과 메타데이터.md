# 데이터 저장과 메타데이터

수집한 데이터는 어딘가에 저장하고, 장치에서 저장소로, 저장소에서 학습·테스트 환경으로 옮겨야 한다. 이 문서는 저장 방식의 선택, 데이터 버전 관리, 데이터를 저장소에 올리는 방법, 그리고 데이터셋의 가치를 크게 높이는 메타데이터 수집을 정리한다.

---

## 1. 저장 방식 선택

- **원칙**: 감당할 수 있는 가장 단순한 방법을 고른다. 한 대의 워크스테이션에 들어갈 양이면 로컬 파일시스템이 가장 편하다. 엣지 AI 데이터셋은 대체로 작아 초대형 규모용 기술이 거의 필요 없다.
- **데이터가 흩어져 있는 현실**: 운영 SQL 데이터베이스, 시계열 데이터베이스, 로그 파일, 데이터 레이크, 데이터 웨어하우스, 클라우드 서비스, IoT 플랫폼 등에 분산돼 있다. 원본 센서 데이터, 정제 데이터, 레이블을 각기 다른 곳에 두어도 괜찮다.
- **변환 파이프라인 필요**: NumPy, pandas, scikit-learn, TensorFlow, PyTorch, MATLAB 같은 도구는 단순하고 효율적인 파일시스템 기반 형식을 기대한다. 대규모 분산 학습에서도 실제 데이터는 디스크에 단순하게 저장된다.

### 저장 솔루션 비교(표 7-2 요지)

| 유형 | 장점 | 단점 |
|---|---|---|
| 로컬 파일시스템 | 빠르고 단순 | API·백업·분산 학습 없음, 수 TB 한계 |
| 네트워크·클라우드 파일시스템 | 여러 머신에서 접근, 대용량 | 느리고 마운트 설정이 복잡 |
| 클라우드 오브젝트 스토리지 | 간단한 API, 대규모 | 사용하려면 내려받아야 함 |
| 피처 스토어(feature store) | 버전 관리·메타데이터·질의 | 내려받아야 하고 복잡·고비용 |
| 엔드투엔드 플랫폼 | 엣지 AI 전용, 탐색 도구 내장 | 단순 저장보다 비쌈 |

- **로컬 파일시스템**: 접근이 매우 빠르며 클라우드를 써도 학습 전에는 로컬로 복사하는 경우가 대부분이다. 다만 백업 없이 한 머신에 두면 위험하고 다인 접근이 불편하다.
- **네트워크 공유·클라우드 파일시스템**: Amazon FSx, Azure Files, Google Cloud Filestore 등. 드라이브로 마운트해야 해서 접근이 다소 복잡하다.
- **클라우드 오브젝트 스토리지**: Amazon S3, Azure Blob Storage, Google Cloud Storage 등은 HTTP API를 제공해 입출력이 쉽다. 하드웨어가 충분하면 임베디드 장치도 업로드에 쓸 수 있다. 속도가 느려 보통 로컬 디스크로 내려받아 쓴다.
- **피처 스토어**: 비교적 새로운 흐름. Amazon SageMaker Feature Store, Azure Databricks Feature Store, Google Cloud Vertex AI Feature Store, 오픈소스 `Feast` 등이 있다.
- **엔드투엔드 플랫폼**: 피처 스토어와 비슷하지만 엣지 AI 전용이며 센서 데이터 탐색 도구와 임베디드 개발 도구 연동을 제공한다.

---

## 2. 데이터 버전 관리

- 소스 코드를 버전 관리하듯 데이터도 버전 관리하는 것이 합리적이다.
- **효과**: 어떤 모델이 어떤 데이터로 학습됐는지 기록하고, 출처를 파악하며, 현장 문제를 개별 샘플까지 추적할 수 있다.
- 데이터셋 버전별 현장 성능을 비교할 수 있어 데이터 중심 ML에 강력한 도구이며, 머신러닝 운영(MLOps) 실무의 일부다.

---

## 3. 데이터를 저장소로 옮기기

- **현장 연결이 좋을 때**: 연결·대역폭·에너지가 충분하면 장치에서 API로 직접 올린다. 엔드투엔드 플랫폼의 장치용 API가 가장 쉽고, IoT 플랫폼에 올린 뒤 다른 시스템으로 복사하는 방법도 좋다.
  - 임베디드 장치에서 클라우드 오브젝트 스토리지로 직접 업로드하는 것은 대체로 권하지 않는다. API가 임베디드용으로 설계되지 않아 자료 구조가 비효율적이고 클라이언트 라이브러리가 작은 타깃에 안 들어갈 수 있다. 임베디드 리눅스 장치는 이 문제가 덜하다.
- **연결이 나쁘거나 없을 때**: 엣지에서 저장했다가 주기적으로 수거해야 한다. 기존 하드웨어에 저장 장치를 추가하거나, 근처에 데이터를 받아 저장하는 별도 시스템을 두고 그 시스템이 더 나은 연결을 갖추거나 물리적으로 수거하게 한다.

---

## 4. 메타데이터 수집

- 수집 시스템을 설계할 때 데이터가 수집된 맥락을 최대한 많이 남긴다. 수집 일시, 수집 장치, 정확한 센서 모델, 현장 내 장치 위치, 수집에 관여한 사람 등이 포함된다.
- 메타데이터는 데이터셋 전체, 일부 레코드, 개별 레코드 단위로 모두 존재할 수 있다. "Datasheets for Datasets"(Gebru 등, 2018)는 데이터셋 전체와 부분집합을 문서화하는 표준을 제시하며 모범 사례지만, 더 구조적이고 세밀하며 기계가 읽을 수 있는 메타데이터 수집이 큰 이점을 준다.

### 개체별 메타데이터

- 특정 기계의 진동, 특정 사람의 키워드 발화, 개별 가축의 생체 신호처럼 개체에 속하는 샘플은 개체 정보를 최대한 담는다.
  - 기계: 정확한 제조사·모델, 생산 배치(production run), 설치 장소, 수행 업무
  - 발화자: 연령·성별·질환 같은 신체적 특성, 억양·인종·국적 같은 문화적 특성, 직업·소득 수준 같은 개인적 특성
- 샘플 단위로 붙여야 메타데이터로 데이터셋을 하위 그룹으로 나눌 수 있다.

### 메타데이터의 쓸모

- **개발 단계**: 데이터셋 구성과 대표성·균형이 부족한 곳을 파악한다. 예: 고장 감지 데이터 대부분이 특정 생산 배치 기계에서 왔다면 다른 배치의 데이터를 더 수집한다.
- **평가 단계**: 하위 그룹별 약점을 파악한다. 예: 키워드 모델이 고령 화자에서 더 잘 동작한다면 젊은 화자 데이터를 더 모은다.
- 샘플 수준의 메타데이터가 없으면 데이터셋의 구성과 모델이 그룹별로 어떻게 동작하는지 보이지 않는다. 메타데이터는 위험을 줄인다.
