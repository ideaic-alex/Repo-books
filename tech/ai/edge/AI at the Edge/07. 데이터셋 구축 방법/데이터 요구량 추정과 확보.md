# 데이터 요구량 추정과 확보

프로젝트 초기에 가장 흔히 나오는 질문은 "데이터가 얼마나 필요한가"다. 하지만 정답은 프로젝트마다 크게 다르다. 이 문서는 필요한 데이터 양을 가늠하는 방법, 데이터를 확보하는 경로별 장단점, 엣지 환경에서만 겪는 수집의 어려움과 대처법을 정리한다.

---

## 1. 데이터 요구량 가늠하기

- **ML과 비ML의 차이**: 신호 처리(DSP)나 휴리스틱처럼 사람이 직접 작성한 알고리즘은 데이터를 주로 테스트에 쓴다. 그래서 대표성만 확보하면 되고, 머신러닝보다 필요한 양이 훨씬 적다.
- **선례 찾기**: 비슷한 문제를 푼 논문, 벤치마크, 오픈소스, 기술 블로그를 찾아본다. 예를 들어 `Papers with Code`의 State-of-the-Art 항목은 과제별 벤치마크 데이터셋과 성능 추이를 보여 준다.
  - 키워드 스포팅 예: Google Speech Commands 데이터셋은 10개 키워드를 분류하며 키워드당 발화가 1.5~4천 개 있고, 정확도 98.37%로 풀려 있다. 과제가 비슷하면 대략적인 기준으로 삼을 수 있다.
- **적은 데이터로 되는 방법 찾기**
  - 딥러닝은 데이터가 많이 필요한 편이므로, 대신 쓸 수 있는 고전 ML 방법이 있는지 먼저 본다.
  - 딥러닝이 꼭 필요하면, 사전 학습된 특성 추출기를 쓰는 전이 학습(transfer learning)을 쓸 수 있는지, 또는 기존 데이터셋으로 직접 학습시킬 수 있는지 본다.
  - 퓨샷(few-shot) 키워드 스포팅 연구는 키워드당 예제 5개와 검증용 대규모 데이터만으로도 모델을 학습할 수 있음을 보였다.

### 과제별 상대적 요구량(표 7-1 요지)

| 과제 | 요구량 | 이유 |
|---|---|---|
| 시계열 분류 | 낮음 | DSP가 어려운 부분을 많이 처리해 준다 |
| 시계열 회귀 | 중간 | 레이블이 더 세밀해 분류보다 어렵다 |
| 비음성 오디오 분류 | 중간 | 배경 소음·음향 환경이 다양하다 |
| 음성 오디오 분류 | 낮음 또는 높음 | 전통적으로 수 시간 필요, 퓨샷 기법이 줄여 준다 |
| 가시광 영상 분류 | 낮음 | 공개 데이터 기반 전이 학습이 가능하다 |
| 가시광 객체 탐지 | 중간 | 전이 학습은 되지만 분류보다 어렵다 |
| 비가시 스펙트럼 비전 | 높음 | 전이 학습이 보통 불가능하다 |

- 이 수치는 매우 대략적인 값이다. 흔한 과제일수록 필요한 데이터를 줄여 주는 기법이 많다. 언어 모델을 처음부터 학습시킬 때 쓰는 거대한 데이터는 엣지 AI에서 보통 필요 없으므로, 데이터 규모에는 상한이 있는 셈이다.

## 2. 데이터 요구량 추정 절차

1. 이상적인 데이터셋의 조건(크기는 제외)을 만족하는 작은 데이터셋을 확보한다.
2. 가장 단순하면서 합리적인 후보 모델을 고른다. 최신 기법에 끌리기 전에 단순한 대안부터 배제한다.
3. 데이터를 같은 크기의 덩어리로 나눈다. 원본의 균형과 분포를 유지하도록 층화 임의 추출(stratified random sampling)을 쓰며, 약 8덩어리로 시작한다.
4. 한 덩어리로 학습하고 성능 지표를 기록한다. 하이퍼파라미터 최적화(AutoML)를 쓰면 하이퍼파라미터 영향을 배제할 수 있어 좋다.
5. 덩어리를 하나씩 추가하며, 매번 처음부터 다시 학습하고 지표를 기록한다.
6. 전체 데이터를 쓸 때까지 반복한 뒤, 지표를 차트로 그린다.

- **곡선 해석**: 곡선이 계속 오른다면 데이터를 더 모을수록 성능이 오른다는 뜻이고, 추세선으로 필요한 양을 대략 추정할 수 있다. 정체(plateau)가 보이면 같은 종류의 데이터를 더 모아도 소용이 없다. 이럴 때는 모델이나 특성 공학을 바꾸거나, 잡음을 줄이는 식으로 데이터를 개선하는 방법을 고려한다.
- **한계**: 이 방법은 데이터셋이 이상적이라는 가정에 의존한다. 대표성, 균형, 신뢰성이 어떤지는 알려 주지 않는다. 그래도 수집 계획을 세우는 데는 쓸모가 있다.

## 3. 데이터 확보 경로

위험(품질 문제)과 노력(비용)은 서로 맞바꾸는 관계다. 이에 따라 아래 여섯 가지 경로가 있으며, 여러 경로를 섞어 쓰기도 한다.

- **이전 성공 프로젝트의 데이터 재사용**: 품질을 이미 알고 있고 노력도 적게 들어서 가장 좋다. 다만 지금 프로젝트와 관련성이 유지돼야 한다.
- **사내 기존 데이터 저장소**: 출처와 수집 방식을 알 수 있어 위험이 낮지만, 정리 작업이 필요하다. 예를 들어 IoT 시스템의 기계 데이터는 레이블이 없는 경우가 많고, 레이블을 추가하려면 비용이 많이 든다.
- **파트너·협력자의 데이터**: 품질을 보증할 수 없고, 정리가 필요할 수 있다.
- **공개 데이터셋**: 여러 사람이 검증했고 벤치마크가 있다는 점이 장점이다. 하지만 저품질 출처를 짜깁기해서 오류가 많거나 너무 작을 수 있고, 문서화되지 않은 편향이 있을 수 있다. 그래도 평가용 코너 케이스를 구하는 좋은 출처가 될 수 있다.
- **외부 업체나 다른 팀에 수집 위탁**: 수집과 레이블링을 전문으로 하는 회사도 있다. 정해진 절차를 지키는지 보장하기 어려워 위험이 있고, 비용도 크다.
- **직접 수집**: 설계자가 수집을 이끌기 때문에 소통 오류의 위험이 가장 낮지만, 비용도 가장 크다.

### 데이터 제약 극복

- 데이터가 부족하면 목표를 조금 단순하게 바꾼다. 예를 들어 특정 고장을 예측할 데이터가 없는 예지 정비 프로젝트라면, 정상 데이터로 학습해서 어떤 종류든 변화를 감지하는 범용 시스템으로 목표를 바꿀 수 있다. 오탐은 늘 수 있지만 필요한 데이터가 줄어들어 실현할 수 있게 된다.

## 4. 엣지에서 데이터를 모을 때의 어려움

일반적인 사용 사례일수록 검증된 공개 데이터가 있다. 하지만 엣지에는 틈새 사례와 특이한 센서가 많고, 기업은 데이터를 잘 공유하지 않는다.

- **연결성과 대역폭(connectivity and bandwidth)**: 원격지에서는 현장 수집이 어렵다. 위성 같은 네트워크 장비를 임시로 설치하거나, 스니커넷(sneakernet, 저장 장치를 사람이 직접 운반하는 방식)을 쓴다.
- **브라운필드 하드웨어(brownfield)**: 이미 설치된 기존 장비는 데이터 수집을 염두에 두고 만들어지지 않았다. 샘플을 저장할 메모리, 업로드할 네트워크, 자주 수집해도 버틸 에너지 예산이 필요하다. 임시로 산업용 데이터 로거(data logger)나 `Arduino Pro` 같은 빠른 IoT 개발 플랫폼을 설치할 수 있다.
- **그린필드 하드웨어(greenfield)**: 새 하드웨어는 완성되기까지 시간이 걸리는데, 데이터셋과 알고리즘 개발은 그와 병행해야 한다. 대표성 있는 데이터를 최대한 빨리 확보해야 하며, 빠른 IoT 개발 플랫폼으로 먼저 수집을 시작할 수 있다.
- **센서 차이(sensor differences)**: 현장에 있는 센서와 새 장치의 센서가 다르거나, 부착 위치가 다를 수 있다. 가능한 한 일찍 두 센서의 데이터를 나란히 비교해서 문제가 되는지 판단한다. 문제가 된다면 브라운필드와 같은 방법으로 대처한다.
- **레이블링(labeling)**: 센서 데이터는 쉽게 모을 수 있어도, 그 데이터를 실제 활동과 연결하기는 어렵다. 소 귀표에 단 가속도계로 먹기·걷기·자기를 분류하는 경우를 보자. 초기 수집 때 타임스탬프가 있는 영상도 함께 찍어 두면 레이블링에 쓸 수 있다.

## 5. 합성 데이터

- **합성 데이터(synthetic data)**: 촬영하거나 측정한 것이 아니라 인공적으로 만든 데이터다. 충분히 현실적이면 데이터 요구를 채우는 데 도움이 된다.
- **유형**: 물리 시뮬레이션 기반(가상 센서 시계열), 절차적 생성(환경 소음 오디오), 생성 이미지(3D 렌더, 딥러닝 모델 출력)가 있다.
- 주로 실제 데이터를 확장하는 용도로 쓴다. 예를 들어 합성한 배경 소음을 실제 오디오에 섞어서, 소음과 음성을 구분하는 분류기를 학습시킨다.
- **Sim2Real**: 시뮬레이션 데이터만으로 학습해 실제 세계의 과제를 푸는 접근이다. 로봇공학에서 중요하면서도 어려운 연구 주제다. 학습은 합성 데이터로 하고, 테스트는 실제 데이터로 한다.
