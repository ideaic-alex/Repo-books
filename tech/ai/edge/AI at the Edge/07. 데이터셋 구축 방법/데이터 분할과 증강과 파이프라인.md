# 데이터 분할과 증강과 파이프라인

반복 개발 흐름에 맞춰 데이터셋을 훈련·검증·테스트로 나누고, 훈련 데이터만 증강하며, 이 모든 처리를 재현 가능한 파이프라인으로 묶어 시간에 따라 키워 가야 한다. 이 문서는 분할 방법과 흔한 함정, 데이터 증강, 데이터 파이프라인과 지속적인 데이터셋 구축을 정리한다.

---

## 1. 훈련·검증·테스트 분할

- **훈련(training) 분할**: 알고리즘 개발, 보통 모델 학습에 직접 쓴다.
- **검증(validation) 분할**: 반복 개발 중 모델을 평가한다. 새 버전을 만들 때마다 검증 데이터로 성능을 확인한다.
- **테스트(testing) 분할**: 프로젝트 마지막까지 따로 두었다가 최종 단계에서, 한 번도 접하지 않은 데이터에서도 잘 동작하는지 확인한다.
- **분리 이유는 과적합(overfitting) 탐지**: 모델이 특정 데이터셋에서만 정답을 맞히고 새 데이터에 일반화하지 못하는 상태다.
  - 훈련 정확도와 검증 정확도가 비슷하면(95%, 94%) 일반화가 잘된 것이다.
  - 검증 정확도가 크게 낮으면(95%, 76%) 과적합 신호이므로 모델을 바꿔야 한다.
- **테스트 분할이 따로 필요한 이유**: 검증 성능을 높이려고 모델을 반복 조정하면 검증 데이터 정보가 모델로 새어(leak) 들어가 검증 데이터에도 과적합될 수 있다. 그러면 검증 신호를 믿을 수 없다. 모든 반복이 끝난 뒤에 쓰는 테스트 분할이 진짜 성능을 알려 준다.
- **테스트 분할은 엄격하게**: 반복적으로 쓰면 테스트 분할에도 과적합된다. 테스트에서 과적합이 드러나면 모델을 미세 조정하지 말고, 다른 모델 유형이나 다른 특성·신호 처리처럼 근본적으로 다른 접근으로 개발을 다시 시작한다. 여러 접근을 시도한 뒤 그들의 테스트 성능을 비교한다. 훈련·검증에서 만족하기 전에는 쓰지 않는다.

### 분할 방식

- 보통 비율에 따라 무작위 추출한다. 일반적으로 먼저 80/20으로 나눠 20%를 테스트로 두고, 남은 80%를 다시 80/20으로 나눠 훈련과 검증으로 쓴다.
- 데이터 변이가 작다면 검증·테스트를 더 작게 하고 훈련에 더 많이 쓸 수 있다. 핵심은 각 분할이 전체의 대표 표본이라는 점이다. 균형과 다양성도 전체와 같아야 한다.
- 하위 그룹이 많거나 일부가 적으면 **층화 추출(stratified sampling)** 이 좋다. 하위 그룹별로 따로 분할한 뒤 합쳐 각 분할이 전체와 같은 균형을 갖게 한다.
- **k겹 교차 검증(k-fold cross-validation)**: k개의 서로 다른 훈련·검증 쌍으로 k번 학습·평가해 결과를 평균한다. 특정 분할의 우연에 덜 휘둘리며 작은 데이터셋에서 특히 유용하지만 k번 학습하므로 시간이 걸린다.

### 분할의 함정

- **분할을 손으로 고르기(curating splits)**: 어려운 레코드를 훈련에 몰아넣으면 테스트로 성능을 알 수 없고, 테스트에 몰면 모델이 학습하지 못한다. 선택은 무작위 알고리즘의 몫이다. scikit-learn에 분할 도구가 있다.
- **균형·대표성 문제**: 클래스뿐 아니라 비공식 하위 그룹(센서 종류 등)도 분할마다 비율이 맞도록 층화 추출을 고려한다.
- **과거를 예측하기(predicting the past)**: 시계열 예측 모델은 이전 값으로 학습하고 이후 값으로 검증·테스트해야 한다. 그렇지 않으면 미래 정보가 과거로 새어 현재 값으로 과거를 예측하는 모델이 된다.
- **중복 값(duplicate values)**: 원본이나 분할 과정에서 중복이 분할 사이에 걸치면 과적합 측정이 망가진다.
- **분할 바꾸기(changing splits)**: 여러 접근을 테스트 성능으로 비교하려면 같은 테스트 분할을 써야 한다. 매번 다르면 차이가 분할 때문인지 알 수 없다.
- **증강된 테스트 데이터(augmented testing data)**: 증강은 훈련 데이터에만 적용한다. 검증·테스트가 순수한 실제 데이터여야 실세계 성능을 가늠할 수 있다.

## 2. 데이터 증강

- **데이터 증강(data augmentation)**: 현실에서 자연스럽게 나타나는 변이를 흉내 낸 무작위 인공 변형을 넣어 제한된 데이터를 최대한 활용하는 기법이다. 이미지의 밝기·대비 조절, 회전, 확대 등이 예이며 오디오에는 배경 소음 혼합, 시계열에는 다양한 변환이 가능하다. 특성 공학 전과 후 모두 적용할 수 있다.
- **증강 유형**
  - 가산(additive): 무작위 잡음이나 실제 환경에서 뽑은 배경 소음 등 다른 신호를 더한다.
  - 감산(subtractive): 값을 제거하거나 가리고, 시간 구간이나 주파수 대역을 지운다.
  - 기하(geometric): 회전, 이동, 압축, 늘이기 등 공간적으로 조작한다.
  - 필터 기반(filter-based): 개별 값의 속성을 무작위량만큼 올리거나 내린다.
- **효과**: 훈련 데이터의 변이가 늘어 모델이 데이터셋 전체를 외우는 대신 일반적인 관계를 학습하게 되어 과적합이 줄고 일반화가 좋아진다.
- **훈련 분할에만 적용**: 증강 방식의 설계는 반복 개발의 일부인데, 검증·테스트까지 증강하면 방식이 바뀔 때마다 평가 데이터도 바뀌어 모델 간 비교가 불가능해진다.
- 대부분의 ML 프레임워크가 증강 기능을 내장하고 있으며 과학 문헌의 증강 프로토콜도 오픈소스로 공개돼 있다.
- **온라인과 오프라인**
  - 온라인(online): 학습 중 레코드를 쓸 때마다 무작위 변형을 적용한다. 변이가 매우 풍부하지만 계산이 무거우면 학습이 크게 느려진다.
  - 오프라인(offline): 각 레코드를 정해진 횟수만큼 변형해 더 큰 증강 데이터셋으로 저장한 뒤 학습한다. 학습은 빠르지만 변형 수가 유한해 변이가 적다.
- 적절한 증강 구성은 도메인 전문성이 필요하다. 예컨대 오디오에 어떤 배경 소음을 섞을지는 응용 맥락을 아는 전문가가 판단한다.

## 3. 데이터 파이프라인

- 이 장의 작업(수집, 저장, 평가, 레이블링, 포맷, 감사, 정리, 샘플링, 특성 공학, 분할, 증강)을 순서와 무관하게 이은 것이 **데이터 파이프라인(data pipeline)** 이다. 현장의 센서와 애플리케이션에서 출발해 내부 시스템으로 들어와 저장·결합·레이블링·품질 점검을 거쳐 학습·평가에 쓸 준비를 마친다. 프로젝트마다 다르고 복잡도도 크게 다르다.
- 파이프라인은 핵심 인프라로 다룬다. 깔끔한 코드로 구현하고 문서화, 버전 관리, 반복 실행에 필요한 의존성 정보를 갖춰야 한다. 변경은 데이터셋에 큰 하류 영향을 줄 수 있어 정확히 알아야 한다.
- 악몽 시나리오: 데이터셋을 만든 과정이 문서화되지 않았거나 더 이상 실행할 수 없어 소실되는 것. 그러면 구축 결정과 엔지니어링을 이해할 수 없어 문제 디버깅이 어렵고, 새 데이터가 생겨도 의미 있는 개선이 어렵다. 복잡한 센서 데이터가 흔한 엣지 AI에서 특히 중요한데 이런 일이 흔하다.
- MLOps(machine learning operations)는 머신러닝 프로젝트의 운영 관리를 다루는 공학 분야다(9장과 10장에서 상세히 다룸). MLOps가 부각되며 데이터 파이프라인도 제대로 취급되기 시작했다. 새 데이터를 추가하고 더 나은 모델을 학습해 시간이 지나며 개선하는 것이 드리프트와 싸우는 핵심 도구다.

---

## 4. 시간에 따른 데이터셋 구축

- 데이터셋은 한 시점의 스냅샷이라 결국 대표성을 잃는다. 드리프트와 싸우려면 항상 새 데이터를 모아야 하고, 꾸준히 들어오는 새 데이터로 최신 모델을 학습·배포할 수 있다.
- 연결이 나쁜 엣지 장치는 현장 성능 측정이 어렵다. 새 데이터를 계속 수집하면 배포된 알고리즘의 성능을 파악하고, 성능이 떨어지면 장치 교체 등을 판단할 수 있다. 새 데이터가 없으면 알 방법이 없다.
- 드리프트와 무관하게도 데이터가 많으면 자연 변이가 늘어 일반화가 좋은 모델이 나온다.
- 데이터 중심 ML 관점에서 데이터 수집은 반복 개발 피드백 루프의 일부다. 모델의 부족한 부분을 보고 필요한 추가 데이터 유형을 정해 루프를 닫는다.
- **개선의 장애물**: 현장에 임시로만 있는 맞춤 수집 하드웨어, 연속이 아닌 배치 방식의 수집, 장기 수집 예산 부재 등. 설계 단계에서 장기 모니터링 예산을 확보하는 식으로 완화를 시도한다.
- 피할 수 없다면 드리프트로 인한 감지 불가능한 성능 저하 위험을 문서화해 최종 사용자에게 알려, 우회 가능 여부를 판단하게 해야 한다. 가장 아는 사람으로서 이를 강조할 책임이 있다.
- 잘 만든 파이프라인이 있으면 새 레코드를 추가하는 마찰이 크게 줄어든다. 믿을 만한 파이프라인이 없으면 새 데이터가 원래 데이터와 일관되게 맞는지 보장할 수 없어 추가가 위험해진다.
- 데이터셋 구축은 프로젝트 시작부터 이어지며 사실상 끝이 없는 지속적 과정이고, 반복 단계마다 변한다.
