# 임베디드 개발과 전자 도구

엣지 AI는 임베디드 소프트웨어 공학의 하위 분야이고, 전기공학·전자공학과도 맞닿아 있다. 임베디드 장치는 내부 상태를 들여다보기 어려워 디버깅이 힘들고, 센서 드라이버나 저수준 통신 프로토콜까지 직접 다뤄야 한다. 이 문서는 그런 어려움 때문에 필요한 하드웨어 도구, 개발 보드, 소프트웨어 도구, 에뮬레이터, 임베디드 Linux, 자동화된 하드웨어 테스트를 정리한다.

---

## 1. 임베디드 하드웨어 도구

- **장치 프로그래머(device programmer)**: 임베디드 장치에 새 프로그램을 올리는 하드웨어다. 대개 장치마다 다른 것을 써야 한다.
- **디버그 프로브(debug probe)**: 임베디드 프로세서에 연결해서 실행 중인 프로그램을 분석할 수 있게 해 준다. 이것도 장치마다 다르다. 중단점 설정, 변수 확인, 단계별 실행처럼 로컬에서 디버깅하는 것과 비슷하게 쓸 수 있다.
- **USB-UART 어댑터**: 개발 워크스테이션과 장치 사이에서 임의의 데이터를 주고받는다. 범용으로 쓸 수 있다.
- **멀티미터(multimeter)**: 전압, 전류, 저항을 측정해서 회로 상태를 파악한다.
- **오실로스코프(oscilloscope)**: 장치나 PCB의 신호를 시간에 따른 전압으로 보여 준다.
- **활용 예**: 프로그램이 특정 지점에 도달하면 프로세서의 특정 핀을 토글하게 만들고, 멀티미터로 핀 값이 바뀌었는지 확인해서 동작을 검증한다. 직렬(UART) 케이블은 속도가 비교적 낮지만, 센서 데이터를 적당한 시간 안에 옮기기에는 충분해서 흔히 쓴다.

---

## 2. 개발 보드와 시작하기

- **개발 보드(dev board)**: 임베디드 프로세서만으로는 아무것도 할 수 없다. 개발 보드는 프로세서와 입출력, 때로는 센서까지 갖춰서 바로 쓸 수 있게 만든 플랫폼이다.
- **목적**: 특정 칩이 프로젝트에 적합한지 평가하고, 하드웨어 개발이 끝나기를 기다리지 않고 소프트웨어 개발을 진행하기 위해 쓴다. 자체 하드웨어가 준비되면 거기로 옮긴다. 다만 소량 생산용으로 설계된 Arduino Pro 같은 신속 프로토타이핑 플랫폼은 예외다.
- **여러 보드 비교**: 하드웨어를 정할 때는 보드 몇 가지를 구해서 초기 딥러닝 모델을 각각 돌려 보고, 상대적인 성능을 확인하는 것이 좋다.
- **플랫폼 연동**: 일부 엔드투엔드 플랫폼은 보드와 깊이 연동되어 있어서, 코드를 한 줄도 쓰지 않고 센서 데이터를 수집하거나 모델을 배포하고 평가할 수 있다.
- **입문용**: 임베디드 경험이 적다면 `Arduino`와 `Arduino Pro` 제품이 좋은 출발점이다. 초보자에게 쉽지만 실제 애플리케이션을 만들 만큼 강력하다. ML 엔지니어나 두 분야 모두 처음인 사람에게 알맞다.

## 3. 임베디드 소프트웨어 도구

- **언어**: 엣지 AI에서 임베디드 소프트웨어 개발은 대체로 C++ 개발을 뜻한다.
- **IDE, SDK**: 프로세서 업체가 자기 하드웨어에 잘 맞는 통합 개발 환경(IDE)을 제공한다. 업체의 SDK, 드라이버, 라이브러리는 품질이 고르지 않고, 개념 증명 수준인 경우가 많다.
- **RTOS**: 반복되는 보일러플레이트 코드를 줄이려고 쓴다. 간단한 OS 기능을 라이브러리 형태로 제공해서 내 프로그램과 함께 컴파일하고, API로 주변장치를 제어하거나 네트워크 통신을 한다.
- **툴체인(toolchain)**: 업체가 제공하는 프로그램과 스크립트 모음이다. 소스 코드를 프로그램으로 만들고 장치에 플래시(flash)한다.

### 일반적인 개발 흐름

1. 소스 코드를 수정한다.
2. 업체가 제공한 컴파일러와 링커로 바이너리를 만든다.
3. 스크립트로 장치에 코드를 플래시한다.
4. 직렬 연결로 장치와 통신하면서 테스트한다.

- **로컬 테스트**: 범용 C++ 코드는 개발 머신에서 단위 테스트로 돌릴 수 있다. 하지만 프로세서 고유의 하드웨어 API를 쓰는 코드는 그렇게 할 수 없다. 이런 코드는 장치에서만 테스트하거나 에뮬레이터를 써야 한다.

---

## 4. 에뮬레이터와 시뮬레이터

- **에뮬레이터(emulator)**: 프로세서를 개발 머신에서 가상으로 재현해서, 장치에 플래시하지 않고 임베디드 코드를 실행한다. 실제 하드웨어와 속도가 같지는 않지만 충분히 유용하다.
- **사이클 정확 시뮬레이터(cycle-accurate simulator)**: 실제 하드웨어에서 실행될 때 걸리는 클록 사이클 수를 정확히 알려 준다. 이 수를 클록 속도로 나누면 지연 시간을 정밀하게 추정할 수 있다. AI 알고리즘의 지연 시간을 추정할 때 유용하다.
- **시뮬레이션(simulation)**: 에뮬레이트한 프로세서에 센서와 통신 하드웨어까지 포함해서, 장치 전체를 소프트웨어로 흉내 낸다. 멀티프로세서 보드나 장치 네트워크를 표현하는 시뮬레이션도 있다.
- **도구**: 모든 프로세서에 에뮬레이터가 있는 것은 아니다. `Renode`는 여러 프로세서 구조를 위한 에뮬레이션·시뮬레이션 환경이다. `Arm Virtual Hardware`는 클라우드에서 Arm 프로세서를 에뮬레이트한다.

---

## 5. 임베디드 Linux와 SoC 개발

- **마이크로컨트롤러와의 차이**: SoC와 엣지 서버는 전체 OS를 돌릴 만큼 연산력과 메모리가 있어서 PC나 웹 서버 개발과 비슷하다. 전문 기술이 덜 필요하다는 것이 큰 장점이다.
- **언어와 라이브러리**: 거의 모든 언어로 개발할 수 있다. 저수준 언어는 빠르고 고수준 언어는 유연하다는 트레이드오프는 여기서도 같다. Google은 일부 인기 플랫폼용으로 미리 빌드한 `TensorFlow Lite runtime`을 제공한다. SciPy의 신호 처리 함수 같은 Python 라이브러리도 그대로 쓸 수 있다.
- **컨테이너 배포**: 임베디드 애플리케이션을 Linux 컨테이너로 패키징하면 설치하고 쓰기가 쉬워진다.
- **기성 보드 활용**: 용도에 맞는 SoC 플랫폼(예를 들어 산업용으로 튼튼한 케이스에 든 제품)을 사서 센서를 연결하고 애플리케이션을 설치하는 방식이 흔하다.
- **어려움**: 미리 빌드된 패키지가 없어서 소스에서 라이브러리를 직접 빌드해야 할 때가 있다.
- **보안**: 임베디드 Linux는 네트워크에 있는 다른 기계처럼 단단히 잠가 두어야 한다. 보안이 취약한 IoT 장치는 해킹당해 다른 시스템을 공격하는 데 쓰이는 것으로 악명이 높다.

## 6. 자동화된 하드웨어 테스트

- **문제**: 지속적 통합(CI) 테스트는 모범 사례지만, 하드웨어와 상호작용하는 코드는 대상 장치에서만 테스트할 수 있다. 장치가 멈추면 물리적으로 만지지 않고는 재시작하거나 새 펌웨어를 올리기 어려운 상태에 빠지기 쉽다.
- **자동화 시스템**: 새 코드를 플래시하고, 테스트 사이에 전원을 껐다 켜고(power cycle), I/O 포트와 센서 입력을 넣어 주는 일을 할 수 있는 소프트웨어와 하드웨어의 조합이다.
- **구조**: 대개 직접 만들어 쓴다. 팀의 CI 도구, 그리고 코드를 돌릴 장치들에 모두 연결된 호스트 시스템이 중심이 된다.
- **예**: 키워드를 감지하는 마이크를 테스트하려면, 호스트에 스피커를 붙여서 필요할 때 키워드를 재생하게 할 수 있다.
