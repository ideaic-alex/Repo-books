# MLOps와 모델 최적화 도구

모델을 작게 만드는 도구, 실험을 체계적으로 관리하는 도구, 그리고 이 모든 것을 묶는 MLOps 개념을 다룬다. 알고리즘 개발은 수백, 수천 번의 시도를 거친다. 그래서 이 시도들을 과학적으로 추적하고 자동화하는 체계가 꼭 필요하다.

---

## 1. 모델 압축과 최적화 도구

- **필요성**: 엣지 장치에는 작고 효율적인 모델이 필요하다. 특히 딥러닝은 파라미터 수와 연산량이 빠르게 늘어난다.
- **제공처**: 딥러닝 프레임워크가 제공하거나, 특정 최적화를 지원하는 하드웨어 업체가 제공한다.
- **TensorFlow Lite converter**: 연산자 융합(operator fusion)과 기본 양자화(quantization)에서 사실상 표준이다. TensorFlow Lite 모델 파일 형식도 업계 표준에 가깝다. ONNX 같은 다른 형식도 있지만 TFLite 형식이 압도적으로 많이 쓰인다.
- **TensorFlow Model Optimization Toolkit**: 그 밖의 최적화·압축 기법을 모아 놓은 오픈소스 도구다.
- **추론할 때도 도구 지원이 필요하다**: 대부분의 최적화는 추론 단계에서 특별한 도구가 있어야 효과를 낸다. 지금 가장 잘 지원되는 것은 양자화이고, 8비트 양자화 연산자 구현은 널리 퍼져 있다.
- **희소성(sparsity)의 함정**: 말은 그럴듯하게 들리지만, 이를 지원하는 하드웨어가 매우 드물다.

---

## 2. 실험 추적(experiment tracking)

- **필요성**: 무작정 바꿔 보지 말고 아이디어를 체계적으로 시험해야 한다. 실험 하나에는 데이터 샘플 선택, DSP 알고리즘, 모델, 하이퍼파라미터(hyperparameter) 등 많은 변수가 얽혀 있다.
- **역할**: 어떤 실험을 어떤 변수 설정으로 돌렸고 결과가 어땠는지 기록한다. 노트에 적어 두고 잊지 않기를 바라던 비공식적인 방식을 대신한다. 학습 스크립트, 데이터셋, 학습된 모델 같은 산출물(artifact)도 저장해서 실험을 재현할 수 있게 한다.
- **TensorBoard**: TensorFlow 생태계의 공식 구성 요소이고 가장 단순한 선택지다. 학습 로그를 웹 화면에서 시각화하고 비교할 수 있어서, 학습 코드를 최적화하고 디버깅할 때 강력하다. 다만 프로젝트 전 기간의 영구 저장소로는 맞지 않고, 실험 횟수가 매우 많을 때도 잘 맞지 않는다. TensorFlow와 PyTorch를 모두 지원한다.
- **MLflow**: 데이터베이스를 갖춘 복잡한 웹 애플리케이션이다. 실험 추적, 모델 저장, 재현 가능한 패키징을 지원한다. 장기간 쓰기에 적합하고 수천 건의 실험까지 확장할 수 있지만, TensorBoard 같은 최적화·디버깅 기능은 없다.
- **Weights & Biases**: 단순한 API와 잘 만든 웹 화면을 갖춘 대표적인 상용 도구다. 월 비용만 내면 설치, 유지보수, 보안을 서비스 업체가 맡아 준다는 장점이 있다.

---

## 3. 자동화된 머신러닝(AutoML)

- **개념**: 실험 추적이 되고 있다면 실험 실행도 소프트웨어로 자동화할 수 있다. 데이터셋과 제약 조건을 주면, 여러 변수 조합을 시험하는 실험을 알아서 설계해 가장 좋은 모델과 알고리즘을 찾는다.
- **하이퍼파라미터 최적화(hyperparameter optimization)**: 가능한 모든 조합을 차례로 시도하는 그리드 탐색(grid search)부터, `Hyperband`처럼 효율을 높이려고 탐색을 지능적으로 제어하는 알고리즘까지 다양하다.
- **만능은 아니다**: 문제를 구조화하고 탐색 공간을 올바르게 정하려면 여전히 도메인 전문성이 필요하다. AutoML이 대신해 주는 일은 시행착오를 반복하는 지루한 작업이다.
- **MLOps로의 확장**: 어떤 시스템은 시험할 실험 목록만 내놓고, 어떤 시스템은 분산 컴퓨팅으로 실험 실행까지 조율한다. 가장 복잡한 형태는 신경망 구조 탐색(neural architecture search, NAS)이다.
- **구체적인 도구**: `Ray Tune`은 분산 인프라에서 하이퍼파라미터 튜닝을 조율하는 오픈소스다. Weights & Biases의 Sweeps는 자체 하드웨어에서 실험을 조율하는 상용 호스팅 제품이다.
- **엣지 AI에서 특히 유용하다**: 엣지용 모델은 작고 학습이 빨라서 많은 옵션을 시도하기 쉽다. 또 엣지 AI에서는 정확도뿐 아니라 가장 작고 빠르고 전력을 적게 쓰는 모델도 찾아야 한다. 일반 AutoML 도구는 이런 조건을 고려하지 못하지만, 일부 엔드투엔드 엣지 AI 플랫폼은 고려한다.

---

## 4. MLOps

- **정의**: 머신러닝 워크플로의 많은 부분을 추적하고 관리하는 기술이자 기법이다. 데이터 저장, 실험 추적, AutoML 등을 모두 포괄한다. ML 프로젝트를 하고 있다면 의식하지 못해도 이미 MLOps를 하고 있는 셈이다.
- **ML 파이프라인(ML pipeline)**: 데이터를 받아 변환하고(신호 처리 같은 특징 공학 포함), 모델을 학습시켜 결과를 평가하는 과정을 스크립트로 만든 것이다. 데이터 파이프라인을 확장한 개념이다. 실험을 반복하거나 새 데이터가 들어올 때 자동으로 다시 학습하고 결과를 비교하기에 편리하다.
- **구현 규모**: 가장 단순한 형태는 Python이나 Bash 스크립트를 한 대의 기계에서 돌리는 것이다. 복잡한 형태는 분산 인프라에서 각 단계를 병렬로 실행한다. 단계마다 별도 컨테이너를 두고 차례로 호출하는 방식이 흔하다.
- **조립 방식**: 데이터셋 관리, 실험 추적, 모델 저장을 각각 다른 도구로 조립할 수도 있고, 전 단계를 아우르는 종합 프레임워크를 쓸 수도 있고, 둘을 섞어 쓸 수도 있다.

### ml-ops.org가 꼽는 MLOps 업무

1. 데이터 엔지니어링
2. 데이터·ML 모델·코드의 버전 관리
3. 지속적 통합·지속적 전달(CI/CD) 파이프라인
4. 배포와 실험 자동화
5. 모델 성능 평가
6. 운영 환경에서의 모델 모니터링

### 엣지 AI에서 추가되는 업무

- 장치와 센서에서 데이터 수집
- 신호 처리(DSP)와 규칙 기반 알고리즘
- 온디바이스 성능 추정
- 모델 압축과 최적화
- 엣지 장치에서 쓸 수 있게 하는 변환과 컴파일
- 현장에 배포된 모델의 버전 추적

- **이유**: 대부분의 MLOps 시스템은 모델을 웹 서비스로 서빙(serving)한다고 가정하고 만들어졌기 때문이다. 그래서 위의 업무는 엣지 AI에서 따로 챙겨야 한다.
- **MLOps 스택(stack)**: 개발, 배포, 유지보수를 돕는 소프트웨어 도구들을 묶은 것이다. Valohai가 만든 스택 템플릿 개념을 엣지 ML에 맞게 응용할 수 있고, 스택의 각 칸마다 해법이 필요하다. 스택을 조금씩 조립해 나갈 수도 있고, 엣지 AI 전용 종합 MLOps 플랫폼을 쓸 수도 있다.
- **더 읽을 자료**: ml-ops.org 사이트, 『Introducing MLOps』, Google Cloud의 MLOps 소개 글이 있다. 다만 대부분 서버에서 돌리는 모델을 염두에 둔 내용이다.
