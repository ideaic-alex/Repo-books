# 팀 역할과 채용 그리고 학습

엣지 AI 개발에는 지식, 기획, 알고리즘, 제품 엔지니어링, 기술 지원에 걸친 여러 역할이 관여한다. 한 사람이 여러 역할을 겸할 수 있으므로 역할마다 사람을 따로 뽑을 필요는 없다. 이 문서는 역할 지도, 신생 분야의 채용 현실, 학습 자료를 활용하는 태도를 정리한다.

---

## 1. 지식과 이해 역할

- **도메인 전문가(domain expert)**: 프로젝트 영역의 과학적 원리를 아는 사람. 제품 관리자가 시장 등 주변 맥락을 이해한다면, 도메인 전문가는 상황 자체의 과학을 안다. 산업 자동화라면 해당 공정, 의료라면 의학·생물학 전문가다.
- **윤리·공정성 전문가(ethics and fairness expert)**: 해롭거나 비효과적인 제품을 낳는 실수를 피하는 역할. 사용 기술과 함정, 따라야 할 절차를 알아야 하고, 윤리 문제가 도메인마다 다르므로 도메인 지식도 필요하다.

---

## 2. 기획과 실행 역할

- **제품 관리자(product manager)**: 제품이 무엇이어야 하고 무엇을 하며 누구를 위한 것인지 결정한다. 문제와 시장을 깊이 이해하고 기술 역할과 협력하며, 권한보다 영향력으로 이끈다.
- **프로젝트 관리자(project manager)**: 복잡한 작업을 여러 사람에 걸쳐 조율한다. 예를 들어 제품 개발에 쓸 데이터셋 수집을 조직한다.
- **프로그램 관리자(program manager)**: 여러 프로젝트로 이뤄진 상위 전략을 조율한다. 회사가 여러 사업 부문에 엣지 AI를 도입할 때 필요하다.

---

## 3. 알고리즘 개발 역할

- **데이터 과학자(data scientist)**: 엣지 AI 프로젝트의 기반 데이터를 수집·유지·이해한다. 데이터 정제, 분석, 특징 공학(feature engineering) 기술을 갖고, 머신러닝까지 겸하는 경우가 많다.
- **DSP 엔지니어(DSP engineer)**: 신호 처리(DSP) 알고리즘을 개발·구현한다. 알고리즘 개발과 저수준 프로그래밍 양쪽에 강하다. 이미지 데이터에 딥러닝을 쓰는 경우를 제외하면 대부분의 프로젝트에서 매우 중요하다.
- **ML 실무자(ML practitioner)**: 문제를 여러 학습 알고리즘의 관점으로 구조화하고 데이터셋으로 알고리즘을 개발한다. 연구실과 현장 양쪽에서 성능을 어떻게 평가할지 정하는 것이 핵심이다.
- **DSP와 ML의 협업**: DSP는 정교한 형태의 특징 공학이므로 두 역할은 매우 긴밀히 일한다.

---

## 4. 제품 엔지니어링 역할

- **하드웨어 엔지니어(hardware engineer)**: 센서와 프로세서, 회로 기판(PCB) 설계를 맡는다. 알고리즘 설계는 하드웨어 제약을, 하드웨어 설계는 알고리즘 설계를 서로 반영해야 하는 양방향 관계다.
- **임베디드 소프트웨어 엔지니어(embedded software engineer)**: 센서와 연동하고 알고리즘을 실행하며 출력을 해석해 결정을 내리는 저수준 코드와 임베디드 애플리케이션을 구현한다.
- **임베디드 ML 엔지니어(embedded ML engineer)**: ML 알고리즘이 특정 하드웨어에서 최대한 효율적으로 돌게 하는 역할. 머신러닝 수학과 저수준 최적화에 능하고, 아직 새롭지만 분야와 함께 성장 중이다.
- **산업 디자이너(industrial designer)**: 제품의 물리적 형태를 만든다. 센서 위치를 옮기면 출력이 달라져 데이터셋이 쓸모없어질 수 있으므로 전자·알고리즘 팀과 긴밀히 소통해야 한다.
- **소프트웨어 엔지니어(software engineer)**: 서버 측 등 임베디드 외 소프트웨어를 개발한다. 임베디드와 다른 기술이 필요하다.

---

## 5. 기술 지원 역할

- **MLOps 엔지니어(MLOps engineer)**: 팀이 쓰는 MLOps 솔루션을 구축·유지한다. 본질은 DevOps이지만 엣지 AI 워크플로의 요구를 이해해야 한다.
- **보안 실무자(security practitioner)**: 팀과 데이터와 제품의 보안을 챙긴다. 자문 역할과 위험을 줄이는 선제 조치 역할을 겸한다.
- **품질 보증 엔지니어(quality assurance engineer)**: 테스트 계획을 설계·실행해 제품이 설계 목표를 충족하는지 확인한다.

---

## 6. 엣지 AI 채용의 현실

- **경력자 부족**: 신생 분야라 엣지 AI 경력 엔지니어는 전 세계에 수백 명 수준이며 대부분 첫 프로젝트에 매진 중이다.
- **진입 장벽 하락**: 최고 경력자도 몇 년 앞서 있을 뿐이고, 엔드투엔드 플랫폼 등 도구 발전으로 진입 장벽이 크게 낮아졌다. 핵심은 알고리즘 개발과 임베디드 엔지니어링 두 축이다.
- **응용형 vs 학술형 ML 인력**: 응용 경험자는 문제 정의(problem framing) 경험이 풍부해 첫 채용이나 단독 채용으로 유리하다. 학술 연구자도 적합할 수 있으나 일반 개발 환경에 익숙하지 않아 적응이 오래 걸리고, 대신 수가 많아 채용이 쉽다. 연구자는 기존 기법의 반복 적용에 지루해할 수 있으므로 역할 기대치를 분명히 알려야 한다.
- **센서 데이터 경험 부족**: 비전은 흔하지만 오디오는 드물고, 전자 센서가 내는 고주파 시계열 데이터는 대부분의 ML 인력에게 낯설다.
- **DSP 엔지니어 활용**: DSP 엔지니어는 ML 실무자와 비슷한 워크플로와 도구를 쓰고 센서 데이터 특징 공학에 능숙하다. 이들에게 머신러닝 기초를 가르치는 것이 한 방법이며, DSP와 ML 인력이 함께 있는 팀이 훨씬 수월하다.
- **임베디드 엔지니어**: 인터프리터나 컴파일러 생성 코드는 보통 라이브러리 통합 수준이지만, 문제가 생기면 내부를 파고들어야 하므로 딥러닝 이해가 도움이 된다. 모델을 장치용 형태로 변환하는 번거로운 작업도 맡기 쉽다. 고전 ML 모델을 C++로 구현하는 일도 흔하며, 임베디드용 좋은 C++ 라이브러리는 아직 없지만 고수준 언어 참조 구현이 있어 이식은 대체로 쉽다.
- **전망**: ML 지식을 가진 임베디드 엔지니어를 구하기는 한동안 어렵겠지만, 유능한 임베디드 엔지니어라면 현재 도구를 어렵지 않게 익힐 수 있어 걸림돌은 아니다.

---

## 7. 학습 자료와 학습 태도

- **행동 지향**: 세부에 빠져 학습만 하다 시작을 못 하는 함정을 경계한다. 다음 단계에 필요한 만큼만 배우고 다시 평가하며, 하드웨어 제품은 팀이 필요하므로 최소한만 알고 전문가를 합류시킨다.
- **실습 자료**: Coursera의 임베디드 머신러닝 입문과 컴퓨터 비전 과정, HarvardX의 Applied TinyML for Scale, 『TinyML Cookbook』, 『TinyML』, 『Designing Machine Learning Systems』, 『Making Embedded Systems』.
- **이론 자료**: HarvardX의 Tiny Machine Learning 과정, Steven Smith의 DSP 안내서(무료 공개), Géron의 『Hands-On Machine Learning』, Chollet의 『Deep Learning with Python』, TinyML Foundation 유튜브 채널, TinyML 논문·프로젝트 GitHub 저장소.
- **이론의 위상**: 이론 자료는 제품 개발의 선행 조건이 아니다. 압도되거나 깊은 구멍에 빠지지 말 것.
