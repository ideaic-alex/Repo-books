# TransMode 운송수단 선택 시스템과 텍스트 상담

저자는 더 복잡한 지식 베이스를 보이기 위해 운송수단 선택 전문가 시스템 TransMode를 만들었다. 전체 규칙은 장 끝의 부록에 실려 있다. 이 문서는 시스템이 하는 일과 입력 변수, 그리고 설명력이 거의 없는 전통적 텍스트 문답 상담의 실제 모습과 그 규칙 추적을 정리한다. 이어서 이 상담이 왜 투명성과 유연성 양쪽에서 부족한지를 저자의 평가대로 짚는다.

---

## 1. 시스템의 목적과 입력 변수

운송 중개인(broker)은 고객의 화물을 항공, 트럭, 철도, 소포 서비스 중 어떤 수단으로 옮길지 결정한다. TransMode는 이 판단을 다음 열 가지 요인으로 내린다.

| 변수 | 질문 내용 |
|---|---|
| 화물 중량 | 전체 화물 무게(lb) |
| 품목 1개 무게 | 품목 하나의 무게(oz) |
| 품목 1개 가치 | 품목 하나의 달러 가치 |
| 파손 가능성 | 품목이 얼마나 깨지기 쉬운가(높음, 보통, 낮음) |
| 운송 거리 | 마일 단위 거리 |
| 운송 시간 | 며칠 안에 도착해야 하는가 |
| 특수 품목 | 위험 광물, 위험 화학물질, 농산물, 없음 |
| 부패성 | 부패하기 쉬운가(예, 아니오) |
| 문전 서비스 | 문 앞까지 배달이 필요한가(예, 아니오) |
| 서비스 빈도 | 운송이 얼마나 자주 이루어지나(매일, 매주, 매월, 드물게) |

이 정보는 고객에게서 얻어 TransMode에 입력하고, 시스템은 이 입력을 바탕으로 권고를 낸다.

---

## 2. 전통적 텍스트 문답 상담

전통적 대화 방식에서는 시스템이 사용자에게 일련의 질문을 던진다. 예시 상담에서 사용자는 한 고객의 화물 정보를 다음과 같이 입력한다.

| 질문 | 입력값 |
|---|---|
| 화물 전체 무게 | 10,000 lb |
| 운송 거리 | 2,500마일 |
| 도착 기한 | 14일 |
| 품목 1개 가치 | 500달러 |
| 품목 1개 무게 | 10.0 oz |
| 파손 가능성 | 높음 |

질문은 시스템이 정한 순서로 하나씩 나오며, 입력이 끝나면 시스템은 최종 결정으로 권고 운송수단이 트럭(TRUCKING)이라고 내놓는다.

---

## 3. 규칙 추적의 내용

사용자가 권고가 어떻게 나왔는지 규칙 추적을 요청하면 다음 순서로 규칙이 발화되었음을 알게 된다. 각 규칙의 의미를 풀어 쓰면 다음과 같다.

1. `R3`: 화물 중량이 5,000lb 초과 15,000lb 이하이므로 `Load-Type`을 `large-shipment`로 정한다.
2. `R37`: `Load-Type`이 `large-shipment`이면 대안을 `rail-or-trucking`으로 좁히고 선호를 트럭으로 둔다.
3. `R12`: 운송 시간이 10일을 넘으므로 `Speed-Rating`을 `slow`로 둔다.
4. `R8`: 거리가 1,000마일을 넘으므로 `Distance-Range`를 `long`으로 둔다.
5. `R14`: 거리 범위가 `long`이고 속도 등급이 보통 또는 느림이면 `Haul-Type`을 `long-slow`로 둔다.
6. `R24`: 품목 1개 무게와 가치가 모두 입력되었으면 `Value-Weight-Ratio`를 가치 나누기 무게로 계산한다. 여기서는 500/10 = 50.0이다.
7. `R26`: 가치 대 무게 비율이 20달러 이상 100달러 미만이면 `Valuable-Rating`을 `high`로 둔다.
8. `R30`: `Valuable-Rating`과 `Fragility-Rating`이 모두 `high`이면 `Loss-and-Damage-Rating`을 `important`로 둔다.
9. `R51`: 대안이 `rail-or-trucking`이고 손실 및 파손 등급이 important 또는 somewhat important이면 권고를 `TRUCKING`으로 정한다.

따라서 모두 아홉 개 규칙이 발화되어 트럭 권고에 이르렀다.

### 3.1 아홉 규칙의 구조 읽기

나열된 순서만 보면 아홉 규칙이 한 줄로 이어진 것처럼 보이지만, 실제로는 세 갈래의 하위 추론이 마지막 규칙 하나로 모이는 구조다. 텍스트 추적은 이 구조를 드러내지 않는다는 점이 문제다.

| 갈래 | 규칙 | 하는 일 |
|---|---|---|
| 적재 | `R3`, `R37` | 중량에서 적재 유형을 정하고 대안을 철도 또는 트럭으로 좁힌다 |
| 운송 거리 | `R12`, `R8`, `R14` | 시간에서 속도 등급, 거리에서 거리 범위를 정하고 둘을 합쳐 운송 거리 유형을 만든다 |
| 손실·파손 | `R24`, `R26`, `R30` | 가치와 무게의 비율, 귀중도를 거쳐 손실·파손 등급을 정한다 |
| 결론 | `R51` | 대안과 손실·파손 등급을 합쳐 트럭을 권고한다 |

상담 과정에서 사용자가 받은 질문은 열 변수 중 여섯 개뿐이었다. 특수 품목, 부패성, 문전 서비스, 서비스 빈도는 묻지 않았다. 권고에 필요한 정보가 이미 모였기 때문인데, 사용자는 왜 그 질문들이 생략되었는지 텍스트 추적만으로는 알기 어렵다.

---

## 4. 저자의 평가: 투명성과 유연성의 결핍

저자는 이 인터페이스가 투명성 면에서 매우 제한적이라고 평가한다.

- **투명성 측면**: 규칙 추적은 어느 규칙이 어떤 순서로 발화되었는지는 알려 주지만 처리하고 이해하기 어렵다. 시스템이 쓰는 문제 해결 전략이 있다 해도 이해하기 어렵고, 권고를 정당화하는 기저 도메인 원리도 제공되지 않는다. 결국 시스템이 어떻게 작동하는지에 대한 적절한 멘탈 모델을 얻을 수 없다.
- **유연성 측면**: 텍스트 문답 대화는 정해진 순서로, 중간에 끼어들 수 없이 질문을 던지는 경직된 방식이다. 사용자가 다양한 방식으로 시스템을 탐색하거나 가정을 시험하거나 추가 정보를 구하기 어렵다.

저자는 이 전문가 시스템 상담을 더 잘 만들 필요가 있다고 결론짓고, 다음 절들에서 이 인간-컴퓨터 대화를 개선해 투명성과 유연성을 높이는 방법을 보인다. 그 방법에는 전략적 지식을 그림으로 보여 주는 다이어그램도 포함된다.
