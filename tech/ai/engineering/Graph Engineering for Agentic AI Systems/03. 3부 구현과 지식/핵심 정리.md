# 핵심 정리

이 문서는 3부(7장과 8장)의 요점을 한곳에 모은 복습용 정리다. 각 요점 끝의 **→ 자세히** 링크를 따라가면 해당 장으로 이동한다. 제품과 수치는 책이 2026년경 시점에 소개한 내용이다.

---

## 1. 한눈에 보는 요점

- **그래프 엔지니어링은 제품이 아니라 패턴이다**: 노드, 엣지, 공유 상태, 멈추고 재개하고 갈라지는 런타임이 전부이며 LangGraph는 그 한 구현이다.
  - *쉽게 말하면*: 로고가 아니라 그래프의 모양을 먼저 본다.
  - → 자세히: [7장 에이전트 그래프를 실어 보낼 수 있는 프레임워크](07%EC%9E%A5%20%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%20%EA%B7%B8%EB%9E%98%ED%94%84%EB%A5%BC%20%EC%8B%A4%EC%96%B4%20%EB%B3%B4%EB%82%BC%20%EC%88%98%20%EC%9E%88%EB%8A%94%20%ED%94%84%EB%A0%88%EC%9E%84%EC%9B%8C%ED%81%AC.md)
- **다섯 토폴로지는 누가 다음 노드를 정하는지가 다르다**: 컴파일된 상태 그래프, 크루, ADK 워크플로, 손으로 짠 DAG, 컴파일된 루프가 있고 각각 되돌아갈 수 있는지와 상태의 형태가 다르다.
  - *쉽게 말하면*: 같은 일을 그려도 되돌릴 수 있는 길이 있는 그림과 없는 그림이 있다.
  - → 자세히: [7장 에이전트 그래프를 실어 보낼 수 있는 프레임워크](07%EC%9E%A5%20%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%20%EA%B7%B8%EB%9E%98%ED%94%84%EB%A5%BC%20%EC%8B%A4%EC%96%B4%20%EB%B3%B4%EB%82%BC%20%EC%88%98%20%EC%9E%88%EB%8A%94%20%ED%94%84%EB%A0%88%EC%9E%84%EC%9B%8C%ED%81%AC.md)
- **고도는 냅킨 테스트로 고른다**: 그림이 이름 있는 패턴이면 높은 고도, 런타임 팬아웃·중첩·재개가 필요하면 낮은 고도에서 시작하고, 그릴 수 없으면 루프에 머문다.
  - *쉽게 말하면*: 종이에 못 그리면 아직 그래프가 아니다.
  - → 자세히: [7장 에이전트 그래프를 실어 보낼 수 있는 프레임워크](07%EC%9E%A5%20%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%20%EA%B7%B8%EB%9E%98%ED%94%84%EB%A5%BC%20%EC%8B%A4%EC%96%B4%20%EB%B3%B4%EB%82%BC%20%EC%88%98%20%EC%9E%88%EB%8A%94%20%ED%94%84%EB%A0%88%EC%9E%84%EC%9B%8C%ED%81%AC.md)
- **런타임은 가져다 쓰고 비즈니스만 직접 짠다**: 상태 스키마, 멱등 키, 사람 게이트, 비용 한도는 직접 정하고, A2A는 소유하지 않은 그래프와의 경계에만 쓴다.
  - *쉽게 말하면*: 엔진은 사 오고 운전 규칙은 우리가 쓴다.
  - → 자세히: [7장 에이전트 그래프를 실어 보낼 수 있는 프레임워크](07%EC%9E%A5%20%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%20%EA%B7%B8%EB%9E%98%ED%94%84%EB%A5%BC%20%EC%8B%A4%EC%96%B4%20%EB%B3%B4%EB%82%BC%20%EC%88%98%20%EC%9E%88%EB%8A%94%20%ED%94%84%EB%A0%88%EC%9E%84%EC%9B%8C%ED%81%AC.md)
- **실행 그래프와 지식 그래프는 다른 방이다**: G_A는 일의 흐름, G_K는 타입과 시간과 출처가 있는 기억이며 하나가 다른 하나의 역할을 맡으면 안 된다.
  - *쉽게 말하면*: 일하는 방과 서류 보관실을 따로 둔다.
  - → 자세히: [8장 메모리로서의 지식 그래프](08%EC%9E%A5%20%EB%A9%94%EB%AA%A8%EB%A6%AC%EB%A1%9C%EC%84%9C%EC%9D%98%20%EC%A7%80%EC%8B%9D%20%EA%B7%B8%EB%9E%98%ED%94%84.md)
- **GraphRAG는 검색 패턴이고 질문 유형으로 고른다**: 단일 조회는 벡터, 멀티홉은 그래프 순회, 전체 주제는 커뮤니티 요약, 변하는 사실은 시간 그래프이며 비용 수치는 출처 있는 것만 쓴다.
  - *쉽게 말하면*: 모든 질문에 같은 도구를 쓰지 않는다.
  - → 자세히: [8장 메모리로서의 지식 그래프](08%EC%9E%A5%20%EB%A9%94%EB%AA%A8%EB%A6%AC%EB%A1%9C%EC%84%9C%EC%9D%98%20%EC%A7%80%EC%8B%9D%20%EA%B7%B8%EB%9E%98%ED%94%84.md)
- **기억은 검증을 통과해야 들어가고 시간 두 개를 가진다**: 모델이 제안하고 형태 검사가 처분하며, 엔티티 해석 오차는 홉마다 곱해지고, 유효 시간과 기록 시간은 체크포인트와 별개의 시계다.
  - *쉽게 말하면*: 서류는 검사를 통과해야 보관하고, 언제 참이었는지와 언제 알았는지를 따로 적는다.
  - → 자세히: [8장 메모리로서의 지식 그래프](08%EC%9E%A5%20%EB%A9%94%EB%AA%A8%EB%A6%AC%EB%A1%9C%EC%84%9C%EC%9D%98%20%EC%A7%80%EC%8B%9D%20%EA%B7%B8%EB%9E%98%ED%94%84.md)

## 2. 3부를 관통하는 질문

| 질문 | 3부가 보여 주는 답 |
|------|-------------------|
| 프레임워크를 무엇으로 비교하나? | 브랜드가 아니라 토폴로지, 고도, 잠금(중력) |
| 손으로 짠 DAG로 충분한 때는? | 일이 정직하게 순환 없을 때만. 수정이 필요하면 순환을 지원하는 런타임 |
| 루프를 컴파일하는 것은 언제 정당한가? | 체크포인터나 인터럽트 같은 런타임이 필요할 때 |
| 지식 그래프를 만들어야 하나? | 멀티홉, 시간, 코퍼스 전체 질문이 있고 해석과 검증을 감당할 수 있을 때만 |
| 기억이 낡거나 오염되는 것을 어떻게 막나? | 유효 구간 무효화, 고정 술어 어휘, 형태 검사, 쓰기 노드 단일화, 각종 상한 |
| 두 그래프는 어디서 만나나? | 기억 질의 노드 하나. 제어 흐름은 G_K 안으로 들어가지 않는다 |

---

> **3부 한 줄 요약**
> 일의 모양을 먼저 정해 런타임과 고도를 고르고, 기억은 실행 그래프와 분리된 지식 그래프로 두어 하나의 문으로 읽고 검증된 것만 쓴다.
