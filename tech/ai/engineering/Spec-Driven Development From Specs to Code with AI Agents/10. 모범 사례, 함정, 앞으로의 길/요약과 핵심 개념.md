# 요약과 핵심 개념

10장은 두 덩어리로 이뤄진다. 규율이 왜 중요하고 어떻게 무너지는지를 다루는 앞부분(규율, 실패 양상, 검토, 확장)과, 팀에 어떻게 들여오고 어떻게 키우며 어디서 시작하는지를 다루는 뒷부분(도입, 성숙도, 한계, 앞으로의 길)이다. 이 문서는 두 덩어리를 한 번에 되짚고 핵심 용어를 정리한다.

이 장에는 별도의 'Key Takeaways' 절이 없고 'Final Reflection'(마지막 성찰)으로 책이 끝난다. 그 핵심은 이렇다. 문제는 코드를 충분히 빨리 만들지 못하는 것이 아니라 시작 전에 의도를 충분히 명확히 하지 않는 것이며, 경계 컨텍스트와 안정적 식별자와 관찰 가능한 동작을 지켜야 한다.

---

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | 속도와 의도 | 의도 없는 속도는 더 빠른 혼란. 코드 생성 전에 의도를 명시하고 안정화 |
| 2 | 복잡함이 아니라 규율 | 모든 동작 변경은 예외 없이 스펙에서 시작. 작은 예외가 드리프트를 만듦 |
| 3 | 규율이 값진 곳 | 오래 사는 시스템. 짧은 프로토타입은 제외 |
| 4 | 다섯 가지 실패 양상 | 모호함, 과잉 명세, 약해진 추적성, AI의 스펙 우회, 굳어 버린 스펙과 해결책 |
| 5 | 검토와 확장 | 사람의 검토는 대체 불가. 경계 컨텍스트로 명확성을 확장 |
| 6 | 도입과 성숙 | 작게 시작, 팀 검토, 구현 뒤 스펙에서 스펙 먼저로, 워크플로가 규율을 강화 |
| 7 | 한계, 앞으로, 시작 | 임시 시스템엔 가볍게, 스펙은 AI의 통제면, 유스케이스 하나로 시작 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 드리프트 | 작은 예외가 쌓여 스펙과 구현이 서서히 어긋나는 현상 |
| 모호함 | '보통', '~해야 한다', '필요에 따라' 같은 말. 해결은 명시적 규칙과 측정 가능한 결과, 관찰 가능한 사후 조건 |
| 과잉 명세 | DB 스키마, UI 레이아웃, 내부 구조까지 쓰는 것. 시스템 바깥에서 검증할 수 없으면 스펙이 아님 |
| 약해진 추적성 | ID 재사용이나 무시로 의도, 동작, 코드의 연결이 끊어짐. ID는 구조적 연결자 |
| AI의 스펙 우회 | 유스케이스 참조 없이 AI에게 개선을 시키는 것. 항상 유스케이스 ID를 참조하고 diff 기반으로 동기화 |
| 굳어 버린 스펙 | 코드만 바뀌어 스펙이 낡은 문서가 된 상태. 동작이 바뀌면 유스케이스를 먼저 갱신 |
| 성숙도 | 문서의 양이 아니라 의도와 구현의 정렬 정도 |
| 통제면(control surface) | AI 지원 개발에서 안정적 동작 계약인 스펙이 맡는 역할 |
| 시작 절차 | 유스케이스 하나 쓰기, 다른 사람과 검토, 구현, ID 참조, 변경은 스펙 먼저 |

## 3. 자주 놓치는 점

- 스펙 주도 개발은 요란하게 실패하지 않는다. 작은 예외가 조용히 쌓여 무너진다.
- 모든 시스템에 같은 엄격함을 요구하지 않는다. 판단 기준은 유지보수, 확장, 인계가 있는지다.
- 모호함과 과잉 명세는 반대 방향의 실패다. 기준은 관찰하고 검증할 수 있는지다.
- 테스트가 많아도 스펙이 틀리면 틀린 동작이 굳는다. 도메인 정확성의 책임은 사람에게 있다.
- 사람의 책임이 줄어드는 것이 아니라 가장 싼 곳(의도 수준)으로 옮겨 간다.
- 도입 초기의 느린 느낌은 예상되는 반응이다. 이미 다툼이 있는 부분의 작은 유스케이스로 가치를 보이면 된다.
- 첫 목표는 완벽한 스펙이 아니라 의도를 먼저 적는 습관이다.
- 도구는 명확성을 강화하지만 대체하지 않는다. 규율을 아는 팀에게만 도움이 된다.
