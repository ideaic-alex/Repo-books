# 모범 사례, 함정, 앞으로의 길

10장은 책의 마지막 장으로, 저자가 스펙 주도 개발로 일하며 배운 것을 모은다. 규율이 왜 통하고, 팀이 어디서 그것을 잃으며, 부담 없이 도입하려면 어떻게 해야 하고, 접근의 한계는 어디인지를 다룬다. 끝에는 오늘 당장 시작하는 방법과 저자의 마지막 성찰이 있다.

---

## 1. 핵심 요점

- 의도 없는 속도는 더 빠른 혼란이다. 스펙 주도 개발은 코드 생성 전에 의도를 명시하고 안정화하는 단순한 규율이다.
- 어려운 것은 압박 속의 일관성이다. 코드만 고친 버그 수정, 스펙에 돌아오지 않은 회의 결정, ID 재사용 같은 작은 예외가 드리프트를 만든다. 모든 동작 변경은 예외 없이 스펙에서 시작한다.
- 규율은 오래 살아남고 진화할 시스템에서 가장 값지다. 짧은 프로토타입이나 버릴 스크립트에는 필요 없다.
- 실패 양상은 모호함, 과잉 명세, 약해진 추적성, AI의 스펙 우회, 굳어 버린 스펙의 다섯 가지이며 각각 해결책이 있다.
- 자동화는 의도의 정확성을 보장하지 않는다. 틀린 스펙에서 나온 완벽한 테스트도 틀린 동작을 굳히므로 사람의 검토는 대체되지 않는다.
- 도입은 이미 다툼이 있는 부분의 작은 유스케이스로 시작해 팀이 함께 검토한다. 성숙은 구현 뒤 스펙에서 스펙 먼저로, 그리고 워크플로가 규율을 강화하는 단계로 자란다.
- 코드 비용이 떨어질수록 스펙은 AI의 통제면으로서 중요해진다. 시작은 유스케이스 하나, 지킬 것은 경계 컨텍스트, 안정적 식별자, 관찰 가능한 동작이다.
