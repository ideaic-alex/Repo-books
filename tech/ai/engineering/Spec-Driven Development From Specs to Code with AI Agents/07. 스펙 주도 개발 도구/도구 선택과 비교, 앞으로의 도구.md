# 도구 선택과 비교, 앞으로의 도구

도구는 선택이지만 막상 고를 때가 오면 기준이 필요하다. 원서는 팀 규모, AI 사용 수준, 워크플로를 얼마나 강제해야 하는지에 따라 알맞은 구성이 다르다고 말한다. 이 문서는 상황별 선택 지침, 네 가지 선택지의 비교, 그리고 빠르게 변하는 도구 환경에서 무엇을 보고 골라야 하는지를 정리한다. 7장의 핵심 정리도 함께 푼다.

---

## 1. 상황별 선택 지침

- 혼자 일하거나 AI 보조 개발을 막 시작한 작은 팀이라면 전용 도구가 필요 없다. Git 저장소의 Markdown 파일, `CLAUDE.md`나 `AGENTS.md` 같은 가이드라인 파일(AI 에이전트가 먼저 읽는 프로젝트 지침 파일), AI 에이전트면 AIUP를 적용하기에 충분하다. 규율은 도구가 아니라 스펙에서 나온다.
- 팀이 커지고 여러 개발자가 AI 에이전트를 병행해 쓰면 비공식 규율이 무너지기 시작한다. 사람마다 프롬프트 스타일이 다르고, 단계를 건너뛰고, 스펙의 품질이 고르지 않아진다. 이때는 워크플로 순서를 강제하는 도구가 실제 가치를 준다. GitHub Spec Kit이 잘 맞는다. 가볍고 CLI 기반이며, 이미 GitHub를 쓰면서 새 IDE를 도입하지 않고 구조를 더하려는 팀에 알맞다.
- 팀이 완전한 IDE 경험을 선호하고 편집기 안에서 AI가 구조화된 산출물과 긴밀히 일하기를 원하면 Amazon Kiro를 평가할 만하다. 세 산출물 구조가 AIUP 단계에 자연스럽게 대응하고, IDE 통합 덕에 팀 모두가 워크플로를 볼 수 있다.
- AIUP 마켓플레이스는 다른 역할이다. Kiro나 Spec Kit을 대체하지 않고, 그 위에 얹을 수 있는 재사용 가능한 버전 관리 프로세스 지식을 제공한다. 프로젝트 간에 일관된 AI 동작, 스킬로 묶은 스택별 지침, 워크플로를 다시 쓰지 않고 AI 에이전트를 바꿀 수 있는 능력이 필요할 때 쓴다.

## 2. 네 가지 선택지 비교

원서의 표 7-1은 네 가지를 짧게 비교한다. 추출본에서 대소문자가 일부 깨졌지만 열 구조는 읽을 수 있어 아래와 같이 정리했다.

| 선택지 | 주된 역할 | 통합 방식 | 워크플로 강제 |
|---|---|---|---|
| Markdown과 AI 에이전트 | 최소한의 출발점 | 어떤 편집기나 에이전트든 | 낮음, 팀의 규율에 달림 |
| Amazon Kiro | IDE 중심의 구조화된 워크플로 | 전용 AI 코딩 환경 | 높음 |
| GitHub Spec Kit | CLI 기반 생애 주기 강제 | CLI와 저장소 워크플로 | 높음 |
| AIUP 마켓플레이스 | 재사용 가능한 프로세스 계층과 스택 지침 | 스킬, 플러그인, MCP 연동 | 중간에서 높음 |

네 가지 모두 산출물 형식으로 일반 Markdown을 쓴다. 우연이 아니다. Markdown은 사람과 AI 에이전트가 모두 읽을 수 있고, Git에서 버전 관리가 되며, 독점 도구가 필요 없다. 차이는 그 토대 위에 무엇을 쌓느냐에 있다.

### 도입 비용

표가 담지 못하는 것이 도입 비용이다.

- Amazon Kiro는 IDE를 바꿔야 한다.
- GitHub Spec Kit은 CLI 도구와 새 생애 주기를 배워야 한다.
- AIUP 마켓플레이스는 플러그인을 설치하고 스킬 모델을 이해해야 한다.
- 일반 Markdown은 규율 외에는 아무것도 요구하지 않는다.

원서의 조언은 필요한 최소에서 시작하고, 도구가 풀어 주는 불편을 실제로 느낄 때 도구를 더하라는 것이다.

## 3. 앞으로의 도구에 기대할 것

AI 보조 개발의 도구 환경은 빠르게 변한다. Amazon Kiro와 GitHub Spec Kit도 2년 전에는 널리 알려지지 않았다. 다음 세대 도구도 비슷하게 빨리 나타날 것이고, 지금 도구 중 일부는 크게 바뀌거나 사라질 것이다. 그래서 도구 선택은 승자를 고르는 일보다 어떤 성질이 중요한지 이해하는 일에 가깝다. 원서는 네 가지 성질을 든다.

| 성질 | 이유 |
|---|---|
| 열린 산출물 형식 | 독점 형식이면 종속(lock-in)이 생긴다. 특정 앱을 실행해야만 자기 스펙을 읽을 수 있다면 그 앱이 바뀌거나 사라질 때 문제다. Git의 일반 Markdown은 도구와 무관하게 읽기, 버전 관리, 이식이 보장된다 |
| 에이전트 독립성 | 한 AI 모델이나 제공자에만 작동하면 위험하다. 모델은 개선되고, 제공자는 가격을 바꾸고, 새 에이전트가 나온다. AIUP는 이런 이유로 에이전트 독립적으로 설계되었다. 새 도구는 AI 에이전트를 제품이 아니라 교체 가능한 부품으로 다루는 쪽을 고른다 |
| 검토 가능성 | 좋은 도구는 AI 행동을 더 예측 가능하게 하고, 덜 보이게 하지 않는다. AI가 하는 일을 숨기거나 생성 산출물을 검사하기 어렵게 만드는 도구는 잘못된 방향이다. 스펙 주도 개발의 가치는 중요한 결정이 모두 검토 가능한 산출물을 거친다는 데서 나온다 |
| 점진적 도입 | 한 번에 모든 것을 바꾸라는 도구는 채택되지 않는다. 좋은 도구는 워크플로의 한 부분에서 시작해 넓힐 수 있다. AIUP 자체도 전체 방법론 없이 유스케이스 스펙만으로 시작해 이점 대부분을 얻을 수 있다 |

원서는 이 네 성질이 단기 기능 목록보다 중요하다고 말한다. 도구가 장기적이고 유지보수 가능한 AI 보조 개발을 위해 만들어졌는지, 좋은 시연만을 위한 것인지 가려 주기 때문이다.

---

## 4. 7장 핵심 정리

- 스펙 주도 개발은 도구가 아니라 규율 있는 스펙에 달려 있다.
- Amazon Kiro, GitHub Spec Kit, AIUP 마켓플레이스는 모두 구조화된 산출물, 버전 관리, 워크플로 순서를 중심에 둔다. 범위와 스타일은 다르지만 AI가 스펙에서 일할 때 더 좋은 결과를 낸다는 통찰을 공유한다.
- 마켓플레이스는 이를 실무에서 구현하는 한 방법일 뿐이며, 근본 생각이 구체적 구현보다 중요하다. 프로세스 지식은 묶고, 버전을 매기고, 재사용할 수 있으며, 프로젝트와 팀과 AI 에이전트를 넘어 AI 동작을 일관되게 한다.
- 다음 8장은 간단한 작업 관리자 예제로 요구사항에서 유스케이스 스펙, 엔터티 모델, 구현, 테스트까지 전 과정을 보여 준다.
