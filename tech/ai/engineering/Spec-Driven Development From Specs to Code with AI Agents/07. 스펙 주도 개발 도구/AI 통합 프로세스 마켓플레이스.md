# AI 통합 프로세스 마켓플레이스

AI 통합 프로세스 마켓플레이스(AI Unified Process Marketplace)는 저자가 이 방식의 작업을 지원하려고 만든 실제 구현이다. 필수 제품이 아니며, 스펙 주도 워크플로와 지침, 기술 스택별 기능을 실제 프로젝트용으로 어떻게 묶을 수 있는지 보여 주는 한 예다. 저자는 기존 도구가 자신이 필요한 방식으로 프로세스와 스택 지침을 묶어 주지 않아서 만들었다고 밝힌다.

현재는 Claude Code용으로 패키징되어 있다. 설치 방식과 슬래시 명령 흐름을 Claude Code가 제공하기 때문이다. 다만 그 밑의 스킬(skill, AI 에이전트에게 정해진 일을 하는 방법을 안내하는 재사용 가능한 구조화된 능력)은 Claude Code에 묶여 있지 않다. 방법론과 스킬 개념은 이식할 수 있다.

---

## 1. 마켓플레이스가 제공하는 것

스킬은 요구사항 쓰기, 엔터티 모델 만들기, 유스케이스 초안 쓰기, 특정 스택에서 유스케이스 구현하기 같은 정해진 일을 에이전트에게 안내한다. 마켓플레이스는 세 가지를 제공한다.

- 핵심(Core) AI 통합 프로세스 스킬
- 스택별(stack-specific) 스킬
- MCP 서버 연동

AIUP 지식을 재사용 가능하고 버전이 매겨진 구성 요소로 묶어, 일관되게 설치하고 실행할 수 있게 한다. 저장소 주소는 `https://github.com/AI-Unified-Process/marketplace`다.

## 2. 코어 플러그인과 스택 플러그인

마켓플레이스의 핵심 설계 결정은 방법론과 실행의 분리다. 플러그인(plugin, 기능을 묶어 설치하는 확장 단위)이 이 분리를 맡는다.

### 2-1. 코어 플러그인

AI 통합 프로세스 코어 플러그인(`aiup-core`)은 기술 스택과 무관하다. 핵심 스펙 산출물을 위한 스킬을 제공하며, Claude Code에서는 슬래시 명령으로 쓴다.

- requirements
- entity-model
- use-case-diagram
- use-case-spec

이 스킬들은 `/docs` 산출물에만 작동한다. 코어는 요구사항 관례, 시스템 유스케이스 구조, 추적성 규칙, ID 일관성, 관찰 가능한 행동의 강제를 이해한다. 프레임워크, 데이터베이스, UI 라이브러리는 전혀 모른다. 그래서 방법론이 안정적으로 유지된다.

### 2-2. 스택 플러그인

이 장의 예는 `aiup-vaadin-jooq` 플러그인을 쓴다. Flyway 마이그레이션 생성, 유스케이스 구현, 브라우저리스 테스트, Playwright 테스트 같은 기능을 제공하며, Claude Code에서는 다음 이름으로 호출한다.

- flyway-migration
- implement
- browserless-test
- playwright-test

스택 플러그인은 안정된 프로세스 모델을 특정 기술 생태계와 잇는 확장 지점이다. 한 팀은 Vaadin, Spring Boot, jOOQ, Flyway를 쓰고, 다른 팀은 React나 .NET 또는 전혀 다른 스택을 쓸 수 있다. 추가할 수 있는 스택의 종류에는 제한이 없고, AIUP 자체를 바꾸지 않고도 새 스택을 도입할 수 있다.

| 구분 | 이름 | 하는 일 |
|---|---|---|
| 코어 | aiup-core | requirements, entity-model, use-case-diagram, use-case-spec (/docs만 다룸) |
| 스택 | aiup-vaadin-jooq | flyway-migration, implement, browserless-test, playwright-test |

## 3. 스킬과 슬래시 명령

스킬은 프로세스 지식의 재사용 단위다. Claude Code에서 슬래시 명령(slash command)은 스킬을 부르는 형태일 뿐이다. 예는 다음과 같다.

```
/use-case-spec UC-001
/implement UC-001
/browserless-test UC-001
```

이것들은 즉흥적인 프롬프트가 아니라 구조화된 스킬을 직접 호출하는 것이다. Claude Code에서는 모든 스킬을 슬래시 명령으로 부를 수 있어 둘의 구분은 운영보다 개념에 가깝다. 핵심은 AI가 처음부터 즉흥으로 하는 것이 아니라 묶인 프로세스 지식을 따른다는 점이다. 스킬이 Claude Code에 묶이지 않으므로 같은 지식을 다른 에이전트 환경에 맞춰 쓸 수도 있다.

## 4. MCP 연동

마켓플레이스는 MCP(Model Context Protocol)도 연동할 수 있다. MCP는 AI 애플리케이션을 외부 시스템과 도구에 연결하는 개방형 표준이고, 그 표준에 따라 지식을 제공하는 쪽이 MCP 서버다.

MCP가 유용해지는 때는 에이전트가 구현 단계에 이르러 정확한 기술 지식이 필요할 때다. 외부 지식이 없으면 에이전트는 학습 때 배운 것에 의존한다. 널리 쓰이는 프레임워크라면 대체로 충분하지만, 학습 데이터에는 기준 시점이 있고, 오류가 있고, API가 바뀌면 낡는다. 그 결과 컴파일이 잘 안 되거나, 더는 쓰지 않는 메서드를 쓰거나, 모르는 API를 짐작하는 그럴듯한 코드가 나오기 쉽다.

MCP는 에이전트가 필요한 순간에 믿을 만한 기술 지식에 접근하게 해 이 위험을 줄인다. 복잡한 쿼리의 jOOQ DSL 패턴을 짐작하는 대신 jOOQ MCP 서버에 묻는다. 브라우저리스 테스트 메서드를 지어내는 대신 Vaadin MCP 출처에서 현재 API와 시그니처를 확인한다. 실제로는 다음 같은 출처에 구조적으로 접근하게 한다.

- Vaadin API 문서
- jOOQ DSL 참조
- Vaadin 테스트 패턴
- Playwright 자동화 문서

MCP 출처는 프레임워크 문서, DSL 참조, 테스트 패턴, API 스키마, 사내 코딩 표준, 아키텍처 지침처럼 다양한 구조화된 지식을 공개할 수 있다. 알맞은 조합은 프로젝트마다 다르며, 이것이 마켓플레이스를 닫힌 제품이 아니라 층(layer)으로 설계한 이유 중 하나다. 한 줄로 줄이면 스펙은 코드가 무엇을 해야 하는지를 정하고, MCP는 에이전트가 선택한 스택에서 그것을 올바르게 하도록 돕는다. 둘이 합쳐져 행동 지침과 기술적 근거를 함께 준다.

## 5. 프로세스 계층으로서의 마켓플레이스

기존 도구는 작업이 벌어지는 주된 장소가 되려 한다. 마켓플레이스는 다른 역할을 맡는다. 특정 IDE에 묶지 않고, 특정 AI 에이전트를 요구하지 않고, 독점 형식을 강제하지 않는다. 대신 서로 다른 에이전트와 환경에서 쓸 수 있는 패키지된 프로세스 지식을 제공한다.

다른 AI 에이전트와 함께 쓸 수 있고, Amazon Kiro나 GitHub Spec Kit과 결합할 수도 있고, 단독으로 쓸 수도 있다. AI 에이전트가 스펙과 상호작용하는 방식을 표준화한다. 그래서 또 하나의 개발 도구라기보다 프로세스 계층(process layer)으로 이해하는 편이 맞다.

---

## 6. 핵심 정리

- 마켓플레이스는 필수 제품이 아니라 저자가 만든 구현 예이며, 현재 Claude Code용으로 패키징되어 있고 스킬 개념은 이식 가능하다.
- 코어 플러그인(aiup-core)은 스택과 무관하게 /docs 산출물만 다루고, 스택 플러그인(aiup-vaadin-jooq 등)이 기술 생태계와 연결한다. 새 스택을 AIUP 변경 없이 추가할 수 있다.
- 슬래시 명령은 스킬의 호출 형태이며, 즉흥 프롬프트가 아니라 묶인 프로세스 지식을 실행한다.
- MCP 서버는 구현 단계에서 최신 API 문서와 패턴을 제공해 학습 데이터의 낡음과 오류에서 오는 위험을 줄인다.
- 마켓플레이스는 IDE, 에이전트, 형식에 묶이지 않는 프로세스 계층이다.
