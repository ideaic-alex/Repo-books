# 요약과 핵심 개념

이 장은 네 덩어리로 이뤄진다. 도구는 선택이고 규율이 필수라는 기본 태도, Kiro와 Spec Kit이라는 두 업계 도구, 저자가 만든 AI 통합 프로세스 마켓플레이스, 그리고 도구를 고르는 기준과 앞으로 중요한 성질이다. 이 문서는 네 덩어리를 한 번에 되짚고 핵심 용어를 정리한다.

원서의 요약은 이렇게 이어진다. 스펙 주도 개발은 도구가 아니라 규율 있는 스펙에 달려 있다. 세 도구 모두 구조화된 산출물, 버전 관리, 워크플로 순서를 중심에 두고, 마켓플레이스는 그것을 실무에 옮기는 한 방법이다. 프로세스 지식은 묶고 버전을 매겨 재사용할 수 있고, 그 덕에 AI 동작이 프로젝트와 팀과 에이전트를 넘어 일관된다. 다음 장은 작업 관리자 예제를 처음부터 끝까지 따라간다.

---

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | 도구에 대한 태도 | Markdown, Git, AI 에이전트면 충분하고 도구는 규율을 돕는다 |
| 2 | Amazon Kiro | Requirements, Design, Tasks 세 산출물의 사슬 |
| 3 | GitHub Spec Kit | 헌장, 스펙, 계획, 작업, 구현의 강제된 순서 |
| 4 | 마켓플레이스 | 코어와 스택 플러그인, 스킬, 슬래시 명령, MCP로 이뤄진 프로세스 계층 |
| 5 | 도구 선택 | 규모와 필요에 맞춰 최소에서 시작해 필요할 때 더한다 |
| 6 | 앞으로의 도구 | 열린 형식, 에이전트 독립성, 검토 가능성, 점진적 도입 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 가이드라인 파일 | CLAUDE.md, AGENTS.md처럼 에이전트가 읽는 프로젝트 지침 파일 |
| Amazon Kiro | 스펙 주도 개발을 강조하는 AI 코딩 환경(IDE) |
| Requirements.md / Design.md / Tasks.md | Kiro의 의도와 인수 기준 / 설계 결정 / 실행 단계 산출물 |
| GitHub Spec Kit | IDE가 아닌 스펙 주도 AI 개발 도구 모음과 워크플로 |
| specify CLI / .specify | Spec Kit의 명령줄 도구 / AI가 참고하는 프로젝트 기억 디렉터리 |
| AIUP 마켓플레이스 | 프로세스 지식과 스택 지침을 패키징한 저자의 구현. 프로세스 계층 |
| 코어 플러그인(aiup-core) | 스택 무관. requirements, entity-model, use-case-diagram, use-case-spec 스킬 |
| 스택 플러그인 | 특정 기술 스택용. aiup-vaadin-jooq는 flyway-migration, implement, browserless-test, playwright-test 제공 |
| 스킬 | 에이전트에게 정해진 일을 안내하는 재사용 가능한 능력 |
| 슬래시 명령 | Claude Code에서 스킬을 부르는 형태(예: /use-case-spec UC-001) |
| MCP 서버 | 개방형 표준 MCP로 에이전트에게 최신 기술 지식을 제공하는 출처 |
| 종속(lock-in) | 독점 형식 때문에 특정 도구 없이는 스펙을 읽지 못하는 상태 |

## 3. 자주 놓치는 점

- 도구가 규율을 만들어 주지는 않는다. 규율은 스펙에서 나온다.
- Kiro, Spec Kit, 마켓플레이스는 서로 경쟁하지 않는다. 마켓플레이스는 다른 도구 위에 얹을 수 있다.
- 코어 플러그인은 /docs 산출물만 다루며 프레임워크는 모른다. 스택 지식은 스택 플러그인에 있다.
- 슬래시 명령과 스킬의 구분은 운영보다 개념에 가깝다. Claude Code에서는 모든 스킬이 슬래시 명령으로 불린다.
- 마켓플레이스는 현재 Claude Code용으로 패키징되었지만 스킬 개념은 이식 가능하다.
- 도입 비용을 따진다. Kiro는 IDE 교체, Spec Kit은 CLI와 생애 주기 학습, 마켓플레이스는 플러그인과 스킬 모델 이해가 필요하다.
- 도구는 바뀌므로 이름보다 성질을 본다. 승자를 고르기보다 열린 형식, 에이전트 독립성, 검토 가능성, 점진적 도입을 점검한다.
