# 엔터티 모델과 요구사항 카탈로그 예시

앞 문서에서 요구사항을 어떻게 모으고 분류하는지 보았다면, 이번에는 그 결과물이 실제로 어떤 모양인지 본다. 3장은 작업 관리(task manager) 앱이라는 작은 예제를 하나 잡고, 요구사항 카탈로그와 엔터티 모델이 어떻게 생겼는지 표로 보여 준다.

두 산출물은 크기가 작다. 요구사항 카탈로그는 "무엇을 이뤄야 하는가"를 항목별로 적고, 엔터티 모델은 "시스템이 다루는 명사"를 정의한다. 도서관에 비유하면 카탈로그는 도서 목록 카드이고, 엔터티 모델은 '대출자', '도서' 같은 용어의 뜻을 적어 둔 약속 사전이다.

---

## 1. 요구사항 카탈로그 예시

요구사항 카탈로그(Requirements Catalog)의 모든 항목은 고유하고 바뀌지 않는 ID를 받는다. ID 규칙은 2장에서 설명한 관례를 따른다. 이 ID 덕분에 유스케이스, 코드, 테스트를 가로지르는 추적성(traceability, 요구사항에서 코드와 테스트까지 연결을 따라갈 수 있는 성질)이 생긴다.

원서의 표 3-1은 세 가지 종류가 한 줄씩 들어 있는 카탈로그다.

| ID | 제목 | 설명 |
|---|---|---|
| FR-001 | Assign Task | 사용자로서 다른 사용자에게 작업을 할당해 일이 분산되게 하고 싶다 |
| NFR-001 | Task Response Time | 작업 관련 연산은 1초 안에 끝나야 한다 |
| C-001 | Platform Constraint | 백엔드는 Java 21과 PostgreSQL 16에서 실행되어야 한다 |

- FR은 기능 요구사항, NFR은 비기능 요구사항, C는 제약이다. 접두어만 봐도 종류가 구분된다.
- FR-001은 사용자 스토리 형태("사용자로서 ... 하고 싶다 ... 하도록")로 쓰였다.
- NFR-001은 "1초"라는 측정 가능한 기준을 담았다. 4장에서 "빠르게"라는 모호한 말을 이런 항목을 참조하는 것으로 바꾸라고 하는 근거가 여기서 만들어진다.

참고(노트 작성자): PDF 추출본에서 이 표는 글자 대소문자가 깨져 있었다(예: 'Fr-001', 'nFr-001', 'postgresq L'). 위 표는 본문에 반복해서 나오는 ID 표기(FR-001, NFR-001, C-001)와 일반적인 제품 이름 표기에 맞춰 복원했다. 제목 'Assign Task', 'Task Response Time', 'Platform Constraint'의 영문 대소문자도 같은 방식으로 복원한 것이다.

## 2. 엔터티 모델은 시스템의 명사

엔터티 모델(Entity Model)은 시스템의 명사를 정의한다. 요구사항과 시스템 유스케이스가 함께 쓰는 공통 언어를 제공한다. 특히 AIUP에서는 엔터티 모델이 전통적인 용어집(glossary)을 대신한다. 엔터티 이름 하나하나가 곧 도메인 용어이고, 짧은 설명을 선택적으로 붙여 뜻을 분명히 하고 오해를 막는다.

요구사항과 유스케이스는 엔터티를 이름으로 참조한다. 그래서 용어가 자동으로 일관되고, 따로 관리할 용어집이 없다. 이 방식은 스펙을 최소한으로 유지하면서도 사람과 AI 도구 모두에게 분명한 어휘를 준다.

### 2-1. 예제 엔터티 두 가지

작업 관리 앱의 엔터티 모델(원서 그림 3-2)에는 User와 Task가 있다. 두 엔터티의 의미는 짧은 설명으로 남긴다.

- User: 작업을 만들 수 있고 작업을 할당받을 수 있는, 등록된 사람.
- Task: 설명, 마감일, 상태를 가진 하나의 일 단위.

### 2-2. 속성 표

각 엔터티는 속성(attribute)마다 데이터 타입, 길이, 검증 규칙을 적는다.

| 엔터티 | 속성 | 타입(길이) | 검증 규칙 |
|---|---|---|---|
| User | id | UUID(36) | 필수, 유일, 변경 불가 |
| User | name | string(100) | 필수, 비어 있지 않음 |
| User | email | string(255) | 필수, 유일, 올바른 이메일 형식 |
| User | active | Boolean | 필수, 기본값 true |
| Task | id | UUID(36) | 필수, 유일, 변경 불가 |
| Task | description | string(500) | 필수, 비어 있지 않음 |
| Task | dueDate | Date | 선택, 오늘이거나 미래여야 함 |
| Task | status | enum | 필수, 허용 값은 OPEN, ASSIGNED, DONE |

이 정도의 상세함이면 엔터티 모델은 단순하면서도 검증, 데이터베이스 설계, AI 지원 생성에 쓸 만큼 정밀하다고 책은 말한다.

참고(노트 작성자): 추출본에서 status의 허용 값이 'open, assiGneD, Done'처럼 대소문자가 섞여 깨져 있다. 4장과 5장 예제가 OPEN, ASSIGNED로 쓰는 것에 맞춰 대문자로 복원했고, 마지막 값 DONE도 같은 규칙으로 적었다. 또 원서 그림 3-2(엔터티 관계도)는 싣지 않았다. 표의 내용만 옮겼으며, 두 엔터티 사이의 선 모양은 추출본에서 확인되지 않아 적지 않았다.

## 3. 엔터티 모델과 용어 일관성

엔터티 이름은 유스케이스 문장에 그대로 들어간다. 예를 들어 "System assigns the Task to the User"처럼 쓰면 Task, User가 엔터티 모델의 이름과 같은 말이 된다. 이름이 곧 용어이므로 문서마다 'job', 'ticket', 'member'처럼 다른 말을 섞어 쓸 이유가 없어진다.

이 점은 AI가 생성하는 결과에도 중요하다. AI에게 용어를 맞추라고 따로 지시하지 않아도, 엔터티 모델을 입력으로 주면 같은 어휘로 코드와 테스트를 만들 수 있다. 3장의 요약도 같은 말을 한다. 유스케이스가 엔터티를 이름으로 참조하므로 테스트와 구현이 같은 용어와 개념을 쓰고, 모두가 같은 대상을 같은 방식으로 이야기하며 같은 동작을 검증하게 된다.

참고(노트 작성자): 위 'System assigns the Task to the User' 문장과 'job', 'ticket', 'member' 같은 대체 용어는 설명용으로 만든 예시이며 원서의 문장이 아니다.

## 4. 핵심 정리

- 요구사항 카탈로그의 모든 항목은 고유하고 변하지 않는 ID를 받고, FR/NFR/C 접두어로 종류를 구분한다.
- 비기능 요구사항(NFR-001)은 "1초 이내" 같은 측정 가능한 값으로 쓴다.
- 엔터티 모델은 도메인 명사를 정의하고 용어집을 대신한다. 따로 관리할 용어집이 없다는 것이 장점이다.
- 속성마다 타입, 길이, 검증 규칙을 적어 검증, DB 설계, AI 생성에 바로 쓸 수 있게 한다.
- 예제 엔터티는 User(id, name, email, active)와 Task(id, description, dueDate, status)이다.
