# 시스템 유스케이스의 구조와 좋은 흐름

요구사항 카탈로그가 "무엇을 이루고 싶은가"를 높은 수준에서 말한다면, 시스템 유스케이스는 그 의도를 구체적이고 테스트 가능한 동작으로 펼친다. 3장의 중심 내용이 이 부분이다. 유스케이스가 어떤 필드로 이뤄지는지, 예제는 어떻게 생겼는지, 흐름은 어떻게 써야 좋은지, 유스케이스끼리 어떤 관계를 맺는지 차례로 본다.

식당 주문에 비유하면 요구사항은 "점심을 먹고 싶다"이고, 유스케이스는 "메뉴판을 본다, 주문한다, 음식이 나온다, 계산한다"처럼 손님과 식당이 주고받는 단계의 기록이다.

---

## 1. 요구사항에서 유스케이스로

기능 요구사항은 사용자가 이루려는 바를 높은 수준에서 표현할 뿐, 세부 동작은 정하지 않는다. 시스템 유스케이스(System Use Case)는 이 의도를 구조화되고 테스트할 수 있는 동작으로 확장한다. 원서의 예는 다음과 같다.

- 요구사항 FR-001: 사용자는 작업을 할당할 수 있다.
- 유스케이스 UC-001: Assign Task

유스케이스는 구체적인 상호작용 단계, 대안, 오류 경우를 적는다. 코드, 테스트, 검증을 이끄는 주된 실행 가능한 스펙(executable specification)의 역할을 한다.

시스템 유스케이스 하나는 외부 행위자(actor)와 시스템 사이의, 의미 있는 결과로 이어지는 상호작용 하나를 기술한다.

## 2. 유스케이스 다이어그램

AIUP는 시스템 범위를 사용자 관점에서 보이려고 UML 유스케이스 다이어그램을 쓴다. 그림은 PlantUML로 쓴다. Mermaid에는 유스케이스 다이어그램 종류가 없기 때문이다. 텍스트로 쓰면 Git에 저장하고, 풀 리퀘스트에서 검토하고, 일관되게 다시 생성할 수 있다.

다이어그램은 어떤 행위자가 시스템과 상호작용하고 시스템이 어떤 기능을 제공하는지를 흐름 세부 없이 한눈에 보여 준다. 다이어그램이 "시스템이 무엇을 제공하는가"에 답한다면, 각 시스템 유스케이스(UC-###)는 주 흐름, 대안 흐름, 예외를 포함한 상세하고 테스트 가능한 동작을 적는다. 실무에서는 유스케이스 목록에서 다이어그램을 생성하거나 갱신하는 경우가 많아, 스펙 파일과 어긋나지 않게 유지된다. 원서의 그림 3-3은 Assign Task의 높은 수준 개요를 보여 주며 상세 유스케이스를 보완할 뿐 대신하지는 않는다.

## 3. 유스케이스의 구조

AIUP 유스케이스는 보통 다음 요소를 가진다(원서 표 3-4).

| 필드 | 목적 |
|---|---|
| ID | 고유 식별자(예: UC-001) |
| 제목 | 목표를 짧게 설명 |
| 행위자 | 시스템과 상호작용하는 외부 역할 |
| 목표 | 기대하는 결과 |
| 상태 | 초안, 검토됨, 승인됨 |
| 사전 조건 | 상호작용이 시작되기 전에 참이어야 하는 조건이나 상태 |
| 트리거 | 유스케이스를 시작하는 사건 |
| 주 성공 시나리오(주 흐름) | 성공 경로의 순서 있는 단계 |
| 대안 흐름 | 변형이지만 여전히 성공으로 끝나는 경우 |
| 예외 흐름 | 실패나 오류 경로 |
| 사후 조건 | 성공적으로 끝난 뒤 참이어야 하는 조건이나 상태 |
| 비즈니스 규칙 | 실행 중 적용되는 규칙 |
| 연결된 요구사항 | FR-001, NFR-001, C-001 같은 ID |

사전 조건과 사후 조건은 상태 쪽 약속이고, 주 흐름·대안 흐름·예외 흐름은 동작 쪽 약속이다. 대안 흐름은 다른 길을 가도 목적을 이루는 경우이고, 예외 흐름은 목적을 이루지 못하는 경우라는 점이 다르다.

## 4. 예제 유스케이스 UC-001

원서의 예제는 다음과 같다(축약하지 않고 핵심 값을 옮겼다).

```text
UC-001 Assign Task
Actor: User
Goal: 다른 활성 사용자에게 작업을 할당한다
Status: Documented
Preconditions: 사용자 인증됨 / 작업이 존재하며 미할당
Trigger: 사용자가 "Assign Task"를 선택
Main Flow:
 1 시스템이 작업 상세와 활성 사용자 목록을 표시
 2 사용자가 대상 사용자를 선택
 3 시스템이 대상 사용자가 활성인지 검증
 4 시스템이 작업을 할당
 5 시스템이 대상 사용자에게 알리고 성공을 확인
Alternate 3a: 대상 사용자가 비활성 -> 오류 표시, 2단계로 복귀
Exception 4a: 데이터베이스 사용 불가 -> 오류 기록, 사용자에게 알림
Postconditions: 작업이 선택한 활성 사용자에게 할당됨 / 대상 사용자에게 알림
Linked Requirements: FR-001, NFR-001, C-001
```

이 예에서 눈여겨볼 점은 세 가지다.

- 대안 흐름 번호 3a는 "주 흐름 3단계에서 갈라진다"는 뜻이다. 예외 4a도 4단계에서 갈라진다.
- 비활성 사용자는 사용자가 다시 고를 수 있으므로 2단계로 돌아가는 대안이다.
- 연결된 요구사항에 기능(FR), 비기능(NFR), 제약(C)이 모두 걸려 있다.

참고(노트 작성자): 이 예제의 Status는 원서에서 'Documented'로 적혀 있는데, 상태 필드 설명(표 3-4)은 초안·검토됨·승인됨이라고 한다. 두 서술이 어긋나 보이지만 원서가 이 차이를 따로 설명하지는 않는다. 위 코드블록은 원문을 줄이고 한국어로 풀어 쓴 것이며, 원문 문구 그대로가 아니다.

원서의 그림 3-4는 이 주 흐름을 활동 다이어그램(activity diagram)으로 그린 것으로, 판단 지점과 흐름의 갈래를 한눈에 보이게 한다. 그림은 싣지 않았고, 위 단계 목록과 3a 대안이 같은 정보를 글로 담고 있다.

## 5. 좋은 흐름을 쓰는 네 가지 권고

### 5-1. 단계를 관찰 가능하게 쓴다

각 단계는 시스템 밖에서 보거나 확인할 수 있는 것을 적는다. 내부 구현 세부는 피한다. 시스템이 무엇을 하고 무엇을 보여 주는지를 쓰고, 어떻게 구현했는지는 쓰지 않는다.

### 5-2. 능동태를 쓴다

누가 동작하는지 분명히 밝힌다. 모호한 표현 대신 "시스템이 ...를 표시한다", "사용자가 ...를 선택한다"처럼 쓴다. 사람과 AI 도구 모두에게 읽기 쉽고 애매함이 줄어든다.

### 5-3. 대안·예외 흐름에서 단계 번호를 참조한다

대안 흐름과 예외 흐름은 갈라지는 정확한 단계를 가리켜야 한다. 그러면 흐름을 따라가기 쉽고, 어떤 조건이 정상 동작을 바꾸는지가 분명해진다.

### 5-4. 유스케이스 하나에 목표 하나

유스케이스는 의미 있는 결과 하나에 집중해야 한다. 목표가 여럿 보이면 별도의 유스케이스로 쪼갠다. 그래야 작고 집중되며 테스트하고 유지하기 쉽다.

## 6. 유스케이스 사이의 관계

UML 유스케이스 다이어그램은 유스케이스 사이의 관계를 표현할 수 있다. 원서의 표 3-5는 세 종류를 든다.

| 관계 | 의미 | 예 |
|---|---|---|
| include | 여러 유스케이스가 쓰는 재사용 가능한 하위 흐름 | 사용자 인증이 많은 흐름에 포함됨 |
| extend | 단계를 더하는 선택적 동작 | 2단계 인증(2FA) 추가가 Login을 확장 |
| generalization | 상위 유스케이스의 특수화된 버전 | Submit Order → Submit Bulk Order |

책의 주의는 이렇다. 유스케이스 다이어그램의 관계는 이해하기 어려울 때가 있으므로, 관계는 명료함을 더할 때만 사용한다.

참고(노트 작성자): 추출본의 표에서 'authenticate user included in many flows'와 'add 2Fa extends Login' 등 소문자·대소문자가 깨진 부분을 읽히는 대로 복원했다. include/extend/generalization의 한국어 표기는 원서 영어를 그대로 두고 설명만 붙였다.

## 7. 핵심 정리

- 요구사항(FR-001)은 의도이고, 유스케이스(UC-001)는 단계, 대안, 오류를 담은 테스트 가능한 동작이다.
- 유스케이스 다이어그램은 PlantUML로 쓴다. Mermaid에는 이 다이어그램 종류가 없고, PlantUML은 Git에서 검토·재생성이 가능하다.
- 유스케이스는 ID, 제목, 행위자, 목표, 상태, 사전 조건, 트리거, 주 흐름, 대안 흐름, 예외 흐름, 사후 조건, 비즈니스 규칙, 연결된 요구사항으로 구성된다.
- 좋은 흐름은 관찰 가능한 단계, 능동태, 단계 번호 참조, 목표 하나라는 네 가지 권고를 따른다.
- include, extend, generalization 관계는 명료함을 더할 때만 쓴다.
