# 요약과 핵심 개념

3장은 날것의 대화를 스펙으로 바꾸는 과정을 세 덩어리로 보여 준다. 첫째는 워크숍 결과를 AI가 요약, 추출, 분류하고 사람이 검토하는 요구사항 수집, 둘째는 요구사항 카탈로그와 엔터티 모델이라는 두 정적 산출물, 셋째는 동작을 담는 시스템 유스케이스와 그 메타데이터, 추적성이다. 이 문서는 세 덩어리를 한 번에 되짚고 핵심 용어를 정리한다.

원서의 요약은 이렇게 이어진다. 요구사항은 의도를, 유스케이스는 동작을, 엔터티 모델은 공유 구조를 담당하며, 셋이 AIUP의 실행 가능한 스펙 묶음을 이룬다. AI는 작성을 돕고 사람은 의도와 결정을 쥔다. 안정적인 식별자와 명시적 참조로 동작, 코드, 테스트가 항상 원래 의도까지 추적된다. 다음 장은 이 스펙들을 실행 가능한 계약으로 바꾸는 법을 다룬다.

---

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | 워크숍(도메인 스토리텔링, 이벤트 스토밍) | 구조 없는 날것의 산출물 |
| 2 | AI 요약, 추출, 분류 | 기능/비기능/제약으로 나뉘고 ID가 붙은 후보 항목 |
| 3 | 사람의 검토 | 중복 병합, 모순 해결, 누락 보완, 모호한 표현 수정이 끝난 요구사항 |
| 4 | 요구사항 카탈로그와 엔터티 모델 작성 | FR-001, NFR-001, C-001 및 User, Task 속성 표 |
| 5 | 시스템 유스케이스 작성 | UC-001 Assign Task(사전 조건, 주 흐름, 3a, 4a, 사후 조건) |
| 6 | 메타데이터와 추적성 | linkedRequirements와 entities로 요구사항에서 코드와 테스트까지 연결 |
| 7 | AI의 초안 작성, 검증, 일관성, 다이어그램, 리팩터링 지원 | 사람이 통제하는 반복 개선 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 스펙(명세) | 검토, 버전 관리, 발전이 가능하도록 글로 쓴 요구와 동작의 기술 |
| 스펙 주도 개발 | 스펙을 먼저 쓰고 그것으로 구현, 테스트, 검증을 이끄는 개발 방식 |
| AI 통합 프로세스(AIUP) | 요구사항, 엔터티 모델, 시스템 유스케이스를 핵심 산출물로 쓰는 프로세스 |
| 요구사항 카탈로그 | 기능(FR), 비기능(NFR), 제약(C) 항목을 고유 ID와 함께 모은 목록 |
| 엔터티 모델 | 도메인 명사와 속성을 정의하며 용어집을 대신하는 산출물 |
| 시스템 유스케이스 | 행위자와 시스템 사이의 의미 있는 상호작용 하나를 단계, 대안, 결과로 적은 것 |
| 주 성공 시나리오(주 흐름) | 성공 경로의 순서 있는 단계 |
| 대안 흐름 / 예외 흐름 | 성공으로 끝나는 변형 / 실패나 오류 경로 |
| 사전 조건 / 사후 조건 | 시작 전에 참이어야 하는 조건 / 성공 종료 후 참이어야 하는 조건 |
| 비즈니스 규칙 | 실행 중 적용되는 규칙 |
| 인수 기준 | 사전 조건, 흐름, 사후 조건에서 얻는 검증 가능한 기준 |
| 실행 가능한 스펙 | 개발자와 AI 도구가 해석 없이 구현과 검증에 쓸 만큼 정밀한 스펙 |
| 추적성 | 안정적 ID와 참조로 요구사항, 유스케이스, 코드, 테스트를 이어 따라갈 수 있는 성질 |
| PlantUML | 유스케이스 다이어그램을 텍스트로 쓰는 도구(Mermaid에는 이 종류가 없음) |
| include / extend / generalization | 재사용 하위 흐름 / 선택적 추가 동작 / 특수화된 버전 |

## 3. 자주 놓치는 점

- AI가 만든 구조화된 결과는 "완성돼 보여도" 완성이 아니다. 검토를 서두르면 오해가 문서로 굳는다.
- AI는 서로 다른 입력의 모순된 진술을 그대로 보존하기 쉽다. 검토에서 직접 걸러야 한다.
- 워크숍의 진짜 가치는 문서가 아니라 토론 중 생긴 공통의 머릿속 모델이다. 검토가 그것을 문서로 옮긴다.
- 엔터티 모델이 용어집을 대신하므로, 유스케이스는 엔터티 이름을 그대로 써야 한다.
- 대안 흐름과 예외 흐름은 갈라지는 단계 번호를 반드시 가리킨다(예: 3a, 4a).
- 유스케이스 하나에 목표 하나만 둔다. 목표가 둘이면 쪼갠다.
- 관계(include, extend, generalization)는 명료함을 더할 때만 쓴다. 어려워지면 쓰지 않는다.
- 참고(노트 작성자): 원서 예제에서 UC-001의 상태가 'Documented'로 적혀 상태 필드 설명(초안, 검토됨, 승인됨)과 다르게 보인다. 책이 이 차이를 설명하지 않으니 예제의 표기로만 이해하면 된다.
