# 메타데이터, 추적성, AI의 유스케이스 작성·검증 지원

유스케이스를 사람이 읽는 글로만 두면 기계가 점검할 길이 좁다. 그래서 AIUP는 유스케이스에 메타데이터(metadata, 데이터를 설명하는 데이터)를 붙인다. 메타데이터가 있으면 요구사항에서 코드와 테스트까지 이어지는 추적성(traceability)이 생기고, AI가 검사를 대신 도울 수 있다. 이 문서는 3장의 마지막 부분인 메타데이터 예제, 추적성 사슬, AI가 유스케이스 생애 주기에서 하는 일, 그리고 장의 요약을 다룬다.

화물 택배에 비유하면 유스케이스 본문은 상자 안의 물건이고, 메타데이터는 상자에 붙은 송장이다. 송장이 있어야 어디서 와서 어디로 가는지 시스템이 추적하고 빠진 것이 없는지 대조할 수 있다.

---

## 1. 유스케이스 메타데이터

원서는 유스케이스 메타데이터가 AI 지원 점검을 가능하게 하고, 이것이 요구사항에서 코드와 테스트까지의 추적성을 만든다고 설명한다. 예제는 UC-001에 붙은 YAML 형식의 정보다.

```yaml
id: UC-001
name: Assign Task
actors:
  - User
linkedRequirements:
  - FR-001
  - NFR-001
  - C-001
entities:
  - User
  - Task
postconditions:
  - Task assigned to target user
  - Target user notified
```

각 키가 하는 일을 풀어 보면 다음과 같다.

- id, name: 유스케이스의 고유 식별자와 이름이다. 추적성의 출발점이다.
- actors: 상호작용하는 외부 역할이다.
- linkedRequirements: 이 유스케이스가 충족하려는 요구사항 ID 목록이다. 기능(FR), 비기능(NFR), 제약(C)이 한곳에 모인다.
- entities: 이 유스케이스가 참조하는 엔터티 이름이다. 엔터티 모델과 대조할 수 있다.
- postconditions: 성공 후 참이어야 하는 결과를 기계가 읽을 수 있는 형태로 요약한다.

참고(노트 작성자): 원서는 이 메타데이터를 어느 파일 형식에 어떻게 저장하는지(본문 상단, 별도 파일 등)는 밝히지 않는다. 위 설명에서 각 키의 풀이는 키 이름에서 읽을 수 있는 의미를 풀어 쓴 것이다.

## 2. 추적성 사슬

원서의 그림 3-5는 추적성 사슬(Traceability Chain)을 보여 준다. 본문이 말하는 핵심은 요구사항에서 코드와 테스트까지 연결이 이어진다는 것이다. 3장 요약도 같은 취지로, 안정적인 식별자와 명시적 참조 덕분에 동작, 코드, 테스트를 언제든 원래의 의도까지 거슬러 올라갈 수 있다고 한다.

이 사슬이 작동하는 이유는 세 가지 장치가 겹치기 때문이다.

| 장치 | 연결해 주는 것 |
|---|---|
| 안정적이고 불변인 ID | 요구사항, 유스케이스, 코드, 테스트가 같은 번호로 서로를 가리킨다 |
| 연결된 요구사항(linkedRequirements) | 유스케이스에서 요구사항으로 올라간다 |
| 엔터티 이름 참조 | 유스케이스, 테스트, 구현이 같은 용어를 쓴다 |

참고(노트 작성자): 추출본에서 그림 3-5의 내부 글자는 읽히지 않았다. 사슬을 구성하는 칸의 정확한 이름과 순서는 확인하지 못했고, 위 표는 본문 문장에서 말한 범위(요구사항에서 코드와 테스트까지)만 정리한 것이다.

## 3. AI가 유스케이스 생애 주기에서 하는 일

AI 도구는 유스케이스의 전 생애 주기를 지원한다. 원서의 표 3-6은 다섯 가지 활동을 든다.

| 활동 | AI 지원 내용 |
|---|---|
| 초안 작성(Drafting) | 사용자 스토리를 구조화된 유스케이스로 확장한다 |
| 검증(Validation) | 연결된 요구사항이 얼마나 다뤄졌는지 확인한다 |
| 일관성(Consistency) | 용어를 엔터티 모델 정의에 맞춘다 |
| 다이어그램 작성(Diagramming) | PlantUML과 Mermaid 다이어그램을 생성한다 |
| 리팩터링(Refactoring) | 중복이나 겹침을 찾아낸다 |

표 아래의 한 줄이 중요하다. 사람이 계속 통제하며 의도와 정확성을 확인한다. 1번 문서의 검토 원칙이 유스케이스 단계에도 그대로 이어진다는 뜻이다.

여기에서 메타데이터의 쓸모가 분명해진다. 검증은 linkedRequirements를 읽어야 가능하고, 일관성 점검은 entities를 엔터티 모델과 비교해야 가능하다. 메타데이터가 없는 유스케이스는 AI가 문장의 뜻을 추측해야 하지만, 메타데이터가 있으면 목록끼리 대조하면 된다.

참고(노트 작성자): 위 마지막 문단의 '검증은 linkedRequirements를 읽어야 가능하고' 같은 연결은 표 3-6과 메타데이터 예제를 함께 놓고 풀어 쓴 해석이며, 원서가 이렇게 직접 연결해 쓴 것은 아니다.

## 4. 3장의 요약

원서는 3장 끝에서 산출물이 함께 일하는 방식을 다음처럼 정리한다.

- 요구사항은 의도를 적는다. 시스템이 달성할 것과 제약을 상세 동작 없이 담아 이후 모든 작업의 비즈니스 목표와 경계가 된다.
- 시스템 유스케이스는 이 의도 위에 동작을 쓴다. 추상적 목표를 구체적이고 관찰 가능하며 테스트 가능한 흐름으로 바꾸고, 대안과 오류 상황까지 포함한다.
- 유스케이스가 테스트 가능한 이유는 구조에 있다. 사전 조건은 필요한 준비를, 주 흐름은 기대하는 성공 경로를, 대안·예외 흐름은 타당한 변형과 실패를, 사후 조건은 실행 후 참이어야 하는 관찰 가능한 결과를 정한다. 이 요소들이 모여 수동으로든 자동 테스트로든 검증할 수 있는 분명한 인수 기준(acceptance criteria)이 된다.
- 엔터티 모델은 공유 구조를 만든다. 요구사항과 유스케이스가 일관되게 쓰는 도메인 개념과 어휘를 정의한다.
- 이 산출물들이 AIUP의 실행 가능한 스펙 묶음이다. 개발자와 AI 도구를 이끌 만큼 정밀하면서 사람이 읽기에 가볍다. AI는 요약, 추출, 일관성 점검, 생성으로 작성을 돕고, 사람은 의도와 결정을 쥔다.

3장은 다음 장에서 이 스펙들을 실행 가능한 계약으로 바꾸는 방법을 설명한다고 예고하며 끝난다.

## 5. 핵심 정리

- 유스케이스 메타데이터(id, name, actors, linkedRequirements, entities, postconditions)는 AI 지원 점검과 추적성의 바탕이다.
- 추적성은 안정적 ID, 연결된 요구사항, 엔터티 이름 참조로 요구사항에서 코드와 테스트까지 이어진다.
- AI는 유스케이스의 초안 작성, 검증, 일관성 확인, 다이어그램 생성, 리팩터링(중복 탐지)을 돕는다.
- 사람은 의도와 정확성을 끝까지 확인한다.
- 사전 조건, 주 흐름, 대안·예외 흐름, 사후 조건이 모이면 인수 기준이 된다. 이 연결은 4장에서 더 구체적으로 다룬다.
