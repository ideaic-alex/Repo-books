# 요약과 핵심 개념

2장은 세 덩어리로 이뤄진다. AI 통합 프로세스의 다섯 원칙과 세 가지 산출물, Git과 식별자로 만드는 버전 관리와 추적성 및 다섯 활동의 수명주기, 그리고 RUP와의 비교와 지금 통하는 이유다. 이 문서는 세 덩어리를 한 번에 되짚고 핵심 용어를 정리한다.

원서의 요약은 이렇게 이어진다. 원칙이 스펙의 작성, 버전 관리, 활용을 이끌고, 세 산출물이 완전하고 가벼운 스펙 세트를 이루며, 반복적 수명주기가 스펙과 구현을 정렬 상태로 두고, 내장된 추적성이 모든 산출물을 잇고, AI가 읽는 구조화된 자연어로 AI 준비가 된 프로세스가 된다. 다음 장은 요구사항에서 스펙으로 가는 방법이다.

---

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | 왜 프로세스가 필요한가 | 애자일이 못 푼 흩어진 의도를 스펙이 단일 진실의 원천이 되어 해결 |
| 2 | 다섯 가지 핵심 원칙 | 실행 가능한 스펙, 최소주의, 설계된 추적성, AI 협업, 모든 것의 버전 관리 |
| 3 | 프로세스 모양과 세 산출물 | 연속된 순환 고리와 요구사항 카탈로그, 엔터티 모델, 시스템 유스케이스 |
| 4 | 버전 관리와 추적성 | Markdown과 Git, FR, NFR, C, UC 식별자로 내장된 연결 |
| 5 | 수명주기 | 명세, 생성, 검증, 검토, 정제의 짧은 반복 |
| 6 | RUP 비교와 지금 통하는 이유 | 무거운 모델링을 AI, 자동화, 가벼운 도구가 대체 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| AI 통합 프로세스(AIUP) | 단순한 산출물과 AI의 도움으로 스펙을 개발의 토대로 만드는 가벼운 방법. RUP에서 영감을 받음 |
| 실행 가능한 스펙 | 코드 생성, 테스트 틀, 검증을 이끌 만큼 정확한 스펙. 형식 언어가 아니라 구조화된 텍스트와 모호하지 않은 동작이 조건 |
| 최소주의 | 명확성을 더하거나 자동화를 가능하게 하는 산출물만 만든다 |
| 스펙 코어 | 요구사항 카탈로그, 엔터티 모델, 시스템 유스케이스 세 산출물 |
| FR / NFR / C | 기능 요구사항 / 비기능 요구사항 / 제약의 식별자 접두사 |
| UC | 시스템 유스케이스의 식별자 접두사. 유스케이스 하나가 Markdown 파일 하나 |
| 사용자 스토리 vs 시스템 유스케이스 | 의도를 표현 vs 동작을 정의. 스토리가 대화를 열고 유스케이스가 계약으로 공식화 |
| 추적성 | 요구사항, 유스케이스, 코드, 테스트가 ID로 연결되어 양방향으로 따라갈 수 있는 성질 |
| 수명주기 | 명세, 생성, 검증, 검토, 정제의 반복. 고정 단계와 인계가 없다 |
| docs-as-code / diagram-as-code | 문서와 도표를 텍스트로 쓰고 Git으로 관리하는 방식 (Markdown, AsciiDoc, PlantUML, Mermaid.js) |

## 3. 자주 놓치는 점

- AI 통합 프로세스는 직선 단계가 아니라 순환 고리다. 하루에 여러 번 돌 수도 있다.
- 실행 가능한 스펙이 형식 언어를 뜻하지 않는다. 구조화된 텍스트면 충분하다.
- 엔터티에는 별도 ID를 붙이지 않는다. 이름을 일관되게 쓰는 것이 암묵적 추적성이 된다. 식별자는 요구사항(FR, NFR, C)과 유스케이스(UC)에만 쓴다.
- 생성물은 최종 해법이 아니라 출발점이다. 사람의 검토와 최종 승인은 빠지지 않는다.
- 정제 활동에서는 스펙과 코드를 따로 바꾸지 않는다.
- 추적성을 위한 링크는 세 군데다. 유스케이스의 요구사항 ID, 유스케이스 속 엔터티 이름, 코드와 테스트의 유스케이스 ID.
- RUP와의 차이는 도구의 무게와 단계 구조, 자동화에서 가장 크다. 목표(스펙을 중심에 두기)는 같다.
