# 버전 관리, 추적성, 수명주기

이 문서는 2장의 가운데 부분을 다룬다. 모든 산출물을 Git에 어떻게 두는지, 식별자로 어떻게 추적성(Traceability, 요구사항에서 코드와 테스트까지 연결을 따라갈 수 있는 성질)을 만드는지, 그리고 명세, 생성, 검증, 검토, 정제의 다섯 활동으로 이뤄진 수명주기를 정리한다.

비유하면 버전 관리는 일기장, 추적성은 일기장 속 쪽 번호와 색인, 수명주기는 하루에도 몇 번씩 도는 '쓰고 확인하고 고치기' 습관이다.

---

## 1. 버전 관리 실무

AI 통합 프로세스의 모든 산출물은 Git 저장소에 평범한 Markdown 파일로 저장된다. 그래서 스펙이 일반 개발 워크플로의 일부가 되고 소스 코드와 같은 규율로 다뤄진다. Markdown은 사람이 읽을 수 있고, 변경 차이를 보기 쉽고, 도구와 AI 시스템이 잘 지원한다.

산출물 종류마다 폴더 구조를 둘 수 있다. 원서의 전형적인 구성은 다음과 같다.

```
/specs
  entity_model.md
  requirements_catalog.md
  use_cases.puml
  /usecases
    UC-001_assign_task.md
    UC-002_complete_task.md
```

이 구조는 산출물을 찾기 쉽게 하고, 요구사항에서 엔터티 모델, 시스템 유스케이스로 이어지는 흐름을 분명히 보여 준다. 여기서 use_cases.puml은 PlantUML로 쓴 유스케이스 개요 다이어그램 파일로 보인다(참고(노트 작성자): 원문은 파일 이름만 보이며 내용 설명은 없다).

### 1.1 식별자 형식

- FR-### : 기능 요구사항
- NFR-### : 비기능 요구사항
- C-### : 제약
- UC-### : 시스템 유스케이스

이 식별자가 스펙, 코드, 테스트에 걸쳐 오래가는 연결을 만든다.

### 1.2 Git에 스펙을 두는 이점

- 누가 언제 무엇을 왜 바꿨는지 모든 변경의 전체 이력이 남는다.
- 브랜치와 병합이 쉬워 팀이 스펙을 협업으로 발전시킬 수 있다.
- 커밋, 풀 리퀘스트, 스펙 업데이트가 직접 연결된다.
- AI 도구가 변경 차이(diff)를 분석해 불일치, 낡은 동작, 빠진 업데이트를 찾아낼 수 있다.

스펙을 Git에 두면 최신 상태로 유지되고, 검토할 수 있고, 그것이 이끄는 코드와 긴밀하게 연결된다.

## 2. 추적성

추적성은 모든 동작을 의도까지 거슬러 연결할 수 있게 하는 성질이다. 이해관계자가 원하는 것과 시스템이 실제로 하는 것을 이어 준다. AI 통합 프로세스에서 추적성은 사후에 하는 수작업이 아니라, 스펙의 구조 안에 처음부터 내장되어 있다.

원서의 추적성 지도를 글로 풀면 다음 흐름이다.

| 단계 | 하는 일 |
|---|---|
| 1. 요구사항 | 기능 요구사항, 비기능 요구사항, 제약이 의도와 경계를 표현한다 |
| 2. 시스템 유스케이스 | 요구사항에서 영감을 받아 구체적 시스템 동작을 서술한다 |
| 3. 도메인 엔터티 | 유스케이스가 엔터티를 참조해 의도와 구현 사이의 다리가 된다 |
| 4. 코드와 테스트 | 유스케이스에서 만들어지며 언제나 출처 유스케이스를 가리킨다 |

이렇게 되면 탐색이 쉬워진다. 팀원은 사용자 목표에서 출발해 연결된 유스케이스를 따라가 관련 코드와 테스트를 빨리 찾을 수 있다. 반대 방향도 같다. 코드가 바뀌면 어떤 동작과 어떤 비즈니스 의도가 영향받는지 곧바로 알 수 있다.

추적성은 산출물 사이의 안정적 참조로 달성된다.

- 각 시스템 유스케이스가 관련 요구사항 ID를 나열한다.
- 엔터티는 유스케이스 안에서 이름으로 참조한다.
- 테스트와 코드 주석이 유스케이스 ID로 되돌아가는 링크를 단다.

이 링크가 명시적이고 기계가 읽을 수 있으므로 AI 에이전트가 자동으로 활용한다. 에이전트는 다음을 할 수 있다.

- 커버리지를 검증하고 빠진 구현을 찾는다.
- 코드가 진화할 때 낡은 스펙을 식별한다.
- 추적성 매트릭스나 규정 준수 보고서를 생성한다.

그래서 추적성은 가볍지만 강력하다. 코드를 원래 의도까지 거슬러 갈 수 있게 해서 스펙, 구현, 비즈니스 목표가 계속 정렬되도록 한다.

## 3. 수명주기: 다섯 활동의 반복

AI 통합 프로세스의 수명주기는 스펙과 구현을 동기화하는 단순하고 반복되는 주기다. 의도적으로 짧고 연속적이다. 고정된 단계나 인계는 없다. 팀은 필요한 만큼, 때로는 하루에 여러 번 이 활동들을 오간다. 활동은 명세(Specify), 생성(Generate), 검증(Validate), 검토(Review), 정제(Refine) 다섯 가지다.

| 활동 | 내용 |
|---|---|
| 명세 | 팀이 의도와 구조를 포착한다. 요구사항 카탈로그 갱신, 시스템 유스케이스 정제, 엔터티 모델 조정이 포함된다. 목표는 완전함이 아니라 시스템이 다음에 해야 할 일을 설명할 만큼의 명확성이다. 사람과 AI 도구가 모두 이해하는 단순하고 구조화된 언어로 쓴다 |
| 생성 | AI 도구가 스펙을 입력으로 코드 뼈대, 테스트 틀, 다이어그램을 만든다. 속도와 일관성에 집중한다. 생성물은 최종 해법이 아니라 출발점이며 항상 스펙의 현재 상태를 반영한다 |
| 검증 | 생성된 코드와 기존 코드를 스펙에 비춰 확인한다. 테스트가 유스케이스 흐름과 비즈니스 규칙이 올바로 구현되었는지 검증한다. CI 파이프라인에서 자동화해 코드나 스펙의 변경이 합의된 동작을 깨지 않게 할 수 있다 |
| 검토 | 사람이 스펙과 생성물을 모두 검토한다. 정확성, 가독성, 아키텍처 품질을 확인한다. AI가 돕지만 결정, 절충, 최종 승인의 책임은 사람에게 있다 |
| 정제 | 검증과 검토의 피드백에 따라 팀이 스펙과 코드를 함께 업데이트한다. 모호함을 없애고, 규칙을 명확히 하고, 예외 상황을 더한다. 어떤 것도 따로 바꾸지 않는다 |

그리고 주기는 다시 반복된다. 반복할수록 스펙이 더 정밀해지고, 구현이 더 안정되고, 오해와 재작업의 위험이 줄어든다.

### 3.1 활동을 읽는 요령

- 명세의 목표가 완전함이 아니라는 점을 놓치기 쉽다. 다음에 만들 것을 설명할 만큼만 쓰고 반복에서 키워 간다.
- 생성물은 초안이다. 검증과 검토를 거치지 않은 생성물을 최종물로 보지 않는다.
- 정제에서 스펙과 코드를 따로 바꾸지 않는다는 규칙이 앞의 원칙(모든 것의 버전 관리, 설계된 추적성)을 실제 작업에서 지키는 장치다.

## 4. 핵심 정리

- 산출물은 평범한 Markdown 파일로 Git에 두며 폴더 구조로 요구사항, 엔터티 모델, 유스케이스의 흐름을 드러낸다.
- 식별자는 FR, NFR, C, UC 네 가지 접두사를 쓴다.
- 추적성은 유스케이스의 요구사항 ID 나열, 엔터티 이름 참조, 코드와 테스트에서 유스케이스 ID로의 링크로 이뤄진다. AI 에이전트가 이를 이용해 커버리지, 낡은 스펙, 추적성 매트릭스를 다룬다.
- 수명주기는 명세, 생성, 검증, 검토, 정제의 짧은 반복이며 단계 인계가 없다.
