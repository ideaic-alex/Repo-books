# 머리말과 이 책에 대하여

이 문서는 Simon Martinelli가 쓴 'Spec-Driven Development: From Specs to Code with AI Agents'(Apress Pocket Guides, 2026)의 저자 소개, 기술 감수자 소개, 감사의 글, 머리말(Introduction)을 정리한 것이다. 이 책이 누구를 위해 쓰였는지, 10개 장이 어떤 순서로 이어지는지, 따라 하려면 무엇을 준비해야 하는지를 먼저 훑어 둔다. 본격적인 내용으로 들어가기 전에 전체 지도를 손에 쥐는 용도다.

이 책은 스펙 주도 개발(Spec-Driven Development, 코드보다 먼저 시스템이 해야 할 일을 글로 명확히 적고, 코드와 테스트를 그 글에서 이끌어 내는 개발 방식)을 다루는 짧은 안내서다. 저자가 만든 AI 통합 프로세스(AI Unified Process, AIUP)라는 구체적인 작업 방식을 중심으로 설명한다. 이 노트는 장별로 같은 형식으로 정리하며, 이 문서는 그 첫머리에 해당한다.

---

## 1. 책의 목적과 대상 독자

머리말은 저자의 30년 경험에서 출발한다. 저자는 COBOL로 시작해 Java로 옮겨 오며 업무용 소프트웨어를 만들었고, 그동안 같은 사실을 거듭 배웠다고 말한다. 소프트웨어에서 어려운 부분은 코드가 아니라는 것이다. 무엇을 만들지 알아내고, 그것을 명확히 적고, 시스템이 커지는 동안 그 공통된 이해를 살려 두는 일이 어렵다.

AI 코딩 도구는 코드를 쓰는 속도를 바꿨지만 이 어려운 부분은 바꾸지 못했고, 오히려 더 어렵게 만들었다고 저자는 본다. 도구가 몇 초 만에 수백 줄을 만들어 내면 위험은 느린 타이핑이 아니라 의도의 기록이 없는 채로 엉뚱한 것을 빠르게 만드는 일이 된다.

그래서 이 책이 제안하는 방식은 의도를 중심에 두는 것이다. 원하는 동작을 명확한 스펙(Specification, 명세)으로 적고, 스펙을 테스트에 묶고, 코드 작성이라는 무거운 일은 AI에게 맡긴다. 스펙이 진실의 원천으로 남고 코드는 거기서 따라 나오므로, 둘을 언제든 맞대어 확인할 수 있다.

AI 통합 프로세스가 전부 새로운 발명은 아니다. 머리말에 따르면 유스케이스는 Ivar Jacobson이 소개하고 Alistair Cockburn이 다듬은, 오래된 행위 기록 방법이다. 이 책이 새로 더하는 것은 이 오래된 생각을 AI 도구와 실제로 돌아가는 테스트 묶음에 연결해서 전체가 정직하게, 서로 어긋나지 않게 유지되도록 하는 점이다. 결과물은 새 프로젝트뿐 아니라 우리가 대부분의 시간을 쓰는 대규모 기존 시스템에도 쓸 수 있는 프로세스라고 한다.

대상 독자(Who This Book Is For)는 다음과 같이 밝혀져 있다.

- 개발자, 소프트웨어 아키텍트, 기술 리드
- 요구사항 엔지니어와 테스터
- 공통점은 AI 도구를 쓰되 자기 시스템의 통제권을 잃고 싶지 않은 사람이라는 점이다.

특정 프레임워크를 알아야 하는 것은 아니다. 예제는 저자가 가장 잘 아는 기술 스택을 쓰지만 방법 자체는 그 스택에 의존하지 않는다고 한다. 명확한 요구사항, 유지보수할 수 있는 코드, 1년 뒤에도 이해할 수 있는 소프트웨어에 관심이 있다면 대상 독자다.

저자가 밝힌 접근 방식의 원칙도 있다. 길잡이는 '단순하게 유지하라'다. AI 통합 프로세스는 역할과 문서가 많은 무거운 프로세스가 아니라, 하나씩 도입할 수 있는 작은 실천의 묶음이다. 유스케이스 하나로 시작해 명확히 적고, 나머지는 거기서 자라게 두라고 권한다.

## 2. 저자와 기술 감수자

저자 Simon Martinelli의 이력은 'About the Author'에 적힌 대로 정리하면 다음과 같다.

| 항목 | 내용 |
|---|---|
| 호칭 | Java Champion, Vaadin Champion, Oracle ACE Pro |
| 경력 | 소프트웨어 아키텍트, 개발자, 컨설턴트, 트레이너로 30년 이상 |
| 대표 업적 | AI 통합 프로세스의 창안자이며 스펙 주도 개발의 적극적인 옹호자 |
| 사업 | Martinelli LLC 대표. 팀이 AI 주도 개발에 빠르게 적응하도록 코칭함 |
| 활동 | 국제 콘퍼런스, 기고, 블로그 'Keep IT Simple'(AI, 아키텍처, 현대 Java 개발을 다룸) |
| 교육 | 스위스의 두 대학에서 소프트웨어 아키텍처, 영속성, DevOps, 클라우드 네이티브 개발을 강의 |

기술 감수자는 Neerja Bhatnagar다. 19년 이상의 경력을 가진 소프트웨어 엔지니어로, 그중 9년은 대형 기술 기업에서 대규모 백엔드 시스템을 만들었다. 미국 California State University, Chico에서 컴퓨터과학 석사 학위를 받았고 현재는 에이전트 거버넌스(AI 에이전트의 행동을 통제하는 일)에 집중하는 초기 단계 스타트업에서 일한다.

감사의 글(Acknowledgments)에서 저자는 Apress 팀, 꼼꼼하게 읽고 솔직한 피드백을 준 기술 감수자, 이 책의 아이디어를 직접 써 보고 어려운 질문을 던져 준 동료와 고객과 커뮤니티 친구들에게 감사한다. AI 통합 프로세스는 많은 실제 프로젝트와 대화에서 자라났다고 적었다. 끝으로 아내 Lisa의 인내와 지지에 감사를 전한다.

저자의 경력은 책의 성격과 이어진다. 오래 업무용 시스템을 다룬 사람이라서 관심이 신규 프로젝트보다 오래 사는 시스템의 유지보수와 현대화에 있고, 예제가 Java 중심인 것도 이 때문으로 보인다. 참고(노트 작성자): 이 연결은 저자 소개와 머리말을 읽고 추정한 것이며 원문이 직접 그렇게 말하는 것은 아니다.

## 3. 책의 구성

머리말의 'How This Book Is Organized'에 따르면 책은 실제 프로젝트에서 밟게 되는 길, 곧 첫 질문에서 동작하는 시스템으로, 다시 팀 전체로 가는 길을 따른다. 1~2장은 왜 필요한지와 전체 그림, 3~6장은 방법의 핵심, 7~8장은 도구와 사례, 9~10장은 단일 프로젝트를 넘어선 확장과 교훈이다. 장마다 앞 장 위에 쌓이지만 필요한 주제로 바로 건너뛰어도 된다고 머리말은 밝힌다. 제목은 이 노트에서 쓰는 한국어 이름이다.

| 장 | 한국어 제목 | 한 줄 요약 |
|---|---|---|
| 1 | 왜 스펙 주도 개발인가 | 스펙 주도 개발이 왜 필요한지, 그것 없이는 무엇이 잘못되는지 묻는다 |
| 2 | AI 통합 프로세스 개요 | 세부로 들어가기 전에 AI 통합 프로세스의 전체 그림을 요약해 보여 준다 |
| 3 | 요구사항에서 스펙으로 | 요구사항을 스펙으로 바꾸는 방법. 목차상 요구사항 수집, 사람의 검토, 엔터티 모델, 시스템 유스케이스 작성을 다룬다 |
| 4 | 실행 가능한 스펙 작성 | 실행될 수 있을 만큼 정확한 스펙을 쓰는 법. 목차상 모호함 제거, 유스케이스 각 요소 작성, 인수 기준을 다룬다 |
| 5 | 스펙이 코드를 이끄는 실무 | 스펙이 실제로 코드를 이끄는 과정. 목차상 UC-012 사례, 가이드라인 파일, 스킬, MCP 서버, 변경 동기화를 다룬다 |
| 6 | 테스트로서의 스펙 | 스펙을 테스트로 바꾸는 법. 목차상 테스트 트로피, TDD 위치, AI 테스트 생성 워크플로를 다룬다 |
| 7 | 스펙 주도 개발 도구 | 이 방식을 뒷받침하는 도구. 목차상 Amazon Kiro, GitHub Spec Kit, AI 통합 프로세스 마켓플레이스를 다룬다 |
| 8 | 사례 연구: 간단한 작업 관리자 만들기 | 작업 관리자를 단계별로 만들며 지금까지의 내용을 하나로 묶는다 |
| 9 | 스펙 주도 개발 규모 확장 | 팀 단위로 스펙 주도 개발을 확장하는 방법을 보인다 |
| 10 | 모범 사례, 함정, 앞으로의 길 | 모범 사례와 흔한 함정을 모아 실수를 겪지 않고 배우게 한다 |

참고(노트 작성자): 머리말 본문은 3~6장을 '요구사항에서 스펙(3장), 실행 가능한 스펙(4장), 스펙을 테스트로(5장), 스펙이 코드를 이끎(6장)' 순으로 소개한다. 그러나 PDF 목차의 5장은 'Specs Driving Code in Practice', 6장은 'Specs As Tests'이다. 두 정보가 5장과 6장에서 서로 뒤바뀌어 있으므로 이 노트는 실제 장 제목인 목차를 따른다.

3~8장은 이 노트의 담당 범위 밖이므로 위 요약은 목차와 머리말에서 확인되는 내용으로만 적었다.

## 4. 읽는 순서

머리말은 책을 앞에서부터 읽을 것을 전제로 하되, 필요한 주제로 건너뛰는 것도 허용한다. 이 노트가 권하는 순서는 다음과 같다.

- 처음 접하는 독자: 1장으로 문제의식을 잡고 2장으로 AI 통합 프로세스의 전체 그림을 얻은 뒤, 3~6장의 핵심 방법을 순서대로 읽고 8장 사례로 확인한다.
- 이미 AI 코딩 도구를 쓰는 독자: 1장과 2장을 빠르게 훑고 5장, 6장으로 간다.
- 도구를 고르려는 독자: 2장 뒤에 7장을 읽는다.
- 팀이나 조직 도입을 고민하는 독자: 2장 뒤에 9장과 10장을 읽는다. 9장은 규모 확장, 10장은 도입 방법과 함정이다.
- 가볍게 시작하고 싶은 독자: 10장 끝부분의 '시작하는 곳'을 먼저 읽고 유스케이스 하나를 써 본다.

## 5. 실습 준비물

8장의 'Project Setup'과 'Local Setup'(PDF 127~130쪽)에 따르면 사례 연구는 Task Manager 저장소를 예로 든다. 목표는 이 저장소를 복제해 같은 순서를 따라가 본 뒤 자기 프로젝트에 조금만 고쳐 적용하는 것이다. 이 프로젝트는 최고의 작업 관리자를 만들려는 것이 아니라 스펙, 코드, 테스트가 어긋나지 않고 함께 진화하는 모습을 보이려는 작은 예제다.

| 준비물 | 용도 |
|---|---|
| Java 25 이상 | 어느 JDK 배포판이든 된다. 원서는 Eclipse Temurin을 기본 선택으로 권한다. Linux와 macOS에서는 SDKMAN으로 버전을 관리할 수 있다 |
| Docker | 실행 중이어야 한다. 꺼져 있으면 Testcontainers가 PostgreSQL을 띄우지 못해 연결 오류로 실패한다 |
| Git | 저장소 복제와 단계별 태그 확인에 쓴다 |
| 프로젝트 기술 스택 | Spring Boot(애플리케이션 프레임워크), Vaadin(프런트엔드), jOOQ(DB 접근), PostgreSQL(데이터베이스), Testcontainers(로컬 DB 구성) |
| AI 에이전트 | 장의 시작에서 AI 통합 프로세스와 Claude Code를 쓰는 안내라고 밝힌다. 원서는 능력 있는 AI 에이전트, Markdown 파일, Git, 명확한 스펙이면 충분하고 특별한 도구는 필요 없다고 말한다 |

설치를 확인하는 순서는 저장소를 복제하고 폴더로 들어간 뒤 `./mvnw spring-boot:test-run`을 실행하는 것이다. 이 명령은 테스트 클래스패스로 애플리케이션을 띄우고 Testcontainers로 PostgreSQL을 시작하며 브라우저에서 로그인 화면을 보여 준다.

실습은 열 단계이며 각 단계가 저장소의 Git 태그에 대응한다. `git checkout <태그>`로 그 시점의 프로젝트 상태를 볼 수 있다.

- 1 init(비전과 초기 설정), 2 requirements(요구사항 카탈로그), 3 entity_model(엔터티 모델과 용어집), 4 use_cases_diagram(유스케이스 개요 다이어그램), 5 scaffolding(프로젝트 뼈대)
- 6 database_migration(DB 스키마 마이그레이션), 7 spec_UC-006(첫 유스케이스 스펙), 8 implement_UC-006(구현), 9 test_UC-006(브라우저 없는 테스트), 10 e2e_UC-006(Playwright 종단 간 테스트)

참고(노트 작성자): PDF 추출본에서 7번 태그가 'spec_uC-006'처럼 대소문자가 섞여 있다. 추출 과정의 손상으로 보이며, 원래는 다른 태그처럼 UC-006일 가능성이 높으나 확인할 수 없다.

원서는 AI 통합 프로세스가 선택 도구와 슬래시 명령을 제공한다고 소개한다. 이 도구들은 워크플로를 바꾸지 않고 템플릿, 구조, 안전장치를 줘서 반복을 쉽게 할 뿐이다. 장의 슬래시 명령도 특정 명령 이름에 의존하라는 뜻이 아니라 규율 있는 작업 방식을 보이는 예다. 사례 저장소는 `/docs` 폴더가 시스템 동작을 설명하는 권위 있는 문서라는 규칙 하나를 따른다.

## 6. 이 노트의 읽는 법

이 노트는 원서를 장별 폴더로 나누어 한국어로 새로 풀어 쓴 학습 노트다. 번역서가 아니라 설명 노트이므로 원문 문장을 그대로 옮기지 않고, 원칙, 산출물, 절차, 수치, 사례, 주의점을 같은 정보량으로 다시 구성한다.

- 각 장 폴더에는 Readme.md가 있고, 그 안에 핵심 요점과 문서 목록이 있다. 장에 들어가면 Readme.md를 먼저 읽고 필요한 문서로 이동한다.
- 영어 용어는 처음 나올 때 한국어 풀이를 붙인다. 스펙, 스펙 주도 개발, AI 통합 프로세스, 요구사항 카탈로그, 엔터티 모델, 시스템 유스케이스, 실행 가능한 스펙, 추적성, 바운디드 컨텍스트(경계 컨텍스트), 가이드라인 파일, 스킬, MCP 서버, 바이브 코딩, 코드 우선 같은 용어는 노트 전체에서 같은 말로 통일한다.
- 제품 이름, 코드, 명령어, 경로는 영어 그대로 둔다.
- 원서의 그림은 싣지 않고 글과 표로 풀어 설명한다.
- 원문에 없는 보충은 '참고(노트 작성자):'로 표시한다. PDF 추출이 깨진 곳은 문맥으로 복원하고 불확실하면 그렇게 밝힌다.
- 이 노트는 머리말, 1장, 2장, 9장, 10장을 다룬다. 3~8장은 별도 노트에서 다룬다.

이 문서만 읽어도 책의 전체 흐름은 잡힌다. 다음 단계는 1장 '왜 스펙 주도 개발인가'다. 코드 우선 방식이 왜 시스템을 이해하기 어렵게 만드는지부터 보면 2장 이후가 훨씬 쉬워진다.
