# 9~10단계와 반복 UI 단위 테스트, E2E 테스트, 스펙 먼저 바꾸고 동기화

구현이 끝나면 같은 유스케이스 스펙에서 테스트가 나온다. 9단계는 브라우저 없이 도는 빠른 브라우저리스 테스트이고, 10단계는 실제 브라우저로 전체 스택을 도는 Playwright 종단 간(E2E) 테스트다. 구현, 단위 테스트, E2E 테스트 세 가지가 모두 같은 스펙에서 나왔다는 것이 이 장의 핵심 주장이다.

이어서 반복 절은 프로젝트가 첫 릴리스 뒤에도 정합성을 잃지 않고 바뀌는 방법을 다룬다. 답은 스펙을 먼저 바꾸고, 나머지를 동기화한다는 것이다.

---

## 1. 9단계: UI 단위 테스트

테스트는 같은 유스케이스 스펙에서 파생된다. 브라우저리스 테스팅은 브라우저를 띄우지 않고도 Vaadin 뷰에 대해 메모리 안에서 도는 빠른 단위 테스트를 쓰게 해 준다.

### 1-1. 스펙과 테스트의 대응

테스트 시나리오는 유스케이스에 곧바로 대응한다. 주 성공 시나리오는 정상 경로 테스트가 되고, 대안 흐름은 추가 테스트 케이스가 된다. 테스트는 뷰가 스펙대로 동작하는지, 곧 필터링, 데이터 표시, 가장자리 사례까지 확인한다.

### 1-2. 원서의 예

원서의 단순화한 예는 메서드 `user_with_single_team_sees_tasks()`다. 위의 주석은 UC-006 주 성공 시나리오의 1~3단계(사용자가 화면으로 이동하고, 시스템이 팀을 판단하고, 단일 팀을 자동 선택)와 BR-001(Team Membership Required), BR-002(All Team Tasks Visible), BR-003(Task List Ordering, updated_at 내림차순)을 가리킨다. 본문은 Given, When, Then 구조다.

- Given: 정확히 한 팀에 접근 권한이 있는 사용자로 로그인한다. 예제 값은 `login("singleTeamUser", List.of(Role.USER))`다.
- When: 사용자가 팀 작업 화면(`TaskView`)으로 이동한다.
- Then: 시스템이 단일 팀을 자동 선택한다. "Team" 라벨의 콤보 상자 값이 null이 아니고, 팀 이름이 "Development Team"이며, 팀 선택기가 읽기 전용(read-only)이다.

```java
login("singleTeamUser", List.of(Role.USER));
UI.getCurrent().navigate(TaskView.class);
ComboBox<Team> teamSelector = _get(ComboBox.class, spec -> spec.withLabel("Team"));
softly.assertThat(teamSelector.getValue().name()).isEqualTo("Development Team");
softly.assertThat(teamSelector.isReadOnly()).isTrue();
```

원서는 이 테스트가 존재하는 이유를 강조한다. 이 행동이 유스케이스에 있기 때문에 있는 것이지, 누군가 나중에 추가하는 것을 기억해서 생긴 것이 아니다. 생성 명령은 `/browserless-test UC-006`이고, 결과는 `git checkout test_UC-006`으로 본다.

참고(노트 작성자): 원서의 단언 코드 일부(`assertSoftly` 블록 끝과 이어지는 `...`)는 생략되어 있다. 위 코드는 핵심 줄만 옮긴 것이며 원문 그대로가 아니다.

## 2. 10단계: 종단 간 테스트

단위 테스트에 더해 Playwright로 종단 간 테스트를 쓴다. 이 테스트는 데이터베이스까지 포함한 전체 애플리케이션 스택에서 실제 브라우저로 돈다. 브라우저리스 테스트를 보완하며, 개별 컴포넌트만이 아니라 시스템 전체가 기대대로 작동하는지 확인하고, 단위 테스트가 찾지 못하는 통합 문제를 잡는다.

원서의 Playwright 예는 9단계와 같은 이름의 `user_with_single_team_sees_tasks()`다. 흐름은 다음과 같다.

- Given: 같은 단일 팀 사용자로 로그인한다. 예제 값은 `login("singleTeamUser", "user")`다.
- When: `http://localhost:` 뒤에 로컬 서버 포트를 붙인 주소로 이동하고 `waitForVaadin()`으로 Vaadin이 준비되기를 기다린다.
- Then: 텍스트 "Team"을 가진 `vaadin-combo-box`를 찾아 보이는지 확인한다.

생성 명령은 `/playwright-test UC-006`이고, 최종 결과는 `git checkout e2e_UC-006`으로 본다.

참고(노트 작성자): 원서 반복 절에는 이 명령이 `/playwright_-est`로 깨져 있다. 10단계의 `/playwright-test`와 7장 이름을 기준으로 복원했다. 같은 절의 `/browerless-test`도 `/browserless-test`의 오타로 보고 바로잡았다.

구현, 단위 테스트, E2E 테스트의 세 단계가 모두 같은 스펙에서 나왔다. 원서는 이것이 핵심 아이디어라고 말한다. 하나의 스펙에서 여러 파생 산출물이 나온다.

| 단계 | 산출물 | 실행 방식 | 보는 것 |
|---|---|---|---|
| 8 | 구현 | 애플리케이션 | 스펙의 흐름과 규칙 |
| 9 | 브라우저리스 테스트 | 메모리 안에서 브라우저 없이 | 뷰의 동작(필터링, 표시, 가장자리) |
| 10 | Playwright 테스트 | 실제 브라우저, 전체 스택과 DB | 시스템 전체의 동작 |

## 3. 반복: 스펙을 먼저 바꾸고 동기화

반복에서 AIUP의 강점이 가장 잘 보인다. 처음 열 단계는 시스템을 맨땅에서 만들었다. 실제 프로젝트는 첫 릴리스에서 끝나지 않는다. 요구사항이 바뀌고, 사용자가 의견을 주고, 버그가 나타난다. 문제는 스펙, 코드, 테스트의 정합성을 잃지 않고 시스템을 바꾸는 방법이다. 답은 간단하다. 스펙을 먼저 바꾸고, 나머지를 동기화한다.

### 3-1. 예: 우선순위 열 추가

이해관계자가 UC-006의 작업 목록에 정해진 정렬 순서를 가진 priority(우선순위) 열을 보여 달라고 요청한다고 하자. 전통적인 작업 흐름에서는 개발자가 바로 코드로 뛰어들고 테스트는 나중에, 혹은 끝내 고치지 않는다. 시간이 지나면 문서와 구현 사이에 드리프트가 생긴다. AIUP에서는 순서가 늘 같다.

1. 스펙을 갱신한다. 엔터티 모델에 priority 속성을 더한다. 유스케이스에 새 열과 정렬 순서에 대한 비즈니스 규칙을 더한다. 아직 고치기 싼 시점에 이해관계자와 변경을 검토한다.
2. 필요하면 마이그레이션을 만든다. 엔터티 모델이 바뀌었다면 `/flyway-migration`으로 스키마 갱신을 만든다. 비즈니스 규칙만 바뀌었다면 이 단계는 건너뛴다.
3. `/implement UC-006`을 다시 실행한다. 에이전트가 갱신된 스펙을 읽고 기존 코드를 조정한다. 처음부터 다시 만들지 않는다.
4. `/browserless-test UC-006`과 `/playwright-test UC-006`을 다시 실행한다. 새 비즈니스 규칙은 새 테스트 케이스를 만든다. 바뀌지 않은 행동의 기존 테스트는 그대로 남는다.

### 3-2. 버그 수정도 같은 패턴

버그는 스펙이 불완전하거나 코드가 스펙과 맞지 않는다는 뜻이다. 어느 쪽이든 첫 단계는 스펙을 확인하는 것이다. 스펙이 옳으면 구현 명령을 다시 실행한다. 스펙이 틀렸으면 스펙부터 고친다.

### 3-3. 엄격한 순서의 이점

이 엄격한 순서는 흔한 문제를 막는다. 동작은 하는데 아무도 설명하지 못하는 코드다. 또 AI 지원을 더 효과적으로 만든다. 에이전트가 모호한 지시를 짐작하는 대신 갱신된 스펙을 읽기 때문이다.

기능을 더하든, 규칙을 바꾸든, 버그를 고치든 작업 흐름은 같다. 명령은 바뀌지 않고 스펙만 바뀐다. 원서는 이것이 저장소의 핵심 목적, 곧 드리프트 없는 통제된 진화를 보여 주는 것이라고 말한다.

## 4. 핵심 정리

- 9단계는 브라우저 없이 메모리에서 도는 빠른 브라우저리스 테스트다. 주 성공 시나리오는 정상 경로, 대안 흐름은 추가 케이스가 되며, 이 테스트는 스펙에 행동이 있어서 존재한다.
- 10단계는 Playwright로 실제 브라우저와 전체 스택(DB 포함)을 도는 E2E 테스트이며, 컴포넌트 단위로는 못 찾는 통합 문제를 잡는다.
- 구현, 단위 테스트, E2E 테스트가 같은 스펙에서 나온다. 하나의 스펙에서 여러 파생 산출물이 나온다.
- 변경은 스펙 갱신, 필요 시 마이그레이션, 구현 재실행, 테스트 재실행 순서다. 버그도 스펙 확인부터 시작한다.
- 8장 전체의 결론은 `/docs`가 단일 진실 원천(single source of truth)이고, 규칙이 바뀌면 스펙이 먼저 바뀌며, 코드와 테스트가 뒤따라 통제된 진화가 이뤄진다는 것이다. 시스템 유스케이스가 구현, 단위 테스트, E2E 테스트를 한 문서에서 이끈다.
- 다음 9장은 시스템이 커지고 여러 팀이 병렬로 일할 때 경계가 있는 컨텍스트(bounded context)가 스펙을 관리 가능하게 유지하는 방법과, AI가 기계적인 일을 맡을 때 엔지니어의 역할이 어떻게 바뀌는지를 다룬다.
