# 1~4단계 비전, 요구사항, 엔터티 모델, 유스케이스 다이어그램

첫 네 단계는 코드를 한 줄도 쓰지 않고 `/docs` 폴더의 문서를 차례로 쌓는다. 비전에서 요구사항 카탈로그가 나오고, 요구사항에서 엔터티 모델이 나오고, 이것들을 바탕으로 유스케이스 개요 다이어그램이 나온다. 앞 문서가 다음 문서의 입력이 되는 사슬이다.

요리로 비유하면 이 단계는 장보기 전에 메뉴를 정하고, 재료 목록을 만들고, 식탁에 오를 요리를 훑어보는 일이다. 이 문서는 각 단계에서 무엇을 쓰고, 어떤 명령을 쓰고, 어떤 결과가 나오는지 순서대로 정리한다.

---

## 1. 1단계: 비전으로 시작

출발점은 `docs/vision.md`의 짧은 비전이다. 일부러 작고 검토하기 쉽게 쓴다. 이 단계에는 슬래시 명령이 없다. 문제와 사용자에 대해 아는 것을 바탕으로 손으로 쓴다.

예제 시스템이 지원하는 흐름은 몇 가지뿐이다.

- 작업 만들기
- 작업 목록 보기
- 작업 완료하기
- 기본 검증과 상태 처리

완성된 제품으로 커지지 않으면서 아이디어에서 구현까지의 전체 순환을 보여 주기에 충분하다. 원서가 보여 주는 비전은 이런 내용이다. Simple Task Manager는 팀이 작업을 분명하고 통제된 방식으로 관리하도록 돕는 협업 웹 애플리케이션이며, 관찰 가능한 행동, 명확한 규칙, 요구사항에서 코드와 테스트까지의 추적성에 초점을 둔다. 스펙 주도 개발을 보여 주는 사례 연구로 쓰이고, 목표는 기능이 풍부한 것이 아니라 잘 명세된 것이다.

비전에는 비즈니스 목표도 들어간다. 팀이 작업을 만들고, 배정하고, 완료할 수 있게 한다. 사용자가 접근이 허용된 작업만 보고 바꾸게 한다. 명확한 작업 흐름과 비즈니스 규칙을 강제한다. 스펙, 구현, 테스트를 시간이 지나도 일관되게 유지한다.

1단계 결과는 `git checkout init`으로 본다. 그러면 Git이 'detached HEAD' 상태 안내를 출력한다. 브랜치 밖에서 둘러보는 상태이며, 거기서 한 커밋은 브랜치로 돌아가면 버려져도 브랜치에는 영향이 없다는 설명이다.

## 2. 2단계: 초기 요구사항

비전을 `docs/requirements.md`의 요구사항 카탈로그로 바꾼다. 책 전체의 관례가 그대로 적용된다.

| 접두사 | 뜻 |
|---|---|
| FR-### | 기능 요구사항 |
| NFR-### | 비기능 요구사항 |
| C-### | 제약 조건 |

이 시점의 요구사항은 상세한 상호작용 흐름이 아니라 의도를 담는다. 시스템이 무엇을 지원해야 하는지를 정하고, 그것이 어떻게 동작하는지는 나중의 유스케이스가 설명한다. 발췌 예는 ID, 제목, 사용자 스토리 세 열의 표이며 다음과 같다.

- FR-001 Create Task: 팀원으로서 팀의 작업 항목을 기록하려고 작업을 만들고 싶다.
- FR-002 Assign Task: 팀 리더로서 일이 분명하게 분배되도록 팀원에게 작업을 배정하고 싶다.
- FR-003 Complete Task: 팀원으로서 진행 상황이 팀에 보이도록 작업을 완료로 표시하고 싶다.

가볍지만 이미 버전 관리되고, 검토할 수 있고, 추적할 수 있다. AIUP 도구에서는 `/requirements` 명령이 비전을 바탕으로 초기 요구사항 집합을 제안한다. 결과는 여전히 사람이 검토해야 한다. 2단계 결과는 `git checkout requirements`로 본다.

## 3. 3단계: 엔터티 모델

요구사항이 갖춰지면 다음은 `docs/entity-model.md`의 엔터티 모델이다. 생성 명령은 원서 본문에 `/entity_model`로 적혀 있다.

참고(노트 작성자): 7장과 이 장의 다른 곳에서 코어 플러그인의 스킬 이름은 `entity-model`(하이픈)이다. 본문의 밑줄 표기 `/entity_model`은 Git 태그 이름 `entity_model`과 혼동된 표기로 보이나, 원서에 근거가 없어 확정할 수 없다. 표기가 다를 때는 설치된 스킬 이름을 따른다.

이 작은 프로젝트에서도 모델에는 나중에 마이그레이션, 유스케이스, 테스트에 필요한 개념이 이미 들어 있다. 엔터티는 네 개다.

- Team
- Task
- TeamMembership
- TaskAudit

예컨대 Task 엔터티의 속성은 id, team_id, title, description, status, assigned_to, created_by, created_at, updated_at이다.

원서가 강조하는 점은 엔터티 모델이 데이터베이스 밑그림 이상이라는 것이다. 시스템의 공유 어휘다. 여기서 정한 이름이 스펙, 스키마 변경, 코드, 테스트에서 그대로 쓰인다. 다음 단계에서 데이터베이스 스키마가 모델에서 합의되지 않은 개념을 지어내면 안 되기 때문에 이것이 중요하다. 3단계 결과는 `git checkout entity_model`로 본다.

## 4. 4단계: 유스케이스 다이어그램

상세 유스케이스를 쓰기 전에 높은 수준의 개요를 만들면 도움이 된다. 저장소에서는 `docs/use_cases.puml`의 PlantUML 다이어그램이다. 다이어그램의 목적은 두 가지다.

- 이해관계자에게 시스템 범위를 한눈에 보여 준다.
- 아직 상세 스펙이 필요한 유스케이스의 체크리스트가 된다.

명령은 `/use-case-diagram`이다. 출력은 원서의 그림 8-2와 비슷한 유스케이스 다이어그램이며, 그림은 싣지 않는다. 4단계 결과는 `git checkout use_cases_diagram`으로 본다.

## 5. 단계별 입력과 산출 정리

| 단계 | 입력 | 명령 | 산출물 |
|---|---|---|---|
| 1 | 문제와 사용자 지식 | 없음(손으로 작성) | docs/vision.md |
| 2 | 비전 | /requirements | docs/requirements.md |
| 3 | 요구사항 | /entity-model(본문 표기는 /entity_model) | docs/entity-model.md |
| 4 | 위 문서들 | /use-case-diagram | docs/use_cases.puml |

---

## 6. 핵심 정리

- 1~4단계는 코드 없이 `/docs`의 문서를 쌓는 단계이며, 앞 산출물이 뒤 산출물의 입력이 된다.
- 비전은 손으로 쓰고, 나머지는 슬래시 명령이 초안을 제안하되 결과는 사람이 검토한다.
- 요구사항은 FR, NFR, C 접두사로 의도를 담고, 상세 흐름은 유스케이스가 맡는다.
- 엔터티 모델은 Team, Task, TeamMembership, TaskAudit을 정의하는 공유 어휘로, 이후 모든 산출물이 이 이름을 쓴다.
- 유스케이스 다이어그램은 범위 그림이자 상세 스펙이 필요한 유스케이스의 체크리스트다.
