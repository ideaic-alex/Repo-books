# 요약과 핵심 개념

이 장은 네 덩어리로 이뤄진다. 환경과 도구 준비, 1~4단계의 스펙 문서 쌓기, 5~6단계의 기술 기반, 7~10단계의 첫 유스케이스에서 구현과 테스트를 파생하는 일이다. 마지막에 스펙을 먼저 바꾸는 반복이 붙는다. 이 문서는 전체를 한 번에 되짚고 핵심 용어를 정리한다.

원서의 요약은 이렇게 이어진다. 열 단계를 작지만 실제적인 프로젝트에서 따라갔고, Task Manager는 운영용이 아니라 학습용 샌드박스지만 비전에서 E2E 테스트까지 AIUP의 전체 순환을 보여 준다. `/docs` 폴더가 단일 진실 원천이다. 시스템 유스케이스는 하나의 문서에서 구현, 단위 테스트, E2E 테스트를 이끈다. 결과는 작고, 추적 가능하고, 문서화된 의도와 정렬된 통제된 진화다. 다음 장은 시스템이 커지고 여러 팀이 병렬로 일할 때를 다룬다.

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| /docs 폴더 | 시스템 행동의 권위 있는 설명. 단일 진실 원천이다 |
| Git 태그 | 열 단계 각각의 프로젝트 상태. `git checkout <태그>`로 확인 |
| 요구사항 카탈로그 | FR-###, NFR-###, C-###로 의도를 담은 목록(requirements.md) |
| 엔터티 모델 | 시스템의 공유 어휘. 스키마, 스펙, 코드, 테스트가 같은 이름을 쓴다 |
| 유스케이스 다이어그램 | PlantUML 개요도. 범위 그림이자 스펙 작성 체크리스트 |
| 스캐폴딩 | 스택별 생성기로 만든 초기 뼈대. 전용 슬래시 명령 없음 |
| Flyway 마이그레이션 | 엔터티 모델에서 파생한 버전 붙은 스키마 스크립트 |
| 시스템 유스케이스(UC-006) | 사전 조건, 번호 매긴 주 성공 시나리오, 대안 흐름, 사후 조건, 비즈니스 규칙, 요구사항 참조 |
| CLAUDE.md 가드레일 | 패키지 구조, 이름 규칙, 아키텍처 패턴을 정의해 에이전트가 따르게 하는 가이드라인 파일 |
| 브라우저리스 테스트 | 브라우저 없이 메모리에서 Vaadin 뷰를 검증하는 단위 테스트 |
| Playwright 테스트 | 실제 브라우저로 전체 스택을 검증하는 종단 간 테스트 |
| 스펙 먼저, 동기화 | 변경은 스펙부터, 이어서 마이그레이션, 구현, 테스트를 다시 생성한다 |

## 3. 자주 놓치는 점

- 슬래시 명령은 예시이며 프로세스가 특정 명령 이름에 의존하지 않는다. 비전과 스캐폴딩에는 명령이 없다.
- Docker가 꺼져 있으면 Testcontainers가 PostgreSQL을 못 띄워 연결 오류가 난다.
- 스택은 예시이며 다른 스택이어도 작업 흐름(스펙이 먼저)은 같다.
- 마이그레이션은 엔터티 모델에서 파생해야 한다. 모델에 없는 개념을 스키마가 지어내면 안 된다.
- 비즈니스 규칙만 바뀌었다면 마이그레이션 단계는 건너뛴다.
- 구현 명령을 다시 실행하면 처음부터가 아니라 기존 코드를 갱신된 스펙에 맞게 조정한다.
- 버그를 만나면 코드를 먼저 고치지 않고 스펙부터 확인한다. 스펙이 옳으면 구현을 재생성하고, 틀렸으면 스펙을 먼저 고친다.
- 추출본의 태그와 명령 표기에는 대소문자와 철자 깨짐이 있다(`spec_uC-006`, `/playwright_-est`, `/entity_model` 등). 각 문서의 참고 표시를 확인한다.
