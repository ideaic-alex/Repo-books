# 5~6단계 스캐폴딩과 DB 마이그레이션

스펙 문서가 갖춰지면 이제 기술적 출발점이 필요하다. 5단계에서 애플리케이션의 뼈대를 만들고, 6단계에서 엔터티 모델을 바탕으로 데이터베이스 스키마를 만든다. 두 단계의 성격은 대조적이다. 5단계는 스택에 강하게 의존해서 슬래시 명령이 없고, 6단계는 스펙에서 파생되는 단계라서 명령이 있다.

---

## 1. 5단계: 프로젝트 스캐폴딩

핵심 스펙이 자리를 잡았다. 비전은 목적을 설명하고, 요구사항은 기대하는 능력을 짚고, 엔터티 모델은 도메인에 대한 첫 공유 이해를 주고, 유스케이스 다이어그램은 주요 상호작용을 보여 준다. 아직 없는 것은 이 산출물들이 실행 가능해질 자리를 주는 애플리케이션 뼈대다. 이 단계는 그 초기 구조를 만들고, 이후 마이그레이션, 유스케이스 스펙, 구현, 테스트가 그것을 다듬는다.

### 1-1. 스택에 따라 달라지는 부트스트랩

부트스트랩(bootstrapping, 처음 구조를 세우는 일)의 방법은 선택한 기술 스택에 달려 있다. 이 사례는 Spring Boot, Vaadin, jOOQ를 쓰는데, 이것은 예제 전체에 쓰인 스택을 반영할 뿐 스펙 주도 개발의 일반 요구사항이 아니다. 다른 팀은 다른 구성을 쓸 수 있고, 작업 흐름은 같다. 스펙이 여전히 먼저 온다.

기본 Spring Boot 애플리케이션은 Spring Initializr로 만들 수 있다. 이 예제에서는 이 유형의 애플리케이션에 필요한 기본 구조를 이미 갖춘 템플릿에서 시작한다. UI는 Vaadin, 데이터베이스 접근은 jOOQ다. 장의 핵심에서 주의를 흩뜨리지 않으면서 동작하는 기준선을 준다.

### 1-2. 슬래시 명령이 없는 이유

AIUP 마켓플레이스에는 이 단계의 전용 슬래시 명령이 없다. 의도적이다. 프로젝트 부트스트랩은 스택 의존성이 강해서 선택한 생태계의 표준 생성기나 템플릿으로 처리하는 편이 낫다.

### 1-3. 완료의 기준

중요한 것은 결과가 집중되어 있고, 일관되고, 다음 단계에 쓸 준비가 되었다는 점이다. 부트스트랩이 끝나면 프로젝트는 성공적으로 빌드되어야 하고, 마이그레이션 추가, 유스케이스 구현, 테스트 파생의 기술적 토대가 되어야 한다. 원서의 표현으로 스캐폴드는 프로세스의 결과물이 아니라 진짜 일이 시작되게 하는 기초일 뿐이다.

원서는 8단계에서 CLAUDE.md의 가드레일이 스캐폴딩 단계에서 마련되었다고 말한다(8단계에서 다시 나온다). 이 가이드라인 파일에 패키지 구조, 이름 규칙, 아키텍처 패턴이 정의되어 있다고 읽힌다.

참고(노트 작성자): 이 절에서 CLAUDE.md가 스캐폴딩에서 만들어졌다는 서술은 원서 8단계의 "scaffolding step의 CLAUDE.md guardrails" 언급에서 가져온 것이다. 5단계 본문 자체는 CLAUDE.md를 직접 언급하지 않는다.

결과는 `git checkout scaffolding`으로 본다. 초기 부트스트랩 직후의 상태가 체크아웃되고, 다음 단계가 데이터베이스 마이그레이션을 더하며 스펙을 동작하는 시스템으로 바꾸기 시작한다.

## 2. 6단계: 데이터베이스 마이그레이션

어떤 유스케이스를 구현하기 전에 데이터베이스 스키마가 있어야 한다. 이 단계에서는 3단계의 엔터티 모델을 바탕으로 Flyway 마이그레이션 스크립트를 만든다. 쓰는 명령은 `/flyway-migration`이다.

### 2-1. 무엇이 만들어지나

마이그레이션 스크립트는 핵심 엔터티의 테이블을 만든다. 팀, 작업, 팀 멤버십, 작업 감사 기록이다. 각 스크립트는 `V002__create_team.sql`, `V003__create_team_membership.sql`처럼 버전이 붙어, 스키마가 통제되고 반복 가능한 방식으로 진화한다.

참고(노트 작성자): 원서는 V002부터 예시를 든다. V001의 내용은 말하지 않는다. 스캐폴딩 템플릿이 먼저 만든 것으로 짐작할 수 있으나 원서에 근거가 없어 확정하지 않는다.

### 2-2. 스펙 주도 단계라는 점

이것은 스펙 주도 단계다. 마이그레이션 스크립트는 임시방편으로 지어낸 것이 아니라 엔터티 모델에서 파생된다. 속성 이름, 타입, 관계가 `docs/entity-model.md`에 정의된 것과 일치한다.

### 2-3. Task 테이블 발췌

원서의 단순화한 발췌는 task 테이블이다. 핵심만 옮기면 다음과 같다.

```sql
create table task (
    id          bigint       not null primary key default nextval('task_seq'),
    team_id     bigint       not null,
    title       varchar(200) not null,
    description varchar(2000),
    status      varchar(20)  not null,
    assigned_to username,
    created_by  username     not null,
    created_at  timestamp    not null,
    updated_at  timestamp    not null,
    constraint ck_task_status
        check (status in ('DRAFT', 'OPEN', 'ASSIGNED', 'DONE'))
    -- 외래 키 3개: team(id), "user"(username) x2
);
```

위 코드는 지면 때문에 외래 키 제약 세 개를 주석으로 줄였다. 실제 발췌에서 `fk_task_team`은 team_id가 team(id)를 참조하게 하고, `fk_task_assigned_to`와 `fk_task_created_by`는 각각 assigned_to와 created_by가 "user" 테이블의 username을 참조하게 한다.

읽는 요령은 다음과 같다.

| 항목 | 값 |
|---|---|
| title 길이 | 최대 200자, 필수 |
| description 길이 | 최대 2000자, 선택 |
| status 허용 값 | DRAFT, OPEN, ASSIGNED, DONE |
| 기본 키 | task_seq 시퀀스 값을 기본으로 사용 |

참고(노트 작성자): assigned_to와 created_by의 타입 `username`은 원서에서 정의를 보여 주지 않는다. 사용자 이름을 담는 별도 타입(도메인)으로 보이나 확정할 수 없다.

작은 예제에서도 모델과 구현의 연결이 보인다. 엔터티 이름과 속성이 관계형 스키마로 곧바로 흘러 들어간다. 6단계 결과는 `git checkout database_migration`으로 본다.

---

## 3. 핵심 정리

- 5단계는 스택에 의존하는 부트스트랩이라 전용 슬래시 명령이 없다. 선택한 생태계의 생성기나 템플릿을 쓰며, 이 예제는 Spring Initializr 기반 템플릿에서 시작한다.
- 스캐폴드는 프로세스의 결과가 아니라 토대이며, 프로젝트가 빌드되면 끝난 것이다. 스택이 달라도 스펙이 먼저라는 작업 흐름은 같다.
- 6단계는 `/flyway-migration`으로 엔터티 모델에서 버전 붙은 마이그레이션을 파생한다. 팀, 작업, 팀 멤버십, 작업 감사 기록 테이블이 만들어진다.
- 스키마는 모델에 없는 개념을 지어내지 않고, 이름, 타입, 관계가 docs/entity-model.md와 일치한다.
