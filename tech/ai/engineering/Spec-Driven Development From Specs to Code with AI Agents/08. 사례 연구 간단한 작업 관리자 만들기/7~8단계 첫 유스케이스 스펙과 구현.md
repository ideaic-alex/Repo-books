# 7~8단계 첫 유스케이스 스펙과 구현

이 두 단계에서 작업 흐름이 "명세(Specify)"에서 "생성(Generate)"으로 넘어간다. 7단계에서 첫 시스템 유스케이스인 UC-006 View Team Tasks의 스펙을 쓰고, 8단계에서 그 스펙을 읽은 AI 에이전트가 실제 코드를 만든다. 코드는 스펙에서 파생되는 것이지 지어내는 것이 아니라는 원칙이 핵심이다.

---

## 1. 7단계: 첫 유스케이스 스펙 쓰기

프로젝트의 핵심은 `docs/use-cases/`에 있는 시스템 유스케이스로 정의된다. 저장소에서 이름 규칙을 볼 수 있다. 원서 예는 UC-006_View_Team_Tasks.md 형태이고 이런 식의 파일이 이어진다.

참고(노트 작성자): 원서 추출본은 파일명을 `UC- 006_View_Team_Tasks.md`처럼 공백이 낀 채 보여 준다. 줄바꿈 때문에 생긴 공백으로 보고 붙여서 적었다. 앞 문서의 저장소 구조에 보이는 `UC-001-create-task.md` 형식과도 구분자가 다르지만, 원서가 그렇게 보여 주므로 둘 다 그대로 적는다.

### 1-1. 유스케이스에 들어가는 것

각 시스템 유스케이스는 다음을 담는다.

- 사전 조건
- 번호가 붙은 단계의 주 성공 시나리오
- 명확한 발동 조건이 있는 대안 흐름
- 사후 조건
- 명시적 비즈니스 규칙
- 연결된 요구사항(FR, NFR, C)에 대한 참조

### 1-2. 왜 UC-006인가

이 실습은 UC-006: View Team Tasks로 시작한다. 전체 작업 흐름을 보여 주기에 충분히 단순하면서, 필터링, 데이터 표시, 역할 기반 동작을 보여 주기에 충분히 풍부해서 고른 유스케이스다.

### 1-3. 명령과 결과 구조

명령은 `/use-case-spec UC-006`이다. 이것은 유스케이스 템플릿을 담은 마켓플레이스 스킬의 호출이다. 원서의 압축 발췌는 이런 구조다.

- 개요: Use Case ID UC-006, 이름 View Team Tasks, 주 행위자 Team Member, 목표는 팀에 속한 모든 작업을 보고 팀의 업무량을 파악하는 것, 상태 Documented.
- 사전 조건: 사용자가 인증되어 있다.
- 주 성공 시나리오 여섯 단계(아래 표).
- 비즈니스 규칙 BR-001 Team Membership Required: 팀의 구성원인 사용자만 그 팀의 작업을 볼 수 있다.

| 단계 | 내용 |
|---|---|
| 1 | 사용자가 팀 작업 화면으로 이동한다 |
| 2 | 시스템이 사용자가 속한 팀을 판단한다 |
| 3 | 사용자가 정확히 한 팀에 속하면 시스템이 그 팀을 선택한다 |
| 4 | 여러 팀에 속하면 팀 선택기를 보여 주고 사용자가 팀을 고른다. 여러 팀이면 마지막으로 쓴 팀을 기본으로 선택한다 |
| 5 | 시스템이 선택된 팀의 작업을 가져온다 |
| 6 | 시스템이 작업 목록을 표시한다 |

이 발췌는 압축본이다. 이후 9단계 코드 주석에서 BR-002(All Team Tasks Visible)와 BR-003(Task List Ordering, updated_at 내림차순 정렬)이 함께 나오므로 전체 스펙에는 규칙이 더 있다고 볼 수 있다. 7단계 결과 전체는 `git checkout spec_UC-006`으로 본다.

## 2. 8단계: 유스케이스 구현

여기서 작업 흐름은 "명세"에서 "생성"으로 넘어간다. 7단계의 유스케이스 스펙이 동작하는 코드가 된다. AI 에이전트가 스펙을 읽고 필요한 구성 요소를 만든다. Vaadin 뷰, 서비스 클래스, jOOQ 쿼리, 번역이다.

### 2-1. 핵심 원칙

코드는 스펙에서 파생되는 것이지 지어내는 것이 아니다. 코드의 필드 이름, 검증 규칙, 흐름 단계가 유스케이스 문서에 정의된 것과 곧바로 대응한다. 스펙에 사용자가 상태로 작업을 걸러 볼 수 있다고 적혀 있으면 생성된 뷰에 상태 필터가 들어간다.

원서가 보여 주는 생성 UI 논리는 대략 이렇다.

```java
statusFilter.addValueChangeListener(event ->
    taskGrid.setItems(taskService.findTasks(teamId, event.getValue())));
```

상태 필터 값이 바뀌면 팀 ID와 선택한 상태로 서비스에서 작업을 찾아 그리드에 채운다는 뜻이다.

### 2-2. 가드레일의 효과

여기서 스캐폴딩 단계의 CLAUDE.md 가드레일이 빛을 발한다. AI 에이전트가 이미 정의된 패키지 구조, 이름 규칙, 아키텍처 패턴을 따르는 것은 그것들이 명시적으로 정의되어 있기 때문이다.

### 2-3. 명령과 결과

Vaadin, Spring Boot, jOOQ로 유스케이스를 구현하는 스킬은 `/implement UC-006`이다. 결과는 `git checkout implement_UC-006`으로 본다.

참고(노트 작성자): 원서는 이 단계가 만드는 파일 목록이나 서비스 클래스의 구체 이름을 보여 주지 않는다. 위 구성 요소(뷰, 서비스, jOOQ 쿼리, 번역)가 원서가 밝힌 전부다.

## 3. 7~8단계가 보여 주는 흐름

| 단계 | 입력 | 명령 | 산출물 |
|---|---|---|---|
| 7 | 요구사항, 엔터티 모델, 다이어그램 | /use-case-spec UC-006 | docs/use-cases의 UC-006 문서 |
| 8 | UC-006 스펙, CLAUDE.md | /implement UC-006 | Vaadin 뷰, 서비스, jOOQ 쿼리, 번역 |

---

## 4. 핵심 정리

- 시스템 유스케이스는 사전 조건, 번호 매긴 주 성공 시나리오, 발동 조건 있는 대안 흐름, 사후 조건, 비즈니스 규칙, 요구사항 참조로 이뤄진다.
- 첫 유스케이스 UC-006 View Team Tasks는 필터링, 데이터 표시, 역할 기반 동작을 보여 줄 만큼 풍부해서 골랐다. 주 성공 시나리오는 팀 판단, 단일 팀 자동 선택, 다중 팀 선택기(마지막 사용 팀 기본), 작업 조회와 표시의 여섯 단계다.
- 8단계에서 흐름이 명세에서 생성으로 넘어가며, 코드의 필드와 규칙, 흐름은 스펙에서 파생된다.
- CLAUDE.md 가드레일 덕분에 에이전트가 패키지 구조, 이름 규칙, 아키텍처 패턴을 따른다.
