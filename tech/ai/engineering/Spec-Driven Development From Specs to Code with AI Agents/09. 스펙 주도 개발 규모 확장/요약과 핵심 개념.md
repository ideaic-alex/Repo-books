# 요약과 핵심 개념

9장은 두 덩어리로 이뤄진다. 규모를 키울 때 병목이 요구공학으로 옮겨 가고, 팀은 작아지며, 경계 컨텍스트로 스펙을 작게 나눠 소유한다는 구조 이야기가 하나다. 다른 하나는 소수의 엄격한 규칙, 칸반 흐름, 스펙 파이프라인, 스펙 대시보드로 일관성과 진척을 관리하는 운영 이야기다. 이 문서는 두 덩어리를 한 번에 되짚고 핵심 용어를 정리한다.

원서의 장 요약은 네 가지로 모인다. 한계 요인은 코딩 속도가 아니라 동작을 명확히 정의하는 능력이고, 경계 컨텍스트가 확장을 다룰 만하게 하며, 엔지니어의 시간은 번역에서 명확화와 검토와 경계 보호로 옮겨 가고, 거버넌스는 소수 규칙의 일관된 적용으로 충분하다.

---

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | 병목의 이동 | 코딩 속도에서 의도의 명확성으로. 요구사항 빈틈이 즉시 틀린 구현으로 드러남 |
| 2 | 요구공학과 팀 크기 | 요구공학은 AI가 대신 못 하는 일. 모호성이 줄어 최적 팀 규모가 작아짐 |
| 3 | 경계 컨텍스트와 소유 | 컨텍스트별 스펙 코어, 명시적 계약, 비즈니스 역량 단위 팀 소유 |
| 4 | 엔지니어의 일과 병렬 개발 | 명확화, 정제, diff 검토, 경계 보호. 팀 간 충돌 없는 병렬 |
| 5 | 거버넌스 | 네 가지 원칙을 버전 관리되는 가이드라인 파일에 명시 |
| 6 | 흐름과 파이프라인 | 유스케이스 단위 칸반, 컨텍스트별 파이프라인과 독립 배포 |
| 7 | 스펙 대시보드 | 요구사항과 유스케이스 단위로 상태, 커버리지, 회귀 안정성을 추적 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 새로운 병목 | AI가 구현을 가속한 뒤 속도를 제한하는 요구공학, 곧 명확하고 완전하고 일관된 스펙을 만드는 속도 |
| 요구공학 | 시스템이 해야 할 일을 이해하고, 명시하고, 진화하는 동안 일관되게 유지하는 일 |
| 바운디드 컨텍스트(경계 컨텍스트) | 자기 요구사항 카탈로그, 엔터티 모델, 유스케이스, 버전 이력, 아키텍처 책임을 가진 구획된 비즈니스 역량. DDD에서 유래 |
| 자기완결 시스템 | 각 컨텍스트가 자기 UI, 로직, 데이터를 소유하고 독립 진화하는 아키텍처 |
| 경계 있는 소유 | 팀이 모놀리스 일부가 아니라 비즈니스 역량과 스펙 코어 전체를 책임지는 구조 |
| 거버넌스 네 원칙 | 스펙 먼저 갱신, 식별자 재사용 금지, 관찰 가능한 동작만 서술, 컨텍스트별 스펙 코어 소유 |
| 칸반 흐름 | 유스케이스 하나가 Draft, Review, Approved, Implemented, Verified, Deployed를 지나는 연속 흐름 |
| 스펙 파이프라인 | 커밋마다 단위, E2E, 회귀 테스트로 동작과 스펙의 일치를 검증하고 어긋난 유스케이스를 지목 |
| 스펙 대시보드 | 저장소 안 Markdown으로 유지하는 동작 중심 진척 표 |
| 회귀 | 이전에 구현된 동작이 의도치 않게 깨지는 것 |

## 3. 자주 놓치는 점

- 팀 규모 축소는 AI만의 효과가 아니다. 경계 컨텍스트와 경계 있는 소유가 뒷받침해야 하며, 아키텍처가 받쳐 주지 않으면 통하지 않는다.
- 컨텍스트를 나눈다고 요구공학이 사라지지 않는다. 컨텍스트 사이의 가로지르는 관심사(예: 주문 관리와 청구의 모순)를 찾아 푸는 일은 더 구조화될 뿐 계속된다.
- 컨텍스트 사이 통합은 이벤트, API, 공유 식별자 같은 명시적 계약이다. 숨은 데이터베이스 결합은 허용되지 않는다.
- 스프린트를 전면 부정하는 것은 아니다. 스크럼에서 남길 것은 정기적 이해관계자 협업이며, 짧은 주간 또는 격주 정제 세션으로 충분하다.
- 커버리지는 코드 줄 수가 아니라 구조적 완결성이다. 요구사항은 승인되고 구현되고 검증된 유스케이스에 연결되어야 완료다.
- 티켓을 닫았다는 것은 완료가 아니다. 의도가 검토된 유스케이스로 표현되고, 구현되고, 파생 테스트가 검증해야 한다.
- 대시보드의 숫자는 원서의 예시이며 실제 프로젝트의 기준값이 아니다.
