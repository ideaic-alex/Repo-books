# 스펙 주도 개발 규모 확장

9장은 스펙 주도 개발이 개인과 소규모 팀을 넘어 여러 팀과 큰 시스템으로 커질 때 무엇을 해야 하는지를 다룬다. AI가 구현을 빠르게 하면 병목은 요구공학으로 옮겨 가고, 이를 다루는 구조적 수단은 경계 컨텍스트(바운디드 컨텍스트)다. 거버넌스, 칸반 흐름, 스펙 파이프라인, 스펙 대시보드가 이를 운영 수준에서 뒷받침한다.

---

## 1. 핵심 요점

- 규모를 키우면 병목이 코딩 속도에서 의도의 명확성, 곧 요구공학으로 옮겨 간다. AI는 구현 완충 장치를 없애 요구사항의 빈틈이 바로 틀린 구현으로 드러나게 한다.
- 모호성을 메우던 큰 팀이 필요 없어져 최적 팀 규모가 줄어든다. 단, 이는 아키텍처가 뒷받침할 때만 성립한다.
- 경계 컨텍스트는 요구사항 카탈로그, 엔터티 모델, 유스케이스, 버전 이력, 아키텍처 책임을 각자 소유한다. 컨텍스트 사이는 이벤트, API, 공유 식별자 같은 명시적 계약으로만 잇는다.
- 팀은 모놀리스 일부가 아니라 비즈니스 역량을 소유하며, 스펙팀, 코딩팀, 테스트팀으로 나누지 않는다. 엔지니어는 명확화, 유스케이스 정제, AI diff 검토, 경계 보호에 더 시간을 쓴다.
- 거버넌스는 가볍지만 엄격하다. 스펙 먼저 갱신, 식별자 재사용 금지, 관찰 가능한 동작만 서술, 컨텍스트별 스펙 코어 소유의 네 원칙을 가이드라인 파일에 둔다.
- 스프린트보다 유스케이스 단위 칸반이 맞다(Draft, Review, Approved, Implemented, Verified, Deployed). 컨텍스트마다 파이프라인이 있어 독립 배포한다.
- 진척은 닫힌 티켓이 아니라 동작의 수준에서 잰다. 저장소 안 Markdown 스펙 대시보드가 요구사항과 유스케이스의 완료, 커버리지, 회귀 안정성을 보여 준다.
