# 요약과 핵심 개념

1장은 세 덩어리로 이뤄진다. 코드 우선 개발이 왜 시스템을 이해하기 어렵게 만드는지, 스펙 주도 개발이 순서를 어떻게 뒤집는지, 그리고 스펙을 진실의 원천으로 삼을 때 얻는 효과와 그에 대한 오해다. 이 문서는 세 덩어리를 한 번에 되짚고 핵심 용어를 정리한다.

원서의 장 요약은 이렇게 이어진다. 코드 우선은 취약한 시스템을 낳고, 스펙 주도 개발은 스펙을 중심에 둔다. AI 덕분에 실행 가능한 스펙이 현실적이 되었고 그 결과 비즈니스 정렬, 유지보수성, 효율이 좋아진다. 다음 장은 AI 통합 프로세스를 소개한다.

---

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | 발코니 아키텍처와 바이브 코딩 경험 | 코드만으로는 의도와 이유를 알 수 없고, 코드는 진실이 아니라 결정의 결과물이라는 문제의식 |
| 2 | 코드 우선의 문제 | 문서 노후, 숨은 규칙, 베테랑 의존, 신입 적응 지연 |
| 3 | 스펙 주도의 의미 | 스펙이 계약이고 코드, 테스트, 문서가 따라온다. 로그인 예로 확인 |
| 4 | 요구사항에서 유스케이스로, 애자일이 남긴 것 | 사용자 스토리는 의도, 유스케이스는 동작. 흩어진 의도를 Git의 스펙으로 모음 |
| 5 | 왜 지금인가 | 모델 주도 개발의 실패 이유와 AI 시대의 달라진 조건 |
| 6 | 진실의 원천, 이점, 오해 | 여섯 가지 이점과 세 가지 오해의 반박 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 발코니 아키텍처 | 빠른 수정과 급한 기능이 쌓여 원래 구조가 보이지 않게 된 코드 |
| 바이브 코딩 | AI에게 코드 조각을 묻고 기능을 빠르게 만들지만 전체 개요와 이유가 사라지는 방식 |
| 코드 우선 | IDE를 열고 코드부터 쓰며 문서와 테스트는 나중에 붙이는 방식 |
| 스펙 주도 개발 | 의도한 동작을 스펙으로 먼저 쓰고 코드, 테스트, 문서를 거기서 이끌어 내는 방식 |
| AI 통합 프로세스(AIUP) | 저자가 만든 스펙 주도 개발의 실용적 틀. 가벼운 산출물 세 가지를 쓴다 |
| 요구사항 카탈로그 | 기능 요구사항, 비기능 요구사항, 제약을 담은 목록 |
| 엔터티 모델 | 핵심 도메인 개념과 관계. 공통 어휘(용어집)이기도 하다 |
| 시스템 유스케이스 | 행위자와 시스템의 상호작용을 단계, 대안, 실패까지 쓴 관찰 가능한 동작 서술. 핵심 실행 가능한 계약 |
| 진실의 원천 | 스펙이 중앙에서 다른 산출물을 이끌고, 피드백은 스펙 수정으로 반영되는 구조 |
| 살아 있는 문서 | 스펙에서 파생되므로 설계상 최신인 문서 |

## 3. 자주 놓치는 점

- 스펙 주도 개발은 피드백을 막지 않는다. 코드나 테스트에서 나온 피드백은 스펙을 고치는 쪽으로 흘러야 하고, 스펙이 항상 권위 있는 기준으로 남는다.
- 사용자 스토리를 버리는 것이 아니다. 사용자 스토리는 의도를 표현하고, 유스케이스가 그 의도를 관찰 가능한 동작으로 옮긴다.
- 스펙 작성은 새 일이 아니라 이미 다른 곳(회의, 디버깅, 반복 설명)에 쓰던 노력을 앞으로 옮기는 것이다.
- 모델 주도 개발이 실패한 이유는 목표가 아니라 방법이었다. 복잡한 표기법, 무거운 도구, 한꺼번에 도입해야 하는 부담, 마지막 20%의 수작업이 문제였다. AI 통합 프로세스는 Markdown과 점진적 도입으로 이를 피한다.
- 스펙이 현대화의 자산인 이유는 기술과 무관하게 비즈니스 지식을 담기 때문이다. 구현은 바뀌어도 스펙은 안정적이다.
- AI는 모호한 요구도 자신 있게 코드로 만든다. 그래서 속도가 오를수록 명확한 스펙이 더 필요하다.
