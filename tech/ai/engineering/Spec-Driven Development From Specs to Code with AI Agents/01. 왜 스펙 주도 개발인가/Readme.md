# 왜 스펙 주도 개발인가

1장은 스펙 주도 개발이 왜 필요한지를 묻는다. 코드 우선 방식으로 만든 시스템은 이해하고 고치고 현대화하기가 어렵다는 점에서 출발해, 스펙을 실행 가능한 계약으로 삼아 비즈니스와 IT 사이의 명확성을 되찾는다는 생각을 소개한다. 저자의 바이브 코딩 실패 경험과 AI 통합 프로세스가 태어난 배경도 함께 나온다.

---

## 1. 핵심 요점

- 오래된 코드는 발코니를 계속 덧댄 건물과 같아서 원래 의도와 결정의 이유가 보이지 않는다. 그 지식은 기억이나 주석이 아니라 스펙에 있어야 한다.
- 저자는 바이브 코딩으로 자원봉사자 관리 시스템을 만들다 전체 조망을 잃었고, 모든 것을 버리고 스펙부터 다시 시작하면서 AI 통합 프로세스를 만들었다.
- AI 통합 프로세스는 요구사항 카탈로그, 엔터티 모델, 시스템 유스케이스라는 가벼운 산출물 세 가지를 쓰고 모두 버전 관리한다.
- 코드 우선은 문서 노후, 숨은 규칙, 베테랑 의존, 신입 적응 지연을 낳는다.
- 스펙 주도 개발에서는 스펙이 계약이며, 코드와 테스트와 문서가 그것을 따른다. 사용자 스토리는 의도를, 시스템 유스케이스는 동작을 담는다.
- 모델 주도 개발은 복잡한 표기법과 마지막 20%의 수작업 때문에 실패했지만, AI가 구조화된 자연어를 이해하게 되면서 Markdown 스펙이 현실적이 되었다.
- 이점은 비즈니스 정렬, 재작업 감소, 유지보수성, 살아 있는 문서, 효율, 현대화 대비 여섯 가지다. 오해(느리다, 그냥 문서다, 시간이 없다)는 모두 일을 앞당길 뿐이라는 점에서 반박된다.
