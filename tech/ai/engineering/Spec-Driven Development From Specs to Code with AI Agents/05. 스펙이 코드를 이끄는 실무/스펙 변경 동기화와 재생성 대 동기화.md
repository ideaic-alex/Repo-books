# 스펙 변경 동기화와 재생성 대 동기화

첫 구현은 시작일 뿐이다. 실제 소프트웨어 작업의 대부분은 나중에 동작이 바뀔 때 일어난다. 5장은 UC-012의 비즈니스 규칙이 바뀌는 사례로, 스펙을 먼저 고치고 코드를 그 뒤에 맞추는 방법을 보여 준다. 그리고 여기서 중요한 구분이 나온다. 코드를 처음부터 다시 만드는 재생성(regeneration)과, 바뀐 동작만 반영하는 동기화(synchronization)다.

옷 수선에 비유하면, 소매 길이만 바꾸고 싶은데 옷 전체를 새로 짓는 것이 재생성이고, 소매 부분만 고치는 것이 동기화다. 새 옷이 필요하면 새로 짓는 편이 낫고, 잘 맞는 옷의 소매만 문제라면 수선이 맞다.

---

## 1. 변경 사례: 팀 리드의 예외

원래 UC-012는 활성 사용자만 작업을 받도록 했다. 옛 비즈니스 규칙은 이랬다.

- BR-012-1: 활성 사용자만 작업을 받을 수 있다.

나중에 비즈니스가 팀 리드(Team Lead)는 특별한 경우에 비활성 사용자에게도 작업을 할당할 수 있다고 결정한다. 이때 순서가 중요하다. 먼저 유스케이스를 고친다.

### 1-1. 스펙의 수정 내용

| 항목 | 수정 후 |
|---|---|
| BR-012-1 | 활성 사용자는 작업을 받을 수 있다 |
| BR-012-2 | 비활성 사용자는 할당하는 사용자가 Team Lead 역할일 때만 작업을 받을 수 있다 |
| A1 | 대상 사용자가 비활성이고 할당자가 Team Lead가 아님: 시스템이 할당을 거부하고, 비활성 사용자는 팀 리드에게서만 작업을 받을 수 있다고 표시하며, 작업은 변경 없음 |
| A2 | 대상 사용자가 비활성이고 할당자가 Team Lead임: 시스템이 할당을 허용하고, 팀 리드가 할당했음을 기록하며, 작업이 할당되었음을 확인해 줌 |

A1과 A2는 둘 다 "대상 사용자가 비활성"을 트리거로 쓰되, 할당자의 역할 조건을 하나 더 붙여 서로 겹치지 않게 갈라 놓았다. 트리거 조건이 두 개씩인 점이 4장에서 말한 명시적 규칙의 사례다.

참고(노트 작성자): 앞서 소개한 UC-012의 BR-012-2는 "할당된 작업은 담당자가 정확히 한 명"이었는데, 이 변경 사례에서는 같은 번호 BR-012-2가 팀 리드 규칙을 가리킨다. 원서는 이 번호 재사용에 대해 따로 설명하지 않는다. 변경 사례만의 별도 서술로 읽는 것이 안전하다.

## 2. 스펙을 먼저 고치고 검토한 뒤에 구현을 바꾼다

원서의 순서는 분명하다. 이 스펙 변경이 이루어지고 검토된 뒤에만 구현을 바꾼다. 그다음 개발자가 에이전트에게 코드를 동기화하라고 요청한다. 원서가 이 장면에서 보이는 명령은 앞서 처음 구현할 때와 같은 `/implement UC-012`다.

참고(노트 작성자): 5장 앞부분에는 변경 후 요청이 "갱신된 UC-012에 맞춰 구현을 동기화해 줘"로 나오지만, 이 대목의 명령은 첫 구현과 똑같이 적혀 있다. 원서는 명령 이름이 중요하지 않다고 했고, 구분은 명령이 아니라 에이전트가 이전 버전과 현재 버전을 비교하는 방식에서 생긴다고 읽을 수 있다. 이 해석은 노트 작성자의 것이다.

## 3. 동기화는 재생성과 다르다

- 재생성: 구현을 처음부터 다시 만든다. 보통 큰 diff가 나온다. 기존 구조가 다시 쓰이고, 직접 한 리팩터링이 사라질 수 있다. diff에 무관한 변경이 너무 많아 리뷰가 어려워진다.
- 동기화: 갱신된 유스케이스가 기술하는 행동 변화만 적용한다.

### 3-1. 에이전트가 하는 동기화

에이전트는 UC-012의 이전 버전과 현재 버전을 비교한다. 할당 규칙이 바뀐 것을 확인하고, 영향받는 부분만 고친다.

- 검증 로직
- 역할 확인
- UI 피드백 메시지
- 비활성 사용자 테스트
- 갱신된 사후 조건이 요구한다면 감사 로그(audit logging)

나머지는 그대로 두어야 한다. 책은 이것을 스펙 주도 개발의 가장 중요한 실무 이점 중 하나로 꼽는다. 스펙 변경이 작고 검토 가능한 구현 변경을 만든다.

## 4. 재생성 대 동기화 선택표

원서는 상황별로 어느 쪽이 나은지 표로 정리한다.

| 상황 | 더 나은 접근 | 이유 |
|---|---|---|
| 기존 구현이 없는 새 유스케이스 | 생성 | 보존할 기존 코드가 없다 |
| 기존 유스케이스의 작은 동작 변경 | 동기화 | 영향받는 동작만 바뀌어야 한다 |
| 엔터티 모델에 필드 하나 추가 | 동기화 | 기존 구조가 안정적으로 남아야 한다 |
| 버릴 프로토타입 | 재생성 | 장기 보존이 중요하지 않다 |
| 운영 중인 기능의 수정 | 동기화 | 리뷰 가능성과 안전이 중요하다 |
| 큰 아키텍처 재편 | 신중히 재생성 | 일반적 변경이 아니라 의도된 이전(migration)이다 |

오래 사는 시스템에서는 동기화가 대체로 더 안전한 기본값이다. 기존 설계 결정을 지키고 diff를 작게 유지한다.

### 4-1. AI가 있을 때 더 중요한 이유

AI는 아주 많은 코드를 아주 빠르게 만들 수 있다. 동기화 규율이 없으면 작은 동작 변경이 큰 재작성이 될 수 있다. 그러면 리뷰가 어려워지고 의도하지 않은 표류(drift)의 위험이 커진다. 앞의 가이드라인 파일 예제에 "유스케이스를 동기화할 때 기존 코드를 재생성하지 않는다"와 "변경을 요청된 유스케이스의 범위에 한정한다"가 들어 있던 이유가 여기서 드러난다.

## 5. 핵심 정리

- 첫 구현은 시작일 뿐이고 대부분의 작업은 이후 동작이 바뀔 때 일어난다. 변경은 스펙부터 고치고 검토한 뒤 구현한다.
- UC-012의 예: BR-012-1과 팀 리드 규칙으로 규칙이 바뀌고, A1(팀 리드 아님은 거부)과 A2(팀 리드는 허용하고 기록)로 갈라진다.
- 재생성은 처음부터 다시 만들어 큰 diff와 리팩터링 손실을 부르고, 동기화는 바뀐 동작에 해당하는 부분만 반영한다.
- 에이전트는 이전과 현재의 UC-012를 비교해 검증, 역할 확인, UI 메시지, 비활성 사용자 테스트, 필요하면 감사 로그만 고친다.
- 새 유스케이스와 버릴 프로토타입은 생성/재생성, 작은 변경과 운영 기능 수정은 동기화, 큰 아키텍처 재편은 신중한 재생성이다.
