# 테스트, 검토, 사람의 책임, 전체 변경 흐름

구현과 동기화를 다루었다면, 이제 나머지 퍼즐 조각이 남는다. 테스트는 어디서 나오는가, 사람은 무엇을 검토하는가, AI가 있어도 사람의 책임은 어떻게 남는가, 그리고 이 모든 것이 하루의 작업 리듬으로 어떻게 이어지는가. 이 문서는 5장의 후반부와 장의 핵심 정리를 다룬다.

시험 출제에 비유하면, 교과서(유스케이스)에서 학습 내용(코드)과 시험 문제(테스트)가 모두 나온다. 채점자(리뷰어)는 학생의 답안(코드)이 교과서와 맞는지를 보고, 교과서 자체가 틀리지 않았는지는 교사(사람)가 책임진다.

---

## 1. 테스트도 같은 유스케이스를 따른다

테스트에 대한 본격 논의는 다음 장(6장)에 있지만 연결만큼은 여기서 짚는다. UC-012를 구현할 때 테스트도 같은 유스케이스에서 도출해야 한다.

- 주 성공 시나리오는 정상 경로 테스트가 된다.
- 대안 흐름은 추가 테스트 시나리오가 된다.
- 비즈니스 규칙은 단언이 된다.

### 1-1. 규칙 변경 전후의 테스트

| 시점 | 테스트 항목 |
|---|---|
| UC-012 첫 버전 | 열린 작업을 활성 사용자에게 할당하면 성공한다 |
| 〃 | 비활성 사용자에게 할당하면 실패한다 |
| 〃 | 실패한 할당은 작업을 변경하지 않는다 |
| 〃 | 성공한 할당은 작업 상태를 ASSIGNED로 바꾼다 |
| 규칙 변경 후 | 일반 사용자가 비활성 사용자를 지정하면 실패한다 |
| 〃 | 팀 리드가 비활성 사용자를 지정하면 성공한다 |
| 〃 | 실패한 할당은 여전히 작업을 변경하지 않는다 |
| 〃 | 유스케이스가 요구하면 팀 리드의 할당이 기록된다 |

테스트는 독립적으로 발명되지 않는다. 같은 행동 계약의 검증 관점(verification view)이다. 그래서 코드와 테스트가 스펙과 정렬되고, 나중에 다른 유스케이스가 바뀔 때 팀이 회귀(regression) 방지를 얻는다.

## 2. 스펙과 코드를 함께 검토하기

사람의 검토는 여전히 필수다. AI는 구현 코드를 생성하고, 테스트를 갱신하고, 프로젝트 규칙을 따를 수 있다. 하지만 비즈니스 정확성에 책임질 수는 없다. 리뷰어는 두 가지를 확인해야 한다.

첫째, 스펙이 맞아야 한다. 유스케이스가 의도한 동작을 기술하는가? 규칙이 명시적인가? 대안이 분명한가? 사후 조건이 충분히 강한가?

둘째, 구현이 스펙과 맞아야 한다. 생성된 코드는 유스케이스가 말하는 것을 하되, 그보다 많지도 적지도 않아야 한다.

### 2-1. UC-012의 리뷰 질문

- 코드는 열려 있고 미할당인 작업만 할당하는가?
- 현재 규칙에 따라 비활성 사용자를 거부하는가?
- 할당이 실패하면 작업을 그대로 보존하는가?
- UI가 올바른 피드백을 보여 주는가?
- 테스트가 주 성공 시나리오와 대안 흐름을 다루는가?
- 의미 있는 모든 변경이 유스케이스로 거슬러 추적되는가?

이 리뷰 방식은 대화를 바꾼다. 코드가 "좋아 보이는가"를 묻는 대신, 코드가 승인된 동작을 충족하는지를 묻는다. 책은 이것이 훨씬 강한 질문이라고 말한다.

## 3. 사람의 책임은 사라지지 않는다

AI와 함께하는 스펙 주도 개발은 개발자를 과정에서 빼지 않는다. 그들의 판단이 가장 중요해지는 곳을 바꾼다. 개발자와 아키텍트의 일은 다음과 같다.

- 경계를 정의한다.
- 스펙을 쓰고 검토한다.
- 어떤 동작이 올바른지 결정한다.
- 프로젝트 규칙을 정의한다.
- 생성된 diff를 검토한다.
- 구현이 이해 가능하고 유지보수 가능한 상태로 남도록 한다.

AI는 스펙에서 코드와 테스트로 가는 기계적인 번역을 돕는다. 번역 작업은 반복적이고 실수하기 쉬워서 이 도움은 값지다. 하지만 의미에 대한 책임은 사람에게 남는다. 가장 중요한 결정은 과정의 앞쪽으로 이동한다. 유스케이스를 쓰고, 검토하고, 승인하는 때가 그 시점이고, 모호함을 가장 싸게 고칠 수 있는 곳이다. 스펙이 틀리면 AI는 틀린 것을 빠르게 구현하고, 스펙이 명확하면 AI는 일관되게 구현하도록 도울 수 있다.

## 4. 전체 변경 흐름

원서의 그림 5-2는 새 유스케이스의 전체 흐름을, 그림 5-3은 기존 유스케이스의 동기화 흐름을 보여 준다. 기존 유스케이스에서는 흐름이 비슷하되 초점이 동기화에 있다. 그림은 싣지 않고, 본문이 장 전체에서 설명한 순서를 글로 풀면 다음과 같다.

| 단계 | 새 유스케이스 | 기존 유스케이스 |
|---|---|---|
| 1 | 유스케이스를 쓰고 검토, 승인한다 | 유스케이스를 먼저 고치고 검토한다 |
| 2 | 에이전트에게 구현을 요청한다 | 에이전트에게 동기화를 요청한다 |
| 3 | 에이전트가 유스케이스, 가이드라인, 기존 코드, 기술 맥락으로 코드와 테스트를 만든다 | 에이전트가 이전과 현재 버전을 비교해 영향받는 부분만 고친다 |
| 4 | 풀 리퀘스트에서 스펙을 먼저, 구현을 나중에 검토한다 | 같은 순서로 검토한다 |

참고(노트 작성자): 그림 5-2와 5-3의 내부 글자는 추출본에서 확인되지 않았다. 위 표는 그림이 아니라 본문의 서술(구현 요청, 에이전트가 읽는 자료, 풀 리퀘스트 검토 순서, 동기화 설명)을 모아 노트 작성자가 정리한 것이어서 그림의 칸 이름과 다를 수 있다.

이것이 AIUP의 일상적인 리듬이다. 스펙이 먼저 바뀌고, 코드와 테스트가 뒤따르며, 리뷰가 순환을 안전하게 지킨다.

## 5. 장의 핵심 정리(원서의 Key Takeaways)

- 스펙은 개발을 능동적으로 이끌 때 가치가 생긴다. 시스템 유스케이스는 문서가 아니라 구현과 변경의 출발점이다.
- 개발자는 AI에게 막연한 개선을 요청하지 않고 UC-012처럼 특정 유스케이스를 가리켜 구현이나 동기화를 요청한다.
- 에이전트는 유스케이스만이 아니라 연결된 요구사항, 엔터티 모델, 가이드라인 파일, 기존 코드, MCP 서버 같은 도구의 기술 맥락을 함께 쓴다.
- 유스케이스 요소는 코드로 자연스럽게 대응한다. 사전 조건은 확인, 주 흐름은 정상 경로 구현, 대안 흐름은 분기와 검증, 사후 조건은 기대 결과, 비즈니스 규칙은 명시적 로직과 단언이다.
- 가이드라인 파일은 실행 가능한 프로젝트 기억이고, 스킬과 플러그인은 AI 상호작용을 반복 가능하게 하며, 방법론은 기술이 바뀌어도 안정적이다.
- 동기화는 재생성과 다르다. 새 유스케이스는 처음부터 생성해도 되지만 기존 동작은 대개 동기화해야 diff가 작고 설계 결정이 보존되며 리뷰가 안전하다.
- 버전 관리는 안전망이고, 사람의 검토는 필수다. AI는 명확한 스펙을 코드와 테스트로 옮기지만 동작이 비즈니스에 옳은지는 팀의 책임이다.

다음 장은 같은 원리를 테스트에 적용한다고 예고한다. 구현을 이끄는 같은 시스템 유스케이스가 검증도 이끌며, 코드는 유스케이스의 구현 관점이고 테스트는 검증 관점이라는 것이다.
