# 가이드라인 파일, 스킬, 플러그인, MCP 서버, 버전 관리

유스케이스는 시스템이 무엇을 해야 하는지를 정한다. 하지만 에이전트는 이 프로젝트가 어떻게 만들어지는지도 알아야 하고, 쓰는 프레임워크의 현재 API가 어떤지도 알아야 하며, 결과가 안전하게 검토되는 장소도 필요하다. 5장은 이 필요를 채우는 다섯 가지 장치를 소개한다. 가이드라인 파일(guideline file), 스킬(skill), 플러그인(plugin), MCP 서버(Model Context Protocol server), 그리고 버전 관리다.

공사 현장에 비유하면, 유스케이스는 설계 도면, 가이드라인 파일은 현장 규칙집, 스킬은 반복 작업의 작업 지침서, 플러그인은 특정 공법(예: 목조, 철골)에 맞춘 도구 세트, MCP 서버는 최신 자재 규격을 찾아보는 카탈로그, 버전 관리는 언제든 되돌릴 수 있는 시공 기록이다.

---

## 1. 가이드라인 파일은 프로젝트의 기억

유스케이스는 무엇을 할지를 정한다. 에이전트는 이 프로젝트가 어떻게 만들어지는지도 알아야 한다. 그 정보는 저장소 루트의 CLAUDE.md나 AGENTS.md 같은 가이드라인 파일에 둔다. 책의 예제 스택에서는 이런 규칙이 들어갈 수 있다.

```text
# Project Guidelines
- Java, Spring Boot, Vaadin, jOOQ, PostgreSQL을 쓴다.
- 비즈니스 로직은 애플리케이션 서비스에 구현한다.
- Vaadin 뷰에 SQL 쿼리를 넣지 않는다.
- 데이터베이스 접근에는 jOOQ를 쓴다.
- Vaadin 뷰는 얇게 유지한다.
- 생성하는 테스트에 유스케이스 ID를 참조한다.
- 유스케이스를 동기화할 때 기존 코드를 재생성하지 않는다.
- 변경을 요청된 유스케이스의 범위에 한정한다.
```

이 규칙은 UC-012에 들어가지 않는다. 작업 할당에만 해당하지 않고 프로젝트 전반에 적용되기 때문이다. 가이드라인 파일은 실행 가능한 프로젝트 기억(executable project memory)으로 작동한다. 모든 작업에서 지켜야 할 안정적인 규칙을 에이전트에게 주어, 같은 아키텍처 결정을 프롬프트마다 되풀이하지 않게 한다.

### 1-1. 짧게 유지하고 Git에 둔다

- 파일은 짧아야 한다. 너무 크면 에이전트가 요청마다 너무 많은 정보를 처리해야 하고, 사람이 검토하고 유지하기도 어려워진다.
- 특정 워크플로에만 해당하는 규칙은 전역 가이드라인 파일이 아니라 스킬이나 작업별 지시에 둔다.
- Git에 저장되므로 변경이 눈에 보인다. 팀이 아키텍처 규칙을 바꾸면 다른 중요한 프로젝트 변경과 똑같이 검토된다.

## 2. 스킬과 플러그인은 반복 가능한 워크플로

`/implement UC-012`라는 명령은 더 예쁜 프롬프트가 아니다. 반복 가능한 워크플로를 나타낸다. 명령 뒤에는 스킬이 있다. 스킬은 에이전트에게 특정 종류의 일을 어떻게 하는지 알려 주는 재사용 가능한 능력이다. 원서가 드는 예는 다음과 같다.

- 요구사항을 시스템 유스케이스로 확장하기
- 유스케이스 구현하기
- 엔터티 모델 변경에서 Flyway 마이그레이션 생성하기
- 유스케이스 흐름에서 Karibu 테스트 도출하기
- 끝에서 끝까지(end-to-end) 시나리오용 Playwright 테스트 만들기

스킬은 AI 상호작용에 구조를 준다. 에이전트가 무엇을 읽고, 무엇을 만들고, 어떤 제약을 지킬지를 정의한다.

참고(노트 작성자): Flyway는 데이터베이스 스키마 마이그레이션 도구, Karibu는 Vaadin 뷰를 서버 쪽에서 테스트하는 라이브러리, Playwright는 브라우저 기반 종단 간 테스트 도구다. 원서는 이름만 나열하며, 이 한 줄 풀이는 노트 작성자가 보탠 것이다.

### 2-1. 플러그인은 스택에 맞추는 장치

플러그인은 이 구조를 특정 기술 스택에 맞게 만든다. AIUP 자체는 Java, Vaadin, jOOQ, Spring Boot에 의존하지 않는다. 그것들은 구현 선택이다. 스택 플러그인이 일반적인 프로세스를 구체적인 기술 스택에 이어 준다. 책의 예제에서 Vaadin과 jOOQ 플러그인은 다음을 할 줄 안다.

- 유스케이스에서 Vaadin 뷰 만들기
- 엔터티 모델을 위한 jOOQ 쿼리 생성하기
- 프로젝트 구조에 맞는 애플리케이션 서비스 작성하기
- Vaadin 뷰용 Karibu 테스트 생성하기
- 전체 시스템 동작용 Playwright 테스트 생성하기

다른 팀이 다른 스택용 플러그인으로 같은 프로세스를 쓸 수 있다. 방법론은 그대로이고 실행 계층만 바뀐다. 이 분리가 중요한 이유는 스펙이 프레임워크와 도구보다 오래 살아야 하기 때문이다. 오늘 쓴 시스템 유스케이스는 팀이 나중에 UI 프레임워크를 바꾸어도 여전히 쓸모 있어야 한다. 구현 플러그인은 바뀔 수 있지만 동작은 스펙에 정의된 채로 남는다.

## 3. MCP 서버는 기술적 정확성을 위한 장치

스펙은 시스템이 무엇을 해야 하는지를 정의한다. 프레임워크 API의 세부까지 정의하지는 않는다. 예를 들어 UC-012는 시스템이 작업 상세와 활성 사용자 목록을 표시한다고 말하지만, Vaadin Grid를 어떻게 설정하는지, ComboBox를 어떻게 바인딩하는지, jOOQ 쿼리를 어떻게 쓰는지는 설명하지 않는다. 여기서 기술적 맥락이 중요해진다.

요즘 AI 에이전트는 많은 프레임워크를 알지만 지식이 불완전하거나 오래되었을 수 있다. API가 바뀌고, 모범 사례가 바뀌고, 컴포넌트가 진화한다. 에이전트가 학습 데이터에만 의존하면, 그럴듯해 보이지만 현재 라이브러리 버전과 맞지 않는 코드를 만들 수 있다. MCP 서버(Model Context Protocol server)는 생성 시점에 에이전트가 구조화된 기술 문서와 도구에 접근하게 해 이 문제를 줄인다.

### 3-1. UC-012에서 각 입력이 하는 일

| 입력 | 에이전트에게 알려 주는 것 |
|---|---|
| 스펙 | 활성 사용자를 표시해야 한다는 것 |
| Vaadin 문서(MCP 경유) | UI를 올바르게 구현하는 방법 |
| jOOQ 문서(MCP 경유) | 쿼리를 올바르게 쓰는 방법 |
| 프로젝트 가이드라인 파일 | 코드가 어디에 속하는지 |

이 입력들은 서로 보완한다. 책은 이를 세 줄로 요약한다. 스펙은 시스템이 무엇을 해야 하는지, 가이드라인은 이 프로젝트가 어떻게 구조화되었는지, MCP는 현재 기술 API가 어떻게 작동하는지다. 그래서 환각이 줄어든다. 에이전트가 현재 Vaadin이나 jOOQ API의 동작을 추측하지 않고 관련 기술 맥락을 조회할 수 있다. 단, MCP는 스펙을 대체하지 않는다. 구현을 돕는 장치이고, 동작의 진실 원천은 여전히 스펙이다.

## 4. 버전 관리는 안전망

모든 스펙 산출물, 가이드라인 파일, 코드, 테스트가 같은 저장소에 있어야 한다. 이는 필수다. UC-012의 전형적인 구현은 브랜치에서 일어난다. 풀 리퀘스트는 유스케이스와 생성되거나 수정된 모든 코드를 담는다. 변경이 하나의 단위로 검토된다. 풀 리퀘스트에는 다음이 보여야 한다.

- /docs/use-cases/UC-012-assign-task.md
- src/main/...
- src/test/...

### 4-1. 검토 순서

리뷰어는 스펙에서 시작한다. 동작이 맞는가? 규칙이 명시적인가? 사후 조건이 분명한가? 대안 흐름이 충분히 완전한가? 그다음에야 구현을 본다. 이 순서가 중요하다. 코드를 먼저 리뷰하면 동작이 무엇이어야 하는지 합의하기 전에 구현을 무심코 승인할 수 있다.

1. 스펙을 검토한다.
2. 동작이 맞는지 확인한다.
3. 구현을 검토한다.
4. 코드가 스펙과 맞는지 확인한다.
5. 테스트가 명시된 흐름과 규칙을 다루는지 확인한다.

버전 관리는 AI가 만든 작업을 안전하게 만들기도 한다. 생성 결과가 틀렸다면 브랜치를 버리면 된다. 나쁜 생성의 비용은 한정되고, 리뷰 없이 main 브랜치로 들어가는 것은 없다.

## 5. 핵심 정리

- 가이드라인 파일(CLAUDE.md, AGENTS.md)은 프로젝트 전반에 적용되는 실행 가능한 기억이다. 짧게 유지하고, 워크플로 전용 규칙은 스킬에 두며, Git에서 검토한다.
- 스킬은 반복 가능한 워크플로(유스케이스 확장, 구현, 마이그레이션, 테스트 도출 등)를 정의한다.
- 플러그인은 AIUP를 구체적 기술 스택에 잇는다. 방법론은 안정적이고 실행 계층만 바뀐다.
- MCP 서버는 생성 시점에 현재 기술 문서와 도구를 제공해 환각을 줄이되 스펙을 대체하지 않는다. 스펙은 동작, 가이드라인은 구조, MCP는 현재 API다.
- 스펙, 코드, 테스트, 가이드라인은 한 저장소에 둔다. 리뷰는 스펙을 먼저, 구현을 나중에 하며, 잘못된 생성은 브랜치를 버려 안전하게 되돌린다.
