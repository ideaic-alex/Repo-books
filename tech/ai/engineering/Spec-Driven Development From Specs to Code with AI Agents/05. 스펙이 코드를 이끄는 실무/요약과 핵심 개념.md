# 요약과 핵심 개념

5장은 이미 잘 쓰인 스펙이 실제 개발 작업을 어떻게 움직이는지를 UC-012 하나로 보여 준다. 흐름은 세 덩어리다. 첫째는 능동 스펙과 에이전트의 입력(유스케이스, 요구사항, 엔터티 모델, 가이드라인 파일, 기존 코드), 둘째는 이를 받쳐 주는 장치(스킬, 플러그인, MCP 서버, 버전 관리), 셋째는 규칙이 바뀔 때의 동기화와 테스트, 검토, 사람의 책임이다. 이 문서는 세 덩어리를 한 번에 되짚고 핵심 용어를 정리한다.

원서의 요약은 이렇게 이어진다. 스펙은 개발을 능동적으로 이끌 때 가치가 있고, 유스케이스 요소는 코드로 자연스럽게 대응하며, 가이드라인 파일은 실행 가능한 프로젝트 기억이다. 동기화는 재생성과 다르고, 버전 관리는 안전망이며, 사람의 검토는 필수다. 다음 장은 같은 유스케이스가 검증도 이끄는 것, 곧 테스트를 다룬다.

---

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | 수동 스펙을 능동 스펙으로 | "UC-012를 구현해 줘"처럼 특정 유스케이스를 가리키는 요청 |
| 2 | UC-012 예제 확인 | 7단계 주 흐름, A1, 사후 조건, BR-012-1, BR-012-2 |
| 3 | 에이전트의 입력 구성 | 유스케이스와 요구사항, 엔터티 모델, 가이드라인 파일, 기존 코드의 경계 있는 맥락 |
| 4 | 첫 구현과 매핑 | 뷰, 서비스, 쿼리, 검증, 테스트가 유스케이스에 추적됨 |
| 5 | 가이드라인, 스킬, 플러그인, MCP, 버전 관리 | 프로젝트 규칙, 반복 워크플로, 현재 API 조회, 브랜치와 풀 리퀘스트 |
| 6 | 규칙 변경과 동기화 | 팀 리드 예외를 스펙에 먼저 반영한 뒤 영향 부분만 수정 |
| 7 | 테스트, 검토, 사람의 책임 | 같은 유스케이스에서 나온 테스트, 스펙 우선 리뷰, 의미에 대한 인간 책임 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 수동적 스펙 / 능동적 스펙 | 개발이 무시하는 문서 / 변경의 출발점이자 통제 지점이 되는 스펙 |
| 경계 있는 맥락 | 에이전트가 유스케이스와 주변 파일을 함께 읽어 얻는 한정된 작업 맥락 |
| 가이드라인 파일 | CLAUDE.md나 AGENTS.md. 프로젝트 전반에 적용되는 규칙을 담은 짧은 파일 |
| 스킬 | 에이전트에게 특정 종류의 작업 방법을 알려 주는 재사용 가능한 능력 |
| 플러그인 | AIUP를 특정 기술 스택(예: Vaadin, jOOQ)에 잇는 실행 계층 |
| MCP 서버 | 생성 시점에 구조화된 기술 문서와 도구를 에이전트에게 제공하는 서버 |
| 유스케이스와 코드의 매핑 | 사전 조건은 확인, 단계는 화면과 서비스, 규칙은 검증으로 이어지는 대응 |
| 재생성 | 구현을 처음부터 다시 만드는 것. 큰 diff가 나온다 |
| 동기화 | 갱신된 유스케이스가 기술하는 행동 변화만 코드에 반영하는 것 |
| 검증 관점 | 같은 행동 계약에서 나온 테스트. 코드는 구현 관점이다 |
| 추적성 | 모든 의미 있는 코드 변경이 유스케이스로 거슬러 추적됨 |

## 3. 자주 놓치는 점

- 좋은 스펙을 써 놓고 즉흥적 프롬프트로 돌아가면 스펙이 다시 수동적 문서가 되고 코드와 어긋난다.
- 유스케이스에는 스키마, UI 컴포넌트, 서비스 클래스, SQL을 쓰지 않는다. 그래야 코드를 이끌 만큼 안정적이다.
- 가이드라인 파일이 길어지면 요청마다 처리할 정보가 많아지고 유지하기 어렵다. 워크플로 전용 규칙은 스킬에 둔다.
- MCP 서버는 스펙을 대체하지 않는다. 동작의 진실 원천은 스펙이다.
- 리뷰는 스펙을 먼저 한다. 코드부터 보면 동작에 합의하기 전에 구현을 승인할 수 있다.
- 기존 기능의 작은 변경을 재생성하면 큰 diff와 리팩터링 손실이 생긴다. 운영 중인 기능은 기본적으로 동기화한다.
- 생성된 코드가 유스케이스에 없는 동작을 더해도, 있는 규칙을 빠뜨려도 둘 다 문제다.
- 테스트는 따로 발명하지 않고 같은 유스케이스에서 도출한다. 규칙이 바뀌면 테스트도 같이 바뀐다.
- 참고(노트 작성자): 원서의 UC-012 변경 사례에서 BR-012-2가 처음에는 "담당자 정확히 한 명", 변경 후에는 "팀 리드 규칙"을 뜻한다. 또 변경 후 요청 명령이 `/implement UC-012`로 적혀 있어 앞에서 말한 "동기화해 줘" 문구와 다르다. 원서는 둘 다 따로 설명하지 않으므로 사례별 서술로 읽는다. 아울러 그림 5-1, 5-2, 5-3의 내부 글자는 추출본에서 확인하지 못했다.
