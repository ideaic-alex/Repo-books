# 유스케이스 요소와 코드 매핑

개발자가 에이전트에게 UC-012를 구현하라고 하면 에이전트는 무엇을 읽고, 어떤 순서로 일하며, 결과를 어떻게 확인할까? 이 문서는 에이전트가 코드를 쓰기 전에 읽는 자료, 처음 구현할 때의 흐름, 그리고 유스케이스의 각 요소가 어떤 구현 결과로 이어지는지를 정리한 매핑 표를 다룬다.

번역 사전에 비유하면, 유스케이스는 원문이고 코드는 번역문이다. 원문의 문장마다 대응하는 번역문이 있으면 검수자는 문장 단위로 짝을 맞춰 가며 틀린 곳을 쉽게 찾는다. 유스케이스와 코드의 매핑은 바로 그 대응표 역할을 한다.

---

## 1. 에이전트가 코드를 쓰기 전에 읽는 것

개발자가 에이전트에게 UC-012 구현을 요청해도 에이전트는 유스케이스만 보고 일하지 않는다. 유스케이스를 주된 입력으로 읽지만, 주변 프로젝트 맥락도 필요하다. 전형적인 저장소에서 관련 파일은 다음과 같다.

| 파일 | 에이전트가 거기서 얻는 것 |
|---|---|
| /docs/requirements.md | 의도와 제약 |
| /docs/entity-model.md | 도메인 용어 |
| /docs/use-cases/UC-012-assign-task.md | 구현할 동작 |
| CLAUDE.md 또는 AGENTS.md | 모든 에이전트 상호작용에 적용되는 프로젝트 규칙 |
| src/main, src/test | 기존 구현 구조와 테스트 |

이 조합이 중요한 이유는 하나라도 빠졌을 때의 문제로 설명된다.

- 유스케이스가 없으면 어떤 동작을 구현해야 하는지 모른다.
- 엔터티 모델이 없으면 일관되지 않은 용어를 쓸 수 있다.
- 가이드라인 파일이 없으면 프로젝트 관례를 무시할 수 있다.
- 기존 코드가 없으면 애플리케이션에 맞지 않는 것을 만들 수 있다.

그래서 에이전트는 고립된 프롬프트가 아니라 경계가 있는 맥락(bounded context)에서 일한다.

## 2. 처음 구현하는 흐름

유스케이스가 검토되고 승인되면 개발자는 에이전트에게 구현을 요청할 수 있다. 명령 기반 워크플로에서는 이렇게 보일 수 있다.

```text
/implement UC-012
```

명령 이름 자체는 중요하지 않다. 중요한 것은 요청의 구조다. 에이전트는 기능을 발명하라는 요청이 아니라 특정 유스케이스를 구현하라는 요청을 받는다. 원서의 그림 5-1은 이 흐름을 보여 준다.

참고(노트 작성자): 원서 그림 5-1의 내부 내용은 추출본에서 확인되지 않았다. 흐름은 본문의 서술(유스케이스 입력, 가이드라인과 기술 지식 적용, 코드 변경 검토)로 이해하면 된다.

### 2-1. UC-012 구현에 걸리는 시스템 부분

Assign Task의 구현은 시스템의 여러 부분에 걸칠 수 있다.

- 작업 상세와 대상 사용자를 보여 주는 Vaadin 뷰
- 할당을 수행하는 애플리케이션 서비스
- 할당 가능한 사용자를 불러오는 jOOQ 쿼리
- 비활성 사용자를 거부하는 검증 로직
- 주 흐름과 대안 흐름을 검증하는 테스트

중요한 것은 어느 파일이 바뀌는지가 아니라 왜 바뀌는지다. 모든 변경은 유스케이스로 거슬러 올라가 추적되어야 한다. 생성된 코드가 UC-012에 없는 동작을 추가하면 문제다. UC-012의 비즈니스 규칙을 놓쳐도 문제다. 리뷰의 기준점은 유스케이스다.

## 3. 유스케이스 요소가 코드로 이어지는 방식

시스템 유스케이스는 구현 관심사로 자연스럽게 대응되도록 구조화되어 있다. UC-012의 경우 원서가 보이는 매핑은 다음과 같다.

| 유스케이스 요소 | 구현의 결과 |
|---|---|
| 사전 조건 | 작업이 존재하고, 열려 있고, 이미 할당되지 않았는지 확인 |
| 주 흐름 2단계 | 작업 상세와 활성 사용자 표시 |
| 주 흐름 5단계 | 선택한 사용자가 활성인지 검증 |
| 주 흐름 6단계 | 애플리케이션 서비스에서 작업 할당 |
| 대안 흐름 A1 | 비활성 사용자를 거부하고 분명한 메시지 표시 |
| 성공 사후 조건 | 담당자를 저장하고 작업 상태를 ASSIGNED로 설정 |
| 실패 사후 조건 | 작업을 변경하지 않고 둠 |
| BR-012-1 | 활성 사용자 검증 규칙 추가 |
| BR-012-2 | 담당자가 정확히 한 명임을 보장 |

참고(노트 작성자): 추출본의 이 표는 대소문자가 깨져 있었다(예: 'aSS igneD'). 본문의 ASSIGNED 표기에 맞춰 복원했다. 표에서 주 흐름 1, 3, 4, 7단계는 원서가 따로 매핑하지 않았다. 원서는 "UC-012의 경우 매핑이 이럴 수 있다"고 했을 뿐이어서 전체를 망라한 표는 아니다.

### 3-1. 매핑이 주는 두 가지 이점

이 매핑은 구현을 근거 위에 올려 둔다. 에이전트는 동작을 추측하지 않고도 유스케이스에서 코드 구조를 도출할 수 있다. 리뷰도 쉬워진다. 리뷰어는 생성된 diff를 유스케이스와 절 단위로 견줄 수 있다.

- 코드가 사전 조건을 확인하는가?
- UI가 주 흐름을 지원하는가?
- 서비스가 비즈니스 규칙을 강제하는가?
- 실패 경로가 작업을 변경하지 않은 채 두는가?

그러면 리뷰는 생성된 코드에 대한 일반적인 의견이 아니라 행동 계약과의 비교가 된다.

## 4. 핵심 정리

- 에이전트는 유스케이스, 요구사항, 엔터티 모델, 가이드라인 파일, 기존 소스와 테스트를 함께 읽는다. 하나라도 빠지면 동작, 용어, 관례, 적합성 중 하나를 잃는다.
- 요청은 `/implement UC-012`처럼 특정 유스케이스를 구현하라는 구조다. 명령 이름은 중요하지 않다.
- UC-012 구현은 뷰, 애플리케이션 서비스, jOOQ 쿼리, 검증 로직, 테스트에 걸칠 수 있고, 각 변경은 유스케이스에 추적되어야 한다.
- 사전 조건은 확인으로, 주 흐름은 화면과 서비스 동작으로, A1은 거부 메시지로, 사후 조건은 저장과 상태로, 비즈니스 규칙은 검증으로 이어진다.
- 리뷰는 diff를 유스케이스 절과 견주는 행동 계약 비교다.
