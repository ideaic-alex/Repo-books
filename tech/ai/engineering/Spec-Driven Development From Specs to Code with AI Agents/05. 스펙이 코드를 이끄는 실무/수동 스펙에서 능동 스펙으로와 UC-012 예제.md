# 수동 스펙에서 능동 스펙으로와 UC-012 예제

앞 장들은 요구사항, 엔터티 모델, 시스템 유스케이스라는 스펙 산출물을 만들었다. 이 시점의 스펙은 분명하고, 검토할 수 있고, 버전 관리가 된다. 그런데 하나의 질문이 남는다. 그다음에는 무엇이 일어나는가? 스펙은 개발 방식을 실제로 바꿀 때만 가치가 있다. 팀이 좋은 유스케이스를 써 놓고도 즉흥적인 프롬프트(ad hoc prompting)로 돌아가 버리면, 스펙은 다시 수동적인 문서가 된다. 에이전트는 승인된 산출물이 아니라 가장 최근 프롬프트를 따라 일하고, 2주 뒤에는 코드와 스펙이 어긋나 어느 쪽이 맞는지 아무도 모르게 된다.

5장은 이 간극을 메운다. 시스템 유스케이스가 일상 개발 작업의 출발점이 되는 모습을, 하나의 예제로 첫 구현, 검토, 이후 변경, 동기화까지 따라가며 보인다. 이 문서는 5장의 도입, 수동 스펙과 능동 스펙의 차이, 그리고 장 전체에 쓰이는 예제 UC-012를 다룬다.

---

## 1. 5장의 목표

예제는 UC-012 Assign Task다. 빠르게 이해할 만큼 작지만 과정의 중요한 부분을 보여 줄 만큼 현실적이다. 책이 밝히는 목표는 모든 도구를 자세히 설명하는 것이 아니라(그것은 뒤에서 한다) 실행 모델을 보이는 것이다. 그 모델은 세 단계다.

1. 시스템 유스케이스가 AI 에이전트의 입력이 된다.
2. 에이전트가 프로젝트 가이드라인과 기술 지식을 적용한다.
3. 결과를 평범한 코드 변경으로 검토한다.

## 2. 수동 스펙과 능동 스펙

수동적 스펙(passive specification)은 시스템을 기술하지만 작업을 이끌지 않는다. 잘 쓰였을 수도 있고 Git에 저장되어 있을 수도 있다. 하지만 개발자가 시스템을 바꿀 때 무시한다면 그것은 또 하나의 문서일 뿐이다.

능동적 스펙(active specification)은 다르다. 구현의 출발점이다. 코드를 건드리기 전에 무엇이 바뀌어야 하는지를 정의한다. 개발자는 AI 에이전트에게 "검증을 좀 추가해 줘"나 "폼을 만들어 줘"라고 하지 않는다. 특정 유스케이스를 구현하거나 동기화하라고 요청한다.

### 2-1. 프롬프트가 달라진다

| 구분 | 프롬프트 | 에이전트가 해야 하는 일 |
|---|---|---|
| 즉흥적 | 작업 할당 폼에 검증을 추가해 줘 | 범위, 용어, 규칙, 기대 결과를 모두 추측한다 |
| 능동 스펙 | UC-012를 구현해 줘 | 승인된 행동 계약을 읽고 그 경계 안에서 일한다 |
| 변경 후 | 갱신된 UC-012에 맞춰 구현을 동기화해 줘 | 바뀐 계약에 맞는 부분만 반영한다 |

첫 프롬프트는 열려 있고, 둘째와 셋째는 승인된 행동 계약을 가리킨다. 이것이 스펙 주도 개발의 실질적인 의미다. 스펙은 설명일 뿐 아니라 변경의 통제 지점(control point)이다.

참고(노트 작성자): 원서가 영어로 쓴 세 문장("Add validation to the task assignment form.", "Implement UC-012.", "Synchronize the implementation with the updated UC-012.")을 위 표에서 한국어로 풀어 썼다.

## 3. 실행 예제 UC-012 Assign Task

팀이 이미 다음 시스템 유스케이스를 쓰고 검토했다고 가정한다.

```text
UC-012 Assign Task   Primary Actor: User   Status: Approved
Goal: 열린 작업을 다른 활성 사용자에게 할당한다
Linked Requirements: FR-004 작업을 사용자에게 할당 /
  NFR-002 작업 연산은 1초 이내 / C-001 백엔드는 Java와 PostgreSQL 사용
Preconditions: 사용자 인증됨 / 작업 존재 / 작업이 열려 있고 아직 미할당
Main Success Scenario:
 1 사용자가 작업 상세를 연다.
 2 시스템이 작업과 활성 사용자 목록을 표시한다.
 3 사용자가 대상 사용자를 선택한다.
 4 사용자가 할당을 확정한다.
 5 시스템이 대상 사용자가 활성인지 검증한다.
 6 시스템이 작업을 선택한 사용자에게 할당한다.
 7 시스템이 작업이 할당되었음을 확인해 준다.
A1 대상 사용자가 비활성: 시스템이 할당을 거부하고, 활성 사용자만 작업을 받을 수 있다고
  표시한다. 작업은 변경 없음.
Postconditions: 성공 - 작업이 선택한 활성 사용자에게 할당, 상태 ASSIGNED / 실패 - 작업 변경 없음
Business Rules: BR-012-1 활성 사용자만 작업을 받을 수 있다.
  BR-012-2 할당된 작업은 담당자가 정확히 한 명이어야 한다.
```

### 3-1. 3·4장 예제와 다른 점

- 주 흐름이 7단계다. 선택(3단계) 뒤에 "확정"(4단계)이 따로 있어, 검증(5단계)과 할당(6단계)이 확정 이후에 일어난다.
- 상태가 승인됨(Approved)이다. 3장 예제의 'Documented'와 달리 상태 필드의 허용 값 중 하나다.
- 비즈니스 규칙에 UC 번호가 들어간 ID(BR-012-1, BR-012-2)를 쓴다. 유스케이스에 묶인 규칙임이 ID에서 드러난다.
- 연결된 요구사항이 FR-004, NFR-002, C-001이다. 3장 예제의 FR-001, NFR-001과 번호가 다르며, 각각 별개의 설명용 예시다.

## 4. 이 유스케이스가 변경의 원천인 이유

이 유스케이스는 변경의 단일 출처(source of truth)다. 행위자, 목표, 사전 조건, 주 흐름, 대안 흐름, 사후 조건, 비즈니스 규칙을 정의한다.

반대로 이 유스케이스는 데이터베이스 스키마를 기술하지 않는다. Vaadin 컴포넌트, 서비스 클래스, SQL 쿼리, 컨트롤러 메서드도 언급하지 않는다. 그것들은 구현 관심사다. 유스케이스는 관찰 가능한 동작을 기술하고, 그래서 코드를 이끌 만큼 안정적이다. 이는 4장의 관찰 가능한 동작 원칙이 실무에서 어떻게 쓰이는지 보여 주는 대목이다.

참고(노트 작성자): Vaadin은 Java용 웹 UI 프레임워크이고 jOOQ는 Java에서 SQL을 타입 안전하게 쓰게 해 주는 라이브러리다. 원서는 5장에서 이 둘을 예제 스택의 일부로 쓰지만 이 풀이는 노트 작성자가 보탠 것이다.

## 5. 핵심 정리

- 스펙은 코드를 바꾸는 방식을 바꿀 때만 가치가 있다. 수동적 스펙은 곧 코드와 어긋난다.
- 능동 스펙은 구현의 출발점이다. 요청은 "UC-012를 구현해 줘" 또는 "갱신된 UC-012에 맞춰 동기화해 줘"처럼 특정 유스케이스를 가리킨다.
- 실행 모델은 유스케이스 입력, 가이드라인과 기술 지식 적용, 평범한 코드 변경으로서의 검토다.
- UC-012는 승인된 유스케이스이며 FR-004, NFR-002, C-001과 BR-012-1, BR-012-2를 가진다.
- 유스케이스는 스키마, 컴포넌트, 서비스, SQL을 말하지 않는다. 그래서 안정적이다.
