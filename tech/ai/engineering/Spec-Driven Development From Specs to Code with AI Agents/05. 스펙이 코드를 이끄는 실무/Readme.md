# 05. 스펙이 코드를 이끄는 실무

이 장은 잘 쓴 스펙을 일상 개발 작업의 출발점으로 만드는 방법을 다룬다. 시스템 유스케이스가 AI 에이전트의 입력이 되고, 에이전트가 프로젝트 가이드라인과 기술 지식을 적용하며, 결과를 평범한 코드 변경으로 검토하는 실행 모델을 보인다.

UC-012 Assign Task 하나를 끝까지 따라가며 첫 구현, 검토, 이후 규칙 변경, 동기화를 차례로 설명한다. 도구의 세부보다 실행 모델을 이해하는 데 초점이 있다.

---

## 1. 핵심 요점

- 수동적 스펙은 문서로 남고, 능동적 스펙은 구현의 출발점이 된다. 요청은 "UC-012를 구현해 줘"처럼 특정 유스케이스를 가리킨다.
- 에이전트는 유스케이스, 요구사항, 엔터티 모델, CLAUDE.md 또는 AGENTS.md, 기존 소스와 테스트를 함께 읽는다.
- 유스케이스 요소는 코드로 대응된다. 사전 조건은 확인, 주 흐름은 화면과 서비스, A1은 거부 메시지, 사후 조건은 저장과 상태, 비즈니스 규칙은 검증이다.
- 가이드라인 파일은 짧게 유지하는 프로젝트 기억이고, 스킬과 플러그인은 반복 가능한 워크플로와 스택 적응을 맡는다.
- MCP 서버는 현재 기술 문서를 제공해 환각을 줄인다. 스펙은 동작, 가이드라인은 구조, MCP는 현재 API다.
- 스펙, 코드, 테스트, 가이드라인은 한 저장소에 두고, 리뷰는 스펙을 먼저 한다. 잘못된 생성은 브랜치를 버려 되돌린다.
- 규칙이 바뀌면 스펙을 먼저 고치고 동기화한다. 동기화는 바뀐 동작만 반영하고, 재생성은 새 유스케이스나 버릴 프로토타입에 쓴다.
- 테스트도 같은 유스케이스에서 도출하며, 의미에 대한 책임은 끝까지 사람에게 있다.
