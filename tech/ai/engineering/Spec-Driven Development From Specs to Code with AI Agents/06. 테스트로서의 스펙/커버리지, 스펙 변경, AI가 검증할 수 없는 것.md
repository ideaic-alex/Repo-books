# 커버리지, 스펙 변경, AI가 검증할 수 없는 것

테스트를 쌓은 뒤에는 세 가지 질문이 남는다. 얼마나 덮었는가를 무엇으로 재는가, 스펙이 바뀌면 테스트는 어떻게 반응하는가, 그리고 AI가 만든 테스트를 누가 보증하는가다. 이 문서는 6장의 마지막 세 절을 정리하고, 장 전체의 핵심 정리도 함께 풀어 쓴다.

---

## 1. 커버리지는 스펙의 완성도

전통적인 테스트 커버리지는 코드 몇 줄이 실행되었는지를 묻는다. 유용하지만 충분하지 않다. 스펙 주도 커버리지는 더 중요한 질문을 던진다. 스펙의 어느 부분이 실제로 검증되고 있는가다.

목표는 스펙 커버리지를 완전하게 만드는 것이다.

- 모든 주 성공 시나리오에 대응하는 정상 경로 테스트가 있어야 한다.
- 모든 대안 흐름과 예외 흐름은 의미 있는 곳에서 덮어야 한다.
- 모든 비즈니스 규칙은 테스트 묶음 어딘가에서 단언되어야 한다.

덮이지 않은 코드 한 줄은 받아들일 수 있다. 하지만 덮이지 않은 비즈니스 규칙은 시스템 보호의 구멍이다.

## 2. 추적성을 테스트 코드에 드러내기

저자는 현재 프로젝트에서 이 추적성을 테스트 코드 안에 명시한다.

- 테스트 클래스 이름에 유스케이스 식별자와 이름을 넣는다. 원서 예는 `UC002CreateFormTest`다.
- 테스트 메서드는 검증하는 정확한 흐름이나 비즈니스 규칙을 가리킨다.
- Java에서는 전용 어노테이션으로 이 참조를 구조화해 남긴다.

원서의 예에서는 `@UseCase(id = "UC-02", scenario = "A1")`가 붙은 메서드 `create_form_without_title_shows_validation_error()`가 UC-02의 대안 흐름 A1을 검증한다고 표시한다.

이렇게 하면 커버리지 보고가 코드 실행에서 스펙 검증으로 옮겨 간다. 의도한 행동 중 어느 부분이 보호되고 어느 부분이 아직 비었는지 눈에 보인다. 연결이 명시적이므로 AI 에이전트도 코드 수준이 아닌 스펙 수준에서 빈틈을 추론할 수 있다.

## 3. 유스케이스가 바뀔 때

스펙 주도 테스트의 진짜 가치는 행동이 진화할 때 드러난다. 원서의 구체적 예를 보자. 어떤 유스케이스에서 활성 사용자에게만 작업을 배정할 수 있다. 나중에 비즈니스가 특별한 경우 관리자는 비활성 사용자에게도 작업을 배정할 수 있어야 한다고 결정한다.

변경은 스펙에서 시작한다. 비즈니스 규칙을 고치고, 대안 흐름을 추가하고, 유스케이스를 검토해 승인한다. 그다음 동기화가 돌아 구현이 바뀌고 관련 테스트가 맞춰 갱신된다.

이 시점에 시스템 나머지 부분의 가드레일이 작동한다. 실패하는 경우는 세 가지다.

| 상황 | 실패하는 테스트 |
|---|---|
| 고친 규칙이 관리자만이 아니라 모든 사용자에게 비활성 사용자 배정을 허용 | 해당 시나리오의 비즈니스 규칙 테스트 |
| 다른 유스케이스가 옛 제한을 암묵적으로 전제 | 그 유스케이스의 테스트 |
| UI 안내가 새 흐름과 어긋남 | UI 테스트 |

각 실패는 거짓 경보가 아니라 실제 정합성 문제를 가리킨다. 파생 테스트가 없으면 이런 회귀가 운영 환경까지 눈에 띄지 않을 수 있다. 있으면 동기화 중에 잡힌다.

## 4. AI는 테스트를 만들되 검증하지는 못한다

AI는 스펙에서 테스트를 생성하고, 유스케이스가 바뀔 때 갱신하고, 빠진 커버리지를 찾는 일을 도울 수 있다. 시스템이 커질수록 스펙과 테스트의 정합을 유지하기가 어려워지므로 이것은 가치가 있다.

하지만 생성된 테스트가 의도한 행동을 반영하는지는 AI가 판단하지 못한다. 테스트는 그럴듯해 보이면서도 엉뚱한 사후 조건을 단언하거나, 오해한 비즈니스 규칙을 인코딩하거나, 아무도 원하지 않은 것을 검증할 수 있다. 그래서 생성된 테스트는 반드시 사람이 검토해야 한다.

- 단언은 스펙과 대조한다.
- 비즈니스 규칙은 이해관계자의 의도와 대조한다.
- 바뀐 테스트도 새로 생성된 테스트와 같은 주의로 본다.

원서의 문장을 우리말로 줄이면, AI는 기계적인 일을 빠르게 하고 인간의 검토가 정확성을 지킨다.

---

## 5. 6장 핵심 정리

- 테스트는 시스템 유스케이스에서 파생된다. 주 흐름, 대안 흐름, 예외 흐름, 비즈니스 규칙이 모두 실행 가능한 검사로 대응된다.
- 테스트는 구현 세부가 아닌 관찰 가능한 행동을 보호하므로 리팩터링과 동기화가 안전하다.
- 업무 애플리케이션의 올바른 모델은 피라미드가 아니라 트로피이고, 통합 테스트가 핵심 층이다. Vaadin의 E2E 층은 브라우저리스 테스팅과 Playwright 두 도구가 나눠 맡는다.
- TDD는 스펙 우선 흐름 안에서 로직, 서비스, API에 더 잘 맞고 UI에는 덜 맞는다.
- 커버리지는 코드 실행만이 아니라 스펙을 기준으로 판단하며, 이름 규칙과 어노테이션이 추적성을 사람과 기계가 읽을 수 있게 만든다.
- AI는 테스트를 효율적으로 생성하고 갱신하지만, 의도를 표현하는지 확인하는 것은 사람의 검토뿐이다.
- 이 다음 질문은 이런 작업 방식을 어떤 도구가 지원하는가이며, 7장이 이를 다룬다. 원서 설명으로는 단순한 Markdown과 Git 구성에서 AI 통합 프로세스 마켓플레이스까지 선택지를 살핀다.
