# TDD의 위치와 AI 테스트 생성 흐름

스펙이 먼저 온다면 테스트 주도 개발(Test-Driven Development, TDD, 테스트를 먼저 쓰고 구현하는 방식)은 여전히 쓸모가 있을까. 원서의 답은 쓸모가 있지만 조직 원리의 자리는 아니라는 것이다. 이 문서는 TDD가 들어맞는 곳과 들어맞지 않는 곳, 그리고 AI에게 테스트 뼈대를 만들게 한 뒤 검토하는 절차를 정리한다.

---

## 1. TDD는 스펙 주도 안의 국소 기법

AIUP에서 시스템 유스케이스가 여전히 맨 앞이다. 존재해야 할 행동을 정의하기 때문이다. TDD는 그 큰 스펙 주도 프로세스 안에서 쓰는 국소적 설계 기법이 된다. 순서는 분명하다.

1. 유스케이스를 명확히 하고 갱신한다.
2. 테스트를 먼저 쓰는 설계가 도움이 되는 곳을 정한다.
3. 구현한다.

스펙은 무엇이 일어나야 하는지를 정하고, TDD는 특정 규칙, 서비스, API가 코드에서 어떻게 실현될지를 다듬는 데 도움을 준다.

## 2. TDD가 잘 맞는 곳

### 2-1. 비즈니스 로직

TDD가 가장 자연스럽게 맞는 곳이다. 비즈니스 규칙은 대체로 결정적이고, UI와 무관하며, 사전 조건과 사후 조건으로 표현되고, 고립해서 검증하기 쉽다. 고전적인 레드-그린-리팩터(red-green-refactor) 주기가 아주 잘 돌아간다. 비즈니스 규칙 하나를 담은 실패하는 테스트를 쓰고(레드), 그것을 통과시킬 최소한의 로직을 구현하고(그린), 테스트를 초록으로 유지한 채 정리한다(리팩터). 각 테스트는 유스케이스의 규칙이나 사후 조건 하나에 곧바로 대응하고, 자라나는 가드레일의 일부가 된다.

### 2-2. 애플리케이션 서비스와 API

서비스는 내부 구조가 생기기 전에 허용 입력, 기대 출력, 검증 동작, 관련 부작용을 정하는 테스트를 먼저 쓸 수 있다. API 엔드포인트는 컨트롤러 로직을 쓰기 전에 바깥에서 본 행동을 테스트로 정의할 수 있다. 어떤 요청을 받아들이는지, 입력을 어떻게 검증하는지, 어떤 응답과 상태 코드를 돌려주는지, 오류를 어떻게 표현하는지다. 두 경우 모두 테스트는 유스케이스에서 나온 행동 계약을 표현하고, 구현은 그 계약을 따르며, 유스케이스 ID와의 추적성(traceability, 요구에서 코드와 테스트까지 연결을 따라갈 수 있는 성질)이 유지된다.

## 3. TDD가 맞지 않는 곳: UI

UI는 다르다. UI 테스트는 구체적인 컴포넌트가 존재하고, 레이아웃이 결정되었고, 상호작용 지점이 정의되어 있다고 전제해야 한다. UI가 생기기 전에는 비교할 의미 있는 대상이 없다. 먼저 테스트를 쓰려 하면 UI가 안정되면서 다시 써야 하는 깨지기 쉬운 임시 틀이 되기 쉽다. 원서는 이것을 규율의 실패가 아니라 기법과 계층의 불일치라고 부른다.

그래서 UI 행동에는 이 순서가 합리적이다. 관찰 가능한 행동을 스펙으로 정하고, UI를 구현하고, 그다음에 테스트를 쓴다. 요점은 TDD를 일률적으로 적용하는 것이 아니라 만드는 대상의 성격에 맞는 곳에 적용하는 것이다.

| 대상 | 권장 순서 |
|---|---|
| 비즈니스 로직, 서비스, API | 스펙 갱신, 테스트 먼저, 구현 |
| UI | 스펙 갱신, 구현, 테스트 |

## 4. AI로 테스트 만들기

유스케이스에서 테스트를 끌어내는 기계적인 부분은 AI에 잘 맞는다. 유스케이스에 이미 흐름, 비즈니스 규칙, 사전 조건, 사후 조건이 들어 있으므로 에이전트가 첫 테스트 뼈대를 빠르게 만들 수 있다. 중요한 것은 생성 속도가 아니라 그 뒤의 검토 품질이다.

### 4-1. 서비스와 저장소 테스트

저자는 보통 에이전트에게 Spring Boot와 Testcontainers를 쓰는 JUnit 5 테스트를 생성하게 하고, 흐름 하나와 비즈니스 규칙 하나당 테스트 메서드를 하나씩 두라고 한다. 생성된 메서드에는 다음 조건을 둔다.

- 메서드 이름은 자신이 다루는 흐름이나 규칙을 따라 짓는다.
- 어노테이션으로 유스케이스 ID를 참조한다.
- 사후 조건을 단언으로 쓴다.
- 내부 구현 세부는 검사하지 않는다.

### 4-2. Vaadin UI 테스트

AIUP 마켓플레이스는 `/browserless-test` 슬래시 명령(slash command, 채팅 입력창에서 `/이름`으로 부르는 명령)을 제공한다. 유스케이스와 관련 뷰 클래스를 입력으로 받아, 흐름에 적힌 관찰 가능한 UI 행동에 대한 브라우저리스 테스트 뼈대를 만든다. 이렇게 하면 생성된 테스트가 나머지 테스트 묶음의 관례와 맞는다. 마켓플레이스와 명령은 7장에서 다룬다.

## 5. 생성된 테스트를 받아들이기 전 세 가지 질문

에이전트가 두 계층의 테스트 클래스를 돌려주면, 받아들이기 전에 테스트 메서드마다 이 질문을 던진다.

1. 단언이 유스케이스의 사후 조건과 일치하는가.
2. 준비 단계가 명시된 사전 조건만 반영하는가.
3. 규칙을 어길 때 테스트가 정말로 실패하는가.

세 번째 질문은 일부러 망가뜨린 구현에 테스트를 돌려 보아야 답할 수 있다. 검증 로직을 지웠는데도 테스트가 실패하지 않는다면 그 테스트는 그 규칙을 지키고 있지 않은 것이다.

## 6. 유스케이스가 바뀔 때의 갱신

유스케이스가 바뀌어도 같은 프롬프트가 쓰인다. 유스케이스의 변경분(diff)과 기존 테스트 클래스를 함께 넘기면 에이전트가 추가와 수정을 제안한다. 세 질문 검토는 새로 생긴 메서드뿐 아니라 바뀐 모든 메서드에 똑같이 적용한다. 비즈니스 규칙의 문구를 조금 바꿨을 뿐인데, 구조는 같지만 엉뚱한 것을 단언하는 테스트가 나올 수 있기 때문이다.

---

## 7. 핵심 정리

- 스펙이 먼저이고 TDD는 그 안의 국소 기법이다. 순서는 유스케이스 갱신, 테스트 선행 여부 결정, 구현이다.
- 비즈니스 로직, 서비스, API는 테스트를 먼저 쓰는 방식이 잘 맞고, UI는 구현 뒤에 테스트를 쓰는 편이 낫다.
- AI는 흐름과 규칙마다 테스트 메서드를 하나씩 만들게 하고, 이름 규칙, 유스케이스 ID 어노테이션, 사후 조건 단언, 내부 세부 미검사를 조건으로 둔다.
- 검토 질문 세 가지 중 세 번째는 일부러 망가뜨린 구현으로 확인한다. 변경된 테스트도 새 테스트와 같은 강도로 검토한다.
