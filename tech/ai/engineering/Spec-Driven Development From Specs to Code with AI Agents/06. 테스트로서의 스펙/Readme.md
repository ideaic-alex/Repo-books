# 테스트로서의 스펙

이 장은 스펙 주도 개발에서 테스트가 맡는 역할을 다룬다. AI 통합 프로세스(AIUP)에서 테스트는 시스템 유스케이스에서 파생되는 검증 뷰이며, 빠르게 바뀌는 코드를 붙잡아 주는 실행 가능한 가드레일이다. 먼저 AI 시대에 테스트가 더 중요해지는 이유와 스펙에서 테스트가 나오는 방식을 보고, 이어서 테스트 피라미드 대신 쓰는 테스트 트로피와 그 다섯 층을 살핀다.

그다음 TDD가 놓이는 자리와 AI로 테스트를 생성해 검토하는 절차를 정리하고, 마지막으로 스펙 기준의 커버리지, 스펙이 바뀔 때의 반응, 그리고 AI가 검증하지 못하는 것을 다룬다. 원서의 코드 예는 Java, Spring Boot, Vaadin 기준이다.

---

## 1. 핵심 요점

- 테스트는 시스템 유스케이스의 검증 뷰이고, 코드와 같은 원천에서 함께 진화한다.
- 주 성공 시나리오는 정상 경로 테스트, 대안 흐름은 개별 시나리오, 예외 흐름은 부정 테스트, 비즈니스 규칙은 명시적 단언이 된다.
- 테스트는 내부 구조가 아니라 관찰 가능한 행동을 보호하므로 리팩터링과 동기화가 안전해진다.
- 업무 애플리케이션에는 피라미드보다 테스트 트로피가 맞다. 정적 분석, 단위, 통합, 브라우저리스, Playwright 순의 다섯 층이고 통합 테스트가 핵심이다.
- UI가 있는 유스케이스는 브라우저리스 테스트, UI가 없으면 통합 테스트가 주 테스트다.
- TDD는 스펙 안의 국소 기법으로, 비즈니스 로직, 서비스, API에 잘 맞고 UI는 구현 뒤에 테스트한다.
- 생성된 테스트는 사후 조건 일치, 사전 조건만 준비, 규칙 위반 시 실제 실패라는 세 질문으로 검토한다.
- 커버리지는 스펙 기준으로 재고, 테스트는 반드시 사람이 검토한다.
