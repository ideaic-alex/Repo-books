# 요약과 핵심 개념

이 장은 네 덩어리로 이뤄진다. 테스트를 스펙의 검증 뷰이자 가드레일로 보는 관점, 테스트 트로피로 계층을 나누는 전략, TDD와 AI 테스트 생성의 위치, 그리고 스펙 기준 커버리지와 사람 검토다. 이 문서는 네 덩어리를 한 번에 되짚고 핵심 용어를 정리한다.

원서의 요약은 이렇게 이어진다. 테스트는 시스템 유스케이스에서 파생되고 관찰 가능한 행동을 보호한다. 올바른 모델은 테스트 트로피이며 Vaadin에서는 브라우저리스 테스팅과 Playwright가 E2E 층을 맡는다. TDD는 스펙 우선 흐름 안에서 역할이 있고, 커버리지는 스펙 기준으로 판단하며, AI가 만든 테스트는 사람이 검토해야 한다. 다음 장은 이런 방식을 지원하는 도구를 다룬다.

---

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | AI 시대의 테스트 | 속도가 커진 만큼 테스트가 세 역할(스펙 충족, 부작용 포착, 드리프트 방지)을 맡는다 |
| 2 | 스펙에서 테스트로 | 흐름과 규칙이 테스트로 대응되어 다른 유스케이스를 지키는 방화벽이 된다 |
| 3 | 테스트 트로피 | 다섯 층, 통합과 브라우저리스가 중심, Playwright는 선택적 |
| 4 | TDD와 AI 생성 | 로직, 서비스, API는 테스트 선행, UI는 구현 후 테스트, 세 질문으로 검토 |
| 5 | 스펙 커버리지와 변경 | 규칙이 하나도 빠지지 않게 단언하고, 변경 시 실패가 정합성 문제를 알려 준다 |
| 6 | AI의 한계 | 생성은 AI, 의도 확인은 사람 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 검증 뷰 | 시스템 유스케이스에서 파생된 테스트. 코드는 구현 뷰다 |
| 가드레일 | 통제된 진화를 가능하게 하는 실행 가능한 안전 장치 |
| 회귀 | 잘 되던 동작이 변경 뒤 다시 깨지는 현상 |
| 관찰 가능한 행동 | 테스트가 보호해야 할 대상. 내부 구조는 아니다 |
| 테스트 피라미드 | 단위 테스트를 가장 많이 두는 전통 모델 |
| 테스트 트로피 | 정적 분석, 단위, 통합, 브라우저리스, Playwright 순으로 쌓고 가운데가 넓은 모델 |
| 정적 분석 | 코드를 실행하지 않고 규칙 위반을 찾는 검사(SonarQube, ArchUnit 등) |
| 단위 테스트 | 비즈니스 로직을 고립해 검증. 빠르고 개수가 많다 |
| 통합 테스트 | Testcontainers의 실제 DB로 서비스와 저장소를 검증. 핵심 층 |
| 브라우저리스 테스팅 | 브라우저 없이 서버 쪽에서 Vaadin UI 전체 흐름을 검증 |
| Playwright | 실제 브라우저로 렌더링, CSS, 다운로드 등을 검증. 선택적으로 사용 |
| 레드-그린-리팩터 | 실패 테스트, 최소 구현, 정리의 TDD 주기 |
| 스펙 커버리지 | 코드 줄이 아니라 스펙의 흐름과 규칙이 검증된 정도 |
| 추적성 | 테스트 이름과 `@UseCase` 어노테이션으로 유스케이스 ID와 연결하는 성질 |

## 3. 자주 놓치는 점

- 브라우저리스 테스트는 브라우저 테스트가 아니다. 서버 쪽 컴포넌트 트리를 직접 다루는 E2E다.
- 유스케이스마다 한 번 판단한다. UI가 있으면 브라우저리스, 없으면 통합 테스트가 주 테스트다.
- 모든 유스케이스에 Playwright가 필요한 것은 아니다.
- TDD를 모든 층에 일률 적용하지 않는다. UI는 구현 뒤에 테스트를 쓴다.
- 테스트가 통과한다고 규칙을 지키는 것은 아니다. 규칙을 어긴 구현에서 실제로 실패하는지 확인한다.
- 변경된 테스트도 새 테스트처럼 검토한다. 문구가 조금만 달라도 엉뚱한 것을 단언할 수 있다.
- 덮이지 않은 코드 줄보다 덮이지 않은 비즈니스 규칙이 더 큰 구멍이다.
