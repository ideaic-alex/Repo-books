# 테스트 트로피와 계층별 전략

테스트를 어떤 비율로 어디에 쌓을지 정하는 모델이 필요하다. 흔히 아는 모델은 테스트 피라미드(test pyramid)다. 바닥에 단위 테스트를 많이 두고, 중간에 통합 테스트를 그보다 적게, 꼭대기에 종단 간(E2E) 테스트를 가장 적게 두라는 모델이다. 브라우저를 띄우는 UI 테스트가 비싸던 전통적 구조를 기준으로 만들어졌다.

원서는 Vaadin과 Spring Boot 같은 프레임워크로 만드는 현대 업무 애플리케이션에는 피라미드가 전부를 말해 주지 못한다고 본다. 대신 켄트 C. 도즈(Kent C. Dodds)가 소개한 테스트 트로피(test trophy)를 권한다. 이 문서는 트로피의 다섯 층과 각 층의 쓰임을 정리한다.

---

## 1. 테스트 트로피란

트로피 모양은 가운데가 불룩하다. 가장 아래에 정적 분석이 있고, 그 위에 순수한 로직을 위한 작은 단위 테스트 층이 있으며, 서비스와 저장소를 위한 큰 통합 테스트 층이 중간을 차지하고, 맨 위에 작은 종단 간 테스트 층이 있다. 넓은 가운데는 의도된 것이다. 통합 테스트가 투자 대비 효과가 가장 좋기 때문이다. 실제 인프라로 실제 행동을 검증하면서 브라우저 비용은 치르지 않는다.

업무 애플리케이션의 흥미로운 행동은 대부분 서비스와 데이터베이스 상호작용에 있다. 고립된 함수나 브라우저에 있지 않다. 그 층을 실제 인프라로 철저히 검증하면 브라우저 자동화의 깨지기 쉬움 없이 확신을 얻는다.

## 2. 유스케이스별 판단 규칙

트로피는 시스템 유스케이스마다 적용할 명확한 결정 규칙을 준다.

- UI가 있는 유스케이스의 주 테스트는 브라우저리스(browserless) 테스트다. 브라우저 없이 화면부터 데이터베이스까지 전체 흐름을 실행한다.
- UI가 없는 유스케이스, 예를 들어 REST API나 백그라운드 작업의 주 테스트는 통합 테스트다. 서비스나 엔드포인트를 직접 호출해 결과를 단언한다.

어느 쪽인지는 스펙이 알려 준다. 테스트마다 고민할 필요 없이 유스케이스마다 한 번만 판단하면 된다.

## 3. 다섯 층 하나씩

### 3-1. 정적 분석

트로피의 바닥이다. SonarQube, Checkstyle, FindBugs, NullAway, ArchUnit 같은 도구가 테스트를 돌리기도 전에 문제를 잡는다. 정적 분석(static analysis)은 코드를 실행하지 않고 읽기만 해서 문제를 찾는 검사다. Spring Boot 프로젝트에서는 ArchUnit이 구조 규칙을 직접 강제할 수 있다. 서비스가 웹 계층에 의존하지 않는다거나, 저장소만 데이터베이스에 접근한다는 규칙이다. 이 검사는 즉시 끝나고 인프라가 필요 없다.

### 3-2. 단위 테스트

단위 테스트(unit test)는 비즈니스 로직을 고립시켜 검증한다. 빠르고 인프라 의존이 없으며 개별 비즈니스 규칙과 사후 조건에 곧바로 대응한다. "작업 제목은 비어 있으면 안 된다"가 단위 테스트다. "30%를 넘는 할인은 관리자 승인이 필요하다"도 그렇다. 개수는 많아야 하지만 트로피의 중심 층은 아니다.

### 3-3. 통합 테스트

통합 테스트(integration test)는 업무 애플리케이션에서 트로피의 핵심이다. 애플리케이션 서비스와 저장소를 실제 데이터베이스에 대고 검증한다. Testcontainers가 테스트 실행 동안 데이터베이스 컨테이너를 띄우고, 테스트는 서비스 메서드를 호출한 뒤 결과 데이터베이스 상태나 반환값을 단언한다.

이 층은 영속화, 트랜잭션, 제약 조건 강제가 유스케이스가 기대하는 대로 함께 동작하는지 확인한다. 기본선은 주 성공 시나리오마다 통합 테스트 하나이고, 데이터베이스 제약이나 검증이 얽힌 예외 흐름은 테스트를 더 둔다.

원서 예제는 `TaskServiceIT` 클래스이고, 핵심만 옮기면 다음과 같다. 어노테이션 `@UseCase`로 유스케이스 ID와 시나리오를 테스트에 붙인다는 점이 중요하다.

```java
@Test
@UseCase(id = "UC-05", scenario = "Main")
void assign_task_to_active_user_succeeds() {
    var task = taskService.assignTask(activeUserId, taskId);
    assertThat(task.getAssignee()).isEqualTo(activeUserId);
}
```

### 3-4. 종단 간 테스트: Vaadin의 두 가지 방식

종단 간(E2E) 테스트는 UI에서 관찰되는 행동을 다룬다. Vaadin 애플리케이션에서는 두 도구가 실용적이고 목적이 다르다.

브라우저리스 테스팅(Browserless Testing)은 Vaadin UI를 브라우저 없이 서버 쪽 시뮬레이션에서 실행한다. 중요한 점은 이것이 브라우저 테스트가 아니라는 것이다. 서버 쪽 컴포넌트 트리와 직접 상호작용한다. 그래서 빠르고 안정적이며 화면 설정 없이 어떤 CI 환경에서도 돌릴 수 있다. 트로피에서 특별한 자리에 있다. UI 층부터 데이터베이스까지 유스케이스 전체를 훑으니 E2E이지만, 브라우저가 필요 없어 속도와 신뢰성은 통합 테스트에 가깝다.

원서 예는 `TaskViewTest`이고 이름은 `assign_to_inactive_user_shows_error`다. 화면으로 이동해 Assign 버튼을 클릭하고 "User is not active" 알림이 뜨는지 확인한다. 시나리오는 UC-05의 대안 흐름 A1이다.

Playwright는 실제 브라우저를 구동한다. 렌더링된 HTML, CSS 동작, 키보드 상호작용, 파일 다운로드처럼 실제 브라우저 환경에 달린 동작을 검증해야 할 때 맞는 선택이다. 느리고 인프라가 더 필요하므로 브라우저 동작 자체가 시험 대상일 때만 골라서 쓴다.

모든 유스케이스에 둘 다 필요하지는 않다. 브라우저 고유의 의미 있는 동작이 없으면 Playwright 테스트가 필요 없다. 어느 층이 적용되는지는 스펙이 알려 준다.

| 쓰임 | 브라우저리스 | Playwright |
|---|---|---|
| 적합한 검증 | 화면 이동, 폼 검증, 컴포넌트 상태, 브라우저 없는 전체 유스케이스 흐름 | 렌더링 결과, CSS, 파일 처리, 브라우저 특유의 상호작용 |

## 4. 트로피 한눈에 보기

원서의 표 6-1은 다섯 층의 특징을 비교한다. 넓은 가운데인 통합 테스트와 브라우저리스 테스트에서 대부분의 유스케이스가 커버된다. 정적 분석과 단위 테스트는 싸고 빠른 토대이고, Playwright는 맨 위에서 브라우저가 관련될 때만 선택적으로 쓴다.

| 층 | 속도 / 브라우저 | 범위 / 양 |
|---|---|---|
| 정적 분석 | 즉시 / 없음 | 코드 규칙 / 모든 코드 |
| 단위 테스트 | 빠름 / 없음 | 비즈니스 로직 / 많음 |
| 통합 테스트 | 중간 / 없음 | 서비스와 DB / 유스케이스별로 가장 많음 |
| 브라우저리스 테스트 | 중간 / 없음 | 전체 UI 흐름 / 유스케이스별로 가장 많음 |
| Playwright | 느림 / 있음 | 브라우저 동작 / 선택적 |

---

## 5. 핵심 정리

- 업무 애플리케이션에는 피라미드보다 가운데가 넓은 테스트 트로피가 맞는다. 통합 테스트가 효과 대비 비용이 가장 좋기 때문이다.
- UI가 있는 유스케이스는 브라우저리스 테스트, UI가 없는 유스케이스는 통합 테스트를 주 테스트로 삼는다. 판단은 테스트마다가 아니라 유스케이스마다 한다.
- 정적 분석(ArchUnit 등)과 단위 테스트는 싼 토대이고, 통합 테스트는 Testcontainers로 실제 DB를 쓴다.
- Playwright는 브라우저 동작 자체가 검증 대상일 때만 선택적으로 쓴다.
- 참고(노트 작성자): 원서의 표 6-1은 추출 과정에서 글자 대소문자가 깨져 있어 열 의미를 보며 정리했다. 위 표의 속도, 양 항목은 그 표를 기준으로 했다.
