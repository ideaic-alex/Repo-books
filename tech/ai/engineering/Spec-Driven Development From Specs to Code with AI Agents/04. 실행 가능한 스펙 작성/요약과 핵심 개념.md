# 요약과 핵심 개념

4장은 스펙의 "무엇"에서 "어떻게 쓰는가"로 시선을 옮긴다. 흐름은 크게 세 덩어리다. 실행 가능하다는 말의 정의와 관찰 가능한 동작 원칙, 모호함을 없애는 두 습관(명시적 규칙, 한 문장 한 규칙), 그리고 유스케이스 요소별 작성법과 인수 기준 도출, 딱 필요한 만큼만 쓰는 원칙이다. 이 문서는 이 세 덩어리를 한 번에 되짚고 핵심 용어를 정리한다.

원서의 요약은 이렇게 이어진다. 실행 가능한 스펙은 추측 없이 구현과 검증이 이어질 만큼 정밀하며, 해석을 없애는 것이 목적이다. 시스템 유스케이스가 중심 산출물이다. 딱 필요한 만큼의 스펙이 대규모 사전 설계를 막고, AI가 개입할수록 명확한 스펙이 AI 출력을 믿을 만하게 만드는 경계가 된다. 다음 장은 스펙이 코드를 직접 이끄는 모습을 다룬다.

---

## 1. 장 전체 흐름

| 순서 | 주제 | 결과 |
|---|---|---|
| 1 | 읽기 쉬움과 실행 가능함의 구분 | 세 시험(해석 일치, 인수 기준 도출, AI 빈칸 채우기) |
| 2 | 관찰 가능한 동작 원칙 | 내부 구현을 뺀 유스케이스, 기술이 바뀌어도 안정적인 계약 |
| 3 | 모호한 표현을 명시적 규칙으로 | "보통, 빠르게" 대신 사전 조건, NFR 참조, 관찰 가능한 결과 |
| 4 | 한 문장 한 규칙 | 검증과 할당처럼 쪼개진 규칙, 작은 diff |
| 5 | 유스케이스 요소별 작성 | 결과형 목표, 출발선 사전 조건, 약한 초안을 고친 주 흐름, 단계에 묶인 A1, 성공/실패 사후 조건, ID가 있는 규칙 |
| 6 | 인수 기준 도출 | 주 흐름은 정상 경로, 대안은 시나리오, 규칙은 단언, 사후 조건은 최종 상태 점검 |
| 7 | 딱 필요한 만큼의 스펙 | 현재 요구만 담은 UC-001, 미래 기능은 새 요구사항으로 |

## 2. 핵심 개념 정리

| 개념 | 한 줄 설명 |
|---|---|
| 실행 가능한 스펙 | 숨은 해석 없이 구현, 테스트, 검토할 수 있는 계약 |
| 관찰 가능한 동작 | 밖에서 보고 검증할 수 있는 행위자 행동과 시스템 응답 |
| 내부 구현 세부 | 트랜잭션, 리포지터리 호출, 내부 메시지 등. 유스케이스에 쓰지 않는다 |
| 모호한 표현 | 보통, 빠르게, 대개, 가능하면, 필요에 따라, 해야 한다 같은 미결정의 신호 |
| 한 문장 한 규칙 | "그리고/또는"이 든 문장은 규칙을 나눠 쓴다는 원칙 |
| 주 성공 시나리오 | 행위자와 시스템이 번갈아 나오는 관찰 가능한 단계의 정상 경로 |
| 대안 흐름 | 특정 단계의 트리거로 시작하는 비즈니스 변형(비활성 사용자 등) |
| 사전 조건 / 사후 조건 | 출발선 / 성공과 실패에서 보장되는 최종 상태 |
| 비즈니스 규칙 | ID를 붙여 직접 가리킬 수 있게 한 짧고 독립적인 규칙 |
| 인수 기준 | 유스케이스에서 도출한 검증 기준. 테스트가 이를 실행 가능하게 만든다 |
| 딱 필요한 만큼의 스펙 | 다음 올바른 한 걸음에 충분하되 필요 이상으로 크지 않은 스펙 |

## 3. 자주 놓치는 점

- 읽기 쉬운 문서와 실행 가능한 문서는 다르다. 문장이 분명하게 들려도 중요한 결정이 빠질 수 있다.
- 모호함은 사라지지 않고 아래로 옮겨 간다. 코드 리뷰, 실패 테스트, 운영 결함, 확인 회의로 나타난다.
- 목표를 행동("작업을 할당한다")이 아니라 결과("다른 활성 사용자에게 작업을 할당한다")로 쓰면 비즈니스 조건이 드러난다.
- 사전 조건에 일반 검증 로직을 넣거나 아예 빼면 흐름이 불완전하거나 가정이 숨는다.
- 한 단계에 검증, 권한 확인, 규칙 적용, 저장을 몰아넣으면 대안·예외 흐름이 정확한 단계를 가리킬 수 없다.
- 결과를 수동태("성공적으로 할당된다")로 끝내면 행위자가 어떻게 아는지 빠진다. 확인 메시지와 보이는 상태 변화를 쓴다.
- 데이터베이스 중단이나 네트워크 타임아웃 같은 기술 실패를 비즈니스 대안 흐름에 섞지 않는다.
- 사후 조건 쓰기가 어렵다면 유스케이스가 아직 덜 명세된 신호다.
- 인수 기준을 못 뽑으면 추측을 시작하지 말고 스펙을 다듬는다. 딱 필요한 만큼이 곧 모호함 허용은 아니다.
- 참고(노트 작성자): 원서 4장의 예제들은 BR-012/BR-013, BR-001/BR-002, UC-001처럼 설명마다 다른 번호를 쓴다. 한 가지 연속된 카탈로그가 아니라 각각의 설명용 예시로 읽으면 된다.
