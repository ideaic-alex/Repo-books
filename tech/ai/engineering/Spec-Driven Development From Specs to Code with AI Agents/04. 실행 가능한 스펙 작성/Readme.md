# 04. 실행 가능한 스펙 작성

이 장은 구조에서 솜씨로 넘어간다. 3장이 유스케이스가 무엇인지를 설명했다면, 4장은 유스케이스를 어떻게 잘 쓰는지를 다룬다. 서로 다른 사람이 읽어도 같은 이해에 이르고, 테스터가 인수 기준을 끌어내고, AI가 빠진 규칙을 지어내지 않아도 되는 수준이 "실행 가능한" 스펙이다.

작업 할당(Assign Task) 예제의 약한 초안과 강한 버전을 나란히 놓고, 관찰 가능한 동작, 한 문장 한 규칙, 유스케이스 요소별 작성법, 인수 기준 도출, 딱 필요한 만큼만 쓰는 원칙을 설명한다.

---

## 1. 핵심 요점

- 실행 가능한 스펙은 코드가 아니라 계약이다. 형식 표기법 없이 Markdown만으로도 충분하다.
- 세 시험으로 점검한다. 두 사람이 다르게 상상하면, 테스터가 인수 기준을 못 뽑으면, AI가 규칙을 지어내야 하면 아직 실행 가능하지 않다.
- 관찰 가능한 동작만 쓴다. 밖에서 검증할 수 없는 문장(트랜잭션, 리포지터리 호출 등)은 유스케이스에 속하지 않는다.
- AI는 모호함을 증폭한다. "보통, 빠르게, 가능하면" 같은 말을 명시적 규칙, 측정 가능한 NFR 참조, 관찰 가능한 결과로 바꾼다.
- 한 문장에 규칙 하나. "그리고/또는"이 있으면 쪼갠다. 작은 단위가 diff와 동기화를 쉽게 한다.
- 개요의 목표는 결과로, 사전 조건은 출발선으로, 주 흐름은 관찰 가능한 단계로, 대안 흐름은 단계에 묶인 트리거와 최종 상태로, 사후 조건은 성공과 실패로, 비즈니스 규칙은 ID를 붙여 쓴다.
- 인수 기준은 유스케이스에서 도출한다. 주 흐름은 정상 경로, 대안 흐름은 시나리오, 규칙은 단언, 사후 조건은 최종 상태 점검이 된다.
- 딱 필요한 만큼의 스펙을 쓴다. 오늘의 동작은 명시적으로, 내일의 동작은 추측하지 않는다.
