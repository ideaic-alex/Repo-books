# 유스케이스 각 요소 작성법

AIUP에서 시스템 유스케이스는 실행 가능한 스펙의 중심 산출물이다. 요구사항은 왜 중요한지를 설명하고, 엔터티 모델은 도메인의 공통 언어를 정의하며, 시스템 유스케이스는 목표를 이루려고 시스템이 어떻게 동작하는지를 적는다. 그래서 유스케이스가 프로세스의 한가운데에 놓인다.

구조는 3장에서 소개했으므로, 여기서는 각 부분을 어떻게 써야 단순한 서술이 아니라 실행 가능한 글이 되는지에 집중한다. 개요, 사전 조건, 주 성공 시나리오, 대안 흐름, 사후 조건, 비즈니스 규칙의 여섯 요소를 차례로 본다. 요리 레시피에 비유하면 개요는 요리 이름과 완성 사진, 사전 조건은 준비물, 흐름은 조리 순서, 사후 조건은 완성된 모습의 기준이다.

---

## 1. 유스케이스가 계약인 이유

시스템 유스케이스는 행위자와 시스템 사이의 의미 있는 상호작용 하나를 정의한다. 시작점, 정상적인 성공 경로, 관련된 대안, 보장되는 결과를 적어 이해관계자의 의도를 명시적인 행동 계약으로 바꾼다. 관찰 가능한 동작을 쓰기 때문에, 코드로 생각하지 않는 역할도 이해할 수 있다.

- 비즈니스 이해관계자는 동작이 기대와 맞는지 검증한다.
- 개발자는 구현 작업을 도출한다.
- 테스터는 인수 기준을 도출한다.
- AI 도구는 사용자가 아마 이런 뜻이었을 것이라고 추측하는 대신 안정적인 계약을 근거로 일한다.

## 2. 개요를 잘 쓰기

개요는 유스케이스의 정체성과 의도를 정한다. 유스케이스 ID는 안정적 추적성을 만들고, 이름은 목표를 분명하고 구체적으로 말해야 한다. 주 행위자는 상호작용을 시작하는 쪽을 밝히고, 목표는 행위자의 관점에서 성공한 결과를 서술한다.

흔한 약점은 목표를 결과가 아니라 행동으로 쓰는 것이다. "Assign task(작업을 할당한다)"는 행동의 이름이다. "Assign a task to another active user(다른 활성 사용자에게 작업을 할당한다)"는 성공한 결과를 서술하고, 이미 중요한 비즈니스 조건(대상 사용자는 활성이어야 한다)을 암시한다. 개요는 독자를 빠르게 안내하되 전체 흐름을 설명하려 들면 안 된다. 그것은 주 시나리오와 대안 흐름의 일이다.

## 3. 좋은 사전 조건 쓰기

사전 조건은 유스케이스가 시작되기 전에 이미 참이어야 하는 것이다. 흐름 안에서 하는 검증이 아니라 출발선을 정하는 가정이다. 예는 이렇다.

- 행위자가 인증되어 있다.
- 작업이 존재한다.
- 작업이 현재 할당되지 않은 상태다.

이 문장들은 유스케이스가 유효한 맥락을 분명히 한다. 하나라도 참이 아니면 유스케이스는 기술한 형태로 시작하지 않는다. 다른 유스케이스가 적용되거나, 비즈니스 대안 흐름을 따로 정해야 한다.

팀이 사전 조건을 잘못 쓰는 방식은 두 가지다. 아예 빼서 숨은 가정을 만들거나, 일반적인 검증 로직을 거기에 넣어 흐름을 불완전하게 만든다. 좋은 사전 조건은 질문 하나에 답한다. 기술된 상호작용의 첫 단계가 일어나기 전에 이미 무엇이 참이어야 하는가?

## 4. 강한 주 성공 시나리오 쓰기

주 성공 시나리오는 행위자의 첫 행동부터 성공적인 결과까지의 정상 경로다. 서술형 요약이 아니라 관찰 가능한 단계의 순서다. 각 단계는 순서가 있고, 밖에서 보이며, 능동적 표현으로 쓰고, 하나의 동작에 집중한다. 행위자 행동과 시스템 응답이 번갈아 나오면 따라가기 쉬운 자연스러운 리듬이 생긴다.

```text
1 행위자가 작업 상세를 연다.
2 시스템이 작업 상세와 활성 사용자 목록을 표시한다.
3 행위자가 대상 사용자를 선택한다.
4 시스템이 선택한 사용자가 활성인지 검증한다.
5 시스템이 작업을 선택한 사용자에게 할당한다.
6 시스템이 할당을 확인해 준다.
```

모든 단계를 밖에서 이해하고 검증할 수 있다. 약한 주 흐름의 특징은 기술적 세부가 들어가고, 중요한 결정이 빠지고, 여러 규칙이 한 단계에 섞이고, "요청을 처리한다" 같은 흐릿한 표현이 있고, 눈에 보이는 결과 없이 끝난다는 것이다. 잘 쓴 주 흐름은 테스터가 이미 테스트 케이스를 스케치할 만큼 구체적이다.

### 4-1. 약한 초안 해부

책은 같은 유스케이스의 약한 첫 초안을 놓고 단계별로 어디가 실패하는지 짚는다.

| 약한 단계 | 문제 |
|---|---|
| 2. 시스템이 요청을 처리하고 필요한 데이터를 불러온다 | 관찰할 수 없다. 내부 작업이어서 테스터가 단언을 쓸 수 없다 |
| 3. 사용자가 누군가를 골라 폼을 제출한다 | 결정이 숨었다. 어떤 사용자가 선택 가능한지, 비활성 사용자가 목록에 나오는지, 선택 중 무엇이 보이는지 열려 있다 |
| 4. 시스템이 입력 검증, 권한 확인, 비즈니스 규칙 적용, 데이터베이스 갱신을 한다 | 독립된 규칙 네 개가 한 단계에 있다. 하나가 바뀌면 어느 단계를 고칠지 불분명하고, 대안·예외 흐름이 정확한 단계 번호를 가리킬 수 없다 |
| 5. 작업이 성공적으로 할당된다 | 수동태다. 결과는 말하지만 행위자가 어떻게 아는지 없다. 확인 메시지도, 보이는 상태 변화도, 알림도 없다 |

초안의 1단계(사용자가 할당 화면을 연다)는 문제로 지적되지 않았다. 권장 버전은 이 문제를 모두 해결한다. 각 단계가 관찰 가능하고, 한 가지 동작만 말하며, 행위자와 시스템이 분명히 번갈아 나오고, 결과가 데이터베이스에서만이 아니라 사용자에게 보인다. 이 차이는 문체의 문제가 아니다. 약한 주 흐름은 대안 흐름을 쓰기 어렵게 하고, 테스트 도출을 어렵게 하며, AI 에이전트에게 해석의 여지를 너무 많이 준다. 강한 주 흐름은 구현이 바뀌어도 살아남는 안정적 계약을 정의한다.

## 5. 쓸모 있는 대안 흐름 쓰기

대안 흐름은 주 성공 시나리오에서 예상되는 이탈을 기술한다. 무작위 엣지 케이스가 아니라 의도적으로 다뤄야 하는 의미 있는 비즈니스 변형이다. 선택한 대상 사용자가 비활성인 것은 기술적 실패가 아니라 스펙에 보여야 하는 비즈니스 관련 대안이다.

각 대안 흐름은 주 성공 시나리오의 특정 단계에 묶인 분명한 트리거로 시작해야 한다. 그래야 이탈이 어디서 일어나는지 정확히 알 수 있다. 원서 예는 이렇다.

```text
A1. 선택한 사용자가 비활성
트리거: 4단계에서 선택한 사용자가 비활성이다.
흐름:
 1 시스템이 행위자에게 선택한 사용자가 작업을 받을 수 없음을 알린다.
 2 시스템이 작업을 할당하지 않는다.
 3 유스케이스가 작업 할당의 변경 없이 끝난다.
```

"오류가 표시된다"라고만 쓰는 것보다 훨씬 강하다. 조건, 응답, 최종 상태가 모두 명시되기 때문이다.

### 5-1. 비즈니스 대안과 기술적 실패를 구분

흔한 실수는 비즈니스 대안과 기술적 실패를 한 범주에 섞는 것이다. 둘은 구분해야 한다.

| 구분 | 예 | 다루는 곳 |
|---|---|---|
| 비즈니스 관련 대안 | 비활성 사용자, 권한 없음, 이미 완료된 작업 | 유스케이스의 대안 흐름 |
| 기술적 처리 | 데이터베이스 중단, 네트워크 타임아웃 | 기술적 처리. 비즈니스 유스케이스를 지배해선 안 된다 |

유스케이스는 비즈니스 관점에서 기대되는 시스템 동작을 정의한다.

## 6. 명확한 사후 조건 쓰기

사후 조건은 유스케이스가 끝난 뒤 보장되는 것을 정한다. 결과를 고정하는 닻이라서 중요하다. 사후 조건이 없으면 흐름이 그럴듯해 보여도 실제 결과는 불분명하다.

- 성공 사후 조건: 성공적으로 완료된 뒤 참이어야 하는 것(예: 작업이 선택한 활성 사용자에게 할당됨).
- 실패 사후 조건: 유스케이스가 성공하지 못했을 때 그대로 참으로 남는 것이 보장되는 것(예: 작업 할당이 변경되지 않은 채 남음).

사후 조건은 테스트를 직접 개선한다. 좋은 테스트는 메시지가 나왔는지만 보지 않고 최종 상태가 사후 조건과 맞는지 확인한다. 사후 조건을 쓰기 어렵다면 대개 유스케이스가 아직 덜 명세되었다는 신호다.

## 7. 명시적인 비즈니스 규칙 쓰기

비즈니스 규칙은 산문 속에 묻히지 않고 눈에 보이며 재사용할 수 있어야 한다. 자기만의 식별자와 분명한 문구를 가지면, 여러 유스케이스와 테스트, 리뷰 토론에서 참조하기 쉽다. 예는 이렇다.

- BR-001: 활성 사용자만 작업 할당을 받을 수 있다.
- BR-002: 완료된 작업은 재할당할 수 없다.

규칙은 짧고, 정확하고, 서로 독립적이다. 숨은 규칙은 결함의 흔한 원인이다. 유스케이스가 완전해 보여도 핵심 제약이 단락 깊숙한 문장 하나에만 있으면 사람도 AI도 놓치기 쉽다. 리뷰에서 던질 좋은 질문은 이것이다. 이 규칙이 중요하다면 그것을 직접 가리킬 수 있는가? 아니라면 명시적인 규칙으로 올려야 한다.

## 8. 핵심 정리

- 개요의 목표는 행동이 아니라 결과로 쓴다. "Assign task"가 아니라 "다른 활성 사용자에게 작업을 할당한다"이다.
- 사전 조건은 흐름 안의 검증이 아닌 출발선이다. 빼먹거나 검증 로직을 넣는 것이 흔한 오용이다.
- 주 성공 시나리오는 관찰 가능하고, 하나의 동작씩이고, 능동적이며, 행위자와 시스템이 번갈아 나오고, 눈에 보이는 결과로 끝난다.
- 대안 흐름은 특정 단계에 묶인 트리거, 응답, 최종 상태를 쓰고, 비즈니스 대안과 기술적 실패를 구분한다.
- 사후 조건은 성공과 실패 양쪽에서 보장되는 상태를 적고, 비즈니스 규칙은 ID를 붙여 직접 가리킬 수 있게 한다.
