# SPARQL로 쓰는 추론 규칙

앞 문서에서 rdfs:subClassOf의 뜻이 "IF ... THEN ..." 꼴의 추론 규칙 하나라는 것을 봤다. 이 문서는 그 규칙을 SPARQL로 적는 방법과, 왜 의미를 추론으로 정의하는 방식이 웹 환경에서 잘 맞는지를 다룬다.

원서는 이후 RDFS와 OWL의 추론을 설명할 때 SPARQL CONSTRUCT를 계속 쓴다. 그래서 이 표기에 익숙해지면 뒤 장들이 훨씬 쉬워진다.

---

## 1. 검색 쿼리로 직접 풀기

추론 없이도 Shirts를 모두 찾을 수는 있다. 6장에서 배운 SPARQL의 경로 기능을 쓰면 된다. 원서가 처음 보여 주는 쿼리는 다음과 같다.

```sparql
SELECT ?item
WHERE {?class rdfs:subClassOf :Shirts .
       ?item a ?class . }
```

이 쿼리는 Shirts의 하위 클래스를 찾고, 그 클래스에 속한 개체를 가져온다. 쓸 만한 실무식 접근이지만, 원서가 다른 곳에서 보여 주는 형태(`rdfs:subClassOf*`)와 달리 이 쿼리는 한 단계 아래 하위 클래스만 본다. 손자 클래스까지 찾으려면 경로에 `*`를 붙여야 한다. 원서도 뒤에서 `*`가 들어간 버전을 쓴다.

RDFS는 이렇게 "쿼리를 어떻게 쓰느냐"로 의미를 정하지 않는다. 더 선언적으로, 의미를 추론으로 준다. 시맨틱 웹에서 추론은 "주어진 정보로부터 이미 말해진 것처럼 취급할 수 있는 다른 정보를 알아내는 것"이다.

## 2. CONSTRUCT로 추론 규칙 적기

SPARQL CONSTRUCT는 데이터에서 찾은 그래프 패턴을 바탕으로 새 트리플을 만든다. 그래서 추론 규칙을 적기에 알맞다. 타입 전파 규칙은 이렇게 쓴다.

```sparql
CONSTRUCT {?r rdf:type ?B}
WHERE { ?A rdfs:subClassOf ?B .
        ?r rdf:type ?A }
```

WHERE 부분이 "IF" 조건이고, CONSTRUCT 부분이 "THEN" 결론이다. 원서는 이 방식이 정확하고 간결하며, SPARQL 쿼리 예제도 많이 보여 줄 수 있고, SPARQL과 다른 시맨틱 웹 언어의 관계도 드러낸다고 설명한다.

| 방식 | 하는 일 | 의미를 어디에 두는가 |
|---|---|---|
| SELECT 쿼리로 직접 탐색 | 하위 클래스를 따라가며 원하는 개체를 가져온다 | 쿼리를 쓰는 사람의 몫 |
| CONSTRUCT 규칙 | 조건이 맞는 곳에 새 트리플을 만들어 낸다 | 규칙 자체 |
| 추론 엔진 | 표준에 정의된 규칙을 자동으로 적용한다 | 표준(RDFS, OWL)이 정한 추론 패턴 |

표에서 아래로 갈수록 쿼리 작성자의 부담이 줄고 의미가 데이터 모델 쪽으로 옮겨 간다.

## 3. SHACL-Rules로 규칙을 모델에 붙이기

SPARQL을 추론 규칙을 적는 데 쓰는 것은 책을 쓰기 위한 편의만이 아니다. SPARQL 자체가 추론 언어의 바탕이 될 수 있다. 그런 제안 중 하나가 SHACL-Rules(Steyskal 외, 2017)다. SHACL-Rules에는 SPARQL로 추론을 다루는 여러 구문이 있지만, 이 책에서는 특정 CONSTRUCT 쿼리를 특정 모델의 추론 정의로 쓰라고 지정하는 수단 정도로 쓴다.

예를 들어 Shirt 클래스의 모든 구성원에게 타입 전파 규칙이 적용된다고 선언하려면 다음처럼 쓴다.

```turtle
:Shirt sh:rule "CONSTRUCT { $this rdf:type ?B }
  WHERE {?A rdfs:subClassOf ?B .
         $this rdf:type ?A }" .
```

여기서 `$this`는 특별한 뜻을 가진 변수다. sh:rule로 붙은 클래스의 구성원, 이 예에서는 :Shirt의 모든 구성원을 가리킨다. 원서는 앞으로 RDFS와 OWL의 추론이 SPARQL로 쓸 수 있는 구조와 어떻게 연결되는지 보여 주려고 SHACL-Rules를 가끔 쓴다고 밝힌다.

## 4. 추론으로 의미를 정의하면 좋은 점

의미를 추론 패턴으로 정의하는 것은 우아하다. 원서가 말하는 실용적인 이유는 웹이라는 환경에 있다.

우리 데이터는 웹에 산다. 여러 출처의 데이터와 합쳤을 때도 일관되게 동작해야 한다. 용어의 의미를 추론에 두면, 처음 보는 용어 조합이 나와도 의미를 풀기 쉽다. 예를 들어 한 클래스가 두 클래스의 하위 클래스로 지정되는 일은 충분히 있을 수 있다. 이런 선언의 뜻을 정해야 한다.

시소러스처럼 비공식으로 의미를 정하는 환경이라면, 그 뜻은 사람이 토론해서 정한다. "넓은 용어"의 감은 분명하니 그 직관으로 "그런 상황은 막자", "관련된 모든 용어의 검색 동작을 정의하자" 같은 입장을 주장할 수 있다. 하지만 비공식으로 정의된 구성 요소는 새로운 조합이 나올 때마다 합의나 권위 있는 선언으로 해결해야 한다.

### 다중 상속

OOP에서도 같은 문제가 있다. 클래스 하나가 서로 다른 두 클래스의 하위 클래스인 경우로, 다중 상속(multiple inheritance)이라고 부르고 이 문제를 두고 말이 많다. 언어마다 답이 다르다.

| 체계 | 다중 상속에 대한 답 |
|---|---|
| C# | 허용하지 않는다 |
| Java | 인터페이스 상속과 구현 상속을 구별한다 |
| Common Lisp Object System | Meta-Object Protocol 같은 복잡한 정의 체계를 쓴다 |
| RDFS (추론 기반 시맨틱 웹) | 기본 추론 규칙이 상호작용한 결과가 곧 답이다 |

각각은 해당 언어의 설계 사정에 맞춘 답이다. 반면 RDFS는 따로 토론이나 설계 결정이 필요 없다. 규칙을 두 번 적용하면 된다. A가 B의 하위 클래스이고 C의 하위 클래스이기도 하면, A의 개체 x는 B의 개체이고 C의 개체이기도 하다.

```turtle
:A rdfs:subClassOf :B .
:A rdfs:subClassOf :C .
:x rdf:type :A .
```

이 세 트리플에서 `:x rdf:type :B`와 `:x rdf:type :C`가 모두 나온다. (이 예시는 원서 문장을 코드로 옮긴 것이다.) 단순한 규칙 하나가 어떤 맥락에서도 subClassOf의 뜻을 정해 주므로, 여러 출처의 데이터를 합치다가 처음 보는 관계 조합이 생기기 마련인 시맨틱 웹에 특히 잘 맞는다.

---

## 5. 정리

- 추론 규칙은 SPARQL CONSTRUCT로 간결하게 쓸 수 있다. WHERE가 조건, CONSTRUCT가 결론이다.
- SHACL-Rules는 CONSTRUCT 쿼리를 클래스에 붙여 그 모델의 추론 정의로 쓰는 제안이고, `$this`는 그 클래스의 구성원을 가리킨다.
- 의미를 추론으로 정하면 여러 출처가 섞여 처음 보는 조합이 생겨도 기본 규칙의 결과로 의미가 정해진다.
- 다중 상속은 OOP 언어마다 해법이 다르지만, RDFS에서는 규칙을 두 번 적용하는 것으로 충분하다.
