# 좋은 모델링과 나쁜 모델링

이 장은 모델을 처음부터 어떻게 시작하고, 이름을 어떻게 짓고, 모델이 의도대로 동작하는지 어떻게 확인하는지를 다룬다. 앞 장들이 모델의 재료를 알려 줬다면 이 장은 그 재료를 쓰는 습관을 다룬다. 책이 내놓는 조언은 법칙이 아니라 권장 습관이며, 따라 하면 안 되는 예제에는 안티패턴이라는 딱지가 붙어 있다.

핵심은 한 가지다. 모델이 쓸모 있는지는 이름이 그럴듯한지가 아니라 모델이 내놓는 추론이 의도와 맞는지로 판단한다. 안티패턴 다섯 가지를 그 눈으로 하나씩 점검한다.

---

## 1. 핵심 요점

- 모델은 웹에서 찾아 쓰기, 조직의 기존 자산 활용, 처음부터 설계 세 가지 방법으로 시작할 수 있다.
- 시맨틱 웹 모델은 다른 출처의 정보와 합쳐지므로 지금의 요구사항뿐 아니라 예상되는 변화까지 대비한다. 시나리오와 역량 질문으로 목적과 범위를 잡는다.
- 이름만 보고 뜻을 믿는 희망적 이름 붙이기를 조심한다. 모델이 말한 바는 추론으로 확인한다.
- URI의 로컬 이름은 불투명한 이름과 읽히는 이름에 각각 장단점이 있고, 이름을 바꿔야 할 때는 FIBO처럼 폐기 표시와 `owl:equivalentClass`로 옛 URI를 살린다.
- 클래스와 개체는 구성원을 상상할 수 있는지, 속성의 구체적 값을 아는지로 가른다.
- 클래시즘, 클래스 펀닝, 배타성, 객체화, 개념 팽창이 이 장의 안티패턴이다. 앞의 셋은 제약, 클래스-개체 거울 패턴, 교집합으로 고친다.
- 객체화는 요구사항 자체가 AAA, 열린 세계, 이름 중복 허용과 충돌하므로 모델을 고쳐서 해결되지 않는다.
- 경계 사례로 모델을 시험해 어떤 추론이 나오는지 보는 모델 테스트가 가장 강력한 점검 수단이다.
