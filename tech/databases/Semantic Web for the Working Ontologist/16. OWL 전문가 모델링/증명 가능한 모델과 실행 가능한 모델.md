# 증명 가능한 모델과 실행 가능한 모델

OWL 2의 하위 집합들이 갈라지는 뿌리에는 "왜 모델을 만드는가"라는 철학 차이가 있다. 한쪽은 모델의 의미를 수학적으로 따져서 확실히 증명하고 싶어 하고, 다른 쪽은 모델을 프로그램처럼 돌려서 데이터를 합치고 싶어 한다. 이 문서는 두 입장을 비교하고, 그 사이에서 판정 가능성(decidability)이라는 개념이 어떤 역할을 하는지 설명한다.

---

## 1. 증명 가능한 모델

### 1.1 정확한 뜻을 따지고 싶은 이유

형식을 갖춘 모델링(formal modeling)을 하는 이유는 우리 모델이 무슨 뜻인지를 정확하게 해 두기 위해서다. 시맨틱 웹에서는 서로 다른 출처의 개념이 같은 것을 가리키는지 의심 없이 판단할 수 있게 된다는 점이 특히 중요하다.

책의 예시를 보자. 내가 정의한 "제임스 딘 영화"는 제임스 딘이 출연한 영화다. 다른 사람이 정의한 "제임스 딘 영화"는 제임스 딘에 관한 영화일 수도 있고, 제목에 제임스 딘이 들어간 영화일 수도 있다. 이름만 보면 똑같지만 정의는 다르다. 이름만으로는 이 차이를 알 수 없고, 형식을 갖춘 정의가 있어야 차이가 드러난다. 정의가 형식을 갖추면 두 클래스가 같은지, 한쪽이 다른 쪽을 포함하는지, 서로 무관한지를 자동으로 가려낼 수 있다.

### 1.2 OWL의 논리적 바탕

이 철학이 OWL을 논리로 정의하게 만들었다. OWL의 구성 요소는 하나하나가 형식 논리의 문장이다. OWL DL이 쓰는 논리 체계의 이름은 기술 논리(Description Logic)다. 이름 그대로 클래스, 개체, 그 사이 관계를 형식적으로 기술하는 논리다. 이 책 전체에서 다룬 OWL의 추론이 정확히 무엇인지는 기술 논리에 바탕을 둔 모델 이론(model theory)이 정한다.

논리를 바탕으로 삼으면 좋은 점이 많다. 수십 년, 길게는 수 세기에 걸쳐 쌓인 논리학의 성과를 그대로 쓸 수 있다. 논리 구조의 성질도 잘 알려져 있고, 언어가 필요로 하는 모든 추론을 논리가 정의해 준다.

### 1.3 걸림돌: 컴퓨터가 자동으로 처리할 수 있는가

문제는 컴퓨터다. 우리는 이 논리를 컴퓨터가 자동으로 처리해서, 주어진 모델이 함의하는 모든 추론을 알아내길 바란다. 내 "제임스 딘 영화"와 네 "제임스 딘 영화"가 정말 같다고 자동으로 확인하려면, 한쪽에서 참인 사실이 다른 쪽에서도 모두 참이고, 거짓인 사실도 모두 거짓임을 보여야 한다.

만약 이런 자동화가 원리적으로 불가능한 논리를 바탕으로 삼으면 어떻게 되는가. 두 개념이 같은지조차 정확히 판정하지 못할 수 있다. 증명 가능한 연결을 모델링의 본질로 여긴다면 그것은 실패다. 어떤 질문이 유한한 시간 안에 자동으로 답을 얻을 수 없는 논리는 받아들일 수 없다.

### 1.4 판정 가능성이란

논리학에서 이 문제를 판정 가능성이라고 부른다. 정의는 이렇다. 어떤 체계에 대해, 그 체계의 모든 식이 성립하는지(정리인지) 아닌지를 가려내는 효과적인 방법이 존재하면 판정 가능(decidable)하고, 없으면 판정 불가능(undecidable)하다.

| 구분 | 뜻 | 일상 비유 |
|---|---|---|
| 판정 가능 | 어떤 입력이 와도 유한한 시간 안에 맞다/아니다를 알려 주는 방법이 있다 | 어떤 문제를 줘도 반드시 답을 내는 계산기 |
| 판정 불가능 | 일부 입력에서는 그런 방법이 원리적으로 없다 | 어떤 문제는 영원히 끝나지 않을 수 있는 계산기 |

판정 가능성에서 가장 놀라운 점은 판정 불가능해지기가 얼마나 쉬운가이다. 논리가 형식적이라서 인내심과 공학 기술만 충분하면 어떤 논리든 올바르고 완전하게 처리하는 프로그램을 만들 수 있을 것 같다. 하지만 이 개념의 중요성을 확립한 가장 영향력 있는 정리 중 하나는, 정수 산술을 할 수 있는 정도의 아주 단순한 논리 체계조차 판정 불가능하다는 점을 보여 준다. 쓸모 있는 내용을 표현하면서도 판정 가능한 논리 체계를 찾아내는 일은 오히려 어렵다.

### 1.5 OWL DL과 타블로 알고리즘

이 아슬아슬한 줄타기가 OWL DL이라는 하위 집합이 생긴 동기다. OWL DL은 판정 가능한 특정 기술 논리에 바탕을 둔다. 따라서 OWL DL로 쓴 어떤 모델이든 입력으로 받아 다음 세 가지를 알아내는 알고리즘을 설계할 수 있다.

- 어떤 클래스가 다른 어떤 클래스와 동치인가
- 어떤 클래스가 다른 어떤 클래스의 하위 클래스인가
- 어떤 개체가 어떤 클래스의 구성원인가

가장 널리 쓰이는 알고리즘은 타블로 알고리즘(Tableau Algorithm)이다. 기본 원리는 클래스 사이에 가능한 관계를 모두 추적하면서, 모델의 논리 문장과 어긋나는 것을 하나씩 배제하는 것이다. 이 알고리즘은 OWL DL 모델의 모든 함의를 유한한 시간 안에 찾아낸다고 보장된다. 시간이 꽤 오래 걸릴 수도 있다는 단서가 붙는다. 또한 모델이 실제로 OWL DL에 속하는지도 자동으로 판별할 수 있어서, 보장이 성립하지 않는 경우에는 프로그램이 그 사실을 알려 줄 수도 있다.

정리하면 OWL DL로 모델링하는 방식은 모델이 분명하고 모호하지 않으며 기계가 처리할 수 있어야 한다는 직관을 뒷받침한다. 타블로 알고리즘은 컴퓨터 시스템이 클래스의 동치 여부를 판단하는 도구가 된다.

## 2. 실행 가능한 모델

### 2.1 데이터를 합치는 레시피로서의 모델

시맨틱 웹에서 모델을 만드는 다른 동기는 여러 출처의 정보를 모아 한 분야에 대한 통합된 그림을 만드는 것이다. 한 출처는 호텔 체인이 어느 장소에 호텔을 두는지를 알려 주고, 다른 출처는 특정 장소에 어떤 호텔이 있는지를 알려 준다고 하자. 형식 모델은 이 둘을 서로의 역(inverse)으로 취급해서 합칠 수 있다고 알려 준다. 모델이 불완전한 정보에 새 정보를 채우는 방법을 알려 주는 레시피가 되어, 다른 출처와 합칠 수 있게 된다.

이렇게 보면 모델은 프로그램과 닮았다. 데이터를 다른 상황에서 쓸 수 있도록 바꾸는 방법을 간결하게 적은 것이다.

### 2.2 판정 불가능한 언어로도 프로그램은 짠다

이 관점에서는 판정 가능성이 어떤 의미를 가질까. FORTRAN이나 Java 같은 일반 프로그래밍 언어도 이 의미에서 판정 불가능하다. 이 사실은 보통 정지 문제(Halting Problem)로 설명한다. 임의의 프로그램과 그 입력을 받아서 그 프로그램이 멈추는지 알려 주는 프로그램은 원리적으로 만들 수 없다.

그런데도 이 언어들은 훌륭한 공학 언어로 자리 잡았다. 정확성이나 의미조차 자동으로 판정할 수 없는데 어떻게 프로그램을 짤까. 그 답이 곧 프로그래밍이라는 일의 본질이다. 임의의 프로그램이 끝나는지는 일반적으로 알 수 없어도, 지금 짜는 특정 프로그램이 끝나고 어떤 답을 내는지는 대개 알 수 있다. 좋은 프로그램을 만드는 기술은 모든 입력에서 끝나는 프로그램, 더 나아가 관심 있는 입력에서 실제로 잘 동작하는 프로그램을 쓰는 것이다.

### 2.3 모델도 디버깅하는 것이다

이런 시각에서는 판정 가능성이 일차적 관심사가 아니다. 모델도 프로그램처럼 설계한다. 어떤 상황에서 모델이 제대로 동작하지 않으면 엔지니어가 올바르게 동작할 때까지 디버깅한다. 모든 추론을 반드시 찾아 준다는 알고리즘의 보장이 필요하지 않으니, OWL을 처리하는 엔진의 선택 폭이 훨씬 넓어진다. 규칙 시스템, 데이터로그(datalog) 엔진, 데이터베이스, 심지어 SPARQL까지 쓸 수 있다.

### 2.4 웹에서는 완벽함이 목표가 아닐 수 있다

웹 응용에서는 분석하려는 데이터셋이 아주 크거나, 계속 바뀌거나, 정돈되어 있지 않은 경우가 많다. 어설픈 휴리스틱 프로그램이 웹에서 긁어 온 데이터를 분석하는 데 100% 올바른 모델이 꼭 필요한지 물을 수 있다. 사람들이 구글을 쓰는 이유는 항상 완벽한 답은 못 줘도 좋은 답을 자주 찾아 주기 때문이다. 시맨틱 웹 시스템 중에는 이런 거칠고 현실적인 웹 응용을 겨냥한 것이 있고, 이런 곳에서는 증명 가능한 정확성보다 효율적인 계산이 더 중요하다.

### 2.5 의미를 정하는 방식이 다르다

이 실행 가능한 모델링 방식이 OWL 하위 집합 일부의 주된 동기다. 이 하위 집합에서 구성 요소의 의미는 프로그래밍 언어의 구성 요소 의미와 비슷한 방식으로 정해진다. 절차적 언어에서 한 문장의 의미는 그 문장을 실행할 때 기계가 하는 동작으로 정해진다. 마찬가지로 실행 가능한 모델의 의미는 추론 엔진이 그 모델을 처리할 때 하는 동작으로 정해진다. 모델이 정보를 일정한 구조로 바꾸는 방법을 서술하기 때문에 정보 통합이 이루어진다.

## 3. 두 철학 비교

| 비교 항목 | 증명 가능한 모델 | 실행 가능한 모델 |
|---|---|---|
| 모델을 만드는 목적 | 의미를 정확히 하고 개념이 같은지 증명한다 | 여러 출처의 정보를 합치고 변환한다 |
| 모델을 보는 눈 | 논리 문장의 모음 | 프로그램에 가까운 것 |
| 의미를 정하는 방법 | 기술 논리의 모델 이론 | 추론 엔진이 수행하는 동작 |
| 판정 가능성 | 핵심 조건 | 주된 관심사가 아니다 |
| 오류가 났을 때 | 보장이 깨졌다고 알려 준다 | 엔지니어가 디버깅한다 |
| 처리 도구 | 타블로 알고리즘 | 규칙 시스템, 데이터로그, 데이터베이스, SPARQL 등 |
| 어울리는 환경 | 정확성이 중요한 모델링 | 크고 지저분하며 변하는 웹 데이터 |
| 대응하는 하위 집합 | OWL 2 DL | 다음 문서에서 볼 EL, QL, RL |

표에서 보듯 두 철학은 서로 틀린 것이 아니라 목적이 다르다. 같은 OWL 용어를 쓰지만, 한쪽은 "모든 답을 보장하는 완전한 추론"을, 다른 쪽은 "쓸 만한 속도와 기존 기술과의 결합"을 중시한다.

## 4. 판정 가능성 개념 정리

| 용어 | 뜻 | 이 장에서의 역할 |
|---|---|---|
| 판정 가능성(decidability) | 모든 식이 성립하는지 가려내는 방법이 존재하는 성질 | OWL DL이 지키려는 성질 |
| 기술 논리(Description Logic) | 클래스, 개체, 관계를 형식적으로 기술하는 논리 | OWL DL의 논리적 바탕 |
| 타블로 알고리즘 | 가능한 관계를 추적하며 모순되는 것을 배제하는 알고리즘 | OWL DL 추론의 대표 알고리즘 |
| 정지 문제 | 임의의 프로그램이 멈추는지 판정하는 문제 | 일반 프로그래밍 언어가 판정 불가능한 예 |
| 모델 이론 | 논리 문장의 의미를 수학적으로 정하는 이론 | OWL 추론의 공식 정의 |

판정 불가능한 언어로도 실무에서 프로그램을 짜는 것처럼, 모델도 그렇게 다룰 수 있다는 것이 이 문서의 핵심이다. 반대로 판정 가능성을 포기하지 않으려면 표현력을 어느 정도 제한해야 한다. 이 긴장이 바로 하위 집합이 필요해진 이유다.
