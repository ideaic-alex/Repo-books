# 선수 조건 다시 보기

12장에서 선수 조건(prerequisite)을 allValuesFrom으로 모델링했다. 어떤 질문의 선수 조건이 모두 충족되었는지를 "모든 값이 SelectedAnswer"라는 제약으로 쓴 것이다. 그때 남은 문제가 열린 세계 가정이었다. 새 선수 조건을 누가 언제 추가할지 모르는데, 모든 조건이 충족되었다고 어떻게 말할 수 있을까.

이 문서는 선수 조건 예제를 이용해 세계를 닫는 여러 방법을 정리한다. 기수 0으로 "선수 조건이 없다"고 말하는 방법, 개수를 세어 "이게 전부다"라고 말하는 방법을 보고, 마지막에 allValuesFrom, someValuesFrom, hasValue가 값의 존재를 각각 어떻게 보장하는지 비교한다.

---

## 1. 복습: 활성화된 질문

12장의 모델은 선수 조건이 모두 선택된 답변이면 그 질문이 EnabledQuestion이라는 것이었다.

```turtle
q:hasPrerequisite a owl:ObjectProperty .
[ a owl:Restriction ;
  owl:onProperty q:hasPrerequisite ;
  owl:allValuesFrom q:SelectedAnswer ]
  rdfs:subClassOf q:EnabledQuestion .
```

제약이 이름 있는 클래스 EnabledQuestion의 하위 클래스라는 점을 기억하자. 어떤 개체가 이 제약을 만족하면, 즉 값이 모두 SelectedAnswer의 멤버이면 그 개체는 EnabledQuestion의 멤버이기도 하다.

---

## 2. 선수 조건이 아예 없는 경우

선수 조건이 전혀 없다면 확인할 조건이 없으므로 그 질문은 EnabledQuestion이어야 한다. 그렇다면 선수 조건이 없다는 사실은 어떻게 알릴까. 속성의 서로 다른 값 개수를 말하는 기수 제약을 쓴다.

```turtle
c:WhatProblem a [ a owl:Restriction ;
                  owl:onProperty q:hasPrerequisite ;
                  owl:cardinality 0 ] .
```

이렇게 선언하면 `c:WhatProblem q:hasPrerequisite ?` 꼴의 트리플은 존재하지 않는다는 것을 안다. 즉 선수 조건이 없다. 그러면 이 개체는 다음 allValuesFrom 제약도 만족한다.

```turtle
c:WhatProblem a [ a owl:Restriction ;
                  owl:onProperty q:hasPrerequisite ;
                  owl:allValuesFrom q:SelectedAnswer ] .
```

따라서 `c:WhatProblem a q:EnabledQuestion`이 추론된다.

### 값이 하나도 없는데 "모든 값이 ~"가 성립한다?

값이 없는데 모든 값이 어떤 클래스의 멤버라는 말이 이상하게 들릴 수 있다. allValuesFrom은 속성 이름과 상관없이 "충족해야 할 조건을 건다"고 생각하면 이해가 쉽다. 일상 예로, 자녀가 없는 사람은 자녀가 모두 아들이라고 할 수 있다.

```turtle
:ParentOfBoysOnly owl:equivalentClass
  [ a owl:Restriction ;
    owl:onProperty :hasChild ;
    owl:allValuesFrom :Boy ] .
```

이 클래스의 멤버 여부는 hasChild 트리플마다 조건이 걸리는 방식으로 판단한다. 트리플 `:ElizabethII :hasChild :Charles` 는 "Charles가 Boy여야 한다"는 조건을 ElizabethII에게 건다. :Charles a :Boy가 있으니 이 조건은 충족된다.

그래도 ElizabethII가 ParentOfBoysOnly라고 추론하지는 못한다. 모든 조건이 충족되어야 하는데, 열린 세계에서는 우리가 모르는 사실이 더 있을 수 있기 때문이다. 나중에 `:ElizabethII :hasChild :Anne`이 알려지면 충족되지 않는 조건이 생긴다. 모르는 조건이 늘 더 있을 수 있다는 것이 열린 세계의 의미다.

그래서 allValuesFrom으로 정의된 클래스의 멤버임을 추론하기는 일반적으로 어렵다. 한 가지 방법은 "없다"고 단언하는 것이다. 엘리자베스 1세는 자식 없이 죽은 것으로 유명하니 이렇게 쓸 수 있다.

```turtle
:ElizabethI a [ a owl:Restriction ;
                owl:onProperty :hasChild ;
                owl:cardinality 0 ] .
```

그러면 조건이 하나도 없으니 `:ElizabethI a :ParentOfBoysOnly`가 추론된다. 기수 제약으로 적어도 엘리자베스의 자녀에 관해서는 세계를 닫은 셈이다.

자식이 없는 사람의 자녀가 모두 아들이라는 결론은 직관에 어긋난다고 느끼는 사람이 많다. 하지만 allValuesFrom을 선수 조건으로 보면 이해가 쉽다. 선수 조건이 없는 것은 조건이 충족된 것이다. OWL의 의미론은 allValuesFrom을 이렇게 해석한다.

| 상황 | hasChild 값 | ParentOfBoysOnly로 추론되는가 |
|---|---|---|
| Charles 한 명만 알려짐(Boy) | Charles | 안 된다. 다른 자녀가 알려질 수 있다 |
| Anne이 추가로 알려짐 | Charles, Anne | 안 된다. Anne이 Boy라는 사실이 없어 조건이 충족되지 않는다 |
| cardinality 0 선언 | 없음 | 된다. 충족할 조건이 없다 |

읽는 법은 "열린 세계에서 모든 조건이 충족되었다고 말하려면 조건의 총수를 알아야 한다"는 것이다. 기수 0은 총수가 0임을 알려 준다.

## 3. 선수 조건의 개수를 세는 방법

"모든 조건이 충족되었다"를 알아내는 또 다른 방법은 선수 조건이 몇 개인지 세는 것이다. 제임스 딘 영화를 센 것과 같다. 선수 조건이 정확히 하나라고 해 보자.

```turtle
c:TvSymptom a [ a owl:Restriction ;
                owl:onProperty q:hasPrerequisite ;
                owl:cardinality 1 ] .
c:TvSymptom q:hasPrerequisite d:STV .
d:STV a q:SelectedAnswer .
```

선수 조건 하나가 SelectedAnswer임을 알고, 기수가 1이므로 다른 것은 없다. 그러므로 모든 선수 조건이 SelectedAnswer 멤버라는 것도 안다. 따라서 `c:TvSymptom`은 allValuesFrom q:SelectedAnswer 제약의 멤버가 된다.

개수가 더 많아도 같은 논리가 이어진다. 개체가 서로 다르다는 것을 알면 된다.

```turtle
c:TVTurnedOn a [ a owl:Restriction ;
                 owl:onProperty q:hasPrerequisite ;
                 owl:cardinality 2 ] .
c:TVTurnedOn q:hasPrerequisite c:TVSnothing .
c:TVTurnedOn q:hasPrerequisite c:STVSnosound .
c:TVSnothing owl:differentFrom c:STVSnosound .
c:TVSnothing a q:SelectedAnswer .
c:STVSnosound a q:SelectedAnswer .
```

두 선수 조건이 서로 다르고 둘 다 q:SelectedAnswer이며 기수가 2이므로, 선수 조건은 이 둘뿐이다. 그러므로 `c:TVTurnedOn`은 allValuesFrom q:SelectedAnswer 제약의 멤버로 추론된다. 원서에는 이 예의 개체 이름이 TVSnothing, STVSnosound처럼 적혀 있어서 그대로 옮겼다.

| 닫는 방법 | 필요한 정보 | 결론 |
|---|---|---|
| cardinality 0 | 값이 없다 | 어떤 allValuesFrom도 성립 |
| cardinality n + 알려진 n개 값 | 값이 정확히 n개, 모두 서로 다름(differentFrom), 각각의 타입 | allValuesFrom 성립 |

n개가 알려진 경우 differentFrom이 꼭 필요하다. 두 이름이 같은 대상이라면 개수가 달라지기 때문이다.

---

## 4. 값의 존재 보장: allValuesFrom, someValuesFrom, hasValue

선수 조건 예제는 allValuesFrom의 숨은 성질 하나를 보여 줬다. 개체 A가 속성 P에 대한 allValuesFrom 제약의 멤버라고 해서 A P ? 꼴의 트리플이 하나라도 있다는 보장은 없다. 그럼 someValuesFrom은 어떨까. 개체 A가 속성 P에 someValuesFrom C 제약의 멤버라면 다음 두 트리플이 있다고 해석한다.

```turtle
A P X .
X rdf:type C .
```

이 두 트리플이 있으면 A P ? 꼴의 트리플이 확실히 있다. 즉 allValuesFrom과 달리 someValuesFrom은 값이 존재함을 보장한다. hasValue는 더 분명하다. 값이 있음은 물론 그 값이 무엇인지까지 지정한다. A가 속성 P에 hasValue X 제약의 멤버이면 `A P X`가 추론된다.

| 제약 | 값이 존재함을 보장하는가 | 추론되는 것 |
|---|---|---|
| allValuesFrom C | 보장하지 않음 | 값이 있다면 모두 C의 멤버 |
| someValuesFrom C | 보장함 | 값 X가 있고 X는 C의 멤버 |
| hasValue X | 보장함(값까지 지정) | A P X 트리플 |

읽는 법은 "모두"는 값이 없어도 참일 수 있고, "어떤"과 "특정"은 값이 있어야 참이라는 것이다. 이 차이가 기수와 합쳐지면 앞에서 본 소거법과 개수 세기가 가능해진다.
