# Facebook Open Graph Protocol

Facebook은 처음에 자기 안에 갇힌 세계로 시작했다. 어떤 것은 Facebook 안에 있고, 아니면 없었다. 2010년에 도입한 Open Graph Protocol(OGP)은 Facebook이 다른 웹 사이트와 새로운 방식으로 이어지게 해 준 장치다. 이 문서는 OGP가 무엇을 풀려고 했는지, 모델이 얼마나 단순한지, 왜 기존 어휘를 쓰지 않고 새로 만들었는데도 시맨틱 웹 관점에서 문제가 아닌지, 웹 페이지에 어떻게 심는지를 다룬다.

OGP는 FOAF와 대조되는 사례다. FOAF가 오래 가며 서서히 자라는 어휘라면, OGP는 단순함을 최우선으로 삼아 빠르게 퍼졌다.

---

## 1. 풀려던 문제: "좋아요"의 범위

OGP의 가장 눈에 띄는 모습은 Facebook의 "like"(좋아요) 기능의 확장이다. Facebook의 모든 자원에는 "like" 버튼이 있다. 사용자가 누르면 그 페이지가 프로필에 좋아하는 것으로 올라가고, 지인이 볼 수 있으며, 그 대상의 업데이트 소식을 받아볼 수 있다. 자기 취향을 프로필에 드러내는 아주 간단한 방법이다.

문제는 Facebook 안의 페이지에만 "like"를 누를 수 있었다는 점이다. 주요 신문의 기사나 마음에 드는 공연 목록을 봐도 "like"를 누를 방법이 없었다. OGP는 Facebook의 범위를 Facebook 밖의 페이지로 넓혔다. 이를 통해 Facebook은 전 세계적 링크드 데이터 네트워크에 한 걸음 가까워졌다. 연결 자체는 대단하지 않다. 사람들이 무언가를 좋아한다고 말하는 정도다. 그래도 링크된 데이터 웹을 향한 혁신적인 걸음이다.

이를 가능하게 하려면 두 가지 장애를 넘어야 했다.

| 장애 | 필요한 것 |
|---|---|
| 웹 페이지 저자가 페이지를 Facebook에 설명할 언어 | 단순한 모델(어휘) |
| 그 설명을 웹 페이지 자체에 넣을 방법 | 페이지 안에 넣는 간단한 표기 |

참고로 Facebook은 OGP 외에도 페이지에 "like" 버튼을 다는 여러 방법을 만들었다.

## 2. OGP의 모델

OGP에는 웹 페이지 저자가 페이지가 설명하는 여러 대상을 Facebook에서 "like"할 수 있는 모양으로 설명하게 해 주는 아주 단순한 모델이 있다. 설명하고 싶은 대상으로는 스포츠, 사업체(바, 식당 등), 사람(배우, 음악가, 저자 등), 장소, 제품, 웹 사이트가 있다. RDFS로 쓴 OGP 모델의 비규범(non-normative) 버전은 이런 종류를 스물네 개 정도 나열할 뿐이다.

또 OGP는 설명에 쓸 속성도 정의한다.

| 속성 영역 | 예 |
|---|---|
| 위치 | "Palo Alto, California" 같은 지명, 위도와 경도 같은 좌표 |
| 표시용 | 대상을 나타내는 이미지 |
| 연락처 | 전화번호, 이메일, 팩스 번호 |
| 식별자 | UPC, ISBN, URL |

OGP 모델은 이 속성들을 클래스와 연결하지 않는다. 예컨대 전화번호는 사람이나 사업체가 가진다거나, ISBN은 책이 가진다는 식의 대응을 하지 않는다. 타입(클래스)과 속성을 제공할 뿐이다. 앞서 본 FOAF가 domain, range로 클래스와 속성을 잇던 것과 대비된다.

## 3. "새로 만들었다"는 비판과 시맨틱 웹의 답

OGP는 기존 표준을 쓰지 않았다는 이유로 폐쇄적이고 비협조적이라는 비판을 받았다. FOAF에는 사람에게 연락하고 식별하는 속성이 이미 있고, W3C에는 위도와 경도 속성이 든 지리 공간 표준이 있다. 기존 표준이나 신생 표준 중 OGP가 쓰는 타입과 속성에 대응하는 것이 거의 다 있는데도 OGP는 새 것을 정의했다. 웹의 혼란에 표준을 하나 더 얹는 것 아니냐는 지적이다.

원서는 이 비판이 시맨틱 웹에 대한 오해에서 나왔다고 본다. 사내에서 서로 다른 팀이 같은 개념에 다른 컬럼 이름을 쓰는 상황에 비유할 수 있다. 전사 표준 이름을 강제할 수는 없고, 각 팀에 나름의 이유가 있다. 시맨틱 웹의 비고유 이름 가정(Nonunique Naming Assumption, 같은 것에 다른 이름이 붙는 일이 있다는 전제)이 바로 이 사정을 인정한다. 분산 시스템에서는 같은 대상에 새 이름을 붙이는 일이 생길 수밖에 없고, 모두가 같은 이름을 쓰게 만들 수도 없다.

Facebook의 사용자 시험에서는 콘텐츠 관리자가 여러 출처의 이름을 기억하기 싫어했다. `foaf:mbox`, `geo:lat`, `sioc:Site`를 각각 외워야 하는 상황이다. 그들은 어휘를 하나의 네임스페이스에 두고 몇십 개 단어만 기억하면 콘텐츠를 설명할 수 있기를 원했다.

시맨틱 웹의 해법은 이 모델들이 모두 웹에 공존하게 두는 것이다. `og:`는 OGP의 네임스페이스 접두어인데, `og:email`과 `foaf:mbox`가 나란히 있고 `og:latitude`와 `geo:lat`도 함께 있다. 어느 쪽이 다른 쪽을 이겨야 한다고 요구하지 않는다. OGP는 여러 이름을 기억하고 싶지 않은 콘텐츠 관리자를 위해 단일 네임스페이스를 유지하고, FOAF나 W3C 등 다른 기관은 자기 모델을 유지한다. 모든 것이 RDF 자원이므로 이 모델들이 어떻게 이어지는지는 RDFS-Plus로 말하면 된다.

OGP의 RDFS 모델은 이 관계를 이렇게 표현한다.

```turtle
og:latitude rdfs:seeAlso geo:lat .
og:email rdfs:seeAlso foaf:mbox .
```

### 왜 equivalentProperty가 아닌가

원서는 이 모델의 구체성이 부족하다고 지적할 수도 있다고 말한다. `owl:equivalentProperty`처럼 더 표현력이 있는 것 대신 `rdfs:seeAlso`를 썼기 때문이다. `owl:equivalentProperty`를 쓰면 FOAF가 mbox라 부르는 것은 OGP가 email이라 부르는 것이고 그 반대도 성립한다는 점이 분명해진다. `rdfs:seeAlso`는 그런 약속을 하지 않는다. `og:email`을 더 알고 싶다면 FOAF의 이 자원을 보라고 가리킬 뿐이다. 그래도 OGP와 다른 온톨로지를 연결한다는 목적에는 `rdfs:seeAlso`로 충분하다.

| 연결 방식 | 의미 | 약속의 강도 |
|---|---|---|
| owl:equivalentProperty | 두 속성은 같은 뜻이다. 한쪽이 mbox라 부르는 것을 다른 쪽은 email이라 부르고, 그 반대도 성립한다 | 강하다 |
| rdfs:seeAlso | 참고할 만한 관련 자원이 이쪽이다 | 약하다 |

이 표는 연결에는 강도 선택이 있다는 점을 보여 준다. 확신이 서지 않을 때는 약한 연결로 시작할 수 있다.

## 4. OGP를 웹 페이지에 심기

저자는 단순한 OGP 모델로 페이지가 무엇에 대한 것인지 설명할 수 있지만, 그 정보를 어떻게든 공개해야 한다. 가장 쉬운 방법은 설명을 웹 페이지 안에 직접 넣는 것이다. 그러면 저자가 한 주제에 대해 페이지 한 개만 관리하고 필요한 정보를 다 그 안에 둘 수 있다.

Facebook은 RDFa(4.1절)를 단순화한 버전으로 OGP 데이터를 페이지에 심는다. 어휘와 마찬가지로 사용자 시험에서 정보 삽입은 매우 단순해야 한다는 결과가 나왔다. 특히 저자가 방법에 대해 많은 결정을 내려야 해서는 안 된다.

해법은 OGP 데이터를 모두 페이지 머리말(header)의 HTML 태그에 넣는 것이다. 이 책의 웹 페이지 workingontologist.org는 머리말에 이런 정보를 가지고 있다.

```html
<meta property="og:type" content="book"/>
<meta property="og:url" content="http://www.workingontologist.com/"/>
<meta property="og:image" content="http://covers.elsevier.com/165_FW/9780123735560.jpg"/>
<meta property="og:site_name" content="Working Ontologist"/>
```

원서의 URL 표기에 줄바꿈이 있어 위처럼 이어 붙여 옮겼으므로 원문과 글자 하나하나는 다를 수 있다. 이 태그들은 Facebook에 이 사이트가 책에 관한 것이고, 이름이 Working Ontologist이며, URL이 `http://workingontologist.org/`이고, 표지 그림 링크가 있다는 점을 알려 준다. 이 조각에서 `og:`로 시작하는 단어와 타입 "book"은 모두 OGP 모델에서 온 것이다. 이 정도면 Facebook이 페이지에 "like" 버튼을 달아 사용자가 업데이트를 따라가게 하기에 충분하다.

| meta 태그의 property | 담는 정보 |
|---|---|
| og:type | 페이지 대상의 종류(이 예에서는 book) |
| og:url | 대상의 주소 |
| og:image | 대상을 나타내는 그림(표지)의 링크 |
| og:site_name | 사이트 이름 |

meta 태그 하나를 트리플 하나로 볼 수 있다. property 값이 서술어, content가 목적어에 해당한다는 해석이며 원서가 이렇게 풀어 쓴 것은 아니다. 원서는 "like" 버튼 하나당 최소 트리플 네 개가 생긴다고 말한다.

## 5. 정리

| 항목 | 내용 |
|---|---|
| 목적 | Facebook 밖의 웹 페이지도 "like"할 수 있게 한다 |
| 모델 규모 | 단순한 타입 스물네 개 안팎과 그와 비슷한 수의 속성 |
| 다른 어휘와의 관계 | rdfs:seeAlso로 FOAF, 지리 어휘 등에 느슨하게 연결 |
| 심는 방식 | RDFa를 단순화해 페이지 머리말의 meta 태그에 넣는다 |
| 설계 원칙 | 단순함. 저자가 내릴 결정을 최소화한다 |

OGP는 새 어휘를 만들어도 기존 어휘와의 연결을 기계가 읽는 형태로 처음부터 내장해서 정보 고립(silo)이 되지 않게 한 사례다.
