# 애플리케이션 코드와 웹 포털

스토어와 쿼리 엔진이 준비되면 그 위에 실제로 일하는 애플리케이션이 올라간다. 이 문서는 RDF 애플리케이션이 일반 데이터베이스 애플리케이션과 어떻게 같고 다른지, 애플리케이션을 어떤 언어와 방식으로 짜는지, 대표적인 사용 사례, 데이터를 가져오는 시점에 대한 판단, 그리고 RDF를 뒷단에 둔 웹 포털의 구조를 정리한다.

---

## 1. 데이터베이스 애플리케이션 구조와의 비교

데이터베이스 애플리케이션은 데이터베이스와 쿼리 엔진만 있는 것이 아니다. 애플리케이션 환경 안에서 데이터를 분석하거나 보여 주는 애플리케이션 코드가 함께 있다. 애플리케이션이 데이터베이스에 접근하는 길은 쿼리 인터페이스 하나뿐이다. 원서의 그림 4.2가 이 구조를 보여 준다. 위에서 아래로 사용자 인터페이스와 분석 같은 애플리케이션이 있고, 그 밑에 쿼리 엔진, 맨 아래에 데이터베이스가 있다.

RDF 애플리케이션도 구조는 비슷하다. 다만 다음 요소가 더 들어간다. 원서의 그림 4.3이 이 모습을 보여 준다.

- RDF 파서와 시리얼라이저
- 변환기(converter)와 스크레이퍼(scraper, 웹 페이지에서 데이터를 긁어 오는 도구)
- RDF 병합 기능
- RDF 쿼리 엔진

| 구분 | 데이터베이스 애플리케이션 | RDF 애플리케이션 |
|---|---|---|
| 맨 위 | 사용자 인터페이스, 분석 등의 애플리케이션 | 같다 |
| 중간 | 쿼리 엔진 | 쿼리 엔진, 병합 기능 |
| 맨 아래 | 데이터베이스 | RDF 스토어 |
| 입력 쪽 | 없다 | 파서/시리얼라이저, 변환기와 스크레이퍼 |
| 입력 원천 | 데이터베이스 하나 | RDF 파일, 웹 페이지, 스프레드시트, 데이터베이스 등 |

이 표의 핵심은 "입력 쪽이 늘어난다"는 점이다. RDF 애플리케이션은 데이터가 여러 곳에서 오는 것을 전제로 하기 때문에 입력 쪽 부품이 추가된다.

---

## 2. 애플리케이션을 만드는 방법

애플리케이션은 몇 가지 형태를 띨 수 있다.

- 가장 흔한 것은 일반 프로그래밍 언어로 짜는 방식이다. 원서는 Java, C, Python, Perl을 인기 있는 선택지로 든다. 이때 RDF 기능은 그 언어용 API(Application Programming Interface) 바인딩으로 제공된다.
- RDF 스토어가 쿼리 시스템의 일부로 스크립트 언어를 제공하는 경우도 흔하다. 관계형 데이터베이스 애플리케이션을 위해 고급 SQL 방언이 스크립트 기능을 주는 것과 비슷하게, RDF 기능에 프로그램으로 접근하게 해 준다.

어떤 방법으로 기능이 제공되든 그것을 쓰는 책임은 애플리케이션에 있다.

---

## 3. 전형적인 RDF 애플리케이션

원서가 드는 예는 다음과 같다.

| 애플리케이션 | 하는 일 |
|---|---|
| 캘린더 통합 | 여러 사람과 팀의 약속을 하나의 캘린더 화면에 보여 준다 |
| 지도 통합 | 여러 웹 사이트, 스프레드시트, 데이터베이스에서 모은 관심 지점의 위치를 하나의 지도에 보여 준다 |
| 주석 달기(annotation) | 사용자 커뮤니티가 정보에 (URI가 붙은) 키워드를 달아 다른 사람이 참고하게 한다. 이른바 태깅이다 |
| 콘텐츠 관리 | 여러 콘텐츠 저장소에 있는 정보 자원(문서, 웹 페이지, 데이터베이스 등)의 단일 색인을 만든다 |

네 가지 예의 공통점은 "서로 다른 곳에 흩어진 데이터를 한 화면이나 한 색인으로 모은다"는 것이다. RDF의 병합 능력이 가장 잘 드러나는 용도다.

## 4. 어떤 데이터를 언제 가져오나

애플리케이션은 어떤 정보 원천을 긁어 오거나 변환할지 결정한다. 예를 들면 XML로 된 일정 기록, 웹 페이지에 있는 주소 목록, 콘텐츠 서버의 디렉터리 목록 같은 것이다.

### 변하는 속도에 따라 시점을 나눈다

데이터가 얼마나 자주 바뀌는지에 따라 이 과정의 일부는 애플리케이션 밖에서 오프라인으로 해도 된다.

| 구분 | 예 | 처리 방식 |
|---|---|---|
| 천천히 바뀌는 데이터 | 뉴욕 지하철역 위치, 시어스(Sears) 카탈로그 항목, 흔한 화학 구조의 분석 | 애플리케이션과 무관하게 미리 RDF로 가져올 수 있다 |
| 자주 바뀌는 데이터 | 팀원의 캘린더 데이터, 거래(판매) 데이터, 실험 결과 | 정기적으로 갱신해야 한다 |

### 어디에 두고 무엇을 공개하나

| 구분 | 예 |
|---|---|
| RDF 스토어 안에만 두는 데이터 | 이 팀에 대한 비공개 정보, 주문 정보, 특허 받은 화학식 |
| RDF 형태로 공개해 다른 애플리케이션이 쓰게 하는 데이터 | 기차 시간표, 카탈로그 특가, 특정 화학 물질에 대한 FDA 조사 결과 |

두 표는 "모든 데이터를 같은 방식으로 다루지 않아도 된다"는 점을 알려 준다. 변하는 속도와 공개 여부에 따라 가져오는 시점과 보관 장소를 정하면 된다.

## 5. 합친 뒤에는 평범한 DB 애플리케이션처럼

필요한 데이터 원천을 모두 변환하고, 가져오고, 파싱하고 나면 애플리케이션은 스토어의 병합 기능으로 모든 데이터가 합쳐진 하나의 연합 그래프(federated graph)를 만든다. 이후의 모든 쿼리는 이 연합 그래프를 대상으로 한다. 쿼리가 연합 전략이나 일정을 알 필요가 없다. 연합은 병합을 수행할 때 이미 끝났기 때문이다.

이 시점부터 애플리케이션은 다른 데이터베이스 애플리케이션과 거의 똑같이 움직인다. 팀원의 약속을 보여 주는 웹 페이지는 그 정보를 묻는 쿼리를 포함한다. 약속이 서로 다른 곳에서 왔고 팀 구성원 정보는 또 다른 곳에서 왔더라도, 쿼리는 연합된 정보 그래프를 대상으로 한다.

---

## 6. RDF를 뒷단에 둔 웹 포털

애플리케이션의 프런트 엔드가 웹 서버인 경우, 구조는 데이터베이스 기반 웹 포털로 이미 잘 알려져 있다(그림 4.2). 페이지는 데이터베이스 쿼리 결과로 웹 페이지를 만들 수 있게 하는 여러 기술로 생성한다. 원서가 드는 기술은 CGI, ASP, JSP, React, Angular다.

웹 초기에는 웹 페이지를 파일 시스템의 정적 파일로 두는 것이 보통이었다. 데이터베이스 기반 포털로 옮겨 간 이유는 관계형 데이터베이스에 나타나는 복잡하게 얽힌 데이터 구조를 웹 사이트가 반영하게 하려는 것이었다.

그림 4.3의 시스템 구조는 시맨틱 웹 포털을 만드는 데도 똑같이 쓸 수 있다. RDF 스토어가 데이터베이스 기반 포털에서 데이터베이스가 하는 역할을 맡는다. 중요한 점은 두 구조 모두 표현(presentation) 계층이 분리되어 있다는 것이다. 덕분에 시맨틱 웹 포털의 웹 페이지를 만드는 데도 데이터베이스 기반 포털과 똑같은 기술을 쓸 수 있다.

### 다른 점은 데이터가 여러 곳에서 온다는 것

| 구분 | 일반 데이터 기반 웹 포털 | RDF 기반 웹 포털 |
|---|---|---|
| 페이지 생성 기술 | CGI, ASP, JSP, React, Angular 등 | 같은 기술을 쓸 수 있다 |
| 뒷단 저장소 | 데이터베이스 | RDF 스토어 |
| 한 페이지의 정보 출처 | 보통 한 곳 | 분산된 RDF 스토어 덕분에 보통 여러 곳 |
| 여러 출처 합치기 | 따로 다루지 않는다 | 스토어의 병합 기능이 기반 구조의 일부로 지원한다 |

RDF가 뒷단일 때는 분산 웹 포털을 만드는 일과 모든 정보가 로컬인 포털을 만드는 일 사이에 차이가 없다. 원서의 표현을 빌리면, RDF를 쓰면 연합 포털을 만드는 것이 사일로(silo, 칸막이로 막힌) 포털을 만드는 것만큼 쉽다.
