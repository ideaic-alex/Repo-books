# RDF 스토어와 쿼리 엔진

RDF 스토어는 트리플을 저장하는 데이터베이스이고, 쿼리 엔진은 그 안에서 원하는 정보를 꺼내는 창구다. 이 문서는 스토어가 일반 데이터베이스와 어떻게 비슷하고 어디서 갈리는지, 가장 단순한 구현은 어떤 모양인지, 표준화 덕분에 무엇이 쉬워지는지, 그리고 SPARQL 쿼리가 SQL과 어떻게 다른지를 정리한다.

---

## 1. RDF 스토어란

데이터베이스는 데이터를 저장해 두었다가 나중에 쓸 수 있게 해 주는 프로그램이다. RDF 데이터 저장소도 다르지 않다. RDF 데이터를 담는 시스템을 RDF 스토어라고 부른다. 보통 스토어에는 파서와 시리얼라이저가 딸려 있다. 파서는 스토어를 채우고, 시리얼라이저는 스토어의 정보를 내보낸다. 관계형 같은 일반 저장소처럼 쿼리 엔진도 함께 들어 있을 수 있다.

일반 데이터 저장소는 보통 다음 성능 요소로 구분한다.

- 저장할 수 있는 데이터의 양
- 데이터를 읽고 갱신하는 속도
- 쿼리 엔진이 지원하는 쿼리 언어의 종류

이 기준은 RDF 스토어에도 똑같이 적용된다.

### 병합이 기본 기능이다

관계형 저장소와 다른 점은 두 데이터셋을 합치는 병합(merge)이 기본 기능이라는 것이다. RDF 데이터 모델이 유연해서 병합 연산의 정의가 분명하다.

- 각 저장소는 RDF 트리플의 집합을 나타낸다.
- 두 개 이상의 데이터셋을 병합한 결과는 원본에 있던 모든 트리플을, 그리고 그 트리플만 담은 하나의 데이터셋이다.
- 출처와 상관없이 URI가 같은 자원은 병합된 데이터셋에서 같은 것으로 취급한다.

예를 들어 한 데이터셋에 ex:Hamlet의 저자 트리플이 있고, 다른 데이터셋에 ex:Hamlet의 공연 정보 트리플이 있다면, 병합 결과에서 이 둘은 하나의 ex:Hamlet에 대한 정보가 된다. 두 곳의 URI가 같기 때문이다. 이 예는 이해를 돕기 위해 만든 것이다.

그래서 RDF 스토어는 평소 데이터 저장소를 평가하는 기준 외에 병합 과정이 얼마나 효율적인지도 평가할 수 있다.

## 2. 가장 단순한 구현은 세 칸짜리 표 하나

RDF 스토어의 구현은 직접 만든 데이터베이스부터 전문 업체의 완제품까지 다양하다. 개념상 가장 단순한 관계형 구현은 주어, 서술어, 목적어를 각각 한 열로 하는 세 열짜리 표 하나다. 원서의 표 4.1은 로스앤젤레스 지하철(Metro) 역 이름과 주소를 이렇게 정리했다.

| Subject | Predicate | Object |
|---|---|---|
| metro:item0 | rdf:type | metro:Metro |
| metro:item0 | dc:title | "Allen Station" |
| metro:item0 | simile:address | "395 N. Allen Av., Pasadena 91106" |
| metro:item1 | rdf:type | metro:Metro |
| metro:item1 | dc:title | "Chinatown Station" |
| metro:item1 | simile:address | "901 N. Spring St., Los Angeles 90012-1862" |
| metro:item2 | rdf:type | metro:Metro |
| metro:item2 | dc:title | "Del Mar Station" |
| metro:item2 | simile:address | "230 S. Raymond Av., Pasadena 91105-2014" |

이 모양은 3장에서 RDF 트리플을 처음 소개할 때 쓴 표현 그대로다. 관계형 데이터베이스 표 형태이므로 SQL 같은 일반 관계형 도구로 접근할 수 있다. 숙련된 SQL 프로그래머라면 "표에서 metro:Metro 인스턴스 전부의 dc:title을 나열하라" 같은 질문에 답하는 쿼리를 어렵지 않게 쓴다.

다만 구현 방식으로는 뚜렷한 문제가 몇 개 있다.

| 문제 | 설명 |
|---|---|
| 첫 열의 정보 중복 | 위 표에서 metro:item0이 세 줄에 되풀이된다 |
| URI 같은 문자열에 대한 인덱스 | 긴 문자열 값에 인덱스를 만들기가 어렵다 |

저자들은 최적화의 세부 내용까지 들어가지 않는다. 그것은 완제품을 내놓는 업체의 (때로는 비공개인) 해법의 영역이다. URI에 대한 인덱스 문제는 잘 알려진 여러 데이터 조직 알고리즘으로 풀 수 있다. 제대로 된 RDF 스토어 업체들은 이 인덱싱 해법의 확장성과 효율로 제품을 차별화한다.

## 3. 표준화가 가져오는 이식성

RDF 스토어는 품질을 평가하는 방식에서 관계형 저장소와 많이 닮았다. 눈에 띄는 차이는 RDF 데이터 모델과 RDF/XML 직렬화 문법이 표준화되어 있다는 데서 나온다.

| 구분 | 관계형 저장소 | RDF 스토어 |
|---|---|---|
| 시장 | 몇몇 경쟁 업체가 수십 년째 지배 | 여러 업체와 프로젝트가 경쟁 |
| 기반 | 모두 관계 대수라는 같은 기본 아이디어 | 모든 제품이 같은 RDF 데이터 모델을 공유 |
| 데이터 이동 | 전체 DB를 자동으로 가져올 표준 직렬화 언어가 없음 | 표준 형식(RDF/XML, Turtle, JSON-LD, N3 등)으로 모두 가져오고 내보낼 수 있음 |
| 이전 작업 | 가능하지만 보통 DB 프로그래머가 원본의 세부 사항을 일일이 추적해 목표 시스템에 충실히 재현해야 함 | 일상적인 작업 |

표를 읽는 핵심은 마지막 두 줄이다. 관계형 저장소 간 이전은 사람의 수고가 필요하고, RDF 스토어 간 이전은 표준 형식 덕분에 일상적이다.

이 장점은 일찍부터 공격적으로 표준화를 진행한 결과다. 처음엔 한 RDF 스토어로 시작하고, 필요해지면 다른 스토어로 옮길 수 있다고 안심해도 된다. 또 여러 RDF 스토어에 나뉘어 있고 업체도 서로 다른 데이터를 연합하는 일도 단순해진다.

## 4. RDF 쿼리 엔진

RDF 스토어는 보통 쿼리 언어로 접근한다. 이 점은 관계형 데이터베이스나 XML 저장소와 같다. RDF 초창기에는 RDF 기반 제품이나 오픈 소스 프로젝트마다 서로 다른 쿼리 언어가 있었다. W3C는 이 언어들의 공통 기능을 바탕으로 표준 RDF 쿼리 언어 SPARQL을 만들었다. SPARQL의 자세한 내용은 6장에서 다룬다.

쿼리 엔진은 스토어와 아주 밀접하다. 쿼리를 풀 때 엔진은 스토어의 인덱스와 내부 표현에 기댄다. 스토어가 쿼리 엔진에 맞게 잘 조율될수록 성능이 좋아진다.

제품 선택의 기준은 규모에 따라 달라진다.

| 규모 | 중요하게 보는 것 |
|---|---|
| 대규모 애플리케이션 | 아주 큰 데이터셋에서도 성능이 유지되는 스토어와 쿼리 엔진 |
| 소규모 애플리케이션 | 비용, 설치 용이성, 플랫폼, 오픈 소스 여부, 다른 기업 시스템과의 기본 연동 같은 다른 요소 |

### SPARQL 엔드포인트

SPARQL에는 쿼리와 결과를 주고받는 프로토콜이 포함되어 있다. 그 덕분에 쿼리 엔진이 웹 서비스로 동작할 수 있다. 이렇게 대량의 구조화된 RDF 데이터에 접근하게 해 주는 서비스를 SPARQL 엔드포인트(endpoint, 쿼리를 받는 접속 지점)라고 하며, 이것이 시맨틱 웹의 또 다른 데이터 원천이 된다.

트리플 스토어가 아닌 데이터베이스에도 SPARQL 접근을 제공할 수 있다. 이 경우 SPARQL 쿼리를 밑바탕 저장소의 쿼리 언어로 번역해 주면 된다. W3C는 최근 관계형 저장소를 위한 SPARQL에서 SQL로의 번역을 표준화하는 작업을 시작했다고 원서는 말한다. 이 서술은 책이 쓰인 시점 기준이다.

## 5. 관계형 쿼리와의 비교

RDF 쿼리 엔진은 여러 면에서 관계형 저장소의 쿼리 엔진과 비슷하다. 데이터에 대한 표준 인터페이스를 제공하고, 데이터를 바라보는 형식을 정의한다. 차이는 바탕이 되는 사고방식에 있다.

| 구분 | 관계형 쿼리 | RDF 쿼리 |
|---|---|---|
| 바탕 | 조인과 외래 키 참조로 이루어진 관계 대수 | 술어 논리(predicate calculus)의 문장에 가까움 |
| 조건을 표현하는 방법 | 표를 조인한다 | 패턴 사이의 제약을 통일 변수(unification variable)로 표현한다 |
| 쿼리가 기술하는 것 | 둘 이상의 원본 표를 합쳐 만든 새 표 | 원본 RDF 그래프의 일부를 기술하여 만든 새 그래프 |
| 서브쿼리 | 표 단위로 풀어야 해서 필요해지는 경우가 있다 | 필요성이 적어, 많은 경우 한 번의 쿼리로 같은 효과를 낸다 |
| 셀프 조인 | 특별한 경우로 존재 | SPARQL에는 이에 해당하는 개념이 없다 |

RDF 쿼리가 기술하는 원본 그래프는 다시 여러 그래프를 병합한 결과일 수 있다. 그래프가 본질적으로 재귀적인 구조라서 표 기반 쿼리에서 생기는 여러 세부 문제가 단순해진다는 것이 원서의 설명이다.

### 단일 표로 구현한 경우

RDF 스토어를 관계형 데이터베이스의 표 하나로 구현했다면, 그 안에서 그래프 패턴을 찾는 일은 모두 그 표에 대한 셀프 조인이 된다. 익숙한 SQL 환경에서 이렇게 일하는 개발자도 있다. 오라클은 다른 접근을 택해, 그래프 쿼리에 맞게 최적화한 자체 SPARQL 확장을 SQL에 넣어서 SQL 프로그래머도 RDF 쿼리에 접근하게 했다. 이 SPARQL 엔진은 SQL 스크립트 언어의 표/조인 구조와 매끄럽게 통합되어 있다.
