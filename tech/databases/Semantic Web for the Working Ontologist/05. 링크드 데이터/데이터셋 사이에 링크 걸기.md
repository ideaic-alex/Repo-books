# 데이터셋 사이에 링크 걸기

RDF 트리플은 원래 한 리소스에서 다른 리소스로 가는 링크다. 그래서 어떤 RDF 데이터셋이든 이미 링크를 담고 있다. 하지만 이것만으로는 데이터의 웹이 되지 않는다. 각 데이터 출처가 자기 도메인의 URI만 쓴다면 그 출처는 외딴섬이고, 데이터의 웹은 없다. 데이터의 웹을 엮으려면 데이터셋을 넘나드는 링크가 필요하다. 한 데이터셋 트리플의 주어나 목적어가 다른 데이터셋의 URI를 재사용해야 한다는 뜻이다.

이런 링크가 많을수록 데이터의 웹은 촘촘히 이어지고, 여러 데이터 출처를 찾고, 크롤링하고, 통합하고, 둘러보고, 모으는 일이 좋아진다. 이 문서는 외부 링크를 만드는 네 가지 방법과 스키마 링크의 가치, 어휘를 찾는 LOV, 그리고 링크드 데이터가 만들어지는 과정을 설명한 "데이터투이" 비유를 정리한다.

---

## 1. 외부 링크를 만드는 네 가지 방법

| 번호 | 방법 | 언제 | 장단점 |
|---|---|---|---|
| 1 | 새 데이터셋이 공통 대상에 자체 URI를 만들고, 나중에 같은 대상임을 연결한다 | 데이터의 웹에 들어갈 기대 없이 독립적으로 만든 데이터셋일 때 가장 흔하다 | 나중에 "이 URI가 다른 데이터셋의 그 대상과 같다"는 사실을 찾아 연결해야 한다 |
| 2 | 새 데이터셋 설계자가 기존 데이터셋이 이미 만든 URI를 재사용한다 | 설계 단계에서 노력할 수 있을 때 | 처음에 품이 더 든다. 설명하려는 것에 해당하는 URI가 무엇인지 판단해야 한다. 대신 나중에 두 대상이 같은지 확인할 필요가 없다. 설계자가 이미 분명히 했기 때문이다 |
| 3 | 표준은 있지만 링크드 데이터로는 공개되지 않은 경우, 그 표준으로 URI를 직접 만든다 | 방법 2의 변형 | 규칙만 알면 URI를 스스로 조립할 수 있다 |
| 4 | 데이터셋이 스키마로 링크한다 | 방법 2의 변형 | 클래스와 속성 이름을 재사용한다. 같은 스키마를 쓰면 데이터셋을 통합하기 쉽다 |

### 방법 3의 예: 국가 코드

ISO는 세계 각국의 짧은 코드(3자 이내)를 게시한다. OMG(Object Management Group)는 Languages, Countries, and Codes(LCC)에서 이 전략을 쓴다. 영국(Great Britain)의 ISO 코드 URI는 다음과 같다.

```
http://www.omg.org/spec/LCC/Countries/ISO3166-1-CountryCodes/GB
```

OMG에서 조회할 필요 없이 이 슬래시 URI를 직접 만들 수 있다. 영국의 ISO 두 자리 코드가 `GB`임을 알면, 아래 주소 뒤에 두 자리 국가 코드만 붙이면 된다.

```
http://www.omg.org/spec/LCC/Countries/ISO3166-1-CountryCodes/
```

### 방법 4: 스키마로 링크하기

스키마 언어는 뒤의 장에서 다룬다. RDFS(8장), RDFS-Plus(9장), SKOS(11장), OWL(12장)이다. 이런 스키마 언어는 보통 클래스와 속성 같은 메타데이터 개체를 정의하고, 그것으로 데이터를 정렬한다. 이 클래스와 속성도 HTTP URI로 식별된다.

URI 입장에서는 방법 2와 같다. 다만 URI가 클래스 이름과 속성 이름을 가리킨다는 점이 다르다. 데이터가 원래 관계형 저장소에 있었다면 테이블 이름과 필드 이름에 해당한다. 둘 이상의 데이터셋이 같은 스키마를 재사용하면 데이터셋을 연합(federate)하기가 쉬워진다.

---

## 2. 스키마 링크의 예: FIBO

금융 산업 비즈니스 온톨로지(FIBO, Financial Industry Business Ontology)는 금융 상품에 대한 스키마 정보를 제공한다. 그중 `LoanDrawdown`이라는 클래스가 있다. 금융 전문가가 아닌 사람을 위해 풀면, 자동차 대출이나 주택 담보 대출처럼 조금씩 갚아 나가는 종류의 대출이다. FIBO는 이런 대출에 차용인(borrower), 대출 기관(lender), 만기까지의 시간, 잔액 등이 있다고 명시한다.

두 데이터셋이 스키마 정보를 FIBO에 링크하기로 하면, 두 출처의 데이터를 쉽게 합칠 수 있다. 예를 들어 특정 차용인의 대출과 잔액을 모두 찾을 수 있다.

---

## 3. 어휘 찾기: LOV

FIBO는 링크드 데이터로 공개된 여러 스키마 중 하나일 뿐이다. 데이터가 다루는 분야에 따라 웹에 공개된 스키마가 문자 그대로 수백 개 있다. 웹의 다른 것들처럼 꿈에 그리던 스키마를 찾으려면 디렉터리와 검색 엔진 기능을 제공하는 웹 애플리케이션이 있다. 그중 하나가 LOV(Linked Open Vocabularies)다. 가장 잘 알려진 어휘와 그 링크를 찾을 수 있다.

| 하고 싶은 일 | 쓸 수 있는 것 |
|---|---|
| 내 분야의 기존 스키마(어휘) 찾기 | LOV 같은 어휘 디렉터리와 검색 |
| 금융 상품 스키마 | FIBO |
| 국가 코드 URI 만들기 | OMG LCC의 슬래시 URI 규칙 |

---

## 4. 데이터투이: 링크드 데이터를 요리에 빗대기

책은 링크드 데이터를 만들고 쓰는 전체 과정을 라타투이(ratatouille) 요리의 비결에 빗대어 "데이터투이(datatouille)"라고 부른다. 남프랑스식 완벽한 라타투이를 만드는 비결 중 하나는 채소를 하나씩 따로 익히는 것이다(1단계). 각각 알맞게 익으면 요리사가 섞어서 하나의 요리로 익힌다(2단계). 라타투이는 활용도가 높아서 다른 요리의 재료로도 쓴다(3단계).

| 단계 | 요리 | 링크드 데이터 |
|---|---|---|
| 1 | 채소를 따로 익힌다 | 각 데이터 출처를 소유자가 따로 다듬고 준비한다. 데이터 제공자마다 데이터 선택(민감도, 익명성 등), 데이터셋 특징(속도, 양 등), 데이터 인프라(기존 소프트웨어, 유지 비용 등)에 제약이 있어서 각자 링크드 데이터를 만든다 |
| 2 | 섞어서 하나의 요리로 익힌다 | 누구나 공개된 데이터를 쓰고 링크해서 새 데이터를 만든다. 집계 데이터, 통계, 마이닝, 추론 결과 같은 것이다 |
| 3 | 라타투이를 다른 요리의 재료로 쓴다 | 이 새 데이터가 다시 출처가 되어, 소유자가 링크드 데이터로 웹에 공개할 수 있다 |

이 표가 말하는 것은 링크드 데이터가 한 방향으로 흐르는 일회성 작업이 아니라는 점이다. 소비자가 만든 결과물이 다시 게시되어 다른 사람의 재료가 된다.
