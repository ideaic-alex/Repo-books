# 웹에 데이터를 엮는다는 것

링크드 데이터(Linked Data)는 웹이 이미 잘 쓰고 있는 구조를 그대로 빌려 와서 "데이터의 웹"을 만드는 방법이다. 하이퍼텍스트 웹이 HTML 페이지끼리 링크로 연결되어 있듯, 데이터의 웹은 데이터 조각끼리 링크로 연결된다. 이 문서는 그 바탕이 되는 생각과 팀 버너스리(Tim Berners-Lee)가 제시한 세 가지 규칙, 그리고 URI로 "세상의 모든 것"에 이름을 붙이는 방식을 정리한다.

처음 공부하는 개발자는 "RDF만 알면 되는 것 아닌가"라고 생각하기 쉽다. 하지만 RDF 트리플은 URI가 있어야 서로 이어진다. 링크드 데이터는 RDF에 "웹에서 이름을 붙이고, 찾아가고, 서로 연결하는 규칙"을 더한 것이다.

---

## 1. 웹 위의 데이터와 데이터의 웹

웹에 데이터를 올리는 일은 쉽다. 스프레드시트나 PDF 파일을 웹 페이지에 걸어 두면 된다. 하지만 이것은 "웹에 데이터가 있는 것"일 뿐이다. 데이터의 웹(Web of data)은 전 세계의 데이터가 서로 연결되어, 찾고 둘러보고 수집하고 통합할 수 있는 상태를 말한다.

| 구분 | 웹 위의 데이터 | 데이터의 웹 |
|---|---|---|
| 예 | 웹 페이지에 올려 둔 엑셀, PDF | 서로 링크로 연결된 RDF 데이터셋 |
| 연결 | 파일 단위로 떨어져 있다 | 데이터 항목끼리 링크가 있다 |
| 쓰는 형식 | 문서 형식 위주 | RDF와 그 직렬화 형식 |
| 활용 | 사람이 내려받아 직접 읽는다 | 찾기, 둘러보기, 크롤링, 통합이 가능하다 |

표에서 핵심은 "링크가 파일 사이가 아니라 데이터 항목 사이에 있다"는 점이다. 링크드 데이터는 데이터셋과 그 안의 데이터 요소가, 웹 페이지와 앵커 텍스트가 이어지는 방식으로 이어진다. HTML이 다른 페이지로 가는 링크를 적는다면, RDF는 다른 데이터 설명으로 가는 링크를 적는다.

### 웹 구조를 그대로 재사용한다

월드 와이드 웹(WWW)의 설계자들은 웹이 전 세계 규모로 커질 수 있게 몇 가지 선택을 했다. 구성 요소를 열린 표준으로 정의해서, 어떤 소프트웨어나 하드웨어에서도 돌고 특정 구현이나 분야에 묶이지 않게 한 것이다. 데이터의 웹은 이 기반을 최대한 재사용한다. 그래서 기존 웹과 호환되는 확장이 되고, 탈중앙, 확장성, 개방성 같은 성질도 그대로 이어받는다.

하이퍼텍스트 웹을 데이터의 웹으로 넓히려면 딱 두 가지를 바꾸면 된다.

| 바꾸는 것 | 이전 | 이후 |
|---|---|---|
| 주고받는 형식 | HTML과 문서 형식 | HTML에 더해 RDF와 그 직렬화 형식(Turtle, JSON-LD 등) |
| 이름 붙이는 방식 | URL(Uniform Resource Locator) | URI(Uniform Resource Identifier) 또는 IRI(Internationalized Resource Identifier) |

URL은 "웹에 있는 문서의 주소"에 가깝다. URI와 IRI로 일반화하면 웹에 없는 것, 곧 사람, 고양이, 개념까지 이름을 붙일 수 있다. IRI는 한자나 한글 같은 여러 언어의 문자를 쓸 수 있는 URI라고 보면 된다.

## 2. 링크드 데이터 세 가지 규칙

팀 버너스리는 링크드 데이터 설계 메모에서 모범 사례를 밝혔고, 이 생각은 Heath와 Bizer(2011)가 확장해 정리했다. 책은 데이터를 공개할 때 지킬 규칙을 세 가지로 요약한다.

| 규칙 | 내용 | 쉬운 풀이 |
|---|---|---|
| 1 | 모든 것에 HTTP URI로 이름을 붙인다 | 이름이면서 곧바로 찾아갈 수 있는 주소 |
| 2 | 그 URI에 접속하면 서버가 설명을 돌려준다. 웹 표준 언어(특히 RDF와 그 문법)로 준다 | 이름을 입력하면 "이게 뭔지" 알려 준다 |
| 3 | 설명 안에 다른 것들의 HTTP URI 링크를 넣는다 | 클라이언트가 링크를 따라 계속 새 데이터를 발견한다 |

규칙 1이 중요한 이유는 HTTP URI가 "이름(URI)"이면서 "조회 수단(HTTP 접근)"이기 때문이다. 이름만 있으면 그것이 무엇인지 알 방법이 없지만, HTTP URI는 접속해 보면 된다. 참고로 요즘 웹 사이트 대부분은 HTTP의 보안 버전인 HTTPS를 쓴다. 책에서 "HTTP URI"라고 하면 HTTPS 주소도 포함해서 말한다.

이 규칙은 하이퍼텍스트 웹의 작동 방식을 자연스럽게 확장한 것이다. 페이지를 올리면 HTTP URI(URL)가 생기고, 누군가 접속하면 서버가 페이지를 주고, 페이지는 다른 페이지의 URI를 링크로 건다. 데이터에도 똑같이 적용하면 다음 효과가 생긴다.

- 규칙 1 덕분에 누구나 우리 데이터 요소를 참조할 수 있다. 누가 우리 URI를 한 번이라도 쓰면, 그 사람의 데이터셋과 우리 데이터셋이 이어진다.
- 규칙 2와 3 덕분에 이어진 데이터를 발견할 수 있다. 한 데이터셋에 도착한 사람이 따로 검색하지 않고도 다른 데이터셋을 찾아낸다.

## 3. 고양이를 http://cat 이라고 부르기

하이퍼텍스트 웹에서 URL은 "웹에 있는 것"을 가리킨다(예: `http://my-site.fr`). 데이터의 웹에서는 URI로 "세상에 존재하는 것 전부"를 웹에서 가리킨다. 책의 저자 파비앙의 고양이 미치(Mytsie)는 `http://animals.org/cat#mytsie` 같은 URI로 부를 수 있다. IRI를 쓰면 한자 같은 다른 언어 문자로 된 주소도 가능하다.

이 차이는 말장난이 아니다. 웹을 "웹 안의 내용"에 대한 데이터 교환에만 쓰지 않고, 페이지, 사람, 자동차, 고양이, 아이디어, 나라, 상품, 서비스, 정책, 관계 같은 모든 것에 대한 데이터를 교환하는 데 쓸 수 있게 된다.

URL, URI, IRI의 "R"은 Resource(리소스)다. 웹 구조에서 리소스는 "식별할 수 있는 것은 무엇이든"을 뜻한다. 실제로 URI는 이미 매우 다양한 것에 이름을 붙이는 데 쓰인다.

| 대상 | 출처 | URI |
|---|---|---|
| 파리 | DBpedia | `http://dbpedia.org/resource/Paris` |
| 단백질 MUC18 | UniProt | `http://www.uniprot.org/uniprot/P43121` |
| 빅토르 위고의 이름 | 미국 의회도서관 | `http://id.loc.gov/authorities/names/n79091479` |
| 자비에 돌란 | Wikidata | `http://www.wikidata.org/entity/Q551861` |
| Inria의 파비앙 간동 | Inria | `http://ns.inria.fr/fabien.gandon#me` |
| 뉴욕의 2016년 12월 31일 23시 | timeanddate.com | 연월일시분초가 질의 문자열로 들어간 긴 주소 |

표를 보면 도시, 단백질, 저자 이름, 사람, 특정 시각까지 모두 URI 하나로 이름이 붙는다. 이 출처들은 데이터의 웹에서 핵심 역할을 하는 곳이며, 뒤의 문서에서 다시 살펴본다.

## 4. URI가 하는 일: 식별, 조회, 병합

URI에 기대는 것이 분산 데이터, 웹 기반 구조, 서로 다른 출처에서 서로 다른 방식으로 만든 데이터셋의 통합의 핵심이다. URI는 두 가지를 해 준다.

1. 전 세계에서 통하는 식별 수단이다. 어휘(vocabulary)의 용어와 설명 대상(주어)이 무엇인지 모호하지 않게 한다. 애플리케이션은 "내가 지금 맞는 데이터를 맞는 방식으로 처리하고 있다"를 이것으로 확인한다.
2. 디레퍼런싱(dereferencing) 수단이다. URI로 웹의 어떤 위치를 찾아가서 더 많은 정보를 내려받는 방법이다. 애플리케이션은 필요할 때 이것으로 데이터를 더 가져온다.

여러 RDF 그래프와 데이터셋에서 같은 URI를 재사용하면 그 URI가 접합 지점이 된다. 출처가 어디든 데이터셋을 합칠 수 있고, 잠재적으로는 거대한 전 세계 그래프가 만들어진다. RDF 그래프가 이렇게 늘어날 수 있다는 성질이 전 세계 데이터의 웹을 엮는 방법이다.

## 5. 대상, 표현, 식별자를 구분하기

웹 리소스의 URL과 현실 사물의 URI를 섞어 쓰면 혼란이 생긴다. 같은 URI를 고양이와 그 고양이에 관한 문서에 같이 쓴다고 하자. 거기에 "크기"라는 속성을 붙이는 순간, 이것이 고양이의 크기인지 문서의 크기인지 알 수 없다.

그래서 모범 사례는 다음과 같다.

- 서로 다른 리소스에는 서로 다른 URI를 쓴다.
- 고양이, 고양이에 관한 문서, 고양이 사진은 서로 다른 것임을 인정한다.
- 웹의 표준 방식으로 이 URI들의 관계를 알아낸다. 예를 들어 고양이를 가리키는 URI에서 그 고양이를 설명하는 문서의 URL을 얻는다. 방법은 [HTTP와 웹의 세 기둥](HTTP%EC%99%80%20%EC%9B%B9%EC%9D%98%20%EC%84%B8%20%EA%B8%B0%EB%91%A5.md)에서 다룬다.

| 대상 | 무엇인가 | 웹에 있는가 | 이름 붙이는 방식 |
|---|---|---|---|
| 고양이 미치 | 현실의 동물 | 없다 | 고양이용 URI |
| 미치의 사진 | 이미지 파일 | 있다 | 사진용 URL |
| 미치를 소개하는 페이지 | 문서 | 있다 | 문서용 URL |

좋은 링크드 데이터 습관은 고양이 URI로 조회하면 그 고양이를 설명하는 문서(사진을 찾을 수 있는 문서)로 안내하는 것이다.

## 6. HTTP URI와 디레퍼런싱, Follow Your Nose

HTTP URI는 "무엇이든 이름 붙일 수 있고, HTTP로 조회한다"는 약속을 가진 URI다. 사람이든 웹 크롤러 같은 소프트웨어 에이전트든 이 URI를 만나면 그 주소로 HTTP 요청을 보내 리소스에 대해 더 알아낼 수 있다. HTTP URI는 설명을 얻는 방법이 이미 있다. 그것이 HTTP 프로토콜이다. 디레퍼런싱은 하이퍼텍스트 웹의 초석이고 웹 초창기부터 잘 작동해 왔다.

URN(Uniform Resource Name)이나 DOI(Digital Object Identifier) 같은 다른 URI 방식은 디레퍼런싱을 하려면 별도의 서비스나 관행이 필요하다.

책은 이 식별자를 URL이라고 부르지 않는다. 가리키는 대상이 그 주소에 있는 것이 아닐 수도, 아예 웹에 없을 수도 있다는 점을 강조하기 위해서다. 미치는 절대 웹에 "있을" 수 없으니 URL을 줄 수는 없다. 하지만 HTTP URI로 웹에서 식별할 수는 있고, 그 주소에 가면 미치에 대한 설명(사진 한두 장도 가능)을 받는다.

이런 방식, 즉 HTTP URI를 식별자로 쓰고 HTTP 디레퍼런싱으로 더 많은 정보를 주는 방식을 웹 설계 패턴 Follow Your Nose(코를 따라가라, Dodds와 Davis 2012)라고 한다.

| 역할 | 책임 |
|---|---|
| 데이터 게시자 | HTTP URI가 실제로 적절한 정보를 주는 웹 리소스로 이어지게 만든다 |
| 데이터 소비자 | 링크를 언제 따라갈지 정한다. 성능, 신뢰, 확장성, 품질 같은 사정에 따라 다르다 |

그리스 신화의 아리아드네가 테세우스에게 미궁에서 빠져나올 실을 준 것처럼, 게시자는 소비자가 데이터 출처로 돌아와 더 알아볼 수 있는 HTTP URI를 제공한다. 링크를 따라갈지는 어디까지나 소비자 마음이다.
