# 표 데이터 자동 분류

이 문서는 도전 문제 29와 30을 다룬다. 표(테이블) 데이터를 RDF로 가져오면 모든 행이 같은 타입의 개체가 되는데, 어떤 열의 값에 따라 행마다 다른 타입을 주고 싶을 때가 많다. 코드를 짜서 해결할 수도 있지만, OWL의 hasValue 제한을 쓰면 모델만으로 해결된다. 이 방법은 데이터가 어디서 오든 값과 타입이 서로 맞게 유지해 주는 효과도 있다.

---

## 1. 문제: 표를 가져오면 모든 행이 같은 타입이 된다

3장에서 표 형태의 데이터를 RDF로 바꾸는 방법을 봤다. 행 하나를 개체 하나로, 열 이름을 속성으로, 칸의 값을 속성 값으로 만든다. 책은 그때의 예시 표(표 3.12)를 여기에 표 12.1로 다시 싣는다. 제조업체의 제품 목록이다.

| ID | 모델 번호 | 제품 라인(Product line) |
|---|---|---|
| 1 | ZX-3 | Paper machine |
| 2 | ZX-3P | Paper machine |
| 3 | ZX-3S | Paper machine |
| 4 | B-1430 | Feedback line |
| 5 | B-1430X | Feedback line |
| 6 | B-1431 | Active sensor |
| 7 | DBB-12 | Monitor |
| 8 | SP-1234 | Safety valve |
| 9 | SPX-1234 | Safety valve |

원서의 표는 이 밖에 부서(Division), 생산지(Manufacture location), SKU, 재고(Available) 열도 담고 있다. 예를 들어 1번 행의 생산지는 Sacramento, SKU는 FB3524, 재고는 23이다. 위 표에서는 이번 문제에 필요한 열만 남겼다.

이 표의 행들은 다음과 같은 트리플이 된다(표 12.2에서 제품 1의 일부).

```turtle
mfg:Product1 mfg:Product_ID 1 .
mfg:Product1 mfg:Product_ModelNo ZX-3 .
mfg:Product1 mfg:Product_Product_Line Paper machine .
```

실제 트리플의 목적어는 문자열 값이다(표에서 보인 표기는 책 그대로다). 행마다 mfg:Product라는 같은 타입이 붙는다. 표의 이름에서 온 타입이다. 제품 라인 값은 몇 가지로 정해져 있고 미리 알려져 있다. "Paper machine", "Feedback line", "Safety Valve" 등이다.

### 원하는 모습

더 정교하게 가져오려면 행마다 개체는 하나 두되, 제품 라인 열의 값에 따라 다른 타입을 붙이면 된다.

```turtle
mfg:Product1 rdf:type ns:Paper_machine .
mfg:Product4 rdf:type ns:Feedback_line .
mfg:Product7 rdf:type ns:Monitor .
mfg:Product9 rdf:type ns:SafetyValve .
```

표에서 어떤 열이 타입 정보를 담는 일은 매우 흔하다. 단순한 방식으로 가져오면 모든 행이 같은 타입이 된다.

## 2. 해결 방법 두 가지

| 방법 | 설명 | 특징 |
|---|---|---|
| 소프트웨어로 해결 | 가져오기 도구를 정교하게 만들어서 어느 열이 타입을 정하는지 사용자가 지정하게 한다 | 코드를 더 많이 짜야 한다 |
| 모델로 해결 | OWL 모델과 추론 엔진이 같은 일을 하게 한다 | 단순하게 가져온 트리플만으로 충분하다 |

이 문서의 도전 문제는 두 번째 방법을 택한다.

## 3. 도전 30: OWL로 자동 분류하기

과제는 3장에서 설명한 단순 가져오기로 만든 트리플만 가지고, 제품 라인 열의 값에 따라 각 개체의 타입 정보를 추론하는 OWL 모델을 만드는 것이다.

### 해법: hasValue 제한 + equivalentClass

행들이 속하게 될 클래스, 곧 제품 라인들은 이미 알려져 있으므로 먼저 클래스를 선언한다.

```turtle
ns:Paper_Machine rdf:type owl:Class .
ns:Feedback_Line rdf:type owl:Class .
ns:Active_Sensor rdf:type owl:Class .
ns:Monitor rdf:type owl:Class .
ns:Safety_Valve rdf:type owl:Class .
```

각 클래스에는 mfg:Product_Product_Line 속성이 해당 값인 개체만 들어가야 한다. 이를 만드는 클래스 생성 도구가 owl:hasValue 제한이다.

```turtle
ns:Paper_Machine owl:equivalentClass
  [ a owl:Restriction ;
    owl:onProperty mfg:Product_Product_Line ;
    owl:hasValue "Paper machine" ] .
ns:Feedback_Line owl:equivalentClass
  [ a owl:Restriction ;
    owl:onProperty mfg:Product_Product_Line ;
    owl:hasValue "Feedback line" ] .
```

나머지 세 클래스(Active_Sensor, Monitor, Safety_Valve)도 값만 "Active sensor", "Monitor", "Safety Valve"로 바뀌고 같은 모양이다.

### 추론 과정

mfg:Product1("ZX-3")을 보자. 표에서 가져온 다음 트리플이 있다.

```turtle
mfg:Product1 mfg:Product_Product_Line "Paper machine" .
```

이 트리플은 Paper_Machine 제한의 조건을 만족하므로 다음이 추론된다.

```turtle
mfg:Product1 rdf:type
  [ a owl:Restriction ;
    owl:onProperty mfg:Product_Product_Line ;
    owl:hasValue "Paper machine" ] .
```

이 제한은 mfg:Paper_Machine의 정의와 equivalentClass이므로 최종 결론이 나온다.

```turtle
mfg:Product1 rdf:type mfg:Paper_Machine .
```

| 단계 | 사실 | 출처 |
|---|---|---|
| 1 | mfg:Product1 mfg:Product_Product_Line "Paper machine" | 표에서 가져온 트리플 |
| 2 | mfg:Product1이 hasValue 제한의 구성원 | 제한의 조건 충족 |
| 3 | mfg:Product1 rdf:type mfg:Paper_Machine | equivalentClass 의미 |

### 반대 방향도 일관된다

이 정의는 표가 아닌 다른 출처의 데이터가 들어와도 일관성을 유지해 준다. 다른 곳에서 새 제품이 다음처럼 정의되었다고 하자.

```turtle
os:ProductA rdf:type mfg:Paper_Machine .
```

equivalentClass의 의미에 따라 Paper_Machine 구성원은 모두 제한의 구성원이기도 하다.

```turtle
os:ProductA rdf:type
  [ a owl:Restriction ;
    owl:onProperty mfg:Product_Product_Line ;
    owl:hasValue "Paper Machine" ] .
```

제한의 의미에 따라 다음 결론이 따라 나온다.

```turtle
os:ProductA mfg:Product_Product_Line "Paper Machine" .
```

결과적으로 제품 정보가 어떤 경로로 시스템에 들어오든 rdf:type과 mfg:Product_Product_Line 양쪽으로 일관되게 표현된다. 표에서 오면 값에서 타입이, 타입으로만 선언된 데이터는 타입에서 값이 채워진다.

| 들어온 데이터 | 모델이 채워 주는 것 |
|---|---|
| 제품 라인 값만 있음(표에서 가져옴) | 해당 클래스의 rdf:type |
| rdf:type만 있음(다른 출처) | 제품 라인 값 |

원문에는 값 철자가 "Paper machine"과 "Paper Machine"으로 섞여 있다(대소문자). 책의 코드를 그대로 따랐지만, 실제로 쓸 때는 문자열 값이 정확히 일치해야 같은 값으로 취급되므로 철자를 통일해야 한다.

## 4. 정리

- 표를 단순하게 가져오면 모든 행이 같은 타입이 되지만, hasValue 제한과 equivalentClass를 쓰면 열 값에 따라 타입을 자동으로 붙일 수 있다.
- 값에서 타입으로, 타입에서 값으로 양방향 추론이 된다.
- 해결의 열쇠는 "제품 라인 값이 미리 알려져 있다"는 점이다. 클래스 하나당 제한 하나를 써야 한다.
- 가져오기 코드를 고치지 않고 모델만 추가해서 분류를 얻는다는 점이 이 방식의 장점이다.
