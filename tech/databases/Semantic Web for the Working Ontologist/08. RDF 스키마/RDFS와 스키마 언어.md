# RDFS와 스키마 언어

RDF는 데이터를 트리플이 모인 그래프로 표현하는 방법일 뿐, 그 그래프를 어떤 규칙으로 써야 하는지는 알려 주지 않는다. RDFS(RDF Schema, RDF 스키마 언어)는 바로 그 규칙, 곧 "이 그래프에서 쓰는 어휘가 무슨 뜻인가"를 말하는 도구다. 이 문서에서는 스키마 언어가 원래 어떤 일을 하는지 다른 기술과 견주어 보고, RDFS가 그것들과 어떻게 다른지 살펴본다.

RDF 모델링이 그래프를 다루는 일이라면 RDFS 모델링은 집합을 다루는 일이다. 개체들이 어떤 집합에 속하는지, 속성들이 서로 어떤 관계인지를 RDFS로 적는다. 그리고 그 의미는 "이런 트리플이 있으면 저런 트리플을 새로 만들어 낼 수 있다"라는 추론 규칙으로 정해진다.

---

## 1. RDFS가 답하려는 질문

RDF 그래프에는 개체(인스턴스)와 속성이 가득하다. 그런데 다음 같은 질문은 RDF만으로는 답하기 어렵다.

- 어떤 개체 집합이 다른 개체 집합과 어떤 관계인가.
- 개체를 설명하는 데 쓰는 속성들은 다른 개체 집합과, 그리고 속성끼리는 어떤 관계인가.

RDFS는 데이터를 통합하고 모델링할 때 필요한 이런 질문에 답을 적는 방법을 제공한다. 이미 배운 rdf:type이 "이 개체는 저 집합의 구성원이다"를 말해 주긴 했지만, RDF 자체는 단순히 그래프 구조를 만들 뿐이다. RDFS는 이 그래프 구조를 질서 있고 표준적인 방식으로 쓰도록 가이드를 준다. 그래프에서 쓸 어휘(vocabulary)에 대해 이야기할 수 있게 해 주는 셈이다.

## 2. 스키마 언어는 기술마다 하는 일이 다르다

스키마 언어라는 말은 익숙하지만 기술마다 맡은 역할이 꽤 다르다. 원서는 세 가지 예를 든다.

| 기술 | 스키마가 하는 일 | 예 |
|---|---|---|
| 문서 모델링(XML) | 문서가 허용된 형식을 따르는지 확인한다. 파서가 자동으로 검사할 수 있다 | XML Schema 정의 |
| 관계형 데이터베이스 | 표의 열 머리글과 키 정보를 준다. 열의 의미나 어떤 열이 색인인지는 표 안에 없기 때문에 스키마에 둔다 | 테이블 스키마 |
| 객체지향 프로그래밍(OOP) | 클래스 구조가 정보를 정리하고, 상속 정책에 따라 인스턴스가 쓸 수 있는 메서드와 그 구현을 정한다 | 클래스 다이어그램 |

이 표에서 XML과 관계형 DB의 스키마는 정보를 해석하거나 검사하는 쪽에 가깝다. OOP의 클래스 구조는 정보를 해석하기보다, 정보를 기술하고 거기에 적용할 변환(메서드)을 체계적으로 정해 준다는 점에서 성격이 다르다.

이렇게 쓰임새가 제각각이니 "스키마 언어"라는 이름이 아무 의미도 없는 것 아니냐는 생각이 들 수 있다. 그래도 공통점은 있다. 어느 경우든 스키마는 시스템에 담긴 정보에 대해 무언가를 말해 준다. 한마디로 스키마는 데이터에 대한 정보다.

그렇다면 RDF에서 스키마는 무엇일까. 핵심은 데이터에 의미를 부여하는 것이고, RDFS는 이를 추론 패턴으로 의미를 지정하는 방식으로 해낸다.

## 3. 스키마와 데이터를 한 몸으로 두는 RDFS

대부분의 모델링 시스템은 데이터와 스키마를 뚜렷이 나눈다. 관계형 DB의 스키마는 보통 DB 안의 테이블로 표현되지 않고, 객체지향의 객체 모델은 객체로 표현되지 않으며, XML의 DTD는 올바른 XML 문서가 아니다. 물론 요즘 시스템은 스키마를 데이터와 같은 형태로 다루기도 한다. Common Lisp의 메타 객체 프로토콜이나 Java의 리플렉션 API는 객체 모델을 객체로 보여 주고, XSD는 XML 스타일 정의를 XML 언어로 적는다.

RDFS는 처음부터 RDF로 정의되었다. 스키마 정보가 전부 RDF 트리플이다. 일반 리소스와 스키마 리소스의 관계도 다른 어떤 리소스 사이의 관계와 똑같이 트리플로 맺는다. 원서는 이를 DTD 때 XML 표준이 겪은 문제에서 배운 교훈이라고 설명한다.

이 설계가 주는 이점은 설계가 깔끔하다는 것에 그치지 않는다.

| 이점 | 설명 |
|---|---|
| 의미를 간단히 정의 | 트리플 패턴 위에서 동작하는 추론 규칙만으로 RDFS의 의미를 형식적으로 기술할 수 있다 |
| 끝까지 같은 방식 | 데이터도, 의미를 담은 스키마도, 추론 결과도 모두 트리플이라 이 과정이 필요한 만큼 계속 이어질 수 있다 |
| 분산 가능 | 시맨틱 웹의 정보에 맥락을 주는 스키마 정보도 시맨틱 웹 위에 흩어져 있을 수 있다 |
| 도구 재사용 | RDF 데이터에 쓰는 도구를 스키마에도 그대로 쓴다 |

도구 재사용을 구체적으로 보면, 스키마를 SPARQL로 질의하고, SHACL(Shapes Constraint Language, 데이터 모양 검증 언어)로 검증하고, RDF 편집기로 고치고, 링크드 데이터 방식으로 공개하고, RDF 시각화 도구로 그려 볼 수 있다는 뜻이다. 스키마용 도구를 따로 배울 필요가 없다.

## 4. rdfs:Class로 집합을 선언한다

RDFS에서 집합을 지정하는 기본 구성 요소는 rdfs:Class다. RDFS도 RDF이므로 "이것은 클래스다"라는 말 역시 트리플로 한다. 서술어가 rdf:type이고 목적어가 rdfs:Class인 트리플이다. 원서가 이후 논의에 쓰는 예는 다음과 같다.

```turtle
:AllStarPlayer rdf:type rdfs:Class .
:MajorLeaguePlayer rdf:type rdfs:Class .
:Surgeon rdf:type rdfs:Class .
:Staff rdf:type rdfs:Class .
:Physician rdf:type rdfs:Class .
```

이것들은 다른 트리플과 똑같은 트리플이다. 이 트리플이 데이터가 아니라 스키마를 가리킨다는 것을 아는 방법은 rdfs: 네임스페이스에 있는 rdfs:Class라는 용어를 썼다는 사실 하나뿐이다.

그렇다면 새로 얻는 것은 무엇일까. 3장에서 이미 rdf:type으로 어떤 것이 집합의 구성원이라고 말해 봤다. 집합임을 굳이 명시해서 얻는 이득은 집합 구성원이 된다는 것이 무슨 뜻인지를 설명할 수 있게 된다는 점이다. 순수 RDF에서 집합 소속의 "의미"는 질의를 돌려서 나온 결과가 전부였다. rdf:type도 사용자가 정의한 다른 속성과 다르게 동작하지 않았다. RDFS는 그 의미를 추론 방식으로 정한다.

## 5. "새 키워드"가 아니라 "특별한 의미를 가진 리소스"

RDFS는 특별한 리소스들을 도입해 RDF를 "확장"한다. 프로그래밍 언어에 예약어를 추가하는 것과 비슷해 보이지만 중요한 차이가 있다. RDF에서는 어떤 리소스든 어떤 트리플에서나 쓸 수 있다(누구나 어떤 주제에 대해서든 무엇이든 말할 수 있다. 이 원칙을 AAA 슬로건이라 부른다). 그래서 특정 리소스를 "새 키워드"로 지정해도 언어를 실제로 늘린 것은 아니다. 표준이 특정 트리플에 특별한 의미를 정해 놓았을 뿐이다.

특별한 리소스의 의미는 이렇게 정의한다. "이런 상황(트리플 패턴)이면 이런 새 트리플을 추가(추론)할 수 있다." 7장에서 본 rdfs:subClassOf의 타입 전파 규칙이 그 예이고, 다음 문서에서 rdfs:subPropertyOf로 같은 방식을 살펴본다.

| RDFS 이해의 포인트 | 한 줄 정리 |
|---|---|
| 스키마도 트리플 | 클래스, 하위 클래스, 속성, domain, range가 모두 RDF 트리플이다 |
| 키워드가 아니라 표준 의미 | rdfs: 이름을 쓴 트리플에 표준이 정한 추론 의미가 붙는다 |
| 의미 = 추론 | 어떤 패턴에서 어떤 트리플이 새로 생기는지가 곧 그 구성 요소의 의미다 |
| 검사가 아니라 추론 | 스키마를 어긴 데이터를 거르지 않고 새 정보를 만들어 낸다 |

정리하면 RDFS는 데이터를 검사하는 울타리가 아니라, 데이터에서 새 사실을 끌어내는 규칙 모음이다. 이 관점이 뒤의 domain과 range를 이해하는 열쇠가 된다.
